    9. 架构方案设计（秒杀、下单、支付、幂等、双写一致性）

    📅 2019-09-22

    第 1 题　接口幂等性，支付场景防止重复扣款、重复下单

    问题

    接口如何保证幂等性？支付场景，用户网络卡顿前端重复提交，后端多次收到同一笔支付请求，
    订单状态已经支付成功，却生成多条交易流水，造成重复扣款，问题出在哪？如何彻底杜绝？

    候选人回答：

    加唯一索引、用 token 过滤重复请求就够了。

    连环追问

    1. 前置防重 Token 方案，在分布式集群场景下有什么缺陷？如果 Token 校验成功后，业务执行中途服务宕机，前端重试会发生什么？
    2. 数据库唯一索引做幂等，适合什么场景？有什么短板？
    3. 基于状态机的幂等怎么落地，支付订单状态流转有哪些状态，如何防止状态被重复变更？
    4. Redis 分布式锁做幂等，有什么坑？如何避免锁失效带来的重复执行？
    5. MQ 消费重复消息（生产者重试、broker 重发），幂等该如何处理？
    6. 支付这种资金场景，幂等需要哪些兜底校验和对账机制？

    参考答案

    事故根源

    简单的前置 token / 内存判断，只能拦截未进入业务的重复请求，无法保证「校验通过后，业务执行过程中断」的场景。

    时序举例：
    ①第一次请求：校验 token 通过 → 开始执行扣款、生成流水；业务执行一半，服务宕机 / 网络返回超时；数据库订单状态更新成功，但响应没返回给前端。

    ②前端看不到成功结果，重复提交相同请求。此时简单 token 可能已经失效，或者只做一次前置拦截，无法识别这笔已经执行成功的业务，再次执行扣款，产生多条流水，重复扣款。 本质：只做请求入口拦截，没有在业务写库这一层做幂等防护，无法覆盖执行中途异常重试场景。幂等的核心：同一个业务请求，无论调用多少次，业务结果只生效一次，不会产生多次数据变更。

    三层幂等防御体系（支付 / 订单核心接口）

    第一层：前端 / 网关层，前置拦截（第一道防线，减轻后端压力，不能单独作为保障）

    1. 防重 Token 方案 下单前后端生成全局唯一 Token 返回前端；提交支付请求携带该 Token。后端收到请求，先删除 Redis 内这个 Token；删除成功才允许进入业务。

    2. 优点：在网关层拦截大部分重复点击，减少打到数据库的流量。

    3. 缺陷：Token 一旦删除，业务执行中途宕机，前端重试拿不到旧 Token，需要重新获取新 Token，会绕过拦截。所以 Token 只是前置防护，不能单独用来保障资金幂等。

    4. 前端按钮置灰，禁止重复点击；网关层基于请求指纹限流。

    第二层：业务数据库层（核心防线，资金场景必须有）方案 A：业务流水号唯一索引（推荐支付场景）给业务唯一流水号（out_trade_no，我方生成的订单交易号）建立唯一索引。

    • 每次支付请求，携带固定业务流水号；
    • 插入交易流水表时，唯一索引冲突直接报错，不会新增多条流水；优势：数据库层面强约束，原子性，崩溃安全。 局限：只针对插入类幂等；更新场景不适用。

    方案 B：订单状态机 + 乐观锁（订单状态流转首选）订单状态：待支付 → 支付中 → 已支付 → 已退款。 更新 SQL：

    update order set status = 'PAID', version=version+1 where
order_no = #{orderNo} and status='WAIT_PAY' and version =
#{oldVersion};
    • 只有状态为待支付的订单，才允许变更为已支付；
    • 已经支付成功的订单，where 条件不命中，update 返回影响行数 0，不执行任何业务变更；
    • version 版本号做乐观锁，防止并发同时更新。

    重点：基于状态机的条件更新，是订单状态防重复变更最可靠手段，已经支付的订单，任何重复请求都不会再次执行扣款逻辑。

    方案 C：分布式幂等表单独一张幂等记录表，主键是业务唯一流水号。 执行业务前，先尝试插入幂等记录；插入成功才执行业务；插入失败说明已处理，直接返回上次成功结果。

    业务和幂等记录放在同一个数据库事务内，保证原子。

    分布式锁（Redis）：可以用来做并发控制，但不能单独作为幂等最终保障。Redis 锁存在超时、主从切换丢锁风险，锁失效就会出现重复执行；锁只能控制并发，兜底必须依靠数据库约束。

    第三层：异步、消息场景兜底 + 事后对账MQ 消费场景（生产者重试、Broker 自动重发会产生重复消息）：

    • MQ 消息携带业务唯一流水号，消费前查幂等表，已处理直接跳过；
    • 消费业务和幂等记录落库放在同一事务，保证 “业务执行 + 标记已处理” 原子。

    资金场景兜底

    1. 全链路日志：记录流水号、请求参数、时间、结果，方便排查；
    2. 定时对账任务：我方交易流水和第三方支付平台流水定时对账，发现不一致自动告警，人工处理资损；
    3. 补偿机制：出现异常状态，状态机驱动补偿 / 回滚，不依赖人工记忆。

    不同方案选型

    1. 新增流水类（支付交易记录）：唯一索引；
    2. 订单状态变更：状态机 + 乐观锁条件更新；
    3. MQ 消费、跨服务调用：幂等记录表 + 唯一业务号；
    4. 前端防重复提交：Token（仅前置，不可单独兜底）。

    面试高分话术

    这个重复扣款事故根源是只做了入口层的前置防重拦截，没有在业务落库层建立幂等约束。当前一次支付请求业务执行成功、但是响应返回前端前服务宕机，前端重试提交，前置 Token 拦截失效，再次执行扣款，生成多条流水。前置 Token 只能减轻压力，不能单独保障资金类接口幂等。

    核心接口幂等需要三层防御。

    第一层是网关和前端的前置防护，使用一次性 Token 拦截重复点击，减少无效请求打到业务层，但不能作为最终保障。

    第二层是数据库层面的核心防护，也是资金场景必须落地的。支付流水使用业务交易号建立唯一索引，防止重复插入流水；订单状态流转使用状态机 + 乐观锁条件更新，只有待支付状态的订单才能变更为已支付，已经支付成功的订单，update 不会命中，不会重复执行扣款。也可以使用独立幂等表，业务执行和幂等标记放在同一个数据库事务内，保证原子性。

    Redis 分布式锁可以做并发控制，但存在锁超时、主从切换丢锁风险，不能单独作为幂等兜底。

    第三层是异步场景和事后兜底。MQ 消费重复消息，依靠业务唯一流水号 + 幂等表处理；支付场景还要定时和支付渠道对账，发现流水不一致及时告警，防止资损。

    核心原则：幂等的最终保障必须落在数据库的原子约束上，任何内存、Redis 层面的方案，都只是辅助。

    考察核心

    初级工程师只知道 token、唯一索引名词，分不清前置拦截和底层数据库约束的差异，不知道业务执行中途宕机这个致命场景；不清楚状态机在订单幂等的价值，也没有对账兜底思维。

    高级工程师重点体现：

    1. 能复现 “业务执行成功、响应丢失，前端重试导致资损” 这个时序；
    2. 区分 Token 只是前置防护，数据库才是幂等最终保障；
    3. 区分唯一索引、状态机乐观锁、幂等表各自适用场景；
    4. 知道 Redis 锁的缺陷，不能单独做幂等；
    5. 资金场景要有对账兜底的工程意识。

    核心思想：
    幂等不是一次请求拦截，而是保证同一个业务标识，多次调用只会产生一次数据变更，并且要能扛住服务宕机、
    网络超时重试这类异常时序。

    第 2 题　接口幂等：前端置灰、唯一主键为什么挡不住 MQ 重复投递与回调重试？

    举例说明：用户点击支付，前端置灰只挡住了重复点击；但支付渠道因为回调超时重试了三次，每次都新建一条交易流水，最终出现重复扣款。只有服务端用支付单号做唯一索引并配合状态机，才能真正拦住。

    问题根源

    前端置灰、数据库唯一主键只能解决前端重复提交，解决不了异步 MQ 重复投递、回调重试、网络超时重试这类分布式场景的重复请求。 例子里支付回调消息重复来，代码没有状态判断，直接执行更新，就把已经支付成功的订单又改回待支付；消息丢失又会出现钱扣了订单状态不变。

    核心：

    幂等的目标，同一个业务请求多次到达，业务效果只生效一次，结果不变，不能只靠单一手段。

    三层防御

    第一层：请求入口拦截（前置拦截，挡掉大部分重复）

    1. 前端：按钮置灰、防重复点击，仅用于用户手动提交场景；不能作为唯一方案，绕过后端直接调用接口就失效。

    2. 网关层：传递全局唯一请求号 requestId，Redis 缓存这个请求标识，短时间内相同标识直接拦截返回上次结果；适合同步接口。 作用：低成本拦截，减少打到业务服务的重复流量，但是解决不了跨服务 MQ 重复消息。

    第二层：业务层幂等校验（业务核心层，最常用）基于业务唯一单据号（支付流水号、订单号、消息 msgId）做校验，

    主流 3 种实现：

    1. 状态机（优先推荐，订单 / 支付场景首选）
      订单有固定流转状态：待支付 → 已支付。 更新前判断当前状态，只有当前状态 = 待支付，才允许改成已支付；如果已经是已支付，直接返回成功，不执行业务逻辑。❌拒绝缺少状态判断，不管现在是什么状态，收到支付通知就无脑更新。

    2. 防重表（幂等表）
      单独一张幂等记录表，主键是业务唯一 ID；执行业务前先查这条记录，不存在才执行业务 + 插入幂等记录；
      用数据库唯一索引保证原子。适合资金、核心账务。

    3. Redis 判重
      收到消息先查 Redis 有没有该业务 ID；没有才执行业务，执行成功写入 Redis 标记；适合高性能场景；
      要注意 Redis 宕机、数据丢失风险，不能单独做最终保障。

    第三层：数据库兜底（最终防线，保证数据不会错乱）

    1. 唯一索引：防止重复插入相同业务单据；

    2. 乐观锁 / 状态条件更新：update 的时候带上状态条件，update order setstatus=paid where order_no=xxx and status=unpaid； 这条 SQL 天然原子，就算前面两层失效，数据库层面也不会多次变更。

    • ❌ 不推荐全链路都上分布式锁：锁会串行、降低吞吐，成本高，没必要。幂等优先靠状态 + 唯一标识而不是锁。

    配套补充:

    1. MQ 场景：消息的 msgId 作为幂等 key；消费成功再 ack，失败进入死信，人工补偿；

    2. 数据不一致兜底：定时对账任务，核对支付流水和订单状态，发现差异自动修复或者告警；

    3. 超时场景：区分「请求重复」和「消息丢失」，幂等只解决重复；消息丢失要靠消息确认、回查机制；

    4. 过期清理：Redis 幂等标记、幂等表旧数据定期清理，避免无限膨胀。

    30 秒面试口述标准答案（直接背）

    重复执行问题，只靠前端置灰和唯一索引不够，处理不了 MQ 重复投递、回调重试这类分布式场景。
    做三层幂等防御：
    第一层:网关基于全局请求号拦截重复请求；
    第二层:业务层用状态机，以业务单据 ID 作为幂等标识，只有满足前置状态才执行更新，已经处理过直接返回成功；
    第三层:数据库用带状态条件的 update 做兜底，保证数据不会被重复变更。同时搭配定时对账，处理消息丢失、中间件异常带来的数据不一致，不用全链路加分布式锁，避免性能下降。

    延伸追问

    问：状态机和幂等表怎么选？

    答：订单这类有明确流转阶段的，优先状态机；没有状态、只是单纯不能重复新增记录的场景，用独立幂等表。

    问：Redis 做幂等有什么坑？

    答：Redis 数据丢失、过期、主从切换丢标记，所以 Redis 只能做前置拦截，不能单独作为唯一幂等保障，数据库必须兜底。

    第 3 题　支付订单幂等性架构设计

    场景复盘

    重复来源：前端重复提交、接口超时重试、MQ 重复消费；

    候选人

    只知道单独建一张去重表 + 唯一索引，但是回答不了一系列 硬核问题：
    高并发锁竞争、去重表数据膨胀清理、MQ 消费查库性能差、订单状态流转幂等、多方案取舍、故障兜底、网关层拦截。

    核心认知：

    幂等不是只有「去重表唯一索引」一种；要分层、多方案组合，区分场景，同时做全链路防护，
    并且要有兜底补偿，不能单靠一张去重表扛所有流量。

    三层高分逻辑

    第一层：多种幂等方案选型，清楚各自适用场景与缺陷

    1. 唯一请求号 + 去重表（分布式 ID/requestNo） 适合大部分写接口。请求携带全局唯一请求号，先插入幂等记录；唯一索引保证只有一条成功。

      缺点：高并发插入存在锁竞争；表会持续膨胀，需要按 TTL 定时归档清理历史数据；每次都要写库，MQ 大批量消费场景下性能压力大。

      优化：前置 Redis（分布式锁 + 幂等标记）做热拦截，Redis 命中直接返回，减少 DB 访问；Redis 只存短期记录，过期自动淘汰。

    2. 状态机幂等（订单状态流转）【支付订单首选】 订单本身有状态：待支付→已支付→已发货。
      更新时带上状态条件：update order set status=已支付 where id=xxx and status=待支付。 天然幂等，不需要额外去重表；重复支付请求过来，订单已经不是待支付，更新行数为 0，直接返回成功。

      局限：只适合有明确状态流转的业务，单纯无状态写操作不适用。

    3. 乐观锁（version 版本号） 更新携带版本号，版本不匹配更新失败；适合并发更新资源，防止覆盖，不是通用防重复。

    4. 前端防重 Token + 网关层拦截 前端提交前拿一次性 Token，网关校验 Token，消费后失效；只能挡用户手动重复点击，挡不住网络重传、下游重试、MQ 重复消息，只能作为前置辅助手段，不能当作唯一幂等方案。

    第二层：分流量场景优化，解决性能痛点

    1. MQ 消费场景：优先 Redis 做幂等标记（requestId 作为 key，设置过期时间），先查 Redis，命中直接跳过消费；Redis 兜底失败再落库去重表，大幅降低 DB 压力；

    2. 高并发写：Redis 预拦截，减少 DB 唯一索引冲突报错；避免大量并发插入同一去重区间带来的行锁竞争；

    3. 去重表治理：设置 TTL，定时归档、清理数月前的历史幂等记录，防止表越来越大，索引性能衰减；

    4. 区分读 / 写接口：读接口天然幂等，不需要额外处理；有资金变更、下单这类副作用写接口强制幂等。

    第三层：兜底与故障防护（幂等机制失效时的最后防线）

    1. 对账补偿：定时对账任务，比对订单、支付流水，发现重复扣款、重复下单的数据，自动冲正或者人工告警；这是支付系统的底线；

    2. 降级预案：如果 Redis、幂等去重表不可用，核心链路可以切换为状态机条件更新兜底（依托业务主表本身，不依赖独立去重表）；

    3. 监控：监控唯一索引冲突数、重复请求量、MQ 重复消费告警，提前发现异常流量。

    30秒口述标准答案:

    幂等不能只依赖去重表唯一索引，要多方案搭配。
    第一层根据业务选型：
    有状态流转的订单支付优先使用状态机条件更新，自带幂等；通用接口使用唯一请求号，搭配 Redis 前置拦截减轻数据库压力；乐观锁适合防并发覆盖，前端 Token 和网关拦截只能辅助挡住用户重复点击，挡不住网络重传和 MQ 重复。

    第二层做性能优化:
    MQ消费优先走 Redis 短周期标记，去重表按 TTL 归档清理，控制锁竞争和数据膨胀。

    第三层兜底:
    依赖定时对账流水核对，就算幂等组件故障，也能及时发现脏数据、做资金冲正，保证支付订单不会重复扣钱。

    高频延伸追问

    Q：Redis 宕机，Redis 幂等标记丢了怎么办？

    A：Redis 只是热拦截，最终的判定还是 DB 去重表或者订单状态；Redis 丢失会降级到查库，性能下降，但不会破坏正确性。

    Q：状态机幂等和去重表幂等怎么选？

    A：订单、支付这种自带状态流转的优先状态机，少一张表，性能更好；无状态、一次性的业务操作用 requestNo + 去重表。

    Q：唯一索引冲突报错，直接抛异常给前端体验很差怎么处理？

    A：捕获唯一索引异常，先查询这条 requestNo 对应的业务结果，查到已成功，直接返回上次成功结果，对外屏蔽报错。

    第 4 题　Redis 查-执-写幂等击穿（并发重复支付事故）

    场景复盘 实现方案：

    同一个支付流水号，先查 Redis，无标记则执行业务，执行完成再写入 Redis 过期标记。
    现象：两条请求几乎同时到达（间隔 < 10ms），Redis 集群正常，事后单独重试又可以正常拦截，但并发下两次支付逻辑全部执行成功，出现重复扣款。

    根因本质：

    查 Redis、执行业务、写 Redis 是三段独立操作，没有原子性，存在竞态窗口（TOCTOU 问题：Check Then Operate）。两个并发线程几乎同时查询 Redis，都查到标记不存在，双双进入支付业务逻辑，之后各自写入 Redis 标记。标记最后确实存在，但业务逻辑已经跑了两遍。这就是最经典的幂等击穿。

    三层高分防御体系

    第一层：把 Redis 的操作改成原子抢占，消灭竞态窗口不能分开 GET -> 执行业务 -> SET；要用 Redis 原子命令抢占锁 / 抢占标记：

    • 推荐 SETNX（set if not exist） 或者 SET key value NX EXexpireTime。

    • 逻辑：请求进来，一步原子抢占标记；抢占成功，才允许往下走支付逻辑；抢占失败直接返回已处理。

    • 重点：先抢占成功，再执行业务；而不是先查再执后写，消除中间的时间间隙。

    • 注意区分：这个 NX 只是前置拦截，Redis 依然不能作为唯一可信数据源，Redis 宕机、主从切换丢数据都会失效。

    • ❌错误时序：GET → 判断不存在 → 执行业务 → SET 正确时序：SET NX，成功才执行业务

    第二层：业务层的数据库刚性兜底（资金链路不可省略）Redis 只是高速前置拦截，绝对不能替代数据库的最终约束，两层防护：

    1. 支付流水表，给支付流水号建立唯一索引；数据库是最终可信源。就算 Redis击穿、Redis 丢标记，数据库唯一索引会拦截第二条写入，抛出唯一冲突，阻止生成第二条支付流水，守住资损底线。

    2. 更进一步，订单状态机约束：update order set status=已支付 whereorder_id=xx and status=待支付；利用状态条件做乐观约束，就算流水号被绕过，也不允许订单重复流转到已支付。

    第三层：故障兜底、监控和补偿，应对 Redis 本身的风险

    1. Redis 风险：主从异步复制、主从切换、网络分区、过期淘汰，都可能导致标记丢失。Redis 只做高性能前置拦截，降级后落到数据库校验；

    2. 监控：监控 Redis NX 抢占失败量、数据库唯一索引冲突异常，并发击穿的时候会有尖峰，提前告警；

    3. 定时对账补偿：支付、订单、账户流水定时对账，是资金系统最后一道防线；就算前面两层全部失效，对账也能发现重复扣款，执行退款冲正。

    30秒口述标准答案:

    这个事故是典型的 TOCTOU 检查后执行竞态问题：分开的查 Redis、执行业务、写 Redis 不是原子操作，两个并发请求同时查到无标记，双双执行业务，造成幂等击穿。
    修复分三层：
    第一层把 Redis 改成 SET NX 原子抢占，抢占成功才执行业务，消除并发窗口；
    第二层数据库支付流水号加唯一索引，搭配订单状态机条件更新，作为刚性兜底；
    第三层 Redis 只做前置高性能拦截，不能作为唯一数据源，配合冲突监控和定时对账，防止 Redis 主从切换、标记丢失带来资损。

    高频延伸追问

    Q：SET NX 成功之后，如果支付逻辑执行到一半服务宕机，Redis 标记已经打上，业务没成功，会不会导致这笔支付永远无法重试？

    A：这是另外一个经典坑。两种方案：
    方案 1：用分布式锁 + 看门狗续期，业务完成后主动删除 key；
    方案 2：状态标记分阶段，Redis 标记区分【处理中 / 成功】，设置合理过期时间；业务失败时主动清理 Redis 标记，允许重试；数据库流水表记录业务最终状态，以 DB 为准。

    Q：为什么压测没测出来？

    A：压测很多是串行或者错开的请求；只有同一个流水号极短时间双发才会触发这个窗口，场景很难构造，大促流量随机并发才暴露。

    Q：能不能用 Lua 脚本？

    A：可以，Lua 脚本保证查询 + 标记设置在 Redis侧原子执行，也是可选方案；SET NX 更简单通用。

    第 5 题　Redis 和数据库双写怎么保证一致？

    举例说明：

    线程 A 先删缓存但还没写库，线程 B 此时查询读到旧库存并回填缓存，
    随后 A 才写库。结果数据库库存已是 0，缓存里仍是 10，用户看到有货、点进去却下不了单。

    候选人浅层回答：

    先删缓存再写数据库；或者先写数据库再删缓存。

    连环追问

    场景：商品库存缓存，线程 A 先删缓存，还没来得及写库；线程 B 查询，把旧的数据库数据加载回缓存；
    A 再写库。最终 DB 库存是 0，Redis 残留旧库存，引发超卖。

    1. 先删缓存再写库为什么会出现这个不一致场景？
    2. 那换成先写数据库，再删缓存还会有问题吗？
    3. 怎么解决这个不一致？难道直接弃用缓存，所有请求直连数据库？

    参考答案：

    一、两种基础方案的缺陷

    方案 1：先删缓存 → 再写数据库（失效，就是题目里的事故场景） 时序：

    线程 A：删除缓存 key
    线程 B：查询，缓存 miss，读取 DB 旧数据，回写到 Redis
    线程 A：写入新数据到 DB 结果：DB 是新值，Redis 是旧值，永久不一致，库存超卖。
    这个并发漏洞是天然存在，大促高并发下极易触发。

    方案 2：先写数据库 → 再删缓存（工业界主流基础方案，不是绝对完美，只是概率低很多）
    正常时序：写 DB 成功 → 删除缓存；下次查询缓存 miss，从 DB 加载最新数据。
    漏洞（极低概率）：
    线程 A 查询，缓存刚好过期，准备从 DB 读数据
    线程 B 更新，写 DB 成功，删除缓存
    线程 A 拿到旧 DB 数据，写回 Redis 也会不一致，但发生条件苛刻：查询操作耗时 > 更新事务耗时，业务场景出现概率很低。

    结论：优先选「先写 DB，后删缓存」，而不是先删缓存。但这两个方案都只能做到最终一致性，无法做到强一致。

    二、配套兜底方案（三层防御，生产必备）

    1. 主流程：先更新数据库，再删除缓存 写操作优先落地数据库，再失效缓存。

    2. 删除缓存失败兜底：消息队列重试 删除缓存如果网络异常失败，发送消息到MQ，异步重试删除；多次失败可以人工告警。

    3. 定时全量校对（兜底修复脏数据） 定时任务，遍历核心商品，比对 DB 与Redis 数据，不一致则直接刷新缓存。解决前面极低概率的并发脏数据，也处理缓存删除丢失、Redis 宕机等异常。

    4. 库存这类强约束场景：不能只依赖缓存做扣减 库存扣减的判断基准必须是数据库。Redis 库存仅作为流量前置拦截，最终扣减、扣减校验以数据库事务为准。

    缓存脏了最多是多放行少量请求，数据库层一定要有库存大于 0 的锁校验，防止超卖。
    这就是案例事故的核心根源：业务直接信任 Redis 缓存里的库存数值，拿缓存值作为扣减依据。

    三、能不能做到强一致性？

    分布式场景下，DB+Redis 两套独立存储，无法简单做到强一致性。 想要强一致，不能同时用两套存储做读写，只能：

    • 方案 A：不用缓存，全部请求直连数据库（性能差，大促扛不住）
    • 方案 B：使用分布式事务（代价极高，性能差，业务很少用）业务上绝大多数场景接受最终一致性，使用「先写 DB，后删缓存 + MQ 重试 + 定时校对」。

    追问：本题考察核心是什么？

    参考答案：

    初级开发只会背两种顺序，不知道并发时序漏洞，分不清两种方案风险差异。

    高级工程师要理解：

    1. 明白「先删缓存再写 DB」高并发下极易出现脏读回填，不适合高并发场景；
    2. 清楚「先写库后删缓存」依然存在理论上的漏洞，只是概率更低；
    3. 区分：缓存架构一般追求最终一致性，强一致会牺牲巨大性能；
    4. 核心认知：库存这类场景，数据库才是可信数据源，缓存只是前置优化，不能作为最终扣减判断依据；缓存脏了，数据库必须兜底防超卖。

    核心思想：
    缓存更新策略不能只看正常流程，要思考并发时序异常；缓存只能加速查询，不能替代数据库作为数据真值。

    第 6 题　Redis 缓存和数据库配合

    场景

    常规流程：先查缓存，miss 查库，回写缓存。运营后台修改商品价格，数据库更新成功

    候选人浅层回答：

    更新缓存不及时，每次更新直接写新值进 Redis。

    连环追问

    1. 如果更新时直接主动 set 新值到缓存，会存在什么并发问题？
    2. 优先选「更新数据库后删除缓存」而不是更新缓存，为什么？
    3. 只靠主流程还存在极低概率不一致，配套兜底怎么做？

    参考答案：

    一、事故根因

    采用更新数据库之后，没有处理缓存，旧的缓存 key 还留在 Redis，过期时间还没到。
    用户查询直接命中缓存，读取到 199 旧数据，不会访问数据库。

    很多新手只实现了读流程（查缓存→miss 查库→回写缓存），写流程完全没设计缓存失效逻辑，更新数据库之后不去清理缓存，旧缓存一直存活。

    二、两种写缓存方案对比

    方案 A：
    更新数据库，同时直接更新缓存（主动 set 新值）不推荐作为首选。
    并发问题： 线程 A 更新 DB 为 99，准备写缓存；
    线程 B 更新 DB 为 89，写缓存； 网络时序颠倒，B 的缓存写入先完成，A 后写入。
    数据库最终是 89，但缓存被 A 覆盖写成 99，永久脏数据。
    并发更新场景，直接更新缓存容易发生写覆盖。

    方案 B：先更新数据库，成功之后删除缓存 key（失效缓存）（工业界主流）
    原理：不主动把新数据塞缓存，直接删掉旧缓存。下一次用户查询缓存 miss，自动从数据库加载最新数据写回缓存。

    • 规避多线程并发更新导致的缓存覆盖问题；
    • 缺点：存在极低概率不一致场景：查询线程刚好在缓存过期瞬间读到旧 DB 数据，回写缓存，但是发生条件苛刻，业务大多可接受。
    • ❌ 不要用：先删缓存，再写数据库，高并发极易出现前面讲的脏读回填。

    三、三层防护完整方案

    1. 主流程：写操作【先更新数据库，成功再删除缓存】 数据库事务提交成功之后，执行删除缓存。如果删除缓存失败（网络抖动、Redis 短暂不可达），进入重试机制。
    2. 失败兜底：MQ 异步重试删除 删除缓存失败时，发送消息到 MQ，异步重试删除缓存；设置重试次数上限，超过阈值触发告警人工介入。解决瞬时网络异常导致缓存删不掉的情况。
    3. 兜底校对：定时任务校对数据 针对商品价格这类敏感数据，定时任务批量比对数据库和缓存，发现不一致直接刷新缓存。用于修复极低概率并发脏数据，也能处理 MQ 消息丢失等极端情况。

    四、特殊场景区分

    1. 普通商品详情（最终一致性，可短暂容忍延迟）：采用上面这套「先写库，后

    2. 删缓存 + MQ 重试 + 定时校对」。

    3. 价格、库存这类强敏感业务： 不建议完全依赖缓存展示作为最终判断依据；下单扣减、价格校验以数据库为准，缓存只做页面展示加速，就算缓存短暂脏，核心交易逻辑以数据库真值为准。

    4. 如果业务完全不能容忍任何短暂不一致： 不能使用这套缓存方案，要么不使用缓存全部直连 DB；或者使用分布式事务，代价很高，性能差，一般业务不会选用。

    追问：本题考察核心是什么？

    参考答案：

    初级开发只会写读缓存逻辑，忽略写流程，以为缓存只是查询加速。

    高级工程师要理解：

    1. 缓存架构是读 + 写双流程，只做读流程，更新数据后不清理缓存，一定会读到旧数据；
    2. 区分「更新缓存」和「删除缓存」两种方案，明白直接更新缓存存在写覆盖的并发缺陷；
    3. 懂得主流程 + 异步重试 + 定时校对的多层兜底，理解缓存只能做到最终一致性；
    4. 业务层面分清：页面展示可以接受短暂最终一致，核心交易逻辑必须以数据库为准，不能信任缓存。

    核心思想：
    缓存更新不要去更新 value，优先失效 key；缓存是查询加速层，数据真值永远保存在数据库，
    同时要有多层兜底机制处理各种异常。

    第 7 题　秒杀超卖问题完整解析

    举例说明：

    库存只剩 1 件，两个请求几乎同时执行 select 库存（都读到 1）并判断充足，
    随后各自 update 扣减，结果库存变成 -1，同一件商品卖出去两次。

    问题根源

    普通写法：
    select 库存 > 0 → update 库存-1 select 和 update 是两条独立 SQL，不具备原子性。高并发下多个线程同时读到库存 > 0，一起执行扣减，就发生超卖；单线程、低并发看不出问题，压测 / 线上大流量才暴露。

    本质：

    共享资源的原子性被破坏。

    三层防御方案（视频里说的三层）

    第一层：前端 + 网关拦截（挡掉无效流量，保护后端）

    1. 前端按钮置灰、防重复点击；
    2. 网关层限流、验证码、黑名单；
    3. 令牌桶限流，控制进入秒杀服务的总并发，拦截刷子。 作用：削峰，减少到达业务服务的请求，不解决超卖，先挡流量。

    第二层：Redis 预扣库存（承接高并发，核心防超卖）

    秒杀库存提前加载到 Redis； 用Lua 脚本原子执行：判断库存、扣减库存，Lua 保证多条命令原子，不会并发穿透； Redis 扣减成功之后，发送消息到 MQ 异步创建订单、扣 DB 库存；

    • 这里 Redis 是高速缓冲，不直接依赖 DB 扛峰值。

    风险：Redis 和 DB 不一致，靠状态机、补偿任务对账。

    第三层：数据库最终兜底（最后一道防线，防止 Redis 异常导致超卖）两种常用方案，二选一：

    • 悲观锁：select stock from goods where id=? for update，锁住商品行；适合库存少、并发不极致的场景，锁竞争大性能差；

    • 乐观锁（版本号方案，推荐） update goods set stock = stock - 1,version = version + 1 where id=? and stock>0 and version = #{oldVersion} 只有版本号匹配才扣减，更新返回行数 = 1 代表扣减成功；返回 0 说明已经被别的请求扣走，拒绝下单。 数据库这一层，哪怕 Redis 出问题，也不会超卖，兜底保障。

    补充配套能力（面试官继续追问必说）

    1. 幂等：每个请求唯一订单号，防止重复下单；
    2. 超时回滚：Redis 扣库存成功，但是订单创建失败，要回补 Redis 库存；
    3. 异步解耦：MQ 异步生成订单、扣数据库，避免同步 DB 拖垮接口；
    4. 对账补偿：定时任务核对 Redis、DB、订单表库存差异，发现不一致人工 / 自动修复；
    5. 防黄牛：账号维度限购，一人一单。

    面试连贯口述标准答案（直接背）

    超卖的根本原因是库存查询和扣减不是原子操作，并发场景多个请求同时读到有效库存，一起执行扣减。
    秒杀做三层防护：
    第一层前端 + 网关限流验证码，拦截无效流量；
    第二层 Redis+Lua 脚本原子预扣库存，扛高并发，扣成功后发 MQ 异步落单；
    第三层数据库乐观锁兜底，SQL 带上 stock>0 和 version 版本条件，保证数据库层面绝对不会超卖。同时做幂等、限购、定时对账补偿，处理数据不一致问题。

    延伸追问：乐观锁失败很多怎么办？

    乐观锁冲突高会大量更新失败，适合秒杀这种短时间一次性抢购；如果冲突极高，可以改成 Redis Lua 为主，数据库仅兜底，不要让大量请求直接打到 DB 乐观锁。

    延伸追问：为什么不直接用分布式锁？

    分布式锁也能解决，但是锁会串行，并发能力下降；秒杀追求吞吐，优先 Lua原子扣减，性能更好。

    第 8 题　电商下单系统设计（订单创建、库存扣减、支付回调、超时取消全流程）

    设计方案:

    1. 网关层：流量入口、限流、风控、验签

    2. 订单服务：创建订单、状态流转、关单、查询

    3. 库存服务：预扣库存、确认扣减、释放库存（核心防超卖）

    4. 支付服务：对接第三方支付、支付回调处理

    5. 消息中间件（RocketMQ/Kafka）：异步解耦、可靠通知

    6. 定时 / 延时任务：超时未支付自动取消订单、回滚库存

    7. 兜底补偿服务：对账、异常修复

    分析

    流量削峰与前置防护（第一道防线）下单是热点链路，不能直接打到业务 DB。

    • 网关：令牌桶限流、IP / 账号维度风控；恶意请求直接拦截；活动预热静态商品页、商品详情走缓存；
    • 前端按钮防重复提交 + 后端全局唯一幂等号（traceNo），一次提交一个单号，杜绝重复下单；
    • 削峰：高并发活动场景，可采用消息排队下单（异步下单），用户进入排队页，适合秒杀；普通电商同步下单。

    下单核心流程 + 库存方案（防超卖重点）采用库存预扣（冻结）模式，而不是直接扣减：

    A:用户提交下单请求，携带幂等号、商品 SKU、数量；
    B:订单服务先做参数校验，调用库存服务冻结库存；

    • 库存设计：库存分【可售库存 + 冻结库存】；更新用数据库行锁 or Redis 库存 + Lua 脚本；
    • 选型：普通商品：MySQL 行锁；秒杀热点 SKU：Redis+Lua 预冻结，异步同步到 DB；

    冻结成功 → 创建订单，订单状态：待支付；

    冻结失败 → 直接返回库存不足，流程终止；

    • 关键点：先冻库存，再生成订单，顺序不能反过来，否则超卖风险极高。

    支付链路与回调处理（幂等、防重复回调）订单创建后，跳转第三方支付（微信 / 支付宝）：

    A:调用支付渠道，生成支付链接，记录支付流水；支付流水表和订单关联；

    B:第三方异步回调通知支付结果；回调是高危重复调用场景：
    - 支付流水唯一索引，回调先查流水状态，保证回调幂等；
    - 收到支付成功：更新订单状态→已支付，发 MQ 消息；库存服务收到消息，把【冻结库存】转为【实际扣减】；
    - 支付失败：触发释放冻结库存，订单标记支付失败；

    C:补偿：支付渠道回调可能丢消息，增加主动轮询任务，定时查询第三方支付状态，避免状态卡死。

    D:超时取消订单（延时关单，释放库存）需求：用户下单后 N 分钟未支付，自动取消订单、解冻库存。 不推荐定时轮询扫订单表（大数据量拖垮 DB）

    方案：使用延时消息（RocketMQ 延时队列 / Redis zset）

    a:创建待支付订单成功，发送一条延时消息（比如 15min）；

    b:延时消息到期被消费；消费时先查当前订单状态：

    • 如果还是【待支付】：订单关闭、状态改为已取消，发送 MQ 通知库存服务解冻冻结库存；
    • 如果已经支付：直接丢弃这条延时消息，不处理；兜底：延时消息丢失的情况，后台低频率补偿扫描任务（夜间 / 低峰），只扫少量边界异常订单，不作为主流程。

    c:分布式事务一致性方案（非常高频追问）整个链路：冻结库存 → 创建订单 → 支付成功扣库存，跨多个服务，不用 2PC（性能差、阻塞） 采用本地消息表 / 可靠消息最终一致性（事务消息）

    • 下单冻结库存 + 创建订单：在订单服务本地事务，成功后发送事务消息；
    • 所有下游（库存确认、物流、积分）消费消息，消费成功才 ack；消费失败重试，多次失败进入死信队列人工对账；
    • 死信、状态不一致，由对账系统兜底修复。

    d:存储、状态机、运维兜底设计

    1. 订单表：
    • 分库分表：按用户 ID 哈希分片；冷热分离，历史订单归档；
    • 严格状态机流转：待支付 → 已支付 / 已取消；禁止随意改状态；状态变更留操作日志；

    1. 库存：热点 SKU 读写分离、缓存；库存变更流水记录；

    2. 对账系统（核心兜底）：

    • 每日定时：订单、支付流水、库存三方对账；找出不一致数据（冻结没释放、扣减没订单、支付成功订单未更新）；
    • 告警：异常订单推送工单人工处理；
    1. 降级：库存服务不可用时，下单直接关闭；支付回调单独隔离线程池，避免主链路阻塞。

    精简口述完整版（面试直接讲）

    口诉:这套下单系统覆盖下单、库存冻结、支付回调、超时关单，整体基于可靠消息做最终一致性：
    首先网关层限流风控，使用全局幂等号防重复下单；
    下单时先冻结库存，再创建待支付订单，避免超卖；
    库存冻结采用 MySQL 行锁或者 Redis Lua，热点商品放 Redis。
    订单创建成功后下发延时消息，用来实现 15 分钟超时未支付自动关单、解冻库存，避免轮询扫表；
    支付由第三方异步回调，支付流水做幂等，支付成功后发可靠消息，把冻结库存转为真实扣减；
    回调丢失则配合主动轮询补偿。 整个链路不用强一致事务，使用 RocketMQ 事务消息，本地消息表保证消息可靠投递；
    下游消费失败进入死信。
    最后增加状态机管控订单流转，分库分表存储订单，配套定时对账系统，做库存、订单、支付三方对账，修复消息丢失、回调异常带来的数据不一致，同时做好服务隔离、线程池隔离、降级熔断保障高峰期稳定。

    面试官高频追加问题（附带答案）

    Q：为什么不先创建订单再扣库存？

    A：并发下大量订单生成之后库存不够，会产生大量无效订单，出现超卖。

    Q：延时消息如果丢了怎么办？

    A：延时消息是主方案，配套低频率补偿扫描任务，只扫少量异常，不做主流程。

    Q：Redis 预扣库存宕机怎么办？

    A：Redis 记录冻结流水，异步同步 D
    B；以 DB 库存为准，定时核对 Redis 和 DB 库存差异。

    Q：超卖还有什么兜底？

    A：库存扣减时 DB 层面加乐观锁 / 行锁，作为最后兜底防线。

    第 9 题　第三方支付对接系统设计（P7 面试题）

    考点：

    不是调 SDK、写回调；核心是幂等、状态机、多渠道适配、可靠通知、对账资金安全、故障兜底，
    资金链路容错优先级远高于普通业务。

    六大得分点

    支付单模型 & 状态机（根基）不能直接拿订单去对接支付，独立支付流水表（payment_record），一笔订单可以有多笔支付流水（多次支付、补付）。

    关键字段：
    支付流水号（我方唯一，幂等主键）、订单号、渠道（微信 / 支付宝 / 银联）、渠道交易号、金额、状态、回调原始报文、版本号、创建 / 更新时间。 状态闭环（严格单向流转，禁止乱改）： INIT(待发起) → PAYING(支付中) → SUCCESS(支付成功) / FAIL(支付失败) / CLOSED(超时关闭) / REFUND(已退款)

    • 状态变更必须写操作日志，谁、什么时候、触发来源（回调 / 主动查询 / 后台人工），满足审计。

    核心：订单状态 和 支付流水状态 解耦，订单依赖支付结果，但支付链路独立。

    幂等设计（重中之重，资金红线）两个场景都会重复调用：渠道异步回调、我方主动轮询查询。

    1. 我方支付流水号作为唯一幂等 key，数据库唯一索引；

    2. 收到回调第一步：先查这条支付流水当前状态；

    • 已经终态（成功 / 失败 / 关闭）：直接返回渠道 success，不执行业务逻辑，避免重复入账、多次扣权益；
    • 非终态：校验签名、金额、渠道订单号一致，校验通过再推进状态、发消息；

    1. 签名校验不能省：验签失败直接丢弃，防伪造回调；

    2. 接口层面：回调接口对外只给渠道访问，加白名单。

    踩坑：很多新人拿到回调就直接改订单，渠道重试回调造成多次发货、多次记账。

    双链路结果确认机制（解决回调丢失、回调延迟）渠道回调是不可靠通知：网络抖动、我方服务宕机，回调会丢或者很晚到。 ✅

    主链路：渠道异步回调； 补偿链路：定时轮询任务，按支付流水号主动调用渠道查询接口； 策略：
    刚创建的支付单高频查；超过一定时间逐步降低轮询频率；到达最大有效期直接关闭支付单；
    以渠道侧状态为准，我方状态只是镜像；禁止只依赖回调，只靠回调等于把资金状态交给网络。

    多渠道适配 + 隔离设计微信、支付宝、银联、其他第三方接口协议、字段、回调格式、错误码完全不一样：

    1. 策略模式抽象支付网关：上层统一接口 createPay()、queryPayResult()、refund()，每个渠道单独实现；

    2. 渠道配置化：渠道开关、费率、超时时间、appid 密钥、回调地址配置在配置中心，动态切换；

    3. 故障隔离：不同渠道独立线程池、独立限流；微信挂了不影响支付宝；

    4. 降级：渠道异常时，前端提示切换其他支付方式。

    消息解耦 + 最终一致性支付成功后要通知订单、库存、积分、财务记账等多个下游：

    1. 回调 / 轮询拿到成功状态后，先落库更新支付流水为成功，再发可靠 MQ 消息；

    2. 下游消费做自己业务，消费失败重试，多次失败进死信；

    3. 不用同步调用下游；如果下游同步阻塞，回调超时，渠道会重复回调，放大风险；资金库更新优先，通知下游异步。

    4. 对账、差错处理、审计兜底（资金系统生命线）回调、轮询只是实时链路，对账是每日兜底防线：

    A:日切对账：每天拉取渠道对账单，和我方支付流水对账；

    • 单边账：渠道显示成功，我方没收到成功通知；
    • 差异账：金额不一致；

    B:差错单自动标记告警，人工工单处理；支持人工复核补单、退款；

    C:退款链路也要一套独立状态机、幂等、对账；

    D:所有原始回调报文、渠道返回报文全量落库归档，用于排查客诉、审计。

    面试精简口述版
    本对接第三方支付，核心是资金链路的可靠性，我会独立设计支付流水表，和订单解耦，用严格状态机管控支付单流转。
    第一做好幂等，以我方支付流水号为主键，回调先查状态，终态直接返回，防止重复入账，同时强制验签；
    第二采用回调 + 主动轮询双确认机制，不能只依赖渠道回调，解决消息丢失；
    第三用策略模式封装各个支付渠道，做配置化和资源隔离，渠道故障互不影响； 支付成功落库之后异步发 MQ 通知订单、财务等下游系统；
    最后每日拉取渠道账单做资金对账，识别单边账、差异账，配套报文归档和审计日志，保障资金可追溯、差错可修复。

    高频追问

    Q：回调接口为什么一定要快速返回？

    A：渠道有超时，超时会无限重试；我们业务逻辑（改订单、发消息）放到 MQ 异步，回调接口只做验签、幂等判断、入库，快速返回成功。

    Q：支付成功消息丢了怎么办？

    A：轮询会发现状态成功但下游未处理，对账环节也会识别单边账，人工或者补偿任务修复。

    Q：金额校验为什么很重要？

    A：防止攻击者篡改回调参数，把 100 元改成 0.01 元，必须比对回调里的金额和本地支付流水预存金额。

    Q：支付超时关闭，是渠道关还是我方关？

    A：两边配合，我方设置有效期，到期主动关单；同时轮询确认渠道真实状态，避免单方面关单和渠道不一致。
