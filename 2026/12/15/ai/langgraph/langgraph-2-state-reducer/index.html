    LangGraph 02 · 状态、channel 与 reducer

    📅 2026-12-15

    02 状态、channel 与 reducer

    默认 reducer 是「覆盖」；累积、去重、清空都得显式声明｜依据官方 Graph API · State / Reducers 自绘

    版本不一致提示

    • 本篇基线是 LangGraph 1.2.x + Python 3.13，示例不调用模型，纯本地可跑；
    • 官方明说 create_agent 的 state schema 必须是 TypedDict，Pydantic 模型不支持；手搭图可以用 TypedDict / dataclass / BaseModel，性能上前两者更好；
    • 用 add_messages 而不是 operator.add 做消息通道：前者能按 id 更新已有消息（人工介入改消息就靠它），后者只能追加；
    • Overwrite 可以绕过 reducer 强制覆盖（含清空），官方单列了一节，本篇只在坑里点名，不当主路径。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 说清 state 的「schema + channel + reducer」三层结构，以及节点返回的更新到底被谁合并；
    2. 会写 operator.add、自定义去重函数两种 reducer，知道默认覆盖会带来什么事故；
    3. 能判断什么时候该用 MessagesState / add_messages，而不是自己拿 list 硬拼。

    二、前置知识

    • 读完 LG01，知道节点返回的是「部分更新」；
    • 会写 Python 的 TypedDict 与 Annotated（不熟也行，本篇会给完整代码）；
    • 对「不可变」有直觉：节点函数不该原地修改传进来的 list。

    三、理论讲解（官方定义）

    顺序照官方 Graph API 的 State → Schema → Reducers → MessagesState 四节。

    1. state 的两层：schema 与 reducer

    官方的定义是：LangGraph 把状态存在 channel 里——schema 的每个 key 就是一个 channel。每个 channel 持有值，并定义「更新怎么合并进来」。

    • schema：声明有哪些 channel、什么类型；
    • reducer：一个二元函数，决定「旧值 + 新值」怎么变成新值。

    没有 reducer 的 channel 用最后写入胜出（last-write-wins）。

    2. reducer 的签名

    官方给的签名是二元的：

    new_value = reducer(left=current_state[key], right=node_update[key])
    • left：合并前 state 里这个 key 的当前值；
    • right：节点这次返回的这个 key 的值。

    所以 reducer 不需要知道图的结构，它只处理「一个 key 的两个值怎么合成一个」。

    3. 三种 schema 写法

    写法
    适合
    官方提示
    TypedDict
    绝大多数图，性能最好
    create_agent 只接受这一种
    dataclass
    需要给字段默认值
    同样轻量，可用于 StateGraph
    Pydantic BaseModel
    需要校验、要类型转换
    手搭图可用，但 create_agent 不支持

    4. 内置 reducer：operator.add

    import operator
from typing import Annotated
from typing_extensions import TypedDict

class State(TypedDict):
    notes: Annotated[list[str], operator.add]

    operator.add 对 list 就是拼接：["hi"] + ["bye"] → ["hi", "bye"]。它只做追加，不能改已有元素。

    5. 消息通道：MessagesState 与 add_messages

    官方专门解释了为什么消息不能只用 operator.add：

    • 聊天模型要的是消息列表；
    • 人工介入时要修改已有消息（比如把某条工具结果改掉），operator.add 做不到；
    • add_messages 会按消息 id 合并：新 id 追加，已有 id 覆盖。

    MessagesState 是预置好的「只有一个 messages key、reducer 是 add_messages」的 schema，要加字段就继承它：

    from langgraph.graph import MessagesState

class ChatState(MessagesState):
    documents: list[str]

    6. 多 schema：输入、输出与私有通道

    官方还提到一种进阶用法：给图声明不同的输入 schema 与输出 schema——输入只暴露用户该给的字段，输出只暴露想返回的字段，中间过程用私有 channel。本篇不展开，知道有这条路即可（官方在同页「Schema」小节给了说明）。

    7. 绕过 reducer：Overwrite

    要给一个带累积 reducer 的 key 做「重置/清空」，官方给了 Overwrite：显式告诉运行时「这次不要合并，直接替换」。它不是常规路径，只在「必须清空累积值」时用。

    四、原理拆解

    把 state 想成一张有多列的共享表格：

    • 每个节点交上来的是一张「只填了几列的小纸条」；
    • 每列有自己的规则：有的「写在后面就覆盖」，有的「往后接一段」，有的「重复的不算」；
    • 合并发生在一轮结束时，所以同一轮里两个节点看不到对方刚写的内容。

    三个关键判断：

    1. 默认规则是覆盖：没写 reducer 的列，后交的纸条赢；
    2. 并行写同一列必然打架：要么各写各的列，要么给这列配好合并规则；
    3. 节点里读的是本轮开始时的值：所以别在节点里「先读再写同一个累积字段」还指望它包含同轮别人的贡献。

    五、场景说明

    1. 累积证据（RAG 检索结果）：Annotated[list, operator.add]；
    2. 去重标签、去重来源：自定义 reducer 里判重；
    3. 对话历史：MessagesState / add_messages，不要用 operator.add；
    4. 计数器、当前阶段：普通 key，覆盖语义正好；
    5. 必须清空累积值时：Overwrite，而不是在 reducer 里塞 if right == [] 这种隐式约定。

    六、示例代码

    步骤 1：环境准备

    无。这就是纯状态篇的好处：不用 API key 也能验证全部行为。

    步骤 3：导入

from typing import Annotated

    步骤 4：最小可运行代码

    存成 state_demo.py，uv run state_demo.py。

    import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

def unique(left: list[str], right: list[str]) -> list[str]:
    """自定义 reducer：保留左，追加右里没出现过的。"""
    out = list(left)
    for item in right:
        if item not in out:
            out.append(item)
    return out

class State(TypedDict):
    topic: str
    notes: Annotated[list[str], operator.add]     # 追加
    tags: Annotated[list[str], unique]            # 去重追加
    round: int                                    # 默认覆盖

def plan(state: State):
    return {"notes": [f"拆解：{state['topic']}"], "tags": ["planning"], "round": 1}

def research(state: State):
    return {"notes": ["资料 A", "资料 B"], "tags": ["research", "planning"], "round": 2}

def wrap(state: State):
    return {"notes": [f"共 {len(state['notes'])} 条笔记"]}

builder = StateGraph(State)
builder.add_node("plan", plan)
builder.add_node("research", research)
builder.add_node("wrap", wrap)
builder.add_edge(START, "plan")
builder.add_edge("plan", "research")
builder.add_edge("research", "wrap")
builder.add_edge("wrap", END)
graph = builder.compile()

result = graph.invoke({"topic": "状态机", "notes": [], "tags": [], "round": 0}, version="v2")
print("notes =", result.value["notes"])
print("tags  =", result.value["tags"])
print("round =", result.value["round"])

    步骤 5：预期输出

    notes = ['拆解：状态机', '资料 A', '资料 B', '共 3 条笔记']
tags  = ['planning', 'research']
round = 2

    三行分别验证三件事：notes 是追加（4 条都在）；tags 里 planning 只出现一次（去重生效）；round 是 2 而不是 1（覆盖语义，后写的赢）。

    步骤 6：验证是否成功

    • 把 research 的返回改成 return state：notes 里会出现重复条目——旧值被当成新值又追加了一遍，这是「返回整份 state」和累积 reducer 撞在一起的典型结果；
    • 把 tags 的 reducer 去掉，再看输出：['planning', 'research'] 会变成 ['research', 'planning']，planning 被后写的那次覆盖掉、且顺序变了；
    • 把 wrap 挪到 research 同一轮并行（add_edge("plan", "research") + add_edge("plan", "wrap")）：wrap 里那条「共 N 条」会是 1 而不是 3——本轮写入互相不可见（LG04 讲原因）。

    七、常见坑（官方明确限制/版本差异）

    1. 以为默认 reducer 会合并。默认是覆盖；要累积必须写 Annotated[..., operator.add]。
    2. 拿 operator.add 做消息通道。它只能追加，人工介入要改某条消息时会失效；用 add_messages / MessagesState。
    3. 节点里原地改 list。state["notes"].append(x) 改的是读到的对象，不是「返回更新」，行为取决于运行时序，别这么写；改成返回新 list。
    4. 并行分支写同一个 key 却没有 reducer。后写的覆盖先写的，而且轮次顺序不保证（LG04 / LG02b 图示）。
    5. 给 create_agent 传 Pydantic state。官方明确不支持，只接受 TypedDict。

    八、课后小结

    • state = schema（有哪些 channel）+ reducer（每个 channel 怎么合并）；
    • 默认 reducer 是覆盖，累积要 operator.add，去重要自定义函数；
    • MessagesState 的 messages 用 add_messages，按 id 合并，别用 operator.add；
    • 合并发生在 super-step 结束时，同轮写入互相不可见；
    • 要强制清空累积值，用 Overwrite，不要写隐式约定。

    九、思考题

    1、为什么 reducer 的签名是 (left, right)，而不是「直接拿到整份 state」？

    参考回答：reducer 只对一个 key 负责，(left, right) 让它与图结构解耦——同一个函数可以挂到任何 key 上，也便于单独测试。拿整份 state 会让合并逻辑互相纠缠。

    2、MessagesState 相比 Annotated[list, operator.add] 多解决了什么问题？

    参考回答：按 id 更新。add_messages 会在同 id 时替换旧消息，这支撑了人工介入里「改一条消息再继续」；operator.add 只会一直往后追加。

    3、同一轮里两个并行节点，A 写 answer、B 读 answer，B 能读到 A 的值吗？

    参考回答：不能。合并发生在 super-step 结束，B 读到的仍是本轮开始时的值。要串行就加边；要并行就各写各的 key。

    4、什么时候该用 Overwrite？

    参考回答：某个 key 挂了累积型 reducer，但这次必须把它整体替换掉或清空（比如换会话、重置计数器）。普通覆盖语义的 key 不需要它。
