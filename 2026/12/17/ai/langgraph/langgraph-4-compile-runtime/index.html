    LangGraph 04 · 编译、super-step 与运行配置

    📅 2026-12-17

    04 编译、super-step 与运行配置

    recursion_limit 数的是轮次，不是节点调用次数｜依据官方 Graph API · 执行模型自绘

    版本不一致提示

    • 本篇基线是 LangGraph 1.2.x + Python 3.13；官方要求 Python ≥ 3.10；
    • 1.x 的 invoke() / stream() 默认仍是 version="v1"（返回 dict / 旧 chunk 结构）；1.1 起可传 version="v2" 拿 GraphOutput 与 StreamPart，本系列统一显式传 v2；
    • recursion_limit 官方默认是 25，超限抛 GraphRecursionError；它是「轮次上限」，不是「节点调用上限」；
    • durability（"exit" / "async" / "sync"）属于持久化篇的内容，本篇只在运行参数里点名，真实语义在 LG07 讲。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 说清一个 super-step 里发生了什么：并行执行、轮末合并、下一轮才可见；
    2. 会用 stream_mode="updates" 把每一轮的产出打出来，用 recursion_limit 给循环设上限并看懂报错；
    3. 分清 config 里 configurable / tags / metadata / recursion_limit 各自管什么，以及 version="v2" 返回的 GraphOutput 怎么用。

    二、前置知识

    • 读完 LG01–LG03：会 compile、会写节点与边、知道 Command / Send 会产生并行分支；
    • 理解「状态是共享快照」；
    • 有一个可用的模型 key（本篇示例会调一次模型，用来演示并行耗时）。

    三、理论讲解（官方定义）

    顺序照官方 Graph API 的 Compiling → 执行模型（super-step）→ 运行配置几节，补充 1.1 版本说明里的 version="v2"。

    1. compile() 除了校验还做了什么

    官方的说法是：编译检查图结构（例如孤立节点），并把运行时选项挂到执行对象上——checkpointer、store、断点都在这一步绑定。

    compile() 可以反复调用：同一份 builder 编出带 checkpointer 的、不带 checkpointer 的两个对象，是常见做法（测试与生产分开）。

    2. super-step 是执行单位

    LangGraph 的执行是「按轮推进」的：

    1. 这一轮该跑的节点并行执行；
    2. 全部跑完后，把它们的返回值按 channel 的 reducer 合并进 state；
    3. 再根据边和路由决定下一轮跑谁。

    由此推出三条结论，官方在并行边、reducer 两节分别提过：

    • 同一轮的节点读到的都是本轮开始时的 state，看不到同轮别人的写入；
    • 一轮里两个节点写同一个 key，没有 reducer 就是覆盖；
    • 「扇出」是同一轮多分支，不是线程池调度。

    3. recursion_limit

    官方示例用 config={"recursion_limit": 25}。它限制的是图推进的轮次数，超过就抛 GraphRecursionError。默认值 25——一个正常的 Agent 循环通常在 5–10 轮内结束，25 已经很宽松。

    这条限制存在的意义：模型可能一直要工具、条件边可能一直把你送回同一个节点，没有上限就是死循环。

    4. config 里有什么

    字段
    管什么
    常见用法
    configurable
    运行时可变配置
    会话标识、多轮对话
    recursion_limit
    轮次上限（顶层字段）
    给循环兜底
    tags
    给这次运行打标签
    追踪、按标签过滤
    metadata
    附带的键值信息
    业务侧关联（订单号等）

    thread_id 只是 configurable 里的一个约定键，LG05 会讲它怎么和 checkpointer 配合。

    5. version="v2" 的返回对象

    1.1 的版本说明写了两件事：

    • invoke(..., version="v2") 返回 GraphOutput，状态在 .value，中断在 .interrupts；
    • stream(..., version="v2") 返回统一的 StreamPart（type / ns / data），每种模式有自己的 TypedDict。

    默认仍是 v1。官方建议新代码显式传 v2，原因很实际：v1 的 dict 与旧 chunk 结构在多节点并行、子图场景下不好区分来源。

    四、原理拆解

    把一轮 super-step 想成一次班组交接：

    • 这一轮所有工人（节点）同时上班，各自拿着上班时拿到的那份工件干活；
    • 下班时统一把各自改的部分交到仓库（合并）；
    • 下一班的人才能看到上一班的全部改动。

    三个关键判断：

    1. 并行不是「同时改一个本子」：每人一份复印件，下班才汇总；
    2. 合并顺序不保证：所以依赖顺序的累积要小心（比如「第一条」「最后一条」）；
    3. 轮次上限是安全阀：它防的不是慢，是「永远不结束」。

    五、场景说明

    1. 并行取数：FAQ 查库 + 模型回答同时跑，合并时拼成一条回复；
    2. 循环型 Agent：手搭工具循环时，靠 recursion_limit + 显式退出条件双保险；
    3. 调试顺序问题：用 stream_mode="updates" 看每一轮到底跑了谁；
    4. 多环境编译：同一 builder 编出带/不带 checkpointer 的两个版本，测试用内存、生产用 Postgres。

    步骤 1：环境准备

cd lg-runtime

    步骤 2：凭证配置

    .env 放 OPENAI_API_KEY，load_dotenv() 读取。

    步骤 3：导入

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

    步骤 4：最小可运行代码

    存成 runtime_demo.py，uv run runtime_demo.py。

    import time
from dotenv import load_dotenv
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.errors import GraphRecursionError
from langchain.chat_models import init_chat_model

load_dotenv()
model = init_chat_model("openai:gpt-5-nano")

class State(TypedDict):
    q: str
    faq: str
    answer: str
    merged: str

def load(state: State):
    return {"q": state["q"].strip()}

def faq_lookup(state: State):
    time.sleep(0.3)                       # 假装在查库
    return {"faq": "FAQ：退款 7 个工作日到账"}

def llm_answer(state: State):
    return {"answer": model.invoke(state["q"]).text}

def merge(state: State):
    return {"merged": f"{state['faq']} / {state['answer']}"}

builder = StateGraph(State)
builder.add_node("load", load)
builder.add_node("faq_lookup", faq_lookup)
builder.add_node("llm_answer", llm_answer)
builder.add_node("merge", merge)
builder.add_edge(START, "load")
builder.add_edge("load", "faq_lookup")     # 两条出边 → 下一轮并行
builder.add_edge("load", "llm_answer")
builder.add_edge("faq_lookup", "merge")
builder.add_edge("llm_answer", "merge")
builder.add_edge("merge", END)
graph = builder.compile()

if __name__ == "__main__":
    t0 = time.perf_counter()
    result = graph.invoke({"q": " 退款多久到账？ ", "faq": "", "answer": "", "merged": ""}, version="v2")
    print(f"耗时 {time.perf_counter() - t0:.2f}s")
    print(type(result).__name__)
    print(result.value["merged"])

    print("---- 每一轮跑了谁 ----")
    for chunk in graph.stream({"q": "退款多久到账？", "faq": "", "answer": "", "merged": ""}, stream_mode="updates"):
        print(list(chunk.keys()))

    步骤 5：预期输出

    耗时 0.6s
GraphOutput
FAQ：退款 7 个工作日到账 / 退款一般 7 个工作日内到账，具体以支付渠道为准。
---- 每一轮跑了谁 ----
['load']
['faq_lookup', 'llm_answer']
['merge']

    第二轮一次冒出两个节点，就是「同一 super-step 并行」的可视证据；耗时接近 max(查库, 模型) 而不是两者相加（具体秒数随模型响应变化，看的是「没被 0.3 秒叠加」）。

    步骤 6：验证是否成功

    • 把 faq_lookup 的 sleep 调到 2 秒：总耗时仍由模型决定，不会被串行相加；
    • 在 merge 里打印 state：能看到 faq 与 answer 都在——合并发生在轮末，merge 是下一轮才跑的；
    • 把 add_edge("load", "faq_lookup") 改成 add_edge("load", "llm_answer")、再 add_edge("llm_answer", "faq_lookup")：两轮变串行，耗时相加，updates 里也不再同时出现两个节点。

    再单独验一次轮次上限：

    class Loop(TypedDict):
    n: int

def tick(state: Loop):
    return {"n": state["n"] + 1}

def again(state: Loop):
    return state["n"] < 10          # 永远为 True，制造死循环

b = StateGraph(Loop)
b.add_node("tick", tick)
b.add_edge(START, "tick")
b.add_conditional_edges("tick", again, {True: "tick", False: END})
g = b.compile()
try:
    g.invoke({"n": 0}, config={"recursion_limit": 5})
except GraphRecursionError as e:
    print("触到上限：", type(e).__name__)

    预期输出 触到上限： GraphRecursionError。这里 recursion_limit=5 大约只允许 5 轮 tick，n 停在 4 附近。

    七、常见坑（官方明确限制/版本差异）

    1. 以为节点按添加顺序串行。只要有两条出边，下一轮就是并行；顺序由边决定，不由 add_node 的先后决定。
    2. 并行分支配 reducer 不当。同轮写同一 key 必然冲突，默认覆盖、顺序还不保证。
    3. recursion_limit 当成节点数上限。它数的是轮次；一轮两个节点只算一轮。
    4. 把 thread_id 放在 config 顶层。它属于 configurable，写错位置不会报错，但也不生效（LG05 详述）。
    5. v1 / v2 结构混用。传了 version="v2" 就不要再 result["merged"]，用 result.value["merged"]；stream 的 chunk 结构同理。
    6. 以为编译一次就固定。compile() 可重复调用，不同运行时选项要分别编译，别在同一个对象上改来改去。

    八、课后小结

    • 一轮 super-step = 并行执行 + 轮末合并，下一轮才可见；
    • 并行分支写同一 key 要靠 reducer，顺序不保证；
    • recursion_limit 数轮次，默认 25，超限抛 GraphRecursionError；
    • config 分 configurable / 顶层限制 / tags / metadata 几类；
    • version="v2" 给 GraphOutput 与 StreamPart，本系列统一显式传。

    九、思考题

    1、为什么并行分支「互相看不见」对方的写入，而不是「看到最新值」？

    参考回答：因为合并发生在轮末。每个节点读的是本轮开始时的快照，运行时不做中途同步——这保证了同一轮内执行结果与调度顺序无关，可复现。

    2、recursion_limit=25 意味着最多跑 25 个节点吗？

    参考回答：不是，是 25 轮。一轮里并行几个节点都只算一轮；所以一个「每次只跑一个节点」的循环，上限就是 25 次。

    3、stream_mode="updates" 与 "values" 的区别是什么？

    参考回答：updates 每轮只给这一轮节点返回的增量（谁改了什么），values 每轮给完整 state。调试「谁跑了、改了什么」用 updates，回放完整状态用 values（LG09 展开五种模式）。

    4、compile() 为什么允许带不同参数重复调用？

    参考回答：运行时选项（checkpointer、store、断点）是执行环境的差异，不是图结构的差异。同一份图在测试、生产、本地调试需要不同配置，重复编译比复制代码更可靠。
