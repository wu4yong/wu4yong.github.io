    LangGraph 05 · checkpointer 与线程

    📅 2026-12-18

    05 checkpointer 与线程

    没有 checkpointer 就没有线程，也就没有续跑、回放、人工介入｜依据官方 Checkpointers / Persistence 页自绘

    版本不一致提示

    • 本篇基线是 LangGraph 1.2.x + Python 3.13，示例不调用模型，纯本地可跑；
    • MemorySaver 是 InMemorySaver 的旧名，官方排障页现在只提 InMemorySaver，本篇统一用新名；
    • 官方把 durability 分三档（"exit" / "async" / "sync"），默认是 "async"：进程在写入途中崩掉，仍可能丢最后一个检查点；
    • thread_id 在 Postgres 里长度有限，官方建议不超过 255 字符，超了是数据库报错不是 Python 报错。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 说清 checkpointer 到底存什么、存在哪个粒度上，以及为什么它必须挂在 compile() 上；
    2. 会选 InMemorySaver / SqliteSaver / PostgresSaver，知道 thread_id 是「指针」而不是「会话 ID」；
    3. 能用 get_state / get_state_history 读出状态与整串历史，并知道检查点为什么会无限增长。

    二、前置知识

    • 读完 LG04，知道 super-step 是执行单位；
    • 知道 invoke 的第二个参数是 config，里面有 configurable；
    • 对「进程重启就没了」有直觉——这正是内存版 checkpointer 的边界。

    三、理论讲解（官方定义）

    1. 持久化有两套系统，本篇只讲第一套

    官方把持久化拆成互补的两层：

    • checkpointer：把一个线程的图状态按检查点存下来，管短期记忆、断点续跑、时间旅行；
    • store：把应用自己定义的数据存成键值，跨线程，管长期记忆（LG08 专讲）。

    本篇只管 checkpointer；两者可以同时挂在一张图上。

    2. checkpointer 存在哪、存多细

    • 粒度：每个 super-step 边界一个检查点；
    • 额外还有任务级写入：同一轮里先完成的节点，它的输出会先落到 checkpoint_writes，所以同轮别的节点失败后重启，已完成的活不用重算（官方叫 pending writes）；
    • 命名空间：每个检查点带 checkpoint_ns，根图是空字符串 ""，子图是 "节点名:uuid"，嵌套用 | 拼。

    3. thread 与 thread_id

    thread_id 是「这条线」的指针：同一个 ID 再 invoke 就是接着这条线走；换一个 ID 就是全新线程、空状态。

    官方给了一张「同一 thread 下四种调用分别做什么」的表，值得背下来：

    你想干什么
    怎么调
    实际行为
    提交新输入
    invoke(input, config)
    把输入并进已存状态，从入口点重新开始
    从错误里续跑
    invoke(None, config)
    载入最新检查点，重跑没完成的部分
    回答 interrupt()
    Command(resume=x) 作输入
    把值交回 interrupt()，被中断的节点整段重跑
    回放历史
    invoke(None, snapshot.config)
    从那条历史检查点往后重新执行

    注意第三条：invoke(None, config) 不是「继续空跑」，是「把上次没干完的活干完」。

    实现

    四、原理拆解

    把 checkpointer 想成给每个线程录了一部行车记录仪：

    • 车每开一段（一个 super-step）就存一帧（一个检查点）；
    • get_state 是「看最后一帧」，get_state_history 是「把整段录像倒着放」——官方明确说返回逆序，最新的在最前；
    • 每一帧都记着 values（当时的状态）、next（下一步该跑哪些节点）、config（含 checkpoint_id）、metadata（source / step / 本轮写入）；
    • 回放就是从某一帧开始往后重放，之前的帧不会重算，之后的节点会重跑（含模型调用、外部请求）。

    一个关键推论：检查点是按轮存的，不是按节点存的。所以并行分支里「跑到一半」的进度只能靠任务级写入保命，不能靠 get_state_history 回到分支中间——那条记录只存在于整轮边界。

    五、场景说明

    1. 多轮对话：同一个 thread_id 反复 invoke，历史自然累积，不用自己拼 messages；
    2. 断点续跑：外部 API 挂了，修好后 invoke(None, config) 从最后一帧继续；
    3. 人工介入前置（LG06）：interrupt() 能暂停，前提就是状态存得下来；
    4. 测试回放（LG07/LG14）：固定 thread 回放，比 mock 整条链路更接近真实。

    六、示例代码

    步骤 1：环境准备

    uv init lg05-checkpoint
cd lg05-checkpoint
uv add langgraph

    本篇不调模型，只装运行时。pip 等价：pip install -U langgraph。

    步骤 2：凭证配置

    无。checkpointer 是纯本地机制。

    步骤 3：导入

    from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

    步骤 4：最小可运行代码

    存成 checkpoint_demo.py，uv run checkpoint_demo.py。

    from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

class State(TypedDict):
    topic: str
    step: int
    log: list[str]

def plan(state: State):
    return {"step": 1, "log": [f"plan:{state['topic']}"]}

def draft(state: State):
    return {"step": 2, "log": ["draft"]}

def polish(state: State):
    return {"step": 3, "log": ["polish"]}

builder = StateGraph(State)
builder.add_node("plan", plan)
builder.add_node("draft", draft)
builder.add_node("polish", polish)
builder.add_edge(START, "plan")
builder.add_edge("plan", "draft")
builder.add_edge("draft", "polish")
builder.add_edge("polish", END)

checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

cfg_a = {"configurable": {"thread_id": "A"}}
r1 = graph.invoke({"topic": "检查点", "step": 0, "log": []}, cfg_a, version="v2")
print("A 第一轮 step =", r1.value["step"])

# 同一 thread 再跑一次：状态接着往下走，不重置
r2 = graph.invoke({"topic": "检查点"}, cfg_a, version="v2")
print("A 第二轮 step =", r2.value["step"])
print("A 第二轮 log =", r2.value["log"])

# 换 thread：全新状态
cfg_b = {"configurable": {"thread_id": "B"}}
r3 = graph.invoke({"topic": "另一个线程", "step": 0, "log": []}, cfg_b, version="v2")
print("B step =", r3.value["step"])

snap = graph.get_state(cfg_a)
print("A 最新 next =", snap.next)
print("A 历史条数 =", len(list(graph.get_state_history(cfg_a))))

    步骤 5：预期输出

    A 第一轮 step = 3
A 第二轮 step = 3
A 第二轮 log = ['plan:检查点', 'draft', 'polish', 'plan:检查点', 'draft', 'polish']
B step = 3
A 最新 next = ()
A 历史条数 = 9

    读法：第二轮 log 里出现了两遍三段，说明同一线程的状态被读进来又接着写；next 是空元组表示「跑完了」；历史 9 条＝两轮 × 4 个检查点 + 1 个输入态（第一轮 4 条、第二轮 4 条、加上最初的空检查点）。

    步骤 6：验证是否成功

    • 把 checkpointer 去掉再跑：invoke(..., cfg_a) 会直接报错——没有 checkpointer 就不能传 thread_id，这是官方硬限制；
    • 把第二轮换成 graph.invoke(None, cfg_a, version="v2")：log 不再增长，因为上一轮已经跑完，没有待办；
    • 把 InMemorySaver() 换成 SqliteSaver(...)（见写法 A）重跑两次进程：第二轮 log 仍能接上，这是内存版做不到的。

    写法 A · 落盘：同一份代码换成 SQLite

    uv add langgraph-checkpoint-sqlite
    import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

conn = sqlite3.connect("checkpoints.db", check_same_thread=False)
checkpointer = SqliteSaver(conn)
graph = builder.compile(checkpointer=checkpointer)

    生产换 Postgres，只差两行：

    from langgraph.checkpoint.postgres import PostgresSaver
checkpointer = PostgresSaver.from_conn_string("postgresql://...")
checkpointer.setup()   # 建表 + 索引，第一次运行必须调用

    七、常见坑（官方明确限制/版本差异）

    1. 拿 InMemorySaver 当生产方案。官方排障页写得很直白：进程重启全部丢失，生产必须 PostgresSaver / SqliteSaver。
    2. thread_id 超长。Postgres 存 thread_id 的列有长度上限，官方建议压到 255 字符以内；UUID 也建议截断或哈希。
    3. 检查点无限增长。长会话越跑越多，延迟和存储成本一起涨；官方建议定期修剪或设保留策略，别等出事。
    4. 以为子图改动会立刻出现在父图。子图有自己的 checkpoint_ns，父图看到的是「子图当节点」那一轮的整块结果；要跨边界共享数据用 store（LG08）。
    5. 以为 invoke(None) 会重跑全部。它只补未完成的节点；要从头再来，用新的 thread_id。

    八、课后小结

    • checkpointer = 线程级状态快照，compile(checkpointer=...) 时挂上；
    • 一个 super-step 一个检查点，另有任务级写入兜住同轮已完成的节点；
    • thread_id 是指针：同 ID 接着走，换 ID 全新开始；
    • get_state 读最新、get_state_history 逆序读全串；
    • durability 默认 "async"，要「每步必落盘」显式传 "sync"。

    九、思考题

    1、为什么检查点按 super-step 存，而不是每个节点存一次？

    参考回答：super-step 是「一轮的原子边界」，同轮并行节点必须一起提交才有一致状态；按轮存能让「同轮部分失败」用任务级写入恢复，又不至于把状态切得太碎。

    2、invoke(None, config) 和 invoke({}, config) 有什么区别？

    参考回答：None 是「不提供新输入，继续未完成的活」；{} 是一次正常的新输入（空输入），会从入口点重新走一遍。前者用于续跑，后者会真的再跑一轮。

    3、同一个 thread_id 并发跑两次会怎样？

    参考回答：会互相踩检查点。官方没承诺并发安全，生产上「一个线程同一时刻只有一个执行」要靠外部锁或队列保证；要并行请用不同 thread。

    4、为什么官方把 durability 默认设成 "async"？

    参考回答：同步写检查点会拖慢每一步；异步写在下一步执行时落盘，性能与可靠性折中。真不能丢（比如支付前），显式传 "sync"。
