    📅 2026-12-12

    14 综合实战：文档问答 Agent（含评测与上线）

    最后一讲的产出不是「能跑」，而是「能评估、能上线、能改」｜依据官方 Agents / Evaluation / LangGraph 页面自绘

    版本不一致提示

    • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
    • 评测部分依赖 langsmith 账号与服务，免费额度与接口按官方当前页面为准；
    • 本地运行时用 langgraph dev，上线到 Agent Server 的配置格式随版本演进，以官方部署页为准。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 按「装配—护栏—评测—上线」四段，把 LC01–LC13 的能力装成一个可交付的文档问答 Agent；
    2. 写出一个最小评测集，用「答案是否正确 / 是否带出处 / 是否该拒答」三条判据量化效果，而不是凭感觉调提示；
    3. 知道本地怎么跑（langgraph dev）、部署到 Agent Server 需要哪些配置，以及上线前必须补的三件事。

    二、前置知识

    • 读完 LC08（create_agent）、LC09/L10（中间件）、LC11（上下文）、LC12（记忆）、LC13（RAG）；
    • 有一个能跑的向量库（LC13 的 InMemoryVectorStore 就够）；
    • 了解 pyproject.toml 与 uv 的基本操作。

    三、理论讲解（官方定义）

    1. 「Agent」在上线时到底是什么

    官方对 create_agent 的定义值得再强调一次：它返回的是一个编译好的 LangGraph 图，不是黑盒对象。这意味着它可以：

    • 被当成子图嵌进更大的 StateGraph（官方在「Subagents / 多 Agent」里就是这么用的）；
    • 被 Agent Server 直接托管，自动获得持久化、流式与中断能力（官方说明 Agent Server 会自动配置 checkpointer）。

    2. 官方对「可靠性」的定性

    官方在 Context engineering 页给过一句判断：Agent 失败的多数原因不是模型能力，而是「正确的上下文没给到」。这句话在实战里的含义是：调提示和调检索，比换更大的模型更有效。

    3. 评测的官方口径

    LangSmith 的评测由三部分组成：数据集（dataset）、目标函数（要评测的应用）、评估器（evaluator）。官方示例的最小评估器就是「把输出和参考答案比对」，更实用的是 LLM-as-judge（用一个模型判分）。

    对本项目，「带出处」与「该拒答」这两条无法靠字符串比对，必须自定义评估器——这正是本讲要补的能力。

    4. 上线前的三个必补项

    官方文档反复出现的三个上线前提：

    1. 持久化后端：InMemorySaver 换成数据库（LC12）；
    2. 护栏：HumanInTheLoopMiddleware（写操作）、PIIMiddleware（脱敏）、调用上限（LC09）；
    3. 可观测：LANGSMITH_TRACING=true + LANGSMITH_API_KEY，否则线上出错只能靠猜。

    四、原理拆解

    评测不是最后一步，而是「改提示 / 改检索 / 换模型」的依据｜自绘

    三条经验，来自前面每一讲的坑：

    1. 装配要少而清楚。工具控制在少数几个高区分度的，检索工具一个、记忆工具一两个、写操作一两个；工具越多，模型选错的概率越大（LC11 官方原话）。
    2. 护栏放在装配层，不放在提示里。「不要删除数据」写在 system prompt 里只是建议，HumanInTheLoopMiddleware 才是闸门。
    3. 评测先定判据再改代码。没有评测集，每次「感觉变好了」都不可复现；判据一旦定死，改提示、改切分、换模型就有了对比基线。

    五、场景说明

    1. 内部知识助手：员工问制度/流程，答案必须带文档出处，答不出就说没有；
    2. 客服一线：政策类问题走 RAG，订单类问题调业务工具，写操作走人工确认；
    3. 交付形态：先本地 langgraph dev 给团队试用，再部署到 Agent Server 接内部 IM；
    4. 迭代节奏：每次改切分参数或提示，跑同一套评测集，看三条判据的通过率。

    步骤 4：装配与评测代码

    src/doc_agent/agent.py：装配（检索 + 记忆 + 护栏）。

    import os
from dataclasses import dataclass
from langchain.agents import create_agent
from langchain.agents.middleware import PIIMiddleware, ModelCallLimitMiddleware, HumanInTheLoopMiddleware, SummarizationMiddleware
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_core.documents import Document
from langchain.tools import tool
from langgraph.checkpoint.memory import InMemorySaver

@dataclass
class Context:
    user_id: str

DOCs = [("handbook.md", "退款政策：下单后 7 天内可无理由退款。"), ("ops.md", "发货时效：现货 48 小时内发出。")]
docs = [Document(page_content=t, metadata={"source": s}) for s, t in DOCs]
splits = RecursiveCharacterTextSplitter(chunk_size=200, chunk_overlap=40, add_start_index=True).split_documents(docs)
store = InMemoryVectorStore(OpenAIEmbeddings(model="text-embedding-3-small"))
store.add_documents(splits)

@tool
def search_docs(query: str) -> str:
    """检索内部文档，回答政策问题前必须调用。"""
    hits = store.similarity_search(query, k=3)
    return "\n".join(f"[{d.metadata['source']}] {d.page_content}" for d in hits) or "未检索到相关片段"

@tool
def issue_refund(order_id: str) -> str:
    """发起退款。写操作，需要人工确认。"""
    return f"{order_id} 退款已提交"

agent = create_agent(
    model="openai:gpt-5-nano",
    tools=[search_docs, issue_refund],
    system_prompt="政策问题只用 search_docs 的内容作答并标注来源；检索不到就说没有依据，不要推测。",
    context_schema=Context,
    checkpointer=InMemorySaver(),
    middleware=[
        PIIMiddleware("email", strategy="redact"),
        HumanInTheLoopMiddleware(interrupt_on={"issue_refund": True}),
        ModelCallLimitMiddleware(run_limit=6),
        SummarizationMiddleware(model="openai:gpt-5-nano", trigger=("tokens", 6000), keep=("messages", 20)),
    ],
)

    src/doc_agent/eval.py：三条判据的评估器。

    from langsmith import evaluate

CASES = [
    {"question": "退款期限是多久？", "must_cite": "handbook.md", "should_refuse": False},
    {"question": "保修期多久？", "must_cite": None, "should_refuse": True},
]

def target(inputs: dict) -> dict:
    r = agent.invoke({"messages": [{"role": "user", "content": inputs["question"]}],
                      "user_id": "eval-user"},
                     context=Context(user_id="eval-user"),
                     config={"configurable": {"thread_id": "eval"}})
    return {"answer": r["messages"][-1].text}

def cites_source(outputs: dict, reference_outputs: dict) -> dict:
    if reference_outputs.get("must_cite") is None:
        return {"key": "cite", "score": 1}
    return {"key": "cite", "score": 1 if reference_outputs["must_cite"] in outputs["answer"] else 0}

def refuses_when_unknown(outputs: dict, reference_outputs: dict) -> dict:
    if not reference_outputs.get("should_refuse"):
        return {"key": "refuse", "score": 1}
    ok = any(w in outputs["answer"] for w in ["没有依据", "未检索到", "无法回答"])
    return {"key": "refuse", "score": 1 if ok else 0}

evaluate(target, data="doc-agent-cases", evaluators=[cites_source, refuses_when_unknown])

    • 在 Studio 里问「给 a@b.com 用户退款」，应看到 PII 把邮箱替换为 [REDACTED_EMAIL]，并且 issue_refund 触发中断等确认；

    差异集中在「模型怎么初始化」这一层，往下 invoke / stream / bind_tools 的链路基本不变：

    • 智谱、通义不进统一入口。init_chat_model 认不出 zhipuai / tongyi 这两个 provider 名，要直接实例化 ChatZhipuAI、ChatTongyi（两个类都在 langchain-community 里）；两家也都提供 OpenAI 兼容端点（智谱 https://open.bigmodel.cn/api/paas/v4、通义 https://dashscope.aliyuncs.com/compatible-mode/v1），用 ChatOpenAI(base_url=...) 也能打通，但 provider 专有字段可能不被提取或保留。

    • 通义的类默认走流式，ChatTongyi(model="qwen-plus") 之后拿到的就是流式结果；要做视觉用 qwen-vl-max。

    七、常见坑（官方明确限制/版本差异）

    1. 评测集当「测试」写死在后端。官方把评测放在 LangSmith 侧（dataset + evaluators），本地只留 target；把断言硬编码进业务代码，会让线上回归变慢。
    2. 用字符串比对判「带出处」。答案里可能写「来源：handbook.md」也可能写「见 handbook」，判据要按「关键标识是否出现」设计，别要求精确句。
    3. 上线忘了换 checkpointer。InMemorySaver 重启即失，官方在 Agent Server 侧会自动配持久化，自建服务则要自己换。
    4. 写操作只在提示里禁止。HumanInTheLoopMiddleware 按工具名拦；漏配一个写工具就等于没有护栏。
    5. 不看轨迹就调提示。没有 LANGSMITH_TRACING，你无法知道失败是「没检索到」还是「检索到了没引用」。

    八、课后小结

    • create_agent 返回编译好的图，可嵌子图、可被 Agent Server 托管；
    • 四段：装配（能力）、护栏（边界）、评测（方向）、上线（形态）；
    • 评测三判据：答对、带出处、该拒答；后两条必须自定义评估器；
    • 上线三必补：持久化、护栏、可观测；
    • 本地 langgraph dev，配置放 langgraph.json。

    九、思考题

    1、为什么评测集要单独维护，而不是写在代码注释里？

    参考回答：评测集是「效果的方向盘」：改提示、改切分、换模型都要跑同一套用例才有可比性。放在 LangSmith 的 dataset 里，团队可共享、可版本化、可增量补充；写死在代码里既难维护也无法回归历史。

    2、「该拒答」为什么必须单独做一条判据？

    参考回答：RAG 系统最危险的失败不是答错，而是「没有依据却答得像真的」。拒答率单独量化，才能发现模型在越界；混在「答对率」里会被正确答案淹没。

    3、护栏为什么不能只靠 system prompt？

    参考回答：system prompt 是建议，模型可以不听；中间件是代码层的强制路径——PII 会在请求进入模型前替换，HITL 会在工具执行前中断。凡是有真实后果的操作，都必须落在代码层。

    4、这套东西要接内部 IM，最少还要做什么？

    参考回答：把 thread_id 换成「用户 + 会话」的稳定标识、把 checkpointer 换成数据库版、把中断后的确认做成 IM 里的按钮回调，并接上 LANGSMITH_TRACING 观察线上失败样本。
