    LangChain 11 · 上下文工程：调什么、改什么、何时压

    📅 2026-12-09

    11 上下文工程：调什么、改什么、何时压

    Agent 不可靠，多数不是模型不够强，而是「该给的信息没给到」｜依据官方 Context engineering 页自绘

    版本不一致提示

    • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
    • 官方示例模型名（如 gpt-6.1-sol、claude-sonnet-4-6）随 provider 更新，request.override(...) 的用法不受影响；
    • 本篇涉及的部分能力（request.tools / request.model 的改写）以当前官方页面为准，1.0 早期版本字段可能更少。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 用官方那张「三类上下文」表说清：模型上下文、工具上下文、生命周期上下文各管什么，哪些是临时的、哪些会落进状态；
    2. 会写 wrap_model_call + request.override(...)，按状态 / 长期记忆 / 运行时配置动态改提示、改消息、改工具、改模型；
    3. 知道什么时候该裁剪（RemoveMessage + REMOVE_ALL_MESSAGES）、什么时候该摘要（SummarizationMiddleware），并说清两者的代价。

    二、前置知识

    • 读完 LC08（循环与 checkpointer）、LC09（内置中间件）、LC10（六个钩子）；
    • 知道 request.messages 是 request.state["messages"] 的快捷方式；
    • 手上有 InMemorySaver 能跑多轮。

    三、理论讲解（官方定义）

    1. 官方对「失败原因」的判断

    官方原文把 Agent 失败归成两条：模型能力不够，或者**「正确的上下文」没传给模型**——并明确说，更多时候是第二条。上下文工程（context engineering）的定义是：用正确的格式，在对的时机，提供对的信息与工具，这是 AI 工程师的头号工作。

    2. 三类上下文（官方表）

    上下文类型
    你控制什么
    临时 / 持久
    模型上下文（Model Context）
    每次模型调用里放什么：指令、消息历史、工具、响应格式
    临时
    工具上下文（Tool Context）
    工具能读到什么、能写回什么（state / store / runtime context）
    持久
    生命周期上下文（Life-cycle Context）
    模型与工具调用之间发生什么：摘要、护栏、日志
    持久

    3. 三个数据源

    数据源
    作用域
    典型内容
    运行时上下文（Runtime Context）
    会话级、静态配置
    user_id、密钥、数据库连接、权限、环境
    状态（State）
    会话级、短期记忆
    当前消息、上传文件、认证状态、工具结果
    存储（Store）
    跨会话、长期记忆
    用户偏好、抽取的画像、历史数据

    4. 五个可动的地方

    官方把「模型上下文」拆成五项，并强调它们都能从 state / store / runtime context 取值：System Prompt、Messages、Tools、Model、Response Format。

    • 改 System Prompt：@dynamic_prompt，按消息条数、用户偏好、权限、环境拼出不同指令；
    • 改 Messages：wrap_model_call 里 request.override(messages=...)，把上传文件摘要、写作风格、合规条款插到消息末尾（官方提示：模型更在意靠后的消息）；
    • 改 Tools：request.override(tools=...) 按认证状态、功能开关、角色过滤工具——工具太多会稀释注意力，太少则能力不够；
    • 改 Model：按对话长度换上下文更大的模型、按用户偏好换模型、按环境换；
    • 改 Response Format：按场景决定输出结构。

    5. 临时改动 vs 持久改动（官方明确区分）

    • 临时：wrap_model_call 里 request.override(...)，只影响这一次模型调用，不改状态；
    • 持久：从 wrap_model_call 返回 ExtendedModelResponse + Command，或用 before_model / after_model / wrap_tool_call 直接改状态。

    这条区分是关键：想「这一轮多说点背景」用临时；想「用户说了名字就记住」必须持久。

    四、原理拆解

    窗口是固定的，五项输入竞争同一个预算；裁剪与摘要的选择，本质是「决定丢什么」｜自绘

    两个必须记住的机制：

    1. RemoveMessage 要靠 add_messages 这个 reducer 生效。官方写法是返回 {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), *new_messages]}——先把整段清空、再把保留的消息塞回去；直接覆盖 state["messages"] 不会按 reducer 语义工作。
    2. 删消息要保结构合法。官方明确提醒：部分 provider 要求历史以 user 开头，绝大多数要求带 tool_calls 的 assistant 消息后面必须跟对应的 tool 结果——删的时候要对齐，不然请求直接 400。

    裁剪与摘要的取舍：裁剪零成本但丢信息，摘要多一次模型调用但保信息；官方把两者并列为 short-term memory 的常用策略，没有谁更优，取决于「丢掉的旧信息还有没有用」。

    五、场景说明

    1. 长对话客服：@dynamic_prompt 按消息条数加「请更简洁」，before_model 裁剪保留首条 + 最近几条；
    2. 多租户后台：context_schema 传 user_role，wrap_model_call 里按角色收窄工具集（viewer 只给 read_*）；
    3. 对外写作助手：从 store 读写作风格，拼成一段「你的语气 / 常用称呼 / 范文」插到消息末尾；
    4. 合规敏感行业：按用户司法辖区与行业注入合规约束，属于运行时配置，不进状态。

    六、示例代码

    💡 本篇示例跑 OpenAI，换 DeepSeek 只改三处：uv add langchain-deepseek、.env 里换成 DEEPSEEK_API_KEY、init_chat_model(..., model="deepseek-chat", model_provider="deepseek")。下面的代码除模型名与 provider 外一行不改；涉工具调用与结构化输出时用 deepseek-chat（官方集成页写明 deepseek-reasoner 不支持这两项），两家完整对照见 LC02 第六节。

    步骤 1：环境准备

    uv add "langchain[openai]" langgraph
# pip 等价：pip install -U "langchain[openai]" langgraph

    步骤 2：凭证配置

    同 LC01，OPENAI_API_KEY 放 .env。

    步骤 3：导入

    from dataclasses import dataclass
from typing import Any, Callable
from langchain.agents import create_agent
from langchain.agents.middleware import before_model, dynamic_prompt, wrap_model_call, AgentState, ModelRequest, ModelResponse
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langgraph.runtime import Runtime
from langchain.tools import tool

    步骤 4：最小可运行代码

    存成 context_demo.py，uv run context_demo.py。

    from dataclasses import dataclass
from typing import Any, Callable
from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.agents.middleware import before_model, dynamic_prompt, wrap_model_call, AgentState, ModelRequest, ModelResponse
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.runtime import Runtime

@dataclass
class Context:
    user_role: str

@dynamic_prompt
def role_prompt(request: ModelRequest) -> str:
    """按角色拼系统提示。"""
    role = request.runtime.context.user_role
    base = "你是企业助手，回答要给出依据。"
    return base + ("\n你是管理员，可以操作全部数据。" if role == "admin" else "\n你是只读用户，只能查询数据。")

@wrap_model_call
def viewer_readonly(request: ModelRequest, handler: Callable[[ModelRequest], ModelResponse]) -> ModelResponse:
    """只读用户只给读工具（临时改动，不改状态）。"""
    if request.runtime.context.user_role != "admin":
        request = request.override(tools=[t for t in request.tools if t.name.startswith("read_")])
    return handler(request)

@before_model
def trim_history(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    """超过 10 条就保留首条 + 最近 4 条。"""
    messages = state["messages"]
    if len(messages) <= 10:
        return None
    keep = [messages[0], *messages[-4:]]
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), *keep]}

@tool
def read_orders(status: str) -> str:
    """按状态查询订单，status 取 pending / shipped / delivered。"""
    return f"status={status} 的订单共 12 条"

load_dotenv()
agent = create_agent(
    model="openai:gpt-5-nano",
    tools=[read_orders],
    middleware=[role_prompt, viewer_readonly, trim_history],
    context_schema=Context,
    checkpointer=InMemorySaver(),
)
cfg = {"configurable": {"thread_id": "ctx-1"}}
for i in range(6):
    r = agent.invoke({"messages": [{"role": "user", "content": f"第{i}问：查一下 shipped 订单"}]},
                    config=cfg, context=Context(user_role="viewer"))
state = agent.get_state(cfg)
print("保留消息数:", len(state.values["messages"]))
print("最后回复:", r["messages"][-1].text[:40])

    步骤 5：预期输出

    保留消息数: 5
最后回复: status=shipped 的订单共 12 条

    消息数稳定在 5 条（首条 + 最近 4 条），说明 trim_history 每轮都在压，REMOVE_ALL_MESSAGES + RemoveMessage 的组合生效了。

    步骤 6：验证是否成功

    • 把 user_role 换成 admin 再跑一次，工具集不再被过滤（可加日志打印 request.tools 验证）；
    • 打印 system prompt 会看到管理员版多一句权限说明，说明 @dynamic_prompt 生效；
    • 只保留状态检查：get_state 里消息数不随时间增长，说明持久改动落在 checkpointer 里。

    七、常见坑（官方明确限制/版本差异）

    1. 删消息删出非法历史。带 tool_calls 的 assistant 消息必须保留对应 tool 结果，否则多数 provider 直接报错。
    2. 把临时改动当成持久改动。wrap_model_call 里 override(messages=...) 不会写进状态，下一轮就没了；要记住必须走 Command 或 node 型钩子。
    3. 工具全塞给模型。官方明确：工具过多会「淹没上下文」并增加出错率，该按角色/阶段收窄。
    4. 只压不看效果。裁剪会丢信息（官方示例里「删旧消息后模型就忘了用户名字」），关键事实要么落 store、要么在提示里留一条摘要。
    5. 用摘要替代裁剪处理工具结果。官方摘要只压文本消息，工具返回的大 JSON 建议先在工具里自己精简。

    八、课后小结

    • 失败多数源于「上下文没给对」，不是模型不行；
    • 三类上下文：模型（临时）、工具（持久）、生命周期（持久）；
    • 三个数据源：runtime context（静态配置）、state（会话内）、store（跨会话）；
    • 五项可动：system prompt、messages、tools、model、response format；
    • 临时用 override，持久用 Command；裁剪靠 RemoveMessage + reducer，摘要靠 SummarizationMiddleware。

    九、思考题

    1、为什么官方把「工具」也算作模型上下文的一部分？

    参考回答：工具定义是随请求一起发给模型的，占了 token、也影响模型选择动作的方式；换一套工具等于换了一套「能做什么」的上下文，所以它和提示、消息同属一次调用的输入。

    2、request.override(tools=...) 与「不加这个工具」有什么本质差别？

    参考回答：前者是运行时按条件收窄，同一份代码可以服务不同角色；后者是编译期固定，权限差异只能靠多套 Agent。官方把动态工具选择列为上下文工程手段，正是因为它按「当前会话」适配能力。

    3、为什么裁剪必须保留 tool_calls 与 tool 结果的配对？

    参考回答：消息历史是一份有结构的协议记录，不是纯文本；删掉结果只留调用，模型会以为工具没返回而重复调用，多数 provider 还会直接拒绝这种不合法历史。

    4、摘要与裁剪都能控长度，什么时候必须用摘要？

    参考回答：当被压掉的信息还会被追问（用户画像、已确认的结论、关键数字）时，裁剪等于把它永久遗忘；摘要把它转成一段文字保留下来，代价是多一次模型调用且细节会损失。
