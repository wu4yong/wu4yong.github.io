    LangChain 10 · 自定义中间件

    📅 2026-12-08

    10 自定义中间件

    node 型钩子顺序执行、wrap 型钩子嵌套执行；after_* 逆序回来｜依据官方 Custom middleware 页自绘

    版本不一致提示

    • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
    • 旧 0.x 没有中间件机制，对应能力分散在 AgentExecutor 的回调与自定义 Agent 里，v1 统一收敛到六个钩子；
    • 官方示例模型名随 provider 更新（如 gpt-6.1-sol），钩子签名不受影响。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 六个钩子各自「什么时候跑、能改什么、能返回什么」，一张表说清；
    2. 会写 node 型（返回 dict 改状态）与 wrap 型（决定 handler 调几次）两种中间件，装饰器与类两种写法都认得；
    3. 会用 jump_to 提前结束，并说清多中间件时的执行顺序：before_* 正序、after_* 逆序、wrap_* 嵌套。

    二、前置知识

    • 读完 LC08（循环）、LC09（内置件）；
    • 会写装饰器函数、知道 Callable 类型标注；
    • 理解 AgentState 就是一个带 messages 的字典。

    三、理论讲解（官方定义）

    1. 六个钩子的分工

    官方把钩子分两族：

    node 型（顺序执行在固定时点）：

    钩子
    何时跑
    before_agent
    Agent 开始前，每次调用一次
    before_model
    每次模型调用前
    after_model
    每次模型响应后
    after_agent
    Agent 结束后，每次调用一次

    wrap 型（包住调用）：

    钩子
    何时跑
    wrap_model_call
    包住每次模型调用
    wrap_tool_call
    包住每次工具调用

    官方对用途的定位也很直接：node 型适合日志、校验、改状态；wrap 型适合重试、缓存、改写请求——「你决定 handler 被调用零次（短路）、一次（正常）、多次（重试）」。

    2. node 型：返回 dict 就是改状态

    官方原文：node 型钩子直接返回 dict，dict 会按图的 reducer 合并进 Agent 状态。

    from langchain.agents.middleware import before_model, after_model, AgentState
from langchain.messages import AIMessage
from langgraph.runtime import Runtime
from typing import Any

@before_model(can_jump_to=["end"])
def check_message_limit(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    if len(state["messages"]) >= 50:
        return {"messages": [AIMessage("Conversation limit reached.")], "jump_to": "end"}
    return None

@after_model
def log_response(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    print(f"Model returned: {state['messages'][-1].content}")
    return None

    注意 @before_model(can_jump_to=["end"])：声明「允许跳到 end」之后，返回里的 jump_to 才生效。

    3. wrap 型：handler 调几次由你定

    from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
from typing import Callable

@wrap_model_call
def retry_model(request: ModelRequest, handler: Callable[[ModelRequest], ModelResponse]) -> ModelResponse:
    for attempt in range(3):
        try:
            return handler(request)
        except Exception as e:
            if attempt == 2:
                raise
            print(f"Retry {attempt + 1}/3 after error: {e}")

    wrap 型的签名固定是 (request, handler)；handler 收到的是「请求」，你可以在调用前 request.override(...) 改内容——官方给动态改 system prompt 的例子就是这么做的：

    new_system_message = SystemMessage(content=list(request.system_message.content_blocks) + [{"type": "text", "text": "Additional context."}])
return handler(request.override(system_message=new_system_message))

    4. wrap 型怎么改状态

    官方说明：node 型返回 dict 即可；wrap 型要改状态，模型侧返回 ExtendedModelResponse + Command，工具侧直接返回 Command。这比 node 型绕，所以能用 node 型改状态就别用 wrap 型。

    5. 执行顺序（多条中间件时）

    官方给的规则：

    • before_*：按注册顺序，从第一个到最后一个；
    • after_*：逆序，从最后一个到第一个；
    • wrap_*：嵌套，第一个中间件包住后面所有。

    一句话记法：进的时候排队进，出的时候倒着出，包裹的从外到内。这决定了「谁先看到原始请求」「谁最后收尾」。

    6. 提前结束：jump_to

    官方给的三个目标：

    jump_to
    跳到哪
    "end"
    直接结束（或第一个 after_agent）
    "tools"
    工具节点
    "model"
    模型节点（或第一个 before_model）

    使用前提是钩子声明了 can_jump_to（装饰器用 @hook_config(can_jump_to=["end"]) 或装饰器参数）。官方给的拦截例子：after_model 里发现回复含 BLOCKED，就返回一条固定话术并 jump_to="end"。

    7. 修饰符 @dynamic_prompt

    官方在「便利装饰器」里列了 @dynamic_prompt：按运行时信息生成系统提示，是「动态提示」这一最常见需求的快捷写法，等价于在 before_model 里改 system_message。

    四、原理拆解

    三条规则是同一个道理：中间件像洋葱，剥开从外到内，合上从内到外｜自绘

    用「进门安检」打比方：

    • before_agent / before_model 是进门前依次过的安检口，先注册的先检查；
    • wrap_model_call / wrap_tool_call 是「把你的材料拿去办」的那只手，它可以不办（短路）、办一次、办三次（重试）；
    • after_model / after_agent 是出来时按相反顺序回收，最后注册的最先响应。

    所以两个实践结论：

    1. 想拦在最前（比如输入校验、限流）→ 放列表第一位，用 before_model / wrap_model_call；
    2. 想最后收尾（比如统一日志、统一脱敏出口）→ 放列表最后，靠 after_* 逆序先跑拿到最终结果。

    五、场景说明

    1. 审计日志：after_model 打一行「这轮模型说了什么、用了多少 token」；
    2. 成本闸门：before_model 里数消息条数/ token，超阈值直接 jump_to="end"；
    3. 动态提示：wrap_model_call + request.override 注入用户画像、当前时间；
    4. 工具级重试：wrap_tool_call 里按异常类型重试（LC07 的写法），配 Command 改状态要谨慎。

    步骤 1：环境准备

    步骤 2：凭证配置

    同 LC01，OPENAI_API_KEY 放 .env。

    步骤 3：导入

    步骤 4：最小可运行代码

    存成 custom_middleware.py，uv run custom_middleware.py。

    from dotenv import load_dotenv
from typing import Any, Callable
from langchain.agents import create_agent
from langchain.agents.middleware import before_model, after_model, wrap_model_call, AgentState, ModelRequest, ModelResponse
from langchain.messages import AIMessage, SystemMessage
from langgraph.runtime import Runtime

@before_model(can_jump_to=["end"])
def message_budget(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    """消息太多就直接收口，防止无限循环。"""
    if len(state["messages"]) >= 12:
        return {"messages": [AIMessage("本轮对话过长，已为你截断。")], "jump_to": "end"}
    return None

@after_model
def audit(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    last = state["messages"][-1]
    print(f"[audit] 模型输出 {len(last.text)} 字，tool_calls={len(last.tool_calls)}")
    return None

@wrap_model_call
def inject_context(request: ModelRequest, handler: Callable[[ModelRequest], ModelResponse]) -> ModelResponse:
    """把一句运行时事实塞进 system prompt。"""
    blocks = list(request.system_message.content_blocks) + [{"type": "text", "text": "当前时间：2026-12-08。"}]
    return handler(request.override(system_message=SystemMessage(content=blocks)))

load_dotenv()
agent = create_agent(
    model="openai:gpt-5-nano",
    tools=[],
    system_prompt="你是简洁助手，回答不超过两句话。",
    middleware=[message_budget, inject_context, audit],
)
print(agent.invoke({"messages": [{"role": "user", "content": "现在几点？用一句话说。"}]})["messages"][-1].text)

    步骤 5：预期输出

    [audit] 模型输出 12 字，tool_calls=0
2026 年 12 月 8 日。

    [audit] 行说明 after_model 跑了；回答里带上日期，说明 wrap_model_call 改写的 system prompt 生效了。

    步骤 6：验证是否成功

    • 把用户消息改成一个会触发多步的请求（例如带工具），观察 tool_calls 数字变化，说明钩子能看到每轮模型输出；
    • 连发多轮把消息数堆到 12 条以上，看到「本轮对话过长」并立即结束，说明 jump_to="end" 生效；
    • 临时去掉 can_jump_to=["end"] 再跑，跳转会失效（用来确认声明是必需的）。

    差异集中在「模型怎么初始化」这一层，往下 invoke / stream / bind_tools 的链路基本不变：

    • 智谱、通义不进统一入口。init_chat_model 认不出 zhipuai / tongyi 这两个 provider 名，要直接实例化 ChatZhipuAI、ChatTongyi（两个类都在 langchain-community 里）；两家也都提供 OpenAI 兼容端点（智谱 https://open.bigmodel.cn/api/paas/v4、通义 https://dashscope.aliyuncs.com/compatible-mode/v1），用 ChatOpenAI(base_url=...) 也能打通，但 provider 专有字段可能不被提取或保留。
    • Claude 走统一入口，写法和 DeepSeek 一样是换个字符串；但要盯 max_tokens——官方迁移指南的 Breaking changes 里写了 langchain-anthropic 的默认值变化，结论是显式传，别依赖默认；logprobs 也不支持。
    • 通义的类默认走流式，ChatTongyi(model="qwen-plus") 之后拿到的就是流式结果；要做视觉用 qwen-vl-max。
    • 能力面各不同：工具调用、结构化输出、图像/音频输入的支持情况在这几家之间并不一致，换之前按各自官方集成页的能力表核一遍，别照抄 DeepSeek 的「一律 deepseek-chat」经验。

    七、常见坑（官方明确限制/版本差异）

    1. node 型返回 None 与返回 {} 的差别。都表示「不改状态」，但想表达「我处理过了」时不要返回假数据，否则会被当真合并。
    2. wrap 型忘记调 handler。等于短路，工具/模型不会执行；这是能力也是事故源，日志里要留痕。
    3. jump_to 没声明 can_jump_to。官方要求钩子先声明允许跳转，否则返回的 jump_to 不生效。
    4. 在 before_model 里做重试。node 型没有 handler，控制不了调用次数；重试必须用 wrap_model_call。
    5. 顺序放反。before_* 正序、after_* 逆序、wrap_* 嵌套；想「最后脱敏」却放在最前，就会先脱敏再加工，等于没脱。

    八、课后小结

    • 六个钩子：before_agent、before_model、after_model、after_agent、wrap_model_call、wrap_tool_call；
    • node 型返回 dict 改状态；wrap 型要改状态得用 ExtendedModelResponse + Command；
    • wrap 型由你决定 handler 调几次，是重试/短路/缓存的唯一正确位置；
    • 顺序：进正序、出逆序、包裹嵌套；
    • 提前结束用 jump_to，且钩子必须声明 can_jump_to。

    九、思考题

    1、什么需求必须用 wrap 型，node 型做不到？

    参考回答：需要控制「调用次数」的需求：重试、缓存命中短路、降级到备用模型、按预算决定调不调。node 型在时点上介入，没有 handler，无法决定调用几次。

    2、为什么 after_* 要逆序执行？

    参考回答：让中间件形成对称的「进—出」栈结构：后进的处理先收尾，保证「谁最后包住调用，谁最先看到结果」，与 wrap 型嵌套语义一致，避免收尾顺序与包裹顺序相反造成的逻辑错位。

    3、before_model 里数消息条数直接 jump_to="end"，和 ModelCallLimitMiddleware 有什么不同？

    参考回答：前者是你自定的业务规则（比如按消息条数、按内容敏感词），语义与文案完全可控；后者是官方通用上限，按调用次数计。两者可并存：官方件兜底，自定义件做业务口径。

    4、动态改 system prompt，用 @dynamic_prompt 还是 wrap_model_call + override？

    参考回答：只改提示、不需要控制调用次数，用 @dynamic_prompt 更简洁；还要顺带重试/缓存/短路，就用 wrap_model_call，一次包住所有逻辑。
