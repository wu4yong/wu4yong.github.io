    📅 2026-12-19

    06 人工介入：interrupt 与恢复

    恢复时节点从头重跑，interrupt() 之前的代码会再执行一遍｜依据官方 Interrupts · Rules of interrupts 自绘

    版本不一致提示

    • 本篇基线是 LangGraph 1.2.x + Python 3.13，示例不调用模型，纯本地可跑；
    • interrupt 暂停后必须用 checkpointer 才能恢复，官方示例统一用持久化后端，本篇用 InMemorySaver 演示；
    • response_schema（给人工输入做类型校验）需要 langgraph ≥ 1.2.12，本篇只提能力，不把它当主路径；
    • 官方明确：Command(resume=...) 是唯一「作为输入传给 invoke」的 Command；update / goto / graph 是用来从节点返回的。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 会用 interrupt(payload) 暂停、用 Command(resume=...) 恢复，并知道恢复必须同 thread_id；
    2. 记住「节点恢复时从头重跑」这条规则，能判断哪些代码放在 interrupt 前后；
    3. 会用「一节点一次 interrupt + 条件边回环」做输入校验，而不是写 while True。

    二、前置知识

    • 读完 LG05，会挂 checkpointer、知道 thread_id 是指针；
    • 知道 Command(goto=...) 能决定下一步（LG03）；
    • 知道 invoke(..., version="v2") 返回 GraphOutput，带 .value / .interrupts。

    三、理论讲解（官方定义）

    1. interrupt 是什么

    官方定义：在节点的任意位置调用 interrupt()，图就暂停，把传入的值交给调用方，然后用持久化层把状态存住，无限期等恢复。

    三个要素：

    • 动态断点：跟 interrupt_before/after 那种「编译期定死的静态断点」不同，interrupt() 可以按业务条件触发；
    • 状态落盘：靠 checkpointer；内存版重启就没了；
    • 恢复靠 thread：thread_id 就是游标，复用同一个才会接上。

    2. 恢复的机制

    decision = interrupt({"question": "批准吗？", "details": "..."})   # 返回值 = resume 传进来的东西

    恢复时：

    graph.invoke(Command(resume=True), config=cfg, version="v2")

    True 就成了 interrupt() 的返回值，节点继续往下走。

    官方给了三条硬规则：

    1. 恢复必须用同一个 thread_id；
    2. Command(resume=...) 的值可以是任何 JSON 可序列化对象；
    3. 节点会从头重跑——interrupt() 之前的代码再执行一遍。

    3. 为什么要「一节点一次」

    一个节点里可以调多次 interrupt()，但恢复时是按下标匹配 resume 值的：

    • 每次恢复都从节点开头重放；
    • 第 N 次恢复会把前 N−1 次 interrupt 全部重放一遍；
    • 如果两次执行之间 interrupt 的个数或顺序变了（条件跳过、循环里按数据长度调），下标就错位。

    所以官方给了标准姿势：一个节点只调一次 interrupt()，用条件边回环重问。

    4. 静态断点只用于调试

    compile(interrupt_before=["a"]) / interrupt_after=["b"] 能在节点前后停住，恢复用 invoke(None, config)。官方原话：不推荐用于人工介入流程，它是单步调试用的。

    四、原理拆解

    把 interrupt() 想成在流水线上按了暂停键，还顺手把当班进度拍了张照：

    • 暂停键按下时，运行时抛一个内部异常，把控制权交回调用方，同时把「当前检查点 + 待恢复的任务」写进 checkpointer；
    • 恢复不是「从暂停那一行继续」，而是「把这一整个工位重新做一遍」——机器重新启动，人在旁边把答案递进去；
    • 所以 interrupt() 之前的代码必须是可重复执行的（幂等）：查库、写库、发邮件的动作要么放 interrupt() 之后，要么自己保证重复执行不出事。

    三个关键判断：

    1. 暂停点越靠后越好：把贵操作放 interrupt() 之后，省得每次恢复都重算；
    2. 状态里要留「问题」：校验失败时把新问题写回 state，下一次进来读它，才能问出不一样的话；
    3. 恢复值不是输入：Command(resume=x) 只回答当前这个暂停点，不要拿它当「用户新一轮消息」续聊。

    五、场景说明

    1. 审批闸门：发邮件、扣款、写库前让人点一次确认；
    2. 改稿后放行：模型起草完，人改完内容再继续；
    3. 输入校验：年龄、金额这类必须合格的字段，不合格就重问；
    4. 工具调用前审核：把 tool_calls 摊给人看，允许改参数再执行。

    六、示例代码

    步骤 1：环境准备

    uv init lg06-interrupt
cd lg06-interrupt
uv add langgraph

    步骤 2：凭证配置

    无。审批流是纯状态机。

    步骤 3：导入

from typing_extensions import TypedDict

    步骤 4：最小可运行代码

    存成 approval_demo.py，uv run approval_demo.py。

    from typing import Literal, Optional
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command, interrupt

class State(TypedDict):
    action: str
    status: Optional[Literal["pending", "approved", "rejected"]]
    audit: list[str]

def draft(state: State):
    return {"status": "pending", "audit": [f"起草：{state['action']}"]}

def approval(state: State) -> Command[Literal["publish", "cancel"]]:
    # 一个节点只调一次 interrupt
    decision = interrupt({"question": "批准这个动作吗？", "details": state["action"]})
    return Command(goto="publish" if decision else "cancel")

def publish(state: State):
    return {"status": "approved", "audit": ["已发布"]}

def cancel(state: State):
    return {"status": "rejected", "audit": ["已取消"]}

builder = StateGraph(State)
builder.add_node("draft", draft)
builder.add_node("approval", approval)
builder.add_node("publish", publish)
builder.add_node("cancel", cancel)
builder.add_edge(START, "draft")
builder.add_edge("draft", "approval")
builder.add_edge("publish", END)
builder.add_edge("cancel", END)

graph = builder.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "approval-1"}}

run1 = graph.invoke({"action": "给客户发报价单", "audit": []}, cfg, version="v2")
print("第一次：", run1.value["status"], run1.interrupts)

run2 = graph.invoke(Command(resume=True), cfg, version="v2")
print("批准后：", run2.value["status"], run2.value["audit"])

    步骤 5：预期输出

    第一次： pending (Interrupt(value={'question': '批准这个动作吗？', 'details': '给客户发报价单'}, ...),)
批准后： approved ['起草：给客户发报价单', '已发布']

    第一次没有 .value["status"] 变 approved，只有 pending + 一个 interrupts 元组——图停住了；第二次 resume 传 True，approval 拿到 True 走 publish。

    步骤 6：验证是否成功

    • 把 Command(resume=True) 换成 Command(resume=False)：走到 cancel，status 是 rejected，说明恢复值真的决定了走向；
    • 去掉 checkpointer 再跑：第一次 invoke 直接报错（interrupt 需要持久化）；
    • 换一个 thread_id 去 resume：报「没有待恢复的任务」，因为那是另一条线；
    • 在 draft 里打印一行、在 approval 的 interrupt 前打印一行：第二次 resume 时两处都会再打印一次，这就是「从头重跑」。

    写法 A · 输入校验：一节点一次 + 条件边回环

    审批是「一次问完」，校验是「问到达标为止」。区别就在这个回环：

    class FormState(TypedDict):
    age: int | None
    pending_question: str | None

def collect_age(state: FormState):
    question = state.get("pending_question") or "请输入年龄"
    answer = interrupt(question)          # 每次进节点只调一次
    if isinstance(answer, int) and 0 < answer < 130:
        return {"age": answer, "pending_question": None}
    return {"pending_question": f"「{answer}」不是合法年龄，请重输"}

def route(state: FormState):
    return END if state.get("age") is not None else "collect_age"

builder = StateGraph(FormState)
builder.add_node("collect_age", collect_age)
builder.add_edge(START, "collect_age")
builder.add_conditional_edges("collect_age", route)
graph = builder.compile(checkpointer=InMemorySaver())

    为什么不能写成 while True: answer = interrupt(...)：恢复会重放整个节点，第 N 次恢复要重放前 N−1 轮提问，越用越慢，而且下标一对不上就串味。

    七、常见坑（官方明确限制/版本差异）

    1. while True 里反复 interrupt。每次恢复重放全部轮次，第一次恢复重放 1 遍、第二次 2 遍；官方明确要求改用条件边。
    2. 条件跳过 interrupt。同节点里 if 条件: interrupt(...)，两次执行个数不同 → 下标错位，恢复值张冠李戴。
    3. 在 interrupt() 前写外部副作用。恢复会重跑，重复建记录、重复发通知；要么放后面，要么幂等。
    4. 拿 Command(update=...) 当普通输入续聊。官方原话：只有 Command(resume=...) 适合当 invoke 的输入，其它参数是给节点返回用的。
    5. 恢复时换了 thread_id。恢复的不是同一条线，报错或行为诡异。
    6. 把静态断点当 HITL。interrupt_before/after 是调试单步用的，业务审批用 interrupt()。

    八、课后小结

    • interrupt(payload) 暂停并落检查点，Command(resume=x) 恢复，x 成为 interrupt() 的返回值；
    • 恢复必须同 thread_id；节点从头重跑，interrupt 前的代码要幂等；
    • 一个节点只调一次 interrupt，校验类需求用条件边回环；
    • 多个并行分支同时中断时，按 Interrupt.id 组一个 resume 映射一次交回去；
    • interrupt_before/after 只用于调试，不是人工介入方案。

    九、思考题

    1、为什么恢复后节点要「从头重跑」，而不是从 interrupt() 那一行继续？

    参考回答：运行时只能从检查点恢复「输入状态」，没有保存函数内部的栈帧；重跑整个节点是唯一确定性的复原方式。代价就是前面的副作用必须幂等。

    2、审批节点里能不能先写审计日志再 interrupt()？

    参考回答：不能。恢复会重跑，日志会重复。正确做法是把 interrupt() 放前面，批准后再写日志；或者写日志时用幂等键去重。

    3、Command(resume=True) 能不能直接当下一轮用户消息用？

    参考回答：不能。它只回答当前暂停点，不进 state 的 messages；要多轮对话请传普通输入 dict。

    4、并行两个节点都 interrupt() 了，怎么一次恢复？

    参考回答：读 result.interrupts 里每个 Interrupt 的 id，组 {id: 答案} 传给 Command(resume=映射)，一次调用把两个都答上。
