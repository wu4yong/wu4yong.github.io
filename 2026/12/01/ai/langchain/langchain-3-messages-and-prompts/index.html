    LangChain 03 · 消息与提示模板：content_blocks 与 trim_messages

    📅 2026-12-01

    03 消息与提示模板：content_blocks 与 trim_messages

    消息 = 角色 + 内容 + 元数据；v1 把内容统一成 content_blocks，跨 provider 一致｜依据 docs.langchain.com/oss/python/langchain/messages 自绘

    版本不一致提示

    • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方 Quickstart 的示例环境是 Python 3.11，仅解释器版本不同；
    • 旧 0.x 消息对象只有 content 一个字段、各家 provider 格式不一；v1 才把输出统一到 content_blocks；
    • 旧教程里「直接取 response.content 里的字符串」的写法属于版本差异，不是本篇写错。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 分清 SystemMessage、HumanMessage、AIMessage、ToolMessage 各自代表谁说的话，什么时候该用哪个；
    2. 会用 content_blocks 读模型输出，而不是在 response.content 里猜结构；
    3. 历史消息变长时，用 trim_messages 按 token 预算裁剪，而不是靠 [-10:] 硬切。

    二、前置知识

    • 第 01、02 篇已完成：能初始化模型并 invoke；
    • 知道「上下文窗口」的概念，知道超了会报错或截断。

    三、理论讲解（官方定义）

    骨架照官方 Messages 页：Basic usage（Text prompts / Message prompts / Dictionary format）→ Message types（System / Human / AI / Tool）→ Message content（Standard content blocks / Multimodal / Content block reference）。trim_messages 不在 Messages 页正文，但官方迁移指南的 Namespace 表把它列在 langchain.messages 之下，本篇作为「官方导出、实践常用」的能力单独一节。

    1. 消息是什么（官方原文直译）

    官方定义：消息是 LangChain 中模型上下文的基本单位，代表模型的输入与输出，既携带内容也携带元数据。一条消息包含三部分：

    • Role——标识消息类型（如 system、user）；
    • Content——实际内容（文本、图片、音频、文档等）；
    • Metadata——可选字段，如响应信息、消息 ID、token 用量。

    官方强调：LangChain 提供跨所有 provider 通用的标准消息类型，因此换模型时消息行为一致。

    2. 三种基本用法（官方 Messages「Basic usage」）

    Text prompts：直接传字符串，适合单次、无需保留历史的生成。

    response = model.invoke("Write a haiku about spring")

    Message prompts：传消息对象列表，适合多轮、多模态、需要系统指令。

    from langchain.messages import SystemMessage, HumanMessage, AIMessage

messages = [
    SystemMessage("You are a poetry expert"),
    HumanMessage("Write a haiku about spring"),
    AIMessage("Cherry blossoms bloom..."),
]
response = model.invoke(messages)

    Dictionary format：用 OpenAI chat completions 的字典格式。

    messages = [
    {"role": "system", "content": "You are a poetry expert"},
    {"role": "user", "content": "Write a haiku about spring"},
    {"role": "assistant", "content": "Cherry blossoms bloom..."},
]
response = model.invoke(messages)

    官方给了三条选择标准：单次独立请求用字符串；要管多轮、多模态、系统指令用消息对象；要跟 OpenAI 生态对齐用字典。

    3. 四种消息类型（官方 Messages「Message types」）

    类型
    代表
    导入路径
    典型用途
    SystemMessage
    初始指令，给模型定角色与规则
    langchain.messages
    设定人设、约束输出格式
    HumanMessage
    用户输入
    langchain.messages
    提问、上传图片/音频/文件
    AIMessage
    模型输出
    langchain.messages
    携带文本、工具调用、用量元数据
    ToolMessage
    工具执行结果
    langchain.messages
    把工具返回值回灌给模型

    版本备注：【v0.x 与 v1 一致，无迁移动作】。消息类型本身在 0.x 就是这套；v1 的变化在于统一导出到 langchain.messages（迁移指南 Namespace 表：消息类型与 content blocks 从 langchain-core 再导出）。

    4. HumanMessage 的文本与元数据（官方「Human message」「Text content」「Message metadata」）

    文本内容两种写法等价：

    # 消息对象
response = model.invoke([HumanMessage("What is machine learning?")])

# 字符串是单个 HumanMessage 的快捷方式
response = model.invoke("What is machine learning?")

    元数据可以带 name 与 id：

    human_msg = HumanMessage(
    content="Hello!",
    name="alice",   # 可选：区分不同用户
    id="msg_123",   # 可选：追踪用的唯一标识
)

    官方提醒：name 字段的行为因 provider 而异，有的用它做用户标识，有的直接忽略，需要查对应 provider 的文档。

    5. AIMessage 的属性（官方「AI message」）

    官方列出的属性：

    属性
    类型
    含义
    text
    string
    消息的文本内容
    content
    string | dict[]
    原始内容
    content_blocks
    ContentBlock[]
    标准化的内容块
    tool_calls
    dict[] | None
    模型发起的工具调用，未调用时为空
    id
    string
    消息唯一标识（LangChain 生成或 provider 返回）
    usage_metadata
    dict | None
    用量元数据，可用时含 token 计数
    response_metadata
    ResponseMetadata | None
    响应元数据

    官方还说明：有时需要手动构造 AIMessage 插进历史，让模型「以为」这句话是它说的（例如构造少样本示例）。

    6. 工具调用、用量与结束原因（官方「Tool calls」「Token usage」「Finish reason」）

    model_with_tools = model.bind_tools([get_weather])
response = model_with_tools.invoke("What's the weather in Paris?")

for tool_call in response.tool_calls:
    print(tool_call["name"], tool_call["args"], tool_call["id"])

    用量：

    response = model.invoke("Hello!")
response.usage_metadata
# {'input_tokens': 8, 'output_tokens': 304, 'total_tokens': 312,
#  'input_token_details': {...}, 'output_token_details': {...}}

    结束原因有个前置条件：官方写明该能力需要 langchain-core>=1.8.4 且集成负责映射（如 langchain-openai、langchain-anthropic、langchain-google-genai、langchain-aws 的相应版本）。response_metadata 里会出现三个键：

    键
    含义
    finish_reason
    provider 的原始值，如 Anthropic 的 end_turn、Gemini 的 MAX_TOKENS
    normalized_finish_reason
    归一化后的统一取值
    finish_state
    仅 Anthropic：complete，或需要续发请求时的 suspended

    归一化取值官方列了：stop、length、context_exceeded、tool_call、content_filter、refusal、error、other。工程上判断「是不是被截断」看 normalized_finish_reason == "length" 就够了。

    7. 标准化内容块 content_blocks（官方「Standard content blocks」）

    这是 v1 最该掌握的一处变化。官方迁移指南「Standard content」一节的说法是：v1 把不同 provider 各自的内容格式统一成标准块，读完 content_blocks 就不用再对着 content 里嵌套的 provider 私有字段做分支。

    常见块类型（官方 content block reference 列出，各 provider 支持程度不同）：

    type
    承载什么
    text
    纯文本
    reasoning
    推理过程（部分模型提供）
    tool_call
    完整的工具调用（含 id、name、args）
    tool_call_chunk
    流式过程中的工具调用片段
    image
    图片（多模态输入/输出）
    audio
    音频
    file
    文件
    refusal
    模型拒答（与 normalized_finish_reason=refusal 对应）

    版本备注：【旧版是把 provider 原始内容放在 content 里各写各的，v1 已改为提供标准化 content_blocks】。来源：LangChain v1 migration guide · Standard content。

    四、原理拆解

    provider 原始 content → 标准化 content_blocks → 业务代码只认 type｜自绘

    消息像快递面单，三栏必填：寄件人（role）、包裹内容（content）、面单信息（metadata）。

    content_blocks 的作用是「统一包装规格」。以前每家 provider 的包裹长得不一样：OpenAI 用 tool_calls、Anthropic 用 tool_use 块、Gemini 又是另一套字段，你写业务代码得先判断「这是谁家的包裹」。v1 之后，全部先拆成标准件：文本是 text 块、工具调用是 tool_call 块、图片是 image 块。你只按 block["type"] 分派，不用管 provider。

    五、场景说明

    1. 多轮客服：SystemMessage 定人设 + 历史 HumanMessage/AIMessage 交替 + 每轮追加新 HumanMessage；
    2. 多模态问答：HumanMessage 里放 image 块 + 文本块，同一个接口；
    3. 长会话控成本：历史超过预算时用 trim_messages 裁剪，保留 system 与最近若干轮；
    4. 工具闭环：AIMessage.tool_calls → 执行 → ToolMessage 回灌，这是第 05、08 篇的骨架。

    六、示例代码

    💡 本篇示例跑 OpenAI，换 DeepSeek 只改三处：uv add langchain-deepseek、.env 里换成 DEEPSEEK_API_KEY、init_chat_model(..., model="deepseek-chat", model_provider="deepseek")。下面的代码除模型名与 provider 外一行不改；涉工具调用与结构化输出时用 deepseek-chat（官方集成页写明 deepseek-reasoner 不支持这两项），两家完整对照见 LC02 第六节。

    步骤 1：环境准备

    同第 01 篇步骤 1；本篇只依赖 langchain 与 provider 包，无额外依赖：

    uv add "langchain[openai]"
# pip 等价：pip install -U "langchain[openai]"

    步骤 2：凭证配置

    同第 01 篇步骤 2，需要 OPENAI_API_KEY。

    步骤 3：导入

    from langchain.chat_models import init_chat_model            # 模型入口
from langchain.messages import (                            # v1 统一消息导出
    SystemMessage, HumanMessage, AIMessage, ToolMessage,
    trim_messages,
)
from langchain.messages import count_tokens_approximately    # 轻量 token 估算

    步骤 4：最小可运行代码

    存成 main.py，uv run main.py 执行（pip 方案：python main.py）。

    from langchain.chat_models import init_chat_model
from langchain.messages import SystemMessage, HumanMessage, AIMessage, trim_messages
from langchain.messages import count_tokens_approximately

model = init_chat_model("openai:gpt-5-nano")

history = [
    SystemMessage("你是一名数据库助教，回答控制在三句以内。"),
    HumanMessage("什么是覆盖索引？"),
    AIMessage("覆盖索引是指查询需要的列全部在索引里，不必回表。"),
    HumanMessage("那它一定更快吗？"),
]

# 1) 正常调用，读标准化内容块
response = model.invoke(history)
for block in response.content_blocks:
    print(block["type"], block.get("text"))

# 2) 历史太长时按 token 预算裁剪：保留 system + 最近的消息
trimmed = trim_messages(
    history,
    max_tokens=200,                 # 预算，按 token 算
    token_counter=count_tokens_approximately,  # 官方示例里常用的估算器
    strategy="last",                # 从最新往回留
    include_system=True,            # 系统消息一定要留
    start_on="human",               # 裁剪后必须以用户消息开头
)
print(len(history), "->", len(trimmed))

    步骤 5：预期输出

    text 覆盖索引不一定更快，取决于回表成本和索引选择性。
4 -> 3

    裁剪前后条数会因预算不同而变化，结构大致为：先打印内容块类型与文本，再打印「原条数 -> 裁剪后条数」。

    步骤 6：验证是否成功

    看到 content_blocks 打印出 text 类型的块、且裁剪后条数小于原条数、首条仍是 HumanMessage，就说明消息结构与裁剪都跑通了。

    七、常见坑（官方明确限制/版本差异）

    1. 还在用 response.content 猜结构。官方已提供 content_blocks，用 content 就要自己判 provider 私有格式，这正是 v1 想消灭的。
    2. name 字段以为通用。官方写明行为因 provider 而异，别把 name 当稳定标识，用 id 追踪更靠谱。
    3. 拿 finish_reason 判断截断。要跨 provider 判断，用 normalized_finish_reason == "length"；且该字段要求 langchain-core>=1.8.4 与集成支持，版本不够时字段就是空的。
    4. trim_messages 用 [-10:] 代替。按条数切不看 token，长消息一样爆窗；官方给的是按 token 预算裁。
    5. 裁剪后角色错位。裁完第一条变成 AIMessage 会引起部分 provider 报错或行为异常，用 start_on="human" 约束。

    本篇涉及 API 在 LangChain v1 迁移指南中的对应条目：Standard content（content_blocks 标准化）、Namespace（消息类型与 trim_messages 从 langchain-core 再导出）。trim_messages 的签名本身，官方迁移指南与 Release Notes 均未标注变更。

    八、课后小结

    • 消息三要素：role、content、metadata；
    • 四种角色：System / Human / AI / Tool，导入统一在 langchain.messages；
    • 读模型输出优先用 content_blocks，按 type 分派；
    • 判断截断看 normalized_finish_reason；
    • 长历史用 trim_messages 按 token 预算裁，并约束起点角色。

    九、思考题

    1、model.invoke("你好") 和 model.invoke([HumanMessage("你好")]) 有什么区别？

    参考回答：官方明确说字符串是「单个 HumanMessage 的快捷方式」，两者等价。区别只在需要附加 name、id 或混排多种角色时，必须用消息对象。

    2、为什么要用 content_blocks 而不是 content？

    参考回答：因为 content 保留 provider 的原始结构，各家字段不同；content_blocks 是 v1 标准化后的统一形状，按 type 分派即可跨 provider 复用业务逻辑。官方迁移指南把这列为 v1 的 Standard content 变更。

    3、trim_messages 里 include_system=True 不加会怎样？

    参考回答：系统消息会被当作普通历史一起裁掉，模型失去人设与规则约束，输出风格漂移。官方参数就是为「保留系统指令」设计的，长会话场景应当开启。

    4、一条 AIMessage 里会同时出现 text 和 tool_call 两种块吗？

    参考回答：会。模型可以先输出一句话再发起工具调用，此时 content_blocks 里既有 text 块也有 tool_call 块；判断「是否要执行工具」看 tool_calls 是否非空，而不是看文本有没有内容。
