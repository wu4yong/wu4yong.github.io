    📅 2026-05-03

    多线程共享变量与线程安全

    本章核心目标：解决多线程访问共享变量的线程安全问题，保证临界区代码执行的原子性，掌握synchronized、Lock锁、线程状态、活跃性问题、线程安全分析等核心知识点。

    本章知识体系：共享问题 → synchronized解决方案 → 线程安全分析 → Monitor与wait/notify → 线程状态转换 → 线程活跃性问题 → ReentrantLock锁

    3.1 多线程共享带来的安全问题

    共享带来的问题之故事篇

    ● 老王（操作系统）有一个功能强大的算盘（CPU），现在想把它租出去，赚一点外快

    ● 小南、小女（线程）来使用这个算盘来进行一些计算，并按照时间给老王支付费用 ● 但小南不能一天24小时使用算盘，他经常要小憩一会（sleep），又或是去吃饭上厕所（阻塞 io 操作），有时还需要一根烟，没烟时思路全无（wait）这些情况统称为（阻塞）
    ● 在这些时候，算盘没利用起来（不能收钱了），老王觉得有点不划算 ● 另外，小女也想用用算盘，如果总是小南占着算盘，让小女觉得不公平 ● 于是，老王灵机一动，想了个办法 [ 让他们每人用一会，轮流使用算盘 ] ● 这样，当小南阻塞的时候，算盘可以分给小女使用，不会浪费，反之亦然 ● 最近执行的计算比较复杂，需要存储一些中间结果，而学生们的脑容量（工作内存）不够，所以老王申请了一个笔记本（主存），把一些中间结果先记在本上 ● 计算流程是这样的
    ● 但是由于分时系统，有一天还是发生了事故 ● 小南刚读取了初始值 0 做了个 +1 运算，还没来得及写回结果 ● 老王说 [ 小南，你的时间到了，该别人了，记住结果走吧 ]，于是小南念叨着 [ 结果是1，结果是1...] 不甘心地到一边待着去了（上下文切换） ● 老王说 [ 小女，该你了 ]，小女看到了笔记本上还写着 0 做了一个 -1 运算，将结果 -1 写入笔记本 ● 这时小女的时间也用完了，老王又叫醒了小南：[小南，把你上次的题目算完吧]，小南将他脑海中的结果 1 写入了笔记本
    ● 小南和小女都觉得自己没做错，但笔记本里的结果是 1 而不是 0

    3.1.1 通俗场景理解

    操作系统（老王）的CPU（算盘）支持多线程分时复用，多个线程（小南、小女）轮流占用CPU执行任务。线程执行中会出现阻塞（sleep、IO、wait），此时CPU切换给其他线程，提升资源利用率。

    为存储计算中间结果，线程会读写主存中的共享变量，分时切换+共享读写会引发数据错乱问题：

    典型场景：小南读取变量0、执行+1未写回时，时间片用完发生上下文切换；小女读取变量0、执行-1并写回-1；后续小南恢复执行，将内存覆盖写为1，最终结果不符合预期。

    3.1.3 问题根源：非原子操作

    Java中静态变量的自增、自减并非单条指令，而是由多条JVM字节码组成，多线程下指令会交错执行，破坏原子性。

    3.1.4 核心概念定义

    1. 临界区（Critical Section）

    存在多线程对共享变量读写操作的代码块。仅多线程读共享资源无安全问题，读写共存才会触发风险。

    示例临界区代码：

    static int counter = 0;
// 临界区：存在共享变量读写
static void increment(){ counter++; }
static void decrement(){ counter--; }

    2. 竞态条件（Race Condition）

    多个线程在临界区执行，因线程执行序列随机交错，导致最终结果不可预测的现象，是线程安全问题的核心诱因。

    3.2 synchronized 互斥解决方案

    3.2.1 锁解决方案分类

    阻塞式方案：synchronized（内置锁）、Lock（显式锁），通过互斥阻塞保证原子性

    非阻塞式方案：原子变量（CAS实现，无阻塞）

    3.2.2 synchronized 核心原理

    俗称对象锁，JVM内置互斥锁机制：同一时刻仅一个线程持有锁执行临界区代码，其他线程获取锁失败则阻塞，彻底避免指令交错，保证临界区代码原子性。

    互斥与同步区别：

    互斥：保证临界区同一时刻单线程执行，解决竞态条件

    同步：控制线程执行顺序，让线程等待其他线程执行到指定节点

    3.2.3 基础语法与修复案例

    语法格式：

    synchronized(锁对象){
    // 临界区代码
}
    **修复共享变量错乱问题**： 
    static int counter = 0;
static final Object room = new Object(); // 唯一共享锁对象


    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 5000; i++) {
                synchronized (room) {
                    counter++;
                }
            }
        }, “t1”);
    

    Thread t2 = new Thread(() -> {
    for (int i = 0; i < 5000; i++) {
        synchronized (room) {
            counter--;
        }
    }
}, "t2");

t1.start();
t2.start();
t1.join();
t2.join();
log.debug("{}",counter); // 最终结果固定为0

    

    }

    你可以做这样的类比： ● synchronized(对象) 中的对象，可以想象为一个房间（room），有唯一入口（门）房间只能一次进入一人进行计算，线程 t1，t2 想象成两个人 ● 当线程 t1 执行到 synchronized(room) 时就好比 t1 进入了这个房间，并锁住了门拿走了钥匙，在门内执行count++ 代码 ● 这时候如果 t2 也运行到了 synchronized(room) 时，它发现门被锁住了，只能在门外等待，发生了上下文切换，阻塞住了 ● 这中间即使 t1 的 cpu 时间片不幸用完，被踢出了门外（不要错误理解为锁住了对象就能一直执行下去哦），这时门还是锁住的，t1 仍拿着钥匙，t2 线程还在阻塞状态进不来，只有下次轮到 t1 自己再次获得时间片时才能开门进入 ● 当 t1 执行完 synchronized{} 块内的代码，这时候才会从 obj 房间出来并解开门上的锁，唤醒 t2 线程把钥匙给他。t2 线程这时才可以进入 obj 房间，锁住了门拿上钥匙，执行它的 count-- 代码. 用图表示

    思考
    synchronized 实际是用对象锁保证了临界区内代码的原子性，临界区内的代码对外是不可分割的，不会被线程切换所打断。

    为了加深理解，请思考下面的问题
    ● 如果把 synchronized(obj) 放在 for 循环的外面，如何理解？– 原子性
    ● 如果 t1 synchronized(obj1) 而 t2 synchronized(obj2) 会怎样运作？– 锁对象
    ● 如果 t1 synchronized(obj) 而 t2 没有加会怎么样？如何理解？– 锁对象

    3.2.4 锁机制通俗类比

    锁对象=唯一房间，线程=使用者：

    1. 线程获取锁=进入房间、锁门拿钥匙，执行临界区代码

    2. 其他线程尝试获取同一锁=门外阻塞等待

    3. 线程时间片用完，锁不会释放，下次获取时间片继续执行

    4. 临界区代码执行完毕，自动释放锁，唤醒阻塞线程竞争锁

    3.2.5 进阶思考问题

    1. synchronized放for循环外：将5000次循环整体作为原子操作，并发度更低，安全性更高

    2. 两个线程使用不同锁对象：锁互不干扰，无法实现互斥，依然存在竞态条件

    3. 单线程加锁、另一线程不加锁：无互斥效果，未加锁线程可随意执行临界区，线程安全失效

    3.2.6 面向对象优化写法

    将共享变量和锁封装到工具类，通过this作为锁对象，封装性更强：

    class Room {
    int value = 0;
    // 实例方法锁this对象
    public void increment() {
        synchronized (this) { value++; }
    }
    public void decrement() {
        synchronized (this) { value--; }
    }
    public int get() {
        synchronized (this) { return value; }
    }
}

    3.3.1 方法锁等价关系

    3.4 变量线程安全深度分析

    3.4.1 成员变量/静态变量线程安全

    成员变量和静态变量是否线程安全？

    • 如果它们没有共享，则线程安全
    • 如果它们被共享了，根据它们的状态是否能够改变，又分两种情况
      • 如果只有读操作，则线程安全
      • 如果有读写操作，则这段代码是临界区，需要考虑线程安全

    局部变量是否线程安全？

    • 局部变量是线程安全的
    • 但局部变量引用的对象则未必
    • 如果该对象没有逃离方法的作用访问，它是线程安全的
    • 如果该对象逃离方法的作用范围，需要考虑线程安全

    小结：

    • 无共享：线程安全
    • 共享且仅读：线程安全
    • 共享且读写共存：存在临界区，线程不安全

    3.4.3 典型案例：集合线程安全问题

    不安全写法（成员变量集合）：多线程共享同一个ArrayList，add/remove交替执行，大概率报索引越界异常

    安全写法（局部变量集合）：每个线程创建独立ArrayList实例，无共享，彻底规避安全问题

    从这个例子可以看出 private 或 final 提供【安全】的意义所在，请体会开闭原则中的【闭】

    拓展：private、final修饰方法/变量，可防止子类重写、外部篡改，提升线程安全性（开闭原则之闭）

    小结：

    • 基本数据类型局部变量：线程安全，每个线程栈帧独立创建，无共享
    • 引用类型局部变量：
      • 未逃离方法作用域：线程安全
      • 逃离方法作用域（返回、赋值给全局变量、开启新线程操作）：线程不安全

    3.4.4 常见线程安全类

    String、Integer等不可变类、StringBuffer、Vector、Hashtable、JUC包下所有类

    这里说它们是线程安全的是指，多个线程调用它们同一个实例的某个方法时，是线程安全的。也可以理解为

    Hashtable table = new Hashtable();


    new Thread(()->{
        table.put(“key”, “value1”);
    }).start();
    

    new Thread(()->{
        table.put(“key”, “value2”);
    }).start();

    • 它们的每个方法是原子的
    • 但注意它们多个方法的组合不是原子的，见后面分析

    核心注意点：线程安全类的单一方法是原子的，但多个方法组合操作非原子，依然存在竞态条件

    示例：Hashtable先判断null再put，两步操作不原子，存在并发风险

    Hashtable table = new Hashtable();
// 线程1，线程2
if( table.get("key") == null) {
    table.put("key", value);
}

    3.4.5 不可变类线程安全原理

    String、Integer等类内部状态不可修改，所有修改操作都会返回新对象，原对象数据永久不变，天然线程安全。

    3.4.6 实战场景线程安全分析

    覆盖Servlet、切面、DAO层等常见业务场景，核心结论：全局共享可变变量不安全，局部变量、无状态对象安全，典型风险点：

    • Servlet全局可变成员变量：不安全

    • 切面全局计时变量：多线程共享篡改，不安全

    • DAO层全局Connection连接：共享争抢，不安全

    • 方法内临时创建的连接、集合：线程安全

    • 外星方法（抽象方法交由子类实现）：行为不可控，易引发线程安全问题

    3.5.1 问题现象

    多线程并发卖票，sell方法存在判断余量-扣减票数两步非原子操作，出现超卖、票数总和不一致问题。

    3.5.2 问题根源

    多个线程同时判断票数充足，全部进入扣减逻辑，超出剩余票数。

    3.5.3 优化方案

    给sell方法加synchronized锁，保证判断+扣减原子执行；同时sellCount需使用Vector（线程安全），不可用ArrayList（线程不安全）。
