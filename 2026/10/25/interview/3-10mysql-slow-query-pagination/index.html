3-10 MySQL 百万订单分页

📅 2026-10-25
MySQL 慢查询优化，百万订单分页筛选索引失效故障复盘

第 03-10 题　MySQL 慢查询优化，百万订单分页筛选索引失效故障复盘

候选人浅层回答： 给查询字段加索引、避免全表扫描，规范 SQL 写法就够用了。

核心拆解一句话结论

本题考察对底层原理和线上实战能力的综合理解，不能只停留在背结论。

连环追问

电商后台订单表百万数据，管理员筛选历史订单分页查询，接口频繁超时、页面加载缓慢；查询字段已经建好普通索引，但慢查询持续告警，数据库 CPU 居高不下，拖累其他业务。

  1. 索引明明建好了却没有生效，一般有哪些原因？怎么一步步定位？
  2. 能不能只靠加索引解决慢查询？如何从 SQL、索引、架构全链路根治慢查询？

一、索引建了但查询依然很慢 / 不走索引的常见原因

  1. 索引失效语法问题 隐式类型转换、where 条件对索引字段使用函数、运算、like 以 % 开头、or 两边字段一个有索引一个无索引，都会直接让索引失效。
  2. 联合索引不满足最左前缀原则 联合索引顺序设计不合理，查询没有命中最左字段，无法使用该联合索引。
  3. 优化器代价评估后主动放弃索引 过滤后返回结果集占比太高、索引区分度差、小表全表扫描更快、统计信息不准，优化器判定走索引代价更高，主动选择全表扫描。
  4. 回表开销巨大 普通二级索引只存主键，查询大量列、大量行时频繁回表，随机IO 过高，即使走索引，性能依旧很差。
  5. 分页深度问题（本案例高频坑） limit 100000,10 这种深分页，数据库要扫描前面十万行数据再丢弃，索引也救不了深分页。

二、慢查询排查闭环流程

  1. 抓告警与日志：开启慢查询日志，抓取慢 SQL，拿到 SQL 文本、执行耗时、扫描行数；
  2. explain 查看执行计划：看 type、key、rows、Extra，确认有没有走预期索引、有没有 Using filesort、Using temporary；
  3. 定位根因：区分是索引失效、回表、排序分组、深分页，还是锁等待、资源瓶颈；
  4. 针对性优化 SQL 和索引；
  5. 压测验证，持续监控慢查询。

三、三层优化体系（SQL 层 → 索引层 → 架构层）

第一层：SQL 语句优化（优先做，成本最低）

1. 杜绝 select *，只查询业务需要的字段；

2. 改写 like、函数、条件，避免索引字段做计算；

3. 优化分页：禁止大 offset 深分页，改用主键书签分页（id > 上一页最大 id limit

10）；

4. 减少不必要的 order by、group by，尽量利用索引有序性避免文件排序；

5. 拆分复杂大 SQL，避免单条 SQL 扫描海量数据。

第二层：索引精细化设计

  1. 根据查询条件、排序字段设计联合索引，遵守最左前缀；
  2. 优先建立覆盖索引，把 where、order by、select 字段都放进索引，消除回表；
  3. 低区分度字段不单独建索引；定期清理无用、低频冗余索引；
  4. 索引不是越多越好，索引会增加写入开销。

第三层：架构兜底优化（后台报表、海量历史查询场景）

  1. 读写分离：后台报表、历史统计查询走从库，不和线上主业务争抢资源；
  2. 数据冷热分离：历史订单归档到归档库 / 分表，活跃订单和几年前历史数据分开；
  3. 引入缓存：高频后台查询结果缓存，减少重复查询；
  4. 大数据量报表：同步到 Elasticsearch、数仓，检索、统计不在 MySQL 里面做；
  5. 限流：后台管理员查询增加查询限流，防止恶意 / 异常查询打爆数据库。

四、本案例（订单后台分页筛选）推荐落地方案

  • 筛选条件 + 排序字段构建联合覆盖索引，消除回表和 filesort；
  • 把 offset 分页改成书签分页；
  • 后台查询路由到从库；
  • 超久历史订单归档，减小主表数据体积；
  • 复杂多条件导出、统计查询放到 ES 或者数据仓库。

追问：本题考察核心是什么？

参考答案：初级开发的思维局限在 “慢了就加索引”，只会简单规避索引失效语法。高级工程师要有完整调优体系思维：

  1. 明白索引只是优化手段之一，不是万能解药；索引存在 ≠ 一定会被使用、一定会变快；
  2. 看得懂 explain 执行计划，能够区分索引失效、回表、文件排序、深分页等不同瓶颈；
  3. 能区分在线业务查询和后台报表查询，使用冷热分离、读写分离、搜索引擎等架构方案；
  4. 具备风险意识：后台管理系统的报表、分页查询，很容易成为数据库的隐形杀手，要做资源隔离和限流。

核心思想：MySQL 慢查询优化，是 SQL 写法、索引结构、数据生命周期、架构资源隔离一起配合的系统工程，而不是单一靠建索引
