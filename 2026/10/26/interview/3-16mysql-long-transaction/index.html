3-16 MySQL 长事务危害

📅 2026-10-26
线上长事务引发连接打满、死锁、CPU 高、主从延迟，完整应急、排查、根治方案

第 03-16 题　线上长事务引发连接打满、死锁、CPU 高、主从延迟，完整应急、排查、根治方案

候选人浅层回答： 背诵表面结论，没有深入到原理和线上场景。

核心拆解一句话结论

考察重点：不是简单 “删代码缩短事务”，而是应急止损 → 定位根因 → 针对性治理 → 长效防控整套闭环，同时处理衍生问题：行锁排队雪崩、主从延迟、undo 膨胀、跨服务事务困境。

一、第一步：故障应急止损（优先保障核心业务，几分钟内操作）

目标：先阻断雪崩，恢复核心接口，再慢慢定位，不能直接重启库。

  1. 限流熔断：对触发长事务的接口 / 定时任务降级、限流，隔离故障流量，防止继续抢占连接和锁；非核心统计、导出、后台任务直接暂停。
  2. kill 掉正在执行的长事务会话 通过 information_schema.innodb_trx找到长时间运行的事务 trx_id、trx_mysql_thread_id，执行 kill thread_id；

注意：kill 后事务会回滚，大事务回滚本身也很重，不要一次性批量 kill，分批操作。

4. 临时扩容数据库连接（如果还有余量），给核心业务预留连接；

5. 读写分离场景：临时把强一致查询切回主库，避免从库延迟导致业务读到旧数

3. 据引发逻辑错误。

二、第二步：根因排查（定位是哪类长事务）

核心查询：innodb_trx + show engine innodb status（锁等待、死锁日志）、慢日志、业务埋点。 常见几类根因：

  1. 事务内混入远程 RPC/HTTP 调用（最高频坑）：数据库 SQL 写完，事务不提交，等待外部接口返回；网络抖动就变成超长事务；
  2. 事务内大批量循环 DML，一次性更新上万行，单事务处理量太大；
  3. 事务内包含大查询，大表无索引扫描，SQL 执行耗时久，事务一直挂着；
  4. 代码 bug：异常分支没有提交 / 回滚，事务一直不关闭；
  5. 分布式事务场景：TCC/SAGA 协调器阻塞，分支事务不提交。

关键指标：事务持续时长、持有锁的行范围、undo 增长速率、binlog 提交间隔。

三、第三步：分场景根治方案（面试官追问重点）

场景 1：事务里面有远程调用 RPC / 第三方接口

  • 原则：事务里面绝对不要放远程调用 改造思路：
  1. 先提交本地 DB 事务，把「待调用外部服务」记录到本地任务表（任务状态：待执行）；
  2. 事务提交释放锁；
  3. 独立异步线程 / MQ 消费这条任务记录，发起远程调用；
  4. 调用成功更新任务状态；调用失败重试、死信告警；
  5. 配套幂等，防止重试重复调用第三方。

本质：把外部调用移出锁区间，数据库事务只做本地状态落盘。

场景 2：大批量数据更新，单事务处理太多行（批量 DML）不能一次性拆成无事务循环（容易中间宕机，数据半更新）。 方案：分批小事务

  • 分页分批，每一批只处理几百～几千条；每一批单独开启事务、提交、释放锁；
  • 业务允许的前提下，放到凌晨低峰执行；
  • 加合理分页条件（主键 id 分批，避免偏移量分页）；
  • 禁止一次性 update 全表、大范围无索引更新。

场景 3：事务内存在慢查询、大表扫描

6. 优先加索引，优化 SQL；

7. 如果是统计类只读查询，直接移出事务，丢到从库执行；

8. 报表统计不要和业务写逻辑放在同一个事务里；报表走离线数仓。

场景 4：主从延迟暴涨的配套处理

根源：大事务一次性生成大量 binlog，从库回放跟不上。 治理：

  1. 上面的分批小事务，打散 binlog；
  2. 业务侧做延迟感知：读取前判断从库延迟，延迟超过阈值，自动路由到主库；
  3. 核心强一致查询走主库，非实时展示类放从库；
  4. 避免大批量 DDL，DDL 本身也是重事务。

场景 5：undo 日志膨胀问题undo 不能手动清理，undo 只有当没有活跃事务需要这个快照时才回收。 根治手段就是消灭长事务；应急只能杀掉长事务等待 undo 回收； 长期：控制事务时长，不要长时间打开只读事务（很多框架自动开启只读事务，非常隐蔽）。

场景 6：跨服务分布式事务场景（不能拆本地事务）不能用数据库长事务跨节点锁等待。根据一致性容忍度选型：

  1. 强一致：TCC，把资源锁定放在 try 阶段，缩短锁定时间，不要长时间占用资源；
  2. 最终一致：SAGA，本地小事务 + 补偿逻辑，避免全局锁等待；
  3. 尽可能降低分布式事务范围，把非强一致逻辑剥离出去，走 MQ 异步。

场景 7：业务链路特殊，业务上暂时无法拆分事务兜底方案（不推荐长期使用，只是临时手段）：

  1. 缩小锁范围：精确更新，避免范围锁、间隙锁；索引必须到位，减少锁覆盖行数；
  2. 隔离流量：把这个链路单独压控，低峰期执行；
  3. 锁超时设置合理，避免无限等待；
  4. 业务层面做补偿对账，兜底异常。

死锁配套优化统一所有 SQL 加锁顺序，避免循环等待； 尽量按主键顺序更新；减少同一个事务内多表交叉更新。

四、三层核心逻辑（面试官想要的三层框架）

第一层：编码与规范层（事前预防）

  1. 规约：事务内部禁止 RPC、HTTP、大查询、耗时逻辑；事务尽量短小，“快开快关”；
  2. 框架层面禁止隐式长只读事务（很多 ORM 自动开启事务）；
  3. 代码评审、SQL 审核环节拦截超大事务、事务内远程调用。

第二层：监控告警与熔断层（事中感知止损）监控指标：

  • 活跃事务时长 TOP、锁等待时间、死锁次数、undo 占用、主从延迟、binlog提交间隔；
  • 设置告警：事务超过阈值（比如 3s/5s）告警；
  • 限流熔断：识别长事务流量，自动降级。

第三层：对账补偿兜底层（事后兜底）即使做了拆分、异步化，依然存在极端故障。 定时对账任务，校验跨服务、跨表数据一致性，发现不一致自动告警、触发补偿逻辑。

五、初级 vs 高级工程师区别

初级：只想到精简代码、拆分事务，回答很笼统，回答不了衍生问题：undo 膨胀、主从延迟、RPC 在事务里怎么办、不能拆分的时候怎么办。 高级：

  1. 先应急止损，知道 kill 会话的风险（回滚开销），不是上来改代码；
  2. 区分不同类型长事务的改造方案，清楚 RPC 在事务内是头号杀手；
  3. 理解 MVCC、undo、binlog、主从延迟之间的联动关系；
  4. 有完整工程化体系：规范、SQL 审核、监控、限流、灰度改造，而不是单次修复。
