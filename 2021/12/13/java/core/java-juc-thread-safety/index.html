    Java JUC 线程安全

    📅 2021-12-13

    多线程共享变量与线程安全

    本章核心目标：解决多线程访问共享变量的线程安全问题，保证临界区代码执行的原子性，掌握synchronized、Lock锁、线程状态、活跃性问题、线程安全分析等核心知识点。

    本章知识体系：共享问题 → synchronized解决方案 → 线程安全分析 → Monitor与wait/notify → 线程状态转换 → 线程活跃性问题 → ReentrantLock锁

    3.1 多线程共享带来的安全问题

    共享带来的问题之故事篇

    ● 老王（操作系统）有一个功能强大的算盘（CPU），现在想把它租出去，赚一点外快

    ● 小南、小女（线程）来使用这个算盘来进行一些计算，并按照时间给老王支付费用
    ● 但小南不能一天24小时使用算盘，他经常要小憩一会（sleep），又或是去吃饭上厕所（阻塞 io 操作），有时还需要一根烟，没烟时思路全无（wait）这些情况统称为（阻塞）

    ● 在这些时候，算盘没利用起来（不能收钱了），老王觉得有点不划算
    ● 另外，小女也想用用算盘，如果总是小南占着算盘，让小女觉得不公平
    ● 于是，老王灵机一动，想了个办法 [ 让他们每人用一会，轮流使用算盘 ]
    ● 这样，当小南阻塞的时候，算盘可以分给小女使用，不会浪费，反之亦然
    ● 最近执行的计算比较复杂，需要存储一些中间结果，而学生们的脑容量（工作内存）不够，所以老王申请了一个笔记本（主存），把一些中间结果先记在本上
    ● 计算流程是这样的

    ● 但是由于分时系统，有一天还是发生了事故
    ● 小南刚读取了初始值 0 做了个 +1 运算，还没来得及写回结果
    ● 老王说 [ 小南，你的时间到了，该别人了，记住结果走吧 ]，于是小南念叨着 [ 结果是1，结果是1…] 不甘心地到一边待着去了（上下文切换）
    ● 老王说 [ 小女，该你了 ]，小女看到了笔记本上还写着 0 做了一个 -1 运算，将结果 -1 写入笔记本
    ● 这时小女的时间也用完了，老王又叫醒了小南：[小南，把你上次的题目算完吧]，小南将他脑海中的结果 1 写入了笔记本

    ● 小南和小女都觉得自己没做错，但笔记本里的结果是 1 而不是 0

    3.1.1 通俗场景理解

    操作系统（老王）的CPU（算盘）支持多线程分时复用，多个线程（小南、小女）轮流占用CPU执行任务。线程执行中会出现阻塞（sleep、IO、wait），此时CPU切换给其他线程，提升资源利用率。

    为存储计算中间结果，线程会读写主存中的共享变量，分时切换+共享读写会引发数据错乱问题：

    典型场景：小南读取变量0、执行+1未写回时，时间片用完发生上下文切换；小女读取变量0、执行-1并写回-1；后续小南恢复执行，将内存覆盖写为1，最终结果不符合预期。

    3.1.2 Java代码复现问题

    两个线程分别对静态变量自增、自减5000次，最终结果大概率不为0：

    static int counter = 0;
public static void main(String[] args) throws InterruptedException {
    Thread t1 = new Thread(() -> {
        for (int i = 0; i < 5000; i++) {
            counter++;
        }
    }, "t1");

    Thread t2 = new Thread(() -> {
        for (int i = 0; i < 5000; i++) {
            counter--;
        }
    }, "t2");

    t1.start();
    t2.start();
    t1.join();
    t2.join();

    log.debug("{}",counter);

    3.1.4 核心概念定义

    1. 临界区（Critical Section）

    存在多线程对共享变量读写操作的代码块。仅多线程读共享资源无安全问题，读写共存才会触发风险。

    示例临界区代码：

    static int counter = 0;
// 临界区：存在共享变量读写
static void increment(){ counter++; }
static void decrement(){ counter--; }

    2. 竞态条件（Race Condition）

    多个线程在临界区执行，因线程执行序列随机交错，导致最终结果不可预测的现象，是线程安全问题的核心诱因。

    3.2 synchronized 互斥解决方案

    3.2.1 锁解决方案分类

    阻塞式方案：synchronized（内置锁）、Lock（显式锁），通过互斥阻塞保证原子性

    非阻塞式方案：原子变量（CAS实现，无阻塞）

    3.2.2 synchronized 核心原理

    俗称对象锁，JVM内置互斥锁机制：同一时刻仅一个线程持有锁执行临界区代码，其他线程获取锁失败则阻塞，彻底避免指令交错，保证临界区代码原子性。

    互斥与同步区别：

    互斥：保证临界区同一时刻单线程执行，解决竞态条件

    同步：控制线程执行顺序，让线程等待其他线程执行到指定节点

    3.2.4 锁机制通俗类比

    锁对象=唯一房间，线程=使用者：

    1. 线程获取锁=进入房间、锁门拿钥匙，执行临界区代码

    3.4 变量线程安全深度分析

    3.4.1 成员变量/静态变量线程安全

    成员变量和静态变量是否线程安全？

    • 如果它们没有共享，则线程安全
    • 如果它们被共享了，根据它们的状态是否能够改变，又分两种情况
      • 如果只有读操作，则线程安全
      • 如果有读写操作，则这段代码是临界区，需要考虑线程安全

    局部变量是否线程安全？

    • 局部变量是线程安全的
    • 但局部变量引用的对象则未必
    • 如果该对象没有逃离方法的作用访问，它是线程安全的
    • 如果该对象逃离方法的作用范围，需要考虑线程安全

    小结：

    • 无共享：线程安全
    • 共享且仅读：线程安全
    • 共享且读写共存：存在临界区，线程不安全

    3.5.1 问题现象

    多线程并发卖票，sell方法存在判断余量-扣减票数两步非原子操作，出现超卖、票数总和不一致问题。

    3.5.2 问题根源

    多个线程同时判断票数充足，全部进入扣减逻辑，超出剩余票数。

    3.5.3 优化方案

    给sell方法加synchronized锁，保证判断+扣减原子执行；同时sellCount需使用Vector（线程安全），不可用ArrayList（线程不安全）。

    3.6 常见坑

    ● 加锁对象不一致：锁的是不同实例，等于没锁；多实例场景要用静态锁或类级别锁；
    ● 锁可变对象：String、Integer 等不可变对象每次拼接/装箱都产生新对象，锁的是新地址，互斥直接失效；
    ● 只加读或只加写：临界区读写不齐，加锁只是降低概率，可见性还得靠同一把锁或 volatile；
    ● 局部变量逃逸后仍当线程安全：被 return、被存进共享集合、被 lambda 捕获之后就不再线程私有；
    ● 线程安全类拼起来用：ConcurrentHashMap 单次操作安全，”先 get 再 put”这种组合仍是竞态，要用原子方法或外部加锁。
