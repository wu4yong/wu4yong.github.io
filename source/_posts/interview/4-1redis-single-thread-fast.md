## 第 04-1 题　Redis 是单线程，性能却很高，可达十万级 QPS，如何理解？

**候选人浅层回答：** Redis 是内存数据库，内存读写远快于磁盘；性能瓶颈不在CPU，而在内存和网络。

## 核心拆解一句话结论

本题考察对底层原理和线上实战能力的综合理解，不能只停留在背结论。

## 连环追问

1. 既然内存读写很快，为什么不直接改成多线程，利用多核 CPU，4 核机器 QPS理论翻 4 倍？
2. 上下文切换代价真的大到要放弃多核吗？如果单线程这么强，为什么所有高性能服务不全用单线程？
3. Redis6.0 为什么又引入多线程？

## 一、Redis 单线程高性能的完整原因

1. 全部数据放内存，内存访问速度远高于磁盘，不存在磁盘 IO 等待，这是基础。
2. IO 多路复用（epoll）+ 非阻塞 IO。单线程可以监听数万 socket 连接，只在网络事件就绪的时候处理。大部分连接处于空闲等待网络包的状态，不是占用 CPU。
3. 命令执行单线程串行：所有命令在主线程串行执行，内部复杂数据结构（dict、zset）不需要加锁，避免锁竞争、死锁的开发与运行开销。

重点澄清误区：这里的 “单线程”，指执行命令的主线程是单线程；Redis 内部还有独立子进程 / 线程做 RDB、AOF 刷盘等后台任务，并不是整个 Redis 只有一个线程。

1. Redis 命令本身大多是简单 O (1)/O (logN) 操作，CPU 计算并不是瓶颈，瓶颈通常是网络 IO。 网络收包、解析协议、回包，才是大量耗时操作，而不是内存读写。

## 二、为什么早期 Redis 没有把命令执行改成多线程？

不是上下文切换开销大到不能用多核，而是收益很低，代价巨大：

- 如果命令执行改成多线程，同一个 key 会被多个线程并发读写。Redis 大量复杂数据结构都需要加锁保护。锁竞争、死锁、调试难度上升，开发维护成本暴涨。
- 本来瓶颈是网络 IO，不是 CPU；就算把命令执行并行，CPU 不是瓶颈，整体QPS 提升很小。
- 不是所有系统都适合单线程：如果业务是 CPU 密集，或者大量阻塞 IO（数据库调用），单线程会直接卡住，所以不能全部服务都做成单线程。

一句话：早期 Redis 的瓶颈在网络，不在 CPU，为了多线程加锁带来的复杂度，得不偿失。

## 三、Redis6.0 引入多线程的真相

Redis6 多线程，只是多线程处理网络 IO；命令执行仍然是单线程串行执行！

- 工作：主线程接收连接，把 socket 读、协议解析、写回响应包交给 IO 线程池并行处理；
- 核心：解析完的命令，仍然交给主线程串行执行；读写 hash、zset 等数据结构依旧不用锁。
- 目的：多核机器下，网络包的读取、协议解析、写回这些 IO 密集工作分到多个 CPU 核心，解决网络 IO 成为瓶颈的场景。
- 限制：不会把命令执行并行，保留原来无锁、简单安全的模型。

所以：开 4 个 IO 线程不能让 QPS 直接翻 4 倍，只有网络 IO饱和场景才有明显提升；CPU 饱和场景提升很小。

<strong>追问：</strong>本题考察核心是什么？

<strong>参考答案：</strong> 初级开发只会记住 “内存快 + 避免上下文切换”。高级工程师要理解：

1. 分清：命令执行单线程 ≠ Redis 整个进程只有一个线程；
2. 性能瓶颈判断：早期瓶颈大多是网络 IO，不是 CPU，这是不做命令多线程的根本原因，而不是单纯怕上下文切换；
3. Redis6 多线程只是IO 多线程，命令执行依旧串行，没有破坏原有无锁安全模型；
4. 架构取舍思维：模型好坏看瓶颈，不是单线程一定强，多线程一定更快。

<strong>核心思想：</strong>单线程是为了简化并发控制，规避锁；Redis6 多线程只是把网络收发卸载到多核，核心数据操作依然串行。

###  高级工程师要分清：
