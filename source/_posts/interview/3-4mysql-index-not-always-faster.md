## 第 03-4 题　MySQL 加了索引，查询就一定更快吗？

**候选人浅层回答：** 索引是用来加速查询的 B + 树结构，给查询字段建立索引，SQL 就能跑得更快。

## 核心拆解一句话结论

本题考察对底层原理和线上实战能力的综合理解，不能只停留在背结论。

## 连环追问

1. 既然索引是提升检索效率的，那为什么有时候加了索引之后，SQL 反而跑得更慢？
2. 那我建区分度很高的索引，执行计划也明确命中索引，是不是就一定没问题？

## 一、索引本质

索引是数据库空间换时间的数据结构，核心目的是减少扫描行数。 InnoDB 使用 B + 树组织索引；创建索引，数据库就要额外维护一棵有序 B + 树。查询时可以沿着树快速定位，避免全表逐行扫描。 代价：占用磁盘空间；新增、修改、删除数据时，需要同步更新索引树，增加写操作开销。 重点：索引只是给优化器多了一个可选的执行路径，不等于一定会提升性能。

## 二、加索引反而变慢的典型场景

1. 表数据量很小 几百行以内的小表，顺序全表扫描本身极快。走二级索引还要先扫描索引树，再回表读取行数据，两次 IO，开销反而高于顺序扫描。优化器甚至可能主动放弃索引。
2. 索引字段区分度很低（选择性差） 例如状态、性别这类枚举字段，大量行的值相同。如果查询条件过滤后返回大量数据，走索引依然要读取大量索引页，并且大量回表；随机 IO 远大于全表扫描的顺序 IO，性能更差。
3. 回表成本过高 二级索引叶子节点只存聚集索引主键 id，查到 id 后还要回主键索引拿全部字段。当查询返回结果集很大，大量回表，随机 IO 暴涨，速度不如直接全表扫描。覆盖索引可以解决这个问题，避免回表。
4. 优化器统计信息不准，选错执行计划 统计信息没有及时更新，优化器误判行数，错误选择索引；测试环境正常，线上数据分布倾斜后，执行计划漂移，索引带来负收益。
5. 索引本身维护开销拖累写入 大量冗余索引，读可能微涨，但插入、更新、删除变慢；高写入业务，盲目加索引会拖垮整体吞吐。

## 三、就算命中索引，依然可能慢的原因

1. 没有做成覆盖索引，大量回表；
2. 范围查询过大，索引过滤后结果集占比很高；
3. 索引字段上做函数运算、隐式类型转换，索引失效；
4. 联合索引不满足最左前缀，索引利用率低；
5. 索引页不在缓冲池，大量磁盘冷 IO。

## 四、索引设计正确思路

1\. 优先评估索引收益：过滤后返回行数占比很低，索引才有价值；

2\. 优先使用覆盖索引，消除回表；

3\. 优先给高区分度、高频过滤字段建索引；低区分度字段不要单独建索引；

4\. 定期检查索引利用率，清理低频、无效冗余索引；

5\. 不能只看 explain 有没有走索引，还要评估回表开销、IO 类型（顺序 IO / 随

6\. 机 IO）；

6\. 读写权衡：写入压力大的表，索引数量要收敛。

<strong>追问：</strong>本题考察核心是什么？

<strong>参考答案：</strong>初级开发固化思维，认为索引 = 提速，只会背 B + 树、最左前缀。

高级工程师要理解：

1. 索引是有成本的，收益是有前提条件的，不是万能优化手段；
2. 明白 InnoDB 二级索引的回表机制，区分顺序 IO 和随机 IO 的性能差异；
3. 理解优化器的选择逻辑：走不走索引，是优化器基于代价估算做出的选择；
4. 会判断索引什么时候正收益、什么时候负收益，不是慢 SQL 就无脑加索引；
5. 建立代价思维：查询收益、磁盘空间、写入开销、回表成本综合评估。

<strong>核心思想：</strong>索引只是一种查询备选路径，能不能变快，取决于过滤比例、区分度、是否回表、数据量、IO 模型，而不是只要建了索引就一定更快。
