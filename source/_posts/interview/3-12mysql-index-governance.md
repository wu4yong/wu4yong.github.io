## 第 03-12 题　慢 SQL、索引治理，不能无脑建索引

**候选人浅层回答：** 给查询字段加上索引，避免全表扫描，提升 SQL 执行效率。

## 核心拆解一句话结论

本题考察对底层原理和线上实战能力的综合理解，不能只停留在背结论。

## 连环追问

1. 如何从 SQL 编写、索引设计、架构层面完整治理慢查询？
2. 能不能遇到查询慢，就无脑给所有查询字段建立索引？

## 一、事故根因

只给单独字段建立普通单列索引，而业务是多字段联合查询。

1\. 单列索引各自独立，MySQL 一次 SQL 一般只能选用其中一个单列索引，剩下条件只能过滤回表；回表量大，SQL 依旧慢。

2\. 多条件查询，优化器会评估各个单列索引成本，统计信息波动，会出现索引选择摇摆，时而走索引、时而全表扫描，造成索引失效反复复现。

3\. 不能无脑给全部字段建索引：索引不是越多越好。

1\. 索引占用磁盘存储空间；

2\. DML（insert/update/delete）需要维护全部索引，索引越多，写入性能越差，订单大促写入压力大，过多索引会拖垮订单入库、支付更新；

3\. 大量索引会增加优化器选择执行计划的开销。

幽灵陷阱：很多人遇到慢查询，直接给 where 条件每一个字段单独建索引，以为问题解决，实际联合查询场景依旧性能很差，故障反复发生。

## 二、完整治理方案：SQL 编写、索引设计、架构三层防御

1. SQL 编码层面

1\. 杜绝select \*，只查询业务需要字段，尽量使用覆盖索引减少回表；

2\. 联合查询遵循最左前缀原则，等值条件放前面，范围条件放后面；

3\. 避免索引列做函数运算、隐式类型转换、like 前缀 % 等索引失效写法；

4\. 控制分页，避免大 offset 分页；大结果集不要一次性查询全部，分批处理；

5\. 业务层面限制查询条件，禁止无边界的全量筛选，例如时间范围强制限制最大查询区间。

2. 索引设计层面

1\. 多条件联合查询优先创建联合索引，而不是一堆单列索引；根据业务查询频率设计联合索引顺序；

2\. 评估索引收益：查询收益 vs 写入损耗。大促订单这类写入压力很高的表，严格控制索引数量；

3\. 索引字段要具备高区分度，低区分度字段（status 状态）不适合单独建索引；

4\. 定期analyze table 更新表统计信息，防止 MySQL 优化器选错索引；

5\. 上线前使用生产量级仿真数据做 explain 执行计划校验，小测试环境执行计划不能代表线上。

3. 架构层面（兜底，防止慢 SQL 拖垮核心业务）

1\. 读写分离：订单筛选这类查询压力，全部丢到从库执行，主库只承担订单写入、支付更新核心链路；

2\. 热点查询增加缓存，避免频繁查询数据库；

3\. 复杂多条件订单筛选，不要强压 MySQL；统计、筛选类业务迁移到 ES 搜索引擎；

4\. 业务增加防护：SQL 执行超时时间，接口增加限流，防止大量慢 SQL 打满数据库；

5\. 监控告警：慢查询日志、CPU、连接数监控，慢 SQL 及时发现。

## 三、线上故障应急处理

1. 故障爆发 CPU 打满：优先限流、降级筛选接口，把流量压下去，保护订单支付写入核心链路；
2. 不要在高峰期随意新增索引，大表 DDL 会锁表，加剧故障；索引优化选业务低峰变更；
3. 排查 explain 确认执行计划，判断是索引设计不合理还是 SQL 写法问题。

<strong>追问：</strong>本题考察核心是什么？

<strong>参考答案：</strong> 考察能不能跳出 “慢查询就加索引” 的固化思维。 很多开发只知道索引可以加速查询，忽略索引对写入的代价；分不清单列索引和联合索引适用场景。 高级后端要权衡查询收益与写入损耗，不能无脑堆索引；需要从 SQL 编码、索引设计、存储架构整套体系解决慢查询，而不是只靠新增索引这一招。同时区分核心写入链路和查询链路，通过读写分离、搜索引擎做架构隔离，避免分析类查询拖垮核心交易
