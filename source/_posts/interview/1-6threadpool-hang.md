## 第 1-6 题　线程池线程集体卡住、队列堆满、CPU/DB 压力正常，服务假死，只能重启恢复

**候选人浅层回答：** 流量超预期了，加大线程池参数。

## 核心拆解一句话结论
这类故障的根因不是「线程不够」，而是**线程被永久阻塞、无法归还**：CPU 不高、数据库空闲、线程数量充足，但线程全部处于 WAITING/BLOCKED，任务不推进、队列持续堆积。调大线程数与队列只会让卡死的线程更多、推迟雪崩时间。真正的解法是「所有阻塞点强制超时 + 资源池隔离 + 任务生命周期管控与熔断」。

## 场景描述
线程池参数按最佳实践配置、压测通过；大促流量在预估范围内、任务逻辑简单，但线程池线程全部卡住、队列打满、服务超时假死。

## 根因分析（线上高频四类）

这类现象的典型特征：CPU 不高、数据库空闲、线程数量充足，但线程全部处于 WAITING/BLOCKED 状态，不推进任务，队列持续堆积。常见根因分几类：

1. **任务内部存在无超时的同步阻塞调用**
   - 第三方 RPC、HTTP 接口、Redis / 中间件调用、锁获取，没有设置超时。远端服务僵住、连接挂死，线程就永久卡在等待，不会抛出异常、不会主动释放。压测时第三方服务正常，复现不出来；线上依赖抖动才触发。
2. **死锁、循环等待**
   - 多个任务之间互相持有对方需要的锁（synchronized、ReentrantLock、分布式锁），形成等待环，线程全部卡死。没有报错日志，只是停在锁等待。
3. **连接池耗尽阻塞**
   - 任务里使用 HTTP 连接池、数据库连接池、Redis 连接池，连接拿不到，一直阻塞等待获取连接；线程卡在获取连接这一步，不是业务逻辑慢。连接池耗尽是非常容易被忽略的坑。
4. **无界等待的 Future、CountDownLatch、锁条件等待**
   - 异步编排、多任务协作时，依赖其他任务信号，信号因为异常永远不会发出，线程无限 await。

误区：单纯调大线程数、队列容量，只会让卡死的线程变多，故障更严重；队列放大只是推迟雪崩时间，不能解决阻塞。

## 第一步：应急排查定位（线上止损流程）

1. **立刻导出线程栈（jstack），这是最核心手段**。看所有池内线程的栈状态：
   - 大量卡在 waiting for lock → 死锁 / 热点锁排队；
   - 卡在 http client / dubbo / redis client 等待响应 → 下游调用无超时；
   - 卡在获取连接（getConnection）→ 连接池耗尽；
   - 卡在 await()、countDownLatch.await() → 信号丢失。
2. 区分：是单个依赖慢，还是死锁环；
3. 临时止损方案：
   - 优先：熔断 / 切流、隔离该下游依赖；
   - 兜底：重启实例（治标）；
   - 配套：把堆积的任务捞出来（落库 / MQ），避免任务丢失。

## 第二层：三层防御体系（根治方案）

**第一层：所有阻塞点强制超时 + 超时兜底，杜绝永久等待。** 任何会阻塞的调用，一律强制设置超时时间，不能用默认无超时：

- RPC、HTTP、Redis、MQ、DB 查询都配置超时；
- 锁获取也设置超时（tryLock(timeout)，不要无限 lock）；
- CompletableFuture、CountDownLatch、CyclicBarrier 等待都加超时；
- 超时触发后抛出异常，线程释放回池子，而不是永久卡住。

**第二层：资源池隔离，连接池、线程池分开管控。**

1. 业务线程池和下游调用线程池 / 连接池解耦：HTTP 连接池、Dubbo 连接池单独设置上限，并且有空闲连接回收、连接保活、失效检测，防止连接僵死不释放；
2. 业务按强弱依赖、不同下游，拆分独立线程池：A 下游卡住，只耗尽它专属池，不会把订单主线程池全部卡死；
3. 连接池、线程池都做监控：连接等待时长、连接获取失败数、线程 WAITING 数量，提前告警，不等卡死。

**第三层：任务生命周期管控、监控与熔断防护。**

1. 任务埋点：每个任务进入、执行结束、耗时记录，超长任务告警；
2. 线程池指标不能只监控队列大小、活跃线程数；必须监控线程状态分布（RUNNABLE / WAITING / BLOCKED），WAITING 线程持续上涨就是卡死前兆；
3. 增加任务级熔断：同一个下游持续超时，触发熔断，不再发起调用，快速失败；
4. 持久化兜底：内存线程池只处理短时任务；核心异步流程上游使用 MQ，任务落地，就算线程池全挂，消息不会丢，换实例后继续消费。

## 连环追问要点整理

1. 流量在预估范围，两倍流量压测都正常，为什么线上会偶发全池线程阻塞卡死？
   - 压测环境依赖稳定、连接健康，复现不出依赖偶发僵死、连接半开、锁竞争时序问题，属于时序类隐蔽 bug，必须靠「阻塞必带超时」的代码规范兜底。
2. 线上遇到这类无声卡死，怎么快速定位根因、紧急止损？
   - 先 jstack 看线程卡在哪（锁 / 下游客户端 / 获取连接 / await），区分单点依赖慢还是死锁环，再熔断切流隔离、捞回堆积任务，重启只是兜底。
3. 怎么设计方案，避免以后每次故障只能重启续命？
   - 三层防御：阻塞点强制超时、资源池隔离、任务埋点 + 线程状态监控 + 熔断 + MQ 持久化兜底。

阻塞调用与线程池配置:
```java
// 所有阻塞调用强制超时，超时即抛异常、归还线程
// HTTP
RequestConfig.custom()
    .setConnectTimeout(500)
    .setSocketTimeout(1000);
// Redis / Dubbo / DB 查询同样必须显式配置超时

// 锁获取用超时，不用无限 lock
if (lock.tryLock(300, TimeUnit.MILLISECONDS)) {
    try { doBusiness(); } finally { lock.unlock(); }
}

// 异步编排等待也要有超时
future.get(800, TimeUnit.MILLISECONDS);
countDownLatch.await(1, TimeUnit.SECONDS);
```

## 面试回答完整话术
  - 线程池假死的典型特征是 CPU 不高、数据库空闲、线程充足，但线程全部 WAITING/BLOCKED、任务不推进、队列堆积。根因不是流量大，而是线程被永久阻塞：无超时的 RPC/HTTP/Redis 调用、死锁环路、连接池耗尽、无界 await。
  - 排查第一手段是 jstack：看线程卡在锁、下游客户端、getConnection 还是 await，据此判断是单点依赖卡住还是死锁环；应急先熔断切流、隔离依赖，把堆积任务捞回落库或 MQ，重启只是兜底。
  - 根治做三层防御：一是所有阻塞点强制超时，不能用默认无超时；二是资源池隔离，业务线程池与各下游连接池解耦，按下游拆独立池；三是任务埋点、线程状态分布监控、任务级熔断，核心异步流程上游用 MQ 持久化兜底。
  - 注意压测覆盖不了这类时序类隐蔽 bug，最终要靠「任何阻塞操作必须带超时」的编码规范。

  设计取舍：线程池的稳定性不取决于参数调得多漂亮，而取决于池里每一处依赖是否可控、每一次等待是否有终点。

## 追问：本题考察核心是什么？
  参考答案：
  初级工程师只关注线程池七个参数，认为线程池问题就是线程大小、队列、拒绝策略的问题。

###  高级工程师要分清：
  1. 线程池最大风险不是流量大，而是线程被永久阻塞无法归还；这种故障静默、无报错日志，极具迷惑性；
  2. jstack 是定位这类假死事故的第一工具，具备线上快速排障思路；
  3. 超时不是可选配置，是阻塞调用的强制规范；
  4. 线程池只是执行载体，它的稳定性，受制于里面每一处依赖、每一个锁、每一个连接池；
  5. 架构上不能把核心异步流程完全寄托在内存线程池，必须有消息队列做持久化兜底。
  核心思想：线程池管控不是调参，是对线程生命周期、所有阻塞依赖、外部资源池的全链路风险管控，提前切断无限等待的可能性。
