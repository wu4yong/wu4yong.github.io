## 第 03-9 题　MySQL 索引高并发踩坑，CPU 飙升线上故障复盘

**候选人浅层回答：** 建合适的联合索引、避免索引失效语法，就能提升查询性能。

## 核心拆解一句话结论

本题考察对底层原理和线上实战能力的综合理解，不能只停留在背结论。

## 连环追问

测试环境 SQL explain 走索引，看起来一切正常，也避开了隐式转换、函数操作这些常见索引失效写法。一旦线上流量上来，登录、信息查询接口频繁超时，数据库 CPU 持续 99%，大量慢查询拖垮整个服务。

1. 根源在哪？索引优化不能只看单条 SQL，系统性优化思路有哪些？
2. 索引是不是建得越多越好？

## 一、索引带来的隐性风险

很多人以为索引就是用来加速查询，只关注会不会走索引，忽略索引本身的代价和优化器行为： 1）索引过多 单表索引太多，磁盘占用上涨，写入、更新、删除时需要同步维护所有索引，写性能大幅下降。高并发写入场景下，IO 和 CPU 开销会持续走高。

2）索引区分度不足 索引字段基数低、区分度很差，比如性别、状态这类字段。

优化器评估后，认为走索引不如全表扫描，主动放弃索引，触发全表扫描，查询性能断崖下跌。

3）索引失效隐性场景 隐式类型转换、反向范围查询、or 连接条件不当等，都会导致索引失效。哪怕开发自认为规避了常规写法，复杂组合条件下依然踩坑。

4）优化器选择偏差 统计信息不准、数据分布倾斜，explain 在测试环境走索引，线上数据量变了，执行计划突变，大量请求变成慢查询，瞬间打满 CPU。

## 二、索引与 SQL 系统性优化方案

1）控制索引数量 单张表索引建议不超过 5 个，按需新建，无用索引及时清理，降低索引维护成本。

2）控制索引粒度，合理设计联合索引 遵循最左前缀原则，优先把区分度高的字段放前面；不要盲目把所有查询字段塞进联合索引。定期通过慢查询日志、performance_schema 分析索引利用率，下线低频无用索引。

3）SQL 改写优化 避免一次性查询大批量数据；分页限制单页条数，大数据量场景分批查询；避免 select \*，只查询需要字段；优化范围查询、or 条件，减少索引失效概率。

4）高频查询增加缓存兜底 热点高频查询增加 SQL 缓存，减少重复请求打到数据库，降低数据库查询压力。

5）慢查询全链路监控 开启慢查询日志，接入监控平台，抓取执行计划变化；关注执行计划突变，而不是只看 SQL 语法。

## 三、数据库架构兜底方案

核心业务数据库采用主从架构，读请求分发到从库，分担主库查询压力； 增加查询限流，防止突发流量、异常查询 SQL 打垮数据库； 做好读写分离，区分实时强一致查询和可延迟查询。

## 四、完整排查闭环流程

1. 告警触发：数据库 CPU 持续高、接口超时；
2. 抓取慢 SQL，查看执行计划，核对是否预期走索引；
3. 排查：索引数量、索引区分度、数据分布、统计信息是否准确；
4. 验证：是否存在隐式转换、范围查询不当等隐性索引失效；
5. 优化：清理冗余索引、改写 SQL、调整联合索引；
6. 架构兜底：缓存、读写分离、查询限流；
7. 回归压测验证，持续监控执行计划与慢查询。

<strong>追问：</strong>本题考察核心是什么？

<strong>参考答案：</strong>初级开发只会背索引最左前缀、索引失效几种语法。高级工程师要建立系统性思维：

1. 索引是有成本的，不是越多越好，索引同时影响读和写；
2. explain 只是参考，执行计划会随数据分布、数据量变化，测试环境正常不代表线上稳定；
3. 数据库优化不是只靠建索引，需要 SQL 优化、缓存、读写分离、限流组合兜底；
4. 具备线上故障复盘能力：看懂慢查询、定位执行计划漂移，建立全链路监控意识。

<strong>核心思想：</strong>索引优化不是单纯调 SQL 语法，是查询收益、写入成本、数据分布、架构方案之间的综合权衡。
