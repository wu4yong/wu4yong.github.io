## 第 03-6 题　MySQL 索引：执行计划显示走索引，但 SQL 依然很慢

**候选人浅层回答：** 背诵表面结论，没有深入到原理和线上场景。

## 核心拆解一句话结论

本题考察对底层原理和线上实战能力的综合理解，不能只停留在背结论。

## 场景回顾

候选人只会背索引失效：左 like、函数、隐式转换。 面试官连环灵魂拷问：

1. explain 明明走二级索引，为什么还是很慢？
2. 大范围二级索引查询，为什么优化器觉得不如全表扫描？
3. 走主键索引，表从百万涨到千万，性能明显变差，主键索引也失效了？
4. MySQL 优化器什么时候主动放弃索引、选全表扫描，判断逻辑是什么？

核心本质：索引不是免费加速工具，索引本身有 IO 代价；优化器是基于代价模型选择执行方案，不是有索引就一定优先走索引。

## 三层高分逻辑

第一层：二级索引 —— 回表成本（最常见）InnoDB 二级索引叶子节点存主键值，查到后需要回表，去聚簇索引读取完整行数据。 如果命中行数占整张表比例很高（一般超过 20% 左右，经验阈值）：

- 二级索引 → 大量回表，随机 IO 非常多；
- 全表扫描是顺序 IO，顺序 IO 远快于大量随机 IO； 所以优化器评估后，认为走索引的总代价更高，主动放弃二级索引，走全表扫描。 覆盖索引可以解决：把查询需要的字段全部放进联合索引，避免回表。

第二层：主键（聚簇）索引也会变慢，和 B + 树、页、IO 有关主键索引就是聚簇索引，本身不会失效，但数据量上涨后性能下滑原因：

1. B + 树层数变高：百万数据一般 3 层，千万级数据 B + 树深度增加，多一次磁盘页读取；
2. 数据页不能全部放进 Buffer Pool：热点页缓存命中率下降，大量访问落到磁盘IO；
3. 范围查询：主键范围扫描，如果扫描区间很大，依然要遍历大量数据页；主键索引永远有效，只是扫描的数据量、磁盘 IO 变多，延迟上涨，不是失效。

第三层：优化器代价模型（优化器怎么选）MySQL 优化器统计信息（cardinality 基数、行数、过滤比例）估算代价： 代价 ≈ IO 代价（主要） + CPU 代价

- 估算返回行数很少：索引代价低，选择索引；
- 估算返回行数占比高：大量回表随机 IO，代价高，放弃索引，走全表扫描；坑点：统计信息不准（采样估算、数据倾斜、很久没 analyze），会导致优化器判断出错，选错执行计划。

## 秒口述标准答案

就算执行计划显示走索引，查询慢主要有三层原因：第一是二级索引查询返回数据量大，大量回表带来随机 IO 开销，性能甚至不如顺序扫描的全表；第二是主键聚簇索引虽然不会失效，但千万级数据下 B + 树深度增加、Buffer Pool 缓存命中率下降，磁盘 IO 变多，范围查询延迟上涨；第三是 MySQL 优化器依靠统计信息做代价估算，当预估扫描行数占比高时，会主动放弃索引走全表扫描，如果统计信息不准，还会出现选错计划的情况。优先用覆盖索引消除回表，同时维护统计信息、控制扫描行数。

## 高频延伸追问

Q：20% 这个阈值是固定的吗？ A：不是硬编码固定值，只是经验值，受Buffer Pool 大小、磁盘性能、行大小影响。机器缓存越大，这个阈值会更高。

Q：怎么解决统计信息不准？ A：analyze table 更新统计信息；避免数据极端倾斜；也可以用 force index 临时强制索引（不建议线上长期使用）。 Q：覆盖索引原理？ A：查询字段全部在二级索引里，不需要回表，避免随机 IO。

Q：主键查询为什么也要 limit？ A：主键范围查询不加 limit，扫描行数多，B + 树遍历大量数据页，IO 上升。
