# Nest

## SOLID

## 一、单一职责原则（Single Responsibility Principle，SRP）

- 一个类应该只有一个引起它变化的原因。简单来说，一个类应该只负责一项职责，而不应该承担过多的功能。

## 二、开放 - 封闭原则（Open - Closed Principle，OCP）

- 软件实体（类、模块、函数等）应该对扩展开放，对修改封闭。也就是说，当需要增加新功能时，应该通过扩展现有代码来实现，而不是修改已有的代码。

## 三、里氏替换原则（Liskov Substitution Principle，LSP）

- 子类对象能够替换其父类对象，而程序的行为不会发生改变。也就是说，子类应该能够完全替代父类，并且不会破坏程序的正确性。

## 四、接口隔离原则（Interface Segregation Principle，ISP）

- 客户端不应该依赖它不需要的接口。一个类对另一个类的依赖应该建立在最小的接口上。也就是说，不应该强迫客户端实现它们不需要的方法

## 五、依赖倒置原则（Dependency Inversion Principle，DIP）

- 高层模块不应该依赖低层模块，两者都应该依赖抽象；抽象不应该依赖细节，细节应该依赖抽象。简单来说，就是要依赖于抽象接口，而不是具体实现类。

## 单一职责原则在 Nest 分层中的落地

- SRP 要求一个类只有一个引起它变化的原因，在 Nest 里首先体现为控制器、Service、DAO 各管一摊：控制器只做请求编排，取出参数、调用 Service、返回结果，不堆积业务规则
- Service 承载业务规则和用例编排，数据访问封装在 DAO/Repository 里，Service 通过它读写数据，不直接写底层存储细节
- 横切关注点（日志、鉴权、校验、异常处理）从业务类里抽离到中间件、守卫、管道、拦截器、异常过滤器，避免每个业务类重复实现同一套逻辑
- 一个 Service 类只对应一组紧密相关的职责；职责膨胀时按业务能力拆成多个模块和提供者，而不是把所有流程塞进一个大类
- 控制器方法里只做参数取出和结果返回，不写分支判断、不拼数据库查询条件；这类内容下沉到 Service，数据访问再下沉到 Repository
- 横切关注点从业务类抽离后，业务类的变化原因就只剩业务规则本身，不会因为日志格式、鉴权方式的调整而被迫改动
- 判断职责是否单一的一个直观标准：这个类被修改是因为业务规则变化，还是因为通用机制（鉴权、校验、日志）变化；两者混杂就需要继续拆分

## 依赖倒置原则与 IoC 容器

- DIP 要求高层模块不依赖低层模块，两者都依赖抽象；细节依赖抽象，而不是高层直接依赖具体实现类
- Nest 的依赖注入正是这一原则的落地方式：Service 在构造器上声明所需的依赖类型，由 IoC 容器按 token 解析并注入，Service 不负责 `new` 出依赖对象
- 非类的抽象依赖（配置对象、第三方客户端）先注册成 token，再用 `@Inject()` 显式注入，消费方面对的是抽象接口和约定，而不是具体构造过程
- 抽象类型要能被运行期解析，必须用类而不是被编译擦除的 `interface`；需要接口契约又要保留元数据时，通常用类或配合提供者 token 表达
- 业务层面向接口和 token 编程，具体数据库客户端、第三方 SDK 这类细节封装在提供者内部，不向上泄漏
- 依赖方向随分层自上而下指向抽象：控制器依赖 Service 抽象，Service 依赖 Repository 抽象，底层实现可以整体替换而不改上层调用

## 开放封闭原则与扩展点

- OCP 要求对扩展开放、对修改封闭：新增功能时通过扩展现有代码实现，而不是改动已有业务代码
- 在 Nest 里，新增一种校验规则可以新增管道，新增一种鉴权策略可以新增守卫，新增一类响应包装可以新增拦截器，既有处理方法不需要跟着改
- 策略类作为提供者注册进模块，需要切换实现时调整模块的 `providers` 绑定，而不是在调用方写一串条件分支
- 模块边界让变更收拢在局部内：一个模块内部的实现调整，只要 `exports` 出去的提供者形状不变，导入它的模块不受影响
- 横切能力以独立组件形式存在，新增组件并挂到合适范围即可复用，不侵入既有控制器和 Service
- 当一个新需求总是逼着修改多处既有业务代码时，通常说明抽象边界没有划对，应抽出新的提供者或扩展点，而不是继续在旧代码上加分支

## 里氏替换与接口隔离的对应

- LSP 要求子类对象能够替换父类对象而程序行为不变；在 Nest 体系里，同一接口的不同实现可以互相替换注入，守卫、管道、拦截器都实现固定接口（`CanActivate`、`PipeTransform`、`NestInterceptor`），框架只依赖接口契约
- 只要新实现满足同一提供者接口的契约，就可以替换原有实现注入到消费方，消费方代码不需要改动
- ISP 要求客户端不依赖它不需要的接口：管道只暴露 `transform()`，守卫只暴露 `canActivate()`，拦截器只暴露 `intercept()`，组件按需实现自己用到的那部分契约，不被迫实现空方法
- 分层之间的接口保持细粒度：Service 暴露的方法对应明确的用例，控制器不绕过 Service 直接触碰数据访问层
- 接口隔离在 Nest 组件接口上体现得最直接：每个扩展点只暴露一个职责方法，组件按需实现，不需要为用不到的能力提供空实现
- 这些原则落到 Nest 工程上的直接收益是：业务规则集中、横切逻辑可复用、替换实现不影响调用方，模块和组件随规模增长仍可测试和维护

## 与 Nest 扩展点的对应

- 单一职责对应分层：控制器编排、Service 规则、DAO 访问各管一段
- 依赖倒置对应 IoC：高层声明抽象依赖，容器按 token 注入具体实现
- 开放封闭对应扩展点：新增守卫、管道、拦截器即可扩展行为，不改既有业务方法
- 里氏替换对应提供者接口：同接口不同实现可互换注入
- 接口隔离对应扩展点接口：守卫只实现 `canActivate`，管道只实现 `transform`
- 横切关注点从业务类抽出，是 SRP 在 Nest 体系里最直接的实践
- 模块封装是 OCP 和 DIP 在组织边界上的体现

## 工程落地的检查点

- 控制器方法只做参数取出和结果返回，业务分支判断下沉到 Service
- Service 不直接拼底层存储细节，数据访问封装在 Repository/DAO 里
- 横切逻辑（日志、鉴权、校验、异常）抽成守卫、管道、拦截器、过滤器，不写进业务类
- 依赖通过构造器注入，业务类面向抽象和 token 编程，不负责 `new` 具体实现
- 新增策略时新增提供者或扩展点，不在既有代码里堆条件分支
- 模块对外只导出必要提供者，内部实现可整体替换
- 接口实现满足同一契约时可以互相替换注入，消费方代码不改动
- 每个扩展点只暴露一个职责方法，组件按需实现，不提供空方法
- 分层接口保持细粒度，Service 暴露的方法对应明确用例，控制器不绕过 Service 直触数据层
