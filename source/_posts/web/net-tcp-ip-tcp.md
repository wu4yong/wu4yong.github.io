# 计算机网络

## TCP 协议

- TCP 是一种面向连接的，可靠的协议。
- TCP 是明文传输的。因为 HTTP 协议使用的就是 TCP 协议。所以 HTTP 是明文的
- TCP 仅仅支持单播
- TCP 是面向字节流的

### 1.5 TCP 的拥塞控制

- 对网络中某一个资源的需求超过了该资源所能提供的可用部分，网络性能就要变坏，这种情况就叫做拥塞。
- 四种算法： 慢开始，拥塞避免，快重传，快恢复(拥塞窗口大小的意思就是，一次发送能发送 TCP 报文段的个数)

![TCP拥塞控制基础算法](@@CDN@@/assets/img/web/net-tcp-ip-tcp/img-01.webp)

- 在发生重传计时器超时时，有可能是出现了拥塞，也有可能是出现了报文段的丢失，不搞清楚是什么原因发生了重传计时器超时就直接降低拥塞窗口的大小会降低效率。采用**快重传算法**来区别是发生了拥塞还是发生了丢失，可以有效提高传输效率。
- 快恢复算法： 当使用快重传算法发现有个人报文段丢失时，不在启动**慢开始算法**，而是启动**快恢复算法**。快恢复算法不会直接把拥塞窗口大小直接改为 1，而是改为当前窗口大小的一半。

![TCP连接释放四次挥手](@@CDN@@/assets/img/web/net-tcp-ip-tcp/img-04.webp)

- 为什么 TCP 客户端在第二次发送完连接释放报文段后仍需要等待 2MSL 的时间后才关闭。是为了防止第二次连接释放报文段丢失后，TCP 服务端认为他发送的第二次连接释放报文段丢失，所以会启动 TCP 超时重传。如果此时客户端已经关闭的话，客户端收不到信息，TCP 服务端就会一直超时重传。等待两个 MSL 时间来确保 此次连接中没有剩余的 TCP 报文段干扰下一次 TCP 连接。
- 因为 TCP 是全双工通信的。四次挥手是客户端和服务端分别释放连接的过程。
- 每两次挥手其实是一次释放连接的过程。为什么一次释放需要两次挥手。假如客户端想要断开连接。客户端发送了连接释放请求。如果服务端没有回应，客户端并不知道自己的请求已经正确到达了服务端。每次释放时的第一次挥手是请求，第二次挥手是回应请求已经收到。
- 前两次的挥手是为了关闭从客户端到服务端的 TCP 连接，两次挥手之后服务器仍然可以给客户端发送少量数据。
- 后两次的挥手是为了关闭从服务端到客户端的 TCP 连接，至此 TCP 连接才真正释放。

## 三、TCP 报文段首部

- TCP 首部前两个字段是 16 位的源端口和目的端口
- 序号字段标识本报文段第一个数据字节的编号；同步位 SYN 置位时，序号是初始序列号 ISN，第一个数据字节从 ISN+1 开始
- 确认号字段在 ACK 置位时有效，表示期望收到的下一个字节的序号，连接建立后确认号一直发送
- 数据偏移字段以 32 位字为单位标识 TCP 首部长度，数据从首部之后开始
- 控制标志位包括 CWR、ECE、URG、ACK、PSH、RST、SYN、FIN，分别对应拥塞窗口减小、ECN 回显、紧急指针有效、确认有效、推送、复位连接、同步序号、数据发送完毕
- 窗口字段标识发送方当前愿意接收的字节数，配合滑动窗口做流量控制
- 校验和覆盖首部和数据，紧急指针在 URG 置位时表示紧急数据的位置

## 四、序号、确认与重传

- TCP 把交付的数据看作按字节编号的流，每个字节都有对应的序号
- 确认号是累计确认：收到该确认号之前的字节都已被接收方收到
- 报文段在规定时间内没有收到确认，发送方触发超时重传
- 快速重传不必等待重传计时器超时：收到重复确认后提前重传丢失的报文段，之后进入快恢复流程

## 五、流量控制与拥塞控制

- 接收方通过窗口大小通告自己还能接收多少字节，发送方不能超过接收窗口的上限，避免压垮接收方缓冲区
- 拥塞窗口由发送方根据网络拥塞状况自行调节，与接收窗口共同限制在途数据量
- RFC 5681 定义了四种相互配合的拥塞控制算法：慢开始、拥塞避免、快重传、快恢复
- 慢开始在拥塞窗口小于慢开始阈值时使用，拥塞避免在拥塞窗口大于阈值时使用
- 快重传发现丢失报文段后，快恢复不直接把拥塞窗口退回 1，而是把窗口降到阈值附近后继续增长
