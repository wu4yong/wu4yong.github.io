# 前端工程化

## monorepo

## 一、项目架构

### 1.1 传统化架构

组件库、用户中心、脚手架、图表库、工具库

- 独立项目结构，所有的项目都是分开的 git 仓库
- 技术栈独立
- 规范化、自动化相关处理每个项目之间都是割裂的
- 依赖管理、版本控制很难统一管理
- 部署、docker、CI/CD 等很难形成统一

### 1.2 Monorepo

- 混合项目结构，所有的工程形成子包管理
- 技术栈高度统一（团队基建、业务项目、子服务、技术栈）
- 规范化、自动化、流程化项目间共享
- 依赖管理、版本控制高度统一
- 部署、docker、CI/CD 等统一部署流程

## 二、基于 monorepo 架构的实践方案

### 2.1 现阶段

- 混合项目结构，所有的工程形成子包管理
  1. 技术栈高度统一
  2. 代码集中化管理
- 代码共享、团队积累
  1. 工具函数共享：提升开发效率
  2. 公共业务组件共享：提升开发效率、降低特性DI、将重心放到逻辑上
  3. 公共业务逻辑共享：提升开发效率、降低特性DI、统一代码风格
- 配置文件共享：eslint、prettier、stylelint、commitlint
  1. 统一代码规范、统一代码风格
  2. 避免上库时的代码冲突
- externals
  1. 将三方依赖的加载修改为 APP 内部加载
  2. 降低云端部署文件体积、显著提升加载速度
- 示例模版项目
  1. 用来代替脚手架
  2. 规定项目的方方面面: 项目规范、代码规范、网络请求、数据校验、公共组件封装、安全区域的适配、日志、异常监控、dsbridge、Mock 服务

  1. 根据项目的需求，自动生成基础结构

## 三、工作空间的依赖管理

- npm 工作空间在根 `package.json` 的 `workspaces` 字段里声明子包路径，`npm install` 时会把工作区内的包符号链接到根目录的 `node_modules` 中
- pnpm 工作空间在根目录的 `pnpm-workspace.yaml` 里用 `packages` 字段列出子包目录，配置思路与 npm 的 `workspaces` 字段对应
- 公共依赖安装一份放在根目录的 `node_modules` 下，各个子包通过符号链接引用同一份副本，避免同一依赖在多个包里重复安装
- 工作空间内部的包互相引用时，使用对方 `package.json` 里声明的 `name` 作为导入名，本地链接后可以直接联动调试
- 子包各自声明的依赖相互独立，被提升到根目录的只是可以共享的部分；属于 peer 依赖的版本要求仍按各包自己的声明解析
- 提升后同一版本的依赖只保留一份；版本要求相互冲突的依赖，仍会按嵌套结构分别存放
- 符号链接让本地包改动后无需反复发布安装，调试期直接引用源码即可

## 四、脚本与命令组织

- 根目录可以放共享的 eslint、prettier、stylelint、commitlint 等配置，子包直接继承，不再各自维护一份
- npm 用 `--workspace=<包名>` 针对单个工作空间执行命令，`--workspaces`（复数）对所有工作空间依次执行
- pnpm 用 `-r` / `--recursive` 递归执行，用 `-F` / `--filter` 按包名过滤要操作的子包
- 工作空间依赖之间存在循环时，递归执行的脚本不保证拓扑顺序，包管理器检测到循环依赖会给出警告
- 统一的入口脚本放在根目录的 `package.json` 里，对内屏蔽各子包启动、构建、测试命令的差异
- 子包自己的 scripts 仍然保留，仅在需要联动时由根目录脚本批量触发
- 新增子包时先在工作空间配置里登记路径，安装命令才会识别到这个包
- 缺少目标脚本的子包不会报错中断批量执行，配合对应的忽略缺失脚本参数即可跳过

## 五、版本发布与本地依赖

- 工作空间包的版本发布，可以用包管理器自带的版本命令按递归方式批量递增版本号
- 发布前本地协议声明的工作空间依赖会被替换成实际版本号或 semver 范围，不需要先在本地发一个中间版本给消费者安装
- 本地包在开发期被工作空间内其他包引用，发布出去的产物里不再保留本地链接关系，而是指向已发布的版本

## 六、集中化管理的收益与边界

- 公共规范、工具链和示例模板集中在仓库内维护，业务子包只消费不复制，升级时改动一处即可覆盖所有子包
- 跨包复用的工具函数、业务组件和业务逻辑沉淀在独立子包里，版本跟随仓库统一演进，避免各项目各自实现造成的风格分裂
- 集中管理不等于所有内容都放进根目录：通用能力抽成独立子包，业务项目保留自己的页面与业务逻辑，边界仍然按包划分
- 依赖提升减少了重复安装，但 peer 依赖、版本冲突的解析仍按各包声明处理，不能假设所有子包共享同一份依赖实例
- 新增子包、接入既有脚本和共享配置都有固定路径可遵循，新人上手时先看仓库根目录的说明与示例模板即可
