### global

- global 中存在很多很多属性(类似于浏览器的 window, 但是用户在全局定义的属性不会自动放到 global 中)
- JS 中不使用声明符号的变量会被放到 window 上，是 JS 的一个设计缺陷

### 特殊的全局对象

- 它们并不是真正的全局对象(不可以在控制台使用)，它们是模块中的变量，只不过每个模块都有，看起来像全局对象
- `__dirname` 当前文件的所在目录
- `__filename` 当前文件所在的目录 + 文件名
- `exports` `module` `require()`

## Node 与浏览器运行环境的区别

- Node 运行的是 JavaScript 语言本身，但不提供浏览器特有的 DOM、BOM 和页面窗口对象，因此操作页面元素、读写 Cookie 这类浏览器 API 在 Node 里不存在
- 浏览器里全局对象是 `window`，Node 里的全局对象是 `global`（现代代码也可使用 `globalThis` 作为跨运行环境的全局对象引用）；Node 中用不带声明符号的方式定义变量，不会自动挂到全局对象上
- Node 面向服务器场景，提供文件系统、网络、进程、流等核心模块；浏览器面向页面渲染和用户交互，两套环境的内置能力围绕各自场景设计
- 同一段纯 JavaScript 逻辑（字符串处理、数组计算、正则等）可以在两边运行，但一旦用到环境专属 API，代码就需要区分运行环境
- Node 没有浏览器的文档对象模型和窗口对象，页面相关的概念（DOM 节点、事件绑定、渲染树）在 Node 里没有对应物
- 浏览器环境里很多能力由宿主提供，Node 环境里则通过内置核心模块和 npm 包补齐，两者的标准库并不重合
- 全局可用的对象要区分真假全局：`__dirname`、`__filename`、`exports`、`module`、`require()` 看起来像全局变量，实际是每个模块内部的局部变量，离开模块包装器并不存在

## CommonJS 模块包装与模块变量

- Node 里每个文件被当作一个独立模块，模块代码会被 Node 包进一个函数包装器，因此模块内声明的局部变量是私有的，不会自动暴露给其他模块
- `__dirname` 是当前文件所在目录的绝对路径，`__filename` 是当前文件所在目录加文件名；它们不是真正的全局对象，而是每个模块内都有的模块级变量
- `exports`、`module`、`require()` 同样是模块内可用的局部变量：`exports` 是 `module.exports` 的引用简写，`require()` 用来加载其他模块，加载拿到的是被导出模块的 `module.exports` 对象
- 模块导出的内容通过 `module.exports` 或在其上挂属性完成；重新给 `exports` 赋值只会改变这个局部引用，不会改变真正被导出的 `module.exports`
- `require()` 接收模块标识：核心模块名、相对路径、绝对路径，或 `node_modules` 下的包名
- 模块缓存键是解析后的文件绝对路径，同一路径重复加载返回同一导出对象，不会重复执行模块代码
- 模块内声明的函数和变量不会污染其他模块的作用域，各模块通过显式 `require()` 建立依赖关系

## 单线程、事件循环与 Libuv

- Node 默认单线程处理 JavaScript 代码，异步 I/O 操作通过 Libuv 这个 C 库卸载到后台处理，完成后由事件循环把回调放回主线程执行，开发者不需要处理多线程的锁问题
- Libuv 同时承担事件循环和平台异步行为的跨平台实现，这是 Node 跨平台能力的基础
- 单线程不等于没有后台任务：文件读写、网络连接等 I/O 由内核和线程池在后台完成，主线程在等待期间可以继续发起后续 I/O 任务，这也是 I/O 密集型场景下性能较好的原因
- 长时间的 CPU 密集运算会占住主线程时间片，导致事件循环无法发起后续 I/O 任务；应对方式是把大任务拆小、及时让出主线程，或通过 `child_process`、子进程把计算挪到独立进程
- 进程内未捕获的错误会引起整个应用退出，因此服务端代码需要在关键路径上处理异常，避免单点错误拖垮整个进程
- 单线程模型省去了多线程编程里共享状态、加锁同步的复杂度，上下文切换代价小；代价是 CPU 密集任务会阻塞主线程，需要靠拆分任务或子进程绕开
- 多核 CPU 的利用通常通过子进程或集群方式启动多个 Node 进程，由进程各自处理请求，而不是在单进程内开多线程跑 JavaScript

## REPL 与模块加载

- REPL 是 Node 自带的交互式运行环境，输入 `node` 回车即可进入，在这里可以逐行输入 JavaScript 表达式并立即看到结果，适合验证语法和小片段逻辑
- 核心模块在 Node 安装时就已内置，加载速度快；文件模块和第三方包通过文件路径或 `node_modules` 解析加载，二次加载优先走模块缓存
- 同一模块被多次 `require()` 时，第二次及以后直接返回缓存里的导出对象，不会重复执行模块代码
- Node 的异步能力建立在事件循环之上：定时器、I/O 回调、网络事件按各自归属阶段进入队列，主线程逐个取出执行，从而在单线程下维持并发处理

## 事件循环与并发模型补充

- I/O 操作卸载到内核和后台线程池，主线程在等待期间可以继续发起后续任务，这是 I/O 密集场景下吞吐较好的原因
- 长时间 CPU 密集运算会占住主线程，阻塞后续回调；大任务应拆分或挪到子进程
- 未捕获错误会导致进程退出，服务端代码需要在关键路径处理异常
- 纯 JavaScript 逻辑可在浏览器和 Node 间复用，环境专属 API 不能跨环境调用

## CommonJS 模块解析的基本规则

- `require()` 解析顺序：先判断是否为核心模块（如 `fs`、`path`、`http`），核心模块直接内置返回
- 核心模块之外，按相对路径或绝对路径定位文件；路径标识以 `./`、`/` 开头的是文件或目录
- 文件查找依次尝试 `.js`、`.json`、`.node` 扩展名；目录则找 `index.js`、`index.json`、`index.node`
- 目录还会读取其 `package.json` 的 `main` 字段确定入口
- 路径都解析不到时，向祖先目录的 `node_modules` 逐级查找第三方包
- `require.resolve()` 返回解析后的文件路径，而不是执行模块，可用来检查模块能否被找到
- 模块首次加载时执行包装器函数，导出对象写入缓存；后续加载直接取缓存
- 循环依赖场景下，一方可能拿到尚未完成导出的对象，使用时要注意取值时机
- 重新给 `exports` 赋值不会改到 `module.exports`，模块对外暴露的始终是后者
- 模块包装器内的局部变量对其他模块不可见，跨模块通信只能通过导出对象
