# 技术文档总结

## 原子化 CSS

## 框架对比和优劣势

* Tailwindcss(推荐，使用度更高，React 脚手架推荐) 
* UnoCSS 

## 和内联样式的差别

1. 有约束的设计：从预定义的设计系统重选择样式。使得构建视觉上一致的 UI 更加容易
2. 响应式设计：使用响应工具轻松构建响应式界面
3. 聚焦、悬停状态：通过状态变量轻松定义

## 适用场景

* 团队的 UI 样式不是特别严格
* 团队自己的组件已经全面适配了 UI 的样式

## 带来的好处

* 不用写 CSS 类名
* 减少打包的体积(CSS 体积仅有 x KB 左右)
* 删除 DOM 结构时候，会自动删除 CSS，不会有代码冗余
* 很方便的实现主题模式和响应式布局
* Chrome Devtools 调试时很直观，没有以前各种 class 属性层层覆盖的问题

## 原子类的生成方式

- Tailwind 扫描源码中出现的类名，只把实际用到的工具类编译进产物，未使用的样式不会进入最终 CSS
- 工具类是单一用途的 class，一条类名对应一条 CSS 声明，避免为每个样式单独命名 CSS 类
- 状态与响应式通过修饰符组合，例如 `hover:bg-black`、`lg:text-xl`，同一个工具类可以叠加多个修饰符
- 方括号写法可以直接填入任意值，例如 `top-[117px]`，并能继续叠加 `hover`、`lg` 等修饰符
- 框架未内置的 CSS 属性，可以用任意属性写法 `[mask-type:luminance]` 直接在类名里表达
- 类名在标记中直接表达样式，浏览器 DevTools 里能看到具体生效的声明，不需要层层回溯被覆盖的 class
- 删除不再使用的 DOM 结构后，对应的工具类也不会残留在样式表中，减少历史 CSS 冗余
- 工具类按类别前缀组织，例如 `bg-` 背景色、`text-` 文字、`p-` 内边距、`flex` 布局，命名有统一规律
- 产物 CSS 体积只包含实际用到的工具类，与框架内置工具类的总数没有直接关系
- 状态样式集中通过修饰符表达，减少为 hover、disabled 等状态单独编写的 CSS 类
- 复合类与工具类搭配使用时，先确定哪些样式属于可复用组件，哪些属于单处布局
- 团队约定好类名使用边界后，标记层保持以结构和内容为主，样式通过类名表达

## @layer 与 @apply

- `@layer` 把自定义样式放进 `base`、`components`、`utilities` 三层，由层级决定最终声明顺序
- `base` 层用于重置规则与纯 HTML 元素的默认样式，`components` 层用于可被工具类覆盖的复合类，`utilities` 层用于单一用途工具类
- 层内未被使用的自定义样式也会被按需移除；不放进 `@layer` 的自定义 CSS 会始终保留在编译产物里
- `@apply` 在自定义类里复用已有工具类；定义在 `components` 层的类，仍然可以被工具类覆盖

```css
@layer components {
  .card {
    @apply rounded-lg bg-white p-6 shadow-xl;
  }
}
```

- 引用主题值时可以使用 `theme()` 函数读取配置中的颜色、间距、圆角等尺度
- 自定义工具类放进 `utilities` 层后，同样支持 `hover`、响应式等修饰符
- 写在 `components` 层的复合类适合表达 `card`、`btn`、`badge` 这类项目内重复出现的样式组合

## 修饰符与任意值的配合

- 响应式写法面向移动优先，基础样式面向小屏，断点修饰符在更大屏幕上覆盖对应样式
- 伪类与状态修饰符（hover、focus、disabled 等）和响应式修饰符可以串联使用
- 深色模式可以通过对应的 `dark:` 修饰符按主题策略切换样式
- 任意值解决设计系统覆盖不到的边角情况，常规样式仍优先使用内置工具类，避免类名里塞满临时数值
- 同一元素上工具类与复合类并存时，依靠层级和修饰符判断最终生效的声明
- 与内联样式相比，原子类可以复用、可以被状态修饰符组合、参与按需编译；内联样式无法直接写 hover 与媒体查询

## 与组件样式的配合

- 第三方组件或项目内复合组件的定制样式，适合放在 `components` 层统一管理
- Vue、Svelte 这类单文件组件的 `<style>` 是逐个独立处理的，`@layer` 在组件样式块内不可用，需要写在全局样式表中
- 组件内部样式与原子类混用，会增加覆盖顺序的判断成本，项目内需要约定二者的使用边界
- 主题模式与响应式布局通过修饰符和 CSS 变量切换，不需要为每套主题单独维护一套类名
- 业务侧直接使用封装好的组件时，原子类主要落在组件内部，页面层级尽量保持结构清晰
- 颜色、间距、字号优先从主题尺度选取，随意填写的数值会破坏设计系统的一致性
- 响应式写法遵循移动优先，基础样式面向小屏，断点修饰符在更大屏幕上覆盖
- 原子类解决的是样式表达与按需生成的问题，组件抽象与职责划分仍由项目结构承担
- 封装组件时把重复样式收敛到组件内部，页面层级只保留结构类名
- 项目内统一工具类与复合类的使用顺序，减少样式覆盖的判断成本
- 任意值写法只用于设计系统覆盖不到的局部样式，避免类名被临时数值填满
- 主题色与尺度通过配置集中维护，工具类引用同一套设计变量
- 标记层不再承担命名 CSS 类的职责，类名直接对应样式声明
- 多人协作时统一原子类的使用习惯，减少同一样式写出多种类名组合
