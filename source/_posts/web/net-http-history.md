# 计算机网络

## HTTP 历史

## HTTP 0.9

1. 协议规定由客户端发起请求，由服务端响应请求
2. 协议诞生之初的目的只是用来传输超文本内容 HTML, 因此仅支持 GET 请求
3. 因为仅用来传输 HTML, 所以没有多余的请求头。请求报文只有一行，响应报文只有一行
4. 以 ASCII 字符流编码的格式返回 HTML 文档
5. 服务端发送完响应就关闭 TCP 连接
6. 虽然设计理念简单，但是充分验证了 WEB 服务的可行性

## HTTP 1.0

1. 增加了 HEAD(查询资源可行性) POST 方法
2. 增加了响应状态码，标记可能的错误原因
3. 增加了 HTTP Header 的概念，让 HTTP 处理请求和响应更加灵活，传输的数据不再局限于文本
4. 缺点：一个 TCP 请求只能发送一个 HTTP 请求，引入了非标准字段 Connection: keep-alive 来达到复用 TCP 的目的
5. 核心改动：增加了 Header 的概念

## HTTP 1.1

1. 增加了 PUT， DELETE， OPTIONS, PATCH 等方法
2. 长连接: TCP 连接复用，即 TCP 不默认关闭，可以被多个请求复用
3. 管道机制：一个 TCP 连接可以同时发送多个请求(但是要求响应的顺序和请求的顺序必须一致)
4. 允许响应数据分块：利于传输大文件

### 缺点

1. 虽然通过长连接来实现 TCP 复用的机制，但是一个连接同一时刻只能处理一个请求。如果前面的请求没有完成，后面的请求会处于阻塞状态`队头阻塞`
2. 利用管道机制在一定程度上能缓解`队头阻塞`问题，但是管道要求响应顺序和请求顺序一致，如果前面的请求很耗费时间(处理大量图片)，即使后面的请求已经处理完成了，但是仍需要等待前面的结果有响应之后才能返回数据。
3. Header 中的内容过多导致协议开销大，没有对应的压缩传输优化方案

## HTTP2

1. 二进制协议：不再使用 ASCII 编码传输，改用二进制来传输，每个请求或者响应的数据包被称为`数据流`
2. 多路复用：废弃了 HTTP1.1 中的管道，在同一个 TCP 连接中可以同时发送多个请求，并且不用按照顺序处理响应，避免了队头阻塞问题(由于可以同时处理多个请求，因此相邻的两个数据流可能不属于同一个响应，因此给每个流添加唯一的编号 ID)
3. 请求优先级：允许指定请求的优先级，使得关键请求被优先响应(请求 HTML 的优先级高，等网页显示出来之后在请求图片等文件)
4. 头部信息压缩：专用算法进行头部数据压缩，减少数据的传输量。对于一些固定的头部信息会通过客户端和服务端同时维护一张头部信息表，传输的时候只传输索引
5. 服务端主动推送：允许服务器主动向客户端发送数据(webSocket 协议)

## HTTP3

1. HTTP 协议运行于 TCP 协议之上，TCP 协议也会发生丢包导致阻塞的问题，因此 HTTP3 构想使用 UDP 协议来传输 HTTP。

## HTTP/2 的帧与流

- HTTP/2 是二进制协议，通信的基本单位是帧，HEADERS 帧和 DATA 帧构成请求与响应的主体
- 每个请求响应对关联到一条独立的流，流用一个 31 位整数编号；客户端发起的流用奇数编号，服务器发起的流用偶数编号
- 同一条 TCP 连接上可以并行承载多条流，某条流被阻塞不会影响其他流的推进
- 流编号在连接内不能复用，长期运行的连接编号耗尽时需要建立新连接
- HTTP 字段通过 HPACK 压缩后放在 HEADERS、CONTINUATION、PUSH_PROMISE 帧中传输
- HTTP/2 保留了 HTTP 原本的方法、状态码和头部语义，改动集中在报文分帧和二进制传输表示上
- HTTP/1.1 默认保持持久连接，一条 TCP 连接可以连续承载多个请求和响应
- HTTP/1.1 的管道方式要求响应按请求顺序返回，前面的请求未完成会阻塞后面的响应
- HTTP/2 的流复用取代了 HTTP/1.1 管道，流之间可以独立调度和结束
- HTTP/2 的帧携带流编号，接收方按编号把帧归并回对应的请求和响应

## HPACK 头部压缩

- HPACK 用静态表和动态表把常见头部字段映射成索引，传输时可以只传索引而不传完整字段名
- 静态表是预定义的只读表，动态表是编码解码上下文各自维护的表，初始为空
- 同一个连接上请求方向和响应方向的动态表相互独立
- 头部字段名在 HTTP/2 消息中统一转成小写
- 动态表有容量上限，编码器通过控制表项更新来限制解码器占用的内存

## HTTP/3 与 QUIC

- HTTP/3 不再直接运行在 TCP 之上，而是运行在 QUIC 传输协议之上
- QUIC 基于 UDP 封装，在流级别提供可靠、按序的交付，并在整条连接上做拥塞控制
- 每个请求响应对占用一条 QUIC 流，流之间相互独立，一条流丢包不会阻塞其他流
- QUIC 内部集成了 TLS 1.3 作为握手协议，连接建立阶段同时完成加密协商
- HTTP/3 在 ALPN 协商中使用的标识是 h3，QUIC 版本 1 要求使用 TLS 1.3 或更高版本作为握手协议
- HTTP/3 沿用了 HTTP/2 的二进制帧思路，把帧放在 QUIC 流上传输
- HTTP/3 的头部压缩使用 QPACK，而不是 HTTP/2 的 HPACK
- HTTP/2 时期存在的 TCP 层丢包队头阻塞，由 QUIC 在流级别隔离交付的方式缓解
- 从 HTTP/1.x 到 HTTP/2，报文从文本行组织改为二进制帧组织，HTTP 语义本身没有变化

## 流与帧的对应关系

- HTTP/2 中一条流对应一次请求响应，流可以独立打开、结束和取消
- 帧头的流编号把分片的帧归并到所属流，接收方按流重组消息
- HTTP/3 的请求响应对占用一条 QUIC 双向流，流之间的可靠交付相互独立
- QUIC 在连接级做拥塞控制，在流级做流量控制
- HPACK 与 QPACK 都借助静态表和动态表压缩重复的头部字段
