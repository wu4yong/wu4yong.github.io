# 前端工程化

## Webpack 的构建流程

## 一、构建过程的三大流程

1. 初始化流程：从配置文件和  Shell  语句中读取与合并参数，并初始化需要使用的插件和配置插件等执行环境所需要的参数
2. 编译构建流程：从 Entry 发出，针对每个 Module 串行调用对应的 Loader 去翻译文件内容，再找到该 Module 依赖的 Module，递归地进行编译处理
3. 输出流程：对编译后的 Module 组合成 Chunk，把 Chunk 转换成文件，输出到文件系统

## 二、详细流程

### 2.1 初始化参数

- 从配置文件中和 shell 语句中读取合并参数，得到最终的参数

### 2.2 开始编译

- 根据参数初始化 Comiler 对象，加载所有配置的插件, 执行对象的 run 方法开始执行编译

### 2.3 确认入口

- entry 配置项

### 2.4 编译模块

- 从入口文件出发，调用所有配置的 loader 对模块进行翻译，再找出该模块依赖的模块，递归的进行处理

### 2.5 完成编译

- 得到了每个模块被翻译后的最终内容以及他们之间的依赖关系

### 2.6 输出资源

- 根据入口和模块之间的依赖关系，组装成一个个包含多个模块的 chunk，再把每个 chunk 转换成一个单独的文件加入到输出列表中，这步是可以修改输出内容的最后机会

### 2.7 输出完成

- 在确定好输出内容后，根据配置确定输出的路径和文件名，把文件内容写入到文件系统

## 三、webpack 的核心概念

- webpack 是一个静态模块打包工具，处理应用时从一个或多个入口出发，内部构建出依赖图，再把所有需要的模块组合成一个或多个 bundle
- Entry：打包工具构建依赖图的起点，webpack 从 entry 指定的模块出发，找出它直接和间接依赖的所有模块
- Output：告诉 webpack 产物生成在哪里、文件如何命名；主产物默认 `./dist/main.js`，其他产物输出到 `./dist` 目录
- Loaders：webpack 原生只认识 JavaScript 和 JSON，loader 把其他类型文件转成可纳入依赖图的模块
- Plugins：在 loader 之外执行更宽范围的任务，比如包优化、资源管理、环境变量注入
- Mode：通过 `mode` 选项让 webpack 应用对应模式的内置优化，默认值是 production
- 不使用配置文件打包时，entry 默认是 `./src/index.js`；这个文件不存在时 webpack 会报入口解析错误
- 打包工具的输入是源码模块，输出是浏览器可直接加载的静态资源
- 依赖图保证只打包被实际引用的模块，未被任何入口链路引用的模块不会进入产物

## 四、Loader 与 Plugin 的分工

- loader 作用在单个文件的转换上，配置写在 `module.rules` 里，用 `test` 匹配文件、`use` 指定 loader
- 一个文件可以经过多个 loader 链式处理，执行顺序按配置倒序
- loader 只处理匹配到的文件，不感知依赖图里的其他模块
- babel-loader 负责把 JS 交给 Babel 转译；css-loader 解析 CSS 里的 `@import` 和 `url()`；style-loader 把处理后的样式通过 `<style>` 标签注入页面
- loader 配置里的 `test` 是正则匹配，不要给正则加引号；加引号后会被当成字面路径
- plugin 作用于整个构建流程，可以监听编译生命周期里的事件，在时机合适时修改产物
- 使用 plugin 需要先 import，再放进配置的 `plugins` 数组；多数 plugin 可以通过选项对象定制行为
- 同一个 plugin 可以在配置里多次使用，因此实例需要调用 `new` 创建
- plugin 示例：HtmlWebpackPlugin 会生成 HTML 文件，并把编译出的 bundle 自动插入页面
- DefinePlugin 用来在编译期把代码里的全局常量替换成具体值
- 概念上不要混用：把 `.css` 转成模块靠 loader，生成 HTML 文件并自动注入产物链接靠 plugin

```js
module: {
  rules: [{ test: /\.js$/, use: "babel-loader" }],
}
```

## 五、模块递归与产物组装

- 从入口出发后，打包工具读取模块里的依赖声明（`import`、`require`），递归找到被依赖的模块，形成完整的依赖图
- 每个模块经过 loader 翻译后，打包工具记录模块之间的引用关系，而不是把文件内容简单拼接
- 递归过程中遇到无法解析的模块，编译阶段就会报错
- 依赖图里的模块按入口和分割点组装成 chunk，chunk 是打包工具内部的代码组织单位；bundle 则是最终输出到磁盘的文件
- 模块之间的引用关系在编译期确定，运行时只需要按记录的关系加载对应 chunk
- 一个 chunk 可以包含多个模块；代码分割后，一个 bundle 也可以由多个 chunk 组成
- 编译阶段得到的是每个模块翻译后的最终内容和模块间依赖关系；输出阶段才把 chunk 写成文件
- 异步加载的模块会被拆成独立 chunk，运行时按需请求，不需要随首屏一起下载
- 输出阶段把 chunk 转换成文件，加入输出列表；这一步仍可以被 plugin 修改
- 产物写入文件系统后，构建流程结束；开发服务器模式下产物保留在内存中，不写磁盘
- 编译流程里的每个阶段都有对应钩子，plugin 通过钩子介入，而不是改写打包工具内部代码
- 多个入口会各自构建依赖图，再按配置合并产物；共享的公共依赖可以被提取到单独的 chunk 里复用
