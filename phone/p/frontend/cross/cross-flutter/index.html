跨端 Flutter

分类：frontend · cross ｜ 标签：web

跨端开发

Flutter

页面渲染

  • Flutter 的渲染不依赖原生系统的 UI 组件，而是依靠 Skia 图形渲染引擎自绘界面，从底层图形绘制到界面交互逻辑都由 Flutter 框架和 Dart 代码处理。
  • Flutter 不依赖原生系统的 UI 组件，所以在不同的平台上拥有完全一致的界面表现

逻辑执行

运行阶段

  • Flutter 会被编译成 Dart 字节码，然后在 Dart 虚拟机中运行。

生产阶段

  • Flutter 会通过 AOT 编译，将 Dart 代码编译为 Android、IOS、桌面端等平台特性的机器码

优势点

  1. 各平台页面表现的高度一致性
  2. 较高的性能，拥有堪比原生的性能和流畅性
  3. 热重载
  4. 虽然是非官方的方案，但是已经有团队维护了支持鸿蒙的方案

缺点

  1. 一些较底层的功能实现受限，还是得依赖原生开发
  2. 没有热更新

框架与引擎分层

  • Flutter 框架层主要用 Dart 编写，包含 Widget、渲染、动画、绘制、手势等基础能力
  • Flutter 引擎层主要用 C++ 编写，负责在每一帧绘制时把合成好的场景光栅化，并提供图形、文本布局、文件与网络 IO、Dart 运行时等底层实现
  • 嵌入层（Embedder）负责把 Flutter 接入具体操作系统，平台相关的适配工作由嵌入层承接
  • 框架通过 dart:ui 这一层 API 调用引擎能力，业务代码一般不直接接触引擎

渲染管线

  • 界面先由 Widget 树描述，再由渲染对象树参与布局和绘制，最终交给引擎光栅化上屏
  • Widget 本身是对界面的不可变描述，状态变化时框架重建 Widget 树，再对比更新底层的渲染对象
  • 因为界面由 Flutter 自绘而不是套用各平台原生控件，同一套界面在不同平台上的表现更容易保持一致
  • 渲染过程中的合成与光栅化由引擎统一处理，平台原生视图只在需要接入既有原生界面时才混入

开发期与发布期的编译方式

  • 开发阶段应用运行在 Dart 虚拟机中，支持有状态的热重载，修改代码后不必完整重新编译即可看到效果
  • 热重载尽量保留当前应用状态，热重启则会重新初始化应用状态，两者用于不同的调试场景
  • 发布阶段应用直接编译为目标平台的机器码，面向 Web 目标时则编译为 JavaScript 或 WebAssembly
  • Dart 在 JIT、AOT、原生与 Web 等不同模式之间，语言语义差异很小，多数开发者不会直接碰到模式相关的区别

Platform channels

  • Flutter 提供平台通道（platform channel）作为 Dart 代码与宿主平台原生代码之间的通信机制
  • 通道由名称和编解码器共同定义，Dart 侧与原生侧在同一通道上收发消息
  • 数据会从 Dart 类型序列化为标准格式，再在 Kotlin 或 Swift 一侧还原为对应的数据表示
  • 需要调用系统特有能力时，通过平台通道桥接到原生实现，而不是在 Dart 层硬套 Web 或 JS 侧的接口

与原生界面的互操作

  • 既有原生页面可以嵌入 Flutter 页面，Flutter 界面中也可以通过平台视图混入原生组件，适合按模块逐步迁移项目
  • 插件生态把常用的原生能力封装为 Flutter 可调的包，业务代码通过统一的 Dart 接口使用这些能力
  • 平台通道和插件之下，仍然是各端原生代码在调用系统服务，跨端层只负责完成消息和能力的对接

设计语言与组件库

  • 框架层提供 Material 和 Cupertino 两套设计风格的组件库，分别对应 Android 和 iOS 的界面观感习惯
  • 业务代码在同一套 Widget 体系下组织界面，需要贴近某一平台风格时选用对应组件库的组件
  • 设计语言层面的差异由组件库承接，底层渲染仍走统一的 Flutter 自绘管线

多端复用与差异处理

  • 同一套 Dart 业务代码在 Android、iOS、桌面和 Web 等目标之间复用，差异部分通过平台通道和插件处理
  • 各端系统能力无法在 Dart 层统一抽象时，仍落到原生实现，再由通道把结果交回 Flutter 侧
  • 跨端开发时需要区分可以复用的界面与逻辑，以及必须保留各端原生处理的系统能力

渲染与性能关注点

  • 每一帧界面由引擎统一光栅化上屏，动画和手势在框架层处理，再交回渲染管线更新画面
  • 界面重建频繁或组件层级过深时，需要关注 Widget 重建范围和渲染对象的对比更新开销
  • 自绘路线保证了多端表现一致，但复杂动画和大量绘制仍受设备图形性能约束

第三方包生态

  • Flutter 框架之外有第三方包生态，常用的原生能力和 UI 组件可以通过包的形式引入项目
  • 包内部通常通过平台通道对接原生实现，业务侧仍按 Dart 接口调用，不必重复编写原生胶水代码
  • 选用第三方包时需要关注其维护状态、平台覆盖范围和与当前框架版本的兼容性
