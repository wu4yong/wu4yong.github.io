NestJS 基础

分类：frontend · nest ｜ 标签：web

Nest

Nest 基础

  • 完全支持 TS
  • 结合 AOP 面向切面的编程方式
  • Nest 拥有 Spring 风格: DI 依赖注入，IOC 控制反转
  • 结合了 OOP（面向对象编程）、FP（函数式编程）和 FRP（函数式响应式编程）

DTO

DTO 是 Data Transfer Object 的缩写，表示数据传输对象，一般用于 Controller 层与 Service 层之间的数据传递。

DAO

DAO 是 Data Access Object 的缩写，表示数据访问对象，一般用于 Service 层与数据库之间的数据传递。

启动入口与根模块

  • Nest 应用从一个根模块开始引导，根模块是 Nest 构建应用依赖图的起点，小型应用可以只有根模块，大型应用按能力拆成多个模块
  • 启动文件里通过 NestFactory.create() 传入根模块创建应用实例，再调用 listen() 监听端口对外提供服务
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(3000);
}
bootstrap();
  • 控制器、服务、守卫、拦截器等组件都注册在模块内部，由 Nest 的 IoC 容器统一实例化和装配
  • 应用结构按模块组织，每个模块封装一组紧密相关的能力，模块之间通过显式的 imports 和 exports 协作
  • 根模块把各个功能模块组合起来，容器在引导阶段解析模块间的依赖关系，再按依赖顺序实例化提供者
  • 模块是推荐的组件组织方式：控制器、服务、配置收拢在一处，随规模增长应用结构仍然清晰可维护

TypeScript 元数据与依赖注入

  • Nest 依赖注入读的是 TypeScript 编译期发射到类上的参数类型元数据，构造器参数上的类型注解就是容器查找依赖用的 token
  • 能被容器按类型解析的必须是类：interface、type 别名在编译后不存在，写成接口类型会让容器拿不到 token，启动时报依赖无法解析
  • 非类的依赖（配置对象、第三方客户端）需要先注册成 token，再用 @Inject() 显式指定注入目标
  • 单例 provider 在应用引导时解析依赖并实例化一次，之后所有依赖方共享同一个实例；需要按请求或按消费方独立实例时，可以调整注入作用域
  • 注入作用域有三种：DEFAULT 是默认单例，整个应用共享一份；REQUEST 为每个进入的请求新建实例，请求处理完回收；TRANSIENT 每个注入它的消费方拿到独立实例
  • 守卫、拦截器、管道、异常过滤器这类组件和普通 provider 一样，支持通过构造器注入同一模块内可用的依赖
  • 控制器注入了 request 作用域的提供者时，控制器本身也会沿注入链变成 request 作用域，每个请求新建一份实例
  • 解析不到依赖时，容器在启动阶段就报错，而不是等到运行调用时才暴露空引用问题
  • 提供者可以是普通类，也可以是值、工厂或第三方实例，通过模块的 providers 注册后由容器统一管理
  • 注入 token 既可以是类，也可以是字符串或符号；非类依赖通过 @Inject() 显式指定对应的 token
  • 同一提供者在默认作用域下全局共享一份实例，消费方拿到的是同一个对象引用

DTO 与 DAO 在分层中的位置

  • DTO 描述跨层传递的数据形状，控制器用它约束请求体、查询参数的结构，管道可以基于类上的验证装饰器校验入参
  • 定义 DTO 推荐用类而不是 TypeScript 接口：接口在编译后被擦除，管道在运行期拿不到它的元数据，类会作为真实实体保留下来
  • DAO 负责封装对数据库的访问，Service 层通过 DAO 读写数据，业务规则不直接写在数据访问代码里
  • 分层的目的是让请求编排、业务规则、数据访问各归其位，控制器不堆积业务逻辑，Service 不直接操作底层存储细节
  • 跨层传递的数据只保留必要字段，管道可以在系统边界剔除处理方法不该收到的多余属性，避免脏数据进入业务层
  • DTO 解决的是层与层之间传什么数据的问题，DAO 解决的是业务层怎么拿到数据的问题，两者处于不同方向的边界上
  • 同一 DTO 可以复用于创建、更新等多个接口，按场景配不同校验装饰器
  • 请求参数在进入 Service 前由管道完成校验和转换，Service 内部不必重复判空和类型转换

控制器、提供者与模块的协作

  • 控制器负责接收请求并调用提供者，提供者承载业务逻辑，模块把两者注册到一起并声明对外暴露的能力
  • 提供者通过构造器声明依赖，容器在实例化时按 token 查找并注入；控制器和提供者都可以注入其他提供者
  • 模块的 providers 数组声明由容器管理的提供者，controllers 数组声明需要实例化的控制器，imports 引入其他模块导出的提供者
  • 一个应用从根模块出发，容器解析所有模块和提供者的依赖关系，按顺序完成实例化，再把控制器挂到路由上
  • 业务代码一般不直接 new 提供者，实例的创建和生命周期交给容器，便于统一替换实现和测试
  • 控制器不直接持有数据库连接或第三方客户端实例，这些由提供者封装后注入
  • 模块只导出需要对外复用的提供者，模块内部实现对上游不可见
  • 提供者之间通过构造器依赖建立关系，容器按依赖顺序完成实例化

应用引导阶段做了什么

  • NestFactory.create() 完成模块装配、提供者实例化和依赖注入，返回应用实例
  • 引导阶段解析不到依赖、循环依赖无法解析时，会在启动时报错，而不是在第一次请求时才暴露
  • 应用实例上可以配置全局前缀、CORS、全局管道、守卫、拦截器和过滤器，再调用 listen() 对外监听端口
  • 启动文件只负责装配和启动，业务能力分布在各模块的控制器和提供者里
  • 全局注册的组件作用于整个应用；方法、控制器范围的组件只覆盖声明它的那一层
  • 组件可以通过构造器注入其他提供者，容器按依赖关系完成装配
  • 应用的请求处理链路依次经过中间件、守卫、拦截器、管道、处理方法、拦截器后置和异常过滤器
  • 分层和依赖注入的目标是把业务规则、横切逻辑、数据访问分开，随规模增长仍可测试和替换实现
