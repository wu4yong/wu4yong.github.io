NestJS AOP 切面编程

分类：frontend · nest ｜ 标签：web

Nest

AOP 切面编程

  • 一个请求会经过 controller、service、repository 三个地方，如果想要调用链路中加入一些通用的逻辑(日志记录，权限控制，异常处理)。直接加在 controller 中可以实现，但是不优雅，因为这些通用的逻辑会侵入业务层。在调用 controller 之前和之后通过的加入逻辑，这个横向的扩展点就叫切面，这种透明的加入一些切面逻辑的编程方式叫做 AOP 面向切面编程
  • 执行顺序：请求 -> middleware(中间件) -> Guard(守卫) -> (路由前)Inteceptor(拦截器) -> Pipe(管道) -> 路由处理程序 -> (路由后)Inteceptor(拦截器) -> ExceptionFilter(异常过滤)(如果有异常) -> 响应

Nest 中的切面扩展点

  • 中间件：在路由处理程序之前执行，能访问 request、response 和 next，适合鉴权、日志这类不依赖具体路由上下文的横切逻辑
  • 守卫：在所有中间件之后、拦截器和管道之前执行，依据运行时条件决定请求能否进入路由处理程序，通常承担授权职责
  • 拦截器：包裹请求/响应流，可以在路由处理程序之前和之后绑定逻辑，也可以转换返回结果或转换抛出的异常
  • 管道：在方法被调用之前处理入参，负责把输入数据转换成所需形式，或者验证输入是否合法
  • 异常过滤器：在异常从处理流程中抛出后接管响应，控制返回给客户端的错误状态码和响应体内容
  • 这些扩展点都可以声明式地挂在方法、控制器或全局范围内，不需要在每个业务方法里手工调用
  • 一个请求从进入到返回，会依次经过中间件、守卫、路由前拦截器、管道、路由处理程序、路由后拦截器，最后由异常过滤器处理途中抛出的异常
  • 横切逻辑集中在这些组件里维护，业务方法只处理自身职责，调整通用行为时不需要逐个改动业务代码
  • 不同扩展点各有定位：中间件处理不依赖路由上下文的通用工作，守卫做路由级授权，拦截器编排前后置逻辑和结果转换，管道专注入参，过滤器只在异常分支介入
  • 把通用逻辑从业务链路里抽离之后，控制器和 Service 的代码更短、更聚焦，也更容易单独测试

拦截器与 AOP 的对应

  • 拦截器是 Nest 里最接近 AOP 概念的抽象：调用 next.handle() 进入路由处理程序的位置，就是 AOP 术语里的切入点（Pointcut）
  • 处理程序之前的逻辑写在 handle() 调用之前，处理程序之后的逻辑通过 handle() 返回的 RxJS Observable 来编排
  • 拦截器既能扩展基本行为，也可以在满足条件时完全重写处理程序，例如缓存命中时直接返回缓存结果，不再调用 handle()
  • 日志、计时、统一响应包装、异常转换这类跨多个控制器的需求，都适合放在拦截器里实现，而不是散落在每个业务方法中
  • 拦截器返回的是流而不是最终结果，因此可以用 map 转换成功结果，用 catchError 替换抛出的异常
import { Injectable, NestInterceptor, ExecutionContext, CallHandler } from '@nestjs/common';
import { Observable } from 'rxjs';
import { tap } from 'rxjs/operators';

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    console.log('Before...');
    const now = Date.now();
    return next
      .handle()
      .pipe(tap(() => console.log(`After... ${Date.now() - now}ms`)));
  }
}
  • 如果 intercept() 实现里不调用 handle()，路由处理程序根本不会被执行；拦截器本质上包裹了整条请求/响应流
  • 多个拦截器按注册顺序包裹处理程序，外层拦截器的前置逻辑先执行、后置逻辑后执行，形成嵌套的处理链

ExecutionContext 与 ArgumentsHost

  • 守卫、拦截器、管道、异常过滤器拿到的上下文对象都来自同一套抽象：ArgumentsHost 是对原始处理函数参数的包装，ExecutionContext 在它之上补充了当前执行过程的信息
  • 在 HTTP 场景下可以用 switchToHttp() 取出 request 和 response；同一套过滤器逻辑也可以面向微服务、WebSocket 等其他上下文编写
  • 这种抽象让横切逻辑不绑定具体平台，一处实现即可复用到不同的执行上下文
  • 守卫和拦截器的 canActivate、intercept 方法接收的都是 ExecutionContext 实例，异常过滤器的 catch 方法接收的是 ArgumentsHost 实例
  • 通过上下文对象还能拿到当前绑定的控制器类和处理方法，守卫据此读取挂在路由上的自定义元数据，做细粒度的权限判断

横切关注点与业务代码的分离

  • 日志记录、权限控制、异常处理这类逻辑在多个调用链中重复出现，直接写进 controller 会侵入业务层，散落各处也难以统一调整
  • 切面方式在调用 controller 之前和之后透明地加入通用逻辑，业务代码只关心自身职责，横切能力集中维护、按需挂载
  • 新增一种横切能力时，通常是新增一个对应类型的组件并挂到合适范围，而不是改动既有业务方法
  • 中间件和守卫偏好在请求进入前做判断，拦截器能同时照顾进入前和返回后，管道专注入参，过滤器只在异常分支介入，职责边界彼此不重叠
  • 横切组件和业务组件一样可以经过依赖注入容器装配，需要读取配置或调用其他 Service 时，通过构造器注入即可

各扩展点的注册范围

  • 方法范围：组件挂在单个处理方法上，只作用于该方法
  • 控制器范围：组件挂在控制器类上，作用于该控制器内的所有处理方法
  • 全局范围：组件注册到整个应用的所有路由；从模块外注册的全局组件处于模块上下文之外，无法注入依赖，需要注入依赖时通过 APP_* token 在模块内注册
  • 同类型的多个组件按注册顺序依次执行，先注册的先介入处理流程
  • 全局组件在整个应用的每个路由上生效，方法和控制器范围的组件只覆盖声明它的那一层

典型横切需求的归属

  • 访问日志：记录进入时间、请求路径、耗时，适合拦截器在前后置阶段完成
  • 鉴权授权：判断当前身份能否访问路由，适合守卫结合路由元数据完成
  • 入参校验与转换：在方法调用前把字符串转成所需类型并校验合法性，适合管道完成
  • 统一错误响应：把各类异常转成固定结构的错误响应，适合异常过滤器完成
  • 请求体解析、CORS、压缩这类平台级处理，适合在中间件或应用实例配置层完成
  • 响应字段包装、空值替换、超时控制，适合拦截器对流的操作完成
  • 同一需求可以拆到多个扩展点协作：守卫放行后，管道校验入参，拦截器包装结果，过滤器兜底异常
  • 选择扩展点时先看需求发生在链路的哪一段：进入前判断用守卫或中间件，前后都要照顾用拦截器，只处理入参用管道，只处理异常用过滤器
