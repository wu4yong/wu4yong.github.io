Nest

模块

模块元数据

  • 模块是用 @Module() 装饰的类，装饰器提供的元数据被 Nest 用来组织和管理应用结构
  • @Module() 接收一个对象，包含四类配置：providers 是由 Nest 注入器实例化、至少在本模块内共享的提供者；controllers 是本模块需要实例化的控制器集合；imports 是本模块所需提供者来自哪些已导出模块的列表；exports 是本模块对外提供、可被导入它的模块使用的提供者子集
import { Module } from '@nestjs/common';
import { CatsController } from './cats.controller';
import { CatsService } from './cats.service';

@Module({
  controllers: [CatsController],
  providers: [CatsService],
  exports: [CatsService],
})
export class CatsModule {}
  • 每个 Nest 应用至少有一个根模块，它是 Nest 构建应用图（模块与提供者之间依赖关系的内部结构）的起点
  • 模块默认封装自己的提供者：只有当前模块内部、或被导入模块显式导出的提供者，才能被注入到本模块的控制器和其他 provider 中
  • 模块的 imports 列出本模块需要用到的提供者来自哪些模块；只有被对方模块 exports 出去的提供者，才能在本模块被注入
  • 把提供者封装在模块内部后，模块对外暴露的公开接口就是 exports 列表，内部实现细节不会直接泄露给消费方

共享模块与导出

  • 在 Nest 中模块默认是单例的，同一个 provider 实例可以在多个模块之间共享
  • 想把某个 Service 提供给其他模块使用，先把它加入本模块的 exports 数组，导入该模块的其他模块才能访问到这个 Service
  • 把同一个 provider 直接在每个需要它的模块的 providers 里各注册一次也能运行，但每个模块会得到各自独立的实例；实例越多内存占用越高，持有内部状态时还可能出现状态不一致
  • 模块不仅可以导出自己的提供者，还可以把导入进来的模块再导出，让间接导入它的模块也能拿到对应提供者
  • 模块类本身也可以注入 provider（例如读取配置），但模块类之间由于循环依赖的原因，不能作为 provider 被注入
  • 根模块组合所有功能模块，容器从根模块出发解析完整的应用依赖图，再按依赖关系实例化各个提供者
  • 一个模块可以同时导入多个模块，也可以把导入的模块再导出，形成模块之间的间接复用

全局模块

  • Nest 默认把提供者封装在模块作用域内：不先导入封装它的模块，就无法在别处使用它的提供者
  • 想让一组提供者（如辅助工具、数据库连接）开箱即用、到处可注入，可以用 @Global() 装饰器把模块标记为全局模块
import { Module, Global } from '@nestjs/common';

@Global()
@Module({
  providers: [CatsService],
  exports: [CatsService],
})
export class CatsModule {}
  • 全局模块只应注册一次，通常放在根模块或核心模块中；注入全局模块提供者的模块不需要再把它加进 imports 数组
  • 规范并不建议把所有东西都做成全局模块：imports 数组以显式方式把模块的 API 提供给其他模块，结构更可控，也避免无关模块之间产生不必要的耦合

模块单例与实例隔离

  • 默认作用域下，一个 provider 在整个应用里只有一份实例，应用引导完成后单例提供者就已实例化，之后所有消费方共享
  • 同一个 provider 被两个模块的 providers 分别注册时，得到的是两份不同实例，每个模块各持有一份，而不是全局共享
  • 动态模块可以在运行期按传入的选项配置提供者，适用于提供者依赖导入方所给参数的场景；重复调用动态模块的配置方法会生成另一套独立配置的实例
  • 模块是推荐的组件组织方式：把紧密相关的控制器、服务和配置收拢在一处，模块之间通过显式导入导出协作，应用结构随规模增长仍可维护
  • 模块边界让变更收拢在局部内：一个模块内部的实现调整，只要 exports 出去的提供者形状不变，导入它的模块不受影响

模块四数组的分工

  • providers：由 IoC 容器实例化并管理生命周期的提供者，服务、守卫、管道、拦截器等都在这里注册
  • controllers：需要被实例化并挂到路由上的控制器
  • imports：本模块依赖的其他模块，从中取得已导出的提供者
  • exports：本模块对外暴露的提供者或模块，供导入方使用
  • 一个控制器只有出现在模块的 controllers 数组里，才会被容器装配并路由
  • 未导出的提供者只在模块内部可见，外部模块无法注入

模块的封装与共享

  • 模块默认封装内部声明的提供者：只有模块 exports 出去的提供者，导入该模块的其他模块才能拿到
  • 提供者在默认单例作用域下被整个应用共享一份实例，模块只是组织边界，不隔绝实例
  • 模块可以再导出它导入的模块，让上游模块一次性拿到下层模块暴露的提供者
  • 模块类自身可以注入本模块的提供者，但模块类本身不会作为提供者被注入到其他类
  • @Global() 把模块标记为全局模块，全局模块只注册一次，导入它的模块无需再写 imports
  • 动态模块通过 forRoot()、forFeature() 这类方法返回带配置的模块定义；重复调用生成相互独立的模块实例
  • 模块边界把相关的控制器、提供者收拢在一起，对外只暴露必要的提供者，内部实现可以整体替换
