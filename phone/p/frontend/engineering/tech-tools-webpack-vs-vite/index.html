技术总结 webpack 与 Vite 对比

分类：frontend · engineering ｜ 标签：web

技术文档总结

Webpack 和 Vite 对比

  • webpack 是一个用于现代 JavaScript 应用程序的 静态模块 打包工具(对标 Rollup)
  • Vite 是一个更上层的工具链方案，对标的是 (webpack + 针对 web 的常用配置 + webpack-dev-server)

一、开箱即用，配置简单

  • 由于 Webpack 没有预设场景，设计的十分灵活，导致配置项复杂，插件机制和内部逻辑晦涩难懂。即使是最常见的 WEB 场景也需要大量的配置。并且大量的 loader 之间虽然单独发布但是却隐藏隐式耦合(各种版本之间)。
  • Vite 则预设了场景 WEB,并且将大部分常见的 WEB 构建需求都直接做成了默认的配置(TS JS ES6 file CSS SCSS font 等)，并且 Vite 也提供了脚手架方便集成 ESlint Prettier TS Test。

二、构建项目的区别

2.1 Webpack

  1. Webpack 在启动时，会先构建项目模块的依赖图，如果在项目中的某个地方改动了代码，Webpack 则会对相关的依赖重新打包，随着项目的增大，其打包速度也会下降。

2.2 Vite

  • Vite 其核心原理是利用浏览器现在已经支持 ES6 的 import, 碰见 import 就会发送一个 HTTP 请求去加载文件。Vite 以 原生 ESM 方式提供源码。这实际上是让浏览器接管了打包程序的部分工作
  • Vite 启动一个 koa 服务器拦截这些请求，并在后端进行相应的处理将项目中使用的文件通过简单的分解与整合，然后再以 ESM 格式返回返回给浏览器。Vite 整个过程中没有对文件进行 打包编译，做到了真正的 按需加载，所以其运行速度比原始的 webpack 开发编译速度快出许多
  • 在开发阶段使用 ESbuild 进行 转译。Esbuild 则选择使用 Go 语言编写能够充分利用 CPU 的多核性能。Esbuild 具有非常快的速度，打包速度却是其他工具的 10 ～ 100 倍。(快就一个字，开发时能实现秒开)

  • 在生产环境下使用 Rollup 进行打包。尽管 esbuild 速度更快，但 Vite 采用了 Rollup 灵活的插件 API 和基础建设，这对 Vite 在生态中的成功起到了重要作用。目前来看，我们认为 Rollup 提供了更好的性能与灵活性方面的权衡。

三、Vite 为什么要比 Webpack 快

  • 按需编译：当浏览器请求某个模块时，再根据需要对模块内容进行编译
  • 充分利用现代浏览器 ES 特性：所以开发阶段的 babel 转化工作会省略很多
  • 高效底层语言：ESBuild 使用 Go 语言编写，使用 ESBuild 进行转译，能够充分利用 CPU 多核的运算

Webpack 的核心概念

  • webpack 是现代 JavaScript 应用的静态模块打包工具，从入口出发构建内部依赖图，再把所需模块组合成 bundle
  • 核心概念包括 entry、output、loaders、plugins、mode
  • 开箱只理解 JavaScript 与 JSON，其他类型的文件由 loader 转换为可纳入依赖图的模块
  • 插件用于打包优化、资源管理和环境变量注入，在配置的 plugins 数组中注册
  • mode 取 development、production 或 none，启用对应环境的内置优化
  • 配置文件里通过 module.rules 声明 loader 的匹配条件与使用方式
  • 项目增大后，依赖图需要整体重建，改动带来的重新打包范围与模块数量相关
  • 依赖图从入口递归解析 import、require 等模块引用，再决定哪些模块进入产物
  • loader 按规则链式转换不同类型的文件，插件则贯穿编译与打包的各个阶段
  • 代码分割可以借助动态导入等方式，把公共模块与异步加载的部分单独拆分

Vite 的开发与构建流程

  • 开发阶段以原生 ESM 方式提供源码，浏览器请求到哪个模块再处理哪个模块，按需编译
  • 裸模块导入（例如 my-dep）由 Vite 预构建，并改写为浏览器可访问的 URL；依赖请求通过 HTTP 头做强缓存
  • 预构建同时把 CommonJS、UMD 模块转换为浏览器可识别的 ESM 格式
  • HMR 基于原生 ESM 提供，框架侧有首方集成，例如 Vue 单文件组件与 React Fast Refresh
  • 生产构建完成打包与代码分割，异步 chunk 用到的 CSS 会单独抽取，加载对应 chunk 时自动引入
  • 配置文件与脚手架内置了常见的 WEB 构建需求，TypeScript、JSX、CSS、预处理器、字体等按默认约定处理
  • 动态导入需要符合对应的路径规则，Vite 据此判断哪些文件会被纳入打包
  • HMR 在不刷新整页、不丢失应用状态的前提下替换改动模块，框架侧负责接入对应的刷新逻辑
  • 静态资源在构建流程中按配置输出，并在产物里生成对应的引用路径

选型时对照的维度

  • 配置复杂度、冷启动速度、HMR 体验、插件生态、产物优化与浏览器目标
  • webpack 设计灵活、配置面广；Vite 预设 WEB 场景，常见构建需求走默认配置
  • 现有项目的技术栈与迁移成本，也是对比打包工具时需要考虑的因素
  • 框架官方模板通常已选定对应的构建工具，升级框架时优先跟随其默认方案
  • 历史包袱较重、依赖大量 loader 与插件定制的项目，切换构建工具前需要先核对生态兼容情况

开发与生产的差异

  • 开发阶段的目标是快速反馈与按需编译，生产阶段的目标是产物优化、代码分割与静态资源交付
  • 同一份框架源码，在开发与生产下经过的处理流程不同，对比构建速度时需要区分这两个场景
  • 打包工具的能力不只体现在启动速度上，还包括产物拆分、静态资源处理、环境变量与框架集成等方面
  • 代码分割可以把公共模块与异步加载的部分单独拆分，改善首屏加载与缓存命中率
  • 模板 HTML 的产物注入、静态资源输出与压缩，属于构建流程在生产阶段承担的工作
  • 两种工具都支持模块级的代码分割与公共依赖提取，具体配置方式随各自生态不同
  • 对比时把开发体验与产物质量分开评估，避免只用启动速度概括整个构建工具链
  • 构建工具的配置方式与生态插件，决定了项目定制化需求的落地成本
  • 现有依赖对 loader、插件的使用情况，是迁移构建工具前需要先梳理的内容
  • 框架官方文档给出的默认集成方案，通常已经覆盖常见的开发与构建需求
  • 开发环境保留源码与模块映射，便于定位问题；生产产物经过压缩与优化，体积和可读性不同
  • 依赖预构建与按需编译主要改善开发启动体验，生产阶段仍需完整打包
  • 静态资源与代码分割策略在生产构建阶段统一落地
  • 框架集成在两种构建模式下分别对接对应的处理流程
  • 对比工具链时同时看开发反馈速度与最终产物表现，不只取单一指标
