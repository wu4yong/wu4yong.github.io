对AI的感受

  1. AI小白，对AI没耐心
  2. 大概知道AI需要什么，但是懒得整理、提供。又期望AI能自己理解。最后将时间浪费在修正AI的输出结果上，不从源头找问题
  3. 明白怎么使用AI，但是自己对代码和业务不熟悉。无法把握代码质量

注意事项

  1. 阶段性的提交代码，只要有能用的就提交代码

Project Rules 的存放与作用

  • 项目规则存放在 .cursor/rules 目录下，随代码库一起版本管理，作用域限定在当前项目
  • 规则是提供给 Agent 与内联编辑的系统级指令，可以写成持久化的上下文、偏好或固定工作流
  • 规则文件可以用路径模式限定适用范围，引用到匹配文件时自动附带；规则内部也可以用 @file 引用其他文件作为上下文
  • User Rules 是跨项目生效的全局偏好；.cursorrules 属于旧版遗留格式，官方推荐改用 Project Rules
  • 子目录可以有自己的 .cursor/rules 目录，规则作用域限定在该文件夹内
  • 规则适合沉淀项目内的领域知识、固定流程和代码风格约定，而不是只写一次的临时提示
  • 每条规则可以附语义描述，说明什么场景下应该生效，便于工具按相关性附带规则
  • 规则文件之间可以通过 @file 引用串联，把相关上下文组合到同一条规则里
  • 项目规则进入版本管理后，团队成员在不同环境下读到的上下文保持一致

整理需求时的上下文要点

  • 需求拆成明确的功能点，附上接口协议、交互方式和参考项，AI 输出才具备可审查性
  • 开发者自身需要熟悉代码与业务，才能判断输出质量、识别边界情况
  • 阶段性提交已经可用的代码，避免一次性堆叠大量改动后再统一修正
  • 拆分功能多窗口实现时，每个窗口聚焦一个明确的目标，减少上下文混杂
  • 缺少参考项或协议说明时，先补齐上下文再让 AI 继续，而不是反复修改已经跑偏的输出
  • 前端项目里，组件结构、样式约定、接口字段这些信息最好一并提供，减少 AI 自行假设
  • 提示词里写清功能点、约束条件和验收标准，输出范围更容易控制
  • 先在规划阶段梳理改动范围与步骤，确认后再进入编码，减少大范围返工
  • 多窗口拆分时，每个窗口只处理一个明确目标，避免上下文混杂导致输出跑偏

审查 AI 输出的关注点

  • 先看结构是否符合项目约定，再看接口调用、类型与边界处理是否完整
  • 对生成的代码逐条确认业务含义，不直接整段保留未经理解的实现
  • 规则、接口文档、参考项这些材料沉淀下来，后续同类需求可以复用
  • 输出内容与现有代码风格不一致时，先确认是项目约定需要调整，还是 AI 没有读到对应规则
  • 涉及状态管理、路由、请求封装等公共模块的改动，重点检查是否影响其他页面
  • 审查通过后再进入下一个功能点，避免问题在多轮生成中叠加
  • 改动 diff 先通读一遍，再配合项目内已有的检查手段验证，确认没有遗漏边界情况
  • 公共模块上的改动，重点确认对其他页面和已有流程的影响范围
  • 生成的组件需要回头核对样式、响应式与交互状态，而不是只看功能是否跑通

前端场景下的使用节奏

  • 先让 AI 理解现有代码结构和约定，再动手写新功能，而不是上来直接生成整段实现
  • 组件、样式、接口调用分步骤确认，每一步保留可回退的提交节点
  • 遇到 AI 反复修正仍不可用的情况，回到需求描述和参考材料本身找问题，而不是继续在输出上打补丁
  • 项目规则随代码一起维护，团队成员切换环境后可以复用同一套上下文约定
  • 生成前端组件后，检查样式、响应式和交互状态是否与设计约定一致
  • 规划阶段先梳理改动范围与步骤，再进入编码，减少大范围返工
  • 阶段性保留可回退的提交节点，出问题时可以回到上一个可用状态
  • 外部工具与数据源可以通过 MCP 接入，作为规则与代码之外的补充上下文
  • 规则内容聚焦可复用的约定与流程，一次性的临时提示不必写进项目规则
  • 新成员接入项目时，项目规则可以帮助快速理解代码结构与风格约定
  • 输出不符合预期时，先检查上下文材料是否齐全，再判断模型本身的能力限制
  • 前端改动涉及样式与交互时，把设计约定和已有组件用法一并提供给 AI
  • 每轮生成后保留可用状态，确认无误再继续下一个功能点
  • 项目规则随代码评审一起维护，过时的约定及时更新
  • 分点描述需求时附上预期的交互结果，输出更容易对照验收
  • 审查 AI 改动时结合现有测试与检查手段，不只凭阅读判断
  • 前端组件复用已有写法，规则里注明可参考的组件与样式约定
  • 上下文材料不足导致的偏差，补齐后再继续生成，不在错误输出上反复修补
  • 规则与参考材料沉淀后，同类需求可以减少重复描述
  • 输出审查聚焦业务含义与边界情况，不追求表面上的代码完整
  • 项目约定更新时，同步检查已有规则是否仍然适用
