四、策略模式的结构

  • 策略模式把一组可互换的算法分别封装成独立的策略对象，它们对外提供统一的调用方法
  • 上下文对象持有当前使用的策略对象，需要执行算法时把请求委托给策略对象，自己不实现具体算法
  • 不同策略之间可以互相替换，新增一种策略不需要改动上下文的代码
  • 策略模式让算法的变化和使用算法的客户端分开，客户端可以根据条件选择合适的策略
  • 策略对象只负责自己那一种算法，上下文只负责选择和委托，两者的职责边界比较清晰
  • 策略接口由上下文约定，具体策略只要实现这个接口就能被替换
  • 策略模式的参与者包括上下文、抽象策略和具体策略，具体策略实现同一套接口
  • 客户端只需要知道选择哪个策略，不需要了解策略内部的计算过程

五、JS 中的实现

  • JavaScript 中常用对象字面量配合键名来组织策略，把每种算法写成一个函数，调用时按键名取出对应策略执行
const strategies = {
  normal: function (price) {
    return price;
  },
  half: function (price) {
    return price * 0.5;
  },
  fullReduction: function (price) {
    return price >= 100 ? price - 20 : price;
  },
};

function computePrice(strategyName, price) {
  const strategy = strategies[strategyName];
  return strategy(price);
}

console.log(computePrice("half", 100)); // 50
  • 新增策略只需要在策略对象里补一个方法，不需要在调用方堆叠 if else 或 switch 分支
  • 策略对象之间互不依赖，单独替换或测试某一种策略都比较方便
  • 策略执行需要的参数由上下文传入，策略内部不关心参数来自页面还是接口
  • 找不到指定策略时可以退回默认策略，避免调用方每次都判断是否存在对应算法
  • 策略函数的返回值形式保持一致，上下文拿到结果后按同一套流程处理
  • 策略对象可以在运行时替换，上下文持有的策略引用更换后，后续执行走新的算法
  • 策略函数接收上下文传入的数据，计算完成后把结果交回上下文

六、策略模式与条件分支的对照

  • 未使用策略时，选择算法的逻辑散落在调用方的 if else 或 switch 中，新增规则要改多处
  • 使用策略后，选择逻辑集中在上下文，规则本身收敛到策略对象内部
  • 策略对象可以被单独复用，不需要为不同调用方各写一份算法
  • 策略模式处理的是同一种问题下的不同算法，并不是用来替代所有分支判断
  • 抽出策略后，调用方只面对统一的入口，不再感知内部有多少种规则
  • 条件分支集中后，新增规则的改动范围被限制在策略集合内部

七、策略对象的组织方式

  • 策略数量少时放在同一个对象字面量里即可，规则变多后可以按业务拆成独立模块
  • 每个策略模块导出统一签名的函数，上下文按名称引入对应策略
  • 策略之间不互相调用，需要组合多个算法时由上下文编排
  • 策略的选择条件属于上下文职责，不要写进策略内部让策略判断自己该不该被使用
  • 策略模块单独导出后，可以在其他页面或服务中复用同一套规则
  • 策略文件按业务域划分后，查找和替换某条规则的位置更明确

八、优点与注意事项

  • 优点：消除臃肿的条件分支语句，把变化的算法隔离在各自的策略内部
  • 优点：符合开放封闭原则，新增策略时扩展已有代码而不是修改原有分支
  • 优点：策略可以在不同上下文之间复用，同一种算法不必在多处重复书写
  • 优点：策略之间互相独立，修改一种策略不会影响其他策略
  • 注意事项：策略数量会随着业务规则增长，策略变多时需要额外组织和命名
  • 注意事项：客户端必须了解各个策略的区别，才能在正确的场景选择正确的策略
  • 注意事项：策略之间需要约定统一的方法名和参数形式，否则上下文无法透明地替换策略
  • 注意事项：如果策略之间有大量重复逻辑，可以再抽取公共部分，避免每个策略各写一遍
  • 注意事项：策略命名要能体现算法本身，不要用和调用场景绑定的名字，否则换个场景就难以复用
  • 注意事项：策略模式适合规则会持续增加、需要频繁调整算法的业务；算法长期固定时，单独的策略层会显得多余
  • 注意事项：策略返回的结果交给上下文统一处理，策略内部不直接操作页面或外部系统
  • 注意事项：新增策略时先确认是否属于同一类问题，不相关的算法不要塞进同一个策略集合
