设计模式 单例模式

分类：frontend · pattern ｜ 标签：web

设计模式

单例模式

一、概念

保证一个类仅有一个实例，并提供一个访问它的全局访问点

二、应用

2.1 全局缓存(Vuex、Pinina)

三、优缺点

四、JS 中的单例实现

  • 最常见的写法是用一个变量缓存已经创建好的实例，下次获取时直接返回缓存
  • 缓存实例的变量通常放在闭包内部，外部不能直接改写，只能通过获取实例的函数访问
let instance = null;

function getCache() {
  if (!instance) {
    instance = {
      data: [],
    };
  }
  return instance;
}

const cacheA = getCache();
const cacheB = getCache();
console.log(cacheA === cacheB); // true
  • 把获取实例的函数暴露出去，缓存变量留在闭包内，外部无法直接清空或替换 instance
  • 也可以把判断写在构造函数内部：构造时先查看是否已有实例，有就返回已有实例，不再新建对象
  • 多次获取同一个单例得到的应该是同一个引用，所有调用方看到的是同一份状态和方法
  • ES module 模块在被多次 import 时只执行一次，模块导出的对象在各个引用方之间是同一个实例，利用这一点也可以实现天然的单例
  • 模块顶层声明的变量不会进入全局作用域，导入的绑定不能在导入方重新赋值

五、创建时机

  • 饿汉式：模块加载时就把实例创建好，之后直接返回；实现简单，但如果这个实例一直没被用到，初始化的开销就浪费了
  • 懒汉式：第一次获取实例时才创建，之后复用缓存；实例确实可能用不到时更省初始化成本，但每次获取都要先判断缓存是否存在
  • 上面示例中的 getCache 就是懒汉式写法：调用第一次时创建 instance，之后的调用直接返回缓存
  • 懒汉式在实例创建成本低、或者几乎一定会被用到时优势不明显，饿汉式写法反而更直接

六、适用场景

  • 全局唯一的缓存对象，例如存储共享状态、字典表、配置项
  • 全局只允许出现一个的组件，例如弹窗、登录框、日志管理器
  • 全局事件总线、消息订阅中心这类只需要一份分发机制的对象
  • 页面上同时只能打开一个的弹层、抽屉、确认框
  • 全局唯一的工具函数集合、格式化处理器这类不需要每份拷贝的对象
  • 资源昂贵且不需要重复创建的对象，例如数据库连接、线程池这类需要统一管理的资源
  • 单例适合状态需要在整个应用内共享的场景；如果不同模块需要各自独立的一份状态，就不应该用单例

七、单例与全局变量的区别

  • 全局变量只是把名字挂到外部作用域，任何代码都可以直接读写，没有约束
  • 单例把实例的创建和访问收敛到一个入口函数内部，外部只能通过这个入口拿到实例，不能随意替换缓存
  • 单例可以延迟创建实例，全局变量在声明时就已经初始化
  • 全局变量命名冲突后互相覆盖，单例的缓存放在闭包或模块内部，不会和外部名字冲突

八、优点与注意事项

  • 优点：避免重复创建相同对象，减少内存占用和重复初始化的开销；对外提供统一的访问入口
  • 注意事项：单例带来的全局状态会让模块之间产生隐式依赖，单独测试某个模块时需要额外处理这个全局实例
  • 注意事项：单例的生命周期和应用绑定，实例内部持有的外部资源如果不主动释放，会一直留在内存中
  • 注意事项：在需要多实例并行的场景下，例如多租户、多份独立配置，强行复用同一个实例会把互不相关的数据混在一起
  • 注意事项：单例模式掩盖了对象之间的依赖关系，阅读代码时不容易看出一个模块依赖了哪些全局对象
  • 注意事项：单例内部状态被任意调用方改写后，出问题时需要沿着所有引用方排查，定位比局部对象更困难
  • 单例共享的方法和状态被多处调用时，修改内部实现需要回归所有使用方

九、什么时候不该用单例

  • 同一类资源需要按业务分别隔离时，单例共享状态反而会串数据
  • 对象创建成本很低、用完即可丢弃时，缓存实例带来的复杂度没有收益
  • 模块需要独立测试、替换 mock 实例时，全局唯一的缓存会限制依赖注入
  • 状态本身有生命周期，需要在特定时机重建时，长期持有的单例不容易重置
  • 单例内部如果持有可替换的策略或配置，这些协作者仍然可以通过入口传入，不必写死在实例里
  • 设计单例前先确认这份状态是否真的全局唯一，多数场景下普通对象配合依赖传递就足够
  • 单例能解决的是重复创建和统一访问的问题，不能用来替代状态管理本身的设计
