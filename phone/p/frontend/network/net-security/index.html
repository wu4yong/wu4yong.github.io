计算机网络

网络安全

XSS

  • 跨站脚本攻击, XSS 其实就是 Html 的注入问题，攻击者的输入没有经过严格的控制进入了数据库，最终显示给来访的用户，导致可以在来访用户的浏览器里以浏览用户的身份执行 Html 代码，数据流程如下：攻击者的 Html 输入—> web 程序—>进入数据库—> web 程序—>用户浏览器。
  • XSS 更偏向于代码实现(即写一段拥有跨站请求功能的 JavaScript 脚本注入到一条帖子里，然后有用户访问了这个帖子，这就算是中了 XSS 攻击了)
  • XSS 利用的是用户对指定网站的信任

预防 XSS

  • 过滤用户的输入
  • 不直接将用户的输入存储，而是遍历节点只得到用户输入的值。不仅仅是简单的去掉 script 标签。每个 DOM 节点的事件都能执行 js 代码

CSRF

  • 跨站请求伪造通常缩写为 CSRF 或者 XSRF， 是一种挟制用户在当前已登录的 Web 应用程序上执行非本意的操作的攻击方法。
  • 冒充用户发起请求（在用户不知情的情况下, 完成一些违背用户意愿的请求(如恶意发帖，删帖，改密码，发邮件等)。
  • CSRF 更偏向于一个攻击结果，只要发起了冒牌请求那么就算是 CSRF 了。
  • CSRF 利用的是网站对于用户浏览器的信任
  1. 登录受信任的网页 A,并在本地生成 Cookie
  2. 在不登出网页 A 的情况下(并且是在同一个浏览器中), 访问危险网页 B。B 网页通过一些方式来诱导用户点击恶意链接。该链接能够生成对 A 网站服务器 的请求, 并且这个请求是在用户的浏览器中发出的，这个请求会附带用户浏览器中的 cookie 信息。

预防 CSRF

  • 黑客只是利用用户浏览器中的 cookie 信息来伪造用户进行请求，但是黑客并不会知道 cookie 中的信息包含什么。
  1. 服务器端判断 referer 这个字段，如果不是自己的网站，就返回错误。
  2. CSRF Token 方法， Token 是服务器端生成的字符串。存储在客户端中。每次客户端请求的时候就会在请求中带上 Token 值。如果请求中的 Token 值和服务器端中的 Token 值对应不上，则请求失败。

XSS 的常见类型

  • 存储型 XSS：攻击者的脚本被保存到目标服务器（例如数据库、评论区），后续访问页面的用户都会取回并执行这段脚本
  • 反射型 XSS：恶意代码随请求参数提交给服务器，服务器在错误信息、搜索结果等响应中把它反射回浏览器执行
  • 基于 DOM 的 XSS：载荷在受害者浏览器中通过修改 DOM 环境被执行，页面响应本身没有变化，但原有脚本以意外的方式运行
  • 三类 XSS 的共同点是网站接受了攻击者构造的输入，并且在未做净化的情况下把它放进页面
  • 注入脚本运行在受害者浏览器中，可以读取页面内容和本地存储，并以用户身份向站点发起请求
  • DOM 型 XSS 的载荷不经过服务器反射，直接由前端脚本把不可信数据写进可执行位置，服务端日志里可能看不到完整载荷
  • 反射型 XSS 通常需要诱导用户点击特制链接，载荷只在单次响应中出现
  • 存储型 XSS 危害面更大，恶意内容会被后续所有访问该页面的用户执行

输出编码与净化

  • 把用户输入渲染到页面前，需要按所处上下文（文本、HTML 标签内、属性内、URL 内）做对应的转义编码，而不是只过滤 script 标签
  • 事件属性、javascript: 链接、内联脚本等位置都可能执行脚本，单纯删除标签名不能覆盖全部注入点
  • 输入净化和输出编码是第一道防线，CSP 是在防线失效后阻止恶意脚本执行的补充措施
  • 防御通常分三层：输入侧校验与净化、输出侧按上下文编码、传输侧用 CSP 限制脚本执行范围
  • XSS 防御不能只依赖服务端过滤，前端渲染时的上下文编码同样关键

内容安全策略 CSP

  • CSP 通过 Content-Security-Policy 响应头向浏览器下发指令，限制文档可以加载哪些来源的资源
  • script-src 控制 JavaScript 来源，style-src 控制样式表来源，img-src 控制图片来源，未单独列出的资源类型由 default-src 兜底
  • 除脚本来源外，CSP 还可以限制样式表、图片、字体、iframe 等资源的加载位置
  • 严格的 CSP 可以禁止内联事件处理器、javascript: URL 和 eval() 一类危险接口，只放行带 nonce 或哈希的脚本
  • CSP 指令之间用分号分隔，每个指令由名称和允许的来源值组成
  • CSP 也可以通过文档的 meta 标签声明，但 meta 方式不支持全部 CSP 指令
  • 设置 CSP 不能替代输入净化，两者应当配合使用形成纵深防御

CSRF 的补充防御

  • 当网站只靠 Cookie 识别登录用户，而请求参数又可以被攻击者预测时，就存在 CSRF 风险
  • CSRF 伪造的请求会自动携带浏览器中与目标站点关联的 Cookie，攻击者看不到 Cookie 内容
  • CSRF Token 由服务器生成并随页面下发，敏感请求必须携带与服务端记录一致的 Token，攻击者无法从 Cookie 中读到这个值
  • Cookie 的 SameSite 属性限制跨站请求是否携带 Cookie：Strict 只在同站请求发送，Lax 额外放行安全方法的顶层导航，None 允许跨站携带但必须同时设置 Secure
  • SameSite=Lax 是部分浏览器的默认值；未显式设置时行为因浏览器而异
  • HttpOnly 属性让 Cookie 不被前端脚本读取，可以降低 XSS 窃取会话 Cookie 的风险
  • 校验 Origin 或 Referer 头可以识别请求是否来自本站，Origin 头携带协议和站点信息，Referer 头携带完整来源地址
  • 这两类头在某些浏览器策略或场景下可能被省略，只能作为辅助防线，通常与 Token 方案配合使用
  • 业务操作请求使用 POST 等非安全方法，并配合 CSRF Token 校验

防御措施的组合落地

  • 存储型 XSS 的入库内容在输出到页面前同样需要编码，不能因为已入库就省略转义
  • 反射型 XSS 的参数会出现在 URL 或表单提交中，服务端回显时需要按上下文编码
  • 过滤输入不能替代输出编码：输入可能经过解码、换行拆分或编码变形后再次进入页面
  • CSP 可以按资源类型分别指定来源，未被具体指令覆盖的资源类型回退到 default-src
  • 除脚本外，样式表和图片等资源来源也可能被用来植入攻击内容
  • CSRF 攻击成立的前提是请求可以修改服务器状态，纯读取类 GET 请求一般不构成伪造风险
  • 带 Token 的请求还要校验 Token 与当前会话绑定，避免 Token 被跨会话复用
  • Cookie 设置 Secure 后只在 HTTPS 连接上发送，明文 HTTP 不会携带该 Cookie
  • 敏感操作应校验请求方法和业务参数，而不是只检查 Cookie 是否存在
  • 防御措施需要分层落地：输入校验、输出编码、Cookie 属性、CSP 响应头相互配合
