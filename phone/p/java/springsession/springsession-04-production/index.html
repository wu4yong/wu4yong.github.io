生产实践：容量、灰度与故障排查

会话层是”平时没人看、出事全站挂”的组件。这一篇把生产上真正会遇到的几件事列清：容量怎么估、Redis 掉了会怎样、灰度上线怎么不踢人、日志里该看什么。

会话流量与缓存池的容量管理

1.3 灰度发布不踢人

新版本要改 Session 里存的数据结构时，滚动发布会导致”旧格式读不出来 → 全员掉登录”。

风险

推荐”兼容读取 + 双写”：上线期新老两版同时能解析，等旧会话自然过期后再删兼容代码。

1.6 与网关、鉴权的衔接

  • 网关做鉴权时不要自己解析 Session，让它透传到下游，避免两套解析逻辑
  • 网关若用 SESSION Cookie 做限流 key，注意隐私与泄漏风险
  • Feign 跨服务调用不自动带 Cookie，需要显式传递（或用 token 方案）
// Feign 透传 Cookie
template.header("Cookie", request.getHeader("Cookie"));

1.9 清单

  1. 会话实例与业务缓存分开，避免被 LRU 淘汰
  2. 容量按”在线数 × 平均会话大小”估，写入量看属性数量与 flush-mode
  3. 改数据结构时用”兼容读取 + 双写”，别直接换格式
  4. 401 突增先查 Cookie 的 SameSite / domain / secure
  5. 登录后 changeSessionId()，防会话固定攻击
  6. 网关不重复解析会话，Feign 需显式透传 Cookie
  7. 会话 key 数与 save 耗时是最该盯的两个指标
