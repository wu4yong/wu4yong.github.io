Spring Boot（七）内部工作流程

分类：java · springboot ｜ 标签：SpringBoot

掌握 Spring Boot 内部工作流程

SpringApplication.run() 那一行背后有十几个步骤，搞清顺序就能回答很多”为什么”：为什么 @PostConstruct 比 CommandLineRunner 早？为什么 Tomcat 是在 refresh 阶段启动的？为什么监听器能拿到”启动完成”事件？这一篇按源码顺序走一遍。

启动流程的四个关键阶段：环境准备、上下文创建、刷新、事件发布

1.1 入口：三个构造函数阶段

    SpringApplication.run(DemoApplication.class, args);

1.3 refresh 内部：Bean 与容器

refresh 实际调用 AbstractApplicationContext.refresh()，展开后是 Spring 那套经典流程：

  1. prepareRefresh：记录启动时间、初始化占位属性
  2. obtainFreshBeanFactory：拿到 BeanFactory
  3. prepareBeanFactory：注册 ApplicationContext 等可注入对象
  4. postProcessBeanFactory：子类扩展（Servlet 上下文在这里注册 request/session 作用域）
  5. invokeBeanFactoryPostProcessors：处理 @Configuration、@ComponentScan、自动配置
  6. registerBeanPostProcessors：注册 BeanPostProcessor（AOP、@Autowired 注入都靠它）
  7. onRefresh：Servlet 容器在这里创建并启动 Tomcat
  8. registerListeners：注册监听器
  9. finishBeanFactoryInitialization：实例化所有非懒加载单例（你的 @Service 在这一步被创建）
  10. finishRefresh：发布 ContextRefreshedEvent、启动 LifecycleProcessor（SmartLifecycle 组件开始工作）

所以 Tomcat 启动早于业务 Bean 实例化，但端口真正开始对外服务是在 finishRefresh 之后——这解释了为什么”日志里 Tomcat started 了，但接口还没通”。

1.6 调试启动流程

# 1. 条件评估报告（看自动配置为什么生效/不生效）
java -jar demo.jar --debug

# 2. 打开 Spring 内部日志
java -jar demo.jar --logging.level.org.springframework=DEBUG

# 3. IDE 里断点打在这三处最有效
#   SpringApplication.run
#   AbstractApplicationContext.finishBeanFactoryInitialization
#   ServletWebServerApplicationContext.onRefresh

--debug 输出的 “Condition evaluation report” 会分 Positive / Negative matches 两栏，把每个自动配置类的判定条件列出来，是排查”Bean 没装上”的首选手段。

1.7 实际能用上的三个推论

  1. @PostConstruct 里别做远程调用：它在 Bean 初始化阶段，一堆 Bean 还没好，失败会直接导致启动失败
  2. 预热逻辑放 CommandLineRunner：此时容器已就绪，但还没接流量（ApplicationStartedEvent 之后、ReadyEvent 之前）
  3. 健康检查依赖 /actuator/health：它就是靠 ApplicationReadyEvent 之后的状态判断，别在 StartedEvent 时就宣布成功

1.9 清单

  1. SpringApplication.run 主线：准备环境 → 建上下文 → refresh → 事件 → runners
  2. Tomcat 在 onRefresh 创建，业务 Bean 在 finishBeanFactoryInitialization 实例化
  3. ApplicationStartedEvent 时端口已监听，ApplicationReadyEvent 时才算可接流量
  4. Bean 生命周期顺序：构造 → 注入 → @PostConstruct → afterPropertiesSet → AOP → @PreDestroy
  5. 五个扩展点里，CommandLineRunner 和 ApplicationListener 最实用
  6. --debug 的条件评估报告是排查自动配置的利器
  7. 预热逻辑放 runner，远程调用别放 @PostConstruct
