Spring Boot（五）线上灵活配置

分类：java · springboot ｜ 标签：SpringBoot

解决线上灵活配置

“配置改一下就要重新发版”是很常见的痛点。Spring Boot 提供了三种能力来解决：外部化配置（不改包就能改）、类型安全绑定（@ConfigurationProperties）、动态刷新（改完不重启）。这一篇把这三件事讲透，并给出敏感配置的处理办法。

配置文件外置、远程下发、热刷新三步走

1.1 属性绑定：@Value 该退场了

散落的 @Value 有三个问题：字符串硬编码、没有校验、IDE 无法跳转。

// 老写法
@Value("${app.pool.size:10}")
private int poolSize;
// 推荐：整块绑定
@Data
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    private String name = "demo";
    private Pool pool = new Pool();

    @Data
    public static class Pool {
        private int size = 10;
        private Duration timeout = Duration.ofSeconds(3);
    }
}

注册有两种方式：

// 1. 启动类上开扫描（2.3+，推荐）
@SpringBootApplication
@ConfigurationPropertiesScan
public class DemoApplication { }

// 2. 在配置类上显式开启
@Configuration
@EnableConfigurationProperties(AppProperties.class)
public class AppConfig { }

@ConfigurationProperties 的四个隐性好处：松散绑定（pool-size / poolSize / POOL_SIZE 都能绑）、类型转换（Duration、DataSize、List 自动转）、JSR-303 校验、IDE 元数据提示（spring-boot-configuration-processor）。

1.2 校验与默认值

@Data
@Validated                                  // 开启校验
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    @NotBlank
    private String name = "demo";

    @Min(1) @Max(64)
    private int maxConn = 8;

    @DurationMin(seconds = 1)
    private Duration timeout = Duration.ofSeconds(3);
}

启动时配置不合法会直接失败，比”跑到一半才发现连接池大小是 0”强得多。要引入 spring-boot-starter-validation。

jar 外配置的标准写法：

java -jar demo.jar \
  --spring.config.additional-location=file:/opt/app/config/ \
  --spring.profiles.active=prod

additional-location 是”追加”，jar 内的配置仍会加载并与外部合并（外部优先）；spring.config.location 则是”替换”，jar 内的不再生效——线上一般用前者。

也可以用固定目录约定：Spring Boot 默认会找 ./config/、./、classpath:/config/、classpath:/ 四处，所以把 application-prod.yml 丢到 jar 同级的 config/ 里就能生效，连参数都不用加。

1.4 环境变量：容器里的正解

spring:
  datasource:
    url: jdbc:mysql://${DB_HOST:127.0.0.1}:${DB_PORT:3306}/demo
    username: ${DB_USER}
    password: ${DB_PWD}

${KEY:default} 是”取不到就用默认值”，${KEY} 取不到会启动失败——敏感项刻意不给默认值，强制运维注入。

环境变量的命名转换规则：app.pool.size → APP_POOL_SIZE（点变下划线、全大写）。容器里 docker run -e APP_POOL_SIZE=20 即可。

1.5 动态刷新

不重启改配置，取决于配置从哪里来：

方式
是否需要重启
适用
改 jar 外文件（不刷新）
要重启
简单可靠
Spring Cloud Config + @RefreshScope
不用
微服务体系内
Nacos / Apollo 配置中心
不用（配合监听）
企业主流
Actuator refresh 端点（Spring Cloud Context）
不用
单体应用也可以接

@RefreshScope 的语义是”这个 Bean 在配置变更时被销毁重建”：

@RefreshScope                     // 需要 spring-cloud-context
@Component
public class DynamicHolder {
    @Value("${app.dynamic.value:default}")
    private String value;

    public String get() { return value; }
}

代价是：它只对重新创建时重新绑定的 @Value 生效，普通 @ConfigurationProperties 对象不会自动更新；而且每次刷新都重建 Bean，持有状态的组件不要随便标。

判断标准：改完要不要紧盯着生效。要紧盯的就不能放 jar 里。

1.8 常见坑

  1. ${KEY} 没设默认值，容器少了变量直接启动失败（本地能跑、线上起不来）
  2. @ConfigurationProperties 类没加 @Component 也没开扫描 → 不生效
  3. 松散绑定把 app.max-conn 和 app.maxConn 当成两个配置，Map 类型尤其容易混
  4. 用了 spring.config.location 覆盖，jar 内公共配置全丢，启动报”找不到数据源”
  5. @RefreshScope 标在单例状态类上，刷新后状态丢失
  6. 把密码写在 application.yml 里提交到仓库——最难恢复的事故

1.10 清单

  1. 弃用散落的 @Value，改用 @ConfigurationProperties 整块绑定
  2. 开 @ConfigurationPropertiesScan，配置类不用逐个注册
  3. 加上 @Validated + JSR-303，让非法配置在启动时就失败
  4. jar 外 config/ 目录 + additional-location 是”不改包改配置”的标准做法
  5. 敏感项用 ${KEY} 不给默认值，避免本地默认值带进生产
  6. 高频开关走配置中心 + @RefreshScope，别放 yml
  7. 密码一律加密或环境变量注入，绝不进仓库
