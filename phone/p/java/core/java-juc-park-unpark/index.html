Park/Unpark 线程阻塞与唤醒

Wait/Notify 必须配合 Monitor 锁使用，而且只能”随机唤醒一个”，限制不少。JUC 提供了另一套更灵活的阻塞唤醒工具：
LockSupport.park() 和 LockSupport.unpark(Thread)。它不依赖任何锁对象，能精确唤醒指定线程，还允许”先唤醒、后等待”。
ReentrantLock、Semaphore、CountDownLatch 等 AQS 组件底层的阻塞唤醒，用的都是它。

6.1 通俗小故事：停车场的通行证

把线程比作一辆要进停车场的车，park 是”没证就在闸机前等”，unpark 是”给你发一张通行证”：

● 车开到闸机前，手里没有通行证，只能停着等（调用 park，线程进入 WAITING）
● 管理员递上一张通行证（调用 unpark），车凭这张证抬杆通过（park 立即返回）
● 通行证只有”有 / 没有”两种状态，不会累积：连发两张，过闸机时只消耗一张，多出来的那张不算数
● 车可以先领证、后到场：先发证，车来了不用等，直接抬杆
● 车在等的时候被人按喇叭催（线程被 interrupt），也会先返回，之后再自己判断还要不要继续办

这张”通行证”，在底层就是 Parker 对象里的一个 _counter 许可位（0 或 1）。

6.2 核心 API 与语义

LockSupport 是 java.util.concurrent.locks 包下的工具类，方法全是静态的，日常用的就这几个：

LockSupport.park()：阻塞当前线程，直到拿到许可或被中断。调用时若许可已经是 1，则立即消耗许可并返回，不阻塞；

LockSupport.park(Object blocker)：语义同上，额外记录一个”阻塞对象”，只在 jstack 诊断时标明线程卡在谁身上；

LockSupport.parkNanos(long nanos) / LockSupport.parkUntil(long deadline)：限时阻塞，超时自动返回，期间也可以被 unpark 提前唤醒；

LockSupport.unpark(Thread thread)：给指定线程发放许可。目标线程正在 park 就被唤醒；它还没 park 时，许可先存着，等它下次 park 直接放行。

和 wait/notify 相比，最关键的三点差别：不需要持有锁、能指定唤醒哪个线程、唤醒可以先于等待发生。

6.3 底层原理：一个许可位 + Unsafe

每个 Java 线程在 JVM 里都挂着一个 Parker 对象，核心就是一个 _counter 许可位（0 或 1）加一把互斥量和条件变量。

park 流程：先原子读取 _counter，若大于 0，就 CAS 成 0 并直接返回（相当于”有证直接过闸机”）；若是 0，则把自己挂到条件变量上等待，真正让出 CPU。

unpark 流程：把目标线程的 _counter 置为 1（不累加，重复 unpark 仍然是 1）；若目标线程正挂在条件变量上，就唤醒它。

最终都落到 sun.misc.Unsafe.park() / Unsafe.unpark() 两个 native 方法，走操作系统层面的互斥量和条件变量，阻塞期间不占 CPU 时间片。

理解了许可位，后面那些”看起来反直觉”的现象就都能解释：为什么先 unpark 后 park 也生效、为什么 unpark 两次只能过一次 park、为什么 park 不抛 InterruptedException 却会被打断。

6.4 与 wait/notify 的对比

两者解决的都是”线程等条件”，但实现路径完全不同，逐项对一下：

● 依赖锁：wait/notify 必须在 synchronized 内调用，否则抛 IllegalMonitorStateException；park/unpark 不依赖任何锁，随处可调
● 唤醒精度：notify 只能从 WaitSet 里随机挑一个唤醒；unpark 精确指定某个线程
● 顺序要求：wait/notify 必须先 wait 后 notify，通知发早了就丢失；park/unpark 可以先 unpark 后 park，许可会保留
● 线程状态：两者都进入 WAITING / TIMED_WAITING，区别是 wait 挂在对象的 WaitSet 上，park 挂在当前线程的 Parker 上
● 中断表现：wait 抛 InterruptedException 必须捕获；park 直接返回、不抛异常，但中断标记保留，需要自己判断

一句话总结：wait/notify 是绑在锁上的协作机制，park/unpark 是独立于锁的线程调度原语，AQS 系列组件全部基于后者。

6.5 代码实战

6.5.1 最基本的一对一唤醒

主线程睡 1 秒后唤醒子线程，验证 park 阻塞与 unpark 放行的基本配对：

public static void main(String[] args) throws InterruptedException {
    Thread t1 = new Thread(() -> {
        log.debug("t1 开始执行");
        LockSupport.park();          // 没有许可，阻塞在这里
        log.debug("t1 被唤醒，继续执行");
    }, "t1");
    t1.start();

    Thread.sleep(1000);
    log.debug("主线程调用 unpark");
    LockSupport.unpark(t1);
}

6.5.2 先 unpark 再 park：许可会保留

这是 wait/notify 做不到的：先发证、后到场，线程 park 时直接通过，不会阻塞。

public static void main(String[] args) throws InterruptedException {
    Thread t1 = new Thread(() -> {
        log.debug("t1 准备 park，此时许可已经是 1");
        LockSupport.park();          // 直接返回，不阻塞
        log.debug("t1 没有阻塞，直接通过");
    }, "t1");

    LockSupport.unpark(t1);          // 线程还没启动就先发许可
    Thread.sleep(2000);

    t1.start();
}
11:05:02.183 [t1] c.TestPark - t1 准备 park，此时许可已经是 1
11:05:02.183 [t1] c.TestPark - t1 没有阻塞，直接通过

6.5.3 许可不累积：unpark 两次只能过一次 park

许可只是一个 0/1 标志位，不是计数器。连续 unpark 两次，第二次 park 依然会阻塞。

public static void main(String[] args) throws InterruptedException {
    Thread t1 = new Thread(() -> {
        LockSupport.park();
        log.debug("第一次 park 通过");
        LockSupport.park();          // 许可已被上一次消耗，这里会再次阻塞
        log.debug("第二次 park 通过");
    }, "t1");
    t1.start();

    Thread.sleep(1000);
    LockSupport.unpark(t1);          // 第一次通知
    LockSupport.unpark(t1);          // 第二次通知，但许可不会变成 2
}
11:07:41.266 [t1] c.TestPark - 第一次 park 通过

输出只有一行，线程卡在第二次 park 上，正好验证许可上限为 1。

6.5.4 中断响应：不抛异常，但会返回

park 被 interrupt 打断时不抛 InterruptedException，而是正常返回，并且中断标记会保留，需要自己判断是否收工。

public static void main(String[] args) throws InterruptedException {
    Thread t1 = new Thread(() -> {
        log.debug("t1 开始 park");
        LockSupport.park();
        log.debug("t1 已被打断，中断标记：{}", Thread.currentThread().isInterrupted());
    }, "t1");
    t1.start();

    Thread.sleep(1000);
    t1.interrupt();                  // 打断等待中的线程
}
11:09:30.885 [t1] c.TestPark - t1 开始 park
11:09:31.888 [t1] c.TestPark - t1 已被打断，中断标记：true

如果希望被打断后不再往下走，要在 park 之后自己判断：

LockSupport.park();
if (Thread.currentThread().isInterrupted()) {
    log.debug("检测到中断，放弃后续任务");
    return;
}

6.5.5 限时等待：parkNanos / parkUntil

不想无限期阻塞时用带超时的版本，超时自动返回：

public static void main(String[] args) {
    Thread t1 = new Thread(() -> {
        long start = System.currentTimeMillis();
        LockSupport.parkNanos(TimeUnit.SECONDS.toNanos(2));   // 最多等 2 秒
        long cost = System.currentTimeMillis() - start;
        log.debug("parkNanos 返回，等待耗时 {} ms", cost);
    }, "t1");
    t1.start();
}
11:12:05.402 [t1] c.TestPark - parkNanos 返回，等待耗时 2013 ms

parkUntil(long deadline) 用法一致，只是把”等多久”换成”等到某个时间点”（毫秒时间戳）。

6.5.6 实战：park/unpark 实现三个线程交替打印

同样的事情用 wait/notify 要做三把锁加循环判断，用 park/unpark 只需按名字互发许可：

static Thread t1, t2, t3;

public static void main(String[] args) {
    t1 = new Thread(() -> {
        LockSupport.park();
        System.out.print("a");
        LockSupport.unpark(t2);
        LockSupport.park();
        System.out.print("a");
    }, "t1");

    t2 = new Thread(() -> {
        LockSupport.park();
        System.out.print("b");
        LockSupport.unpark(t3);
        LockSupport.park();
        System.out.print("b");
    }, "t2");

    t3 = new Thread(() -> {
        LockSupport.park();
        System.out.print("c");
        LockSupport.unpark(t1);
        LockSupport.park();
        System.out.print("c");
    }, "t3");

    t1.start();
    t2.start();
    t3.start();

    LockSupport.unpark(t1);          // 先放行 t1，之后靠链式唤醒
}

6.6 和 AQS 的关系

ReentrantLock.lock() 抢不到锁时，最终就是调用 LockSupport.park(this) 把线程挂起；unlock() 释放锁后，AQS 从等待队列里取出后继节点，调用 LockSupport.unpark(node.thread) 把它唤醒。
Semaphore、CountDownLatch、CyclicBarrier、读写锁的阻塞唤醒链路都是同一套。所以吃透 park/unpark，等于拿到了读懂 AQS 源码的钥匙。

6.7 常见坑

● 误以为许可可以累积：unpark 调 N 次也只算 1 个许可，多出来的通知直接丢弃；
● park 之后不检查中断标记：park 被打断只是返回，不会说明原因，要自己 isInterrupted() 判断；
● 自旋等待里不给退出条件：自己实现等待循环时，务必配合超时或状态检查，否则容易永久挂住；
● 把 blocker 参数当锁用：park(Object blocker) 的 blocker 只写进线程的 parkBlocker 字段供 jstack 排查，不参与任何同步语义；
● 条件判断漏了可见性：park/unpark 不涉及锁，共享条件变量仍然要靠 volatile 或加锁保证可见性。
