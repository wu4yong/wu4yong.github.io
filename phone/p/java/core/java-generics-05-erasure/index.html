Java 泛型（五）类型擦除

分类：java · core ｜ 标签：Java

类型擦除

上一篇讲”不能写”时，原因都指向同一处：类型擦除。泛型信息只活在编译期，编译完成后 List<String> 和 List<Integer> 在字节码里是同一个 List，元素类型退化为上界（无界就是 Object）。理解擦除，才能看懂桥方法、才能解释编译器给你插的那几行 checkcast。

类型擦除：尖括号里的类型在编译后被擦掉，只剩上界

1.1 擦除的三条规则

声明
擦除后的实际类型
T（无上界）
Object
T extends Number
Number
T extends Comparable<T>
Comparable
T extends Serializable & Comparable<T>
Serializable（第一个上界）
List<T>
List
List<? extends Number>
List（元素的静态类型是 Number）

也就是说：尖括号里的东西在运行期全部消失，只留下上界。

1.2 用字节码验证

public class ErasureDemo {
    public <T> T first(List<T> list) {
        return list.get(0);
    }
}

反编译：

javac ErasureDemo.java && javap -c -p ErasureDemo.class
public java.lang.Object first(java.util.List);
  Code:
     0: aload_1
     1: iconst_0
     2: invokeinterface #2, 2      // InterfaceMethod java/util/List.get:(I)Ljava/lang/Object;
     7: areturn

三条证据：

  1. 方法签名里的 List<T> 变成了 java.util.List（参数类型擦除）
  2. 返回值 T 变成了 java.lang.Object（无界 → Object）
  3. 方法体里没有转型：因为是 Object 返回

再看调用方就懂了：

ErasureDemo d = new ErasureDemo();
String s = d.first(list);        // 编译器在这里插 checkcast
invokevirtual  // Method first:(Ljava/util/List;)Ljava/lang/Object;
checkcast     #5  // class java/lang/String      ← 编译器自动插入

所以”泛型不需要强转”只是源码层面的错觉，字节码里转了一次，只是你不用写。

1.3 桥方法：多态与擦除的妥协

擦除会破坏重写关系。看这个例子：

public class StringBox extends Box<String> {   // Box<T> 里 public T get()
    @Override
    public String get() { return "x"; }
}

Box.get() 擦除后是 Object get()，而子类写的是 String get()——签名不一致，多态就断了。编译器的解法是自动生成一个桥方法：

javap -c -p StringBox.class
public java.lang.String get();
  ...
public java.lang.Object get();          // 桥方法（bridge），synthetic
  Code:
     0: aload_0
     1: invokevirtual  // Method get:()Ljava/lang/String;
     4: areturn

桥方法的存在导致一个经典现象：反射拿到的同名方法有两个。

for (Method m : StringBox.class.getDeclaredMethods()) {
    System.out.println(m.getName() + " -> " + m.getReturnType()
            + (m.isBridge() ? " [bridge]" : ""));
}
// get -> class java.lang.String
// get -> class java.lang.Object [bridge]

这也是 getDeclaredMethod("get") 偶尔抛 NoSuchMethodException 或拿到桥方法的原因——要按参数类型和 isBridge() 过滤。

1.4 擦除带来的六个”不能”

class Demo<T> {
    // 1. 不能 new 类型参数
    // T t = new T();

    // 2. 不能拿类型参数的 class
    // Class<T> c = T.class;

    // 3. 不能 instanceof
    // if (o instanceof T) {}

    // 4. 不能创建泛型数组
    // T[] arr = new T[10];

    // 5. 不能对静态成员用类级类型参数
    // static T shared;

    // 6. 不能捕获多个泛型异常类型
    // catch (MyException<T> e) {}
}

根本原因都一样：运行期不知道 T 是什么。

绕过方式统一是”把类型信息显式传进来”：

class Box<T> {
    private final Class<T> type;                 // 用字段记住类型
    public Box(Class<T> type) { this.type = type; }

    public T create() throws Exception {
        return type.getDeclaredConstructor().newInstance();   // 反射构造
    }

    public boolean is(T t) { return type.isInstance(t); }     // 替代 instanceof

    @SuppressWarnings("unchecked")
    public T[] newArray(int n) {
        return (T[]) Array.newInstance(type, n);              // 反射建数组
    }
}

这也是为什么泛型工具类经常要一个 Class<T> 参数：擦除掉的类型信息，只能从外面补回来。

1.5 泛型信息到底丢了多少

不是全丢。编译器会把泛型签名写进 class 文件的 Signature 属性，反射可以读到：

public class Repo extends Base<Order> { }

// 运行时仍能读到父类的泛型实参
ParameterizedType pt = (ParameterizedType) Repo.class.getGenericSuperclass();
System.out.println(pt.getActualTypeArguments()[0]);   // class Order

1.6 为什么一定要擦除

历史原因只有一个：向后兼容。

Java 5 引入泛型时，ArrayList、HashMap、Collections 已经被大量使用，还有第三方库的二进制 jar。如果改成”每个实例化生成一份代码”（像 C++ 模板），老代码和老 class 文件全部作废，整个生态要重编。

擦除让 List<String> 与老的 List 二进制兼容：老代码看到的是 List，新代码多一层编译期检查。代价就是我们这一篇列的所有限制。

1.7 一个常见误区：getClass() 相同

List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
System.out.println(a.getClass() == b.getClass());   // true

两者在运行期是同一个 ArrayList 类。所以在泛型容器上做”类型判断”是无效操作：

// 错误做法：以为能区分
if (list instanceof List<String>) { }        // 编译错误

// 正确做法：靠 Class<T> 校验元素，或者干脆在设计上避免

1.8 清单

  1. 擦除规则：无界 → Object，有界 → 第一个上界
  2. 字节码里 List<T> 就是 List，T 就是 Object/上界
  3. 源码里看不到的转型，是编译器插入的 checkcast
  4. 子类重写泛型方法会生成桥方法，反射里同名方法会有两个
  5. 不能 new T()、T.class、instanceof T、new T[]——都因为运行期不知道 T
  6. 补类型信息的标准做法：构造函数/方法传 Class<T>
  7. Signature 属性保留了泛型声明，反射能读，方法体里的类型读不到
  8. 擦除是为兼容 Java 5 之前的老集合，代价就是这一整篇的限制
