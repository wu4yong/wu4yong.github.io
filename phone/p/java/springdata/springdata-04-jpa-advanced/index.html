Spring Data（四）事务、审计与批量处理

分类：java · springdata ｜ 标签：SpringData

事务边界、审计字段与批量写入

JPA 跑通不难，难的是”事务边界划在哪、审计字段谁填、一万条数据怎么插得快”。这一篇只讲这三件在生产里最容易出问题的事。

事务链环绕数据源，锁与批量写入并存

1.1 事务边界

@Service
public class OrderService {

    @Transactional(rollbackFor = Exception.class)
    public void create(OrderDTO dto) {
        orderRepository.save(order);          // 不提交
        stockRepository.deduct(dto);          // 不提交
    }                                          // 方法结束才 commit
}
要点
说明
rollbackFor = Exception.class
默认只回滚 RuntimeException，受检异常不回滚
方法必须是 public
代理拦截，private/同类内部调用失效
事务内不要做远程调用
连接被长时间占用
事务内不要开线程
新线程不共享事务上下文

自调用失效：同类内部 this.method() 绕过了代理，@Transactional 不生效。要么拆到另一个 Bean，要么注入自身代理（AopContext.currentProxy()）。

1.2 只读事务

@Transactional(readOnly = true)
public List<Order> list() { ... }

readOnly 让 Hibernate 关闭脏检查（dirty checking），查询列表场景能省掉一次全量比对，性能提升在实体多时很明显。

1.3 审计字段

@EntityListeners(AuditingEntityListener.class)
@MappedSuperclass
public abstract class BaseEntity {
    @CreatedDate
    private LocalDateTime createdAt;
    @LastModifiedDate
    private LocalDateTime updatedAt;
    @CreatedBy
    private String createdBy;
    @LastModifiedBy
    private String updatedBy;
}
@EnableJpaAuditing(auditorAwareRef = "auditorProvider")
@Configuration
public class JpaConfig {
    @Bean
    public AuditorAware<String> auditorProvider() {
        return () -> Optional.ofNullable(SecurityContextHolder.getContext())
                .map(SecurityContext::getAuthentication)
                .map(Authentication::getName);
    }
}
注解
触发时机
注意
@CreatedDate
insert 前
字段类型用 LocalDateTime
@LastModifiedDate
update 前
与 @Version 不同，这是时间戳
@CreatedBy
insert 前
需要 AuditorAware
@LastModifiedBy
update 前
同上

忘了 @EnableJpaAuditing 的后果是字段永远为 null，且不报错。

1.4 乐观锁

@Version
private Integer version;
场景
行为
两个事务同时更新
后提交者抛 OptimisticLockException
读多写少
几乎无冲突，推荐
写冲突频繁
需要业务层重试
try {
    repo.save(entity);
} catch (OptimisticLockException e) {
    // 重新查询最新数据，重算后重试
}

乐观锁解决的是”覆盖写”，不是”并发写”——高冲突业务该用悲观锁（@Lock(LockModeType.PESSIMISTIC_WRITE)）或数据库行锁。

1.5 批量插入

JPA 单条 save 一万条会慢到不可接受（每条一条 insert + 一次 flush 检查）。正确姿势：

spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 500              # 每 500 条发一批
        order_inserts: true
        order_updates: true
@Service
public class BatchService {
    @PersistenceContext
    private EntityManager em;

    @Transactional
    public void batchInsert(List<User> users) {
        for (int i = 0; i < users.size(); i++) {
            em.persist(users.get(i));
            if (i % 500 == 0) {
                em.flush();
                em.clear();          // 释放一级缓存，防止内存爆
            }
        }
    }
}
关键点
原因
batch_size
合并成多值 insert
order_inserts
相同 SQL 归并，才能凑批
em.flush() + em.clear()
控制内存与批大小
用 IDENTITY 主键
会退化成逐条插入，批量场景要换

一万条数据在 MySQL + IDENTITY 下可能 40 秒，换成 SEQUENCE/雪花 ID + 批量参数后能到 2 秒级。

1.6 只读大批量导出

@Transactional(readOnly = true)
public void export() {
    try (Stream<User> stream = userRepository.streamAllBy()) {
        stream.forEach(this::writeLine);
    }
}

Stream 查询是游标式读取，不把整个结果集放进内存。必须 try-with-resources 关闭，否则连接不释放。

1.7 常见坑

  1. @Transactional 写在 Controller 上 → 事务范围过大，远程调用也包在事务里
  2. 事务内 save 后立即查列表 → 可能读到一级缓存旧值，需 flush
  3. 审计字段类型用 Date → 时区混乱，统一 LocalDateTime
  4. 批量 save 没用 EntityManager → Hibernate 无法攒批
  5. @Version 字段被 DTO 覆盖为 null → 更新时丢失乐观锁保护

1.9 清单

  1. @Transactional 放 Service，rollbackFor = Exception.class
  2. 同类自调用会绕过代理，事务失效
  3. 查询列表加 readOnly = true，省掉脏检查
  4. 审计字段必须配 @EnableJpaAuditing，否则静默为 null
  5. @Version 防覆盖写，冲突要业务层重试
  6. 批量插入必须配 batch_size + order_inserts，并定期 flush/clear
  7. 大批量导出用 Stream 查询并确保关闭
