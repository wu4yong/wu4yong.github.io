派生查询、JPQL 与 Specification

四层查询手段从简到繁：方法名派生 → @Query → Specification → 原生 SQL。选错了要么写得又长又不可读，要么把 “简单查询” 变成”维护不动的手写 SQL”。

方法名、过滤条件与分页组合成一次查询

1.2 派生查询的边界

List<Order> findByUserIdAndStatusOrderByCreatedAtDesc(Long userId, String status);

能写，但已经不好读了。经验阈值：条件 ≥ 4 个、或出现 Or 嵌套、或需要 join，换手段。

1.3 @Query（JPQL）

// 单表 + 参数
@Query("select u from User u where u.status = :status and u.age > :age")
List<User> findActiveAdults(@Param("status") String status, @Param("age") Integer age);

// join fetch 解决 N+1
@Query("select o from Order o join fetch o.user where o.status = :status")
List<Order> findWithUser(@Param("status") String status);

// 更新（必须配 @Modifying 与事务）
@Modifying
@Transactional
@Query("update User u set u.status = :status where u.id = :id")
int updateStatus(@Param("id") Long id, @Param("status") String status);
要点
说明
:param
命名参数，配 @Param
?1
位置参数，少用
u.status
用实体字段名，不是列名
@Modifying
增删改必须加，否则被当成查询
clearAutomatically
更新后清一级缓存，避免读到旧值

批量更新后要 entityManager.clear()（或 @Modifying(clearAutomatically = true)），否则同一事务里再查还是旧数据。

1.4 原生 SQL

@Query(value = "select * from tb_order where amount > ?1", nativeQuery = true)
List<Order> findBigOrders(BigDecimal amount);

// 返回投影（不返回实体）
@Query(value = "select status, count(*) as cnt from tb_order group by status", nativeQuery = true)
List<Object[]> countByStatus();

原生的代价：不参与实体缓存、字段改名不报错、分页要自己处理。只在需要数据库专有语法（窗口函数、特定索引提示）时使用。

1.5 Specification：动态条件

public class OrderSpecs {
    public static Specification<Order> status(String status) {
        return (root, query, cb) ->
                status == null ? null : cb.equal(root.get("status"), status);
    }

    public static Specification<Order> amountBetween(BigDecimal min, BigDecimal max) {
        return (root, query, cb) -> {
            if (min == null && max == null) return null;
            if (max == null) return cb.greaterThanOrEqualTo(root.get("amount"), min);
            return cb.between(root.get("amount"), min, max);
        };
    }
}

组合使用：

Specification<Order> spec = Specification.where(null);
if (dto.getStatus() != null) spec = spec.and(OrderSpecs.status(dto.getStatus()));
if (dto.getMin() != null) spec = spec.and(OrderSpecs.amountBetween(dto.getMin(), dto.getMax()));

Page<Order> page = orderRepository.findAll(spec, PageRequest.of(0, 10));
优势
说明
返回 null 即忽略
条件是空的自然不生效
类型安全
root.get("status") 拼错在运行期才报，但至少不是拼 SQL
可组合
and / or / not 任意拼
可复用
每个条件是一个独立方法

Specification 也可用于 count、delete、exists，且天然支持分页排序。

1.6 投影（只查需要的字段）

// 接口投影
public interface UserNameOnly {
    String getUsername();
    Integer getAge();
}

@Query("select u.username as username, u.age as age from User u where u.status = :s")
List<UserNameOnly> findNames(@Param("s") String status);

// 构造器投影
@Query("select new cn.demo.dto.UserDto(u.id, u.username) from User u")
List<UserDto> findDtos();

大列表查询只取必要字段，能省掉大量无用列的网络与序列化开销。

1.7 排序与分页的两种写法

// 一：Pageable 直接传
Page<Order> findByStatus(String status, Pageable pageable);

// 二：@Query + Pageable（必须返回 Page，且查询本身别写 order by 冲突）
@Query("select o from Order o where o.amount > :min")
Page<Order> findBig(@Param("min") BigDecimal min, Pageable pageable);

@Query 里的 order by 与 Pageable 的 Sort 同时存在时，后者会被忽略——排序统一放 Pageable。

1.9 清单

  1. 条件 1–3 个用方法名派生，4 个以上换 @Query 或 Specification
  2. @Modifying 必须配合事务，更新后清缓存再查
  3. Specification 条件返回 null 即被忽略，天然适配可选筛选项
  4. 只取部分字段用投影，接口投影与构造器投影都可选
  5. @Query 的 order by 会被 Pageable 的排序覆盖，排序统一放 Pageable
  6. 原生 SQL 不参与实体缓存，字段改动不报错，慎用
  7. 多表 join 用 join fetch 一次取齐，比懒加载逐条取快一个量级
