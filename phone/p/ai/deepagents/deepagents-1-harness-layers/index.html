Deep Agents 01 · 三层关系与选型

分类：ai · deepagents ｜ 标签：系统课 · Deep Agents · LangChain

01 三层关系与选型

同一个 tool-calling loop，三层各加各的东西；选错层，后面每一讲都会显得多余｜依据官方 overview / comparison 页自绘

版本不一致提示

  • 本篇基线是 deepagents 0.7.42 + langchain 1.5.2 + langgraph 1.2.24 + Python 3.13；
  • deepagents 不是 LangChain 的子模块，是独立库：它把 langchain 当零件层、langgraph 当运行时，自己只负责「把长任务需要的能力装好」；
  • 0.7.42 实测：create_deep_agent 默认给模型 7 个文件工具 + 1 个 task 工具（ls / read_file / write_file / edit_file / delete / glob / grep + task），而 create_agent 只给 tools= 里那几个；
  • 官方把 create_deep_agent 的返回值写成 CompiledStateGraph，它本身就是一张能 invoke / stream 的 LangGraph，不是另一套运行时；
  • 本篇示例不调模型：用一个「记录工具表的假模型」把两层的工具面打印出来，没有 key 也能跑。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用一句话说清框架 / 运行时 / harness 各管什么，不再把它们当同义词；
  2. 拿到一个需求，用「步数是否固定、要不要碰文件、要不要拆活」三条判据选层级；
  3. 跑通一段对比脚本，亲眼看到 create_deep_agent 比 create_agent 多给了哪些工具。

二、前置知识

  • 读过 LC08 create_agent 循环（知道 agent 就是一个 tool-calling loop）；
  • 知道 LangGraph 里的「图 / 状态 / checkpointer」大致是什么（LG01–LG05 任读一篇即可）；
  • 本机有 uv，Python 3.11+（本系列统一 3.13）。

三、理论讲解（官方定义）

官方原话是：Deep Agents 是「agent harness for complex, multi-step work」，它在 LangChain 与 LangGraph 之上加规划、虚拟文件系统、子代理与长期记忆。关键词是 harness（骨架），不是 framework（框架）。

2. harness 到底多给了什么

官方列了五类能力，对应到代码就是五个参数或五个中间件：

  • 执行环境：tools= + backend= + permissions=（能做事的范围）
  • 上下文管理：skills= + memory= + 自动压缩与卸载（能记多久）
  • 委派：TodoListMiddleware + task 工具 + subagents=（能拆多细）
  • 控制：interrupt_on=（人能不能插进来）
  • 可观测：LangSmith trace（子代理会各成一段子树）

3. 与 Claude Agent SDK 的差异

官方 comparison 页给了三条硬差别，值得记住：

  • 模型不锁：Deep Agents 走 LangChain 的模型抽象，provider:model 想换就换；
  • 后端可换：文件系统是插拔的（内存 / 本地磁盘 / store / 沙箱），不是绑死在某一个容器里；
  • 运行时是 LangGraph：断点、恢复、时间旅行、事件流这些能力直接继承，不用另造一套。

四、原理拆解：为什么小任务不该上 harness

打个比方：create_agent 是一把瑞士军刀，create_deep_agent 是一辆工具车。

工具车多出来的每一样东西都有重量：

  1. 系统提示更长：文件工具的用法、路径约定、task 的派活规则，每轮都要占 token；
  2. 工具更多：默认 8 个工具（7 文件 + 1 task），模型选错工具的概率随工具数上升；
  3. 链路更深：一次 task 就是一棵子树，trace 读起来更费劲，评测也更难定位。

所以判据不是「谁更高级」，而是任务形状：

  • 步数固定、每步做什么你写得出来 → LangGraph 自绘图，别让模型自己决定流程；
  • 步数不定、要边做边看 → harness 才有价值；
  • 完全不碰文件、也不拆活 → create_agent 就够。

五、场景说明

三个真实需求，三种答案：

  1. 「把这条 SQL 改写成参数化查询」：一步、无文件、无拆活 → create_agent + 一个工具，甚至直接一次模型调用。
  2. 「每天扫 30 个仓库，找出过期依赖并提 PR」：步数随仓库变化、要读写文件、要并行 → harness（后面 DA04 / DA11 / DA12 全是这个场景）。
  3. 「退款审批：先查单、再核规则、再等人批」：流程固定、审批点固定 → LangGraph 自绘图 + interrupt（LG06），harness 反而把固定流程变随机。

一句话判据：流程能画死就别交给模型规划，流程画不死才上 harness。

六、示例代码

步骤 1：环境准备

uv init da01-layers
cd da01-layers
uv add deepagents

步骤 2：凭证配置

本篇示例不需要任何模型 key：用一个记录工具表的假模型代替真模型。真正跑模型时再看下面「写法 A」里的 key 变量。

步骤 3：导入

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain.agents import create_agent
from deepagents import create_deep_agent

步骤 4：最小可运行代码

存成 compare.py，uv run compare.py。假模型只做一件事：在 bind_tools 被调用时把工具名记下来。

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from langchain.agents import create_agent
from deepagents import create_deep_agent

seen = {}

def search(q: str) -> str:
    """Search the web."""
    return "ok"

class Recorder(FakeListChatModel):
    """不调真模型，只记录它被绑定了哪些工具。"""
    def bind_tools(self, tools, **kw):
        seen["tools"] = [
            getattr(t, "name", None) if not isinstance(t, dict) else t.get("name")
            for t in tools
        ]
        return self

msg = {"messages": [{"role": "user", "content": "hi"}]}

plain = create_agent(model=Recorder(responses=["ok"]), tools=[search])
plain.invoke(msg)
print("create_agent     :", seen["tools"])
print("create_agent 节点:", list(plain.get_graph().nodes))

deep = create_deep_agent(model=Recorder(responses=["ok"]), tools=[search])
deep.invoke(msg)
print("create_deep_agent     :", seen["tools"])
print("create_deep_agent 节点:", list(deep.get_graph().nodes))

步骤 5：预期输出

create_agent     : ['search']
create_agent 节点: ['__start__', 'model', 'tools', '__end__']
create_deep_agent     : ['ls', 'read_file', 'write_file', 'edit_file', 'delete', 'glob', 'grep', 'task', 'search']
create_deep_agent 节点: ['__start__', 'model', 'tools', '_ParentNotifierMiddleware.after_agent', 'PatchToolCallsMiddleware.before_agent', '__end__']

第二行的 8 个工具就是「harness 多给的东西」，最后那个 search 是你自己传的。

步骤 6：验证是否成功

  • create_agent 的工具表里只有 search——说明 loop 本身不会凭空加能力；
  • create_deep_agent 的工具表里多出 7 个文件工具 + task——这就是你要付的上下文成本；
  • 两个返回值的类型都是 CompiledStateGraph（print(type(deep)) 可验证）——说明 harness 不是另一套运行时。

写法 A · 统一入口：真跑一次

有 key 时把假模型换掉即可，其余代码不变：

agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    tools=[search],
    system_prompt="你是研究员，长材料先落盘再总结。",
)
out = agent.invoke({"messages": [{"role": "user", "content": "把三份 md 合成一份摘要"}]})
print(out["messages"][-1].content)

model 传字符串时，内部走 init_chat_model(provider:model)；要改 temperature、max_tokens 这类参数，就自己 init_chat_model 建好实例再传进来。

七、常见坑（官方明确限制/版本差异）

  1. 把 harness 当「更高级的 create_agent」。不接文件系统、不开子代理，那你只多付了 8 个工具的 token。
  2. 以为规划是默认的。0.7 起 write_todos 要显式传 TodoListMiddleware，老文章里的默认行为已经变了。
  3. 给只有一步的任务上 harness。模型要多想一轮「要不要写 todo」，纯亏。
  4. 以为 harness 会替你做重试与幂等。它给的是断点与恢复能力，业务幂等还是你自己写。
  5. 模型不支持 tool calling。表现为 agent 直接回一段文本、一个工具都不调；先 print 工具表确认绑上了。
  6. 拿 create_deep_agent 的返回当「另一个对象」。它就是 CompiledStateGraph，get_graph() / stream() / checkpointer 全都照旧。

八、课后小结

  • 三层分工：框架给零件，运行时给执行，harness 给「长任务需要的那五件」；
  • harness 的成本是「更长的系统提示 + 更多工具 + 更深的链路」，小任务付不起；
  • 三选一的判据是任务形状，不是「谁更强」；
  • create_deep_agent 默认多给 7 个文件工具 + task；
  • 0.7 起规划是 opt-in，别再按老默认写。

九、思考题

1、为什么说 create_deep_agent 不是「另一套运行时」？

参考回答：它返回的就是 CompiledStateGraph，invoke / stream / checkpointer / interrupt 全部走 LangGraph；harness 只是把一组中间件与工具预装到这张图上。

2、一个「把 PDF 转成 Markdown」的任务，你会选哪层？

参考回答：如果只有固定几步（读 → 转 → 写），LangGraph 自绘图或 create_agent + 一个转换工具即可；只有当页数不定、要分批处理并落盘中间结果时，才上 harness。

3、harness 多给的 8 个工具，什么时候是负担？

参考回答：任务完全不碰文件、也不需要拆活时；每轮都带着这些工具说明，模型选错工具的概率上升，token 也白花。

4、为什么不建议在固定审批流程里用 harness 的规划？

参考回答：固定流程的价值是「每次都一样」，模型自己规划的步数会漂移；审批点该用 LangGraph 的 interrupt 显式画出来。
