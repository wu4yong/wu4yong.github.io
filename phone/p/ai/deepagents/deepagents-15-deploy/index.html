15 上生产：两种跑法

同一份 agent 定义，差别只在「谁提供运行时」｜依据官方 going-to-production 与 managed quickstart 页自绘

版本不一致提示

  • 本篇基线是 deepagents 0.7.42 + langgraph 1.2.24 + Python 3.13；Managed 侧命令行是 mda（managed-deepagents 包）；
  • Managed Deep Agents 目前在 LangSmith Cloud 与 BYOC 上公测（beta）；BYOC 要求 CLI / SDK v0.10 或更高；
  • 自托管侧：FilesystemBackend 与 LocalShellBackend 直连宿主机，官方明确不要在已部署的 agent 里用；要跑代码就换沙箱后端；
  • langgraph.json 是 Agent Server 的构建入口，dependencies / graphs / env 三个字段先写对，再谈部署；
  • 生产调用必须带 thread_id（续跑同一对话）与 context（本次运行的用户 / 密钥 / 开关），两者独立、通常一起传；
  • 持久化由 LangGraph checkpointer 提供：中断、崩溃恢复、time travel 都建立在它上面；Agent Server 自带，自托管要自己配；
  • 本讲不伪造部署结果：没有可用的 LangSmith 付费工作区时，只给命令、产物与验收清单。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 判断该走 SDK 自托管还是 Managed，并说清六件事分别归谁；
  2. 把本地能跑的 agent 变成一个可部署工程（langgraph.json / mda init 两种入口）；
  3. 上线前按清单逐项过：持久化、沙箱、身份、调度、观测、成本。

二、前置知识

  • 读完 DA06 沙箱与解释器（部署侧的执行环境就是它）；
  • 有 LangGraph 部署概念（LG15 部署）；
  • 知道 LangSmith 的 trace / 项目概念（LS03 追踪 级别即可）；

三、理论讲解（官方定义）

1. 两种跑法

  • SDK 自托管：你自己编译 agent，跑在自己的进程 / 容器 / Agent Server；线程、运行记录、store、checkpointer 由你提供（Agent Server 会替你配好，自建则自己接）。
  • Managed Deep Agents：你把 agent 写成一个工程目录（agent.py + instructions.md + schedules/ + tools/），用 mda 部署到 LangSmith 托管的 Agent Server，平台供给 threads / runs / store / checkpointer / 沙箱。

官方推荐路径是 Managed（「不想管基础设施」时），自托管留给「要自定义路由、认证、应用代码」的团队。

3. langgraph.json 三个字段

字段
作用

装什么包；["."] 表示装当前目录（读 pyproject.toml / requirements.txt）

.env 路径；构建时注入，运行时可读

4. Managed 的工程形态

  • agent.py：define_deep_agent(name=..., model=..., tools=[...])，name 也是默认部署名；
  • instructions.md：部署时同步到 LangSmith Context Hub，改口径不必重新部署；
  • schedules/*.py：每个文件一个 define_schedule(...)，文件名就是调度名；
  • tools/：自己写的 @tool，用 connections.get(...) 取运行时密钥。

四、原理拆解：为什么「能跑」不等于「能上线」

本地 invoke 能跑，靠的是三件临时品：进程内存、当前工作目录、你的终端。上线时这三件都会消失：

  1. 进程内存 → checkpointer。没有它，中断无法恢复、崩溃无法续跑、长任务等于一次性；
  2. 当前工作目录 → 沙箱 / 后端。部署环境里 FilesystemBackend 指向的是容器文件系统，官方直接劝退；
  3. 你的终端 → 身份与入口。多用户场景必须把 user_id / org_id 从 context 传进来，否则所有用户共用一份记忆。

所以「上生产」不是加一个部署命令，而是把这三件临时品换成平台件。Managed 把三件都包了；自托管你要逐件自己接。

五、场景说明

  • 选 Managed：团队没有 K8s / 运维，任务以「对话 + 定时摘要」为主，需要 Slack / HTTP 入口，想直接用 LangSmith 的 trace 与评测；
  • 选自托管：已有 Agent Server 与 CI/CD，需要自定义认证、路由、私有网络内的工具，或不能把数据放到托管侧；
  • 两边都要注意：沙箱的生命周期（按 thread 还是按 assistant）、长任务的 TTL、schedule 跑出来的 run 有没有人看。

六、示例代码

步骤 1：环境准备

uv init da15-deploy
cd da15-deploy
uv add deepagents

步骤 2：凭证配置

自托管本地跑 langgraph dev 不需要 LangSmith key；接 trace 与 Managed 才需要 LANGSMITH_API_KEY。

步骤 3：导入

import json
from pathlib import Path

步骤 4：最小可运行代码（部署前先校验工程文件）

存成 check_project.py，uv run check_project.py。不连服务器，只确认 langgraph.json 能被 Agent Server 正确解析。

import json
from pathlib import Path

cfg = json.loads(Path("langgraph.json").read_text(encoding="utf-8"))

assert "graphs" in cfg, "缺 graphs：Agent Server 不知道要跑哪个图"
assert "dependencies" in cfg, "缺 dependencies：构建时不会装你的包"
assert "env" in cfg, "缺 env：密钥不会注入"

for graph_id, target in cfg["graphs"].items():
    path, _, var = target.partition(":")
    assert Path(path).exists(), f"{graph_id} 指向的文件不存在: {path}"
    print(f"graph {graph_id}: {path} -> {var}")

print("工程文件校验通过")

同目录准备一份 langgraph.json：

{
  "dependencies": ["."],
  "graphs": { "agent": "./agent.py:agent" },
  "env": ".env"
}

步骤 5：预期输出

graph agent: ./agent.py -> agent
工程文件校验通过

步骤 6：验证是否成功

  • 三条断言都过 → 字段齐全；
  • graphs 里的文件真实存在 → 构建期不会 404；
  • 换成真实部署后，这个脚本仍可作为 CI 里的「部署前门禁」。

写法 A · SDK 自托管：自己提供运行时

工程骨架：

da15-deploy/
  agent.py
  langgraph.json
  .env

agent.py 里把 checkpointer 换成持久化 saver（演示用内存 saver，生产换 PostgresSaver 或 SqliteSaver，需另装 langgraph-checkpoint-* 包）：

from deepagents import create_deep_agent
from langgraph.checkpoint.memory import InMemorySaver

agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    system_prompt="你是工单助手。",
    checkpointer=InMemorySaver(),   # 生产换 PostgresSaver
)

启动与部署：

uv run langgraph dev      # 本地 Agent Server，端口 2024
uv run langgraph deploy   # 推到你的部署目标

已部署的 agent 有两个硬约束：不要用 FilesystemBackend / LocalShellBackend（直连宿主机）；需要跑代码就换沙箱后端，并按 thread 或 assistant 决定沙箱生命周期（官方用的是 async graph factory，因为创建沙箱是 IO）。

调用侧永远带两样：

agent.invoke(
    {"messages": [{"role": "user", "content": "查 1024"}]},
    config={"configurable": {"thread_id": "t-1024"}},
    context={"user_id": "u-7", "plan": "pro"},
)

写法 B · Managed：mda 从零到部署

uvx --from managed-deepagents mda init research-assistant
cd research-assistant
uv sync
uv run mda dev      # 本地 Agent Server + LangSmith Studio
uv run mda deploy   # 打包成托管部署

agent.py：

from managed_deepagents import define_deep_agent

agent = define_deep_agent(
    name="research-assistant",
    model="openai:gpt-6.1-sol",
    tools=[{"type": "web_search"}],
)

定时任务放 schedules/daily_digest.py，文件名就是调度名：

from managed_deepagents import define_schedule

schedule = define_schedule(
    cron="0 8 * * 1-5",            # 五字段 cron，不是六字段
    timezone="Asia/Shanghai",
    prompt="汇总昨天的工单变化，只列需要人处理的。",
    thread={"mode": "persistent"}, # 每次跑共享一条线程时加；省略即每次新线程
)

要点：cron 必须是标准五字段；省略 timezone 按 UTC；mda deploy 在部署到达 DEPLOYED 后才创建 / 重建 cron，所以别用 --no-wait 去加调度。

七、常见坑（官方明确限制/版本差异）

  1. 把 deepagents-cli 当生产运行时。它是本地交互入口，不是 Agent Server。
  2. 部署里用 FilesystemBackend。官方明确劝退，等于把容器文件系统交给模型。
  3. 没配 checkpointer 就跑长任务。进程重启全丢，中断也恢复不了。
  4. 沙箱与业务数据同网段。隔离的意义全没了。
  5. schedule 落到默认环境。跑出来的 run 没人看，等于白烧 token。
  6. mda deploy --no-wait 加调度。部署没到 DEPLOYED，cron 不会 reconcile。
  7. instructions.md 提交进仓库前先查一遍。里面常混着内部口径与客户名。
  8. thread_id 用随机值。每次都是新对话，记忆与断点全都接不上。

八、课后小结

  • 两种跑法共用 harness，差别在「谁提供 threads / store / checkpointer / 沙箱 / 调度」；
  • 自托管先写对 langgraph.json，再配持久化 saver 与沙箱；
  • Managed 用 mda init / dev / deploy，instructions.md 与 schedules/ 是它的两个特色入口；
  • 生产调用 = thread_id + context，两者都要；
  • 上线前过六项：持久化、执行环境、身份、调度、观测、成本。

九、思考题

1、为什么部署环境禁用 FilesystemBackend？

参考回答：它直连宿主机文件系统，等于把服务器目录暴露给模型；沙箱才有隔离边界。

2、thread_id 与 context 各解决什么？

参考回答：thread_id 定位对话与检查点；context 承载本次运行的用户、密钥、开关，是工具与中间件读的运行时数据。

3、Managed 的 instructions.md 为什么可以「改了不重新部署」？

参考回答：部署时它被同步到 LangSmith Context Hub，运行时从 Hub 读取，改内容不需要重建镜像。

4、什么时候该选自托管，哪怕要多养一套基础设施？

参考回答：需要自定义认证 / 路由 / 私有网络工具，或数据不能出托管侧时；这时基础设施成本是合规成本的一部分。
