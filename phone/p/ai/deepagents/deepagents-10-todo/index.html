10 任务规划

清单是账本：pending → in_progress → completed，答案另写｜依据官方 todo-list 与实测工具描述自绘

版本不一致提示

  • 本篇基线是 deepagents 0.7.42 + langchain 1.5.2 + Python 3.13；
  • 0.7 起任务规划是 opt-in：不传 TodoListMiddleware 就没有 write_todos（实测工具面里没有它）；
  • 中间件从 langchain.agents.middleware 导入（不是 deepagents），配置项是 system_prompt 与 tool_description；
  • 三态固定为 pending / in_progress / completed，不接受自定义状态；
  • 清单落在 state 的 todos 键上（实测 out["todos"] 可直接读到），换线程就丢，跨轮要 checkpointer；
  • 工具描述里官方明确写了：write_todos 不交付答案，最终结论必须是之后的一条正文消息。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 打开 TodoListMiddleware，并验证 write_todos 真的进了工具面；
  2. 写出符合官方四条的清单推进节奏（开工标 in_progress、未完成至少留一条、阻塞另建、别乱用）；
  3. 分清「清单完成」与「任务交付」——后者必须是正文。

二、前置知识

  • 读完 DA09 上下文预算；
  • 知道 middleware= 的合并规则（同名替换、异名插在核心栈后）；
  • 有 LangChain create_agent 的中间件概念（LC09 中间件 级别即可）。

三、理论讲解（官方定义）

1. 它给 agent 什么

TodoListMiddleware 做两件事：加一个 write_todos 工具、加一段教模型怎么用的系统提示。清单本身是结构化的（每条有 content 与 status），不是自由文本。

2. 三个状态

状态
含义
什么时候用
pending
还没开始
建清单时除第一条外都用它
in_progress
正在做
开工前先标；可多个并行
completed
真正做完
验证通过才标

3. 官方写进工具描述的四条规矩

  1. 开工前把第一个任务标 in_progress；
  2. 除非全部完成，始终至少有一个 in_progress；
  3. 有错误或阻塞就保持 in_progress，另建一条「解决什么」；
  4. 只对 3 步以上的任务用；寒暄、一问一答不要用。

另外一条容易被忽略：最后一条 todo 标 completed 不等于交付。工具描述原文要求「计算结果、摘要、对比、数据必须以正文形式出现在最后一次 write_todos 之后的消息里」。

四、原理拆解：清单为什么能提升完成率

长任务失败通常不是能力不够，而是中途丢目标：上下文被工具结果冲淡，模型忘了还剩哪几步。

清单的作用是把「还剩什么」外置成结构化 state：

  • 每一轮模型都能看到当前 todos（在上下文里），不必靠记忆；
  • 状态变化是显式的，压缩摘要时也不会把「做到哪」抹掉（它在独立 state 键里）；
  • 用户可以看进度（前端投影见 DA14），中断后也能续。

代价是每轮多占一点上下文，且模型可能过度使用清单。所以官方才要求「3 步以上才用」。

五、场景说明

  • 适合：多文件改造、批量数据清洗、调研 → 起草 → 校对 → 交付这类阶段明确的活；
  • 不适合：单次问答、两三次工具调用就能完事的任务；
  • 配合使用：与子代理一起用（主代理维护清单、把一条拆给子代理）、与 HITL 一起用（审批点作为清单的一条）；
  • 别做：把清单当日志，每做一件小事就新增一条，清单会膨胀成噪声。

六、示例代码

步骤 2：凭证配置

步骤 3：导入

import itertools
from langchain_core.messages import AIMessage
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain.agents.middleware import TodoListMiddleware
from deepagents import create_deep_agent

步骤 4：最小可运行代码（干跑，不需要 key）

存成 todos.py，uv run todos.py。假模型先发一次 write_todos，再给正文，验证清单进了 state。

import itertools
from langchain_core.messages import AIMessage
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain.agents.middleware import TodoListMiddleware
from deepagents import create_deep_agent

class Fake(GenericFakeChatModel):
    def bind_tools(self, tools, **kw):
        return self

todo_call = AIMessage(
    content="",
    tool_calls=[{
        "name": "write_todos",
        "args": {"todos": [
            {"content": "读三份材料", "status": "in_progress"},
            {"content": "写摘要", "status": "pending"},
        ]},
        "id": "t1",
    }],
)
agent = create_deep_agent(
    model=Fake(messages=itertools.cycle([todo_call, AIMessage(content="摘要已生成")])),
    middleware=[TodoListMiddleware()],
)
out = agent.invoke(
    {"messages": [{"role": "user", "content": "两步任务"}]},
    config={"configurable": {"thread_id": "todo-1"}},
)

print("state 键:", [k for k in out.keys()])
print("清单:", out["todos"])
print("工具回执:", next(m.content for m in out["messages"] if m.type == "tool"))
print("最终正文:", out["messages"][-1].content)

步骤 5：预期输出

state 键: ['messages', 'files', 'todos']
清单: [{'content': '读三份材料', 'status': 'in_progress'}, {'content': '写摘要', 'status': 'pending'}]
工具回执: Updated todo list to [{'content': '读三份材料', 'status': 'in_progress'}, {'content': '写摘要', 'status': 'pending'}]
最终正文: 摘要已生成

步骤 6：验证是否成功

  • todos 出现在 state 键里 → 清单被独立保存，不混在消息里；
  • 工具回执是 Updated todo list to [...] → 写入成功；
  • 最后一条是正文 → 交付与清单分离。

写法 A · 真跑一遍

agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    middleware=[TodoListMiddleware()],
    system_prompt="任务超过 3 步就先写清单；每完成一步立刻更新，不要批量改。",
)
out = agent.invoke(
    {"messages": [{"role": "user", "content": "把这三份材料合成一份周报，先给提纲再写全文"}]},
    config={"configurable": {"thread_id": "todo-2"}},
)
print(out["todos"]); print(out["messages"][-1].content)

写法 B · 自定义提示与工具描述

TodoListMiddleware(
    system_prompt="清单只放交付级步骤，最多 7 条；子步骤写在 /workspace/plan.md。",
    tool_description="维护任务清单。每条必须可验证（例如「tests 全绿」）。",
)

两个参数都可覆盖，工具签名不变。

七、常见坑（官方明确限制/版本差异）

  1. 以为默认就有。0.7 起要显式加 TodoListMiddleware，否则工具面里没有 write_todos。
  2. 从 deepagents 导入。这个类在 langchain.agents.middleware。
  3. 把清单当交付。全部标 completed 但没有正文，用户什么也没拿到。
  4. 状态用词自造。只认 pending / in_progress / completed。
  5. 清单跨会话消失。它在 state 里，换 thread_id 就没了；要续就配 checkpointer。
  6. 小事也开清单。官方明确：3 步以下、纯对话不该用，反而增加噪声与 token。
  7. 阻塞时标 completed。工具描述要求保持 in_progress 并另建一条「解决什么」，否则会掩盖问题。

八、课后小结

  • 0.7 起 write_todos 要显式开 TodoListMiddleware；
  • 三态：pending / in_progress / completed；
  • 四条规矩来自官方工具描述，最关键是「未完成时始终有一条 in_progress」；
  • 清单在 state["todos"]，独立于消息，摘要也不会抹掉；
  • 清单不等于答案，交付必须是正文。

九、思考题

1、为什么清单要单独放 state 键，而不是塞进消息里？

参考回答：消息会被压缩摘要，而清单必须准确；独立通道保证「做到哪」不被摘要丢掉。

2、什么信号说明该开清单了？

参考回答：步骤 ≥3、跨多个工具或文件、需要中途交付阶段成果、或用户自己列了多条要求。

3、阻塞时为什么不能标完成？

参考回答：标完成会让模型以为这一步已过，后续基于错误前提继续；保持 in_progress + 新建阻塞条目才能暴露问题。

4、清单和子代理怎么配合？

参考回答：主代理维护交付级清单，把其中一条作为 task 交给子代理；子代理的中间步骤不进主清单。
