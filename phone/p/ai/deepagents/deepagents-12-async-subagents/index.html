分类：ai · deepagents ｜ 标签：系统课 · Deep Agents · LangChain

12 异步子代理

启动即返回 task_id，主管继续对话；状态存在独立的 async_tasks 通道｜依据官方 async-subagents 页自绘

版本不一致提示

  • 本篇基线是 deepagents 0.7.42 + langgraph 1.2.24 + Python 3.13；
  • 异步子代理要跑在 Agent Protocol 服务器（LangSmith Agent Server 或自托管的 Agent Protocol 服务）上；本地 langgraph dev 也算；
  • AsyncSubAgent(name, description, graph_id, url?, headers?)：url 省略走 ASGI 进程内，给了走 HTTP 远程；
  • graph_id 必须与部署的 langgraph.json 里注册的 graph 名一致；
  • 配置后主管会多出 5 个工具：start_async_task / check_async_task / update_async_task / cancel_async_task / list_async_tasks（实测工具面）；
  • 任务状态存在独立 state 通道 async_tasks，不随消息摘要丢失；
  • 通知（完成后自动唤醒主管）需要 0.7.26+，通知 metadata 需要 0.7.33+；update_strategy="enqueue" 需要 0.7.30+。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清同步子代理与异步子代理的差别（谁等谁、状态存哪、能不能中途改）；
  2. 配一个 AsyncSubAgent，并验证主管的工具面多出五个工具；
  3. 知道上线前必须处理的两件事：worker 槽位、别轮询。

二、前置知识

  • 读完 DA11 子代理；
  • 有 LangGraph 部署概念（LG15 部署 级别即可）；
  • 知道 langgraph.json 里 graph 是怎么注册的。

三、理论讲解（官方定义）

1. 它解决什么

同步子代理会阻塞主管：主管必须等它跑完才继续。异步子代理则立刻返回 task_id，主管可以继续和用户对话，稍后收通知或主动查。

2. 同步 vs 异步（官方对照）

维度
同步
异步
执行
主管阻塞到子代理完成
立即返回，主管继续
运行位置
主管的 run 内
服务端独立线程的 run
中途干预
不能
update 改指令、cancel 停

另外：同步子代理无状态（每次都是新上下文）；异步子代理有状态，任务线程能跨多次交互保留。

3. 五个工具

  • start_async_task：起任务，立刻拿 task_id（就是子代理线程 id）；
  • check_async_task：看状态，附结果 / 错误 / 待输入；
  • update_async_task：发新指令（默认打断当前 run，同一线程带上完整历史重跑）；
  • cancel_async_task：取消；
  • list_async_tasks：列出所有跟踪中的任务（可按状态筛）。

4. 通知

在 Agent Server 上，子代理完成、失败、需要输入时会通知主管：主管忙时在下一次模型调用前收到；主管空闲时，同部署的 deep agent 子代理会把它唤醒。通知以 HumanMessage 形式到达。

四、原理拆解：为什么状态不能放消息里

主管会做上下文压缩（DA09）。如果 task_id 只存在工具调用/结果消息里，几轮摘要之后就可能被压掉——主管再也找不到自己起过哪些任务。

所以异步任务元数据放在独立 state 通道 async_tasks：task id、agent 名、thread id、run id、状态、三个时间戳。list_async_tasks 永远能从通道里读回来。

这也是「异步不是简单并发」的原因：并发要配一套可恢复的任务账本，否则中断一次就全丢。

五、场景说明

  • 长任务：深度调研、批量抓取、全库扫描；
  • 可并行的多任务：同时跑 3 个调研，谁先完成谁先通知；
  • 要中途改方向：用户说「别查 A 了，改查 B」→ update_async_task；
  • 不适合：几十秒能跑完的活（异步的开销大于收益）、需要严格顺序依赖的流水线。

六、示例代码

步骤 1：环境准备

uv init da12-async
cd da12-async
uv add deepagents

步骤 2：注册 graph

langgraph.json（主管与子代理同部署时）：

{
  "graphs": {
    "supervisor": "./src/supervisor.py:graph",
    "researcher": "./src/researcher.py:graph"
  }
}

步骤 3：导入

from deepagents import AsyncSubAgent, create_deep_agent

步骤 4：最小可运行代码（干跑，不需要 key / 不需要服务器）

存成 async_tools.py，uv run async_tools.py。只验证主管的工具面，不真的起任务。

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from deepagents import AsyncSubAgent, create_deep_agent

seen = {}

class Recorder(FakeListChatModel):
    def bind_tools(self, tools, **kw):
        seen["tools"] = [getattr(t, "name", "") for t in tools]
        return self

subs = [
    AsyncSubAgent(name="researcher", description="深度调研", graph_id="researcher"),
    AsyncSubAgent(name="coder", description="代码实现", graph_id="coder", url="https://coder.example.dev"),
]
agent = create_deep_agent(model=Recorder(responses=["ok"]), subagents=subs)
agent.invoke({"messages": [{"role": "user", "content": "hi"}]}, config={"configurable": {"thread_id": "async-1"}})

five = [n for n in seen["tools"] if n.endswith("_async_task") or n == "list_async_tasks"]
print("五个工具:", five)

步骤 5：预期输出

五个工具: ['start_async_task', 'check_async_task', 'update_async_task', 'cancel_async_task', 'list_async_tasks']

步骤 6：验证是否成功

  • 五个工具都在 → 异步中间件生效；
  • 不起任务也能构造 agent（真正运行要连 Agent Protocol 服务器）；
  • 两个子代理分别走 ASGI（无 url）与 HTTP（有 url）两种传输。

写法 A · 真跑：起任务 → 让用户继续聊

agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    subagents=[AsyncSubAgent(name="researcher", description="深度调研", graph_id="researcher")],
    system_prompt="启动异步任务后，立刻把控制权交回用户。不要紧接着 check。",
)
out = agent.invoke(
    {"messages": [{"role": "user", "content": "帮我调研这三家公司的定价策略，慢慢来"}]},
    config={"configurable": {"thread_id": "async-2"}},
)
print(out["messages"][-1].content)     # 通常是「已启动，你可以继续问别的」

写法 B · 中途改指令

# 由主管在后续轮次调用 update_async_task
{"name": "update_async_task", "args": {"task_id": "<task-id>", "instructions": "只看企业版定价"}, "id": "u1"}

默认会打断当前 run、带完整历史重跑；要排队则用 update_strategy="enqueue"（0.7.30+）。

七、常见坑（官方明确限制/版本差异）

  1. 没有 Agent Protocol 服务器。本地直接 invoke 起任务会失败；先 langgraph dev 或部署。
  2. graph_id 写错。必须与 langgraph.json 注册名一致，否则找不到图。
  3. 启动后立刻 check。官方把这个列为典型故障：会把异步退化成阻塞；靠通知，别轮询。
  4. worker 槽位不足。1 主管 + 3 异步 = 4 槽；不够就排队（--n-jobs-per-worker）。
  5. task_id 被截断。模型自行缩写会导致 check/cancel 失败；在提示里要求「原样传完整 id」。
  6. 状态报告是旧的。对话里看到的状态可能是历史值；报状态前先 check / list。
  7. waiting 任务被 update。会丢掉待审批请求；要保留就先处理它要的输入。

八、课后小结

  • 异步 = 独立线程 + 五工具 + 通知；
  • 状态存 async_tasks 通道，摘要不会把它冲掉；
  • url 省略走进程内 ASGI，给了走远程 HTTP；
  • 上线要算 worker 槽位，且不要轮询；
  • 同步适合「等结果再往下走」，异步适合「边聊边跑」。

九、思考题

1、为什么 task_id 必须放独立 state 通道？

参考回答：消息会被摘要压缩，task_id 一旦丢失就无法 check / cancel；独立通道保证任务账本始终可读。

2、Agent Server 的通知机制省掉了什么？

参考回答：省掉了主管主动轮询；完成 / 失败 / 要输入时自动唤醒或在下一次模型调用前送达。

3、update 默认打断当前 run，什么场景该用 enqueue？

参考回答：新指令是对当前工作的补充而非改方向时；排队可以避免丢掉已跑了一半的进度。

4、什么时候不该用异步？

参考回答：任务短、强顺序依赖、或用户正等着结果继续下一步——异步只会增加协调成本。
