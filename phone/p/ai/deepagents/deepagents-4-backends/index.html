04 虚拟文件系统与后端

同一套 / 路径，背后可以是内存 state、本地磁盘、LangGraph store，或按前缀路由｜依据官方 backends 页自绘

版本不一致提示

  • 本篇基线是 deepagents 0.7.42 + langgraph 1.2.24 + Python 3.13；
  • 后端类都在 deepagents.backends：StateBackend、FilesystemBackend、StoreBackend、CompositeBackend（另有 LocalShellBackend、ContextHubBackend，见 DA06 与官方 runtime 页）；
  • StateBackend 不能在 graph 外读写：单独 StateBackend().read(...) 会报「必须在 LangGraph 执行内使用」，预置文件要在 invoke 时传 files（实测）；
  • FilesystemBackend(root_dir=None, virtual_mode=True, max_file_size_mb=10) 可以独立使用，返回的是 WriteResult / ReadResult / LsResult / GlobResult 对象，不是裸字符串；
  • read() 返回的 file_data 是 dict（{'content': ..., 'encoding': 'utf-8'}），不是字符串——这一条文档没写清，是 0.7.42 实测；
  • 路径统一写虚拟绝对路径（/notes/a.md），后端负责映射到真实位置。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说出四种后端各自把文件存到哪、活多久、能否跨线程；
  2. 用 FilesystemBackend 在脚本里直接读写，并读得懂四个返回对象；
  3. 用 CompositeBackend 按路径前缀路由：临时文件留内存、成果落磁盘。

二、前置知识

  • 读完 DA03 工具与 MCP；
  • 知道 thread_id 是文件归属单位（DA02）；
  • 本机有可写的目录（示例会用 C:\Windows\Temp 下的一个沙箱根）。

三、理论讲解（官方定义）

1. 虚拟文件系统是什么

8 个文件工具操作用的是一套虚拟绝对路径（/notes/plan.md、/workspace/draft.md）。路径到真实存储的映射由后端决定。所以「文件写哪去了」这个问题，答案永远在 backend= 上。

2. 四种后端

后端
存在哪
寿命 / 跨线程
StateBackend（默认）
图 state 里
跟 thread；换 thread 读不到
FilesystemBackend
本地磁盘 root_dir
永久；跨进程可读
StoreBackend
LangGraph store
跨 thread、跨会话
CompositeBackend
按前缀分发到上面几种
取决于被路由到的后端

3. 怎么选（官方口径）

  • 会话内的中间草稿：StateBackend，最省事、零配置；
  • 要落盘给人看、要被别的进程读：FilesystemBackend；
  • 长期记忆、跨线程共享：StoreBackend（或 CompositeBackend 里把 /memories/ 路由过去）；
  • 一套路径多种存储：CompositeBackend。

4. 返回对象

| 方法 | 返回 | 关键字段 |
| write | WriteResult | path、error |
| read | ReadResult | file_data（dict）、total_lines、next_offset |
| ls | LsResult | entries（list of dict） |
| glob | GlobResult | matches（list of dict）、truncated |

entries / matches 的元素是 {'path', 'is_dir', 'size', 'modified_at'}。分页读大文件时用 next_offset 续读，不要一次拉全文。

四、原理拆解：为什么默认是内存

StateBackend 把文件放进图 state 的一个字段，好处是：一次 invoke 里读写零延迟、不碰磁盘、天然随 checkpoint 走。代价是寿命等于 thread。

这解释了两个常见困惑：

  1. 「昨天写的文件今天读不到」——换了 thread_id，或进程重启且没配 checkpointer；
  2. 「脚本里 read_file 报错」——StateBackend 只在图执行内有效，脚本里要用 FilesystemBackend。

也解释了为什么官方推荐「长材料先落盘」：落盘到 FilesystemBackend 后，上下文里只留路径，模型需要时再 read_file 分页读。

五、场景说明

  • 批量文档处理：FilesystemBackend(root_dir="./work")，产出直接留在磁盘给人看；
  • 多轮对话里的草稿：默认 StateBackend 就够，配 checkpointer 后跨轮还在；
  • 跨会话记忆：CompositeBackend 把 /memories/ 路由到 StoreBackend，其余留内存；
  • 代码执行：需要 execute 时要换 LocalShellBackend 或沙箱（DA06），这四个都不带 execute。

六、示例代码

步骤 1：环境准备

uv init da04-backends
cd da04-backends
uv add deepagents

步骤 2：准备目录

New-Item -ItemType Directory -Force -Path C:\Windows\Temp\da04-root | Out-Null

步骤 3：导入

from deepagents.backends import FilesystemBackend, CompositeBackend, StateBackend, StoreBackend

步骤 4：最小可运行代码（脚本内直接读写磁盘）

存成 fs_backend.py，uv run fs_backend.py。

from deepagents.backends import FilesystemBackend

be = FilesystemBackend(root_dir=r"C:\Windows\Temp\da04-root", virtual_mode=True)
print(be.write("/notes/plan.md", "# 周计划\n- 周一：复盘\n"))
print(be.read("/notes/plan.md"))
print(be.ls("/notes"))
print(be.glob("**/*.md"))

步骤 5：预期输出

WriteResult(error=None, path='/notes/plan.md')
ReadResult(error=None, file_data={'content': '# 周计划\n- 周一：复盘\n', 'encoding': 'utf-8'}, total_lines=2, start_line=1, end_line=2, next_offset=None, no_lines_requested=False)
LsResult(error=None, entries=[{'path': '/notes/plan.md', 'is_dir': False, 'size': 30, 'modified_at': '...'}])
GlobResult(error=None, matches=[{'path': '/notes/plan.md', 'is_dir': False, 'size': 30, 'modified_at': '...'}], truncated=False, truncation_reason=None)

步骤 6：验证是否成功

  • 磁盘上真有 da04-root\notes\plan.md；
  • read 的 file_data['content'] 是你写进去的原文；
  • glob("**/*.md") 能匹配到它。

写法 A · 把后端的文件放进 agent 上下文

from deepagents import create_deep_agent
from deepagents.backends import FilesystemBackend

be = FilesystemBackend(root_dir=r"C:\Windows\Temp\da04-root", virtual_mode=True)
agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    backend=be,
    system_prompt="材料都在 /notes 下，先 ls 再 read，长文件分页读。",
)
out = agent.invoke(
    {"messages": [{"role": "user", "content": "把 /notes 下的材料汇总成 /out/summary.md"}]},
    config={"configurable": {"thread_id": "fs-1"}},
)

跑完后 da04-root\out\summary.md 就是 agent 的产物——这是「落盘交付」最直接的形态。

写法 B · 按前缀路由（混合后端）

from deepagents import create_deep_agent
from deepagents.backends import CompositeBackend, FilesystemBackend, StateBackend

be = CompositeBackend(
    default=StateBackend(),                                  # 其余路径：线程内内存
    routes={"/reports/": FilesystemBackend(root_dir="./reports")},   # 成果落盘
)
agent = create_deep_agent(model="openai:gpt-6.1-sol", backend=be)

规则是「最长前缀优先」：/reports/a.md 走磁盘，/workspace/x.md 走内存。

后端是 harness 层的东西，与 provider 无关——这是本系列里少数「换模型完全不影响写法」的一讲。

七、常见坑（官方明确限制/版本差异）

  1. 在脚本里用 StateBackend。会直接报「必须在 LangGraph 图执行内使用」；预置文件请在 invoke 时传 files。
  2. read() 当字符串用。返回是 ReadResult，正文在 res.file_data['content']。
  3. root_dir 写相对路径却换了工作目录。FilesystemBackend 按进程 cwd 解析，跑批时用绝对路径最稳。
  4. virtual_mode=True 时传真实绝对路径给工具。工具只认虚拟路径，C:\... 会被当成非法路径。
  5. 以为 FilesystemBackend 有 execute。没有；要 shell 用 LocalShellBackend（DA06）。
  6. 超大文件塞进后端。max_file_size_mb 默认 10，超过会拒写；大文件先切分。
  7. CompositeBackend 路由前缀漏尾斜杠。"/reports" 与 "/reports/" 匹配行为不同，统一写带尾斜杠的形式最稳。

八、课后小结

  • 8 个文件工具读写的是虚拟路径，真实位置由后端决定；
  • 四种后端：内存（默认）、磁盘、store、路由器；
  • FilesystemBackend 可独立使用，四个返回对象要会读；
  • read 的正文在 file_data['content']，大文件用 next_offset 续读；
  • 后端与 provider 无关，换模型不改写法。

九、思考题

1、为什么默认后端选内存而不是磁盘？

参考回答：一次 invoke 内零延迟、不碰 IO，且随 checkpoint 自动持久化到会话；对「临时草稿」这个主场景最划算。

2、StoreBackend 的 namespace 为什么是个 callable 而不是字符串？

参考回答：它要从 runtime 里取用户 / 会话标识，按调用方动态拼出命名空间，才能做到「同一用户跨线程共享、不同用户隔离」。

3、什么情况下必须用 CompositeBackend？

参考回答：一套业务路径里同时存在「临时」与「要留」两类文件时，例如 /workspace 留内存、/reports 落盘、/memories 进 store。

4、next_offset 解决的是什么问题？

参考回答：大文件不能一次全读进上下文；分页读让模型按需拉取，避免把上下文打满。
