05 权限规则

规则按声明顺序判定，第一条命中即定；没有命中就放行｜依据官方 permissions 页自绘

版本不一致提示

  • 本篇基线是 deepagents 0.7.42；permissions= 需要 0.5.2+，mode="interrupt" 需要 0.6.8+，delete 单文件精确匹配需要 0.7.3+；
  • FilesystemPermission(operations=[...], paths=[...], mode=...) 里 mode 有三种取值：allow / deny / interrupt（文档正文只写前两种，interrupt 在下面的小节里）；
  • 权限只作用于内置文件工具（ls、read_file、glob、grep、write_file、edit_file、delete）；自定义工具、MCP 工具不受约束；
  • 权限不约束沙箱的 execute：能跑 shell 的后端，路径限制形同虚设；
  • 判定是 first-match-wins，没有命中就放行（默认宽松）；
  • 拒绝时的返回是工具消息 Error: permission denied for write on /etc/x.md（实测原文）；
  • interrupt 模式需要checkpointer，否则没有地方暂停。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 写出「只允许 /workspace/**、其余全禁」这类规则集，并知道顺序为什么重要；
  2. 用 mode="interrupt" 把敏感写入卡成人工审批；
  3. 说清权限的覆盖边界：它管不到自定义工具、MCP 工具和沙箱 execute。

二、前置知识

  • 读完 DA04 虚拟文件系统与后端；
  • 知道 operations 的语义：read 覆盖 ls / read_file / glob / grep，write 覆盖 write_file / edit_file / delete；
  • 想试 interrupt 的话，知道 LangGraph 的 checkpointer 是干嘛的（LG05 级别即可）。

三、理论讲解（官方定义）

1. 规则结构

| 字段 | 取值 | 含义 |
| operations | read / write | 这条规则管哪类操作 |
| paths | glob 列表 | ** 递归、{a,b} 择一 |
| mode | allow / deny / interrupt | 允许 / 拒绝 / 暂停等人工审批 |

2. 判定顺序

规则按声明顺序逐条匹配，第一条 operations 与 paths 都命中的规则决定结果；全都不命中就放行。

所以「白名单」必须写成两段：先 allow 目标区，再 deny 全盘兜底。只写 allow 一条，等于没限制。

3. 四个动作

  • allow：放行；
  • deny：拒绝，工具返回 Error: permission denied ...，模型看到错误后可以改路径重试；
  • interrupt：不执行，抛人工审批中断，审批者可以 approve / edit / reject（与 interrupt_on 的流程一致，DA13 详讲）；
  • 无命中：放行。

4. 覆盖边界（最容易踩的一条）

官方明确：权限只管内置文件工具。自定义工具里自己 open() 文件、MCP server 自己访问磁盘、沙箱里 execute("rm -rf /")——权限都拦不住。要管这些，得用后端策略钩子或干脆不给这类工具。

四、原理拆解：为什么是 first-match-wins

glob 规则之间会重叠（/workspace/** 与 /** 都匹配 /workspace/a.md）。如果用「最具体优先」之类的规则，重叠判断会变得难以预测；改用声明顺序，语义就变成「你按优先级排」，代价是顺序写错就失效。

官方给了正反两例，本质一样：

  • 正确：/workspace/.env deny → /workspace/** allow → /** deny；
  • 错误：/workspace/** allow 放前面，后面的 .env deny 永远轮不到。

delete 还有个细节：删目录是全有或全无——它检查目标及所有子孙路径的 write 权限，任何一条被拒就整体拒绝，不会删一半。删单文件是精确匹配（0.7.3+），所以更窄的 allow 能赢过后面的兜底 deny。

五、场景说明

  • 沙箱化工作区：只许 /workspace/** 读写，其余全禁——最常用的一套；
  • 保护密钥：/workspace/.env 单独 deny，放在最前面；
  • 只读知识库：/memories/** 的 write deny，读照旧——组织级政策常用；
  • 高危写入审批：/secrets/** 用 interrupt，配合 checkpointer；
  • 不该指望权限的场景：给 agent 装了 shell 的沙箱、把文件读写封进自定义工具的服务。

六、示例代码

步骤 1：环境准备

uv init da05-perms
cd da05-perms
uv add deepagents

步骤 2：凭证配置

本讲示例用假模型，不需要 key；interrupt 示例需要一个 checkpointer（InMemorySaver 即可）。

步骤 3：导入

from deepagents import create_deep_agent, FilesystemPermission
from langchain_core.messages import AIMessage

步骤 4：最小可运行代码（干跑，不需要 key）

存成 perms.py，uv run perms.py。让假模型直接发一个 write_file 调用，分别打到允许路径与禁止路径。

import itertools
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage
from deepagents import create_deep_agent, FilesystemPermission

class Fake(GenericFakeChatModel):
    def bind_tools(self, tools, **kw):
        return self

def model_calling(path):
    call = AIMessage(
        content="",
        tool_calls=[{"name": "write_file", "args": {"file_path": path, "content": "hi"}, "id": "1"}],
    )
    return Fake(messages=itertools.cycle([call, AIMessage(content="done")]))

rules = [
    FilesystemPermission(operations=["read", "write"], paths=["/workspace/**"], mode="allow"),
    FilesystemPermission(operations=["read", "write"], paths=["/**"], mode="deny"),
]

for path, thread in (("/workspace/a.md", "ok"), ("/etc/x.md", "blocked")):
    agent = create_deep_agent(model=model_calling(path), permissions=rules)
    out = agent.invoke(
        {"messages": [{"role": "user", "content": "写个文件"}]},
        config={"configurable": {"thread_id": thread}},
    )
    tool_msg = next(m for m in out["messages"] if m.type == "tool")
    print(path, "→", tool_msg.content)
    print("  files:", list((out.get("files") or {}).keys()))

步骤 5：预期输出

/workspace/a.md → Updated file /workspace/a.md
  files: ['/workspace/a.md']
/etc/x.md → Error: permission denied for write on /etc/x.md
  files: []

步骤 6：验证是否成功

  • 允许路径：工具真的写了，files 里有它；
  • 禁止路径：工具被拦，files 为空，模型拿到的是 Error: permission denied ...；
  • 注意 write_file 的参数名是 file_path 而不是 path，写错会先撞参数校验（本篇实测踩过）。

写法 A · 三层规则：先保护、再放行、最后兜底

rules = [
    FilesystemPermission(operations=["read", "write"], paths=["/workspace/.env"], mode="deny"),
    FilesystemPermission(operations=["read", "write"], paths=["/workspace/**"], mode="allow"),
    FilesystemPermission(operations=["read", "write"], paths=["/**"], mode="deny"),
]
agent = create_deep_agent(model=model, permissions=rules)

顺序就是优先级：越具体的越往前。

写法 B · 敏感写入转人工审批

from langgraph.checkpoint.memory import InMemorySaver

agent = create_deep_agent(
    model=model,
    permissions=[
        FilesystemPermission(operations=["write"], paths=["/secrets/**"], mode="interrupt"),
    ],
    checkpointer=InMemorySaver(),
)

out = agent.invoke(
    {"messages": [{"role": "user", "content": "把密钥写进 /secrets/prod.md"}]},
    config={"configurable": {"thread_id": "approve-1"}},
)
print(out.get("__interrupt__"))     # 待审批的中断对象

审批与恢复的写法与 interrupt_on 一致（Command(resume=...)），DA13 有完整流程。

七、常见坑（官方明确限制/版本差异）

  1. 只写 allow 一条就以为锁住了。没有命中就放行，必须补 /** 的 deny 兜底。
  2. 规则顺序反了。宽规则在前，窄规则永远轮不到，.env 保护形同虚设。
  3. 以为权限能管自定义工具。自己 open() 的自定义工具完全绕过权限。
  4. 以为权限能管 MCP / 沙箱。MCP server 与 execute 都不在内置文件工具之列。
  5. interrupt 没配 checkpointer。中断没有落点，跑不出审批流程。
  6. CompositeBackend + 沙箱默认后端时写了越界路径。官方规定权限路径必须落在已知 route 前缀内，否则直接 NotImplementedError。
  7. interrupt 用无锚点模式。/**/secrets 这类无前缀模式会让批量工具（ls / glob / 目录 delete）保守地大面积触发中断；要用 /secrets/** 这样带字面前缀的写法。

八、课后小结

  • 规则三字段：operations / paths / mode（三种模式）；
  • 判定 first-match-wins，无命中放行——白名单必须配兜底 deny；
  • 拒绝表现为工具消息 Error: permission denied ...；
  • 只管内置文件工具，自定义 / MCP / 沙箱 execute 都在覆盖之外；
  • interrupt 是「转人工」，需要 checkpointer。

九、思考题

1、为什么「只写 allow」等于没设权限？

参考回答：未命中即放行，模型只要换个路径就绕过去了；必须有兜底 deny 把域外全封。

2、文件权限与工具白名单，哪个更硬？

参考回答：工具白名单更硬——工具不在表里，模型根本没有通道；权限是「有工具但按路径拦截」，仍可能被非内置工具绕过。

3、给子代理单独的权限会发生什么？

参考回答：permissions 字段会整体替换父代理的规则，不是叠加；所以子代理的规则里通常要自己写全「allow 目标 + deny 兜底」。

4、为什么删目录是全有或全无？

参考回答：避免删一半留下不一致状态；宁可整单拒绝让调用方处理，也不产生部分删除。
