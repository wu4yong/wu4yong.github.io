11 子代理

子代理的中间调用不回流主上下文；主代理只拿一份报告｜依据官方 subagents 页自绘

版本不一致提示

  • 本篇基线是 deepagents 0.7.42 + langchain 1.5.2 + Python 3.13；
  • 每个 deep agent 永远有一个 general-purpose 子代理（实测 task 描述里默认列出它，且标注「has access to all tools as the main agent」）；
  • 自定义子代理的 tools 一旦指定就是整体替换继承来的工具，不是追加；
  • skills 不继承：只有 general-purpose 继承主代理技能；子代理有技能时会跑自己的 SkillsMiddleware；
  • mode="fork" 需要 0.7.13+（beta），且 fork 不能再调 task、不能传 skills；
  • permissions 在子代理上是整体替换父代理规则，不是叠加；
  • 子代理的报告不直接呈现给用户，主代理要自己转述。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用 subagents= 定义子代理，并验证 task 工具里出现了它的名字与描述；
  2. 判断该用 isolated 还是 fork；
  3. 用「工具收窄 + 独立上下文」控制主代理的上下文与风险。

二、前置知识

  • 读完 DA10 任务规划；
  • 知道工具白名单与权限（DA03 / DA05）；
  • 了解 task 是内置工具（DA02 的工具表里有）。

三、理论讲解（官方定义）

1. 子代理是什么

子代理是独立的 agent 实例：有自己的上下文、自己的工具面、自己的提示，由主代理通过 task(subagent_type=..., description=...) 调用，跑完返回一份报告。

它解决两个问题：上下文隔离（中间过程不回流主上下文）与能力/权限分离（不同子代理给不同工具）。

2. 必填与选填

必填：name、description、system_prompt（isolated 模式）。

选填：tools、model、middleware、interrupt_on、skills、permissions、response_format、mode。

description 是主代理唯一的选人依据——要写成「什么时候交给它」，而不是「它是什么」。

3. isolated 与 fork

判据：新活 → isolated；接着干父代理已经查清的事 → fork。

4. general-purpose

永远存在的兜底子代理：同工具、同模型（可覆盖）、继承技能。它的主要用途就是上下文隔离——把重活丢给它，只拿结论回来。

四、原理拆解：一次 task 发生了什么

  1. 主代理发 task 工具调用，参数是 subagent_type + description；
  2. 中间件按名字找到子代理，用它的提示、工具、模型起一次独立的 run；
  3. 子代理在自己的上下文里循环：读文件、调工具、可能再委派；
  4. 结束时返回一份最终报告，作为 ToolMessage 回到主代理；
  5. 主代理基于报告继续，或把它写进交付物。

关键点：第 3 步的所有中间消息都不会进主代理的上下文。这是「20 次工具调用只换回一段结论」的原因，也是为什么子代理的 system_prompt 里要明确「返回什么格式」。

五、场景说明

  • researcher：检索、抓页、落盘到 /notes，只回「发现 + 链接」；
  • coder：改代码、跑测试，只回「改了哪些文件 + 测试结果」；
  • reviewer：只读审查，permissions 全禁写；
  • 并行：多个独立子任务，一次消息里发多个 task 调用（官方工具描述明确支持并发）；
  • 不该拆：两三步就能完成的事——多一层就多一次提示与调用开销。

六、示例代码

步骤 1：环境准备

uv init da11-subagents
cd da11-subagents
uv add deepagents

步骤 2：凭证配置

本讲干跑不需要 key；子代理可以各自用不同 provider 的 key（model 可覆盖）。

步骤 3：导入

from deepagents import create_deep_agent

步骤 4：最小可运行代码（干跑，不需要 key）

存成 subagents_check.py，uv run subagents_check.py。截获 task 工具描述，验证子代理被正确登记。

from langchain_core.language_models.fake_chat_models import FakeListChatModel
from deepagents import create_deep_agent

def lookup(query: str) -> str:
    """Query the internal KB."""
    return "kb"

seen = {}

class Recorder(FakeListChatModel):
    def bind_tools(self, tools, **kw):
        for t in tools:
            if getattr(t, "name", "") == "task":
                seen["task"] = t.description
        return self

agent = create_deep_agent(
    model=Recorder(responses=["ok"]),
    tools=[lookup],
    subagents=[{
        "name": "researcher",
        "description": "只做检索，不做写入。用户要查资料时交给它。",
        "system_prompt": "你是检索员，找到资料落盘 /notes，只回结论与来源。",
        "tools": [lookup],
    }],
)
agent.invoke({"messages": [{"role": "user", "content": "hi"}]}, config={"configurable": {"thread_id": "sub-1"}})

d = seen["task"]
print("有 general-purpose:", "general-purpose" in d)
print("有 researcher:", "researcher" in d)
print("描述进提示:", "只做检索，不做写入" in d)

步骤 5：预期输出

有 general-purpose: True
有 researcher: True
描述进提示: True

步骤 6：验证是否成功

  • 默认子代理在列 → 没有把兜底能力弄丢；
  • 自己定义的子代理在列 → 登记成功；
  • 描述原文出现在 task 工具描述里 → 主代理能据此选人（这就是写清 description 的意义）。

写法 A · 三个子代理分工

research = {
    "name": "researcher",
    "description": "检索与抓页，产出资料清单。需要外部信息时用它。",
    "system_prompt": "把资料写到 /notes/，最后只回 5 条要点与来源。",
    "tools": [search, fetch_page],
}
coder = {
    "name": "coder",
    "description": "改代码并跑测试。需要落地实现时用它。",
    "system_prompt": "改完必须跑 pytest，只回改动文件与用例结果。",
    "tools": [run_tests],          # 文件工具由中间件自带，不用手写进 tools
    "model": "anthropic:claude-sonnet-5",
}
agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    tools=[write_report],
    subagents=[research, coder],
)

注意 coder 的 tools 是替换，不是追加：它拿不到主代理的 write_report。

写法 B · fork：接着父代理的活干

writer = {
    "name": "comment-writer",
    "description": "基于主代理已查清的问题，起草 PR 评论。",
    "system_prompt": "按已发现的问题逐条写评论，不要重新审查。",
    "mode": "fork",
}

fork 继承父对话与提示，指令跟在任务消息里，能复用提示缓存；代价是不能再用 task。

七、常见坑（官方明确限制/版本差异）

  1. description 写成介绍。要写「什么时候用」，否则主代理不会选它。
  2. 以为 tools 是追加。指定即替换，主代理的工具不会自动传下去。
  3. 以为技能会继承。只有 general-purpose 继承；自定义子代理要自己给 skills。
  4. 把报告当交付。子代理报告对用户不可见，主代理必须转述或落盘。
  5. fork 里再调 task。不支持；fork 必须自己干完。
  6. 给子代理过宽权限。默认继承父权限，但 permissions 一旦设置是整体替换——写漏就会出现「本该禁的没禁」。
  7. 子代理输出太长。它的输出会进主上下文；在 system_prompt 里限字数/限条数。
  8. 为两步骤任务拆子代理。开销大于收益，直接做。

八、课后小结

  • 子代理 = 独立上下文 + 独立工具 + 独立提示，通过 task 调用；
  • general-purpose 永远存在，同工具同模型，可用于兜底隔离；
  • description 决定选人，system_prompt 决定产出格式；
  • isolated 适合新活，fork 适合接手父代理已查清的事；
  • 子代理的中间过程不进主上下文，报告才进。

九、思考题

1、子代理为什么能省上下文？

参考回答：只有最终报告回到主代理，中间的几十次工具调用与结果都留在子代理自己的上下文里。

2、tools 替换而不是追加，好处是什么？

参考回答：可以真正做权限分离——子代理只拿到它需要的能力，误用与注入面都小。

3、什么时候必须用 fork？

参考回答：任务依赖父代理已经建立的判断与中间发现，且重做成本高（例如已定位的问题、已读过的 diff）。

4、为什么官方保留了 general-purpose？

参考回答：没有专门子代理时也要有隔离手段；它同工具同模型，等于「把重活挪出去」的默认通道。
