Deep Agents 13 · 人工审批

分类：ai · deepagents ｜ 标签：Deep Agents · LangChain · 系统课

13 人工审批

被拦下的是这一次工具调用，不是整轮对话；决策一旦给出，图从检查点原地续跑｜依据官方 human-in-the-loop 页自绘

版本不一致提示

  • 本篇基线是 deepagents 0.7.42 + langchain 1.5.2 + langgraph 1.2.24 + Python 3.13；
  • 配了 interrupt_on，create_deep_agent 会自动往栈里插 HumanInTheLoopMiddleware，不需要你手动 middleware=；
  • 必须自己传 checkpointer：实测 checkpointer=True 对根图直接报 RuntimeError: checkpointer=True cannot be used for root graphs，要传 InMemorySaver() 或外部持久化 saver；
  • 恢复用 Command(resume={"decisions": [...]})，且必须与首次调用同一个 thread_id；
  • 决策 edit 的载荷键名是 edited_action（内含 name 与 args）；只给 args 会撞 KeyError: 'edited_action'；
  • 条件中断的 when 谓词需要 langchain>=1.3.3；文件权限中断 mode="interrupt" 需要 deepagents>=0.6.8；
  • interrupt_on 拦的是工具调用，管不住沙箱里 execute 的 shell。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清中断发生在「模型已经决定、工具还没执行」的那一格；
  2. 配出四种决策（approve / edit / reject / respond），并知道每种决策回到模型时是什么形状；
  3. 用 when 把审批收窄到「只拦危险的那几次调用」，而不是每个写操作都弹窗。

二、前置知识

  • 读完 DA05 权限规则，知道 permissions= 的 first-match-wins；
  • 有 LangGraph 中断概念（LG06 中断 级别即可）；
  • 知道 checkpointer 是干什么的（LG05 检查点）。

三、理论讲解（官方定义）

1. 它解决什么

「模型想做的事」和「真正被允许做的事」之间要有一道门。interrupt_on 就在这道门上：命中名单的工具调用先不执行，把调用参数交给人看，人给决策，图再从检查点继续。

2. 三种配置形态

  • True：默认开，四个决策全可用；
  • False：显式关掉（写出来是为了让配置可读）；
  • InterruptOnConfig：细配，字段是 allowed_decisions / description / args_schema / when。

3. 四种决策

决策
含义
回到模型的东西
approve
原样执行
工具真实结果，如 Updated file /workspace/out.md
edit
改参数再执行
带一句「人工替换过这次调用」的提示 + 执行结果
reject
跳过执行
User rejected the tool call for … with reason: …
respond
人直接当工具回答
内容即工具结果，工具不执行

respond 只适合「问人」型工具（如 ask_user）。拿它去拒一个会写东西的工具，模型会把你的话当成成功的工具结果。

4. 中断载荷长什么样

一次被拦下的调用，invoke 返回里会多出 __interrupt__：

out["__interrupt__"][0].value
# {
#   "action_requests": [
#     {"name": "write_file",
#      "args": {"file_path": "/workspace/out.md", "content": "hello"},
#      "description": "Tool execution requires approval\n\nTool: write_file\nArgs: {...}"}
#   ],
#   "review_configs": [
#     {"action_name": "write_file",
#      "allowed_decisions": ["approve", "edit", "reject", "respond"]}
#   ]
# }

action_requests 是等人批的动作，review_configs 是每个动作当前允许的决策。前端照这两个数组渲染，不要自己猜有哪些按钮。

5. 五个细项

  • allowed_decisions：按风险裁剪。删库只给 ["approve", "reject"]，发邮件给 ["approve", "edit", "reject"]；
  • description：给人看的说明，可写成固定字符串或按请求生成的函数；
  • args_schema：给编辑表单用的参数结构；
  • when：条件谓词，返回 False 就直接放行、不进审批批次；
  • interrupt_mode："batched"（默认，一轮里的多个调用合成一次审批）或 "per_call"。

四、原理拆解：为什么它必须挂在检查点上

Deep Agents 的图是「模型节点 ↔ 工具节点」的循环。审批中间件在模型节点之后、工具节点之前截住调用：

  1. 模型产出 tool_calls；
  2. 中间件发现命中名单 → 抛 interrupt，本次 invoke 返回，图停在检查点；
  3. 人给决策 → Command(resume=...) 回到同一个 thread_id；
  4. 中间件按决策重建这次工具调用（或直接造一条 ToolMessage），工具节点照常往下跑。

第 2 步和第 4 步之间可能隔了几小时。所以「状态」必须落在 checkpointer 里，而不是进程内存里——这也是为什么没有 checkpointer 时，恢复会直接报错。

batched 的意义：模型一轮里同时调了 delete_file 和 send_email，你只收到一个中断，action_requests 里两条，decisions 必须按同样顺序给两条。顺序错位不会报参数错，而是把批准发给了另一条——这是最隐蔽的一类事故。

五、场景说明

  • 该开：不可逆（删文件、关单、退款）、对外（发邮件、发消息、调用第三方下单）、花钱、改生产数据；
  • 不该开：只读查询、可回滚的内部草稿、同一次任务里会被调用几十次的批量工具（弹窗会把人逼疯）；
  • 按工具粒度：官方推荐的姿势是同一个 agent 里 read_file: False、delete_file: {"allowed_decisions": ["approve","reject"]}，而不是整轮都要审批。

六、示例代码

步骤 1：环境准备

uv init da13-hitl
cd da13-hitl
uv add deepagents

步骤 2：凭证配置

本讲用假模型干跑，不需要任何 key。真实模型见写法 A。

步骤 3：导入

from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage, HumanMessage
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command
from deepagents import create_deep_agent

步骤 4：最小可运行代码（干跑，验证中断真的发生）

存成 hitl_gate.py，uv run hitl_gate.py。假模型只发一次 write_file 调用，脚本打印中断载荷。

from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage, HumanMessage
from langgraph.checkpoint.memory import InMemorySaver
from deepagents import create_deep_agent

class Fake(GenericFakeChatModel):
    """假模型：补上 bind_tools，才能进 agent 的工具循环。"""
    def bind_tools(self, tools, **kw):
        return self

call = AIMessage(content="", tool_calls=[{
    "name": "write_file",
    "args": {"file_path": "/workspace/out.md", "content": "hello"},
    "id": "w1",
}])

agent = create_deep_agent(
    model=Fake(messages=iter([call, AIMessage(content="done")])),
    interrupt_on={"write_file": True},
    checkpointer=InMemorySaver(),
)

cfg = {"configurable": {"thread_id": "hitl-1"}}
out = agent.invoke(
    {"messages": [HumanMessage(content="把结论写到 /workspace/out.md")]},
    config=cfg,
)

pending = out["__interrupt__"][0].value
print("待审动作:", [a["name"] for a in pending["action_requests"]])
print("可做决策:", pending["review_configs"][0]["allowed_decisions"])

步骤 5：预期输出

待审动作: ['write_file']
可做决策: ['approve', 'edit', 'reject', 'respond']

步骤 6：验证是否成功

  • 返回里有 __interrupt__ → 中间件确实插进去了；
  • files 里还没有 /workspace/out.md → 工具确实没执行（这一步是关键，别只看有没有中断）；
  • 打印的 allowed_decisions 与你的配置一致。

写法 A · 四种决策各走一遍，看它们回到模型是什么

每次决策都要一个新的 agent（假模型的响应流是一次性的），所以把构造包成函数：

from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage, HumanMessage
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command
from deepagents import create_deep_agent

class Fake(GenericFakeChatModel):
    def bind_tools(self, tools, **kw):
        return self

def build():
    call = AIMessage(content="", tool_calls=[{
        "name": "write_file",
        "args": {"file_path": "/workspace/out.md", "content": "hello"},
        "id": "w1",
    }])
    return create_deep_agent(
        model=Fake(messages=iter([call, AIMessage(content="after")])),
        interrupt_on={"write_file": True},
        checkpointer=InMemorySaver(),
    )

def run(decision):
    agent = build()
    cfg = {"configurable": {"thread_id": "x"}}
    out = agent.invoke({"messages": [HumanMessage(content="写文件")]}, config=cfg)
    out = agent.invoke(Command(resume={"decisions": [decision]}), config=cfg)
    tool = [m for m in out["messages"] if m.type == "tool"][-1]
    print(decision["type"], "→", tool.content[:40])

run({"type": "approve"})
run({"type": "reject", "message": "路径不对，写到 /workspace/reports/"})
run({"type": "edit", "edited_action": {
    "name": "write_file",
    "args": {"file_path": "/workspace/out.md", "content": "edited"},
}})
run({"type": "respond", "message": "不用写了，直接给结论"})

真实输出（截断）：

approve → Updated file /workspace/out.md
reject → User rejected the tool call for `write_file` with reason: 路径不对…
edit → Note: a human reviewer replaced this tool call before it ran…
respond → 不用写了，直接给结论

注意 edit 的载荷是 edited_action，不是 args；respond 的 message 会原样变成工具结果。

写法 B · 只拦危险的那几次：when 条件中断

from deepagents import create_deep_agent
from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents.middleware import ToolCallRequest

def outside_workspace(request: ToolCallRequest) -> bool:
    """只审「写到 /workspace 之外」的调用。"""
    path = request.tool_call["args"].get("file_path", "")
    return not path.startswith("/workspace/")

agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    interrupt_on={
        "write_file": {
            "allowed_decisions": ["approve", "reject"],
            "when": outside_workspace,
        },
    },
    checkpointer=InMemorySaver(),
)

实测：写 /workspace/a.md 不中断、直接落盘；写 /etc/x.md 才中断，且 review_configs 里只剩 ["approve", "reject"]。

同一扇门还能用权限规则开：FilesystemPermission(operations=["write"], paths=["/secrets/**"], mode="interrupt")，命中路径的 write_file 会走同一套审批流程，并与 interrupt_on 合并成一个审批批次。

七、常见坑（官方明确限制/版本差异）

  1. 没传 checkpointer。Cannot use Command(resume=...) without checkpointer；中断能发生，但恢复不了。
  2. checkpointer=True。根图不允许，实测直接 RuntimeError；要传 saver 实例。
  3. 恢复时换了 thread_id。找不到断点，看起来像「决策丢失」。
  4. 决策顺序与 action_requests 不对齐。批量审批时错位会把批准发给另一条调用。
  5. edit 只给 args。键名必须是 edited_action{name,args}，否则 KeyError。
  6. 拿 respond 当拒绝。它的内容会被模型当成成功结果，副作用工具照样「算办完了」。
  7. 审批开在只读工具上。read_file/ls 也弹窗，人很快就会全部点通过——审批形同虚设。
  8. 拒绝不给 message。模型只知道「没执行」，容易换个参数再试；写清「别重试、改走哪条路」。
  9. 以为它管得住 shell。沙箱里 cat .env 不经过任何工具审批。

八、课后小结

  • 中断点在「模型决定之后、工具执行之前」，恢复靠检查点 + 同一 thread_id；
  • 四种决策各有形状：approve 给真结果、edit 给替换提示、reject 给拒绝理由、respond 给人话；
  • 审批要按工具、按条件收窄，别按轮次；
  • 权限规则 mode="interrupt" 与 interrupt_on 共用同一条审批路径；
  • 它是人的门，不是权限系统；沙箱边界仍要靠 DA06。

九、思考题

1、为什么 interrupt_on 恢复必须带同一个 thread_id？

参考回答：中断把「待执行的调用」写进了该线程的检查点；换线程等于去另一份快照里找断点，自然找不到。

2、reject 与 respond 都能让工具不执行，区别在哪？

参考回答：reject 告诉模型「这次被拒了」，带原因；respond 直接把人的话当工具结果，模型会认为工具成功返回。

3、批量审批里为什么决策要按顺序给？

参考回答：decisions 是按 action_requests 位置匹配的，不按工具名匹配；错位会把决策套到另一条调用上。

4、什么情况下不该用 interrupt_on，而该用权限 deny？

参考回答：根本不允许做的事（如读 .env）用 deny，因为它没有「人批准就放行」的余地；interrupt 只留给「有时可以、需要人判断」的动作。
