05 筛选与数据集

筛的是「已经发生过的事」，固化的是「以后每次都要跑一遍的题」｜依据官方 Filter traces / Manage datasets 页自绘

版本不一致提示

  • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + Python 3.13；
  • 过滤语法是 trace filter 表达式，字段名区分大小写：metadata.tenant、feedback_score、tags 是 2026 年后的常用写法；
  • client.list_runs 的 filter 作用于 run，trace_filter 作用于整条 trace；要按整条 trace 过滤用后者；
  • dataset 的 example 永久保留，trace 会按套餐保留期删除——把问题样本固化进 dataset 才是长期资产；
  • create_example(..., split="...") 里的 split 是字符串自由值，不是预定义的 train/test 枚举；官方没有 create_dataset_split，split 靠 list_dataset_splits 读、靠写 example 时带值；
  • 本篇必须有真实 key：Client() 构造不需要联网，但任何读取（list_runs / list_datasets）都会打到 API，无 key 直接 401——这一段没法离线演练。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用表达式从 trace 池里筛出「某租户 + 差评 + 生产标签」的问题样本；
  2. 用 Python SDK 把筛出来的 run 固化成 dataset 的 example，并带上 split；
  3. 说清 trace 与 dataset 的寿命差别，以及为什么不能只靠「留着 trace」。

二、前置知识

  • 读完 04，能从多视图定位问题 run；
  • 知道 metadata / tags / feedback 三种富化的含义（02）。

三、理论讲解（官方定义）

1. 过滤的两个层次

  • run 级：只看单个 run 的属性（run_type、name、status、latency）；
  • trace 级：看整条 trace 的根属性与聚合值（feedback_score、tags、metadata）。

两者语法一致，但作用对象不同。「这条会话的评分低于 0.5」必须用 trace 级，否则子 run 的分数会混进来。

2. 常用表达式

目标
表达式
按租户
eq(metadata.tenant, "A")
差评
lt(feedback_score, 0.5)
生产标签
has(tags, "prod")
指定 run 类型
eq(run_type, "llm")
慢请求
gt(latency_sec, 3)

表达式里的字段名直接对应 run 的属性名；metadata 下的键用点号访问。

3. 降采样

官方支持对 trace 采样后再评测（例如只取 20% 的生产流量跑在线评测器）。采样是在筛选之后做的，所以「先筛出目标人群，再按比例抽样」的顺序不要反。

4. dataset 与 example

  • dataset：一组输入（必要时带 reference outputs）；
  • example：dataset 里的一条题目；永久保留，不受 trace 保留期影响；
  • split：example 上的一个字符串标签，用来区分 smoke / regression 这类子集。

从 trace 造 example 有两个关键参数：use_source_run_io=True（把这条 run 的 inputs / outputs 直接抄成 example 的输入 / 参考输出）与 source_run_id。

四、原理拆解：为什么「筛 → 固化」要分两步

trace 是流水：会按保留期消失，且带着大量无关上下文；dataset 是题库：只留「输入 + 应有答案」，可以反复跑、可以版本化对比。

所以正确姿势是：

  1. 在 trace 池里按表达式筛出问题样本；
  2. 逐条判断「这是不是一类会被反复问到的问题」；
  3. 是 → 固化成 example，并打 split；
  4. 不是 → 只记一笔，不占题库。

一个容易犯的错：直接把「当时的模型输出」抄成 reference_outputs。那条输出可能本来就是错的，抄进去等于把错误固化成标准答案。

五、场景说明

某租户 A 报「退款答复不一致」。你在 trace 池里筛 eq(metadata.tenant,"A") + lt(feedback_score,0.5)，得到 12 条；其中 5 条属于同一类问题（退款到账时间说法不一），把这 5 条固化成 example，打 split="regression"；后面每次改 prompt 都跑这个子集，就能确认「这次改动有没有让老问题复发」。

六、示例代码

步骤 1：环境准备

uv init ls05-dataset
cd ls05-dataset
uv add langsmith python-dotenv

步骤 2：凭证配置

.env：LANGSMITH_TRACING=true、LANGSMITH_API_KEY=...、LANGSMITH_PROJECT=ticket-agent-dev。

步骤 3：导入

from langsmith import Client

步骤 4：最小可运行代码

存成 dataset.py，uv run dataset.py。没有真实 run 时，先造三条带 metadata 的 run，再筛、再固化。

import os
from dotenv import load_dotenv
from langsmith import Client, traceable

load_dotenv()
client = Client()

@traceable
def answer(q: str) -> str:
    return f"回答：{q}"

if __name__ == "__main__":
    # 1) 造 3 条 trace，带租户 metadata
    ids = []
    for q, tenant in [("退款怎么走？", "A"), ("多久到账？", "A"), ("发票怎么开？", "B")]:
        run = answer(q, langsmith_extra={"metadata": {"tenant": tenant}})
        ids.append(run)

    # 2) 筛：租户 A 的 trace（trace 级过滤用 trace_filter）
    runs = client.list_runs(
        project_name=os.getenv("LANGSMITH_PROJECT"),
        trace_filter='eq(metadata.tenant, "A")',
        is_root=True,
        limit=10,
        select=["id", "inputs", "outputs"],
    )
    picked = list(runs)
    print("matched:", len(picked))

    # 3) 固化：数据集 + 带 split 的 example
    ds_name = "refund-regression"
    if ds_name not in [d.name for d in client.list_datasets()]:
        client.create_dataset(dataset_name=ds_name, description="退款答复回归集")

    for r in picked:
        client.create_example(
            inputs=r.inputs,
            dataset_name=ds_name,
            split="regression",
            source_run_id=r.id,
        )

    print("splits:", [s for s in client.list_dataset_splits(ds_name)])

步骤 5：预期输出

matched: 2
splits: ['regression']

步骤 6：验证是否成功

  • UI 的 Datasets 里出现 refund-regression，含 2 条 example；
  • 每条 example 的 split 是 regression，source_run_id 指向刚才的 run；
  • 把 trace_filter 改成 'eq(metadata.tenant, "B")' 再跑一次：matched: 1，说明过滤确实按 metadata 生效；
  • 关掉上报（LANGSMITH_TRACING=false）再跑：matched: 0，因为本机这次没产生 trace——这也说明「筛的是已上传的历史」，不是本地内存。

写法 A · 用 Run 对象直接造 example

# use_source_run_io=True 时，inputs / outputs 会被 run 的输入输出覆盖
client.create_example(
    inputs={},                      # 占位，最终被 run.inputs 覆盖
    dataset_name="refund-regression",
    split="smoke",
    source_run_id=picked[0].id,
    use_source_run_io=True,
)

适合「这条 run 的输入输出正是我想留下的题面与答案」的场景；如果 run 的输出是错的，别开这个开关，手工写 reference_outputs。

七、常见坑（官方明确限制/版本差异）

  1. run 级过滤查 trace 级字段。用 filter 查 feedback_score 会查不到，改用 trace_filter。
  2. 把当时输出抄成 reference。错误答案固化进题库，后面所有实验都以错为对。
  3. 以为 split 是枚举。它是自由字符串，写错名字不会报错，只会多出一个空 split。
  4. 筛完直接全量固化。题库膨胀、跑一次评测十分钟；只留「会反复出现」的类别。
  5. 依赖 trace 长期存证。保留期一到就没了；要留证据必须落 dataset 或导出。
  6. 采样写在筛选前。先按比例抽样会漏掉小租户的问题样本。

八、课后小结

  • 过滤分 run 级（filter）与 trace 级（trace_filter），字段名区分大小写；
  • 采样在筛选之后；
  • dataset 的 example 永久保留，trace 会过期——问题样本要尽早固化；
  • split 是自由字符串，靠 create_example(..., split=...) 打标、list_dataset_splits 读取；
  • 参考输出必须人工确认，不要抄当时的模型输出。

九、思考题

1、为什么 feedback_score 要用 trace 级过滤？

参考回答：分数是「这条会话好不好」的判定，挂在根 run 上；run 级过滤会命中子 run 的分数，导致重复计入与误筛。

2、dataset 与 trace 的寿命差异对流程有什么影响？

参考回答：trace 是短期证据，dataset 是长期题库；流程上必须「先固化、再清理」，否则改完 prompt 就没有对比基准了。

3、什么信号说明该新建一个 dataset 而不是往老题库里加？

参考回答：输入形态变了（换了任务类型）、参考输出标准变了、或者评测器口径变了；混在一个 dataset 里会让历史实验无法比较。

4、只筛「差评」样本有什么风险？

参考回答：题库会偏向难例，测出的分数不能代表线上分布；要按比例掺入正常样本，或者另建一个 smoke 子集做基线。
