09 在线评测与标注

线上评测负责「发现」，标注队列负责「定性」，数据集负责「不再犯」｜依据官方 Online evaluation 页自绘

版本不一致提示

  • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + Python 3.13；
  • 本篇必须有真实 key；在线评测（online evaluators）的挂载只能在平台侧配置（Evaluators → Rules：选评测器 + filter + 采样率），SDK 0.16.2 里没有 create_run_rule 之类的写接口；
  • 标注队列的 SDK 接口是 create_annotation_queue / add_runs_to_annotation_queue / list_runs_from_annotation_queue，队列状态只有 needs_my_review / needs_others_review / completed；
  • 在线评测是异步跑在 trace 上的，分数会晚于 trace 出现；刚跑完就查 feedback_score，可能还是空的。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 在平台上挂一组在线评测（格式硬校验 + 抽样 judge），并说清 filter 与采样各挡掉多少成本；
  2. 用 SDK 把低分 trace 批量推进标注队列，让人工只审该审的；
  3. 把人工结论落成 feedback、再一键转成 dataset 的 example，形成闭环。

二、前置知识

  • 读完 08 离线实验与门禁，知道分数怎么算；
  • 有线上流量进到某个环境（01）。

三、理论讲解（官方定义）

1. 在线评测与离线评测的分工

  • 离线：给定题库，跑一遍，得到「版本之间的相对好坏」；优点是可比，缺点是题不代表线上分布；
  • 在线：在生产 trace 上打分，得到「真实流量的绝对水位」；优点是真实，缺点是没有参考答案，只能用无参考判据。

所以在线评测常用的三类判据是：格式/结构校验（有没有 JSON、字段齐不齐）、安全与合规（敏感词、越权承诺）、无参考质量 judge（是否回答了问题、是否自相矛盾）。

2. filter 与 sampling

  • filter：只让某一类 trace 进评测（例如 eq(metadata.tenant,"A") 或只测带工具调用的）；
  • sampling：按比例抽样（例如 10%），控制 judge 的 token 成本。

两者顺序是先 filter 再 sample；反了就会「抽到的样本里没有目标人群」。

3. 标注队列

队列是「人审的工作台」：一条 trace 进去，带着 rubric（评分说明）与待填的 feedback 表单。审完写 feedback，状态置 completed。队列的价值不在于「收集意见」，而在于把意见变成可复跑的题。

四、原理拆解：闭环的每一跳靠什么衔接

  1. trace 进环境 → 平台按 Rule 触发评测器 → 写 feedback（key + score）；
  2. 低分 trace 被 filter 命中 → 脚本/Rule 推进队列；
  3. 人审 → 写 human_* feedback（与机器分数并存，不覆盖）；
  4. create_example_from_run 把该 run 的输入转成 example（参考输出要人写，不能抄 run 的输出）；
  5. 下次离线实验覆盖这条题 → 通过 → 线上继续跑同一 Rule 验证。

关键：第 4 步是唯一把「线上偶发」变成「永久考题」的地方。不做这一步，前面的分都是消耗品。

五、场景说明

退款 Agent 上线后，格式错误率偶发升高。做法：

  • Rule A：格式校验，全量跑（code 评测，几乎零成本）；
  • Rule B：无参考 judge（「是否给出明确到账时间」），只对 10% 流量 + 只对 has(tags,"prod") 跑；
  • Rule C：格式失败或 judge 低于 0.5 的 trace，自动进 refund-review 队列；
  • 每天清一次队列：确认是模型问题还是用户问题，是模型问题就转成 example。

六、示例代码

步骤 1：环境准备

uv init ls09-online
cd ls09-online
uv add langsmith python-dotenv

步骤 2：凭证配置

.env：LANGSMITH_API_KEY、LANGSMITH_PROJECT=ticket-agent-prod。

步骤 3：导入

from langsmith import Client

步骤 4：最小可运行代码

存成 queue.py，uv run queue.py。

import os
from dotenv import load_dotenv
from langsmith import Client

load_dotenv()
client = Client()
PROJ = os.getenv("LANGSMITH_PROJECT")
Q_NAME = "refund-review"

# 1) 建队列（幂等：按名字找，没有才建）
q = next((q for q in client.list_annotation_queues() if q.name == Q_NAME), None)
if q is None:
    q = client.create_annotation_queue(
        name=Q_NAME,
        description="退款 Agent 低分样本复审",
        rubric_instructions="1) 是否给出明确到账时间 2) 是否承诺了做不到的事 3) 是否需要转人工",
    )

# 2) 捞低分 trace（trace 级过滤，只看根 run）
bad = list(client.list_runs(
    project_name=PROJ,
    trace_filter="lt(feedback_score, 0.6)",
    is_root=True,
    limit=20,
    select=["id", "inputs", "outputs"],
))

# 3) 推进队列
client.add_runs_to_annotation_queue(q.id, run_ids=[r.id for r in bad])
print("queued:", len(bad))

# 4) 审完的样本：写人工分 + 转成 dataset example
if bad:
    client.create_feedback(run_id=bad[0].id, key="human_ok", score=0)
    client.create_example_from_run(run=bad[0], dataset_name="refund-faq")

print("queue status:", {s: len(list(client.list_runs_from_annotation_queue(q.id, status=s)))
                        for s in ("needs_my_review", "completed")})

步骤 5：预期输出

queued: 3
queue status: {'needs_my_review': 3, 'completed': 0}

（queued 的条数取决于你环境里真实的低分 trace，没数据时可能为 0。）

步骤 6：验证是否成功

  • 平台 Annotations 页出现 refund-review 队列，条目带 rubric 三条说明；
  • 在队列里点开一条：能看到 trace 详情与 feedback 表单；
  • 给它打 human_ok = 0 后刷新：该条状态变 completed，且原 trace 上同时存在机器分与人工分两个 key；
  • refund-faq dataset 里多了一条 example，inputs 与 run 一致——但参考输出是空的，需要人去补，这就是官方不给自动填的原因。

写法 A · 让 Rule 自动推进队列

平台的 Rule 支持「命中 filter 的 trace 自动进队列」，比脚本轮询更省事：Rule → filter lt(feedback_score, 0.6) → action「add to annotation queue」。脚本适合做批量补偿（例如漏网的、或按租户单独捞）。

七、常见坑（官方明确限制/版本差异）

  1. 在线评测全量跑。judge 按 token 计费，全量一周账单能吓人；先 5%–10%。
  2. judge 与线上模型同源。同源会一起错，在线分数变成「自己给自己打分」。
  3. 队列没人清。feedback 烂在队列里，等于没做；给队列定「每天清空」的 owner。
  4. 把 run 的输出当 reference。线上输出可能本来就是错的，create_example_from_run 只搬输入，参考要人写。
  5. 刚跑完就查 feedback_score。在线评测异步执行，分数会晚到；脚本里要留重试或延后窗口。
  6. filter 写 run 级条件查 trace。feedback_score 属于 trace 级，用 trace_filter。
  7. 不同 Rule 用同名反馈 key。两条 Rule 的分数混成一列，趋势无法区分。

八、课后小结

  • 在线评测管「发现」，离线评测管「比较」，两者不可替代；
  • filter 决定人群，sampling 决定成本，顺序不能反；
  • 在线评测的挂载在平台侧（Rules），SDK 只做批量补偿；
  • 队列是工作台，create_example_from_run 才是把事故变成考题的那一步；
  • 人工分与机器分用不同 key 并存，别覆盖。

九、思考题

1、为什么在线评测不能有参考答案？

参考回答：生产流量没有「标准答案」可对照，也没有人会给每条 trace 标参考；只能用无参考判据（格式、合规、自洽性）来打分。

2、采样率该怎么定？

参考回答：先按「能覆盖到足够多失败样本」的最小比例起步（如 5%），看一周内的失败条数是否够支撑排障，再决定加减；不要按「看起来完整」定 100%。

3、队列里的人工分和机器分为何要并存？

参考回答：两者回答不同问题——机器分是「规模化初筛」，人工分是「校准与定性」。并存才能算「机器判官与人判的一致率」，为 judge 调参提供依据。

4、如果一条低分 trace 是「用户问题本身无解」，还要转 example 吗？

参考回答：要，但参考输出应写成「明确告知无法办理并给出替代路径」，这样它考的是「拒答质量」而不是「答对」。
