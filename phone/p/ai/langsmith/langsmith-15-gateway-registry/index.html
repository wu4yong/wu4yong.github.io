15 网关与注册

网关解决「不写代码也有调用链」，注册表解决「谁在用、谁负责」｜依据官方 LLM Gateway 页自绘

版本不一致提示

  • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + openai SDK + Python 3.13；
  • LLM Gateway 走 OpenAI 兼容接口：把 base_url 指到网关，模型调用就自动带上 trace，业务代码不用加装饰器；
  • Agent Registry / Fleet 是平台侧能力，SDK 0.16.2 没有登记与编排接口，本篇这部分以平台操作为准；
  • 网关侧 trace 与业务侧埋点会各记一份，同一请求在 UI 里可能出现两条链——不是 bug，是两层观测；
  • 网关转发会产生额外一跳延迟（通常几十毫秒级），对延迟敏感链路要实测再决定是否全量走网关。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 把模型调用改走网关，验证「零代码也有 trace」，并认出双份 trace；
  2. 判断哪些流量该走网关、哪些该保留直连；
  3. 用注册表把散落的 agent 收成可治理的清单，明确负责人与环境归属。

二、前置知识

  • 读完 14 发现与修复；
  • 手上至少有一个「不方便改代码」的调用方（老服务、第三方脚本、另一个团队的应用）。

三、理论讲解（官方定义）

1. Gateway 做了什么

它是模型调用的前置代理：接收 OpenAI 兼容请求 → 转发给真实 provider → 同时把这次调用记成 run（含模型、token、耗时、状态）。所以：

  • 不用改业务代码，只改 base_url 与 key；
  • 覆盖的是「模型调用」这一层，工具调用、检索、业务逻辑仍要自己埋点；
  • 多 provider 可以在网关侧统一配，业务侧只认一个地址。

2. 双份 trace 从哪来

如果业务代码里已经用 @traceable 埋了一层，网关又记一份，就会出现「业务 run 下面挂一个网关 run」或两条平行链。判断方法：看 run_type 与 name——网关侧通常是网关自己的命名，业务侧是你的函数名。

正确姿势是选一层为主：要么业务侧埋全、网关只做转发（关掉网关 trace），要么网关记全、业务侧精简。两边都全量记，run 数与成本都会翻倍。

3. Agent Registry 与 Fleet

  • Registry：登记「有哪些 agent、归哪个 workspace、负责人是谁、跑在哪个环境」，是治理清单，不托管运行；
  • Fleet / Managed Deep Agents：平台侧直接跑 agent，不写部署代码；适合标准化场景（客服问答、文档处理）。

两者解决的是不同问题：Registry 解决「看不见」，Fleet 解决「跑不起来」。

四、原理拆解：为什么改一个 base_url 就能有调用链

网关在 HTTP 层做拦截，所以它拿得到的信息是「请求体 + 响应体 + 时间」：

  • 请求里的 model、messages、temperature → run 的 inputs 与 metadata；
  • 响应里的 usage → token 统计；
  • HTTP 状态与耗时 → status 与 latency。

它拿不到的是「这次调用属于哪个业务会话」——除非你把 thread_id 之类的信息放进请求头或 metadata 透传。所以网关 trace 往往「有调用、没上下文」，要和业务侧 trace 用 trace_id / 时间窗对齐。

五、场景说明

老 CRM 系统里有一段直连 OpenAI 的代码，团队不愿动。把它的 OPENAI_BASE_URL 指到网关后，所有调用立刻有了 trace 与成本统计；再在网关上按 workspace 分 key，就能区分「哪个系统花了多少钱」。代价是这段代码的 trace 里没有业务上下文，排障时要靠时间窗去业务日志里对。

六、示例代码

步骤 1：环境准备

uv init ls15-gateway
cd ls15-gateway
uv add openai python-dotenv

步骤 2：凭证配置

.env：

GATEWAY_BASE_URL=https://gateway.smith.example.com/v1
GATEWAY_API_KEY=lsv2_pt_xxxxxxxx

步骤 3：导入

import os
from openai import OpenAI

步骤 4：最小可运行代码

存成 via_gateway.py，uv run via_gateway.py。

import os
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()

# 只改两个参数：base_url 与 key
client = OpenAI(
    base_url=os.getenv("GATEWAY_BASE_URL"),
    api_key=os.getenv("GATEWAY_API_KEY"),
)

resp = client.chat.completions.create(
    model="gpt-4.1-mini",
    messages=[{"role": "user", "content": "退款多久到账？"}],
    temperature=0,
    extra_headers={"X-Session-Id": "T-9d2"},          # 可选：透传会话标识给网关（header 名以网关文档为准）
)
print(resp.choices[0].message.content)

步骤 5：预期输出

3 个工作日到账。

步骤 6：验证是否成功

  • 平台对应环境里出现这次调用的 run，run_type 为 llm，带 token 与耗时；
  • 把 GATEWAY_BASE_URL 换回 provider 直连再跑一次：没有新 run——证明 trace 是网关带来的；
  • 如果业务侧同时也埋了 @traceable，UI 里会出现两层；确认你要保留哪一层，另一层关掉；
  • 用网关的 key 分 workspace 各建一个：两个系统的用量在账单里能分开。

写法 B · Registry 的登记清单

登记时至少写清四件事：agent 名、所属 workspace、负责人、运行环境。少写负责人，半年后没人敢动；少写环境，排障时会看错对象。

七、常见坑（官方明确限制/版本差异）

  1. 以为网关能替代埋点。它只覆盖模型调用，检索 / 工具 / 业务逻辑仍要自己埋。
  2. 双份 trace 双份成本。两层都全量记，run 数翻倍。
  3. 网关 trace 没有业务上下文。不传 session / thread 标识，就只能靠时间窗对。
  4. 延迟没实测就全量切。多一跳代理，长尾请求可能被放大。
  5. Registry 登记了但没负责人。清单变成摆设。
  6. 把网关 key 当 provider key 用。两者格式与权限不同，混用会 401。

八、课后小结

  • 网关的价值是「零代码覆盖模型调用」，边界是「只有模型调用」；
  • 双份 trace 要主动选一层为主，不是越多越好；
  • 网关 trace 缺业务上下文，靠 header 透传或时间窗对齐；
  • Registry 解决「看不见」，Fleet 解决「跑不起来」；
  • 前四家 provider 在网关侧协议统一，Claude 要分支。

九、思考题

1、为什么网关拿不到「这次调用属于哪个会话」？

参考回答：它只看到 HTTP 请求，不知道上层的 thread / session 语义；除非业务把标识放进 header 或 metadata 透传。

2、什么情况下应该关掉业务侧埋点、只留网关？

参考回答：业务逻辑简单、只关心模型调用与成本、且不想维护埋点代码时；一旦需要看检索与工具链，就必须回到业务侧埋点。

3、Registry 的第一字段为什么是负责人而不是版本号？

参考回答：治理的对象是「谁能让它停/改」，版本号会变、负责人不变；没有负责人的资源在事故中无人认领。

4、网关全量切的最大风险是什么？

参考回答：单点故障——网关不可用时所有模型调用一起失败；要有降级直连的开关，而不是硬编码 base_url。
