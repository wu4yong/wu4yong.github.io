16 综合实战

每一步都要留下一个能被人接手的产物，否则闭环只是流程图｜本篇自绘

版本不一致提示

  • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + openai SDK + Python 3.13，被测对象是 LG16 的工单 Agent；
  • 本篇必须有真实 key + 一个可用模型；脚本里所有 # ← 换成你的 处都要替换，否则跑不通；
  • 门禁阈值、采样率、告警渠道都要按你的业务定，本篇给的是可运行的骨架，不是参数推荐；
  • 部署部分（LS12）不在本篇执行，只给「实验通过后怎么发布」的顺序；
  • 全套跑完会产生实验与 feedback，占配额，别在共享组织里反复压测。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 把 LG16 的工单 Agent 接进 LangSmith，六步各留下一个产物（trace / 队列 / dataset / 实验 / 门禁结果 / 告警规则）；
  2. 用一份脚本跑通「抽单 → 建库 → 三评测器 → 两版对比 → 门禁」；
  3. 把门禁接进 CI，让「分数掉了」在合并前就被挡住，而不是上线后才知道。

二、前置知识

  • 全系列前 15 讲，尤其 08 门禁 与 09 在线评测；
  • 有 LG16 的工单 Agent（含审批节点与人工介入）。

2. 为什么每一步都要「产物」

闭环最常见的断点是「做了但没留下东西」：抽了单没进队列、审了没写 feedback、修了没补 example。产物是交接物，也是下一次的输入。

3. 三评测器怎么分工

  • format_ok（code）：输出是否为合法结构、字段齐不齐——零成本、必跑；
  • has_sla（judge）：是否给出明确处理时限——无参考判据，用无参考 judge；
  • no_overpromise（judge）：是否承诺了做不到的事——合规类，抽样跑。

四、原理拆解：门禁为什么放在第 6 步而不是第 5 步

实验只产出「数字」，门禁要产出「决策」。两者的差别是：

  • 实验有随机性（repetitions），数字会抖；
  • 决策需要容差与退化条数（LS08）；
  • 决策还要有人可读的失败清单，否则值班只会重跑。

所以第 6 步必须有三个输出：退出码、退化清单、告警。少了任何一个，门禁都会退化成「看一眼分数」。

五、场景说明

工单 Agent 上线后第一周：审批阈值 500 被误判 3 次、退款答复承诺「当天到账」2 次。第二周把这两类落成 regression 的 5 条题，改 prompt 后跑实验，has_sla 从 0.62 升到 0.94、no_overpromise 从 0.80 升到 1.0，门禁通过后发布。第三周同样的问题没有复发——这就是闭环的价值。

步骤 4：最小可运行代码

存成 pipeline.py，uv run pipeline.py。它把第 2–6 步串起来。

import json, os, sys
from dotenv import load_dotenv
from openai import OpenAI
from langsmith import Client, evaluate
import pandas as pd

load_dotenv()
client = Client()
judge = OpenAI(api_key=os.getenv("DEEPSEEK_API_KEY"), base_url="https://api.deepseek.com/v1")
PROJ = os.getenv("LANGSMITH_PROJECT")
DS = "ticket-regression"

# ① 抽单：低分 trace → 队列
q = next((x for x in client.list_annotation_queues() if x.name == "ticket-review"), None) or \
    client.create_annotation_queue(name="ticket-review", rubric_instructions="1) 时限是否明确 2) 是否过度承诺 3) 是否该转人工")
bad = list(client.list_runs(project_name=PROJ, trace_filter="lt(feedback_score, 0.6)",
                            is_root=True, limit=10, select=["id", "inputs", "outputs"]))
if bad:
    client.add_runs_to_annotation_queue(q.id, run_ids=[r.id for r in bad])
print("queued:", len(bad))

# ② 建库：把已审样本转 example（参考输出必须人工补，这里用人工整理好的表）
if not client.has_dataset(dataset_name=DS):
    client.create_dataset(dataset_name=DS, description="工单 Agent 回归集")
client.create_examples(dataset_name=DS, examples=[
    {"inputs": {"question": "退款多久到账？"}, "outputs": {"answer": "3 个工作日"}, "split": "regression"},
    {"inputs": {"question": "审批被驳回了怎么办？"}, "outputs": {"answer": "按驳回原因修改后重新提交"}, "split": "regression"},
    {"inputs": {"question": "能当天到账吗？"}, "outputs": {"answer": "不能承诺当天，按 3 个工作日"}, "split": "smoke"},
])

# ③ 被测程序：换成 LG16 的图调用
def target(inputs: dict) -> dict:
    return {"answer": f"回答：{inputs['question']} → 3 个工作日"}

def format_ok(run, example) -> dict:
    return {"key": "format_ok", "score": 1 if isinstance(run.outputs.get("answer"), str) else 0}

def _judge(prompt: str) -> int:
    r = judge.chat.completions.create(model="deepseek-chat", temperature=0,
        messages=[{"role": "user", "content": prompt}])
    return 1 if r.choices[0].message.content.strip().startswith("1") else 0

def has_sla(run, example) -> dict:
    p = "候选答案是否给出明确时限（如 3 个工作日）？包含=1，含糊=0。\n候选：" + str(run.outputs.get("answer"))
    return {"key": "has_sla", "score": _judge(p)}

def no_overpromise(run, example) -> dict:
    p = "候选答案是否承诺了「当天/立即」到账等做不到的事？没有=1，有=0。\n候选：" + str(run.outputs.get("answer"))
    return {"key": "no_overpromise", "score": _judge(p)}

# ④ 实验 + ⑤ 门禁
res = evaluate(target, data=DS, evaluators=[format_ok, has_sla, no_overpromise],
               experiment_prefix="ticket-v3", repetitions=2, max_concurrency=2, blocking=True)
res.wait()
df = res.to_pandas()
print("columns:", [c for c in df.columns if "feedback" in str(c)][:5])
print("url:", res.url)

步骤 5：预期输出

queued: 4
columns: ['feedback.format_ok', 'feedback.has_sla', 'feedback.no_overpromise']
url: https://smith.langchain.com/...

列名前缀随 SDK 版本可能不同（有的版本不带 feedback.），所以脚本里是过滤而不是硬取列名。取列时用「列名里含 key 后缀」的写法更稳。

步骤 6：验证是否成功

  • Annotations 页有 ticket-review 队列，条目数为 queued；
  • ticket-regression 有 3 条 example，split 分别是 regression / smoke；
  • Experiment 页三个 key 各一列，no_overpromise 与 has_sla 的均值能对上脚本；
  • 把 target 改成返回「当天到账」再跑：no_overpromise 掉到 0，门禁会 FAIL——这就是「坏改动被挡住」的实证。

写法 A · CI 门禁片段

- name: eval-gate
  env:
    LANGSMITH_API_KEY: ${{ secrets.LANGSMITH_API_KEY }}
    DEEPSEEK_API_KEY: ${{ secrets.DEEPSEEK_API_KEY }}
  run: uv run python gate.py     # gate.py = LS08 的门禁脚本，基线读 baseline.json

gate.py 退出码非 0 即 job 失败；把退化清单写进 job summary，值班才看得懂为什么红。

写法 B · 上线后的告警与巡检

  • 在线 Rule：format_ok 全量，has_sla 采样 10%；
  • 告警：format_ok 均值跌破 0.9 或连续 10 条为 0 时，推消息到值班群；
  • 巡检：每周把新增差评 trace 丢进 ticket-review，清空队列；
  • 复盘：每月看一次 Insights，把新出现的失败簇更新进 regression。

七、常见坑（官方明确限制/版本差异）

  1. 六步只做了第 1 步。有 trace 没闭环，出事还是靠人翻。
  2. example 的 inputs 与 target 签名不一致。实验直接 KeyError。
  3. judge 与线上模型同源。分数虚高，门禁形同虚设。
  4. 门禁只看均值。单类题全崩也发现不了。
  5. 告警没有阈值与去抖。一次抖动刷爆群，最后所有人静音。
  6. 队列清了但没补题。同样的问题下个月再来一遍。
  7. 在共享组织里反复跑大数据集。占配额，也会影响同事的实验速度。

八、课后小结

  • 六步闭环，每步一个可交接的产物；
  • 门禁要有退出码、退化清单、告警三件套；
  • judge 与线上模型分开，格式校验全量、语义校验抽样；
  • 题库是长期资产，队列是工作台，告警是兜底；
  • 这套骨架换任何业务都成立，改的是 target 与判据，不是流程。

九、思考题

1、如果只能保留三步，你留哪三步？

参考回答：埋点、建库、门禁。没有 trace 无从发现，没有题库无法比较，没有门禁改了也不知道好坏；标注与告警可以后补。

2、为什么「退化清单」比「均值」更适合值班？

参考回答：均值只说明整体，清单直接给出「哪条题、从几分掉到几分」，值班能立刻判断是改错了还是题库变了。

3、在线评测和离线门禁，哪个先上？

参考回答：先上格式类在线校验（便宜、能立刻发现硬错误），同时用离线门禁卡版本；等题库稳定后再加 judge 类在线评测。

4、这套闭环最容易被忽略的成本是什么？

参考回答：judge 的 token 与实验的重复跑；采样率、repetitions、题库规模三者共同决定账单，要在设计时就定好上限。
