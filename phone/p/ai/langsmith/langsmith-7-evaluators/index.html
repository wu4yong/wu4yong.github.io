07 评测器

code 判「格式对不对」，judge 判「意思对不对」，pairwise 判「哪个更好」｜依据官方 Evaluation concepts 页自绘

版本不一致提示

  • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + Python 3.13；
  • 本篇必须有真实 key，并且要有一个可调用的模型（LLM-as-judge 用），示例默认接 DeepSeek，其他 provider 的换法见文末速查表；
  • 评测函数签名固定：def ev(run, example) -> dict，返回至少一个 key 与 score（或 value）；返回多个 {"key": ..., "score": ...} 列表即为 composite；
  • 官方把评测器分 human / heuristic（code）/ LLM-as-judge / pairwise 四类；pairwise 在 SDK 侧没有独立的 running 接口，实际用法是在同一 dataset 上比两次实验（LS08 展开）；
  • judge 的 prompt 里不要放参考答案，否则判官会照着抄，分数虚高。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 判断一个需求该用 code、judge 还是人工，并说清各自的误判模式；
  2. 写一个 code 评测器（结构比对）与一个 LLM-as-judge（要点覆盖），挂在同一份 dataset 上跑出两列分数；
  3. 会换 judge 模型：OpenAI / DeepSeek / 智谱 / 通义 / Claude 各自要改哪一行。

二、前置知识

  • 读完 06 数据集，有一个能跑的 dataset；
  • 知道 run.outputs 与 example.reference_outputs 的区别。

2. 三种常见组合

  • 格式 + 事实：code 判「是不是合法 JSON、字段齐不齐」，judge 判「答案对不对」；
  • 分层阈值：code 先卡硬门槛（schema 错直接 0 分），judge 只在通过的样本上跑，省 token；
  • 人工兜底：judge 分数落在中间区间的样本进标注队列（LS09）。

3. judge 的评分口径

官方建议 judge 用离散档位（如 0 / 0.5 / 1）而不是连续 0–100，原因是模型对 0–100 的刻度几乎没有稳定分辨力，同一份输出两次打分能差 20 分。档位少、定义清楚，跨实验才可比。

四、原理拆解：一次实验里评测器怎么被调用

  1. 平台按 example 逐条调你的 target，拿到输出并记为一次 run；
  2. 对每个 run，按你给的评测器列表逐个调用 ev(run, example)；
  3. 每个返回 dict 里的 key 就是实验表里的一列，score 是该格的分值；
  4. 一列一个 key，相同 key 的多次返回（如 composite 里拆成多条）会按 key 归并；
  5. 汇总时按 example 求平均，得到这一列的 experiment 分数。

所以「两列分数不同」通常不是模型不同，而是两列看的字段不同——把 key 命名清楚，比调参重要。

五、场景说明

退款 FAQ 的答案有三条硬要求：必须是 JSON、必须给到账时间、不能承诺「立即到账」。

  • 是否合法 JSON、有没有 answer 字段 → code 评测器，零成本、必跑；
  • 到账时间是否说对（3 个工作日）→ judge，因为用户问法千变万化，字符串匹配必然漏；
  • 语气是否合规 → 人工抽检，进标注队列。

步骤 4：最小可运行代码

存成 eval.py，uv run eval.py。

import json, os
from dotenv import load_dotenv
from openai import OpenAI
from langsmith import Client, evaluate

load_dotenv()
client = Client()
judge = OpenAI(api_key=os.getenv("DEEPSEEK_API_KEY"), base_url="https://api.deepseek.com/v1")
DS = "refund-faq"

def target(inputs: dict) -> dict:
    # 被测程序：真实项目里换成你的 agent
    return {"answer": json.dumps({"answer": "3 个工作日到账", "channel": "原路退回"}, ensure_ascii=False)}

def fmt(run, example) -> dict:
    raw = run.outputs.get("answer", "")
    try:
        obj = json.loads(raw)
        ok = isinstance(obj.get("answer"), str)
    except Exception:
        ok = False
    return {"key": "json_ok", "score": 1 if ok else 0}

JUDGE_PROMPT = """判断候选答案是否包含「3 个工作日」这一到账时间口径。
只回答一个数字：包含=1，不包含或含糊=0。
候选答案：{answer}"""

def facts(run, example) -> dict:
    ans = run.outputs.get("answer", "")
    r = judge.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "user", "content": JUDGE_PROMPT.format(answer=ans)}],
        temperature=0,
    )
    txt = r.choices[0].message.content.strip()
    return {"key": "has_sla", "score": 1 if txt.startswith("1") else 0}

if __name__ == "__main__":
    res = evaluate(
        target,
        data=DS,
        evaluators=[fmt, facts],
        experiment_prefix="ls07-baseline",
        max_concurrency=2,
    )
    print(res)

步骤 6：验证是否成功

  • Experiment 页面看到两个 key 各成一列，每列有均值；
  • 打开任一行：json_ok 显示 1，has_sla 显示 0 或 1，说明两个评测器都作用在同一条 run 上；
  • 把 JUDGE_PROMPT 改成「包含=1，否则=0」并去掉「含糊」字样，再跑一次：has_sla 的均值会变——同一个答案，判据措辞不同结果就不同，这是 judge 的固有脆弱性；
  • 在 target 里故意返回 "3天"：json_ok 仍是 1（结构没坏），has_sla 变 0——两列各管一件事，这正是组合的意义。

前四家都能用 openai SDK，只改 base_url + model；Claude 要换 SDK，返回结构也不同（content[0].text）。判断分数解析逻辑时，别假设返回一定是纯文本。

写法 B · 判官也要被评测

judge 的稳定性靠「黄金集」验：准备 20 条人工已判过分的样本，用同一个 judge 跑一遍，算它与人判的一致率。一致率低于 80%，先改 rubric，别急着信它给的分数。官方在 judge 文档里把这一步叫「校准」，不做校准的 judge 只能当筛子，不能当尺子。

写法 C · pairwise 用在哪

官方没有给 pairwise 单独的 running 接口；实操是同一个 dataset 跑两次实验，再用 Experiment 对比页的 pairwise 视图看「A 比 B 好多少」。注意把 A/B 顺序换一遍再跑，抵消位置偏见。

七、常见坑（官方明确限制/版本差异）

  1. judge prompt 里放参考答案。判官照着抄，分数统一偏高，且与真实质量脱钩。
  2. code 评测器用 in 判结构。'"answer"' in raw 对坏 JSON 也会为真；解析成对象再判。
  3. judge 用 0–100。刻度太细，模型分辨力不足，跨实验漂移大。用 0/0.5/1。
  4. pairwise 不换序。A 放前面总赢，结论无效。
  5. judge 与线上模型同源。同源会一起错，judge 分数虚高；换一家做判官。
  6. 评测器 key 命名重复。两列合并成一列，看着像「模型退步」。
  7. run.outputs 拿不到字段就断言 0 分。先确认 target 的返回结构，否则测的是自己的 bug。

八、课后小结

  • 四类评测器分工明确：code 判结构、judge 判语义、pairwise 判优劣、human 兜底；
  • 一列一个 key，命名比调参重要；
  • judge 用离散档位，且必须做校准（和人判的一致率）；
  • 前四家 provider 走 OpenAI 兼容层，只改 base_url + model；Claude 换 SDK；
  • pairwise 靠两次实验 + 对比视图，记得换序。

九、思考题

1、为什么 code 评测器不能替代 judge？

参考回答：它只能判「可机械验证的属性」（格式、字段、包含关系），判不了「意思对不对」；用户问法一变，字符串匹配就失效。

2、judge 分数和人工分数差很多，先改什么？

参考回答：先改 rubric（把判据写成可判定的一句话 + 档位定义），再查提示里有没有参考答案泄漏，最后才考虑换模型。

3、为什么「格式 + 事实」两列要分开而不是合成一列？

参考回答：合成后一个 0 分说不清是格式坏还是事实错，排障时要重新拆；分开列能直接看出「这次改动坏在哪一层」。

4、pairwise 为什么比单边打分更可靠？

参考回答：相对比较把「绝对标准」这个难点绕开了，模型只需判断「哪个更符合要求」；代价是只能比、不能给绝对分，也不适合监控长期趋势。
