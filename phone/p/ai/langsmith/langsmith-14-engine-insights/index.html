14 发现与修复

人肉翻 trace 的尽头是聚类；但聚类给出的结论仍要人复核｜依据官方 Engine 页自绘

版本不一致提示

  • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + Python 3.13；
  • Engine 与 Insights 是平台侧能力，SDK 没有对应写接口：本篇的脚本只做「按错误签名粗聚类」，作为对照手段；
  • Engine 的产物是「问题簇 + 根因假设 + 修复建议 + 建议补充的回归用例」，不会自动改你的 prompt；
  • Insights 的结论是分布性的（哪类请求多、哪类失败高频），不带分母时不要当成结论；
  • 本篇示例需要 key；没有线上流量时，聚类脚本会返回空。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 Engine 的四步（检测 / 归因 / 建议 / 回归）各自产出什么、哪一步必须人复核；
  2. 用 Insights 读出「失败集中在哪类请求」，并把结论落成一条可复跑的题；
  3. 用脚本按错误签名做粗聚类，作为 Engine 之外的低成本对照。

二、前置知识

  • 读完 09 在线评测与标注，线上已经有 feedback；
  • 读完 13 平台形态与治理，知道成本与权限边界。

三、理论讲解（官方定义）

1. Engine 的四步

步骤

关键：它给的是假设。把 Engine 的建议直接上线，等于把「聚类算法的猜测」当成事实。

2. Insights 看什么

Insights 面向「分布」：哪些意图占比高、哪些失败模式高频、哪些租户集中出问题。它回答「先修哪个」，不回答「怎么修」。

3. 两者与评测闭环的关系

Engine / Insights 属于「发现」层，产出的样本仍要走 LS09 的路径：进队列 → 人审 → 落 dataset → 离线验证。跳过人工那一步，就是把噪声写进题库。

四、原理拆解：聚类为什么不可靠，以及怎么用才可靠

自动聚类的核心是「把相似的失败放在一起」。相似性通常基于 embedding 或错误签名，于是有两个必然的失真：

  1. 不同原因、相似表象会被并簇（都表现为「答非所问」，但一个是检索没召回、一个是 prompt 丢约束）；
  2. 同原因、不同表象会被拆散（同一处空指针在十个租户下的十种报错文案）。

所以正确用法是：用簇来缩小排查范围，用 run 树来确认根因。簇给方向，树给证据。

五、场景说明

退款 Agent 一周内有 40 条差评。人肉看 40 条要两小时。做法：先让 Engine 聚成 3 簇（「金额算错」「承诺立即到账」「答非所问」），再看每簇里最典型的一条 trace 的 Turns/Details，确认根因是工具参数错、还是 prompt 里少了约束。修完把每簇挑 2 条落成 example，打 regression。

六、示例代码

步骤 1：环境准备

uv init ls14-triage
cd ls14-triage
uv add langsmith python-dotenv

步骤 2：凭证配置

.env：LANGSMITH_API_KEY、LANGSMITH_PROJECT=ticket-agent-prod。

步骤 3：导入

from collections import Counter
from langsmith import Client

步骤 4：最小可运行代码

存成 triage.py，uv run triage.py。用错误签名做粗聚类，输出「哪类错误最多、各取一条样本」。

import os, re
from collections import defaultdict
from dotenv import load_dotenv
from langsmith import Client

load_dotenv()
client = Client()
PROJ = os.getenv("LANGSMITH_PROJECT")

# 1) 捞近一周的低分根 run
runs = list(client.list_runs(
    project_name=PROJ,
    trace_filter="lt(feedback_score, 0.6)",
    is_root=True,
    limit=200,
    select=["id", "error", "outputs", "inputs"],
))
print("bad runs:", len(runs))

def signature(r):
    # 粗签名：错误类型 + 输出里的关键短语
    err = (r.error or "").split(":")[0].strip()
    out = str((r.outputs or {}).get("answer", ""))[:40]
    tag = "no_error"
    for kw in ("立即到账", "金额", "转人工", "无法"):
        if kw in out:
            tag = kw
            break
    return f"{err or 'ok'}|{tag}"

buckets = defaultdict(list)
for r in runs:
    buckets[signature(r)].append(r)

for sig, items in sorted(buckets.items(), key=lambda kv: -len(kv[1])):
    print(f"{len(items):>3}  {sig}")
    print("     sample:", items[0].id)

步骤 6：验证是否成功

  • 每个桶的条数与 UI 里按 filter 搜出来的数量一致；
  • 点开任一 sample 的 trace：Turns 里能看出「慢/错」的具体 run，Details 里能确认根因；
  • 把最有价值的一簇里挑 2 条，走 LS09 的 create_example_from_run 落进 regression；
  • 在平台 Insights 里对照：Engine 的簇划分与你的粗签名是否一致，不一致的簇要人工看（往往就是「同表象不同因」）。

写法 A · 用簇缩小范围，用树确认根因

r = client.read_run("<sample-run-id>")
dt = (r.end_time - r.start_time).total_seconds() if r.end_time else None
print(r.run_type, r.name, r.status, dt)          # 先看这一步对不对
print((r.error or "")[:200])                     # 再看错误栈首行

顺序永远是：簇 → trace → 关键 run 的 Details → 结论。跳过任何一层都会误判。

写法 B · Insights 结论落成一条题

Insights 说「『多久到账』类问法失败最多」，你要做的是写一条 example：输入是那类问法，参考输出写「3 个工作日」，split="regression"。写题，不写结论——结论会过期，题不会。

七、常见坑（官方明确限制/版本差异）

  1. 把 Engine 的建议直接上线。建议是假设，未经 run 树验证就会「修错地方」。
  2. 信簇的大小。簇大不等于影响大，要结合流量与租户权重。
  3. Insights 没有分母就下结论。「这类多」要问「占多少、比上周多多少」。
  4. 聚类后不落题。下次同样的问题再发生，还得再翻一遍。
  5. 用输出文本当唯一签名。模型换个措辞，签名就散；错误类型 + 关键短语组合更稳。
  6. 拿 Engine 生成的用例直接进 CI。未经人确认的用例会把错误期望固化。

八、课后小结

  • Engine 四步，只有第一步是纯自动，其余都要人复核；
  • 簇给方向、树给证据，顺序不能反；
  • Insights 回答「先修哪个」，不回答「怎么修」；
  • 发现层的产出必须落成 dataset 的 example 才算闭环；
  • 粗签名聚类是可复现的低成本对照手段。

九、思考题

1、为什么自动聚类的结论必须回到 run 树验证？

参考回答：相似性基于表象（文本、embedding、错误码），同表象可能不同因；run 树能看到每一步的实际输入输出，才区分得开。

2、Engine 生成的回归用例，为什么不能直接用？

参考回答：用例的「期望输出」由算法推断，可能把当前错误行为当成正确标准；必须人工确认参考输出。

3、Insights 的哪个指标最该先看？

参考回答：失败率 × 流量占比的组合（影响面），而不是单纯的失败数量；一个长尾簇失败 50 次可能就是噪声。

4、你的粗签名方案有什么已知盲区？

参考回答：措辞变化会导致签名漂移；错误栈被平台截断时只剩首行；多语言输出时关键词失效。
