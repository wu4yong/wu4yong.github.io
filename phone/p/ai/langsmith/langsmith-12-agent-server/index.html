12 Agent Server

部署不是「把代码放上去」，而是先决定「控制面在哪、数据面在哪」｜依据官方 Agent Server 页自绘

版本不一致提示

  • 本篇基线是 LangSmith 平台（2026-11 文档）+ langgraph 1.2.24 + langgraph_sdk + Python 3.13；
  • 2026 年官方把 Deployment 更名为 LangSmith Agent Server，老文章里的 deployment 指的是同一套东西；
  • Cloud 托管需要 Plus 及以上套餐，自建带控制面 / BYOK 需要 Enterprise；计费含算力与数据库两项，不是「按 agent 数」；
  • Agent Server 的能力面是 assistants / threads / runs 三件套；langgraph_sdk 里对应 client.assistants / client.threads / client.runs；
  • client.runs.stream() 在 langgraph_sdk 里，不在 langsmith SDK 的 client.runs（后者是异步资源，没有 stream 方法）；
  • 本篇示例需要一个跑起来的 server（本地 langgraph dev 或已部署实例），纯本地无服务时只能读代码。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 按「数据能不能出 VPC、谁运维」选出四种拓扑里的一个，并说清控制面与数据面各在哪；
  2. 用 langgraph.json 起一个本地 server，用 langgraph_sdk 建 thread、跑 run、看 stream；
  3. 用 RemoteGraph 把远端 agent 当本地图调用，并知道「不重新部署换 prompt」是怎么实现的。

二、前置知识

  • 读完 11 Playground 与 Context，prompt 已经在平台上版本化；
  • 有一条能跑的 LangGraph 图（LG 系列的工单 Agent 即可）。

控制面指「谁负责调度、鉴权、版本、UI」；数据面指「run 数据、状态、模型调用落在哪」。企业选型的第一个问题永远是：「trace 和状态能不能出我的 VPC」，答案决定是 Cloud 还是 Hybrid/自建。

2. 三件套

  • assistant：一个可调用的「配置实例」——同一个 graph，用不同 assistant 挂不同 prompt / 模型；
  • thread：会话容器，等价于 LG 系列的 thread_id；
  • run：一次执行，挂在 thread 上，由 assistant 产生。

这套命名把「图（graph）」与「配置（assistant）」分开了：改 prompt 只需更新 assistant，不用重新部署 graph——这就是官方说的「不重新部署换 prompt/context」。

3. RemoteGraph

官方提供 RemoteGraph，把远端部署的图包装成本地可 invoke 的对象。适合「本地脚本 / 另一个服务要调远端 agent」的场景，不必自己写 HTTP 客户端。

四、原理拆解：一次远端调用经过什么

  1. 客户端按 assistant_id 找到对应配置（graph + prompt + 模型参数）；
  2. 带 thread_id 发起 run，服务端从 checkpointer 读出该 thread 的状态；
  3. 执行图，逐步产出的中间状态按 stream_mode 推回；
  4. run 结束时写回状态，并把这次 trace 落到对应环境。

关键点：thread 的状态在服务端，客户端不需要（也不应该）自己保存 messages 历史；这也是「无状态客户端 + 有状态服务端」的分界线。

五、场景说明

工单 Agent 先在本地 langgraph dev 调通，再部署到 Cloud。上线后运营要在不改代码的前提下把「审批阈值」从 500 调到 800——做法是更新 assistant 的 config，而不是重新部署。若客户要求数据不出 VPC，就换 Hybrid：控制面还在托管侧，run 数据与模型调用留在客户环境。

六、示例代码

步骤 1：环境准备

uv init ls12-server
cd ls12-server
uv add langgraph langgraph-sdk langsmith python-dotenv

步骤 2：配置 langgraph.json

{
  "dependencies": ["."],
  "graphs": { "ticket_agent": "./ticket_agent.py:graph" },
  "env": ".env"
}

graphs 的 key 就是部署后 assistant 对应的 graph 名。

步骤 3：本地起服务

langgraph dev          # 默认 http://127.0.0.1:2024

langgraph dev 是开发用：内存态、无鉴权、单进程。不要拿它当生产。

步骤 4：最小可运行代码

存成 client_demo.py，uv run client_demo.py（server 已起）。

import os
from langgraph_sdk import get_client

client = get_client(url=os.getenv("LANGGRAPH_URL", "http://127.0.0.1:2024"))

# 1) assistant：配置实例（graph_id 对应 langgraph.json 里的 key）
assistants = client.assistants.search()
print("assistants:", [a["assistant_id"] for a in assistants])
aid = assistants[0]["assistant_id"] if assistants else "ticket_agent"

# 2) thread：会话容器
thread = client.threads.create()
tid = thread["thread_id"]

# 3) run：在 thread 上跑一次
for chunk in client.runs.stream(
    tid, aid,
    input={"messages": [{"role": "user", "content": "退款怎么走？"}]},
    stream_mode="updates",
):
    print(chunk.event, chunk.data)

步骤 5：预期输出

assistants: ['ticket_agent']
metadata {...}
updates {'retrieve': {...}}
updates {'model': {...}}

（事件名取决于你的图；重点是 thread_id 复用后状态延续。）

步骤 6：验证是否成功

  • 同一个 tid 再发一次 run，图能看到上一轮的 messages（证明状态在服务端）；
  • 换一个 tid 再发，图从空状态开始；
  • 在 LangSmith 的对应环境里能找到这两次 run 的 trace；
  • 用 client.threads.get_state(tid) 读出当前状态，与图里打印的一致。

写法 A · 用 RemoteGraph 当本地图调

from langgraph.pregel.remote import RemoteGraph

remote = RemoteGraph(
    "ticket_agent",
    url="https://your-deployment.example.com",
    api_key="lsv2_pt_xxx",
)
out = remote.invoke(
    {"messages": [{"role": "user", "content": "退款怎么走？"}]},
    config={"configurable": {"thread_id": "T-9d2"}},
)
print(out["messages"][-1].content)

RemoteGraph 的第一个参数是 assistant_id，不是 graph 名；两者在 Cloud 上通常同名，但别假设。

写法 B · 更新 assistant 换配置（不重新部署）

client.assistants.update(aid, config={"configurable": {"approval_threshold": 800}})

改完立刻对新 run 生效；已在跑的 run 不受影响。这就是「秒级换配置」的实现路径。

七、常见坑（官方明确限制/版本差异）

  1. 把 langgraph dev 当生产。内存态、无鉴权、重启即丢状态。
  2. 以为部署后持久化自动配好。Postgres checkpointer 仍要自己接，Cloud 侧也要确认环境配置。
  3. assistant 名与 langgraph.json 的 key 不一致。调用时报「找不到 assistant」。
  4. 客户端自己维护 messages 历史。服务端已有 thread 状态，重复拼接会造成重复上下文。
  5. langsmith SDK 找 client.runs.stream。那是 langgraph_sdk 的方法，两个 SDK 别混。
  6. 把 Cloud 当「免费能部署」。Plus 起，且按算力与数据库计费。
  7. 把 key 写进 langgraph.json。等于把凭证提交进 git。

八、课后小结

  • 四种拓扑的差别在「控制面 / 数据面各在哪」，选型先问数据能不能出 VPC；
  • 三件套：assistant（配置实例）、thread（会话）、run（一次执行）；
  • 状态在服务端，客户端无状态；
  • 换 prompt / 配置 = 更新 assistant，不用重新部署；
  • RemoteGraph 的入参是 assistant_id，不是 graph 名。

九、思考题

1、为什么要把 graph 与 assistant 分成两个概念？

参考回答：graph 是代码逻辑（要发版），assistant 是配置实例（可热更）；分开后「同一份代码跑多套配置」才成立，也不用为了改参数重新部署。

2、Hybrid 拓扑解决了什么问题？

参考回答：把控制面（调度、UI、鉴权）托管出去降低运维成本，同时把数据面留在客户环境满足合规；代价是网络与升级协调更复杂。

3、thread 状态放服务端，客户端要注意什么？

参考回答：不要重复发送历史消息、不要假设本地缓存是真源；需要读状态就用 threads.get_state，跨实例时以服务端为准。

4、为什么不建议用 langgraph dev 做灰度？

参考回答：它无鉴权、状态在内存、单进程，既不能承受并发也无法保证重启不丢；灰度至少要有持久化与鉴权。
