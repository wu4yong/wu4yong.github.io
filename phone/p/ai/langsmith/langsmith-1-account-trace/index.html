01 账号与环境

一条函数调用 = 一个 run；函数里再调函数，就是子 run｜依据官方 Observability 页自绘

版本不一致提示

  • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + Python 3.13；
  • 官方在 2026 年把「项目（project）」收进 workspace → agent → environment 模型，四个环境固定为 Production / Staging / Development / Local；老接口里的 project_name / session_id 仍指向环境背后的 trace 存储，不要当成新对象；
  • 环境变量已统一为 LANGSMITH_* 前缀；老文章里的 LANGCHAIN_TRACING_V2 / LANGCHAIN_PROJECT 仍兼容，本系列一律用新前缀；
  • 免费层足够跑本讲到 M3 的全部示例；部署类内容有套餐门槛，见 LS12。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 建好 workspace 与 agent，说清四个环境各自装什么数据；
  2. 拿到 API key，配好四个环境变量，并知道每一个的作用；
  3. 用 @traceable 把一次函数调用变成 trace，在 UI 里找到它、认出它的父子结构。

二、前置知识

  • 会 uv（或 pip + venv），能跑一个 Python 脚本；
  • 有一个能登录 smith.langchain.com 的账号（Google / GitHub / 邮箱均可）；
  • 不需要 LangChain 或 LangGraph 基础。

三、理论讲解（官方定义）

1. 三层容器：workspace / agent / environment

官方的数据组织是三层：

  • workspace：团队或项目的边界，成员与权限在这一层；
  • agent：一个稳定的业务标识（例如 ticket-agent），traces 按它归属；
  • environment：固定四种——Production、Staging、Development、Local，一个 agent 的 traces 按环境分开存。

这样拆的好处很直接：查线上行为时不用手动排除测试流量——Production 环境里本来就没有测试数据。

3. 为什么要 @traceable

官方把埋点分成两类：integrations（框架与 provider 的自动埋点）和 manual instrumentation（手动插桩）。@traceable 是最轻的手动方式——给函数套一个装饰器，这个函数就成为一个 run；函数内部再调被装饰的函数，就自动成为子 run。

四、原理拆解：一行装饰器背后发生了什么

  1. 调用时 SDK 先创建 run（拿到 run id、trace id、parent run id）；
  2. 执行你的函数，把入参记为 inputs、返回值记为 outputs；
  3. 结束时补上结束时间、状态（成功/异常）、错误栈；
  4. 后台线程批量把 run 上报到 LANGSMITH_ENDPOINT，落到 agent 的对应环境；
  5. UI 按 trace id 把同一棵树的 run 拼回去。

关键点：上报是异步的，函数不会因为埋点变慢；也正因如此，脚本跑完立刻关进程可能丢最后几条——加 client.flush() 或让进程正常退出即可。

五、场景说明

最典型的第一个场景：一个已经上线的客服脚本，线上偶发「答非所问」。你不想改业务代码，只想先看清它到底调了什么、每一步花了多久——@traceable 就是成本最低的入口。

六、示例代码

步骤 1：环境准备

uv init ls01-hello
cd ls01-hello
uv add langsmith

步骤 2：凭证配置

.env：

LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_pt_xxxxxxxx
LANGSMITH_PROJECT=ticket-agent-dev
LANGSMITH_ENDPOINT=https://api.smith.langchain.com

uv add python-dotenv 后 load_dotenv()；生产环境直接用平台的环境变量，不落盘 .env。

步骤 3：导入

from langsmith import traceable, tracing_context

步骤 4：最小可运行代码

存成 hello.py，uv run hello.py。

import os
from dotenv import load_dotenv
from langsmith import traceable, tracing_context

load_dotenv()

@traceable
def retrieve(q: str) -> str:
    # 假装这是检索：真实项目里换成向量库调用
    return f"doc::{q}"

@traceable(run_type="llm")
def model(q: str, ctx: str) -> str:
    return f"{ctx} → 回答：{q} 的退款 3 天到账"

@traceable
def answer(q: str) -> str:
    ctx = retrieve(q)
    return model(q, ctx)

if __name__ == "__main__":
    print(answer("退款怎么走？"))

    # 想临时关掉上报（比如压测、脱敏调试）
    with tracing_context(enabled=False):
        print(answer("这条不会进 UI"))

步骤 5：预期输出

doc::退款怎么走？ → 回答：退款怎么走？ 的退款 3 天到账
doc::这条不会进 UI → 回答：这条不会进 UI 的退款 3 天到账

终端只看到两行文本，但第一条已经在 UI 里长成一棵两层的树。

步骤 6：验证是否成功

  • 打开 smith.langchain.com → 选 workspace → 找到 ticket-agent-dev 环境 → Runs 列表里出现刚才那次 answer；
  • 点开 answer：里面应有 retrieve 与 model 两个子 run；
  • 把 LANGSMITH_TRACING 改成 false 再跑一次：Runs 列表不再增加；
  • 把 LANGSMITH_PROJECT 改成另一个名字再跑：run 落到另一处，说明这个变量确实是「存哪儿」而不是「叫什么」。

写法 A · 无 key 的离线模式

没有账号也想跟做，只要不开上报：

import os
os.environ["LANGSMITH_TRACING"] = "false"   # 先关，SDK 不会尝试联网

from langsmith import traceable

@traceable
def answer(q): ...

函数照常返回、装饰器照常生效，只是不产生 trace。等拿到 key，删掉这一行即可——代码结构不用改。

七、常见坑（官方明确限制/版本差异）

  1. key 写进代码。一旦进 git 就等于泄漏；用环境变量或 .env（且 .env 在 .gitignore 里）。
  2. 只设 LANGSMITH_TRACING 不设 LANGSMITH_PROJECT。数据落到默认环境，与测试流量混在一起，后面筛选要手工排除。
  3. 以为 Local 环境是「本地存储」。它同样是一次环境选择，只是约定用来放本机调试数据；不想上报请用 tracing_context(enabled=False)。
  4. 脚本里 os._exit()。上报是后台线程，强退会丢尾部 run。
  5. 把 LANGSMITH_API_KEY 和模型 key 搞混（sk- 与 lsv2_ 前缀不同，用途也完全不同）。

八、课后小结

  • 数据是三层容器：workspace → agent → environment，四环境固定；
  • 四个变量各管一件事：开不开、能不能上报、落到哪、上报到哪；
  • @traceable 一行就能把一个函数变成 run，父子关系由调用关系自动决定；
  • 没 key 时用 LANGSMITH_TRACING=false 或 tracing_context(enabled=False) 降级，不影响代码结构；
  • 上报是异步的，脚本要正常退出。

九、思考题

1、为什么官方要把「项目」拆成 agent + environment，而不是一个大桶？

参考回答：因为排障时要的是「线上这条 trace，而不是混着测试的同一个桶」。按环境分开存，查询天然带过滤条件，也方便对 Production 单独设在线评测与告警。

2、@traceable 为什么不影响函数性能？

参考回答：采集在本地做，上报走后台队列，函数本身只多一次 run 对象的创建与结束标记；真正可能影响的是极端高频调用下的队列压力，这时该降采样而不是删埋点。

3、同一次调用里两次 @traceable 套同一个函数会怎样？

参考回答：会得到两层同名 run，白增一层噪音且容易混淆统计口径；一个函数只套一个。

4、线上排障时，你会先看哪个环境、哪个对象？

参考回答：Production 环境的 trace：先看 Turns 找慢，再看 Details 找错，最后回 Messages 看对话是否被错误带偏（LS04 展开）。
