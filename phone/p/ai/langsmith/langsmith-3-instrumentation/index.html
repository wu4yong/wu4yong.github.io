03 三种埋点

覆盖范围越大越省事，越小越可控；同一应用可以混用｜依据官方 Observability 页自绘

版本不一致提示

  • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + Python 3.13；
  • 官方把埋点分两类：integrations（自动）与 manual instrumentation（手动，三种：@traceable、trace 上下文、RunTree）；
  • RunTree 是最低级 API，不会替你推断父子关系，需要自己 create_child；
  • 自动埋点只对「已支持的框架与 provider」生效，自研 HTTP 调用不在其中；
  • 本篇前两种方式可在 LANGSMITH_TRACING=false 下跑通（结构照建、不上报）；RunTree.post() 不受该开关约束，无 key 时会打出 401 警告，但不影响执行；

一、学习目标

学完这一讲，你要能做到三件事：

  1. 判断一个项目该用自动集成还是手动埋点，边界在哪；
  2. 用 @traceable、trace 上下文、RunTree 三种手动方式各写一遍；
  3. 在 UI 里认出「这棵树是我埋出来的」，并解释每一层的父子关系。

二、前置知识

  • 读完 02 概念体系，知道 run 树是怎么拼的；
  • 跑过 01 的 @traceable 示例。

三、理论讲解（官方定义）

1. 自动埋点（integrations）

官方对 integrations 的定义是「自动埋点，等价于通用可观测性里的 auto-instrumentation」：用受支持的框架或 provider（LangChain、LangGraph、OpenAI、Anthropic、CrewAI、Vercel AI SDK、Pydantic AI 等）时，无需改代码就能捕获输入、输出与元数据。

边界：它只覆盖它认识的东西。你自己 requests.post 调一个内部 API，自动埋点看不到。

3. 三个必须写对的字段

  • run_type：llm / tool / chain / retriever 等。UI 的图标、统计口径、评测器的取数都依赖它；
  • name：默认是函数名。同名多层会让统计口径混在一起；
  • 父子关系：前两种由调用栈自动推断；RunTree 必须显式 create_child。

四、原理拆解：调用栈就是树

@traceable 与 trace 的共同点是用上下文变量记住「当前父 run」：

  1. 进入被装饰的函数，创建一个 run，并把自己设为当前 run；
  2. 函数内部再调用被装饰的函数时，新 run 的 parent 就是当前 run；
  3. 退出时结束 run、写回 outputs，并把上下文还原成上一层。

所以「嵌套」不需要你手写，只要真的在函数内部调用。反过来，如果你把子任务丢到线程池 / 另一个进程，上下文不会自动传过去——这时要么显式传 parent，要么退回 RunTree。

RunTree 则是完全手动的：post() 声明开始，create_child() 建子节点，end(outputs=...) 收尾。它不做推断，也不会因为异常自动收尾。

五、场景说明

一个「检索 → 模型 → 工具」的三步脚本：

  • 外层 answer 想看到整棵树 → @traceable；
  • 中间有个「重排」只是一段逻辑，不必单独成函数 → trace 上下文；
  • 有个自研的流式客户端，SDK 不认识 → RunTree 手工挂。

三种混用，才是一棵完整、层级正确的树。

步骤 3：导入

步骤 4：最小可运行代码

存成 instrument.py，uv run instrument.py。

import os
from dotenv import load_dotenv
from langsmith import traceable, trace
from langsmith.run_trees import RunTree

load_dotenv()

@traceable(run_type="retriever")
def retrieve(q: str) -> list[str]:
    return [f"doc-1::{q}", f"doc-2::{q}"]

def rerank(docs: list[str]) -> list[str]:
    # 不是独立函数层级，只想在树里留一个「重排」节点
    with trace("rerank", run_type="chain", inputs={"n": len(docs)}):
        return sorted(docs, key=len)

@traceable(run_type="llm")
def model(q: str, docs: list[str]) -> str:
    return f"回答：{q}（依据 {len(docs)} 篇）"

@traceable
def answer(q: str) -> str:
    docs = rerank(retrieve(q))
    return model(q, docs)

@traceable(run_type="tool")
def call_vendor_api(payload: dict) -> dict:
    # 假装这是自研客户端；真实项目里在这里手工建 RunTree
    return {"ok": True, "echo": payload}

def manual_tree(q: str) -> dict:
    rt = RunTree(name="vendor_job", run_type="chain", inputs={"q": q})
    rt.post()
    child = rt.create_child(name="vendor_http", run_type="tool", inputs={"url": "/v1/ask"})
    child.post()
    out = call_vendor_api({"q": q})
    child.end(outputs=out)
    rt.end(outputs={"done": True})
    return out

if __name__ == "__main__":
    print(answer("退款怎么走？"))
    print(manual_tree("退款怎么走？"))

回答：退款怎么走？（依据 2 篇）
{'ok': True, 'echo': {'q': '退款怎么走？'}}

步骤 6：验证是否成功

在 ticket-agent-dev 环境里应该看到两棵树：

  • answer 下挂 retrieve（retriever）→ rerank（chain）→ model（llm），三层的 run_type 各不相同；
  • vendor_job 下挂 vendor_http，这是 RunTree 手工建的，父子关系与调用栈无关；
  • 点开 rerank：它的 inputs 里有 n: 2，说明 trace 上下文的入参确实传上去了。

写法 A · 把 RunTree 用在异步任务里

import asyncio
from langsmith.run_trees import RunTree

async def job(rt: RunTree, q: str):
    ch = rt.create_child(name="async_step", run_type="tool", inputs={"q": q})
    ch.post()
    await asyncio.sleep(0.1)
    ch.end(outputs={"ok": True})

rt = RunTree(name="batch", run_type="chain", inputs={"n": 1})
rt.post()
asyncio.run(job(rt, "退款"))
rt.end(outputs={"done": 1})

异步 / 线程池里上下文不会自动跟过去，所以把 rt 当参数传进去，是最稳的做法。

七、常见坑（官方明确限制/版本差异）

  1. 手写埋点全用默认 run_type。全是 chain，UI 分类与统计全糊。
  2. 装饰器套在生成器 / async 生成器上。流式产出期间 run 已结束，中途的 chunk 不会进树；流式场景改用 RunTree 或框架自带埋点。
  3. 线程池里调被装饰函数。上下文不传递，子 run 变成孤立根节点。
  4. RunTree 异常路径不 end。run 一直挂起，UI 里显示未完成；用 try/finally 收尾。
  5. 嵌套层级过深。每一步都建节点，run 数暴涨，既贵又难读——树是给人看的，不是审计日志。
  6. 同一函数套两个装饰器。两层同名 run，统计翻倍。
  7. 以为 RunTree 跟着 LANGSMITH_TRACING 走。它直连上报接口；不想发就根本别 post()。

八、课后小结

  • 自动集成覆盖它认识的框架与 provider，自研调用不在其中；
  • 手动三档按覆盖范围分：函数 → 代码块 → 任意结构；
  • 前两档靠调用栈自动建树，RunTree 必须自己 create_child；
  • run_type 决定 UI 分类与后续取数，别一律 chain；
  • 跨线程 / 异步 / 流式，优先把 RunTree 显式传下去。

九、思考题

1、什么时候该放弃 @traceable 改用 RunTree？

参考回答：需要手工指定父子、需要跨线程/跨进程、或者是流式输出（run 的结束时间晚于函数返回）时。其余场景装饰器更省事。

2、为什么 trace 上下文没有函数名可当 name？

参考回答：它包的是代码块而不是函数，官方要求显式给名字；不给名会得到一个泛化名称，后续按 name 过滤时找不着。

3、自动埋点已经有一棵树了，再手写一层会怎样？

参考回答：树里会多一层「你的包装」，通常无害但会增加 run 数；如果包装层没有额外信息，删掉它。

4、埋点太多导致的成本上升，先砍哪里？

参考回答：先砍高频、低信息量的中间层（重排、拼串这类），保留根节点与关键分支；再考虑在入口处降采样。
