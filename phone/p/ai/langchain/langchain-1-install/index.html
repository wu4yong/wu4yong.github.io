LangChain 01 · 安装与最小工程

分类：ai · langchain ｜ 标签：系统课 · LangChain · AI

01 安装与最小工程

v1 把 langchain 收缩为「入口 + 核心组件」，provider 拆成独立包，旧链迁到 langchain-classic｜依据 docs.langchain.com 迁移指南自绘

版本不一致提示

  • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方 Quickstart 的示例环境写的是 Python 3.11，只是解释器版本不同，装包与 API 行为一致；
  • 旧教程里 pip install langchain 之后直接用 LLMChain、AgentExecutor 的写法属于 0.x，与 v1 的包拆分不兼容；
  • 包结构请按「langchain 入口 + provider extra + langchain-classic 储物间」三层理解，不要照 0.x 的单包心智模型装。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 v1 里 langchain / langchain-core / provider 包 / langchain-classic 各自负责什么，为什么装完 langchain 还调不动模型；
  2. 从零起一个能跑的最小工程：虚拟环境、依赖、.env、import、跑通一次模型调用；
  3. 看到 ModuleNotFoundError、ValueError: model provider not supported 这类报错时，知道是包没装对，而不是代码写错。

二、前置知识

  • 会 Python 基础语法，能在命令行里执行 uv / pip / python（本系列默认 uv，没有就装一个，装法见本篇第三节）；
  • 知道「环境变量」是什么（不要求熟练）；
  • 不需要任何 LangChain 旧版经验——这一讲按 v1 从零讲，旧写法只在不教就会踩坑的地方提一句「v1 已改为……」。

三、理论讲解（官方定义）

这一节的顺序照官方 Quickstart 的前两节（Install dependencies → Set up API keys），再补官方 v1 迁移指南 的「Simplified package」一节的包结构。

1. 安装依赖（官方 Quickstart「Install dependencies」）

官方给出的三条安装路径，按你的工具链选一条：

# 01 安装与最小工程
uv python pin 3.13
uv init
uv add langchain
uv sync

# 01 安装与最小工程
pip install -U langchain

# 01 安装与最小工程
python3.13 -m venv .venv
source .venv/bin/activate
# 01 安装与最小工程
pip install -U langchain

三种方式装出来的包完全一样，区别只在「谁来管虚拟环境和锁文件」：uv 用 pyproject.toml + uv.lock，pip 用你手写的 requirements.txt 或干脆不锁。本系列后续的命令一律写 uv add / uv run，pip 用户在命令后面注释里能看到等价写法。

机器上还没有 uv 的话，一条命令就够：pip install uv（Windows 也可 winget install astral-sh.uv，macOS/Linux 可用 brew install uv 或官方安装脚本）。

Python 版本是硬门槛。官方迁移指南的「Breaking changes → Dropped Python 3.9 support」明确写了 v1 不再支持 Python 3.9，因此 v1 的最低版本是 3.10。
官方 Quickstart 的示例环境钉的是 3.11，本系列统一用 3.13——当前 3.13 已是主流稳定版，v1 全部依赖都能正常安装；
两者不矛盾：3.10 只是下限，往上到 3.13 都在支持范围，越新的版本在性能和 asyncio 表现上越好。

2. 配置凭证（官方 Quickstart「Set up API keys」）

官方的原话是：从任意受支持的 provider 拿一个 API key（例如 Google Gemini 或 OpenAI），把 key 设在 shell 环境变量或 .env 文件里。以 OpenAI 为例：

# 01 安装与最小工程
export OPENAI_API_KEY="your-api-key"

# 01 安装与最小工程
OPENAI_API_KEY=your-api-key

要读 .env，官方要求用 python-dotenv 的 load_dotenv()。其他 provider 的环境变量名各不相同：Anthropic 是 ANTHROPIC_API_KEY，Google 是 GOOGLE_API_KEY，OpenRouter 是 OPENROUTER_API_KEY，AWS Bedrock 是 AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY + AWS_REGION（完整清单见官方 Quickstart 的分页签）。

4. 旧功能去哪了：langchain-classic（官方迁移指南「Simplifying the package」）

官方列的搬家清单：旧式 Chain（LLMChain、ConversationChain 等）、Retriever（如 MultiQueryRetriever）、indexing API、hub 模块、Embedding 相关模块（如 CacheBackedEmbeddings）、langchain-community 的再导出、以及其他已废弃能力。

from langchain_classic.chains import LLMChain
from langchain_classic.retrievers import ...

版本备注：【旧版是 from langchain.chains import LLMChain 这类写法，v1 已改为安装 langchain-classic 并从 langchain_classic 导入】。来源：LangChain v1 migration guide · Simplified package。

5. provider 包要单独装（官方 Models 页「Initialize a model」）

官方在 Models 页给每个 provider 配了安装命令，形式是 extra。用 uv 时把 extra 一起写进包名：

uv add "langchain[openai]"
uv add "langchain[anthropic]"
uv add "langchain[google-genai]"
uv add "langchain[aws]"
uv add "langchain[huggingface]"
uv add langchain-deepseek
uv add langchain-openrouter

# 01 安装与最小工程
pip install -U "langchain[openai]"

DeepSeek 走的是独立包 langchain-deepseek（没有 extra），因此清单里单独一行；它对应的 provider 名是 deepseek，环境变量是 DEEPSEEK_API_KEY，与 OpenAI 的 key 分开存。本系列主线示例用 OpenAI，第 02 篇给了一份同代码换 DeepSeek 的对照演示。

uv add 会顺带写进 pyproject.toml 并更新 uv.lock，团队里别人 uv sync 就装到同一套版本；pip 则要自己记着 pip freeze > requirements.txt。

这些包不是可选的装饰：init_chat_model("openai:gpt-5-nano") 在运行时要去查 langchain_openai，没装就直接报错。

6. 最小工程结构（实践补充）

【实践补充，非官方文档内容】 官方 Quickstart 只给了单文件示例，工程化落地建议这样分：

lc-demo/
├─ pyproject.toml       # uv 的依赖声明（pip 方案换成 requirements.txt）
├─ uv.lock              # 锁死实际版本，进仓库
├─ .env                 # 凭证，必须进 .gitignore
├─ src/
│  ├─ config.py        # 读环境变量，集中出口
│  ├─ model.py         # init_chat_model 的唯一创建点
│  └─ main.py          # 业务入口
└─ tests/
   └─ test_smoke.py    # 一条「能不能调通」的冒烟测试

三条理由：凭证只有 config.py 一个出口，泄漏时只需改一处；模型只有 model.py 一个创建点，换 provider 不搜全仓库；冒烟测试能在 CI 里第一时间发现 key 过期或包没装。

四、原理拆解

装包 → 凭证 → 导入 → 初始化 → 调用 → 验证，v1 的失败几乎都落在前四环｜自绘

把 LangChain 想成家里的影音系统：

  • langchain-core 是插座标准（消息、Runnable、工具接口的定义），所有设备都得按它接线；
  • langchain 是遥控器，只保留「开机、选台、调音量」这几个真正常用的键；
  • provider 包是各品牌电视的驱动（langchain-openai、langchain-anthropic……），遥控器本身不认识电视，是驱动去认的；
  • langchain-classic 是储物间，旧型号的线材都收在那里，要用自己去拿。

这个类比能解释最常见的困惑：装了遥控器却没有驱动，按开机键当然没反应。报错信息里的 model provider not supported 说的就是这个——不是模型名字写错，是驱动没装。

五、场景说明

三种典型起步方式，选一种即可：

  1. 学习 / 脚本：单文件 + .env，官方 Quickstart 就是这个形态，跑通优先；
  2. 服务化：src/ 分包 + pyproject.toml / uv.lock 锁版本（pip 方案用 requirements.txt），key 从部署平台注入（环境变量），代码里不出现明文；
  3. 多 provider 并存：model.py 里用 init_chat_model 按配置字符串切换，不要在业务代码里 ChatOpenAI(...) 硬编码——这是 v1 官方推荐的统一入口。

  • 智谱、通义不进统一入口。init_chat_model 认不出 zhipuai / tongyi 这两个 provider 名，要直接实例化 ChatZhipuAI、ChatTongyi（两个类都在 langchain-community 里）；两家也都提供 OpenAI 兼容端点（智谱 https://open.bigmodel.cn/api/paas/v4、通义 https://dashscope.aliyuncs.com/compatible-mode/v1），用 ChatOpenAI(base_url=...) 也能打通，但 provider 专有字段可能不被提取或保留。

七、常见坑（官方明确限制/版本差异）

  1. 只装 langchain，没装 provider 包。官方 Models 页为每个 provider 单独给了安装命令，uv 下写 uv add "langchain[xxx]"（pip 下 pip install -U "langchain[xxx]"），缺包时 init_chat_model 会直接失败。判断方法：报错里出现 provider 名称 → 补装对应包。
  2. Python 3.9。官方迁移指南「Dropped Python 3.9 support」是明确的破坏性变更，3.9 上装 v1 会失败或装到旧版。
  3. 旧 import 找不到。from langchain.chains import ... 在 v1 会 ModuleNotFoundError，因为 Chain 已迁到 langchain-classic（官方迁移指南原文列举）。
  4. 把 key 写进代码。官方 Quickstart 一律用环境变量或 .env；写进代码再提交，等于把账单交给别人。
  5. max_tokens 在 langchain-anthropic 上的默认值变化。官方迁移指南的 Breaking changes 里列有「Default max_tokens in langchain-anthropic」一项，正文未给统一数值，结论是：不要依赖默认值，显式传。

本篇涉及的 API 在 LangChain v1 迁移指南中有对应条目的有：langchain 包命名空间收缩（Simplified package）、langchain-classic 迁移、Python 3.9 支持移除。其余安装命令本身无版本语义。

八、课后小结

  • v1 的 langchain 只有五个入口模块：agents、messages、tools、chat_models、embeddings；
  • 装 langchain 不等于能调模型，provider 包必须单独装；
  • Python 最低 3.10，本系列统一用 3.13；
  • 旧 Chain / Retriever / hub 都在 langchain-classic；
  • 工程化的底线是：key 只有一个出口、模型只有一个创建点、有一条冒烟测试。

九、思考题

1、为什么官方要把 langchain 的命名空间砍到只剩五个模块？砍掉的东西去哪了？

参考回答：因为 v1 的定位收敛为「智能体构建」，入口越少，学的人越不需要在几十个模块里猜该用哪个。被砍掉的旧 Chain、Retriever、indexing、hub 等统一迁到 langchain-classic，需要时单独安装、单独导入，主包保持轻量。

2、uv add langchain 之后立刻 init_chat_model("openai:gpt-5-nano") 报 provider 不支持，最可能的原因是什么？

参考回答：provider 包没装。init_chat_model 需要 langchain-openai 才能构造 ChatOpenAI，官方在 Models 页为每个 provider 单独给了安装命令，正确做法是 uv add "langchain[openai]"（pip：pip install -U "langchain[openai]"）。

3、from langchain.chains import LLMChain 在 v1 报 ModuleNotFoundError，是版本装错了吗？

参考回答：不是。v1 已把旧 Chain 迁到 langchain-classic，正确写法是 uv add langchain-classic 后 from langchain_classic.chains import LLMChain。官方迁移指南明确说明这是有意的包拆分，不是安装问题。

4、为什么官方示例的 key 都从环境变量读，而不是写在代码里？

参考回答：代码会进版本库、进镜像、进日志，key 一旦写死就等于公开泄漏；环境变量由运行环境注入，换环境不用改代码，泄漏时只需换一处注入点。

十、下一篇预告

下一篇标题：02 模型初始化与 provider 切换。

一句话内容：讲透 v1 唯一的模型入口 init_chat_model——它怎么把 "provider:model" 字符串变成具体模型对象、参数表里每一项在什么时候必须显式给、换 provider 时到底要改几行代码。

承接关系：本篇跑通的 model.invoke("...") 用的就是 init_chat_model 的返回值，但那只是「能用」；下一篇把这个对象拆开，讲清它的参数与调用方式，否则后面讲工具、讲 Agent 时你不知道模型层还能调什么。
