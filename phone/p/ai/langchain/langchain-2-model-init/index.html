LangChain 02 · 模型初始化与 provider 切换

分类：ai · langchain ｜ 标签：系统课 · AI · LangChain

02 模型初始化与 provider 切换

provider:model 字符串 → provider 包 → 具体 ChatModel 实例，换模型只改一个字符串｜依据 docs.langchain.com/oss/python/langchain/models 自绘

版本不一致提示

  • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方 Quickstart 的示例环境是 Python 3.11，仅解释器版本不同；
  • max_retries 在 init_chat_model 文档里默认 6，官方又写明 ChatOpenAI、ChatAnthropic 自身默认 2 次，这属于封装层与集成层两个不同默认值，官方原文并列存在，本篇照原样保留、不合并成单一结论；
  • langchain-anthropic 的 max_tokens 默认值在 v1 有变化（迁移指南 Breaking changes），官方未给统一数值，结论是显式传值。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用 init_chat_model 初始化任意受支持 provider 的模型，并说清 "provider:model" 与 model_provider= 两种写法的区别；
  2. 看懂模型参数表里 temperature、max_tokens、timeout、max_retries 各自管什么，知道哪些必须显式给；
  3. 在不动业务代码的前提下，把一个 provider 换成另一个 provider。

二、前置知识

  • 第 01 篇已完成：环境、凭证、langchain + provider 包装好，能跑通一次 invoke；
  • 知道什么是 token（不要求会估）。

三、理论讲解（官方定义）

本轮骨架照官方 Models 页的组织：Basic usage（Initialize a model / Supported providers and models / Key methods）→ Parameters → Connection resilience → Invocation。本篇只讲到 Invocation 的 invoke，stream / batch 留给第 04 篇讲流式时展开。

1. 模型的两种用法（官方 Models「Basic usage」）

官方把模型的使用分成两类：

  1. With agents——在创建 agent 时动态指定模型；
  2. Standalone——脱离 agent 循环直接调用，用于文本生成、分类、抽取。

官方强调「同一套模型接口在两种场景下通用」，所以这一讲先把 standalone 讲透，第 08 篇再把它交给 create_agent。

2. 初始化模型（官方 Models「Initialize a model」）

官方原文：入门 standalone 最省事的方式是用 init_chat_model，从你选的 provider 初始化一个模型。它给了两种写法：

# 02 模型初始化与 provider 切换
model = init_chat_model("gpt-5-nano")

# 02 模型初始化与 provider 切换
model = init_chat_model("claude-sonnet-4-6", model_provider="anthropic")

导入路径：from langchain.chat_models import init_chat_model（v1 路径，官方迁移指南 Namespace 表列出）。

官方定义（直译）：init_chat_model 根据模型标识符从指定的 chat model provider 初始化一个聊天模型；标识符可以用 provider:model 的冒号形式一次给全，也可以用 model_provider 单独指定。

其余 provider 专有参数（如 Azure 的 azure_deployment、ChatOpenAI 的 use_responses_api）以官方 chat model integrations 页为准，官方说明每家的参数集不同。

3. 受支持的 provider（官方 Models「Supported providers and models」）

官方原话大意：LangChain 通过专门的集成包支持所有主流 provider，每个包实现同一套标准接口，因此可以换 provider 而不重写业务逻辑；新模型名不需要等 LangChain 发版，因为 provider 包把模型名直接透传给 provider 的 API。

这句话要记住，它意味着两件事：模型名是「透传」的，官方没列的新型号通常也能用；接口是统一的，invoke 的用法不随 provider 变。

DeepSeek 就在这套体系里：LangChain 的官方集成页有 ChatDeepSeek，装的是独立包 langchain-deepseek（没有 extra），init_chat_model 里对应的 provider 名是 deepseek。本篇第六节给了一份「同一份代码换 DeepSeek」的完整演示，第七节补了它与 OpenAI 的对照和坑。

4. 关键方法（官方 Models「Key methods」）

官方列了三个：

  • Invoke：模型接收消息作为输入，生成完整响应后返回消息；
  • Stream：调用模型，但边生成边返回（第 04 篇）；
  • Batch：把多个请求打包批量发送，处理更高效。

5. 参数与连接韧性（官方 Models「Parameters」「Connection resilience」）

官方把标准参数归纳为 model、api_key、temperature、max_tokens、timeout、max_retries，并说明用 init_chat_model 时这些参数作为 **kwargs 传进去：

model = init_chat_model(
    "claude-sonnet-4-6",
    temperature=0.7,
    timeout=30,
    max_tokens=1000,
    max_retries=6,  # 默认值，网络不稳时可加大
)

「Connection resilience」一节的事实：多数集成会自动重试失败请求，重试网络错误、限流（429）、服务端错误（5xx），不重试 401 未授权、404 这类客户端错误；默认重试次数因包而异——官方点名 ChatOpenAI 与 ChatAnthropic 默认 2 次，ChatGoogleGenerativeAI 默认 6 次，ChatOllama 不重试。而通过 init_chat_model 看到的 max_retries 默认值是 6，这两处口径不同，官方原文并列存在，实际行为以你用的 provider 包为准。

四、原理拆解

同一个 model 对象，三种调用方式：一次一答、边生成边返、打包并发｜自绘

init_chat_model 干的事，等价于前台登记：

你递过去一张写着「openai:gpt-5-nano」的单子（字符串），前台先看冒号前的姓（provider），去对应的通讯录（已安装的 provider 包）里找人，把冒号后的名（model）连同你附带的偏好（temperature 等）一起报上去，最后交给你一个「已经能对话的人」（BaseChatModel 实例）。

所以三类报错都能对上号：

  • 姓不认识 → provider 包没装（第 01 篇的坑）；
  • 名不存在 → 模型名写错，或该 provider 没这个型号；
  • 人到了但不肯说话 → 凭证问题，401。

五、场景说明

  1. 本地调试省钱：init_chat_model("ollama:qwen3") 走本地，不烧钱；
  2. 生产多模型灰度：配置里放 MODEL_NAME=openai:gpt-5-nano，代码只读配置，切换 provider 不用改代码；
  3. 同一应用内多模型：便宜模型做分类、强模型做总结，各建一个实例即可，互不影响。

六、示例代码

步骤 1：环境准备

同第 01 篇步骤 1；本篇额外依赖是 provider 包，本篇用 langchain[openai]：

uv add "langchain[openai]"
# 02 模型初始化与 provider 切换

步骤 2：凭证配置

同第 01 篇步骤 2，本篇需要 OPENAI_API_KEY。

步骤 3：导入

from langchain.chat_models import init_chat_model  # v1：统一模型入口

步骤 4：最小可运行代码

存成 main.py，然后 uv run main.py（pip 方案：python main.py）。

from langchain.chat_models import init_chat_model

# 02 模型初始化与 provider 切换
model = init_chat_model(
    "openai:gpt-5-nano",
    temperature=0.3,   # 越低越稳定，抽取类任务建议 0~0.3
    timeout=30,        # 单次请求上限，超时会重试
    max_retries=6,     # 官方默认值；弱网可提到 10~15
)

# 02 模型初始化与 provider 切换
response = model.invoke("把这句话翻译成英文：今天下雨了。")

print(response.text)              # 文本
print(response.content_blocks)    # 标准化内容块（第 03 篇细讲）
print(response.usage_metadata)    # token 用量

步骤 5：预期输出

It rained today.
[{'type': 'text', 'text': 'It rained today.'}]
{'input_tokens': 18, 'output_tokens': 6, 'total_tokens': 24}

输出内容会因模型不同而不同，结构大致为：文本、内容块列表、用量字典三部分。

步骤 6：验证是否成功

response.text 不为空且 response.content_blocks 里能看到 {'type': 'text', ...}，说明初始化与调用都通了。想验证「换 provider 只改字符串」，把模型换成 "ollama:qwen3"（本地已起 Ollama，先 uv add "langchain[ollama]"）再 uv run main.py 一次，代码其余部分一行不用动。

写法 A · 统一入口：同一份代码换成 DeepSeek

上面六步跑的是 OpenAI。现在把 provider 换成 DeepSeek 走一遍，全程只动三处：装哪个包、读哪个环境变量、model 与 model_provider 两个字符串。

环境准备：DeepSeek 是独立集成包，不在 langchain 的 extra 里，要单独装。

uv add langchain-deepseek
# 02 模型初始化与 provider 切换

凭证配置：.env 里加 DEEPSEEK_API_KEY（DeepSeek 平台生成），与 OPENAI_API_KEY 并存，互不覆盖。

DEEPSEEK_API_KEY=sk-...

最小可运行代码：存成 main_deepseek.py，uv run main_deepseek.py。

import os

from dotenv import load_dotenv
from langchain.chat_models import init_chat_model

load_dotenv()

assert os.environ.get("DEEPSEEK_API_KEY"), "DEEPSEEK_API_KEY 没有加载成功"

# 02 模型初始化与 provider 切换
model = init_chat_model(
    model="deepseek-chat",        # 通用对话档；deepseek-reasoner 是推理档
    model_provider="deepseek",    # 对应 langchain-deepseek
    temperature=0.3,
    timeout=30,
    max_retries=2,                # ChatDeepSeek 的默认重试次数
)

response = model.invoke("把这句话翻译成英文：今天下雨了。")

print(type(response))
print(response.text)
print(response.content_blocks)
print(response.usage_metadata)

预期输出：结构和 OpenAI 一模一样，只是 id、用量数字不同。

<class 'langchain.messages.AIMessage'>
It rained today.
[{'type': 'text', 'text': 'It rained today.'}]
{'input_tokens': 20, 'output_tokens': 5, 'total_tokens': 25}

验证是否成功：response.text 有内容、content_blocks 里是 {'type': 'text', ...} 就通了。反过来说，invoke / stream / batch / bind_tools / with_structured_output 这些方法名一个都没变，官方那句「换 provider 不重写业务逻辑」在这里兑现。

写法 B · 底层类：直接用 ChatDeepSeek

init_chat_model 是官方推荐的统一入口；需要传 DeepSeek 专有参数时，也可以像其他 provider 一样直接实例化集成包里的类。

from langchain_deepseek import ChatDeepSeek

llm = ChatDeepSeek(
    model="deepseek-chat",
    temperature=0.3,
    timeout=30,
    max_retries=2,
)

print(llm.invoke("用一句话解释什么是 LangChain").text)

两点按官方文档说清：ChatDeepSeek 的基类是 BaseChatOpenAI（API Reference 写的），所以 OpenAI 兼容协议那套参数基本通用；DeepSeek 自家的扩展字段官方没在集成页单列，要传就查 DeepSeek 平台文档，再通过 extra_body 透传（【实践补充，非官方文档内容】这一步没有官方示例，属通用做法）。

init_chat_model 只认「provider:model」这张单子，包不同、底层 API 不同，交回来的都是同一类 BaseChatModel｜依据 docs.langchain.com Models 与 ChatDeepSeek 集成页自绘

七、常见坑（官方明确限制/版本差异）

  1. 两处都写 provider 且不一致。init_chat_model("openai:gpt-5-nano", model_provider="anthropic") 这种写法不会报错，但实际行为容易误判；统一只用一种写法。
  2. 以为 max_retries=6 对所有 provider 生效。官方 Models 页明确点名 ChatOpenAI / ChatAnthropic 默认 2 次、ChatGoogleGenerativeAI 6 次、ChatOllama 不重试——重试是 provider 包的能力，不是模型接口的保证。
  3. 401 / 404 一直重试。官方写明客户端错误不重试，遇到 401 先查 key，别调大 max_retries。
  4. langchain-anthropic 的 max_tokens 默认值在 v1 有变化。官方迁移指南 Breaking changes 列有「Default max_tokens in langchain-anthropic」条目，正文未给统一数值，实践结论：显式传 max_tokens，不依赖默认。
  5. 把模型名当版本号。官方说明模型名由 provider 透传，因此 gpt-5-nano 是否可用取决于 provider 侧，不是 LangChain 版本。
  6. 拿 OpenAI 的 key 去调 DeepSeek。两家凭证分开：OPENAI_API_KEY 只对 openai provider 有效，调 deepseek 要 DEEPSEEK_API_KEY，混用必 401，且 401 不重试。
  7. 用 deepseek-reasoner 做工具调用或结构化输出。官方集成页明确写它不支持 tool calling 与 structured output，这两项是 deepseek-chat 的能力；第 05、06、08 篇照 deepseek-chat 写。
  8. 裸改 base_url 冒充 OpenAI 端点。官方 Models 页说明 OpenAI 兼容端点可以用 model_provider="openai" + base_url=... 接，但也写明 provider 专有字段可能不被提取或保留；调 DeepSeek 优先装 langchain-deepseek，别走裸改。

本篇涉及 API 在 v1 迁移指南中的对应条目：Models 页本身未标注 init_chat_model 的签名变更；迁移指南 Breaking changes 中与本篇相关的是 langchain-anthropic 的 max_tokens 默认值。除此之外，官方迁移指南与 Release Notes 均未标注 init_chat_model 的跨版本差异。

八、课后小结

  • init_chat_model 是 v1 唯一的模型初始化入口，导入路径 langchain.chat_models；
  • 模型标识符支持 provider:model 与 model_provider= 两种写法，别混用；
  • 标准参数六个：model、api_key、temperature、max_tokens、timeout、max_retries；
  • 重试只对网络错误、429、5xx 生效，401/404 不重试；
  • 换 provider 的代价应该只是改一个字符串；
  • 换到 DeepSeek 就是三处改动：装 langchain-deepseek、用 DEEPSEEK_API_KEY、写 model="deepseek-chat" + model_provider="deepseek"。

九、思考题

1、为什么官方推荐用 init_chat_model，而不是直接 ChatOpenAI(model=...)？

参考回答：init_chat_model 把「选哪家 provider」收敛成一个字符串，业务代码不出现 provider 类名，切换 provider 只改配置；直接实例化 provider 类会把厂商绑进代码，换一家就要改 import 和构造调用。两者底层等价，官方把前者作为统一入口。

2、max_retries 在 init_chat_model 文档里默认 6，但官方又说 ChatOpenAI 默认重试 2 次，冲突吗？

参考回答：不冲突，是两个层面。6 是 init_chat_model 这个封装层传入的默认值，2 是 ChatOpenAI 集成自身在未显式指定时的默认重试次数。官方把两处口径并列写出，实际以你最终构造出的 provider 包行为为准；对稳定性有要求时显式传值最稳。

3、模型名 gpt-5-nano 在 LangChain 里需要等框架发版支持吗？

参考回答：不需要。官方说明 provider 包把模型名直接透传给 provider 的 API，所以新模型名通常立刻可用，前提是 provider 侧确实提供该模型。

4、什么情况下应该把 temperature 设成 0？

参考回答：需要可复现、可对比的输出时，例如分类、信息抽取、结构化输出、评测基线。创意写作、对话润色这类任务才需要调高。注意官方未承诺 temperature=0 一定完全确定，provider 实现仍有差异。
