13 RAG：加载、切分、向量库与带出处的检索

每一段都能替换，互不影响；RAG 难的不是接线，是「切得对、检索得到、引用得住」｜依据官方 Retrieval / Semantic search 页自绘

版本不一致提示

  • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
  • 官方示例用 Nike 10-K 的 PDF 演示，本篇换成你自己的文本/PDF，接口一致；
  • InMemoryVectorStore 在 langchain-core 里；RecursiveCharacterTextSplitter 在 langchain-text-splitters 里，二者都是独立包。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 RAG 的三条架构路线（2-Step / Agentic / Hybrid）差别与适用场景；
  2. 会跑完整链路：Document → 切分 → embedding → InMemoryVectorStore.add_documents → as_retriever；
  3. 会把检索包成 @tool 交给 Agent，并让回答带上 source / page 出处，而不是「凭空作答」。

二、前置知识

  • 读完 LC05（工具协议）、LC08（Agent 循环）；
  • 知道 Document(page_content, metadata) 两个字段的意义；
  • 有一个能跑的 OpenAI key（embedding 也用同一把）。

三、理论讲解（官方定义）

1. 官方为什么需要检索

官方开篇给的判断非常直白：LLM 有两个硬限制——上下文有限（吃不下整个语料）与知识静态（训练数据冻结在某个时点）。检索的作用是在查询时把相关的外部知识取回来，这就是 RAG（Retrieval-Augmented Generation）的基础。

2. 三条架构（官方对照表）

架构
说明
可控性 / 灵活性 / 延迟
典型场景
2-Step RAG
先检索、再生成，顺序固定
高 / 低 / 快
FAQ、文档机器人
Agentic RAG
由 Agent 决定何时、怎么检索
低 / 高 / 不稳定
多工具的调研助手
Hybrid
两者结合，加校验步骤
中 / 中 / 不稳定
需要质量把关的领域问答

官方还补了一句延迟口径：2-Step 的最大模型调用次数是已知且有上限的，所以延迟更可预期；实际耗时还会受检索 API、网络、数据库影响。

3. 五段链路与可替换点

官方把检索管线画成：Sources → Document Loaders → Documents → 切分 → 向量化 → Vector Store →（查询向量）→ Retriever → 交给 LLM，并强调每个组件都是模块化的，换 loader / splitter / embedding / vector store 不用改应用逻辑。

4. 切分的关键参数

官方推荐通用文本用 RecursiveCharacterTextSplitter，示例参数是 chunk_size=1000、chunk_overlap=200，并特别提示 add_start_index=True——这样每个块会带上在原文档里的字符偏移 start_index，是「带出处」的基础。

5. 检索的三档

vector_store.as_retriever(search_type=..., search_kwargs={"k": n}) 支持：

search_type
含义
similarity
纯相似度（默认）
mmr
最大边际相关：兼顾相似与多样，避免召回一堆近似重复块
similarity_score_threshold
按分数阈值过滤，分数不够的块不返回

官方同时提醒：不同 provider 的分数语义不同，有的是距离（越小越像），有的是相似度（越大越像），别跨库比较阈值。

四、原理拆解

检索质量 = 切分质量 × 检索模式 × 提示约束；三者缺一，回答就会「看起来对」｜自绘

三个决定效果的地方，比换向量库重要得多：

  1. 切分粒度。块太大，一个块里混着几个主题，检索到却答不准；块太小，上下文不完整，模型只能猜。1000 / 200 是官方示例的起点，不是标准答案。
  2. 检索模式。文档里有大量重复表述时，similarity 会把同一段的不同措辞都召回来，浪费窗口；mmr 用多样性惩罚换覆盖度。
  3. 提示约束。工具返回里带上 source 与 page，并在 system prompt 里要求「答案必须能对应到片段，找不到就说找不到」，这是「带出处」的实现方式——官方在 Agentic RAG 示例里就是要求「引用相关片段」。

另外要知道 RAG 和 LC12 的分工：store 记的是「用户的事」，向量库记的是「文档的事」；前者靠 namespace/key 精确取，后者靠相似度模糊找。

五、场景说明

  1. 内部文档问答：PDF / Markdown 入库，Agent 调 search_docs，回答附「文件名 + 页码」；
  2. 2-Step 场景：客服 FAQ，先检索再固定模板生成，延迟可控、答案可预测；
  3. Agentic 场景：多个知识源（文档库 + 数据库 + 网页），让 Agent 自己挑工具；
  4. Hybrid 场景：先改写查询再检索，检索后判断「够不够」，不够就换查询重试。

六、示例代码

💡 本篇示例跑 OpenAI，换 DeepSeek 只改三处：uv add langchain-deepseek、.env 里换成 DEEPSEEK_API_KEY、init_chat_model(..., model="deepseek-chat", model_provider="deepseek")。下面的代码除模型名与 provider 外一行不改；涉工具调用与结构化输出时用 deepseek-chat（官方集成页写明 deepseek-reasoner 不支持这两项），两家完整对照见 LC02 第六节。

步骤 4：最小可运行代码

存成 rag_demo.py，uv run rag_demo.py。示例不依赖外部 PDF，用三段文本模拟文档，跑通链路后再换真实文件。

from dotenv import load_dotenv
from langchain_core.documents import Document
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain.tools import tool
from langchain.agents import create_agent

RAW = [
    ("handbook.md", "退款政策：下单后 7 天内可无理由退款，超过 7 天需提供质量问题证明。"),
    ("handbook.md", "发票说明：电子发票在订单完成后 24 小时内开具，可在订单详情页下载。"),
    ("ops.md", "发货时效：现货商品 48 小时内发出，预售商品以商品页标注时间为准。"),
]

load_dotenv()
docs = [Document(page_content=t, metadata={"source": s, "page": i}) for i, (s, t) in enumerate(RAW)]
splitter = RecursiveCharacterTextSplitter(chunk_size=200, chunk_overlap=40, add_start_index=True)
splits = splitter.split_documents(docs)
vector_store = InMemoryVectorStore(OpenAIEmbeddings(model="text-embedding-3-small"))
vector_store.add_documents(splits)

@tool
def search_docs(query: str) -> str:
    """检索内部文档。回答政策类问题前必须先调用，返回内容带 source 与 page。"""
    hits = vector_store.similarity_search(query, k=3)
    if not hits:
        return "未检索到相关片段"
    return "\n".join(
        f"[{d.metadata['source']} p.{d.metadata['page']}] {d.page_content}" for d in hits
    )

agent = create_agent(
    model="openai:gpt-5-nano",
    tools=[search_docs],
    system_prompt="只用 search_docs 的返回内容作答，并在末尾列出引用来源；检索不到就直说没有依据。",
)
r = agent.invoke({"messages": [{"role": "user", "content": "退款期限是多久？"}]})
print(r["messages"][-1].text)

步骤 5：预期输出

下单后 7 天内可无理由退款，超过 7 天需提供质量问题证明。
来源：handbook.md p.0

步骤 6：验证是否成功

  • 打印 len(splits) 与 splits[0].metadata，确认每个块带 source、page、start_index；
  • 问一个文档里没有的问题（如「保修多久」），应得到「没有依据」而不是编造——这是提示约束生效的证据；
  • 把 search_type 换成 mmr（vector_store.as_retriever(search_type="mmr", search_kwargs={"k": 3})）对比召回差异。

七、常见坑（官方明确限制/版本差异）

  1. 块切得太大。一个块混多个主题，检索命中但答非所问；官方示例 1000/200 针对的是长财报，短文档要往下调。
  2. 忘了 add_start_index=True。想要「第几段 / 第几字符」出处时，这个元数据是前提。
  3. 跨库比分数。官方明确各 provider 分数语义不同，同一阈值换个库就失效。
  4. 把整库内容塞进提示。RAG 的意义是「按需取」，全塞等于放弃检索，还会触发长上下文分心（LC11）。
  5. 没有「检索不到」分支。工具返回空要显式说没找到，否则模型会顺着惯性编。

八、课后小结

  • LLM 两处硬伤：上下文有限、知识静态，检索就是补这两处；
  • 三条架构：2-Step（可控快）、Agentic（灵活慢）、Hybrid（加校验）；
  • 五段链路都可替换，切分参数与检索模式比换库更影响效果；
  • similarity / mmr / similarity_score_threshold 三档各有用途；
  • 带出处靠 metadata + 提示约束，两者缺一不可。

九、思考题

1、什么时候必须用 Agentic RAG，而不是 2-Step？

参考回答：当「要不要检索、检索哪个源」本身取决于中间结果时——比如先查订单号、再决定查政策库还是物流库。2-Step 的检索是前置固定动作，做不到这种按需决策。

2、mmr 解决的是什么问题？

参考回答：纯相似度会召回大量语义重复的块，占满窗口却信息量低；mmr 在相似度和多样性之间做惩罚，让召回覆盖更多不同表述，适合文档里同一件事反复出现的场景。

3、为什么「带出处」不只是加一个字段？

参考回答：字段让用户能核对，提示约束让模型不敢脱离片段作答，检索质量决定片段本身对不对——三层合起来才是可追溯，只有字段而没有约束，模型照样会自由发挥。

4、生产上把 InMemoryVectorStore 换成什么？

参考回答：按规模选：小规模可用 Chroma / PGVector（本地可持久化），大规模用 Qdrant / Milvus / Pinecone 等托管或集群方案；官方语义检索教程列了这些集成，接口都遵循同一套 VectorStore 抽象。
