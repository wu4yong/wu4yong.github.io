04 流式输出

模型层的 stream() 只吐 token；Agent 层的 stream_mode 才决定你看到的是进度、token 还是自定义事件｜依据官方 Streaming 页自绘

版本不一致提示

  • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
  • version="v2" 需要 LangGraph 1.1 以上，低于该版本只能按元组解包，这是本篇最需要注意的版本门槛；
  • 官方页面里的模型名（如 gpt-6.1-sol）随 provider 更新，模型名由 provider 透传，与本系列示例不同不代表写法过时。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 分清「模型级流式」和「Agent 级流式」——前者是 model.stream() 返回 AIMessageChunk，后者是 agent.stream(stream_mode=...) 返回带模式标签的事件；
  2. 会选 stream_mode：messages（token）、updates（每步状态）、custom（自己塞的进度），以及列表组合用法；
  3. 会处理 v1 的两处坑：version="v2" 的 StreamPart 结构与旧 (mode, chunk) 元组的区别，以及 provider 不支持流式时怎么关掉。

二、前置知识

  • 读完 LC02（invoke 的入参、AIMessage 字段）与 LC03（content_blocks）；
  • 知道生成器（for ... in ...）是什么，本篇大量迭代；
  • 环境沿用 LC01 的 lc-demo 工程，已有 langchain[openai]。

三、理论讲解（官方定义）

1. 模型层：stream() 的返回不是消息，是消息块

官方 Models 页「Key methods」把 Stream 定义为：调用模型，但边生成边返回。它的返回类型是 AIMessageChunk，不是 AIMessage——块与消息的区别，在于块可以被「加」起来：

chunk1 + chunk2   # AIMessageChunk 支持相加，结果仍是 AIMessageChunk

把一批块累加到最后，等价于一次 invoke 的结果。这条性质是后面 Agent 流式、断点续传、UI 增量渲染的基础。

2. Agent 层：三种 stream mode

官方 Streaming 页把 Agent 的流式能力归成三个模式，作为列表传给 stream() / astream()：

模式
吐什么
典型用途
updates
每个 Agent 步骤后的状态更新；同一步内多个节点的更新会分开吐
展示「正在调用工具」「工具返回了」
messages
任意调用 LLM 的节点产生的 (token, metadata) 元组
打字机效果、字幕
custom
工具或节点里用 stream writer 主动写的任意数据
「已抓取 10/100 条」这类进度

messages 模式最常用的用途是 token 级输出；updates 是「步骤级」，粒度粗但省流量。

3. reasoning（思考）与 tool call 也在流里

官方 Streaming 页单列两节：

  • 思考流：部分模型会先做内部推理再给答案，推理 token 以 content block 的 reasoning 类型出现，需要模型侧开启推理输出，然后在 messages 流里按 type == "reasoning" 过滤；
  • 工具调用流：messages 模式会吐出增量 JSON 的 tool_call_chunk，等工具真正执行时，完整、已解析的 tool call 出现在状态更新里。官方给的做法是 stream_mode=["messages", "updates"]——一边看 JSON 逐字拼，一边看解析完的调用。

4. v2 输出格式（版本差异点）

官方写明：version="v2" 需要 LangGraph 1.1 或更高。开启后每个 chunk 是统一的 StreamPart 字典：

{"type": "updates" | "messages" | "custom", "ns": ..., "data": ...}

不开 v2（当前默认）则要按元组解包 for mode, chunk in agent.stream(...)。v2 还改了 invoke() 的返回：变成 GraphOutput，用 .value 拿状态、.interrupts 拿中断。

5. 关掉流式

官方给了两种写法：在支持该参数的集成上 ChatOpenAI(..., streaming=False)；不支持的模型用基类都认的 disable_streaming=True。部署到 LangSmith 时，不想让某个模型输出被流给客户端，就设这两个之一。

四、原理拆解

invoke 是「攒完再给」，stream 是「给一块算一块」，两者的终点是同一条 AIMessage｜自绘

用送快递打比方：

  • invoke 是等你收齐一整车货再签收，快但看不到过程；
  • stream 是每到一个包裹就通知你，慢一点点但你知道进度；
  • stream_mode 决定通知的是什么——messages 通知「箱子里每件商品」（token），updates 通知「第几个包裹到了」（步骤），custom 是你自己让快递员打的电话（进度条）。

关键点：流式不改变结果，只改变「你什么时候能看到」。所以调试时先用 invoke 看全量结果，确认逻辑对了，再换 stream 做交互，是本系列推荐的顺序。

五、场景说明

  1. 聊天界面：必须 messages 模式，否则用户盯着转圈等 8 秒；
  2. 长任务 Agent：「查库 → 调工具 → 再查」这种多步，updates 模式给状态文案，messages 给正文，二者组合；
  3. 批量数据处理：工具里用 get_stream_writer() 写「已处理 30/200」，前端进度条；
  4. 后台批跑 / 评测：直接 invoke，流式在这里没有收益，反而增加拼接成本。

六、示例代码

步骤 1：环境准备

uv add "langchain[openai]"
# 04 流式输出

步骤 2：凭证配置

同 LC01，需要 OPENAI_API_KEY，写在 .env，由 load_dotenv() 读入。

步骤 3：导入

from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.messages import AIMessageChunk   # 块类型，用于类型判断与累加

步骤 4：最小可运行代码

存成 stream_demo.py，uv run stream_demo.py（pip 方案：python stream_demo.py）。

from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.messages import AIMessageChunk

load_dotenv()
model = init_chat_model("openai:gpt-5-nano")

acc = None                      # 累加器：用来把块拼回完整消息
for chunk in model.stream("用三句话讲清楚什么是流式输出"):
    acc = chunk if acc is None else acc + chunk
    print(chunk.text, end="", flush=True)   # 边生成边打印

print()                                     # 换行
print(type(acc))                            # AIMessageChunk
print(len(acc.content_blocks), "blocks")    # 拼完后的块数量

想看点更细的块结构，把循环体换成打印 chunk.content_blocks：能看到每块都是 {'type': 'text', 'text': '...'} 的增量片段，最后一块可能带 usage_metadata。

步骤 5：预期输出

流式输出是把模型的生成结果分块返回……（逐字出现）
<class 'langchain.messages.AIMessageChunk'>
1 blocks

逐字出现的速度取决于 provider 与网络，块数取决于模型的分词粒度，具体数字不必对上。

步骤 6：验证是否成功

三条判据：

  1. 文字是逐渐出现而不是一次性刷出，说明真的在流式；
  2. 循环里没有报 AttributeError，说明你用的是 chunk.text 而不是把块当字符串；
  3. 累加结果的 content_blocks 长度 ≥ 1 且文本与打印的总文本一致，说明「块能加」这条性质成立。

写法 A · 统一入口：同一份代码换成 DeepSeek

deepseek-chat 走 SSE 逐 token 返回，stream 这条链路完全等价：

差异集中在「模型怎么初始化」这一层，往下 invoke / stream / bind_tools 的链路基本不变：

  • 智谱、通义不进统一入口。init_chat_model 认不出 zhipuai / tongyi 这两个 provider 名，要直接实例化 ChatZhipuAI、ChatTongyi（两个类都在 langchain-community 里）；两家也都提供 OpenAI 兼容端点（智谱 https://open.bigmodel.cn/api/paas/v4、通义 https://dashscope.aliyuncs.com/compatible-mode/v1），用 ChatOpenAI(base_url=...) 也能打通，但 provider 专有字段可能不被提取或保留。

七、常见坑（官方明确限制/版本差异）

  1. 把 chunk 当消息用。AIMessageChunk 没有 usage_metadata 的完整值（通常只在末尾），也没有稳定的 id；要完整消息就累加，别直接读字段。
  2. 不传 version="v2" 却按 v2 结构取值。默认仍是 (mode, chunk) 元组解包，v2 的 StreamPart 要显式开启，且需要 LangGraph 1.1+。
  3. 想用 messages 模式却拿到了 updates 的内容。多模式组合时必须按 chunk["type"] 分派，否则会把状态字典当 token 打出来。
  4. provider 不支持流式。部分集成没有 streaming 参数，用基类通用的 disable_streaming=True；官方提醒：不支持时硬开会静默退化为一次性返回。
  5. reasoning 流拿不到。官方写明推理输出必须在模型侧开启，且要看 content block 的 reasoning 类型；模型没开推理，messages 流里就只有普通文本。

八、课后小结

  • stream() 返回 AIMessageChunk，块可以相加，加完等价于一次 invoke；
  • Agent 层三种模式：updates（步骤）、messages（token）、custom（自定义），可用列表组合；
  • 工具调用的增量 JSON 在 tool_call_chunk，解析完的调用看 updates；
  • version="v2" 统一成 StreamPart（需要 LangGraph 1.1+），invoke 同时变成 GraphOutput；
  • 能不用流式的地方（批跑、评测）就别用。

九、思考题

1、为什么 AIMessageChunk 支持相加，而 AIMessage 不支持？

参考回答：块是同一个消息的碎片，相加就是把碎片按顺序合并成完整内容与合并元数据，这是流式 UI 增量渲染与「块拼回消息」的必需品；完整消息已经终态，没有合并语义，所以官方只给块定义 +。

2、stream_mode 选 messages 和选 updates，分别在什么场景下更合适？

参考回答：要看「用户在意的是字还是步骤」。聊天打字机效果用 messages；多步 Agent 想让用户知道「现在在调工具、工具返回了什么」用 updates。两者可组合，按 type 分派处理。

3、工具调用的流式输出里，为什么既要 tool_call_chunk 又要完整 tool call？

参考回答：tool_call_chunk 是未完成的增量 JSON，只能展示「正在生成调用」；真正执行需要已解析、id 完整的 tool call，官方建议用 ["messages","updates"] 组合，前者看进度，后者拿可执行版本。

4、version="v2" 开启后，为什么老的流式代码会报错？

参考回答：v1 默认返回 (mode, chunk) 元组，v2 返回统一的 StreamPart 字典（type/ns/data）。原来的 for mode, chunk in ... 解包在 v2 下拿不到预期结构，需要改成按 chunk["type"] 取值；同时 v2 依赖 LangGraph 1.1 以上。
