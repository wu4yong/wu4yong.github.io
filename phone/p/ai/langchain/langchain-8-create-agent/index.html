08 create_agent 循环

循环没有「最大轮数」这个魔法参数，退出条件是「模型这一轮不再给 tool_call」｜依据官方 Agents 页自绘

版本不一致提示

  • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
  • 旧 0.x 的 AgentExecutor + max_iterations 在 v1 已从主包移除，对应的「轮数上限」能力改由中间件提供；
  • 官方示例模型名随 provider 更新（如 gpt-6.1-sol），不影响 create_agent 的写法。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 create_agent 的几个关键参数，以及哪些必须给、哪些给了才有对话记忆；
  2. 画出 Agent 的一轮循环：模型节点怎么产出 tool_call、工具节点怎么回灌 ToolMessage、什么时候停；
  3. 会用 checkpointer + thread_id 做多轮，会用 context_schema + context 把身份传进工具。

二、前置知识

  • 读完 LC05（工具协议）、LC07（失败回灌）、LC03（消息结构）；
  • 知道「状态」这个词在 Agent 语境里指「这一轮对话累积的消息与自定义字段」；
  • 不要求懂 LangGraph 的图 API，本讲只用到 create_agent 对外暴露的部分。

三、理论讲解（官方定义）

1. create_agent 是一个「装好的图」

官方 Agents 页的定位很直白：create_agent 返回的是一个编译好的 LangGraph，中间件钩子就跑在这张图里。所以你拿到的 agent 既能 invoke / stream，也能当子图塞进更大的 StateGraph。

2. 循环本体

官方 Middleware Overview 对循环的描述是：「调用模型 → 让模型选择要执行的工具 → 当它不再调用工具时结束」。落到节点上：

  1. model 节点：把当前 messages 发给模型，拿回一条 AIMessage；
  2. 判断：AIMessage.tool_calls 非空 → 进 tools 节点；为空 → 结束；
  3. tools 节点：按每个 tool call 执行工具，产出 ToolMessage（带 tool_call_id）追加进 messages；
  4. 回到 model 节点，带着新的 ToolMessage 再问一次。

这也解释了两个常见现象：模型「多调一轮」不一定是 bug，而是它还有没消化的工具结果；「循环停不下来」通常是工具总在返回错误、模型一直重试。

3. 状态里到底有什么

AgentState 的最小形态就是 messages，官方在中间件、工具章节里反复用 state["messages"] 读写。要在状态里加字段，就继承 AgentState 传给 state_schema；这也是 LC05 里「工具用 Command 改状态」的落点。

4. 多轮记忆：checkpointer + thread_id

官方给的范式：

from langchain_core.utils.uuid import uuid7
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(model=..., tools=[], checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": str(uuid7())}}

同一个 thread_id 复用 = 同一段对话；换 thread_id = 新会话。官方提醒：部署到 LangSmith Agent Server 时会自动配好 checkpointer，本地跑必须显式传。

5. 每次调用的上下文：context_schema + context

如果要把「用户 ID、租户、开关」传给工具与中间件，用 context_schema 声明形状，invoke 时传 context：

@dataclass
class Context:
    user_id: str

agent = create_agent(model=..., tools=[], context_schema=Context, checkpointer=InMemorySaver())
result = agent.invoke({"messages": [...]}, config={"configurable": {"thread_id": "t1"}}, context=Context(user_id="user-123"))

工具里通过 runtime.context 取（LC05）。这条链路和「把 user_id 塞进工具参数」是两回事：前者不可伪造。

四、原理拆解

正常退出靠「不给 tool_call」，异常退出靠中间件与上限兜底｜自绘

把 Agent 想成客服工单的流转：

  • model 节点是坐席，看工单（messages）决定「自己能答」还是「要查系统」；
  • tools 节点是后台，查完往工单上贴一条结果（ToolMessage）；
  • 坐席看到结果再判断：能答就答（本轮无 tool_call，流程结束），还要再查就继续开单。

三个关键判断：

  1. 谁决定停：模型，不是框架。框架只认「这一轮有没有 tool_call」。
  2. 为什么需要上限：模型可能一直要工具（尤其工具总失败时），ModelCallLimitMiddleware / ToolCallLimitMiddleware 是安全带。
  3. 记忆从哪来：messages 是每轮传入的，checkpointer 负责把它跨轮存住；不传 checkpointer，第二轮就是「失忆的新会话」。

五、场景说明

  1. 单轮问答 Agent：tools 空、不传 checkpointer，最省；
  2. 多轮客服：checkpointer + 稳定 thread_id（如用户会话 ID），配 context_schema 传租户；
  3. 多 Agent 协作：给每个 Agent 设 name，流式里靠 lc_agent_name 区分谁在说话；
  4. 要审计的流程：中间件里做调用上限 + 日志，把每轮 tool call 落库。

步骤 4：最小可运行代码

存成 agent_demo.py，uv run agent_demo.py。

from dataclasses import dataclass
from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.tools import tool, ToolRuntime
from langchain_core.utils.uuid import uuid7
from langgraph.checkpoint.memory import InMemorySaver

ORDERS = {"SO-2026-0001": "已发货，预计明天送达"}

@tool
def get_order(order_id: str, runtime: ToolRuntime) -> str:
    """查询订单状态。订单号形如 SO-2026-0001。"""
    # runtime 里能拿到上下文，本例只用来演示「注入参数不进 schema」
    return ORDERS.get(order_id, "没有这个订单")

@dataclass
class Ctx:
    user_id: str

load_dotenv()
agent = create_agent(
    model="openai:gpt-5-nano",
    tools=[get_order],
    system_prompt="你是订单客服，需要查单就调用 get_order。",
    context_schema=Ctx,
    checkpointer=InMemorySaver(),
)

config = {"configurable": {"thread_id": str(uuid7())}}

r1 = agent.invoke({"messages": [{"role": "user", "content": "SO-2026-0001 到哪了？"}]},
                  config=config, context=Ctx(user_id="u-1"))
print("轮次消息数:", len(r1["messages"]))         # 用户 + tool_call + tool 结果 + 回答

r2 = agent.invoke({"messages": [{"role": "user", "content": "那明天能到吗？"}]},
                  config=config, context=Ctx(user_id="u-1"))
print("轮次消息数:", len(r2["messages"]))         # 累加，说明记忆生效
print(r2["messages"][-1].text)

步骤 5：预期输出

轮次消息数: 5
轮次消息数: 7
能，预计明天送达。

第二轮消息数比第一轮多 2（一条用户消息 + 一条回答），说明 checkpointer 把历史带过来了；具体条数取决于模型是否选择调工具。

步骤 6：验证是否成功

  • 第一轮 messages 里能找到 ToolMessage，说明 tools 节点跑过；
  • 第二轮的消息数 ≥ 第一轮 + 2，说明同一 thread_id 记忆生效；
  • 把 config 换一个 thread_id 再问「那明天能到吗」，模型会说「不知道你指哪个订单」，说明记忆边界正确。

写法 A · 统一入口：同一份代码换成 DeepSeek

Agent 循环、ToolRuntime、checkpointer 都是框架侧能力，只换模型串：

uv add langchain-deepseek
# 08 create_agent 循环
import os
from dataclasses import dataclass
from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.tools import tool, ToolRuntime
from langchain_core.utils.uuid import uuid7
from langgraph.checkpoint.memory import InMemorySaver

ORDERS = {"SO-2026-0001": "已发货，预计明天送达"}

@dataclass
class Ctx:
    user_id: str

@tool
def get_order(order_id: str, runtime: ToolRuntime) -> str:
    """查询订单状态。订单号形如 SO-2026-0001。"""
    return ORDERS.get(order_id, "没有这个订单")

load_dotenv()
assert os.environ.get("DEEPSEEK_API_KEY")

agent = create_agent(
    model="deepseek:deepseek-chat",
    tools=[get_order],
    system_prompt="你是订单客服，需要查单就调用 get_order。",
    context_schema=Ctx,
    checkpointer=InMemorySaver(),
)
cfg = {"configurable": {"thread_id": str(uuid7())}}
print(len(agent.invoke({"messages": [{"role": "user", "content": "SO-2026-0001 到哪了？"}]},
                        config=cfg, context=Ctx(user_id="u-1"))["messages"]))
print(agent.invoke({"messages": [{"role": "user", "content": "那明天能到吗？"}]},
                    config=cfg, context=Ctx(user_id="u-1"))["messages"][-1].text)

InMemorySaver 挂在 graph 上而不是挂在模型上，所以换 provider 后「第二轮消息数累加」的现象不变。ToolRuntime 注入的参数同样不进 schema——这一点由 LangChain 处理，DeepSeek 只负责按 schema 填 args。

差异集中在「模型怎么初始化」这一层，往下 invoke / stream / bind_tools 的链路基本不变：

  • 智谱、通义不进统一入口。init_chat_model 认不出 zhipuai / tongyi 这两个 provider 名，要直接实例化 ChatZhipuAI、ChatTongyi（两个类都在 langchain-community 里）；两家也都提供 OpenAI 兼容端点（智谱 https://open.bigmodel.cn/api/paas/v4、通义 https://dashscope.aliyuncs.com/compatible-mode/v1），用 ChatOpenAI(base_url=...) 也能打通，但 provider 专有字段可能不被提取或保留。
  • Claude 走统一入口，写法和 DeepSeek 一样是换个字符串；但要盯 max_tokens——官方迁移指南的 Breaking changes 里写了 langchain-anthropic 的默认值变化，结论是显式传，别依赖默认；logprobs 也不支持。
  • 通义的类默认走流式，ChatTongyi(model="qwen-plus") 之后拿到的就是流式结果；要做视觉用 qwen-vl-max。
  • 能力面各不同：工具调用、结构化输出、图像/音频输入的支持情况在这几家之间并不一致，换之前按各自官方集成页的能力表核一遍，别照抄 DeepSeek 的「一律 deepseek-chat」经验。

七、常见坑（官方明确限制/版本差异）

  1. 不传 checkpointer 却期待多轮记忆。messages 是每次调用传进去的；没有 checkpointer，上一轮不在状态里。
  2. thread_id 每次新建。用 uuid7() 每轮生成新 ID 等于每轮新会话；稳定 ID 应由业务给（会话 ID、用户+日期）。
  3. 把 user_id 当工具参数。应走 context_schema + runtime.context，否则模型可伪造。
  4. 指望框架自己限轮数。官方没有「最大轮数」基础参数，要靠 ModelCallLimitMiddleware / ToolCallLimitMiddleware。
  5. 子 Agent 不设 name。多 Agent 流式时无法区分来源，官方给的键是 lc_agent_name。

八、课后小结

  • create_agent 返回编译好的图，中间件钩子跑在图里；
  • 循环 = model → (有 tool_call?) tools → model …，退出条件是「模型本轮无 tool_call」；
  • 状态最小是 messages，要加字段就继承 AgentState 传 state_schema；
  • 多轮靠 checkpointer + 稳定 thread_id；
  • 身份类信息走 context_schema + context + runtime.context。

九、思考题

1、Agent 循环的终止条件是什么？为什么不在框架里写死「最多 N 轮」？

参考回答：终止条件是「这一轮模型没有给 tool_calls」。官方不写死轮数，因为合理轮数随任务差异极大；需要上限时用 ModelCallLimitMiddleware 显式配置，把策略交给使用者。

2、messages 与 checkpointer 各自负责什么，缺一个会怎样？

参考回答：messages 是本次调用状态的载体，checkpointer 负责跨调用持久化。只传 messages 不传 checkpointer = 每轮失忆；只配 checkpointer 不传 thread_id = 记忆没有归属，多个会话互相串。

3、工具为什么可能「多调一轮」？什么时候说明出问题了？

参考回答：模型拿到 ToolMessage 后需要再推理一次才能给最终答复，所以多一轮是正常的。异常信号是同一工具、同一参数被反复调用且结果相同——通常说明回灌内容没让模型看懂，或工具在静默失败。

4、context 与「把用户 ID 塞进 system_prompt」相比好在哪？

参考回答：context 是结构化、不可伪造、可被工具与中间件直接读取的数据；写进提示词只是文本，既会被模型改写，也会泄漏到日志与输出里。
