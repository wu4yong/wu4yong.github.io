05 工具定义与调用协议

模型只看到 schema 里的字段；ToolRuntime 这类注入参数在 schema 之外，由运行时补上｜依据官方 Tools 页自绘

版本不一致提示

  • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
  • 旧 0.x 用 @tool + InjectedState / InjectedStore 注解注入，v1 统一收敛到 ToolRuntime，写法不可混用；
  • 官方示例里的模型名（如 glm-5p2、gpt-6.1-sol）随 provider 更新，与写法无关。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 写一个模型能正确调用的工具：名字、描述、类型标注、默认值，各起什么作用；
  2. 会用 args_schema 表达复杂入参（Pydantic / JSON Schema），知道什么时候必须写；
  3. 分清「模型能填的参数」和「运行时注入的参数」——ToolRuntime 为什么不出现在 schema 里，它能拿到什么。

二、前置知识

  • 读完 LC03（content_blocks、tool_call 块）与 LC04（流式里的 tool_call_chunk）；
  • 会写 Python 函数、类型注解、dataclass；
  • 了解 Pydantic 的 BaseModel 与 Field（不熟也能跟，本书只用到 description 与 default）。

三、理论讲解（官方定义）

1. 最基本的定义：@tool

官方：「最简单的方式是用 @tool 装饰器。默认情况下，函数的 docstring 会成为工具的描述，用来帮助模型判断何时使用它。」

from langchain.tools import tool

@tool
def search_database(query: str, limit: int = 10) -> str:
    """Search the customer database for records matching the query.

    Args:
        query: Search terms to look for
        limit: Maximum number of results to return
    """
    return f"Found {limit} results for '{query}'"

官方加了两条硬要求：

  • 类型标注是必需的，它决定工具的输入 schema；
  • docstring 要「informative and concise」，模型靠它判断要不要调这个工具。

2. 名字与描述的定制

  • 自定义名字：@tool("web_search")，之后 search.name == "web_search"；
  • 自定义描述：@tool("calculator", description="Performs arithmetic calculations. Use this for any math problems.")。

官方明确建议工具名用 snake_case：web_search 而不是 Web Search。理由是「有些 provider 会拒绝带空格或特殊字符的名字」，用字母、下划线、连字符最稳。

3. 复杂入参：args_schema

官方给两种写法：Pydantic 模型、JSON Schema。Pydantic 示例（完整保留官方字段语义）：

from pydantic import BaseModel, Field
from typing import Literal
from langchain.tools import tool

class WeatherInput(BaseModel):
    """Input for weather queries."""
    location: str = Field(description="City name or coordinates")
    units: Literal["celsius", "fahrenheit"] = Field(default="celsius", description="Temperature unit preference")
    include_forecast: bool = Field(default=False, description="Include 5-day forecast")

@tool(args_schema=WeatherInput)
def get_weather(location: str, units: str = "celsius", include_forecast: bool = False) -> str:
    """Get current weather and optional forecast."""
    ...

判断标准很简单：字段少、类型简单 → 直接靠函数签名；有枚举、有范围约束、要写字段说明 → 用 args_schema。Literal 与 Field 的 description 会进 schema，这是模型唯一能看到「这个字段该怎么填」的说明位。

4. 注入参数：ToolRuntime

官方有一整节「Access context」。核心结论：给函数签名加 runtime: ToolRuntime，调用时由运行时自动注入，该参数不会出现在发给模型的 schema 里。官方原话是「the parameter is not included in the tool schema sent to the model」。

读状态的最小例子：

from langchain.tools import tool, ToolRuntime

@tool
def get_message_count(runtime: ToolRuntime) -> str:
    """Get the number of messages in the conversation."""
    return f"There are {len(runtime.state['messages'])} messages."

5. 工具改状态：返回 Command

官方在「Update state」一节给了硬要求：要更新 Agent 状态，用 Command，并且必须在 update 里带一条 ToolMessage，让模型看到这次调用的结果：

from langgraph.types import Command

return Command(update={
    "user_name": new_name,
    "messages": [ToolMessage(content=f"User name set to {new_name}.", tool_call_id=runtime.tool_call_id)],
})

官方还提醒：多个工具可能并行调用，同一个状态字段被并发更新时要定义 reducer 决定冲突合并方式。

四、原理拆解

工具不是函数调用，是「协议往返」：模型只能看到 schema，结果必须变成 ToolMessage 才能回到对话里｜自绘

把工具想成一张填好的表单：

  • 函数签名 / args_schema 是表单的格子，模型只能往格子里填；
  • docstring 与字段 description 是表格说明，模型读它才知道格子该填什么；
  • ToolRuntime 是你（服务端）预先盖好的章，模型看不见，也不该看见；
  • 返回的字符串 / Command 是处理结果，必须以 ToolMessage 的形态回到对话，模型才会「知道」工具干了什么。

所以工具出问题基本落在三处：描述不清（模型选错工具或不填参数）、schema 太松（模型乱填）、返回不对（结果没进消息流，模型下一轮当作没发生）。

五、场景说明

  1. 查数类（query_db、search_docs）：query + limit，用签名就够；
  2. 写操作类（send_email、write_file）：字段要严格，枚举与必填都写进 args_schema，后面配 HITL 中间件做人工确认；
  3. 需要身份（get_my_orders）：不接收 user_id 参数，从 runtime.context 取，避免模型伪造；
  4. 需要上下文（summarize_so_far）：从 runtime.state["messages"] 读历史，而不是让模型把历史再贴一遍。

步骤 4：最小可运行代码

存成 tool_demo.py，uv run tool_demo.py。

from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.messages import HumanMessage, SystemMessage
from langchain.tools import tool

@tool("get_order_status")
def get_order_status(order_id: str, with_logistics: bool = False) -> str:
    """查询订单状态。

    Args:
        order_id: 订单号，形如 SO-2026-0001
        with_logistics: 是否附带物流轨迹
    """
    # 真实项目这里换成数据库/接口调用
    base = f"订单 {order_id} 状态：已发货"
    return base + "；物流：成都→乐山，今日派送" if with_logistics else base

load_dotenv()
model = init_chat_model("openai:gpt-5-nano")

messages = [
    SystemMessage("你是订单客服，需要查单时调用 get_order_status。"),
    HumanMessage("帮我看下 SO-2026-0001 到哪了，要看物流。"),
]
ai = model.invoke(messages)          # 第一轮：模型决定调用哪个工具
print(ai.tool_calls)                 # 看模型填的参数

for call in ai.tool_calls:           # 本地执行工具（真实项目里由 Agent 循环做）
    result = get_order_status.invoke(call)   # 传整个 tool_call，工具自己取 args
    print(type(result), result.content)

步骤 5：预期输出

[{'name': 'get_order_status', 'args': {'order_id': 'SO-2026-0001', 'with_logistics': True}, 'id': 'call_xxx', 'type': 'tool_call'}]
<class 'langchain.messages.ToolMessage'> 订单 SO-2026-0001 状态：已发货；物流：成都→乐山，今日派送

模型给的 args 会因模型与措辞不同略有差别，但字段名应与 schema 一致；id 每次不同。

步骤 6：验证是否成功

  • ai.tool_calls 非空且 name 等于 get_order_status，说明名字与描述起到了作用；
  • args 里出现 order_id 与 with_logistics，说明签名与默认值被正确转成 schema；
  • get_order_status.invoke(call) 返回 ToolMessage 而不是抛异常，说明这条「schema → call → ToolMessage」的协议闭环成立。

差异集中在「模型怎么初始化」这一层，往下 invoke / stream / bind_tools 的链路基本不变：

  • 智谱、通义不进统一入口。init_chat_model 认不出 zhipuai / tongyi 这两个 provider 名，要直接实例化 ChatZhipuAI、ChatTongyi（两个类都在 langchain-community 里）；两家也都提供 OpenAI 兼容端点（智谱 https://open.bigmodel.cn/api/paas/v4、通义 https://dashscope.aliyuncs.com/compatible-mode/v1），用 ChatOpenAI(base_url=...) 也能打通，但 provider 专有字段可能不被提取或保留。

  • 通义的类默认走流式，ChatTongyi(model="qwen-plus") 之后拿到的就是流式结果；要做视觉用 qwen-vl-max。

七、常见坑（官方明确限制/版本差异）

  1. 不写类型标注。官方明确「Type hints are required」，没有标注就没有输入 schema，模型无法构造参数。
  2. 描述写成「查询数据」。描述太泛，模型会在两个相似工具之间乱选；官方要求 informative and concise，把「查什么、什么时候用」写进去。
  3. 工具名带空格或中文。官方建议 snake_case，部分 provider 会直接拒绝。
  4. 把 user_id 当工具参数。模型可以伪造任意字符串；身份类信息走 runtime.context，官方在 Access context 一节就是这么示范的。
  5. 改状态却只返回字符串。用 Command(update=...) 且必须带 ToolMessage，否则模型看不到结果；并发更新同一字段时官方要求定义 reducer。

八、课后小结

  • @tool 用 docstring 当描述、类型标注当 schema，两者缺一不可；
  • 名字用 snake_case，可用 @tool("name", description=...) 覆盖；
  • 复杂入参用 args_schema（Pydantic / JSON Schema），枚举与约束写进字段；
  • ToolRuntime 参数由运行时注入，不进 schema；
  • 要改状态返回 Command，且 update 里必须有 ToolMessage。

九、思考题

1、为什么官方要求类型标注必需，而不是从 docstring 里猜类型？

参考回答：schema 要发给模型、还要做入参校验，必须是机器可读的结构；docstring 是自然语言，只能给模型当提示。用类型标注一次性产出 schema 与校验规则，避免两套描述不一致。

2、ToolRuntime 参数不出现在 schema 里，这个设计解决了什么问题？

参考回答：它把「模型能决定的」和「运行时可信的」分开。用户 ID、会话、stream writer 这些不该由模型填，否则可被伪造或误填；运行时注入既安全，又不污染给模型看的表单。

3、工具描述写得含糊会怎样，怎么排查？

参考回答：模型会选错工具或漏填必填字段。排查方法是把 ai.tool_calls 打出来看 name 与 args：名字错了是描述问题，参数缺失是 schema 或描述里没写清字段含义。

4、工具执行完为什么必须返回 ToolMessage（或 Command 里带它）？

参考回答：对话只认消息。没有 ToolMessage，模型下一轮就看不到工具结果，会重复调用或凭空回答；tool_call_id 是它把结果与那次调用对上的唯一凭据。
