07 工具失败处理

失败不是一种，是三种；处理位置也不同：wrap_model_call、wrap_tool_call、handle_errors｜依据官方 Custom middleware 与 Tools 页自绘

版本不一致提示

  • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
  • 旧 0.x 用 handle_tool_error=True 或工具类里的 _handle_error，v1 收敛到中间件 wrap_tool_call，两套写法不兼容；
  • 官方示例里 ToolCallRequest 的导入路径为 langchain.tools.tool_node，随小版本可能调整，导入失败时以官方当前页面为准。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用 @wrap_tool_call 把工具异常转成 ToolMessage 回灌给模型，让 Agent 继续走而不是崩；
  2. 用 @wrap_model_call 做模型调用的有限重试，并且知道重试该放在哪一层；
  3. 识别「静默失败」——返回空字符串、返回 None、吞异常——为什么它比报错更危险，以及怎么改。

二、前置知识

  • 读完 LC05（@tool 与 ToolMessage）、LC06（handle_errors）；
  • 知道 Python 的 try / except，会写 Callable 作为参数；
  • 了解「中间件」这个词即可，细节在 LC09、LC10。

三、理论讲解（官方定义）

1. 官方的标准解法：wrap_tool_call 转异常

官方 Tools 页在「Tool errors」一节给的示例，就是本讲主线：用 wrap_tool_call 中间件包住工具执行，捕获异常后返回一条 ToolMessage。

from collections.abc import Callable
from langchain.agents import create_agent
from langchain.agents.middleware import wrap_tool_call
from langchain.messages import ToolMessage
from langchain.tools.tool_node import ToolCallRequest

@wrap_tool_call
def handle_tool_errors(
    request: ToolCallRequest,
    handler: Callable[[ToolCallRequest], ToolMessage],
) -> ToolMessage:
    """Convert tool exceptions into ToolMessages the model can handle."""
    try:
        return handler(request)
    except Exception as e:
        return ToolMessage(
            content=f"Tool error: Please check your input and try again. ({e})",
            tool_call_id=request.tool_call["id"],
        )

agent = create_agent(model=..., tools=[...], middleware=[handle_tool_errors])

三个要点：

  • 签名固定为 (request, handler)，返回值是 ToolMessage；
  • handler(request) 才是真正执行工具，你不调它，工具就不会跑（可以据此做短路）；
  • 异常必须变成消息，且必须带 tool_call_id，模型才能把错误与那次调用对上。

2. 两种重试，位置不同

官方 Custom middleware 页把钩子分成两族：

钩子
时机
适合放什么
before_agent / after_agent
每次调用前后各一次
初始化、收尾统计
before_model / after_model
每次模型调用前后
改提示、限流、日志、early exit
wrap_model_call
包住每次模型调用
重试、缓存、降级、改 system prompt
wrap_tool_call
包住每次工具调用
工具重试、异常转消息、参数清洗

也就是说：模型调用的重试放 wrap_model_call，工具调用的重试放 wrap_tool_call，两者不要混在一起。把工具重试塞进模型重试里，会让整个多步流程从头再跑一遍，成本翻倍。

官方给的 wrap_model_call 重试写法：

@wrap_model_call
def retry_model(request: ModelRequest, handler: Callable[[ModelRequest], ModelResponse]) -> ModelResponse:
    for attempt in range(3):
        try:
            return handler(request)
        except Exception as e:
            if attempt == 2:
                raise
            print(f"Retry {attempt + 1}/3 after error: {e}")

3. 执行顺序（决定重试覆盖范围）

官方在 Execution order 一节写明：before_* 按注册顺序执行，after_* 逆序执行，wrap_* 是嵌套——第一个中间件包住后面所有。所以：

  • 想「外层重试、内层记录」：把重试中间件放列表前面；
  • 想「先清洗参数再执行」：清洗的 wrap_tool_call 要排在重试外层，否则重试会带着脏参数反复打。

4. handle_errors 属于第三层

LC06 讲的 ToolStrategy(handle_errors=...) 只管「结构化校验失败」，不处理工具抛异常。三层分工是：

失败类型
处理位置
处理方式
模型调用超时 / 5xx / 429
wrap_model_call
有限重试，401/404 不重试
工具内部异常
wrap_tool_call
转 ToolMessage，或按异常类型重试
结构化输出校验失败
ToolStrategy.handle_errors
让模型按 schema 重出

5. 错误信息怎么写才有用

官方示例文案是 Tool error: Please check your input and try again. ({e})——注意它既说「错了」，也说「下一步该干什么」。只写 Error 的文案，模型只会原样再调一次；写「参数 order_id 格式应为 SO-年份-序号」的文案，模型第二次就能纠正。

四、原理拆解

异常沿调用栈往上走，最先接住它的中间件决定后续一切｜自绘

把 Agent 想成一个办事窗口：

  • 工具是窗口里的办事员，办不成会喊一声（抛异常）；
  • wrap_tool_call 是窗口前的接待员，听到喊声就写一张条子（ToolMessage）递给客户（模型），客户据此改主意；
  • wrap_model_call 是电话交换台，客户连着打不通就重拨几次，但不会替办事员办事；
  • handle_errors 是质检，只查客户交上来的表格格式对不对。

三层各管一段，混用就会出现「办不成 → 重拨电话 → 再办一次 → 还是办不成」的空转。

五、场景说明

  1. 外部 API 不稳（HTTP 429 / 502）：wrap_tool_call 里按异常类型重试 2 次，仍失败就回灌「上游限流，请稍后再试」；
  2. 参数格式错（订单号写错）：不重试，直接回灌「格式应为 SO-2026-0001」，让模型自己改；
  3. 写操作失败（发邮件失败）：回灌明确状态，避免模型「以为发出去了」继续下一步；
  4. 模型调用抖动：wrap_model_call 重试，注意官方口径——401/404 这类客户端错误不重试。

步骤 4：最小可运行代码

存成 tool_failure.py，uv run tool_failure.py。

from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.agents.middleware import wrap_tool_call
from langchain.messages import ToolMessage
from langchain.tools import tool
from langchain.tools.tool_node import ToolCallRequest
from collections.abc import Callable
import re

@tool
def get_order(order_id: str) -> str:
    """按订单号查询订单，订单号形如 SO-2026-0001。"""
    if not re.fullmatch(r"SO-\d{4}-\d{4}", order_id):
        # 故意的「坏输入」：让工具抛异常，由中间件接住
        raise ValueError(f"订单号格式应为 SO-年份-序号，收到：{order_id}")
    return f"订单 {order_id}：已发货"

@wrap_tool_call
def tool_guard(request: ToolCallRequest, handler: Callable[[ToolCallRequest], ToolMessage]) -> ToolMessage:
    try:
        return handler(request)
    except ValueError as e:          # 参数类错误：不重试，告诉模型怎么改
        return ToolMessage(content=f"参数不合法，请修正后重调：{e}", tool_call_id=request.tool_call["id"])
    except Exception as e:           # 其他错误：回灌，不让 Agent 崩
        return ToolMessage(content=f"工具执行失败：{type(e).__name__}: {e}", tool_call_id=request.tool_call["id"])

load_dotenv()
agent = create_agent(
    model="openai:gpt-5-nano",
    tools=[get_order],
    middleware=[tool_guard],
)

result = agent.invoke({"messages": [{"role": "user", "content": "查一下订单 12345 到哪了"}]})
print(result["messages"][-1].text)

步骤 5：预期输出

订单号格式不对，需要形如 SO-2026-0001 的格式，请提供正确订单号。

模型会先调 get_order("12345")，被 tool_guard 接住并回灌「参数不合法」，随后自己组织一句道歉/追问。若你给的是合法订单号，输出会变成该订单的物流状态。

步骤 6：验证是否成功

三条判据：

  1. 全程没有抛出 ValueError 到终端，说明异常被中间件接住了；
  2. messages 里能看到一条 ToolMessage（内容以「参数不合法」开头），说明回灌成功；
  3. 模型第二轮没有再拿同样的错参数去重试，说明错误文案起到了纠偏作用。

七、常见坑（官方明确限制/版本差异）

  1. ToolMessage 忘带 tool_call_id。模型无法把错误对应到那次调用，会重复调用或直接放弃。
  2. 捕获了异常却 return None。wrap_tool_call 的返回类型是 ToolMessage；返回 None 会让后续节点拿到空值，表现为「模型当作没发生」。
  3. 把重试写在工具函数内部。工具内部 sleep 重试会占住执行槽，且外层中间件看不到真实失败次数；官方范式是重试放在 wrap_* 层。
  4. 401 / 404 也重试。官方在 Models 的 Connection resilience 一节明确：客户端错误不重试；模型层重试也要遵守这条，否则只是把账单刷大。
  5. 静默失败。工具返回空字符串或 "ok" 掩盖失败，模型会以为成功并继续下一步——这类 bug 在日志里最难看，因为「什么都没报错」。

八、课后小结

  • 工具异常的标准出口是 wrap_tool_call + ToolMessage + tool_call_id；
  • 模型调用重试放 wrap_model_call，工具重试放 wrap_tool_call，不要混层；
  • wrap_* 是嵌套执行，顺序决定谁接住异常；
  • handle_errors 只管结构化校验，不管工具异常；
  • 错误文案要写「错在哪 + 下一步怎么改」，否则模型只会原样重试。

九、思考题

1、wrap_tool_call 的 handler 不调用会怎样？

参考回答：工具根本不会执行，中间件直接返回自己构造的 ToolMessage 就是短路。这既是风险也是能力：可以做「参数不合规直接打回」「命中缓存直接返回」这类优化，但要清楚自己在跳过真实执行。

2、为什么工具重试不能放在 wrap_model_call 里？

参考回答：wrap_model_call 包的是整次模型调用，重试意味着整轮「模型决策 → 工具执行」重来，已经成功的步骤会被重复执行、成本翻倍；工具级失败应该只重跑那次工具。

3、工具失败时返回「空字符串」为什么是最差实践？

参考回答：空字符串是合法返回值，模型无法区分「查到了但没内容」和「查失败了」，会继续按成功路径推理；正确做法是回灌明确的失败内容（含错误类型与修正建议），让模型进入纠错分支。

4、before_model 与 wrap_model_call 都能改提示，选哪个？

参考回答：只改内容、不需要控制执行次数用 before_model；需要重试、缓存、短路、或包住 handler 做前后处理用 wrap_model_call。判断依据是「要不要控制 handler 被调用几次」。
