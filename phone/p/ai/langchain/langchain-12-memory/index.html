12 短期与长期记忆

同一份代码，换一个存储后端，记忆的寿命就从「一次会话」变成「永久」｜依据官方 Short-term / Long-term memory 页自绘

版本不一致提示

  • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
  • 官方示例模型名随 provider 更新，checkpointer / store 的接口不受影响；
  • PostgresSaver、PostgresStore 来自 langgraph-checkpoint-postgres，官方标注为可选依赖，装在哪个版本以官方安装页为准。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 分清两层记忆：checkpointer（thread 内、短期）与 store（跨 thread、长期），并说清各自的键结构；
  2. 会写：checkpointer=InMemorySaver() + 稳定 thread_id 记会话；store.put/search 记画像；工具里用 runtime.store 读写；
  3. 知道生产上该换成什么后端（Postgres / SQLite / Redis / MongoDB），以及「记忆该由谁来写」的取舍。

二、前置知识

  • 读完 LC08（create_agent 与 checkpointer）、LC11（上下文与持久改动）；
  • 知道 thread_id 是会话的主键；
  • 了解 ToolRuntime 注入参数不进模型 schema（LC05）。

三、理论讲解（官方定义）

1. 两层记忆的定义

官方对短期记忆的说法：让应用记住单个 thread / 会话内的交互。thread 像一封邮件串起多条消息；会话历史是最常见的短期记忆形态，用 checkpointer 把 state 持久化到数据库或内存，thread 随时可恢复。

对长期记忆：跨会话、跨 thread 存取，建立在 LangGraph store 之上，数据是「按 namespace + key 组织的 JSON 文档」。

2. 短期记忆的关键点

  • 只需在 create_agent 里传 checkpointer；
  • 状态在每次 invoke 或每个步骤（如工具调用）完成时更新，步骤开始时读取；
  • state_schema 可扩展 AgentState，加自己的字段（如 user_id、preferences），并通过 invoke 传入。

官方还点明一个现实问题：即便模型支持超长上下文，长上下文本身也会让模型「分心」，并且更慢更贵——所以要裁剪、删除、摘要（LC11 已讲）。

3. 长期记忆的键结构

namespace = ("users",)     # 类似文件夹，常带 user_id / org_id
key = "user_123"           # 类似文件名
store.put(namespace, key, {"name": "John Smith", "language": "English"})

store.get(namespace, key) 返回带 value 与元数据的 StoreValue；store.search(namespace, filter={...}, query="...") 支持按内容过滤 + 向量相似度检索（需要给 store 配 IndexConfig(embed=..., dims=...)）。

4. 工具里的读写

  • 读：@tool def get_user_info(runtime: ToolRuntime[Context])，runtime.store.get(("users",), runtime.context.user_id)；
  • 写：同样的 runtime.store.put(...)，官方示例用 TypedDict 定义给模型看的字段结构；
  • 前提：create_agent(..., store=store) 必须传，否则 runtime.store 是 None。

5. 生产环境

官方给的替换路径很直接：短期用 PostgresSaver.from_conn_string(DB_URI) + checkpointer.setup()；长期用 PostgresStore.from_conn_string(DB_URI) + store.setup()。内存版（InMemorySaver / InMemoryStore）明确是给开发和测试用的。

四、原理拆解

两层记忆的分界线只有一条：换个 thread_id，短期记忆就查不到；换个 namespace，长期记忆还能读到｜自绘

三条判断线，能解决绝大多数「记忆不生效」的问题：

  1. thread_id 决定「这是不是同一段对话」。同一个 id 连续 invoke 就是多轮；换 id 就是新会话，即便用户是同一个人。
  2. namespace 决定「这份记忆属于谁」。官方建议把 user_id / org_id 放进 namespace；只放 key 会把不同租户的数据混在一个目录里。
  3. runtime.store 是否存在，取决于你有没有把 store 传给 create_agent。忘了传，工具里 assert runtime.store is not None 会直接炸。

再记一条官方原话的含义：短期记忆存在 state 里，所以它能被「上下文工程」改写（裁剪、摘要都作用在 state 上）；长期记忆存在 store 里，中间件的裁剪动不到它——想让记忆免于被压掉，就落 store。

五、场景说明

  1. 多轮客服：thread_id 用会话 id，短期记忆装本次对话；用户画像落 store，跨会话复用；
  2. 个人助手：store.put(("preferences",), user_id, {...}) 记写作风格、常用地址、禁用话题；
  3. 团队协作：namespace 用 (org_id, "shared") 存团队级知识，(org_id, user_id) 存个人偏好；
  4. 合规要求可追溯：把关键决策写进 store 并保留时间戳（store 的 value 是任意 JSON），便于审计。

步骤 4：最小可运行代码

存成 memory_demo.py，uv run memory_demo.py。

from dataclasses import dataclass
from dotenv import load_dotenv
from langchain.agents import create_agent
from langchain.tools import tool, ToolRuntime
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore

@dataclass
class Context:
    user_id: str

class UserInfo(TypedDict):
    nickname: str
    city: str

@tool
def save_profile(user_info: UserInfo, runtime: ToolRuntime[Context]) -> str:
    """保存用户资料。当用户主动告知昵称或城市时调用。"""
    assert runtime.store is not None
    runtime.store.put(("users",), runtime.context.user_id, dict(user_info))
    return "资料已保存"

@tool
def load_profile(runtime: ToolRuntime[Context]) -> str:
    """读取用户资料。回答涉及用户个人信息前先调用。"""
    assert runtime.store is not None
    item = runtime.store.get(("users",), runtime.context.user_id)
    return str(item.value) if item else "没有历史资料"

load_dotenv()
store = InMemoryStore()
agent = create_agent(
    model="openai:gpt-5-nano",
    tools=[save_profile, load_profile],
    store=store,
    context_schema=Context,
    checkpointer=InMemorySaver(),
)
ctx = Context(user_id="u_001")

# 12 短期与长期记忆
c1 = {"configurable": {"thread_id": "chat-A"}}
agent.invoke({"messages": [{"role": "user", "content": "我叫阿勇，常驻成都"}]}, config=c1, context=ctx)

# 12 短期与长期记忆
c2 = {"configurable": {"thread_id": "chat-B"}}
r = agent.invoke({"messages": [{"role": "user", "content": "帮我查一下我的资料"}]}, config=c2, context=ctx)
print("会话B回复:", r["messages"][-1].text)
print("store 直读:", store.get(("users",), "u_001").value)

步骤 5：预期输出

会话B回复: 你的资料：昵称 阿勇，城市 成都。
store 直读: {'nickname': '阿勇', 'city': '成都'}

会话 B 是全新 thread_id，短期历史为空；能答出资料，说明走的是 store。

步骤 6：验证是否成功

  • 把 c2 改成同一个 thread_id（chat-A）再跑，模型不需要调工具也能凭历史回答——这是短期记忆在起作用；
  • 临时删掉 store=store 参数，工具里的 assert 会抛错，说明 store 必须显式传入；
  • 换 user_id 为 u_002 再跑，读到「没有历史资料」，说明 namespace + key 的隔离有效。

七、常见坑（官方明确限制/版本差异）

  1. 以为换了 thread_id 记忆就没了。短期记忆确实没了；但 store 仍能读到——搞混这两层，会误判「记忆丢失」。
  2. 用 InMemorySaver 上线。官方明确它是开发用的，进程重启即失；生产换 Postgres / SQLite。
  3. namespace 不带 user_id。多个用户共用一个 namespace + key，会互相覆盖（官方示例特意把 user_id 放进 namespace）。
  4. store 写入不做去重。同名 key 反复 put 是覆盖语义，想保留历史要自己设计多 key 或版本字段（官方未给默认策略）。
  5. 工具里忘记 assert runtime.store is not None。忘了传 store 时报的是 NoneType 错误，排查成本高；显式断言能立刻定位。

八、课后小结

  • 短期=thread 内，靠 checkpointer + thread_id；长期=跨 thread，靠 store + namespace/key；
  • state_schema 扩展自定义字段，context_schema 传身份；
  • 工具读写长期记忆：runtime.store.get/put/search，前提是 create_agent(store=...)；
  • 生产换 Postgres（Saver / Store 各一个包），内存版只用于开发；
  • 想让记忆免于被上下文裁剪，就落 store。

九、思考题

1、checkpointer 和 store 都能「记住」，区别到底是什么？

参考回答：作用域与键不同。checkpointer 按 thread_id 存整份图状态（含消息历史），只在同一 thread 内可读；store 按 namespace+key 存 JSON 文档，跨 thread 可读。前者是「这段对话的过程」，后者是「这个人的事实」。

2、为什么短期记忆能被 SummarizationMiddleware 压缩，而 store 里的记忆不会？

参考回答：摘要中间件作用于 state["messages"]；store 是另一个存储，中间件不碰它。这也正是把关键事实落 store 的理由——它不会因为上下文压缩而消失。

3、多租户场景，namespace 应该怎么设计？

参考回答：至少两级：(org_id, user_id) 存个人数据，(org_id, "shared") 存组织共享数据；这样既隔离租户，又能做组织级共享，还能用 store.search 在单层内做过滤检索。

4、生产上要同时换 PostgresSaver 和 PostgresStore 吗？

参考回答：看你要哪种记忆。只要多轮会话，换 Saver 就够；要跨会话画像，再上 Store。两者都来自 langgraph-checkpoint-postgres，但都是独立对象，各自 setup() 建表。
