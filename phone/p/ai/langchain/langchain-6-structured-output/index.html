06 结构化输出：response_format 与两种策略

两条策略的终点一致：agent.invoke(...)["structured_response"]；差别在「谁保证格式」｜依据官方 Structured output 页自绘

版本不一致提示：

  • 本篇基线是 LangChain v1（1.x）+ Python 3.13，官方示例环境是 Python 3.11，仅解释器版本不同；
  • ProviderStrategy.strict 需要 langchain>=1.2；response_format 走 profile 动态判断需要 langchain>=1.1，低于该版本要手工设 profile；
  • 官方示例模型名（如 gpt-6.1-sol）随 provider 更新，写法不受影响。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用 create_agent(..., response_format=Schema) 拿到可校验的结构化结果，而不是让模型「尽量输出 JSON」；
  2. 说清 ProviderStrategy 与 ToolStrategy 的差别、自动选择规则，以及什么时候必须显式指定；
  3. 会配 handle_errors，让校验失败变成一次有限重试，而不是抛异常打断流程。

二、前置知识

  • 读完 LC05（schema 思维与 args_schema）；
  • 会写 Pydantic BaseModel 与 Field；本讲也用到 dataclass、TypedDict；
  • 知道「工具调用」的大致过程（LC05 的协议闭环）。

三、理论讲解（官方定义）

1. response_format 的四种取值

官方：「用 response_format 控制 Agent 如何返回结构化数据」，取值是：

  • ToolStrategy[SchemaT]：借工具调用来产出结构化输出；
  • ProviderStrategy[SchemaT]：用 provider 的原生结构化输出能力；
  • type[SchemaT]：只给 schema 类型，由 LangChain 自动选最优策略；
  • None：不显式要求结构化输出（默认）。

自动选择的规则，官方写得很明确：

  • 模型与 provider 支持原生结构化输出（官方点名 OpenAI、Anthropic(Claude)、xAI(Grok)，另在 Provider strategy 一节补了 Gemini）→ 用 ProviderStrategy；
  • 其他模型 → 用 ToolStrategy；
  • JSON Schema 字典必须显式包一层策略（ProviderStrategy(...) 或 ToolStrategy(...)），直接传给 response_format 不会被自动识别。

另外，自 langchain>=1.1 起，是否支持原生结构化输出是从模型的 profile data 动态读的；读不到时可以手工指定：

model = init_chat_model("...", profile={"structured_output": True})

2. 结果放在哪：structured_response

官方原话：结构化响应放在 Agent 最终状态里的 structured_response 键。也就是说：

result = agent.invoke({"messages": [{"role": "user", "content": "..."}]})
result["structured_response"]

Pydantic schema 返回校验过的实例，dataclass / TypedDict / JSON Schema 返回字典——这条差异官方在 Provider strategy 的 schema 说明里逐项写明。

3. ProviderStrategy 的两个参数

官方给的类定义是 ProviderStrategy(schema, strict=None)：

  • schema：Pydantic 模型、dataclass、TypedDict 或 JSON Schema（JSON Schema 要求顶层有 title 与 description）；
  • strict：要求严格贴合 schema，部分 provider 支持（官方点名 OpenAI、xAI），该参数需要 langchain>=1.2，默认 None 即关闭。

4. ToolStrategy 的三个参数

ToolStrategy(schema, tool_message_content=None, handle_errors=True)：

  • schema 支持 Pydantic / dataclass / TypedDict / JSON Schema / Union 类型（联合类型时模型自己挑最合适的那一支）；
  • tool_message_content：结构化结果生成后回给模型的工具消息内容，不填则用默认展示；
  • handle_errors：校验失败时的处理策略，默认 True：
取值
行为
True
捕获所有错误，用默认文案提示模型重试
str
捕获所有错误，用你给的文案
type[Exception] / 元组
只捕获指定异常类型
Callable[[Exception], str]
自定义文案生成函数
False
不重试，异常直接抛出

5. 有工具时的额外条件

官方提醒：如果同时传了 tools，模型必须支持「工具 + 结构化输出」并用；否则两条约束会互相打架。

四、原理拆解

同一个 schema、两条路：原生 JSON 更稳但受 provider 限制，工具调用兜底通用但多一轮｜自绘

用填表打比方：

  • ProviderStrategy 是「官方模板打印机」——provider 直接把表单格式固化在 API 里，填出来的东西天然合规；
  • ToolStrategy 是「先让你填一张表，我再校验」——借工具调用把 schema 变成一次「提交表单」的动作，提交后 LangChain 再按 Pydantic 校验。

所以取舍很直白：

场景
选谁
理由
OpenAI / Anthropic / Gemini / xAI，格式第一
直接传 schema 类型（自动走 Provider）
少一轮交互，格式最稳
本地模型、开源模型
ToolStrategy
它们通常没有原生结构化输出
校验失败要重试、要自定文案
ToolStrategy(..., handle_errors=...)
只有它带重试开关

ProviderStrategy(schema, strict=True)

五、场景说明

  1. 信息抽取（简历、发票、合同）：字段固定、要落库，必须结构化；
  2. 分类与打标：Literal 限定取值，比让模型「输出正面/负面」稳得多；
  3. 工具参数中转：把「先让模型产出结构化意图，再根据意图路由」当成一个显式的阶段；
  4. 评测基线：结构化结果可直接做字段级 diff，比字符串比对可靠。

六、示例代码

步骤 1：环境准备

uv add "langchain[openai]" pydantic
# pip 等价：pip install -U "langchain[openai]" pydantic

步骤 2：凭证配置

同 LC01，OPENAI_API_KEY 放 .env。

步骤 3：导入

from pydantic import BaseModel, Field
from typing import Literal
from langchain.agents import create_agent
from langchain.agents.structured_output import ToolStrategy   # 需要显式指定策略时用

步骤 4：最小可运行代码

存成 structured_demo.py，uv run structured_demo.py。

from dotenv import load_dotenv
from pydantic import BaseModel, Field
from typing import Literal
from langchain.agents import create_agent
from langchain.agents.structured_output import ToolStrategy

class Ticket(BaseModel):
    """客服工单的结构化结果。"""
    category: Literal["退款", "物流", "质量", "其他"] = Field(description="工单分类")
    urgency: int = Field(description="紧急程度 1-5，5 最急", ge=1, le=5)
    summary: str = Field(description="一句话摘要，不超过 30 字")

load_dotenv()

# 强制走工具调用策略，便于在不同 provider 上复现同一行为
agent = create_agent(
    model="openai:gpt-5-nano",
    tools=[],
    response_format=ToolStrategy(Ticket, handle_errors="请按 schema 重新输出，字段缺失会被打回。"),
)

result = agent.invoke({
    "messages": [{"role": "user", "content": "我买的鞋穿两天开胶了，想退货，很急。"}]
})

print(type(result["structured_response"]))
print(result["structured_response"])

步骤 5：预期输出

<class 'pydantic.main.Ticket'>
category='质量' urgency=5 summary='新鞋穿两天开胶，要求退货'

具体分类与摘要措辞会因模型不同而不同，category 一定落在四个枚举值内，urgency 一定在 1–5 之间——这两点是 schema 在起作用。

步骤 6：验证是否成功

  • type(...) 是 Pydantic 实例（不是 str、不是 dict），说明走的是校验过的路径；
  • category 只出现枚举里的值，说明 Literal 生效；
  • 把用户输入换成一句无关的话（如「今天天气不错」），看是否仍返回结构体（多数会被归到「其他」或触发一次重试），据此确认 handle_errors 在什么情况下介入。

七、常见坑（官方明确限制/版本差异）

  1. 直接把 JSON Schema 字典塞给 response_format。官方明确：字典必须包在显式策略里，否则不会被识别成结构化输出的意图。
  2. 以为 strict 处处可用。官方点名只有部分 provider 支持，且 strict 参数要求 langchain>=1.2；不支持的 provider 传了不生效。
  3. 同时用工具又要求结构化输出，但模型不支持两者并用。官方写明这是硬条件，碰到就先去掉 tools 验证 schema 是否本身没问题。
  4. handle_errors=False 还想「自动纠正」。官方语义就是不重试、异常直接抛；要兜底就别关它。
  5. 拿 response 而不是 structured_response。结构化结果放在最终状态的 structured_response 键；去 messages[-1].content 里找，会拿到模型啰嗦的解释文本。

八、课后小结

  • response_format 四选一：ToolStrategy / ProviderStrategy / 直接给 schema 类型（自动选）/ None；
  • 支持原生结构化输出的 provider（OpenAI、Anthropic、Gemini、xAI）优先走 Provider；
  • 结果在 structured_response，Pydantic 给实例、其余给字典；
  • JSON Schema 字典必须显式包策略；
  • 校验失败的重试开关只有 ToolStrategy.handle_errors 提供。

九、思考题

1、为什么不直接让模型「输出 JSON 字符串」然后自己 json.loads？

参考回答：模型输出的字符串不保证是合法 JSON，也不保证字段齐、类型对；response_format 走的是 schema 约束加校验，失败还能按 handle_errors 重试，把「格式是否可信」从提示词技巧变成工程约束。

2、同一个 schema，ProviderStrategy 与 ToolStrategy 的结果有什么区别？

参考回答：结果类型一致（都落在 structured_response），差别在保证方式与成本：Provider 用 API 原生能力、通常一轮出结果但受 provider 限制；ToolStrategy 借一次工具调用提交表单，多一轮交互但通用，且带重试开关。

3、handle_errors 写成 False 适合什么场合？

参考回答：适合「宁可失败也不要瞎重试」的场合，例如写库前抽取关键字段、或已经把重试放到更外层（队列、任务重试）。此时异常直接抛出，便于上层做统一失败处理。

4、为什么官方强调 JSON Schema 字典要显式包策略？

参考回答：字典本身既可能是「结构化输出 schema」，也可能是普通工具参数，框架无法仅凭类型判断意图；显式策略把意图说明清楚，避免歧义。
