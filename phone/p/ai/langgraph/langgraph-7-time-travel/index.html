07 时间旅行、分叉与持久化强度

回放是「从旧点往后重跑」，分叉是「改旧点再往后重跑」，两者都不回滚原历史｜依据官方 Use time-travel / Checkpointers 页自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13，示例不调用模型，纯本地可跑；
  • durability 有三档："exit" / "async"（默认）/ "sync"，官方口径是「越靠后越慢但越不容易丢」；
  • update_state 不会回滚线程，它只是从指定检查点长出一条新分支，原分支的历史一直在；
  • 默认情况下子图继承父图的 checkpointer，只有编译时写 checkpointer=True 才有子图内部的检查点，才能玩到子图内部的时间旅行。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 会用 get_state_history 找历史检查点，用 invoke(None, snapshot.config) 做回放；
  2. 会用 update_state(..., as_node=...) 从某点分叉，并说清它为什么不叫「回滚」；
  3. 能按业务选 durability 三档，知道每档在崩溃时会丢什么。

二、前置知识

  • 读完 LG05，知道检查点、thread_id、get_state；
  • 读完 LG04，知道 super-step 是检查点的落点；
  • 知道 invoke 传 None 表示「接着跑」（LG05 那张四行表）。

三、理论讲解（官方定义）

1. 两种时间旅行

官方把它拆成两个动作：

  • Replay（回放）：从某个旧检查点重新执行后面的节点，用来复现或重试；
  • Fork（分叉）：在某个旧检查点上改状态再往后跑，用来试「如果当时改成这样就怎样」。

共同点：检查点之前的节点不重跑（结果已经存了）；检查点之后的节点全部重跑，包括模型调用、外部请求，以及 interrupt()（可能给出不同结果）。

2. 历史怎么读

for snap in graph.get_state_history(config):
    print(snap.next, snap.config["configurable"]["checkpoint_id"])

get_state_history 返回 逆序：最新的在前。每个 StateSnapshot 带 values / next / config / metadata / tasks。要找「跑 write_joke 之前」的那一条，就看 snap.next == ("write_joke",)。

3. 回放 vs 分叉的调用差别

动作
调用
效果
回放
invoke(None, snap.config)
从这条检查点往后重跑，不改状态
分叉
update_state(...) 拿到新 config，再 invoke(None, ...)

续跑
invoke(None, config)

4. as_node 什么时候必须写

update_state 默认会推断这次更新「像是哪个节点写的」，然后从那个节点的后继继续。官方说推断在「从旧检查点分叉」时几乎总是对的，但有三种情况要显式指定：

  • 并行分支：同一轮多个节点都写过状态，推断不出来（InvalidUpdateError）；
  • 没有执行历史：新线程上预置状态（测试常用）；
  • 想跳过节点：把 as_node 写成更靠后的节点，让图以为它已经跑过。

5. durability 三档

档位
何时写检查点

"sync"
下一步开始前同步写完

钱、库存、幂等键这类不能重来的

6. 子图的时间旅行

默认子图继承父图 checkpointer，父图把整个子图当成一个 super-step：只能从「子图之前」回放，回放就从子图第一个节点重跑，回不到子图内部两点之间。

要让子图自己可回放，编译时 compile(checkpointer=True)，它就有了独立的历史与命名空间。

四、原理拆解

把线程想成一条 Git 分支，检查点就是 commit：

  • 回放＝git checkout <commit> 之后再跑一遍后续步骤（但不动已有 commit）；
  • 分叉＝在那个 commit 上 commit --amend 出新的一条，旧分支还在；
  • 「回滚」不存在——官方没有「删掉后面几个检查点」的 API，这也是 update_state 不叫 rollback 的原因。

三个关键判断：

  1. 回放会重算钱：后面节点的模型调用、外部请求都会真跑，测试时别拿生产 key 乱回放；
  2. 分叉会越长越多：每次 update_state 都新增一条历史，长会话里要配修剪策略；
  3. 选档位看「能不能重算」：能重算就用默认 async，不能重算就 sync，别为了性能赌崩溃概率。

五、场景说明

  1. 复现 bug：线上某轮结果不对，回放到那一步看中间状态；
  2. A/B 试写：同一份输入，分叉改 prompt / 改参数，对比两版输出；
  3. 人工修正后重跑：审批时人改了字段，从修正点分叉往前走，原记录留档；
  4. 崩溃恢复演练：把 durability 调成 "exit"，看进程被杀后能从哪继续。

步骤 4：最小可运行代码

存成 travel_demo.py，uv run travel_demo.py。

from typing_extensions import TypedDict, NotRequired
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

class State(TypedDict):
    topic: NotRequired[str]
    outline: NotRequired[str]
    post: NotRequired[str]
    runs: list[str]          # 记录每个节点被执行的次数，用来看谁被重跑

def pick_topic(state: State):
    return {"topic": "时间旅行", "runs": state.get("runs", []) + ["pick_topic"]}

def make_outline(state: State):
    return {"outline": f"提纲：{state['topic']}", "runs": state["runs"] + ["make_outline"]}

def write_post(state: State):
    return {"post": f"正文（{state['outline']}）", "runs": state["runs"] + ["write_post"]}

builder = StateGraph(State)
builder.add_node("pick_topic", pick_topic)
builder.add_node("make_outline", make_outline)
builder.add_node("write_post", write_post)
builder.add_edge(START, "pick_topic")
builder.add_edge("pick_topic", "make_outline")
builder.add_edge("make_outline", "write_post")
builder.add_edge("write_post", END)

graph = builder.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "tt-1"}}
graph.invoke({"runs": []}, cfg, version="v2")

history = list(graph.get_state_history(cfg))
print("历史条数 =", len(history))
for snap in history:
    print("step =", snap.metadata.get("step"), "next =", snap.next)

# 回放：找到「要跑 write_post 之前」的那一条
before_post = next(s for s in history if s.next == ("write_post",))
replay = graph.invoke(None, before_post.config, version="v2")
print("回放后 post =", replay.value["post"])
print("回放后 runs =", replay.value["runs"])

# 分叉：在同一条检查点上改 topic，再往后跑
fork_cfg = graph.update_state(before_post.config, values={"topic": "分叉主题"})
forked = graph.invoke(None, fork_cfg, version="v2")
print("分叉后 post =", forked.value["post"])
print("分叉后历史条数 =", len(list(graph.get_state_history(cfg))))

读法：回放没有重跑 pick_topic，只重跑了 write_post（runs 里只有它出现两次）；分叉用的也是同一条检查点，但 outline 保持旧值、topic 被改掉，因为 make_outline 在分叉点之后重跑了。

步骤 6：验证是否成功

  • 把回放换成 graph.invoke({}, cfg, version="v2")：这是「新输入」，从入口点重跑全部三个节点，runs 会比回放长得多；
  • 给 update_state 加 as_node="make_outline"：图会认为提纲是它写的，从 write_post 继续，runs 里不会再多一次 make_outline；
  • 把 InMemorySaver 换掉并让进程崩溃：在 durability="exit" 下中间检查点根本没有，恢复只能从头（写法 A）。

写法 A · 持久化强度：三档怎么试

# 每步同步落盘：最稳，最慢
graph.invoke({"runs": []}, cfg, version="v2", durability="sync")

# 默认档：下一步执行时异步写
graph.invoke({"runs": []}, cfg, version="v2")            # 等价于 durability="async"

# 只在退出时写：长跑最快，崩了一无所有
graph.invoke({"runs": []}, cfg, version="v2", durability="exit")

判断口径很简单：这一步产生的状态能不能重算。能重算就 async；不能（比如已经拿到支付幂等键）就 sync。

七、常见坑（官方明确限制/版本差异）

  1. 以为 update_state 会回滚。官方原话：它不回滚线程，只从指定点长出新分支，原历史保留。
  2. 并行分支上不写 as_node。同轮多个节点写过状态时推断失败，直接 InvalidUpdateError。
  3. durability="exit" 还指望崩溃不丢。中间状态根本没写，恢复只能从头。
  4. 回放时打生产 key。后面的节点会真跑，模型调用与外部请求都会重来一遍。
  5. 想在子图内部回放却没给子图 checkpointer。默认继承父图，父图把子图当一个 super-step。
  6. 改完节点名再恢复旧线程。历史检查点里的 next 记的是老名字，恢复会找不到。

八、课后小结

  • 时间旅行 = 回放（不改状态）+ 分叉（改状态长新枝），都从检查点往后重跑；
  • get_state_history 逆序返回，用 snap.next 定位「某节点之前」；
  • update_state 不是回滚，是分支；as_node 在并行/无历史/跳节点时必须显式；
  • durability 默认 async，钱与幂等键用 sync，可重算的长跑用 exit；
  • 子图要内部可回放，必须 compile(checkpointer=True)。

九、思考题

1、回放和「重新 invoke 一次同样的输入」差在哪？

参考回答：回放从中间的检查点起跑，之前的节点不重算、不会重复产生副作用；重新 invoke 是从入口点整条重跑，前面节点的外部副作用会再来一遍。

2、为什么 update_state 之后 outline 没变、post 变了？

参考回答：分叉点在第 2 步之后，make_outline 属于「之后的节点」，重跑时读到了新的 topic；pick_topic 在分叉点之前，不重跑，所以它写的东西保持原样。

3、durability="sync" 能不能完全避免重复副作用？

参考回答：不能。它只保证检查点及时落盘，节点本身仍是「至少一次」执行；重复副作用要靠幂等键在外部系统去重。

4、为什么官方不建议把时间旅行当「撤销」用？

参考回答：历史只增不减，没有删除检查点的公开 API；「撤销」会让人误以为原记录被抹掉，而实际只是多了一条分支。
