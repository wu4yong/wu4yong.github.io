12 多 Agent 拓扑

差别只在「谁决定下一步」；官方已停止维护 langgraph-supervisor 包｜依据官方 migrate-from-langgraph-supervisor 自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13 + LangChain 1.5（多 Agent 的入口在 LangChain 侧）；
  • 官方已明确：langgraph-supervisor 包不再积极维护，主管模式请改用「subagents 当工具」或子图节点自己接；
  • 三种拓扑在本篇分别落到 create_agent(tools=[...])、Command.PARENT、active_agent 上，代码都需要模型，跑通要 key；
  • 未接通真实 key 时，示例只保证结构正确，不保证输出内容。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 分清 supervisor / handoff / network 三种拓扑，知道各自「谁决定下一步」；
  2. 会用「专家当工具」写主管，用 Command.PARENT 做交接，用 active_agent 做自由转；
  3. 说清交接时最容易被忽略的事：上下文（messages）到底传多少。

二、前置知识

  • 读完 LG10，知道子图与 Command(graph=Command.PARENT)；
  • 读过 LC08（create_agent），知道 Agent 就是「模型 + 工具 + 循环」；
  • 知道 messages 是有 reducer 的 channel，追加而不是覆盖。

三、理论讲解（官方定义）

1. 先分清「多 Agent」解决什么问题

不是为了炫技，而是为了三件事：分工（不同 prompt/工具）、上下文隔离（别让一个 Agent 背着全公司的工具）、并行（互不依赖的子任务同时跑）。

官方把主流做法归成三类：subagents（子 Agent 当工具）、handoffs（交接）、skills/router（按能力或意图分流）。本篇用「拓扑」的视角讲前两类 + network。

3. 主管模式：专家当工具

官方迁移指南给的姿势：

billing_team = create_agent(model, tools=[call_refunds, call_invoices], system_prompt="...")

@tool("billing_team", description="处理账单、退款、发票")
def call_billing_team(query: str) -> str:
    result = billing_team.invoke({"messages": [{"role": "user", "content": query}]})
    return result["messages"][-1].text

supervisor = create_agent(model, tools=[schedule_event, call_billing_team], ...)

主管只看得到「高层工具」，看不到每张发票 API；子 Agent 的上下文是独立的，这是它最大的价值。

4. 交接模式：Command(goto=...)

专家 A 干到一半发现该 B 接手，就让工具返回 Command：

@tool
def transfer_to_sales(runtime: ToolRuntime) -> Command:
    """转给销售。"""
    return Command(goto="sales_agent", update={"active_agent": "sales_agent"})

goto 指向父图的节点名（子图里要写 graph=Command.PARENT）。update 里顺手把「当前谁在接待」记下来。

5. 自由转：active_agent + 条件边

def route(state) -> str:
    return state.get("active_agent") or "triage"

所有 Agent 都是节点，条件边读 active_agent 决定下一个；每个 Agent 都能把 active_agent 改成别人。灵活，但要靠 recursion_limit 和终止条件兜底。

四、原理拆解

把多 Agent 想成一家公司怎么派活：

  • 主管制：前台统一接单，派给专业组，专业组干完回前台（上下文天然收敛）；
  • 交接制：客户在专业组之间直接转，前台只做首访（上下文要显式挑，最容易传脏）；
  • 自由转：谁都能把客户推给别人（最容易出现「踢皮球」死循环）。

三个关键判断：

  1. 上下文是钱：整份 messages 往下传，token 成本随轮次平方增长；交接时必须裁剪或摘要；
  2. 职责边界写在 prompt 里不够，还要写在工具描述里——模型是靠 tool description 决定转不转的；
  3. 一定要有出口：network 拓扑不给终止条件，等于把 recursion_limit 当业务规则用。

五、场景说明

  1. 客服分流：售前/售后/账单三个专家，triage 首访后交接；
  2. 研究助手：主管 + 搜索专家 + 写作专家 + 校对专家，主管当工具调用；
  3. 多租户运维：按租户切 Agent，active_agent 控制权限边界；
  4. 单 Agent 拆不动时：工具超过 20 个、prompt 超过 3k token，就该拆。

存成 supervisor_demo.py，uv run supervisor_demo.py。

import os
from dotenv import load_dotenv
load_dotenv()

from langchain.agents import create_agent
from langchain.tools import tool
from langchain.chat_models import init_chat_model

model = init_chat_model("deepseek:deepseek-chat")

@tool
def refund_policy(order_id: str) -> str:
    """查询某订单的退款政策。"""
    return f"订单 {order_id}：7 天内可全额退，超过按 50% 折算。"

@tool
def invoice_lookup(order_id: str) -> str:
    """查询某订单的发票状态。"""
    return f"订单 {order_id}：发票已开具，抬头为个人。"

billing = create_agent(
    model,
    tools=[refund_policy, invoice_lookup],
    system_prompt="你是账单专家，只回答退款与发票问题，查不到就说查不到。",
)

@tool("billing_team", description="处理账单、退款、发票类问题；输入一句用户原话。")
def call_billing_team(query: str) -> str:
    result = billing.invoke({"messages": [{"role": "user", "content": query}]})
    return result["messages"][-1].text

supervisor = create_agent(
    model,
    tools=[call_billing_team],
    system_prompt="你是总台，先判断问题属于哪块，账单类转给 billing_team；其它类直接答。",
)

out = supervisor.invoke({"messages": [{"role": "user", "content": "订单 A-1001 能退吗？"}]})
print(out["messages"][-1].text)

步骤 5：预期输出

订单 A-1001：7 天内可全额退，超过按 50% 折算。

（具体措辞随模型波动；关键是总台把问题交给了 billing_team，由子 Agent 回答。）

步骤 6：验证是否成功

  • 打印 out["messages"]：会看到总台 → billing_team 工具调用 → ToolMessage → 总台收口，四段；
  • 换一个非账单问题（「今天几号」）：总台直接答，不会调 billing_team，说明路由生效；
  • 把 description 删掉再试：模型经常不知道什么时候该转，路由准确率明显下降——描述就是接口。

写法 A · 交接：Command.PARENT 直接跳父图节点

from langgraph.types import Command
from langchain.tools import ToolRuntime

@tool
def to_sales(runtime: ToolRuntime) -> Command:
    """转给销售专家。"""
    return Command(goto="sales", update={"active_agent": "sales"})

builder = StateGraph(State)
builder.add_node("triage", triage_agent)
builder.add_node("sales", sales_agent)
builder.add_edge(START, "triage")
builder.add_conditional_edges("triage", route_by_active)
builder.add_conditional_edges("sales", route_by_active)
graph = builder.compile(checkpointer=InMemorySaver())

route_by_active 读 state["active_agent"]，没有就回 triage。

写法 B · 自由转：active_agent + 上限

def route_by_active(state) -> str:
    nxt = state.get("active_agent")
    if state.get("resolved") or not nxt:
        return END
    return nxt

graph.invoke(inputs, {"configurable": {"thread_id": "t1"}, "recursion_limit": 12}, version="v2")

上限必须设：recursion_limit 是 network 拓扑唯一的安全阀。

七、常见坑（官方明确限制/版本差异）

  1. 还在用 langgraph-supervisor 包。官方已停止维护，迁移指南就一句话：改成 subagents 当工具。
  2. 交接时把整份 messages 往下传。token 会爆炸，且模型会被前一个 Agent 的口气带偏；要显式挑或摘要。
  3. 子图里 goto 写了父图节点名却没传 graph=Command.PARENT。会在子图内找不到节点，报错。
  4. network 拓扑不设上限。两个 Agent 互相推诿，跑到 GraphRecursionError 才停。
  5. 工具描述写「内部工具」。模型靠 description 决策，写不清就等于没接。
  6. 把多 Agent 当性能优化。它增加调用次数与延迟；单 Agent 能解决就别拆。

八、课后小结

  • 三种拓扑：主管（专家当工具）/ 交接（Command 跳转）/ 自由转（active_agent）；
  • 主管模式上下文天然隔离，交接模式最灵活也最容易传脏；
  • langgraph-supervisor 已停止维护，主管改用 subagents-as-tools；
  • 子图跳父图要 Command.PARENT；network 必须设 recursion_limit；
  • 工具描述就是路由接口，写不清模型就不会用。

九、思考题

1、主管模式里子 Agent 的上下文为什么不共享？

参考回答：子 Agent 用 invoke 单独跑，消息只进它自己的状态；主管只收到最后一句文本。这正是「上下文隔离」的收益，也是信息丢失的来源——需要什么就显式塞进 query。

2、交接模式下，为什么 update 里要写 active_agent？

参考回答：goto 只决定「下一步跑谁」，下一轮条件边需要知道「现在谁在接待」，否则会回到 triage 重新分诊，来回打转。

3、network 拓扑和 handoff 的本质区别是什么？

参考回答：handoff 是「我指定下一个是谁」，network 是「我改一个字段，路由规则决定下一个是谁」。前者点对点，后者有一个全局状态驱动。

4、多 Agent 一定会更贵吗？怎么控？

参考回答：会。每次交接至少多一次模型调用。控的办法：主管只给高层工具、交接时摘要上下文、设 recursion_limit、把可并行的用 Send 并行。
