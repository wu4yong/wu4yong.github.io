03 节点、边、Command 与 Send

边只决定「下一步是谁」；要同时改状态，才轮得到 Command｜依据官方 Graph API · Edges 自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13，示例用规则路由，不调模型，全部可离线验证；
  • 官方明确：同一个节点要么用静态边、要么用动态路由（条件边 / Command），混着写两路都会跑；
  • Command 除了 update / goto，还能带 graph=（跨子图）与 resume=（恢复中断），后两者分别在 LG10、LG06 用；
  • Send 的并行写回依赖 reducer 合并，没配 reducer 的 key 会互相覆盖（LG02）。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 分清三种边（固定边、条件边、条件入口）各自适用什么形状的流程，路由函数的返回值有哪几种合法形态；
  2. 判断什么时候该用 Command——「路由依赖本节点刚算出来的结果」时；
  3. 用 Send 做 map-reduce：条目数运行时才知道、要并行处理、结果靠 reducer 合回来。

二、前置知识

  • 读完 LG01、LG02：会写节点、知道 reducer 怎么合并；
  • 知道「一个节点有多条出边时，下一轮并行跑」；
  • 不需要模型，路由用规则写，先把控制流搞清楚。

三、理论讲解（官方定义）

顺序照官方 Graph API 的 Nodes → Edges → Send → Command 四节。

1. 节点函数的三种参数

官方说节点可以接：state、config（RunnableConfig，里面有 thread_id / tags）、runtime（Runtime，含 context、store、stream_writer）。函数签名按需取，不用全写。

省略节点名时用函数名：

builder.add_node(answer_node)        # 节点名就是 "answer_node"
builder.add_node("answer", answer_node)   # 显式命名，等价

路由函数只读 state，返回四种东西之一：节点名、END、名称列表（扇出到多个节点并行）、Send 对象列表。也可以再给一个「返回值 → 节点名」的映射字典，把路由函数的输出收敛成有限枚举。

3. 不能混用

官方写得很直接：对同一个节点，静态边和动态路由只能选一种。既 add_edge("a", "b") 又在 a 里返回 Command(goto="c")，两条路径都会跑。

4. Command：更新与路由合成一步

Command 的字段：update（状态更新）、goto（下一跳）、graph（父图目标）、resume（中断恢复值）。

什么时候必须用：下一跳取决于你这个函数里刚算出来的东西。典型是「分类节点自己算出类别，然后直接去对应处理节点」——用条件边也行，但要多写一个只读 state 的路由函数；Command 把它合成一步。

官方同时提醒：只路由不改状态时优先条件边，Command 是给「两件事一起做」的场景。

返回类型建议标上 Command[Literal["a", "b"]]，否则可视化里画不出边。

5. Send：map-reduce

Send(node, arg) 用在「同一个节点要按条目跑多次，条目数运行时才知道」的场景。从条件边返回一组 Send，每个 Send 指定目标节点和这一次的输入——注意它拿到的是你给的那份数据，不是整份 state。

并行写回同一个 key 时，靠 reducer 合并（LG02）。这也是 map-reduce 在 LangGraph 里的标准写法：split → N 个 worker → merge。

6. 边与 super-step 的关系

一个节点有多条出边、或路由函数返回名称列表时，这些目标在下一个 super-step 并行执行。所以「扇出」不是并发调用，是同一轮的多个分支（LG04 讲执行顺序）。

四、原理拆解

把图想成快递分拣中心：

  • 固定边是传送带，包裹只能往一个方向走；
  • 条件边是分拣员，看一眼面单（state）决定丢进哪个滑槽；
  • 条件入口是门口的分流：进来就先判断，走快速通道还是普通通道；
  • Command 是「分拣员自己就是打包员」：他刚封好箱（改了状态），顺手就把箱子推去对应滑槽，不需要另一个人再看一眼；
  • Send 是「一份清单上有 N 个包裹」：分拣员照着清单给每个包裹开一张工单，N 个工位同时处理，最后按规则汇总。

三个关键判断：

  1. 谁决定走向：边（或路由函数）、Command，二者取其一；
  2. 扇出是不是并行：是同一 super-step 的多分支，不是线程池；
  3. Send 的输入是定制的：每个 worker 只拿到自己的那一份，所以它适合「按条目拆分」而不是「共享上下文」。

五、场景说明

  1. 客服分流：退款 / 技术 / 人工三条路——条件边或 Command；
  2. 有缓存走缓存：条件入口，第一个节点就要判断；
  3. 批量处理（每份文档分别摘要）：Send + merge；
  4. 多 Agent 交接：Command(goto=..., graph=Command.PARENT)（LG12 展开）；
  5. 不该用的场景：只有一条固定路径时别硬套条件边，多写一个路由函数只是增加故障点。

步骤 4：最小可运行代码

存成 flow_demo.py，uv run flow_demo.py。三个图共用一套 state：

import operator
from typing import Annotated, Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command, Send

class Ticket(TypedDict):
    text: str
    route: str
    replies: Annotated[list[str], operator.add]

def refund(state: Ticket):    return {"route": "退款", "replies": ["已为你登记退款"]}
def technical(state: Ticket): return {"route": "技术", "replies": ["请重启后重试"]}
def human(state: Ticket):     return {"route": "人工", "replies": ["已转人工客服"]}

# 图 A：条件边 + 映射字典
def classify(state: Ticket) -> str:
    if "退款" in state["text"]:
        return "refund"
    if "报错" in state["text"] or "失败" in state["text"]:
        return "technical"
    return "human"

def build_with_edges():
    b = StateGraph(Ticket)
    b.add_node("classify", classify)
    b.add_node("refund", refund)
    b.add_node("technical", technical)
    b.add_node("human", human)
    b.add_edge(START, "classify")
    b.add_conditional_edges("classify", classify, {"refund": "refund", "technical": "technical", "human": "human"})
    for n in ("refund", "technical", "human"):
        b.add_edge(n, END)
    return b.compile()

# 图 B：同一逻辑改用 Command
def dispatch(state: Ticket) -> Command[Literal["refund", "technical", "human"]]:
    text = state["text"]
    if "退款" in text:
        return Command(update={"route": "退款"}, goto="refund")
    if "报错" in text or "失败" in text:
        return Command(update={"route": "技术"}, goto="technical")
    return Command(update={"route": "人工"}, goto="human")

def build_with_command():
    b = StateGraph(Ticket)
    b.add_node("dispatch", dispatch)
    for n, f in (("refund", refund), ("technical", technical), ("human", human)):
        b.add_node(n, f)
        b.add_edge(n, END)
    b.add_edge(START, "dispatch")
    return b.compile()

# 图 C：Send 并行
class Batch(TypedDict):
    items: list[str]
    replies: Annotated[list[str], operator.add]
    route: str

def split(state: Batch):
    return [Send("worker", {"item": x}) for x in state["items"]]

def worker(state: dict):
    return {"replies": [f"处理完：{state['item']}"]}

def merge(state: Batch):
    return {"route": f"共 {len(state['replies'])} 份"}

def build_fanout():
    b = StateGraph(Batch)
    b.add_node("split", lambda state: {})
    b.add_node("worker", worker)
    b.add_node("merge", merge)
    b.add_edge(START, "split")
    b.add_conditional_edges("split", split)     # 返回 Send 列表
    b.add_edge("worker", "merge")
    b.add_edge("merge", END)
    return b.compile()

if __name__ == "__main__":
    g1 = build_with_edges()
    print("条件边 :", g1.invoke({"text": "我要退款", "route": "", "replies": []}, version="v2").value)

    g2 = build_with_command()
    print("Command:", g2.invoke({"text": "接口一直报错", "route": "", "replies": []}, version="v2").value)

    g3 = build_fanout()
    print("Send    :", g3.invoke({"items": ["a.docx", "b.pdf", "c.txt"], "replies": [], "route": ""}, version="v2").value)

图 C 里 split 节点本身不写状态，只负责「被条件边调用后返回 Send 列表」。官方写法也是把 Send 从条件边里返回，split 的返回值会被忽略。

步骤 5：预期输出

条件边 : {'text': '我要退款', 'route': '退款', 'replies': ['已为你登记退款']}
Command: {'text': '接口一直报错', 'route': '技术', 'replies': ['请重启后重试']}
Send    : {'items': [...], 'replies': ['处理完：a.docx', '处理完：b.pdf', '处理完：c.txt'], 'route': '共 3 份'}

replies 的顺序在 Send 场景下不保证，只保证三条都在。

步骤 6：验证是否成功

  • 把图 A 的 add_conditional_edges 删掉、只留 add_edge("classify", "refund")：所有工单都进退款，说明走向完全由边决定；
  • 给 dispatch 同时加 b.add_edge("dispatch", "human")：技术工单会同时进 technical 和 human，replies 两条都在——这就是官方说的「混用两路都跑」；
  • 把 Ticket 的 replies 去掉 reducer 再跑图 C：只会剩一条，Send 的并行写回被覆盖。

写法 A · 把规则路由换成模型路由

规则路由换成模型时，只换 classify 这一个节点，边不动。用结构化输出让模型直接给出枚举（细节见 LC06）：

from typing import Literal
from pydantic import BaseModel
from langchain.chat_models import init_chat_model

class Route(BaseModel):
    route: Literal["refund", "technical", "human"]

model = init_chat_model("deepseek:deepseek-chat")
router = model.with_structured_output(Route)

def classify(state: Ticket) -> str:
    return router.invoke(f"判断这张工单该走哪条路：{state['text']}").route

add_conditional_edges 的映射字典不变——模型只是把「读 state 得到分支名」这件事做得更通用。

七、常见坑（官方明确限制/版本差异）

  1. 同一节点既加静态边又返回 Command：两路都跑，症状是「莫名其妙多执行了一个节点」。
  2. 路由函数返回不存在的节点名：运行时直接报错，且错误信息只给名字，不给候选列表。
  3. 在路由函数里改状态：路由函数的返回值被当成「去哪」，返回的 dict 不是状态更新。
  4. Send 的输入写成整份 state：每个 worker 拿到同一份数据，等于没拆；Send 第二个参数要放这一条的数据。
  5. Send 并行写回没 reducer：只剩最后一条（LG02）。
  6. Command 不标返回类型：可视化与部分校验拿不到目标节点，排错时很难看出边在哪。

八、课后小结

  • 节点可接 state / config / runtime 三种参数，省略名字时用函数名；
  • 边有三种形态，路由函数返回节点名 / END / 名称列表 / Send；
  • 同一节点只能选静态边或动态路由，不能混；
  • Command 用于「更新 + 路由一起做」，纯路由优先条件边；
  • Send 用于 map-reduce，并行写回靠 reducer。

九、思考题

1、什么情况下必须用 Command，用条件边做不到？

参考回答：下一跳依赖本节点算出来的中间结果、且这个结果不打算落进 state 时。用条件边就得把结果写进 state 再让路由函数读一遍，多一次状态往返，也更容易出现「路由函数与节点逻辑不一致」。

2、Send 和「一个节点有多条出边」有什么区别？

参考回答：多条出边是「固定的几个目标并行」；Send 是「同一个目标节点按运行时条目数跑 N 次，每次输入不同」。前者拓扑写在图上，后者拓扑由数据决定。

3、为什么路由函数不该改状态？

参考回答：它的返回值语义是「去哪」，不是「改什么」。要改状态就在节点里改，路由只读——这样图的可视化和调试都能对上。

4、混用静态边和 Command 会怎样，怎么排查？

参考回答：两条路径都会执行，表现为某个节点被额外触发、或同一轮出现两份结果。排查方式是先注释掉 add_edge，看行为是否只剩一条路径。
