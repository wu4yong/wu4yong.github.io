11 节点级可靠性：重试、超时、补偿

重试是「自动再试」、超时是「一次能跑多久」、补偿是「试完还不行怎么收场」｜依据官方 Fault tolerance / Configure nodes 自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13；timeout / error_handler 需要 langgraph ≥ 1.2，1.1 及以前只有 RetryPolicy；
  • timeout 只对 async 节点生效，给同步节点写 timeout 会在 compile() 时直接报错；
  • RetryPolicy 默认重试大多数异常，但官方列了一串「不重试」的内置异常（ValueError、TypeError、RuntimeError 等），别以为它会傻乎乎全试；
  • 重试是「至少一次」语义，不是「恰好一次」；重复副作用要靠幂等键在外部系统去重。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 会用 RetryPolicy 配重试次数、退避与异常白名单，知道默认哪些异常不重试；
  2. 会用 timeout（run_timeout / idle_timeout）掐住单次执行，知道它只管 async；
  3. 会用 error_handler 拿 NodeError 返回 Command 做补偿，并能用 request_drain() 优雅停机。

二、前置知识

  • 读完 LG03，知道 Command(goto=...) 能跳节点；
  • 读完 LG05，知道检查点只在 super-step 边界提交；
  • 读过一点 asyncio（async def / await）。

三、理论讲解（官方定义）

1. 三个可组合的机制

官方说得很清楚：节点失败（慢 API、网络抖动、未捕获异常）有三套机制可组合——

  • Retries：按异常类型与退避自动再试；
  • Timeouts：限制单次尝试的最长时间；
  • Error handling：重试全用完之后，跑一个恢复函数。

执行顺序固定：尝试失败 → 重试策略决定是否再试 → 重试耗尽后才跑 error handler。三者可以用 set_node_defaults 一次性配给所有节点。

retry_on 默认是 default_retry_on：重试大多数异常，但排除 ValueError、TypeError、ArithmeticError、ImportError、LookupError、NameError、SyntaxError、RuntimeError、ReferenceError、StopIteration、StopAsyncIteration、OSError 及其子类；对 requests / httpx 只重试 5xx。NodeTimeoutError 默认可重试。

3. 超时：两种掐法

from langgraph.types import TimeoutPolicy
builder.add_node("call_model", call_model, timeout=TimeoutPolicy(idle_timeout=30))
  • idle_timeout：多久没动静就掐（适合流式、慢慢吐 token 的调用）；
  • run_timeout：整次执行最多多久（适合有硬上限的批处理）；
  • 触发后抛 NodeTimeoutError，带 node / elapsed / kind（"idle" / "run"）/ 两个配置值。

关键限制：只支持 async 节点；重试时计时器归零，失败那次的写入会在下次尝试前清掉。

4. 补偿：error_handler

from langgraph.errors import NodeError

def refund(state: State, error: NodeError) -> Command:
    return Command(update={"status": f"已补偿：{error.error}"}, goto="finalize")

builder.add_node("charge", charge, retry_policy=RetryPolicy(max_attempts=3, retry_on=ConnectionError),
                 error_handler=refund)
  • 签名是 (state, error: NodeError)，可以再加 config；
  • 返回 state 或 Command 都行，Command 能同时改状态 + 选下一步；
  • 只在重试耗尽或异常不在重试名单时触发；
  • handler 自己不会再被 error_handler 兜住（防递归）。

5. 优雅停机：drain

from langgraph.runtime import RunControl
from langgraph.errors import GraphDrained

control = RunControl()
# 信号里：control.request_drain("sigterm")
try:
    graph.invoke(inputs, config, control=control)
except GraphDrained as e:
    print(e.reason)     # 检查点已存，稍后 invoke(None, config) 续跑

语义：协作式，只在 super-step 之间生效——正在跑的节点跑完、正在重试的重试完才停；子图的 drain 请求会冒泡到父图。

四、原理拆解

把节点想成外包工序，三道关就是三层保险：

  1. 重试：这一步是「可再试的」吗？（网络抖动 → 试；ValueError → 别试，纯属代码错）；
  2. 超时：这一步「一次最多给多久」？（卡住的下游要能被掐断，否则整个图陪着等）；
  3. 补偿：试完还不行，「账怎么平」？（退款、置失败态、转人工）。

三个关键判断：

  1. 重试不带事务：失败那次的写入在检查点层面会被丢弃（检查点只在轮末提交），但外部副作用不会回滚；
  2. 幂等键必须来自已持久化的状态，不能在节点里现生成——重试会生成新键，去重就失效；
  3. drain 不是 kill：它不取消已跑起来的 asyncio 任务，要给硬上限就再叠一层超时。

五、场景说明

  1. 调外部 API：5xx 重试、超时掐断、连续失败转降级分支；
  2. 扣款/下单：error_handler 做 Saga 补偿（退款、释放库存）；
  3. 长任务停机：SIGTERM 时 request_drain，把进度留在检查点；
  4. 批量抓取：run_timeout 卡住异常慢的单条，避免拖垮整批。

步骤 4：最小可运行代码

存成 reliability_demo.py，uv run reliability_demo.py。

import asyncio
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.runtime import Runtime
from langgraph.types import Command, RetryPolicy, TimeoutPolicy
from langgraph.errors import NodeError

class State(TypedDict):
    order_id: str
    charge_key: str
    status: str
    attempts: list[int]

async def reserve_key(state: State):
    # 先落一个可复现的幂等键；它必须在扣款之前单独一步
    return {"charge_key": state.get("charge_key") or f"charge:{state['order_id']}"}

async def charge(state: State, runtime: Runtime):
    attempt = runtime.execution_info.node_attempt      # 1 起算，重试会 +1
    print(f"charge 第 {attempt} 次尝试")
    if attempt < 3:
        await asyncio.sleep(1.2)                       # 前两次慢，触发 idle_timeout
    return {"status": "charged", "attempts": [attempt]}

async def finalize(state: State):
    return {"status": state["status"]}

def compensate(state: State, error: NodeError) -> Command:
    return Command(update={"status": f"compensated:{error.node}:{error.error}"}, goto="finalize")

builder = StateGraph(State)
builder.add_node("reserve_key", reserve_key)
builder.add_node(
    "charge", charge,
    timeout=TimeoutPolicy(idle_timeout=0.8),
    retry_policy=RetryPolicy(max_attempts=3),
    error_handler=compensate,
)
builder.add_node("finalize", finalize)
builder.add_edge(START, "reserve_key")
builder.add_edge("reserve_key", "charge")
builder.add_edge("charge", "finalize")
builder.add_edge("finalize", END)

graph = builder.compile()
result = asyncio.run(graph.ainvoke(
    {"order_id": "A-1001", "status": "new", "attempts": []},
    version="v2",
))
print("status =", result.value["status"])
print("attempts =", result.value["attempts"])

步骤 5：预期输出

charge 第 1 次尝试
charge 第 2 次尝试
charge 第 3 次尝试
status = charged
attempts = [3]

读法：前两次都因为 idle_timeout=0.8 秒被掐（NodeTimeoutError 默认可重试），第三次不再 sleep、直接返回，成功；attempts = [3] 说明「失败那次的写入被丢弃了，只有成功那次的结果进了状态」——这正是官方说的「整段重跑」。

步骤 6：验证是否成功

  • 把 max_attempts 改成 2：第三次不会再试，compensate 被触发，status 变成 compensated:charge:...；
  • 把 timeout 从节点上删掉：第一次就慢慢跑完，attempts 只有 [1]；
  • 把 charge 改成同步函数（去掉 async）再挂 timeout：compile() 直接报错——同步节点不支持超时；
  • 在 reserve_key 里把 charge_key 改成每次新 UUID：重试后幂等键变了，外部去重失效（这是坑，见第七节）。

写法 A · 图级默认：set_node_defaults

graph = (StateGraph(State)
         .set_node_defaults(retry_policy=RetryPolicy(max_attempts=3),
                            timeout=TimeoutPolicy(run_timeout=30))
         .add_node("reserve_key", reserve_key)
         .add_node("charge", charge)          # 自动继承默认
         .add_node("finalize", finalize, error_handler=compensate)  # 单个覆盖
         .compile())

官方两条注意：默认在 compile() 时解析，set_node_defaults 写在 add_node 前后都行；父图的默认不会传给子图，每张图各配各的。

写法 B · 优雅停机

from langgraph.runtime import RunControl
from langgraph.errors import GraphDrained
import signal

control = RunControl()
signal.signal(signal.SIGTERM, lambda *_: control.request_drain("sigterm"))
try:
    graph.invoke(inputs, config, control=control)
except GraphDrained as e:
    log.info("已停机并留下检查点：%s", e.reason)

重启后 graph.invoke(None, config) 接着跑。

七、常见坑（官方明确限制/版本差异）

  1. 同步节点挂 timeout。compile() 阶段就报错，不是运行期才发现。
  2. 指望 error_handler 兜住「第一次失败」。它在重试耗尽后才跑；有 RetryPolicy 时先重试。
  3. 以为重试等于恰好一次。官方写明是「至少一次」，重复扣款要靠幂等键；键必须来自已持久化状态，别在节点里现生成。
  4. 把 RuntimeError 之类当可重试。默认名单明确排除一批内置异常，需要就自己写 retry_on。
  5. set_node_defaults 想继承到子图。不会，每张图独立。
  6. 用 request_drain 当强制终止。它只在 super-step 之间协作停机，不取消在跑的任务。
  7. DeltaChannel 想直接上生产。1.2 里它还是 beta，长线程收益大但兼容性要先测。

八、课后小结

  • 三道关顺序固定：重试 → 超时 → 补偿；后一道只在前一道用尽后生效；
  • RetryPolicy 默认 3 次、0.5 秒起、指数退避、带抖动；一批内置异常不重试；
  • timeout 只对 async 节点，idle_timeout 看静默、run_timeout 看总时长；
  • error_handler(state, NodeError) 返回 state 或 Command，是 Saga 补偿的落点；
  • 重试是至少一次，副作用必须幂等，幂等键要来自持久状态；
  • set_node_defaults 图级配置，不跨图继承。

九、思考题

1、为什么超时只在 async 节点上生效？

参考回答：同步函数一旦进入执行就独占线程，运行时无法在中间打断它；async 才能在 await 点被取消。这也是「要超时就得写 async」的根因。

2、retry_on 默认排除 ValueError，合理吗？

参考回答：合理。ValueError 通常意味着代码或数据本身有问题，重试只会重复同样的错误、白烧配额；网络类异常才值得再试。

3、为什么幂等键不能在同一节点里临时生成？

参考回答：节点失败时返回值不会进检查点；重试会重新生成一个不同的键，下游就当成两笔业务。正确做法是在前一步单独落键，让它先被检查点记住。

4、error_handler 返回 Command(goto=...) 相比直接抛出异常好在哪？

参考回答：抛异常会让整条 run 失败、状态停在半路；Command 能把「补偿结果」写进状态并继续走收尾节点，业务上有完整的结束态。
