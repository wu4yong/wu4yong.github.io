08 Store：跨线程长期记忆

checkpointer 会随图自动更新，store 只在你显式 put 时才变｜依据官方 Persistence / Stores 页自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13，示例不调用模型，纯本地可跑；
  • 节点里访问 store 的官方姿势是给节点函数加 runtime: Runtime 参数，用 runtime.store；旧版「节点签名里直接注入 store」的写法仍能见到，本篇用前者；
  • InMemoryStore 只适合开发；生产官方点名 PostgresStore / MongoDBStore / RedisStore / UpstashStore；
  • Agent Server 会自动配 store，自建环境不会——这也是本地跑着好好的、上线读不到记忆的常见原因。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 checkpointer 与 store 的分工，知道 store 不会随图自动更新；
  2. 会设计 namespace（谁的 + 哪一类），用 put / get / search 读写；
  3. 能在节点里通过 runtime.store 拿到 store，并让新线程读到同一用户的旧记忆。

二、前置知识

  • 读完 LG05，知道 checkpointer 是线程级；
  • 知道 compile(checkpointer=..., store=...) 可以同时挂两个后端；
  • 对「键值存储 + 前缀匹配」有直觉（像 Redis 的 key 前缀，但这里是元组）。

三、理论讲解（官方定义）

1. 两套持久化的分工

官方把两者说成「互补」：一个跟踪当前线程，一个跟踪跨线程的持久信息。大多数应用两个都要。

2. 数据的形状

  • namespace：一个字符串元组，类似文件夹，比如 ("user-1", "memories")；
  • key：namespace 里的唯一 ID，通常是 UUID；
  • value：任意 JSON 可序列化的字典。

namespace 可以任意长、任意含义，官方明确说「不必是按用户分的」——按租户、按业务域、按 Agent 名都行。

3. 三个方法

store.put(namespace, key, value)                       # 写/覆盖
item = store.get(namespace, key)                       # 读单条，没有返回 None
items = store.search(namespace, limit=10)              # 前缀搜，默认 10 条

search 还支持：

  • filter={"字段": "值"}：按内容等值过滤；
  • query="..."：语义检索（前提是 store 配了 embedding，InMemoryStore(index=...)）；
  • offset：翻页。

放进去时还能控制「哪些字段参与向量化」：put(..., index=["food_preference"])，或 index=False 表示「能读不能搜」。

4. 前缀匹配的语义

官方对实现方的要求写得很清楚：

  • search(("alice",)) 会返回 ("alice",)、("alice", "memories") 等所有子命名空间下的条目；
  • get(("alice", "memories"), key) 是精确查找，要接近 O(1)。

这条决定了设计：想「按用户全量搜」就把用户 ID 放第一段。

四、原理拆解

把 store 想成公司档案柜，checkpointer 是每个人的工作台抽屉：

  • 抽屉里的东西随工作自动增加（图一跑，检查点就写）；
  • 档案柜不会自己长东西——你不 put，它就一直是空的；
  • 换一个工位（新线程）抽屉是空的，但档案柜还是那个，凭工号（namespace）就能取到旧档案。

三个关键判断：

  1. store 不是 state 的一部分：节点改了 store，state 不会跟着变，也不会触发 reducer；
  2. 写入时机要选：写在前台（节点里）会拖慢响应，写在后台（另起任务）会延迟生效；
  3. namespace 是权限边界：多租户系统里把租户 ID 放第一段，能天然隔离。

五、场景说明

  1. 用户画像：语言偏好、语气偏好、常用地址，新会话直接读；
  2. 事实记忆：「这个客户上次投诉的是物流」，跨会话可查；
  3. 共享知识：团队级的规则、术语表，所有 Agent 共用；
  4. Agent 自我改进：把被人工改过的 prompt 存回去，下次直接读新版本。

步骤 4：最小可运行代码

存成 store_demo.py，uv run store_demo.py。

from dataclasses import dataclass
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore
from langgraph.runtime import Runtime

@dataclass
class Context:
    user_id: str

class State(TypedDict):
    message: str
    reply: str

NS = "memories"

def remember(state: State, runtime: Runtime[Context]):
    # 前台写入：本轮学到的东西存进档案柜
    user_id = runtime.context.user_id
    namespace = (user_id, NS)
    runtime.store.put(namespace, "pref-lang", {"key": "pref_lang", "value": "中文，短句优先"})
    return {}

def answer(state: State, runtime: Runtime[Context]):
    namespace = (runtime.context.user_id, NS)
    items = runtime.store.search(namespace, limit=5)
    facts = "；".join(i.value["value"] for i in items)
    return {"reply": f"{state['message']} → 依据记忆：{facts or '（暂无）'}"}

builder = StateGraph(State, context_schema=Context)
builder.add_node("remember", remember)
builder.add_node("answer", answer)
builder.add_edge(START, "remember")
builder.add_edge("remember", "answer")
builder.add_edge("answer", END)

store = InMemoryStore()
graph = builder.compile(checkpointer=InMemorySaver(), store=store)

# 线程 1：先写记忆
cfg1 = {"configurable": {"thread_id": "chat-1"}}
r1 = graph.invoke({"message": "帮我写个周报", "reply": ""}, cfg1, context=Context(user_id="u-1"))
print(r1.value["reply"])

# 线程 2：全新线程，同一个 user
cfg2 = {"configurable": {"thread_id": "chat-2"}}
r2 = graph.invoke({"message": "今天写什么", "reply": ""}, cfg2, context=Context(user_id="u-1"))
print(r2.value["reply"])

# 换用户：读不到别人的记忆
cfg3 = {"configurable": {"thread_id": "chat-3"}}
r3 = graph.invoke({"message": "今天写什么", "reply": ""}, cfg3, context=Context(user_id="u-2"))
print(r3.value["reply"])

步骤 5：预期输出

帮我写个周报 → 依据记忆：中文，短句优先
今天写什么 → 依据记忆：中文，短句优先
今天写什么 → 依据记忆：（暂无）

第二行是关键：线程换了、checkpointer 完全不相干，但同 namespace 读到了旧记忆；第三行说明 namespace 第一段就是隔离边界。

步骤 6：验证是否成功

  • 把 namespace = (user_id, NS) 改成 (NS, user_id) 再跑：前缀搜索仍是通的（顺序不影响「能不能搜到」），但「搜 u-1 的全部记忆」就不成立了——这是顺序设计的代价；
  • 把 put 的 key 固定成 "pref-lang" 连跑两次不同值：第二次覆盖第一次，store 是键值语义，没有 reducer；
  • 把 store.search 的 limit 设成 0：返回空列表，别拿它当「不限量」。

七、常见坑（官方明确限制/版本差异）

  1. 拿 store 当 state 用。store 不参与 reducer、不会随图更新合并，节点里改它，其它节点完全不知道。
  2. namespace 拼错。少一段、多一段都读不到；建议常量 + 函数统一拼，别到处手写元组。
  3. 以为自建环境会自动配 store。官方只说 Agent Server 自动处理；本地 compile(store=...) 必须自己传。
  4. search 不给 limit 就以为全量。默认只返回 10 条，长列表会静默截断。
  5. 把 index=False 的数据拿去做 query 检索。没向量化的字段搜不到，只能 filter。
  6. 多租户不隔离第一段。("memories", user_id) 这种顺序会让「按用户前缀搜」失效。

八、课后小结

  • checkpointer 管线程内，store 管跨线程；两者互补，互不自动同步；
  • store 是 namespace + key + JSON 的三层结构，namespace 支持前缀匹配；
  • 三个方法：put / get / search(limit, filter, query, offset)；
  • 节点里用 runtime.store，namespace 用第一段做隔离；
  • 写在节点里简单但慢，写后台快但延迟，按业务选。

九、思考题

1、为什么 store 不做 reducer？

参考回答：它存的是「应用定义的事实」，不是「图的一轮状态」。合并语义因业务而异（该覆盖、该追加、该按 id 更新），框架不做猜测，交给业务代码。

2、search(("alice",)) 与 search(("alice", "memories")) 差多少？

参考回答：前者包含所有子命名空间（memories、prefs……），后者只在 memories 下找。设计 namespace 时先想清楚「要不要一次搜全」。

3、记忆写在节点里还是后台任务里，怎么选？

参考回答：要「这一轮立刻用上」就写节点里；要「不拖慢响应」就写后台。后者要知道写入延迟，别在同一个轮次里读刚写的东西。

4、为什么同一个 user 换了 thread 还能读到记忆？

参考回答：namespace 只用 user_id，没有掺 thread_id；checkpointer 的线程是另一套键，与 store 无关。
