09 流式输出：五种模式

version="v2" 之后所有模式统一成 StreamPart(type / ns / data)，多模式混跑靠 type 分流｜依据官方 Streaming 页自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13，示例的前四种模式不调用模型即可跑通；
  • version="v2" 需要 langgraph ≥ 1.1；不传就是 v1，chunk 形状会随模式数量、subgraphs 开关变化，极容易写错；
  • 官方新增 checkpoints / tasks 两个模式（debug 是二者合集），本篇列出但不逐个演示；
  • stream_events(version="v3") 的事件流仍是 beta，正文出现处标 beta，不作为推荐路径。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 values / updates / messages / custom / debug 各吐什么、给谁看；
  2. 用 version="v2" 的 StreamPart 统一读流，多模式并行时不写分支地狱；
  3. 会在节点里用 get_stream_writer() 推自定义进度，并用 subgraphs=True 收子图吐出的内容。

二、前置知识

  • 读完 LG04，知道一轮 super-step 里有多个节点；
  • 读完 LG08，知道状态是怎么被写回来；
  • 知道「流式」在 LangChain 系列里的含义（LC04 讲的是模型 token 流，本篇是图的流）。

三、理论讲解（官方定义）

1. 模式清单

模式
吐什么
典型用途
values
每一步之后的完整状态
进度面板、调试时看全貌
updates
每个节点这一步写了哪些 key
只关心增量、省带宽
messages
模型调用产生的 (token, 元信息)
前端打字机效果
custom
节点里 get_stream_writer() 推的任意数据
进度百分比、阶段提示
debug
checkpoints + tasks + 额外元信息
排障、看任务起止

checkpoints / tasks 可以单独用：前者要 checkpointer，后者要 checkpointer（拿任务起止与结果/错误）。

2. v2 的统一形状

传了 version="v2"，不管几种模式、有没有子图，每一块都是：

{"type": "values" | "updates" | "messages" | "custom" | "checkpoints" | "tasks" | "debug",
 "ns": (),        # 命名空间元组，子图事件才非空
 "data": ...}     # 各模式自己的负载

官方给每个模式配了 TypedDict（ValuesStreamPart 等），StreamPart 是它们的可辨识联合——编辑器和类型检查器能按 type 收窄。

不传 v2 时：单模式返回裸数据；多模式返回 (mode, data)；带子图变成 (ns, data)；多模式 + 子图是 (ns, mode, data) 三元组。这就是必须显式传 v2 的理由。

3. messages 模式的两个细节

  • 它是模型输出，不是图状态：拿到的是 token 与元信息；
  • 想只收某个节点的 token，用 metadata["langgraph_node"] 过滤；
  • 父图包着 create_agent 这类编译好的子图时，不加 subgraphs=True 收不到内层 token。

4. invoke 也能带 stream_mode

invoke(input, stream_mode="updates", version="v2") 会返回 list[StreamPart] 而不是 GraphOutput；只要不是默认 values，返回形状就变。要最终状态还是用 stream 自己收尾。

四、原理拆解

把流式想成给一条装配线装了摄像头，档位可调：

  • values：每一步拍一张全景照（状态全量）；
  • updates：每一步只拍「这一工位动了什么」；
  • messages：镜头怼到模型嘴上，逐字拍；
  • custom：工位自己举牌子（writer({...})）；
  • debug：全景 + 每个任务的开始/结束/错误。

三个关键判断：

  1. 多模式不是合并成一条，是按发生顺序交错吐出，靠 type 分流；
  2. ns 是子图坐标：根图是 ()，子图是 ("节点名:task_id",)，嵌套继续往后接；
  3. 顺序只在同一节点内保证：并行分支的 updates 谁先到不保证。

五、场景说明

  1. 聊天界面：messages 逐字 + custom 显示「正在查订单」；
  2. 长任务进度：updates 每步报「已检索 / 已起草」；
  3. 排障：debug 看每个任务的输入输出与耗时；
  4. 多 Agent：subgraphs=True 把各子 Agent 的输出按 ns 分栏。

步骤 4：最小可运行代码

存成 stream_demo.py，uv run stream_demo.py。

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.config import get_stream_writer

class State(TypedDict):
    topic: str
    outline: str
    post: str

def outline(state: State):
    writer = get_stream_writer()
    writer({"stage": "outline", "progress": 30})
    return {"outline": f"提纲：{state['topic']}"}

def write(state: State):
    writer = get_stream_writer()
    writer({"stage": "write", "progress": 70})
    return {"post": f"正文（{state['outline']}）"}

builder = StateGraph(State)
builder.add_node("outline", outline)
builder.add_node("write", write)
builder.add_edge(START, "outline")
builder.add_edge("outline", "write")
builder.add_edge("write", END)
graph = builder.compile()

for mode in ["values", "updates", "custom", "debug"]:
    print(f"--- {mode} ---")
    for part in graph.stream({"topic": "流式"}, stream_mode=mode, version="v2"):
        if mode in ("values", "updates"):
            print(part["type"], part["ns"], part["data"])
        elif mode == "custom":
            print(part["type"], part["data"])
        else:
            print(part["type"], part["data"].get("step"), list(part["data"].keys()))

步骤 6：验证是否成功

  • 一次传两个模式：stream_mode=["updates", "custom"]，会按发生顺序交错吐出，用 part["type"] 分流；
  • 把 version="v2" 去掉：单模式拿裸 dict，双模式拿 (mode, data) 元组，同一段代码会崩——这就是不传 v2 的代价；
  • 去掉 writer(...) 那两行：custom 一条都不吐（但不会报错）。

七、常见坑（官方明确限制/版本差异）

  1. 以为 messages 会给你图更新。它给的是模型 token；要状态变化用 updates / values。
  2. 并行分支的 updates 顺序当承诺。官方只说同节点内有序，跨分支不保证；要顺序就加边。
  3. v1 与 v2 的 chunk 结构混用。v1 下多模式是元组，v2 是 StreamPart；迁移时全部改判断方式，别一半一半。
  4. custom 没进 stream_mode 列表。节点里 writer() 调了也不会吐；多模式时列表里必须有 "custom"。
  5. 包着子图却收不到 token。父图要 subgraphs=True，再按 ns 判断来源。
  6. checkpoints / tasks 没挂 checkpointer。这两个模式依赖持久化，不挂就是空的。

八、课后小结

  • 五个常用模式：values（全量）、updates（增量）、messages（token）、custom（自定义）、debug（全信息）；
  • version="v2" 让所有模式统一成 StreamPart(type / ns / data)；
  • ns 标识子图来源，subgraphs=True 才收子图事件；
  • get_stream_writer() 推自定义进度，messages 用 langgraph_node 过滤；
  • stream_events(version="v3") 是 beta，先别上生产。

九、思考题

1、为什么 values 与 updates 不是二选一，而是可以同时开？

参考回答：两者粒度不同：前端可能既要「全量渲染」又要「只转发增量」。同时开会交错吐，用 type 分流即可，代价是带宽。

2、messages 模式拿到 (token, metadata)，metadata 里最该关心哪个字段？

参考回答：langgraph_node——它告诉你这块 token 是哪个节点产生的，多节点/子图混跑时靠它分栏。

3、custom 与 updates 都能报进度，区别是什么？

参考回答：updates 是框架按状态变更自动吐的，粒度是「节点」；custom 是节点主动写，粒度可以细到「第 3/10 条记录」，且不进状态。

4、为什么官方强调「不传 v2 时形状会随选项变」是坑？

参考回答：调用方要写 if 判断四种不同形状，代码随模式数量膨胀；v2 把这些收敛成一种，迁移一次以后都不用改。
