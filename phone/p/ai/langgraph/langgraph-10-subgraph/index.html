10 子图与状态传递

子图的 checkpointer 三档：None 每次从头、True 按线程累积、False 完全无状态｜依据官方 Subgraphs · Persistence 自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13，示例不调用模型，纯本地可跑；
  • 官方把子图的持久化写成三档：compile()（None，默认）/ compile(checkpointer=True) / compile(checkpointer=False)，含义与旧文档不完全一样，本篇按现行口径；
  • 子图事件的 ns 形如 ("节点名:task_id",)，嵌套时继续往后拼，流式分栏全靠它；
  • Command(graph=Command.PARENT) 用于「子图里跳到父图的节点」，1.x 保留，但只在子图被当节点挂载时成立。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 会用两种接法挂子图：共享 key 直接 add_node(compiled)、schema 不同写包装节点；
  2. 知道子图 checkpointer 三档的区别，能选出「每次从头」还是「按线程累积」；
  3. 会在子图里 interrupt、在父图恢复，并用 ns 把子图输出分栏。

二、前置知识

  • 读完 LG09，认识 ns 与 subgraphs=True；
  • 读完 LG05，知道 checkpointer 与命名空间；
  • 读完 LG02，知道父子 key 的类型必须一致，否则 reducer 会炸。

三、理论讲解（官方定义）

1. 子图就是「当节点用的图」

官方定义很短：subgraph 是被当作另一个图的节点使用的图。好处三条：搭多 Agent、复用一组节点、多团队并行开发（只要接口（输入输出 schema）对得上）。

2. 两种通信方式

接法
什么时候用
怎么做
直接挂
父子共享 key，子图读写同一批 channel
add_node("sub", sub)
包装节点
父子 schema 不同，或需要在中间做转换
在节点函数里 sub.invoke(...)，手写映射

直接挂最省事，但要求「key 名字与类型都对得上」；包装节点最灵活，代价是映射代码要自己维护。

3. 子图的持久化三档

写法
语义
适合
compile()（None，默认）
每次调用从头开始，继承父图 checkpointer 以支持 interrupt 与断点续跑
大多数场景、多数多 Agent
compile(checkpointer=True)
同一线程内状态累积，下次接着上次
需要多轮记忆的子 Agent（如研究助手）
compile(checkpointer=False)
完全不检查点，像普通函数调用
纯计算、不需要中断

官方还提醒：多个不同的按线程子图要各自有稳定命名空间，否则会互相覆盖。稳妥做法是「每个子 Agent 包一层 StateGraph 并给唯一节点名」。

4. 子图里中断、父图恢复

子图继承父图 checkpointer 时，interrupt() 照常工作：恢复仍在父图的 config（同一个 thread_id）上做，不是拿子图单独 invoke。

5. 跨层跳转

子图里要直接跳父图的节点，用 Command(graph=Command.PARENT, goto="父图节点")。多 Agent 交接常用这招（LG12 细讲）。

四、原理拆解

把子图想成总装厂里的一个分包车间：

  • 直接挂＝这个车间和总厂共用一套工位编号（channel），原料直接流进去；
  • 包装节点＝车间有自己的工位编号，进出都要在门口搬运（写映射函数）；
  • 检查点＝车间的进度记录：None 表示「这次干完就清空、下次重新开工」，True 表示「记在本子上，下次接着干」。

三个关键判断：

  1. key 不匹配是最常见的静默 bug：子图写了父图没有的 key，字段直接消失，不报错；
  2. 子图是「一个 super-step」：父图只在子图整体结束后提交一次检查点，所以默认回放只能从子图之前；
  3. 命名空间是隔离手段：同一个子图被调用两次，默认按调用顺序分配命名空间，重排调用就会串状态。

五、场景说明

  1. 检索 → 摘要：把「查资料 + 压缩」封成子图，父图只管编排；
  2. 专家 Agent：计费专家、物流专家各是一张子图，主管按需调用；
  3. 复用组件：同一段「校验 → 改写」在多个图里复用；
  4. 多团队并行：接口定好，各自编译自己的子图。

步骤 4：最小可运行代码

存成 subgraph_demo.py，uv run subgraph_demo.py。

from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

# ---------- 接法一：共享 key，直接挂 ----------
class SharedState(TypedDict):
    question: str
    docs: list[str]
    answer: str

def retrieve(state: SharedState):
    return {"docs": ["文档 A", "文档 B"]}

def summarize(state: SharedState):
    return {"answer": f"基于 {len(state['docs'])} 篇资料回答：{state['question']}"}

sub_builder = StateGraph(SharedState)
sub_builder.add_node("retrieve", retrieve)
sub_builder.add_node("summarize", summarize)
sub_builder.add_edge(START, "retrieve")
sub_builder.add_edge("retrieve", "summarize")
sub_builder.add_edge("summarize", END)
sub = sub_builder.compile()

parent_builder = StateGraph(SharedState)
parent_builder.add_node("rag", sub)              # 直接当节点
parent_builder.add_edge(START, "rag")
parent_builder.add_edge("rag", END)
graph = parent_builder.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "sub-1"}}
r = graph.invoke({"question": "LangGraph 有什么用", "docs": [], "answer": ""}, cfg, version="v2")
print("接法一 answer =", r.value["answer"])

# 看子图输出带命名空间
for part in graph.stream({"question": "再问一次", "docs": [], "answer": ""}, cfg,
                         stream_mode="updates", subgraphs=True, version="v2"):
    print(part["type"], part["ns"], part["data"])

步骤 5：预期输出

接法一 answer = 基于 2 篇资料回答：LangGraph 有什么用
updates ('rag:<task_id>',) {'retrieve': {'docs': ['文档 A', '文档 B']}}
updates ('rag:<task_id>',) {'summarize': {'answer': '基于 2 篇资料回答：再问一次'}}
updates () {'rag': {'answer': '基于 2 篇资料回答：再问一次'}}

读法：子图内部两个节点的更新带 ns，父图只看到「rag 这个节点整体写了什么」——父图把子图当一个 super-step。

步骤 6：验证是否成功

  • 把子图的 key 改成 documents（父图仍是 docs）：answer 里的篇数变成 0，字段静默消失；
  • 把 add_node("rag", sub) 换成包装函数 lambda s: sub.invoke({"question": s["question"], "docs": [], "answer": ""})：需要自己把返回值映射回去，这就是接法二（写法 A）；
  • 把子图 compile(checkpointer=True) 再跑两轮：子图自己的状态会跨轮累积（docs 越攒越多）。

写法 A · 接法二：父子 schema 不同，写包装节点

class ParentState(TypedDict):
    user_input: str
    final: str

class ChildState(TypedDict):
    query: str
    hits: list[str]
    digest: str

def child_node(state: ParentState):
    child_cfg = {"configurable": {"thread_id": "child"}}
    out = sub.invoke({"query": state["user_input"], "hits": [], "digest": ""},
                     child_cfg, version="v2")
    return {"final": out.value["digest"]}     # 只把需要的字段搬回父图

parent = (StateGraph(ParentState)
          .add_node("child", child_node)
          .add_edge(START, "child")
          .add_edge("child", END)
          .compile(checkpointer=InMemorySaver()))

映射只搬必要字段，别整份 state 往回塞——这是「父子 key 不一致」时最稳的边界。

子图里 interrupt、父图恢复

def approve(state: ChildState):
    ok = interrupt("子图里也要人点头")
    return {"digest": "已通过" if ok else "被拒"}

# 恢复仍在父图 config 上做
graph.invoke(Command(resume=True), cfg, version="v2")

七、常见坑（官方明确限制/版本差异）

  1. 父子 key 名字对不上。字段静默丢失，不报错；类型对不上则 reducer 直接炸。
  2. 在子图自己的 config 上恢复 interrupt。恢复要用父图的 thread_id，否则找不到待恢复任务。
  3. 同一个子图调用两次不隔离。默认按调用顺序分命名空间，重排调用就串状态；给每个子 Agent 唯一节点名。
  4. 想让子图内部可回放却没开检查点。默认继承父图，父图把子图当一个 super-step。
  5. compile(checkpointer=False) 还想用 interrupt。官方明确：完全无检查点就没有中断与断点续跑。
  6. 把子图当 API 边界。子图不是服务，别指望它自带鉴权、限流；那些是部署层的事（LG15）。

八、课后小结

  • 子图＝当节点用的图，两种接法：共享 key 直接挂、schema 不同写包装；
  • 子图默认被父图当成一个 super-step，流式里靠 ns 区分；
  • checkpointer 三档：None 每次从头、True 按线程累积、False 完全无状态；
  • 子图 interrupt 在父图 config 上恢复；跨层跳转用 Command(graph=Command.PARENT)；
  • 多子图要稳定命名空间，否则互相覆盖。

九、思考题

1、为什么共享 key 时可以直接 add_node(compiled)，而不同 schema 就不行？

参考回答：直接挂的前提是「子图读写的就是父图的 channel」，运行时按 key 对接；schema 不同就没有公共 channel，必须有人在中间搬数据，只能写包装节点。

2、默认（None）档下，为什么父子状态不会自动累积？

参考回答：默认每次调用从头开始，只为支持本次调用内的 interrupt 与续跑；跨调用记忆要显式 checkpointer=True。

3、子图里 interrupt 之后，父图的 next 会显示什么？

参考回答：父图会看到子图这个任务处于「未完成」，next 里是子图所在的那个节点名；恢复后从该任务继续，而不是从父图入口重来。

4、为什么官方警告「同一个子图调用两次」有命名空间风险？

参考回答：命名空间按调用顺序（第一次、第二次）分配，重排调用顺序后旧检查点会被新调用读到，状态就串了；固定唯一节点名能避免。
