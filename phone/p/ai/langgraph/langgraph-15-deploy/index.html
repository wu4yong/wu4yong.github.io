LangGraph 15 · 部署清单

分类：ai · langgraph ｜ 标签：AI · 系统课 · LangGraph

15 部署清单

langgraph.json 的 graph 名就是 SDK 里的 assistant_id；其余是持久化、凭证与停机｜依据官方 Deployment / langgraph.json 自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13，部署形态以 LangSmith Cloud 为默认路径（官方文档的主推）；
  • 本地自测要装 langgraph-cli[inmem]，langgraph dev 起的是内存版服务，不能当生产；
  • 云上部署官方给的等待时间约 15 分钟，期间 Studio 才能看到图；
  • 生产持久化必须换 PostgresSaver / PostgresStore；内存版重启即丢（LG05/LG08）。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 会写 langgraph.json，知道 graph 名与 assistant_id 的关系；
  2. 能在本地 langgraph dev 自测，再用 SDK 调通 runs.stream；
  3. 能按五题清单检查上线条件（持久化、thread_id、凭证、drain、修剪）。

二、前置知识

  • 读完 LG11，知道 request_drain 与重试；
  • 读完 LG08，知道 checkpointer 与 store 的生产选型；
  • 有一份能跑的图（LG13/LG16 任意一个）。

三、理论讲解（官方定义）

1. 官方给的托管形态

  • LangSmith Cloud：全托管，GitHub 仓库直连，负责扩缩容、持久化、后台执行；
  • Hybrid / Standalone / 自托管：官方也提供，适合有合规或内网要求的团队；
  • 自建也完全可以：把图包成 FastAPI 服务，自己接 Postgres——只是这些运维工作归你。

2. langgraph.json：唯一必须写对的文件

{
  "graphs": { "agent": "./agent.py:graph" },
  "dependencies": ["."],
  "env": ".env"
}
  • graphs 的 key（这里是 agent）＝部署后的 assistant_id；
  • value 是「文件路径:变量名」，图必须是已编译的；
  • dependencies 指向项目本身，装依赖时用；
  • env 指向凭证文件，别把 key 写进 json。

3. 调用方式

云上拿到 API URL 后，两种调用：

from langgraph_sdk import get_sync_client
client = get_sync_client(url=API_URL, api_key=LANGSMITH_KEY)
client.runs.stream(None, "agent", input={"messages": [...]}, stream_mode="updates")

或直接 REST：POST /runs/stream，body 里带 assistant_id / input / stream_mode。

4. 上线前五题

  1. 持久化是不是 Postgres？（checkpointer 与 store 都要）；
  2. thread_id 从哪来、长度是否 ≤255（Postgres 限制）；
  3. 凭证是不是只走环境变量；
  4. 长任务收到 SIGTERM 有没有 request_drain；
  5. 有没有检查点修剪与成本上限。

四、原理拆解

把部署想成把图纸变成能接单的门店：

  • langgraph.json＝门牌号（告诉平台「图在哪、叫什么」）；
  • 构建＝装修（装依赖、打包镜像）；
  • API/SDK＝前台（接单、按 thread 分流、流式回话）；
  • 运维＝后勤（数据库、凭证、备份、停机）。

三个关键判断：

  1. 线程是资源：一个 thread_id 一条历史，前端必须自己生成与保存，别每次新建；
  2. 部署即状态：图没变但 checkpointer 换了，等于所有人的会话重置——迁移要提前计划；
  3. 流式是默认：/runs/stream 与 SDK 的 stream 是主路径，前端不要等整轮跑完再显示。

五、场景说明

  1. 内部工具：langgraph dev 本地跑，团队内网用；
  2. 对外服务：LangSmith Cloud + 前端直连 API；
  3. 合规场景：自托管，Postgres 在内网，凭证走 KMS；
  4. 多环境：dev / staging / prod 三套部署，各自独立数据库与 key。

步骤 4：最小可运行代码

agent.py：

import os
from dotenv import load_dotenv
load_dotenv()

from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.checkpoint.memory import InMemorySaver

model = init_chat_model("deepseek:deepseek-chat")

def respond(state: MessagesState):
    return {"messages": [model.invoke(state["messages"])]}

builder = StateGraph(MessagesState)
builder.add_node("respond", respond)
builder.add_edge(START, "respond")
builder.add_edge("respond", END)

graph = builder.compile(checkpointer=InMemorySaver())   # 本地自测；生产换 PostgresSaver

langgraph.json：

{
  "graphs": { "agent": "./agent.py:graph" },
  "dependencies": ["."],
  "env": ".env"
}

本地起服务：

uv run langgraph dev

输出里会给本地 URL 与 Studio 链接；打开 Studio 能逐节点看状态。

步骤 5：预期输出

from langgraph_sdk import get_sync_client
client = get_sync_client(url="http://127.0.0.1:2024")

步骤 6：验证是否成功

  • 请求里带同一个 thread_id 两次：第二次能接上上下文（本地内存版重启后失效）；
  • 把 langgraph.json 里的 key 改成 bot：SDK 调 "agent" 会报 assistant 不存在——assistant_id 就是这个 key；
  • 删掉 .env：启动即报缺 key，说明凭证没被硬编码进代码。

写法 A · 换生产持久化

from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.store.postgres import PostgresStore

with PostgresSaver.from_conn_string(os.environ["PG_URL"]) as cp:
    cp.setup()
    store = PostgresStore.from_conn_string(os.environ["PG_URL"])
    store.setup()
    graph = builder.compile(checkpointer=cp, store=store)

写法 B · 优雅停机

import signal
from langgraph.runtime import RunControl
from langgraph.errors import GraphDrained

control = RunControl()
signal.signal(signal.SIGTERM, lambda *_: control.request_drain("sigterm"))
try:
    graph.invoke(inputs, config, control=control)
except GraphDrained as e:
    print("drained:", e.reason)     # 检查点已存，重启后可续跑

七、常见坑（官方明确限制/版本差异）

  1. 把 langgraph dev 当生产。[inmem] 就是内存版，重启全丢。
  2. graphs 的 key 与调用名不一致。SDK/REST 都用这个 key 当 assistant_id。
  3. 凭证写进 langgraph.json 或代码。官方口径是 env 指文件、变量走环境。
  4. thread_id 让前端每次新建。上下文全丢；应由前端按会话保存并复用。
  5. thread_id 超 255 字符。Postgres 直接报错，不是 Python 层。
  6. 没做停机处理。滚动发布时正在跑的 run 被硬杀，检查点可能丢最后一步（durability 默认 async）。
  7. 检查点不修剪。上线三个月后表比业务表还大。

八、课后小结

  • langgraph.json 三件事：graphs 映射、依赖、env；
  • graph 的 key＝assistant_id，调用方按这个名找图；
  • 本地 langgraph dev 只用于自测，生产必须 Postgres；
  • 调用走 /runs/stream 或 SDK，thread_id 由前端负责；
  • 上线前过五题清单：持久化、线程、凭证、drain、修剪。

九、思考题

1、为什么 langgraph.json 里的图必须是「已编译」的？

参考回答：平台启动时要直接拿到可执行的 CompiledStateGraph 对象；未编译的 builder 不能被 invoke，也不含 checkpointer 配置。

2、assistant_id 与图里的节点名是什么关系？

参考回答：没有关系。assistant_id 是部署配置里的图入口名；节点名是图内部的路由单位，两者不在一个层级。

3、为什么 thread_id 应该由前端生成并保存？

参考回答：thread 属于「一段会话」，只有前端知道会话边界；后端每次新建会让多轮对话失去上下文，也没法续跑。

4、生产环境把 durability 设成 sync 的代价是什么？

参考回答：每步都要同步写检查点，延迟上升、数据库压力更大；换来的是崩溃时最多丢最后一步以内的状态。按业务能不能重算来选。
