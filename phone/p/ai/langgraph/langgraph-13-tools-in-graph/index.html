13 图内工具循环

ToolNode 负责并发执行、异常兜底与状态注入；循环的出口由你自己写｜依据官方 ToolNode / Quickstart 自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13；ToolNode 在 langgraph.prebuilt 里，没有随 1.x 一起弃用（弃用的是 create_react_agent）；
  • tools_condition 是官方给的现成条件函数，等价于「有 tool_calls 就去 tools，否则结束」；
  • 工具里读图状态/上下文用注入参数（InjectedState / ToolRuntime），别用闭包硬编码；
  • ToolNode 默认 handle_tool_errors=True：工具抛异常会变成一条 ToolMessage 回给模型，而不是让整条 run 崩掉。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 手搭「llm_call ⇄ tool_node」循环，说清出口在哪；
  2. 会用 ToolNode 的并发、异常兜底、状态注入三个能力；
  3. 会给循环加上限与终止条件，避免无限工具调用。

二、前置知识

  • 读完 LG03，知道条件边怎么写；
  • 读完 LG02，知道 messages 用 add_messages 追加；
  • 知道 AIMessage.tool_calls 与 ToolMessage.tool_call_id 的配对关系。

三、理论讲解（官方定义）

1. 循环的四个零件

零件
作用
关键点
llm_call
调模型，产出带 tool_calls 的回复

官方 Quickstart 里就是这四样，一句话：「模型想用工具，图负责真的去用」。

2. ToolNode 到底替你做了什么

  • 并发：一条 AIMessage 里有三个 tool_calls，三个同时跑，不是串行；
  • 异常兜底：工具内部抛异常 → 生成一条带错误的 ToolMessage（模型能看到并自我修正）；
  • 状态注入：工具签名里声明 InjectedState / ToolRuntime，运行时把当前 state / context 塞进来；
  • 配对：自动把结果按 tool_call_id 对回去，模型不会拿到错位的结果。

3. tools_condition 是什么

官方预置的条件函数，读最后一条消息的 tool_calls：有就返回 "tools"，没有返回 END。只有一种情况要自己写：你想在「没调用工具」时走别的分支（比如转人工、转总结）。

4. 循环的出口

三种出口，按需要选：

  • 模型不再调用工具 → END（最常见）；
  • 调用次数到上限 → 走降级节点（推荐，比报错友好）；
  • 命中某个业务条件（比如拿到订单号）→ 直接跳收尾节点。

四、原理拆解

把循环想成一个反复问医生的过程：

  • 医生（模型）说「我需要验血」（tool_calls）；
  • 护士（ToolNode）去执行，把结果贴回病历（ToolMessage）；
  • 医生看结果，再决定「还要不要加查一项」；
  • 直到医生说「结论如下」，循环结束。

三个关键判断：

  1. tool_calls 是模型的意图，不是事实：模型可能编一个不存在的工具名，ToolNode 会报「未找到工具」并回一条错误消息；
  2. 一轮可以多个调用：ToolNode 并发跑，但外部有副作用时要自己保证顺序或幂等；
  3. 每轮都进一次模型：3 轮工具 = 4 次模型调用，成本与延迟按轮数涨。

五、场景说明

  1. 检索增强：先搜再答，模型决定搜什么；
  2. 多步计算：查库存 → 算折扣 → 出报价；
  3. 数据库问答：生成 SQL → 执行 → 看结果 → 修正 SQL；
  4. 带审批的工具：敏感工具前面插一个 interrupt()（LG06）。

步骤 4：最小可运行代码

存成 tool_loop.py，uv run tool_loop.py。

import os
from dotenv import load_dotenv
load_dotenv()

from langchain.tools import tool
from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.prebuilt import ToolNode, tools_condition

model = init_chat_model("deepseek:deepseek-chat")

@tool
def stock(sku: str) -> str:
    """查某 SKU 的库存数量。"""
    return {"A-1001": "库存 12 件", "B-2002": "库存 0 件"}.get(sku, "无此 SKU")

@tool
def quote(sku: str, qty: int) -> str:
    """按 SKU 与数量算报价（单价 99，10 件以上打 9 折）。"""
    unit = 99 * (0.9 if qty >= 10 else 1)
    return f"{sku} × {qty} = {unit * qty:.0f} 元"

tools = [stock, quote]
llm = model.bind_tools(tools)

def llm_call(state: MessagesState):
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(MessagesState)
builder.add_node("llm_call", llm_call)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "llm_call")
builder.add_conditional_edges("llm_call", tools_condition)
builder.add_edge("tools", "llm_call")

graph = builder.compile()
out = graph.invoke(
    {"messages": [{"role": "user", "content": "A-1001 还有货吗？买 20 件多少钱？"}]},
    {"recursion_limit": 8},
    version="v2",
)
print(out.value["messages"][-1].text)
print("总消息数 =", len(out.value["messages"]))

步骤 6：验证是否成功

  • 打印每条消息的 type：会看到 human → ai(tool_calls) → tool → ai(tool_calls) → tool → ai；
  • 问一个不需要工具的问题（「你好」）：消息数只有 2，tools_condition 直接走 END；
  • 把 quote 里的 qty 改成 float 传字符串：ToolNode 回一条参数校验失败的消息，run 不崩。

写法 A · 工具里读图状态

from langgraph.prebuilt import InjectedState
from typing import Annotated

@tool
def my_orders(query: str, state: Annotated[dict, InjectedState]) -> str:
    """按当前用户查订单。"""
    user_id = state.get("user_id", "unknown")
    return f"{user_id} 的订单：{query} 命中 2 条"

需要线程/配置时用 ToolRuntime：

from langchain.tools import ToolRuntime

@tool
def trace_tool(x: str, runtime: ToolRuntime) -> str:
    """读 thread_id 做审计。"""
    return f"{x} @ {runtime.config['configurable']['thread_id']}"

写法 B · 自带上限的出口

def route(state: MessagesState) -> Literal["tools", "summarize", END]:
    if not state["messages"][-1].tool_calls:
        return END
    if sum(1 for m in state["messages"] if getattr(m, "tool_calls", None)) >= 3:
        return "summarize"          # 到上限转降级，不再硬跑
    return "tools"

builder.add_conditional_edges("llm_call", route)

七、常见坑（官方明确限制/版本差异）

  1. 没绑工具就进循环。模型不会返回 tool_calls，tools_condition 永远走 END，看起来「工具没用上」。
  2. 工具返回值不是 JSON 可序列化。ToolNode 序列化失败，整轮报错。
  3. 循环不设上限。模型反复调同一个工具，直到 GraphRecursionError（默认 25 轮）。
  4. 工具里用闭包读 state。闭包拿到的是建图时的旧值；要用 InjectedState / ToolRuntime。
  5. 把 ToolNode 当执行器做副作用。重试与回放会重跑工具（LG11），发邮件、扣款这类必须幂等。
  6. tools_condition 与自定义边混用。同一个源节点挂两条条件边，路由会互相抢；只留一条。

八、课后小结

  • 循环四件：llm_call（绑工具）、should_continue、ToolNode、回边；
  • ToolNode 管并发、异常兜底、状态注入、结果配对；
  • tools_condition 是默认出口，业务分支自己写；
  • 工具读状态用注入参数，不要闭包；
  • 循环必须有上限与降级路径，别把 recursion_limit 当业务规则。

九、思考题

1、为什么 tool_calls 要由模型产出，而不是图直接决定调哪个工具？

参考回答：工具选择依赖自然语言语义，只有模型能做；图的职责是「安全、可控地执行」，两者分工正好。

2、ToolNode 并发执行三个工具，其中一个失败会怎样？

参考回答：默认把失败转成一条错误 ToolMessage，其余两个照常返回；模型下一轮能看到「哪个失败了」，决定重试或改参数。

3、InjectedState 与 ToolRuntime 该用哪个？

参考回答：只要读当前图状态用 InjectedState；需要 thread_id、store、运行配置这类运行期信息用 ToolRuntime。

4、为什么「到上限转 summarize」比直接报错好？

参考回答：报错让整条 run 失败、用户拿不到任何答案；降级节点能带着已有结果收尾，把「没查全」说清楚，业务上是可用结果。
