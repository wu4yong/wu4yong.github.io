14 测试与评测

越往下越接近真实、也越贵；官方三个抓手：graph.nodes / update_state / 整图 invoke｜依据官方 Test · Unit tests 自绘

版本不一致提示

  • 本篇基线是 LangGraph 1.2.x + Python 3.13，测试框架官方示例用 pytest；
  • graph.nodes["名字"].invoke(...) 绕过 checkpointer，适合单节点测试，不代表整图行为；
  • 局部执行靠 update_state(as_node=...) + interrupt_after=...，官方示例用的是静态断点；
  • 官方示例里还在用 MemorySaver（InMemorySaver 旧名）；本篇用 InMemorySaver，行为一致。

一、学习目标

学完这一讲，你要能做到三件事：

  1. 写出节点级单测、局部路径测试、整图断言三类用例；
  2. 用 update_state(as_node=...) 从中间节点起跑、用 interrupt_after 在某节点后停下；
  3. 给 Agent 设计「结果 + 路径 + 成本」三维评测，而不是只比字符串。

二、前置知识

  • 读完 LG07，会 update_state 与 interrupt_after；
  • 读完 LG13，知道工具循环最容易回归；
  • 会写 pytest：assert、fixture、参数化。

三、理论讲解（官方定义）

1. 官方给的三个抓手

抓手
怎么做
用来测什么
整图断言
compile(cp) 后 invoke，断言最终 state
路由、reducer、端到端
单节点直调
nodes["n1"].invoke(...)
单个节点的输入输出
局部执行
update_state(as_node=...) + interrupt_after
中间一段路径

2. 关键习惯：每次新建图 + 新 checkpointer

官方示例特意写成工厂函数：

def create_graph() -> StateGraph: ...

每个用例 create_graph() 再 compile(InMemorySaver())，thread_id 每个用例独立。原因：检查点是全局可变的，共用会互相污染，且失败用例难复现。

3. 单节点测试的边界

compiled.nodes["node1"].invoke(state) 直接调节点函数：

  • 好处：快、不跑其它节点、不碰 checkpointer；
  • 代价：测不到「边怎么选」「reducer 怎么合并」；
  • 注意：它绕过 checkpointer，所以节点里的 interrupt() 这类行为在这里不成立。

4. 局部执行的三步

  1. compile(checkpointer=InMemorySaver())；
  2. update_state(config, values=..., as_node="前一个节点")，模拟「前一个节点刚跑完」；
  3. invoke(None, config, interrupt_after="目标节点")，跑完目标节点就停。

这招能在不重构图的前提下，只测中间一段。

四、原理拆解

把测试想成给一条流水线分段验收：

  • 单节点＝检查单个工位的加工精度；
  • 局部路径＝只让中间三个工位转，前后不动；
  • 整图＝整条线跑一遍，看成品与节拍；
  • 轨迹评测＝不只看成品，还看「走了哪些工位、返工几次」。

三个关键判断：

  1. 单元测试别断言模型的字：模型输出会变，断言「字段是否存在、是否命中规则」；
  2. 路径断言很有价值：steps 里记了走过哪些节点，比断言最终文本更稳；
  3. 评测要有基线：同一批数据跑两版，比较通过率与平均轮数，否则「感觉变好了」不算数。

五、场景说明

  1. 改 prompt 前后：整图断言 + 轨迹评测对比；
  2. 加工具：单节点测参数校验，整图测是否误调用；
  3. 改 reducer：只跑局部路径，快速验证合并逻辑；
  4. 上线前回归：固定数据集 + 固定 thread_id 前缀，可重放。

步骤 4：最小可运行代码

存成 test_graph.py，uv run pytest -q。

import pytest
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

class State(TypedDict):
    my_key: str
    steps: list[str]

def create_graph() -> StateGraph:
    def n1(s): return {"my_key": "hello from n1", "steps": ["n1"]}
    def n2(s): return {"my_key": "hello from n2", "steps": s["steps"] + ["n2"]}
    def n3(s): return {"my_key": "hello from n3", "steps": s["steps"] + ["n3"]}

    g = StateGraph(State)
    g.add_node("n1", n1)
    g.add_node("n2", n2)
    g.add_node("n3", n3)
    g.add_edge(START, "n1")
    g.add_edge("n1", "n2")
    g.add_edge("n2", "n3")
    g.add_edge("n3", END)
    return g

def test_full_graph():
    graph = create_graph().compile(checkpointer=InMemorySaver())
    r = graph.invoke({"my_key": "init", "steps": []},
                     {"configurable": {"thread_id": "t-full"}}, version="v2")
    assert r.value["my_key"] == "hello from n3"
    assert r.value["steps"] == ["n1", "n2", "n3"]

def test_single_node():
    graph = create_graph().compile(checkpointer=InMemorySaver())
    r = graph.nodes["n2"].invoke({"my_key": "init", "steps": ["n1"]})
    assert r["my_key"] == "hello from n2"
    assert r["steps"] == ["n1", "n2"]

def test_partial_from_n2_to_n2():
    graph = create_graph().compile(checkpointer=InMemorySaver())
    cfg = {"configurable": {"thread_id": "t-part"}}
    graph.update_state(cfg, values={"my_key": "init", "steps": ["n1"]}, as_node="n1")
    r = graph.invoke(None, cfg, interrupt_after="n2", version="v2")
    assert r.value["steps"] == ["n1", "n2"]

步骤 6：验证是否成功

  • 把 test_partial 里的 as_node 改成 "n2"：图认为 n2 已跑过，直接从 n3 开始，断言会失败——说明 as_node 语义就是「谁刚跑完」；
  • 去掉 interrupt_after：n3 也会跑，steps 变三条，断言失败；
  • 三个用例共用一个 thread_id：第二个用例会读到第一个的检查点，测试变成「顺序依赖」——这就是「每测独立」的原因。

写法 A · 带模型的用例：断言字段与路径，不断言文字

def test_agent_calls_tool_once():
    graph = create_graph_with_model().compile(checkpointer=InMemorySaver())
    r = graph.invoke({"messages": [{"role": "user", "content": "查 A-1001 库存"}]},
                     {"configurable": {"thread_id": "t-agent"}}, version="v2")
    msgs = r.value["messages"]
    tool_msgs = [m for m in msgs if m.type == "tool"]
    assert len(tool_msgs) == 1                      # 路径：只调一次工具
    assert "12" in tool_msgs[0].text                 # 结果：来自工具而非模型编造
    assert r.value["steps"] == ["llm", "tools", "llm"]

写法 B · 评测：三维打分

CASES = [
    {"q": "查库存", "expect_tools": 1, "expect_keys": ["库存"]},
    {"q": "随便聊聊", "expect_tools": 0, "expect_keys": []},
]

@pytest.mark.parametrize("case", CASES)
def test_trajectory(case):
    r = run(case["q"])
    tools = sum(1 for m in r.value["messages"] if m.type == "tool")
    assert tools == case["expect_tools"]           # 路径维度
    assert all(k in r.value["messages"][-1].text for k in case["expect_keys"])  # 结果维度
    assert len(r.value["messages"]) <= 8            # 成本维度（轮数上限）

三维分别是：结果对不对、路径对不对、成本是否可控。跑两版对比通过率，才是评测。

七、常见坑（官方明确限制/版本差异）

  1. 共用 checkpointer / thread_id。用例互相污染，单跑通过、全跑失败。
  2. 拿 graph.nodes[...] 当整图测。它绕过 checkpointer，interrupt、续跑、持久化都测不到。
  3. 断言模型的完整字符串。模型换个措辞就红，维护成本高；断言字段与规则。
  4. 局部执行忘了 as_node。推断失败或从错的地方起跑（并行分支时直接报 InvalidUpdateError）。
  5. 在 CI 里跑全量模型用例。又慢又花钱；按标记分层，PR 只跑纯函数层。
  6. 只看最终答案不看路径。模型可能「蒙对答案但调错工具」，下次就翻车。

八、课后小结

  • 四层：节点单测 → 局部路径 → 整图断言 → 轨迹评测；
  • 每个用例新建图 + 新 checkpointer + 独立 thread_id；
  • graph.nodes[...] 测单节点，update_state(as_node=...) + interrupt_after 测局部；
  • 带模型的用例断言字段、路径、轮数，不断言文字；
  • 评测要跑两版对比，才有「变好/变差」的结论。

九、思考题

1、为什么官方建议每个用例新建 checkpointer？

参考回答：检查点是可变全局状态，共用会让用例顺序影响结果；新建能保证隔离与可重复，失败也好复现。

2、update_state(as_node="n1") 与直接 invoke 从 n2 起跑，差别在哪？

参考回答：update_state 是「伪造 n1 刚跑完」的历史记录，图会按正常语义从 n1 的后继继续；直接构造 state 起跑则绕过检查点，next、历史都不对。

3、为什么路径断言（工具调用次数）比文本断言更可靠？

参考回答：路径反映「系统怎么工作」，与模型措辞无关；文本会变，路径不会，回归时更能定位问题。

4、CI 里怎么分层跑？

参考回答：纯函数层（节点、局部、整图纯节点）每次 PR 跑；带模型层打 @pytest.mark.llm，只在合并前或定时任务跑，并设预算上限。
