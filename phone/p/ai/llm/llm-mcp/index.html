大模型 MCP

分类：ai · llm ｜ 标签：大模型

大模型

MCP

  • MCP（模型上下文协议）是一种用于将 AI 应用程序连接到外部系统的开源标准
  • 将 MCP 视为用于 AI 应用的 USB-C 端口。正如 USB-C 提供了连接电子设备的标准化方式一样，MCP 也提供了将 AI 应用程序连接到外部系统的标准化方式

架构中的角色

  • MCP 把连接双方分为 AI 应用一侧的宿主与客户端，以及对外提供能力的 MCP 服务器
  • 服务器向客户端暴露数据源、工具和工作流，例如本地文件、数据库、搜索引擎、计算器或专用提示流程
  • 同一个服务器可以被多个支持 MCP 的客户端接入，客户端也可以同时连接多个服务器，把不同来源的能力组合起来使用
  • 协议的价值在于统一连接方式，应用不需要为每一个外部系统单独编写一套对接逻辑

服务端提供的三类能力

  • 资源（Resources）：服务器共享给语言模型作为上下文的数据，例如文件、数据库结构或应用内信息，每个资源用一个 URI 唯一标识，客户端可以列出和读取资源
  • 提示（Prompts）：服务器定义的可复用提示模板和工作流，支持动态参数、引用资源上下文和串联多步交互，通常由用户在客户端显式选择使用
  • 工具（Tools）：服务器提供、可被模型调用执行的动作，用于完成查询、计算或操作外部系统等任务
  • 三类能力分别面向读取数据、复用提示流程和执行动作，服务器在能力声明中告知客户端自己支持哪些功能

传输方式

  • 本地连接使用 stdio 传输：客户端把服务器作为子进程启动，服务器从标准输入读取消息，向标准输出发送消息，标准错误可用于输出日志
  • 远程连接使用 Streamable HTTP 传输：服务器作为独立进程处理多个客户端连接，通过 HTTP POST 和 GET 收发消息，可选借助 Server-Sent Events 流式返回多条服务器消息
  • Streamable HTTP 取代了较早版本协议中的 HTTP+SSE 传输方式，新接入的服务端按当前规范提供统一的 HTTP 端点
  • 除标准传输外，协议允许以可插拔方式实现自定义传输，但需要保留 JSON-RPC 的消息格式和生命周期约定

消息格式

  • MCP 的消息使用 JSON-RPC 编码，消息内容必须是 UTF-8 编码
  • 一条消息对应一次请求、通知或响应，请求和响应通过标识相互关联
  • 协议在消息层区分客户端发起的请求、服务器主动发出的通知，以及对请求的回应

能力发现与声明

  • 服务器在连接时声明自己支持哪些能力，例如资源订阅、资源列表变更通知或提示模板
  • 客户端通过列出接口发现服务器提供的资源和提示，再按标识读取具体内容或取用模板
  • 可选的订阅机制让客户端在单个资源或资源列表发生变化时收到通知，而不需要反复轮询

安全考虑

  • 使用 Streamable HTTP 传输时，服务器需要校验传入连接的 Origin 头，防止 DNS 重绑定攻击
  • 本地运行的服务器应只绑定本机回环地址，而不是监听所有网络接口，并为连接实现必要的认证
  • 服务器必须校验所有资源 URI，敏感资源需要做访问控制，二进制数据要正确编码后再传输

一次典型的连接流程

  • 客户端启动或连接对应的 MCP 服务器，双方先交换各自支持的能力声明
  • 客户端通过列出接口发现服务器提供的资源和提示模板，再按标识读取具体内容
  • 需要执行动作时，模型调用服务器暴露的工具，服务器执行后把结果返回给客户端
  • 整个过程中客户端和服务器按约定的消息格式交互，新增能力由服务器在能力声明中告知

双向通知与消息关联

  • 除客户端发起的请求外，服务器也可以主动发出通知，例如资源内容或资源列表发生变化
  • 请求和响应通过消息标识相互关联，通知则不需要对应的回应消息
  • 订阅机制让客户端在关注的资源更新时收到推送，而不必反复主动查询

SDK 与开发生态

  • 官方提供多语言 SDK 用于开发 MCP 服务器，也有对应的客户端接入库
  • 支持协议的应用和工具可以直接连接符合规范的服务器，服务器一次构建即可在多个客户端复用
  • 接入新的外部系统时，按协议把数据、提示或动作封装成服务器能力，而不是为每个应用单独写对接代码

与传统插件对接的区别

  • 传统对接往往是应用为每个外部系统单独写一套集成逻辑，接口和数据格式互不统一
  • MCP 用一套标准协议描述能力和消息格式，服务器按规范暴露功能，客户端按规范接入
  • 一次构建的 MCP 服务器可以在多个支持协议的客户端中复用，减少重复的对接工作

能力组合的实际形态

  • 一个客户端可以同时连接多个服务器，把文件、数据库、搜索和计算等不同来源的能力组合到同一次对话中
  • 服务器之间不需要直接对接，各自按协议向客户端暴露能力，由客户端负责编排调用顺序
  • 新增一个外部系统时，只需实现对应的 MCP 服务器，既有客户端即可接入，不必改动其他服务器

适用场景

  • 当 AI 应用需要访问本地文件、数据库或专用工具，而这些来源各自有独立接口时，MCP 提供统一的对接规范
  • 同一份服务器能力希望被多个支持协议的客户端复用，而不是为每个应用单独集成时，适合采用 MCP 封装
  • 团队需要把内部数据、提示流程和操作动作标准化对外提供时，可以按协议组织成服务器能力
