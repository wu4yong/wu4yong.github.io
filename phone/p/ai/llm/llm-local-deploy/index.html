大模型 本地化部署

分类：ai · llm ｜ 标签：大模型

大模型

本地部署的动机与约束

  • 本地部署把模型运行在自己的设备上，敏感数据不需要发送到远端服务，也可以在没有网络连接的环境下使用
  • 本地可运行模型的规模受设备显存和内存等硬件条件约束，能跑多大参数规模的模型需要按本机实际资源评估
  • 与按调用量计费的云端 API 不同，本地运行主要消耗本机硬件资源，但模型下载、加载和推理都要占用设备性能
  • 本地部署还需要考虑模型更新、版本管理和多模型并存时的磁盘占用

Ollama 的基本使用

  • Ollama 是在本机运行开源模型的工具，提供命令行来拉取和运行模型
  • ollama pull 从模型库下载指定模型，ollama run 拉取并运行指定模型
  • 本机已经安装的模型可以通过列表命令查看，查看某个模型的 Modelfile 可以使用 ollama show --modelfile
  • 模型库覆盖编程、视觉、嵌入和推理等不同用途的模型，选择时需要对照本机硬件条件

Modelfile 定制模型

  • Modelfile 是创建和分享定制模型的蓝图，用来在基础模型之上叠加运行参数、系统消息和提示模板
  • FROM 指令指定基础模型，是 Modelfile 中必需的部分
  • PARAMETER 设置模型运行参数，例如 temperature、num_ctx、top_k、top_p 等，各参数有官方文档给出的默认取值
  • SYSTEM 指定系统消息，TEMPLATE 定义发送给模型的完整提示模板，MESSAGE 可以写入示例对话历史
  • 写好 Modelfile 后，用 ollama create <模型名> -f <Modelfile 路径> 构建自定义模型，再用 ollama run <模型名> 启动

运行参数的含义

  • temperature 控制生成的随机性，取值越高回答越有创造性，取值越低越偏连贯保守，官方默认值为 0.8
  • num_ctx 设置生成下一个 token 时可用的上下文窗口大小，官方默认值为 2048
  • top_k 和 top_p 用于约束候选词的选择范围，分别从候选数量和概率累积角度降低生成无意义内容的概率，官方默认值分别为 40 和 0.9
  • 停止序列 stop 用于指定遇到后即结束生成的文本片段，可配置多个

本地模型的接入方式

  • Ollama 提供 API 供应用程序调用本地模型，也兼容 OpenAI 和 Anthropic 客户端的接入方式
  • 本地模型可以接入编辑器、终端 Agent 等工具，在开发环境中直接调用本机运行的模型
  • 应用通过本地服务端口与 Ollama 通信，再由 Ollama 加载和运行对应的模型

自定义模型的文件来源

  • Modelfile 的 FROM 可以基于模型库中已有的模型构建，也可以指向包含 Safetensors 权重的模型目录
  • 本地 GGUF 模型文件也可以作为基础模型引入，拆分的 GGUF 分片保留原始分片文件名并用通配符匹配
  • 基础模型确定后，再在其上叠加参数、系统消息和提示模板，形成定制化的模型蓝图

多模型与版本管理

  • 本机可以并存多个模型，按名称和标签区分不同用途或版本
  • 自定义模型基于某个基础模型叠加配置，修改 Modelfile 后重新构建即可得到新的模型版本
  • 模型文件和缓存占用本机磁盘，长期保留多个模型时需要关注存储空间

本地推理的资源占用

  • 模型加载、上下文长度和并发请求都会影响内存和显存占用，上下文窗口越大可携带的对话内容越多，占用也相应增加
  • 设备资源有限时，需要在模型规模、上下文长度和回答质量之间做取舍
  • 推理速度和显存占用随模型大小、量化方式和硬件不同而变化，应按本机实际运行情况调整

本地部署的典型链路

  • 先按硬件条件选择合适规模的模型，下载到本机后确认可以正常启动对话
  • 再通过 Modelfile 叠加系统消息、提示模板和运行参数，构建符合使用习惯的自定义模型
  • 最后把本地模型接入需要的应用或工具，按实际回答质量和资源占用调整参数

与云端 API 的取舍

  • 本地部署在数据隐私、离线可用和长期调用成本上有优势，但可运行的模型规模和整体表现受本机硬件限制
  • 云端 API 通常能调用规模更大、能力更强的模型，但数据需要离开本机，并按调用方式计费
  • 不能假定本地模型与云端大模型表现一致，落地前需要按具体任务评估回答质量、上下文长度和硬件占用

本地模型的使用形态

  • 本地模型可以用于本地对话、编程辅助、文本嵌入等不同用途，模型库按用途分类提供
  • 同一台设备上可以按场景运行不同模型，通过名称区分对话模型和嵌入模型等不同用途的权重
  • 接入编辑器或终端 Agent 后，本地模型在开发环境内直接响应请求，不需要把代码上下文发送到远端服务

部署前后的检查项

  • 部署前先核对本机显存、内存和磁盘空间是否满足所选模型的运行要求
  • 启动后验证对话是否正常、上下文长度是否够用，再按回答质量调整 temperature、top_p 等运行参数
  • 长期使用时关注模型版本更新和磁盘占用，旧版本模型不再需要时再清理对应的本地文件

模型选择的参考因素

  • 按用途选择对话、嵌入或推理类模型，不同用途的模型不能互相替代
  • 对照本机显存、内存和磁盘条件评估模型规模，硬件受限时优先选择更易运行的小尺寸模型
  • 关注模型的发布许可证和适用场景，确认本地使用方式符合模型给出的条款
  • 同一任务可以先在小尺寸模型上验证流程，再按效果和资源情况决定是否更换更大的模型
