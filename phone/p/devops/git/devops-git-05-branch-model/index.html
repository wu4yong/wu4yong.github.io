分支模型与协作

命令会用之后，问题就从”怎么敲”变成”怎么组织”。同一个仓库，分支命名与合并规则不同，协作成本能差十倍。这一章讲几种被验证过的分支模型，以及 PR / Code Review 这套流程。

分支模型：主线、功能、发布、热修复的合并关系

5.1 通俗小故事：三条流水线

分支模型像工厂的三条流水线。
● master 是出货口，只放能交付的成品
● develop 是总装线，半成品都在这
● feature/* 是各车间的工位，各做各的零件，做完送总装
● hotfix/* 是返修通道，出货口出问题立刻从 master 拉出来修

出货口（master）永远可发布，是这套模型的唯一铁律。

5.2 三种常见模型

模型
分支结构
适合场景
代价
Git Flow
master / develop / feature / release / hotfix 五类分支
有固定发布周期的产品
分支多、合并链长
GitHub Flow
master + 短命 feature 分支 + PR

小团队起步建议 GitHub Flow：一条常驻主干，其余分支按功能起、合完即删。分支命得越久，冲突越贵。

5.3 分支命名规范

feature/user-login          # 新功能
fix/order-null-pointer      # 缺陷修复
hotfix/pay-timeout          # 线上紧急
chore/upgrade-deps          # 杂项、依赖升级
docs/api-readme             # 文档

命名带前缀的好处是 git branch 一眼分得清性质，也能在 CI 里按前缀跑不同流水线：

git branch -a | grep '^  feature/'

分支合并后立刻删：

git branch -d feature/user-login          # 本地
git push github --delete feature/user-login   # 远程

5.4 提交信息规范

<type>(<scope>): <subject>
type
含义
feat
新功能
fix
缺陷修复
refactor
重构，不改行为
docs
文档
chore
构建、依赖、杂项
perf
性能优化
test
测试

好的 message 是给半年后的自己和同事看的：fix(posts): correct broken image path in docker series 比 update 有用一万倍。用 git log --oneline 就能当变更日志读。

5.5 PR 与 Code Review

git checkout -b feature/user-login
git push github feature/user-login
# 到平台页面发起 Pull Request: feature/user-login → develop

一个合格 PR 的自带信息：

● 标题与改动一致，一段话说明”为什么改”
● 单次 PR 控制在一个可读范围（几百行以内），太大就该拆
● 描述里写清测试方式与影响面
● 合并前 CI 必须绿，冲突先本地解决

Review 的关注顺序：逻辑正确性 → 边界与异常 → 命名与可读性 → 风格细节。反过来从缩进开始挑，是最低效的评审方式。

共享分支禁止 rebase：它会重写别人的提交 hash，队友下次拉取就会历史分叉。--force-with-lease 也只是”安全一点的强推”，不是许可。

5.7 冲突为什么越来越多

git fetch --all
git log --oneline HEAD..github/develop | wc -l     # 落后多少提交
git diff --stat HEAD...github/develop              # 改了哪些文件

冲突量大致等于”分支活着的天数 × 每天改动行数”。三条降低冲突的习惯：
● 分支短命，一两天内合回
● 每天开工先 git pull --rebase 同步主干
● 大文件、生成物不入库（.gitignore 管住）

5.8 清单

  1. 主干永远可发布，其余分支皆为短命
  2. 分支按 feature/、fix/、hotfix/ 前缀命名
  3. 提交信息走 <type>(<scope>): <subject>
  4. 一个 PR 一件事，合并前 CI 必须绿
  5. 共享分支不 rebase，只对未推送的本地历史变基
  6. 每天先同步主干，再开新活
