DevOps Git 事故救援

分类：devops · git ｜ 标签：git

事故救援

git reset --hard 手滑、刚 merge 进错分支、push 之后发现提交里带了大文件、rebase 把同事的提交搞丢——这些都有救，前提是知道”哪个命令能找回什么”。

事故救援决策树：从报错到恢复动作

6.1 通俗小故事：后悔药柜台

Git 的后悔药分四种，吃错更麻烦。
● reflog 是监控录像：只要你动过 HEAD，就有记录，能回看半小时前在哪个提交
● reset 是”把指针挪回去”，历史本身没消失，只是分支不再指向它
● revert 是”再拍一张反向照片”，历史保留、新增一次抵消提交，适合已推送
● stash 是”先把货暂存到抽屉”，切换分支前把未提交的改动收起来

判断只需一问：这次提交已经推给别人了吗？ 没推 → reset 随便折腾；已推 → revert。

6.2 reflog：先学会这条

git reflog                       # HEAD 最近的动作记录
git reflog --date=iso | head -20
git reset --hard HEAD@{3}        # 回到三步之前

reflog 是本地记录的”HEAD 移动史”，误删分支、误 reset、误 rebase 之后几乎都能从这里找回。默认保留 90 天（gc.reflogExpire）。

git fsck 是更底层的兜底，能捞出没有引用的悬空提交：

git fsck --lost-found
git show <dangling-commit-hash>

6.4 revert：安全的反向提交

git revert <commit>              # 生成一次反向提交
git revert HEAD~3..HEAD          # 撤销一段区间
git revert -m 1 <merge-commit>   # 撤销一次 merge，保留主线

revert 的优势是”历史只增不减”，协作者无需强推、无需清理本地。代价是历史里多出”撤销提交”，看 git log 时要多认一层。

6.5 撤销各种”刚做错的事”

做错了什么
怎么救
改了文件还没 add
git checkout -- 文件 或 git restore 文件
add 了还没 commit
git reset 文件（取消暂存，改动还在）
commit 了还没 push
git reset --soft HEAD~1 重新组织
commit 了且已 push
git revert <hash>，别 reset
提交里混进了大文件/密钥
未推送用 git reset --soft + 重新 add；已推送需 git filter-repo 重写历史，并立刻轮换密钥
误删了本地分支
git reflog 找到最后提交，git branch 名字 <hash>
误 rebase 丢了提交
git reflog + git reset --hard ORIG_HEAD
merge 进错目标
未推送 git reset --hard ORIG_HEAD；已推送 git revert -m 1 <merge>

ORIG_HEAD 是 merge / rebase / reset 之前 HEAD 的快照，出事后第一条命令就该是 git reset --hard ORIG_HEAD。

6.6 stash：临时收起改动

git stash                        # 收起未提交改动
git stash -u                     # 连未跟踪文件一起收
git stash list                   # 列表
git stash apply stash@{1}        # 应用但保留记录
git stash pop                    # 应用并删记录
git stash drop stash@{1}         # 丢掉某条

典型场景：正在改 feature，线上要紧急 hotfix。先 git stash，切 master 修完，回来 git stash pop 继续。

6.7 冲突救援

git status                       # 看 Unmerged paths
git diff                         # 看冲突标记
git checkout --ours 文件         # 全用当前分支版本
git checkout --theirs 文件       # 全用对方版本
git add 文件 && git commit       # 解决完收尾
git merge --abort                # 或直接放弃

冲突标记里 <<<<<<< HEAD 是本分支、>>>>>>> feature/x 是对方。先理解两边各自想干什么，再决定保留哪部分——机械地 --ours 全收，是最常见的”解决了冲突但丢了功能”。

6.8 清理与体检

git status                       # 现在有没有残留
git gc --prune=now               # 清理无用对象（会影响 reflog 之外的悬空提交）
git fsck --lost-found            # 捞悬空提交后再 gc
git count-objects -vH            # 仓库体积
git filter-repo --path 大文件 --invert-paths   # 从历史里彻底删掉某文件

git gc 之后悬空提交就真没了，filter-repo 会重写全部历史——这两条执行前必须备份仓库，并且通知所有协作者重新克隆。

6.9 清单

  1. 出事第一件事：git reflog，别急着重来
  2. 已推送的提交用 revert，不要 reset + 强推
  3. merge / rebase 出错，先 git reset --hard ORIG_HEAD
  4. 提交里混了密钥：先轮换密钥，再改历史
  5. stash 是切换分支前的标准动作
  6. gc / filter-repo 前必须备份并通知协作者
