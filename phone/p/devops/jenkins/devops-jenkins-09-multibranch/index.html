Jenkins 多分支项目

一个仓库、十几个分支、每个分支的流水线规则还不一样。逐个建 Job 是灾难：新增分支要手工建、删分支要手工删、规则改了要改十几处。多分支项目就是让 Jenkins 自己去扫仓库，每个有 Jenkinsfile 的分支自动变成一个 Job。

多分支项目：扫描仓库，为每个分支自动上架

9.1 通俗小故事：按分支分册的书架

● 仓库是一本书，分支是不同的版次
● Jenkinsfile 是每册里都夹着的同一张印刷说明
● 多分支项目是”自动分册的书架”：又出一册新的，书架自己去取、自己贴标签
● 没有 Jenkinsfile 的分支就不会上架——这是它最省心的地方
● PR 也是临时册子，扫一次出现、合入后自动下架

反过来说，那些”顺手推上去的临时分支”不会被误构建，因为里面没有剧本。

代价是”每个分支都要有 Jenkinsfile”，老仓库可能没这个习惯，可以先用 Jenkinsfile 放在子目录的写法过渡。

9.3 创建多分支项目

新建任务 → 输入名字 order-api → 选 "多分支流水线"（Multibranch Pipeline）

必须装的插件：

Pipeline、Git、GitHub Branch Source / GitLab Branch Source
（按托管平台选；GitHub 用户常用 GitHub Branch Source 插件）

9.4 分支源配置

Branch Sources → Add → Git / GitHub / GitLab
  Project Repository: git@gitlab.example.com:team/order-api.git
  Credentials:        gitlab-deploy-key
  Behaviours:
    Discover branches            （发现分支）
    Discover merge requests      （发现 PR / MR）
    Filter by name (with regex)  （过滤分支）

过滤示例（只要 develop、main、release/*）：

Include: ^(develop|main|release/.*)$
Exclude: ^(wip|temp).*

Build Configuration：

Mode:                by Jenkinsfile
Script Path:         Jenkinsfile        （或 ci/Jenkinsfile）

Scan 触发器：

Periodically if not otherwise run: 1 day    （兜底，防 webhook 丢失）

Orphaned Items：选”删除已失效的分支”，分支在远端删除后 Job 自动清理，比保留一堆死 Job 干净。

9.5 分支差异化的写法

默认所有分支跑同一套流程，差异用 when 或 env.BRANCH_NAME 判断：

pipeline {
  agent any
  stages {
    stage('Build') {
      steps { sh 'mvn -B clean package -DskipTests' }
    }
    stage('Deploy Test') {
      when { branch 'develop' }
      steps { sh './scripts/deploy.sh test' }
    }
    stage('Deploy Staging') {
      when { branch pattern: 'release/.*', comparator: 'REGEXP' }
      steps { sh './scripts/deploy.sh staging' }
    }
    stage('Deploy Prod') {
      when { branch 'main' }
      steps {
        input message: '确认发布到生产？', ok: '发布'
        sh './scripts/deploy.sh prod'
      }
    }
  }
}

● input 会在构建里挂住等人工点击，超时由 options { timeout(...) } 控制
● 分支名可用 env.BRANCH_NAME 直接参与构建（如镜像 tag dev-${BUILD_NUMBER}）
● PR 分支的 env.CHANGE_ID 非空，可据此跳过发布、只跑测试

9.6 Webhook 与即时扫描

多分支项目同样支持 webhook，但地址不同：

GitHub:  /github-webhook/   （插件会处理，触发整库扫描）
GitLab:  /project/<multibranch-job-name>
通用:    /multibranch-webhook-trigger/invoke?token=<token>

配到仓库的 Webhook 后，push 会立刻触发”扫描 + 只构建受影响的分支”，不必等每日定时扫描。

排错要点：

● Webhook 报 200 但没构建 → 分支不匹配 Include 正则，或被过滤规则挡掉
● 新分支不出现 → 点任务页左侧 Scan Repository Now，看扫描日志里的 skip 原因
● 分支上的 Jenkinsfile 语法错误 → 该分支 Job 直接失败在解析阶段，不影响其他分支

9.7 与单 Job 的迁移路径

步骤
动作
1
把现有 Job 的构建步骤整理成 Jenkinsfile，提交到 develop
2
新建多分支项目，指向同一仓库
3
只保留 develop 分支做灰度，验证一轮
4
打开 main / release 的发现规则
5
关掉旧 Job（先停用，观察一周再删）
6
更新 README 与团队里的构建入口说明

迁移期两个 Job 会并存，注意别让它们同时部署同一台测试机——用锁资源（lock('test-server')）或直接停用旧 Job。

9.8 常见坑

● 分支太多导致扫描慢：几百个分支时，限制 Include 正则、把扫描间隔设成 1 天
● 每个分支都占 workspace：磁盘会涨，配 buildDiscarder 与定期清理
● Jenkinsfile 里写死分支名：用 env.BRANCH_NAME，否则新分支行为错
● PR 构建触发部署：PR 默认只该跑测试，发布必须 when { not { changeRequest() } }
● 凭据在所有分支可用：敏感凭据配到具体分支的 environment，或只给 main 用的凭据单独命名

9.9 清单

  1. 团队标准做法是多分支项目，别一分支一 Job
  2. Jenkinsfile 进仓库，Script Path 显式指定
  3. Include 正则收紧，过滤 wip/temp 分支
  4. 启”删除已失效分支”，避免死 Job 堆积
  5. Webhook 为主、每日扫描兜底
  6. 差异化部署用 when { branch ... }，不要复制多套 Job
  7. PR 只跑测试，发布用 input 人工确认
