DevOps Jenkins IDE 提交后自动构建发布

分类：devops · jenkins ｜ 标签：jenkins

IDE 提交代码后自动构建并发布任务

推代码那一刻就该知道”这次提交会不会把主干搞挂”。做到这一点只需要一件事：让 Git 服务器在收到 push 时主动告诉 Jenkins。少了这一步，所有自动化都退化成”人记得去点按钮”。

Webhook 触发时序：提交 → 推送 → 构建 → 回执

4.1 通俗小故事：快递到门口就喊一声

● 轮询（Poll SCM）是自己每隔几分钟跑去看快递到没到——费油、慢半拍
● Webhook 是快递员到了直接按门铃——即时、省力
● IDE 的 push 就是”寄件”这个动作，GitLab/GitHub 是快递站
● Jenkins 的 /github-webhook/ 是门铃接口，收到就开工

门铃必须在”外面按得到”：Jenkins 若在内网或本机 localhost，GitHub 根本访问不到，这时候要么给 Jenkins 一个公网地址，要么退回轮询。

生产推荐 Webhook 为主、Poll 作为兜底（如 H/15 * * * *），防止 webhook 丢包。

4.3 GitHub：配 Webhook

  1. 仓库 → Settings → Webhooks → Add webhook
  2. Payload URL：http://jenkins.example.com/github-webhook/（结尾斜杠不能少）
  3. Content type：application/json
  4. 触发事件：Just the push event（要 PR 构建就选 Let me select 并勾 Pull requests）
  5. 建好后点 Recent Deliveries，发一次 Redelivery，看返回码是不是 200

项目里勾选：GitHub hook trigger for GITScm polling。

URL 形态对照
GitHub  → /github-webhook/
GitLab  → /project/<job-name>   （带 job 名，或 /gitlab-webhook/post）
Gitee   → /gitee-webhook/
Bitbucket → /bitbucket-hook/

4.4 GitLab：配 Webhook

仓库 → Settings → Webhooks → Add webhook
  URL:        http://jenkins.example.com/project/order-api-test-deploy
  Trigger:    Push events（可加 Tag push / Merge request events）
  Secret Token: 与 Jenkins 项目里填的一致

项目里勾选：Build when a change is pushed to GitLab，并在”高级”里点 Generate 拿 Secret Token，粘到 GitLab 的 Secret Token。

不想暴露公网时，用 GitLab 插件自带的”轮询 GitLab”也行：插件会自己注册 webhook，但同样要求 Jenkins 可被访问。

4.5 内网怎么办：轮询与反向代理

Build Triggers → Poll SCM → 日程表：
H/5 * * * *      每 5 分钟看一次
H/15 * * * *     每 15 分钟看一次（推荐）

轮询会把所有 Job 的 ls-remote 分摊到不同分钟（H 的哈希散列），不会整点齐刷刷一起打 Git 服务器。

要让外网敲门，两条路：

# 1. 反向代理（nginx），把 /jenkins 转到本地 8080
location /jenkins/ {
    proxy_pass http://127.0.0.1:8080/jenkins/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_read_timeout 300s;
}
# 2. 内网穿透（临时/测试环境）
ssh -R 80:localhost:8080 nokey@localhost.run

走反向代理后，Jenkins 的”系统设置 → Jenkins URL”必须同步成带前缀的地址，否则 webhook 与邮件链接都会指回 localhost:8080。

GitHub 的 commit status 要在项目里勾 Set build status on GitHub commit，配置好后 IDE 的提交列表旁会出现 ✔ / ✘，别人一眼就知道这次 push 能不能合。

分支保护配合：main 只允许通过 PR 合入并要求该 status 通过，等于”红灯不允许进主干”。

4.7 排错顺序

现象
排查点
webhook 返回 404
URL 结尾少了 /，或 job 名写错
返回 403 / 500
CSRF 或 Secret Token 不匹配
返回 200 但没构建
分支过滤没命中（*/develop 写成 develop）
构建跑了但拿到旧代码
浅克隆 + 缓存目录，加 Wipe workspace 或 git clean -xdf
GitHub 显示超时
反向代理 proxy_read_timeout 太短
只有 PR 不触发
事件只勾了 push，没勾 Pull requests

定位技巧：GitLab 的 Webhook 页面有”最近事件”，能看到响应体和耗时；Jenkins 侧看 Manage → System Log 里的 webhook 记录。

4.8 清单

  1. 优先 webhook，Poll SCM 作兜底
  2. URL 结尾斜杠、job 名、token 三样对齐
  3. Jenkins URL 必须写成真实可达地址
  4. 分支过滤写 */develop，不要只写 develop
  5. 构建描述里写 commit 短 SHA，排错省一半时间
  6. 回写 commit status，让 IDE 直接看到结果
  7. 内网 Jenkins 用反代或穿透，别指望 GitHub 访问 localhost
