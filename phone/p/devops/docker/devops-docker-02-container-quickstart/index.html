Docker 容器快速上手

镜像是一个”模板”，容器才是真正跑起来的那个东西。日常操作里 90% 的时间都在和容器打交道：起、停、进、看日志、拷文件、清垃圾。这一章把这些动作按使用频率排一遍。

容器状态流转：创建 → 运行 → 暂停 → 停止 → 删除

2.1 通俗小故事：住酒店

镜像像一套标准化装修图纸，容器就是按图纸开出来的一间客房：
● run 是办理入住，同套图纸可以同时开出很多间房
● exec 是拿房卡进房间干活，不影响别人
● cp 是在房间和前台之间递东西
● stop 是退房但房间暂时保留，rm 才是真的拆房
● 房间里的改动（可写层）在拆房时消失，除非你把它”拍照”成新图纸（commit）

2.2 生命周期：五条命令

docker run -d --name app -p 8080:8080 -e SPRING_PROFILES_ACTIVE=prod \
  -v /data/app/logs:/app/logs --restart unless-stopped myapp:1.0
docker ps                      # 只看运行中的
docker ps -a                   # 含已退出的
docker stop app && docker start app
docker restart app
docker rm -f app               # 强制删（运行中也能删）

run 的参数值得单独记：-d 后台、-it 交互、-p 宿主:容器、-e 环境变量、-v 挂载、--restart 重启策略、--name 固定名字、--network 指定网络。--rm 适合一次性任务（跑完自动清理）。

2.3 进入容器：exec 优先，attach 慎用

docker exec -it app /bin/sh        # 推荐：新开一个进程
docker exec -it app bash           # 有 bash 的镜像
docker exec -u root -it app sh     # 指定用户
docker attach app                  # 慎用：Ctrl+C 会连带停掉主进程

区别在于：exec 在容器里新起一个进程，退出不影响主进程；attach 是接到主进程的 stdin/stdout 上，按 Ctrl+C 很可能直接把容器送走。生产排查一律用 exec。

2.4 看日志与看资源

docker logs -f --tail 100 app                       # 跟日志
docker logs --since 30m app                         # 最近 30 分钟
docker logs -t app | grep ERROR                     # 带时间戳过滤
docker stats --no-stream                            # CPU/内存/网络快照
docker top app                                     # 容器内进程树
docker inspect -f '{{.State.Status}} {{.RestartCount}}' app

docker stats 里的内存是”已用/上限”，接近上限时先看 JVM 堆参数是否和 -m 限制对齐——容器里 JVM 不识别老式限制是经典坑，JDK 8u191+ 才默认 cgroup aware。

2.5 拷文件与查看变更

docker cp app:/app/config/application.yml ./application.yml
docker cp ./patch.sql app:/tmp/patch.sql
docker diff app                    # A 新增 / C 修改 / D 删除
docker commit app myapp:hotfix     # 把当前可写层打成新镜像（仅救急用）

commit 打出来的镜像无法复现、体积膨胀、来源不明，只在线上救急时用；正常流程应该是改 Dockerfile 重新构建（第 4 章）。

2.6 端口、环境与资源限制

docker run -d --name api \
  -p 127.0.0.1:9000:9000 \
  -e TZ=Asia/Shanghai -e JAVA_OPTS="-Xms512m -Xmx512m" \
  --memory 1g --cpus 1.5 --pids-limit 200 \
  --ulimit nofile=65535:65535 \
  --health-cmd "curl -fs http://localhost:9000/actuator/health || exit 1" \
  --health-interval 20s --health-retries 3 \
  api:1.0

● -p 前面加 127.0.0.1 等于只对本机暴露，避免把内部端口直接开给公网
● --memory / --cpus 是硬限制，超了会被 OOMKill 或限流，不是”建议值”
● --pids-limit 能挡住 fork 炸弹
● --health-* 让容器带健康状态，compose 和 swarm 都靠它判断依赖是否就绪

2.7 清理与磁盘治理

docker system df                        # 先看占用
docker container prune                 # 删已退出的容器
docker image prune -a --filter "until=168h"
docker volume prune
docker builder prune --filter "until=168h"
docker system prune -a --volumes       # 危险：会连未使用的卷一起删

注意 prune -a 会清掉所有没被容器引用的镜像，包括你准备回滚用的旧 tag；生产上建议按时间过滤，而不是一把梭。

2.8 一个可复现的练习

docker run -d --name redis -p 6379:6379 redis:7-alpine \
  redis-server --requirepass devpass
docker exec -it redis redis-cli -a devpass ping
docker exec -it redis redis-cli -a devpass set k v
docker logs redis
docker rm -f redis

跑通这条链路，容器的”起-连-查-删”就闭环了。下一章讲怎么把自己的应用做成镜像，并推到仓库。
