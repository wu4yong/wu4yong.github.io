Dockerfile 完全指南

Dockerfile 是一份”从基础镜像开始，一步步把环境搭好”的构建脚本。写法不复杂，难点在顺序、缓存和体积。这一章按”指令 → 顺序 → 多阶段 → 规范”的顺序过一遍。

Dockerfile 到镜像：构建堆栈与逐层缓存

4.1 通俗小故事：装修施工单

进场先定毛坯（FROM），然后刷墙、装灯、摆家具（RUN、COPY）。施工单上每一步都会拍照留档（分层），下一次装修只要上一张照片没变，这步就不用重做。
如果把”贴海报”这种天天换的东西写在最前面，后面所有步骤的照片都会作废，每次都得从头发一遍——这就是缓存失效的代价。

4.2 常用指令速查

FROM eclipse-temurin:17-jre-jammy          # 基础镜像，生产优先 jre 而非 jdk
LABEL maintainer="ops@example.com"          # 元数据，不影响运行
ARG APP_VERSION=1.0                         # 构建期变量，RUN 里可用
ENV TZ=Asia/Shanghai JAVA_OPTS="-Xmx512m"   # 运行期环境变量
WORKDIR /app                                # 后续指令的工作目录，不存在会创建
COPY --chown=app:app app.jar ./app.jar      # 复制文件，支持 --chown
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*  # 构建期执行
EXPOSE 8080                                 # 声明端口，仅为文档与提示
USER app                                     # 切换非 root 用户
VOLUME ["/app/logs"]                         # 声明数据卷
HEALTHCHECK --interval=20s --timeout=3s CMD curl -fs http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "-jar", "/app/app.jar"]  # 固定入口
CMD ["--spring.profiles.active=prod"]        # 默认参数，可被 run 覆盖

ENTRYPOINT + CMD 的组合最好用：前者锁定”跑什么”，后者只提供默认参数，docker run image --debug 就能覆盖。

4.3 顺序决定速度：一个 Java 服务的正确写法

FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /build
COPY pom.xml .
RUN mvn -B -q dependency:go-offline          # 依赖层先落地，代码变了也不用重下
COPY src ./src
RUN mvn -B -q clean package -DskipTests

FROM eclipse-temurin:17-jre-jammy
WORKDIR /app
RUN groupadd -r app && useradd -r -g app app
COPY --from=build --chown=app:app /build/target/app.jar ./app.jar
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]

关键点三个：
● 依赖下载单独一层，pom.xml 不变就永远命中缓存
● 用多阶段构建，编译工具链不进最终镜像，体积从 700MB 级别降到 200MB 以内
● MaxRAMPercentage 比写死 -Xmx 更适合容器，堆随容器内存上限伸缩

4.4 多阶段构建：前端 + 后端一起打包

FROM node:20-alpine AS web
WORKDIR /web
COPY web/package*.json ./
RUN npm ci
COPY web .
RUN npm run build

FROM nginx:1.25-alpine
COPY --from=web /web/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

COPY --from=<stage> 可以跨阶段取产物，最终镜像只剩 nginx 和静态文件。多个 FROM ... AS name 可以并行构建，--target web 还能只构建某一阶段用于调试。

4.5 缓存与构建参数

docker build --build-arg APP_VERSION=$(git rev-parse --short HEAD) -t myapp:$(git rev-parse --short HEAD) .
docker build --no-cache -t myapp:debug .       # 完全不复用缓存，排查"我以为改了"

● ARG 值变了会让它之后的所有层失效，所以不要用变化的 ARG 去触发 RUN 装依赖
● 构建密钥用 --secret，不要 ARG/ENV 传密码，ARG 会留在镜像历史里
● docker history 能看出哪层把体积撑大了，定位最快

4.6 常见反模式

● FROM ubuntu:latest + 手动装 JDK：体积大、版本漂移、维护成本高
● RUN apt-get update 和 install 分成两条：缓存一命中就装到旧索引，报包不存在
● 一条 RUN 里装完不清理 apt 缓存：镜像白白多几十 MB
● COPY . .：把 .git、target、密钥一起带进镜像
● 用 root 跑应用：容器逃逸时权限直接拉满
● ENTRYPOINT java -jar app.jar 用 shell 形式：PID 1 是 shell，信号传不到 JVM，docker stop 会等到超时才被 SIGKILL

最后一条尤其容易被忽略：shell 形式不接收 SIGTERM，优雅停机失效，注册中心里会残留半分钟的死节点。统一用 JSON 数组形式。

4.7 写完之后的自检清单

  1. .dockerignore 是否排除 target/、node_modules/、.git/、*.log
  2. 基础镜像是否固定到明确版本，是否有更小的 -slim / -alpine 选择
  3. 是否切了非 root 用户，/app 目录属主是否正确
  4. 是否有 HEALTHCHECK，端口是否与 EXPOSE 一致
  5. 入口是否 JSON 数组形式，能否正确接收 SIGTERM
  6. docker history 里有没有异常大层
