Docker 的存储

容器删了数据就没了，这是新手上线第一天最容易踩的坑。镜像层只读，容器最上面那层可写层随容器一起销毁，所以”要留住的数据”必须落到三种挂载之一：卷（volume）、绑定挂载（bind mount）、tmpfs。

三种容器存储：卷、绑定挂载、临时文件

5.1 通俗小故事：办公桌与档案柜

容器像一个临时工位：桌面上能随手放东西（可写层），下班清桌，桌上东西全扔。
● 卷是公司档案柜：由 Docker 管理，位置固定、可备份、可被多个工位共享
● 绑定挂载是自己家里的抽屉：宿主机的具体目录直接映射进来，改文件立刻可见
● tmpfs 是写在便签上：只存在于内存，重启即失，适合密钥、缓存这类临时文件

选择逻辑很简单：生产数据用卷，宿主目录已有约定用绑定，绝不落盘的用 tmpfs。别把数据库数据放在绑定挂载到 NFS 上——文件锁与 fsync 语义不保证，迟早出问题。

5.3 卷的日常操作

docker volume create appdata
docker volume ls
docker volume inspect appdata
docker run -d --name mysql -v appdata:/var/lib/mysql -e MYSQL_ROOT_PASSWORD=*** mysql:8
docker volume rm appdata          # 只能删没被容器使用的
docker volume prune               # 清理未被引用的卷，谨慎

查看卷的真实路径：docker volume inspect -f '{{.Mountpoint}}' appdata，然后按普通目录做 tar 备份即可。

5.4 备份与恢复

# 备份：起一个临时容器把卷打包到宿主目录
docker run --rm -v appdata:/data -v /backup:/backup alpine \
  tar czf /backup/appdata-$(date +%F).tar.gz -C /data .

# 恢复
docker run --rm -v appdata:/data -v /backup:/backup alpine \
  sh -c "tar xzf /backup/appdata-2026-11-25.tar.gz -C /data"

要点：备份前让应用停写（或至少 flush），数据库更推荐用 mysqldump 逻辑备份 + 卷备份双保险。

5.5 存储驱动：overlay2 为主

docker info | grep "Storage Driver"

● overlay2：当前默认，性能好、层数上限高，要求 xfs 带 ftype=1、ext4 正常
● btrfs / zfs：支持快照，适合特殊场景，但内存占用和运维复杂度更高
● vfs：不做联合挂载，每层完整复制，慢且占空间，只在驱动不兼容时兜底

存储目录默认 /var/lib/docker，容器多的时候很容易打满根分区。迁到独立盘：

{ "data-root": "/data/docker" }

改完 systemctl restart docker，注意已有镜像不会自动搬过去，需要提前规划。

5.6 容器可写层的代价

可写层用的是”写时复制”：改一个文件要先整份拷上来再改。所以：
● 频繁写大文件的场景（日志、数据库）一定挂出来，别留在可写层
● 可写层的数据不会随镜像分发，commit 出来的镜像会把它固化，体积暴涨
● docker diff 能看到可写层改了哪些文件，排查”为什么容器重启后配置丢了”很有效

5.7 权限与属主坑

绑定挂载最常见的问题是 UID 不匹配：容器里 app 用户是 UID 1000，宿主机目录属主是 root，一写就 Permission denied。
● 用 COPY --chown 与 USER 保持镜像内属主一致
● 宿主机目录提前 chown -R 1000:1000
● 卷首次创建时的属主继承自镜像里该路径的属主，镜像阶段就把目录建好最省事

docker run --rm -v /host/data:/data alpine sh -c "id && ls -ln /data"

一条命令就能确认容器里看到的 UID 与权限，比猜快得多。
