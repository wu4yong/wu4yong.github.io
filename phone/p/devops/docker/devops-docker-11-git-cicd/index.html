DevOps Git 与容器 CI/CD

分类：devops · docker ｜ 标签：Docker

Git 和容器：CI/CD

容器化的最大红利不在”能跑起来”，而在产物唯一：同一份镜像从测试推到预发再到生产，不会出现”测试环境好好的，线上少个包”。要做到这点，流水线必须遵守一条纪律：一次构建，多处部署，用 tag 或 digest 引用同一份镜像。

从代码提交到部署上线的五段流水线

11.1 通俗小故事：车票与座位

Git 提交是一次”订票”，镜像是”车票上的座位号”，部署只是”拿着这张票去坐不同班次的车”。
● 每推一次代码，重新印一张票（构建新镜像，tag 带 commit sha）
● 测试、预发、生产都用这张票，不再重新打印
● 出问题要回滚，就是把票换成上一张（部署旧 tag），而不是改代码重来

如果在每个环境都重新 build 一次，就等于每站重新打印一张票——看起来一样，实际是两段不同的旅途，问题就是这么来的。

11.2 流水线四段

Git push → ① 构建与单元测试 → ② 打镜像并推仓库 → ③ 部署到环境 → ④ 健康校验与回滚

① 构建：编译、跑单测、静态扫描，失败即止。
② 打包：docker build 用 git rev-parse --short HEAD 打 tag，同时打 latest（可选）与日期 tag；推送到 Harbor。
③ 部署：目标机只做 pull + up -d，绝不 build。
④ 校验：探活、冒烟、看错误率；不达标自动回滚上一版。

11.3 一个可用的 GitLab CI 例子

stages: [build, package, deploy]

variables:
  IMAGE: harbor.example.com/dev/myapp
  TAG: $CI_COMMIT_SHORT_SHA

build:
  stage: build
  image: maven:3.9-eclipse-temurin-17
  script:
    - mvn -B -q clean verify
  artifacts:
    paths: [target/*.jar]
    expire_in: 1 week

package:
  stage: package
  image: docker:27
  services: [docker:27-dind]
  before_script:
    - echo "$HARBOR_PASS" | docker login -u "$HARBOR_USER" --password-stdin harbor.example.com
  script:
    - docker build --build-arg JAR_FILE=target/app.jar -t $IMAGE:$TAG .
    - docker push $IMAGE:$TAG

deploy:
  stage: deploy
  image: alpine:3.20
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s) && echo "$SSH_KEY" | ssh-add -
  script:
    - ssh ops@10.0.0.20 "cd /srv/app && IMAGE=$IMAGE TAG=$TAG docker compose pull && IMAGE=$IMAGE TAG=$TAG docker compose up -d && ./smoke.sh"
  environment:
    name: production

关键点：package 只做一次，deploy 通过环境变量把同一个 TAG 传过去，镜像不重建。

11.4 Git 侧的分支策略

● develop 每次推送 → 构建 dev-<sha> 镜像并自动部署测试环境
● main（或 release/*）合并 → 打版本 tag（1.0.0），并推 1.0.0 与 1.0
● 合并请求（MR）→ 只跑构建与单测，不推镜像，省仓库空间
● 回滚 → 直接把部署参数改成上一个 tag，一键回退，不需要 revert 代码

tag 的命名建议 service-1.0.0-<sha>，方便 grep 定位”这个版本对应哪次提交”。

11.5 服务器侧的最小部署脚本

#!/usr/bin/env bash
set -euo pipefail
cd /srv/app
docker compose pull
docker compose up -d --remove-orphans
for i in $(seq 1 30); do
  if curl -fsS http://127.0.0.1:8080/actuator/health > /dev/null; then
    echo "healthy"; exit 0
  fi
  sleep 2
done
echo "unhealthy, rollback"
docker compose down
docker compose up -d   # 用上一份 .env 里的旧 TAG 重启
exit 1

要点：--remove-orphans 清掉配置里删掉的服务；健康检查用 127.0.0.1；失败即回滚，别让坏版本撑过夜。

11.6 镜像与配置分离

同一条纪律的另一半：镜像里不放环境配置。数据库地址、密钥、副本数都应该由部署时的环境变量/配置文件提供。

services:
  api:
    image: ${IMAGE}:${TAG}
    env_file: [.env]
    environment:
      SPRING_PROFILES_ACTIVE: ${PROFILE:-prod}

这样同一份镜像可以从测试直接搬到生产，配置差异留在 .env 里，随环境走，不进镜像。

11.7 常见问题

● latest 满天飞：出问题无法确认跑的是哪版，强制用 sha tag
● CI 里 build 又跑一遍：部署阶段重复构建，违反”一次构建”，还会让”测试过的镜像”与”线上的镜像”不是同一份
● 凭据写在 Dockerfile：ARG 会留在 docker history 里，改用 --secret
● 部署失败无感知：只做了 up -d 不做健康校验，容器 CrashLoop 也不会通知人
● 磁盘慢慢满：服务器只 pull 不清理，定期 docker image prune -a --filter until=168h
