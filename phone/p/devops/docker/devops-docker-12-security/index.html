DevOps Docker 容器安全

分类：devops · docker ｜ 标签：Docker

容器的安全

容器共享宿主机内核，隔离强度弱于虚拟机。这意味着一个配置失误就可能把整台宿主机交出去。安全不是”加个杀毒”，而是把镜像、运行时、网络、主机四个面逐层收紧。

容器安全分层防护：扫描、精简、非 root、只读与限额

12.1 通俗小故事：合租公寓

容器是一个个房间，宿主机是整栋楼，内核是共用的承重墙。
● 房间门没锁（root 用户 + privileged）→ 邻居随手推门就进
● 钥匙串挂门口（密钥写进 ENV）→ 谁都能抄
● 有人在屋里打穿承重墙（内核漏洞 + 特权容器）→ 整栋楼塌
● 一楼开大门（0.0.0.0:2375 暴露 docker.sock）→ 外面的人直接当房东

安全的思路就是：每个房间只开必要的门、只给必要的钥匙、把承重墙看住。

12.2 镜像侧：从源头减少风险

● 基础镜像选官方或可信发布方，固定版本/digest，别用 latest
● 尽量选 -slim / -alpine，少一个安装包就少一个 CVE
● 多阶段构建，编译工具不进运行时镜像
● 构建期密钥用 --secret，不用 ARG/ENV（docker history 能看到）

扫描工具：

docker scout cves myapp:1.0
trivy image --severity HIGH,CRITICAL myapp:1.0
grype myapp:1.0 -o table

CI 里把它设成门禁：出现 CRITICAL 且无豁免即失败。现实中完全零 CVE 做不到，策略应该是”新增高危必须处理、存量有清单与期限”。

12.3 运行时侧：最小权限

docker run -d \
  --user 1000:1000 \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --cap-drop ALL --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges:true \
  --pids-limit 200 --memory 1g --cpus 1.0 \
  --restart unless-stopped \
  myapp:1.0

逐条说明：
● --user：非 root，逃逸后也只拿到普通账号
● --read-only：根文件系统只读，挂马、写后门都落不下来（需要写目录用 --tmpfs 或卷）
● --cap-drop ALL：丢掉绝大多数内核能力，只按需 --cap-add
● no-new-privileges：禁止 setuid 提权
● --pids-limit：挡住 fork 炸弹
● 资源上限：防单容器打满宿主机（也是一种拒绝服务防护）

永远不要在业务容器上加 --privileged、挂 /var/run/docker.sock、挂宿主 /；这些等于直接把宿主机钥匙交出去。

12.4 网络侧

● 容器默认不要 -p 0.0.0.0:端口，只对本机或反向代理暴露
● 内部服务用自定义网络互通，不发布端口
● 出入口做白名单，数据库不直接对公网
● 关闭不需要的端口，docker port 与 ss -lntp 定期核对

如果确实需要远程管理 Docker，走 SSH 隧道或 TLS 双向认证，绝不把 2375/tcp 明文暴露：

# 正确做法：本地 socket 或 TLS
export DOCKER_HOST=ssh://ops@10.0.0.20

12.5 宿主机侧

● Docker 守护进程本身是 root 权限，能操作 docker 组就等于能 root，组成员要严格控制
● 定期升级 Engine 与内核，很多逃逸利用的是已知漏洞
● 开启审计：auditd 监控 /var/lib/docker、/etc/docker
● 与宿主隔离：生产机不装无关服务，容器目录单独分区并设配额
● 多租户场景考虑 gVisor / Kata Containers，用更强的隔离换来性能损耗

docker info | grep -E "Security Options"
# 期望看到 seccomp、apparmor/selinux 已启用

12.6 编排层的安全细节

services:
  api:
    read_only: true
    tmpfs: ["/tmp"]
    security_opt: ["no-new-privileges:true"]
    cap_drop: ["ALL"]
    user: "1000:1000"
    environment:
      - SPRING_PROFILES_ACTIVE=prod
    secrets: [db_password]
secrets:
  db_password:
    file: ./secrets/db_password.txt

compose 的 secrets 会把内容挂到容器内的 /run/secrets/，比环境变量安全（环境变量会出现在 docker inspect 和子进程环境里）。

12.7 上线前自检清单

  1. 镜像是否来自可信基础镜像、是否固定版本
  2. CI 是否跑了 CVE 扫描，高危是否阻断
  3. 是否非 root 运行、根文件系统是否只读
  4. 是否 cap-drop ALL、是否禁用提权
  5. 端口是否只绑内网、是否经过反向代理
  6. 密钥是否走 secret，而非 ENV / ARG / 配置文件入库
  7. 是否有资源上限与日志轮转
  8. Engine 与内核补丁是否跟得上，docker 组是否最小化

做完全部八条，风险从”一次误操作就能被拿到宿主机”降到”需要组合多个未知漏洞”，这已经是绝大多数业务能接受的合理水位。
