Docker Swarm

单机 compose 的上限是一台机器。Swarm 把多台 Docker 主机组成一个虚拟集群，用同样的 compose 语法就能声明”跑 3 个副本””每 30 秒滚动更新一次”。它不复杂、够稳，适合中小规模自建集群。

Swarm 集群：主节点、工作节点与副本分布

8.1 通俗小故事：连锁店与区域经理

Swarm 集群像一个连锁品牌：
● Manager 是区域经理，接总部指令（docker service 命令）、排班、监控门店
● Worker 是门店，只管执行
● 顾客（请求）进门时，门口的迎宾（routing mesh）不问是哪家店，直接分流到有空位的店
● service 是”岗位编制”，--replicas 3 表示这个岗位要 3 个人，谁休假了自动补人

Manager 之间用 Raft 选举 leader，要求奇数个（3 或 5），否则脑裂时无法形成多数。

8.2 建集群

# manager 节点
docker swarm init --advertise-addr 192.168.10.11

# 输出里会给两条 join 命令，到 worker 上执行
docker swarm join --token SWMTKN-1-xxxx 192.168.10.11:2377

# 加更多 manager（高可用）
docker swarm join-token manager

docker node ls
docker node promote <node-id>
docker node inspect <node-id> -f '{{.Status}}'

网络要求：管理端口 2377/tcp、节点通信 7946/tcp+udp、overlay 数据面 4789/udp。云主机安全组不放开这三条，集群会”看着组成了但服务调度不动”。

8.3 部署一个服务

docker service create \
  --name web --replicas 3 \
  --publish 80:80 \
  --limit-memory 256m --reserve-memory 128m \
  --update-delay 10s --update-parallelism 1 \
  --restart-condition on-failure \
  nginx:1.25-alpine

docker service ls
docker service ps web --no-trunc
docker service logs -f web

或者直接用 compose 栈（v3 语法里的 deploy 段）：

services:
  api:
    image: harbor.example.com/dev/myapp:1.0
    ports: ["8080:8080"]
    deploy:
      replicas: 3
      update_config:
        parallelism: 1
        delay: 10s
        order: start-first
      restart_policy:
        condition: on-failure
        max_attempts: 3
      resources:
        limits: { cpus: "1.0", memory: 1g }
      placement:
        constraints: [node.role == worker]
docker stack deploy -c compose.yml app
docker stack services app
docker stack rm app

order: start-first 表示先起新副本再停旧副本，配合 stop_grace_period 可以做零感知更新；stop-first 则是先停后起，省资源但有短暂中断。

8.4 扩缩容与滚动更新

docker service scale web=5
docker service update --image nginx:1.27-alpine web
docker service update --rollback web       # 出问题一键回滚上一版
docker service update --force web          # 强制重建所有副本

滚动更新的节奏由 --update-parallelism 和 --update-delay 控制：一次只动 1 个副本、间隔 10 秒，配合 healthcheck 就能做到”坏的版本自己停下来”。但 Swarm 不会因为新副本健康检查失败而自动回滚，--rollback 是手动的，CI 里要显式写健康校验脚本。

8.5 调度与约束

docker node update --label-add tier=backend node1
docker service create --constraint 'node.labels.tier == backend' --mode global nginx

● --constraint 按节点标签/角色挑机器
● --placement-pref 按可用区打散副本，做容灾
● --mode global 表示全集群只跑一个副本（适合定时任务，但要自己保证不重复执行）
● --endpoint-mode dnsrr 关掉 VIP，改用 DNS 轮询，适合需要客户端感知真实 IP 的场景

8.6 排障要点

docker node ls                       # 节点是否 Ready
docker service ps api --no-trunc     # 副本落在哪台、为什么重启
docker service inspect api --pretty
docker network ls | grep ingress

● 服务一直 pending：多半是资源不足、约束不满足，或镜像在目标节点拉不下来
● 端口访问不通：检查 ingress 网络是否存在、防火墙是否放开 4789/udp
● 副本反复重启：docker service logs 看退出码，137 是 OOM，143 是 SIGTERM

8.7 什么时候不该用 Swarm

Swarm 简单可靠，但生态在收缩：缺少成熟的 CRD、没有强生态的 Operator、监控与灰度能力弱。规模上到几十节点、需要复杂调度与自愈时，Kubernetes 更合适。判断标准很实际：
● 十几台以内、只要”多副本 + 滚动更新 + 内网 overlay”，Swarm 足够
● 需要 HPA、CRD、丰富的生态组件、云厂商托管，直接上 K8s
