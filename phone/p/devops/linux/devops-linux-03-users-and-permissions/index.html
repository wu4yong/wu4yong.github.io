用户与权限

Linux 的权限模型很简单：谁能对哪个文件做什么。三个身份（属主、属组、其他人）× 三种权限（读、写、执行）。简单的东西一旦配错，就是”应用起不来”和”谁都能改配置”两类事故。

权限三要素：读/写/执行 × 所有者/组/其他人

3.1 通俗小故事：楼栋门禁

把服务器当一栋楼：
● 每个账号是一张门禁卡，/etc/passwd 是发卡记录
● 每个文件贴着”这间屋谁能进、谁能动”的规则，就是 rwx
● sudo 是临时授权去物业拿万能钥匙，做完事要还回去
● suid 是”这扇门自带特权”，任何人刷都能进（危险）

运维的核心诉求是”最小权限”：应用只开它需要的门，不给整栋楼的钥匙。

3.2 读懂 rwx 与数字表示

ls -l app.jar
# -rw-r--r-- 1 app app 20480 May  5 09:00 app.jar

九位分成三组：属主、属组、其他人。

对目录来说，x 决定能不能 cd 进去、能不能访问里面的文件；只有 r 没有 x 时，ls 能列名字但进去就报 Permission denied。

3.3 chmod 与 chown

chmod 644 app.yml
chmod 755 start.sh
chmod -R 755 /data/app/bin
chmod u+x deploy.sh            # 只给属主加执行
chmod g-w,o-rwx secret.conf    # 精确增删
chown app:app app.jar
chown -R app:app /data/app     # 递归改属主（目录常用）
chgrp docker /var/run/docker.sock

递归改权限要谨慎：chmod -R 777 是最常见的错误”解决方案”，它把问题从”权限报错”变成”任意进程都能改你的文件”。正确做法是查清到底哪个身份需要什么权限。

3.4 三个特殊位

chmod 4755 /usr/bin/passwd     # suid：以属主身份执行
chmod 2755 /data/shared        # sgid：目录内新文件继承属组
chmod 1777 /tmp                # sticky：目录内只有属主能删自己的文件

● suid 只对二进制有意义，脚本会被内核忽略；排查提权风险时先看它
● sgid 在目录上很实用：多人协作目录让新建文件自动归到同一组
● sticky 是 /tmp 的标准配置，不加的话任何人都能删别人的临时文件

查全站 suid 文件：

find / -perm -4000 -type f 2>/dev/null

3.5 umask：新建文件的默认权限

umask                # 常见 0022 → 新文件 644、新目录 755
umask 0077           # 会话内生效：新文件 600、新目录 700

umask 是”要扣掉的权限”。放到 /etc/profile 或服务单元的 UMask= 里可以持久化。容器里跑的应用如果要写共享卷，umask 不对会出现”宿主能看到、容器写不进去”的怪象。

3.6 账号管理

useradd -m -s /bin/bash deploy            # 建用户并建家目录
passwd deploy                             # 设密码
usermod -aG docker deploy                 # 追加组（-a 不能漏，否则覆盖）
id deploy                                 # 核对组
userdel -r olduser                        # 连家目录一起删
lastlog                                   # 最近登录情况

usermod -aG 漏了 -a 会把用户从其他组里踢出去，这是经典的”加完组反而权限更小”事故。

3.7 sudo 与最小授权

visudo                                   # 安全编辑 /etc/sudoers，会做语法检查
# /etc/sudoers.d/deploy
deploy ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart app, /usr/bin/tail

● 用 /etc/sudoers.d/ 分文件管理，别改主文件
● 命令写绝对路径，避免 PATH 劫持
● 能限定到具体命令就不要给 ALL
● 生产上一般保留密码校验，NOPASSWD 只给自动化账户

审计谁用了 sudo：

journalctl -t sudo -n 50
grep "sudo:" /var/log/auth.log | tail -20

3.8 ACL：比 rwx 更细的授权

setfacl -m u:jenkins:rwx /data/builds        # 给单个用户额外权限
setfacl -m g:ops:rx /data/scripts
getfacl /data/builds                          # 查看
setfacl -b /data/builds                       # 清空 ACL

ACL 适合”这个目录大部分给 app，但 Jenkins 也要写”这种场景，比把所有人塞进同一个组更精确。

3.9 清单

  1. 权限先查清需求，禁止一把 chmod -R 777
  2. 配置 644、私钥 600、脚本 755、家目录 700
  3. 加组用 usermod -aG，别漏 -a
  4. sudo 走 /etc/sudoers.d/，命令写绝对路径
  5. 定期 find / -perm -4000 清点 suid，审视提权面
  6. 多人共享目录用 sgid + ACL，不用全放开
