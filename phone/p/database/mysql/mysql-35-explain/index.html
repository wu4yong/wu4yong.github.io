分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

EXPLAIN 逐列讲：优化器打算怎么执行这条 SQL

四列决定成败：type、key、rows×filtered、Extra｜依据 MySQL 8.4 EXPLAIN Output Format 说明自绘

一、学习目标

  1. 会读 EXPLAIN 的 12 个输出列，知道每个列在回答什么问题；
  2. 记住 type 的优先级阶梯，能一眼判断「这计划还能不能要」；
  3. 区分「估算」与「实测」，知道什么时候必须上 EXPLAIN ANALYZE。

二、前置知识

B+Tree 与回表（MQ18）、联合索引与 ICP（MQ19）、索引失效（MQ20）。看不懂索引，EXPLAIN 只会给你一串看不懂的数字。

三、理论讲解（官方定义）

EXPLAIN 用于展示优化器为一个语句选定的执行计划，不真正执行 SQL。8.4 的输出列固定为：

列 含义
id 查询块序号，值大的先执行；NULL 表示是 UNION 结果或排序结果
select_type SIMPLE／PRIMARY／SUBQUERY／DERIVED／UNION／UNION RESULT
table 本行对应的表或派生表名
partitions 命中/扫描的分区
type 访问类型，性能由好到差的关键列
possible_keys 可能用上的索引（理论上）
key 实际用上的索引
key_len 用到的索引字节数，可反推用了联合索引前几列
ref 与 key 比较的对象：常量、某列、函数
rows 优化器估算的扫描行数（每行一次，不是总计）
filtered 该行经条件过滤后剩余百分比
Extra 额外动作：Using index、Using index condition、Using filesort、Using temporary…

一句口诀：先看 type 判断访问方式，再看 key 是否命中预期索引，最后看 rows × filtered 估真实代价。

四、原理拆解

type 从上到下依次变慢，Extra 里的 filesort/temporary 是需要动手的信号｜依据 MySQL 8.4 EXPLAIN 说明自绘

1. type 的优先级阶梯

const > eq_ref > ref > range > index > ALL，中间还有 ref_or_null、index_merge、unique_subquery、index_subquery。

  • const：主键或唯一索引等值命中单行，读一次即出；
  • eq_ref：JOIN 时被驱动表按主键/唯一索引匹配一行，是 JOIN 的最优解；
  • ref：普通二级索引等值，可能命中多行；
  • range：索引范围扫描（BETWEEN、>、IN）；
  • index：扫整个索引树（比全表扫少读数据页，但仍扫全部索引项）；
  • ALL：全表扫描。

线上出现 ALL 且表不小，基本等于「这条 SQL 没救了」。

2. key_len 怎么算

key_len = 用到的索引列字节数之和（含可空列的 1 字节标志位）。utf8mb4 下 VARCHAR(20) 非空 = 20×4 + 2 = 82；INT = 4；BIGINT = 8。

联合索引 (a, b, c) 上 key_len 只等于 a 的字节数，说明只用到了第一列——第二列没生效，这正是「最左前缀」的可观测证据。

3. rows 与 filtered 才是代价

rows 是估算，来自统计信息与 index dive；rows × filtered 才是优化器认为要处理的行数。两张表的 rows 相乘，就是它估的 JOIN 代价量级。

4. Extra 的四个关键信号

  • Using index＝覆盖索引，不用回表；
  • Using index condition＝ICP，条件下推到索引层过滤，但仍要回表；
  • Using where＝读完行之后在 Server 层再过滤；
  • Using filesort＝排序无法借索引顺序完成；Using temporary＝用了临时表（常见于 GROUP BY、DISTINCT、UNION）。

5. EXPLAIN 的三兄弟

命令 是否执行 用途
EXPLAIN 否 看计划
EXPLAIN FORMAT=JSON 否 看成本明细（cost_info）
EXPLAIN ANALYZE 是 看真实耗时与真实行数（8.0.18+）

EXPLAIN ANALYZE 会真跑一遍，慎用于写语句与重查询。

五、场景说明

  1. 慢 SQL 首诊：先 EXPLAIN 看 type 与 key，判断是「没走索引」还是「走了但不合适」；
  2. 索引上线验收：建索引前后各 EXPLAIN 一次，对比 key 与 rows；
  3. JOIN 调序：看 id 与 table 顺序，确认小表驱动；
  4. 计划漂移排查：同一 SQL 昨天 ref 今天 ALL，去查统计信息（MQ37）；
  5. 分页与排序：Extra 出现 filesort 时，考虑让 ORDER BY 列进索引。

六、示例代码/实操步骤

1. 基础用法

EXPLAIN SELECT o.id, o.amount
FROM t_order o
JOIN t_user u ON u.id = o.user_id
WHERE o.status = 1 AND u.city = 'Chengdu';

2. 看 JSON 里的成本

EXPLAIN FORMAT=JSON
SELECT * FROM t_order WHERE user_id = 100 ORDER BY created_at DESC LIMIT 20;

关注 query_block.cost_info 与 table.cost_info 的 read_cost、eval_cost、prefix_cost。

3. 看真实耗时与真实行数

EXPLAIN ANALYZE
SELECT * FROM t_order WHERE user_id = 100 ORDER BY created_at DESC LIMIT 20;

输出里 actual time=… rows=… 与 rows=…（估算）差距大，就是统计信息不准的直接证据。

4. 验证 key_len 与最左前缀

ALTER TABLE t_order ADD INDEX idx_user_status_time (user_id, status, created_at);

EXPLAIN SELECT * FROM t_order WHERE user_id = 100;                    -- key_len 只有 user_id
EXPLAIN SELECT * FROM t_order WHERE user_id = 100 AND status = 1;     -- key_len 累加
EXPLAIN SELECT * FROM t_order WHERE status = 1;                       -- key = NULL

5. Java 侧怎么落地：把 EXPLAIN 变成发布前检查

  1. 慢 SQL 采集：p6spy / datasource-proxy 拦截执行时间超过阈值的语句，落到日志或消息队列；
  2. 门禁脚本：CI 里对新增 SQL 跑一次 EXPLAIN FORMAT=JSON，type 为 ALL 且 rows 超过 1 万时直接失败；
  3. 单元测试：用 Testcontainers 起 MySQL 8.4，对核心查询断言 key 命中预期索引名；
  4. 上线观察：performance_schema.events_statements_summary_by_digest 里比对 ROWS_EXAMINED / ROWS_SENT 比值；
  5. 告警：比值持续大于 100 视为「扫太多返回太少」，进优化队列。

七、常见坑

  1. 把 rows 当真实行数：它来自统计估算，可能差几个数量级；
  2. possible_keys 有值就以为走了索引：要看 key；
  3. Using index 与 Using index condition 混为一谈：前者不回表，后者要回表；
  4. type=index 当成好计划：扫全索引树依然可能很慢；
  5. EXPLAIN ANALYZE 用在写语句上：会真执行，生产上绝不要试；
  6. 忽略 filtered：rows 小但 filtered 低，仍可能扫很多；
  7. JOIN 只看单表 rows：要看驱动顺序与两表相乘的规模。

八、版本差异

  • 5.6：EXPLAIN 12 列成型，支持 FORMAT=JSON；
  • 5.7：新增 partitions 列更准确，优化器成本模型可切换；
  • 8.0：EXPLAIN ANALYZE（8.0.18+）；EXPLAIN FORMAT=TREE；直方图影响 rows 估算（8.0 起）；
  • 8.4：输出列与 8.0 一致，EXPLAIN ANALYZE 稳定可用，EXPLAIN FOR CONNECTION 用于排查运行中的语句。

九、课后小结

  • EXPLAIN 只回答「打算怎么执行」，不回答「花了多久」；
  • type 阶梯是判断计划好坏的快捷方式，ALL + 大表 = 必须改；
  • key_len 是判断最左前缀是否生效的硬证据；
  • rows × filtered 是优化器眼里的代价，EXPLAIN ANALYZE 才是真实代价；
  • 把 EXPLAIN 接进 CI 与慢 SQL 采集，索引问题才不会靠人肉发现。

十、思考题

  1. type = index 和 type = ALL 有什么区别，哪个更快？

    参考回答：index 是扫整棵二级索引树，只读索引页，不回表；ALL 是扫聚簇索引（整张表）所有数据页。通常 index 更快，但若索引几乎和表一样大，两者差距很小；两者都属于「全扫」，都不是好计划。

  2. 为什么 EXPLAIN 的 rows 与实际差很多？

    参考回答：rows 来自统计信息（持久化采样页）与小范围 index dive 的估算，数据分布倾斜、统计过期、采样页太少都会让估算失真；用 EXPLAIN ANALYZE 看真实行数，再 ANALYZE TABLE 修正统计。

  3. Using index condition 一定比 Using where 好吗？

    参考回答：不一定更好，但通常更省。ICP 把能在索引层判断的条件先过滤，减少回表次数；Using where 是先回表取整行再在 Server 层过滤。是否生效取决于存储引擎是否支持该条件下推，以及条件涉及的列是否都在索引里。

  4. EXPLAIN 里 key 为 NULL 但 possible_keys 有值，说明什么？

    参考回答：优化器认为走索引不划算（例如范围太宽、需要大量回表），主动选了全表扫描。此时应检查选择性与统计信息，而不是直接加 FORCE INDEX。

  5. 线上能不能直接跑 EXPLAIN ANALYZE？

    参考回答：要非常谨慎。它会真实执行语句，重查询会占满 CPU/IO；写语句会真的写数据。只允许在从库/预发环境对只读语句使用，并加超时保护。
