JOIN 优化：驱动表与连接算法

谁当驱动表、用哪种算法，决定一条 JOIN 的全部代价｜依据 MySQL 8.4 JOIN / Hash Join 优化说明自绘

一、学习目标

  1. 说清「驱动表 → 被驱动表」的探测模型，知道 JOIN 成本怎么算；
  2. 分清 NLJ、BNL、Hash Join 的触发条件与代价差异；
  3. 会看 EXPLAIN 判断连接顺序，并用索引或改写把 BNL 变成 NLJ。

二、前置知识

索引与回表（MQ18/MQ38）、EXPLAIN（MQ35）、优化器成本（MQ37）。

三、理论讲解（官方定义）

MySQL 的 JOIN 一直以嵌套循环（Nested-Loop）为基本模型：外层表（驱动表）每取一行，就去内层表（被驱动表）找匹配行。8.0.18 起 InnoDB 支持 Hash Join，用于等值连接且没有可用索引的场景。

算法 触发条件 Extra 提示
Nested Loop Join（NLJ） 被驱动表连接列有索引 无特殊提示，type 为 ref/eq_ref
Block Nested Loop（BNL） 无可用索引，8.0.20 前默认 Using join buffer (Block Nested Loop)
Hash Join 等值连接、无索引，8.0.18+ Using join buffer (hash join)

8.0.20 起，无索引的等值连接默认走 Hash Join，BNL 只在非等值或哈希不可用时出现。

四、原理拆解

小结果集在前，被驱动表连接列有索引｜依据 MySQL 8.4 Nested Loop / Hash Join 说明自绘

1. 成本模型：探测次数

设驱动表结果集为 R 行，被驱动表每次查找代价为 c：

  • NLJ 总代价 ≈ R × c，c 是一次索引查找（含回表）；
  • BNL 总代价 ≈ R × 被驱动表页数（整表读进 join buffer 再逐行匹配）；
  • Hash Join ≈ 两表各扫一遍 + 建哈希表，内存不足会分区落盘。

所以驱动表要小，这是 JOIN 优化的第一原则。EXPLAIN 里第一张表就是驱动表。

2. 优化器怎么选驱动表

按 rows × filtered 估算各表结果集大小，再算两种顺序的总成本，取小的。STRAIGHT_JOIN 可强制按书写顺序，等于关掉这层优化，只在确认优化器判断错误时用。

3. LEFT JOIN 的例外

LEFT JOIN 语义要求左表全部保留，左表必须是驱动表，优化器没有选择权。所以「用 LEFT JOIN 代替 INNER JOIN」会白白丢掉调序空间。

4. 被驱动表没索引会怎样

退化成 BNL/Hash Join：驱动表的每一行都要和内层整表比对。10 万 × 100 万 = 10¹¹ 次比较，这就是「JOIN 一上线数据库就卡死」的典型形态。给被驱动表连接列加索引是最直接的解。

5. Hash Join 的适用与限制

  • 只支持等值连接（=、<=>），<>、> 走不了；
  • 需要内存，join_buffer_size 不够会分区写入磁盘临时文件；
  • 大表 JOIN 大表且都无索引时，它比 BNL 快一个量级，但仍然不该是常态。

五、场景说明

  1. 订单 + 用户：t_user 小、t_order 大 → 用户驱动订单，t_order(user_id) 必须有索引；
  2. 标签 + 文章：多对多中间表驱动，两侧都建索引；
  3. 报表多表串联：先把过滤条件写进 WHERE，让排在前面的表结果集变小；
  4. 大表对拼：无索引的等值连接靠 Hash Join 兜底，但应尽早改成宽表或预聚合；
  5. 分页 JOIN：先分页取主键，再 JOIN 取详情（延迟关联）。

六、示例代码/实操步骤

1. 先看谁在驱动

EXPLAIN SELECT o.id, u.name
FROM t_order o
JOIN t_user u ON u.id = o.user_id
WHERE o.status = 1;

table 列自上而下就是执行顺序，第一行是驱动表。

2. 制造并识别 BNL

-- 被驱动表连接列无索引
ALTER TABLE t_order DROP INDEX idx_user_id;
EXPLAIN SELECT o.id, u.name FROM t_order o JOIN t_user u ON u.id = o.user_id;
-- Extra: Using join buffer (hash join)   ← 8.0.20+

3. 加索引把 BNL 变回 NLJ

ALTER TABLE t_order ADD INDEX idx_user_id (user_id), ALGORITHM=INPLACE, LOCK=NONE;
ANALYZE TABLE t_order;
EXPLAIN SELECT o.id, u.name FROM t_order o JOIN t_user u ON u.id = o.user_id;
-- t_order 的 type 变为 ref，join buffer 消失

4. 小表驱动 + 先收敛

-- 差：大表直接参与 JOIN
SELECT ... FROM t_order o JOIN t_user u ON u.id = o.user_id WHERE u.city = 'Chengdu';
-- 好：先把小表收敛成派生表
SELECT ... FROM (SELECT id, name FROM t_user WHERE city = 'Chengdu') u
JOIN t_order o ON o.user_id = u.id;

5. Java 侧怎么落地：JOIN 写法规范

  1. 禁止无索引 JOIN：DAO 层评审时对每条 JOIN 的 ON 列核对索引；
  2. 优先 INNER JOIN：非必要不用 LEFT JOIN，保留优化器调序空间；
  3. JOIN 表数 ≤ 3：超过 3 张表拆成两次查询，在应用层拼装；
  4. 分页先取主键：PageHelper 深翻页场景改「先查 id 再 IN 查详情」；
  5. 监控：慢日志里出现 Using join buffer 直接进优化队列。

七、常见坑

  1. 大表当驱动表：探测次数被放大几个数量级；
  2. 被驱动表连接列没索引：BNL/Hash Join 兜底，性能断崖；
  3. 用 LEFT JOIN 换 INNER JOIN：丢掉调序自由；
  4. ON 里写过滤条件：外连接时语义不同，且优化器难以下推；
  5. JOIN 列类型不一致：隐式转换导致索引失效（MQ20）；
  6. STRAIGHT_JOIN 当常规手段：统计一变就翻车；
  7. JOIN 后排序：ORDER BY 落在被驱动表列上，容易 filesort。

八、版本差异

  • 5.6：只有 NLJ 与 BNL，join_buffer_size 是主要旋钮；
  • 5.7：BNL 支持多列 join buffer，block_nested_loop 开关；
  • 8.0：Hash Join（8.0.18）、BNL 默认被替代（8.0.20）、EXPLAIN ANALYZE 可看实际行数；
  • 8.4：连接算法与 8.0 一致，Hash Join 为无索引等值连接的默认；optimizer_switch 里 hash_join 可关。

九、课后小结

  • JOIN 的成本 = 驱动表行数 × 单次探测代价，驱动表越小越好；
  • 被驱动表连接列有索引 → NLJ；没索引 → BNL 或 Hash Join；
  • EXPLAIN 第一行就是驱动表，Using join buffer 就是没走索引；
  • LEFT JOIN 锁死驱动表，非必要不用；
  • Hash Join 是兜底而非目标，能加索引就加索引。

十、思考题

  1. 为什么「驱动表要小」？

    参考回答：嵌套循环里驱动表每取一行就要探测被驱动表一次，总代价 ≈ 驱动行数 × 单次探测代价。驱动表从 1000 万降到 1 万，探测次数直接降三个数量级。

  2. EXPLAIN 出现 Using join buffer (hash join) 说明什么？

    参考回答：说明这条等值连接没有可用索引，优化器改用了 Hash Join 兜底（8.0.18+，8.0.20 起成为默认）。它比 BNL 快，但仍意味着全表级扫描，正确做法是给被驱动表连接列建索引。

  3. LEFT JOIN 为什么不能随便调换表顺序？

    参考回答：LEFT JOIN 语义要求保留左表全部行，左表必须是驱动表，右表只是被探测方。换序会改变结果集语义，优化器不能自行调换。

  4. 大表 JOIN 大表都没有索引，能做什么？

    参考回答：短期靠 Hash Join 兜底并调大 join_buffer_size；中期按业务维度预聚合宽表或建冗余列；长期改分片键让 JOIN 变成单表查询或应用层拼装。

  5. JOIN 之后 ORDER BY 很慢，为什么？

    参考回答：ORDER BY 的列通常来自被驱动表，其结果集已经过 JOIN 拼装，无法借用任何单表索引顺序，只能 filesort。解法是让排序发生在单表阶段（先排序取主键再 JOIN），或把排序列冗余进驱动表。
