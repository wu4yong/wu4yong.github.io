增删改：INSERT / UPDATE / DELETE 与批量写入

写入性能不取决于单条语句快不快，而取决于事务多大、锁持有多久、binlog 有多胖｜依据 MySQL 8.4 DML 与 InnoDB 事务章节自绘

一、学习目标

  1. 写对 INSERT 的四种形态，理解 ON DUPLICATE KEY UPDATE 与 REPLACE 的语义差异；
  2. 知道 UPDATE / DELETE 为什么必须先看执行计划，以及大事务的真实代价；
  3. 把批量写入的五个参数（批量大小、事务边界、自增锁模式、连接参数、重试）配到位。

二、前置知识

前两讲的表结构与类型。会用 EXPLAIN、看得懂 SHOW ENGINE INNODB STATUS 的事务段即可。

三、理论讲解（官方定义）

DML 三类语句的官方语义：

  • INSERT：插入新行；INSERT ... ON DUPLICATE KEY UPDATE 在唯一键冲突时转成更新；REPLACE 则是先删后插；
  • UPDATE：修改匹配行，ROW_COUNT() 返回「实际改变的行数」，值没变的行不计入；
  • DELETE：按条件删除行；TRUNCATE TABLE 是 DDL，直接重建表、不可回滚、不写逐行 undo。

几个常被忽略的官方事实：

  • 8.0 起 innodb_autoinc_lock_mode 默认就是 2（交错模式），批量插入不再持有表级自增锁；
  • REPLACE 等价 DELETE + INSERT，会触发两次行操作、两次 binlog，自增 ID 也会跳；
  • ON DUPLICATE KEY UPDATE 的 ROW_COUNT() 语义是：插入 1、更新 2、值没变 0；
  • UPDATE / DELETE 不带 WHERE 不是「快」，而是把整表行锁住并写入巨量 binlog。

四、原理拆解

同一条 INSERT，批量大小与事务边界不同，吞吐能差一个数量级｜依据 MySQL 8.4 InnoDB 与复制章节自绘

1. 四种 INSERT 怎么选

INSERT INTO t_order (order_no, amount) VALUES ('A1', 10.00);
INSERT INTO t_order (order_no, amount) VALUES ('A2', 20.00), ('A3', 30.00);   -- 多值，一次网络往返
INSERT INTO t_order_archive SELECT * FROM t_order WHERE created_at < '2022-01-01';
INSERT INTO t_order (order_no, amount) VALUES ('A1', 10.00)
  ON DUPLICATE KEY UPDATE amount = amount + VALUES(amount);

多值插入是把「N 次网络往返 + N 次解析」压成 1 次，最直接的提速手段。ON DUPLICATE KEY UPDATE 适合幂等写入，但注意它在冲突时先尝试插入再更新，会消耗自增 ID。

2. REPLACE 的隐性代价

REPLACE INTO t_user (id, nickname) VALUES (1, 'new');

语义是「删除冲突行 + 插入新行」：旧行的 created_at 丢失、触发器执行两次、从库多一条 DELETE 事件、AUTO_INCREMENT 继续前进。业务上想要「存在则更新」时，用 ON DUPLICATE KEY UPDATE。

3. UPDATE 的两个关键点

UPDATE t_order SET status = 2 WHERE id = 100;                     -- 主键定位，行锁
UPDATE t_order SET status = 2 WHERE created_at < '2022-01-01';    -- 范围更新，锁多行
  • WHERE 必须能走索引，否则扫描的每一行都加锁，等于放大锁范围；
  • 不要在大范围 UPDATE 里放函数（WHERE DATE(created_at) = ...），列被包住就用不上索引；
  • 大批量更新要分片循环 + 限流，每批 500~1000 行并提交，避免一个事务扛住几万行。

4. DELETE、TRUNCATE、软删除

方式 是否可回滚 空间回收 适用
DELETE 可以（大事务慎用） 不回收，留碎片 按条件删少量
TRUNCATE 不可回滚 直接重建表 清空整表
软删除标记 可以 不回收 需要审计/恢复

DELETE 删掉的行只是标记删除，页空间不会自动还给操作系统；大量删除后要评估 OPTIMIZE TABLE（会重建表，等同 DDL）。

5. 批量写入的五个参数

  1. 批量大小：单批 5001000 行或 14MB，太大触发 max_allowed_packet 与长事务；
  2. 事务边界：每批一个事务提交，别把百万行塞进一个事务；
  3. 自增锁模式：innodb_autoinc_lock_mode=2（8.0 默认），交错分配，批量插入不互相阻塞；
  4. 连接参数：rewriteBatchedStatements=true 让驱动把多条 INSERT 合成多值语句；
  5. 重试与幂等：唯一键 + ON DUPLICATE KEY UPDATE，死锁/超时按指数退避重试。

五、场景说明

  1. 订单落库：唯一键 order_no + ON DUPLICATE KEY UPDATE 做幂等；
  2. 数据导入：LOAD DATA 最快，其次多值 INSERT，最差逐条 INSERT；
  3. 状态批量流转：按主键区间分批 UPDATE，每批提交并记录进度；
  4. 历史数据清理：按时间分区 + DROP PARTITION，比 DELETE 百万行优雅得多；
  5. 归档表迁移：INSERT ... SELECT + 分批，配合主从延迟监控。

六、示例代码/实操步骤

1. 幂等写入

INSERT INTO t_order (order_no, amount, status)
VALUES ('A1001', 99.00, 0)
ON DUPLICATE KEY UPDATE
  amount = VALUES(amount),
  status = VALUES(status),
  updated_at = CURRENT_TIMESTAMP(3);

SELECT ROW_COUNT();   -- 1 插入 / 2 更新 / 0 无变化

2. 分批更新模板

-- 第一批
UPDATE t_order SET status = 3 WHERE status = 1 AND id BETWEEN 1 AND 1000 LIMIT 1000;
-- 后续按上一批最大 id 推进，直到 ROW_COUNT() = 0

LIMIT 只在该语句是单表 UPDATE 时合法，且能防止单条语句锁太多行。

3. 大批量导入

mysql -uapp_rw -p demo -e "LOAD DATA LOCAL INFILE '/tmp/orders.csv' INTO TABLE t_order
FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '\"'
LINES TERMINATED BY '\n' IGNORE 1 LINES (order_no, amount, status);"

LOAD DATA 比逐条 INSERT 快一个量级，注意客户端要开 local_infile。

Java 侧怎么落地：批量写入的三层配置

  1. 连接参数：
spring:
  datasource:
    url: jdbc:mysql://10.0.0.11:3306/demo?rewriteBatchedStatements=true&useServerPrepStmts=true&cachePrepStmts=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai

rewriteBatchedStatements=true 是关键：不开它，addBatch 仍是一条条发。

  1. 代码层批量提交：
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void flushBatch(List<Order> batch) {
    jdbcTemplate.batchUpdate(
        "INSERT INTO t_order(order_no, amount, status) VALUES (?,?,?) " +
        "ON DUPLICATE KEY UPDATE amount=VALUES(amount), status=VALUES(status)",
        batch, 500, (ps, o) -> {
            ps.setString(1, o.getOrderNo());
            ps.setBigDecimal(2, o.getAmount());
            ps.setInt(3, o.getStatus());
        });
}
  1. 外层切批 + 边界事务：
for (List<Order> chunk : Lists.partition(orders, 500)) {
    retryTemplate.execute(ctx -> { orderWriter.flushBatch(chunk); return null; });
}

每次 flushBatch 独立事务（REQUIRES_NEW），失败只回滚这一批，配合唯一键幂等可安全重试；死锁重试间隔用 50ms 起、指数退避，最多 3 次。

  1. MyBatis 侧：ExecutorType.BATCH 的 SqlSession 要手动 flushStatements()，否则攒到 commit 才发；foreach 拼多值 INSERT 时注意单条 SQL 长度，超过 max_allowed_packet 会直接失败。

  2. 监控：批量任务要打「每批行数 / 耗时 / 失败重试次数」，并观察主从 Seconds_Behind_Master，大事务会把延迟拉爆。

七、常见坑

  1. UPDATE / DELETE 忘写 WHERE：全表锁 + 巨量 binlog，从库直接延迟几十分钟；
  2. REPLACE 当 upsert：丢字段、跳自增、触发器双触发；
  3. 一个事务写百万行：undo 膨胀、锁等待、崩溃恢复变慢；
  4. 开着 autocommit=1 逐条插：每行一次提交，吞吐极低；
  5. rewriteBatchedStatements 没开：以为在批量，其实还是逐条；
  6. 批量里混不同表：驱动无法合并，退化成多条语句；
  7. 删除后不回收空间：表越来越大，DATA_FREE 持续增长；
  8. 批量插入不排序主键：随机主键导致页分裂，写入越跑越慢。

八、版本差异

  • 8.0：innodb_autoinc_lock_mode 默认改为 2；VALUES() 函数在 ON DUPLICATE KEY UPDATE 中仍可用，但官方推荐改用行别名（8.0.19 起 AS new）；
  • 8.4：DML 语义无变化，mysql_native_password 默认关闭不影响写入；
  • 9.x：无破坏性变化；向量列的写入方式与普通列一致。

九、课后小结

  • 多值 INSERT 优先，LOAD DATA 最快；
  • 幂等用唯一键 + ON DUPLICATE KEY UPDATE，别用 REPLACE；
  • UPDATE / DELETE 必须能走索引，且分批提交；
  • 批量写入靠五个参数：批量大小、事务边界、自增锁模式、连接参数、重试幂等；
  • 大批量删除优先考虑分区与归档，而不是 DELETE。

十、思考题

  1. ON DUPLICATE KEY UPDATE 的 ROW_COUNT() 返回 2 意味着什么？

    参考回答：表示发生了唯一键冲突并执行了更新，且确实改动了行；返回 1 是纯插入，返回 0 是冲突但新值与旧值相同、没有实际变更。

  2. 为什么说 REPLACE INTO 在生产上要慎用？

    参考回答：它是「删除 + 插入」，会丢失未在语句中列出的列值（回到默认）、触发两次触发器、多写一条 DELETE binlog、消耗新的自增 ID，还可能级联删除子表数据。

  3. 一个事务里更新 10 万行会带来哪些具体问题？

    参考回答：undo 日志暴涨、行锁持有时间长导致其他事务等待、binlog 事件巨大使从库回放延迟、崩溃恢复时间变长；正确做法是按主键或时间分批，每批 500~1000 行提交。

  4. 开了 rewriteBatchedStatements=true 之后还有什么要注意的？

    参考回答：驱动只有在 SQL 结构完全一致、参数类型匹配时才能合并；单条合并后的语句不能超过 max_allowed_packet；另外批量里若混有不同表或不同 SQL，合并会退化为逐条发送。

  5. 为什么批量导入时建议按主键顺序写？

    参考回答：InnoDB 是聚簇索引，按主键递增插入只追加到 B+Tree 尾部；随机主键会不断在中间页插入，引发页分裂与缓冲池抖动，写入吞吐随数据量增大而下降。
