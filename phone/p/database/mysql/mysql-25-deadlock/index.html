死锁：成因、检测与四种规避

两个事务各持一把锁、又各等对方那把，等待图成环即死锁｜依据 MySQL 8.4 InnoDB Deadlocks 章节自绘

一、学习目标

  1. 能用「四条件 + 等待图」解释 InnoDB 死锁是怎么形成的；
  2. 分清死锁（1213）与锁等待超时（1205），知道各自该谁处理；
  3. 掌握四种规避手段及其代价，能在业务代码里落地重试。

二、前置知识

锁的类型（MQ24）、间隙锁（MQ23）、MVCC（MQ22）。死锁本质是「加锁顺序」问题，不是隔离级别问题。

三、理论讲解（官方定义）

官方对死锁的描述很直白：两个或多个事务互相等待对方持有的锁，谁也无法继续。InnoDB 会检测这种循环等待，并回滚其中一个事务（称为 victim），让其它事务继续。

两个错误码必须分清：

错误码 含义 触发条件
1213 Deadlock found when trying to get lock 检测到等待图成环，InnoDB 主动回滚一方
1205 Lock wait timeout exceeded 单纯等太久，超过 innodb_lock_wait_timeout（默认 50 秒）

死锁是立即失败，超时是等到不耐烦。前者靠检测，后者靠时间。

四、原理拆解

检测成环 → 选代价小的一方回滚 → 应用层整事务重试｜依据 MySQL 8.4 死锁检测与锁等待说明自绘

1. 四个必要条件

死锁要同时满足：互斥、持有并等待、不可剥夺、循环等待。数据库侧前三条几乎无法消除（锁天生互斥、事务天然持有、InnoDB 不会强行抢锁），所以工程上只做一件事：打断循环等待。

2. 一个最小的成环例子

-- 会话 A
START TRANSACTION;
UPDATE t SET v = 1 WHERE id = 100;   -- 持有 id=100
UPDATE t SET v = 1 WHERE id = 200;   -- 等待 id=200

-- 会话 B
START TRANSACTION;
UPDATE t SET v = 2 WHERE id = 200;   -- 持有 id=200
UPDATE t SET v = 2 WHERE id = 100;   -- 等待 id=100 → 成环

两边都不提交，等待图出现 A→B、B→A 的环，InnoDB 立刻选一方回滚。

3. 检测机制

  • innodb_deadlock_detect 默认 ON：每次加锁前做等待图检查，发现环就回滚；
  • 检测成本与并发事务数相关，热点行高并发时这项检查本身会吃 CPU，这也是有的系统把它关掉、退化为「靠超时」的原因（不建议默认关）；
  • innodb_print_all_deadlocks = ON 可把所有死锁详情写进 error log，排查时非常有用；
  • 现场信息在 SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段，包含两个事务的 SQL、持有锁与等待锁。

4. 业务里最常见的四种成因

成因 典型写法 为什么成环
交叉顺序 两个事务按不同顺序更新同一批行 最经典的 A→B、B→A
间隙锁 + 插入意向 一边 UPDATE 范围、一边 INSERT 到该间隙 间隙锁与插入意向锁互斥
唯一键冲突 INSERT ... ON DUPLICATE KEY UPDATE 并发 冲突路径上先加 S 锁再升级为 X
先查后改 + RPC FOR UPDATE 拿到锁后调远程接口 持锁时间被外部调用拉长

外键级联、REPLACE INTO、无排序的批量 UPDATE 也常出现在死锁日志里。

5. 四种规避手段

  1. 统一加锁顺序：批量更新前按主键排序，或按固定业务键排序，让所有事务走同一方向；
  2. 缩短事务：锁内不做网络调用、不做大批量计算，拿锁即改即提交；
  3. 降低隔离级别到 RC：RC 下普通 UPDATE 不加间隙锁，能消掉一大类「间隙 + 插入」死锁（需评估幻读语义）；
  4. 应用层重试 + 退避：捕获 1213 后整事务重来，间隔指数增长，并保证操作幂等；1205 同理。

补充两条：把大事务拆成小批（每批 500 行内）、给热点行加应用层分布式锁把并发收窄。

五、场景说明

  1. 库存扣减：UPDATE stock SET n = n - 1 WHERE sku = ? AND n >= 1，单行条件更新，天然不交叉；
  2. 订单状态机：WHERE id = ? AND status = ?，用条件更新替代先查后改；
  3. 批量对账：按 id 升序分批，每批独立提交；
  4. 消息表抢占：SELECT ... FOR UPDATE SKIP LOCKED，让多个 worker 各取各的，避免互相等待；
  5. 秒杀：库存行是热点，重试必须幂等，否则回滚后重放会多扣。

六、示例代码/实操步骤

1. 复现一次死锁

-- 两个会话交替执行，最后一步必有一方报 1213
-- A: UPDATE t SET v=1 WHERE id=100;  UPDATE t SET v=1 WHERE id=200;
-- B: UPDATE t SET v=2 WHERE id=200;  UPDATE t SET v=2 WHERE id=100;

2. 打开死锁日志

SET GLOBAL innodb_print_all_deadlocks = ON;
SHOW VARIABLES LIKE 'innodb_deadlock_detect';
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';

之后每个死锁都会写进 error.log，字段包含 TRANSACTION、HOLDS THE LOCK(S)、WAITING FOR THIS LOCK TO BE GRANTED。

3. 用视图看当前等待关系

SELECT * FROM performance_schema.data_lock_waits;
SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx ORDER BY trx_started;

data_lock_waits 给出「谁在等谁」，innodb_trx 给出事务开始时间与正在跑的 SQL，两边一对就能定位。

4. Java 侧怎么落地：重试模板

// 关键点：整事务重试 + 指数退避 + 幂等
for (int i = 0; i < 3; i++) {
    try {
        return txTemplate.execute(status -> doBiz(id));
    } catch (DeadlockLoserDataAccessException | CannotAcquireLockException e) {
        sleep((long) Math.pow(2, i) * 50);   // 50 / 100 / 200 ms
    }
}
throw new BizException("并发冲突，请重试");

落地要点：

  • Spring 的 DeadlockLoserDataAccessException 对应 1213，CannotAcquireLockException 对应 1205，两者都按可重试处理；
  • 事务方法必须由代理调用（同类内部 this 调用不走事务），@Transactional 才生效；
  • 重试必须幂等：用业务唯一键或状态机条件更新兜底，不要「先查再插」；
  • 批量更新在 Java 侧先 sort by id 再 IN 或分批，顺序统一；
  • 事务里禁止 RPC / 发消息，把外部调用挪到事务提交之后；
  • 死锁率作为监控指标：日志里按 LATEST DETECTED DEADLOCK 计数，突增就回查最近的 SQL 变更。

七、常见坑

  1. 把 1213 当致命错误直接抛给用户：它是可恢复的并发冲突，重试即可；
  2. 在事务里 try/catch 后继续用同一事务：死锁已回滚，连接上的事务状态已失效，必须整段重来；
  3. 重试不幂等：回滚后重放可能重复扣减；
  4. 只调大 innodb_lock_wait_timeout：只是把死锁变成更长的等待，没解决问题；
  5. 以为关了死锁检测就没死锁：只是变成靠超时发现，故障更慢更隐蔽；
  6. ON DUPLICATE KEY UPDATE 无脑用：高并发下冲突路径的锁升级很容易死锁；
  7. 批处理不排序：两个批次方向相反就会互相等。

八、版本差异

  • 5.7：死锁信息同样在 SHOW ENGINE INNODB STATUS，锁视图为 information_schema.INNODB_LOCKS；
  • 8.0：新增 performance_schema.data_locks / data_lock_waits，innodb_deadlock_detect 默认开启，SKIP LOCKED 可用于队列式抢占；
  • 8.4：检测与回滚语义不变，innodb_lock_wait_timeout 默认仍为 50 秒；死锁详情建议统一走 error log + data_lock_waits，旧 INNODB_LOCKS 视图已移除。

九、课后小结

  • 死锁 = 等待图成环，InnoDB 检测到立刻回滚一方，报 1213；等太久是 1205；
  • 打断循环只需一招：统一顺序；其余手段都是辅助；
  • 间隙锁 + 插入意向锁是 RR 下特有的一类死锁，降 RC 可消除；
  • 应用层必须「整事务重试 + 退避 + 幂等」，否则重试会制造新问题；
  • 排查靠 error log 的 LATEST DETECTED DEADLOCK 与 data_lock_waits。

十、思考题

  1. 死锁与锁等待超时有什么本质区别？

    参考回答：死锁是等待图成环，InnoDB 检测到后立刻回滚一方（1213），不需要等满时间；锁等待超时只是等得太久（1205），环可能根本不存在。前者靠检测，后者靠计时。

  2. 为什么「统一加锁顺序」能解决绝大多数死锁？

    参考回答：环一定由方向相反的等待构成。所有事务按同一顺序（如主键升序）申请锁，等待关系只会单向传递，无法回到起点，环就不成立。

  3. 降隔离级别到 RC 为什么能减少死锁？

    参考回答：RC 下普通 UPDATE 不加间隙锁，只剩记录锁，消掉了「间隙锁 + 插入意向锁」这类互斥；代价是失去 RR 的可重复读与部分防幻读能力。

  4. 捕获 1213 之后为什么必须整事务重试，不能只重跑最后一条 SQL？

    参考回答：InnoDB 回滚的是整个事务，之前已执行的语句效果全部撤销，事务对象也已结束；只补跑最后一条会丢掉前面的写，数据就错了。

  5. innodb_deadlock_detect = OFF 会怎样？

    参考回答：不再做等待图检测，死锁不会被立即发现，只能等 innodb_lock_wait_timeout 超时后报 1205，故障持续时间变长、定位更难；只有在检测本身成为 CPU 瓶颈且业务能接受长等待时才考虑。
