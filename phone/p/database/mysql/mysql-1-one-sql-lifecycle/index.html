分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

一条 SQL 的一生：五层各干一件事

连接层 → 解析器 → 优化器 → 执行器 → InnoDB，每一层都能单独出问题｜依据 MySQL 8.4 Reference Manual 自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用一条链路说清 SELECT 从 TCP 到磁盘页经过哪五层，每层干什么；
  2. 遇到「这条 SQL 慢」时，知道先判断哪一层慢，而不是上来就加索引；
  3. 能用 SHOW PROCESSLIST、EXPLAIN、SHOW ENGINE INNODB STATUS 三个命令把层次切开。

二、前置知识

无。会写 SELECT 就行，这一讲是整门课的地基。

三、理论讲解（官方定义）

MySQL 官方文档把服务器分成两部分：Server 层（连接处理、解析、优化、执行）和存储引擎层（真正读写数据）。这个划分不是教学需要，而是产品结构：SHOW ENGINES 能看到的每个引擎，都实现同一套 handler 接口，Server 层不必知道下面是 InnoDB 还是别的。

几个必须先记住的官方事实：

  • 一个连接对应一个线程（线程池插件除外）。连接建立时完成认证，此后这条连接上的语句由这个线程处理。
  • 解析产出的是语法树，语法错误在这一步就返回，根本走不到优化器。
  • 优化器决定的是「执行计划」：走哪个索引、连接顺序、是否用临时表。EXPLAIN 展示的就是它的决策结果，不是执行结果。
  • 执行器按计划逐行向存储引擎要数据，所以「扫了多少行」和「返回多少行」是两个数。
  • InnoDB 的数据以页为单位（默认 16KB），Buffer Pool 是页的缓存，磁盘 IO 以页为粒度。

所以「一条 SQL 慢」至少有五种完全不同的原因，混在一起谈优化就是瞎猜。

四、原理拆解

1. 五个阶段与各自成本

2. 优化器到底在算什么

优化器是基于成本的：它拿统计信息估「走这个索引要读多少页、多少行」，选成本低的那个。这解释了两个高频现象：

  • 表刚大批量导入、还没 ANALYZE TABLE，统计信息是旧的，优化器可能选错索引；
  • 同一个 SQL 在两个库上执行计划不同，因为两边的数据分布不同——执行计划依赖数据，不依赖 SQL 文本。

3. 执行器的「逐行」是什么意思

Server 层调用存储引擎接口，一次拿一行（或一批），在 Server 层做过滤、排序、聚合。所以：

  • 索引能过滤掉的条件下推到引擎（Using index condition）；
  • 引擎过滤不掉的，就要把行回传给 Server 层再判断，这就是「回表多、rows 大但 Extra 没有索引」的典型形态；
  • 排序、分组、DISTINCT 在 Server 层做，数据量大就会落到临时表或 filesort。

4. 存储层：一切落到页

InnoDB 读写的最小单位是页。一次点查的路径是：Buffer Pool 找页 → 没有就发起磁盘读 → 解析行 → 返回。这带来两个直接结论：

  • 命中率决定性能：Buffer Pool 装得下热数据，查询就是内存操作；
  • 写不是直接写磁盘：改的是 Buffer Pool 里的页（变成脏页），由后台线程刷盘，redo log 保证崩溃可恢复。

五、场景说明

按「症状 → 先查哪层」对照，能省掉大量无效动作：

  1. 连接都建不上：看 max_connections、Threads_connected、防火墙与 bind-address，与 SQL 无关；
  2. 简单查询也慢：先看 Buffer Pool 命中率与磁盘 IO，而不是加索引；
  3. 只有某条 SQL 慢：EXPLAIN 看 type、key、rows、Extra，判断是没走索引还是回表太多；
  4. 写入慢、偶发卡顿：SHOW ENGINE INNODB STATUS 看锁等待与脏页刷盘；
  5. 偶发但无法复现：慢日志 + performance_schema，因为问题可能只在特定参数组合下出现。

六、示例代码/实操步骤

1. 起一个实例（安装细节下一讲）

# Docker 起一个 8.4，够验证整条链路
docker run -d --name mysql84 -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=Root_1234 \
  -e MYSQL_DATABASE=demo \
  mysql:8.4

2. 造一张有索引的表，观察计划

CREATE TABLE t_order (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  status TINYINT NOT NULL,
  amount DECIMAL(12,2) NOT NULL,
  created_at DATETIME NOT NULL,
  KEY idx_user_status (user_id, status)
) ENGINE=InnoDB;

INSERT INTO t_order (user_id, status, amount, created_at)
SELECT FLOOR(RAND()*10000), FLOOR(RAND()*5), RAND()*1000, NOW()
FROM information_schema.columns LIMIT 2000;   -- 先灌点数据，别用空表看计划

ANALYZE TABLE t_order;

EXPLAIN SELECT id, amount FROM t_order WHERE user_id = 123 AND status = 1;

重点看四列：type（ref 表示走了索引）、key（用了哪个索引）、rows（预估扫描行数）、Extra（Using index 表示覆盖索引，Using filesort 表示要额外排序）。

3. 把层次切开

SHOW PROCESSLIST;                     -- 第 1 层：连接与当前语句
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_requests';  -- 逻辑读
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';          -- 物理读
SHOW ENGINE INNODB STATUS\G           -- 第 4、5 层：锁等待、脏页、历史

两个计数一除就是命中率：1 - reads / read_requests。命中率突然掉下去，说明热数据装不下了，加索引救不了。

Java 侧怎么落地：一次查询在代码里经过什么

  1. pom 里只需要一个 starter + 驱动（Boot 3 默认 HikariCP）：
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-jdbc</artifactId>
</dependency>
<dependency>
  <groupId>com.mysql</groupId>
  <artifactId>mysql-connector-j</artifactId>
  <scope>runtime</scope>
</dependency>
  1. 配置里必须显式写三件事：时区、SSL 与公钥检索。8.4 默认认证插件是 caching_sha2_password，非 SSL 连接首次认证需要 allowPublicKeyRetrieval=true，否则会报 Public Key Retrieval is not allowed。
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/demo?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Shanghai&characterEncoding=utf8
    username: app_rw
    password: App_1234
    hikari:
      maximum-pool-size: 10      # 先按 max_connections / 实例数 估，不要拍脑袋写 100
      connection-timeout: 3000   # 拿不到连接快速失败，避免请求线程全挂住

  1. 加一个能看计划的入口：开发环境用 EXPLAIN 跑的 SQL 和线上是同一条字符串，才能对得上；线上只允许 EXPLAIN，不允许 EXPLAIN ANALYZE（它会真执行）。

  2. 关键认知：Java 侧看到的「慢」往往不是 SQL 慢，而是拿连接慢（池太小或事务持有连接太久）。connection-timeout 报错 = 连接层问题；SQL 执行时间长 = 优化器/存储层问题，两者别混。

七、常见坑

  1. 用空表看执行计划：空表统计信息没有意义，rows 全是 1，计划不可信。
  2. 把 EXPLAIN 当执行结果：它只是估算，真实行数要看 EXPLAIN ANALYZE 或慢日志里的 Rows_examined。
  3. 只盯 type=ALL：全表扫描在小表上是合理的，几百行扫一遍比走二级索引回表更便宜。
  4. 以为加了索引就一定快：索引本身要维护、要占空间，选择性差的列（如 status 只有 5 个值）单独建索引基本无用。
  5. 忽略连接层：连接池打满时，所有 SQL 都「慢」，但数据库里根本看不到这些语句。
  6. 在从库上做写操作：8.4 的复制默认还是单向，从库写入会直接报错或造成主从数据不一致。

版本差异（8.0 / 5.7 标注）

  • 8.4 默认关闭了 mysql_native_password 插件，只有显式 --mysql-native-password=ON 才加载；老项目从 5.7/8.0 升上来最常见的「连不上」就是这个。
  • 8.0 起默认字符集是 utf8mb4、默认排序规则 utf8mb4_0900_ai_ci；5.7 默认是 latin1 + utf8mb4_general_ci，跨版本对比字符行为时要注意。

八、课后小结

  • MySQL 分 Server 层与存储引擎层，一条 SQL 依次经过连接、解析、优化、执行、存储五段；
  • 优化器是成本模型，EXPLAIN 是它的决策结果，不是执行结果；
  • 执行器逐行向引擎取数，「扫多少行」与「返回多少行」是两个数；
  • InnoDB 以 16KB 页为最小读写单位，Buffer Pool 命中率比索引更影响整体性能；
  • 判断慢先分层：连接 → 解析 → 优化 → 执行 → 存储，一层一层排除。

九、思考题

  1. EXPLAIN 显示 rows=10，但慢日志里 Rows_examined=200000，这两个数为什么差这么远？

    参考回答：EXPLAIN 的 rows 是优化器基于统计信息的估算，统计信息过期或数据分布倾斜时会严重偏低；Rows_examined 是执行器实际向引擎取的行数。差得远说明统计信息不可信，先 ANALYZE TABLE，再看是不是该用 EXPLAIN ANALYZE 确认真实行数。

  2. 一条 SELECT 在从库上比主库慢很多，但两边表结构和数据一样，最可能是什么原因？

    参考回答：先看两边执行计划是否一致（统计信息不同会导致选不同索引），再看从库是否在跑备份、大查询或复制应用线程抢 IO，最后看 Buffer Pool 大小是否不同（从库常被配得更小）。同 SQL 不同计划是最常见的原因。

  3. 为什么「加索引」不能解决 Buffer Pool 命中率低导致的整体变慢？

    参考回答：命中率低意味着热数据页装不进内存，每次查询都要发磁盘 IO；索引只能减少「要访问多少页」，不能减少「每次访问都要读盘」这件事。解法是扩大 Buffer Pool、拆小表或冷却数据，而不是继续加索引。

  4. 8.4 上升级后应用报 Public Key Retrieval is not allowed，根因是什么？

    参考回答：8.4 默认认证插件是 caching_sha2_password，在非 SSL 连接下首次认证需要客户端向服务端索取公钥来加密密码；JDBC 默认不允许这个动作。解法是启用 SSL，或在连接串加 allowPublicKeyRetrieval=true（仅限内网可信环境）。
