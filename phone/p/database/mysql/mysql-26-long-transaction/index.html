mysql-26-长事务与大事务

分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

长事务与大事务的代价

undo 难回收、快照被拖老、锁持更久、日志更大——四条链路同时恶化｜依据 MySQL 8.4 事务与 purge 章节自绘

一、学习目标

  1. 区分「长事务」与「大事务」，知道两者各自伤在哪；
  2. 会用 innodb_trx 与 History list length 量化一个事务的代价；
  3. 能把一个跑了十分钟的批处理拆成可控的小事务。

二、前置知识

MVCC 与版本链（MQ22）、redo/undo 的定位（本模块 MQ30、MQ31 会展开）。本篇先讲「代价」，机制留到后面。

三、理论讲解（官方定义）

官方没有给「长事务」下定义，只说明两件事：

  • 一致性读依赖活跃事务：REPEATABLE READ 下快照由第一次读时的活跃事务集合决定，事务不结束，这个快照就一直是老的；
  • purge 只能清理「早于所有活跃事务」的 undo：只要还有一个事务开着，比它新的版本都得留着。

所以判断标准不是「跑了多久」，而是它占了多少资源：修改行数、持有的锁、产生的 undo、写入的 redo 与 binlog 量。

四、原理拆解

purge 停在水位线下，历史版本只增不减；水位前移时集中清理，IO 抖动｜依据 MySQL 8.4 purge 与多版本说明自绘

1. 四条代价链路

代价 机制 表现
undo 堆积 purge 不能越过最老活跃事务 History list length 持续上升，undo 表空间膨胀
快照拖老 所有快照读都要穿越更长版本链 读变慢，读到「很久以前」的数据
锁持有变久 行锁、next-key、MDL 都跟着延长 并发下降，DDL 被卡在 MDL 队列
日志变大 一个事务只有一个提交点 redo 容量吃紧，binlog 单事件巨大，复制延迟

2. 长事务 ≠ 大事务

  • 长事务：时间跨度长，哪怕只改一行，只要不提交就一直拖住 purge 水位；
  • 大事务：一次改很多行，即使几秒钟结束，也会产生海量 undo、redo、binlog，提交瞬间刷盘形成尖刺。

最糟的是「又长又大」：批处理循环里忘了提交，跑半小时改了几十万行。

3. 量化手段

-- 最老的事务活了多少秒
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS secs,
       trx_rows_modified, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;

SHOW ENGINE INNODB STATUS 的 TRANSACTIONS 段里能看到 History list length，这个数持续上涨就是 purge 追不上的信号。

4. 拆分原则

  1. 按主键区间分批：WHERE id > ? ORDER BY id LIMIT 500，记下最后一条 id 作为下一批起点；
  2. 每批独立提交：批与批之间释放锁、推进 purge 水位；
  3. 失败可重入：每批幂等，重跑不会重复处理（用 processed 标记或唯一键）；
  4. 控制单事务行数：OLTP 建议个位数到几十行，批处理单批 500～1000 行；
  5. 只读事务也要短：长 SELECT 同样持有快照，会拖住 purge。

5. 大事务对复制的额外影响

binlog_format = ROW 时，一个大事务会产生一个巨大的 binlog 事件组，从库必须整组应用才能推进位点，期间 Seconds_Behind_Master 会跳变；主库提交瞬间还要等 redo 落盘，形成写入尖刺。

五、场景说明

  1. 数据迁移：按主键区间分批，每批 INSERT ... SELECT 后立即提交；
  2. 对账跑批：先读后写的逻辑拆成「读一批 → 处理 → 写一批」，不要一个事务贯穿全表；
  3. 发券/积分发放：10 万用户分 200 批，失败重试按批次粒度；
  4. 大 SQL 导入：拆文件、关自动提交再按批 COMMIT；
  5. 在线 DDL 前：先确认没有超过阈值的活跃事务，否则 ALTER 会卡在 MDL。

六、示例代码/实操步骤

1. 建监控视图（一眼看出长事务）

CREATE OR REPLACE VIEW v_long_trx AS
SELECT trx_id, trx_mysql_thread_id AS conn_id, trx_state,
       trx_started, TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS secs,
       trx_rows_modified AS rows_mod, trx_query
FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60;

2. 分批更新的标准写法

-- 每批 500 行，循环直到 affected_rows = 0
UPDATE t_task SET status = 1
WHERE status = 0 AND id > @last_id
ORDER BY id LIMIT 500;
-- 记录本批最大 id 作为下一轮的 @last_id

3. 观察 purge 是否追上

SHOW ENGINE INNODB STATUS\G   -- 看 TRANSACTIONS 段的 History list length
SELECT * FROM information_schema.INNODB_METRICS
WHERE NAME LIKE '%purge%';

4. Java 侧怎么落地：批处理与事务边界

  1. 事务只包住一批：for (batch : batches) { txTemplate.execute(s -> handle(batch)); }，绝不在循环外开一个大事务；
  2. 分页键用主键游标，不要 OFFSET（越翻越慢）；
  3. 单批大小可配：默认 500，按行宽与索引情况调整，压测后定值；
  4. 提交后做副作用：消息、缓存、远程调用都放事务提交后（TransactionSynchronization.afterCommit）；
  5. 超时保护：@Transactional(timeout = 30) 让失控事务自动回滚；
  6. 只读查询限时：SET SESSION max_execution_time = 5000（仅对 SELECT 生效）；
  7. 监控告警：v_long_trx 定时采样，超过 60 秒告警，配合 innodb_trx 输出到日志便于回溯。

七、常见坑

  1. 批处理忘提交：循环里只 execute 不 commit，跑到一半 undo 爆仓；
  2. 用 OFFSET 分页：深分页扫描量线性增长，事务越跑越久；
  3. 事务里调 RPC：等外部接口的几百毫秒全算在锁持有时间里；
  4. 只读事务无所谓：长 SELECT 同样拖住 purge 水位；
  5. 大事务失败后整段重跑：没有批次幂等标记，重复写入；
  6. 把 max_execution_time 当万能：只作用于 SELECT，DML 不受控；
  7. 提交后立刻大批量发消息：尖刺从数据库转移到 MQ，同样要限速。

八、版本差异

  • 5.7：redo 由 innodb_log_file_size + innodb_log_files_in_group 固定配置，扩容量要重启；
  • 8.0.30 起：改为 innodb_redo_log_capacity 统一管理，可动态调整，redo 文件放在 #innodb_redo 目录；旧的 innodb_log_file_size 已弃用；
  • 8.4：沿用 innodb_redo_log_capacity；binlog_format 默认 ROW，大事务对复制的放大效应更明显；innodb_purge_threads 默认 4，可按核数适度上调。

九、课后小结

  • 长事务伤在「不提交」：拖住 purge 水位与快照，与改了多少行无关；
  • 大事务伤在「一次改太多」：undo/redo/binlog 三处同时放大，提交瞬间尖刺；
  • 量化靠 innodb_trx 的 trx_started / trx_rows_modified 与 History list length；
  • 拆分靠主键游标 + 每批提交 + 幂等可重入；
  • 事务里禁止 RPC，副作用放 afterCommit，并给事务设超时。

十、思考题

  1. 一个只改了一行、但开了 10 分钟没提交的事务，危害在哪？

    参考回答：它是最老活跃事务，purge 不能清理比它新的任何 undo，历史版本持续堆积；同时它持有的那一行锁与快照都会保留十分钟，读操作要穿越更长的版本链。

  2. 为什么大事务会导致主从延迟突然变大？

    参考回答：ROW 格式下一个大事务是一个巨大的 binlog 事件组，从库必须整组应用完才能推进位点，期间延迟指标持续上涨，且无法被其它事务插队。

  3. 分批处理时为什么推荐主键游标而不是 OFFSET？

    参考回答：OFFSET 需要扫描并丢弃前 N 行，批次越往后越慢，事务时长不可控；主键游标直接定位区间，扫描量与批大小成正比。

  4. max_execution_time 能防住长事务吗？

    参考回答：不能完全防。它只对 SELECT 生效，UPDATE/DELETE 不受限制；DML 要用事务超时（@Transactional(timeout)）或应用侧限时。

  5. 提交后发消息与事务内发消息，差别是什么？

    参考回答：事务内发消息会把网络耗时算进锁持有时间，还会出现「消息已发、事务回滚」的不一致；放到 afterCommit 才既短又一致（更严格的做法是本地消息表，见 MQ27）。
