幻读与间隙锁：RR 下到底解决了什么

间隙锁不锁记录，只锁「不让别人插进来」；它纯粹是抑制性的，可以共存｜依据 MySQL 8.4 InnoDB Locking 章节自绘

一、学习目标

  1. 分清「快照读的幻读」与「当前读的幻读」，知道 RR 各解决了哪一种；
  2. 理解 next-key lock = 记录锁 + 间隙锁，以及「唯一索引等值查询不加间隙锁」这个例外；
  3. 能判断一条 UPDATE 到底锁了哪几段区间，并用 performance_schema.data_locks 验证。

二、前置知识

MVCC 与 ReadView（MQ22）、索引（MQ18）。本节所有锁都是加在索引记录上的，没索引就锁不住行——这条前提必须记住。

三、理论讲解（官方定义）

幻读：同一事务两次执行同一查询，第二次多出（或少掉）了行。

官方对间隙锁的几条关键表述：

  • 间隙锁锁的是索引记录之间的间隙，包括第一条之前与最后一条之后；
  • 间隙锁是纯粹抑制性的，唯一目的是阻止其他事务往这个间隙插入；共享间隙锁与排他间隙锁不冲突，可以共存；
  • 唯一索引上用等值条件查唯一一行时，只需要记录锁，不需要间隙锁（多列唯一索引只用部分列时仍会加间隙锁）；
  • 把隔离级别改成 READ COMMITTED 后，间隙锁被关闭（仅保留外键检查与唯一性检查所需的部分）。

RR 下 InnoDB 对搜索与索引扫描使用 next-key lock，从而阻止幻行。

四、原理拆解

索引里有 10、11、13、20，就把数轴切成五段；锁一段就是锁住「谁都不能插进来」｜依据 MySQL 8.4 InnoDB Locking 自绘

1. 快照读 vs 当前读

读法 语句 RR 下会幻读吗
快照读 普通 SELECT 不会。ReadView 固定，新插入的行本来就不可见
当前读 SELECT ... FOR UPDATE / UPDATE / DELETE 需要间隙锁兜住，否则会

所以「RR 解决了幻读」这句话要加限定：快照读靠 MVCC，当前读靠间隙锁。

2. next-key lock 的区间

索引值 10、11、13、20，区间被切成：

(-∞, 10]  (10, 11]  (11, 13]  (13, 20]  (20, +∞)

next-key lock 锁住「记录 + 它前面的间隙」。最后一段会额外锁住 supremum（大于所有值的伪记录）。

3. 间隙锁为什么不冲突

间隙锁的功能只有「阻止插入」，它不关心读或写具体行，因此：

  • 两个事务可以对同一个间隙各持一把间隙锁；
  • 间隙锁与间隙锁之间不互斥，只有「插入意向锁」会与间隙锁冲突；
  • 这也是间隙锁容易引发死锁的原因：大家都拿着不冲突的间隙锁，然后都想插入。

4. 唯一索引等值的例外

-- id 是唯一索引，等值命中唯一行 → 只加记录锁，不加间隙
SELECT * FROM t WHERE id = 100 FOR UPDATE;

-- 非唯一索引，或唯一索引只用部分列 → 会加间隙锁
SELECT * FROM t WHERE code = 'A1' FOR UPDATE;

这条例外很实用：能用唯一索引等值定位的加锁读，不会阻塞相邻区间的插入。

5. 插入意向锁

插入前，事务会在目标间隙上加「插入意向锁」（一种特殊的间隙锁）。它与已有间隙锁冲突，于是出现「A 锁了间隙，B 想插入被阻塞」的经典等待。

五、场景说明

  1. 库存扣减：UPDATE ... WHERE id = ? 走唯一索引，只锁一行，并发友好；
  2. 按状态批量处理：UPDATE ... WHERE status = 0 LIMIT 100，会锁住扫描到的区间，注意别让范围过大；
  3. 防重复插入：先 SELECT ... FOR UPDATE 再插入，非唯一索引下会锁间隙，并发插入互相阻塞；
  4. RC 业务：很多高并发系统改 RC，用唯一约束 + 捕获冲突代替间隙锁；
  5. 分页批量任务：按主键区间推进（WHERE id > last_id ORDER BY id LIMIT n），避免大范围锁。

六、示例代码/实操步骤

1. 复现当前读幻读被阻止

-- 索引 idx_user (user_id)，表里 user_id=1 有 2 行
-- 会话 A（RR）
START TRANSACTION;
SELECT COUNT(*) FROM t_order WHERE user_id = 1 FOR UPDATE;  -- 2，且锁住 (1] 附近间隙

-- 会话 B
INSERT INTO t_order (user_id) VALUES (1);   -- 被阻塞，直到 A 提交

若换成唯一索引等值（WHERE id = 5），B 插入相邻 id 不会被阻塞。

2. 查看到底锁了什么

-- 会话 A 执行加锁读后，另一会话查锁视图
SELECT ENGINE_TRANSACTION_ID, OBJECT_NAME, INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks;

-- 谁在等谁
SELECT * FROM performance_schema.data_lock_waits;

LOCK_MODE 出现 X 是 next-key，X,REC_NOT_GAP 是纯记录锁，X,GAP 是纯间隙锁，X,INSERT_INTENTION 是插入意向锁。

3. 用 RC 关掉间隙锁对比

SET SESSION transaction_isolation = 'READ-COMMITTED';
START TRANSACTION;
SELECT COUNT(*) FROM t_order WHERE user_id = 1 FOR UPDATE;  -- 不再锁间隙
-- 另一会话可插入成功 → 当前读出现幻读

4. 减少间隙锁影响的写法

-- 不好：范围大、锁住大量间隙
UPDATE t_order SET status = 1 WHERE created_at < '2022-01-01';

-- 好：按主键区间小批推进
UPDATE t_order SET status = 1 WHERE id > 1000 AND id <= 1100;

Java 侧怎么落地：加锁读的正确姿势

  1. 能用唯一索引等值就用：WHERE id = ? 只锁一行，不会锁间隙；
  2. 避免「先查后插」防重：改用唯一约束 + 捕获 1062，比 SELECT FOR UPDATE + INSERT 更省锁；
  3. 批量更新要分批：每批几十到几百行，按主键推进，缩短持锁时间；
  4. 死锁重试：捕获 1213（死锁）与 1205（锁等待超时），整事务重试，别只重试单条 SQL；
  5. 监控锁等待：把 data_lock_waits 的采样做成告警，锁等待数量突增往往先于故障；
  6. RC + 唯一约束：高并发写入场景用 RC 减少间隙锁，同时用唯一索引兜住正确性。

七、常见坑

  1. 以为 RR 完全没有幻读：当前读在没加间隙锁的场景（如 RC、唯一索引等值）仍可能出现；
  2. 在无索引列上做加锁读：锁会落到聚簇索引的隐藏行上，实际锁住的范围远超预期；
  3. SELECT FOR UPDATE 当读用：本来是快照读就够的场景，加了锁定读直接阻塞写入；
  4. 两个事务互相「先查后插」：各持间隙锁、各等对方释放，典型死锁；
  5. UPDATE ... WHERE 非索引列：扫描全表并锁住所有扫描到的记录，等于全表锁；
  6. RC 下仍依赖间隙锁防重：RC 关闭间隙锁，防重必须靠唯一约束；
  7. LOCK TABLES 与事务混用：表锁与行锁语义交织，容易自锁。

八、版本差异

  • 5.7：间隙锁行为与 8.0 一致；锁视图用 information_schema.INNODB_LOCKS / INNODB_LOCK_WAITS；
  • 8.0：performance_schema.data_locks / data_lock_waits 取代旧视图，字段更全；
  • 8.4：锁机制不变；默认 RR，innodb_lock_wait_timeout 默认 50 秒。

九、课后小结

  • 幻读分两种：快照读靠 MVCC 天然不幻，当前读靠间隙锁阻止；
  • next-key lock = 记录锁 + 前面的间隙；唯一索引等值只加记录锁；
  • 间隙锁是抑制性锁，彼此不冲突，只与插入意向锁冲突；
  • RC 关闭间隙锁，能减少死锁但放开幻读；
  • 锁加在索引上，没索引的加锁读会锁住大量行。

十、思考题

  1. RR 下普通 SELECT 会幻读吗？

    参考回答：不会。普通 SELECT 是快照读，用的是事务开始时的 ReadView，期间新插入的行对该快照不可见，所以行数不会变。

  2. 为什么唯一索引等值查询不需要间隙锁？

    参考回答：等值且唯一，结果最多一行，插入同值会撞唯一约束，插入其他值落在别的间隙，不会影响本次查询结果，所以只锁记录即可。

  3. 两个事务对同一间隙都持有间隙锁，会死锁吗？

    参考回答：间隙锁之间不冲突，本身不会；但如果两者随后都要往这个间隙插入，插入意向锁会与对方的间隙锁冲突，形成互相等待而死锁。

  4. 为什么 UPDATE ... WHERE 无索引列 = ? 很危险？

    参考回答：没有索引就只能全表扫描，InnoDB 会对扫描到的每条记录加锁，等于锁住整张表，并发写入全部被阻塞。

  5. 把隔离级别改成 RC 后，防重复插入该怎么做？

    参考回答：RC 关闭间隙锁，SELECT FOR UPDATE 拦不住并发插入，必须依赖唯一索引/唯一约束，插入冲突时捕获 1062 并做幂等处理。
