mysql-11-多表连接

分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

多表连接：INNER / LEFT、自连接与连接顺序

JOIN 的性能由「谁是驱动表 + 被驱动表有没有索引」决定，语法只决定语义｜依据 MySQL 8.4 Join 与优化器章节自绘

一、学习目标

  1. 分清 INNER JOIN 与 LEFT JOIN 的语义差异，知道 ON 与 WHERE 写错会把外连接变成内连接；
  2. 判断驱动表与被驱动表，理解为什么「被驱动表的连接列必须有索引」；
  3. 会用自连接解决层级、推荐关系这类问题，并知道什么时候该在应用层组装而不是 JOIN。

二、前置知识

单表查询与分组。看得懂 EXPLAIN 多行输出的 table、type、rows、key 即可。

三、理论讲解（官方定义）

SQL 的 JOIN 只有两种本质：内连接取交集，外连接保留一侧的全部行。LEFT JOIN 保留左表所有行，右表没匹配到就补 NULL；RIGHT JOIN 反过来；FULL OUTER JOIN MySQL 不支持，要 UNION 模拟。

官方要点：

  • 8.0.18 起引入 hash join，等值连接且被驱动表没索引时，优化器可能选它而不是嵌套循环；
  • 连接顺序由优化器基于统计信息决定，STRAIGHT_JOIN 可强制按书写顺序；
  • ON 是连接条件，WHERE 是结果过滤——外连接里两者不可互换。

四、原理拆解

有索引走嵌套循环，没索引可能走 hash join，代价差一个量级｜依据 MySQL 8.4 Optimizer 与 8.0.18 Hash Join 说明自绘

1. ON 与 WHERE 的真正区别

-- 正确：左表全部保留，右表没匹配显示 NULL
SELECT o.id, u.nickname
FROM t_order o
LEFT JOIN t_user u ON u.id = o.user_id;

-- 错误：WHERE 把 NULL 行过滤掉了，等价于 INNER JOIN
SELECT o.id, u.nickname
FROM t_order o
LEFT JOIN t_user u ON u.id = o.user_id
WHERE u.status = 1;

第二条里，未匹配的右表行 u.status 是 NULL，NULL = 1 为 UNKNOWN，整行被丢弃——外连接退化成内连接。想「只统计有效用户但仍保留订单」，要写成 ON u.id = o.user_id AND u.status = 1。

2. 驱动表怎么选

  • 驱动表是外层循环，行数越少越好；
  • 被驱动表的连接列必须有索引，否则每一行都要全表扫；
  • 优化器通常选「过滤后行数少」的表做驱动，统计信息过期时会选错，此时 STRAIGHT_JOIN 或 ANALYZE TABLE 纠正；
  • 三表以上连接，EXPLAIN 的 table 列从上到下就是执行顺序。

3. 连接算法

算法 触发条件 特征
Nested Loop 被驱动表连接列有索引 最常见，ref / eq_ref
Block Nested Loop 无索引、无 hash join 条件 8.0 之前的老路径，较慢
Hash Join 等值连接且无可用索引 8.0.18 起，Extra 显示 Using join buffer (hash join)
Batched Key Access 有索引且开启 MRR/BKA 批量取键，减少随机 IO

hash join 不是万能：它要建哈希表、吃内存，被驱动表很大时也会溢出到磁盘。

4. 连接列必须「同型同规则」

连接列的类型、字符集、排序规则要一致：

  • INT 连 BIGINT 可以，但 VARCHAR 连 INT 会触发隐式转换，索引失效；
  • 两表字符集或排序规则不同（如 utf8mb4_general_ci 与 0900_ai_ci），轻则报 Illegal mix of collations，重则索引失效；
  • 连接列长度差太多（VARCHAR(32) 连 VARCHAR(255)）不影响索引使用，但要注意比较语义。

5. 自连接

层级结构（分类树、组织架构）常用自连接：

SELECT c.id, c.name, p.name AS parent_name
FROM t_category c
LEFT JOIN t_category p ON p.id = c.parent_id;

推荐关系、共同好友这类「同表两组行」的查询也是自连接。层级很深时（超过 3 层）自连接会指数级膨胀，改用闭包表或递归 CTE（见 MQ13）。

五、场景说明

  1. 订单详情：订单 JOIN 用户 JOIN 商品，注意只对必要的表做连接；
  2. 报表关联：事实表 JOIN 维表，维表小、放驱动侧；
  3. 统计未匹配：LEFT JOIN ... WHERE 右表.id IS NULL 找「没有下单的用户」；
  4. 自连接层级：分类树取父级名称，只连一层；
  5. 大表关联：先各自过滤再连接，避免把全表拉进 JOIN。

六、示例代码/实操步骤

1. 建表与三表连接

SELECT o.id, o.amount, u.nickname, p.title
FROM t_order o
JOIN t_user u  ON u.id = o.user_id
JOIN t_product p ON p.id = o.product_id
WHERE o.status = 2
  AND o.created_at >= '2022-11-01'
ORDER BY o.id DESC
LIMIT 20;

三个连接列 u.id、p.id 都是主键，被驱动侧天然有索引，这是最理想形态。

2. 找出没有订单的用户

SELECT u.id, u.nickname
FROM t_user u
LEFT JOIN t_order o ON o.user_id = u.id
WHERE o.id IS NULL;

3. 检查执行顺序与算法

EXPLAIN FORMAT=TREE
SELECT o.id, u.nickname FROM t_order o JOIN t_user u ON u.id = o.user_id WHERE o.status = 2;

FORMAT=TREE 直接给出连接树与算法（8.0 起可用），比传统表格更直观。

4. 强制连接顺序（谨慎使用）

SELECT STRAIGHT_JOIN o.id, u.nickname
FROM t_order o JOIN t_user u ON u.id = o.user_id
WHERE o.status = 2;

只有确认优化器选错时才用；统计信息修好后应去掉，否则数据分布变化会再次踩坑。

Java 侧怎么落地：JOIN 还是应用层组装

  1. JOIN 只用于「强关联且必须一起返回」的数据：详情页主表 + 维表适合 JOIN；列表页要拼 5 张表时，优先各查一次在内存组装；
  2. 警惕 N+1：MyBatis 的嵌套查询（select 属性）默认逐行触发子查询，循环 1000 次就是 1000 次往返，改用 JOIN 一次取回或批量 IN；
  3. 结果映射要防重复：一对多 JOIN 会让主表行重复，resultMap 用 collection 聚合，或用 GROUP BY + GROUP_CONCAT 在 SQL 侧压平；
  4. 分页别在 JOIN 后做：先按主表分页取 ID，再回表关联，避免「JOIN 出百万行再 LIMIT 10」；
  5. 连接字段类型对齐：实体里 Long 对 BIGINT、String 对 VARCHAR，字符集由连接串统一，别让驱动做隐式转换。

七、常见坑

  1. LEFT JOIN 后 WHERE 过滤右表：退化成内连接；
  2. 被驱动表连接列没索引：退化成全表扫，hash join 也救不了大表；
  3. 连接列类型/字符集不一致：索引失效或直接报错；
  4. 多表 JOIN 后 SELECT *：列数爆炸、回表变多；
  5. LEFT JOIN 一对多再 COUNT(*)：计数被放大，要 COUNT(DISTINCT o.id)；
  6. 笛卡尔积：漏写连接条件，行数相乘直接把库拖垮；
  7. 深分页 + JOIN：先 JOIN 再 LIMIT，扫描量是页数的百倍。

八、版本差异

  • 5.7：无 hash join，等值无索引连接只能走 BNL，大表关联很慢；
  • 8.0：8.0.18 起引入 hash join；EXPLAIN FORMAT=TREE 可用；降序索引支持连接场景；
  • 8.4：连接算法与 8.0 一致，无破坏性变化。

九、课后小结

  • 内连接取交集，外连接保留一侧，FULL OUTER 需 UNION 模拟；
  • ON 管连接、WHERE 管结果，外连接里写错就退化；
  • 驱动表选小的，被驱动表连接列必须有索引；
  • 8.0.18 起无索引等值连接可走 hash join；
  • 连接列类型与字符集必须一致；
  • 深分页先分页主表再关联。

十、思考题

  1. 为什么 LEFT JOIN 后面加 WHERE 右表.col = 值 就变成了内连接？

    参考回答：未匹配的右表行在该列上是 NULL，NULL = 值 结果是 UNKNOWN，WHERE 只保留 TRUE，于是这些行被过滤掉，左表不再「全部保留」，语义上等价于内连接。

  2. EXPLAIN 里被驱动表 type=ALL 说明什么，怎么改？

    参考回答：说明该表在连接时走了全表扫描，通常是连接列没有索引或类型不匹配。给连接列建索引、统一类型与字符集，或者让小表做驱动表即可改善。

  3. 8.0.18 的 hash join 什么条件下才会被选中？

    参考回答：等值连接、被驱动表没有可用索引（或优化器判断哈希更便宜）时；Extra 会显示 Using join buffer (hash join)。它需要建哈希表，内存不足会落盘。

  4. 三表 JOIN 结果比预期多很多，先查什么？

    参考回答：先看是否有漏写或写错的连接条件导致笛卡尔积，再看是否有一对多关系被当成一对一（应使用 COUNT(DISTINCT ...) 或先聚合再连接）。

  5. 什么时候应该放弃 SQL JOIN，改在应用层组装？

    参考回答：关联表多、每张表过滤条件复杂、或只需要部分字段时，多次单表查询 + 内存组装往往更快也更可控；另外跨库、跨服务的数据本来也无法 JOIN。
