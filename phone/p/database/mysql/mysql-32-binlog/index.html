mysql-32-binlog

分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

binlog：三种格式与复制基础

ROW 记行镜像、STATEMENT 记 SQL 原文，复制与闪回都依赖 binlog｜依据 MySQL 8.4 Binary Log 说明自绘

一、学习目标

  1. 分清 redo、undo、binlog 三者各管什么；
  2. 说清 ROW / STATEMENT / MIXED 的差别，知道为什么必须用 ROW；
  3. 会看 binlog 事件序列、会用 binlog 做恢复与排障。

二、前置知识

redo 与两阶段提交（MQ30）、undo（MQ31）。binlog 是 Server 层日志，与存储引擎无关。

三、理论讲解（官方定义）

binlog（二进制日志）记录数据库执行过的写操作，以事件（event）为单位追加写入文件。用途有三：

  • 复制：从库重放主库的 binlog 保持数据一致；
  • 恢复：全量备份 + binlog 可做时间点恢复（PITR）；
  • 审计与排障：闪回、变更追溯。

它与 redo 的本质区别：redo 是引擎层的崩溃恢复日志（物理逻辑），binlog 是 Server 层的数据变更日志（逻辑）。

四、原理拆解

主库写 → dump 推送 → 从库 IO 线程落 relay log → SQL 线程重放｜依据 MySQL 8.4 Replication 说明自绘

1. 三种格式

格式 记录内容 优点 缺点
STATEMENT SQL 原文 日志小 NOW()、UUID()、随机函数导致主从不一致
ROW 每行 change 的前后镜像 精确、可闪回 日志大，批量更新放大明显
MIXED 按语句自动选择 折中 何时切换不透明，排障困难

8.x 默认 ROW，binlog_row_image 默认 FULL（记前后完整镜像）；MINIMAL 只记变更列，省空间但闪回与审计会缺信息。

2. 一次 UPDATE 的事件序列

Gtid / Query(BEGIN) → Table_map → Update_rows → Xid
  • Table_map 给出表 id 与列结构；
  • Update_rows 携带 before/after 镜像；
  • Xid 标记事务提交，与 redo 的 commit 对应。

3. 两阶段提交中的位置

  1. InnoDB 写 redo 并置 prepare；
  2. Server 层写 binlog 并 fsync（sync_binlog = 1）；
  3. redo 置 commit。

binlog 完整即视为事务成立，崩溃恢复按它前滚。

4. 复制链路与延迟来源

环节 组件 常见问题
主库 binlog 写入 大事务产生巨型事件
传输 dump 线程 网络抖动、max_allowed_packet 不足
从库接收 IO 线程 → relay log 磁盘慢
从库应用 SQL 线程 大事务、无索引更新导致长时间卡住

排查顺序：先看从库 SQL 线程是否卡住，再看主库 binlog 速率与单事件大小。

5. 保留策略

binlog_expire_logs_seconds 默认 30 天（2592000 秒）。保留窗口要覆盖「最坏情况下从发现故障到完成恢复」的时间，同时受磁盘容量约束。

五、场景说明

  1. 误删数据恢复：全量备份 + binlog 回放到误操作前一刻；
  2. 主从搭建：从库从备份 + binlog 位点追平；
  3. 数据审计：解析 binlog 得到行级变更；
  4. 闪回工具：基于 ROW 格式生成反向 SQL；
  5. CDC 同步：Canal / Debezium 订阅 binlog 投递到数仓。

六、示例代码/实操步骤

1. 基础配置查看

SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'binlog_format';
SHOW VARIABLES LIKE 'binlog_row_image';
SHOW VARIABLES LIKE 'sync_binlog';
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
SHOW MASTER STATUS;   -- 当前文件与位点（8.4 也可用 SHOW BINARY LOG STATUS）

2. 查看事件内容

SHOW BINLOG EVENTS IN 'binlog.000123' FROM 4 LIMIT 20;
-- 命令行解析
-- mysqlbinlog --base64-output=DECODE-ROWS -v binlog.000123 | less

3. 按时间点恢复

# 1) 恢复最近一次全量备份
mysql -uroot -p < full_20261212.sql

# 2) 回放 binlog 到误操作之前
mysqlbinlog --start-datetime="2026-12-12 09:00:00" \
            --stop-datetime="2026-12-12 10:29:59" \
            binlog.000123 | mysql -uroot -p

4. 清理旧日志

PURGE BINARY LOGS BEFORE '2026-11-12 00:00:00';
-- 或 PURGE BINARY LOGS TO 'binlog.000200';

不要直接 rm 文件，会破坏索引文件导致复制与重启异常。

5. Java 侧怎么落地：与 binlog 协作的实践

  1. CDC 订阅：Canal / Debezium 伪装成从库拉 binlog，Java 侧消费做缓存失效、ES 同步；
  2. 幂等消费：CDC 消息可能重复，用业务主键 + 版本号去重；
  3. 不要依赖 STATEMENT 语义：应用层避免在 SQL 里用非确定性函数做写操作；
  4. max_allowed_packet 对齐：大字段写入要保证主库、从库、CDC 客户端三处配置一致；
  5. 监控：SHOW REPLICA STATUS 的 Seconds_Behind_Source、Relay_Log_Space，以及 binlog 生成速率；
  6. 切换演练：定期用备份 + binlog 做一次 PITR 演练，确认 RTO 达标。

七、常见坑

  1. 改回 STATEMENT 省空间：非确定性函数直接导致主从不一致；
  2. binlog_row_image = MINIMAL：闪回缺旧值，审计也补不齐；
  3. 直接删 binlog 文件：索引与实际文件不匹配，重启或复制报错；
  4. 保留期过短：故障发现晚了，binlog 已被清理，无法 PITR；
  5. 大事务：单个事件巨大，从库应用卡住，延迟飙升；
  6. sync_binlog = 0：崩溃丢事务，主库有数据、binlog 没有，从库追不上；
  7. 误以为 binlog 能替代备份：它只有变更，没有基线数据。

八、版本差异

  • 5.6：默认 binlog_format = STATEMENT，expire_logs_days 按天；
  • 5.7：默认改为 ROW，新增 binlog_row_image；
  • 8.0：expire_logs_days 被 binlog_expire_logs_seconds 取代，支持 binlog 事务压缩（binlog_transaction_compression）；
  • 8.4：默认 ROW + sync_binlog = 1；复制相关视图统一为 SHOW REPLICA STATUS（SHOW SLAVE STATUS 仍兼容但已弃用）。

九、课后小结

  • binlog 是 Server 层逻辑日志，负责复制、恢复、审计；
  • ROW 精确但日志大，STATEMENT 小但会漂移，生产用 ROW；
  • 事件序列：Table_map → *_rows → Xid；
  • binlog 与 redo 靠两阶段提交对齐，binlog 完整即提交；
  • 保留期要覆盖恢复窗口，清理走 PURGE BINARY LOGS。

十、思考题

  1. redo、undo、binlog 各解决什么问题？

    参考回答：redo 解决崩溃恢复（已提交但未落盘的改动前滚）；undo 解决回滚与 MVCC 旧版本；binlog 解决复制、时间点恢复与审计。

  2. 为什么生产必须用 ROW？

    参考回答：ROW 记录行的前后镜像，重放结果确定，不受函数、时间、执行计划影响；STATEMENT 在非确定性函数、触发器、存储过程下会主从不一致。

  3. binlog 已被清理，还能做时间点恢复吗？

    参考回答：不能恢复到清理点之前。只能恢复到最近一次全量备份的时刻，之后的增量已丢失；所以保留期必须覆盖故障发现与恢复窗口。

  4. 从库延迟突然变大，先看哪里？

    参考回答：先看从库 SQL 线程是否卡在某个大事务或大范围更新上，再看 relay log 堆积与主库 binlog 生成速率；定位到具体事件后用 mysqlbinlog 解析该事务。

  5. sync_binlog = 1 与 innodb_flush_log_at_trx_commit = 1 为什么必须成对？

    参考回答：两者共同保证「redo 与 binlog 都落盘」才返回提交成功；任一关掉，崩溃时都可能出现一方有、一方无，导致主从不一致或丢数据。
