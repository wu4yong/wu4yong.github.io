分库分表：垂直、水平与分片键

垂直拆业务，水平拆数据；先想清楚分片键再动手｜依据分库分表实践与 MySQL 8.4 复制说明自绘

一、学习目标

  1. 分清垂直拆分与水平拆分解决的问题，不把两者混为一谈；
  2. 用三条硬要求评估分片键，避免「拆完之后查询全跨片」；
  3. 判断什么时候不该拆，先把手上的单机优化做完。

二、前置知识

索引与优化（M3/M6）、主从复制（MQ43）、事务与分布式事务（MQ27）。

三、理论讲解（官方定义）

MySQL 单表没有内建的分区到多实例能力（PARTITION 只是单实例内的物理分区）。跨实例的「分库分表」属于应用层或中间件层的逻辑分片：

类型 切分依据 典型形态
垂直分库 业务模块 订单库、用户库、商品库
垂直分表 字段冷热 主表 + 扩展表（大字段拆出）
水平分库 行数据取模/范围 order_db_0…N
水平分表 行数据取模/范围 order_0…N

四、原理拆解

拆容易，拼起来才是成本｜依据分库分表实践说明自绘

1. 垂直拆分的收益与代价

收益：库表数量下降、业务边界清晰、故障隔离。
代价：原来的跨表 JOIN 变成跨库调用，事务从本地事务变成分布式事务，报表要跨库聚合。

2. 水平拆分的核心是分片键

分片键（shard key）决定一行数据落在哪个分片，一旦选定几乎不可更改（改等于全量迁数据）。三条硬要求：

  1. 分布均匀：避免热点。按时间递增分片会导致最新分片承担全部写入；
  2. 覆盖主要查询：80% 的查询带上它，才不会跨分片；
  3. 业务不可变：用户 ID 可以，手机号（可能换绑）不行。

3. 跨分片的四件事

  • 跨分片查询：按非分片键查要扫全部分片，通常用「基因法」冗余或 ES 二级索引；
  • 跨分片分页：LIMIT 要各分片取 N 条再归并排序，深翻页几乎不可行；
  • 分布式事务：一次写跨两片，用本地消息表 / TCC / 最终一致；
  • 全局唯一 ID：自增在多分片冲突，用雪花算法或号段模式。

4. 路由与归并

分片中间件（如 ShardingSphere）负责：SQL 解析 → 路由到目标分片 → 各分片执行 → 结果归并（排序、聚合、分页）。归并发生在内存里，跨片结果集大时内存与网络都是瓶颈。

5. 什么时候不该拆

  • 慢在 SQL/索引 → 先优化查询（M6 全部内容）；
  • 单表行数没到量级 → 先归档冷数据、加分区；
  • 读压力大 → 先读写分离 + 缓存；
  • DDL 窗口长 → 先上在线 DDL（MQ50）。

五、场景说明

  1. 订单表按 user_id 分片：用户维度查询天然单片，商家维度查询走异步宽表；
  2. 日志表按月份分片：冷热分离，历史片可下线；
  3. 用户表按手机号 hash：登录场景单片命中；
  4. 商品表垂直拆：基础信息与详情（大文本）分开；
  5. 跨境多租户：按租户 ID 分片，天然隔离。

六、示例代码/实操步骤

1. 先量化，再决定拆不拆

SELECT TABLE_NAME, TABLE_ROWS,
       ROUND((DATA_LENGTH + INDEX_LENGTH) / 1024 / 1024 / 1024, 1) AS gb
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'shop'
ORDER BY DATA_LENGTH DESC LIMIT 10;

单表 > 5000 万行且年增 > 30%，或单库写入已成瓶颈，才进入拆分评估。

2. 分片键评估

-- 分布均匀性：取模后各桶行数是否接近
SELECT MOD(user_id, 8) AS bucket, COUNT(*) FROM t_order GROUP BY bucket;

-- 查询覆盖率：带分片键的 SQL 占比
-- 从慢日志/审计日志统计 WHERE 是否含 user_id

3. 中间件路由示例（ShardingSphere-JDBC）

rules:
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_${0..3}.t_order_${0..7}
        tableStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: order_mod
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: db_mod
    shardingAlgorithms:
      order_mod:
        type: MOD
        props:
          sharding-count: 8
      db_mod:
        type: MOD
        props:
          sharding-count: 4

4. 全局唯一 ID（号段模式）

-- 号段表
CREATE TABLE t_id_segment (
  biz_tag VARCHAR(64) PRIMARY KEY,
  max_id BIGINT NOT NULL,
  step INT NOT NULL DEFAULT 1000,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

UPDATE t_id_segment SET max_id = max_id + step WHERE biz_tag = 'order';
SELECT max_id, step FROM t_id_segment WHERE biz_tag = 'order';

5. Java 侧怎么落地：把分片当成基础设施

  1. 分片键从上下文取：ShardingContext.setUserId()，避免业务代码到处传参；
  2. 禁止无分片键查询：DAO 层拦截 WHERE 不含分片键的 SQL，强制走异步宽表；
  3. 跨片分页禁用：分页接口只提供游标式，offset 上限写死；
  4. 分布式事务选型：核心链路用本地消息表 + 补偿，非核心接受最终一致；
  5. 数据迁移双写：扩容时新旧分片双写 + 校验任务，切换后再关旧写。

七、常见坑

  1. 分片键选错：拆完发现 90% 查询要跨片；
  2. 按时间递增分片：所有写入压在一个分片；
  3. 自增主键跨片冲突：插入直接报唯一键冲突；
  4. 跨片 JOIN：中间件不支持或性能极差；
  5. 深翻页 + 跨片归并：内存与耗时双爆；
  6. 分布式事务当本地事务用：超时、悬挂、空回滚问题频发；
  7. 一次性全量迁移无回滚：切一半出问题无法退。

八、版本差异

  • 5.6/5.7：分片主要靠中间件（MyCat、Sharding-JDBC 早期版本）；
  • 8.0：PARTITION 能力增强（仍限单实例）、CTE/窗口函数让跨片聚合更易在应用层拼；
  • 8.4：分片仍属应用层能力，INSTANT DDL 让分片表的在线变更更容易；复制与 MGR 为分片提供高可用底座。

九、课后小结

  • 垂直拆业务、水平拆数据，两者解决不同问题；
  • 分片键决定成败：均匀、覆盖主要查询、业务不可变；
  • 跨片查询、分页、事务、全局 ID 是四笔固定成本；
  • 拆之前先把手上的单机优化与归档做完；
  • 扩容用双写 + 校验，避免一次性切换无回滚。

十、思考题

  1. 为什么「按时间」做分片键容易出问题？

    参考回答：写入总是集中在最新时间段，落在一个分片上，形成写热点；历史分片虽然空闲但无法分担新写入。且按时间查询之外的条件（如按用户查）会大量跨片。通常用哈希类分片键，或「时间 + 用户 ID」组合。

  2. 分片后 ORDER BY ... LIMIT 为什么变慢？

    参考回答：每个分片只能返回自己的前 N 条，中间件要把各分片结果归并排序后再取全局前 N 条。分片数越多、N 越大，归并成本越高；深翻页时几乎等于全量拉回内存排序。

  3. 手机号适合做用户表的分片键吗？

    参考回答：不适合。手机号可能换绑，属于可变字段，一旦变更就要迁数据；且同一用户可能在多个业务场景用不同标识查询。应选稳定的用户 ID，手机号作为普通唯一索引。

  4. 分片后自增主键为什么会冲突？

    参考回答：每个分片是独立的 MySQL 实例/表，自增序列各自独立，会生成相同的 ID。需要全局唯一方案：雪花算法、号段模式或 UUID（但 UUID 会带来索引膨胀与页分裂）。

  5. 什么情况下应该先优化而不是分片？

    参考回答：慢在缺索引、SQL 写法差、统计信息失真时，优化查询的收益远大于拆库；单表行数没到量级、读多写少时，读写分离 + 缓存更划算；只是 DDL 或备份窗口长，用在线 DDL 与增量备份即可。分片是最后手段。
