redo log：WAL、两阶段提交与崩溃恢复

改内存 → 写 redo → 提交返回 → 异步刷脏，四步把随机写变成顺序写｜依据 MySQL 8.4 InnoDB Redo Log 说明自绘

一、学习目标

  1. 说清 WAL 到底省了什么，为什么「先写日志」能让提交变快；
  2. 记住 redo 与 binlog 的两阶段提交顺序，能判断不同崩溃点的恢复结果；
  3. 会调 innodb_redo_log_capacity 与刷盘参数，知道代价在哪。

二、前置知识

InnoDB 架构（MQ28）、页与行格式（MQ29）。本篇讲「日志先行」这条主线，undo 与 binlog 分别在 MQ31、MQ32 展开。

三、理论讲解（官方定义）

InnoDB 使用 WAL（Write-Ahead Logging）：修改数据页时，先把变更以 redo 记录顺序写入日志并持久化，数据页本身留在 Buffer Pool 里等后台异步刷盘。崩溃重启后，用 redo 把已提交但未落盘的改动重放（前滚），用 undo 回滚未提交的事务。

redo 记录的是物理逻辑日志：对某个页做了什么修改（页号 + 偏移 + 内容），不是完整的 SQL。

四、原理拆解

redo prepare → binlog 落盘 → redo commit；崩溃恢复只认「binlog 完整」这一凭据｜依据 MySQL 8.4 崩溃恢复说明自绘

1. 一次提交的完整链路

  1. 事务修改 Buffer Pool 中的页，同时生成 redo 记录放进 Log Buffer；
  2. COMMIT 时按 innodb_flush_log_at_trx_commit 决定是否 fsync redo；
  3. Server 层把事务写入 binlog（按 sync_binlog 决定是否 fsync）；
  4. redo 打上 commit 标记，事务对客户端可见；
  5. 脏页由 page cleaner 异步刷盘，刷完后 redo 中对应部分可被覆盖（checkpoint 前移）。

2. redo 是环形空间

redo 容量固定（innodb_redo_log_capacity，默认约 100MB），写满就覆盖最老的日志。所以必须保证脏页刷得比覆盖快：write pos 追上 checkpoint 时会强制刷脏，业务上表现为周期性卡顿。

8.0.30 起 redo 由 #innodb_redo 目录下的一组文件管理（最多 32 个），旧的 innodb_log_file_size / innodb_log_files_in_group 已弃用。

3. 为什么必须两阶段提交

redo（引擎层）与 binlog（Server 层）是两份独立日志。若先写 redo 并提交、binlog 还没写就崩溃：主库有数据、从库没有，主从不一致；反之先写 binlog 再崩：从库有数据、主库没有。

两阶段提交把 binlog 当作「提交凭据」：

崩溃点 redo binlog 恢复动作
prepare 前 无 无 无事发生
prepare 后、binlog 前 prepare 缺 回滚
binlog 后、commit 前 prepare 完整 前滚提交
commit 后 commit 完整 无需处理

前提是「双一」：innodb_flush_log_at_trx_commit = 1 且 sync_binlog = 1。

4. 刷盘参数的取舍

参数 取值 语义 代价
innodb_flush_log_at_trx_commit 1（默认） 每提交 fsync 最安全
2 提交写 OS cache，每秒 fsync 宕机丢约 1 秒
0 每秒写并 fsync 丢 1 秒，MySQL 崩溃也丢
sync_binlog 1（默认） 每提交 fsync binlog 最安全
0 / N 交给 OS 或每 N 次 崩溃丢事务，主从不一致

5. 崩溃恢复流程

  1. 找到最近一次 checkpoint，从该 LSN 开始扫描 redo；
  2. 重放已提交事务（redo commit 或 binlog 完整的 prepare 事务）；
  3. 回滚未提交事务（用 undo）；
  4. 恢复期间 innodb_force_recovery 可按级别限制回滚动作，仅在数据抢救时使用。

五、场景说明

  1. 高并发写入：redo 顺序写是小事务快的关键，容量给足避免频繁强制刷脏；
  2. 大批量导入：单事务过大时 redo 生成速率超过刷脏，checkpoint 抖动；
  3. 崩溃恢复演练：故意 kill -9 后重启，验证已提交数据不丢；
  4. 主从切换：半同步 + 双一配置保证切换不丢数据；
  5. 磁盘规划：redo 与数据文件分开盘，避免刷脏与日志写互相抢 IO。

六、示例代码/实操步骤

1. 看 redo 相关配置

SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';
SHOW VARIABLES LIKE 'innodb_log_buffer_size';

2. 观察 checkpoint 与写入位置

SHOW ENGINE INNODB STATUS\G
-- LOG 段：Log sequence number / Log flushed up to / Last checkpoint at

三个值差距越大，说明未刷的脏日志越多；Last checkpoint at 长期不动要警惕。

3. 在线扩容 redo

SET GLOBAL innodb_redo_log_capacity = 4294967296;   -- 4GB

8.0.30+ 支持动态调整，后台按需重分配文件，业务低峰执行更稳。

4. Java 侧怎么落地：与刷盘策略对齐

  1. 别为了压测数字关双一：innodb_flush_log_at_trx_commit=2 能提升 TPS，但宕机丢数据，金融/订单场景不允许；
  2. 事务粒度要小：一个事务只写必要的行，redo 生成速率可控；
  3. 批量导入分批提交：每批 500～1000 行，避免 checkpoint 抖动；
  4. 连接池与提交模式：确认 autocommit 行为，批量场景显式控制事务边界；
  5. 监控：Innodb_os_log_written（redo 写入字节）、Innodb_log_waits（等待日志空间次数），后者非零说明 redo 容量偏小。

七、常见坑

  1. 把 redo 当归档：它会被覆盖，长期备份要靠 binlog；
  2. redo 容量设太小：频繁强制刷脏，出现周期性卡顿；
  3. 只调大 innodb_log_buffer_size 不调容量：缓冲只是攒批，环形空间才是根本；
  4. 以为改了 innodb_log_file_size 还有效：8.0.30 起已弃用，要看 innodb_redo_log_capacity；
  5. 关双一换性能上线：压测好看，故障时丢数据；
  6. redo 与数据同盘：刷脏与日志写抢 IO，延迟抖动；
  7. 崩溃恢复时间预估不足：redo 越大、脏页越多，重启越慢。

八、版本差异

  • 5.7：redo 由 innodb_log_file_size + innodb_log_files_in_group 固定配置，改大小要停库；
  • 8.0：支持在线调整 innodb_log_file_size；8.0.30 起引入 innodb_redo_log_capacity，文件迁到 #innodb_redo 目录；
  • 8.4：统一使用 innodb_redo_log_capacity，旧参数弃用；redo 与 binlog 的两阶段提交语义不变，双一仍是推荐配置。

九、课后小结

  • WAL 把随机写变顺序写，提交只需保证 redo 落盘；
  • redo 是环形空间，容量与刷脏速度必须匹配；
  • redo 与 binlog 靠两阶段提交对齐，binlog 是提交凭据；
  • 崩溃恢复先按 redo 前滚，再用 undo 回滚未提交；
  • 双一是数据安全的底线，性能优化别从这里抠。

十、思考题

  1. 为什么写了 redo 就能提前返回「提交成功」？

    参考回答：redo 持久化后，即使脏页还没落盘，崩溃重启也能按 redo 重放出同样的修改；数据页的落盘被推迟到后台，提交路径上只剩一次顺序写 + fsync。

  2. redo 与 binlog 分别属于哪一层，为什么不能合并成一份？

    参考回答：redo 是 InnoDB 引擎层的物理逻辑日志，用于崩溃恢复；binlog 是 Server 层日志，用于复制与审计，且要兼容非 InnoDB 引擎。两者职责与格式不同，只能靠两阶段提交保持一致。

  3. 崩溃发生在「binlog 写完、redo commit 之前」，为什么是前滚而不是回滚？

    参考回答：binlog 已完整落盘，说明事务在逻辑上已经成立，从库也会应用它；若本地回滚就会与从库不一致，因此按 binlog 判定为提交并前滚。

  4. Innodb_log_waits 持续增长说明什么？

    参考回答：事务在等 redo 空间，通常是 redo 容量太小或刷脏跟不上写入速度；需要扩容 redo 或降低单事务写入量。

  5. 把 innodb_flush_log_at_trx_commit 设为 2 省下的到底是什么？

    参考回答：省掉每次提交的 fsync，把刷盘交给操作系统每秒一次；代价是机器掉电或 OS 崩溃会丢失最后约 1 秒的已提交事务。
