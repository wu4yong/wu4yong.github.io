库与表：DDL、字符集与排序规则

建表只写 ENGINE 是不够的，字符集与排序规则决定了后面所有比较与索引行为｜依据 MySQL 8.4 Charset 与 InnoDB Online DDL 章节自绘

一、学习目标

  1. 写出经得起复查的 CREATE DATABASE / CREATE TABLE，把字符集、排序规则、引擎、主键一次写对；
  2. 说清字符集的四层继承与连接层三个变量，能定位「乱码」和「排序不符合预期」；
  3. 知道 8.4 里 ALTER TABLE 默认走 ALGORITHM=INSTANT，以及哪些变更一定会重建表。

二、前置知识

上一讲的客户端与实例。会用 SHOW CREATE TABLE、看得懂 information_schema 即可。

三、理论讲解（官方定义）

官方对字符集的定义分两层：字符集决定「哪些字符能存」，**排序规则（collation）**决定「怎么比较、怎么排序、唯一性怎么判定」。8.4 的服务端默认是 utf8mb4 + utf8mb4_0900_ai_ci。

几个容易记错的官方事实：

  • utf8 是 utf8mb3 的别名，最多 3 字节，存不了 emoji；8.4 里 utf8mb3 已标记弃用，新库一律 utf8mb4；
  • 字符集不是全局一个，而是四层继承：server → database → table → column，谁近谁生效；
  • SET NAMES utf8mb4 一次改三个会话变量：character_set_client、character_set_connection、character_set_results；
  • 8.4 起 ADD COLUMN / DROP COLUMN 的默认算法就是 INSTANT，不再需要显式写 ALGORITHM=INSTANT。

四、原理拆解

建库时定一层，建表时不写就继承，列上再写一次就覆盖；比较发生在连接层字符集上｜依据 MySQL 8.4 Charset 章节自绘

1. 四层继承：优先级从近到远

CREATE DATABASE demo
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_ai_ci;

CREATE TABLE demo.t_user (
  id      BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  nickname VARCHAR(64) NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

CREATE TABLE 不写 CHARSET 时继承库；列上再写 CHARACTER SET 才覆盖。一个库里混着两种字符集是最常见的隐式转换来源：两表 JOIN 时比较字段字符集不同，要么报 Illegal mix of collations，要么把其中一侧转成另一侧，索引直接失效。

2. 排序规则的三个后缀怎么读

utf8mb4_0900_ai_ci 拆开看：0900 是 UCA 9.0.0 算法版本，ai = accent insensitive（重音不敏感），ci = case insensitive（大小写不敏感）。于是 'a' = 'A' 成立，'café' = 'cafe' 也成立。

  • ..._as_cs：重音敏感、大小写敏感，适合需要严格区分的编码类字段；
  • ..._bin：按字节比较，最快也最「死板」，适合 token、哈希、大小写敏感的账号名；
  • utf8mb4_general_ci：8.0 之前的老默认，排序结果与 0900 不完全一致，新表不要再用。

唯一索引的判定也走排序规则：_ai_ci 下 'Tom' 与 'tom' 冲突，迁库时这点最容易踩。

3. 连接层：乱码真正发生的地方

客户端发来的是字节流，服务端要知道「这串字节按哪个字符集解释」，靠的就是 character_set_client；返回时按 character_set_results 编码。两边不一致 → 存进去是 ? 或乱码。

SHOW VARIABLES LIKE 'character_set%';
SET NAMES utf8mb4;              -- 等价于同时设 client / connection / results
SET collation_connection = utf8mb4_0900_ai_ci;

4. DDL 的三种算法与元数据锁

算法 做的事 代价
INSTANT 只改数据字典，旧行按「行版本」补齐默认值 毫秒级，不重建表
INPLACE 重建聚簇索引或二级索引，允许并发 DML 与表大小成正比
COPY 建新表、逐行拷数据，阻塞写 最慢，DDL 高峰期的元凶

8.4 的 INSTANT 能覆盖加列（任意位置）、删列、改列默认值、改 ENUM/SET 定义、重命名列；改数据类型、加索引、改字符集仍然是 INPLACE 或 COPY。另外 INSTANT 有硬限制：带 FULLTEXT 索引的表、ROW_FORMAT=COMPRESSED 的表、系统库表都不支持；连续 INSTANT 会累积行版本，INFORMATION_SCHEMA.INNODB_TABLES.TOTAL_ROW_VERSIONS 能查。

DDL 还要拿 MDL（元数据锁） 的排他锁。只要表上有未提交的长事务，DDL 就等着，后面所有查询一起排队——这就是「一条 DDL 把库拖死」的机制，lock_wait_timeout 默认值大到几乎等于不超时。

五、场景说明

  1. 新库初始化：一条 CREATE DATABASE ... utf8mb4 ... 0900_ai_ci 定调，后续建表不再逐条写字符集；
  2. 老库迁 utf8mb4：先 ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4（重建表，安排在低峰），再刷连接串；
  3. 加字段上线：8.4 直接 ADD COLUMN，默认 INSTANT，不用 gh-ost（细节见 MQ50）；
  4. 大小写敏感的业务：账号、优惠码这类字段显式 COLLATE utf8mb4_0900_as_cs 或 _bin；
  5. 给非 DBA 讲表结构：SHOW CREATE TABLE 的输出比任何 GUI 都准确。

六、示例代码/实操步骤

1. 建库建表并核对

CREATE DATABASE demo DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE demo;

CREATE TABLE t_order (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_no    VARCHAR(32)  NOT NULL,
  amount      DECIMAL(12,2) NOT NULL DEFAULT 0.00,
  created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

SHOW CREATE TABLE t_order\G
SELECT TABLE_NAME, TABLE_COLLATION FROM information_schema.TABLES WHERE TABLE_SCHEMA='demo';

2. 改字符集：库、表、列三种粒度

ALTER DATABASE demo CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;  -- 只影响以后新建的表
ALTER TABLE t_order CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;  -- 重建表并转数据
ALTER TABLE t_order MODIFY nickname VARCHAR(64) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_bin;  -- 只改一列

第一条不改存量表，这是最常见的误解；第二条才是真正转数据，务必评估耗时与锁。

3. 验证排序规则的实际行为

SELECT 'Tom' = 'tom' COLLATE utf8mb4_0900_ai_ci;   -- 1
SELECT 'Tom' = 'tom' COLLATE utf8mb4_0900_as_cs;   -- 0
SELECT 'café' = 'cafe' COLLATE utf8mb4_0900_ai_ci; -- 1

Java 侧怎么落地：连接串与建表脚本

  1. 连接串固定字符集（Connector/J 8.x 里 characterEncoding=utf8 即 utf8mb4）：
spring:
  datasource:
    url: jdbc:mysql://10.0.0.11:3306/demo?useUnicode=true&characterEncoding=utf8&connectionCollation=utf8mb4_0900_ai_ci&serverTimezone=Asia/Shanghai&rewriteBatchedStatements=true
  1. DDL 不写进 schema.sql 随手执行，用 Flyway / Liquibase 管版本，脚本里显式写 ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci；
  2. 实体字段长度与 DDL 对齐：@Column(length = 64) 只影响校验，不改变表结构，两边必须人工对齐；
  3. 排序规则相关查询不要靠 Java 侧 equalsIgnoreCase 兜底：数据库判重与 Java 判重规则不一致时，唯一键冲突会在插入时才暴露；
  4. 多租户/多库场景：连接池按库配 connectionCollation，别让默认值随驱动版本漂移。

七、常见坑

  1. ALTER DATABASE 以为改了所有表：它只管以后新建的表；
  2. utf8 存 emoji 报 Incorrect string value：那是 utf8mb3，换 utf8mb4；
  3. JOIN 两侧排序规则不同：报错或索引失效，统一到 0900_ai_ci；
  4. utf8mb4_general_ci 与 0900_ai_ci 混用：唯一索引冲突判定不一致，迁库时数据对不上；
  5. DDL 撞上长事务：MDL 排队把整库拖慢，先 SHOW PROCESSLIST 找长事务再执行；
  6. 给大表 CONVERT TO CHARACTER SET：整表重建，务必低峰 + 备份，或走 MQ50 的在线方案；
  7. VARCHAR(255) 惯性写法：utf8mb4 下 255 字符可能占 1020 字节，组合索引很容易超 3072 字节上限。

八、版本差异

  • 8.0：默认已是 utf8mb4 + utf8mb4_0900_ai_ci；原子 DDL 从 8.0 起生效（DDL 要么全成功要么全回滚）；INT(11) 这类显示宽度自 8.0.17 起弃用，8.4 仍接受但无实际作用。
  • 8.4：utf8mb3 明确弃用；ADD/DROP COLUMN 默认 INSTANT；mysql_native_password 默认关闭（与建表无关，但影响建库后第一次连）。
  • 9.x：字符集层面无破坏性变化，VECTOR 类型才登场（见 MQ06 版本差异）。

九、课后小结

  • 字符集四层继承，建库定调、建表继承、列上覆盖；
  • 排序规则决定比较与唯一性，新表统一 utf8mb4_0900_ai_ci，需要严格区分才用 _as_cs / _bin；
  • 乱码发生在连接层，SET NAMES 同时改三个变量；
  • DDL 有三种算法，8.4 加删列默认 INSTANT，改类型/加索引仍会重建；
  • DDL 的真正风险是 MDL 排队，不是执行时间。

十、思考题

  1. ALTER DATABASE demo CHARACTER SET utf8mb4 之后，库里已有的表字符集变了吗？

    参考回答：没变。库级字符集只是新建表的默认值，存量表在创建时就已固化自己的字符集，必须逐表 ALTER TABLE ... CONVERT TO CHARACTER SET 才会真正转换数据。

  2. 为什么 'Tom' = 'tom' 在默认排序规则下返回 1？

    参考回答：默认 utf8mb4_0900_ai_ci 的 ci 表示大小写不敏感，比较时先做大小写折叠；要区分就显式指定 utf8mb4_0900_as_cs 或 utf8mb4_0900_bin。

  3. 一条 ALTER TABLE ADD COLUMN 明明只花了几毫秒，为什么业务侧却出现几分钟的接口超时？

    参考回答：DDL 需要 MDL 排他锁。表上若有未提交的长事务，DDL 会一直等锁；等待期间它已持有 MDL 请求，后续查询全部排队，于是表现为「DDL 很快，但整库卡住」。应先定位长事务或设置较短的 lock_wait_timeout。

  4. 两表 JOIN 报 Illegal mix of collations，你怎么修？

    参考回答：先 SHOW CREATE TABLE 对比两表相关列的字符集与排序规则，把其中一侧 ALTER TABLE ... MODIFY col ... COLLATE utf8mb4_0900_ai_ci 对齐；临时应急可在查询里 COLLATE 强制统一，但会失去索引，只能当止血手段。

  5. 8.4 里哪些 ALTER TABLE 仍然是重建表？

    参考回答：改列数据类型、扩展 VARCHAR 长度、加/删索引、改字符集、ROW_FORMAT 变更等都不支持 INSTANT；加删列、改默认值、改 ENUM/SET 定义、重命名列才走 INSTANT。
