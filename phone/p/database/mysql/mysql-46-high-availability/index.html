高可用方案：MHA、MGR 与 Orchestrator

能自动切换只是及格线，切换后数据对不对才是重点｜依据 MySQL 8.4 Group Replication / 高可用实践自绘

一、学习目标

  1. 会比较 MHA、Orchestrator、MGR、云托管的切换粒度与数据风险；
  2. 知道切换后必须核对的三件事，避免「切过去了但数据不对」；
  3. 理解 MGR 多数派约束，能判断三节点够不够。

二、前置知识

主从复制与 GTID（MQ43）、半同步（MQ44）、binlog 与崩溃恢复（MQ30/MQ32）。

三、理论讲解（官方定义）

高可用（HA）的目标是缩短不可用时间并保证切换后数据正确。MySQL 侧没有内建的自动故障转移，需要外部组件：

方案 切换粒度 数据风险 复杂度
MHA 主从组，秒级 依赖 relay log 补齐，可能丢少量 中（脚本老旧）
Orchestrator 拓扑感知，自动/半自动 同 MHA，可配合半同步 中
MGR（单主） 多数派自动选主 几乎不丢 高（三节点、网络要求）
云多可用区 云平台编排 取决于同步模式 低（托管）

MGR 是 MySQL 官方的组复制方案（5.7.17 引入，8.0 稳定），基于 Paxos 变体，提供认证（certify）：事务在提交前先在各节点认证，冲突则回滚。

四、原理拆解

多数派是硬约束：三节点才能容忍一台故障｜依据 MySQL 8.4 Group Replication 说明自绘

1. 多数派是硬约束

MGR 要求多数节点在线才能提交（3 节点需 2 台）。这是它「几乎不丢数据」的代价：节点数越少越脆，跨机房部署还要评估认证 RTT。

2. 单主 vs 多主

  • 单主（single-primary）：只有 PRIMARY 接受写，切换由组内自动选举，最接近传统主从的使用方式；
  • 多主（multi-primary）：任一节点可写，冲突靠 certify 与回滚，自增主键、唯一键极易冲突，生产慎用。

3. 切换后必须核对的三件事

  1. GTID 集合完整：新主的 executed_gtid_set 应包含旧主已提交的全部事务，否则后续复制会冲突；
  2. 虚拟 IP / DNS 生效：应用重连要快于重试间隔，否则请求打到旧主；
  3. 回切预案：旧主恢复后不能直接以主身份回归，需重新加入并补数据。

4. 脑裂怎么防

切换组件必须能确认「旧主确实失联」（如通过仲裁节点、 fencing 机制）。仅凭「心跳超时」就提升从库，会出现双主同时写入，数据分叉不可逆。

5. 演练比方案更重要

任何 HA 方案没演练过都等于没有。演练要覆盖：主库 kill -9、网络分区、切换后回切、切换期间应用报错量。

五、场景说明

  1. 核心交易库：MGR 单主三节点，同城三机房；
  2. 中型业务：Orchestrator + 半同步，成本可控；
  3. 老系统改造：MHA 过渡，逐步迁 MGR；
  4. 云上部署：用云平台多可用区 + 只读实例；
  5. 报表库：不需要 HA，能重跑即可。

六、示例代码/实操步骤

1. MGR 三节点基础配置

# my.cnf（每个节点）
[mysqld]
server_id=1
gtid_mode=ON
enforce_gtid_consistency=ON
binlog_checksum=NONE
log_replica_updates=ON
binlog_format=ROW
plugin-load-add=group_replication.so
group_replication_group_name="8f0c2c1e-1a2b-4c3d-9e4f-5a6b7c8d9e0f"
group_replication_start_on_boot=OFF
group_replication_local_address="10.0.3.11:33061"
group_replication_group_seeds="10.0.3.11:33061,10.0.3.12:33061,10.0.3.13:33061"
group_replication_single_primary_mode=ON

2. 引导第一个节点并加入其余节点

-- 节点 A
SET GLOBAL group_replication_bootstrap_group=ON;
START GROUP_REPLICATION;
SET GLOBAL group_replication_bootstrap_group=OFF;

-- 节点 B、C
START GROUP_REPLICATION;
SELECT * FROM performance_schema.replication_group_members;

MEMBER_STATE 全为 ONLINE 才算成功。

3. 观察主节点与冲突

SELECT MEMBER_HOST, MEMBER_ROLE, MEMBER_STATE
FROM performance_schema.replication_group_members;

SELECT * FROM performance_schema.replication_group_member_stats\G
-- 关注 COUNT_TRANSACTIONS_ROLLED_BACK（回滚数）

4. Orchestrator 关键动作

orchestrator-client -c topology -alias prod
orchestrator-client -c graceful-master-takeover -alias prod -s 10.0.3.12

切换前确认 RecoveryAnalysis 里有「relay log 可补齐」的结论，否则会丢事务。

5. Java 侧怎么落地：切换期间应用要做什么

  1. 短连接超时：connectionTimeout 1~3s、socketTimeout 明确设置，避免线程长时间挂死；
  2. 重试要幂等：切换期间写请求重试必须业务幂等（唯一键或去重表）；
  3. DNS / VIP 优先：应用连虚拟地址而非固定 IP，由 HA 组件负责漂移；
  4. 熔断：连续 N 次连接失败进入熔断，避免雪崩式重试；
  5. 演练常态化：把切换演练写进季度计划，含应用侧报错率复盘。

七、常见坑

  1. 只有两节点：MGR 两节点无多数派，不如不用；
  2. 脑裂：未做 fencing，旧主仍可写；
  3. 切换后不校验 GTID：新主缺事务，后续复制报冲突；
  4. 多主模式跑高并发写：冲突回滚拖垮吞吐；
  5. 应用硬编码主库 IP：切换后仍连旧主；
  6. MHA 脚本年久失修：与新版本 GTID 语义不兼容；
  7. 从不演练：真故障时脚本跑不通。

八、版本差异

  • 5.6：无官方 HA，主要靠 MHA/MMM；
  • 5.7：MGR 引入（5.7.17），早期稳定性有限；
  • 8.0：MGR 稳定，支持多主、流控（flow control）、成员自动重加入；
  • 8.4：MGR 为推荐 HA 方案之一，group_replication_consistency 可调一致性级别。

九、课后小结

  • HA 的目标是「切得快」且「切完数据对」，两者缺一不可；
  • MHA/Orchestrator 依赖 relay log 补齐，可能丢少量；
  • MGR 靠多数派认证，3 节点最多容忍 1 台；
  • 切换后必查 GTID 集合、VIP 生效、回切预案；
  • 没演练过的 HA 方案等于没有。

十、思考题

  1. 三节点 MGR 为什么不能容忍两台故障？

    参考回答：MGR 要求多数派在线才能认证提交，3 节点的多数派是 2。两台故障只剩 1 台，无法形成多数派，集群进入只读/不可写状态。想容忍更多故障只能扩到 5 节点。

  2. MHA 切换「可能丢少量事务」，丢的是什么？

    参考回答：丢的是旧主已提交但尚未传送到从库的 binlog 事件。MHA 会用 relay log 与 binlog 做差异补齐，但若差异段在旧主磁盘上已不可读（宕机/损坏），就只能放弃这部分，造成丢失。

  3. 为什么切换后要核对 GTID 集合？

    参考回答：若新主的 executed_gtid_set 缺少旧主已提交的事务，后续从库接入或旧主回归时会因 GTID 缺失/冲突而复制中断；业务上则表现为「切换后数据少了」。

  4. 多主模式为什么生产慎用？

    参考回答：任一节点可写会带来写冲突，靠 certify 检测后回滚，冲突率高时吞吐骤降；自增主键、唯一索引、跨节点事务都容易踩坑。除非业务能按分片隔离写入，否则不如单主。

  5. 怎么防止切换时出现双主？

    参考回答：HA 组件必须有 fencing 能力（关停/隔离旧主，如断电、封网、STONITH），并基于仲裁节点判定失联，而不是仅凭单点心跳超时。应用侧配合 VIP 漂移，确保只有一个入口可写。
