mysql-54-incident

分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

常见故障与应急

先止血，再定位，后修复，最后写复盘 —— 顺序不能反｜依据 MySQL 8.4 故障排查 / 运维实践自绘

一、学习目标

  1. 掌握「止血 → 定位 → 修复 → 复盘」的标准动线，不在故障中乱试；
  2. 认识四类高频故障的典型信号与第一动作；
  3. 把复盘写成可执行的改进项，而不是「加强监控」四个字。

二、前置知识

监控四层指标（MQ51）、复制与高可用（MQ43/MQ46）、备份恢复（MQ49）、在线 DDL（MQ50）。

三、理论讲解（官方定义）

MySQL 官方在故障处理上强调「先保服务、后查原因」：错误日志（log_error）记录崩溃与复制错误，performance_schema 与 global_status 记录当时状态，innodb_trx/metadata_locks 记录阻塞链。故障处理的第一原则是缩小影响面，而不是立刻修复根因。

四、原理拆解

每一步都要留下记录，否则复盘只能靠回忆｜依据 MySQL 8.4 故障处理实践自绘

1. 四步动线的边界

  • 止血（分钟级）：摘流量、限流、切从库、重启单实例。目标是恢复服务，不是找原因；
  • 定位（十分钟级）：用监控四层指标缩到一个具体对象（一条 SQL、一个实例、一个锁）；
  • 修复（半小时级）：最小改动，且每一步都可回退；
  • 复盘（次日）：根因、为什么没提前发现、为什么止血慢、哪条规则可固化。

故障中最忌讳的两件事：在压力下做复杂变更、不记录时间点。后者会让复盘变成各说各话。

2. 四类高频故障的信号与第一动作

故障 典型信号 第一动作 别做什么
连接打满 Too many connections 杀空闲连接、扩池、限流 盲目调大 max_connections
CPU 打满 Threads_running 飙升 定位 Top SQL 并限流 直接重启实例
复制中断 Replica_SQL_Running=No 看 Last_SQL_Error 再决定跳过/重搭 不看错误就 SET GLOBAL skip
磁盘写满 binlog / 临时文件暴涨 清理 binlog、扩容 rm 正在写的文件

3. 为什么「重启」常常更糟

重启会触发 crash recovery：大实例可能要几分钟到几十分钟，期间完全不可用；同时重启会丢掉 Innodb_buffer_pool 里的热数据，恢复后一段时间命中率骤降、响应更慢；如果根因是慢 SQL 或锁，重启后很快复现。所以重启是最后手段，不是第一反应。

4. 止血的三个开关

  • 限流：在网关或连接池降并发，给数据库喘息；
  • 切流：切到从库/备库（注意复制延迟与只读一致性问题）；
  • 降级：关掉非核心功能（报表、导出），保住主链路。

5. 复盘的四个必答

  1. 直接原因是什么（指标/日志证据）；
  2. 为什么监控没提前发现（阈值？指标缺失？）；
  3. 为什么止血花了这么久（预案缺失？权限不足？）；
  4. 哪条规则/工具可以固化（自动化、检查项、限流阈值）。

五、场景说明

  1. 大促流量暴涨：先限流 + 扩池，事后按压测结论调容量；
  2. 新上线 SQL 全表扫描：定位到指纹后回滚发布或加索引；
  3. 主库磁盘满：清 binlog + 扩盘，同时检查 binlog_expire_logs_seconds；
  4. 复制中断：先看错误类型，数据不一致就重搭从库，不要盲目跳过；
  5. DDL 卡住引发全表超时：kill 长事务让 DDL 完成，或取消 DDL。

六、示例代码/实操步骤

1. 连接打满时的排查顺序

-- 当前连接与上限
SHOW STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';

-- 谁在占连接（按用户与来源聚合）
SELECT user, host, COUNT(*) AS cnt, MAX(TIME) AS max_idle
FROM information_schema.processlist
GROUP BY user, host ORDER BY cnt DESC;

-- 杀空闲连接（只杀 sleep 且超时的）
SELECT CONCAT('KILL ', id, ';')
FROM information_schema.processlist
WHERE COMMAND='Sleep' AND TIME > 600;

先确认是「连接泄漏」还是「真并发高」：前者杀连接 + 修连接池，后者扩容量 + 限流。

2. CPU 打满时的定位

SELECT DIGEST_TEXT, COUNT_STAR,
       ROUND(AVG_TIMER_WAIT/1000000000,2) AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;

SELECT * FROM information_schema.innodb_trx
ORDER BY trx_started LIMIT 5;

若 Top SQL 是同一指纹，先限流该接口；若是大量小查询，看连接数与 QPS 是否超容量。

3. 复制中断的处理

SHOW REPLICA STATUS\G
-- 看 Replica_SQL_Running、Last_SQL_Errno、Last_SQL_Error、Seconds_Behind_Source

处理顺序：先判断错误类型（唯一键冲突/表不存在/DDL 未执行）→ 确认数据是否已一致 → 一致才考虑 SET GLOBAL sql_replica_skip_counter=1（8.x 语法）→ 不一致则重搭从库（用 MQ49 的备份 + binlog 补齐）。

4. 磁盘写满的应急

# 看谁在涨
du -sh /var/lib/mysql/* | sort -h | tail
du -sh /var/lib/mysql/#innodb_redo

# 清理过期 binlog（用 SQL，不要 rm）
mysql -e "PURGE BINARY LOGS BEFORE DATE_SUB(NOW(), INTERVAL 3 DAY);"

永不 rm 正在被写入的 binlog 文件 —— 会导致复制中断、崩溃后无法恢复。

5. Java 侧怎么落地：把预案写进代码与平台

  1. 连接池配置可热调：maximumPoolSize 走配置中心，故障时可临时下调；
  2. 超时与重试有上限：connectTimeout / socketTimeout / 重试次数都要有界，避免线程堆积；
  3. 降级开关预先埋好：报表、导出、非核心查询有独立开关，一键关闭；
  4. 慢 SQL 熔断：拦截器统计某指纹耗时，超阈值直接拒绝并降级返回缓存；
  5. 故障记录自动化：告警触发时自动记录时间线与当时指标快照，供复盘使用。

七、常见坑

  1. 第一反应重启：crash recovery 期间服务更久不可用，热数据全丢；
  2. 不看错误就跳过复制：造成主从数据永久不一致；
  3. 盲目调大 max_connections：连接数上涨后线程争抢更严重；
  4. rm 正在写的 binlog：复制中断甚至实例崩溃；
  5. 故障中做 DDL 或大变更：二次故障概率极高；
  6. 不留时间线：复盘时无法还原顺序；
  7. 复盘只写「加强监控」：没有责任人与截止时间，等于没改；
  8. 预案只在某个人脑子里：他不在就没人会处理。

八、版本差异

  • 5.6/5.7：复制相关命令为 SHOW SLAVE STATUS、SET GLOBAL sql_slave_skip_counter；
  • 8.0.22+：改名为 SHOW REPLICA STATUS、sql_replica_skip_counter，CHANGE REPLICATION SOURCE TO 取代 CHANGE MASTER TO；
  • 8.0.30+：innodb_redo_log_capacity 统一 redo 容量，磁盘排查要看 #innodb_redo 目录；
  • 8.4 LTS：SHOW BINARY LOG STATUS 取代 SHOW MASTER STATUS；mysql_native_password 关闭后，客户端连不上会表现为认证错误而非网络错误，排查时别误判方向。

九、课后小结

  • 顺序不能反：止血 → 定位 → 修复 → 复盘；
  • 重启是最后手段，crash recovery 与热数据丢失会让故障更久；
  • 四类高频故障各有「第一动作」，背下来比临场想快；
  • 止血三开关：限流、切流、降级；
  • 复盘要落到「谁、何时、做什么」，否则等于没复盘。

十、思考题

  1. 故障时为什么「先止血」比「先找根因」更重要？

    参考回答：根因定位可能耗时数十分钟到数小时，而业务每秒都在受损。止血能立刻缩小影响面（限流/切流/降级），为定位争取时间。且很多故障在压力下会自我放大（连接堆积、锁等待扩散），先降压才能看清真实原因。

  2. 为什么「直接重启实例」往往让故障更久？

    参考回答：重启要做 crash recovery，大实例可能几分钟到几十分钟不可用；重启后 buffer pool 为空，热数据要重新预热，命中率骤降导致响应更慢；若根因是慢 SQL 或锁冲突，重启后立刻复现。等于用更长的不可用换一次没有解决根因的「重启」。

  3. 复制中断时，什么情况下可以跳过错误，什么情况下必须重搭？

    参考回答：可以跳过的前提是「该事务在主库的影响已确认、且跳过不会造成数据不一致」，例如从库已手工补过同一条数据导致的重复键。若错误是表不存在、DDL 未执行、数据页损坏，或无法确认一致性，就必须用备份 + binlog 重建从库，否则不一致会持续扩散。

  4. 磁盘被 binlog 写满，为什么不能直接 rm 文件？

    参考回答：正在写入的 binlog 文件被 rm 后，文件句柄仍被进程持有但目录项消失，复制线程与崩溃恢复会找不到文件，导致复制中断甚至实例无法启动。正确做法是 PURGE BINARY LOGS 让 MySQL 自己安全删除，并同步调小 binlog_expire_logs_seconds 或扩盘。

  5. 一份合格的故障复盘应该包含哪些内容？

    参考回答：时间线（每个动作的时间点与执行人）、影响面（用户/请求/金额）、直接原因与根因（附指标与日志证据）、为什么没提前发现（监控缺口）、为什么止血慢（预案/权限/工具缺口）、改进项清单（每项有责任人与截止时间）、以及可复用的规则或自动化改动。
