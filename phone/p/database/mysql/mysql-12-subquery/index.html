子查询与派生表：EXISTS、IN 与 LATERAL

子查询不是「嵌套的 SQL」，而是四种会被重写成不同执行计划的语法结构｜依据 MySQL 8.4 子查询优化章节自绘

一、学习目标

  1. 分清标量子查询、IN / NOT IN、EXISTS / NOT EXISTS、派生表四类，知道各自的优化路径；
  2. 说清 NOT IN 遇 NULL 的坑，以及 EXISTS 为什么在相关子查询里更稳；
  3. 会用 LATERAL 做「每行取 Top N」这类派生表做不到的事。

二、前置知识

JOIN 与聚合分组。知道优化器会做「半连接」「物化」这类改写即可。

三、理论讲解（官方定义）

按官方分类，子查询有三种位置：标量（返回单值）、行/表（返回结果集）、相关（引用外层列）。MySQL 优化器对它们的处理方式不同：

  • IN / EXISTS 子查询会被尝试改写成 semi-join（半连接），与 JOIN 同代价；
  • 无法改写时物化成临时表（materialization），再与外表连接；
  • 派生表（FROM (SELECT ...) t）在 8.0 默认尝试 merge（合并进外层查询），有聚合、窗口函数、LIMIT 时只能物化；
  • LATERAL（8.0.14 起）允许派生表引用左侧表的列，实现「逐行求值」的相关派生表。

四、原理拆解

能改写成半连接的子查询和 JOIN 一样快，改不写的就只能物化或逐行执行｜依据 MySQL 8.4 Optimizer 章节自绘

1. 标量子查询：逐行执行，最贵

SELECT o.id,
       (SELECT u.nickname FROM t_user u WHERE u.id = o.user_id) AS nickname
FROM t_order o;

优化器不一定能把它转成 JOIN，最坏情况是每行都触发一次子查询。等价写法直接 JOIN，通常更快也更可预测。

2. IN 与 EXISTS：语义相近，路径不同

-- IN：子查询结果会被物化或改写成半连接
SELECT * FROM t_order WHERE user_id IN (SELECT id FROM t_user WHERE status = 1);

-- EXISTS：相关子查询，通常改写成半连接，一旦命中即停止
SELECT * FROM t_order o
WHERE EXISTS (SELECT 1 FROM t_user u WHERE u.id = o.user_id AND u.status = 1);

IN 适合子查询结果集小、可去重的场景；EXISTS 在「只判断存在性」时更自然，优化器也更容易提前终止。二者在 8.0 里多数情况会被重写成同一类计划，但 NOT IN 有致命差异（下一条）。

3. NOT IN 的 NULL 陷阱

SELECT * FROM t_order WHERE user_id NOT IN (SELECT id FROM t_user);  -- 子查询含 NULL 就返回空
-- 安全写法
SELECT * FROM t_order o
WHERE NOT EXISTS (SELECT 1 FROM t_user u WHERE u.id = o.user_id);

NOT IN 等价于「对列表里每个值都不相等」，只要列表有一个 NULL，结果就是 UNKNOWN。NOT EXISTS 没有这个问题，且能改写成 anti-join。

4. 派生表：能 merge 就别物化

-- 可 merge：直接展开进外层，等价于普通 JOIN
SELECT * FROM (SELECT id, user_id, amount FROM t_order WHERE status = 2) t
WHERE t.amount > 100;

-- 只能物化：带聚合/窗口/LIMIT
SELECT * FROM (SELECT user_id, SUM(amount) gmv FROM t_order GROUP BY user_id) t
WHERE t.gmv > 1000;

EXPLAIN 里出现 <derived2> 就是物化了。物化本身不慢，慢的是「物化全量再过滤」——把过滤条件下推不进去时，先在内层缩小结果集。

5. LATERAL：逐行派生

SELECT u.id, u.nickname, o.id AS last_order, o.amount
FROM t_user u,
LATERAL (
  SELECT id, amount FROM t_order WHERE user_id = u.id ORDER BY id DESC LIMIT 1
) o;

普通派生表不能引用 u.id，LATERAL 可以。它适合「每个用户取最近一单」这类 Top-N-per-group，代价是逐行执行子查询，用户量大时要评估。

五、场景说明

  1. 存在性判断：EXISTS / NOT EXISTS 优先；
  2. 集合过滤：IN 配小结果集，大结果集改 JOIN；
  3. 每行取一条：LATERAL 或窗口函数（见 MQ13）；
  4. 先聚合再过滤：派生表 + 外层 WHERE，注意能否下推；
  5. 复杂报表：多层派生表会让优化器放弃 merge，尽量压平成 1~2 层。

六、示例代码/实操步骤

1. 同一需求的三种写法

-- 写法 A：IN（子查询结果小）
SELECT id, order_no FROM t_order WHERE user_id IN (SELECT id FROM t_user WHERE status = 1);

-- 写法 B：EXISTS（只判存在）
SELECT o.id, o.order_no FROM t_order o
WHERE EXISTS (SELECT 1 FROM t_user u WHERE u.id = o.user_id AND u.status = 1);

-- 写法 C：JOIN（要取用户字段）
SELECT o.id, o.order_no, u.nickname FROM t_order o
JOIN t_user u ON u.id = o.user_id AND u.status = 1;

三种写法在 8.0 里常被优化成相似计划，但 C 能顺便带出用户字段，实际项目里最常用。

2. 找出「没有订单的用户」的两种安全写法

SELECT u.id FROM t_user u WHERE NOT EXISTS (SELECT 1 FROM t_order o WHERE o.user_id = u.id);
SELECT u.id FROM t_user u LEFT JOIN t_order o ON o.user_id = u.id WHERE o.id IS NULL;

两者都能走 anti-join，选哪个看可读性；不要用 NOT IN。

3. 每个用户最近一单：LATERAL 与窗口函数

-- LATERAL
SELECT u.id, x.id AS order_id, x.created_at
FROM t_user u,
LATERAL (SELECT id, created_at FROM t_order WHERE user_id = u.id ORDER BY id DESC LIMIT 1) x;

-- 窗口函数（MQ13 详讲）
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY id DESC) rn
  FROM t_order o
) t WHERE rn = 1;

数据量大时窗口函数通常更快：一次扫描 + 排序，而 LATERAL 是逐行子查询。

4. 看优化器怎么改写的

EXPLAIN FORMAT=TREE
SELECT * FROM t_order WHERE user_id IN (SELECT id FROM t_user WHERE status = 1);

树里出现 semijoin、materialize 就能判断走了哪条路径。

Java 侧怎么落地：子查询该不该出现在代码里

  1. Mapper 里少写多层嵌套：两层以上派生表往往无法 merge，改成两次查询在内存合并更可控；
  2. IN 的参数化：IN (?) 只能传一个值，批量要用 foreach 拼列表；列表超过几千个元素要分批，避免 SQL 过长；
  3. EXISTS 配分页：EXISTS 不返回列，分页时先按主表分页再判断存在性；
  4. LATERAL 慎用于列表接口：每行一次子查询，1000 行就是 1000 次，接口 RT 直接翻倍；
  5. 别把子查询结果当缓存：同一子查询在循环里重复执行是典型 N+1，抽到外层或 Redis。

七、常见坑

  1. NOT IN 遇 NULL 返回空集：误判为「没有数据」；
  2. 标量子查询逐行执行：大表上直接超时；
  3. 派生表带 LIMIT 还想 merge：必然物化，外层过滤无法下推；
  4. IN 列表几千个值：SQL 过长、解析变慢；
  5. 相关子查询放在 SELECT 列表里：每行一次，最隐蔽的性能杀手；
  6. LATERAL 逐行执行：行数一多就雪崩；
  7. 子查询与外表类型不一致：触发隐式转换，索引失效。

八、版本差异

  • 5.7：子查询优化能力弱，很多 IN 直接物化；无 LATERAL；
  • 8.0：semi-join / anti-join 改写更完善，派生表 merge 更积极；8.0.14 起支持 LATERAL；EXPLAIN FORMAT=TREE 可看改写结果；
  • 8.4：优化器行为延续 8.0，无破坏性变化。

九、课后小结

  • 四类子查询：标量、IN、EXISTS、派生表，路径各不相同；
  • 存在性判断用 EXISTS，集合过滤用小结果集 IN，要字段就用 JOIN；
  • NOT IN 遇 NULL 恒空，一律换 NOT EXISTS；
  • 派生表能 merge 就快，带聚合/窗口/LIMIT 会物化；
  • LATERAL 用于逐行派生，注意它是「每行一次」。

十、思考题

  1. NOT IN 和 NOT EXISTS 的差别在哪，为什么后者更安全？

    参考回答：NOT IN 对列表逐值比较，列表含 NULL 时比较结果为 UNKNOWN，整个条件不成立，返回空集；NOT EXISTS 只判断子查询是否为空，不涉及 NULL 比较，且能被改写成 anti-join。

  2. 派生表什么时候会被物化，物化的代价是什么？

    参考回答：含聚合、窗口函数、DISTINCT、LIMIT 或 UNION 等无法合并的结构时物化；代价是要先把整个子结果算出来存进临时表，外层过滤无法下推，数据量大时会落盘。

  3. EXISTS 为什么常比 IN 快？

    参考回答：EXISTS 只关心「有没有一行匹配」，找到即停；IN 需要把子查询结果集算出来（或去重物化）再比较。不过 8.0 优化器常把两者改写成同类半连接，实际差异要看执行计划。

  4. LATERAL 与窗口函数都能做「每组取 Top 1」，怎么选？

    参考回答：窗口函数一次扫描 + 排序，适合大结果集；LATERAL 逐行执行子查询，行数少且子查询能走索引时更简单直观。数据量大优先窗口函数。

  5. 一个接口里出现 5 层嵌套子查询，你会怎么改？

    参考回答：先 EXPLAIN FORMAT=TREE 看哪些层被物化；把可独立执行的子查询提到应用层分批查询再合并；把存在性判断改成 JOIN 或 EXISTS；必要时建汇总表或加覆盖索引，把嵌套压到 1~2 层。
