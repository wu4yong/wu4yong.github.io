读写分离：中间件、客户端与延迟读一致性

路由放在哪一层，决定了改造成本与可观测性｜依据 MySQL 8.4 Replication / 读写分离实践自绘

一、学习目标

  1. 说清客户端路由、中间件代理、框架层三种方案的成本差异；
  2. 会判断「读到了旧数据」属于哪种延迟，并选对处置策略；
  3. 能设计一个不会把主库压垮的降级方案。

二、前置知识

主从复制链路（MQ43）、半同步与延迟（MQ44）。

三、理论讲解（官方定义）

读写分离不是 MySQL 的功能，而是部署与路由策略：写请求打主库，读请求打从库。MySQL 只负责把变更通过 binlog 复制到从库，不提供任何读写路由能力。

三种典型落地：

方案 位置 代表 特点
客户端路由 应用内 Spring AbstractRoutingDataSource 改造轻，但每套应用各写一遍
中间件代理 独立进程 ShardingSphere-Proxy、ProxySQL 对应用透明，多一跳网络
框架层（JDBC） Jar 包内 ShardingSphere-JDBC、MyCat 无额外跳数，可精细控制

四、原理拆解

Seconds_Behind_Source 不是唯一指标，也不是最准的｜依据 MySQL 8.4 复制延迟监控说明自绘

1. 「读到自己刚写的数据」为什么会失败

写主库 → 立刻读从库，从库还没回放到该事务，读到旧值。这类问题叫读己之写（read-your-writes），属于一致性范畴，不是「延迟高」这么简单。

2. 三种处置手段

策略 做法 代价
强制走主库 写后 N 秒内的读打主库 主库压力上升
会话粘滞 同会话固定同库 负载不均
半同步 + GTID 校验 读前确认从库已应用到该 GTID 实现复杂，最准

生产上常用组合：核心链路（下单、支付回查）强制走主库；列表与详情走从库 + 延迟阈值熔断。

3. 延迟不能只看一个数

  • Seconds_Behind_Source：只覆盖回放段；
  • Relay_Log_Space：反映拉取段积压；
  • GTID 差值：最可靠的一致性判断；
  • 心跳表时间差：端到端最直观。

4. 从库被摘除后会发生什么

路由层把读流量全压回主库，主库 QPS 瞬间翻倍，可能连锁雪崩。所以「延迟熔断」必须配限流：只把核心流量切回主库，其余降级返回缓存或排队。

五、场景说明

  1. 电商列表页：从库承接，可容忍秒级延迟；
  2. 订单详情：下单后 5 秒内强制主库；
  3. 报表与导出：专属从库，避免抢占业务从库；
  4. 大促扩容：临时加从库承接读峰值；
  5. 多机房：就近读本地从库，跨机房只做容灾。

六、示例代码/实操步骤

1. 客户端路由（Spring）

public class RoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return ReadWriteContext.isWrite() ? "master" : "replica";
    }
}
@Transactional            // 写事务
public void createOrder(Order o) { ... }

@Transactional(readOnly = true)   // 读事务
public Order queryOrder(long id) { ... }

2. 强制走主库的注解

@Master
public Order queryAfterPay(long orderId) { ... }

AOP 在方法进入时把 ReadWriteContext 标记为 write，退出时清理，避免线程池复用污染。

3. GTID 一致性读（简版）

-- 主库写入后拿到 GTID
SELECT @@GLOBAL.gtid_executed;

-- 从库侧等待到该 GTID
SELECT WAIT_FOR_EXECUTED_GTID_SET('3f9a...:1-88213', 1);

WAIT_FOR_EXECUTED_GTID_SET 超时会返回 1，应用据此决定回退主库。

4. 延迟探针

-- 从库
SHOW REPLICA STATUS\G   -- 采集 Seconds_Behind_Source、Relay_Log_Space
SELECT MAX(updated_at) FROM t_heartbeat;   -- 端到端时间差

5. Java 侧怎么落地：路由与降级的工程细节

  1. 事务内禁止切换数据源：一旦进入 @Transactional，全程同库，否则同一事务出现两个连接；
  2. 连接池隔离：主从各自独立 Hikari 池，从库池上限低于主库，避免把从库打满；
  3. 降级开关：配置中心一个 read-from-master 开关，应急时全量切主库；
  4. 灰度：新从库先接 5% 流量，观察延迟与错误率再放量；
  5. 可观测：埋点记录「走了哪个数据源 + 延迟值」，出问题能立刻定位。

七、常见坑

  1. 事务里混用主从：同一逻辑事务跨两个库，回滚不彻底；
  2. 线程池复用污染标记：上一个请求的 write 标记带到下一个请求；
  3. 从库延迟高仍全量读：读到旧数据且无从解释；
  4. 摘从库不限流：主库被打崩；
  5. 从库承接写：主从分叉（必须 super_read_only）；
  6. 只监控 Seconds_Behind_Source：拉取段断了也显示 0；
  7. 忽略连接建立耗时：多一跳代理后 P99 上升，误判为 SQL 慢。

八、版本差异

  • 5.6：无内置路由能力，全靠应用或中间件；
  • 5.7：WAIT_FOR_EXECUTED_GTID_SET 可用，一致性读有了官方函数；
  • 8.0：read_only / super_read_only 更严格，复制元数据表化；
  • 8.4：术语统一 source/replica，读写分离仍属部署策略，一致性读依赖 GTID 函数。

九、课后小结

  • 读写分离是路由策略，MySQL 本身不提供；
  • 三种落地各有成本，框架层 JDBC 通常最均衡；
  • 「读己之写」要用强制主库、会话粘滞或 GTID 校验解决；
  • 延迟要看四个指标，Seconds_Behind_Source 会骗人；
  • 熔断必须配限流，否则把从库问题变成主库故障。

十、思考题

  1. 为什么读写分离不能解决「读到自己刚写的数据」？

    参考回答：写走主库、读走从库，从库回放存在延迟，读请求可能落在尚未应用该事务的从库上，读到旧值。这是路由与复制延迟共同造成的，属于一致性设计问题，需要强制主库或 GTID 校验来解。

  2. 中间件代理相比客户端路由，优势和代价各是什么？

    参考回答：优势是对应用透明、集中治理（限流、审计、故障切换统一在代理层），多语言栈都能复用；代价是多一跳网络与独立运维，故障点多一个，P99 延迟可能上升。

  3. Seconds_Behind_Source = 0 但从库数据仍旧，可能是什么原因？

    参考回答：可能 IO 线程已断（Replica_IO_Running=No）而 applier 已追平，或从库被误写产生分叉，也可能是延迟指标采集口径问题。应同时检查 Relay_Log_Space、GTID 差值与心跳表。

  4. 延迟熔断为什么必须配限流？

    参考回答：摘除从库会把全部读流量压回主库，主库 QPS 骤增可能直接过载。限流能保证只有核心流量回主库，其余走缓存或排队，避免「从库小故障 → 主库大故障」。

  5. 事务方法里能不能中途切数据源？

    参考回答：不能。一个事务绑定一个连接，中途切换会造成同一逻辑事务跨两个库，回滚只对其中一个生效，数据不一致。数据源必须在事务开启前确定。
