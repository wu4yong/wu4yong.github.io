分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

优化器与统计信息：它凭什么选这个索引

优化器只做一件事：按估算成本挑最便宜的执行计划｜依据 MySQL 8.4 Optimizer / 统计信息与直方图说明自绘

一、学习目标

  1. 说清优化器做决策的三个输入：统计信息、index dive、成本模型；
  2. 会排查「选错索引」的六种原因，并用一条命令验证每一种；
  3. 知道 ANALYZE TABLE、直方图、optimizer_trace 各管什么，别只会加 hint。

二、前置知识

EXPLAIN 各列含义（MQ35）、B+Tree 与回表（MQ18）、索引失效（MQ20）。

三、理论讲解（官方定义）

MySQL 优化器是基于成本的优化器（cost-based optimizer）：枚举可能的执行计划，用统计信息估算每个计划的成本，选成本最低的那个。

统计信息主要来自两个地方：

来源 内容 相关参数
持久化统计 表行数、索引基数（Cardinality）、平均行长 innodb_stats_persistent=ON、innodb_stats_persistent_sample_pages=20
index dive 小范围直接读索引页，精确算出范围行数 eq_range_index_dive_limit=200

成本模型把代价拆成 IO 成本（读页数 × 代价）与 CPU 成本（比较行数 × 代价），再加上回表、排序、临时表的额外成本。

四、原理拆解

每一种都能用一条命令验证，不要凭感觉加 hint｜依据 MySQL 8.4 Optimizer Statistics / Histograms 说明自绘

1. 统计信息是怎么采的

InnoDB 默认对每张表随机采样 20 个索引页（innodb_stats_persistent_sample_pages），据此推算整表的行数与索引基数。表越大、数据越倾斜，估算偏差越大。

统计信息写入 mysql.innodb_table_stats 与 mysql.innodb_index_stats，可手动查询：

SELECT table_name, n_rows, clustered_index_size
FROM mysql.innodb_table_stats WHERE database_name = 'shop';

2. index dive 什么时候生效

等值范围查询（IN、=、<=>）行数不多时，优化器会直接读索引页精确计算，而不是用统计估算。当 IN 列表元素数超过 eq_range_index_dive_limit（默认 200），退化为估算——这就是「IN 里塞 300 个值后计划突变」的原因。

3. 直方图补的是「数据分布」

统计信息只有基数（有多少个不同值），不知道分布是否倾斜。8.0 起可对列建直方图：

ANALYZE TABLE t_order UPDATE HISTOGRAM ON status, city WITH 64 BUCKETS;

直方图存在 information_schema.COLUMN_STATISTICS，解决「同一条 SQL 有时快有时慢」的倾斜问题。维护有成本，只给关键查询列建。

4. 六种「选错索引」的根因

原因 现象 验证 处理
统计过期 rows 明显偏离实际 SHOW INDEX 看 Cardinality ANALYZE TABLE
采样页太少 大表估算抖动 调 innodb_stats_persistent_sample_pages 调大采样
分布倾斜 同 SQL 时快时慢 直方图 / 实际分布 建直方图或改写
索引相关性 两列必须同时用才有效 EXPLAIN 两次对比 建联合索引
隐式转换 key 命中但 rows 巨大 SHOW WARNINGS 统一类型
代价模型偏差 明明更优却没选 optimizer_trace 改统计或 hint

5. optimizer_trace 怎么看

SET optimizer_trace = 'enabled=on';
SELECT * FROM t_order WHERE status = 1 AND city = 'Chengdu';
SELECT trace FROM information_schema.OPTIMIZER_TRACE\G
SET optimizer_trace = 'enabled=off';

trace 里能看到候选计划与各自成本（rows_estimation、considered_execution_plans），是判断「优化器为什么选它」的唯一直接证据。

6. hint 的正确姿势

顺序永远是：先修统计 → 再改写 SQL → 最后才用 hint。FORCE INDEX 会把优化器锁死，数据分布一变反而更慢，而且升级后不会自动消失。

五、场景说明

  1. 计划漂移：同一 SQL 昨天好今天坏——先 ANALYZE TABLE；
  2. 大表 IN 查询：元素过多导致 index dive 失效，考虑分批或 EXISTS；
  3. 倾斜字段：status 只有 1% 是异常值，查询异常值时全表扫更划算，这是正常决策；
  4. 多列选择：单列索引各扫一遍 vs 联合索引，看相关性；
  5. 升级验证：8.0 与 8.4 的成本模型常数不同，升级后必须重跑关键 SQL 的计划对比。

六、示例代码/实操步骤

1. 看统计信息与基数

SHOW INDEX FROM t_order;
SELECT * FROM mysql.innodb_index_stats
WHERE database_name = 'shop' AND table_name = 't_order';

Cardinality 与实际 COUNT(DISTINCT col) 差距大 → 统计失真。

2. 刷新统计与调整采样

ANALYZE TABLE t_order;

SET GLOBAL innodb_stats_persistent_sample_pages = 100;   -- 默认 20
ANALYZE TABLE t_order;

3. 建直方图并验证

ANALYZE TABLE t_order UPDATE HISTOGRAM ON status WITH 64 BUCKETS;
SELECT * FROM information_schema.COLUMN_STATISTICS
WHERE TABLE_NAME = 't_order' AND COLUMN_NAME = 'status';

4. 用 trace 复现决策

SET optimizer_trace = 'enabled=on', optimizer_trace_max_mem_size = 1048576;
EXPLAIN SELECT * FROM t_order WHERE status = 1 AND city = 'Chengdu';
SELECT TRACE FROM information_schema.OPTIMIZER_TRACE\G

5. Java 侧怎么落地：把统计维护写进运维脚本

  1. 定时任务：每日低峰对核心表跑 ANALYZE TABLE（数据日增 > 5% 的表必跑）；
  2. 启动自检：应用启动时校验关键索引的 Cardinality，低于阈值打 WARN；
  3. 配置外置：把 innodb_stats_persistent_sample_pages、eq_range_index_dive_limit 写进 my.cnf 的 [mysqld]，随镜像统一发布，不要手改线上；
  4. 批量化改造：MyBatis 里超长 IN 列表按 100 一批拆分，避免踩 200 的 index dive 门槛；
  5. 上线门禁：升级大版本前后各跑一次核心 SQL 的 EXPLAIN FORMAT=JSON，对比 cost_info 差异。

七、常见坑

  1. 迷信 Cardinality 是精确值：它是采样估算；
  2. 一有慢 SQL 就 FORCE INDEX：掩盖了统计失真，后续更难排查；
  3. IN 列表过长：超过 eq_range_index_dive_limit 后估算退化；
  4. 给所有列建直方图：ANALYZE TABLE 变慢、统计维护成本高；
  5. 只 ANALYZE 不观察：刷完统计不对比计划，等于没做；
  6. 忽略索引相关性：单列索引各自选择性都高，但两列组合查询时联合索引才有效；
  7. 升级后不回归：成本常数变了，计划可能整体翻转。

八、版本差异

  • 5.6：持久化统计默认关闭，需显式开启；
  • 5.7：innodb_stats_persistent 默认 ON；优化器成本常数可查 mysql.server_cost/engine_cost；
  • 8.0：直方图（ANALYZE TABLE ... UPDATE HISTOGRAM）、函数索引（8.0.13）、hash join（8.0.18）、optimizer_trace 更完整；
  • 8.4：统计与直方图机制同 8.0，成本模型常数有微调，升级需重跑关键 SQL 对比计划。

九、课后小结

  • 优化器 = 统计信息 + index dive + 成本模型，三者任一失真都会选错；
  • Cardinality 是采样估算，ANALYZE TABLE 是刷新手段；
  • 直方图解决分布倾斜，代价是维护成本，只给关键列建；
  • optimizer_trace 是「为什么选它」的唯一直接证据；
  • hint 是最后手段，先修统计再谈强制索引。

十、思考题

  1. 为什么大表上 IN (300 个值) 的计划可能突然变差？

    参考回答：IN 列表元素数超过 eq_range_index_dive_limit（默认 200）后，优化器放弃逐个做 index dive，改用统计信息估算范围行数，估算往往偏大，从而改选全表扫描或更差的索引。解法是拆批、改 EXISTS，或在确实需要时调大该参数。

  2. Cardinality 与实际不同值数量差很多，会带来什么后果？

    参考回答：优化器会误判索引选择性。基数被低估时它认为走索引过滤不了多少行，倾向全表扫；被高估时又可能选错索引。先 ANALYZE TABLE，仍不准则调大采样页或给倾斜列建直方图。

  3. 直方图和索引统计有什么本质区别？

    参考回答：索引统计只给「有多少个不同值」（基数）与平均分布假设；直方图记录具体值域的分布（等深/等高频），能表达倾斜。前者便宜，后者精确但维护有成本。

  4. 什么时候该用 FORCE INDEX，用完要注意什么？

    参考回答：只在统计已修正、SQL 已优化、优化器仍稳定选错时使用，并且要写注释说明原因与复核周期。注意它会让优化器失去灵活性，数据分布变化或版本升级后可能变成负优化，必须纳入回归清单。

  5. 升级到 8.4 后执行计划变了，第一步做什么？

    参考回答：先对比 EXPLAIN FORMAT=JSON 的成本明细与 rows 估算，确认是统计差异还是成本常数差异；再 ANALYZE TABLE 刷新统计并重测；仍不一致时用 optimizer_trace 看候选计划成本，必要时调参数或改写，不要立刻上 hint。
