单表查询：WHERE、排序、分页与 NULL 语义

单表查询的难点不在语法，而在 NULL、隐式转换和分页——三处都让索引悄悄失效｜依据 MySQL 8.4 SELECT 与 Optimizer 章节自绘

一、学习目标

  1. 写出的 WHERE 一定能走索引，识别出五种让索引失效的写法；
  2. 讲清 NULL 在三值逻辑里的行为，知道 NOT IN 为什么可能返回空结果；
  3. 会用两种方式优化深翻页，能解释 ORDER BY ... LIMIT 的执行代价。

二、前置知识

前一讲的 DML。看得懂 EXPLAIN 的 type、key、rows、Extra 四列即可。

三、理论讲解（官方定义）

SELECT 的逻辑执行顺序是：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT。WHERE 在索引层过滤，ORDER BY 与 LIMIT 在结果层处理——这个顺序决定了为什么「排序字段没索引」会全量排序后再截取。

几条常被忽略的官方事实：

  • SQL 的比较是三值逻辑：TRUE / FALSE / UNKNOWN，NULL 参与任何比较都得 UNKNOWN；
  • COUNT(*) 统计行数，COUNT(col) 不统计 NULL；
  • NOT IN (包含 NULL 的列表) 结果恒为空，因为 x <> NULL 是 UNKNOWN；
  • 字符串列与数字比较时，MySQL 会把字符串列转成数字再比，索引直接失效。

四、原理拆解

NULL 不是「空字符串」，它让比较变成未知；深翻页的代价在「丢弃前 N 行」｜依据 MySQL 8.4 SELECT 与 Optimizer 章节自绘

1. NULL 的正确用法

SELECT * FROM t_user WHERE nickname IS NULL;          -- 对
SELECT * FROM t_user WHERE nickname = NULL;           -- 永远空
SELECT * FROM t_user WHERE nickname <> 'x';           -- 排除了 NULL 行
SELECT COUNT(*), COUNT(nickname) FROM t_user;         -- 5, 3（两列不等）

IS NULL 和 IS NOT NULL 是可以走索引的（B+Tree 里 NULL 也有位置）。真正会翻车的是 NOT IN：子查询结果里只要有一个 NULL，整个条件就是 UNKNOWN，返回空集。

2. 五种让索引失效的写法

-- 1 函数包住列
WHERE DATE(created_at) = '2022-11-19';          -- 改成 created_at >= '2022-11-19' AND created_at < '2022-11-20'
-- 2 隐式类型转换
WHERE phone = 13800000000;                       -- phone 是 VARCHAR，改成 phone = '13800000000'
-- 3 前导通配符
WHERE title LIKE '%mysql%';                      -- 只能后缀匹配：LIKE 'mysql%'
-- 4 排序规则/字符集不一致
WHERE a.name = b.name                            -- 两列 collation 不同会转换
-- 5 OR 连接不同列
WHERE status = 1 OR city = '成都';               -- 可能走 index merge，也可能全表

隐式转换最隐蔽：WHERE id = '1' 是安全的（数字列转字符串常量），但 WHERE varchar_col = 123 是把整列转成数字，索引报废。

3. ORDER BY 与索引

排序能否免掉 filesort，取决于「索引顺序」与「ORDER BY 顺序」是否一致：

-- 有 KEY idx_status_created (status, created_at)
SELECT * FROM t_order WHERE status = 1 ORDER BY created_at DESC LIMIT 10;  -- 可用索引顺序，无 filesort
SELECT * FROM t_order WHERE status = 1 ORDER BY amount DESC LIMIT 10;      -- 需要 filesort
SELECT * FROM t_order ORDER BY status, created_at DESC;                    -- 混合升降序，8.0 起可建降序索引

Extra 里出现 Using filesort 就意味着要对结果集排序，数据量大时非常贵。8.0 起支持 DESC 索引（KEY idx (a ASC, b DESC)），混合排序也能命中。

4. 深翻页的两种解法

-- 慢：先取 100010 行再丢掉前 100000 行
SELECT * FROM t_order ORDER BY id LIMIT 100000, 10;
  • 延迟关联：先用覆盖索引定位主键，再回表取 10 行：
SELECT o.* FROM t_order o
JOIN (SELECT id FROM t_order ORDER BY id LIMIT 100000, 10) t ON o.id = t.id;
  • Keyset 分页（游标）：记住上一页最后一条的主键，下一页从它之后取，代价恒定：
SELECT * FROM t_order WHERE id > 100000 ORDER BY id LIMIT 10;

游标分页不适合「跳页」，适合信息流、导出、批量任务。

5. 用 EXPLAIN 读三件事

EXPLAIN SELECT * FROM t_order WHERE status = 1 ORDER BY created_at DESC LIMIT 10;

看 type（const/ref/range 好，ALL 差）、key（是否命中预期索引）、Extra（出现 Using filesort、Using temporary 就要注意）。

五、场景说明

  1. 列表页：status + created_at 联合索引 + 游标分页；
  2. 条件检索：多条件等值 + 一个范围，把范围条件放联合索引最后一位；
  3. 导出任务：按主键区间批量扫，避免 LIMIT offset；
  4. 统计页：COUNT(*) 在千万行表上很贵，用近似统计或缓存；
  5. NULL 字段：可选字段允许 NULL 但查询时统一 IS NULL / IS NOT NULL。

六、示例代码/实操步骤

1. 建索引并验证

CREATE TABLE t_order (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_no   VARCHAR(32) NOT NULL,
  status     TINYINT NOT NULL DEFAULT 0,
  amount     DECIMAL(12,2) NOT NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  remark     VARCHAR(64) NULL,
  PRIMARY KEY (id),
  KEY idx_status_created (status, created_at),
  KEY idx_order_no (order_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

EXPLAIN SELECT id, order_no FROM t_order WHERE status = 1 ORDER BY created_at DESC LIMIT 10;

id, order_no 都在索引里时是覆盖索引，Extra 会出现 Using index。

2. 游标分页

-- 第一页
SELECT id, order_no, created_at FROM t_order WHERE status = 1 ORDER BY created_at DESC, id DESC LIMIT 10;
-- 下一页：带上上一页最后一条的 (created_at, id)
SELECT id, order_no, created_at FROM t_order
WHERE status = 1 AND (created_at, id) < ('2022-11-19 10:00:00.000', 100234)
ORDER BY created_at DESC, id DESC LIMIT 10;

3. NULL 与 NOT IN 的坑

SELECT * FROM t_user WHERE nickname NOT IN (SELECT nickname FROM t_user WHERE id < 10);  -- 有 NULL 就空
-- 修正：过滤掉 NULL
SELECT * FROM t_user WHERE nickname NOT IN (
  SELECT nickname FROM t_user WHERE id < 10 AND nickname IS NOT NULL
);

Java 侧怎么落地：动态 SQL 与分页

  1. #{} 与 ${}：#{} 走预编译、能防注入；${} 只用于表名/排序字段这类白名单值，绝不接用户输入；
  2. MyBatis 动态条件：
<select id="page" resultType="Order">
  SELECT id, order_no, amount, created_at FROM t_order
  <where>
    <if test="status != null">AND status = #{status}</if>
    <if test="from != null">AND created_at &gt;= #{from}</if>
    <if test="cursorId != null">AND id &gt; #{cursorId}</if>
  </where>
  ORDER BY id DESC LIMIT #{limit}
</select>
  1. 分页别用 PageHelper 的默认 count：大表 COUNT(*) 很贵，可让前端改游标分页，或加 count=false 用近似总数；
  2. NULL 参数：status != null 这类判空要显式写，否则 WHERE status = NULL 永远空；
  3. 返回对象用包装类型：Integer amount 才能表达 NULL，int 会把 NULL 变 0，统计口径直接错。

七、常见坑

  1. = NULL：条件恒假，查不出数据；
  2. NOT IN 遇 NULL：结果为空，误判「没有数据」；
  3. WHERE varchar = 数字：隐式转换导致索引失效；
  4. ORDER BY 字段不在索引里：全量 filesort，LIMIT 也救不了；
  5. LIMIT 100000, 10：越翻越慢，第 10 万页可能几十秒；
  6. SELECT *：多读无用列、破坏覆盖索引；
  7. COUNT(col) 当 COUNT(*)：有 NULL 时数量偏小；
  8. OR 拼多列：优化器可能选 index merge，也可能直接 ALL，要用 EXPLAIN 确认。

八、版本差异

  • 8.0：支持降序索引，ORDER BY a ASC, b DESC 可命中；EXPLAIN ANALYZE 可看真实耗时；
  • 8.4：EXPLAIN 输出与优化器行为延续 8.0，无破坏性变化；
  • 5.7 对比：5.7 的降序索引只是语法接受、实际仍升序，混合排序一定 filesort。

九、课后小结

  • WHERE 要能走索引，五种写法必须避开：函数包列、隐式转换、前导 %、排序规则不一致、跨列 OR；
  • NULL 是三值逻辑，= NULL 恒假，NOT IN 遇 NULL 变空；
  • ORDER BY 顺序与索引顺序一致才免 filesort；
  • 深翻页用延迟关联或游标分页，别用大 offset；
  • EXPLAIN 只看三件事：type、key、Extra。

十、思考题

  1. 为什么 WHERE nickname = NULL 查不到任何行？

    参考回答：SQL 用三值逻辑，NULL 表示「未知」，任何与它的比较结果都是 UNKNOWN，而 WHERE 只保留结果为 TRUE 的行。判断空值必须用 IS NULL。

  2. WHERE phone = 13800000000（phone 是 VARCHAR）为什么索引失效？

    参考回答：MySQL 在比较字符串列与数字时会先把字符串列整体转成数字，转换发生在每一行上，B+Tree 的有序性用不上，于是退化为全表扫描。改成 phone = '13800000000' 即可命中索引。

  3. COUNT(*) 和 COUNT(nickname) 的结果为什么不同？

    参考回答：COUNT(*) 统计行数；COUNT(expr) 只统计 expr 非 NULL 的行。nickname 为 NULL 的行不会被后者计入。

  4. 深翻页为什么越翻越慢，两种解法分别适合什么场景？

    参考回答：LIMIT offset, n 需要先扫描并丢弃前 offset 行，代价随页数线性增长。延迟关联用覆盖索引只取主键再回表，适合仍需跳页的场景；游标分页用上一页末尾主键做条件，代价恒定，适合信息流、导出等顺序浏览场景，但不支持随机跳页。

  5. 一条 ORDER BY created_at DESC LIMIT 10 的查询，什么情况下不需要 filesort？

    参考回答：当 created_at 上有索引（或联合索引的最后一列是它且前面的等值条件固定），优化器可以按索引逆序读 10 行就停，Extra 不出现 Using filesort；否则要先取出全部匹配行排序再截取。
