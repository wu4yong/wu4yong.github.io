mysql-36-slow-log

分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

慢查询日志与 profiling：先把那条慢 SQL 抓出来

慢日志负责发现，聚合工具负责排序，EXPLAIN 负责归因｜依据 MySQL 8.4 Slow Query Log 说明自绘

一、学习目标

  1. 会开慢日志，并配好 long_query_time、log_slow_extra 等关键参数；
  2. 用 mysqldumpslow、pt-query-digest 或 Performance Schema 按总耗时排序；
  3. 区分「单次慢」与「总耗时高」，知道该优化哪一条。

二、前置知识

EXPLAIN 基本读法（MQ35）。慢日志只负责告诉你「哪条慢」，归因仍然是 EXPLAIN 的活。

三、理论讲解（官方定义）

慢查询日志记录执行时间超过 long_query_time 的语句，默认关闭、默认阈值 10 秒：

SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.2;

常用参数：

参数 默认 说明
slow_query_log OFF 开关
slow_query_log_file hostname-slow.log 输出文件，log_output=TABLE 时写 mysql.slow_log
long_query_time 10 阈值（秒，支持小数）
log_queries_not_using_indexes OFF 记录未走索引的语句，易刷爆日志
log_slow_admin_statements OFF 是否记录 ALTER/ANALYZE 等管理语句
min_examined_row_limit 0 扫描行数低于此值不记，用来滤噪
log_slow_extra OFF 8.0.14+，输出更多字段（Rows_affected、Bytes_sent 等）
log_slow_replica_statements OFF 是否记录复制线程的语句

默认 10 秒几乎抓不到东西，线上一般按 P95 定在 0.1～0.5 秒。

四、原理拆解

按总耗时排序，比按单次耗时排序更容易找到真正的瓶颈｜依据 MySQL 8.4 Performance Schema / 慢日志说明自绘

1. 一条慢日志长什么样

# Time: 2022-12-16T10:21:33.512345Z
# User@Host: app[app] @ 10.0.3.21 []  Id: 88213
# Query_time: 3.812  Lock_time: 0.001  Rows_sent: 20  Rows_examined: 480000
SET timestamp=1671186093;
SELECT * FROM t_order WHERE user_id = 100 ORDER BY created_at DESC LIMIT 20;

四个数字先看：Query_time 耗时、Lock_time 等锁耗时、Rows_sent 返回行数、Rows_examined 扫描行数。扫描/返回比值 > 100 基本可以断定索引没用好。

2. 为什么按「总耗时」排

一条 1.3ms 的 SQL 被调用 182 万次，总耗时 2461 秒；另一条 3 秒的 SQL 一天跑一次，总耗时 3 秒。前者才是拖垮实例的那条。聚合工具按 total time 排序，正是为了抓这种「单次不慢、累计很重」的语句。

3. log_queries_not_using_indexes 的陷阱

开了它会记录所有未走索引的语句，包括 SELECT 1、元数据查询这类天然无索引的小语句，日志几分钟就几百 MB。要用就配合 min_examined_row_limit=100，并且只在排查期临时打开。

4. Performance Schema 已经是标配

8.x 里慢日志与 Performance Schema 都在记录，后者更适合做聚合：

表 用途
events_statements_summary_by_digest 按 SQL 指纹聚合，自带总耗时、扫描行数
events_statements_current 看当前正在跑什么
events_stages_* 看阶段耗时，替代已弃用的 SHOW PROFILE

digest 把常量与参数归一成 ?，天然就是「同一类 SQL」的聚合键。

5. SHOW PROFILE 已弃用

8.x 中 SHOW PROFILE 已被标记弃用，阶段耗时统一走 Performance Schema 的 events_stages_*，或直接用 EXPLAIN ANALYZE 看每个迭代器的耗时。

五、场景说明

  1. 日常巡检：每天拉一次 summary_by_digest，按总耗时前十名看趋势；
  2. 突发卡顿：先看 events_statements_current，找出正在跑的重语句；
  3. 上线回归：发布后 24 小时对比慢日志数量与总耗时；
  4. 容量评估：Rows_examined 增长快于业务量增长，说明索引或 SQL 退化；
  5. 复制延迟：log_slow_replica_statements 单独打开，定位从库回放慢的语句。

六、示例代码/实操步骤

1. 开日志并落到表里（便于 SQL 查询）

SET GLOBAL log_output = 'TABLE,FILE';
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.2;
SET GLOBAL min_examined_row_limit = 100;
SET GLOBAL log_slow_extra = ON;

SELECT start_time, query_time, rows_examined, rows_sent, sql_text
FROM mysql.slow_log
ORDER BY start_time DESC LIMIT 20;

2. 用 Performance Schema 聚合前十

SELECT DIGEST_TEXT,
       COUNT_STAR AS calls,
       ROUND(SUM_TIMER_WAIT / 1e12, 1) AS total_s,
       ROUND(AVG_TIMER_WAIT / 1e9, 2) AS avg_ms,
       SUM_ROWS_EXAMINED AS rows_examined,
       SUM_ROWS_SENT AS rows_sent
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'shop'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

3. 看阶段耗时（替代 SHOW PROFILE）

UPDATE performance_schema.setup_instruments
SET ENABLED = 'YES', TIMED = 'YES'
WHERE NAME LIKE 'stage/sql/%';

SELECT EVENT_NAME, COUNT_STAR,
       ROUND(SUM_TIMER_WAIT / 1e12, 3) AS total_s
FROM performance_schema.events_stages_summary_global_by_event_name
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;

4. 命令行聚合工具

pt-query-digest /var/lib/mysql/slow.log | head -n 40
mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log

-s t 按总耗时排，-t 10 取前十。

5. Java 侧怎么落地：慢 SQL 自动进治理流程

  1. 依赖：引入 datasource-proxy 或 p6spy，在 application.yml 里配 logging 级别与阈值；
  2. 拦截：MyBatis 场景用 Interceptor 包一层，记录 MappedStatement.id、参数、耗时；
  3. 上报：超阈值（例如 500ms）写入独立日志或 Kafka topic，避免污染业务日志；
  4. 聚合：定时任务把上报数据按「SQL 指纹」聚合，每天生成 TopN 报表推给值班群；
  5. 门禁：把 TopN 与新上线的 mapper 语句比对，新出现的慢语句阻断发布。

七、常见坑

  1. long_query_time 用默认 10 秒：等于没开；
  2. 只开 log_queries_not_using_indexes：日志被小语句刷爆，真正的慢 SQL 被淹没；
  3. 按单次耗时排序：抓不到高频轻量语句；
  4. 直接看 Rows_examined 绝对值：要结合返回行数看比值；
  5. 在高峰期做全量日志采集：IO 抖动会放大问题；
  6. 忘记日志轮转：慢日志几个 GB 后拖慢写入，需配合 logrotate 或定期 TRUNCATE mysql.slow_log；
  7. SHOW PROFILE 还在用：8.x 已弃用，结果也不完整。

八、版本差异

  • 5.6：慢日志基础能力，log_slow_admin_statements 已存在；
  • 5.7：log_syslog、--log-timestamps 精度提升到微秒；
  • 8.0：log_slow_extra（8.0.14+）；SHOW PROFILE 弃用；Performance Schema 默认更完整；log_slow_replica_statements 拆分（8.0.26+）；
  • 8.4：慢日志参数与 8.0 一致，重点转向 performance_schema 与 EXPLAIN ANALYZE 的组合排查。

九、课后小结

  • 慢日志是「发现」工具，EXPLAIN 是「归因」工具，两者必须配合；
  • 阈值按 P95 定，默认 10 秒等于没开；
  • 排序要按总耗时，高频轻量语句才是隐形杀手；
  • Rows_examined / Rows_sent 比值是判断索引质量的快指标；
  • 线上聚合优先用 events_statements_summary_by_digest，SHOW PROFILE 已经过时。

十、思考题

  1. 为什么线上不建议长期开启 log_queries_not_using_indexes？

    参考回答：它会记录所有未走索引的语句，包括 SELECT 1、系统元数据查询等本来就没有索引可用的小语句，日志体积暴涨、写盘 IO 抖动，真正的问题语句被淹没。排查期临时打开，并配合 min_examined_row_limit 滤掉小语句。

  2. 一条 SQL 单次 1ms、QPS 5000，另一条单次 2 秒、每小时 1 次，先优化哪条？

    参考回答：先优化第一条。它每秒消耗 5 秒的数据库时间，后者一小时才 2 秒；资源占用看的是总耗时（SUM_TIMER_WAIT），不是单次耗时。

  3. Rows_examined 很大但 Rows_sent 很小，通常说明什么？

    参考回答：说明扫了大量行才筛出少量结果，索引选择性差或没走索引，也可能是排序/去重导致的多余扫描。比值超过 100 就该看 EXPLAIN。

  4. 8.x 里想定位一条 SQL 的阶段耗时，应该用什么？

    参考回答：用 Performance Schema 的 events_stages_*（先开 stage/sql/% 的 instrument），或直接 EXPLAIN ANALYZE 看各迭代器耗时。SHOW PROFILE 在 8.x 已弃用。

  5. 慢日志文件越来越大，怎么处理不影响业务？

    参考回答：配置 logrotate 按天切割并压缩，或 log_output=TABLE 时定期 TRUNCATE mysql.slow_log；避免直接 rm 正在写入的文件（句柄仍指向旧 inode，空间不释放），应 mv 后 kill -USR1 或重启日志。
