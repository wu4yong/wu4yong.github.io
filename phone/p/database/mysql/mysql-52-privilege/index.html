mysql-52-privilege

分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

权限体系与最小权限

账号 → 库 → 表 → 列，越往下越细，也越难维护｜依据 MySQL 8.4 Privileges / 账号管理说明自绘

一、学习目标

  1. 理清权限的四层粒度与授权语法，不再一律 GRANT ALL；
  2. 用角色（ROLE）收敛重复授权，做到可复用、可回收；
  3. 把「最小权限」落到账号命名、来源限制与审计上。

二、前置知识

账号认证与 caching_sha2_password（MQ16）、安全加固（MQ53）、审计与日志（MQ36）。

三、理论讲解（官方定义）

MySQL 的权限授予模型是「用户 = 账号 + 主机」的四层结构：

层级 语法 适用范围
全局 ON *.* 所有库所有表（含管理类权限）
库级 ON db.* 指定数据库全部对象
表级 ON db.tbl 单表
列级 SELECT (col1, col2) ON db.tbl 单列

匹配规则第一条：权限检查按最细粒度优先 —— 表级权限优先于库级，列级优先于表级。表级权限会覆盖库级权限（哪怕表级只给了 SELECT，库级的 INSERT 对该表也不生效），这是最容易记错的一点。

8.4 的账号认证变化：mysql_native_password 默认关闭，新账号统一 caching_sha2_password；authentication_policy 取代 default_authentication_plugin。

四、原理拆解

能查、能审、能回收，权限才叫受控｜依据 MySQL 8.4 Roles / GRANT 说明自绘

1. 最小权限的三条实操

  • 只给业务必需的语句权限：应用通常只需 SELECT, INSERT, UPDATE, DELETE，DROP/ALTER/GRANT 一律不给；
  • 来源收敛到网段：app@'10.20.%'，不要 app@'%'；
  • DDL 用独立账号 + 流水线执行：应用账号永不持有 ALTER，避免被注入后直接改表结构。

2. 为什么表级权限会「抢」库级权限

权限检查时，MySQL 先看表级条目：若该表在表级有记录，就以表级为准，不再合并库级。所以「库级给全套、表级只给查询」的结果是这张表只能查。想做「库内默认读写、个别表只读」，正确做法是表级不给该表任何条目，改用只读账号。

3. 角色（ROLE）：把权限打包

CREATE ROLE 'app_rw', 'report_ro';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'app_rw';
GRANT SELECT ON shop.* TO 'report_ro';
GRANT 'app_rw' TO 'order_svc'@'10.20.%';
SET DEFAULT ROLE 'app_rw' TO 'order_svc'@'10.20.%';

角色的价值在变更时体现：新增一个库，只改角色定义，所有绑定该角色的账号自动生效；下线某类权限，REVOKE 一次即可。

4. 管理类权限要单独看

SUPER（8.0 起被拆成 SYSTEM_VARIABLES_ADMIN、SESSION_VARIABLES_ADMIN 等动态权限）、RELOAD、PROCESS、REPLICATION CLIENT 都属于「能看全局状态」的权限。备份账号需要 RELOAD, LOCK TABLES, REPLICATION CLIENT，但不需要 ALL。

5. 审计：权限的另一半

  • SHOW GRANTS FOR 'app'@'10.20.%' 定期比对账号清单，找出多给的权限；
  • mysql.user / mysql.role_edges 是权威来源，导出后做 diff；
  • 高危语句审计（DELETE 无 WHERE、DROP TABLE）用审计插件或代理层记录；
  • 离职/下线账号 DROP USER 并回收其角色绑定。

五、场景说明

  1. 订单服务：app_rw 角色，只给 DML，来源限定应用网段；
  2. 报表平台：report_ro 只读，连从库，避免大查询打主库；
  3. 发布流水线：ddl_rw 只给 ALTER, CREATE, DROP，仅在变更窗口启用；
  4. 备份任务：最小集 SELECT, RELOAD, LOCK TABLES, REPLICATION CLIENT；
  5. 临时排障：建 tmp_<工单号> 账号，带有效期，事后立即删除。

六、示例代码/实操步骤

1. 建账号与授权模板

CREATE USER 'order_svc'@'10.20.%'
  IDENTIFIED WITH caching_sha2_password BY '***'
  REQUIRE SSL
  PASSWORD EXPIRE INTERVAL 180 DAY;

GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'order_svc'@'10.20.%';

REQUIRE SSL 强制走加密连接，配合 MQ53 的 TLS 配置使用。

2. 用角色收敛

CREATE ROLE 'app_rw';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'app_rw';
GRANT 'app_rw' TO 'order_svc'@'10.20.%', 'pay_svc'@'10.21.%';
SET DEFAULT ROLE ALL TO 'order_svc'@'10.20.%';

之后新增服务只需 GRANT 'app_rw' TO ...，不用重复写权限列表。

3. 只读账号连从库

CREATE USER 'report_ro'@'10.30.%' IDENTIFIED WITH caching_sha2_password BY '***';
GRANT SELECT ON shop.* TO 'report_ro'@'10.30.%';
ALTER USER 'report_ro'@'10.30.%' SET RESOURCE LIMIT
  MAX_USER_CONNECTIONS 20;

MAX_USER_CONNECTIONS 限制并发，防止报表把从库打满。

4. 定期审计脚本

-- 列出所有非系统账号及其授权
SELECT DISTINCT GRANTEE FROM information_schema.USER_PRIVILEGES
UNION SELECT DISTINCT GRANTEE FROM information_schema.SCHEMA_PRIVILEGES
UNION SELECT DISTINCT GRANTEE FROM information_schema.TABLE_PRIVILEGES;

-- 找出持有高危全局权限的账号
SELECT GRANTEE, PRIVILEGE_TYPE FROM information_schema.USER_PRIVILEGES
WHERE PRIVILEGE_TYPE IN ('SUPER','SYSTEM_USER','GRANT OPTION')
   OR GRANTEE NOT LIKE "'mysql.%'";

审计结果与 CMDB 的账号台账做 diff，多出来的权限逐条确认。

5. Java 侧怎么落地：账号是配置项，不是硬编码

  1. 账号/口令走配置中心或 KMS：不进代码库、不进镜像；
  2. 一个服务一套账号：便于按服务限流与审计，别共用 root；
  3. 权限随发布走：新功能需要新权限时，走工单 + 流水线授予，而不是临时 GRANT ALL；
  4. 连接串带 requireSSL：jdbc:mysql://...?sslMode=VERIFY_CA；
  5. 启动自检：应用启动时执行 SHOW GRANTS FOR CURRENT_USER()，发现超出预期权限即告警。

七、常见坑

  1. 一律 GRANT ALL：一次注入就能拖库、改表、删库；
  2. 账号主机写成 %：等于对全网开放；
  3. 表级权限与库级混用：误以为「库级给了写，表级只读还能写」；
  4. 共用 root 或共用一个应用账号：出问题无法定位是哪个服务；
  5. 密码写死在代码/配置里：泄露后无法快速轮换；
  6. 忘记 DROP USER：离职人员账号仍在，历史权限仍生效；
  7. 角色未 SET DEFAULT ROLE：授权了角色但账号登录后不生效；
  8. 备份账号给了 ALL：最小集就够了。

八、版本差异

  • 5.6/5.7：账号认证以 mysql_native_password 为主；无角色概念，权限靠逐个 GRANT；
  • 8.0：引入角色（CREATE ROLE）；SUPER 拆为动态权限（SYSTEM_VARIABLES_ADMIN 等）；caching_sha2_password 成为默认；
  • 8.0.27+：ALTER USER ... SET RESOURCE LIMIT 支持按账号限流；
  • 8.4 LTS：mysql_native_password 默认关闭（老客户端需显式启用插件）；authentication_policy 取代 default_authentication_plugin，可配置多因素；GRANT ... WITH GRANT OPTION 的使用建议收敛到极少数管理账号。

九、课后小结

  • 四层粒度：全局 → 库 → 表 → 列；表级优先且覆盖库级；
  • 应用账号只给 DML，DDL 交给流水线专用账号；
  • 角色让授权可复用、可一次性回收；
  • 来源限网段、强制 SSL、口令轮换，是账号卫生的三件套；
  • 审计靠「导出授权 + 台账 diff」，不靠记忆。

十、思考题

  1. 库级给了 INSERT，表级只给了 SELECT，这张表能写吗？

    参考回答：不能。权限检查按最细粒度优先：该表在表级有记录时以表级为准，库级的 INSERT 不再合并进来。所以结果是这张表只能读。要「库可写、单表不可写」，正确做法是不给该表任何表级条目（靠库级生效），再用只读账号访问它。

  2. 为什么 DDL 权限不能给应用账号？

    参考回答：应用账号一旦持有 ALTER/DROP，任何 SQL 注入或代码缺陷都可能直接改表结构甚至删表，影响面从「数据错」升级为「服务崩」。DDL 应由发布流水线用独立账号在变更窗口执行，应用账号永久只有 DML。

  3. 角色和直接 GRANT 相比优势在哪？

    参考回答：角色是一组权限的命名集合，可复用、可统一变更、可一次性回收。新增同类服务只需绑定角色；调整权限只改角色定义，所有绑定账号自动生效；下线时 REVOKE 角色一次即可，不会遗漏。缺点是必须 SET DEFAULT ROLE 才会在登录后生效，容易漏配。

  4. SUPER 在 8.x 里为什么被拆掉？

    参考回答：SUPER 原先是一个「万能」权限，既包含改系统变量，也包含复制、杀会话等能力，粒度太粗。8.0 起拆为 SYSTEM_VARIABLES_ADMIN、SESSION_VARIABLES_ADMIN、CONNECTION_ADMIN 等动态权限，可以按需授予，减少「为了一个功能给整套权限」的情况。

  5. 如何发现某个账号权限过大？

    参考回答：定期导出 information_schema.USER_PRIVILEGES/SCHEMA_PRIVILEGES/TABLE_PRIVILEGES 与 mysql.role_edges，与账号台账（CMDB）做 diff；重点看持有 SUPER/SYSTEM_USER/GRANT OPTION 的账号、来源为 % 的账号、以及长期无访问的账号。多出来的权限逐条确认后 REVOKE。
