mysql-21-事务与隔离级别

分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

事务与 ACID、四种隔离级别

ACID 不是四个并列的口号，而是四套机制在不同层面的保证｜依据 MySQL 8.4 InnoDB Transaction Model 章节自绘

一、学习目标

  1. 说清 ACID 每一项在 InnoDB 里由哪套机制实现，而不是背四个单词；
  2. 记住四种隔离级别各解决什么现象，以及 MySQL 默认为什么是 RR；
  3. 会查、会改隔离级别，并知道改完之后 binlog 与锁行为会有什么变化。

二、前置知识

SQL 基础、索引（MQ18/MQ19）。如果知道「快照读」与「当前读」这两个词，本节会更顺。

三、理论讲解（官方定义）

事务是一组要么全做、要么全不做的操作。ACID 四项：

  • 原子性（Atomicity）：靠 undo log 回滚；
  • 一致性（Consistency）：靠约束、事务边界与应用逻辑共同保证，数据库只提供工具；
  • 隔离性（Isolation）：靠锁与 MVCC；
  • 持久性（Durability）：靠 redo log + WAL 刷盘。

四种隔离级别（SQL 标准）：

级别 脏读 不可重复读 幻读
READ UNCOMMITTED 可能 可能 可能
READ COMMITTED 不可能 可能 可能
REPEATABLE READ 不可能 不可能 InnoDB 用间隙锁基本避免
SERIALIZABLE 不可能 不可能 不可能

MySQL 的默认级别是 REPEATABLE READ，且 InnoDB 在 RR 下用 next-key lock 阻止幻读（这是 InnoDB 相对标准 RR 的加强）。

四、原理拆解

级别越高，锁越多、并发越低；RC 的间隙锁被关闭，代价是可能幻读｜依据 MySQL 8.4 事务隔离与锁章节自绘

1. 并发读的三类异常

-- 脏读：读到别人未提交的数据（RU 才有）
-- 不可重复读：同一事务两次读同一行，值变了（RC 有）
-- 幻读：同一事务两次读，行数变了（RC/RR 的快照读不会，当前读要靠间隙锁）

区分关键：不可重复读是「同一行的值变了」，幻读是「多出或少掉了行」。

2. RR 与 RC 的差别只有一句话

  • RR：事务内第一次快照读建立 ReadView，之后所有快照读都用它；
  • RC：每次快照读都新建 ReadView，所以能看到别人刚提交的数据。
-- 查看当前隔离级别
SELECT @@transaction_isolation;              -- 8.0/8.4 原名 @@tx_isolation
-- 会话级修改
SET SESSION transaction_isolation = 'READ-COMMITTED';
-- 全局修改（影响新连接）
SET GLOBAL transaction_isolation = 'READ-COMMITTED';

3. 快照读与当前读

类型 语句 读什么
快照读 普通 SELECT ReadView 对应的历史版本
当前读 SELECT ... FOR UPDATE / FOR SHARE / UPDATE / DELETE / INSERT 最新已提交版本，并加锁

这就是「RR 下普通 SELECT 看不到别人刚插入的行，但 UPDATE 却能改到它」的原因——两者读的不是同一份数据。

4. 自动提交与显式事务

SELECT @@autocommit;          -- 默认 1
SET autocommit = 0;           -- 关闭自动提交，每条语句都在隐式事务里
START TRANSACTION;            -- 显式开启
SAVEPOINT sp1;                -- 保存点
ROLLBACK TO sp1;              -- 回滚到保存点，不结束事务
COMMIT;                       -- 提交

START TRANSACTION WITH CONSISTENT SNAPSHOT 会在开启事务的同时建立快照，避免「先 SELECT 再 START TRANSACTION」造成的快照时机偏差。

5. 隔离级别与 binlog

binlog_format=STATEMENT 在 RC 下记录的是语句，主从可能因执行顺序不同而数据不一致；所以生产用 RC 时务必 binlog_format=ROW。MySQL 8.0 起默认就是 ROW，这一条已经不再是坑，但迁移老库时要确认。

五、场景说明

  1. 默认业务：RR + 自动提交，普通查询走快照读；
  2. 报表/长查询：RR 下多次查询拿到一致快照，适合对账；
  3. 高并发写入：很多团队改成 RC，减少间隙锁带来的死锁；
  4. 库存扣减：UPDATE ... WHERE stock >= n 靠当前读 + 行锁保证；
  5. 批量任务：显式事务 + 分批提交，避免长事务。

六、示例代码/实操步骤

1. 复现不可重复读

-- 会话 A
SET SESSION transaction_isolation = 'READ-COMMITTED';
START TRANSACTION;
SELECT balance FROM t_account WHERE id = 1;   -- 100

-- 会话 B
UPDATE t_account SET balance = 50 WHERE id = 1;
COMMIT;

-- 会话 A 再读
SELECT balance FROM t_account WHERE id = 1;   -- 50（RC 下变了）

同样流程在 RR 下第二次读仍是 100——因为用的是同一个 ReadView。

2. 复现幻读（当前读）

-- 会话 A（RR）
START TRANSACTION;
SELECT COUNT(*) FROM t_order WHERE user_id = 1 FOR UPDATE;   -- 2

-- 会话 B 插入一条 user_id=1 的记录并提交
-- 若 A 的条件命中了间隙，B 会被阻塞；不阻塞时说明没加间隙锁（如唯一索引等值）

-- 会话 A
SELECT COUNT(*) FROM t_order WHERE user_id = 1 FOR UPDATE;   -- 仍是 2

3. 查看事务与锁

-- 当前运行的事务
SELECT trx_id, trx_state, trx_started, trx_rows_locked, trx_query
FROM information_schema.INNODB_TRX ORDER BY trx_started;

-- 8.0 起的锁视图
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

-- 锁等待超时（默认 50 秒）
SELECT @@innodb_lock_wait_timeout;

4. 保存点与部分回滚

START TRANSACTION;
INSERT INTO t_order (id, user_id) VALUES (1, 100);
SAVEPOINT after_order;
INSERT INTO t_order_item (order_id, product_id) VALUES (1, 200);
ROLLBACK TO after_order;   -- 只回滚明细，订单保留
COMMIT;

Java 侧怎么落地：事务边界与隔离级别

  1. 事务只包住写操作：查询、远程调用、消息发送放到事务外，避免长事务；
  2. @Transactional 要指定 rollbackFor：默认只回滚 RuntimeException，受检异常不回滚是经典事故；
  3. 避免自调用失效：同类内部方法调用不走代理，@Transactional 不生效，注入自身代理或拆类；
  4. 隔离级别在连接串统一：transactionIsolation=TRANSACTION_READ_COMMITTED，别在代码里零散 SET；
  5. 幂等与重试：捕获死锁异常（1213）后整段重试，别在事务里吞异常继续执行；
  6. 只读事务：查询服务用 @Transactional(readOnly = true)，可减少不必要的锁与优化器开销。

七、常见坑

  1. 以为 RR 完全没有幻读：快照读没有，当前读要靠间隙锁；间隙锁在某些场景（唯一索引等值）根本不加；
  2. 长事务拖住 purge：undo 无法清理，版本链越来越长，读性能持续下降；
  3. 事务里做 RPC/MQ：外部调用超时会长时间持锁，还可能造成重复消息；
  4. @Transactional 加在 private 方法上：代理不生效，等于没加；
  5. RC 下仍用 STATEMENT binlog：主从可能不一致（8.0 默认 ROW 已缓解）；
  6. SELECT ... FOR UPDATE 当普通查询用：加锁读会阻塞写入，能快照读就别加锁；
  7. SET autocommit=0 后忘提交：连接归还池时事务还挂着，后续请求莫名锁等待。

八、版本差异

  • 5.7：变量名 tx_isolation；binlog_format 默认 ROW（5.7.7 起）；
  • 8.0：变量更名为 transaction_isolation（tx_isolation 仍兼容）；performance_schema.data_locks / data_lock_waits 取代 innodb_lock_waits；
  • 8.4：默认仍是 RR，机制一致；innodb_lock_wait_timeout 默认 50 秒。

九、课后小结

  • 原子性靠 undo、持久性靠 redo、隔离性靠锁 + MVCC、一致性靠约束与业务；
  • 默认 RR，事务内快照读共用一个 ReadView；RC 每次读新建；
  • 快照读不加锁，当前读读最新版本并加锁；
  • 幻读在 RR 的当前读里靠 next-key lock 阻止，快照读天然看不到新行；
  • RC 关闭间隙锁，能减少死锁但可能幻读，需配 ROW 格式 binlog。

十、思考题

  1. RR 下「同一事务两次读到不同行数」有可能吗？

    参考回答：快照读不会，因为两次都读同一个 ReadView；但如果第二次是当前读（FOR UPDATE），且第一次的条件没加间隙锁，就可能读到新插入的行，表现为行数变化。

  2. RC 为什么能减少死锁？

    参考回答：RC 关闭了间隙锁（除外键与唯一性检查），锁的范围更小、持有时间更短，减少了「交叉等待同一间隙」这类死锁。

  3. START TRANSACTION WITH CONSISTENT SNAPSHOT 解决了什么问题？

    参考回答：普通 START TRANSACTION 不立即建快照，快照在第一条 SELECT 时才建立；如果中间隔了很久，快照时机就被推后。带 WITH CONSISTENT SNAPSHOT 可让快照与事务同时开始。

  4. 为什么说「一致性」不是数据库单独保证的？

    参考回答：数据库只能保证约束与事务原子性；业务一致性（如转账两边金额守恒、库存不为负）需要正确的 SQL 逻辑与约束设计，数据库无法替你判断业务规则。

  5. 长事务为什么会让读变慢？

    参考回答：长事务持有旧 ReadView，undo log 里对应的历史版本无法被 purge，版本链不断变长，后续查询遍历版本链的成本上升，同时占用更多 undo 空间。
