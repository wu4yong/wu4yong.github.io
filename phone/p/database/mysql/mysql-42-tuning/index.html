参数调优：buffer pool、连接数与并发线程

先调内存与日志，再调连接与线程，最后才碰并发上限｜依据 MySQL 8.4 InnoDB 启动参数与连接管理说明自绘

一、学习目标

  1. 会用「容量 → 参数 → 指标 → 风险」四步给关键参数定值；
  2. 知道哪些参数是安全底线（flush_log_at_trx_commit、sync_binlog），哪些可以按容量放大；
  3. 会算 buffer pool 大小与 max_connections 的上限，避免调参把机器调崩。

二、前置知识

InnoDB 架构与 buffer pool（MQ28）、redo 与 binlog（MQ30/MQ32）、慢 SQL 与监控指标（MQ36）。

三、理论讲解（官方定义）

MySQL 的默认参数值是「最小可运行」口径，不是生产口径。关键默认值（8.4）：

参数 默认值 说明
innodb_buffer_pool_size 128MB 数据与索引缓存，最重要的一个参数
innodb_buffer_pool_instances 8 池实例数，< 1GB 时多实例无收益
innodb_log_buffer_size 16MB redo 写盘前的缓冲
innodb_flush_log_at_trx_commit 1 每次提交刷 redo，最安全
sync_binlog 1 每次提交刷 binlog
innodb_redo_log_capacity 约 100MB 统一管理 redo 容量（8.0.30+）
max_connections 151 最大并发连接
thread_cache_size 151 线程缓存
innodb_read_io_threads / write_io_threads 4 / 4 IO 线程数
innodb_page_cleaners 4 脏页清理线程
innodb_purge_threads 4 purge 线程

四、原理拆解

默认值是按「最小可用」设的，生产必须按容量重算｜依据 MySQL 8.4 Server System Variables 说明自绘

1. buffer pool 怎么定

经验公式：

innodb_buffer_pool_size ≈ 热点数据总量 × 1.2，且不超过物理内存的 70%

留 30% 给 OS 页缓存、连接内存（每连接排序缓冲/读缓冲）与其它进程。池不是越大越好：超过物理内存会触发系统换页，性能断崖。

innodb_buffer_pool_instances 的作用是拆分锁竞争，每个实例至少 1GB 才有意义；小实例上设 8 反而增加碎片。

2. 日志参数：安全与性能的取舍

  • innodb_flush_log_at_trx_commit = 1：每次提交都刷盘，崩溃最多丢「未提交」，最安全；
  • 改 2：每秒刷一次，丢 1 秒内已提交事务；
  • 改 0：靠后台线程，丢更多；
  • sync_binlog = 1 同理，改 0 会丢 binlog，影响复制与恢复。

这两项是数据安全底线，改之前必须业务方书面确认，不能为了 QPS 直接调。

3. redo 容量

innodb_redo_log_capacity 取代了 innodb_log_file_size / innodb_log_files_in_group，默认约 100MB。写入量大的实例要按「写入速率 × 覆盖 1 小时」估：太小会频繁触发 checkpoint，表现为 Log sequence number 与 Last checkpoint at 间隔很小、写抖动。

4. 连接数与内存的乘法

max_connections 不是越大越好。每个连接占：

线程栈（约 256KB~1MB）+ sort_buffer_size + join_buffer_size + read_buffer_size

200 连接 × (1MB + 256KB + 256KB) 就接近 300MB，加上 buffer pool 才是真实占用。判断依据是 Threads_connected 峰值 × 1.2，而不是「越大越保险」。

5. 线程数要跟磁盘匹配

innodb_read_io_threads/write_io_threads 默认各 4，SSD 且脏页压力大时才加到 8；innodb_page_cleaners 与 buffer pool 实例数相关，通常与实例数一致；purge_threads 在 undo 膨胀（长事务多）时才需要加。

五、场景说明

  1. 新实例上线：先按容量算 buffer pool 与 redo，其余保持默认；
  2. QPS 上不去：先看是不是锁/慢 SQL，再考虑日志参数（且需评审）；
  3. 写抖动：查 redo 容量与 checkpoint 间隔；
  4. 连接被打满：先查连接泄漏与慢 SQL 占连接，再谈调 max_connections；
  5. 内存吃紧：优先核 buffer pool 是否超过 70%，再看每连接缓冲。

六、示例代码/实操步骤

1. 看当前值与命中率

SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE 'innodb_buffer_pool_instances';

SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.global_status
WHERE VARIABLE_NAME IN (
  'Innodb_buffer_pool_read_requests',
  'Innodb_buffer_pool_reads',
  'Innodb_buffer_pool_pages_free',
  'Innodb_buffer_pool_pages_dirty'
);

命中率 ≈ 1 - reads / read_requests，长期低于 95% 就该扩池。

2. 在线扩 buffer pool（8.0+ 支持动态调整）

SET GLOBAL innodb_buffer_pool_size = 12884901888;  -- 12GB
SHOW STATUS LIKE 'Innodb_buffer_pool_resize_status';

调整是渐进式的，期间观察 resize_status，不要在高负载时段做。

3. 连接与线程现状

SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Max_used_connections';
SHOW STATUS LIKE 'Threads_running';
SHOW VARIABLES LIKE 'max_connections';

Threads_running 长期高于 CPU 核数数倍，说明是慢 SQL 堆积，不是连接数不够。

4. redo 与 checkpoint

SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
SHOW ENGINE INNODB STATUS\G   -- 看 Log sequence number / Last checkpoint at

两者差距长期很小（例如 < 10% 容量），说明 checkpoint 追得太紧，应调大容量。

5. Java 侧怎么落地：连接池与参数对齐

  1. HikariCP：maximumPoolSize 与 max_connections 对齐（多应用共享实例时按比例分配），minimumIdle 不宜过大；
  2. 超时：connectionTimeout、validationTimeout、maxLifetime 必须小于数据库侧 wait_timeout，避免拿到已被服务端关闭的连接；
  3. 启动校验：应用启动时读一次 SHOW VARIABLES，把 buffer pool、max_connections 记入健康检查；
  4. 参数外置：所有服务端参数写进 my.cnf 的 [mysqld]，随镜像/配置中心发布，禁止线上 SET GLOBAL 长期生效；
  5. 变更纪律：一次只改一项，记录基线指标（QPS、P99、命中率），观察一周再改下一项。

七、常见坑

  1. buffer pool 设到物理内存 90%：触发系统换页，性能反降；
  2. max_connections 调到 1000+：内存被连接吃光，慢 SQL 依旧；
  3. 为 QPS 把 flush_log_at_trx_commit 改 0：一次断电丢一批已提交事务；
  4. redo 容量太小：频繁 checkpoint，写抖动；
  5. sort_buffer_size 全局调大：并发 × 缓冲直接压垮内存；
  6. 线上 SET GLOBAL 不落配置：重启即失效，事故时找不到差异；
  7. 一次性改十个参数：出问题无法归因。

八、版本差异

  • 5.6：redo 由 innodb_log_file_size × innodb_log_files_in_group 决定，改需重启；
  • 5.7：innodb_buffer_pool_size 支持在线调整；innodb_page_cleaners 引入；
  • 8.0：innodb_redo_log_capacity（8.0.30+）统一管理 redo，最多 32 个文件；buffer pool 在线扩缩更平滑；
  • 8.4：默认值延续 8.0，innodb_redo_log_capacity 为唯一 redo 容量入口；mysql_native_password 默认关闭需注意账号兼容。

九、课后小结

  • 参数调优顺序：内存（buffer pool）→ 日志（redo/binlog）→ 连接 → 线程；
  • buffer pool ≈ 热点数据 × 1.2，且不超过物理内存 70%；
  • flush_log_at_trx_commit 与 sync_binlog 是安全底线，改需签字；
  • max_connections 要按峰值 × 1.2 算，并算上每连接内存；
  • 一次只改一个参数，观察一周，写进变更记录。

十、思考题

  1. innodb_buffer_pool_size 是不是越大越好？

    参考回答：不是。它最多占到物理内存的 70% 左右，超过后会挤占 OS 页缓存与连接内存，触发系统换页，性能反而下降。且扩容前应确认热点数据规模，盲目扩大只是浪费内存。

  2. 为什么说 innodb_flush_log_at_trx_commit = 0 是危险配置？

    参考回答：它把 redo 刷盘交给后台线程，实例崩溃或断电会丢掉最近一段已提交事务，破坏「已提交即持久」的承诺。除非业务能接受丢事务（如纯缓存型数据），否则应保持 1。

  3. max_connections 调到 1000 能解决连接打满吗？

    参考回答：通常不能。连接打满多半是连接池配置不当、连接泄漏或慢 SQL 长时间占用连接。盲目调大只会放大内存占用，让问题从「连不上」变成「内存不足 + 更慢」。应先看 Threads_running 与慢日志。

  4. redo 容量太小会有什么表现？

    参考回答：checkpoint 频繁触发，Log sequence number 与 Last checkpoint at 间隔很小，写入出现周期性抖动，redo 文件反复覆盖。表现上像「磁盘没问题但写入忽快忽慢」，调大 innodb_redo_log_capacity 可缓解。

  5. 为什么参数必须写进 my.cnf 而不是只 SET GLOBAL？

    参考回答：SET GLOBAL 只在当前实例生命周期内有效，重启即恢复默认；事故复盘时也无法从配置里看出「当时改了什么」。写进配置文件并纳入版本管理，才能保证环境一致与可追溯。
