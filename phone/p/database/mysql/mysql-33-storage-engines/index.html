存储引擎对比：为什么生产几乎只剩 InnoDB

事务、行锁、崩溃恢复、MVCC——四件事只有一个引擎全给｜依据 MySQL 8.4 Storage Engines 章节自绘

一、学习目标

  1. 列出 MySQL 常见存储引擎及各自的能力边界；
  2. 能用四行对照（事务 / 锁粒度 / 崩溃恢复 / 索引）快速判断该选谁；
  3. 知道 MyISAM 的历史包袱与迁移风险。

二、前置知识

InnoDB 架构（MQ28）、事务与锁（MQ21、MQ24）。引擎是「表级」选项，选择在 CREATE TABLE 时确定。

三、理论讲解（官方定义）

MySQL 采用插件式存储引擎架构，同一个实例里不同表可以用不同引擎。8.x 的默认引擎是 InnoDB（default_storage_engine），系统表也必须使用 InnoDB。

常见引擎：

引擎 一句话定位
InnoDB 事务型引擎，行锁 + MVCC + 崩溃恢复，绝对主力
MyISAM 老式非事务引擎，表锁、无崩溃恢复
MEMORY 数据全放内存，重启即失
ARCHIVE 只插不改的高压缩归档引擎
CSV 以 CSV 文件存储，便于交换数据
BLACKHOLE 吞掉写入不存储，常用于复制中继

四、原理拆解

看四行就够：事务、锁粒度、崩溃恢复、索引结构｜依据 MySQL 8.4 Storage Engines 对比自绘

1. 四条判定线

  1. 要事务吗：要 → InnoDB；不要 → 才考虑其它；
  2. 并发写入多吗：多 → 必须行锁，InnoDB；MyISAM 表锁直接写不动；
  3. 能接受崩溃损坏吗：不能 → InnoDB（redo + undo）；MyISAM 崩溃后要 myisamchk 修复；
  4. 索引结构：InnoDB 是聚簇索引（数据即索引），MyISAM 是非聚簇（索引与数据分离，回表靠行号）。

2. 为什么 MyISAM 被淘汰

  • 表锁：一次写入锁整表，读写互相阻塞；
  • 无事务：业务层要自己做一致性；
  • 崩溃不安全：进程崩溃后表文件可能损坏；
  • 无 MVCC：读会看到写中间态；
  • 只有索引与数据分离带来的「全表扫描略快」这点历史优势，如今也被 InnoDB 的预读与并行扫描抹平。

3. MEMORY 的适用边界

  • 数据存内存，重启丢失，适合临时结果、会话级缓存；
  • 表锁 + 不支持 BLOB/TEXT；
  • 哈希索引等值查极快，范围查不行；
  • 内存表不适合做业务主表，容易 OOM。

4. ARCHIVE 的定位

  • 只支持 INSERT 与 SELECT，不能 UPDATE/DELETE；
  • 高压缩（zlib），适合日志、流水归档；
  • 只有自增列可以有索引，查询基本靠全扫。

5. 引擎粒度与限制

  • 引擎是表级属性，ALTER TABLE ... ENGINE = InnoDB 会重建表（大表耗时且需要额外空间）；
  • 外键、事务、SAVEPOINT 只有 InnoDB 支持；
  • 同一事务里混用引擎，回滚只对 InnoDB 表生效——这是最隐蔽的坑。

五、场景说明

  1. 核心交易：InnoDB，无争议；
  2. 历史流水归档：ARCHIVE 或分区 InnoDB，看是否需要查询；
  3. 临时统计表：MEMORY 或普通 InnoDB 临时表，优先后者；
  4. 数据交换：CSV 引擎导出给外部系统（生产少见）；
  5. 老系统迁移：MyISAM → InnoDB，先评估外键、全文索引、AUTO_INCREMENT 行为差异。

六、示例代码/实操步骤

1. 查看与切换引擎

SHOW ENGINES;
SELECT TABLE_NAME, ENGINE FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'shop';

ALTER TABLE t_log ENGINE = InnoDB;         -- 会重建表，锁表时间长
ALTER TABLE t_log ENGINE = InnoDB, ALGORITHM = INPLACE, LOCK = NONE;  -- 不一定支持

2. 迁移前检查清单

-- 是否有全文索引（MyISAM 全文索引不能直接迁）
SHOW INDEX FROM t_log WHERE Index_type = 'FULLTEXT';
-- 是否有外键依赖
SELECT TABLE_NAME, CONSTRAINT_NAME FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'shop';

3. Java 侧怎么落地：引擎选择的工程约束

  1. DDL 统一模板：建表脚本强制 ENGINE=InnoDB DEFAULT CHARSET=utf8mb4，评审时检查；
  2. ORM 不写引擎：MyBatis / JPA 生成的 DDL 不要带 ENGINE=MyISAM；
  3. 迁移窗口：大表换引擎用 gh-ost / pt-osc，避免长时间锁表；
  4. 混合引擎告警：定时扫描 information_schema.TABLES，发现非 InnoDB 的业务表就告警；
  5. 事务边界：确认 ORM 的事务管理器只对 InnoDB 生效，避免「部分回滚」；
  6. 临时表策略：优先 CREATE TEMPORARY TABLE ... ENGINE=InnoDB，内存表只用于极小结果集。

七、常见坑

  1. 新建表忘写引擎：老版本默认 MyISAM，迁移后无事务；
  2. 以为 MyISAM 插入更快：表锁下并发写直接排队；
  3. MEMORY 表当缓存：重启丢数据，还占内存不释放；
  4. ARCHIVE 表上做 UPDATE：直接报错；
  5. 事务里混引擎：回滚只对 InnoDB 生效，出现「一半回滚」；
  6. 直接 ALTER ENGINE 大表：锁表几小时，业务雪崩；
  7. 忽略全文索引差异：迁移后全文检索失效。

八、版本差异

  • 5.5 之前：默认引擎是 MyISAM，InnoDB 需显式指定；
  • 5.5 起：默认改为 InnoDB；
  • 5.7：InnoDB 支持全文索引与空间索引，MyISAM 的存量理由进一步减少；
  • 8.0：数据字典统一由 InnoDB 管理，系统表必须 InnoDB；default_storage_engine 默认 InnoDB；
  • 8.4：InnoDB 是唯一推荐引擎，MyISAM/MEMORY/ARCHIVE 仍可用但仅限特定场景。

九、课后小结

  • 引擎是表级选项，default_storage_engine 默认 InnoDB；
  • 四条判定线：事务、并发写、崩溃安全、索引结构；
  • MyISAM 表锁 + 无事务 + 崩溃不安全，已被淘汰；
  • MEMORY 只适合临时小结果集，ARCHIVE 只适合只增不改的归档；
  • 迁移大表换引擎要走在线工具，并检查全文索引与外键。

十、思考题

  1. 为什么系统表必须是 InnoDB？

    参考回答：8.0 起数据字典本身存放在 InnoDB 表空间（mysql.ibd），元数据操作也需要事务与崩溃恢复保证一致性，非事务引擎无法承担。

  2. MyISAM 的「查询快」在今天还成立吗？

    参考回答：只在特定全表扫描场景略占优势，且索引与数据分离减少了一次聚簇索引的跳转；但 InnoDB 的预读、并行扫描与 Buffer Pool 已经把差距抹平，而 MyISAM 的并发与安全代价远大于收益。

  3. 事务里同时写 InnoDB 表和 MyISAM 表，回滚会怎样？

    参考回答：只有 InnoDB 表的修改会回滚，MyISAM 表的写入已经生效且无法撤销，造成部分回滚的不一致——这是混用引擎最危险的地方。

  4. MEMORY 引擎适合做业务主表吗？

    参考回答：不适合。重启即丢数据、表锁并发差、不支持大字段，且占用内存不释放；只适合临时结果、会话级小表。

  5. 大表从 MyISAM 迁到 InnoDB，风险点有哪些？

    参考回答：ALTER 重建期间的锁表时间与额外磁盘空间；全文索引需重建；自增与锁行为差异；外键约束需补齐；建议用 gh-ost/pt-osc 在线迁移并做双写校验。
