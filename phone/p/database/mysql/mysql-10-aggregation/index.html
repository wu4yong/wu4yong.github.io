聚合与分组：GROUP BY、HAVING 与 ROLLUP

聚合的坑不在函数，而在分组键、隐式排序和「先过滤还是先分组」｜依据 MySQL 8.4 SELECT 与聚合函数章节自绘

一、学习目标

  1. 说清 WHERE / GROUP BY / HAVING 的执行顺序，知道过滤条件该放哪一层；
  2. 会用 GROUP_CONCAT、WITH ROLLUP、GROUPING() 做出能直接给业务看的分组报表；
  3. 知道 8.0 起 GROUP BY 不再隐式排序，以及 ONLY_FULL_GROUP_BY 为什么必须开着。

二、前置知识

上一讲的单表查询与 EXPLAIN。知道索引顺序与 filesort 的关系即可。

三、理论讲解（官方定义）

聚合函数把多行压成一行：COUNT、SUM、AVG、MIN、MAX，以及 GROUP_CONCAT、JSON_ARRAYAGG 这类聚合器。GROUP BY 按指定列分组，HAVING 对分组后的结果再过滤。

几条官方事实：

  • 执行顺序是 WHERE → GROUP BY → 聚合 → HAVING → ORDER BY → LIMIT，WHERE 里不能出现聚合结果；
  • ONLY_FULL_GROUP_BY 从 5.7 起就是默认开启，SELECT 里出现的非聚合列必须在 GROUP BY 中（或满足函数依赖）；
  • 8.0 起 GROUP BY 不再隐式排序，要顺序必须显式写 ORDER BY；
  • WITH ROLLUP 生成汇总行，GROUPING() 用来区分「真实数据的 0」和「汇总行的 0」。

四、原理拆解

分组能不能用上索引，取决于 GROUP BY 的列顺序与索引前缀是否一致｜依据 MySQL 8.4 Optimizer 章节自绘

1. 过滤放哪一层

SELECT city, COUNT(*) AS orders, SUM(amount) AS gmv
FROM t_order
WHERE status = 2            -- 行级过滤，能用索引
GROUP BY city
HAVING SUM(amount) > 1000   -- 分组后过滤，用不了索引
ORDER BY gmv DESC
LIMIT 10;

把「能走索引的条件」放 WHERE，把「依赖聚合结果的条件」放 HAVING，是分组查询的第一原则。把 status = 2 写进 HAVING 会让所有行都参与分组，白白多算一遍。

2. 分组能不能用上索引

GROUP BY city 且 city 上有索引时，InnoDB 可以按索引顺序扫描，边扫边输出分组，Extra 里没有 Using temporary。一旦出现 Using temporary; Using filesort，说明优化器建了临时表再排序，数据量大时非常贵。

判断依据：GROUP BY 的列必须是某个索引的最左前缀，或者前面已有等值条件把前缀固定住。

3. ROLLUP 与 GROUPING

SELECT city, IF(GROUPING(city) = 1, '全部', city) AS city_label,
       COUNT(*) AS orders
FROM t_order
GROUP BY city WITH ROLLUP;

WITH ROLLUP 会在结果末尾追加汇总行；GROUPING(col) 返回 1 表示这一行是汇总行。没有它，你无法区分「这个城市的订单数真的是 0」和「这是总计行」。

4. 聚合的三个陷阱

  • COUNT(*) 统计行数，COUNT(col) 跳过 NULL，COUNT(DISTINCT col) 去重计数；
  • SUM 遇到全 NULL 返回 NULL，不是 0，报表里要 COALESCE(SUM(x), 0)；
  • AVG 的分母是非 NULL 行数，和「总行数」不是一回事。

5. 大基数分组

GROUP BY user_id 这类高基数分组会产生巨大临时表，内存放不下就落盘。可行做法：先在应用侧按分片键拆分（如 user_id % 16），分别聚合再合并；或把结果预先物化到汇总表，用定时任务增量更新。

五、场景说明

  1. 日报/月报：按 DATE(created_at) 分组（注意函数包列会让索引失效，建议加生成列）；
  2. Top N 城市：GROUP BY city ORDER BY gmv DESC LIMIT 10；
  3. 去重统计：COUNT(DISTINCT user_id)，大表慎用，可用 HyperLogLog 或近似统计；
  4. 拼接明细：GROUP_CONCAT(order_no ORDER BY id SEPARATOR ',')，注意默认 1024 字节上限；
  5. 多维汇总：WITH ROLLUP 一次出「城市 + 总计」。

六、示例代码/实操步骤

1. 一张表跑完四种聚合

CREATE TABLE t_order (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  city       VARCHAR(32) NOT NULL,
  user_id    BIGINT UNSIGNED NOT NULL,
  amount     DECIMAL(12,2) NOT NULL,
  status     TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_city_status (city, status),
  KEY idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

SELECT city,
       COUNT(*)                          AS orders,
       COUNT(DISTINCT user_id)           AS buyers,
       COALESCE(SUM(amount), 0)          AS gmv,
       ROUND(AVG(amount), 2)             AS avg_amount
FROM t_order
WHERE status = 2
GROUP BY city
ORDER BY gmv DESC
LIMIT 10;

2. 按天统计：别让函数包住索引列

-- 慢：DATE(created_at) 让 idx_created 失效
SELECT DATE(created_at) d, COUNT(*) FROM t_order GROUP BY d;
-- 快：范围条件 + 生成列
ALTER TABLE t_order ADD COLUMN created_day DATE
  GENERATED ALWAYS AS (DATE(created_at)) STORED,
  ADD KEY idx_created_day (created_day);

SELECT created_day, COUNT(*) FROM t_order
WHERE created_at >= '2022-11-01' AND created_at < '2022-12-01'
GROUP BY created_day;

3. 校验分组结果

SELECT @@sql_mode;                       -- 确认含 ONLY_FULL_GROUP_BY
EXPLAIN SELECT city, COUNT(*) FROM t_order WHERE status = 2 GROUP BY city;
-- Extra 里出现 Using index 最好，出现 Using temporary 就要评估

Java 侧怎么落地：聚合结果的对象与分页

  1. 聚合结果用专用 DTO，别复用实体：CityStat { String city; long orders; BigDecimal gmv; }，gmv 必须是 BigDecimal；
  2. COUNT 用 long，int 在千万级明细上会溢出；
  3. SUM 的空结果：SQL 侧 COALESCE 兜住，Java 侧再判空一次，避免 NPE；
  4. 分页聚合：GROUP BY ... LIMIT 只能截断分组结果，总数要单独 COUNT(DISTINCT col)，别指望 PageHelper 一把算对；
  5. MyBatis 的 resultMap 要显式映射 DECIMAL 到 BigDecimal，默认映射成 Double 会丢精度。

七、常见坑

  1. 把行级条件写进 HAVING：全量参与分组，性能白白浪费；
  2. GROUP BY 后依赖隐式排序：8.0 起不再排序，翻页结果会「随机」；
  3. COUNT(col) 当 COUNT(*)：有 NULL 时数量偏小；
  4. SUM 空集返回 NULL：报表里出现空白或 NPE；
  5. GROUP_CONCAT 超长：默认 group_concat_max_len=1024，长列表被静默截断；
  6. DATE(col) 分组：索引失效，改用生成列或范围条件；
  7. 高基数分组：临时表落盘，查询从秒级变分钟级。

八、版本差异

  • 5.7：GROUP BY 仍隐式排序；ONLY_FULL_GROUP_BY 已是默认；
  • 8.0：取消隐式排序，必须显式 ORDER BY；函数依赖检测更完善；GROUPING() 可用；
  • 8.4：聚合语义与 8.0 一致，无破坏性变化。

九、课后小结

  • 行级过滤放 WHERE，聚合结果过滤放 HAVING；
  • 分组想用索引，GROUP BY 列要是索引最左前缀；
  • 8.0 起分组不再隐式排序，顺序必须显式写；
  • ROLLUP 配 GROUPING() 才能区分汇总行；
  • 函数包住列会让索引失效，日期分组用生成列。

十、思考题

  1. WHERE 和 HAVING 都能写条件，怎么分工？

    参考回答：WHERE 在分组前对行过滤，能用索引，应放所有与聚合无关的条件；HAVING 在分组后对结果过滤，用于依赖 SUM / COUNT 等聚合值的条件，无法利用索引。

  2. 为什么 SELECT city, COUNT(*) ... GROUP BY city 在 8.0 上翻页结果和 5.7 不一样？

    参考回答：5.7 的 GROUP BY 会隐式按分组列排序，8.0 取消了这一行为，结果顺序由执行计划决定；要稳定顺序必须显式 ORDER BY city 或按聚合值排序。

  3. COUNT(*)、COUNT(col)、COUNT(DISTINCT col) 三者结果什么时候会不同？

    参考回答：列中存在 NULL 时 COUNT(col) 小于 COUNT(*)；列中有重复值时 COUNT(DISTINCT col) 小于 COUNT(col)；三者相等只在「无 NULL 且无重复」时成立。

  4. GROUP BY city WITH ROLLUP 的汇总行为什么不能用 city = '全部' 直接判断？

    参考回答：汇总行由引擎生成，city 列本身可能是 NULL 也可能是某值，直接判断会混淆；必须用 GROUPING(city) 判断是否为汇总行。

  5. 千万行表按 user_id 分组统计，查询很慢，你怎么优化？

    参考回答：先用 EXPLAIN 确认是否 Using temporary；把大查询按分片键拆成多个子查询并行执行后合并；或建汇总表由定时任务增量维护，查询直接读汇总结果。
