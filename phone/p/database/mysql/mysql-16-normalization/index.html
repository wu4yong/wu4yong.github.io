mysql-16-范式与反范式

分类：database · mysql ｜ 标签：MySQL · 数据库 · 系统课

三大范式与反范式：什么时候故意冗余

范式解决一致性与更新异常，反范式解决读性能，两者是权衡而不是对错｜依据关系数据库设计理论与 MySQL 实践自绘

一、学习目标

  1. 用一个例子把 1NF / 2NF / 3NF 讲清楚，而不是背定义；
  2. 知道范式到底防的是什么问题（更新异常、插入异常、删除异常）；
  3. 能判断哪些冗余可以接受、哪些冗余一定会失控，并写得出「冗余字段的同步方案」。

二、前置知识

表结构、主键与外键、函数依赖的基本概念。看到「A 决定 B」能反应过来是函数依赖即可。

三、理论讲解（官方定义）

范式（Normal Form）是关系模型对「表内不该存在部分依赖与传递依赖」的约束：

  • 1NF：每个列都是原子的，不能再拆（不能把「省,市,区」塞进一个列）；
  • 2NF：在 1NF 基础上，非主属性完全依赖于候选键，不存在部分依赖（联合主键里只依赖其中一列）；
  • 3NF：在 2NF 基础上，非主属性不传递依赖于候选键（A→B→C，C 不该存在）；
  • BCNF：所有决定因素都是候选键，3NF 的加强版。

范式不是 MySQL 强制的东西——它没有「范式检查开关」，只是设计方法论。MySQL 侧只提供工具（主键、唯一索引、外键）来支撑你按范式建模。

四、原理拆解

先按 3NF 建模保证一致，再按读写比例对热点路径做定向冗余｜依据关系模型理论与 MySQL 索引特性自绘

1. 一个具体例子看清 1NF → 3NF

-- 反例：一张表塞了所有东西
CREATE TABLE t_order_bad (
  id        BIGINT PRIMARY KEY,
  user_info VARCHAR(200),   -- "1001,张三,138xxxx" 违反 1NF
  items     TEXT,           -- "商品A x 2;商品B x 1" 违反 1NF
  city      VARCHAR(32)     -- 用户的城市，可通过 user_id 得到，属传递依赖
);

拆成 3NF：

CREATE TABLE t_user (
  id    BIGINT PRIMARY KEY,
  name  VARCHAR(32) NOT NULL,
  phone VARCHAR(20) NOT NULL,
  city  VARCHAR(32) NOT NULL
);

CREATE TABLE t_order (
  id      BIGINT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  status  TINYINT NOT NULL
);

CREATE TABLE t_order_item (
  order_id   BIGINT NOT NULL,
  product_id BIGINT NOT NULL,
  qty        INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  PRIMARY KEY (order_id, product_id)
);

注意 t_order_item 里 unit_price 是「下单时的成交价」，属于订单自己的属性；而商品当前价格在 t_product 里——同一概念两个值，是有意的冗余（见下文）。

2. 范式防的三类异常

异常 不范式时会发生什么
更新异常 用户改城市，订单表里 100 条历史行都要改，漏一条就不一致
插入异常 想把新用户登记进来，但没有订单就没有地方放它的信息
删除异常 删掉最后一条订单，用户信息跟着没了

3. 什么时候故意反范式

反范式的本质是用空间与一致性维护成本，换读路径上的 JOIN 与计算。

可以接受的三类冗余：

  1. 读多写少的展示字段：订单列表要显示用户名、商品标题，把 user_name、product_title 冗余进订单快照；
  2. 快照型字段：价格、地址、优惠规则在下单时刻固化，业务上本来就要求和当前值不同；
  3. 预聚合结果：日活、销售额这类统计，写时更新宽表或定时跑批，查询直接命中。

不该做的冗余：

  • 冗余一个高频变化的字段（在线状态、余额）到多张表，同步成本会超过收益；
  • 冗余可以通过索引解决的东西：分页慢不是靠加宽表，而是靠覆盖索引 / 延迟关联（MQ19）；
  • 无同步机制的冗余：改一张表不改另一张，迟早不一致。

4. 冗余的三种同步方案

方案 一致性 复杂度 适用
同事务双写 强（同库同事务） 低 单库、字段少
事务后发消息（MQ） 最终一致，可重试 中 跨服务、跨库
定时对账 + 补偿 最终一致，滞后 中高 兜底，必备

写冗余字段要同时想清楚：谁写、失败怎么办、怎么核对。三者缺一个，冗余就是负债。

5. 宽表与冷热分离

数仓里常见的「宽表」是极端的反范式：把用户、订单、商品全部打平到一张宽表，用空间换查询速度。代价是更新链路复杂，通常由离线/实时同步任务维护，而不作为线上写库的表结构。

五、场景说明

  1. 电商订单：订单表 3NF 为主，冗余 user_name 与下单时价格做快照；
  2. 社交 Feed：feed 表冗余作者头像与昵称，避免每次渲染都查用户表；
  3. 统计看板：stat_daily 预聚合表，按天写入，查询只扫一张表；
  4. 配置中心：字典、枚举这类「变化极慢」的维表，冗余到业务表里完全可接受；
  5. 历史归档：订单归档表直接按查询形态打平，反正不再更新。

六、示例代码/实操步骤

1. 从反例出发拆表

-- 违反 1NF 的写法
INSERT INTO t_order_bad (id, user_info, items) VALUES (1, '1001,张三,13800000000', 'A x2;B x1');

-- 拆表后：一次插入落到三张表，同一个事务里
START TRANSACTION;
INSERT INTO t_order (id, user_id, status) VALUES (1, 1001, 0);
INSERT INTO t_order_item (order_id, product_id, qty, unit_price)
VALUES (1, 2001, 2, 99.00), (1, 2002, 1, 19.90);
COMMIT;

2. 冗余快照字段的正确姿势

CREATE TABLE t_order (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id       BIGINT UNSIGNED NOT NULL,
  user_name     VARCHAR(32) NOT NULL,     -- 快照，不随用户改名变化
  total_amount  DECIMAL(12,2) NOT NULL,
  receiver_city VARCHAR(32) NOT NULL,     -- 快照收货城市
  created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_user_created (user_id, created_at)
) ENGINE=InnoDB;

下单时把当时的值写进去，之后永不回写——这叫快照，不叫冗余，一致性天然成立。

3. 字典维表冗余

-- 维表变化极慢，业务表只存 code + 展示名
CREATE TABLE t_dict_item (
  dict_type VARCHAR(32) NOT NULL,
  item_code VARCHAR(32) NOT NULL,
  item_name VARCHAR(64) NOT NULL,
  PRIMARY KEY (dict_type, item_code)
);

4. 冗余一致性巡检

-- 找出「订单里的用户名」与「用户表当前名」不一致的行（只允许历史快照差异）
SELECT o.id, o.user_name, u.name
FROM t_order o JOIN t_user u ON u.id = o.user_id
WHERE o.user_name <> u.name
LIMIT 20;

5. 判定该不该冗余的三个问题

  1. 这个字段读的频率远高于写吗？
  2. 业务上允许它「过期」吗（快照）？还是必须实时一致？
  3. 同步失败时，有没有对账能发现？

三问都过，才加冗余。

Java 侧怎么落地：实体拆分与冗余字段维护

  1. 实体按表拆，不按页面拆：Order、OrderItem 各一个实体，页面需要的聚合放到 VO 里组装，别为了省一次查询把实体做成「大宽类」；
  2. 快照字段用值对象固化：下单时把 user_name、address 拷进 OrderSnapshot，之后不再读用户表；
  3. 冗余用领域事件同步：UserRenamedEvent → 监听方更新冗余字段，失败进重试队列；
  4. 写路径统一：所有对 t_order 的写入走同一个 Repository，禁掉散落的 UPDATE，否则冗余字段会漏更新；
  5. 对账任务：每天跑一次上面那条巡检 SQL，差异超阈值报警。

七、常见坑

  1. 把 1NF 理解成「不能有数组」：JSON 列存数组在 MySQL 里合法，但查询、索引、约束都会很别扭，能拆表就拆表；
  2. 联合主键表漏了完全依赖：(order_id, product_id) 主键却把 product_name 放进来，改名就产生更新异常；
  3. 冗余高频变化字段：余额、在线状态冗余三份，同步迟早崩；
  4. 快照与冗余混为一谈：快照是「有意保留历史值」，冗余是「要跟源表保持一致」，两者的回写策略完全相反；
  5. 宽表直接当写库：更新一条要改十几处，事务又长又重；
  6. 没有唯一约束兜底：拆表后忘了在子表建 (order_id, product_id) 唯一键，重复写入没人拦。

八、版本差异

  • 5.7 / 8.0 / 8.4：范式本身与版本无关，属于设计方法论；
  • 8.0 起：JSON 类型与函数更完善（JSON_TABLE、多值索引），让「半结构化冗余」有了可用方案，但不改变范式判断；
  • 8.4：多值索引（multi-valued index）可用于 JSON 数组列，能在一定程度上替代「拆成关联表」的做法，但更新语义仍不如关系表清晰。

九、课后小结

  • 1NF 原子、2NF 无部分依赖、3NF 无传递依赖，BCNF 更严；
  • 范式防的是更新、插入、删除三类异常；
  • 反范式的三种合法形态：展示字段、快照、预聚合；
  • 冗余必须回答「谁写、失败怎么办、怎么核对」；
  • 快照不回写，冗余要同步，两者别混。

十、思考题

  1. 订单表里冗余 user_name，用户改名后订单列表还显示旧名字，是 bug 吗？

    参考回答：不是，这通常是快照语义——订单展示的是下单时刻的信息。如果业务要求「实时显示当前昵称」，那就不该冗余，而是在查询时 JOIN 或通过缓存读用户服务。

  2. 为什么说「加宽表解决分页慢」是错误的反范式？

    参考回答：分页慢的根因是回表与深翻页扫描，宽表只是把更多列塞进同一行，扫描量没减少，还增加了行宽与 IO。正确做法是覆盖索引或延迟关联（先取主键再回表）。

  3. 3NF 的表一定没有冗余吗？

    参考回答：不一定。3NF 只约束「非主属性对候选键的依赖」，不代表业务上不会为了读性能额外放快照字段。范式是下限，不是上限。

  4. 冗余字段的双写放在同一个事务里，能保证强一致吗？

    参考回答：同库同事务可以；跨库跨服务不行（无法真正两阶段提交），只能做到最终一致，需要消息重试与对账兜底。

  5. 什么情况下应该放弃拆表、直接用 JSON 列？

    参考回答：字段集合不固定、整体读写、很少按其中某个键过滤的场景（如埋点扩展属性）。一旦需要按内部字段高频查询或聚合，就该拆成关系表。
