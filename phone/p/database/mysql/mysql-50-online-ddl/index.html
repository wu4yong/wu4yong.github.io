在线 DDL：INSTANT、gh-ost 与 pt-osc

INSTANT 只改元数据，COPY 要重建整表 —— 差的是几小时｜依据 MySQL 8.4 Online DDL / INSTANT 说明自绘

一、学习目标

  1. 分清 ALGORITHM=INSTANT / INPLACE / COPY 三档的代价差异；
  2. 会写「指定算法 + 指定锁」的 DDL，让它在预期模式下执行而不是悄悄降级；
  3. 知道大表变更什么时候该交给 gh-ost 或 pt-osc。

二、前置知识

InnoDB 行格式与页结构（MQ20）、redo 与刷盘（MQ30）、元数据锁（MQ26）。

三、理论讲解（官方定义）

MySQL 官方把在线 DDL 的算法定义为三档：

算法 官方描述 是否重建表 允许并发 DML
INSTANT 只修改数据字典中的元数据 否 是
INPLACE 在原表上重建，不产生临时表副本 视操作而定 多数支持
COPY 建临时表 → 拷数据 → 改名 是 否（锁写）

LOCK 子句独立于算法：LOCK=NONE 允许并发读写，LOCK=SHARED 允许读不允许写，LOCK=EXCLUSIVE 全锁。指定 ALGORITHM/LOCK 后，若不满足条件则语句直接报错，不会静默降级 —— 这正是它最大的价值。

四、原理拆解

指定 ALGORITHM 与 LOCK，让 DDL 在预期模式下执行｜依据 MySQL 8.4 Online DDL Operations 说明自绘

1. INSTANT 为什么是秒级

INSTANT 不碰数据页，只在数据字典里加一行「新列的默认值」记录。旧行读取时按字典里的默认值补齐，不需要回填。8.0.12 引入 ADD COLUMN 的 INSTANT，8.0.29 扩展到 DROP COLUMN 的部分场景，8.4 中 ADD/DROP COLUMN 默认即 INSTANT。

代价：每次 INSTANT 变更都会增加行版本号，行记录的「版本」累积到一定数量后，后续操作可能被迫 rebuild。所以频繁加列要定期 OPTIMIZE TABLE 或在低峰重建一次。

2. INPLACE 的两种子模式

  • 不重建（in-place, no rebuild）：只改元数据 + 索引项，如 DROP INDEX、RENAME INDEX；
  • 重建（in-place, rebuild）：扫描原表重建（如 ADD INDEX），期间用 row log 记录并发 DML，最后回放到新结构上。row log 有容量上限（innodb_online_alter_log_max_size 默认 128MB），并发写入太猛会超限失败。

3. COPY 为什么最慢

COPY 建临时表 → 逐行拷贝 → 改名，全程持 SHARED 锁（阻塞写）。耗时 ≈ 数据量 / 拷贝速率，TB 级表要数小时，期间该表基本不可写。改列类型、改字符集、ADD PRIMARY KEY 等常走这档。

4. 大表的三条替代路线

方案 原理 适合
gh-ost 影子表 + binlog 追平，无触发器 高写入、需要可暂停可限速
pt-osc 触发器同步 + 分块拷贝 无 binlog 或触发器可接受
原生 INPLACE 单条 DDL 原地重建 中等表、可接受短时 IO 峰值

gh-ost 通过伪装成从库读取 binlog 来追平变更，因此必须开启 binlog 且 binlog_row_image=FULL；它会创建 _ghc、_del 辅助表，需要相应权限。

5. 元数据锁（MDL）才是真正的杀手

DDL 需要 MDL 排他锁，一旦有长事务持有 MDL 读锁，DDL 会阻塞并把后面的所有查询一起堵住（MDL 请求排队）。生产上 DDL 卡住的典型现象是「表突然全部超时」，而不是 DDL 自己报错。上线 DDL 前必须先查 performance_schema.metadata_locks 与长事务。

五、场景说明

  1. 加普通列：INSTANT，秒级，业务无感；
  2. 加二级索引：INPLACE, LOCK=NONE，大表挑低峰；
  3. 改列类型（INT → BIGINT）：COPY，必须走 gh-ost 或停机窗口；
  4. 改字符集 utf8mb3 → utf8mb4：COPY 且索引全重建，务必用工具；
  5. 删索引：INPLACE，较快，但要注意依赖该索引的查询会退化。

六、示例代码/实操步骤

1. 先确认算法可用性

ALTER TABLE t_order ADD COLUMN remark VARCHAR(200),
  ALGORITHM=INSTANT, LOCK=NONE;

若报 ALGORITHM=INSTANT is not supported，说明该操作不支持 INSTANT（例如列不在末尾、表有全文索引），再考虑 INPLACE。

2. 查看 DDL 进度

-- 8.0.12+ 支持进度查询
SELECT * FROM performance_schema.events_stages_current
WHERE EVENT_NAME LIKE '%alter%';

INPLACE 重建期间能看到 stage/innodb/alter table (read PK and internal sort) 等阶段，用来估算剩余时间。

3. 上 DDL 前先排长事务

SELECT trx_id, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 30;

-- 谁在持有 MDL
SELECT * FROM performance_schema.metadata_locks
WHERE OBJECT_NAME = 't_order' AND LOCK_STATUS = 'GRANTED';

有长事务先 kill 或等其结束，否则 DDL 会排队并拖垮全表查询。

4. gh-ost 执行大表变更

gh-ost \
  --host=db0 --database=shop --table=t_order \
  --alter="MODIFY COLUMN amount BIGINT NOT NULL" \
  --assume-rbr --allow-on-master \
  --max-load='Threads_running=30' \
  --critical-load='Threads_running=80' \
  --chunk-size=1000 --max-lag-millis=1000 \
  --initially-drop-ghost-table --initially-drop-old-table \
  --execute

--max-load/--critical-load 让它自动暂停；--max-lag-millis 保护从库延迟。先用 --dry-run 预检，再切 --execute。

5. Java 侧怎么落地：DDL 走流水线

  1. DDL 不进应用启动脚本：用 Flyway/Liquibase 管理版本，但大表变更单独走运维流水线；
  2. 变更前自动体检：流水线里查长事务、MDL、磁盘余量（INPLACE 重建需要额外空间 ≈ 表大小）；
  3. 强制指定算法：DDL 模板统一带 ALGORITHM=..., LOCK=NONE，不支持就失败，由人决策；
  4. 灰度顺序：先在影子库跑一遍记录耗时，再在从库执行，最后主库；
  5. 变更窗口与限流：gh-ost 挂 --max-load，与业务低峰对齐；监控 Threads_running 与从库延迟。

七、常见坑

  1. 不指定 ALGORITHM：默认可降级为 COPY，悄悄锁表数小时；
  2. 长事务持 MDL：DDL 排队，全表查询一起阻塞；
  3. innodb_online_alter_log_max_size 太小：并发写入把 row log 撑爆，DDL 失败；
  4. INPLACE 重建没留磁盘空间：中途 No space left on device；
  5. gh-ost 在无 binlog/binlog_row_image=MINIMAL 下运行：追平失败或数据不一致；
  6. DDL 与备份窗口重叠：备份被 DDL 锁阻塞；
  7. 从库先执行 DDL 导致复制延迟：主库 DDL 进 binlog，从库重放同样耗时；
  8. 频繁 INSTANT 加列不重建：行版本累积，后续查询变慢。

八、版本差异

  • 5.6：在线 DDL 支持有限，多数变更走 COPY；
  • 5.7：ALGORITHM=INPLACE 覆盖大部分常用操作，ADD INDEX 可 LOCK=NONE；
  • 8.0.12+：ALGORITHM=INSTANT 支持 ADD COLUMN（列在末尾），8.0.29 支持部分 DROP COLUMN；
  • 8.0.20+：双写缓冲改为独立文件，DDL 期间的页写入更可控；
  • 8.4 LTS：ADD/DROP COLUMN 默认走 INSTANT；INT(11) 显示宽度弃用，改列定义时不要再带宽度；innodb_redo_log_capacity 统一 redo 容量，DDL 期间 redo 压力更易评估。

九、课后小结

  • 三档算法：INSTANT 改元数据、INPLACE 原地重建、COPY 拷贝整表；
  • 显式指定 ALGORITHM+LOCK，让不可用的变更直接失败而不是降级；
  • MDL 排队是「整表超时」的真正原因，DDL 前必须排长事务；
  • 大表三路线：gh-ost（binlog 追平）、pt-osc（触发器）、原生 INPLACE（中等表）；
  • DDL 要进流水线：体检、灰度、限速、可回滚。

十、思考题

  1. INSTANT 加列为什么不需要回填数据？

    参考回答：新列的值不是写进每个数据页，而是在数据字典里登记「该列在此版本之后才存在，缺失时取默认值」。读取旧行时按字典补齐，因此不需要扫描全表。缺点是行版本增加，累积过多会触发后续重建。

  2. 为什么说 DDL 卡住时「整张表的查询都会超时」？

    参考回答：DDL 需要申请 MDL 排他锁，若前面有长事务持有 MDL 读锁，DDL 会进入等待队列。MySQL 的 MDL 请求按队列顺序处理，后续新来的普通查询也必须排在 DDL 之后等待，于是整表查询被一起堵住。现象是 DDL 没报错、业务全超时。

  3. INPLACE 与 COPY 的本质区别是什么？

    参考回答：INPLACE 在原表数据文件上重建，期间用 row log 记录并发 DML 并在最后回放，允许并发读写（配合 LOCK=NONE）；COPY 另建临时表逐行拷贝，全程持 SHARED 锁阻塞写，完成后改名替换。前者对业务影响小，后者简单但需要停机窗口。

  4. gh-ost 为什么要求 binlog_row_image=FULL？

    参考回答：gh-ost 靠读取 binlog 事件把变更应用到影子表。MINIMAL 只记录被修改的列，无法构造完整的新行；FULL 记录整行前后镜像，才能精确重放到影子表。此外还需 binlog_format=ROW 与 --assume-rbr 配合。

  5. 大表改列类型为什么不能直接 ALTER？

    参考回答：改类型必须 COPY，全程锁写，TB 级表要数小时，业务写入全阻塞；期间还可能与备份、从库重放叠加，造成长时间不可用。正确做法是用 gh-ost/pt-osc 的影子表方案，或双写迁移新表 + 灰度切流。
