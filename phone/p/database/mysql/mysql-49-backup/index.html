备份恢复：mysqldump、xtrabackup 与 PITR

逻辑备份慢而通用，物理备份快而挑版本，binlog 负责补到最后一条｜依据 MySQL 8.4 Backup and Recovery / binlog 说明自绘

一、学习目标

  1. 分清逻辑备份与物理备份的能力边界，按数据量选对工具；
  2. 用「全量 + binlog + 校验」搭出可回滚到任意时间点的恢复链路；
  3. 知道备份里最容易失手的四个点，把它们写进巡检。

二、前置知识

binlog 与两阶段提交（MQ31）、redo/undo 与刷盘（MQ30）、主从复制（MQ43）。

三、理论讲解（官方定义）

MySQL 官方把恢复手段分两类：

类别 工具 产出 特点
逻辑备份 mysqldump、mysqlpump、mysqlsh util dumpInstance SQL / 文本 跨版本、可编辑、单线程慢
物理备份 冷拷贝、xtrabackup、Clone Plugin 数据文件 快、必须版本一致
增量 binlog 事件流 与全量配合做 PITR

PITR（Point-In-Time Recovery）：先恢复一个全量基线，再重放 binlog 到指定时间点或 GTID，使数据回到「事故前一刻」。

四、原理拆解

备份要能恢复到指定时间点，而不是「有个文件」｜依据 MySQL 8.4 备份恢复与 PITR 说明自绘

1. 逻辑备份的一致性从哪来

mysqldump --single-transaction 在 RR 隔离级别下开一个一致性快照：全程读的是同一个 ReadView，因此导出的数据在时间点上是一致的。但它不锁 DDL：导出期间有人 ALTER TABLE，可能拿到一半新一半旧的表结构。生产上要么在有 DDL 窗口的时段导，要么加 --lock-tables（InnoDB 不推荐）。

2. 物理备份的一致性从哪来

xtrabackup 拷贝数据文件的同时持续跟踪 redo，拷贝过程中产生的脏页变更都被 redo 记录。恢复时先 --prepare 做 crash recovery，把数据文件推到一致状态，再启动实例 —— 所以物理备份不用锁表也能一致。

3. binlog 为什么能补到最后一条

binlog 是已提交事务的顺序日志（binlog_format=ROW 下记录行变更）。全量备份记录了当时的 binlog 位点（--master-data=2 写进备份注释，8.x 用 --source-data），从该位点往后重放即可补齐。重放是幂等的吗？不一定 —— 所以必须精确控制起点，不能重复应用同一段。

4. 三个数字决定恢复能力

  • RTO：从故障到恢复服务的时间 ≈ 恢复全量耗时 + 重放 binlog 耗时；
  • 可回滚窗口：binlog_expire_logs_seconds（8.4 默认 2592000 秒 = 30 天）决定能回到多久之前；
  • 最近一次校验：没有恢复演练的备份，可信度为零。

5. 三个工具怎么选

数据量 推荐 原因
< 10GB mysqldump / mysqlsh 逻辑导出 简单、可跨版本、便于单表恢复
10GB–TB xtrabackup 全量 + 增量 速度快、支持增量与压缩
云上/同版本 Clone Plugin（8.0.17+） 页级克隆，可直接建从库

五、场景说明

  1. 误删表：全量 + binlog 反解出删除前的 INSERT，单表恢复；
  2. 上线前基线：每次大变更前打一份全量 + 记录位点，出事可回滚到变更前；
  3. 异地容灾：每日全量传异地，binlog 实时归档到对象存储；
  4. 建新从库：用 Clone Plugin 或 xtrabackup 直接铺数据，不必走逻辑导出；
  5. 审计取证：按时间点恢复一份到临时实例，供业务核对。

六、示例代码/实操步骤

1. 逻辑全量 + 记录位点

mysqldump -u root -p \
  --single-transaction --quick --routines --triggers --events \
  --source-data=2 \
  --databases shop > shop_$(date +%F).sql

--source-data=2 会在文件头写入 CHANGE REPLICATION SOURCE TO ... SOURCE_LOG_FILE/SOURCE_LOG_POS 注释，这就是 PITR 的起点。

2. 物理全量 + 增量

# 全量
xtrabackup --backup --user=root --password=*** --target-dir=/backup/full
# 增量（基于上一次）
xtrabackup --backup --target-dir=/backup/inc1 --incremental-basedir=/backup/full
# 恢复前 prepare（全量 + 增量依次 apply）
xtrabackup --prepare --apply-log-only --target-dir=/backup/full
xtrabackup --prepare --apply-log-only --target-dir=/backup/full --incremental-dir=/backup/inc1

注意 --apply-log-only：除最后一次 prepare 外都必须带，否则会回滚掉待应用的增量。

3. binlog 归档与重放

# 持续归档（按天切文件）
mysqlbinlog --read-from-remote-server --host=db0 --user=repl \
  --raw --stop-never mysql-bin.000123 > /dev/null &

# 恢复到指定时间点
mysqlbinlog --start-datetime="2022-12-29 09:00:00" \
            --stop-datetime="2022-12-29 10:30:00" \
  /backup/binlog/mysql-bin.0001* | mysql -u root -p shop

8.4 起可用 SHOW BINARY LOG STATUS 取当前位点（取代 SHOW MASTER STATUS）。

4. 校验：恢复演练脚本化

# 恢复到临时实例 → 比对关键表行数与校验和
mysql -h tmp -e "CHECKSUM TABLE shop.t_order" > /tmp/a.txt
mysql -h prod -e "CHECKSUM TABLE shop.t_order" > /tmp/b.txt
diff /tmp/a.txt /tmp/b.txt && echo "checksum ok"

CHECKSUM TABLE 只能做粗校验，关键表再加业务口径的 COUNT(*) 与金额汇总比对。

5. Java 侧怎么落地：备份是平台能力，不是运维脚本

  1. 用 mysqlsh 的 Java 封装或调度平台触发：util.dumpInstance() 支持并发线程与压缩，比 mysqldump 快一个量级；
  2. 备份元数据入库：每次备份记录「开始时间 / 结束时间 / 位点 / 大小 / 校验结果」，供恢复时选基线；
  3. 恢复入口做成接口：传入 targetTime，平台自动选最近基线 + 拼 binlog 区间，人工只做审批；
  4. 定期演练写进流水线：每周在影子实例恢复一次并跑比对任务，失败即告警；
  5. 备份文件加密与权限收敛：备份账号只给 SELECT, RELOAD, LOCK TABLES, REPLICATION CLIENT。

七、常见坑

  1. 只做全量不做 binlog：只能回到昨天；
  2. binlog 保留期短于备份周期：中间出现断档，无法连续重放；
  3. --single-transaction 期间发生 DDL：导出结构不一致；
  4. xtrabackup 版本与 MySQL 小版本不匹配：--prepare 失败；
  5. 增量 restore 忘记 --apply-log-only：增量被回滚；
  6. 备份文件权限过宽：等于把全库数据放在公网可读目录；
  7. 从未演练：真出事时才发现恢复脚本跑不通；
  8. 备份与主库同机同盘：一次磁盘故障两份一起没。

八、版本差异

  • 5.6/5.7：mysqldump --master-data 记录位点；热备主要靠 xtrabackup；
  • 8.0：--source-data 取代 --master-data；mysqlsh util dumpInstance 提供并行逻辑导出；Clone Plugin（8.0.17+）支持页级克隆；
  • 8.0.30+：innodb_redo_log_capacity 统一 redo 容量，物理备份的 redo 跟踪更简单；
  • 8.4 LTS：SHOW BINARY LOG STATUS 取代 SHOW MASTER STATUS；mysql_native_password 默认关闭，备份账号统一用 caching_sha2_password；binlog_expire_logs_seconds 默认 30 天。

九、课后小结

  • 逻辑备份跨版本通用但慢，物理备份快但挑版本，两者都要配 binlog；
  • 一致性来源不同：逻辑靠快照，物理靠 redo 跟踪；
  • PITR = 全量基线 + 精确起点的 binlog 重放；
  • RTO、可回滚窗口、校验时间，是备份可用性的三个数字；
  • 备份账号最小权限、文件加密、离线存放、定期演练，缺一不可。

十、思考题

  1. 为什么 mysqldump 不加 --single-transaction 就可能拿到不一致的数据？

    参考回答：不加该参数时，导出过程会对表加读锁或逐表读取，期间其他事务的提交会被读到「后面」的表里，造成跨表数据不在同一时间点。加了之后所有表都在同一个 ReadView 下读取，时间点一致。注意它只保证数据一致，不保证表结构一致（DDL 不受快照保护）。

  2. 全量备份 + binlog 恢复了，为什么还可能丢数据？

    参考回答：常见三种：全量备份的位点记录不准（用了错的 --source-data 方式）；binlog 中间有断档（保留期太短或被清理）；重放时用了错误的 stop-datetime/GTID 边界，多放或少放事务。还有一类是 binlog 本身没落盘（sync_binlog=0 时崩溃丢事件）。所以要有校验与演练。

  3. 物理备份为什么必须 --prepare 才能启动？

    参考回答：拷贝过程中数据文件处于「崩溃时」状态，含未提交的脏页与未完成的事务。--prepare 执行崩溃恢复：用 redo 前滚已提交事务、用 undo 回滚未提交事务，使数据文件达到一致状态。直接启动会触发 InnoDB 自己的恢复，但增量场景下可能不一致。

  4. binlog 保留期应该设多长？

    参考回答：至少覆盖「最坏情况下从上一个可用全量恢复到现在的间隔」。日备 + 允许一次备份失败 → 至少 3 天；周备 → 至少 10 天；有合规要求按合规走。8.4 默认 30 天，多数业务够用，但要算清存储成本。

  5. 备份演练应该验证什么？

    参考回答：不只看「能启动」。要验证：恢复到指定时间点后关键表行数与金额一致；恢复耗时是否满足 RTO；恢复脚本在无人工干预下能否跑通；备份文件是否完整可解压；账号权限是否足够但不过宽。每次演练留记录，形成可追溯的恢复台账。
