SQL 改写：深翻页、OR、子查询与 UNION

LIMIT 500000, 20 要把前 50 万行读出来再丢掉｜依据 MySQL 8.4 LIMIT 优化与延迟关联实践自绘

一、学习目标

  1. 会三种深翻页改法（游标法、延迟关联、页码上限），知道各自前提；
  2. 把 OR、NOT IN、UNION 这几类常见「慢写法」改成能走索引的形态；
  3. 建立「改写后必须逐段 EXPLAIN 验证」的习惯。

二、前置知识

索引与覆盖（MQ38）、EXPLAIN（MQ35）、优化器（MQ37）。改写的本质是「让优化器有更好的计划可选」。

三、理论讲解（官方定义）

LIMIT offset, n 的语义是「先按顺序取出 offset + n 行，再丢掉前 offset 行」。因此 offset 越大，无用功越多，耗时随页码线性增长。

MySQL 8.4 的优化器对子查询、OR、UNION 都有专门策略（semijoin、物化、index_merge），但策略能否生效取决于写法与索引。

四、原理拆解

改写的目标只有一个：让每一段都能走索引，且不做多余的去重｜依据 MySQL 8.4 子查询优化 / UNION 说明自绘

1. 深翻页的三种改法

改法 写法 前提 代价
游标法（keyset） WHERE id > :last_id ORDER BY id LIMIT 20 排序键唯一且递增 只能顺序翻，不能跳页
延迟关联 子查询只取主键，外层按主键回表 子查询能走覆盖索引 扫描量仍在，但回表量大幅下降
页码上限 业务层限制最大页数 产品可接受 治标不治本

延迟关联的关键：子查询 SELECT id FROM t_order WHERE ... ORDER BY ... LIMIT 500000, 20 只走二级索引（覆盖），拿到 20 个 id 后外层用主键 IN 查整行，把 50 万次回表压成 20 次。

2. OR 为什么慢，怎么改

a = 1 OR b = 2 无法用单个联合索引，优化器要么 index_merge（两次扫描 + 合并），要么全表扫。稳妥写法是拆成两段各自走索引：

SELECT ... WHERE a = 1
UNION ALL
SELECT ... WHERE b = 2 AND a <> 1;   -- 排除重复，避免二次去重

3. NOT IN 的 NULL 陷阱

NOT IN (子查询) 只要子查询结果里有 NULL，整体结果就是空集。这是语义层面的坑，不只看性能。改 NOT EXISTS 或 LEFT JOIN ... WHERE t.id IS NULL，并确认关联列 NOT NULL。

4. IN 子查询与 semijoin

8.0 起 IN (子查询) 有多种 semijoin 策略（FirstMatch、LooseScan、物化后 JOIN）。生产上仍建议写成 EXISTS 或显式 JOIN，计划更稳定、可读性更好。

5. UNION 与 UNION ALL

UNION 强制去重，会建临时表；语义上不需要去重时必须写 UNION ALL。这是最低成本、收益最确定的一条改写。

6. COUNT(DISTINCT) 的重代价

大表 COUNT(DISTINCT col) 需要扫全部匹配行并去重。可改近似统计（业务可接受误差时）或维护预聚合表，别在列表页实时算。

五、场景说明

  1. 后台列表深翻页：优先延迟关联；能改游标就改游标；
  2. 多条件筛选：status + type 各一个索引 → 改 UNION ALL 两段；
  3. 数据同步去重：NOT IN 改成 LEFT JOIN ... IS NULL；
  4. 报表统计：COUNT(DISTINCT) 走预聚合或 HyperLogLog 近似；
  5. 分页接口封装：把「页码上限 + 每页上限」写进公共分页工具类。

六、示例代码/实操步骤

1. 先测出问题

EXPLAIN SELECT * FROM t_order ORDER BY id LIMIT 500000, 20;
-- type=index, rows≈500020, Extra 无 Using index → 大量无用回表

2. 延迟关联改写

SELECT o.*
FROM t_order o
JOIN (
  SELECT id FROM t_order ORDER BY id LIMIT 500000, 20
) t USING (id);

子查询只读索引页，外层按 20 个主键回表，Rows_examined 从 50 万降到约 50 万次索引项读 + 20 次回表。

3. 游标法改写

-- 首页
SELECT * FROM t_order ORDER BY id LIMIT 20;
-- 后续页（last_id 为上一页最后一条的 id）
SELECT * FROM t_order WHERE id > 500000 ORDER BY id LIMIT 20;

4. OR 与 UNION ALL

-- 差
SELECT * FROM t_order WHERE status = 1 OR type = 3;
-- 好
SELECT * FROM t_order WHERE status = 1
UNION ALL
SELECT * FROM t_order WHERE type = 3 AND status <> 1;

5. Java 侧怎么落地：在数据访问层固化改写

  1. 分页工具类：PageQuery 强制 pageSize <= 100、pageNo <= 500，超限直接返回错误；
  2. 延迟关联模板：MyBatis 提供 selectByDeferredJoin 片段，超过阈值页码自动切换；
  3. 游标接口：列表接口同时支持 lastId 参数，前端下拉加载走游标；
  4. 批处理去重：INSERT ... SELECT ... LEFT JOIN ... WHERE t.id IS NULL 替代 NOT IN，并按 1000 一批提交；
  5. SQL 评审清单：禁止 SELECT *、禁止 UNION（除非语义需要去重）、禁止 NOT IN 子查询，纳入 CI 静态扫描。

七、常见坑

  1. 延迟关联的子查询没走覆盖索引：变成两次全扫，更慢；
  2. 游标法用在非唯一排序键上：会漏数据或重复；
  3. UNION ALL 两段条件重叠：产生重复行，业务层没去重；
  4. NOT IN 子查询含 NULL：结果恒为空，测试数据不覆盖就上线；
  5. 改写后没验证：新写法可能触发另一种坏计划；
  6. COUNT(DISTINCT) 放列表页：每页都算一遍全表；
  7. 深度分页 + 排序键非索引列：filesort + 全扫，双重打击。

八、版本差异

  • 5.6：子查询物化优化有限，IN 子查询常退化为全扫；
  • 5.7：semijoin 策略增强，optimizer_switch 可精细控制；
  • 8.0：LATERAL（8.0.14）、CTE、窗口函数、hash join（8.0.18）、SKIP LOCKED；
  • 8.4：沿用 8.0 的优化器能力，EXPLAIN ANALYZE 便于逐段验证改写效果。

九、课后小结

  • LIMIT offset, n 的成本随页码线性增长，深翻页必须改写；
  • 游标法最快但有前提，延迟关联最通用，页码上限是兜底；
  • OR 拆 UNION ALL、NOT IN 改 NOT EXISTS、UNION 改 UNION ALL，是三招最稳的改写；
  • 改写不是凭经验替换，必须逐段 EXPLAIN 验证；
  • 把「页码上限、批大小、禁用写法」固化到代码层，问题才不会复发。

十、思考题

  1. 为什么 LIMIT 500000, 20 会慢？

    参考回答：语义是先按顺序取 500020 行再丢弃前 500000 行。若排序键不是覆盖索引列，每一行都要回表取整行，等于做了 50 万次无用回表；耗时随 offset 线性增长。

  2. 延迟关联为什么能提速？它治的是哪一段开销？

    参考回答：子查询只从二级索引取主键（覆盖扫描，不回表），把「50 万次回表」压成「50 万次索引项读 + 20 次回表」。它治的是回表开销，索引扫描量本身并没有减少。

  3. 游标法（keyset pagination）的前提是什么？

    参考回答：排序键必须唯一且单调（通常用自增主键或唯一时间戳 + id 组合），否则会出现漏行或重复；同时它只支持顺序翻页，不能随机跳页。

  4. a = 1 OR b = 2 有哪些改法，各自的代价是什么？

    参考回答：① 拆 UNION ALL 两段，各走索引，代价是两次查询 + 可能的去重条件；② 建联合索引覆盖常见组合（若能确定查询模式）；③ 保持 index_merge，代价是两索引扫描加合并，通常最慢。优先拆 UNION ALL。

  5. NOT IN (子查询) 结果为空，是性能问题还是语义问题？

    参考回答：是语义问题。SQL 三值逻辑下，只要子查询结果含 NULL，比较结果就是 UNKNOWN，NOT IN 整体不成立，返回空集。改 NOT EXISTS 或 LEFT JOIN ... IS NULL，并确保关联列 NOT NULL。
