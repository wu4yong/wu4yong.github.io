索引基础：B+Tree、聚簇索引与二级索引

聚簇索引叶子存整行，二级索引叶子存主键；回表就是把这次「再跳一次」补上｜依据 MySQL 8.4 InnoDB 索引结构章节自绘

一、学习目标

  1. 画得出一棵 B+Tree，并说清它为什么只有 3 层还能撑住千万行；
  2. 分清聚簇索引与二级索引的叶子各存什么，理解「回表」到底多贵；
  3. 会用 cardinality 与选择性判断一个索引值不值得建。

二、前置知识

主键、约束（MQ15/MQ17）。知道「主键就是数据本身」这条结论会更好理解本节。

三、理论讲解（官方定义）

InnoDB 的索引只有两种物理形态：

  • 聚簇索引（clustered index）：按主键组织，叶子节点存完整行数据；一张表只有一个；
  • 二级索引（secondary index）：按索引列组织，叶子节点存索引列 + 主键值；可以有多个。

叶子页默认 16 KB（innodb_page_size），页内是排序后的记录链表，页间用双向链表串联；非叶子页只存「键 + 子页指针」，所以一页能装很多分支，树很矮。

MySQL 8.4 支持索引类型：BTREE（默认，含 HASH 语义的 USING HASH 仅对 MEMORY）、FULLTEXT、SPATIAL。HASH 索引在 InnoDB 里只有内部的自适应哈希索引（AHI），由引擎自动维护，不能手工建。

四、原理拆解

一次回表 = 一次二级索引查找 + 一次聚簇索引查找，代价接近翻倍｜依据 MySQL 8.4 InnoDB 索引与优化器统计自绘

1. 三层树为什么能撑住千万行

按 16 KB 页、BIGINT 主键（8 B）+ 6 B 页指针 ≈ 14 B 一条分支记录：

  • 单页可容纳约 16384 / 14 ≈ 1170 个分支指针；
  • 叶子页一条记录按 100 B 估，单页约 160 行；
  • 两层（根 + 叶子）：1170 × 160 ≈ 18.7 万 行；三层：1170 × 1170 × 160 ≈ 2.1 亿 行。

所以千万行表通常只有 3 层，一次等值查询最多 3 次页访问，根页还长期驻留 Buffer Pool——这就是 B+Tree 索引快的原因。

2. 聚簇索引与二级索引的差别

CREATE TABLE t_user (
  id     BIGINT PRIMARY KEY,          -- 聚簇索引键
  name   VARCHAR(32),
  phone  VARCHAR(20),
  KEY idx_name (name)                 -- 二级索引
);
查询 走了什么 代价
WHERE id = 10 聚簇索引 1 次树查找，直接拿到整行
WHERE name = '张三' 二级索引 → 回表 1 次二级索引 + 1 次聚簇索引
SELECT id FROM ... WHERE name='张三' 二级索引（覆盖） 1 次树查找，无需回表

回表不是「多余的一步」，而是二级索引设计上的必然：二级索引不存整行，怕的就是每建一个索引就把表复制一遍。

3. 选择性（selectivity）与 cardinality

  • cardinality：索引列上不同值的个数的估计值，由采样统计得到，可通过 ANALYZE TABLE 刷新；
  • 选择性 = cardinality / 行数，越接近 1 越「唯一」，越适合做索引；
  • 经验阈值：选择性低于 0.1 的列（性别、状态、是否删除）单独建索引几乎没用，它们的价值只在于放在联合索引的后面做过滤。
SELECT INDEX_NAME, CARDINALITY, NULLABLE FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA='shop' AND TABLE_NAME='t_user';

4. 索引在磁盘上怎么长大

  • 页分裂：随机插入导致叶子页一分为二，父页多一条指针；
  • 页合并：删除后相邻页填充率过低时合并；
  • 碎片：长期增删后页内空洞变多，OPTIMIZE TABLE（或 ALTER TABLE ... FORCE）可重建；
  • innodb_fill_factor 控制建索引时每页预留空间，默认 100（B+Tree 非叶子页保留部分空间）。

5. 8.0 之后新增的几种索引能力

  • 降序索引：KEY idx (a DESC, b ASC)，8.0 起真正物理有序，5.7 只是语法；
  • 函数索引：KEY idx ((LOWER(name)))，8.0.13 起，解决「函数导致索引失效」；
  • 不可见索引：ALTER TABLE t ALTER INDEX idx INVISIBLE，优化器看不见但仍在维护，用于安全下线索引；
  • 多值索引：KEY idx ((CAST(json_col->'$.tags' AS CHAR(20) ARRAY)))，用于 JSON 数组过滤。

五、场景说明

  1. 用户表按手机号查：phone 二级索引 → 回表拿昵称；
  2. 列表页按状态 + 时间查：(status, created_at) 联合索引，选择性低的 status 放前面限制范围；
  3. 只查 ID 的场景：SELECT id 天然覆盖，不必回表；
  4. 索引下线：先 INVISIBLE 观察一周，确认无影响再 DROP；
  5. JSON 标签筛选：多值索引 + MEMBER OF / JSON_CONTAINS。

六、示例代码/实操步骤

1. 建表与观察树高

CREATE TABLE t_user (
  id        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name      VARCHAR(32) NOT NULL,
  phone     VARCHAR(20) NOT NULL,
  status    TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_phone (phone),
  KEY idx_name_status (name, status)
) ENGINE=InnoDB;
-- 看索引的页数与树高
SELECT INDEX_NAME, STAT_NAME, STAT_VALUE
FROM mysql.innodb_index_stats
WHERE DATABASE_NAME='shop' AND TABLE_NAME='t_user'
  AND STAT_NAME IN ('n_leaf_pages','size');

2. 确认是否回表

EXPLAIN FORMAT=TREE
SELECT id, name FROM t_user WHERE name = '张三';

Extra 出现 Using index 表示覆盖索引、无回表；只有 Using where 加二级索引名，说明发生了回表。

3. 制造覆盖索引

-- 原查询：回表
SELECT id, name, phone FROM t_user WHERE name = '张三';

-- 改成只查索引列，或把 phone 加进索引
ALTER TABLE t_user DROP INDEX idx_name_status,
  ADD INDEX idx_name_status_phone (name, status, phone);

4. 刷新统计信息

ANALYZE TABLE t_user;
SELECT INDEX_NAME, CARDINALITY FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA='shop' AND TABLE_NAME='t_user' AND SEQ_IN_INDEX=1;

5. 函数索引解决失效

-- 原来 WHERE LOWER(name) = 'abc' 走不了 idx_name
ALTER TABLE t_user ADD INDEX idx_name_lower ((LOWER(name)));
EXPLAIN SELECT id FROM t_user WHERE LOWER(name) = 'abc';

Java 侧怎么落地：索引与查询形态对齐

  1. 索引跟着查询建，不跟着字段建：先列出 TOP 20 的查询形态（等值、范围、排序、分页），再决定索引列组合；
  2. 实体查询都带条件字段的白名单：MyBatis 里禁止把前端传入的任意字段拼进 WHERE，否则索引全部失效；
  3. 分页查询坚持「覆盖索引 + 延迟关联」：先 SELECT id 走覆盖索引，再用 ID 批量回表；
  4. 索引变更走 DDL 流水：ADD INDEX 在 8.4 默认 INPLACE，但要评估锁与耗时，大表用 pt-online-schema-change 或 gh-ost；
  5. 监控慢查询里的 rows_examined：它远大于返回行数，就说明回了太多表或索引没命中。

七、常见坑

  1. 给低选择性列单独建索引：如 status，优化器往往直接忽略；
  2. 以为二级索引不占空间：它存索引列 + 主键，主键越宽它越大；
  3. SELECT * 破坏覆盖索引：本来能覆盖的查询一 * 就回表；
  4. cardinality 当成精确值：它是采样估计，偏差大时优化器会选错索引，ANALYZE TABLE 可纠正；
  5. 建了索引但列上有函数：LOWER()、DATE()、IFNULL() 都会让索引失效（除非用函数索引）；
  6. 联合索引顺序随手写：最左前缀不匹配等于没建（MQ19 展开）；
  7. 删除索引很随意：8.0 起先设 INVISIBLE 观察，别直接 DROP。

八、版本差异

  • 5.7：降序索引仅是语法糖；无函数索引、无不可见索引；
  • 8.0：降序索引物理生效；8.0.13 起函数索引；8.0 起不可见索引；8.0.17 起多值索引支持 JSON 数组；
  • 8.4：延续 8.0 能力；ADD COLUMN 默认 INSTANT，但加索引仍是 INPLACE，需要重建索引页。

九、课后小结

  • InnoDB 表 = 聚簇索引，叶子存整行；二级索引叶子存索引列 + 主键；
  • 三层 B+Tree 可支撑亿级行，一次查询最多 3 次页访问；
  • 回表代价约等于再查一次树，覆盖索引是最便宜的优化；
  • 选择性低的列不适合单独建索引，只适合做联合索引的后缀；
  • 8.0 起有函数索引、不可见索引、降序索引、多值索引四种新能力。

十、思考题

  1. 为什么 InnoDB 的二级索引不直接存行地址（像 MyISAM 那样）？

    参考回答：InnoDB 的行会随页分裂移动，物理地址不稳定；存主键值可以在分裂后仍然定位到行，同时天然支持覆盖索引。代价是回表要再查一次聚簇索引。

  2. 三层 B+Tree 大概能放多少行，怎么估？

    参考回答：按 16 KB 页估：分支页约 1170 个指针，叶子页约 160 行，两层约 18.7 万行，三层约 2.1 亿行。实际受行宽影响，行越宽叶子能放的行越少。

  3. Extra 里 Using index 和 Using index condition 有什么区别？

    参考回答：Using index 是覆盖索引，只读索引不回表；Using index condition 是索引下推（ICP），仍要回表，但把能在索引上判断的条件下推到引擎层，减少回表次数。

  4. 一个 status 列只有 3 个值，建索引有用吗？

    参考回答：单独建基本没用，选择性太低，优化器多半不用。但它放在联合索引的前缀里可以限制扫描范围（如 (status, created_at)），放在后缀里可以做 WHERE 过滤。

  5. 索引下线为什么建议先设 INVISIBLE？

    参考回答：不可见索引对优化器隐藏但仍在维护，一旦发现还有查询依赖它，VISIBLE 一下就能恢复；直接 DROP 后重建大表索引可能耗时数小时并影响线上。
