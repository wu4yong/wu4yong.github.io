数据类型总览：五类类型怎么选

类型决定了存储字节、比较规则和能不能建索引，选错一次要还很多年｜依据 MySQL 8.4 Data Types 章节自绘

一、学习目标

  1. 记住五类类型的存储字节与取值范围，能算清一张表的行大小；
  2. 说清 CHAR / VARCHAR / TEXT 的区别，以及为什么 TEXT 不适合做查询条件；
  3. 知道 DATETIME 与 TIMESTAMP 的时区行为差异，以及 JSON 字段怎么建索引。

二、前置知识

上一讲的建表语法与字符集。会用 EXPLAIN 看是否走索引即可。

三、理论讲解（官方定义）

官方把类型分成五大族：数值（整数、定点、浮点、位）、日期时间、字符串（定长、变长、大对象、枚举集合）、空间、JSON。选型只看三件事：取值范围够不够、比较是否精确、能不能被索引。

几条常被忽略的官方事实：

  • DECIMAL 是精确定点，FLOAT / DOUBLE 是近似二进制浮点，金额只能用 DECIMAL；
  • TIMESTAMP 存的是 UTC 秒数，读写按会话时区转换，范围只到 2038-01-19；
  • TEXT / BLOB 不能有默认值（8.0.13 起 TEXT 可用表达式默认值），且不能整列建索引，只能前缀索引；
  • JSON 从 8.0 起是原生类型，按二进制存储，但不能直接建普通索引，要落到生成列上。

四、原理拆解

同一列存 8 字节和存 40 字节，差别会体现在缓冲池命中率与扫描耗时上｜依据 MySQL 8.4 Data Types 章节自绘

1. 整数：够用就好，别一律 BIGINT

类型 字节 有符号范围
TINYINT 1 -128 ~ 127
SMALLINT 2 -32768 ~ 32767
MEDIUMINT 3 -8388608 ~ 8388607
INT 4 ±21.47 亿
BIGINT 8 ±9.22×10¹⁸

INT 上限 21 亿，看着够用；但用「自增 ID + 时间戳拼接」或分库分表乘以步长后，几年就会撞线，主键选 BIGINT 是常态。反过来，状态位、数量这类列用 BIGINT 纯属浪费缓冲池。

2. 定点与浮点：金额不许用 DOUBLE

amount    DECIMAL(12,2)   -- 精确到分，最大 12 位有效数字，其中 2 位小数
ratio     DOUBLE          -- 近似值，只用于统计、图表这类允许误差的场景

DECIMAL 以字符串式定点存储，0.1 + 0.2 在它这里等于 0.3；DOUBLE 里等于 0.30000000000000004。对账差一分钱，八成就是这里错了。

3. 字符串：定长、变长、大对象

  • CHAR(n)：定长，utf8mb4 下每字符最多 4 字节，CHAR(10) 固定占 40 字节；适合定长编码（国家码、性别位）；
  • VARCHAR(n)：变长，另加 1~2 字节长度前缀，实际占「字符字节数 + 前缀」；n 是字符数不是字节数；
  • TEXT / BLOB：行外存储，读它要多一次页访问；ORDER BY、GROUP BY、前缀索引都要额外代价。

InnoDB 的索引键前缀上限是 3072 字节（16KB 页、DYNAMIC 行格式）。utf8mb4 下一列 VARCHAR(768) 就顶满了，组合索引要按字节算。

4. 日期时间：DATETIME 还是 TIMESTAMP

类型 字节 范围 时区行为
DATE 3 1000-01-01 ~ 9999-12-31 无
DATETIME 5（+fsp 1~3） 1000-01-01 ~ 9999-12-31 原样存取，不转换
TIMESTAMP 4（+fsp 1~3） 1970-01-01 ~ 2038-01-19 存 UTC，按会话时区转换
TIME 3（+fsp） -838:59:59 ~ 838:59:59 无

DATETIME(3) 是业务时间的主流选择：不受 2038 限制、语义直白；TIMESTAMP 适合需要「随服务器时区自动换算」的审计时间，但要接受它的范围上限。

5. JSON：能存，但别指望它当查询主力

CREATE TABLE t_event (
  id      BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  payload JSON NOT NULL,
  user_id BIGINT UNSIGNED GENERATED ALWAYS AS (payload->>'$.user_id') STORED,
  PRIMARY KEY (id),
  KEY idx_user (user_id)
);

JSON 自身不可索引，但可以抽成生成列再建索引；JSON_TABLE 能把 JSON 展开成关系行。注意每次读写都要解析，高频过滤字段别塞 JSON。

6. 其他类型

  • ENUM / SET：值少且稳定时省空间，但加成员要 DDL，跨库同步容易出问题；
  • BIT：位标记，BIT(1) 常被驱动映射成布尔；
  • 空间类型（POINT、POLYGON 等）：8.0 起支持 SRID 与 R-tree 索引，地理检索不要自己存经纬度两个 double 再算距离。

五、场景说明

  1. 订单金额：DECIMAL(12,2)，一分不差；
  2. 用户 ID：BIGINT UNSIGNED，为分库分表留余量；
  3. 昵称、地址：VARCHAR(64) / VARCHAR(255)，别用 TEXT；
  4. 长文本、富文本、日志体：TEXT 或对象存储 + 表里只存 URL；
  5. 扩展字段：JSON + 生成列索引，用于「不确定字段」的配置类数据；
  6. 状态机：TINYINT + 应用枚举，比 VARCHAR 省空间也能走索引。

六、示例代码/实操步骤

1. 算清一行到底占多少字节

SELECT TABLE_NAME, AVG_ROW_LENGTH, DATA_LENGTH, INDEX_LENGTH
FROM information_schema.TABLES
WHERE TABLE_SCHEMA='demo' AND TABLE_NAME='t_user';

AVG_ROW_LENGTH 是含行头、页填充的近似值；精确计算要按「列字节 + 行头 + 空值位图」手算，InnoDB 每行还有约 5 字节头与事务信息。

2. 建一张覆盖五类类型的表

CREATE TABLE t_demo_types (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  qty         INT NOT NULL DEFAULT 0,
  amount      DECIMAL(12,2) NOT NULL DEFAULT 0.00,
  code        CHAR(6) NOT NULL,
  title       VARCHAR(128) NOT NULL,
  memo        TEXT NULL,
  born_at     DATETIME(3) NULL,
  updated_at  TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  flags       BIT(4) NOT NULL DEFAULT b'0000',
  ext         JSON NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

3. 验证类型行为

SELECT 0.1e0 + 0.2e0;              -- 0.30000000000000004
SELECT CAST(0.1 AS DECIMAL(3,1)) + CAST(0.2 AS DECIMAL(3,1));  -- 0.3
SELECT LENGTH('中文'), CHAR_LENGTH('中文');   -- 6, 2（utf8mb4 每字 3 字节）
SELECT @@session.time_zone, NOW(), UTC_TIMESTAMP();

4. JSON 检索与生成列

SELECT payload->>'$.order_id' AS order_id FROM t_event WHERE id = 1;
SELECT jt.order_id FROM t_event, JSON_TABLE(payload, '$' COLUMNS (order_id BIGINT PATH '$.order_id')) AS jt;

Java 侧怎么落地：实体映射与踩坑点

  1. 金额一律 BigDecimal，double 在 Java 侧同样会引入误差，落库前 setScale(2, RoundingMode.HALF_UP)；
  2. DATETIME → LocalDateTime，TIMESTAMP → Instant；用 LocalDateTime 接 TIMESTAMP 会丢时区语义，跨时区部署必错；
  3. TINYINT(1) 会被 Connector/J 默认映射成 Boolean（tinyInt1isBit=true），要读数字就把参数改成 false，或直接用 TINYINT 不带 (1)；
  4. JSON 字段用 String 或 @Type(JsonType.class)，别在实体里拆成多个字段再拼回去；
  5. CHAR 的尾随空格：JDBC 读出来不含填充空格，但 CHAR 比较时忽略尾随空格，别在业务里再做 trim 判断；
  6. 批量写入前做类型预校验：用 Bean Validation 限制 @Digits(integer=10, fraction=2)，把 DECIMAL(12,2) 的溢出挡在应用层。

七、常见坑

  1. 金额用 FLOAT/DOUBLE：对账永远差几分，且越算越偏；
  2. INT 存时间戳或雪花 ID：几年后溢出，改主键类型等于重建表；
  3. VARCHAR(255) 建联合索引：utf8mb4 下三列就超 3072 字节；
  4. TEXT 当查询条件：全表扫描 + 行外读页，慢得毫无悬念；
  5. TIMESTAMP 存生日或远期时间：2038 溢出、时区漂移；
  6. ENUM 频繁加值：每次都要 DDL，且不同环境枚举顺序不一致会写坏数据；
  7. JSON 里存主键做关联：没生成列就没索引，JOIN 直接退化成扫全表。

八、版本差异

  • 5.7 → 8.0：JSON 成为原生类型（5.7 已有但 8.0 完善了 JSON_TABLE、->> 等）；utf8mb4 成为默认；INT(11) 显示宽度自 8.0.17 弃用。
  • 8.4：类型体系无破坏性变化，utf8mb3 弃用、mysql_native_password 关闭；显示宽度写法仍被接受但不起作用。
  • 9.x：新增 VECTOR 类型与向量索引，用于向量检索；8.4 没有这个类型，别在 8.4 上照抄 9.x 的建表语句。

九、课后小结

  • 五类类型，选型只看范围、精确、可索引三件事；
  • 整数够用即可，主键留 BIGINT 余量；
  • 金额 DECIMAL，比率 DOUBLE；
  • 变长用 VARCHAR，大对象用 TEXT + 少查；
  • 时间优先 DATETIME(3)，需要时区换算才用 TIMESTAMP；
  • JSON 要索引就落生成列。

十、思考题

  1. DECIMAL(12,2) 最大能存多大的数？

    参考回答：总共 12 位有效数字，其中 2 位小数，所以整数部分最多 10 位，即最大 9999999999.99。

  2. 为什么 TEXT 列不能直接建普通索引？

    参考回答：TEXT 是行外存储的大对象，长度可达 4GB，B+Tree 键放不下也不该放；InnoDB 用前缀索引（KEY (col(20))）解决，代价是前缀相同的行还要回表过滤。

  3. TIMESTAMP 与 DATETIME 在同一时刻写入不同会话时区，读出来为什么会不一样？

    参考回答：TIMESTAMP 落库存 UTC，读时按会话 time_zone 转换；DATETIME 原样存取，不做转换。所以跨时区读写 TIMESTAMP 会「变」，DATETIME 不会。

  4. JSON 字段要按 $.user_id 过滤，怎么让它走索引？

    参考回答：新增 STORED（或 VIRTUAL）生成列 payload->>'$.user_id'，再在该生成列上建索引；查询时直接用生成列或等值表达式，优化器才能命中。

  5. 一张表 20 个 VARCHAR(255) 会导致什么问题？

    参考回答：行大小迅速逼近 65535 字节上限，InnoDB 还会把超长列溢出到行外；缓冲池命中率下降、扫描变慢，联合索引也很容易触发 3072 字节前缀上限。
