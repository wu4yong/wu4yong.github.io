分类：database · mysql ｜ 标签：系统课 · MySQL · 数据库

复制格式与延迟：半同步与并行复制

主库提交时要不要等从库确认 —— 决定数据能丢多少｜依据 MySQL 8.4 Semisynchronous Replication 说明自绘

一、学习目标

  1. 分清异步、半同步、组复制三种模式的「丢数据边界」；
  2. 会配 rpl_semi_sync_source 插件，理解 AFTER_SYNC 与超时降级；
  3. 会用 WRITESET 并行复制把回放延迟压下来，知道大事务与 DDL 的代价。

二、前置知识

主从复制链路与 GTID（MQ43）、binlog 格式（MQ32）。

三、理论讲解（官方定义）

模式 主库何时返回 主库宕机可能丢什么
异步复制（默认） 写完 binlog 立即返回 尚未推送到从库的事务
半同步复制 至少一个从库确认收到后返回 已发送但未确认的事务
组复制（MGR） 多数派认证后提交 几乎不丢（认证即持久）

半同步的关键点：从库只要收到 relay log 事件就回 ACK，并不等回放完成。所以它保证「已提交不丢」，不保证从库数据已最新。

四、原理拆解

回放跟不上，先从并行度和事务粒度下手｜依据 MySQL 8.4 Replication Threads / WRITESET 说明自绘

1. 半同步的两条参数与两种时机

rpl_semi_sync_source_enabled   主库侧插件开关
rpl_semi_sync_source_timeout   等待确认超时（默认 10000ms）
rpl_semi_sync_source_wait_point  AFTER_SYNC（默认）/ AFTER_COMMIT
  • AFTER_SYNC：先等 ACK 再提交，客户端看到「已提交」时从库一定已收到；
  • AFTER_COMMIT：先提交再等 ACK，主库崩溃时可能出现「客户端看到成功但未同步」；
  • 超时后自动降级为异步，且不会自动恢复告警，必须监控 Rpl_semi_sync_source_status（1 表示仍生效）。

2. 并行复制的三代演进

版本 并行维度 限制
5.6 按库（database） 单库无法并行
5.7 LOGICAL_CLOCK（组提交） 依赖主库组提交粒度
8.0.22+ WRITESET（按行集合哈希） 需 binlog_row_image=FULL

WRITESET 的思路是：只要两个事务修改的行集合不相交，就能并行回放。它让单库高并发写入的从库也能并行，是当前最有效的延迟治理手段。

3. 延迟的三种来源

  • 大事务：单事务几十万行，回放必须整段等；
  • DDL 与元数据锁：从库执行 DDL 期间后续事件全排队；
  • 从库资源不足：buffer pool 小、磁盘慢、CPU 被抢占。

调 replica_parallel_workers 只能解决「并发度不够」，解决不了大事务与 DDL。

4. 为什么半同步会拖慢写入

每次提交多一次网络往返（RTT）。同机房 RTT 0.1ms 影响可忽略；跨机房 5ms 以上、QPS 又高时，主库提交吞吐会明显下降。这是「一致性换性能」的直接体现。

五、场景说明

  1. 核心交易库：半同步 + AFTER_SYNC，宁慢不丢；
  2. 日志/统计库：异步即可，丢了能重算；
  3. 延迟敏感从库：WRITESET 并行 + 从库同规格；
  4. 批量导入：拆小批提交，避免从库回放卡死；
  5. 跨机房容灾：评估 RTT 后再决定是否开半同步。

六、示例代码/实操步骤

1. 安装并开启半同步

-- 主从都装插件
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';

SET GLOBAL rpl_semi_sync_source_enabled = ON;
SET GLOBAL rpl_semi_sync_replica_enabled = ON;

写进 my.cnf 才能持久：

[mysqld]
plugin-load-add = semisync_source.so
rpl_semi_sync_source_enabled = ON
rpl_semi_sync_source_timeout = 10000
rpl_semi_sync_source_wait_point = AFTER_SYNC

2. 观察是否真的在半同步

SHOW STATUS LIKE 'Rpl_semi_sync_source_status';
SHOW STATUS LIKE 'Rpl_semi_sync_source_no_tx';
SHOW STATUS LIKE 'Rpl_semi_sync_source_timeout';

no_tx 持续增长 = 已降级为异步；timeout 增长 = 网络或从库 ACK 慢。

3. 开 WRITESET 并行复制

-- 主库
SET GLOBAL binlog_transaction_dependency_tracking = WRITESET;
SET GLOBAL binlog_row_image = FULL;
-- 从库
SET GLOBAL replica_parallel_type = LOGICAL_CLOCK;
SET GLOBAL replica_parallel_workers = 8;   -- 与 CPU 核数匹配
SET GLOBAL replica_preserve_commit_order = ON;

4. 定位回放卡点

SELECT * FROM performance_schema.replication_applier_status_by_worker;
SELECT THREAD_ID, WORKER_ID, APPLYING_TRANSACTION, LAST_APPLIED_TRANSACTION
FROM performance_schema.replication_applier_status_by_worker\G

5. Java 侧怎么落地：把复制模式变成可观测项

  1. 连接串区分：主库 URL 标记 write，从库标记 read，配置中心维护；
  2. 降级告警：定时任务读 Rpl_semi_sync_source_status，为 0 时即使 P0 告警；
  3. 延迟熔断：延迟 > 3s 自动把读流量切回主库（限流保护主库）；
  4. 批量任务约束：批处理每 5000 行提交一次，单事务不超过 1 万行；
  5. 演练：每季度做一次主库 kill -9 演练，验证是否真丢数据。

七、常见坑

  1. 开了半同步就以为不丢：超时降级后静默变异步；
  2. AFTER_COMMIT 配半同步：仍有「看到成功但没同步」的窗口；
  3. 只调 parallel_workers：大事务与 DDL 导致的延迟不会改善；
  4. WRITESET 没开 binlog_row_image=FULL：并行度退化；
  5. 从库规格低于主库：回放能力天然不足；
  6. replica_preserve_commit_order 关闭：并行回放导致数据顺序错乱；
  7. 跨机房硬开半同步：RTT 把主库写入拖垮。

八、版本差异

  • 5.6：并行复制按库；半同步插件名 rpl_semi_sync_master/slave；
  • 5.7：LOGICAL_CLOCK 并行复制；rpl_semi_sync_master_wait_point 可选；
  • 8.0：WRITESET（8.0.22+）；插件改名 rpl_semi_sync_source/replica（8.0.26+）；
  • 8.4：参数名统一为 source/replica 前缀，半同步与并行复制能力延续 8.0，replica_parallel_workers 默认 4。

九、课后小结

  • 异步：能丢；半同步：已提交不丢；MGR：认证即持久；
  • 半同步只保证「从库收到」，不保证「从库回放」；
  • AFTER_SYNC 是安全选项，超时降级必须告警；
  • 并行复制三代：按库 → 组提交 → WRITESET，WRITESET 最强；
  • 延迟治理要同时管大事务、DDL 与从库资源，参数只是其中一环。

十、思考题

  1. 半同步能保证「从库数据一定最新」吗？

    参考回答：不能。从库收到 relay log 事件就回 ACK，回放可能还在后面。它保证的是主库已提交的事务在至少一个从库上有副本，避免主库宕机丢提交。

  2. Rpl_semi_sync_source_status = 0 意味着什么？

    参考回答：说明没有从库在有效半同步状态下确认，主库已降级为异步复制，此时提交不再等待 ACK，宕机可能丢已提交事务。应立即检查从库线程、网络与 rpl_semi_sync_source_timeout。

  3. 为什么 WRITESET 要求 binlog_row_image=FULL？

    参考回答：WRITESET 需要根据行变更计算哈希集合来判断两个事务是否冲突；MINIMAL/NOBLOB 只记录部分列，无法准确还原被修改的行集合，哈希失真会导致并行判断错误。

  4. replica_parallel_workers = 16 一定能降低延迟吗？

    参考回答：不一定。若延迟来自单个大事务或 DDL，事件本身无法拆并行，加 worker 没用；只有当 relay log 里存在大量可并行的小事务（且 replica_preserve_commit_order=ON）时才有收益。

  5. 跨机房部署要不要开半同步？

    参考回答：要看 RTT 与写入 QPS。RTT 高时每次提交多一次往返，主库吞吐会明显下降；若业务不能接受丢事务，应优先考虑同城双活 + MGR 或异步 + 定期校验的方案，而不是硬开跨机房半同步。
