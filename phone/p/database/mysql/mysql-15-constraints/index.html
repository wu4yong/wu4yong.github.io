约束：主键、唯一、外键、CHECK 与默认值

约束是数据库侧最后一道防线，但它只保证「放进去的数据合法」，不保证业务语义正确｜依据 MySQL 8.4 Data Definition 章节自绘

一、学习目标

  1. 分清主键、唯一索引、普通索引的关系与取舍；
  2. 知道外键在 InnoDB 里的真实代价，能判断用还是不用；
  3. 会用 CHECK（8.0.16 起真正生效）替代一部分应用层校验，并理解默认值的表达式写法。

二、前置知识

CREATE TABLE 基本语法、索引概念（MQ18 会展开）。本节只需要知道「唯一约束在存储层就是一个唯一索引」。

三、理论讲解（官方定义）

MySQL 里的约束只有五类：主键（PRIMARY KEY）、唯一（UNIQUE）、外键（FOREIGN KEY）、CHECK、NOT NULL / DEFAULT。

官方要点：

  • 一张表只能有一个主键，主键隐含 NOT NULL 与唯一索引；
  • UNIQUE 在 MySQL 里就是唯一索引，可以建多个，允许包含多个 NULL（NULL 之间不判重）；
  • 外键只在 InnoDB 上生效，MySQL 8.4 的 MyISAM 会解析但忽略外键定义；
  • CHECK 约束自 8.0.16 起真正参与校验，之前只是解析不执行；
  • DEFAULT 自 8.0.13 起支持表达式（DEFAULT (expr)），例如 DEFAULT (UUID())、DEFAULT (CURRENT_TIMESTAMP)。

四、原理拆解

主键与唯一约束最终都落到索引上；外键会在子表上额外加索引并加锁｜依据 MySQL 8.4 CREATE TABLE 与 InnoDB 约束章节自绘

1. 主键与唯一：都靠索引实现

CREATE TABLE t_user (
  id        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  tenant_id BIGINT UNSIGNED NOT NULL,
  email     VARCHAR(128) NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_tenant_email (tenant_id, email)
) ENGINE=InnoDB;
  • 主键 = 聚簇索引的键，决定了行的物理顺序；
  • UNIQUE KEY 是二级索引，插入时要做一次唯一性检查（读一次索引）；
  • 唯一约束放在联合列上时，判重的是整组值，(tenant_id, email) 相同才算冲突；
  • 唯一索引里允许多行 NULL，因为 NULL 不等于 NULL——这条常被误认为「唯一索引不允许空值」。

2. 外键的真实代价

外键不是「免费的数据校验」，它带来三件事：

维度 影响
索引 子表外键列若没索引，InnoDB 自动建一个；父表被引用列必须有索引
锁 父表上做 SELECT ... FOR SHARE 级别的检查，高并发下会争锁
DDL 加外键可能触发表重建，foreign_key_checks=0 才能绕过部分限制
级联 ON DELETE CASCADE 会在大表上级联删除，一条语句锁住大量行

所以互联网业务普遍不在库里建外键，改由应用保证引用完整性；金融、内部系统这类一致性优先的场景可以用。

3. CHECK 约束（8.0.16 起生效）

CREATE TABLE t_order (
  id     BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  amount DECIMAL(12,2) NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,
  CONSTRAINT ck_amount_positive CHECK (amount > 0),
  CONSTRAINT ck_status_range   CHECK (status BETWEEN 0 AND 9)
) ENGINE=InnoDB;

官方限制（写之前必须知道）：

  • 表达式结果必须是 TRUE 或 UNKNOWN，为 FALSE 才报错；
  • 不允许子查询、存储函数、变量、NOW()/CURRENT_USER() 等非确定性函数；
  • 约束名在整个 schema 内唯一，不是表内唯一；不写名字时自动生成 <表名>_chk_<序号>；
  • 可以写 CHECK (...) NOT ENFORCED，即建了但不校验（用于过渡期）；
  • 参与 INSERT / UPDATE / REPLACE / LOAD DATA；INSERT IGNORE 时是警告并跳过该行，不是报错；
  • 被外键 ON UPDATE/DELETE 引用的列不能出现在 CHECK 里。

4. 默认值与隐式默认

  • NOT NULL 列没有 DEFAULT 时，插入不给值会报错（严格模式）；
  • BLOB / TEXT / JSON / GEOMETRY 不能有字面量默认值，8.0.13 起可以用表达式 DEFAULT ('{}')；
  • TIMESTAMP / DATETIME 支持 DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP；
  • 显式默认值对 INSERT ... SELECT、LOAD DATA 同样生效，但 LOAD DATA 里缺失列走默认而非报错。

5. 约束在哪儿查

-- 表上的约束
SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE FROM information_schema.TABLE_CONSTRAINTS
WHERE TABLE_SCHEMA = 'shop' AND TABLE_NAME = 't_order';

-- CHECK 约束的定义
SELECT CONSTRAINT_NAME, CHECK_CLAUSE FROM information_schema.CHECK_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'shop';

8.4 里还可以用 SHOW CREATE TABLE 一次看全，DDL 审核时以它为准。

五、场景说明

  1. 用户表：主键自增 / 雪花，(tenant_id, email) 唯一；
  2. 订单表：CHECK 挡掉负金额与非法状态，避免脏数据进报表；
  3. 配置表：JSON 列用表达式默认值 DEFAULT ('{}')；
  4. 内部系统：保留外键 + ON DELETE RESTRICT，把引用完整性交给库；
  5. 高并发表：去掉外键，改为应用校验 + 定期对账任务。

六、示例代码/实操步骤

1. 建一张带齐五类约束的表

CREATE TABLE t_account (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id    BIGINT UNSIGNED NOT NULL,
  balance    DECIMAL(14,2) NOT NULL DEFAULT 0.00,
  currency   CHAR(3) NOT NULL DEFAULT 'CNY',
  profile    JSON NOT NULL DEFAULT ('{}'),
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_currency (user_id, currency),
  CONSTRAINT ck_balance CHECK (balance >= 0),
  CONSTRAINT ck_currency CHECK (currency IN ('CNY','USD','EUR'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

2. 加约束（在线 DDL）

ALTER TABLE t_account
  ADD CONSTRAINT ck_balance CHECK (balance >= 0),
  ALGORITHM=INPLACE, LOCK=NONE;

加 CHECK 属于「只改元数据 + 校验存量」的操作，8.4 里通常是 INPLACE；但有存量脏数据时会失败，先用查询确认：

SELECT COUNT(*) FROM t_account WHERE balance < 0;

3. 命名与排查

-- 违反约束时报错形如：
-- ERROR 3819 (HY000): Check constraint 'ck_balance' is violated.

-- 找出所有 CHECK
SELECT TABLE_NAME, CONSTRAINT_NAME, CHECK_CLAUSE
FROM information_schema.CHECK_CONSTRAINTS WHERE CONSTRAINT_SCHEMA = DATABASE();

4. 外键的两种写法

-- 允许删除父表行时级联删除子表
ALTER TABLE t_order
  ADD CONSTRAINT fk_order_user FOREIGN KEY (user_id) REFERENCES t_user(id)
  ON DELETE CASCADE ON UPDATE RESTRICT;

-- 临时关闭外键检查（导入数据、加外键前的常见操作，仅当前会话生效）
SET foreign_key_checks = 0;

Java 侧怎么落地：约束与应用校验的分工

  1. DTO 校验挡格式，CHECK 挡底线：@NotNull、@Min(0) 在接口层拦 90% 的脏数据，CHECK 只防「绕过接口的写入」（脚本、其他服务、历史修复 SQL）；
  2. 唯一约束当幂等锁：注册接口用 (tenant_id, email) 唯一索引，捕获 SQLIntegrityConstraintViolationException 后返回「已存在」，比先 SELECT 再 INSERT 少一次竞态；
  3. 别把外键交给 ORM 生成：MyBatis-Plus / Hibernate 的 DDL 生成容易带外键，线上表建议手写 DDL，外键单独评审；
  4. 异常码要能区分：MySQL 错误码 1062 是唯一冲突、3819 是 CHECK 违反、1452 是外键失败，统一异常处理后返回可读提示；
  5. 约束变更要走 DDL 流水：CHECK 加入前先跑存量数据体检，避免上线时 ALTER 失败或锁表。

七、常见坑

  1. 以为 CHECK 一直生效：5.7 与 8.0.16 之前只解析不校验，迁移到 8.4 后存量脏数据会让新写入报错；
  2. 唯一索引以为不许 NULL：实际允许多行 NULL，想要「必填且唯一」得同时 NOT NULL；
  3. 外键列没索引：InnoDB 自动补索引，SHOW CREATE TABLE 里会多出一条，别以为是自己建的；
  4. ON DELETE CASCADE 用在百万级子表：一条删除语句级联删几十万行，锁与 binlog 都会炸；
  5. BLOB/TEXT 直接给字面量默认值：8.0.13 之前直接报错，之后必须写成表达式；
  6. INSERT IGNORE 掩盖 CHECK 失败：只出警告不报错，数据被静默跳过；
  7. 约束名跨表重复：CHECK 名在 schema 内唯一，第二张表再叫 ck_amount 会冲突。

八、版本差异

  • 5.7：CHECK 只解析不执行；DEFAULT 不支持表达式；UUID() 不能做默认值；
  • 8.0：8.0.13 起支持 DEFAULT (expr)；8.0.16 起 CHECK 真正生效；8.0.30 起支持 sql_generate_invisible_primary_key 自动补主键；
  • 8.4：约束行为与 8.0 一致；CHECK_CONSTRAINTS 视图可直接查询；DDL 侧 ADD COLUMN 默认 INSTANT，但加约束仍要校验存量数据。

九、课后小结

  • 主键唯一且非空，唯一索引可多列、允许多个 NULL；
  • 外键带来索引、锁、级联三类代价，互联网业务多数不用；
  • CHECK 8.0.16 起生效，表达式不能含子查询与非确定性函数；
  • DEFAULT (expr) 是 8.0.13 之后的新写法，JSON/TEXT 只能这样给默认值；
  • 约束名在 schema 内唯一，改约束前先体检存量数据。

十、思考题

  1. 唯一索引上为什么可以插多行 NULL？

    参考回答：唯一性检查用 = 比较，而 SQL 里 NULL = NULL 结果是 UNKNOWN 不是 TRUE，所以任意两行 NULL 都不构成「重复」；想要「必填唯一」必须把列声明为 NOT NULL。

  2. 为什么很多互联网公司不在数据库里建外键？

    参考回答：外键会在父表上加共享锁做引用检查，高并发写入时争锁；ON DELETE CASCADE 会级联锁大量行；分库分表后跨库外键根本不支持。所以改由应用层校验 + 对账兜底。

  3. CHECK (amount > 0) 在 5.7 上写了会发生什么？

    参考回答：5.7 会解析并保存这个定义，但不执行校验，负值照样能写进去；迁到 8.0.16+ 后开始真正校验，存量脏数据会让后续写入或 ALTER 失败。

  4. INSERT IGNORE 遇到 CHECK 违反时表现如何？

    参考回答：不报错，产生一条警告并跳过该行，其他行继续插入。这会让脏数据「静默消失」，排查时容易误判为没插入成功。

  5. 加 CHECK 约束时为什么会 ALTER 失败？

    参考回答：MySQL 要校验存量数据是否满足新约束，只要有一行不满足就整体失败。上线前先跑一遍等价的 SELECT ... WHERE NOT (条件) 确认结果为空。
