选类型的四条原则

类型选错不会立刻报错，只会在数据涨起来、要加索引、要扩字段的时候集中爆发｜依据 MySQL 8.4 Data Types 与 InnoDB 索引限制自绘

一、学习目标

  1. 用四条原则把「一个业务字段」推导成一个具体类型，而不是凭习惯写 VARCHAR(255)；
  2. 认出五个最典型的历史包袱，并知道改造成本；
  3. 把这套原则落成一张团队可复用的选型表。

二、前置知识

上一讲的五类类型与字节数。知道 3072 字节索引前缀限制、2038 时间上限即可。

三、理论讲解（官方定义）

官方文档给的是类型定义与存储特性，没有给选型建议；选型是工程判断。可以把判断收敛成四条：

  1. 够用：取值范围覆盖未来 3~5 年业务增长，留一倍余量；
  2. 精确：需要精确比较或累计的字段，不允许近似类型；
  3. 可索引：将来可能进 WHERE、ORDER BY、JOIN 的列，必须能建出高效索引；
  4. 可演进：值域会变的字段，留扩展方式（字典表、JSON、生成列）。

四、原理拆解

先定值域，再定精度，再看索引，最后想演进；顺序颠倒就会反复改表｜依据工程实践与 8.4 类型文档自绘

1. 原则一：够用，但别一步到位到浪费

字段 常见写法 更稳的写法 理由
自增主键 INT BIGINT UNSIGNED 21 亿在分库分表后几年就撞线
数量、次数 BIGINT INT / MEDIUMINT 省缓冲池，扫描更快
状态 VARCHAR(20) TINYINT 1 字节 vs 20 字节，且能走索引
百分比 DOUBLE DECIMAL(5,2) 需要精确到 0.01%

够用的算法是「现有峰值 × 增速 × 3 年」，再对齐到最近的类型宽度，而不是直接上最大。

2. 原则二：精确优先

凡是要累计、要比较、要出报表对账的数值，一律排除 FLOAT / DOUBLE：

  • 金额、单价、税额 → DECIMAL(12,2) 或 DECIMAL(18,4)；
  • 汇率、利率 → DECIMAL(10,6)；
  • 比例、评分（允许误差） → DOUBLE 可以；
  • 计数、排名 → 整数。

3. 原则三：可索引

能索引的前提是「长度可控 + 类型可比较」：

  • VARCHAR(768) 在 utf8mb4 下就吃满 3072 字节前缀上限，组合索引无从谈起；
  • TEXT 只能前缀索引，等值查询还要回表复核；
  • JSON 无索引，必须抽生成列；
  • 时间统一 DATETIME(3)，别一半 TIMESTAMP 一半 VARCHAR('2022-11-17')，后者排序等于字符串排序。

4. 原则四：可演进

值域会变的字段，提前设计演进路径：

  • 状态、类型：TINYINT + 字典表（值→语义在应用或字典表里维护），加状态不用 DDL；
  • 将来要加字段的配置：JSON + 生成列索引；
  • 枚举会无限增长（标签、类目）：独立关联表，别用 ENUM；
  • 短中期会有多语言：VARCHAR 足够，别用 CHAR 固定宽度。

五、场景说明

  1. 新业务建表：按四条原则过一遍，写进建表评审清单；
  2. 接手老库：先按字段扫一遍反例，按「收益/成本」排序改造，不要一次全动；
  3. 分库分表前：主键与分片键类型必须能承载放大后的值域；
  4. 数据同步到数仓：DECIMAL 与 DATETIME 在异构库间语义最稳；
  5. 加 JSON 扩展字段：只放「不确定结构」的数据，别把核心查询字段塞进去。

六、示例代码/实操步骤

1. 一张按原则落地的表

CREATE TABLE t_product (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  spu_code     VARCHAR(32)  NOT NULL,           -- 定长可控，能建唯一索引
  title        VARCHAR(128) NOT NULL,
  price        DECIMAL(12,2) NOT NULL,
  stock        INT NOT NULL DEFAULT 0,
  status       TINYINT NOT NULL DEFAULT 0,      -- 0 草稿 1 上架 2 下架
  tags         JSON NULL,                       -- 值域不定，用 JSON
  tag_first    VARCHAR(16) GENERATED ALWAYS AS (tags->>'$.first') VIRTUAL,
  created_at   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_spu (spu_code),
  KEY idx_status_created (status, created_at),
  KEY idx_tag_first (tag_first)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;

2. 反例与改造成本对照

-- 反例 1：金额用 DOUBLE
`amount` DOUBLE              -- 改成 DECIMAL(12,2)：改列类型 + 重建表 + 历史数据重算
-- 反例 2：主键用 VARCHAR(64)（UUID）
`id` VARCHAR(64) PRIMARY KEY -- 改成 BIGINT：全表重建 + 所有外键/接口跟着改
-- 反例 3：时间用字符串
`created` VARCHAR(19)        -- 改成 DATETIME(3)：范围查询从字符串比较变成时间比较

改造要按「是否影响主键/索引/外部契约」分级，主键类改动必须走停机窗口或双写迁移。

3. 选型自检 SQL

-- 找出超长字符串列、TEXT 列、DOUBLE 金额列
SELECT TABLE_NAME, COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA='demo'
  AND (CHARACTER_MAXIMUM_LENGTH > 255 OR DATA_TYPE IN ('text','longtext','double','float'));

Java 侧怎么落地：把原则写进代码与评审

  1. DTO 与列类型对齐：DECIMAL → BigDecimal、DATETIME → LocalDateTime、TINYINT → Integer（关掉 tinyInt1isBit），映射错会在序列化时暴露成 1.0 之类的脏数据；
  2. 状态用枚举 + code：Java enum 存 TINYINT code，别存 name()，改名即数据漂移；
  3. 金额计算统一 BigDecimal + setScale，禁止 doubleValue() 中转；
  4. JSON 扩展字段封装成值对象：读写都走 Jackson，避免各处 payload.getString("x")；
  5. 建表脚本纳入 Flyway 版本管理，DDL 与实体在同一次提交里评审，防止「代码加了字段、表没加」。

七、常见坑

  1. 主键 INT 自增：分库分表放大后溢出；
  2. 主键 VARCHAR(64) UUID：随机写导致页分裂、索引膨胀；
  3. 金额 DOUBLE：对账差钱，且改动成本极高；
  4. 时间存字符串：范围查询、时区、排序全都错；
  5. ENUM 存业务状态：加值要 DDL，环境间顺序不一致会写坏数据；
  6. TEXT 存标题：查询要行外读页，索引只能前缀；
  7. 一律 VARCHAR(255)：组合索引撞 3072 字节上限，且行大小虚高。

八、版本差异

  • 8.0：utf8mb4 成为默认，JSON 功能完善，8.0.17 起整数显示宽度弃用；
  • 8.4：utf8mb3 弃用、INSTANT 成为加删列默认算法——这让「选错类型后小步改表」变得便宜，但改数据类型仍要重建表；
  • 9.x：新增 VECTOR，向量相似度检索才需要用到，与业务字段选型无关。

九、课后小结

  • 四条原则按顺序用：够用、精确、可索引、可演进；
  • 主键留 BIGINT 余量，计数别滥用 BIGINT；
  • 金额只认 DECIMAL；
  • 能索引的列必须长度可控、类型可比较；
  • 值域会变的字段用字典表或 JSON + 生成列，不用 ENUM 硬编码。

十、思考题

  1. 为什么自增主键推荐 BIGINT UNSIGNED 而不是 INT？

    参考回答：INT 上限约 21 亿，看似够用，但分库分表按步长放大、或历史数据迁移后很容易接近上限；BIGINT 只多 4 字节，却省掉一次重建表 + 全链路改类型的高成本操作，属于典型的「低成本高保险」。

  2. UUID 做主键的代价具体体现在哪里？

    参考回答：UUID 随机分布，插入点散落在 B+Tree 各页，导致频繁页分裂与缓存失效；同时 CHAR(36) / VARCHAR(64) 让主键与所有二级索引都变胖。要全局唯一又要顺序性，用雪花 ID 或 BIGINT 自增。

  3. 状态字段为什么用 TINYINT + 字典表，而不是 ENUM？

    参考回答：ENUM 加值要 ALTER TABLE，且各环境枚举定义顺序不一致会写坏数据；TINYINT 加状态只改应用与字典表，不动表结构，跨库同步也简单。

  4. 「可演进」原则下，什么情况下才应该上 JSON 字段？

    参考回答：结构不确定、字段稀疏、只做整体读取或少量固定条件过滤时。若某字段要频繁过滤/排序，就抽成独立列或生成列并建索引，JSON 只做容器。

  5. 一张表的金额列已经从 DOUBLE 改成 DECIMAL，历史数据要怎么处理？

    参考回答：先加新列 amount_dec DECIMAL(12,2)，双写并回刷历史（UPDATE ... SET amount_dec = ROUND(amount,2)），校验一致后切读、再删旧列；直接 MODIFY COLUMN 会重建表且有精度截断风险，需要备份与低峰窗口。
