版本与选型：8.4 是今天的基线

5.7 已退场、8.0 于 2026-04 生命周期结束、8.4 与 9.7 是当前两条 LTS｜依据 Oracle EOL 公告与发布说明自绘

一、学习目标

  1. 分清 MySQL 的 LTS 轨与 Innovation 轨，知道为什么生产不该跟 Innovation；
  2. 记住 8.0 的 EOL 时点与 8.4 的定位，能回答「我们该升到哪个版本」；
  3. 讲清 LTS 只能逐级升级、不能跨代的原因，并会用官方升级检查工具。

二、前置知识

读过上一讲即可。最好手里有一个正在跑的实例，SELECT VERSION() 看一眼真实版本。

三、理论讲解（官方定义）

官方在 8.0.34 之后明确了双轨制：LTS（Bugfix）轨与Innovation 轨。两条轨都是生产级质量，区别在变更策略：

  • LTS：只在 LTS 系列的首个版本增加或移除特性，后续小版本只做必要修复，因此系列内可以原地升降级；
  • Innovation：季度发版，新特性、弃用、移除都会出现，升级节奏快，适合能持续测试的团队；
  • 支持期：LTS 按 Oracle Lifetime Support 政策，5 年 premier + 3 年 extended。

版本号规则也变过一次：9.7 是最后一个顺序版本号的系列，此后改用日历版本号 YY.M.P（如 26.7 表示 2026 年 7 月）。

四、原理拆解

1. 为什么 LTS 内可以原地升降级

LTS 系列承诺「功能集与数据格式不变」：8.4.0 到 8.4.13 之间没有特性增删，只有修复。因此二进制替换即可，不需要逻辑导出导入。反过来，跨 LTS 系列（8.4 → 9.7）是受支持但要谨慎的升级，官方要求先体检、再验证。

2. 为什么不能跳 LTS

LTS 只能逐级升，不能跨代跳｜依据 Oracle Lifetime Support 与 8.4 发布说明自绘

9.7 引入了 9.0–9.6 Innovation 的全部变更，其中包含移除项。直接从 8.0 跳 9.7，等于一次性吞下两次大版本的行为变化，出问题无法定位。官方支持的路径是 8.0 → 8.4 → 9.7，逐级验证。

3. 8.4 相对 8.0 的四个必须知道的差异

  1. 默认认证插件仍是 caching_sha2_password，但 mysql_native_password 默认关闭：老客户端不升级就连不上；
  2. default_authentication_plugin 参数被 authentication_policy 取代：照抄旧 my.cnf 会启动失败；
  3. InnoDB 相关默认值继续收紧（如 redo 容量、刷盘策略），迁移前必须对一遍参数；
  4. 部分 8.0 已弃用项在 8.4 彻底移除，升级检查工具会把它们列出来。

4. 选型的三个判断问题

  • 这套库有没有人能承担季度升级的测试成本？不能 → 只选 LTS；
  • 现网是 8.0 还是 5.7？是 → 先排 8.4 的升级窗口，8.0 已经没有安全补丁；
  • 要用 9.x 的新特性（如更完善的 JSON、并行复制改进）吗？要 → 走 8.4 → 9.7 路径，别一步到位。

五、场景说明

  1. 新项目：8.4 LTS，mysql:8.4 镜像或官方 yum/apt 源，跟随季度小版本；
  2. 存量 8.0：先做升级评估（方言兼容、驱动版本、认证插件），再安排窗口升 8.4；
  3. 存量 5.7：不能直接到 8.4 的应用要先过 SQL 兼容检查，再按 5.7 → 8.0 → 8.4 分批；
  4. 必须用新特性：选 9.7 LTS 而不是 26.x Innovation，Innovation 只用于预研环境。

六、示例代码/实操步骤

1. 先看清自己是什么版本、什么轨

SELECT VERSION();                    -- 8.4.13 这类，第三段即小版本
SELECT @@version_comment;            -- 官方包会带 MySQL Community Server 字样
SHOW VARIABLES LIKE 'authentication_policy';   -- 8.4 用这个，8.0 是 default_authentication_plugin
SHOW PLUGINS;                        -- 看 mysql_native_password 是否 ACTIVE

2. 用官方工具做升级体检

# MySQL Shell 8.4 自带升级检查器，源库只读，不修改数据
mysqlsh -- util check-for-server-upgrade root@127.0.0.1:3306 \
  --target-version=8.4.13 --output-format=JSON --output-dir=/tmp/upgrade-check

输出会分三类：errors（必须处理）、warnings（评估影响）、notices（提示）。把 errors 清零才算具备升级条件。

3. 升级窗口的四步节奏

# 1) 备份（逻辑 + 物理各一份，见 MQ49）
# 2) 从库先升：停复制 → 换二进制 → 起库 → 观察
# 3) 主从切换，业务验证
# 4) 旧主再升级，回到原拓扑

Java 侧怎么落地：驱动与连接串的版本对齐

  1. 驱动选 mysql-connector-j（com.mysql:mysql-connector-j），8.0 时代的 mysql:mysql-connector-java 已不再发布新版本；
  2. Boot 3 项目不要自己指定驱动版本，交给 Spring Boot BOM 管理，避免与 8.4 服务端的认证插件不匹配；
  3. 连接串对齐 8.4 默认行为：显式 characterEncoding=utf8、serverTimezone=Asia/Shanghai，内网无 TLS 时加 allowPublicKeyRetrieval=true；
  4. 升级前跑一遍集成测试：重点覆盖事务、批量写入、ON DUPLICATE KEY、时间类型，这些是最容易因 sql_mode 差异出问题的地方。

七、常见坑

  1. 把 8.4 的 authentication_policy 当成 8.0 的参数照抄，实例直接起不来；
  2. 升级只换二进制不看 sql_mode，ONLY_FULL_GROUP_BY 等默认值会让旧 SQL 报错；
  3. 从 5.7 一步跳到 8.4，字符集、认证插件、保留字三件事同时爆；
  4. Innovation 轨上生产，季度发版带来的行为变更没人兜；
  5. 升级后不验证从库复制，主库正常但从库因 binlog 格式或 GTID 配置停摆；
  6. 忽略驱动版本，服务端升了 8.4、客户端还是 5.1 驱动，认证直接失败。

八、课后小结

  • MySQL 分 LTS 与 Innovation 两轨，生产只跟 LTS；
  • 8.0 已于 2026-04 EOL，8.4 LTS 是当前基线，9.7 LTS 是下一条 LTS；
  • LTS 系列内可原地升降级，跨 LTS 必须逐级升，不能跳；
  • 8.4 的四个硬差异：认证插件关闭、参数改名、默认值收紧、弃用项移除；
  • 升级前必须用 mysqlsh -- util check-for-server-upgrade 体检。

九、思考题

  1. 为什么官方说 LTS 系列内可以原地升降级，而跨 LTS 不行？

    参考回答：LTS 系列承诺系列内功能集与数据格式不变，只做必要修复，所以二进制替换即可；跨 LTS 会引入上一代 Innovation 的全部特性与移除项，数据字典、参数、SQL 行为都可能变，必须按受支持路径逐级验证，不能靠换二进制完成。

  2. 现网 8.0 已经 EOL，但业务方不愿升级，你能给出什么最低成本的缓释方案？

    参考回答：短期靠网络隔离、最小权限、只读账号收敛风险面，并盯住已知高危漏洞；中期做升级评估（驱动、认证插件、sql_mode），在从库上先升 8.4 做灰度；长期必须排期升级，因为 EOL 后不再有常规安全补丁。

  3. mysql_native_password 在 8.4 默认关闭，为什么这是「升级事故」的高发点？

    参考回答：大量旧客户端、旧 ORM 和旧连接池默认仍请求该插件；服务端没加载插件时认证直接失败，表现为「密码没错但连不上」。解法是升级客户端到支持 caching_sha2_password 的版本，或在过渡期显式启动参数开启插件。

  4. 同样是 LTS，8.4 与 9.7 该怎么选？

    参考回答：看生态与验证成本。8.4 存量最大、云厂商支持最全、文档与案例最多，适合大多数生产；9.7 是更新的 LTS，包含 9.0–9.6 的能力改进，适合新项目或明确需要这些特性的场景，但要先确认驱动、中间件、备份工具的兼容性。
