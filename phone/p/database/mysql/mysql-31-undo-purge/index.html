undo log 与 purge：多版本是怎么留下来的

insert undo 提交即可丢，update undo 要活到没人读旧版本｜依据 MySQL 8.4 Undo Logs / Purge 说明自绘

一、学习目标

  1. 分清 insert undo 与 update undo 的生命周期差别；
  2. 说清 purge 的判定条件，知道 undo 为什么会膨胀；
  3. 会读 History list length、会在线截断 undo 表空间。

二、前置知识

MVCC 与 Read View（MQ22）、长事务（MQ26）、InnoDB 架构（MQ28）。undo 是 MVCC 的「存储侧」，MVCC 是 undo 的「使用侧」。

三、理论讲解（官方定义）

undo log 记录的是如何撤销一次修改：

  • INSERT 的 undo 记录「这条记录是插入的」，回滚即删除；
  • UPDATE 的 undo 记录「修改前的值」，回滚即写回旧值；
  • DELETE 的 undo 记录被删除的行，回滚即恢复（行上的删除标记被清除）。

同一份 undo 还有第二个用途：为 MVCC 提供旧版本。行头 DB_ROLL_PTR 指向 undo，undo 里的 roll_ptr 再指向上一个版本，形成版本链。

四、原理拆解

purge 只有一个判据：这个版本还有没有活跃事务可能读到｜依据 MySQL 8.4 Purge 配置说明自绘

1. 两种 undo 的生命周期

类型 内容 何时可丢
insert undo 新插入的行 事务提交后立即可丢（别人本来就看不见）
update undo 旧值 + 版本信息 提交后仍要保留，直到没有任何活跃事务需要读它

delete 本质上是一次「打删除标记的 update」，走 update undo。

2. purge 的三步判断

  1. 事务已提交（或已回滚）；
  2. 该 undo 对应的版本不再被任何活跃事务的 ReadView 需要；
  3. 没有更老的 purge 任务依赖它。

满足后 purge 线程删除记录、断开版本链、把 undo 页标记为空闲。8.x 默认 4 个 purge 线程（innodb_purge_threads）。

3. History list length 是什么

SHOW ENGINE INNODB STATUS 里的 History list length 表示尚未 purge 的 undo 记录数。它持续上涨，说明有长事务拖住了水位，或者 purge 线程跟不上写入。

这个数不看绝对值，看趋势：稳定在低位正常，只涨不跌要立即排查最老事务。

4. undo 表空间

8.x 默认 2 个 undo 表空间（undo_001、undo_002），innodb_undo_log_truncate 默认开启：当单个 undo 表空间超过阈值时，标记为 inactive，等 purge 清空后截断回初始大小。

SELECT NAME, SPACE_TYPE, STATE, FILE_SIZE
FROM information_schema.INNODB_TABLESPACES
WHERE SPACE_TYPE = 'Undo';

5. 为什么 undo 会膨胀

原因 表现
长事务不提交 水位不动，所有新版本都留着
大批量更新 短时间产生海量 update undo
purge 线程不足 队列堆积，清理速度跟不上
复制延迟 + 大事务 从库只读长查询拖住 purge

五、场景说明

  1. 秒杀后的批量回滚：大量失败事务回滚，undo 短时暴涨；
  2. 对账批处理：一次更新百万行，undo 与 redo 同时放大；
  3. 报表长查询：只读事务也持有 ReadView，会阻止 purge；
  4. 主从延迟：从库延迟时，只读业务读到老快照，间接拉长版本链；
  5. 磁盘告警：undo 表空间吃掉几十 GB，多半是长事务常年不提交。

六、示例代码/实操步骤

1. 观察 undo 与 History list

SHOW ENGINE INNODB STATUS\G       -- TRANSACTIONS 段的 History list length
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS secs
FROM information_schema.innodb_trx
ORDER BY trx_started LIMIT 5;

最老事务就是「水位线」，它不结束，purge 无法前进。

2. 在线截断 undo 表空间

ALTER UNDO TABLESPACE undo_002 SET INACTIVE;
-- 等 purge 清空后，表空间自动截断；需要时可再设为 ACTIVE
ALTER UNDO TABLESPACE undo_002 SET ACTIVE;

SET INACTIVE 期间不会分配新的 undo 到该表空间，保证能清空。

3. 控制 purge 行为

SHOW VARIABLES LIKE 'innodb_purge_threads';
SHOW VARIABLES LIKE 'innodb_undo_log_truncate';
SHOW VARIABLES LIKE 'innodb_max_undo_log_size';

SSD + 多核机器可把 innodb_purge_threads 提到 8，与 innodb_page_cleaners 数量对齐。

4. Java 侧怎么落地：别让事务成为水位

  1. 事务超时：@Transactional(timeout = 30)，超时自动回滚，防止僵尸事务；
  2. 只读查询也限时：报表类接口 SET SESSION max_execution_time，避免长快照；
  3. 批处理按批提交：每批 500 行，undo 峰值可控；
  4. 避免 SELECT ... FOR UPDATE 后等待外部回调：锁与快照都被拉长；
  5. 监控：把 History list length 与最老事务时长做成告警项，超过阈值（如 60 秒 / 1 万条）就介入；
  6. 连接泄漏排查：innodb_trx 里存在大量 sleep 状态的空事务，多半是连接池归还前没提交/回滚。

七、常见坑

  1. 以为 undo 只是回滚用：它同时是 MVCC 的版本存储，删早了读到脏数据；
  2. 只看 undo 表空间大小不看 History list：前者是结果，后者才是水位；
  3. 频繁 SET INACTIVE 又立刻 ACTIVE：截断没完成就恢复分配，白折腾；
  4. purge 线程调太多：与刷脏争 IO，反而拖慢前台；
  5. 长事务当「连接一直开着」：连接池空闲连接若开了事务不提交，同样压住水位；
  6. 回滚大事务：回滚本身也要读 undo，可能比正向执行还慢，尽量拆批；
  7. 磁盘只剩一点余量才清理 undo：截断需要临时空间，空间不足会失败。

八、版本差异

  • 5.6：undo 默认放在系统表空间 ibdata1 里，无法单独截断，容易只涨不缩；
  • 5.7：支持独立 undo 表空间，innodb_undo_tablespaces 需初始化时设定；
  • 8.0：默认 2 个 undo 表空间，支持在线增删与 SET INACTIVE 截断，innodb_undo_log_truncate 默认开启；
  • 8.4：延续 8.0 的 undo 表空间管理与自动截断，innodb_purge_threads 默认 4。

九、课后小结

  • undo 记录「怎么撤销」，同时为 MVCC 保存旧版本；
  • insert undo 提交即可丢，update undo 要等无人读旧版本；
  • purge 的唯一判据是「有没有活跃事务还需要这个版本」；
  • History list length 是水位指标，持续上涨先找最老事务；
  • undo 表空间支持在线截断，但根因永远是长事务。

十、思考题

  1. 为什么 insert undo 提交后就能丢，update undo 却不行？

    参考回答：新插入的行在提交前对别人不可见，提交后也没有「更早的版本」需要保留；update 的旧值要被并发事务的 ReadView 读到，必须等这些事务结束后才能清理。

  2. History list length 一直上涨，第一步查什么？

    参考回答：查 information_schema.innodb_trx 里最老的事务，看它的开始时间、状态与正在执行的 SQL；水位由最老事务决定，找到它才知道是代码问题还是连接泄漏。

  3. 只读的长查询为什么会阻止 purge？

    参考回答：一致性读要用 ReadView 判断可见性，长查询持有的 ReadView 需要读旧版本，purge 若清掉这些 undo，查询就会读到错误数据，所以必须保留。

  4. SET INACTIVE 与直接删 undo 表空间文件有什么区别？

    参考回答：SET INACTIVE 是受控流程：停止向该表空间分配新 undo，等 purge 清空后由后台截断，数据安全；直接删文件会破坏一致性，实例可能无法启动。

  5. 大批量 UPDATE 之后 undo 暴涨，怎么处理？

    参考回答：短期看 purge 是否能追上，必要时临时增加 purge 线程；长期要靠拆批提交，把单事务行数降下来，避免一次生成过多 update undo。
