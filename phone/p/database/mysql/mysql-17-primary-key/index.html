主键选型：自增、雪花与 UUID 的页分裂代价

InnoDB 的表就是一棵按主键排序的 B+Tree，主键决定插入落在哪一页｜依据 MySQL 8.4 InnoDB 索引与 AUTO_INCREMENT 章节自绘

一、学习目标

  1. 说清「聚簇索引」为什么让主键的顺序性直接决定写性能；
  2. 对比自增、雪花、UUID 三种主键的插入形态与索引膨胀代价；
  3. 知道 8.0 之后 AUTO_INCREMENT 持久化、innodb_autoinc_lock_mode=2 这些变化带来的影响。

二、前置知识

索引与聚簇索引的基本概念（MQ18 会详细展开）。这里只需要记住：InnoDB 的主键就是数据本身，不是另建的一棵独立索引。

三、理论讲解（官方定义）

InnoDB 把表组织为按主键排序的 B+Tree（聚簇索引），叶子页里直接存整行；所有二级索引的叶子存的是主键值而不是行地址。

由此得到两条硬结论：

  • 插入的主键是否单调递增，决定新行是否会落在最后一个页、还是插进中间的页（触发页分裂）；
  • 主键长度会复制到每一条二级索引里，主键越宽，二级索引越大。

官方对 AUTO_INCREMENT 还有两个关键点：

  • 8.0 起自增值持久化（写 redo log），重启后不再回退到 MAX(id)+1，5.7 时代靠内存计数器、重启可能重用旧值；
  • innodb_autoinc_lock_mode 自 8.0 起默认 2（interleaved），并发插入不再抢表级 AUTO-INC 锁。

四、原理拆解

随机主键把顺序写变成随机写，还会让每个二级索引都变宽｜依据 MySQL 8.4 InnoDB 索引结构与页分裂机制自绘

1. 顺序插入 vs 随机插入

B+Tree 的叶子页按主键升序排列：

  • 自增主键：每次插入都追加到最右页，页写满就开新页，几乎不分裂，顺序写盘，INSERT 极快；
  • 随机主键（UUIDv4、无序业务号）：插入落在树中间，目标页满了就要分裂成两页并把一半数据挪走，同时更新父页指针。页分裂带来三类代价：额外写、页填充率下降（约 50%）、缓冲区里多一份碎片；
  • 时间有序主键（雪花、UUIDv1/ULID）：近似顺序，只在时钟回拨或机器号跳变时局部乱序，代价远小于随机主键。

2. 主键宽度会复制到每个二级索引

假设表有 5 个二级索引、1000 万行：

主键类型 长度 二级索引额外占用（粗算）
BIGINT 8 B 5 × 1000 万 × 8 B ≈ 380 MB
CHAR(36) UUID 36 B 5 × 1000 万 × 36 B ≈ 1.7 GB
BINARY(16)（UUID_TO_BIN） 16 B 5 × 1000 万 × 16 B ≈ 760 MB

这就是「能用整型就别用字符串主键」的真正原因——它不只影响主表，还影响所有二级索引的高度与 IO。

3. UUID 的两种存法

-- 存字符串：36 字节，随机，页分裂最严重
id CHAR(36) PRIMARY KEY

-- 存二进制并重排时间位：16 字节，且变成时间有序
id BINARY(16) PRIMARY KEY,
-- 写入时
INSERT INTO t (id) VALUES (UUID_TO_BIN(UUID(), 1));

UUID_TO_BIN(uuid, 1) 的第二个参数 swap_flag=1 会把 UUID 的 time-low 与 time-high 交换，让二进制值按时间递增——这一步能把「随机插入」变成「近似顺序插入」，是 UUID 做主键时最关键的优化。

4. 自增主键的三个副作用

  • 暴露业务量：ID 连续可被枚举、可推测订单量，对外接口应使用独立的业务号或混淆 ID；
  • 分库分表后冲突：多实例各自自增会撞，需要步长（auto_increment_increment）或号段服务；
  • 批量插入的锁：8.0 默认 innodb_autoinc_lock_mode=2，批量插入可并发分配；设回 1 会在 INSERT ... SELECT 时锁表。

5. 没有主键会怎样

InnoDB 会隐式建一个 6 字节的 GEN_CLUST_INDEX 行号，它全局递增但不可见，你无法用它做任何优化，二级索引也指向这个隐藏值。8.0.30 起可用 sql_generate_invisible_primary_key=ON 让 MySQL 显式给你补一个 my_row_id，但这只是补救，不如建表时就定好主键。

五、场景说明

  1. 单体业务表：BIGINT UNSIGNED AUTO_INCREMENT，最省事最稳；
  2. 分库分表：雪花 ID（BIGINT，时间在高位）或号段服务，避免跨库冲突；
  3. 对外暴露的 ID：内部自增 + 对外映射混淆码，别直接把自增 ID 给前端；
  4. 日志/事件表：(created_at, id) 联合主键或按时间分区，写入天然有序；
  5. 导入历史数据：先按主键排序再灌入，避免大批随机插入导致页分裂。

六、示例代码/实操步骤

1. 标准自增主键表

CREATE TABLE t_order (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_no   CHAR(20) NOT NULL,          -- 对外业务号，独立于主键
  user_id    BIGINT UNSIGNED NOT NULL,
  amount     DECIMAL(12,2) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user (user_id)
) ENGINE=InnoDB;

2. UUID 主键的正确存法

CREATE TABLE t_event (
  id         BINARY(16) NOT NULL,
  payload    JSON NOT NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id)
) ENGINE=InnoDB;

INSERT INTO t_event (id, payload) VALUES (UUID_TO_BIN(UUID(), 1), '{"k":"v"}');

-- 查询时反解
SELECT BIN_TO_UUID(id, 1) AS uuid, payload FROM t_event LIMIT 5;

3. 观察页分裂与索引大小

-- 表与索引占用的物理空间
SELECT TABLE_NAME, INDEX_NAME, STAT_NAME, STAT_VALUE
FROM mysql.innodb_index_stats
WHERE TABLE_NAME = 't_order' AND STAT_NAME IN ('size','n_leaf_pages');

-- 页填充率与碎片
SELECT NAME, PAGE_SIZE, DATA_LENGTH, INDEX_LENGTH FROM information_schema.INNODB_TABLESPACES
WHERE NAME LIKE 'shop/t_order%';

4. 分批导入避免随机插入

-- 导入前按主键排序，让写入尽量顺序
LOAD DATA LOCAL INFILE '/data/orders.csv'
INTO TABLE t_order
FIELDS TERMINATED BY ',' IGNORE 1 LINES
(id, order_no, user_id, amount);

排序后的 CSV 顺序写入，页分裂次数会显著下降；数据量大时按 1000 行一批提交。

5. 自增步长（分库场景）

-- 两个实例，各自步长 2，避免冲突
SET @@auto_increment_increment = 2;
SET @@auto_increment_offset = 1;  -- 另一实例设为 2

Java 侧怎么落地：ID 生成与实体映射

  1. 主键统一 Long：BIGINT UNSIGNED 对应 Long（注意无符号值上限超出 Long.MAX 的极端情况，规范里约定不超过 2^63-1）；
  2. 三套 ID 分工：id（内部主键，自增/雪花）、xxx_no（对外业务号）、trace_id（链路追踪）互不复用；
  3. MyBatis-Plus 指定策略：@TableId(type = IdType.AUTO) 用于自增库；分库表用 IdType.ASSIGN_ID（雪花），别让框架混用；
  4. UUID 主键在 Java 侧转二进制：UUID_TO_BIN 交给 SQL 做，或 Java 里用 ByteBuffer 转 byte[16]，实体字段类型用 byte[] / 自定义 TypeHandler；
  5. 批量插入用 rewriteBatchedStatements=true：否则 JDBC 逐条发送，自增分配与网络往返都会被放大；
  6. 不要用业务字段做主键：手机号、身份证会变更，改动主键等于重建整棵聚簇索引。

七、常见坑

  1. UUID 直接 CHAR(36) 做主键：随机 + 超宽，页分裂与索引膨胀双杀；
  2. 以为雪花 ID 完全有序：同毫秒内仍靠序列号，跨机器时钟回拨会导致局部乱序，需要兜底方案；
  3. 主键用 VARCHAR 业务号：长度可变、比较慢，且二级索引全被拖宽；
  4. 分库后各自自增：上线才发现 ID 冲突，补数据非常痛；
  5. 修改主键：聚簇索引整体重排，等于重建表；
  6. AUTO_INCREMENT 空洞当成 bug：回滚、批量分配失败都会产生空洞，属正常现象；
  7. 5.7 升级到 8.0 后自增值行为变化：8.0 持久化后重启不再回退，依赖旧行为的脚本会出错。

八、版本差异

  • 5.7：自增值存在内存，重启后取 MAX(id)+1，可能重用已删除的 ID；innodb_autoinc_lock_mode 默认 1；
  • 8.0：自增值持久化（redo log），重启不回退；innodb_autoinc_lock_mode 默认 2；8.0.30 起 sql_generate_invisible_primary_key 可自动生成隐藏主键；UUID_TO_BIN 的 swap_flag 早已可用；
  • 8.4：以上行为保持一致；ADD COLUMN 默认 INSTANT，但改主键仍是重建级操作。

九、课后小结

  • InnoDB 表就是按主键排序的 B+Tree，主键顺序性 = 写性能；
  • 自增最稳，雪花适合分库，UUID 必须转 BINARY(16) 并用 swap_flag=1；
  • 主键宽度会复制进每个二级索引，整型优于字符串；
  • 8.0 起自增值持久化、自增锁模式默认 2；
  • 没有主键会生成不可见的 6 字节行号，优化无从下手。

十、思考题

  1. 为什么 UUID 做主键会「越插越慢」，而自增不会？

    参考回答：自增总是追加到最右叶子页，页满顺序开新页；UUID 随机落到树中间，目标页满了要分裂并搬移一半数据，同时改父页指针，写放大且填充率降到约 50%。

  2. UUID_TO_BIN(UUID(), 1) 里的 1 做了什么？

    参考回答：把 UUID 字符串中的 time-low 与 time-high 两段交换位置，使生成的 16 字节二进制值按时间递增，从而把随机插入变成近似顺序插入，显著减少页分裂。

  3. 为什么主键长度会影响二级索引大小？

    参考回答：InnoDB 二级索引的叶子存的是主键值（用于回表定位），主键多宽，每个二级索引的每条记录就多宽，索引页数与树高都会增加。

  4. 分库分表后自增主键为什么会冲突，有哪几种解法？

    参考回答：各实例独立自增会生成相同 ID。解法有：设置 auto_increment_increment / offset 错开步长、号段服务（一次领一段 ID）、雪花算法（时间+机器号+序列）。

  5. 表没有显式主键时，InnoDB 怎么组织数据？

    参考回答：自动创建一个 6 字节的隐藏列 DB_ROW_ID（GEN_CLUST_INDEX）作为聚簇键，全局递增但用户不可见、不能用于查询优化；8.0.30 起可开启 sql_generate_invisible_primary_key 生成可见的 my_row_id。
