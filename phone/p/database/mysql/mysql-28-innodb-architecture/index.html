InnoDB 架构总览：Buffer Pool、Change Buffer 与 Log Buffer

SQL 层写 binlog，引擎层靠内存改数据、靠日志追平磁盘｜依据 MySQL 8.4 InnoDB Architecture 章节自绘

一、学习目标

  1. 画出 InnoDB 的内存与磁盘结构，说清每个缓冲区解决什么问题；
  2. 理解 Buffer Pool 的分代 LRU 为什么能扛住全表扫描；
  3. 会读几个关键参数，知道调大 / 调小分别影响什么。

二、前置知识

页与行格式（MQ29 紧接本篇）、redo 与 undo（MQ30、MQ31）。本篇是这一模块的地图。

三、理论讲解（官方定义）

InnoDB 的架构分成三层：

  • 内存结构：Buffer Pool（缓冲池）、Change Buffer（写缓冲）、Log Buffer（日志缓冲）、Adaptive Hash Index（自适应哈希索引）；
  • 后台线程：master thread、IO 线程（读/写）、page cleaner、purge thread；
  • 磁盘结构：表空间（系统表空间 ibdata1、独立表空间 .ibd、通用表空间、undo 表空间、临时表空间）、redo log、binlog（Server 层）。

核心原则是 WAL（Write-Ahead Logging）：改数据先改内存页并写 redo，脏页随后异步刷盘；崩溃后按 redo 前滚、按 undo 回滚。

四、原理拆解

新页先进 old 段，命中且停留够久才晋升 young，全表扫描不会污染热数据｜依据 MySQL 8.4 Buffer Pool 说明自绘

1. Buffer Pool 是主战场

  • 数据页、索引页、undo 页、change buffer 页都在这里；
  • 读写都先经过它，命中率直接决定性能；
  • innodb_buffer_pool_size 默认 128MB，生产通常给到物理内存的 60%～75%；
  • innodb_buffer_pool_instances 默认 8，把池切成多份降低互斥；池小于 1GB 时多实例意义不大。

2. 分代 LRU

池内维护三条链：free（空闲页）、LRU（按访问热度排序）、flush（待刷脏页）。LRU 被切成两段：

段 占比 放什么
young（热端） 约 63% 反复命中的页
old（冷端） 约 37%（innodb_old_blocks_pct） 新读入的页

新页先插到 old 段头部；只有在 old 段停留超过 innodb_old_blocks_time（默认 1000ms）后再次被访问，才晋升到 young。这样一次全表扫描读进来的大量页只会冲刷 old 段，热数据留在 young。

3. Change Buffer

对非唯一二级索引的写操作，如果目标页不在 Buffer Pool，InnoDB 不立刻读页，而是把变更记到 Change Buffer，等页被读入时再合并（merge）。

  • 唯一索引不能用：唯一性检查必须读页；
  • innodb_change_buffering 默认 all（insert / delete-mark / purge 都缓冲）；
  • innodb_change_buffer_max_size 默认 25（占 Buffer Pool 的百分比）；
  • 8.0 起 Change Buffer 持久化在系统表空间，崩溃不丢。

4. Log Buffer

redo 先写进 Log Buffer，再由 innodb_flush_log_at_trx_commit 决定何时刷盘：

取值 行为 风险
1（默认） 每次提交刷盘 最安全，一次 fsync
2 提交写 OS cache，每秒刷盘 宕机丢 1 秒
0 每秒写并刷 丢 1 秒，且丢在 MySQL 崩溃时

innodb_log_buffer_size 默认 16MB，大事务多时可适度调大，减少刷盘次数。

5. 后台线程

  • IO 线程：innodb_read_io_threads / innodb_write_io_threads 默认各 4，SSD 可上调；
  • page cleaner：把脏页刷盘，innodb_page_cleaners 默认 4；
  • purge thread：清理 undo，innodb_purge_threads 默认 4；
  • master thread：调度上述线程、负责后台任务节奏。

6. 自适应哈希索引

对频繁等值查询的页，InnoDB 自动建哈希目录，把 B+Tree 查找降为 O(1)。innodb_adaptive_hash_index 默认开启；高并发下哈希锁可能成为瓶颈，可通过 innodb_adaptive_hash_index_parts 分区缓解。

五、场景说明

  1. 读多写少的业务：Buffer Pool 给足，命中率 99% 以上，磁盘几乎只承担刷脏；
  2. 写多（日志、时序）：关注 redo 容量、刷脏节奏与 change buffer 收益；
  3. 大量二级索引：change buffer 能显著减少随机读；
  4. 报表全表扫描：分代 LRU 让报表不把 OLTP 热数据挤出去；
  5. 容器化部署：内存要按容器 limit 配，innodb_dedicated_server 只在独占主机时开。

六、示例代码/实操步骤

1. 看清当前配置

SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE 'innodb_buffer_pool_instances';
SHOW VARIABLES LIKE 'innodb_change_buffering';
SHOW VARIABLES LIKE 'innodb_log_buffer_size';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';

2. 看命中率与内存分布

SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
-- 命中率 ≈ 1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests
SELECT POOL_ID, POOL_SIZE, FREE_BUFFERS, DATABASE_PAGES, MODIFIED_PAGES
FROM information_schema.INNODB_BUFFER_POOL_STATS;

3. 在线调整（8.x 支持动态改）

SET GLOBAL innodb_buffer_pool_size = 8589934592;      -- 8GB
SET GLOBAL innodb_change_buffer_max_size = 25;

Buffer Pool 扩容按 chunk 进行，可在业务低峰执行；缩容需要更多时间清理。

4. Java 侧怎么落地：连接池与内存协同

  1. 连接池上限先按数据库核数定（如 maximumPoolSize = 2 * CPU 左右），再压测收敛，别让连接数把 Buffer Pool 的锁竞争放大；
  2. pom.xml 引 HikariCP，配置 connectionTimeout、maxLifetime（略小于 MySQL wait_timeout）；
  3. 事务内少做全表查询：一次大扫描会把大量页冲进 old 段，挤占热数据；
  4. 监控接入 Innodb_buffer_pool_reads 与 Modified pages，命中率掉到 95% 以下就要评估扩容或加缓存；
  5. 报表类查询走只读实例，避免与 OLTP 抢同一个 Buffer Pool。

七、常见坑

  1. Buffer Pool 给小了：命中率低，所有查询都变随机 IO；
  2. 实例数乱设：池小于 1GB 时多实例无收益，反而增加管理开销；
  3. 把 innodb_flush_log_at_trx_commit 改 0 换性能：宕机丢数据，金融场景不可接受；
  4. 唯一索引指望 change buffer：唯一性检查必须读页，缓冲不了；
  5. 容器里按物理机内存配：超 limit 被 OOM kill；
  6. AHI 全开不分区：高并发等值查询下哈希锁竞争；
  7. 只加内存不看刷脏：脏页比例过高，检查点抖动导致周期性卡顿。

八、版本差异

  • 5.7：change buffer 主要面向 insert，innodb_change_buffering 取值较少；AHI 只有整体开关；
  • 8.0：change buffer 支持 insert / delete-mark / purge 全类型并持久化；新增 innodb_dedicated_server 自动按机器规格推算内存参数；AHI 支持 innodb_adaptive_hash_index_parts；
  • 8.4：架构与参数语义延续 8.0；redo 统一由 innodb_redo_log_capacity 管理；容器部署需显式给 innodb_buffer_pool_size，不要依赖自动推算。

九、课后小结

  • 内存四件套：Buffer Pool 存页、Change Buffer 攒二级索引写、Log Buffer 攒 redo、AHI 加速等值查；
  • 分代 LRU 是抗扫描的关键：old 段 + 停留时间双阈值；
  • change buffer 只对非唯一二级索引起作用，且已持久化；
  • 刷盘策略由 innodb_flush_log_at_trx_commit 决定，默认 1 最安全；
  • 调参先看命中率与脏页比例，再看线程数。

十、思考题

  1. 为什么全表扫描不会把 Buffer Pool 里的热数据全部挤掉？

    参考回答：新页只进入 old 段，且必须在 old 段停留超过 innodb_old_blocks_time 后再次访问才晋升；顺序扫描的页通常只被读一次，很快被淘汰在 old 段。

  2. Change Buffer 为什么只对非唯一二级索引有效？

    参考回答：唯一索引写入前必须读页做唯一性校验，无法延迟合并；非唯一索引不需要校验，可以把变更先攒起来，等页被读入时批量 merge。

  3. innodb_flush_log_at_trx_commit = 2 会丢什么？

    参考回答：提交时只写到 OS cache，每秒才 fsync；MySQL 进程崩溃不丢，但操作系统或机器掉电会丢最后约 1 秒的已提交事务。

  4. Buffer Pool 越大越好吗？

    参考回答：不是。要留足内存给 OS 页缓存、连接与临时表；过大还会拉长崩溃恢复与扩容时的预热时间。按热数据集大小给，通常物理内存 60%～75%。

  5. 报表查询为什么要走只读实例？

    参考回答：报表多为大范围扫描，会大量填充 old 段并产生脏页，和 OLTP 抢同一个 Buffer Pool 与 IO；只读实例隔离后互不影响。
