表空间与文件：ibdata、独立表空间与 undo 表空间

系统表空间、独立表空间、undo、临时、redo 各管一段｜依据 MySQL 8.4 Tablespaces 说明自绘

一、学习目标

  1. 认全数据目录里的关键文件，知道每个文件属于谁；
  2. 分清系统表空间与独立表空间的取舍，理解 innodb_file_per_table；
  3. 会做单表迁移、undo 截断与容量排查。

二、前置知识

InnoDB 架构（MQ28）、页与行格式（MQ29）、undo 与 purge（MQ31）。本篇解决「磁盘到底被谁吃了」。

三、理论讲解（官方定义）

InnoDB 把数据组织成若干表空间（tablespace），每个表空间由一组数据文件构成：

表空间 文件 内容
系统表空间 ibdata1（可多个） 数据字典、change buffer、双写缓冲、部分系统数据
独立表空间 表名.ibd 单表的数据与索引
undo 表空间 undo_001、undo_002 回滚与 MVCC 旧版本
全局临时表空间 ibtmp1 全局临时表、排序溢出
会话临时表空间 temp_*.ibt（在 #innodb_temp） 会话级临时表
redo 日志 #innodb_redo/ 崩溃恢复

innodb_file_per_table 默认 ON，即每张表一个 .ibd；设为 OFF 时所有表都挤进系统表空间。

四、原理拆解

知道每个文件是谁的，才敢删、敢迁、敢扩容｜依据 MySQL 8.4 Tablespace Management 说明自绘

1. 独立表空间 vs 系统表空间

维度 独立表空间（默认） 系统表空间
单表大小 可单独增长与收缩 混在一起，无法单独回收
迁移 TRANSPORTABLE TABLESPACE 可单表搬 只能整库搬
删除表 DROP 后 .ibd 直接删除，空间归还 OS 空间留在 ibdata1 里，不会变小
文件数 表多则文件多 文件少

所以 innodb_file_per_table = ON 几乎是必须的：否则 DROP TABLE 后磁盘不会释放。

2. 系统表空间为什么不能缩

ibdata1 只增不减（除非重建实例导出再导入）。里面放着数据字典、change buffer 与双写缓冲，无法按表拆分回收空间。这也是「磁盘被 ibdata1 吃满」的经典事故。

3. 双写缓冲

脏页刷盘前先写到 doublewrite 区域（连续空间），保证页写入的原子性，防止「页断裂」。8.0.20 起支持独立双写文件（#ib_16384_0.dblwr），不再占用 ibdata1。

4. 表空间迁移

同版本、同页大小时，可用 FLUSH TABLES ... FOR EXPORT + 拷贝 .ibd/.cfg + IMPORT TABLESPACE 做单表迁移，适合大表在低峰搬迁，比逻辑导出快。

5. 容量排查顺序

  1. 各表 .ibd 大小（information_schema.TABLES 的 DATA_LENGTH + INDEX_LENGTH）；
  2. undo 表空间大小（长事务导致膨胀）；
  3. binlog 目录（保留期与写入量）；
  4. redo 目录（innodb_redo_log_capacity）；
  5. 临时表空间（大排序、GROUP BY 溢出）。

五、场景说明

  1. 磁盘告警：先看 ibdata1 是否异常增长，再看 undo 与 binlog；
  2. 大表迁移：用传输表空间而不是 mysqldump；
  3. 单表清理：DROP / TRUNCATE 后确认 .ibd 是否被删除；
  4. 备份规划：物理备份要包含 ibdata1、.ibd、undo、redo；
  5. 容器化：数据目录挂载卷，#innodb_redo 与 #innodb_temp 不要遗漏。

六、示例代码/实操步骤

1. 看表空间与文件

SELECT NAME, SPACE_TYPE, FILE_SIZE, ALLOCATED_SIZE
FROM information_schema.INNODB_TABLESPACES
ORDER BY FILE_SIZE DESC LIMIT 10;

SELECT TABLE_NAME, ROUND((DATA_LENGTH + INDEX_LENGTH) / 1024 / 1024) AS mb
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'shop'
ORDER BY mb DESC LIMIT 10;

2. 确认独立表空间开关

SHOW VARIABLES LIKE 'innodb_file_per_table';
SHOW VARIABLES LIKE 'innodb_data_file_path';

3. 单表迁移（同版本、同页大小）

-- 源库
FLUSH TABLES t_order FOR EXPORT;
-- 拷贝 t_order.ibd 与 t_order.cfg 到目标库数据目录
UNLOCK TABLES;

-- 目标库
ALTER TABLE t_order DISCARD TABLESPACE;   -- 先有同名空表
-- 放入文件后
ALTER TABLE t_order IMPORT TABLESPACE;

4. 清理与回收

DROP TABLE t_history;        -- 独立表空间：文件直接删除，空间归还
TRUNCATE TABLE t_log;        -- 重建表空间，文件大小回落

5. Java 侧怎么落地：容量与运维约束

  1. 归档任务：历史表按月分区或定期 DROP PARTITION，避免单表无限膨胀；
  2. 临时大表：批处理中间结果用临时表并显式 DROP，别留在业务库；
  3. 监控：采集 INNODB_TABLESPACES 与磁盘使用率，设置 80% 告警；
  4. 备份校验：物理备份后核对 ibdata1 + .ibd 数量与总大小；
  5. 发布规范：DDL 前评估 .ibd 增长与磁盘余量，ALTER 需要临时空间。

七、常见坑

  1. innodb_file_per_table = OFF：删表不释放磁盘，ibdata1 越滚越大；
  2. 以为 ibdata1 能缩小：只能重建实例；
  3. 直接删 .ibd 文件：元数据还在，查询直接报错；
  4. IMPORT TABLESPACE 页大小不一致：导入失败，需同版本同 innodb_page_size；
  5. undo 表空间占满磁盘：根因是长事务，扩容只是拖延；
  6. 临时表空间暴涨：大排序、SELECT ... ORDER BY 无索引，ibtmp1 迅速膨胀；
  7. 备份漏掉 redo 与 undo：恢复时无法前滚到一致点。

八、版本差异

  • 5.6：独立表空间可选，undo 在 ibdata1 内；
  • 5.7：独立 undo 表空间；innodb_file_per_table 默认开启；
  • 8.0：数据字典迁入 mysql.ibd；双写支持独立文件（8.0.20+）；redo 迁入 #innodb_redo（8.0.30+）；
  • 8.4：表空间体系与 8.0 一致，innodb_redo_log_capacity 统一管理 redo；支持表空间加密与在线 undo 截断。

九、课后小结

  • 五类表空间：系统、独立、undo、临时、redo，各管一段；
  • innodb_file_per_table = ON 是默认也是必须，否则删表不释放空间；
  • ibdata1 只增不减，容量异常先查它；
  • 单表迁移用传输表空间，同版本同页大小是前提；
  • 容量排查顺序：表 .ibd → undo → binlog → redo → 临时。

十、思考题

  1. 为什么 DROP TABLE 在独立表空间下能释放磁盘，在系统表空间下不能？

    参考回答：独立表空间每表一个 .ibd，删除表即删除文件，空间直接归还 OS；系统表空间所有表共用 ibdata1，删除只释放内部页，文件本身不会缩小。

  2. ibdata1 越来越大，有哪些处理办法？

    参考回答：确认 innodb_file_per_table 已开启；迁移历史表；若确需缩小，只能逻辑导出全库、重建实例再导入（停机窗口长，需充分演练）。

  3. 传输表空间迁移的前提是什么？

    参考回答：源与目标同 MySQL 版本、同 innodb_page_size、表结构完全一致（含索引），并且源表在导出期间只读。

  4. undo 表空间持续膨胀，扩容能解决吗？

    参考回答：不能根治。膨胀根因是长事务或 purge 跟不上，扩容只是延后磁盘打满；应先找出最老事务并缩短事务，再配合 SET INACTIVE 截断。

  5. 容器化部署时，数据目录要特别注意什么？

    参考回答：要包含 ibdata1、各 .ibd、undo_*、#innodb_redo、#innodb_temp 与 binlog 目录；只挂载 datadir 但漏挂子目录，重启后会出现表空间缺失。
