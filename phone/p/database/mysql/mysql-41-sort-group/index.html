排序与分组优化：filesort 与临时表

排序借不到索引顺序，就只能自己排一遍｜依据 MySQL 8.4 ORDER BY / GROUP BY 优化说明自绘

一、学习目标

  1. 分清 filesort 的两种实现与它们的代价差异；
  2. 记住「借索引顺序」的四个条件，能把 filesort 消掉；
  3. 找到 GROUP BY 建临时表的根因，用索引或改写替换掉。

二、前置知识

索引与最左前缀（MQ19/MQ38）、EXPLAIN 的 Extra 列（MQ35）。

三、理论讲解（官方定义）

ORDER BY 有两种执行方式：

方式 条件 Extra
借索引顺序 排序键是索引的有序前缀，且过滤条件与索引前缀一致 无 Using filesort
filesort 无法借用索引顺序 Using filesort

filesort 不是「用文件排序」，而是「在内存或临时文件里排序」：sort_buffer_size 装得下就在内存排，装不下就分块排序再归并（磁盘临时文件）。

GROUP BY 同理：分组列能借索引顺序就逐段聚合，否则建内部临时表。

四、原理拆解

能用索引就别用临时表，能给常量就别让优化器猜｜依据 MySQL 8.4 GROUP BY 优化 / 内部临时表说明自绘

1. 两种 filesort

  • 全字段排序：把 SELECT 需要的所有列读进 sort buffer，排完直接返回，不回表，但行宽大容易溢出磁盘；
  • rowid 排序：只放「排序键 + 主键」，排完按主键回表取其余列，buffer 能装更多行，但多一次回表。

8.0.20 起优化器优先用打包排序（packed sort），把变长字段压缩存放，等价于「尽量全字段但不溢出」。所以 max_length_for_sort_data 已不再是主要旋钮。

2. 借索引顺序的四个条件

  1. ORDER BY 的列是索引的最左连续前缀；
  2. WHERE 中前缀列都是等值条件（范围会打断排序可用性）；
  3. 排序方向一致（全 ASC 或全 DESC；混合方向需要 8.0 的降序索引）；
  4. 排序列不参与函数计算（ORDER BY DATE(created_at) 用不了原索引）。

3. 为什么 ORDER BY ... LIMIT 看起来快却慢

LIMIT 只有在排序能借索引时才真正「提前停」；否则必须把所有匹配行排完才知道前 20 名。这就是「ORDER BY created_at DESC LIMIT 20 扫了 80 万行」的原因。

4. GROUP BY 的三条路

  • 索引有序扫描：分组列是索引最左前缀，逐段聚合，无临时表；
  • 临时表 + 排序：无索引可用，建内部临时表再聚合；
  • 磁盘临时表：临时表超过 tmp_table_size / max_heap_table_size，落盘（Created_tmp_disk_tables 上升）。

5. HAVING 与 WHERE 的分工

WHERE 在聚合前过滤，能减少参与分组的行；HAVING 在聚合后过滤，无法减少扫描。把「能写进 WHERE 的条件」写进 WHERE，是最便宜的一条优化。

五、场景说明

  1. 列表页排序：WHERE status = 1 ORDER BY created_at DESC → 索引 (status, created_at)；
  2. 排行榜：按分数排序且要分页，考虑预计算排名表；
  3. 报表分组：GROUP BY city 无索引 → 建索引或先按城市分片预聚合；
  4. 去重统计：COUNT(DISTINCT) 与 GROUP BY 相似，看能否走覆盖索引；
  5. 大排序溢出：sort_buffer_size 调大会加剧内存压力，优先改索引。

六、示例代码/实操步骤

1. 判断是否 filesort

EXPLAIN SELECT id, amount FROM t_order WHERE status = 1 ORDER BY created_at DESC LIMIT 20;
-- Extra 里出现 Using filesort → 排序没借到索引

2. 建索引消掉 filesort

ALTER TABLE t_order ADD INDEX idx_status_time (status, created_at),
  ALGORITHM=INPLACE, LOCK=NONE;
ANALYZE TABLE t_order;

EXPLAIN SELECT id, amount FROM t_order WHERE status = 1 ORDER BY created_at DESC LIMIT 20;
-- Extra 无 filesort；若 amount 也在索引里则额外出现 Using index

3. 看排序有没有落盘

SHOW GLOBAL STATUS LIKE 'Sort%';
-- Sort_merge_passes > 0 说明发生过磁盘归并
SHOW GLOBAL STATUS LIKE 'Created_tmp%';

Sort_merge_passes 持续增长 = sort_buffer_size 不够或需要排序的数据太多。

4. GROUP BY 消临时表

-- 前：Extra: Using temporary; Using filesort
EXPLAIN SELECT city, COUNT(*) FROM t_user GROUP BY city;

-- 建索引后
ALTER TABLE t_user ADD INDEX idx_city (city);
EXPLAIN SELECT city, COUNT(*) FROM t_user GROUP BY city;
-- Extra 变为 Using index（覆盖）

5. Java 侧怎么落地：让排序在数据库里「顺」起来

  1. 排序参数白名单：前端传入的 orderBy 字段只允许命中已建索引的列，其余拒绝；
  2. 分页与排序绑定：分页 SQL 统一模板 WHERE ... ORDER BY <indexed_col> LIMIT，禁止 ORDER BY RAND()；
  3. 报表走离线：GROUP BY 维度多的统计改成定时任务预聚合到结果表；
  4. 连接池参数：sort_buffer_size 按「并发 × 缓冲」评估，别一调就是 8MB × 200 连接；
  5. 监控：采集 Created_tmp_disk_tables / Created_tmp_tables 比值，超过 30% 报警。

七、常见坑

  1. ORDER BY 列不在索引尾部：前面有范围条件就借不到顺序；
  2. 混合 ASC/DESC：8.0 前无法用索引，需建降序索引；
  3. ORDER BY 用函数：索引完全失效；
  4. 盲目调大 sort_buffer_size：并发高时直接 OOM；
  5. GROUP BY 后 ORDER BY 同一列：多一次多余排序（8.0 已优化部分场景）；
  6. 把过滤条件写进 HAVING：多扫描一遍；
  7. DISTINCT 与 GROUP BY 混用：双份去重开销。

八、版本差异

  • 5.6：filesort 有全字段/rowid 两种，max_length_for_sort_data 是关键参数；
  • 5.7：GROUP BY 隐式排序被移除，不再默认 ORDER BY；
  • 8.0：降序索引（8.0 起真正生效）、打包排序（8.0.20）、EXPLAIN ANALYZE 可看排序实际行数；
  • 8.4：排序/分组机制同 8.0，max_length_for_sort_data 影响力进一步下降。

九、课后小结

  • filesort 是「自己排」，能借索引顺序就不要它；
  • 借索引顺序要满足：最左连续前缀、前缀等值、方向一致、无函数；
  • ORDER BY ... LIMIT 只有在借索引时才是真「提前停」；
  • GROUP BY 无索引必建临时表，超限就落盘；
  • 过滤条件尽量写 WHERE，HAVING 只留聚合后的判断。

十、思考题

  1. 为什么 ORDER BY created_at DESC LIMIT 20 有时要扫几十万行？

    参考回答：排序键不是索引的可借顺序（例如 WHERE status = 2 而索引是 (created_at)），必须先取出所有匹配行排完序，才知道前 20 条是谁；LIMIT 无法提前停止。解法是把过滤列与排序列做成联合索引 (status, created_at)。

  2. 全字段排序与 rowid 排序，哪个更快？

    参考回答：取决于行宽与结果集大小。行窄时全字段排序一次读完、不回表，更快；行宽或结果集大时 rowid 排序能在 buffer 里装更多行、减少磁盘归并，反而更快。8.0.20 后用打包排序自动在两者间取优。

  3. Sort_merge_passes 一直增长说明什么？

    参考回答：说明排序数据超过了 sort_buffer_size，发生了多路归并（读磁盘临时文件）。要么调大 buffer（注意并发内存），要么通过索引消除排序。

  4. GROUP BY city 出现 Using temporary 该怎么改？

    参考回答：先给 city 建索引让分组借索引顺序；若分组维度多且无法建索引，把范围条件压到 WHERE 减少参与行，或改为离线预聚合。调 tmp_table_size 只能缓解落盘，治不了根因。

  5. 混合排序方向（a ASC, b DESC）为什么用不了普通索引？

    参考回答：普通（升序）索引的物理顺序是统一方向的，无法同时满足两个相反方向。8.0 支持降序索引，建 (a ASC, b DESC) 后优化器才能借用；8.0 之前只能改排序方向或在应用层排序。
