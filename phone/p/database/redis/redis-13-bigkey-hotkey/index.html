大 key 与热 key

官方自带的四个发现工具、五条对症治理与判定口径｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清「大 key」与「热 key」是两种不同的风险（一个占内存与阻塞，一个压单点带宽），不要混成一个词；
  2. 会用 redis-cli --bigkeys / MEMORY USAGE / OBJECT ENCODING / --hotkeys 四个官方入口做定位；
  3. 掌握拆分、分批、异步删、控增长、分热点五条治理手段，并知道各自适用前提。

二、前置知识

RD05–RD13 的集合类结构 + RD12（淘汰与内存）。本讲是整个 M2 模块的收口：所有类型的「容量与复杂度」问题，最后都会汇成「大 key」和「热 key」两个声音。

三、理论讲解（官方定义）

先给一个重要的边界：官方文档没有定义「多大算大 key」，也没有给热 key 的阈值。官方给的是工具（--bigkeys、MEMORY USAGE、--hotkeys）与机制说明，阈值必须由业务定。

官方对「删除大 key 会阻塞」的说明（原文要点，见 DEL / UNLINK 文档）：

… DEL … is a blocking command … UNLINK … performs the actual memory reclaiming in a different thread, so it is not blocking.

—— https://redis.io/docs/latest/commands/unlink/

这句话其实给出了「大 key 为什么危险」的官方答案：它的操作是 O(N)，而 O(N) 发生在唯一的主线程上。

四、原理拆解

1. 大 key：内存与阻塞的双重风险

大 key 通常指「单个 key 的 value 体积或元素数量异常大」，具体可观测形态：

  • String 几十 MB；
  • Hash 字段几十万；
  • List / Set / ZSet 元素几十万到百万；
  • Stream 条目几百万且从不截断。

危害链条很清晰：

  1. 单次操作 O(N)：HGETALL、SMEMBERS、LRANGE 0 -1、ZRANGE 0 -1 都要遍历全部元素，主线程被长时间占用，所有客户端一起等；
  2. 网络放大：一次返回几十 MB，客户端反序列化也要几十 MB 内存；
  3. 删除也阻塞：DEL 释放大对象是同步的，官方专门提供 UNLINK 把回收挪到后台线程；
  4. 持久化被拖慢：AOF 追加与 RDB 快照都要处理这份大数据；
  5. 迁移/扩缩容卡住：Cluster 的 slot 迁移按 key 搬，一个大 key 就能拖慢整批；
  6. 淘汰与过期也变慢：释放内存的开销跑不掉。

2. 热 key：单点吞吐被打爆

热 key 是「访问极度集中在某一个 key」。它的风险不在内存，而在单分片/单节点的带宽与 QPS：

  • Cluster 下 key 只能落在一个 slot 上，也就是一台节点；所有请求都压这台机器；
  • 单节点 CPU 打满后，同节点上的其他 key 一起变慢（因为命令串行）；
  • 缓存击穿风险同时放大：这个 key 一失效，请求全部穿透到数据库。

官方可用的定位手段是 redis-cli --hotkeys，但它依赖 LFU：需要把 maxmemory-policy 设为 allkeys-lfu 或 volatile-lfu，否则拿不到频率统计。这一点在官方文档里写明，很多人跑 --hotkeys 拿不到结果是没配 LFU。

4. 五条治理手段的适用前提

  • 拆分：Hash 按字段名哈希取模拆成 user:1:{0..9}；Set 按成员哈希拆；String 按段拆。前提是业务能接受「读多个 key 再聚合」，否则会引入新的复杂度。
  • 分批读：HSCAN / SSCAN / ZSCAN 游标遍历，替代 HGETALL / SMEMBERS。这是不改数据就能降风险的手段，优先做。
  • 异步删：UNLINK 代替 DEL；lazyfree-lazy-user-del 等参数可让部分删除默认走异步（官方有对应配置项）。
  • 控增长：List 用 LTRIM、Stream 用 XTRIM MAXLEN/MINID、ZSet 用 ZREMRANGEBYRANK 只留 TOP N。任何「只追加不裁剪」的结构最终一定是大 key。
  • 分热点：热 key 加本地缓存（进程内 LRU）；或把同一个 key 复制成 N 份（hot:item:1:0..N），请求随机落到一份；或提升该 key 的读取并行度（读从节点）。

五、场景说明

  1. 商品详情缓存：String 存整个 JSON 且带大图 base64 → 典型大 key。改：只存结构化字段，图片走 CDN；
  2. 用户行为 List：LPUSH 从不 LTRIM → 半年后单个 key 百万条。改：LTRIM 到最近 200 条；
  3. 消息 Stream：只 XADD 从不 XTRIM → 无界增长。改：XTRIM MAXLEN ~ 10000；
  4. 爆款商品/热搜：所有请求打同一个 key → 热 key。改：本地缓存 + 多副本 + 读从库；
  5. 大 Hash 用户表：一个 Hash 存整个租户的所有用户 → HGETALL 直接事故。改：按用户 ID 拆成独立 key。

六、示例代码/实操步骤

# 1. 全库扫描找大 key（按类型报告最大的 key）
$ redis-cli -h 127.0.0.1 -p 6379 --bigkeys
# Scanning the entire keyspace to find biggest keys as well as
# average sizes per key type.  You can use -i 0.1 to sleep 0.1 sec
# per 100 SCAN commands (not usually needed).
[00.00%] Biggest string found so far '"user:1:profile"' with 5242880 bytes
[00.00%] Biggest hash   found so far '"user:big"' with 120000 fields
[00.00%] Biggest list   found so far '"feed:u1"' with 500000 items
...
# 结论：这张表就是你的「大 key 清单」

# 2. 单 key 精确占用（含内部开销）
127.0.0.1:6379> MEMORY USAGE user:big
(integer) 9867344               # 约 9.4 MB
127.0.0.1:6379> MEMORY USAGE user:big SAMPLES 100
(integer) 9867344               # 样本越大越准，开销也越大

# 3. 看编码是否已降级
127.0.0.1:6379> OBJECT ENCODING user:big
"hashtable"                     # 从 listpack 降级了，内存已翻倍

# 4. 自建巡检：按类型取长度
127.0.0.1:6379> HLEN user:big
(integer) 120000
127.0.0.1:6379> LLEN feed:u1
(integer) 500000
127.0.0.1:6379> XLEN events:order
(integer) 3000000
# 规则：HLEN > 5000 / LLEN > 10000 / XLEN > 100000 就告警

# 5. 分批读，别 HGETALL
127.0.0.1:6379> HSCAN user:big 0 COUNT 100
1) "128"
2) 1) "f1" 2) "v"
   ...

# 6. 异步删除大 key
127.0.0.1:6379> UNLINK user:big
(integer) 1                     # 立即返回，回收在后台线程进行
127.0.0.1:6379> UNLINK feed:u1
(integer) 1

# 7. 控增长：List 与 Stream 的常规裁剪
127.0.0.1:6379> LTRIM feed:u1 0 199
OK                              # 只留最近 200 条
127.0.0.1:6379> XTRIM events:order MAXLEN ~ 100000
(integer) 2900000               # 近似截断到 10 万条左右
127.0.0.1:6379> XADD events:order MAXLEN ~ 100000 * type done
# 也可以在每次 XADD 就带上 MAXLEN，避免二次裁剪

# 8. 找热 key（必须先切 LFU）
127.0.0.1:6379> CONFIG SET maxmemory-policy allkeys-lfu
OK
127.0.0.1:6379> OBJECT FREQ hot:item:1001
(integer) 187                   # LFU 计数器，仅 LFU 策略下有效
$ redis-cli --hotkeys
# 输出按访问频率排序的 key 列表

# 9. 热 key 多副本：读时随机落到一份
127.0.0.1:6379> MSET hot:item:1001:0 v hot:item:1001:1 v hot:item:1001:2 v
# 客户端逻辑：idx = rand(0..2)，读 hot:item:{id}:{idx}

Java 侧怎么落地：把「发现 + 治理」做进应用

大 key 治理主要靠运维工具，但应用侧有几处必须配合，否则治理完还会长回来。

  1. 写入侧强制控增长：List 每次写完 trim，Stream 每次 XADD 带 MAXLEN，ZSet 定时 removeRangeByRank。这三行代码比任何事后巡检都有效。
tpl.opsForList().rightPush("feed:u1", item);
tpl.opsForList().trim("feed:u1", 0, 199);          // 只留最近 200 条

tpl.opsForStream().add(StreamRecords.newRecord().in("events:order")
        .ofMap(Map.of("type", "created")),
        XAddOptions.maxLen(100_000).approximateTrimming(true));   // MAXLEN ~ 100000

  1. 删除一律 unlink：tpl.unlink(key) 对应 UNLINK；tpl.delete(key) 是同步 DEL，大 key 上会阻塞主线程。

  2. 读取一律分批：opsForHash().entries()、opsForSet().members()、opsForZSet().range(0,-1) 这三个调用在大 key 上等于事故，改 scan / rangeWithScores(0, 99) 分页。

  3. 热 key 的应用侧解法：进程内 Caffeine / Guava Cache 挡一层（TTL 1–2 秒，能挡掉绝大部分重复读）；多副本读时用 ThreadLocalRandom 选下标。

String v = tpl.opsForValue().get("hot:item:1001:" + ThreadLocalRandom.current().nextInt(3));
  1. 巡检脚本：用 RedisCallback 跑 SCAN + HLEN/LLEN/XLEN，超过阈值发告警；不要用 keys()。

七、常见坑（官方明确说明的限制）

  1. 「多大算大 key」官方没有给阈值。任何声称「超过 10 MB 就是大 key」的说法都是工程经验，不是规范。判定应当以「单次操作耗时是否明显拖慢主线程」「体积是否超出带宽预算」为准。
  2. --bigkeys 会扫全库。它在生产上跑会带来持续 SCAN 压力，务必在低峰期或用 -i 限速；它报的是「每类最大的那个」，不是「所有超标 key」。
  3. --hotkeys 依赖 LFU。策略是 noeviction / *-lru 时没有频率统计，跑出来是空的。
  4. MEMORY USAGE 是抽样估算。集合类默认 SAMPLES 5，元素极多时结果有偏差；要精确就对单 key 调大样本。
  5. DEL 大 key 阻塞，UNLINK 才异步。历史代码里的 DEL 要逐个审视；官方也提供了 lazyfree-lazy-user-del 一类配置，让用户侧删除默认走异步。
  6. 编码降级不可逆（见 RD07/RD08/RD09）。一个超长字段就能把一个「本该很小」的 Hash 永久变重。
  7. 拆分要付一致性代价：拆成多个 key 后，读要聚合、写要保证多 key 一致（用 Lua 或接受最终一致）。拆之前先算清楚收益。
  8. 热 key 多副本会带来写一致性问题：多份副本谁先写、写失败怎么补偿，必须有方案；只读场景才适合简单随机读。

版本差异（8.x 标注）

7.4 与 8.x 在这些工具上的能力一致（--bigkeys、--hotkeys、MEMORY USAGE、OBJECT ENCODING、UNLINK 都是长期存在的命令）。8.x 的差异主要在许可与集群/持久化细节，不影响本讲的判定方法。

依据：https://redis.io/docs/latest/commands/memory-usage/

八、课后小结

  • 大 key 的风险是 O(N) 阻塞与内存/带宽放大，热 key 的风险是单分片被打爆；
  • 官方不给阈值，只给工具：--bigkeys、MEMORY USAGE、OBJECT ENCODING、--hotkeys（需 LFU）；
  • 治理五手段：拆分、分批读（*SCAN）、异步删（UNLINK）、控增长（LTRIM/XTRIM/ZREMRANGEBYRANK）、分热点；
  • 「只追加不裁剪」的结构必然长成大 key，控增长要写进设计而不是事后补救；
  • DEL 大 key 阻塞主线程，官方推荐 UNLINK。

九、思考题

  1. 一个大 key 只有 2 MB，但每秒被读 5 万次。它算大 key 还是热 key？该用哪条治理手段？

    参考回答：它不构成「大 key」（2 MB 单次操作不算慢），但绝对是热 key：5 万 QPS 压在同一个 slot、同一台节点上，先到瓶颈的是带宽与单节点 CPU。治理走「分热点」：进程内本地缓存挡掉重复读，或复制 N 份随机读、读从节点扩容。

  2. --bigkeys 与「自建 HLEN 巡检」各能发现什么？为什么生产上通常两个都要？

    参考回答：--bigkeys 基于 SCAN 遍历，报「每类型里最大的那个 key」，能发现你不知道存在的巨无霸，但只给 top 1、且扫全库有压力；自建 HLEN/LLEN/XLEN 巡检能按阈值揪出所有超标 key 并做趋势告警，但依赖你已知 key 命名规律。一个兜底发现未知，一个持续监控已知，互补。

  3. 一个 List 每天 LPUSH 10 万条且从不裁剪，一年后有多长？删除时 DEL 与 UNLINK 的差别体现在哪里？

    参考回答：365 × 10 万 = 3650 万条，按每条几十字节算就是 GB 级。DEL 在主线程同步释放全部内存，几千万节点逐个回收会让实例卡住数秒；UNLINK 只把 key 从键空间摘掉，内存交给后台线程回收，主线程几乎立即返回。

  4. 把一个大 Hash 拆成 10 个小 key 之后，HGET 一次要多几次网络往返？这个代价你接受的前提是什么？

    参考回答：读单个字段仍是一次往返（先算分片号再读对应 key）；只有跨多个字段聚合读时才变成 N 次，可用 Pipeline 压成一次 RTT。接受的前提：业务能容忍跨 key 聚合、写多 key 的一致性能用 Lua 保证、并且拆分后单次操作耗时确实降到可接受水平。

  5. 为什么 --hotkeys 在 allkeys-lru 下拿不到数据？如果你不能改线上策略，还有什么办法定位热 key？

    参考回答：--hotkeys 读的是对象的 LFU 频率计数器（OBJECT FREQ），这个字段只在 *-lfu 策略下维护，LRU 不采样频率。不改策略时的替代：① MONITOR 短时采样（有性能影响）；② 客户端埋点按 key 聚合 QPS；③ APM / 链路追踪里按 key 名统计；④ 业务侧按曝光量反推。
