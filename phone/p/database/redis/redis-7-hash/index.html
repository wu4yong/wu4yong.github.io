Hash 类型：字段级读写与字段级过期

Hash 的字段结构、listpack/hashtable 编码阈值与 7.4 字段级 TTL｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 Hash 是「一个 key 下的字段字典」，以及它和「把一个对象序列化成 String」的本质差别；
  2. 掌握 HSET / HGET / HMGET / HINCRBY / HSCAN 的用法与复杂度，能判断什么时候 HGETALL 会出事；
  3. 知道 listpack 与 hashtable 的转换阈值及其「不可逆」特性，并会用 7.4 新增的 HEXPIRE 系列做字段级过期。

二、前置知识

RD05（String）与 RD06（List）。理解「命令级原子」与「O(N) 命令会阻塞主线程」这两点，是本讲判断风险的前提。

三、理论讲解（官方定义）

官方定义（原文）：

Redis hashes are record types structured as collections of field-value pairs. … Every hash can store up to 4,294,967,295 (2^32 - 1) field-value pairs.

—— https://redis.io/docs/latest/develop/data-types/hashes/

三个硬信息：

  • record type：字段-值对的集合，语义上就是一个「小对象 / 一行记录」；
  • field 与 value 都是字符串，没有嵌套；
  • 单 Hash 最多 2^32-1 组字段。

注意「最多」不等于「应该」。下文的编码阈值会把这个问题讲透。

四、原理拆解

1. Hash vs 序列化成 String：先想清楚差异

同一个用户资料，两种存法：

结论：要按字段改、按字段读，用 Hash；要整对象读写、且对象很小，String 更省事。这是选型的第一原则。

2. 编码：listpack 与 hashtable

官方给的阈值（redis.conf 默认值）：

hash-max-listpack-entries 128     # 字段数上限
hash-max-listpack-value 64        # 单字段/单值字节数上限

规则是「与」的关系：字段数 ≤ 128 且每个字段名与值的长度都不超过 64 字节，才用 listpack；任一条件被突破，立刻转成 hashtable。

两个必须记住的结论：

  1. 转换是单向的。数据删回 100 个字段，编码仍是 hashtable，不会回退——因为回退需要重排整块内存。
  2. 编码影响内存与性能。listpack 省内存但插入是 O(N)（要重排），hashtable 插入 O(1) 但指针开销大。所以「小对象用 Hash 特别省内存」这句话的前提是编码还在 listpack。

查当前编码：OBJECT ENCODING user:1。

3. 7.4 新增：字段级过期

这是 7.4 相对旧版本最重要的 Hash 变化。旧版本里 EXPIRE 只作用于整个 key，想让「会话里每个 token 各自倒计时」只能拆成多个 key，或者自己维护一个 ZSet 记时间。

7.4 起提供了一组字段级命令：

  • HEXPIRE key seconds FIELDS n field...（相对秒）/ HPEXPIRE（相对毫秒）
  • HEXPIREAT / HPEXPIREAT（绝对时间点）
  • HTTL / HPTTL（查剩余时间，同样用 FIELDS 指定字段）
  • HPERSIST（去掉字段过期）
  • HGETEX（读字段的同时设置/清除过期，EX/PX/EXAT/PERSIST 选项）

语义要点：过期到点的字段在逻辑上「不存在」——HGET 返回 nil、HLEN 不计、HKEYS 不列，但内存空间要等后续操作或主动清理才真正回收。别指望它像独立 key 一样被淘汰策略立刻扫到。

五、场景说明

  1. 对象缓存：HSET user:1 name 阿勇 age 30 vip 1 + EXPIRE user:1 3600，改昵称只发一条 HSET；
  2. 购物车：HINCRBY cart:u1 sku:100 2，同一 SKU 数量累加是原子的；
  3. 多维计数：HINCRBY stat:2022-12-28 pv 1 / hits 1，一天一个 Hash，字段是各维度；
  4. 配置/开关集合：HSET feature:flags newCheckout 1，一次 HMGET 取需要的开关；
  5. 限流窗口：HINCRBY rate:uid:minute /api/order 1，配合 EXPIRE 整 key 过期。

不适合：需要按字段值排序或检索（Hash 没有索引）、需要集合运算（用 Set）、字段数量无上界且经常全量读（该拆成多个 key）。

六、示例代码/实操步骤

# 1. 基本字段读写
127.0.0.1:6379> HSET user:1 name 阿勇 age 30 vip 1
(integer) 3                  # 返回新增字段数
127.0.0.1:6379> HGET user:1 name
"阿勇"
127.0.0.1:6379> HMGET user:1 name age city
1) "阿勇"
2) "30"
3) (nil)                     # 不存在的字段返回 nil，不是报错
127.0.0.1:6379> HLEN user:1
(integer) 3
127.0.0.1:6379> HEXISTS user:1 vip
(integer) 1

# 2. 改一个字段不动其他字段
127.0.0.1:6379> HSET user:1 name 阿勇2
(integer) 0                  # 0 表示是更新而非新增
127.0.0.1:6379> HGETALL user:1
1) "name"
2) "阿勇2"
3) "age"
4) "30"
5) "vip"
6) "1"

# 3. 字段级原子计数
127.0.0.1:6379> HINCRBY cart:u1 sku100 2
(integer) 2
127.0.0.1:6379> HINCRBY cart:u1 sku100 3
(integer) 5
127.0.0.1:6379> HINCRBY cart:u1 sku100 -5
(integer) 0                  # 减到 0 字段仍存在（值为 "0"）

# 4. 看编码与阈值
127.0.0.1:6379> OBJECT ENCODING user:1
"listpack"
127.0.0.1:6379> CONFIG GET hash-max-listpack-entries
1) "hash-max-listpack-entries"
2) "128"
# 塞到 129 个字段，编码立刻降级且不可逆
127.0.0.1:6379> EVAL "for i=1,129 do redis.call('HSET', KEYS[1], 'f'..i, 'v') end return redis.call('OBJECT', 'ENCODING', KEYS[1])" 1 big:hash
"hashtable"

# 5. 分批遍历，别 HGETALL
127.0.0.1:6379> HSCAN big:hash 0 COUNT 10
1) "12"
2) 1) "f1"
   2) "v"
   ...

# 6. 7.4 字段级过期（旧版本没有）
127.0.0.1:6379> HSET session:s1 token1 abc token2 def
(integer) 2
127.0.0.1:6379> HEXPIRE session:s1 60 FIELDS 1 token1
1) (integer) 1               # 1=设置成功，2=字段不存在，0=条件未满足
127.0.0.1:6379> HTTL session:s1 FIELDS 2 token1 token2
1) (integer) 58
2) (integer) -1              # -1 表示该字段没有过期时间
127.0.0.1:6379> HPERSIST session:s1 FIELDS 1 token1
1) (integer) 1

# 7. HGETEX：读字段并顺手改过期
127.0.0.1:6379> HGETEX session:s1 EX 30 FIELDS 1 token1
1) "abc"                     # 返回旧值，同时把 token1 的 TTL 设为 30 秒

HEXPIRE 的返回值是「每个字段一个状态码」，多字段时是一个数组——这一点和 EXPIRE 只返回一个整数完全不同，写代码时不能沿用旧判断。

Java 侧怎么落地：对象缓存与购物车

Hash 在 Spring Boot 里用 opsForHash()，但默认的 RedisTemplate 会把 field 与 value 都做 JDK 序列化，命令行里全是乱码。所以要么用 StringRedisTemplate 自己序列化 JSON，要么配一个 HashKeySerializer / HashValueSerializer。

  1. 配一个专门给 Hash 用的模板（key 与 field 用字符串，value 用 JSON）：
@Bean
RedisTemplate<String, Object> hashTemplate(RedisConnectionFactory f) {
    RedisTemplate<String, Object> t = new RedisTemplate<>();
    t.setConnectionFactory(f);
    t.setKeySerializer(new StringRedisSerializer());
    t.setHashKeySerializer(new StringRedisSerializer());     // field 必须可读
    t.setHashValueSerializer(new GenericJackson2JsonRedisSerializer());
    t.afterPropertiesSet();
    return t;
}
  1. 改一个字段就只发一条命令，不要整对象读改写：
hashTemplate.opsForHash().put("user:1", "name", "阿勇");       // HSET
hashTemplate.opsForHash().increment("cart:u1", "sku100", 2);   // HINCRBY，字段值必须是整数
Map<Object, Object> all = hashTemplate.opsForHash().entries("user:1");  // HGETALL，注意 O(N)

  1. 遍历一律用 Cursor，opsForHash().scan(key, ScanOptions.scanOptions().count(100).build()) 对应 HSCAN，用完必须 close()；entries() 就是 HGETALL，大 Hash 上等于事故。

  2. 字段级过期只能在 7.4+ 用，Spring Data Redis 3.2+ 才有 hexpire 封装；低版本要么用原生 RedisCallback 直接发命令，要么退回「整 key 过期 + 拆 key」。

七、常见坑（官方明确说明的限制）

  1. HGETALL 是 O(N)。字段几千以上就会明显阻塞主线程，字段几万直接是事故。读全量请用 HSCAN 分批，或改成按需 HMGET。
  2. 编码降级不可逆。一旦超过 hash-max-listpack-entries 或单值超 64 字节，就永久变成 hashtable，内存占用会显著上涨。大量「本来很小」的 Hash 被一个超长字段（比如塞了个 base64 图片）整体拖降级，是典型翻车现场。
  3. HDEL 删完所有字段后 key 会自动消失，此时再 EXPIRE 会返回 0（key 不存在）。写「先删字段再设过期」的代码要注意顺序。
  4. HINCRBY 的字段必须能解析成整数，否则报错；且同样受 64 位有符号溢出限制。
  5. 字段级过期是 7.4 才有的能力。7.4 之前必须拆 key 或自建 ZSet 索引——很多老项目文档里写的「Hash 不支持字段过期」指的是旧版本，别照抄结论。
  6. Hash 不能按 value 检索，也没有二级索引。需要「查 age > 30 的用户」这种条件，Redis 帮不了你。
  7. 一个 Hash 的字段数没有业务上限，只有 2^32-1 的硬上限；但工程上要自己定阈值，否则会长成「大 key」（RD13 详讲）。

版本差异（8.x 标注）

7.4 引入的字段级过期（HEXPIRE / HPEXPIRE / HEXPIREAT / HPEXPIREAT / HTTL / HPTTL / HPERSIST / HGETEX）在 8.x 继续沿用，语法未变。若你的环境仍是 6.x/7.0–7.2，本节第 3、4 小节的内容不适用，请按「整 key 过期 + 拆 key」的方案设计。

依据：https://redis.io/docs/latest/commands/hexpire/

八、课后小结

  • Hash 是字段字典，一条命令改一个字段，天然避免「读改写」的覆盖问题；
  • 编码规则是「字段数 ≤ 128 且单字段/值 ≤ 64 字节 → listpack」，突破即降级且不可逆；
  • HSET/HGET/HINCRBY 是 O(1)，HGETALL 是 O(N)，大 Hash 必须用 HSCAN；
  • 7.4 才支持字段级过期，HEXPIRE 系列返回的是「每字段状态码」；
  • HDEL 删空后 key 会消失，后续过期设置要重新判断存在性。

九、思考题

  1. 同一个用户资料，用 String 存 JSON 和用 Hash 存字段，在「并发更新不同字段」时差在哪里？举一个 String 方案会丢更新的具体时序。

    参考回答：Hash 的 HSET user:1 name xxx 只改一个字段，不碰别人；String 存 JSON 必须「读出来 → 反序列化 → 改 → 序列化 → 写回」。丢更新的时序：A 与 B 同时 GET 到 {name:old, age:30}，A 改成 name=new 写回，B 改成 age=31 写回时带的是旧的 name，A 的修改被覆盖。

  2. 一个本该很小的 Hash 因为某个字段存了 200 字节的 token 而整体变成 hashtable。内存大概会涨多少倍？怎么在不改数据的前提下救回来？

    参考回答：listpack 是连续紧凑存储，hashtable 每个字段都要 dictEntry + 指针 + 可能重复的 key，通常涨 2–5 倍（取决于字段数与键长），上不封顶。救法只有一条：把超长字段挪出去（单独存一个 key 或缩短/编码后存），再重写这个 Hash；编码转换不可逆，只能删 key 重建。

  3. HGETALL 与 HSCAN 遍历，都能拿到全部字段。前者什么时候可以用，什么时候绝对不能用？

    参考回答：字段数确定且很小（几十个以内）、并且确实需要一次性拿全时才用 HGETALL；字段数不确定、可能上千，或位于线上热路径时绝对不能用——HGETALL 是 O(N) 且同步阻塞主线程，一次调用就能把整个实例拖住。此时用 HSCAN 游标分批 + COUNT。

  4. 7.4 的字段级过期，字段过期后「逻辑不存在但内存未回收」。这对 HLEN 的返回值有什么影响？对内存监控有什么影响？

    参考回答：HLEN 只统计逻辑存在的字段，过期字段不计数——于是会出现「HLEN 很小但 MEMORY USAGE 很大」的错位。内存监控不能只看字段数，要看 MEMORY USAGE key 与 INFO memory；而逻辑过期的字段要等被访问或主动清理才真正释放。

  5. 设计一个「购物车」Hash，字段是 SKU，值是数量。用户清空购物车后 key 会怎样？EXPIRE 放在什么时候设最合适？

    参考回答：HDEL 删掉最后一个字段时，key 会被自动删除，此时再 EXPIRE 返回 0（key 不存在）。所以 EXPIRE 应该在每次 HINCRBY / HSET 之后统一补一次（或用 HINCRBY 后判断是否需要续期），不要指望「先建 key 再删空」还能保留过期时间。
