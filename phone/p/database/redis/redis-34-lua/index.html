Lua 脚本与原子性

EVAL 的四步路径、原子性的真实来源与 SCRIPT LOAD/EVALSHA 机制｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清「脚本是原子的」这句话的准确含义与它的边界；
  2. 用 SCRIPT LOAD + EVALSHA 消除每次传输脚本的开销，并处理 NOSCRIPT；
  3. 正确拆分 KEYS 与 ARGV，让脚本在 Cluster 下也能正确路由。

二、前置知识

RD33（事务的局限）、RD04（RESP）。Lua 是 Redis 用来补「事务不能做条件判断」这块短板的手段。

三、理论讲解（官方定义）

官方对脚本原子性的说明（原文）：

Redis guarantees the script is executed atomically … While the script is running, no other commands from other clients are processed.

—— https://redis.io/docs/latest/develop/programmability/eval-intro/

以及关于脚本内禁止的操作（原文要点）：

Scripts … cannot access … blocking commands … The script can only call Redis commands and use the Lua standard library.

—— 同上

两条定性：

  • 原子性 = 执行期间没有其他命令被处理，和事务是同一个来源（单线程事件循环）；
  • 原子不等于可回滚：脚本中途报错，已执行的写照样保留。

四、原理拆解

1. 一次 EVAL 的完整路径

客户端 → EVAL script numkeys KEYS... ARGV...
服务端 → 计算 SHA1，编译（或从缓存取）
       → 在 Lua 引擎里执行，期间 Redis 命令通过 redis.call 同步进入
       → Lua 返回值转成 RESP（数字/字符串/数组/nil 各有对应类型）

注意「同步进入」这四个字：redis.call 是同步调用，脚本里读到的值就是当时的真实值，这也是它比事务好用的原因——能做条件分支。

2. 原子性的真实边界

说法
准确性
「脚本执行期间不会插入其他命令」
✅ 准确
「脚本内的写要么全成、要么全不成」
❌ 错误，没有回滚
「脚本能保证读到的值在写之前不被改」
✅ 准确（因为不插入）
「脚本不会阻塞其他客户端」
❌ 错误，阻塞是必然的

第四条是实践中最痛的：一个跑 2 秒的脚本会让整个实例停 2 秒。官方为此提供了 busy-reply-threshold（默认 5 秒，lua-time-limit）——超时后其他客户端会收到 BUSY 错误，此时只能等脚本结束或 SCRIPT KILL（仅当脚本还没写过数据）。

3. SCRIPT LOAD 与 EVALSHA

SCRIPT LOAD "return redis.call('GET', KEYS[1])"
# → "e0e1f9fabfc9d4800c877a703b823ac0578ff8db"

EVALSHA e0e1f9fabfc9d4800c877a703b823ac0578ff8db 1 mykey
# → "value"

三点必须知道：

  • 缓存是进程级的，重启、SCRIPT FLUSH、主从切换后都会丢；
  • 缓存不存在时返回 NOSCRIPT，客户端要自动回退到 EVAL；
  • 客户端 SDK（如 Lettuce、Jedis）通常内置这个回退逻辑，但自研客户端必须自己实现。

4. KEYS 与 ARGV 必须分开

EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 user:1 alice
  • numkeys 之后是全部 key，再之后是全部 argv；
  • 所有 key 必须通过 KEYS 传入，不能把 key 拼进脚本字符串；
  • 原因有两个：Cluster 下服务端要用 KEYS 校验同槽与路由；迁移/复制时可以正确重写 key。

把 key 写死在脚本里，在单机看不出问题，上 Cluster 会直接报「脚本里的 key 不在同一个槽」或路由错误。

5. 脚本的复制策略

7.0 起默认按效果复制（effects replication）：主库执行脚本，把脚本产生的写命令传给从库与 AOF，而不是把整个脚本体发过去。好处是确定性——从库不需要重新执行脚本，避免随机函数、时间函数导致的不一致。

这也解释了为什么官方要求脚本「必须是确定的」：同样的输入必须产生同样的写效果，否则主从会分叉。

五、场景说明

  1. 库存扣减：if stock > 0 then DECR ...，条件判断 + 写在一个脚本里；
  2. 限流：按 key 做滑动窗口计数（RD46 会展开）；
  3. 批量条件更新：读一批、判断、再写，事务做不到的都能做；
  4. 一次性数据修补：临时脚本 + EVAL 直接跑，不落任何代码。

不适合：逻辑很长、需要访问外部系统、耗时不可控的任务——这些会把单线程堵死。

六、示例代码/实操步骤

# 1. 最简单的脚本
127.0.0.1:6379> EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 greet hello
OK
127.0.0.1:6379> GET greet
"hello"

# 2. 条件判断（事务做不到的部分）
127.0.0.1:6379> SET stock 10
OK
127.0.0.1:6379> EVAL "
 local s = tonumber(redis.call('GET', KEYS[1]))
 if s == nil or s <= 0 then return -1 end
 redis.call('DECR', KEYS[1])
 return s - 1
" 1 stock
(integer) 9

# 3. 原子性验证：执行期间其他客户端读不到中间态
127.0.0.1:6379> EVAL "redis.call('SET', KEYS[1], 'a'); redis.call('SET', KEYS[1], 'b'); return redis.call('GET', KEYS[1])" 1 atom
"b"                        # 只会看到最终值，中间态不会外泄

# 4. 运行时错误：前面的写不撤销
127.0.0.1:6379> EVAL "redis.call('SET', KEYS[1], 'written'); return redis.call('LPUSH', KEYS[1], 'x')" 1 partial
(error) WRONGTYPE Operation against a key holding the wrong kind of value
127.0.0.1:6379> GET partial
"written"                  # SET 生效了，没有回滚

# 5. SCRIPT LOAD + EVALSHA
127.0.0.1:6379> SCRIPT LOAD "return redis.call('INCR', KEYS[1])"
"2b9a26a1a1f1dcb0a6f4d0b4e1b8e0f9a4b6c1d2"
127.0.0.1:6379> EVALSHA 2b9a26a1a1f1dcb0a6f4d0b4e1b8e0f9a4b6c1d2 1 cnt
(integer) 1
127.0.0.1:6379> EVALSHA ffffffffffffffffffffffffffffffffffffffff 1 cnt
(error) NOSCRIPT No matching script. Please use EVAL.

# 6. 查看脚本缓存与清理
127.0.0.1:6379> SCRIPT EXISTS 2b9a26a1a1f1dcb0a6f4d0b4e1b8e0f9a4b6c1d2
1) (integer) 1
127.0.0.1:6379> SCRIPT FLUSH
OK

# 7. 长脚本会阻塞所有人（不要在生产跑这类）
127.0.0.1:6379> EVAL "local x=0 for i=1,100000000 do x=x+i end return x" 0
# 期间其他客户端会收到：
# (error) BUSY Redis is busy running a script.

# 8. 终止脚本（只在脚本尚未写数据时可用）
127.0.0.1:6379> SCRIPT KILL
# 若脚本已经写过数据：
# (error) UNKILLABLE Sorry the script already executed write commands against the dataset.

七、常见坑（官方明确说明的限制）

  1. 以为脚本能回滚。中途报错，之前的写保留；要「要么全成」得业务自己设计补偿。
  2. 脚本里把 key 写成常量。Cluster 下会路由失败或同槽校验失败，必须通过 KEYS 传。
  3. numkeys 传错。把参数当 key 传，服务端会按 key 校验，报 CROSSSLOT 或参数错误。
  4. 脚本里访问时间/随机数。官方要求脚本确定性，redis.call('TIME') 之类会让效果复制出问题；需要随机可用 redis.set_repl 相关机制或干脆在客户端决定。
  5. 长脚本。默认超过 busy-reply-threshold（5 秒）其他客户端就全被 BUSY 挡住，且已写数据的脚本无法 SCRIPT KILL，只能等或重启。
  6. 依赖脚本缓存常驻。重启/切换/SCRIPT FLUSH 后全丢，必须处理 NOSCRIPT。
  7. 在脚本里调用阻塞命令。官方不允许，BLPOP 这类在脚本内会当作非阻塞处理，直接返回 nil，容易误判。
  8. 脚本体积过大。每次 EVAL 都要传整段脚本并算 SHA1，高频调用必须走 EVALSHA 或改用 Functions（下一讲）。

版本差异（8.x 标注）

7.0 起脚本默认按效果复制；7.4 与 8.x 沿用。busy-reply-threshold 取代了旧的 lua-time-limit 语义。8.x 未改变脚本原子性与不可回滚的边界。

依据：https://redis.io/docs/latest/develop/programmability/eval-intro/

八、课后小结

  • 原子性来源：脚本在事件循环一圈内跑完，期间无其他命令被处理；
  • 原子 ≠ 可回滚，脚本报错后已执行的写保留；
  • KEYS / ARGV 必须分开，所有 key 走 KEYS（Cluster 才能正确路由）；
  • SCRIPT LOAD 返回 SHA1，EVALSHA 调用，NOSCRIPT 要回退 EVAL；
  • 长脚本阻塞全实例，超 busy-reply-threshold 后其他客户端报 BUSY；
  • 7.0 起按效果复制，脚本必须确定性。

九、思考题

  1. 「脚本是原子的」具体保证什么？不保证什么？各举一个例子。
  2. 为什么所有 key 必须通过 KEYS 传入？把 key 拼进脚本在 Cluster 下会怎样？
  3. EVALSHA 返回 NOSCRIPT 时，客户端应该怎么做？为什么不能直接报错给用户？
  4. 脚本跑到一半写了数据，此时能 SCRIPT KILL 吗？为什么官方不允许？
  5. 为什么脚本必须确定性？不确定的脚本在「效果复制」下会引发什么问题？
