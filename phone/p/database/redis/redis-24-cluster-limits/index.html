Cluster 的限制与运维边界

Cluster 的五条硬性限制、hash tag 的正确用法与运维边界｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 背下 Cluster 的五条硬限制，并在评审需求时提前指出哪条会踩；
  2. 用 hash tag 解决「多 key 同槽」的问题，同时知道它的副作用；
  3. 分清哪些事「Cluster 会自己做」（故障转移）、哪些事「必须人做」（迁槽、扩缩容、数据治理）。

二、前置知识

RD22（槽与路由）、RD23（reshard）。本讲是把前两讲的操作经验归纳成「边界清单」，属于上手前必须先读的一篇。

三、理论讲解（官方定义）

官方列出的 Cluster 限制（原文要点）：

Redis Cluster … Multi-key operations … are supported as long as all the keys … hash to the same hash slot. … Redis Cluster does not support multiple databases like the standalone version … the database 0 only.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/

以及 Pub/Sub 的说明（原文要点）：

In a Redis Cluster clients can subscribe to every node, and can also publish to every other node … 7.0 adds sharded Pub/Sub (SSUBSCRIBE).

—— 同上

这两条是「上了 Cluster 之后业务代码要改」的根源：不是性能问题，是模型差异。

四、原理拆解

1. 五条硬限制

限制 具体表现 破法
只有 0 号库 SELECT 1 报错 用 key 前缀区分业务
多 key 必须同槽 MGET k1 k2 跨槽报 CROSSSLOT hash tag {tag} 绑定
事务/Lua 只能在单槽 MULTI 跨节点无效 同槽 + 客户端事务补偿
扩缩容需人工迁槽 槽不会自动均摊 reshard / rebalance
客户端必须支持重定向 单机客户端只看得到部分 key 换 Cluster 客户端或加代理

第一条最容易被低估。很多旧系统用 SELECT 分库做业务隔离，迁到 Cluster 后必须改造成 key 前缀（如 order:1001:...）。

第三条要连着 RD33/RD34（后面的事务与 Lua）一起理解：Cluster 不是「事务不能用」，而是「事务的范围被槽切开了」。

2. hash tag 的正确用法

{order:1001}:items      ┐
{order:1001}:total      ├── 同槽，可 MGET / 可 Lua
{order:1001}:status     ┘

副作用必须知道：

  • 分布退化：所有 key 共享一个 tag 时，它们全落同一槽 → 单节点热点与内存倾斜；
  • 无法嵌套：{a{b}} 只取第一个 } 之前的部分，容易算错；
  • tag 要稳定：用会变的值（如时间戳）做 tag，等于把 key 打散到不同槽，多 key 操作照样失败。

权衡原则：tag 的粒度 = 需要一起操作的 key 的粒度。订单维度做 tag 可以，全站一个 tag 不行。

3. Cluster 会做 vs 人要做

事 谁做 说明
主节点故障自动转移 Cluster 自做 从库提升 + 槽接管，靠 cluster-node-timeout 与多数票
槽的自动均摊 人做 只能 reshard / rebalance
大 key 治理 人做 Cluster 放大了迁移与阻塞的代价
跨槽多 key 重构 人做 业务代码级改造
客户端重定向 客户端库做 服务端只返回 MOVED/ASK

这张表的意义：Cluster 只解决「可用性与容量」，不解决「你的代码模型」。上线前的评审要按上面五条逐条对照业务代码。

4. cluster-node-timeout 与「半死」判定

cluster-node-timeout（默认 15000 ms）决定「多久没响应算节点失败」。这里有个 Cluster 特有的严格规则：如果节点超时但仍存活（半死），Cluster 会拒绝执行故障转移，因为拿不到一致的多数判断——这就是某些「集群卡住、明明有从库却不切」的原因。排查时要先看节点是否真的死了（进程、网络、GC 停顿），再看超时配置。

五、场景说明

  1. 大 key 检查必须在 Cluster 之前：一个 1 GB 的 hash 迁移时会阻塞源节点，也可能撑爆目标节点；
  2. 多 key 业务要先设计 tag：购物车、订单详情、库存扣减，都是典型的「必须同槽」；
  3. Pub/Sub 广播成本：Cluster 中普通 Pub/Sub 是广播到所有节点，消息量大时要评估带宽；7.0+ 用 SSUBSCRIBE 做分片订阅；
  4. 客户端选型：Lettuce / Jedis（Cluster 模式）/ go-redis ClusterClient 都支持重定向，别用只支持单机的老客户端。

六、示例代码/实操步骤

# 1. 验证「只有 0 号库」
127.0.0.1:7000> SELECT 1
(error) ERR SELECT is not allowed in cluster mode

# 2. 验证跨槽多 key 失败
127.0.0.1:7000> MGET user:1 user:2
(error) CROSSSLOT Keys in request don't hash to the same slot

# 3. 用 hash tag 修复
127.0.0.1:7000> MSET "{u:1}:name" alice "{u:1}:age" 30
OK
127.0.0.1:7000> MGET "{u:1}:name" "{u:1}:age"
1) "alice"
2) "30"

# 4. 确认同槽
127.0.0.1:7000> CLUSTER KEYSLOT "{u:1}:name"
(integer) 8133
127.0.0.1:7000> CLUSTER KEYSLOT "{u:1}:age"
(integer) 8133

# 5. 同一槽内跑 Lua（合法）
127.0.0.1:7000> EVAL "return redis.call('GET', KEYS[1])" 1 "{u:1}:name"
"alice"

# 6. 跨槽事务必然失败
127.0.0.1:7000> MULTI
OK
127.0.0.1:7000> SET user:1 a
QUEUED
127.0.0.1:7000> SET user:2 b
(error) CROSSSLOT Keys in request don't hash to the same slot

# 7. 扫描大 key（每节点各跑一次，Cluster 下 SCAN 是单节点语义）
127.0.0.1:7000> SCAN 0 COUNT 1000
# 注意：Cluster 里 SCAN 只扫当前节点，不是全集群

# 8. 检查集群整体状态与槽覆盖
127.0.0.1:7000> CLUSTER INFO
# cluster_state:ok
# cluster_slots_assigned:16384
# cluster_slots_fail:0
127.0.0.1:7000> CLUSTER NODES | wc -l

# 9. 分片订阅（7.0+）
127.0.0.1:7000> SSUBSCRIBE orders
# 只订阅该槽所在节点，避免全网广播

七、常见坑（官方明确说明的限制）

  1. 认为「Cluster 不支持事务」。准确说法是：事务必须在同一槽内，跨槽无效。用 hash tag 收敛即可。
  2. SCAN 只扫当前节点。Cluster 下要遍历全量 key，必须对每个主节点分别 SCAN，否则会漏。
  3. KEYS * 在生产禁用，Cluster 下更危险（每节点都阻塞）。
  4. cluster-node-timeout 一味调大。调大能减少误判，但会让真故障的切换变慢；默认 15 秒是常见起点，跨机房要实测。
  5. 半死节点导致切换卡住。节点超时但未真死时，Cluster 拒绝转移，需要人工介入（kill 或修网络）。
  6. 普通 Pub/Sub 全节点广播。高吞吐场景必须用 SSUBSCRIBE（7.0+），否则网络与 CPU 都被放大数倍。
  7. hash tag 滥用导致倾斜。上线前用 CLUSTER COUNTKEYSINSLOT 抽查几个槽的 key 数，差距过大就要拆 tag。
  8. 客户端缓存的槽表长期不刷新。Cluster 有「槽表变更后主动关闭部分连接」的机制，但客户端库必须实现刷新，否则切换后持续报错。
  9. 扩容只加主不加从。新主的槽在主库挂掉后无人接管，等于给集群埋了一个不可用区。

版本差异（8.x 标注）

7.0 引入分片 Pub/Sub（SSUBSCRIBE/SUNSUBSCRIBE/SPUBLISH），显著降低广播成本；7.4 与 8.x 沿用。8.x 的许可变更（AGPLv3/SSPL）不影响这些命令语义，但影响商业使用前的合规评估。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/、https://redis.io/docs/latest/commands/ssubscribe/

八、课后小结

  • 五条硬限制：只有 0 号库、多 key 必须同槽、事务/Lua 限单槽、扩缩容要人工迁槽、客户端必须支持重定向；
  • hash tag 是唯一的解法，但会让分布退化，粒度要等于「一起操作的 key」；
  • Cluster 自做故障转移，人做迁槽、治理与业务改造；
  • cluster-node-timeout 太短误判、太长迟钝，半死节点会让切换卡住；
  • SCAN 是单节点语义，全量遍历要逐主节点跑；
  • 7.0+ 用 SSUBSCRIBE 替代广播式 Pub/Sub。

九、思考题

  1. 你的业务原先用 SELECT 0/1/2 做租户隔离，迁 Cluster 时怎么改？给出 key 设计方案。
  2. 为什么 MULTI 跨槽会失败？如果业务真的需要跨槽原子性，有哪些替代路径？
  3. 一个 hash tag 被全站共用，CLUSTER SLOTS 上会看到什么？怎么发现并修复？
  4. cluster-node-timeout 60000 有什么代价？在「跨机房 3 主」的集群里你会怎么定这个值？
  5. 为什么 Cluster 下的 SCAN 不能当「全库遍历」用？写出遍历全集群的正确做法。
