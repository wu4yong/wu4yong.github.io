Pipeline 与批量命令

N 次 RTT 与 1 次 RTT 的差别、一次管道的时间构成与两条边界｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 Pipeline 省下来的是「网络往返」，不是「服务端执行时间」；
  2. 判断什么时候该用 Pipeline、什么时候直接用 MGET/MSET 这类批量命令；
  3. 知道 Pipeline 的两条边界（不保证原子性、批量过大撑内存），并能给出分批标准。

二、前置知识

RD04（RESP 与客户端选型）、RD33（事务）。Pipeline 是「客户端侧的批量技巧」，不是服务端特性。

三、理论讲解（官方定义）

官方对 Pipelining 的定义（原文）：

Pipelining is a technique … a client can send multiple requests to the server without waiting for the replies … and finally read the replies in a single step.

—— https://redis.io/docs/latest/develop/using-commands/pipelining/

以及它省掉的是什么（原文要点）：

The cost of … RTT (round trip time) … is paid once instead of N times.

—— 同上

两条定性：

  • 服务端执行时间不变：命令仍然逐条串行执行；
  • 原子性也不会因为管道而获得：中间的请求照样能被其他客户端插入。

四、原理拆解

1. 两条路线的时间账

逐条发送（N 条命令）：

T_total = N × (RTT + T_exec)

Pipeline（N 条一次性发出）：

T_total = RTT + N × T_exec + T_parse

差别就在那个 N × RTT 变成了 1 × RTT。在 1ms RTT、1000 条命令的场景下，这几乎是 1 秒的差距——Pipeline 的收益与 RTT 成正比，与命令数成正比。

反过来，如果 RTT 只有 0.05ms，或者命令本身很慢，Pipeline 的收益就很有限。

2. Pipeline 与批量命令不是一回事

方式
原子性
适用
MGET / MSET / HMGET
单条命令，服务端一次处理
同类型、同结构的批量读写
Pipeline
无（只是打包发送）
异构命令、需要混合读写
MULTI + Pipeline
有（事务包裹）
需要「不被打断」的批量写

MGET 是一条命令，服务端一次遍历完成，比 Pipeline 里发 100 个 GET 更省（省的是命令调度与协议开销）。所以规则是：能用批量命令就不用 Pipeline，能 Pipeline 就不用逐条。

3. 一次管道的时间构成

1 次往返（RTT）
  ↓
N 条命令串行执行（T_exec × N）
  ↓
1 次批量回复读取（解析 N 个回复）

注意最后一步：回复也是打包回来的，客户端要一次性读入并解析全部。这就是内存风险的来源——管道越长，客户端与服务端的缓冲区压力越大。

4. 分批的经验值

官方没有强制上限，工程上的常见做法：

  • 按条数：500–1000 条一批；
  • 按字节：单批不超过几 MB（大 value 场景尤其要按字节算）；
  • 按耗时：一批的预期执行时间不要超过几十毫秒，否则会明显抬高其他客户端延迟。

高并发下还要注意：Pipeline 会把「N 条命令」变成一个「大请求」，服务端要一次性读完再逐条执行，大请求会占用主线程更久，所以别把 10 万条塞进一个管道。

五、场景说明

  1. 数据导入：把 CSV 批量灌库，Pipeline 是最直接的手段；
  2. 批量写缓存：一次预热几千个 key，分 1000 条一批；
  3. 混合读写：需要 SET + EXPIRE 成对操作时，Pipeline 比逐条省一个 RTT；
  4. 不适合：需要「读到结果再决定下一条」的链路（Pipeline 拿不到中间结果）、需要原子性的场景（要包 MULTI 或 Lua）。

六、示例代码/实操步骤

# 1. 用 redis-cli 的 --pipe 模式灌数据（最快的方式）
$ redis-cli --pipe < commands.txt
# commands.txt 内容形如：
# SET k1 v1
# SET k2 v2

# 2. 观察逐条 vs 批量命令的耗时差
127.0.0.1:6379> MULTI
OK
# 对比：1000 次 GET 逐条执行（客户端要循环 1000 次往返）
# 与一次 MGET 1000 个 key：一条命令、一次往返

# 3. 客户端库示例：Python redis-py
# pipe = r.pipeline(transaction=False)
# for i in range(1000):
#     pipe.set(f"k{i}", i)
# pipe.execute()          # 一次写出、一次读回

# 4. 带事务的管道（要原子性就包 MULTI）
# pipe = r.pipeline(transaction=True)
# pipe.incr("counter")
# pipe.expire("counter", 60)
# pipe.execute()

# 5. 用 INFO 观察命令量与网络
127.0.0.1:6379> INFO stats
# total_net_input_bytes:...
# instantaneous_ops_per_sec:...

# 6. 验证 Pipeline 不保证原子性
# 客户端 A：管道里连发 100 条 SET
# 客户端 B：在管道执行期间读同一个 key
# → B 可能读到「执行到一半」的中间状态，这是允许的

第 6 步是关键实验：它不是「偶发问题」，而是官方明确不保证的行为。

Java 侧怎么落地：executePipelined 的四个要点

  1. pom 只引 starter，管道是客户端行为，不需要额外依赖。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. 用 executePipelined，回调里只发命令、不读结果（回调的返回值必须是 null，结果由框架按顺序收集）：
List<Object> res = stringRedisTemplate.executePipelined((RedisCallback<Object>) conn -> {
    for (String k : keys) conn.get(k.getBytes(StandardCharsets.UTF_8));
    return null;                       // 千万不要在这里 get 结果
});

  1. 先比较「能不能用批量命令」：同类型同结构优先 MGET/MSET/HMGET，一条命令比 100 条 GET 省的是命令调度与协议开销；管道只解决 RTT。

  2. 分批：500–1000 条一批，或按字节切（maxBytes / avgValueSize），一批的预期执行时间控制在几十毫秒内。

for (List<String> batch : partition(keys, 800)) {
    List<Object> r = stringRedisTemplate.executePipelined((RedisCallback<Object>) conn -> {
        batch.forEach(k -> conn.get(k.getBytes()));
        return null;
    });
    handle(batch, r);                  // 逐条判断，某条失败不影响其他
}

  1. 管道里禁止阻塞命令（BRPOP/BLPOP）：它会让整条连接在服务端挂起到超时，管道里后面的命令都发不出去。

  2. Cluster 下按节点分组：管道不是一个连接发全部，而是按 key 所在节点拆分；带多 key 的命令仍要同槽（hash tag），否则 CROSSSLOT。

七、常见坑（官方明确说明的限制）

  1. 以为 Pipeline 提升的是服务端性能。服务端执行时间一分没少，省的是 RTT。
  2. 以为 Pipeline 有原子性。中间可能插入其他客户端的命令；要原子请包 MULTI 或用 Lua。
  3. 一次塞太多。客户端与服务端都要缓冲全部请求与回复，容易把内存顶上去，甚至触发 maxmemory 淘汰。
  4. 用 Pipeline 替代批量命令。100 个 GET 打包不如 1 个 MGET，后者省掉命令调度与协议头。
  5. 在 Pipeline 里塞慢命令。整个管道是一次大请求，主线程要连续处理完，慢命令会把延迟放大。
  6. Pipeline 中用 BRPOP 这类阻塞命令。阻塞命令会卡住整个管道，后续命令全部等它。
  7. Cluster 下跨槽。Pipeline 里的 key 分散在多个节点时，客户端要自己按节点拆分管道，否则会收到大量 MOVED。
  8. 把批大小写死成 10 万。应按「条数 + 字节 + 预期耗时」三个维度设上限，而不是只看条数。

版本差异（8.x 标注）

Pipeline 是客户端协议层的技巧，服务端不需要任何配置；7.x 与 8.x 行为一致。差异只在客户端库的实现细节（如自动分片、自动重试）。

依据：https://redis.io/docs/latest/develop/using-commands/pipelining/

八、课后小结

  • Pipeline 把 N 次 RTT 压成 1 次，服务端执行时间不变；
  • 收益与 RTT、命令数成正比，RTT 低或命令慢时收益有限；
  • 批量命令（MGET/MSET）优于 Pipeline，Pipeline 优于逐条；
  • 不保证原子性，要原子包 MULTI 或改用 Lua；
  • 分批按条数 + 字节 + 预期耗时三个维度设限；
  • Cluster 下需要按节点拆分管道。

九、思考题

  1. 1ms RTT、1000 条命令，逐条与 Pipeline 的时间差是多少？如果 RTT 是 0.1ms 呢？

    参考回答：1ms RTT 时，逐条 ≈ 1000×(1ms+exec)，管道 ≈ 1ms+1000×exec，差约 999ms（接近 1 秒）。RTT 0.1ms 时差约 99.9ms，收益小一个数量级——管道省的就是 N×RTT 里的 (N-1) 份。

  2. 为什么 100 个 GET 打包，不如 1 个 MGET？省掉的具体是什么开销？

    参考回答：MGET 是一条命令，服务端一次遍历完成；省掉的是 100 次命令调度（事件循环的读/解析/执行/写回复各 100 轮）、100 份协议头，以及客户端 100 次回复解析。管道只是把 RTT 压成一次，命令数不变。

  3. Pipeline 里放一条 BRPOP 会发生什么？为什么？

    参考回答：整条连接会在服务端进入阻塞态直到超时（或来数据），管道里它之后的命令都排在后面发不出去，客户端表现为「管道卡住」。所以阻塞命令必须单独用一条连接。

  4. Cluster 下把 1000 个不同槽的 key 塞进一个管道，客户端会遇到什么？怎么改？

    参考回答：管道会被按节点拆分重发，出现大量 MOVED 跟进；带多 key 的单条命令还会 CROSSSLOT 失败。改法：按槽/节点分组各发一条管道，或用 hash tag 把相关 key 收进同一槽。

  5. 你的导入任务要灌 500 万条数据，批大小怎么定？给出三个约束条件。

    参考回答：①条数：500–1000 条/批，保证一批在主线程上跑完只用几毫秒；②字节：单批请求体控制在几 MB 内（大 value 时按字节算而不是条数）；③耗时：一批预期执行不超过几十毫秒，否则抬高其他客户端延迟。另外失败重试必须幂等，且避开业务高峰。
