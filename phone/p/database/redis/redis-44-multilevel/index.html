多级缓存：本地 + Redis + 库

L1 进程内、L2 Redis、数据库的三级链路与失效传播｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 画出「请求 → L1 → L2 → 库」的三级链路，并说清每一层挡什么；
  2. 给 L1 设硬上限与短 TTL，而不是把它当成第二个 Redis；
  3. 用 Pub/Sub 或 tracking 实现「多实例 L1 失效广播」，并知道广播丢失时靠什么兜底。

二、前置知识

RD39（缓存模式）、RD37（Pub/Sub）、RD41（一致性窗口）、RD12（淘汰策略）。这一讲是把「一层缓存」扩成「三层」，核心矛盾从「一致性」变成「多副本一致性」。

三、理论讲解（官方定义）

Redis 官方文档本身只描述 Redis 这一层；「多级缓存」是架构实践。官方能给的最直接支撑是**客户端缓存（client-side caching）**这一机制：

Client-side caching is a technique used to create high performance services. It exploits the memory available on application servers … Redis tracks what keys a client has cached … and sends invalidation messages when those keys change.

—— https://redis.io/docs/latest/develop/clients/client-side-caching/

也就是说：官方承认「进程内缓存 + Redis 负责失效通知」这一模式，并提供了 tracking 机制（RD45 详讲）。除此之外的分层设计（TTL 多长、容量多大、如何预热）由业务决定。

规律是越靠近请求越快，容量越小、越容易不一致。多级缓存不是为了「更快」而存在，而是为了「用最便宜的一层挡住绝大部分请求」。

四、原理拆解

1. 三级链路的读路径

GET 请求
 → L1 命中：直接返回（不产生任何网络 IO）
 → L1 未命中 → L2 命中：回填 L1，返回
 → L2 未命中 → 查库：回填 L2 与 L1，返回

每一层都要有「回填上限」：同一时刻允许多少个请求穿透到下一层。没有这个上限，L1 的一次整体失效会把全部流量瞬间打到 L2，再打到库——这就是「多级缓存的雪崩」（RD40）。

2. L1 的三条铁律

  • 容量必须硬上限：如 Caffeine 的 maximumSize、Go 的 LRU 容量。没有上限的进程内 map 就是内存泄漏。
  • TTL 必须短：秒级。L1 是「最快也最旧」的一层，它的正确性完全依赖 TTL 兜底。
  • 只放可重建的数据：进程重启即清空，绝不能存「只有这一份」的数据。

3. 失效怎么传播

写库成功
 → 删 L2（Redis 中的那个 key）
 → 广播「key 失效」→ 各实例收到后删自己的 L1
 → 下一次读从 L2/库重新加载

广播载体有两种：

  • Pub/Sub（RD37）：实现简单，但消息不持久、断线期间的消息会丢；
  • client-side caching 的 tracking（RD45）：由 Redis 主动推送失效，语义更贴合这件事，但要求 RESP3 / 客户端支持。

无论用哪种，都必须假设「广播会丢」，因此 L1 的短 TTL 是最后兜底。想靠广播做到 L1 强一致，代价会吃掉多级缓存的全部收益。

4. 为什么不干脆只用 L2

因为 L2 也有网络往返（哪怕只有 0.3ms）。当单机 QPS 达到几万、且 90% 是同一个热点 key 时，这 0.3ms 乘以请求数就是 Redis 的带宽与连接压力。L1 的价值就在「把不产生网络 IO 的那部分请求吃掉」。

反过来，如果 QPS 不高、热点不集中，多级缓存只会增加「一致性传播」的复杂度而收益很小——这时只用 L2 更划算。

五、场景说明

  1. 首页/详情页热点：L1 挡重复读，L2 挡跨实例重复读；
  2. 配置与字典表：数据量小、变更少，L1 长 TTL + 变更时广播失效；
  3. 商品库存：不适合 L1（多实例不一致），只做 L2，且关键读绕缓存；
  4. 不适合：低 QPS、强一致、写多读少的业务。

六、示例代码/实操步骤

# L2（Redis）侧的读写与失效
127.0.0.1:6379> GET cfg:shop:1
(nil)
127.0.0.1:6379> SET cfg:shop:1 '{"open":true}' EX 300
OK

# 失效广播：写库后广播给所有实例
127.0.0.1:6379> PUBLISH cache:invalidate "cfg:shop:1"
(integer) 3                    # 有 3 个实例在线订阅

# 订阅端（各应用实例启动时执行）
127.0.0.1:6379> SUBSCRIBE cache:invalidate
1) "subscribe"
2) "cache:invalidate"
3) (integer) 1
# 收到消息后：删除本地 L1 中的 cfg:shop:1

# 观察 L2 的压力（判断 L1 是否真的挡住了流量）
127.0.0.1:6379> INFO stats
# keyspace_hits / keyspace_misses
127.0.0.1:6379> INFO clients
# connected_clients:...

L1 用 Caffeine 的关键配置（Java 示意）：

Cache<String, String> l1 = Caffeine.newBuilder()
    .maximumSize(100_000)          // 硬上限，必须有
    .expireAfterWrite(Duration.ofSeconds(5))  // 短 TTL，兜底广播丢失
    .build();

七、常见坑（官方明确说明的限制）

  1. L1 不设上限。进程内 map 无限增长，最终 OOM 或被容器杀掉。
  2. L1 TTL 设成分钟级。广播一丢，多个实例就会长期返回不同的值，排查极其困难。
  3. 以为 Pub/Sub 可靠。官方明确：Pub/Sub 是「至多一次」（fire and forget），订阅端断线期间的消息不会补发。
  4. 只删 L2 忘了广播 L1。写完后某些实例仍返回旧值，看起来像「偶发脏数据」。
  5. 每层都不设穿透上限。一次 L1 整体失效 = 全量请求打到 L2，再打到库。
  6. 把不可重建的数据放 L1。进程重启就丢，且多实例之间逻辑不一致。
  7. 忽略 Redis 内存策略。L2 未配 maxmemory 时不会淘汰，内存上涨到 OOM 才暴露（官方淘汰机制需要显式配置）。
  8. 在 L1 存大对象。进程内内存是「业务堆内存」的一部分，大对象会推高 GC 压力，反而拖慢请求。

版本差异（8.x 标注）

多级缓存是架构模式，与版本无关。8.x 在客户端缓存与集群能力上有持续增强，可作为失效广播的更优载体；PUBLISH/SUBSCRIBE 语义与 7.4 一致。

依据：https://redis.io/docs/latest/develop/interact/pubsub/

八、课后小结

  • 三级链路：L1 本地（纳秒）、L2 Redis（毫秒）、库（十几毫秒）；
  • L1 三铁律：硬上限、短 TTL、只放可重建数据；
  • 失效传播：删 L2 → 广播 → 各实例删 L1；广播会丢，靠短 TTL 兜底；
  • 每层都要有穿透上限，否则一层失效就是全链路雪崩；
  • 低 QPS 场景不要上多级缓存，收益不抵复杂度。

九、思考题

  1. 你的业务里，一个 key 平均每秒被读多少次才值得放进 L1？给出估算方式。
  2. Pub/Sub 断线 30 秒期间发生的变更，订阅端什么时候才能看到？靠什么兜底？
  3. 如果 L1 TTL 从 5 秒改成 60 秒，会带来什么好处与什么风险？
  4. 三个实例 L1 内容不一致，用户刷新页面看到不同结果——你会怎么定位？
  5. 「每层设穿透上限」具体设在哪？入口限流、并发信号量，还是连接池？
