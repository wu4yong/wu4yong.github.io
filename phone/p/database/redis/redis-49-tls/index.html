TLS 与安全加固

服务端证书三件套、客户端配合项与五条加固动作｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 用 tls-port + 三个证书文件把 Redis 的明文端口关掉；
  2. 说清 tls-auth-clients 双向认证对客户端意味着什么；
  3. 说清 protected-mode 到底在什么条件下才生效，不再把它当万能防线。

二、前置知识

RD48（ACL 决定「谁能连」）、RD03（配置项与 CONFIG SET）。TLS 解决「链路上被看见」，ACL 解决「连进来能干什么」，两者不可互相替代。

三、理论讲解（官方定义）

官方 TLS 支持文档的核心表述（原文要点）：

Redis supports TLS … to enable it, use tls-port instead of port … you must specify tls-cert-file, tls-key-file, and optionally tls-ca-cert-file …

Clients can be required to authenticate with a certificate by setting tls-auth-clients yes.

For replication and cluster bus, use tls-replication yes and tls-cluster yes.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/security/encryption/

关于 protected-mode，官方在配置说明中写得很清楚（原文要点）：

Protected mode is a layer of security protection … When protected mode is enabled and no password is set and no bind address is configured, Redis only replies to queries from the loopback interfaces.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/security/

注意这句话的两个前提：「没有密码」且「没有 bind 地址」。 只要你 bind 0.0.0.0 或设了密码，它就不再起作用。这是生产上最常见的误解。

四、原理拆解

1. 加密链路的三段

客户端 ──TLS 握手──> Redis（服务端）
   ① 客户端校验服务端证书（防中间人）
   ② 服务端校验客户端证书（tls-auth-clients yes 时）
   ③ 之后所有 RESP 数据在 TLS 通道内传输

三段里最容易漏的是第 ② 步：只配了服务端证书、没要求客户端证书，等于「任何人都能连上来握手」，只是链路上看不见内容。

2. 集群与哨兵要单独打开加密

tls-replication yes   # 主从复制也走 TLS
tls-cluster yes       # 集群总线（bus 端口）也走 TLS

漏了这两个，会出现「客户端能连但主从同步失败 / 集群节点互相看不见」——这类故障的现象和网络故障高度相似，排查很容易走偏。

3. 五条加固清单，按优先级

动作 作用 常见错误
bind 内网地址 只在指定网卡上监听 写 0.0.0.0 等于全网可达
ACL / requirepass 认证 用弱密码，或干脆留空
禁用危险命令 限制 keys/flushall/config 用 rename-command 而非 ACL
安全组 / 防火墙 网络层隔离 只靠 Redis 自身防护
TLS 链路加密 只在公网开，内网明文

网络层隔离是最有效的一条：把 6379 只对应用网段开放，绝大多数「Redis 被入侵」事件从源头就不会发生。

4. 证书运维：最容易忽略的定时炸弹

证书有有效期。生产上「突然全站连不上 Redis」的经典原因之一，就是证书过期。要做的三件事：

  • 证书到期时间进入监控（提前 30 天告警）；
  • 轮换流程演练过（新证书 + 重启或 CONFIG SET 热加载）；
  • 客户端信任链（CA）也同步更新，别只换服务端。

五、场景说明

  1. 跨机房/跨 VPC 访问：必须 TLS，链路上可能经过不可控网络；
  2. 云托管 Redis：多数云厂商默认要求 TLS，且要求客户端证书；
  3. 同机同网段：TLS 可选，但仍建议保留 ACL + 内网 bind；
  4. 合规场景（等保、金融）：TLS + 双向认证 + 审计日志通常都是硬要求。

六、示例代码/实操步骤

# redis.conf 中的 TLS 与加固片段
port 0                      # 关掉明文端口
tls-port 6379
tls-cert-file /etc/redis/tls/redis.crt
tls-key-file  /etc/redis/tls/redis.key
tls-ca-cert-file /etc/redis/tls/ca.crt
tls-auth-clients yes        # 要求客户端证书
tls-replication yes         # 主从复制也加密
tls-cluster yes             # 集群总线也加密

bind 10.0.1.10              # 只监听内网网卡
protected-mode yes
aclfile /etc/redis/users.acl
# 用 TLS 连接（客户端带 CA 与客户端证书）
$ redis-cli --tls --cacert /etc/redis/tls/ca.crt \
            --cert /etc/redis/tls/client.crt --key /etc/redis/tls/client.key \
            -h 10.0.1.10 -p 6379 PING
PONG

# 确认加密是否真的生效（看 INFO 的 tls 段）
127.0.0.1:6379> INFO stats
# total_connections_received:...
127.0.0.1:6379> INFO persistence
# 用 CLIENT LIST 观察连接类型
127.0.0.1:6379> CLIENT LIST
# id=1 addr=10.0.1.20:53124 ... flags=N ...

# 检查证书有效期（运维必做）
$ openssl x509 -in /etc/redis/tls/redis.crt -noout -dates

# 验证危险命令是否已被 ACL 挡住
127.0.0.1:6379> FLUSHALL
(error) NOPERM this user has no permissions to run the 'flushall' command

七、常见坑（官方明确说明的限制）

  1. 以为 protected-mode 是万能防线。官方明确：只有在「无密码且无 bind」时才限制为回环地址。
  2. bind 0.0.0.0 + 空密码 + 公网 IP。这是被入侵的标准配方。
  3. 只开 tls-port 忘了 port 0。明文端口仍在监听，加密形同虚设。
  4. tls-auth-clients yes 但客户端没配证书。握手阶段就失败，报错常被误认为「证书路径错」。
  5. tls-replication / tls-cluster 漏配。客户端正常、主从不同步、集群节点互相看不见。
  6. 证书过期无监控。到期那天全站连接失败，且故障现象与「网络不通」高度相似。
  7. 用 rename-command 禁命令。官方建议用 ACL；改名会破坏客户端与工具链（RD48）。
  8. 忽略 CONFIG SET 的热加载边界。TLS 证书可以热更新，但部分参数（如端口）必须重启，改之前查文档。

版本差异（8.x 标注）

TLS 支持自 6.0 引入，tls-auth-clients、tls-replication、tls-cluster 在 7.4 与 8.x 语义一致。8.x 在默认配置与许可上有调整，证书配置方式未变。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/security/encryption/

八、课后小结

  • TLS 三件套：tls-port + 证书 + 私钥，配 tls-ca-cert-file 校验对端；
  • 双向认证靠 tls-auth-clients yes，主从与集群要单独开 tls-replication / tls-cluster；
  • 加固五条：bind、ACL、禁危险命令、安全组、TLS；
  • protected-mode 只在「无密码 + 无 bind」时生效，不是主力防线；
  • 证书有效期必须进监控。
