容量规划与压测

内存怎么估、压测怎么做、余量怎么留｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 用「key 数 × 单 key 开销」估算内存，并用 MEMORY USAGE 抽样校准；
  2. 设计一次贴近生产的压测（真实 value 大小 + 真实读写比例）；
  3. 说出为什么单实例内存不该无限增大，以及余量该留多少。

二、前置知识

RD26（SDS 与 redisObject 的内存开销）、RD27（dict）、RD31（碎片）、RD14（RDB 与 fork）。容量规划不是「拍个数」，而是把这些结构开销算进去。

三、理论讲解（官方定义）

官方内存优化文档给出的关键事实（原文要点）：

Small hashes, lists, sets and sorted sets are stored in a very memory efficient way … using a special encoding … up to a configured number of elements and value size.

Using 32-bit instances reduces memory usage … but limits the max memory to 4GB.

—— https://redis.io/docs/latest/develop/reference/optimization/

以及 MEMORY USAGE 的官方说明（原文）：

MEMORY USAGE key [SAMPLES count] reports the number of bytes that a key and its value require to be stored in RAM.

—— https://redis.io/docs/latest/commands/memory-usage/

关于 fork 与 COW，官方在持久化文档中说明：BGSAVE / AOF 重写通过 fork 创建子进程，写时复制（copy-on-write）会让父进程在子进程运行期间的写入产生额外内存占用（依据：https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/）。这就是「余量」的来源之一。

四、原理拆解

1. 内存估算的公式

总内存 ≈ Σ(每个 key 的 key 字节 + value 字节 + 结构开销)
结构开销 = redisObject 头 + SDS 头 + dictEntry + 过期字典条目 + 分配器碎片

实操不建议手算每一项，而是分两步：

① 抽样：MEMORY USAGE 取 100–1000 个典型 key，求平均
② 放大：平均值 × key 总数 × 1.1（留结构差异）

2. 三类容易被漏算的内存

  • 复制缓冲区：repl-backlog-size 默认 1mb，但主从延迟大时需要调大；
  • 客户端缓冲区：每个连接的输入/输出缓冲，大 value + 慢客户端会放大；
  • fork 期间的 COW：BGSAVE 期间父进程的写入会复制页，峰值可能是平时的 1.2–2 倍。

3. 压测的三条真实性要求

① 真实 value 大小：10 字节的假数据测不出带宽与序列化成本
② 真实读写比例：只压读会低估淘汰与 AOF 压力
③ 真实网络路径：跨机房压测和本机压测结论差一个数量级

压测要看的是 P99、evicted_keys、used_memory 曲线、fork 延迟，而不是平均 QPS 一个数。

4. 两条容量红线

  • 单实例内存 10–16GB 上限：RDB fork 的 COW 成本、全量同步的传输量、故障恢复时间都随内存线性上升。超过这个量级，应该分片而不是继续加内存。
  • 余量 ≥ 30%：要同时覆盖「碎片率 1.5」「fork 期间写放大」「复制缓冲区增长」。只留 10% 的实例，在大促写入高峰时就会开始淘汰或写失败。

五、场景说明

  1. 新业务上线：先按「日均 key 数 × 增长系数」估，再压测验证；
  2. 大促扩容：按峰值 QPS 与峰值 key 数重算，不按平均值；
  3. 迁移上云：目标实例内存 = 源实例 used_memory × 1.3（含碎片差异）；
  4. 不适合：把「当前够用」当成结论——容量规划的对象永远是峰值。

六、示例代码/实操步骤

# 1. 抽样估算：看典型 key 的真实占用
127.0.0.1:6379> MEMORY USAGE user:1001
(integer) 320
127.0.0.1:6379> MEMORY USAGE order:2001 SAMPLES 5
(integer) 1840

# 2. 看整体内存与碎片
127.0.0.1:6379> INFO memory
# used_memory_human:3.21G
# used_memory_peak_human:3.66G
# mem_fragmentation_ratio:1.42
# maxmemory_human:4.00G

# 3. 看 key 数量（估算的基础）
127.0.0.1:6379> DBSIZE
(integer) 1240333
127.0.0.1:6379> INFO keyspace
# db0:keys=1240333,expires=980211,avg_ttl=...

# 4. 检查编码是否退化（小对象应使用紧凑编码）
127.0.0.1:6379> OBJECT ENCODING user:1001
"embstr"
127.0.0.1:6379> OBJECT ENCODING big:hash
"hashtable"                   # 超过阈值后退化为 hashtable，内存明显上升

# 5. 压测（redis-benchmark，注意用真实 value 大小）
$ redis-benchmark -h 10.0.1.10 -p 6379 -n 2000000 -c 50 \
  -r 1000000 -d 200 -t get,set --latency
# -d 200 表示 value 200 字节；--latency 输出延迟分布

# 6. 压测期间同步观察（另一个终端）
127.0.0.1:6379> INFO stats
# instantaneous_ops_per_sec / evicted_keys / keyspace_hits

# 7. 确认复制与持久化的额外开销
127.0.0.1:6379> CONFIG GET repl-backlog-size
# 1mb
127.0.0.1:6379> INFO persistence
# rdb_last_bgsave_time_sec / aof_rewrite_in_progress

七、常见坑（官方明确说明的限制）

  1. 用平均 QPS 算容量。峰值通常是平均的 3–10 倍，按平均规划必然不够。
  2. 压测用假数据（10 字节 value）。带宽、序列化、淘汰压力全被低估。
  3. 忽略结构开销。只算 key+value 字节，实际 used_memory 会高出 30%–100%。
  4. 忘记碎片的余量。mem_fragmentation_ratio 到 1.5 时，同样数据要多占 50% 内存。
  5. 单实例无限加内存。fork 的 COW、全量同步、故障恢复都会随之恶化；超过 10–16GB 应考虑分片。
  6. 不留 fork 余量。BGSAVE 期间写入放大，最容易在「内存已经 90%」的实例上触发写失败。
  7. 低效编码没发现。hash/zset 元素超阈值后退化为 hashtable，内存成倍上涨（RD28 的阈值）。
  8. 压测不观察 evicted_keys。压测通过但已经在淘汰，等于数据在悄悄丢。

版本差异（8.x 标注）

MEMORY USAGE 与内存优化建议在 7.4 与 8.x 语义一致。8.x 在集群与大内存场景有优化，但「单实例内存不宜过大」这条工程红线不变。

依据：https://redis.io/docs/latest/commands/memory-usage/

八、课后小结

  • 估算 = 抽样 MEMORY USAGE × key 总数 × 1.1；
  • 别漏算：复制缓冲、客户端缓冲、fork 期间的 COW；
  • 压测要真实：value 大小、读写比例、网络路径；
  • 看 P99 与 evicted_keys，不只看平均 QPS；
  • 单实例 10–16GB、余量 ≥ 30%，超出就分片。

九、思考题

  1. MEMORY USAGE 抽样 500 个 key 得到平均 320 字节，key 总数 120 万，估算总内存是多少？还要加什么？
  2. 为什么压测只压读会低估风险？
  3. used_memory 70% 但 evicted_keys 在涨，可能是什么原因？
  4. fork 期间的写放大最多会占多少内存？怎么验证？
  5. 一个 24GB 的实例你会怎么处理？直接扩到 48GB 还是分片？理由？
