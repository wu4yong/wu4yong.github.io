穿透、击穿与雪崩

三种缓存异常现象的根因、典型来源与对应解法｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 用一句话区分穿透、击穿、雪崩，并说出各自的根因；
  2. 为每种现象给出至少两种解法，并说清解法之间的取舍；
  3. 用 INFO stats 里的 keyspace_misses 判断线上到底发生的是哪一种。

二、前置知识

RD39（缓存模式）、RD12（过期与淘汰）。这一讲是 M7 里「问题诊断」的第一讲：这三个名词经常被混用，但它们对应的根因、监控指标和解法完全不同。

三、理论讲解（官方定义）

这三个概念都不是 Redis 官方文档定义的术语，而是缓存工程的通用命名。Redis 官方文档能提供的支撑是机制层面的说明：

过期删除：Redis 采用「惰性删除 + 定期抽样删除」，key 到期后并不保证立刻消失，而是下次访问时发现过期才删，或被定期任务抽样删掉。

—— https://redis.io/docs/latest/develop/reference/keyspace-notifications/（keyspace 事件与过期相关说明）

淘汰：当内存达到 maxmemory 时，按 maxmemory-policy 淘汰 key。

—— https://redis.io/docs/latest/develop/reference/eviction/

理解这两条，才能明白为什么「同一时刻大批 key 失效」是可能发生的：过期不是均匀发生的。

三个现象的通用定义：

  • 穿透（penetration）：请求的 key 在缓存与库里都不存在，缓存永远不命中；
  • 击穿（breakdown）：单个热点 key 失效的瞬间，大量并发同时回源；
  • 雪崩（avalanche）：大批 key 同时失效，或缓存整体不可用，流量全部压到库上。

四、原理拆解

1. 穿透为什么发生

请求 key=999999（不存在）
  → GET 未命中
  → 查库，库里也没有
  → 不写缓存（因为没数据可写）
  → 下次同样的请求，重复上面三步

它的本质是「缓存无法缓存「不存在」」。来源通常是爬虫遍历 ID、攻击者构造随机 key、上游传错参数。

2. 击穿为什么发生

热点 key 到期（或被人为删除）
  → 瞬间 N 个并发全部 GET 未命中
  → N 个请求同时查库

关键在于「N 个请求里只需要 1 个去查库」，其余应该等它回填。所以解法的核心是「互斥」：让第一个请求去重建，其余等待或读旧值。

3. 雪崩为什么发生

两种触发方式：

  • 时间性雪崩：一批 key 在同一时刻被写入、TTL 又相同，于是同一时刻集体过期；
  • 容量性雪崩：Redis 实例宕机、主从切换、集群大面积故障，缓存层整体消失。

前者靠「TTL 加随机抖动 + 分批预热」解决；后者靠「多级缓存 + 熔断限流 + 数据库保护」解决，不是靠改缓存代码能解决的。

5. 互斥重建的标准写法

# 1. 未命中，先抢锁（锁 key 与被缓存的 key 分开）
SET lock:user:1001 1 NX PX 5000
# 2. 抢到锁 → 查库 → 回填缓存 → 释放锁
# 3. 没抢到 → 短暂 sleep 后重试 GET（或直接返回降级值）

注意第 2 步里「拿到锁后必须再查一次缓存」：在你抢锁的时间里，别人可能已经把值写进去了。少了这次二次检查，就是「串行回源」，热点 key 下延迟会明显上升。

五、场景说明

  1. 商品详情页 ID 遍历攻击：典型穿透，用空值缓存 + 网关限流；
  2. 首页推荐的聚合 key：典型击穿，用互斥重建 + 热点 key 不设过期、后台定时刷新；
  3. 大促开场瞬间：典型时间性雪崩，TTL 加抖动 + 提前预热；
  4. Redis 集群主从切换的 30 秒：典型容量性雪崩，靠本地缓存 + 熔断撑过去（RD44、RD47）。

六、示例代码/实操步骤

# 现象一：穿透。查看未命中率
127.0.0.1:6379> INFO stats
# keyspace_hits:998765
# keyspace_misses:120034        ← 未命中数持续增长，且库里也查不到

# 解法 A：空值缓存（短 TTL，避免长期占位）
127.0.0.1:6379> SET user:999999 "__NULL__" EX 60
OK

# 解法 B：布隆过滤器（Redis 提供 Bloom 模块；无模块时用 SETBIT 近似）
127.0.0.1:6379> BF.ADD user_filter 1001
(integer) 1
127.0.0.1:6379> BF.EXISTS user_filter 999999
(integer) 0                    # 一定不存在 → 直接返回，不查库

# 现象二：击穿。互斥重建
127.0.0.1:6379> SET lock:hot:home 1 NX PX 5000
OK                             # 抢到锁的唯一请求去查库
# ... 查库、回填 ...
127.0.0.1:6379> DEL lock:hot:home
(integer) 1

# 现象三：雪崩的预防 —— 写入时就给 TTL 加抖动
127.0.0.1:6379> SET cfg:shop:1 '...' EX 3600
# 实际代码里 TTL 取 3600 + random(0, 600)，把过期时刻摊开

# 观察 key 的生命周期（排查「是不是同时过期」）
127.0.0.1:6379> TTL cfg:shop:1
(integer) 3598
127.0.0.1:6379> DBSIZE
(integer) 120345

七、常见坑（官方明确说明的限制）

  1. 空值缓存不设 TTL 或设太长。用户在别处创建了这条数据后，缓存里仍是「不存在」，被挡住很久。
  2. 布隆过滤器当「删除」用。官方 Bloom 模块的过滤器不支持删除（只能重建），把已存在的数据删掉后它会持续误判。
  3. 互斥锁没有超时。持有锁的请求卡死，其他请求全部阻塞，比直接查库更糟。
  4. 拿到锁不二次检查缓存。退化成串行回源，热点 key 下 P99 飙升。
  5. 以为 EXPIRE 是精确到点失效。官方机制是惰性 + 定期抽样，大量 key 同一时刻过期时，删除本身也会占用主线程时间。
  6. 雪崩只做缓存侧优化。数据库前的连接池上限、入口限流、熔断才是最后一道防线；缓存侧优化只是把问题延后。
  7. 监控只看命中率不看回源 QPS。命中率 99% 但总量极大时，1% 的回源也可能打挂库；要看的是「库上的 QPS」。
  8. 热点 key 用「永不过期」但忘了更新。数据变了没人刷新，缓存里就是永久旧值。

版本差异（8.x 标注）

Bloom 过滤器属于 Redis Stack / RedisBloom 模块能力，不在 Redis 7.4 核心命令集内；8.x 的模块分发方式有调整，但 BF.ADD / BF.EXISTS 语义不变。若环境无模块，可用 SETBIT/GETBIT 自行实现位图过滤。

依据：https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/

八、课后小结

  • 穿透 = key 根本不存在；击穿 = 单个热点 key 失效；雪崩 = 大批 key 同时失效或缓存整体不可用；
  • 穿透靠「空值缓存 + 布隆过滤器 + 参数校验」；
  • 击穿靠「互斥重建 + 逻辑过期」，锁必须有超时且要二次检查；
  • 雪崩靠「TTL 抖动 + 预热 + 多级缓存 + 熔断限流」；
  • 判断线上是哪种，先看 keyspace_misses 与「库上的 QPS」，别看感觉。

九、思考题

  1. 一个「不存在的 ID」被反复请求，空值缓存和布隆过滤器各自的代价是什么？
  2. 互斥重建时，为什么拿到锁后要再查一次缓存？不查会发生什么？
  3. 逻辑过期读到旧值，业务能接受吗？怎么决定「能」还是「不能」？
  4. TTL 抖动只能缓解时间性雪崩，容量性雪崩怎么办？
  5. 如果让你给「缓存层不可用」设计一个 30 秒的兜底方案，你会写哪三条？
