Redis Functions：把脚本变成可管理的库

FUNCTION LOAD → 注册 → FCALL → 随持久化保存的四步，以及四条使用边界｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 Functions 与 Lua 脚本的三点实质差别（命名、持久化、复制内容）；
  2. 用 FUNCTION LOAD + FCALL 完成一次「注册库 → 调用函数」的完整流程；
  3. 判断一个逻辑该用脚本、Functions 还是事务，并知道 Functions 的边界在哪。

二、前置知识

RD34（Lua 脚本与原子性）。Functions 是脚本的「升级形态」：同样跑在 Lua 引擎里，但是有名字、随数据一起持久化。

三、理论讲解（官方定义）

官方对 Functions 的定位（原文）：

Redis Functions are an evolution of EVAL scripts … functions are … persisted … and managed as part of the dataset.

—— https://redis.io/docs/latest/develop/programmability/functions-intro/

以及注册方式（原文要点）：

A library is … a piece of code that registers one or more functions … loaded with FUNCTION LOAD.

—— 同上

两条定性：

  • Functions 是「数据集的一部分」：随 RDB/AOF 一起保存与复制，重启后仍在；
  • 它仍是 Lua 引擎 + 单线程执行，所以原子性与不可回滚的边界和脚本完全一致。

四、原理拆解

1. 从加载到调用

FUNCTION LOAD "#!lua name=mylib\n redis.register_function('myfunc', function(keys, args) ... end)"
  → 解析 shebang 头，注册库与函数
FCALL myfunc 1 mykey arg1
  → 按名字查找函数，numkeys 之后是 key

第 7 行的 #!lua name=mylib 是库声明头，不是注释。缺了它 FUNCTION LOAD 直接失败——这是最常见的第一个坑。

2. 与脚本的三点实质差别

维度
EVAL 脚本
Functions
标识
SHA1（内容哈希）
库名 + 函数名（可读、可版本化）
生命周期
进程内缓存，重启/flush 丢失
随 RDB/AOF 持久化，重启仍在
复制内容
脚本或效果（7.0 起默认效果）
调用名与参数（更省、更确定）
管理
SCRIPT FLUSH 一把清
FUNCTION LIST/DELETE/FLUSH 按库操作

「随数据集保存」带来一个副作用：加载 RDB 时函数库也会被恢复。所以如果你从别的环境拷了一份 RDB，里面的函数库会一起过来——这在迁移时要留意。

3. 调用与参数

FCALL myfunc 1 key1 arg1 arg2
        ↑     ↑      ↑
      函数名 numkeys  KEYS / 之后是 ARGV

与 EVAL 一样，numkeys 决定前几个参数是 key。key 必须是通过这里传入，Cluster 下服务端要靠它校验同槽。

4. 管理命令

命令
用途
FUNCTION LIST
列出所有库与函数（含 flags、引擎）
FUNCTION DUMP
导出所有库的二进制快照
FUNCTION RESTORE
从快照恢复
FUNCTION DELETE <lib>
删除某个库
FUNCTION FLUSH
清空所有库（危险操作）
FUNCTION STATS
调用次数、耗时等运行状态

FUNCTION FLUSH 没有任何确认机制，一执行所有函数消失，正在调用的客户端立刻 ERR unknown function。生产上必须当成高危命令。

EVAL 与 Functions 在标识、生命周期、复制内容、管理方式上的四点差别，FCALL 的参数结构，以及 FUNCTION FLUSH 的高危性｜依据 Functions 文档自绘

五、场景说明

  1. 团队共用的原子逻辑（扣库存、发券）：注册成库，所有服务统一调用，避免各自写脚本；
  2. 需要跨重启保留的逻辑：不希望每次发布都重新 SCRIPT LOAD；
  3. 审计与版本管理：库名 + 函数名可读，FUNCTION LIST 一眼看出线上有哪些；
  4. 不适合：一次性调试脚本（EVAL 更快）、极短逻辑（Functions 的加载与治理成本不划算）。

六、示例代码/实操步骤

# 1. 加载一个库（注意 shebang 行必须存在）
127.0.0.1:6379> FUNCTION LOAD "#!lua name=mylib
redis.register_function('my_hset_if_absent', function(keys, args)
  if redis.call('EXISTS', keys[1]) == 1 then return 0 end
  redis.call('HSET', keys[1], args[1], args[2])
  return 1
end)"
"mylib"

# 2. 调用
127.0.0.1:6379> FCALL my_hset_if_absent 1 user:1 name alice
(integer) 1
127.0.0.1:6379> FCALL my_hset_if_absent 1 user:1 name bob
(integer) 0                 # 已存在，不覆盖

# 3. 查看库与函数
127.0.0.1:6379> FUNCTION LIST
1) 1) "library_name"
   2) "mylib"
   3) "engine"
   4) "LUA"
   5) "functions"
   6) 1) 1) "name"
         2) "my_hset_if_absent"
         3) "flags"
         4) (empty array)

# 4. 运行状态
127.0.0.1:6379> FUNCTION STATS
# running_script (nil)
# engines
#   LUA
#     libraries_count 1
#     functions_count 1

# 5. 删除库
127.0.0.1:6379> FUNCTION DELETE mylib
OK
127.0.0.1:6379> FCALL my_hset_if_absent 1 user:2 name x
(error) ERR Function not found

# 6. 导出与恢复（迁移用）
127.0.0.1:6379> FUNCTION DUMP
# 二进制快照
127.0.0.1:6379> FUNCTION RESTORE "<dump 内容>"
OK

# 7. 验证「随持久化保存」：执行 SAVE 后重启，函数仍在
127.0.0.1:6379> SAVE
OK
# 重启 redis-server 后：
127.0.0.1:6379> FUNCTION LIST
# 仍能看到 mylib

# 8. 危险操作：清空所有库
127.0.0.1:6379> FUNCTION FLUSH
OK

Java 侧怎么落地：把函数库随应用一起加载

Functions 的价值在「随数据集持久化」，落地时要把「加载」变成启动的一部分，而不是靠人手工敲。

  1. pom 只引 starter，Functions 没有专属 API，走底层 RedisCallback 即可。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. 函数库脚本放 resources/functions/inventory.lua，第一行必须是 shebang 库声明头：
#!lua name=inventory
redis.register_function('decr_stock', function(keys, args)
  local v = tonumber(redis.call('GET', keys[1]) or '0')
  if v - tonumber(args[1]) < 0 then return -1 end
  return redis.call('DECRBY', keys[1], args[1])
end)
  1. 启动时幂等加载（REPLACE 重复加载不报错），加载失败就让应用起不来，避免「代码有、Redis 没库」：
@Component
public class FunctionLoader implements ApplicationRunner {
    private final StringRedisTemplate redis;
    public FunctionLoader(StringRedisTemplate redis) { this.redis = redis; }

    @Override
    public void run(ApplicationArguments args) throws Exception {
        String lib = new String(new ClassPathResource("functions/inventory.lua")
                .getInputStream().readAllBytes(), StandardCharsets.UTF_8);
        redis.execute((RedisCallback<Object>) c -> c.execute(
                "FUNCTION".getBytes(), "LOAD".getBytes(), "REPLACE".getBytes(),
                lib.getBytes(StandardCharsets.UTF_8)));
    }
}
  1. 调用走 FCALL，key 通过 numkeys 传：
Long left = redis.execute((RedisCallback<Long>) c -> (Long) c.execute(
        "FCALL".getBytes(), "decr_stock".getBytes(), "1".getBytes(),
        "stock:1001".getBytes(), "1".getBytes()));
  1. 把 FUNCTION FLUSH 挡在应用之外：ACL 里不给业务账号这个命令，发布流程用 FUNCTION LIST 核对库名与函数名，迁移 RDB 前也先 FUNCTION LIST 看有没有带过来的陌生库。

七、常见坑（官方明确说明的限制）

  1. 漏掉 #!lua name= 头。FUNCTION LOAD 直接报错，这是最高频的失败原因。
  2. 以为 Functions 能回滚。原子性与脚本一致，报错后已执行的写保留。
  3. Cluster 下 key 跨槽。FCALL 会报 CROSSSLOT，必须用 hash tag 收敛（RD24）。
  4. FUNCTION FLUSH 无确认。一条命令清空线上所有库，属于高危操作，必须走变更流程。
  5. 把库当「代码仓库」。Functions 只是执行单元，没有版本回滚能力；想看历史得靠外部代码仓库。
  6. 升级时覆盖同名库。同名的 FUNCTION LOAD 会失败（除非 REPLACE），要么加 REPLACE，要么先 DELETE 再 LOAD——后者有一小段「函数不存在」的空窗。
  7. 以为引擎可以换。7.x 只有 LUA 引擎，官方虽预留了多引擎设计，但不要假设今天能上别的语言。
  8. 忽略内存。函数库与脚本缓存都占内存，且随 RDB 保存；库写太大（几百 KB 代码）会拖慢加载。

版本差异（8.x 标注）

Functions 自 7.0 引入，7.4 与 8.x 语义一致（FUNCTION LOAD / FCALL / FUNCTION LIST 等）。8.x 未新增引擎，差异主要在生态工具与许可条款。

依据：https://redis.io/docs/latest/develop/programmability/functions-intro/

八、课后小结

  • Functions 是脚本的进化形态：有库名与函数名、随 RDB/AOF 持久化、复制调用而非脚本体；
  • 加载必须带 #!lua name=<lib> 头，调用用 FCALL <fn> <numkeys> ...；
  • 原子性与不可回滚的边界和脚本完全一致；
  • 管理层命令：FUNCTION LIST/DUMP/RESTORE/DELETE/FLUSH/STATS；
  • FUNCTION FLUSH 是高危操作，无确认；
  • Cluster 下 key 必须同槽。

九、思考题

  1. Functions 与脚本的三点实质差别是什么？哪一点对「跨重启」最关键？

    参考回答：标识（SHA1 vs 库名+函数名）、生命周期（进程内缓存 vs 随 RDB/AOF 持久化）、复制内容（脚本或效果 vs 调用名与参数）。对跨重启最关键的是生命周期：Functions 跟着数据集走，重启后仍在，客户端不会遇到 NOSCRIPT。

  2. 为什么 FUNCTION LOAD 必须要 shebang 头？缺了会报什么？

    参考回答：#!lua name=mylib 是库声明头而不是注释，服务端靠它拿到库名并注册整个库。缺了会直接失败，报类似 ERR Missing library metadata 的错误。

  3. 「随数据集持久化」带来什么副作用？迁移 RDB 时会遇到什么？

    参考回答：函数库会跟着 RDB 一起被恢复。你从别的环境拷一份 RDB，里面可能带上陌生库或旧版本库：同名库加载会冲突（需 REPLACE），也可能带进不该有的业务逻辑。迁移前先 FUNCTION LIST 核对，必要时先清再恢复。

  4. FUNCTION FLUSH 有没有保护机制？线上误执行的后果是什么？怎么防？

    参考回答：没有任何确认机制，执行即生效。后果是所有库瞬间消失，正在调用的客户端立刻 ERR unknown function，业务中断到重新加载为止。防法：ACL 禁止业务账号执行该命令、加载走启动流程并做 FUNCTION LIST 校验、变更走审批与审计。

  5. 一个高频调用的扣库存逻辑，你会选脚本还是 Functions？给出三条理由。

    参考回答：选 Functions。①随数据集持久化，重启/主从切换后不用客户端重发脚本，也没有 NOSCRIPT 抖动；②复制传调用名与参数，比传脚本体更省也更确定；③可按库 LIST/DELETE 做版本化与灰度回滚。代价是要防 FUNCTION FLUSH，且脚本必须带 shebang 头。
