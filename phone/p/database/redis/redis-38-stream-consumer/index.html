Stream 消费组与 pending

XADD → XGROUP CREATE → XREADGROUP → XACK 四步与 PEL 的构成｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用 XADD + XGROUP CREATE + XREADGROUP + XACK 跑通一条「至少一次」的消息链路；
  2. 说清 PEL（pending entries list）的四个字段，以及它为什么是这套机制的骨架；
  3. 用 XPENDING 与 XAUTOCLAIM 处理「消费者崩溃后消息没人确认」的问题。

二、前置知识

RD10（Stream 类型入门）、RD37（Pub/Sub 的「至多一次」）。本讲要解决的就是 Pub/Sub 解决不了的那部分：不丢、可回放、能确认。

三、理论讲解（官方定义）

官方对消费组的说明（原文）：

Consumer groups … allow a group of clients to cooperate consuming a stream … each message is delivered to a single consumer in the group … the message stays in the PEL until acknowledged.

—— https://redis.io/docs/latest/develop/data-types/streams/

以及 PEL 的定义（原文要点）：

The PEL … stores the IDs of the messages that were delivered to a consumer but not yet acknowledged.

—— 同上

两条定性：

  • 组内一条消息只投给一个消费者（这点和 Pub/Sub 的广播完全不同）；
  • 未 XACK 的消息永远留在 PEL，不会自动重投、不会自动消失。

四、原理拆解

1. 四步链路

XADD orders * type=created order=1001
  → 返回消息 ID（毫秒时间戳-序号，如 1700000000000-0）

XGROUP CREATE orders g1 0
  → 建立消费组 g1，从 ID 0 开始（也要读历史）

XREADGROUP GROUP g1 consumer-a COUNT 10 STREAMS orders >
  → 「>」表示只读新消息，并把它们写进 consumer-a 的 PEL

XACK orders g1 1700000000000-0
  → 从 PEL 移除，表示「已处理完」

四个符号要记死：> 读新消息、0 重读自己的待确认消息、XACK 确认、XGROUP CREATE 需要 MKSTREAM 才能对不存在的 stream 建组。

XPENDING 的摘要模式给出「总数 + 最小 ID + 最大 ID + 各消费者积压数」，扩展模式给出每条消息的四个字段。只有看过扩展模式，才知道消息卡在谁手里、卡了多久。

3. 「至少一次」是怎么成立的

投递 → 写 PEL（消息不会消失）
  → 消费者处理业务
  → 成功 → XACK（从 PEL 移除）
  → 失败/崩溃 → 消息仍在 PEL，可被再次领取

所以语义是「至少一次」：可能重复投递（消费者处理成功但 XACK 之前崩了），业务必须幂等。

4. 崩溃后的接管

消费者 A 崩溃，它的 PEL 条目没人处理。两种接管方式：

  • XCLAIM：手工指定「把某条消息转给 B」，可带 IDLE 条件（闲置超过多少毫秒才转）；
  • XAUTOCLAIM（6.2+）：一次扫描一批闲置消息并自动转给当前消费者，返回「下个游标 + 被接管的消息 + 已删除的失效 ID」。

XAUTOCLAIM 是生产上更实用的那个，因为它不用你遍历整个 PEL。

5. 裁剪与保留

Stream 是「日志」，会一直增长。三个手段：

  • XADD ... MAXLEN ~ 100000：写入时近似裁剪（~ 允许按节点边界裁剪，效率高）；
  • XTRIM：手工裁剪；
  • XDEL：删单条（注意：删了消息，PEL 里可能还有它的 ID，会形成「幽灵条目」，XAUTOCLAIM 会把它们清理掉）。

五、场景说明

  1. 订单事件流：下单 → 库存 → 通知，多个消费组各自消费同一份日志；
  2. 任务分发：一组 worker 竞争消费，天然负载均衡（组内不重复投递）；
  3. 审计与回放：消息留在日志里，可按 ID 重新读；
  4. 不适合：超高吞吐（Stream 单 key 写入仍是单线程）、需要跨机房强一致（异步复制）。

六、示例代码/实操步骤

# 1. 写入三条消息
127.0.0.1:6379> XADD orders * type=created order=1001
"1700000000000-0"
127.0.0.1:6379> XADD orders * type=paid order=1001
"1700000000001-0"
127.0.0.1:6379> XADD orders * type=shipped order=1001
"1700000000002-0"

# 2. 建组（对不存在的 key 要加 MKSTREAM）
127.0.0.1:6379> XGROUP CREATE orders g1 0
OK
127.0.0.1:6379> XGROUP CREATE orders g2 $ MKSTREAM
OK                            # $ 表示只消费「从现在开始」的新消息

# 3. 消费者 A 领取新消息
127.0.0.1:6379> XREADGROUP GROUP g1 consumer-a COUNT 10 STREAMS orders >
1) 1) "orders"
   2) 1) 1) "1700000000000-0"
         2) 1) "type"
            2) "created"
            3) "order"
            4) "1001"

# 4. 看看 PEL 里积压了什么
127.0.0.1:6379> XPENDING orders g1
1) (integer) 1                # 总数
2) "1700000000000-0"          # 最小 ID
3) "1700000000000-0"          # 最大 ID
4) 1) 1) "consumer-a"
      2) "1"                  # 该消费者的积压数

# 5. 扩展模式：谁领的、卡了多久、投过几次
127.0.0.1:6379> XPENDING orders g1 - + 10
1) 1) "1700000000000-0"
   2) "consumer-a"
   3) (integer) 120000        # 闲置毫秒数
   4) (integer) 1             # 投递次数

# 6. 确认
127.0.0.1:6379> XACK orders g1 1700000000000-0
(integer) 1
127.0.0.1:6379> XPENDING orders g1
1) (integer) 0

# 7. 模拟崩溃：consumer-a 领了不确认，consumer-b 接管
127.0.0.1:6379> XREADGROUP GROUP g1 consumer-a COUNT 1 STREAMS orders >
# 不 XACK，直接换消费者
127.0.0.1:6379> XAUTOCLAIM orders g1 consumer-b 0 0-0 COUNT 10
1) "0-0"                      # 下个游标
2) 1) 1) "1700000000001-0"
      2) 1) "type"
         2) "paid"
3) (empty array)              # 被清理的失效 ID

# 8. 重读自己的待确认消息（用 0 而不是 >）
127.0.0.1:6379> XREADGROUP GROUP g1 consumer-b COUNT 10 STREAMS orders 0

# 9. 裁剪防止无限增长
127.0.0.1:6379> XADD orders MAXLEN ~ 100000 * type=created order=1002
127.0.0.1:6379> XLEN orders
(integer) 3
127.0.0.1:6379> XINFO GROUPS orders
# name g1 / consumers 2 / pending 0 / last-delivered-id ...

七、常见坑（官方明确说明的限制）

  1. 以为消费组是广播。组内一条消息只投给一个消费者，要广播就建多个组。
  2. 投递了不 XACK。消息永远留在 PEL，XPENDING 越积越多，最终无法判断「哪些真没处理」。
  3. 把 > 当「重读」。> 只返回新消息；重读自己的待确认消息要用 0。
  4. 消费者名随机生成。每次重启换名字，PEL 会散落在无数「已消失的消费者」名下，接管时难以判断归属。
  5. XDEL 收了消息但 PEL 仍有 ID。这会产生「幽灵条目」，要定期用 XAUTOCLAIM 清理（它返回的第三项就是被清理的 ID）。
  6. 不裁剪 Stream。消息无限增长，内存与 XLEN 一起涨；用 MAXLEN ~ 近似裁剪。
  7. 业务不幂等。「至少一次」意味着可能重复投递（处理成功但 XACK 前崩溃），必须靠业务侧去重。
  8. XAUTOCLAIM 的 min-idle-time 设成 0。会把「正在处理中」的消息抢走，造成并发处理同一条；应按业务最长处理时间设置。

版本差异（8.x 标注）

XAUTOCLAIM 自 6.2 引入，7.x 与 8.x 沿用；Stream 数据结构与消费组语义未变。8.x 的差异主要在周边工具与许可条款。

依据：https://redis.io/docs/latest/develop/data-types/streams/

八、课后小结

  • 四步：XADD 写 → XGROUP CREATE 建组 → XREADGROUP 领（写 PEL）→ XACK 确认；
  • 组内不重复投递，一条消息只给一个消费者；要广播就建多个组；
  • PEL 四字段：消息 ID、消费者名、投递时间、投递次数；
  • 语义是「至少一次」，业务必须幂等；
  • 崩溃接管用 XAUTOCLAIM（min-idle-time 要按处理时长设）；
  • Stream 是日志，必须用 MAXLEN ~ 或 XTRIM 控制增长。
