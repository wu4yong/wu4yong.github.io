Set 类型：唯一性与集合运算

SINTER/SUNION/SDIFF 的语义、六条高频命令与 intset/listpack/hashtable 编码｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 讲清 Set 的两个核心能力：成员唯一与服务端集合运算；
  2. 会用 SADD / SISMEMBER / SINTER / SPOP / SSCAN，并知道每条命令的复杂度代价；
  3. 理解 intset → listpack → hashtable 的编码演进与阈值，能判断什么数据会导致编码降级。

二、前置知识

RD05–RD07。需要理解「O(N) 命令阻塞主线程」和「编码阈值不可逆」这两个概念，它们在 Set 里同样成立。

三、理论讲解（官方定义）

官方定义（原文）：

A Redis set is an unordered collection of unique strings (members). You can use Redis sets to efficiently: Track unique items; Represent relations; Perform common set operations such as intersection, unions, and differences.

—— https://redis.io/docs/latest/develop/data-types/sets/

三句话对应三个能力：

  • unordered + unique：无序、去重，重复 SADD 同一成员不改变集合；
  • track unique items：天然适合 UV 计数、去重名单；
  • set operations：交集、并集、差集在服务端完成，不需要把数据拉到客户端再算。

容量上限（原文）：单个 Set 最多 2^32 - 1 个成员。

四、原理拆解

1. 唯一性是怎么保证的

Set 的底层是哈希表（或 intset/listpack），成员本身是 key。所以：

  • SADD s a 执行两次，第二次返回 0，集合里只有一个 a；
  • SCARD 返回不重复成员数量；
  • 成员相等的判定是二进制相等，"1" 和 1 在协议层是不同的字节序列，会被当成两个成员（客户端一般会做类型转换，但要知道底层规则）。

2. 三个运算的语义与优先级

工程上最容易搞错的是 SDIFF：它是有序参数的运算，SDIFF A B 与 SDIFF B A 结果完全不同。写「我关注的人里他没关注的」就属于这种单向差集。

三个运算都有 *STORE 变体（SINTERSTORE / SUNIONSTORE / SDIFFSTORE），把结果写进一个新 key——这是缓存运算结果的标准手段：结果是稳定的，就没必要每次重算 O(N)。

7.0 起还有 SINTERCARD numkeys key... [LIMIT n]，只求交集基数而不返回成员。判断「两个大集合有没有交集 / 交集是否超过阈值」时，它比 SINTER 省一个数量级的内存。

3. 编码演进：intset → listpack → hashtable

官方三档编码，看数据自动选择：

  1. intset：所有成员都是整数，且数量 ≤ set-max-intset-entries（默认 512）——紧凑的整数数组，有序存放，内存极省；
  2. listpack：7.2 起支持，用于「非整数但规模不大」的集合，阈值 set-max-listpack-entries（默认 128）；
  3. hashtable：规模或类型超出阈值后的通用结构。

规则是「不满足就降级，降级不回退」。所以一个 Set 一旦混进一个字符串成员，intset 立刻不成立；一旦数量超过阈值，也回不去。

这也是 Set 与 Hash 最容易混淆的地方：两者都用 listpack/hashtable，但 Set 多了一档 intset——因为「全整数集合」是最常见的场景（用户 ID、标签 ID），值得单独优化。

五、场景说明

  1. 去重名单：SADD article:1001:likers uid，天然幂等，SCARD 即点赞数（注意这不是 UV 精确统计的唯一方案，超大基数用 HLL 更省）；
  2. 标签/关系：SADD user:1:follows uid2 uid3，共同关注 = SINTER；
  3. 黑白名单：SISMEMBER blacklist:ip 1.2.3.4，O(1) 判断；
  4. 抽奖：SRANDMEMBER draw:pool 3 抽 3 个不重复；SPOP draw:pool 1 抽中即移除（防重复中奖）；
  5. 随机推荐：SRANDMEMBER pool 10 每次不同；
  6. UV 精确统计（小规模）：一个 Set 存一天的去重用户，规模可控时准确无误——相比 HLL 的 0.81% 误差，这是「要精确」时的选择。

不适合：需要排序或按分值取范围（用 ZSet）、需要计数但基数极大（用 HLL）、需要存重复出现的记录（用 List 或 Stream）。

六、示例代码/实操步骤

# 1. 唯一性：重复 SADD 返回 0
127.0.0.1:6379> SADD tags:post1 java redis
(integer) 2
127.0.0.1:6379> SADD tags:post1 redis
(integer) 0
127.0.0.1:6379> SCARD tags:post1
(integer) 2
127.0.0.1:6379> SMEMBERS tags:post1
1) "java"
2) "redis"
# 注意：无序，别依赖返回顺序

# 2. 成员判断
127.0.0.1:6379> SISMEMBER tags:post1 java
(integer) 1
127.0.0.1:6379> SISMEMBER tags:post1 python
(integer) 0
127.0.0.1:6379> SMISMEMBER tags:post1 java python    # 6.2+
1) (integer) 1
2) (integer) 0

# 3. 集合运算
127.0.0.1:6379> SADD follows:u1 u2 u3 u4
127.0.0.1:6379> SADD follows:u2 u3 u4 u5
127.0.0.1:6379> SINTER follows:u1 follows:u2
1) "u3"
2) "u4"
127.0.0.1:6379> SUNION follows:u1 follows:u2
1) "u2"
2) "u3"
3) "u4"
4) "u5"
5) "u1"
127.0.0.1:6379> SDIFF follows:u1 follows:u2
1) "u2"                      # u1 关注但 u2 没关注的
127.0.0.1:6379> SDIFF follows:u2 follows:u1
1) "u5"                      # 反过来的结果完全不同

# 4. 只求交集基数，不取成员
127.0.0.1:6379> SINTERCARD 2 follows:u1 follows:u2
(integer) 2
127.0.0.1:6379> SINTERCARD 2 follows:u1 follows:u2 LIMIT 1
(integer) 1                  # 触达 LIMIT 就停，省算力

# 5. 运算结果落盘，避免重复计算
127.0.0.1:6379> SINTERSTORE common:u1u2 follows:u1 follows:u2
(integer) 2
127.0.0.1:6379> SMEMBERS common:u1u2
1) "u3"
2) "u4"

# 6. 抽奖：不重复 vs 允许重复
127.0.0.1:6379> SADD draw:pool a b c d e
127.0.0.1:6379> SRANDMEMBER draw:pool 3
1) "c"
2) "a"
3) "e"                      # 三个不重复
127.0.0.1:6379> SRANDMEMBER draw:pool -3
1) "b"
2) "b"
3) "a"                      # 负 count 允许重复
127.0.0.1:6379> SPOP draw:pool 1
"d"                          # 真的从集合里删掉了

# 7. 编码与阈值
127.0.0.1:6379> SADD ids:user 1001 1002 1003
(integer) 3
127.0.0.1:6379> OBJECT ENCODING ids:user
"intset"
127.0.0.1:6379> SADD ids:user abc
(integer) 1
127.0.0.1:6379> OBJECT ENCODING ids:user
"listpack"                   # 混入字符串，intset 立刻失效
127.0.0.1:6379> CONFIG GET set-max-intset-entries
1) "set-max-intset-entries"
2) "512"

七、常见坑（官方明确说明的限制）

  1. SMEMBERS 是 O(N)。集合上万成员时就会阻塞主线程，遍历请用 SSCAN；「我要全部成员」和「我要遍历全部成员」是两种需求，后者不该用 SMEMBERS。
  2. SDIFF 参数有序，SDIFF A B ≠ SDIFF B A。写「差集」时务必确认方向，这是最容易出逻辑错误的一条。
  3. 编码降级不可逆。intset 里塞一个非整数成员就永久变 listpack/hashtable，之后内存占用和 CPU 都用不上 intset 的优势。ID 类集合要保证「只存整数」。
  4. SPOP 会真的删除数据。想「抽一次但保留」请用 SRANDMEMBER。两者名字很像，误用会直接丢业务数据。
  5. 大集合上的 SINTER / SUNION 是 O(N*M) 量级，多集合交集在百万级成员时会长时间占用主线程。要么预计算落盘（SINTERSTORE + TTL），要么用 SINTERCARD ... LIMIT。
  6. Set 无序，SMEMBERS 返回顺序不代表任何语义。需要顺序就必须换 ZSet。
  7. Set 不能存重复值，也就不适合「记录每次访问」这类明细场景；UV 与 PV 的存储选择要分开。

版本差异（8.x 标注）

7.2 引入 listpack 编码的 Set（set-max-listpack-entries），7.0 引入 SINTERCARD，6.2 引入 SMISMEMBER。8.x 语义未变。若环境为 6.x，则 listpack 与 SINTERCARD 都不可用，请按 intset/hashtable 两档理解。

依据：https://redis.io/docs/latest/develop/data-types/sets/

八、课后小结

  • Set 是无序不重复的字符串集合，核心价值是去重与服务端集合运算；
  • SINTER / SUNION / SDIFF 语义不同，SDIFF 参数有序；
  • SINTERCARD（7.0）只算基数，配合 LIMIT 可省算力；*STORE 变体用于缓存结果；
  • SPOP 删除、SRANDMEMBER 不删，负 count 表示允许重复；
  • 编码三档 intset → listpack → hashtable，降级不可逆；
  • SMEMBERS 与大集合运算都是 O(N)，线上必须用 SSCAN 与预计算替代。

九、思考题

  1. 「共同关注」用 SINTER，「他关注但我没关注」用哪个命令？为什么参数顺序不能反？
  2. 点赞人数用 SCARD 得到，和用 HLL 的 PFCOUNT 得到，差别在哪？什么规模下你会选哪个？
  3. 一个 Set 存的是用户 ID，本来是 intset，某天有人写进了一个空字符串成员。内存和 CPU 各会发生什么变化？怎么避免？
  4. 两个各有 100 万成员的集合求交集，主线程会被占多久？有哪三种降低影响的做法？
  5. SPOP 与 SRANDMEMBER 在抽奖场景里分别对应什么规则？「每人只能中一次」该用哪个？
