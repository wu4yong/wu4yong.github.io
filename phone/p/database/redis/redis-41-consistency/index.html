缓存与数据库一致性

两种写入顺序的风险窗口与四种收窄手段｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 讲清「先删缓存再更库」和「先更库再删缓存」各自的风险窗口长在哪；
  2. 用延迟双删、删除重试、binlog 订阅中的一种把窗口收窄到业务可接受；
  3. 诚实地回答「我的方案能否做到强一致」，而不是含糊地说「基本一致」。

二、前置知识

RD39（Cache-Aside 的读写顺序）、RD36（Pipeline，批量失效时用得上）、RD37（Pub/Sub，失效广播）。这一讲是 M7 里最容易被低估的一讲：代码写起来只有两行，边界却最多。

三、理论讲解（官方定义）

必须先说明事实：Redis 不提供「缓存与数据库一致」的协议。官方文档中，Redis 的定位是缓存/数据结构服务器，一致性由业务侧负责。

官方关于原子性的说明（这才是能用得上的部分）：

Redis commands are atomic … a single command is executed atomically. Multiple commands can be grouped into a transaction (MULTI/EXEC) or a Lua script, which is also executed atomically.

—— https://redis.io/docs/latest/develop/interact/programmability/eval-intro/

这句话的含义是：Redis 内部的「删缓存」是原子的，但「删缓存」和「更新数据库」是两个系统、两次操作，它们之间没有原子性。所以不一致窗口必然存在，问题只剩「窗口多长、谁能兜底」。

一致性的三个等级，先约定清楚：

等级 定义 典型手段
强一致 任何时刻读到的都是最新值 不走缓存，或读写都走主库事务
最终一致（秒级） 短窗口内可能是旧值，随后收敛 先更库再删缓存 + 重试/订阅
最终一致（分钟级） 窗口更长，靠 TTL 兜底 只做删除，不补偿

四、原理拆解

1. 先删缓存、再更新库：窗口为什么最糟

T1: 写者 DEL cache        → 缓存空了
T2: 读者 GET 未命中 → 查库拿到【旧值】
T3: 读者 SET cache（旧值） → 旧值被回填
T4: 写者 UPDATE db（新值） → 库是新的，缓存是旧的

关键在 T3 发生在 T4 之前：缓存被旧值填满，而且之后再没有任何事件去纠正它（因为写者的删除已经用掉了）。这个旧值会一直留到 TTL 到期。窗口大小 ≈ 「更新库的耗时 + 读者回填的耗时」，且后果是「长期不一致」，不只是短暂。

2. 先更新库、再删缓存：窗口小得多

T1: 写者 UPDATE db（新值） → 库已是新值
T2: 读者 GET 未命中（假设缓存恰好在此时失效）→ 读到旧值? 
    —— 注意：这里读者查库已经能拿到新值，除非它在 T1 之前就开始了查询
T3: 写者 DEL cache
T4: 下一次读 → 未命中 → 查库 → 新值回填

它的风险窗口只有「读者在 T1 之前查库、在 T3 之后回填」这一种交错，概率低、持续时间短，而且一旦 T3 执行成功，后续读会自然收敛到新值。所以主流选择是它。

3. 四种收窄手段

  • 延迟双删：更库 → 删缓存 → sleep(Δt) → 再删一次。Δt 要大于「一次读请求的最大耗时」，目的是把「已经读了旧值但还没回填」的请求的回填结果再删掉。
  • 删除失败重试：删缓存可能失败（网络、超时）。把失败的 key 丢进消息队列，异步重试，直到成功（要设最大重试次数，避免死循环）。
  • 订阅 binlog（变更捕获）：让「删缓存」由数据库变更事件驱动，而不是业务代码。好处是「所有写路径都被覆盖」，包括没走应用的手工 SQL；坏处是链路更长、延迟更高（通常百毫秒级）。
  • 关键读绕过缓存：对「必须最新」的读（如支付结果查询），直接读主库，不进缓存。这不是优化，是取舍。

4. 一个常被忽略的细节：删缓存 vs 改缓存

写的时候一定删，不要改。原因有两条：

  1. 改缓存需要把「新值」完整组装出来，多一次读库/拼装；
  2. 两个并发写者「改缓存」的到达顺序可能与「写库」的顺序相反，缓存被旧值覆盖。

删掉之后，值由「下一次读」重新加载，天然按库的顺序收敛。

五、场景说明

  1. 用户资料：最终一致秒级可接受，先更库再删缓存 + 失败重试；
  2. 商品价格：要求读最新，用 Write-Through 或关键读绕过缓存；
  3. 订单状态：绝不能靠缓存，读走主库 + 版本号校验；
  4. 配置开关：直接用 Pub/Sub 广播失效（RD37），延迟容忍度高、语义简单。

六、示例代码/实操步骤

# 标准顺序：先更库，再删缓存
# UPDATE user SET name='jerry' WHERE id=1001;    -- 先完成库更新
127.0.0.1:6379> DEL user:1001
(integer) 1

# 延迟双删
127.0.0.1:6379> DEL user:1001
(integer) 1
# sleep 300ms（大于一次读请求的最大耗时）
127.0.0.1:6379> DEL user:1001
(integer) 0                    # 第二次通常删不到东西，但能清掉「迟到回填」

# 删除失败的补偿：把 key 写入待重试队列（示意）
127.0.0.1:6379> RPUSH cache:del:retry user:1001
(integer) 1

# 判断「缓存里是不是旧值」：对比库与缓存（排查期临时用）
127.0.0.1:6379> GET user:1001
"{\"id\":1001,\"name\":\"tom\"}"     # 库中已是 jerry，说明缓存过期了

# 失效广播（多实例本地缓存场景，RD44 会用到）
127.0.0.1:6379> PUBLISH cache:invalidate "user:1001"
(integer) 2

七、常见坑（官方明确说明的限制）

  1. 「先删缓存再更库」当成标准做法。它在并发读下会把旧值长期写回缓存，是四种顺序里最差的一种。
  2. 延迟双删的 Δt 拍脑袋。Δt 小于一次读请求耗时，第二次删除起不到作用；Δt 太大又拖长不一致窗口。
  3. 删除失败不重试。网络抖动一次，缓存就脏到 TTL 到期。
  4. 用 MULTI 想跨系统事务。Redis 的 MULTI/EXEC 只在 Redis 内部原子，不能把「更新 MySQL」包进来。
  5. 订阅 binlog 但没做幂等。同一条变更事件可能重复投递，删除操作本身幂等，但下游其他动作不一定。
  6. 忘了缓存「被删除后又被写入」的顺序。写者 A 删缓存 → 写者 B 更库并删缓存 → A 的旧值回填，仍会出现，需要版本号或 TTL 兜底。
  7. 以为 TTL 能解决一切。TTL 只是「最坏情况的上限」，窗口内用户看到的就是旧值，业务是否接受要提前定。

版本差异（8.x 标注）

一致性方案属于应用层设计，与 Redis 版本无关。8.x 在客户端缓存（tracking）与集群运维上有增强，可作为失效广播的更优载体，但语义不变。

依据：https://redis.io/docs/latest/develop/interact/programmability/eval-intro/

八、课后小结

  • Redis 不提供跨系统一致性协议，窗口一定存在；
  • 顺序选「先更库、再删缓存」，不要「先删缓存」；
  • 写操作只删缓存，不改缓存；
  • 收窄手段：延迟双删、删除重试、binlog 订阅、关键读绕缓存；
  • 强一致的读不要进缓存，这是取舍不是缺陷。
