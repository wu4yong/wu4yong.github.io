配置体系：redis.conf 与运行时 CONFIG 的边界

配置六组必看项 + CONFIG GET/SET/REWRITE 回路 + 三条边界｜依据 Redis 7.4 Configuration 文档自绘

一、学习目标

  1. 看得懂一份 redis.conf，知道哪六组参数是上线评审必看的；
  2. 讲清「配置文件」和「运行值」是两套东西，以及 CONFIG SET 与 CONFIG REWRITE 各自改了谁；
  3. 记住三条边界：什么时候 REWRITE 会报错、哪些参数改不了、什么时候改动会丢。

二、前置知识

RD02：知道启动时读的是 redis.conf，不带文件就用内置默认值。

三、理论讲解（官方定义）

官方对配置文件的定义很短，但信息量足：

Redis is able to start without a configuration file using a built-in default configuration… The redis.conf file is a simple text file where each line has the form keyword argument1 argument2 ... argumentN, and comments start with #.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/config/

配套的运行时接口是 CONFIG 命令族，官方对其定位是「检查与修改运行中实例的配置」：

The CONFIG command is used to perform certain operations at runtime… CONFIG GET retrieves the value of a configuration parameter, CONFIG SET sets it, CONFIG REWRITE rewrites the config file.

—— https://redis.io/docs/latest/commands/config-set/

注意措辞：REWRITE 改的是「启动时使用的那个配置文件」。如果启动时压根没有配置文件，这条命令就没有落地的对象。

四、原理拆解

1. 三层配置叠加

一个参数最终生效的值，来自三层叠加：

  1. 内置默认值（编译进二进制）；
  2. 配置文件里写的（可用 include 拆分子文件）；
  3. 命令行参数：redis-server /etc/redis/redis.conf --maxmemory 2gb，命令行优先级最高。

启动时还会覆盖一种特殊情形：如果配置文件里的 port 0 或 unixsocket 组合错误，实例会直接拒绝启动——配置错误是启动期失败，不是运行期失败。

2. 六组必看参数（运维评审清单）

3. CONFIG 命令族的四个动作

  • CONFIG GET <pattern>：读运行值，支持 * 与 maxmemory* 这种 glob 甚至空格分隔的多参数；
  • CONFIG SET <param> <value>：改内存中的运行值，立即生效，通常不落盘；
  • CONFIG REWRITE：把运行值写回启动配置文件，会重排文件、丢掉注释；
  • CONFIG RESETSTAT：重置 INFO stats 里的统计计数器，和配置无关，排障时常用。

理清这条链就能避开绝大部分坑：SET 生效但不持久，重启回退；REWRITE 持久但没版本管理就是灾难。

五、场景说明

  • 线上临时调整 maxmemory 压测内存水位：CONFIG SET 验证 → 观察 → CONFIG REWRITE 落盘（注意它要求有配置文件）；
  • 参数调优实验：先在从节点或测试实例上 SET，比对 INFO memory 前后变化；
  • 版本对齐：把 CONFIG GET * 导出，和上一版本对比，找默认值变更（升级前必做）。

六、示例代码/实操步骤

# 1. 看全部与内存相关的运行值
127.0.0.1:6379> CONFIG GET maxmemory*
1) "maxmemory"          2) "0"
3) "maxmemory-policy"   4) "noeviction"

# 2. 运行时改一个能改的参数（立即生效，重启会丢）
127.0.0.1:6379> CONFIG SET maxmemory 2gb
OK
127.0.0.1:6379> CONFIG GET maxmemory
1) "maxmemory"   2) "2147483648"

# 3. 落盘到配置文件（必须启动时带过配置文件）
127.0.0.1:6379> CONFIG REWRITE
OK

# 4. 复核：文件里应该出现了刚改的那行
#   $ grep -n '^maxmemory' /etc/redis/redis.conf
#   573:maxmemory 2gb

# 5. 如果启动时没带配置文件，第 3 步会报错：
#   (error) ERR The server is running without a config file

验证「重启丢配置」这件事，最稳的做法是做一次演练：CONFIG SET 一个非默认值 → SHUTDOWN → 重启 → CONFIG GET 看它是否回到文件里的值。这个动作在 M3 的恢复演练里还会用到。

Java 侧怎么落地：把配置口径固化到工程

命令行调完参数，真正上线要落进 Java 工程，分三块，别混在一起写。

  1. 连接层配置交给 Spring Boot（spring.data.redis.*），只放「怎么连」：地址、密码、db、超时、池参数。这部分由应用启动时读 yml，不依赖服务端的 CONFIG REWRITE。
spring:
  data:
    redis:
      host: redis.prod.internal
      port: 6379
      password: ${REDIS_PASSWORD}   # 从环境变量/配置中心注入，别写死在仓库里
      database: 0
      timeout: 3s
      lettuce:
        pool: { max-active: 32, max-idle: 16, min-idle: 4, max-wait: 1s }

  1. 服务端参数做成「可审计的 ops 脚本」，而不是手工敲 CONFIG SET：把要改的项写进一个 config/redis-tuning.conf，用 include 挂进主配置，改完走 git + 发布流程；临时验证再用 CONFIG SET + CONFIG REWRITE，两步必须成对出现。

  2. 在 Java 里加一次「配置基线自检」，开机时比对关键项，避免「以为配了其实没配」：

@Component
class RedisConfigGuard {
  @PostConstruct
  void check(StringRedisTemplate tpl) {
    Map<String, String> cfg = tpl.execute((RedisCallback<Map<String, String>>) conn -> {
      Properties raw = conn.serverCommands().getConfig("maxmemory*");   // 等价 CONFIG GET maxmemory*
      Map<String, String> m = new HashMap<>();
      raw.forEach((k, v) -> m.put(String.valueOf(k), String.valueOf(v)));
      return m;
    });
    String maxMemory = cfg == null ? null : cfg.get("maxmemory");
    String policy = cfg == null ? null : cfg.get("maxmemory-policy");
    if ("0".equals(maxMemory) || "noeviction".equals(policy)) {
      log.warn("maxmemory={} policy={}，写满内存会返回 OOM 错误 → 核对 ops 配置", maxMemory, policy);
    }
  }
}

这段代码的价值不在逻辑复杂，而在它把「评审清单」变成了启动期断言：maxmemory、maxmemory-policy、appendonly 三项只要和团队口径不一致，日志里立刻有痕迹。生产上建议只告警不阻断，测试环境可以 fail-fast。

七、常见坑（官方明确说明的限制）

  1. CONFIG REWRITE 要求启动时指定了配置文件，否则直接返回 ERR The server is running without a config file。容器里用 redis-server 裸启动再想 REWRITE，一定踩这个。
  2. 并非所有参数都能运行时修改。官方在 CONFIG SET 文档里说明只有一部分参数支持动态设置，其余修改会返回错误、只能改文件后重启。判断方法只有一条：查官方命令页，别靠经验猜。
  3. CONFIG SET 默认不持久化，忘记 REWRITE 的调优在下次发布后凭空消失，这类问题极难复现。
  4. CONFIG REWRITE 会重写整个文件：注释、顺序、空行全丢。所以线上配置文件必须先纳入版本管理（git），否则一次 REWRITE 就把别人写的注释吃掉了。
  5. maxmemory 0 表示不限制（默认值），配合默认的 noeviction，写满内存后是写命令报错 + 可能被 OOM Killer 杀进程，不是「自动清理」。

版本差异（8.x 标注）

8.x 新增了一批配置项（例如与新增数据类型、集群/多线程相关的参数），默认值也有调整。跨 7.4 → 8.x 升级时，官方建议用 CONFIG GET * 做一次全量 diff，再逐项确认，而不是照抄旧 redis.conf。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/config/

八、课后小结

  • 生效值 = 内置默认 + 配置文件 + 命令行参数，三者叠加；
  • CONFIG SET 改运行值（不持久），CONFIG REWRITE 写回启动配置文件（要求有文件）；
  • 六组必看项：网络、内存、持久化、复制集群、安全、客户端与日志；
  • 调优三步：SET 验证 → REWRITE 落盘 → git 记录。

九、思考题

  1. 线上一个实例 maxmemory 从 0 改成了 4gb，但没有 REWRITE，两天后一次发布重启，会发生什么？如何在不重启的前提下确认它已经持久化？

    参考回答：重启后 maxmemory 退回配置文件里的值（文件里是 0 就是 0），限制消失：内存继续涨，noeviction 下写命令开始报 OOM，或有被 OOM Killer 杀掉的风险。CONFIG GET 读到的是内存值，不能当持久化证据；不重启只能看配置文件本身，CONFIG GET dir 定位文件后再 grep -n '^maxmemory' <那个 conf>。

  2. 为什么 CONFIG REWRITE 要设计成「重写整个文件」而不是「在原位改一行」？这个设计带来了什么运维要求？

    参考回答：配置允许 include、注释、任意书写顺序，原位改一行无法可靠定位，参数可能写在 include 的子文件里。整文件重写的代价是注释与格式不可恢复，于是运维要求变成：配置文件进 git、由模板生成、人工注释另存，绝不把线上 redis.conf 当唯一副本。

  3. 你拿到一份别人交接的 redis.conf，只有 40 行，maxmemory、save、appendonly 都没写。这些参数此刻的实际值是多少，依据是什么？

    参考回答：全部取内置默认值——maxmemory 0（不限制）、save 有默认保存点（如 3600 1 / 300 100 / 60 10000）、appendonly no。依据是官方示例里这些项被注释掉，注释掉即不生效，回落到编译默认值；要确认就读运行值 CONFIG GET maxmemory save appendonly。
