限流与原子计数

三种限流算法的实现要点与误差来源｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 用 INCR + EXPIRE 实现固定窗口限流，并说清它的临界问题；
  2. 用 ZADD + ZREMRANGEBYSCORE 实现滑动窗口，并估算内存开销；
  3. 用一段 Lua 脚本实现令牌桶，理解「读改写必须原子」这条铁律。

二、前置知识

RD05（String 与 INCR）、RD09（ZSet）、RD34（Lua 脚本）、RD22（集群的槽与 hash tag）。限流看起来是「数个数」，实际是「并发 + 原子 + 分布式」三件事的叠加。

三、理论讲解（官方定义）

INCR 的官方定义（原文）：

Increments the number stored at key by one. If the key does not exist, it is set to 0 before performing the operation. … This operation is atomic.

—— https://redis.io/docs/latest/commands/incr/

「原子」这两个字是限流能成立的基础：并发 100 个请求同时 INCR，每个都会拿到唯一且递增的返回值，不会出现两个请求拿到同一个计数。

EXPIRE 的官方定义（原文要点）：

Set a timeout on key. After the timeout has expired, the key will automatically be deleted.

—— https://redis.io/docs/latest/commands/expire/

注意「自动删除」的实际机制是惰性删除 + 定期抽样（RD12），所以「窗口边界」在实践中不是像素级精确的，而是「大约在 T 时刻之后失效」。

四、原理拆解

1. 固定窗口：最简单，也最容易放过 2 倍流量

key = rl:api:{uid}:{分钟}
count = INCR key
if count == 1: EXPIRE key 60
if count > 100: 拒绝

临界问题：窗口按「自然分钟」划分时，用户在 12:00:59 发 100 次、12:01:00 再发 100 次，在 2 秒内通过了 200 次，而阈值是 100/分钟。这不是 bug，是「窗口边界」的固有缺陷。

2. 滑动窗口：精确，但每条请求一条记录

ZADD rl:{uid} now now          # score 与 member 都用时间戳/请求 ID
ZREMRANGEBYSCORE rl:{uid} 0 (now-60000)   # 清掉窗口外的
ZCARD rl:{uid}                 # 窗口内的数量

成本：每个请求一条 ZSet 成员，10 万 QPS × 1 分钟窗口 = 600 万成员，内存与 CPU 都吃不消。所以它适合「中低频、要求准确」的限流（如按用户每日配额），不适合全站入口限流。

3. 令牌桶：允许突发，最贴近真实业务

桶里存两个数：tokens（当前令牌数）、last（上次填充时间）
每次请求：
  elapsed = now - last
  tokens = min(capacity, tokens + elapsed * rate)
  如果 tokens >= 1 → tokens -= 1，放行；否则拒绝

必须在 Lua 里做，因为「读 tokens → 计算 → 写回」三步之间不能插入其他命令。用 EVAL 一次跑完，天然原子。

4. 集群下的「全局限流」问题

限流 key 若按用户维度分片到不同节点，每个节点只能看到自己那部分计数：

3 主节点，单节点阈值 100 → 全局实际通过量可能接近 300

两种选择：

  • 接受分片限流：把阈值写成「单节点 100」，总量按节点数放大，适用于「保护单节点」的目标；
  • 强制全局限流：所有限流 key 用同一个 hash tag（如 rl:{global}:...），落到同一个槽，代价是热点集中（RD22、RD24 讲过 cluster 的槽约束）。

5. 限流的三层位置

  • 网关/入口：按 IP、按接口总量，保护整个系统；
  • 应用内：按用户、按业务动作，保护下游资源；
  • 下游资源侧：数据库连接池上限、线程池上限——这才是最后一道硬约束。

限流不是「让请求变少」，而是「让超出部分以确定的代价被拒绝」。

五、场景说明

  1. 登录/短信验证码：固定窗口按手机号，粗粒度够用；
  2. API 配额：滑动窗口按用户，要求精确；
  3. 秒杀入口：令牌桶允许小突发，配合队列削峰（RD55 会讲）；
  4. 集群全局限流：hash tag 强制同槽，或接受分片总量放大。

六、示例代码/实操步骤

# 1. 固定窗口：一分钟 100 次
127.0.0.1:6379> INCR rl:api:u1001:202302051105
(integer) 1
127.0.0.1:6379> EXPIRE rl:api:u1001:202302051105 60
(integer) 1
127.0.0.1:6379> INCR rl:api:u1001:202302051105
(integer) 2
# 当返回值 > 100 时拒绝请求

# 2. 滑动窗口：60 秒内最多 100 次（ZSet 实现）
127.0.0.1:6379> ZADD rl:sw:u1001 1700000000000 "1700000000000-1"
(integer) 1
127.0.0.1:6379> ZREMRANGEBYSCORE rl:sw:u1001 0 1699999940000
(integer) 0
127.0.0.1:6379> ZCARD rl:sw:u1001
(integer) 1
127.0.0.1:6379> EXPIRE rl:sw:u1001 60

# 3. 令牌桶：Lua 脚本，一次原子完成「补令牌 + 扣令牌」
127.0.0.1:6379> EVAL "local t=redis.call('hmget',KEYS[1],'tokens','last') local tokens=tonumber(t[1]) local last=tonumber(t[2]) local now=tonumber(ARGV[1]) local rate=tonumber(ARGV[2]) local cap=tonumber(ARGV[3]) if tokens==nil then tokens=cap last=now end local delta=math.max(0,now-last) tokens=math.min(cap,tokens+delta*rate) local ok=0 if tokens>=1 then tokens=tokens-1 ok=1 end redis.call('hmset',KEYS[1],'tokens',tokens,'last',now) redis.call('expire',KEYS[1],60) return ok" 1 rl:token:u1001 1700000000000 1 10
(integer) 1                    # 1=放行，0=拒绝

# 4. 查看限流 key 的规模（评估内存）
127.0.0.1:6379> DBSIZE
127.0.0.1:6379> MEMORY USAGE rl:sw:u1001
(integer) 1234

# 5. 集群下的同槽写法（同一 hash tag）
127.0.0.1:6379> CLUSTER KEYSLOT rl:{global}:api
(integer) 12345               # 所有带 {global} 的 key 落在同一个槽

七、常见坑（官方明确说明的限制）

  1. 先 GET 再 INCR。两个命令之间可插入其他请求，高并发下会放过超额流量；限流判定必须原子。
  2. INCR 后忘记 EXPIRE。计数永远不清零，用户被永久限流；EXPIRE 也要在「第一次 INCR」时设置（或用 Lua 合并）。
  3. 固定窗口当精确配额用。临界 2 倍问题真实存在于生产。
  4. 滑动窗口用于全站入口。ZSet 成员数与 QPS 成正比，内存与 CPU 都会爆。
  5. 集群里按 key 维度限流却以为是全局。分片后总量约等于 N × 单节点阈值。
  6. 用 KEYS/SCAN 清限流 key。KEYS 是 O(N) 且阻塞主线程（官方明确警告生产禁用），清理应靠 TTL。
  7. 限流阈值写死在代码里。大促改不了，等于没有限流。
  8. 只限流不排队。直接拒绝会让用户体验陡降；配合队列与降级（RD47）更稳。

版本差异（8.x 标注）

INCR / EXPIRE / ZADD / EVAL 的语义在 7.4 与 8.x 一致。8.x 在脚本与集群工具有演进，但「读改写必须原子」这条工程铁律不变。

依据：https://redis.io/docs/latest/commands/incr/

八、课后小结

  • 限流靠原子计数：INCR 的返回值就是本窗口内第几次；
  • 固定窗口最简单但有临界 2 倍问题；滑动窗口精确但贵；令牌桶可允许突发；
  • 判定与计数必须在一次原子操作内完成（Lua）；
  • 集群下要么接受分片总量放大，要么用 hash tag 强制同槽；
  • 阈值必须可动态调整。

九、思考题

  1. 固定窗口的临界问题，具体发生在哪两个时刻？怎么用滑动窗口消除？
  2. 10 万 QPS 用滑动窗口限流，1 分钟窗口需要多少内存？你估算的依据是什么？
  3. 令牌桶的 rate 与 capacity 分别控制什么？秒杀场景怎么设？
  4. 集群里 3 个主节点、单节点阈值 100，全局最多通过多少？业务能接受吗？
  5. 为什么限流的最后一道防线是「连接池上限」而不是「Redis 计数」？
