四种缓存模式与选型

Cache-Aside / Read-Through / Write-Through / Write-Behind 的职责分工｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用一句话说清四种缓存模式各自「谁负责加载、何时写回」；
  2. 拿到一个业务场景，能按「能不能接受旧值、能不能接受丢写」两问选出模式；
  3. 说出任何一种模式下「Redis 整体不可用」时业务怎么办，而不是等出事才想。

二、前置知识

RD05（String 是最常用的缓存载体）、RD12（过期与淘汰策略）、RD37（Pub/Sub，本模块后续会用到）。这一讲开始进入 M7 缓存工程，重点从「Redis 怎么用」转向「Redis 放在哪一层」。

三、理论讲解（官方定义）

先明确一件事：四种缓存模式不是 Redis 的规范，它们是数据库缓存领域的通用工程范式。Redis 官方文档只规定「Redis 作为缓存时如何配置与运维」（缓存淘汰、maxmemory-policy、客户端缓存等），不规定业务如何组织读写顺序。

官方的定位表述（原文要点）：

Redis is often used as a caching layer … you can configure Redis to evict keys when reaching the max memory limit, and choose an eviction policy.

—— https://redis.io/docs/latest/develop/reference/eviction/

也就是说：Redis 负责「存 + 淘汰」，业务负责「一致性 + 回源」。这一讲讲的四种模式，全部属于后者的范畴。

四种模式的定义，用一句话各自概括：

模式
谁负责加载
写入顺序
Cache-Aside（旁路）
业务代码
先写库，再删缓存
Read-Through（读穿）
缓存层（loader）
同上
Write-Through（写穿）
业务代码
同时写缓存和库
Write-Behind（写回）
业务代码 + 异步刷库
先写缓存，异步写库

四、原理拆解

1. Cache-Aside：最常见的那一种

读：GET key ──命中──→ 返回
        └─未命中──→ 查库 ──→ SET key（带 TTL）──→ 返回

写：UPDATE db ──→ DEL key（不是 SET 新值）

关键点有两个：

  • 写的时候删缓存，而不是更新缓存。 因为「更新缓存」需要把新值重新组装出来（可能来自多表 JOIN），既多一次计算，又可能与并发写的顺序错乱；删掉让下一次读自然回填，语义更干净。
  • 缓存是旁路，不是主路。 Redis 挂了，读请求直接落到库上（变慢但可用），这是 Cache-Aside 最大的优点。

2. Read-Through：把回源逻辑放进缓存层

业务只调 cache.get(key)，缓存层内部发现未命中就去查库、回填、再返回。Java 生态里 Spring Cache 的 @Cacheable、Go 生态里的各种 cache 封装都是这个思路。

代价是：缓存层必须有访问数据库的能力（连接、SQL、序列化规则），它从「一个 KV 客户端」变成了「一个数据访问层」。分层上更整洁，耦合上更重。

3. Write-Through：写路径双写

写：SET cache（新值）──→ UPDATE db

好处是读永远是热的、读到的永远是最新值；坏处是写延迟翻倍，而且缓存故障会放大成写失败（写缓存失败要不要回滚库？这就是分布式事务问题）。所以它通常用在「写少读多、且读必须最新」的场景，比如商品基础信息。

4. Write-Behind：写缓存即返回，异步刷库

写：SET cache（并把变更丢进队列）──→ 立即返回
    后台批量刷库

写吞吐最高，适合计数、点击流、点赞这类「允许短暂丢失」的数据。代价必须说清：缓存宕机时，队列里未落库的写会丢。如果这批数据是钱，就不能用这个模式。

5. 两个判断问题

把选型压缩成两问：

  • 能不能接受「缓存里是旧值」？ 能 → Cache-Aside / Read-Through；不能 → Write-Through，或者干脆绕过缓存读主库。
  • 能不能接受「丢一批写」？ 不能 → Cache-Aside / Write-Through；能 → Write-Behind。

两个都「不能」的场景（比如扣库存），说明这个数据根本不该用「缓存 + 异步」来承载，应该走数据库事务 + 分布式锁（RD42）。

五、场景说明

  1. Cache-Aside：绝大多数读多写少的业务数据（用户资料、配置、文章详情）；
  2. Read-Through：框架层统一封装缓存，希望业务代码零侵入；
  3. Write-Through：商品价格、库存快照这类「读必须最新、写不频繁」的数据；
  4. Write-Behind：浏览量、点赞数、在线人数、埋点计数；
  5. 不适合任何缓存模式：强一致的账户余额——它需要事务，不需要缓存。

六、示例代码/实操步骤

# Cache-Aside 的读（伪代码语义，用 redis-cli 演示命令形态）
127.0.0.1:6379> GET user:1001
(nil)                                  # 未命中 → 业务去查库

127.0.0.1:6379> SET user:1001 '{"id":1001,"name":"tom"}' EX 3600
OK                                     # 回填，务必带 TTL

# Cache-Aside 的写：先更新库，再删缓存
# UPDATE user SET name='jerry' WHERE id=1001;   -- 库操作
127.0.0.1:6379> DEL user:1001
(integer) 1

# Write-Through：写的时候同时写缓存（带 TTL，避免成为「永久脏数据」）
127.0.0.1:6379> SET user:1001 '{"id":1001,"name":"jerry"}' EX 3600
OK

# Write-Behind：先写缓存，再异步刷库
127.0.0.1:6379> INCR post:2001:views
(integer) 1
# 后台任务每 N 秒把增量批量写回数据库

TTL 是这四种模式的共同底线：即使一致性逻辑写错了，TTL 也能把「永久脏数据」变成「一段时间内的旧数据」。

七、常见坑（官方明确说明的限制）

  1. 写的时候更新缓存而不是删缓存。并发写时两次「更新缓存」的到达顺序可能与库不一致，缓存被旧值覆盖且不会自愈。
  2. 回填不带 TTL。一旦某个环节出错，脏数据永远留在缓存里；官方在淘汰策略文档中明确，只有配了 maxmemory 与 maxmemory-policy 才会淘汰，否则内存会一直涨。
  3. 把缓存当存储。Redis 的持久化（RD14–RD16）不保证零丢失，缓存层的数据必须能被重建。
  4. Write-Through 没考虑缓存故障。写缓存失败时业务是否继续？不定义清楚就会变成「有时写成功有时失败」。
  5. Write-Behind 丢了写还不知道。异步队列要有落盘或补偿机制，否则重启即丢。
  6. 没给缓存层设降级。Redis 挂掉后所有请求直达库，大概率把库打挂——这是 M7 后面几讲反复出现的主题（RD40、RD47）。

版本差异（8.x 标注）

缓存模式的工程范式不随 Redis 版本变化。8.x 与 7.4 的差别在运维侧（如 8.0 起许可改为 AGPLv3/SSPL 双许可、集群与工具链调整），不影响本节内容。

依据：https://redis.io/docs/latest/

八、课后小结

  • 四种模式的差别只有两点：谁加载、何时写回；
  • 生产上 90% 是 Cache-Aside：读未命中回填、写更新库后删缓存、全部带 TTL；
  • 选型两问：能不能接受旧值、能不能接受丢写；
  • 两个都不能的强一致数据，不要套缓存模式；
  • 任何模式都要回答「缓存整体不可用时业务怎么活」。

九、思考题

  1. 为什么写的时候推荐「删缓存」而不是「更新缓存」？举一个「更新缓存」出错的并发顺序。
  2. Write-Through 下，写缓存成功但写库失败，缓存里是什么？你打算怎么处理？
  3. Write-Behind 的「丢写」窗口有多大？由什么决定？
  4. 如果业务要求「读到的必须是 1 秒内的最新值」，你会选哪种模式，还需要什么额外机制？
  5. 你能给你的项目画出「请求 → 缓存 → 库」的完整链路，并标出 Redis 挂掉时每一步的变化吗？
