过期策略与内存淘汰

惰性删除 + 定期删除、从节点不主动过期，以及 maxmemory-policy 八种取值｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 分清「过期（expire）」和「淘汰（eviction）」两件完全不同的事，不再把它们混成一句「到点就删」；
  2. 讲清惰性删除 + 定期删除的配合机制，以及为什么从节点不主动删过期 key；
  3. 能根据业务挑对 8 种 maxmemory-policy，并知道 noeviction 为什么是默认值。

二、前置知识

RD05（String 的 SET EX）、RD08/RD09（集合类结构）。需要先会设 TTL，再来理解「TTL 到点之后到底发生了什么」。

三、理论讲解（官方定义）

两条官方原文先摆出来，它们的差别就是本篇的全部重点。

过期（原文）：

Normally Redis keys are created without an associated time to live. The key will simply live forever, unless it is removed by the user in an explicit way … Keys with a time to live are called volatile.

—— https://redis.io/docs/latest/commands/expire/

淘汰（原文）：

When Redis is used as a cache, … it’s common to evict keys … maxmemory-policy configuration directive … The default is noeviction, which means Redis will reply with an error when the memory limit is reached.

—— https://redis.io/docs/latest/develop/reference/eviction/

一句话对照：过期是「时间到了」，淘汰是「内存不够了」。两者的触发条件、作用范围、后果全都不一样，唯一的共同点是「key 会消失」。

四、原理拆解

1. 过期：两种删除方式必须配合

Redis 不在 key 上挂定时器（那样几千万个 key 就是几千万个定时器，成本不可接受）。它用两种被动方式：

惰性删除（lazy）：客户端访问某个 key 时，先检查它的 TTL，过期了就当场删掉并当作不存在返回。优点是零额外开销，缺点是没人访问的过期 key 会一直占内存。

定期删除（active）：服务端每秒执行约 10 次（hz 相关）抽样任务：

  • 从「带 TTL 的 key」集合里随机抽 20 个；
  • 删掉其中已过期的；
  • 如果这 20 个里过期比例超过 25%，就继续再抽一轮，直到比例降下来或达到时间上限。

这就是官方描述的「抽样 + 循环」，它是概率清理，不是扫全表。所以「所有过期 key 都会准时释放」是一个错误预期——内存里可能长期留着没人访问的过期 key，DBSIZE 也照样统计它们。

从节点为什么不主动删：官方明确说明，副本不会自己过期 key，而是等待主节点发来的 DEL。原因是保持主从数据一致——如果副本自己删了、主节点还没删，一主一从就会不一致（读副本会「突然少一个 key」）。所以从节点上的过期 key 在逻辑上是「不可见」的（读它会返回 nil），但物理上仍在内存里。

2. 淘汰：8 种策略，一条开关

两个关键细节：

  1. LRU/LFU 是近似的，不是精确算法。Redis 不维护完整访问时间链，而是随机采样 maxmemory-samples（默认 5）个 key，从中挑「最该淘汰」的那个。样本越大越接近真实，CPU 开销也越高。这就是为什么「LRU 有时候会淘汰一个刚刚访问过的 key」——采样没抽到它。
  2. volatile-* 在没有带 TTL 的 key 时会退化为 noeviction，也就是直接报 OOM。这是线上「明明配了淘汰策略还是写不进去」的头号原因。

noeviction 作为默认值是官方刻意的：Redis 默认把自己当「数据库」而不是「缓存」，默默删数据是危险行为，报错交给使用者决定。

3. LRU 与 LFU 的选择

  • 缓存「最近热」的（比如商品详情，热度随时间变化快）→ allkeys-lru；
  • 缓存「长期热」的（比如配置、榜单，访问频率稳定）→ allkeys-lfu，LFU 还带「频率计数器随时间衰减」的机制，避免老热点永久占位；
  • 混存「必须留住的数据 + 可丢的缓存」→ 给可丢的加 TTL，用 volatile-lru；
  • 缓存里想「先丢快过期的」→ volatile-ttl。

五、场景说明

  1. 纯缓存层：maxmemory 4gb + maxmemory-policy allkeys-lru，这是最常见的组合；
  2. 会话存储：key 全带 TTL，用 volatile-lru，保证「不会淘汰没设 TTL 的配置类 key」；
  3. 同一实例既存缓存又存少量必须保留的数据：必须用 volatile-*，并把「必须保留」的数据不加 TTL——但更稳的做法是拆实例，别把两种语义混在一个库；
  4. 统计类临时 key：volatile-ttl 让「快过期的先走」，适合滑窗计数；
  5. 不允许任何数据被静默删除：noeviction，并在客户端处理 OOM 错误、做降级。

六、示例代码/实操步骤

# 1. 过期时间设置与三种 TTL 返回值
127.0.0.1:6379> SET k1 v EX 10
OK
127.0.0.1:6379> TTL k1
(integer) 10
127.0.0.1:6379> TTL not:exist
(integer) -2                     # key 不存在
127.0.0.1:6379> SET k2 v
OK
127.0.0.1:6379> TTL k2
(integer) -1                     # 存在但没有过期时间

# 2. 相对 / 绝对 / 保留 / 移除
127.0.0.1:6379> EXPIRE k2 60
(integer) 1
127.0.0.1:6379> PEXPIRE k2 60000
(integer) 1
127.0.0.1:6379> EXPIREAT k2 1700000000
(integer) 1
127.0.0.1:6379> PERSIST k2
(integer) 1                      # 去掉 TTL，变成永久 key
127.0.0.1:6379> TTL k2
(integer) -1

# 3. 集合类结构只能整 key 过期
127.0.0.1:6379> HSET user:1 name 阿勇
(integer) 1
127.0.0.1:6379> EXPIRE user:1 60
(integer) 1                      # 整个 key 一起过期（字段级过期见 RD07）

# 4. 看当前淘汰配置
127.0.0.1:6379> CONFIG GET maxmemory
1) "maxmemory"
2) "0"                           # 0 = 不限制，永远不会淘汰
127.0.0.1:6379> CONFIG GET maxmemory-policy
1) "maxmemory-policy"
2) "noeviction"
127.0.0.1:6379> CONFIG GET maxmemory-samples
1) "maxmemory-samples"
2) "5"

# 5. 动态改策略（7.0 起 CONFIG SET 支持多参数）
127.0.0.1:6379> CONFIG SET maxmemory 100mb maxmemory-policy allkeys-lru
OK
127.0.0.1:6379> CONFIG GET maxmemory-policy
1) "maxmemory-policy"
2) "allkeys-lru"

# 6. 观察淘汰是否真的发生
127.0.0.1:6379> INFO memory
# Memory
used_memory_human:...
maxmemory_human:100.00M
maxmemory_policy:allkeys-lru
127.0.0.1:6379> INFO stats
# Stats
evicted_keys:12                  # 发生过 12 次淘汰

# 7. noeviction 下的表现：写不进去
127.0.0.1:6379> CONFIG SET maxmemory 1mb maxmemory-policy noeviction
OK
127.0.0.1:6379> SET big "$(head -c 2000000 /dev/urandom | base64)"
(error) OOM command not allowed when used memory > 'maxmemory'.

排查「为什么写不进去」时的标准动作：看 INFO memory 的 maxmemory_policy、看 INFO stats 的 evicted_keys 是否增长、看 used_memory 是否贴着 maxmemory。

Java 侧怎么落地：TTL 与淘汰在应用层怎么配合

服务端的策略定了，客户端还要做三件事，否则照样出问题。

  1. 写入必须带过期：opsForValue().set(k, v, Duration) 一条命令搞定；不要 set 完再 expire，中间那段窗口里进程挂掉就留下永久 key。

  2. 配置层把策略固化：spring.data.redis.* 只管连接，maxmemory / maxmemory-policy 属于服务端配置，应该写进 redis.conf 的模板并纳入 git，别靠上线后手工 CONFIG SET。

  3. 在应用里兜住 OOM：noeviction 或 volatile-* 退化时写命令会抛 RedisSystemException（消息含 OOM command not allowed）。要区分「读降级」和「写降级」：读失败可以走 DB 兜底，写失败通常要退化成「仅记录日志 + 异步补偿」，不能让整个请求 500。

try {
    tpl.opsForValue().set(key, json, Duration.ofMinutes(30));
} catch (RedisSystemException e) {
    if (e.getMessage() != null && e.getMessage().contains("OOM")) {
        metrics.counter("redis.write.oom").increment();   // 埋点，交给容量治理
        // 这里做降级：不写缓存，直接回落数据库
    } else throw e;
}
  1. 别用 keys() / scan 做「清理过期 key」的补偿：过期删除是服务端概率行为，客户端扫全库只会把主线程拖死。

七、常见坑（官方明确说明的限制）

  1. 不设 maxmemory 就没有淘汰。maxmemory 0 意味着无上限，一直涨到被系统 OOM Killer 干掉——这时候 Redis 进程是被 kill，不是报错。
  2. noeviction 是默认策略，内存满了写命令直接返回 OOM command not allowed，读命令照常。所以「缓存用着用着就写不进去了」先查策略，不是查内存。
  3. volatile-* 在没有带 TTL 的 key 时退化为 noeviction。整个库都是永久 key 却配了 volatile-lru，等于还是 OOM。
  4. 过期 key 不一定及时释放。惰性删除 + 抽样定期删除都是概率性的，DBSIZE 会把过期但未清理的 key 算进去；INFO keyspace 的 expires 字段才是「带 TTL 的 key 数量」。
  5. KEYS 与 SCAN 会看到「逻辑上已过期」的 key 吗？访问时惰性删除会先清掉，所以读操作看不到它们；但内存统计（used_memory）要等定期删除跑过才降下来。
  6. 从节点不主动过期，只等主节点的 DEL。所以「读从库拿到过期数据」不会发生，但「从库内存比主库涨得快」会发生——复制积压与过期传播都有延迟。
  7. LRU/LFU 是近似算法，maxmemory-samples 默认 5。样本太小会「误杀热 key」，调到 10–20 是常见折中，但会多吃 CPU。
  8. maxmemory 不包含 fork 出的子进程开销（RDB/AOF 重写时 CoW 会额外占内存），所以真机上要给 maxmemory 留出余量（一般不超过物理内存的 60%–70%）。

版本差异（8.x 标注）

主线为 7.4。7.0 起 CONFIG SET 支持一次设置多个参数；active-expire-effort（默认 1，范围 1–10）控制定期删除的力度，官方建议在「大量短 TTL key」场景下适度调高。8.x 在淘汰策略集合上没有新增取值。

依据：https://redis.io/docs/latest/develop/reference/eviction/

八、课后小结

  • 过期看时间，淘汰看内存，两者独立，别混为一谈；
  • 过期 = 惰性删除（访问时检查）+ 定期删除（每秒抽样 20 个、过期率 > 25% 继续抽），是概率清理；
  • 从节点不主动过期，等主节点 DEL 同步；
  • 淘汰需要显式 maxmemory，8 种策略分 allkeys / volatile 两池 × lru/lfu/random/ttl；
  • noeviction 是默认，满了报 OOM；volatile-* 无带 TTL 的 key 时同样报 OOM；
  • LRU/LFU 基于 maxmemory-samples（默认 5）采样近似，非精确算法。

九、思考题

  1. 一个 key 设了 EX 10，之后十年没人访问，它会占内存多久？为什么？

    参考回答：理论上只要没被抽样命中就一直占着。惰性删除只在被访问时触发，定期删除是每秒约 10 次、每次抽 20 个的概率清理——没人访问的 key 可能长期没被抽到。所以它占到「被抽样删掉」或「实例重启」为止，不是 10 秒后就释放。

  2. 主从架构下，主节点过期了一个 key，从节点什么时候不可见？此时从节点内存释放了吗？

    参考回答：主节点过期会同步发 DEL 给从节点，从节点收到前，读自己的副本会逻辑上不可见（返回 nil），因为从节点读到过期 key 时会按过期处理而不是返回旧值。内存并未释放——DEL 真正到达前，这块内存还占在从节点上，所以从节点内存可能比主节点高。

  3. 线上缓存频繁报 OOM command not allowed，used_memory 只有 maxmemory 的 40%。最可能的原因是什么？

    参考回答：有两条最可能：① 策略是 volatile-*，但库里几乎没有带 TTL 的 key，于是退化成 noeviction，一超限就报 OOM，与用了多少内存无关；② used_memory 不含 fork 子进程 CoW 与碎片开销，used_memory_rss 已经贴着上限，INFO memory 里对一下 used_memory_rss / mem_fragmentation_ratio 就能确认。

  4. allkeys-lru 与 allkeys-lfu 在「今天爆款、明天无人问」的商品缓存场景里，哪个更合适？为什么？

    参考回答：这里应选 allkeys-lru。爆款的特征是「短时间高频、之后迅速冷却」，LRU 只看最近使用时间，冷却后自然被淘汰；LFU 累计历史访问频次，即使昨天被访问了百万次，今天热度走了仍会靠高计数霸占内存（虽有衰减机制，但衰减慢），容易出现「昨天的爆款把今天的热点挤掉」。

  5. maxmemory 设成物理内存的 100% 会发生什么？为什么官方实践里都建议留出较大余量？

    参考回答：RDB 保存/AOF 重写会 fork 子进程，写时复制（CoW）在写入频繁时可能额外占用与数据量同级的物理内存；加上内存碎片、客户端缓冲区、复制积压缓冲，很容易触发系统 OOM Killer 直接把进程杀掉。所以 maxmemory 通常控制在物理内存的 60%–70% 以内。
