List 类型：两端进出与阻塞语义

List 的双端操作、阻塞命令的三条约束与底层结构｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 讲清 List 是「双端操作的链表」，LPUSH+RPOP 是队列、LPUSH+LPOP 是栈，方向只由命令决定；
  2. 理解 BLPOP / BRPOP / BLMOVE 的阻塞语义，包括超时、事务内不阻塞、多客户端竞争的官方规则；
  3. 知道 List 的容量上限与底层编码，能用 LTRIM 与 UNLINK 控制住「无限增长」和「删除卡顿」。

二、前置知识

RD05（String 类型）与本篇同为「五种基础类型」的前半段。需要先理解「单线程执行、命令级原子」，因为阻塞命令的本质是「把主线程让出来等」。

三、理论讲解（官方定义）

官方对 List 的定义（原文）：

Redis lists are linked lists of string values. Redis lists are frequently used to implement stacks and queues.

—— https://redis.io/docs/latest/develop/data-types/lists/

三个关键词：

  • linked lists：链表结构，头尾操作 O(1)，按下标访问是 O(N)；
  • string values：元素就是字符串，没有「元素类型」概念；
  • stacks and queues：官方直接点名栈与队列两种用法，而不是「队列专用类型」。

容量上限（原文）：

The max length of a Redis list is 2^32 - 1 (4,294,967,295) elements.

—— https://redis.io/docs/latest/develop/data-types/lists/

四、原理拆解

1. 方向决定语义：同一份数据，三副面孔

List 只有「靠近队头（head，左侧）」和「靠近队尾（tail，右侧）」两个操作端。组合出来的三种用法：

组合
语义
典型场景
LPUSH 进 + RPOP 出
FIFO 队列
任务队列、消息排队
LPUSH 进 + LPOP 出
LIFO 栈
撤销栈、最近优先
RPUSH 进 + LPOP 出
FIFO 队列（另一种写法）
生产者写右、消费者读左

注意 LPUSH 是「逐个插到头部」：LPUSH k a b c 之后顺序是 c b a，不是 a b c。要顺序进去，用 RPUSH——这个反直觉点是线上 bug 高发区。

2. 阻塞语义：把主线程「让」出去

普通 LPOP 在空 List 上立刻返回 nil。阻塞版的差别在于：

BLPOP key [key ...] timeout

官方规则（原文要点）：

  • timeout 是秒，可以是小数（6.0 起支持 0.1 这类浮点），0 表示无限阻塞；
  • 超时返回 nil；
  • 在 MULTI/EXEC 事务里，阻塞命令不会阻塞，若无法立即执行就直接返回 nil；
  • 多个客户端阻塞在同一个 key 上时，按「先阻塞先服务」的顺序被唤醒。

为什么事务里必须不阻塞？因为事务是「一批命令一起执行、期间不处理其他客户端请求」，如果在事务中间真的阻塞等待，整个服务就死了。这条限制是保护，不是怪癖。

3. 被阻塞的客户端占不占资源

不占。阻塞的客户端在等待期间不参与命令执行，只是挂在 key 的等待队列上；一旦有 LPUSH 写进数据，服务端唤醒等待者并投递。所以「用 BLPOP 做消费者」比自己写轮询省 CPU——这也是官方推荐的做法。

但要注意：每个阻塞连接仍是一个内核 socket，几千个阻塞消费者会吃掉连接数，这是容量规划问题（RD51 详讲），不是语义问题。

4. 底层结构：quicklist

7.x 的 List 不是纯链表，而是 quicklist——一个由 listpack 节点组成的双向链表。每个节点装一批元素（节点大小受 list-max-listpack-size 控制，默认 128），节点内是紧凑的 listpack。这样兼顾了：

  • 头尾插入 O(1)（链表特性）；
  • 节点内内存连续，省指针开销（listpack 特性）；
  • 中间插入/删除只影响所在节点。

代价是：按下标访问仍然要沿着链表数节点，LINDEX k 1000000 依旧是慢操作。LRANGE 大区间同理。

五、场景说明

官方配方里 List 的位置：

  1. 轻量任务队列：生产者 RPUSH job:queue {...}，消费者 BLPOP job:queue 5；
  2. 最新 N 条：LPUSH feed:uid item + LTRIM feed:uid 0 99，天然只留最近 100 条；
  3. 可靠一点的队列：LMOVE src dst LEFT RIGHT 把「取出」变成「搬到处理中队列」，处理成功再 LREM，进程崩溃时能从 dst 捞回来（这是一套经典写法，官方在 LMOVE 文档里也这么示范）；
  4. 栈式撤销：LPUSH undo:uid op / LPOP undo:uid。

不适合：需要按分值排序（用 ZSet）、需要多消费者分组确认（用 Stream 消费组，RD38 详讲）、需要随机访问中间元素（List 做不到 O(1) 下标）。

六、示例代码/实操步骤

# 1. 队列：右进左出（顺序最符合直觉）
127.0.0.1:6379> RPUSH job:queue job1 job2 job3
(integer) 3
127.0.0.1:6379> LRANGE job:queue 0 -1
1) "job1"
2) "job2"
3) "job3"
127.0.0.1:6379> LPOP job:queue
"job1"

# 2. LPUSH 的顺序陷阱
127.0.0.1:6379> DEL stack
(integer) 1
127.0.0.1:6379> LPUSH stack a b c
(integer) 3
127.0.0.1:6379> LRANGE stack 0 -1
1) "c"
2) "b"
3) "a"        # 逐个插头部，顺序反了

# 3. 阻塞消费：先起一个消费者
# 终端 A：
127.0.0.1:6379> BLPOP job:queue 5
(nil)                        # 5 秒内没有数据，超时返回 nil
# 终端 B 在 5 秒内执行：
127.0.0.1:6379> RPUSH job:queue job4
# 终端 A 立刻返回：
1) "job:queue"
2) "job4"

# 4. 事务里不阻塞
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> BLPOP empty:list 0
QUEUED
127.0.0.1:6379> EXEC
1) (nil)                     # 立刻返回 nil，不会真的等

# 5. 只保留最近 100 条
127.0.0.1:6379> RPUSH feed:u1 a
127.0.0.1:6379> LTRIM feed:u1 -100 -1
OK

# 6. 搬到处理中队列（可靠队列雏形）
127.0.0.1:6379> RPUSH job:queue task1
127.0.0.1:6379> LMOVE job:queue job:doing RIGHT LEFT
"task1"
127.0.0.1:6379> LRANGE job:doing 0 -1
1) "task1"

# 7. 按值删除：count 决定删几个
127.0.0.1:6379> RPUSH nums 1 2 1 2 1
127.0.0.1:6379> LREM nums 2 1
(integer) 2                  # 从头往尾删掉 2 个 "1"

Java 侧怎么落地：把 List 当轻量队列的三个关键点

轻量队列在 Spring Boot 里不需要额外依赖，StringRedisTemplate 的 opsForList() 就是 List 操作。

  1. 生产端用 rightPush 而不是 leftPushAll，和命令行 RPUSH 对齐，顺序才符合直觉；要限制长度，同一个调用里用 trim：
@Service @RequiredArgsConstructor
class JobProducer {
    private final StringRedisTemplate tpl;
    void submit(String payload) {
        tpl.opsForList().rightPush("job:queue", payload);
        tpl.opsForList().trim("job:queue", -1000, -1);   // LTRIM，只留最近 1000 条
    }
}
  1. 消费端用 leftPop(key, timeout) 对应 BLPOP，注意它是一个阻塞调用，必须放在独立线程池里，不能占 Web 请求线程：
String job = tpl.opsForList().leftPop("job:queue", Duration.ofSeconds(5));  // null = 超时

  1. 要可靠一点，用 rightPopAndLeftPush（对应 LMOVE src dst RIGHT LEFT），把消息搬到 job:doing，处理成功再 remove 从 doing 里删；这不是完整 ack，但进程崩溃后 doing 里的消息能人工捞回。真正需要 ack + pending 时换 Stream（RD38）。

  2. 配置上别忘了连接池与超时：阻塞消费意味着长连接，lettuce.pool.max-active 要按消费者线程数配；spring.data.redis.timeout 不要小于阻塞时长，否则客户端会先超时断开。

七、常见坑（官方明确说明的限制）

  1. LPUSH 多值顺序是反的：LPUSH k a b c 结果 c b a。批量入队请用 RPUSH，或用 LPUSH 但接受逆序。
  2. BLPOP 的 timeout 是「秒」，0 是永久阻塞，不是「0 秒」。误传 0 会让消费者线程永远挂住——这是线上「消费线程消失」最常见的根因。
  3. 事务内的阻塞命令不阻塞，直接返回 nil。所以「用 MULTI 包一层保证原子性 + 用 BLPOP 等待」这个组合是不成立的。
  4. BLPOP 支持多个 key，按 key 顺序优先：BLPOP k1 k2 0 中有数据时先返回 k1，不看哪个先到。用多 key 做「优先级队列」时靠的就是这个顺序，别指望公平性。
  5. RPOPLPUSH 自 6.2 起标记废弃，改用 LMOVE（BLMOVE 是它的阻塞版）。旧代码升级时注意替换。
  6. DEL 大 List 会阻塞主线程：官方推荐 UNLINK，把内存释放交给后台线程。
  7. List 没有「按元素去重」能力，重复写入会产生重复元素；需要去重请换 Set 或在写入前判重。
  8. LINSERT 与 LREM 是 O(N)，百万级 List 上频繁调用会明显拖慢主线程。

版本差异（8.x 标注）

主线为 7.4。8.x 对 List 的类型语义没有变更；LMPOP / BLMPOP（7.0 新增的多 key 弹出）继续可用。迁移时关注的是集群槽位与持久化格式，而非 List 命令本身。

依据：https://redis.io/docs/latest/develop/data-types/lists/

八、课后小结

  • List 是双端链表，队列与栈只是命令方向的组合，类型本身不变；
  • LPUSH 逐个头插，批量写入顺序会反，入队优先用 RPUSH；
  • 阻塞命令的 timeout 单位是秒、0 为永久，事务内不阻塞；
  • 多 key 阻塞按 key 顺序优先返回，可当优先级队列用；
  • 底层是 quicklist（listpack 节点链表），头尾 O(1)、下标 O(N)；
  • 容量上限 2^32-1，删除大 List 用 UNLINK，控增长用 LTRIM。

九、思考题

  1. 用 LPUSH + RPOP 做队列，为什么很多人第一次写就把消息顺序搞反了？把命令和结果各写一遍验证。

    参考回答：因为 LPUSH 是逐个插到头部，LPUSH q a b c 得到的是 c b a；于是 LPUSH + RPOP 先弹出的其实是最后写进去的 c，成了 LIFO。想要 FIFO，要么 RPUSH 进 + LPOP 出，要么 LPUSH 进 + RPOP 出并且接受「写入顺序与消费顺序相反」这个前提。

  2. BLPOP k 0 的消费者在生产环境「消失」了，日志没有报错。可能是哪几种原因？

    参考回答：① timeout 传了 0，它表示永久阻塞，消费者确实在等，只是永远等不到数据；② 连接被中间件（LB / 防火墙 / 云 NAT）的空闲超时静默断开，客户端没感知；③ 阻塞命令跑在事务里，直接返回 nil，循环没写退出条件；④ 消费线程池被占满，看日志像「没动静」。排查入口是 CLIENT LIST 看连接状态与 INFO clients。

  3. 为什么 Redis 规定「事务里的阻塞命令不阻塞」？如果强行允许，会出现什么后果？

    参考回答：MULTI/EXEC 期间服务端要连续执行整批命令且不处理其他客户端请求；一旦在中间真的阻塞等待，整个实例就停在那里，所有其他客户端一起挂住。所以官方规定：事务里遇到无法立即执行的阻塞命令，直接返回 nil。

  4. LTRIM feed -100 -1 与 LTRIM feed 0 99 在 feed 只有 50 条时，结果是否相同？为什么？

    参考回答：结果相同，都是「保留全部 50 条」。负数下标从尾部算，-100 在只有 50 条时等价于越界到 0，所以 -100 -1 覆盖全部；0 99 同样覆盖 0..49。差别在语义意图：-100 -1 表达「只留最近 100 条」且在数据增长时依然正确，0 99 表达「留前 100 条」，一旦变成 RPUSH 追加就会把最新的裁掉。

  5. 「可靠队列」的经典做法是 LMOVE 到处理中队列再删。这套做法在进程崩溃、消息重复投递两种故障下分别会发生什么？

    参考回答：崩溃时消息留在 job:doing，不会丢，但要靠人工或定时任务扫 doing 重新投递——没有自动重试。重复投递时因为 LMOVE 是原子搬移，同一个消息不会同时出现在两个队列，但处理成功却删失败（或删之前崩溃）会导致重放，所以业务必须幂等。真要「自动重试 + pending 统计」，用 Stream 消费组。
