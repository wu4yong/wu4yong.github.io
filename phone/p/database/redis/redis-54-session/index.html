会话存储：登录态放哪

会话的写入、校验、续期、失效四步与两条边界｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 用一个 HASH 存下会话所需字段，并用 EXPIRE 决定「多久无操作要重登」；
  2. 说清「每次请求都续期」带来的写放大，以及如何只在必要时续期；
  3. 说清 Redis 成为登录链路单点时，降级策略必须先定。

二、前置知识

RD05（String）、RD07（HASH）、RD12（过期机制）、RD45（客户端缓存，可选）。M9 进入实战串讲，这一讲把「数据结构 + 过期 + 可用性」三件事拼到一起。

三、理论讲解（官方定义）

官方对 HASH 与过期的定义（原文要点）：

HSET key field value — Sets the specified fields to their respective values in the hash stored at key.

EXPIRE key seconds — Set a timeout on key. After the timeout has expired, the key will automatically be deleted.

—— https://redis.io/docs/latest/commands/hset/、https://redis.io/docs/latest/commands/expire/

两条关键结论：

  • 整个 HASH 共享一个 TTL。你不能「只让某个字段过期」，会话里的字段是同生共死的；
  • 过期是「到期后不再可用」，不一定立刻消失。机制是惰性删除 + 定期抽样（RD12），但对业务而言语义就是「过期即失效」。

Redis 不是会话存储的唯一选择（JWT 把状态放在客户端），但它的价值是服务端可撤销：登出、踢人、改权限都能立刻生效。

四、原理拆解

1. 数据结构

session:{sid}  → HASH
  uid: 1001
  role: admin
  login_at: 1700000000
  ip: 10.0.1.20
  ua: Mozilla/5.0 ...

EXPIRE session:{sid} 1800    # 30 分钟无操作即失效

三个设计要点：

  • sid 必须是随机不可猜的字符串（32 字节以上），不能用自增 ID 或手机号；
  • HASH 字段少而小，比整块 JSON 更省内存，也便于局部更新；
  • TTL 是业务语义（如「30 分钟无操作」），不是随手写的数字。

2. 校验与续期

每次请求：
① GETALL session:{sid}     → 不存在则跳登录
② 判断「是否快到续期阈值」
③ 满足条件才 EXPIRE 重置

为什么不是每次都 EXPIRE：高频接口下，每个请求一次写命令会让主线程多一份写压力，并且产生大量无意义的复制流量。常见做法是「剩余 TTL 小于阈值（如 1/3）时才续期」，用一次读换多次写。

3. 撤销与多端

  • 登出：DEL session:{sid}，立刻失效；
  • 踢人：维护 uid → sid 列表（一个 SET），或直接删掉该用户所有 sid；
  • 多端登录：每个端一个独立 sid，互不影响；「只允许一个端」则要在登录时删掉旧 sid。

4. 可用性：Redis 是登录链路的单点

这是本讲最该提前回答的问题。缓存/会话层故障时，业务只有三种选择：

策略
行为
代价
全部跳登录
立刻要求重新认证
用户体验断崖，可能压垮登录接口
只读接口放行
无会话时降级为匿名
权限判断必须另有兜底
本地短期缓存
进程内保留最近会话
多实例不一致（RD44）

选哪一种，必须在设计阶段定，而不是故障当天现场决定。

一个 HASH 承载一个会话（sid 不可猜、字段同生共死）、剩余 TTL 小于 1/3 才续期的写放大取舍，以及 Redis 故障时的三种降级代价｜依据 HSET、EXPIRE 与惰性删除机制自绘

五、场景说明

  1. 后台管理系统：会话量小、要求「改权限立刻生效」，Redis 会话是最合适的；
  2. App 登录态：sid 长期有效 + 定期刷新，注意「续期策略」别写成每次请求都写；
  3. 多端并存：每端独立 sid，配上「踢下线」能力；
  4. 不适合：完全无状态、可容忍令牌到期的公开 API——JWT 更省。

六、示例代码/实操步骤

# 1. 登录成功：写入会话（HASH + TTL）
127.0.0.1:6379> HSET session:9f3a4721 uid 1001 role user login_at 1700000000 ip 10.0.1.20
(integer) 4
127.0.0.1:6379> EXPIRE session:9f3a4721 1800
(integer) 1

# 2. 请求校验：整块读出
127.0.0.1:6379> HGETALL session:9f3a4721
1) "uid"
2) "1001"
3) "role"
4) "user"
...

# 3. 只读剩余 TTL，决定是否续期
127.0.0.1:6379> TTL session:9f3a4721
(integer) 1620                  # 还剩 27 分钟，超过阈值就不续

# 4. 需要续期时重置
127.0.0.1:6379> EXPIRE session:9f3a4721 1800
(integer) 1

# 5. 局部更新（如角色变化）
127.0.0.1:6379> HSET session:9f3a4721 role admin
(integer) 0                     # 0 表示字段已存在、值被覆盖

# 6. 登出 / 踢人
127.0.0.1:6379> DEL session:9f3a4721
(integer) 1

# 7. 单端登录：维护 uid 到 sid 的映射
127.0.0.1:6379> SADD user:1001:sids 9f3a4721
(integer) 1
127.0.0.1:6379> SMEMBERS user:1001:sids

# 8. 观察会话规模
127.0.0.1:6379> DBSIZE
127.0.0.1:6379> INFO keyspace

Java 侧怎么落地：Spring Session Redis 或自建 HASH

  1. pom：直接用 Spring Session 的 Redis 实现，省掉自己写续期逻辑。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<dependency>
  <groupId>org.springframework.session</groupId>
  <artifactId>spring-session-data-redis</artifactId>
</dependency>
  1. application.yml：超时是业务语义（30 分钟无操作），flush-mode 决定什么时候真正写 Redis：
spring:
  session:
    store-type: redis
    timeout: 30m
    redis:
      namespace: app:session     # 多应用共用实例时隔离
      flush-mode: on_save       # 请求结束时一次写入，避免每改一次就往返
  data:
    redis:
      timeout: 300ms
  1. 要自己的 key 结构就自建 HASH（同一会话的字段必须同生共死，别拆成多个 key）：
String sid = RandomStringUtils.random(32, true, true);   // ≥32 字节，不可猜
String key = "session:" + sid;
redis.opsForHash().putAll(key, Map.of("uid", "1001", "role", "admin"));
redis.expire(key, Duration.ofMinutes(30));
  1. 读取顺序固定：先 HGETALL 判存在，再 TTL 判剩余；只有剩余小于阈值（如 1/3）才 EXPIRE 重置，避免每个请求都产生一次写：
Long ttl = redis.getExpire(key);
if (ttl != null && ttl >= 0 && ttl < 600) redis.expire(key, Duration.ofMinutes(30));

  1. 撤销与踢人：登出 DEL session:{sid}；单用户多端用 uid → sids 的 SET 记录在线的 sid，登录新端时把旧 sid 逐个 DEL。别用 KEYS session:* 按用户扫。

  2. 降级要在代码里预置：Spring Session 抛 RedisConnectionFailureException 时，按既定策略走（全跳登录 / 只读放行 / 本地 Caffeine 兜 1～5 分钟），并保证多实例下不依赖本地缓存的强一致。

七、常见坑（官方明确说明的限制）

  1. sid 用可预测的值。自增 ID 或手机号做 sid，等于把会话交给攻击者枚举。
  2. 只存 uid 不存角色/权限。每次请求都去查库，会话的价值就只剩「是否登录」。
  3. 每次请求都 EXPIRE。写放大明显，高 QPS 接口会推高主线程压力与复制流量。
  4. TTL 设成「永久」。用户离职、设备丢失后会话永不失效。
  5. 以为 HASH 字段能单独过期。TTL 属于整个 key，字段只能一起过期（RD07 讲的字段级过期是 7.4 新特性，会话场景一般不用）。
  6. 没做撤销机制。JWT 的痛点是「无法立刻踢人」，用 Redis 会话却不实现撤销，等于白换。
  7. 会话 key 不分片。会话量到千万级时单实例内存吃紧，应按 uid 或 sid 前缀分片。
  8. 没定义降级策略。Redis 故障时「全部跳登录」会引发雪崩式重登（RD47 的三道闸）。

版本差异（8.x 标注）

HSET/HGETALL/EXPIRE 语义在 7.4 与 8.x 一致。7.4 起 HASH 支持字段级过期（HEXPIRE），但会话场景通常整 key 过期更简单。

依据：https://redis.io/docs/latest/commands/hset/

八、课后小结

  • 会话 = 一个 HASH + 一个 TTL，sid 必须随机不可猜；
  • 校验是读，续期是写，别让每个请求都写；
  • 撤销靠 DEL，多端靠多个 sid；
  • Redis 会话的价值是「服务端可撤销」，代价是「多一个单点」；
  • 降级策略在设计阶段就要定。

九、思考题

  1. 会话里为什么建议存 role 而不只是 uid？

    参考回答：每请求都要做权限判断，只存 uid 就得回源查用户表，把会话的价值（少一次查库）抵消掉。存 role 是把「鉴权所需的结论」缓存下来；缺点是角色变更要同步刷新会话（改权限时更新或删除对应 sid），这是可接受的取舍。

  2. 「剩余 TTL 小于 1/3 才续期」相比每次续期，省下了什么？

    参考回答：省掉大部分写操作与随之而来的复制、AOF 开销。每次请求都 EXPIRE 意味着 QPS 级的写放大（还有主从与持久化成本），而 30 分钟会话在 1/3 阈值下最多每 20 分钟写一次；代价是最坏情况下会话会提前一点失效，用一次读换多次写。

  3. 一个用户三个端登录，你要怎么实现「登录新端踢掉旧端」？

    参考回答：为每个端分配独立 sid（不共用），并用 uid → sids 的 SET 维护该用户所有在线会话。登录新端时写入新 sid、把集合里的旧 sid 逐个 DEL（或只保留最近一个）；被踢端的下一次请求因 HGETALL 为空而跳登录。

  4. Redis 故障导致会话全丢，你的系统会怎样？给出三条降级动作。

    参考回答：全丢等于所有用户被登出，且登录接口会被瞬时打满。三条动作：① 全部跳登录（并给登录接口限流与排队）；② 只读接口降级为匿名放行，权限判断用兜底规则；③ 本地短期缓存最近会话顶几分钟，接受多实例不一致。

  5. 会话量 5000 万、平均 300 字节，需要多少内存？要不要分片？

    参考回答：5000 万 × 300 B ≈ 15 GB（还没算 HASH 与 key 的额外开销，实际约 18～20 GB），已经超过单实例 10～16 GB 的容量红线。必须分片（按 uid 哈希或用 hash tag 分组），同时把 TTL 与「按用户维度批量撤销」设计好，否则分片后踢人需要跨节点遍历。
