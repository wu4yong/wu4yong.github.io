客户端缓存与 TRACKING

CLIENT TRACKING 的两种模式与 RESP3 失效推送｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 用 CLIENT TRACKING ON 开启默认模式，并说清服务端记住了什么；
  2. 用 BCAST PREFIX 开启广播模式，说明两种模式在内存与消息量上的取舍；
  3. 说清「失效消息会丢」这条硬约束，以及为什么本地缓存必须自己设 TTL。

二、前置知识

RD44（多级缓存与 L1）、RD04（RESP 协议）、RD37（Pub/Sub 的至多一次）。这一讲是官方对「进程内缓存」唯一给出的一等公民机制，也是 RD44 里「失效广播」的更优载体。

三、理论讲解（官方定义）

官方 Client-side caching 文档的核心表述（原文要点）：

Client-side caching … is implemented using the CLIENT TRACKING command. When tracking is enabled, Redis remembers the keys that a client read, and when one of those keys is modified (or expires), it sends an invalidation message to the client.

In default mode, Redis tracks the keys that were read by the client. In broadcast mode, the client subscribes to prefixes, and Redis sends invalidation messages for all keys matching those prefixes, without tracking individual reads.

—— https://redis.io/docs/latest/develop/clients/client-side-caching/

以及一条必须记住的限制（原文要点）：

Invalidation messages are not guaranteed to be delivered … if a client is disconnected, it will miss invalidations that happen while it is not connected.

—— 同上

四、原理拆解

1. 默认模式：记录「读过什么」

客户端：CLIENT TRACKING ON
   → 之后每次 GET key，服务端在「该连接的追踪表」里记下这个 key
写方：SET key newval（或 DEL、或过期）
   → 服务端向「追踪过这个 key 的连接」推送失效消息

特点：

  • 内存开销与「被追踪的 key 数量」成正比（每个连接一张表，但服务端会对相同 key 做合并）；
  • 消息精准，只发给真正读过的人；
  • 适合「读得集中、写得很分散」的业务，比如读多写少的配置、商品详情。

2. 广播模式：按前缀订阅，不记录读

客户端：CLIENT TRACKING ON BCAST PREFIX user:
   → 服务端不再记录「谁读过哪个 key」
写方：任何以 user: 开头的 key 被修改
   → 服务端向所有订阅了该前缀的连接推送失效消息

特点：

  • 服务端内存开销小（不维护 per-key 追踪表）；
  • 消息量可能很大：没读过的 key 变更也会推给你；
  • 适合「key 空间大、读得分散」的场景，比如海量用户维度数据。

3. 一次失效的完整路径

① 客户端 GET user:1001（默认模式下被记录）
② 写方 SET user:1001 ...
③ 服务端生成失效事件 → 通过 RESP3 的 push 通道下发
④ 客户端收到 __redis__:invalidate 消息 → 删本地副本
⑤ 下一次读 → 重新 GET → 拿到新值

第 ③ 步依赖 RESP3 的 out-of-band 消息（push）。RESP2 下的实现要靠「在普通命令回复中夹带」或额外连接，语义弱一些，工程上建议直接用 RESP3 客户端。

4. 为什么「失效会丢」

官方明确说明：断线期间发生的失效不会补发（服务端不记录历史）。工程结论：

  • 本地缓存必须有自己的 TTL（哪怕很短，如 1–5 秒）；
  • 重连后应主动清空/重建本地缓存，而不是继续用重连前的副本；
  • 对「绝不能旧」的数据，不要放本地缓存。

两种模式的内存与消息取舍、GET→变更→RESP3 push→删本地副本→回源五步，以及断线不补发与 REDIRECT 的关系｜依据 Client-side caching 与 CLIENT TRACKING 文档自绘

五、场景说明

  1. 微服务内的热点配置：默认模式 + 短 TTL，读多写少；
  2. 用户维度数据（订单列表头、个人资料）：广播模式按 user: 前缀订阅；
  3. 与 RD44 的 L1 集成：把 tracking 当作「失效广播」的载体，替代自建 Pub/Sub；
  4. 不适合：客户端不支持 RESP3 / 连接经常抖动且无法容忍旧值的场景。

六、示例代码/实操步骤

# 1. 查看客户端是否支持 tracking（需要 RESP3）
127.0.0.1:6379> HELLO 3
# 返回 map，包含 proto:3

# 2. 默认模式：先开启，再读
127.0.0.1:6379> CLIENT TRACKING ON
OK
127.0.0.1:6379> GET user:1001
"{\"id\":1001,\"name\":\"tom\"}"

# 3. 另一个连接修改这个 key（模拟写方）
127.0.0.1:6379> SET user:1001 '{"id":1001,"name":"jerry"}'
OK
# → 第一个连接会收到 push 消息：__redis__:invalidate ["user:1001"]

# 4. 广播模式：按前缀订阅（不记录读过哪些 key）
127.0.0.1:6379> CLIENT TRACKING ON BCAST PREFIX user:
OK

# 5. 查看追踪状态与统计
127.0.0.1:6379> CLIENT TRACKINGINFO
# flags: on / redirect / bcast / optin / optout ...
127.0.0.1:6379> CLIENT LIST
# 每行末尾有 flags 与 tracking 相关信息

# 6. 关闭追踪
127.0.0.1:6379> CLIENT TRACKING OFF
OK

# 7. 带重定向的形态（把失效消息转发到另一个连接，适合连接池）
127.0.0.1:6379> CLIENT TRACKING ON REDIRECT <subscriber-client-id>

关键提醒：连接池场景下，GET 与「接收 push」往往不是同一条连接，所以要理解 REDIRECT；否则会出现「开了 tracking 但收不到失效」的现象。

Java 侧怎么落地：Lettuce 开 RESP3 + 容器收失效

Spring Data Redis 没有 tracking 的一等 API，做法是「底层命令开 tracking + 容器订阅失效频道」。

  1. pom：Redis 客户端用默认的 Lettuce（支持 RESP3），本地缓存用 Caffeine。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-cache</artifactId>
</dependency>
<dependency>
  <groupId>com.github.ben-manes.caffeine</groupId>
  <artifactId>caffeine</artifactId>
</dependency>
  1. application.yml：连接池与超时先配好，tracking 的两个前提是「同一实例」与「有名字的连接」：
spring:
  data:
    redis:
      host: 10.0.0.11
      client-name: order-svc
      timeout: 500ms
      lettuce:
        pool:
          max-active: 32
          max-wait: 200ms
  1. 打开 RESP3（不切协议收不到 out-of-band 的 push）：
@Bean
LettuceClientConfigurationBuilderCustomizer resp3() {
    return b -> b.clientOptions(ClientOptions.builder()
            .protocolVersion(ClientOptions.ProtocolVersion.RESP3).build());
}
  1. 让专门的监听连接开 tracking，并用 REDIRECT 把失效指给它：先取监听连接的 CLIENT ID，再对业务连接执行
CLIENT TRACKING ON REDIRECT <listener-client-id>

（连接池里 GET 用的连接和收 push 的连接通常不是同一条，不配 REDIRECT 就会「开了却收不到」。）

  1. 容器订阅 __redis__:invalidate，收到就把本地 Caffeine 里的对应副本删掉：
container.addMessageListener((msg, ch) -> {
    for (Object k : (List<?>) msg.getBody()) l1.evict(String.valueOf(k));
}, new ChannelTopic("__redis__:invalidate"));
  1. 兜底仍然靠 TTL：本地缓存 1～5 秒 expireAfterWrite，重连后主动清空；对「绝不能旧」的数据（余额、库存）不要放本地，tracking 只解决「更快发现变化」。

七、常见坑（官方明确说明的限制）

  1. 用 RESP2 客户端开 tracking。收不到真正的 out-of-band 推送，行为依赖实现，容易「看起来开了但没生效」。
  2. 以为失效消息可靠。官方明示断线期间不补发，本地副本必须靠 TTL 兜底。
  3. 本地缓存不设 TTL。一旦漏掉一条失效，副本就是永久的。
  4. 连接池里 GET 与订阅不在同一连接。要用 REDIRECT 指定接收方，否则收不到。
  5. 默认模式追踪海量 key。服务端追踪表膨胀，内存上升；key 空间大时改广播模式。
  6. 广播模式前缀太宽（如 PREFIX "" 或不加前缀）。等于订阅全库变更，推送量爆炸。
  7. 重连后继续用旧副本。重连即断档期，应清空本地缓存重建。
  8. 把 tracking 当成「强一致」。它只是「更快地发现变化」，不是一致性协议。

版本差异（8.x 标注）

CLIENT TRACKING 自 Redis 6.0 引入，7.4 与 8.x 语义一致。8.x 的客户端库与文档组织有调整，命令名与选项未变。

依据：https://redis.io/docs/latest/commands/client-tracking/

八、课后小结

  • tracking 让 Redis 主动通知「你缓存的那份数据变了」；
  • 默认模式记录读过的 key，消息精准、内存随 key 数增长；
  • 广播模式按前缀订阅，内存小、消息多；
  • 失效消息是尽力而为，断线会丢 → 本地必须设短 TTL；
  • 需要 RESP3，连接池场景注意 REDIRECT。

九、思考题

  1. 默认模式下，服务端要为「读过 100 万个不同 key 的一条连接」付出什么代价？

    参考回答：要为这条连接维护一份追踪表，内存随「被追踪 key 数」线性增长（每条记录数十字节量级，100 万条约几十 MB），且每次相关 key 变更都要查表并推送。这个量级不该用默认模式，应改成 BCAST PREFIX 按前缀订阅。

  2. 广播模式订阅 PREFIX user: 时，一个 10 万用户的库会产生多少推送？怎么评估？

    参考回答：推送量与「该前缀下的写次数（含过期删除）」成正比，与「谁读过」无关。评估不要看 key 总数，要看写频率：该前缀每秒 500 次写，就是每个订阅连接每秒 500 条 push，×实例数即网卡与客户端 CPU 的压力。写越密集越不适合宽前缀。

  3. 断线 10 秒期间有 30 次变更，重连后客户端怎么保证数据正确？

    参考回答：官方明确断线期间的失效不补发，所以客户端收不到这 30 条。正确做法是重连后立刻清空本地缓存（全部视为失效）再重建，并用短 TTL 限制最坏窗口；不能靠「等消息补齐」。

  4. 为什么需要 REDIRECT？不用它会出现什么现象？

    参考回答：连接池里执行 GET 的连接与「能收 push 的连接」往往不是同一条，失效消息会推到那条读连接上，而它已归还池中被别的请求复用。不配 REDIRECT 的典型现象是：CLIENT TRACKINGINFO 显示 on，但本地缓存永远不刷新。

  5. 用 tracking 替代自建 Pub/Sub 广播，收益与风险各是什么？

    参考回答：收益是失效由数据变更自动产生、粒度到 key，不用自己设计频道、管理各实例订阅关系，也避免了「改了库忘了发消息」。风险是依赖 RESP3 客户端、消息不保证送达（断线丢）、连接池要配 REDIRECT，并且它只加快发现变化，不是一致性协议。
