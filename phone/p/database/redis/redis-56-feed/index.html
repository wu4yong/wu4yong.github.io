分类：database · redis ｜ 标签：系统课 · Redis · 实战

关注与 Feed：写扩散还是读扩散

推模式下每个粉丝一个收件箱、拉模式下读时聚合｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 用 ZSet 实现「收件箱」并用 ZREMRANGEBYRANK 裁剪；
  2. 说清写扩散与读扩散各自的成本模型，以及大 V 为什么会压垮推模式；
  3. 说清 score 用时间戳时的排序歧义，以及复合 score 的解法。

二、前置知识

RD09（ZSet 与 skiplist）、RD28（ZSet 的编码阈值）、RD36（Pipeline，批量推送时必用）。Feed 场景的核心矛盾是「写的时候多做还是读的时候多做」。

三、理论讲解（官方定义）

官方对 ZSet 的定义（原文要点）：

A sorted set … is a collection of unique elements ordered by an associated score … operations like ZRANGEBYSCORE, ZREMRANGEBYRANK run in logarithmic time.

—— https://redis.io/docs/latest/develop/data-types/sorted-sets/

要用的就是这两点：

  • 按 score 排序：内容发布时间做 score，取「最新 N 条」就是 ZREVRANGE；
  • 对数复杂度：即使收件箱里有十万条，取前 20 条依然很快。

官方对编码的说明同样重要：元素数或元素长度超过阈值时，ZSet 会从 listpack 退化为 skiplist（RD28）。这意味着收件箱一旦变大，单 key 内存与 CPU 都上升，所以必须裁剪。

四、原理拆解

1. 写扩散（推模式）

发布内容：
  for fan in fans:
      ZADD inbox:{fanId} <score> <contentId>

读取：
  ZREVRANGE inbox:{me} 0 19
  • 读极快：一次 ZREVRANGE 就够，不需要合并；
  • 写极贵：粉丝数 × 一次 ZADD。10 万粉丝就是 10 万次写，必须用 Pipeline 分批；
  • 大 V（千万粉丝）在推模式下不可行。

2. 读扩散（拉模式）

发布内容：
  ZADD outbox:{authorId} <score> <contentId>

读取：
  取关注列表 → 对每个 author 取最新 N 条 → 归并排序
  • 写极便宜：一次写入；
  • 读极贵：合并 N 个发件箱，N（关注数）大时延迟高，且每次刷新都要重算。

3. 混合：大 V 走拉、普通用户走推

发布时：
  if 粉丝数 < 阈值（如 10 万）: 逐粉丝 ZADD（推）
  else: 只写自己的 outbox（由读方合并）

读取时：
  ZREVRANGE inbox:{me} 0 19        # 收到的推内容
  + 遍历关注的大 V，各取最新 20 条  # 拉的内容
  → 归并、去重、按时间排序

这是微博类产品的通行做法。阈值是「粉丝数 × 单次推送成本」与「读时合并成本」的平衡点，需要按实际压测确定。

4. 两个实现细节

  • 裁剪：ZREMRANGEBYRANK inbox:{uid} 0 -1001（保留最新 1000 条）。不裁剪，内存随内容无限增长；
  • score 的歧义：同一毫秒发布多条，score 相同，排序不稳定。可用「时间戳 × 1000 + 序号」或「时间戳做整数部分、自增做小数部分」的复合 score。

推模式「读一次、写粉丝数次」与拉模式「写一次、读关注数次」的成本对照、按粉丝规模分流的混合方案，以及裁剪与复合 score 两个实现细节｜依据 Sorted sets 与 ZREMRANGEBYRANK 文档自绘

五、场景说明

  1. 微博式时间线：混合模式，大 V 拉、普通用户推；
  2. 朋友圈：关系闭合、人数少，推模式足够；
  3. 订阅号/公告：读扩散更合适，作者少、读者多；
  4. 不适合：要求「严格时间序 + 全部历史可翻」的场景——收件箱裁剪后历史会丢，需回源到内容库。

六、示例代码/实操步骤

# 1. 关注关系（用 SET 或在 DB 里维护）
127.0.0.1:6379> SADD follow:1001 2001 2002 2003
(integer) 3

# 2. 发布内容：写自己的发件箱
127.0.0.1:6379> ZADD outbox:2001 1700000000000 c_8801
(integer) 1

# 3. 推模式：给粉丝的收件箱各写一条（真实场景用 Pipeline 批量）
127.0.0.1:6379> ZADD inbox:1001 1700000000000 c_8801
(integer) 1

# 4. 读自己的时间线（最新 20 条）
127.0.0.1:6379> ZREVRANGE inbox:1001 0 19 WITHSCORES
1) "c_8801"
2) "1700000000000"

# 5. 拉模式：合并多个发件箱（客户端侧归并）
127.0.0.1:6379> ZREVRANGE outbox:2001 0 19 WITHSCORES
127.0.0.1:6379> ZREVRANGE outbox:2002 0 19 WITHSCORES

# 6. 裁剪：只保留最新 1000 条
127.0.0.1:6379> ZREMRANGEBYRANK inbox:1001 0 -1001
(integer) 0

# 7. 看收件箱规模与编码
127.0.0.1:6379> ZCARD inbox:1001
(integer) 1
127.0.0.1:6379> OBJECT ENCODING inbox:1001
"listpack"                     # 元素多或元素长会变成 skiplist

# 8. 复合 score：时间戳 + 序号（避免同毫秒歧义）
127.0.0.1:6379> ZADD inbox:1001 1700000000000.001 c_8801
(integer) 1

Java 侧怎么落地：Pipeline 推送 + 归并读取

  1. pom 只引 starter，推模式靠 executePipelined，拉模式靠多次 ZREVRANGE 或 ZUNIONSTORE。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. application.yml：把「推/拉的分界」做成配置，别写死在代码里（阈值要靠压测定）：
feed:
  push-threshold: 100000     # 粉丝数低于此值走推
  inbox-keep: 1000           # 收件箱保留条数
  batch-size: 1000           # Pipeline 每批
spring:
  data:
    redis:
      timeout: 300ms
  1. 推送必须分批 Pipeline，1000 条一批，避免 10 万次往返把发布接口拖死：
for (List<Long> batch : partition(fans, batchSize)) {
    redis.executePipelined((RedisCallback<Object>) c -> {
        batch.forEach(f -> c.zSetCommands().zAdd(("inbox:" + f).getBytes(),
                score, contentId.getBytes()));
        return null;
    });
}
  1. 复合 score 用 时间戳 × 1000 + 序号（同一毫秒内的多条内容靠序号区分），用 double 存，读时 ZREVRANGE ... WITHSCORES 再还原时间：
double score = publishMillis * 1000 + (seq % 1000);
  1. 拉模式别在客户端串行读：关注较少用 Pipeline 批量取；关注多（几百）用 ZUNIONSTORE 合并到临时 key（带 EXPIRE 60），再 ZREVRANGE 一次取：
redis.opsForZSet().unionAndStore("tmp:feed:" + uid, outboxKeys, "tmp:feed:" + uid);
redis.expire("tmp:feed:" + uid, Duration.ofSeconds(60));

  1. 裁剪放在写路径末尾（每次推送后 ZREMRANGEBYRANK 0 -1001），或低峰定时任务里做；不裁剪，收件箱会从 listpack 退化成 skiplist（RD28），内存与 CPU 一起涨。

  2. 已读状态另存 HASH/Set（read:{uid} 字段为 contentId），不要塞进收件箱 ZSet，否则时间序语义被破坏。

  3. 读时容错：收件箱里只有 contentId，内容被删/下架要过滤掉再返回，页数不足时回源内容库补齐。

七、常见坑（官方明确说明的限制）

  1. 收件箱不裁剪。内存随发布量线性增长，单个 key 从 listpack 退化为 skiplist 后更贵（RD28）。
  2. 同毫秒发布导致排序不稳定。score 相同则按字典序排，时间线会「跳」；要用复合 score。
  3. 推模式不做 Pipeline。逐条 ZADD 的网络往返会把发布接口拖慢（RD36）。
  4. 大 V 也走推。千万粉丝 = 千万次写，直接打爆 Redis 与发布链路。
  5. 关注关系放 Redis 却无持久化方案。关注是业务数据，Redis 只是加速层，主数据要在库里。
  6. 用 KEYS inbox:* 做统计。O(N) 阻塞主线程，必须用 SCAN 或维护计数器。
  7. 收件箱与内容详情分离但无一致性设计。收件箱里的 contentId 指向的内容可能已删除，读时要容错。
  8. 不做阅读状态存储。已读/未读如果也塞进同一个 ZSet，会破坏「按时间排序」的语义，应另用 HASH/Set。

版本差异（8.x 标注）

ZADD/ZREVRANGE/ZREMRANGEBYRANK 语义在 7.4 与 8.x 一致；编码阈值（zset-max-listpack-entries 等）在 7.2 起把 ziplist 换为 listpack。

依据：https://redis.io/docs/latest/develop/data-types/sorted-sets/

八、课后小结

  • 收件箱 = ZSet，score 是时间，取最新靠 ZREVRANGE；
  • 推模式读快写贵，拉模式写快读贵，混合按粉丝规模分流；
  • 收件箱必须裁剪（ZREMRANGEBYRANK 保留 N 条）；
  • score 用时间戳会有同毫秒歧义，用复合 score；
  • 关注关系是业务数据，Redis 只做加速。

九、思考题

  1. 一个 10 万粉丝的作者发一条内容，推模式要写多少次？用 Pipeline 分几批合适？

    参考回答：10 万次 ZADD（每个粉丝一次）。按每批 1000 条计算是 100 批；实际可调大到 2000～5000 条一批，把批次数压到 20～50，同时注意单批过大时单连接输出缓冲会膨胀。

  2. 读扩散时关注 500 人，一次刷新要发多少条命令？怎么优化？

    参考回答：500 条 ZREVRANGE（每个作者一条），串行执行就是 500 次往返，P99 直接崩。优化：用 Pipeline 一次发 500 条；或 ZUNIONSTORE 把 500 个 outbox 合并到带 TTL 的临时 key，再一次 ZREVRANGE 取 20 条。

  3. 收件箱保留 1000 条，用户翻到第 50 页怎么办？

    参考回答：20 条一页时 1000 条正好只够 50 页，第 50 页之后没有数据可给。正确做法是「深度翻页回源」：超过 N 页后改查内容库（按时间倒序 + 游标分页），收件箱只服务最近的热数据。

  4. 同一毫秒两条内容，score 相同时 ZREVRANGE 的顺序由什么决定？

    参考回答：score 相同时按成员的字典序（lexicographical order）排序，与发布先后来无关，于是时间线会出现「顺序跳」甚至前后刷新不一致。解法是复合 score：时间戳 × 1000 + 序号，让每条内容都有唯一 score。

  5. 你会把「已读」存在哪里？为什么不能放进同一个 ZSet？

    参考回答：另存 HASH（read:{uid} → contentId=1）或 Set/Bitmap。ZSet 的 score 已被「发布时间」占用，塞已读就得改 score 或加成员，直接破坏「按时间排序、按排名取最新 N 条」的语义，裁剪与分页也会算错。
