AOF 重写与混合持久化

重写期间的双写结构、触发条件、7.0 多文件 AOF 与 RDB preamble｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 讲清「重写」不是压缩文件字节，而是按当前数据状态重算一份最小命令集；
  2. 理解重写期间为什么不能停服、新写入怎么不丢（双写缓冲 / 7.0 的增量文件）；
  3. 掌握 auto-aof-rewrite-percentage 与 min-size 两个触发阈值，以及 aof-use-rdb-preamble 混合持久化的收益与代价。

二、前置知识

RD14（RDB）与 RD15（AOF 与 appendfsync）。重写要用到 fork（RDB 那套机制），也要清楚 AOF 为什么「又大又慢」（上一讲）。

三、理论讲解（官方定义）

官方对重写的定义（原文）：

AOF rewriting … Redis is able to automatically rewrite the AOF in background when it gets too big. The rewrite is completely safe … while the rewrite is in progress Redis continues to append new commands to the old AOF file.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/

三个要点：

  • rewrite in background：后台子进程执行，主进程照常服务；
  • gets too big：由体积增长触发，不是定时任务；
  • continues to append to old AOF：期间新命令写进旧文件（并进入重写缓冲 / 新的增量文件），重写完成后合并。

四、原理拆解

1. 重写到底在做什么

一个 key 的历史可能是：

SET k v1
SET k v2
INCR k            # 变成 3
INCR k            # 变成 4
INCR k            # 变成 5

重写之后，这份历史被压缩成等价的最小命令集：

SET k 5

所以重写的本质是：读当前内存里的最终状态，生成「重放出这个状态所需的最少命令」，而不是把旧文件打包压缩。

2. 重写期间的双写结构（经典实现）

  1. 主进程 fork 出子进程，子进程拿到 fork 时刻的数据视图；
  2. 子进程把这些数据写成新的 AOF 文件（临时文件）；
  3. 与此同时，主进程继续处理写命令：既追加到旧 AOF 文件（保证一旦子进程失败还能用旧文件恢复），也追加到重写缓冲区（aof_rewrite_buf）；
  4. 子进程写完，主进程把重写缓冲区里的内容追加到新文件末尾；
  5. 新文件 rename 替换旧文件，重写结束。

第 3 步的「双写」是重写安全性的核心：任何时刻都有一份可用的完整 AOF。

3. 7.0 的多文件 AOF（MP-AOF）

7.0 起改成目录结构，文件分工如下：

文件 内容
appendonly.aof.1.base.rdb（或 .base.aof） 基线：全量数据（默认是 RDB 格式，见混合持久化）
appendonly.aof.1.incr.aof 增量：基线之后的所有写命令
appendonly.aof.manifest 清单：记录哪些文件属于当前 AOF，加载顺序是什么

带来的直接好处：

  • 重写只需重写 base，增量文件可以继续追加，不再需要把增量塞进大块内存缓冲（老实现的 aof_rewrite_buf 在写入猛时能吃几百 MB）；
  • 清单化管理，加载时按 manifest 顺序读，运维也能一眼看清「谁是谁」；
  • 备份时必须整个目录一起拷，只拷 incr.aof 会丢基线。

4. 触发条件：两个阈值同时满足

auto-aof-rewrite-percentage 100      # 当前 AOF 比上次重写后「增长一倍」时
auto-aof-rewrite-min-size 64mb       # 且总体积超过 64 MB

判定逻辑是「与」：体积得先过 64 MB 这个地板，再看增长率是否达到 100%。所以小实例（几 MB）永远不会自动触发——这是刻意的，避免小文件反复重写浪费 CPU。

手动触发：BGREWRITEAOF。它也是后台执行，返回 Background append only file rewriting started。

5. 混合持久化：aof-use-rdb-preamble

默认 yes。含义是：AOF 的 base 部分用 RDB 二进制格式存，后面才是命令日志。

  • 恢复时先加载 RDB 段（快，直接重建内存），再重放增量命令（少，因为基线已经很新）；
  • 相比「纯命令重放几十亿条」，恢复时间从「分钟级」降到「秒级」；
  • 代价：AOF 文件开头不再是可读文本，cat 看不到命令，也不能手工编辑；排查要理解这个结构。

五、场景说明

  1. 写量大且长期运行的实例：AOF 会持续膨胀，必须让自动重写生效（默认配置即可，别乱调大 min-size）；
  2. 重启恢复时间敏感：开混合持久化，把「重放几千万条命令」变成「加载快照 + 少量增量」；
  3. 容器/云盘备份：备份脚本要拷整个 appendonlydir，并校验 manifest；
  4. 迁移：同版本搬迁时 base.rdb + incr.aof 一起拷，比重放命令快。

六、示例代码/实操步骤

# 1. 手动触发重写
127.0.0.1:6379> BGREWRITEAOF
Background append only file rewriting started

# 2. 观察重写状态与结果
127.0.0.1:6379> INFO persistence
# aof_rewrite_in_progress:1
# aof_rewrite_scheduled:0
# aof_last_bgrewriteaof_status:ok
# aof_last_write_status:ok

# 3. 触发阈值是怎么配的
127.0.0.1:6379> CONFIG GET auto-aof-rewrite-percentage
1) "auto-aof-rewrite-percentage"
2) "100"
127.0.0.1:6379> CONFIG GET auto-aof-rewrite-min-size
1) "auto-aof-rewrite-min-size"
2) "67108864"                    # 64 MB

# 4. 体积对比：重写前 vs 重写后
127.0.0.1:6379> INFO persistence
# aof_current_size:838860800      # 800 MB
# aof_base_size:838860800
# 重写完成后
# aof_current_size:96468992       # 92 MB，同一份数据

# 5. 混合持久化开关
127.0.0.1:6379> CONFIG GET aof-use-rdb-preamble
1) "aof-use-rdb-preamble"
2) "yes"

# 6. 目录结构：备份必须整目录拷
$ ls -l /var/lib/redis/appendonlydir/
appendonly.aof.manifest
appendonly.aof.1.base.rdb
appendonly.aof.1.incr.aof
$ cat /var/lib/redis/appendonlydir/appendonly.aof.manifest
file appendonly.aof.1.base.rdb seq 1 type b
file appendonly.aof.1.incr.aof seq 1 type i

# 7. 重写期间别做的事：不要同时跑 BGSAVE
# 同时 fork 两次会显著放大 CoW 内存与磁盘 IO
127.0.0.1:6379> INFO persistence
# rdb_bgsave_in_progress:1
# aof_rewrite_in_progress:1      # 两者并发，内存风险最高

七、常见坑（官方明确说明的限制）

  1. 重写也要 fork，同样有 CoW 内存放大的问题。数据 40 GB 的实例，重写期间额外内存可能接近总量的一半以上，maxmemory 必须留余量。
  2. 重写期间新旧文件并存：磁盘占用会短暂翻倍（旧 AOF + 新 AOF）。磁盘剩余空间不足时重写失败，aof_last_bgrewriteaof_status 会变成 err。
  3. auto-aof-rewrite-percentage 100 是相对「上次重写后大小」，不是相对「数据量」。数据量小但写入频繁（比如一直在 INCR 同一个小 key）也会触发重写。
  4. min-size 调太大 → 文件长期膨胀；调太小 → 低峰期反复重写，吃 CPU 与磁盘。默认 64 MB 是经验值，不必追求「更激进」。
  5. 7.0 起备份必须拷整个 appendonlydir。只拷 incr.aof 等于丢全量基线，恢复出来是残缺数据。
  6. 混合持久化让 AOF 不再是纯文本。脚本里 grep/cat 找命令的做法会失效，必须改用 redis-check-aof 或 redis-cli 观察。
  7. 不要同时跑 BGSAVE 与 BGREWRITEAOF：两个 fork 同时存在，CoW 内存与 IO 峰值叠加，是最容易触发 OOM 的时刻。
  8. 重写完成后的旧文件删除是异步的，磁盘告警可能滞后几秒，监控阈值要给缓冲。

版本差异（8.x 标注）

7.0 引入 MP-AOF（多文件 + manifest），8.x 沿用；aof-use-rdb-preamble 在 7.x 默认 yes。若环境是 6.x，AOF 仍是单文件 + aof_rewrite_buf 双写，备份脚本与磁盘预估都要按「单文件翻倍」来算。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/

八、课后小结

  • 重写 = 按当前数据重算最小命令集，不是压缩字节；
  • 经典实现靠「双写」（旧 AOF + 重写缓冲）保证任何时刻都有一份可恢复文件；
  • 7.0 起改为 base + incr + manifest 的多文件结构，重写只换 base，省掉大块内存缓冲；
  • 自动触发需要 auto-aof-rewrite-percentage（默认 100）与 min-size（默认 64 MB）同时满足；
  • aof-use-rdb-preamble 默认 yes，base 用 RDB 格式，恢复显著加快，代价是不可读文本；
  • 重写要 fork，CoW 与磁盘翻倍是必须预留的资源。

九、思考题

  1. 一个 key 被 INCR 一千万次，重写后 AOF 里还剩几条命令？为什么？
  2. 重写期间主进程写入的命令，如果子进程写完时还没合并进新文件就崩溃了，数据会丢吗？
  3. 为什么 7.0 的多文件 AOF 能省掉「重写缓冲区」？它的增量写到哪去了？
  4. 磁盘只剩 30%、AOF 800 MB，这时自动重写会发生什么？该在监控上加哪条告警？
  5. 同时执行 BGSAVE 与 BGREWRITEAOF，内存与磁盘各会发生什么？为什么这是危险组合？
