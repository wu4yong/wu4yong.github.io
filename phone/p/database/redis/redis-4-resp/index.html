分类：database · redis ｜ 标签：系统课 · Redis · 缓存

RESP 协议与客户端选型

一条 SET 命令的 RESP 编码 + 五种响应类型 + 客户端选型｜依据 Redis 7.4 RESP / Clients 文档自绘

一、学习目标

  1. 能手写出一个 RESP 请求帧，并用 nc 直接发出去看响应；
  2. 记住 RESP2 的五种响应类型与 RESP3 的扩展类型，知道 HELLO 3 在做什么；
  3. 能给一个 Java/Go 项目选对客户端，并把连接池的关键参数配明白。

二、前置知识

RD01 的最小闭环、RD02 的 redis-cli 基本用法。

三、理论讲解（官方定义）

官方对协议的定义：

The Redis protocol, RESP (REdis Serialization Protocol), is a binary-safe protocol… Clients send commands to a Redis server as an array of bulk strings. The reply is encoded as one of the RESP types.

—— https://redis.io/docs/latest/develop/reference/protocol-spec/

两个词值得停一下：binary safe（值可以是任意字节，key 也一样）和 array of bulk strings（请求永远是一个数组，第一个元素是命令名）。这解释了为什么「命令名大小写不敏感」而「key 大小写敏感」——前者是命令表查找，后者是键空间字符串比较。

四、原理拆解

1. 请求帧的构成

发一条 SET name redis7，客户端实际发出的字节是三段长度前缀 + 内容：

*3\r\n     ← 数组，3 个元素
$3\r\nSET\r\n       ← 长度 3 的 bulk
$4\r\nname\r\n      ← 长度 4
$6\r\nredis7\r\n    ← 长度 6

为什么用「长度前缀」而不是「换行分隔」？因为值里可能本身就含 \r\n（比如一段 JSON 或二进制），长度前缀让解析器无需转义——这是 binary safe 的实现代价。

2. 五种响应类型（RESP2）

前缀
类型
示例
语义

+OK
状态短语，不携带数据

Error
-ERR unknown command
错误，客户端要识别成一个异常
:
Integer
:1000
整数，INCR 返回值就是它
$
Bulk string
$6\r\nredis7\r\n

*
Array
*2\r\n$3\r\nfoo\r\n...
数组；*-1 表示 nil 数组

一个常被忽略的点：GET 一个不存在的 key 返回的是 $-1 空 bulk，不是错误。这正是「缓存未命中」在协议层的表现，M7 讲缓存穿透时会回到这里。

3. RESP3 做了什么

HELLO 3 会把连接切到 RESP3，新增类型包括 map（%）、set（~）、double（,）、boolean（#）、null（_）、push（>）等。

对客户端实现的意义：RESP2 里 CONFIG GET 返回的是扁平数组，客户端要自己两两配对；RESP3 直接返回 map。此外 > push 类型让客户端缓存（client-side caching，M7 的 RD45）能异步收到失效通知。

官方明确说明：默认仍是 RESP2，切 RESP3 需要客户端显式握手（Redis 7.x 的多数客户端已支持，但并非默认开启）。

五、场景说明

  • 排障：线上某个客户端说「命令发出去了但没响应」，用 nc 手发一帧能判断是网络、协议还是业务代码问题；
  • 性能：批量场景用 pipelining 把 N 次往返压成 1 次（RD36 详解）；
  • 选型：同步阻塞的 Jedis + 连接池适合传统 Spring 应用；Lettuce 基于 Netty、连接线程安全，适合响应式或高并发场景。

六、示例代码/实操步骤

手工发一帧（不依赖任何客户端）

# 用 nc 直接说 RESP，验证协议理解
printf '*3\r\n$3\r\nSET\r\n$4\r\nname\r\n$6\r\nredis7\r\n' | nc 127.0.0.1 6379
# 返回：+OK

printf '*2\r\n$3\r\nGET\r\n$4\r\nname\r\n' | nc 127.0.0.1 6379
# 返回：$6
#      redis7

# 读一个不存在的 key
printf '*2\r\n$3\r\nGET\r\n$7\r\nmissing\r\n' | nc 127.0.0.1 6379
# 返回：$-1

Redis 还支持 inline command（直接 SET name redis7 加回车），只用于调试；官方建议客户端一律用 RESP 数组格式。

切换 RESP3 并观察差异

连接池骨架（Java / Jedis 口径）

// 关键不是 API，而是这五个参数的生产取值
JedisPoolConfig cfg = new JedisPoolConfig();
cfg.setMaxTotal(64);        // 池内最多连接数，按「并发线程数 × 单次耗时占比」估
cfg.setMaxIdle(32);         // 空闲连接上限，太大则在低峰期也白占服务端 maxclients
cfg.setMinIdle(8);          // 预热下限，避免冷启动时集中建连
cfg.setMaxWait(Duration.ofMillis(500));  // 借不到连接时的等待上限：宁可快速失败
cfg.setTestOnBorrow(false); // 每次借出都 PING 会额外增加一次往返
JedisPool pool = new JedisPool(cfg, "127.0.0.1", 6379, 1000, "S3cretForClass");

七、常见坑（官方明确说明的限制）

  1. * 数组的长度必须准确。长度写错，服务端会按声明长度解析，剩下的字节被当成新命令，出现「响应错位」这种极难查的现象。
  2. $ 后面的长度是字节数不是字符数。中文 key 用 strlen 算，别按字符数数，否则解析失败。
  3. Jedis 连接不是线程安全的，多线程共享一个 Jedis 实例会出现协议错位；Lettuce 的 StatefulRedisConnection 是线程安全的，可以共享。
  4. timeout 设成无限等于给自己埋雷。Redis 单线程执行，某个慢命令会拖住整条连接；官方在客户端文档里建议设置合理的 socket timeout，并配合重试策略。
  5. 切换 RESP3 后，部分客户端库的输出类型会变（比如 CONFIG GET 从数组变 map），升级前要跑一遍回归。

版本差异（8.x 标注）

RESP3 与 HELLO 在 6.0 引入，7.x 沿用；8.x 没有改动协议类型集合，但客户端生态对 RESP3 的默认支持更普遍。主线仍按 RESP2 讲，涉及 push 语义时再点名 RESP3。

依据：https://redis.io/docs/latest/develop/reference/protocol-spec/

八、课后小结

  • 请求永远是「命令名 + 参数」组成的 bulk string 数组，长度前缀保证 binary safe；
  • RESP2 五种类型：+ - : $ *；$-1 就是「不存在」；
  • RESP3 增加 map/set/double/push，HELLO 3 显式切换，默认仍是 RESP2；
  • 选客户端的三个判断点：线程安全、是否异步、连接池是否可控。

九、思考题

  1. 用 nc 发 *3\r\n$3\r\nGET\r\n$4\r\nname\r\n（少一个元素）会发生什么？为什么这种错位在生产上很难定位？
  2. 为什么 GET 不存在 key 返回空 bulk，而 INCR 一个不存在的 key 却直接当成 0 自增成功？两者对「不存在」的处理策略差异，对业务代码意味着什么？
  3. 一个 Spring 应用用 Jedis 单例注入到多线程 Controller，压测时偶发 ERR Protocol error，根因是什么？
