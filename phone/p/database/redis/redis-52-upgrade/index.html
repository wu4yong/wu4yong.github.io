redis-52-版本升级

分类：database · redis ｜ 标签：系统课 · Redis · 运维

版本升级 6 → 7 → 8

从库先升、主从切换、回滚预案与两代 breaking change｜依据 Redis 7.x/8.x 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 列出 6→7 的三项硬变化（AOF 目录结构、Functions、Sharded Pub/Sub）；
  2. 说清 8.x 的许可变化对商用的影响；
  3. 设计一条「从库先升 → 主从切换 → 可回滚」的升级路径，而不是直接换二进制。

二、前置知识

RD14–RD16（RDB/AOF 与重写）、RD35（Functions）、RD37（Pub/Sub）、RD48（ACL）。升级的难点几乎都不是「新功能不会用」，而是「旧配置在新版本里不合法」。

三、理论讲解（官方定义）

AOF 的结构变化（7.0 起），官方文档原文要点：

Starting with Redis 7.0, AOF is stored in a directory (appendonlydir) containing a manifest file and multiple AOF files (base + incr + history).

—— https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/

Functions（7.0 引入），官方原文要点：

Redis Functions are an evolution of Lua scripts … FUNCTION LOAD, FCALL … functions are persisted with the dataset and replicated.

—— https://redis.io/docs/latest/develop/interact/programmability/functions-intro/

Sharded Pub/Sub（7.0 引入），官方原文要点：

SSUBSCRIBE / SPUBLISH … messages are sharded across slots, so Pub/Sub scales with the cluster.

—— https://redis.io/docs/latest/develop/interact/pubsub/

8.x 的许可变化：8.0 起采用 AGPLv3 / SSPL 双许可（此前 7.x 及更早为 BSD）。这对「把 Redis 打包进商业产品」或「以服务形式对外提供」的场景是实质性变化，升级前需要法务评估，而不是技术评估。

这三类变化分别对应：数据文件格式、编程接口、集群行为、合规。

四、原理拆解

1. 升级的顺序

① 读 Release Notes，逐条核对 breaking change
② 从库先升（主库保持旧版本，观察复制与读写）
③ 主从切换（让升级后的从库升主，原主库降为从库并升级）
④ 回滚预案：旧版本二进制 + 旧配置文件必须随时可用

为什么不先升主库：主库先升意味着「一旦不兼容，全站不可用」；从库先升把风险限制在「读请求」范围内。

2. 6 → 7 的兼容性检查清单

检查项
原因
AOF 目录结构
7.0 改为 appendonlydir，旧监控脚本/备份脚本按单文件路径会失效
ziplist → listpack
7.0 起 OBJECT ENCODING 返回 listpack，依赖编码判断的脚本要改（RD28）
客户端库版本
老客户端可能不认识新命令/新错误码
集群工具
redis-cli --cluster 的参数在新版本有变化
Functions
若使用，要规划「脚本迁移到 function」的路径

3. 7 → 8 的额外注意

  • 许可：AGPLv3/SSPL，商用分发必须评估；
  • 配置项：部分默认值与参数名有调整，升级前用 --dry-run 或预发环境跑一遍；
  • 客户端生态：8.x 的工具链与客户端适配需要时间，别在生产做「第一个吃螃蟹的」；
  • 回滚成本：一旦写入 8.x 特有的数据格式或配置，回退到 7.x 可能失败。

4. 回滚不是「降版本启动」

很多人以为回滚就是「把旧二进制换回去重启」。实际问题：

  • AOF：7.x 的 appendonlydir 结构，6.x 不认识；
  • RDB：新版本写的 RDB 版本号更高，旧版本可能拒绝加载；
  • 配置：新版本接受的配置项，旧版本可能直接启动失败。

所以回滚预案要包含「数据回退路径」：保留升级前的 RDB/AOF 备份，以及「回滚后的数据补齐方案」。

读变更→升从库→主从切换→留回滚四步、6→7 的三处实质变化、升级前后必查的四项，以及「回滚不等于换回二进制」与 7→8 的许可变化｜依据 Persistence、Functions 与许可说明自绘

五、场景说明

  1. 小版本升级（7.4 → 7.6）：风险低，从库先升即可；
  2. 大版本升级（6 → 7）：必须预发演练，重点验证 AOF 与客户端；
  3. 跨许可版本（7 → 8）：先法务、再技术；
  4. 不适合：在有状态集群上「滚动重启 + 直接换版本」而不做兼容性验证。

六、示例代码/实操步骤

# 1. 升级前：确认当前版本与配置来源
127.0.0.1:6379> INFO server
# redis_version:6.2.14
# config_file:/etc/redis/redis.conf

# 2. 备份（RDB + AOF 目录整体）
$ redis-cli BGSAVE
$ cp -r /var/lib/redis /backup/redis-$(date +%F)

# 3. 从库升级（换二进制后启动，观察复制）
$ systemctl stop redis
$ apt install -y redis-server=7.4.*
$ systemctl start redis
127.0.0.1:6379> INFO replication
# role:slave
# master_link_status:up
# slave_repl_offset:...          ← 必须持续增长

# 4. 主从切换
127.0.0.1:6379> REPLICAOF NO ONE       # 在升级后的从库上执行
# 客户端切流量到新主库
127.0.0.1:6379> REPLICAOF 10.0.1.11 6379   # 原主库降级并指向新主

# 5. 验证 AOF 新结构（7.0+）
$ ls /var/lib/redis/appendonlydir
# appendonly.aof.1.base.rdb  appendonly.aof.1.incr.aof  appendonly.aof.manifest

# 6. 验证编码返回值变化（6.x 是 ziplist，7.x 是 listpack）
127.0.0.1:6379> OBJECT ENCODING mylist
"listpack"

# 7. 集群体检（升级后必做）
$ redis-cli --cluster check 10.0.1.10:6379

Java 侧怎么落地：客户端版本 + 灰度切流

  1. pom 先确认客户端版本，Redis 7/8 需要 Lettuce 6.2+ 或 Jedis 5.x；Spring Boot 3.x 默认 Lettuce 已满足，2.x 要显式升版本。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<dependency>
  <groupId>org.apache.commons</groupId>
  <artifactId>commons-pool2</artifactId>
</dependency>
  1. application.yml 用「可切换的双集群」写法，灰度期新旧两套并存，切流量只改一个配置项：
redis:
  target: new            # old / new，配置中心热更新
  old: { host: 10.0.0.11, port: 6379 }
  new: { host: 10.0.0.21, port: 6379 }
spring:
  data:
    redis:
      timeout: 500ms
      lettuce:
        pool: { max-active: 64, max-wait: 200ms }
  1. 连接工厂按配置项构建，切换时重建 LettuceConnectionFactory 并 afterPropertiesSet()，不要只改 host 字符串：
@Bean
@RefreshScope
LettuceConnectionFactory redisConnectionFactory(RedisProps props) {
    RedisStandaloneConfiguration cfg =
        new RedisStandaloneConfiguration(props.current().getHost(), props.current().getPort());
    LettuceConnectionFactory f = new LettuceConnectionFactory(cfg);
    f.afterPropertiesSet();
    return f;
}

  1. 启动自检要比版本与关键命令：连上后 INFO server 取 redis_version，并试跑一次业务真正用到的命令（如 FCALL、SSUBSCRIBE），失败就快速退出，别半可用。

  2. 灰度按流量比例或按租户切，先 5% → 30% → 100%；每档观察错误率、P99、evicted_keys 与复制状态，异常就一键切回 old。

  3. 升级前把监控脚本也过一遍：解析 appendonlydir、OBJECT ENCODING 返回值的脚本最容易静默失效——它不报错，只是永远取到 0。

七、常见坑（官方明确说明的限制）

  1. 直接从主库升级。一旦不兼容，全站不可用；应先升从库。
  2. 按旧路径备份 AOF。7.0 起是目录结构，脚本要改。
  3. 依赖 OBJECT ENCODING 的旧判断。ziplist 已变 listpack，监控与容量脚本会误判。
  4. 忽略许可变化。8.x 是 AGPLv3/SSPL，商用分发要先过法务。
  5. 认为回滚 = 换二进制。数据格式与配置项都可能不兼容，回滚要有数据方案。
  6. 不读 Release Notes。breaking change 往往藏在「默认值变更」里，最难排查。
  7. 跳过预发演练。用真实数据量验证 RDB/AOF 加载、客户端协议、集群槽状态。
  8. 升级后不复查监控脚本。字段名、编码、目录结构都可能变化，静默失效最危险。

版本差异（8.x 标注）

本节本身就是版本差异的汇总。写正文与配置时统一以 7.4 为主线，遇到 8.x 的差异单独标注；涉及许可、默认值的判断必须以对应版本的官方 Release Notes 为准。

依据：https://redis.io/docs/latest/

八、课后小结

  • 升级顺序：读变更 → 升从库 → 主从切换 → 保留回滚；
  • 6→7 三大变化：AOF 目录结构、Functions、Sharded Pub/Sub；
  • 7→8 首要变化是许可（AGPLv3/SSPL），其次是工具链与默认值；
  • 回滚要包含数据路径，不只是二进制；
  • 预发用真实数据演练，是唯一可靠的验证方式。

九、思考题

  1. 为什么升级要先升从库？如果只有单实例怎么办？

    参考回答：从库只承接读、且可随时切回主库，先升它能把兼容性问题限制在「读路径 + 复制链路」上，出问题影响面最小。单实例只能用「停机窗口 + 完整备份 + 预发验证」：先在等同数据量的预发环境跑一遍加载与压测，再在低峰停机升级，回滚依赖备份而不是版本回退。

  2. 7.0 的 AOF 目录结构会让哪些既有脚本失效？

    参考回答：所有按「单个 appendonly.aof 文件」写的脚本都会失效——备份脚本（cp appendonly.aof）、体积监控、redis-check-aof 的旧调用方式、以及清理脚本。7.0 起是 appendonlydir/ 下的 base/incr/manifest 多文件，必须按目录备份、按 manifest 判断。

  3. ziplist → listpack 会影响哪些监控项？

    参考回答：OBJECT ENCODING 的返回值、以及以它为判据的容量估算与告警脚本。7.0 起 Hash/List/ZSet 的紧凑编码返回 listpack 而不是 ziplist，凡是字符串匹配 ziplist 的脚本会一直判为「非紧凑编码」，产生误报或漏报。

  4. 8.x 的许可变化，对「自用」和「对外提供服务」的影响有何不同？

    参考回答：内部自用通常仍在 AGPL/SSPL 的容忍范围（不分发、不对外提供 Redis 服务）。一旦把 Redis 打包进对外产品或对外提供托管服务，AGPLv3 的源码开放义务与 SSPL 的服务化条款就会被触发，需要法务评估或改用商业授权/替代方案。

  5. 设计一份「升级失败回滚」的操作清单，至少包含五项。

    参考回答：① 保留旧版本二进制与旧版配置文件（含 appendonlydir 相关项）；② 升级前完成一次可验证的 RDB + AOF 备份并抽检可加载；③ 明确数据回退路径（旧版本无法读新格式时，用备份恢复而非降版本启动）；④ 客户端一键切回旧集群的开关与演练记录；⑤ 回滚判据（错误率、P99、复制状态阈值）与决策人；⑥ 回滚后复查监控脚本是否仍有效。
