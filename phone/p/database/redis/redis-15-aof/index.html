AOF 与三种 appendfsync

命令 → aof_buf → page cache → 磁盘，以及 always/everysec/no 的可靠性差异｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 讲清 AOF 是「命令重放日志」，和 RDB 的「数据快照」是两种根本不同的思路；
  2. 把 always / everysec / no 三种 appendfsync 的可靠性、吞吐代价各说清楚，并能给业务定一个；
  3. 知道 AOF 开启方式、文件体积与恢复速度的代价，理解「开了 AOF 就等于不丢数据」为什么是错的。

二、前置知识

RD14（RDB 快照）。本讲与上一篇是同一枚硬币的两面：RDB 存「数据长什么样」，AOF 存「数据是怎么变成这样的」。

三、理论讲解（官方定义）

官方定义（原文）：

AOF persistence logs every write operation received by the server. These operations can then be replayed again at server startup, reconstructing the original dataset.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/

三个要点：

  • logs every write operation：记录的是命令，不是数据；
  • replayed at startup：启动时逐条重放，重建数据集；
  • write operation：只记写命令，读命令不记（SELECT 这类少数命令除外，官方有说明）。

开关与默认值：

配置项 默认值 含义
appendonly no AOF 默认关闭，需要显式开启
appendfsync everysec 刷盘策略
appendfilename appendonly.aof 文件名（7.0 起实际是 appendonlydir/ 目录）
aof-load-truncated yes 加载时容忍末尾被截断
no-appendfsync-on-rewrite no 重写期间是否暂停 fsync

四、原理拆解

1. 写入链路：四个站

一条写命令的执行与落盘路径：

  1. 命令执行：改内存，同时把这条命令追加到进程内的 aof_buf；
  2. aof_buf：进程内存缓冲区，攒着一批待写命令；
  3. write() 到 page cache：把缓冲写进内核页缓存（此时还在内存里，掉电即丢）；
  4. fsync()：内核把页缓存真正刷到磁盘。只有这一步完成，才算「落盘」。

关键认知：write() 成功 ≠ 数据在磁盘上。这是理解三种 appendfsync 的前提，也是很多「我明明写了 1 万条只丢了 3 条」现象的解释。

2. 三种 appendfsync 的真实差别

策略 行为 最坏丢失 吞吐影响 官方定位
always 每条写命令都 fsync 最多丢一条命令（原则上为 0） 显著下降，通常一个数量级 极少数「不能丢」的场景
everysec 后台线程每秒 fsync 一次 约 1 秒的写入 影响很小 默认值，绝大多数业务
no 只 write()，不主动 fsync 由内核决定，通常 30 秒量级，且不可预测 最快 可容忍大量丢失的纯缓存

everysec 的「约 1 秒」是官方口径，不是精确承诺——它取决于后台线程的调度与磁盘状况，磁盘卡顿时可能超过 1 秒。

no 也不是「不落盘」，而是「交给操作系统」。内核的脏页回写策略决定了最终落盘时间，所以你无法用它承诺任何 RPO。

3. 为什么 AOF 比 RDB 慢、比 RDB 大

  • 慢：每次写都要多一次 write，always 还多一次 fsync；而 RDB 是批量顺序写；
  • 大：AOF 记录的是命令序列。同一个 key 被 INCR 一万次，就有一万条命令；RDB 只存最终值；
  • 恢复慢：启动时要把命令一条条重放，数据量大时可能几分钟到几十分钟，而 RDB 是直接加载内存镜像。

这三点正是「AOF 重写」与「混合持久化」存在的原因——下一篇的主角。

4. AOF 与 RDB 的加载优先级

启动时若同时存在 RDB 与 AOF，只要 appendonly yes，就优先加载 AOF（因为它更完整）。这条规则常导致「我有 dump.rdb 但数据少了」的困惑：其实加载的是 AOF。排查时先确认 appendonly 的取值。

五、场景说明

  1. 订单/账务类主数据：appendonly yes + appendfsync always（或 everysec 配合业务侧补偿），RPO 尽量贴近 0；
  2. 缓存 + 需要快速重建：appendonly no，只留 RDB，重启慢一点但文件小；
  3. 既要可靠又要恢复快：appendonly yes + 混合持久化（下一篇），这是 7.x 的主流配置；
  4. 临时数据/可重算数据：可以完全不开持久化，靠上游重算。

判断标准只有一条：丢多少数据你能接受。能接受「分钟级」就用 RDB；只能接受「秒级」必须 AOF；要求「一条不丢」得上 always 并接受吞吐代价。

六、示例代码/实操步骤

# 1. 开启 AOF（运行时可动态开，但最好改配置文件）
127.0.0.1:6379> CONFIG GET appendonly
1) "appendonly"
2) "no"
127.0.0.1:6379> CONFIG SET appendonly yes
OK
127.0.0.1:6379> INFO persistence
# aof_enabled:1
# aof_rewrite_in_progress:0
# aof_last_bgwriteaof_status:ok

# 2. 查看与切换刷盘策略
127.0.0.1:6379> CONFIG GET appendfsync
1) "appendfsync"
2) "everysec"
127.0.0.1:6379> CONFIG SET appendfsync always
OK
# 注意：切到 always 会立刻带来明显延迟上升，先在预发环境量一下

# 3. 观察 AOF 文件与目录（7.0 起是目录）
$ ls -l /var/lib/redis/appendonlydir/
-rw-r--r-- 1 redis redis  104857600 appendonly.aof.1.base.rdb
-rw-r--r-- 1 redis redis   20480000 appendonly.aof.1.incr.aof
-rw-r--r-- 1 redis redis        100 appendonly.aof.manifest

# 4. AOF 相关指标
127.0.0.1:6379> INFO persistence
# aof_current_size:125829120
# aof_base_size:104857600
# aof_pending_rewrite:0
# aof_buffer_length:0
# aof_delayed_fsync:0            —— 每秒刷盘被延迟的次数，>0 说明磁盘跟不上

# 5. 末尾被截断时如何处理
127.0.0.1:6379> CONFIG GET aof-load-truncated
1) "aof-load-truncated"
2) "yes"                         # 容忍截断，加载到最后一个完整命令并告警

# 6. 重写期间是否暂停 fsync（默认不暂停）
127.0.0.1:6379> CONFIG GET no-appendfsync-on-rewrite
1) "no-appendfsync-on-rewrite"
2) "no"

# 7. 校验 AOF 完整性（shell 里）
$ redis-check-aof /var/lib/redis/appendonlydir/appendonly.aof.1.incr.aof
$ redis-check-aof --fix /var/lib/redis/appendonlydir/appendonly.aof.1.incr.aof

aof_delayed_fsync 是一个极有价值的指标：它统计「本该每秒刷盘但被拖后」的次数。持续大于 0 说明磁盘 IO 已经跟不上写入，此时 everysec 的「1 秒窗口」实际会被拉长。

七、常见坑（官方明确说明的限制）

  1. appendonly 默认是 no。很多人以为「Redis 默认就有 AOF」，结果机器掉电后按 RDB 恢复，丢了十几分钟数据。
  2. everysec 不是「最多丢 1 秒」的硬承诺，是「正常情况下约 1 秒」。磁盘卡住、aof_delayed_fsync 增长时，实际窗口会变长。
  3. no 不等于不写盘，等于「不由 Redis 决定何时写盘」。用它做关键数据存储，等于把 RPO 交给内核。
  4. always 的代价是延迟与吞吐，而不是「绝对不丢」。在某些极端情况（磁盘坏了、内核缓存策略、fsync 返回成功但盘未持久化到介质）仍有理论风险，官方也不承诺绝对零丢失。
  5. 开着 AOF 时，dump.rdb 不会被加载。排查「数据不对」先看 appendonly，别盯着 RDB 文件。
  6. AOF 只记写命令。EXPIRE 这类会改变状态的命令会被记录，但「读」不会被记录；所以 AOF 无法还原「读请求历史」，别拿它当审计日志。
  7. no-appendfsync-on-rewrite yes 会在重写期间放弃 fsync，换取重写速度——这是用可靠性换性能，关键业务不要开。
  8. AOF 文件不能手改。混合持久化后开头是 RDB 二进制段，硬改会直接损坏；需要修就用 redis-check-aof --fix。

版本差异（8.x 标注）

7.0 起 AOF 改为多文件结构（appendonlydir + manifest），不再是单一 appendonly.aof；aof-use-rdb-preamble 在 7.x 默认 yes。8.x 沿用该结构。若环境是 6.x，路径与目录名不同，脚本里写死 appendonly.aof 的备份任务要改。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/

八、课后小结

  • AOF 记录写命令，启动时重放；RDB 存数据快照，两者思路不同；
  • 写入链路四站：命令 → aof_buf → write() 到 page cache → fsync() 落盘；
  • always 最可靠但慢、everysec 默认约丢 1 秒、no 交给内核且不可预测；
  • appendonly 默认 no，必须显式开启；开启后启动优先加载 AOF；
  • AOF 比 RDB 大、恢复慢，这催生了重写与混合持久化；
  • aof_delayed_fsync 增长说明磁盘跟不上，1 秒窗口 会被拉长。

九、思考题

  1. write() 返回成功但机器瞬间掉电，数据会不会丢？这解释了 everysec 的哪个特性？
  2. 一个业务「最多能接受丢 5 秒」，你会选 everysec 还是 always？为什么不是「everysec 刚好够用」这么简单？
  3. 同一份数据，AOF 是 RDB 的 3 倍大。除了「命令冗余」，还有什么原因？
  4. 线上同时有 dump.rdb 和 appendonlydir，重启后加载的是哪个？依据是哪条配置？
  5. aof_delayed_fsync 持续增长，你会先查什么？如果不处理，业务侧会感知到什么？
