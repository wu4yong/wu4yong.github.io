skiplist 与 quicklist：ZSet 与 List 的底层

skiplist 的 L2/L1/L0 分层、ZSet 的 dict + skiplist 双结构与 quicklist 的 listpack 链｜依据 Redis 7.4 源码与官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 讲清 skiplist 的层高随机机制与它为什么能做到平均 O(log N) 的范围查询；
  2. 说清 ZSet 为什么同时维护 dict 与 skiplist，各自负责哪一类命令；
  3. 说清 List 的 quicklist = 双向链表 + listpack 节点，以及节点大小对性能的影响。

二、前置知识

RD09（ZSet 命令）、RD06（List 命令）、RD28（listpack）。本讲讨论这两种类型的结构选择：为什么 ZSet 要两份结构、List 为什么不直接用链表。

三、理论讲解（官方定义）

t_zset.c 注释说明了 ZSet 的双结构（原文要点）：

The elements are added to a hash table … and to a skiplist … The hash table is used to map the element to its score in O(1) … the skiplist is used to get the elements in sorted order.

—— https://github.com/redis/redis/blob/7.4/src/t_zset.c

quicklist.c 的定位（原文要点）：

A quicklist is a linked list of ziplists (now listpacks) … it provides a compromise between memory usage and performance.

—— https://github.com/redis/redis/blob/7.4/src/quicklist.c

两条定性：

  • ZSet = dict（按 member 查 score）+ skiplist（按 score 排序），两份结构共享 member 字符串；
  • List = quicklist（双向链表），每个链表节点装一个 listpack，兼顾「插入快」与「内存省」。

span 这个字段很容易被忽略：它让「第几名」这类排名查询也能走 skiplist，不必再遍历。没有它，ZRANK 就只能 O(N)。

2. 为什么用 skiplist 而不用平衡树

三个务实理由：

  • 范围查询友好：ZRANGEBYSCORE 只需在底层链表上顺序走，不用中序遍历回溯；
  • 实现简单：插入删除只改指针，不需要旋转或分裂，代码量与出错概率都低；
  • 无需维护平衡：层高随机，不存在「失衡后修复」的额外分支。

代价是最坏情况不是严格 O(log N)（由随机性决定），但期望值很稳定。

两份结构共享同一个 member 字符串（用 SDS 指针），所以不会双份存 member。这条经常被误解为「ZSet 内存是两倍」——实际翻倍的是指针与 score，不是字符串本身。

4. quicklist 的节点策略

quicklist
├── node1: listpack（若干 entry）
├── node2: listpack（若干 entry）
└── node3: listpack（若干 entry）

节点大小由 list-max-listpack-size 控制：

  • 正数（默认 128）= 每个节点最多装多少个 entry；
  • 负数 = 每个节点最多多少字节：-1 4KB、-2 8KB、-3 16KB、-4 32KB、-5 64KB。

两个极端都不好：

  • 节点太大 → 单节点内插入要搬移大量数据，LINSERT 变慢，且大 listpack 释放时会造成延迟毛刺；
  • 节点太小 → 退化成「纯双向链表」，每个元素都有两个指针，内存暴涨。

五、场景说明

  1. 排行榜：ZSet 的典型用法，ZREVRANGE 走 skiplist，几百万成员仍然很快；
  2. 延迟队列：score 存时间戳，ZRANGEBYSCORE 0 now 取到期任务，靠的就是 skiplist 的范围查询；
  3. 简单消息队列：List + LPUSH/BRPOP，quicklist 的节点大小决定吞吐；
  4. 大 List 的 LINSERT：中间插入是 O(N)（要定位节点 + 节点内搬移），业务上应避免。

六、示例代码/实操步骤

# 1. 观察 ZSet 的编码与结构选择
127.0.0.1:6379> ZADD rank 100 alice 200 bob 300 carol
(integer) 3
127.0.0.1:6379> OBJECT ENCODING rank
"listpack"                    # 小集合用紧凑编码（RD28）

# 2. 超过阈值后转 skiplist（此处手动调小阈值演示）
127.0.0.1:6379> CONFIG SET zset-max-listpack-entries 2
OK
127.0.0.1:6379> ZADD rank 400 dave
(integer) 1
127.0.0.1:6379> OBJECT ENCODING rank
"skiplist"

# 3. 范围查询与排名
127.0.0.1:6379> ZRANGEBYSCORE rank 150 350
1) "bob"
2) "carol"
127.0.0.1:6379> ZRANK rank carol
(integer) 2                   # O(log N)，靠 span 实现
127.0.0.1:6379> ZSCORE rank carol
"300"                         # O(1)，走 dict

# 4. List 的节点大小（正数=条目数，负数=字节上限）
127.0.0.1:6379> CONFIG GET list-max-listpack-size

2) "128"

127.0.0.1:6379> CONFIG SET list-max-listpack-size -2
OK                            # 改为每节点 8KB

# 5. 观察 List 的内存与编码

Java 侧怎么落地：排行榜与延迟队列

这两个结构在 Java 侧最常被用在「排行榜」和「延迟队列」，写法上有几个必须守的点。

  1. pom 只引 starter，ZSet 与 List 都不需要额外依赖。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. 排行榜分页取，绝不用 ZRANGE 0 -1：
// 第 1 页：前 100 名，带分数
Set<TypedTuple<String>> top = stringRedisTemplate.opsForZSet()
        .reverseRangeWithScores("rank:daily", 0, 99);
// 我排第几：ZRANK 靠 span，O(log N)
Long myRank = stringRedisTemplate.opsForZSet().reverseRank("rank:daily", "u1001");
  1. 同分排序要保持确定：ZADD 的 score 用「业务分 + 时间戳微调」这类组合值，否则同分时依赖 member 字典序，榜单会跳。
double score = points * 1_000_000 + (1_000_000 - System.currentTimeMillis() % 1_000_000);
stringRedisTemplate.opsForZSet().add("rank:daily", "u1001", score);
  1. 延迟队列必须「取 + 删」原子化，否则多消费者会重复执行同一条任务——用 Lua 一步做完：
private static final String POP_DUE = """
local due = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, ARGV[2])
if #due == 0 then return {} end
for i, m in ipairs(due) do redis.call('ZREM', KEYS[1], m) end
return due
""";
List<String> tasks = stringRedisTemplate.execute(
        new DefaultRedisScript<>(POP_DUE, List.class),
        List.of("delay:jobs"), String.valueOf(System.currentTimeMillis()), "50");

  1. 处理失败要回补：任务 ZREM 成功后进程崩溃就等于丢了，所以消费侧要做「先写处理中集合、成功再删、超时回补 ZADD」的对账。

  2. List 做队列时注意节点大小：list-max-listpack-size 默认 128，LPUSH/BRPOP 是两端进出，节点大小只影响单次释放成本，别把大对象塞进 List。

七、常见坑（官方明确说明的限制）

  1. 以为 ZSet 内存是「两份数据」。member 字符串是共享的，翻倍的是指针与 score 结构。
  2. 用 ZSet 存超长 member。member 超过 64 字节会退出 listpack（RD28），并且 skiplist 每个节点都带指针与 span，内存显著上升。
  3. list-max-listpack-size 设成 1。等价于纯双向链表，内存暴涨数倍。
  4. 把 ZCARD 当 O(N)。它是 O(1)，读的是头部计数。
  5. 用 ZRANGE 0 -1 拉全量。几百万成员会一次性构造大回复，阻塞主线程并使网络打满。
  6. 高频 ZRANK 做实时排行榜。单次是 O(log N) 没问题，但大量请求会争抢「单线程执行权」，P99 会被抬起来。
  7. quicklist 节点过大导致释放慢。删大 List 时释放 listpack 是一次性动作，会形成延迟毛刺。
  8. 把 list-max-ziplist-size 当现行配置。7.2 起统一到 list-max-listpack-size，旧名兼容但文档不再提。

版本差异（8.x 标注）

skiplist 的最大层数（32）与提升概率（0.25）在 7.x 与 8.x 一致；quicklist 自 7.2 起节点统一用 listpack，8.x 沿用。8.x 的差异在数据类型扩展与许可，核心结构不变。

八、课后小结

  • skiplist：最大 32 层、晋升概率 0.25、score 升序 + member 字典序、span 支撑 ZRANK；
  • 选 skiplist 而不是平衡树，是为了范围查询简单、实现轻、无需维护平衡；
  • ZSet = dict（O(1) 取 score）+ skiplist（有序范围），member 字符串共享；
  • List = quicklist（双向链表），节点是 listpack，大小由 list-max-listpack-size 控制；
  • 节点过大插入慢、过小内存涨，默认 128 是折中；
  • 大 member、大节点是内存与延迟的两个常见坑。

九、思考题

  1. skiplist 的 span 字段解决了什么问题？如果没有它，ZRANK 会变成什么复杂度？

    参考回答：span 记录「到下一个同层节点跨过了多少个底层节点」，下降时累加即可得到排名，所以 ZRANK 是 O(log N)。没有它就只能沿第 0 层挨个数，退化成 O(N)。

  2. 为什么 ZSet 不「只保留 skiplist」？只保留它会失去什么？

    参考回答：会失去 O(1) 的 ZSCORE/ZADD 定位。skiplist 按 score 有序，member → score 是反查，只能全扫；dict 才让「按成员取分」变成常数时间。

  3. list-max-listpack-size 从 128 改成 1，内存与 LINSERT 性能分别怎么变？

    参考回答：内存明显上涨——每个元素都变成独立节点，多两个指针加节点头，等于退化成纯双向链表；LINSERT 定位是 O(1)，但节点数暴增后 CPU 缓存不友好、释放也慢，整体更差。

  4. 一个 500 万元素的 ZSet，ZRANGE 0 -1 会发生什么？正确做法是什么？

    参考回答：一次性构造 500 万元素的回复，主线程被阻塞、网络与内存被打满，客户端可能直接 OOM。正确做法是分页 ZRANGE start stop（如每页 1000）或 ZSCAN 游标遍历，放到后台任务里做。

  5. 用 ZSet 做延迟队列，多个消费者同时 ZRANGEBYSCORE 同一条任务会怎样？如何保证只被取一次？

    参考回答：都会读到同一条，任务被重复执行。保证唯一的方式是把「取」和「删」合成一个原子操作：用 Lua 脚本执行 ZRANGEBYSCORE + ZREM，谁 ZREM 返回 1 谁才有权处理；再配合「处理中超时回补」兜住崩溃场景。
