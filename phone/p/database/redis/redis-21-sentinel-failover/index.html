Sentinel 故障转移与客户端接入

切换的六步、客户端必须做的三件事与切换期风险｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 按顺序说出一次故障转移的六个动作，知道每一步在日志里长什么样；
  2. 让客户端真正「接住」切换：查地址、订阅通知、处理切换窗口的写失败；
  3. 明确切换期必然存在的三类风险（丢最后一段写入、连接全断、脑裂），并给出应对。

二、前置知识

RD20（Sentinel 架构与选举）。本篇是它的执行面：票投完了，具体怎么动。

三、理论讲解（官方定义）

官方对客户端的要求（原文）：

Clients … need to query the Sentinel … and to subscribe to the +switch-master channel.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/

以及关于选中新主后的行为（原文要点）：Sentinel 会向其余从库发送 REPLICAOF，并发布 +switch-master 消息，通知所有订阅者新主库地址。

两条关键信息：

  • 客户端必须能问、也必须能订阅（只做其中一个，切换时都会漏掉）；
  • 通知是广播型（Pub/Sub），错过一次通知就只能靠下一次查询。

四、原理拆解

1. 六个动作

  1. 确认 odown：领导者已选出，故障节点被多数 Sentinel 认定为下线；
  2. 领导者执行切换：只有选出的那个 Sentinel 真正动手（其他只观察）；
  3. 挑新主：按 replica-priority → offset → runid 的次序选；
  4. 改配置：把新主提升（REPLICAOF NO ONE），其余从库改成指向新主；
  5. 发通知：PUBLISH +switch-master mymaster <old-ip> <old-port> <new-ip> <new-port>；
  6. 旧主归队：旧主恢复后，Sentinel 会把它降级为从库（REPLICAOF 到新主），注意它可能带着一段「新主没有」的数据。

第 4 步和第 6 步是数据风险的来源：新主是「某个从库」，它的数据必然比旧主旧一点；旧主回来后会被清空（全量同步）并丢掉那段差异。

2. 客户端三件事

① 启动/重连时问地址

SENTINEL get-master-addr-by-name mymaster

返回两个元素：IP 与端口。客户端用它们建立连接。

② 订阅切换通知

SUBSCRIBE +switch-master

收到消息就重建连接池、切换写入口。注意：订阅连接本身也要保活与重连，否则切换通知会漏。

③ 处理切换窗口的写失败

切换期间旧主已不可写、新主可能还没被客户端发现，写请求会失败。客户端必须：

  • 有重试（带幂等）；
  • 重试前重新问一次主库地址，而不是死磕旧地址；
  • 把「写失败」与「业务失败」分开上报，避免把切换误报成业务错误。

3. 切换期的三类风险

风险 原因 应对
丢最后一段写入 异步复制，新主 offset 比旧主小 业务侧可补偿；关键数据不能只靠 Sentinel
连接全断 主库地址变了，旧连接全部失效 连接池重建 + 短重试 + 熔断
脑裂 旧主未死但网络分区，仍在接收写 min-replicas-to-write 保护；分区恢复后人工核对

「脑裂」这条要特别说明：如果旧主与多数 Sentinel 失去联系，但客户端还能连上它，旧主会继续接受写入。等分区恢复，Sentinel 把旧主降级为从库，这段写入会被全量同步覆盖掉——数据静默丢失。min-replicas-to-write 1 能在一定程度上阻止这种写入（因为没有健康从库就拒绝写）。

五、场景说明

  1. Spring Boot + Lettuce/Jedis：用 Sentinel 模式（配置 master 名 + Sentinel 列表），不要手写 IP；
  2. Go（go-redis）：NewFailoverClient 支持 Sentinel，自动订阅切换；
  3. 代理层（如 Twemproxy 不支持，Proxy 类方案要另做）：如果用自研代理，代理自身要实现 Sentinel 客户端逻辑；
  4. 演练：SENTINEL FAILOVER 主动切换，量出「写请求失败窗口」的时长，这就是业务要容忍的 RTO。

六、示例代码/实操步骤

# 1. 订阅切换通知（终端 A，观察用）
127.0.0.1:26379> SUBSCRIBE +switch-master
Reading messages... (press Ctrl-C to quit)
1) "subscribe"
2) "+switch-master"
3) (integer) 1
1) "message"
2) "+switch-master"
3) "mymaster 10.0.0.5 6379 10.0.0.6 6379"   ← 旧主 → 新主

# 2. 客户端每次新建连接池前都问一次
127.0.0.1:26379> SENTINEL get-master-addr-by-name mymaster
1) "10.0.0.6"
2) "6379"

# 3. 触发一次切换并观察主库变化
127.0.0.1:26379> SENTINEL FAILOVER mymaster
OK
127.0.0.1:26379> SENTINEL master mymaster
# flags master
# ip 10.0.0.6

# 4. 检查旧主是否已降级（切换完成后）
127.0.0.1:26379> SENTINEL replicas mymaster
# 应能看到旧主 10.0.0.5 出现在从库列表里
# flags slave

# 5. 连接层验证：新主可写
127.0.0.1:6379> SET after:failover 1
OK

# 6. 打开脑裂保护（生产建议）
127.0.0.1:6379> CONFIG SET min-replicas-to-write 1 min-replicas-max-lag 10
OK

# 7. Java（Lettuce）关键片段
# RedisClient client = RedisClient.create(
#   RedisURI.builder()
#     .withSentinel("10.0.0.7", 26379)
#     .withSentinel("10.0.0.8", 26379)
#     .withSentinel("10.0.0.9", 26379)
#     .withSentinelMasterId("mymaster")
#     .build());

# 8. Go（go-redis）
# rdb := redis.NewFailoverClient(&redis.FailoverOptions{
#   MasterName:    "mymaster",
#   SentinelAddrs: []string{"10.0.0.7:26379", "10.0.0.8:26379", "10.0.0.9:26379"},
# })

客户端用 Sentinel 模式的核心差别只有一句：地址是「主库名字」而不是「IP:端口」，解析交给 Sentinel 客户端库。

七、常见坑（官方明确说明的限制）

  1. 只实现「查地址」，没实现「订阅通知」。切换后老连接池还在打旧主，直到连接报错才重建——这段时间全部请求失败。
  2. 订阅连接断了不重连。Pub/Sub 连接没保活，切换通知永远收不到。
  3. 把切换失败当成业务失败直接抛给用户。切换窗口内的写失败应当重试，而不是让用户看到「下单失败」。
  4. 重试仍打旧 IP。重试逻辑必须「先重新解析主库地址」，否则重试也没有意义。
  5. +switch-master 消息格式要按「空格分隔的 5 段」解析：<master-name> <old-ip> <old-port> <new-ip> <new-port>。解析写错会读到错误的 IP。
  6. 旧主归队会丢数据。旧主恢复后是被 REPLICAOF 到新主的，它本地多出来的写入会被全量同步覆盖。不要在切换后「相信旧主上的数据」。
  7. SENTINEL FAILOVER 是人工触发，跳过 odown 判定直接切——演练可用，但生产误用会造成无谓切换。
  8. 切换不保证「零停机」。必有一小段连接不可用，RTO 取决于客户端重连策略，而不是 Sentinel 的速度。

版本差异（8.x 标注）

Sentinel 协议与 +switch-master 消息格式在 7.4 与 8.x 之间一致。8.x 无破坏性变更，客户端库按原有方式接入即可。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/

八、课后小结

  • 切换六步：确认 odown → 领导者执行 → 挑新主 → 改配置 → 广播 → 旧主归队；
  • 客户端三件事：查主库地址、订阅 +switch-master、处理切换窗口写失败；
  • 消息格式是五段空格分隔，解析要严格；
  • 三类风险：丢最后一段写入、连接全断、脑裂；
  • 脑裂靠 min-replicas-to-write 缓解，恢复后要人工核对；
  • 演练要用真实断网测 RTO，而不是只看 Sentinel 日志。

九、思考题

  1. 客户端实现了「查地址」但没订阅通知，切换后会发生什么？问题会在什么时候暴露？
  2. +switch-master 消息里两个 IP 分别是谁？解析错位会导致什么后果？
  3. 旧主恢复后为什么可能丢掉自己的写入？这与「异步复制」有什么关系？
  4. 脑裂期间旧主还能接受写，怎么用配置把这种写入挡掉？挡掉之后业务会看到什么错误？
  5. 你的系统允许「30 秒内写不可用」，客户端重试应该怎么设计才既不打死新主、又能尽快恢复？
