HyperLogLog、GEO 与 Bitmap

三种「为特定问题而生」的结构：估算、定位、标记｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 讲清这三种结构各自「拿什么换什么」，为什么它们不能当通用存储用；
  2. 记住关键精度与容量数字（HLL 0.81%、约 12 KB；Bitmap offset 上限 2^32-1；GEO 底层是 ZSet）；
  3. 遇到 UV 统计、附近的人、签到打卡三类需求，能直接选出正确结构并说清误差与代价。

二、前置知识

RD08（Set）与 RD09（ZSet）。GEO 的底层就是 Sorted Set，不理解 ZSet 就看不懂 GEO 为什么能「按距离排序」。

三、理论讲解（官方定义）

三种结构在官方文档里是 data types 级别的独立章节，不是 String 的子功能：

HyperLogLog is a probabilistic data structure that estimates the cardinality of a set. … The standard error of this estimate is 0.81%.

—— https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/

Redis also supports … geospatial indexes … to store and query geographic coordinates.

—— https://redis.io/docs/latest/develop/data-types/geospatial/

Bitmaps are not a data type in Redis, but a set of bit-oriented operations defined on the String type.

—— https://redis.io/docs/latest/develop/data-types/bitmaps/

注意第三条的措辞：Bitmap 在官方定义里不是独立类型，它是定义在 String 上的一组位操作。这句话决定了它的上限：String 多大，Bitmap 就多大，所以 offset 最大 2^32-1（512 MB）。

四、原理拆解

1. HyperLogLog：用 0.81% 的误差换固定内存

核心特性：

  • PFADD key member... 添加元素，PFCOUNT key... 估算基数，PFMERGE dest src... 合并；
  • 标准误差 0.81%，这是官方给的数字，不是「差不多」；
  • 内存固定，约 12 KB 一个 key（官方表述是「最多 12 KB」），与基数无关——1 万和 1 亿的用户都占这么点；
  • 不能取回成员，也不能做「是否存在」判断（没有 PFEXISTS）。

所以 HLL 的适用边界非常窄也非常明确：只要一个数，不要明细。UV、日活、搜索词去重数量都属于这类。

2. GEO：底层就是 ZSet

官方说得很直白：GEO 索引存在 Sorted Set 里，score 是 geohash 编码。这就解释了三件事：

  1. GEOADD 之后，这个 key 就是一个 ZSet，ZRANGE、ZCARD、ZREM 都能直接用；
  2. 距离检索本质是「按 geohash 前缀的范围 + 逐点算距离」，所以它不是精确的几何计算，而是一次「先粗筛后精算」；
  3. geohash 在 GEO 里用 52 位，这限制了坐标精度——官方文档里也提示了精度与误差的存在。

命令演进要记牢：GEORADIUS 系列在 6.2 起标记废弃，改用 GEOSEARCH / GEOSEARCHSTORE：

GEOSEARCH key FROMMEMBER member | FROMLONLAT lon lat
          BYRADIUS r unit | BYBOX w h unit
          [ASC | DESC] [COUNT n [ANY]] [WITHCOORD] [WITHDIST] [WITHHASH]

BYRADIUS 按半径、BYBOX 按矩形框；ASC/DESC 按距离排序。

3. Bitmap：精确、极省，但要求编号连续

能力清单：

  • SETBIT key offset 0|1 / GETBIT：单点读写；
  • BITCOUNT key [start end [BYBIT|BYTE]]：统计 1 的个数，7.0 起支持按 bit 或按字节区间；
  • BITPOS key bit [start end]：找第一个 0 或 1 的位置；
  • BITOP AND|OR|XOR|NOT destkey key...：多 key 位运算；
  • BITFIELD key [GET|SET|INCRBY type offset]：把 value 当成「多个小整数拼接」来读写（7.x 还加了 BITFIELD_RO）。

空间公式很简单：占用字节数 ≈ 最大 offset / 8。所以它适合「编号连续、以 0 或 1 起步」的场景（用户序号、日期序号），不适合「ID 是雪花算法」的场景。

五、场景说明

需求 结构 为什么
每日 UV / 独立访客估算 HLL 只需一个数，12 KB 扛住上亿基数
「附近的店 / 附近的人」 GEO 按半径 + 距离排序是原生能力
签到打卡、活跃标记 Bitmap 一个人一个月只占 4 字节，BITCOUNT 一次算出天数
用户在线状态（百万级） Bitmap 一人一位，GETBIT O(1)
需要精确成员列表的 UV Set HLL 给不了明细，Set 才精确

反面清单：用 HLL 做「判断某人是否访问过」——做不到；用 Bitmap 存雪花 ID——空间爆炸；用 GEO 做路径规划——它只做点与点的距离与范围检索，不做导航。

六、示例代码/实操步骤

# 1. HLL：去重计数
127.0.0.1:6379> PFADD uv:20230101 u1 u2 u3
(integer) 1
127.0.0.1:6379> PFADD uv:20230101 u1      # 重复添加不改基数
(integer) 0
127.0.0.1:6379> PFCOUNT uv:20230101
(integer) 3
127.0.0.1:6379> PFADD uv:20230102 u3 u4
(integer) 1
127.0.0.1:6379> PFMERGE uv:week uv:20230101 uv:20230102
OK
127.0.0.1:6379> PFCOUNT uv:week
(integer) 4                              # 合并去重后的基数

# 2. HLL 的内存占用：与基数无关
127.0.0.1:6379> MEMORY USAGE uv:20230101
(integer) 12304                          # 约 12 KB，只写 4 个元素也这么大

# 3. GEO：写入与距离
127.0.0.1:6379> GEOADD shops 104.0668 30.5728 leshan-station 104.0701 30.5701 snack-street
(integer) 2
127.0.0.1:6379> GEODIST shops leshan-station snack-street m
"429.1xxx"                               # 两点直线距离（米）
127.0.0.1:6379> GEOPOS shops leshan-station
1) 1) "104.0667xxxx"
   2) "30.5727xxxx"                      # 返回的坐标有精度截断

# 4. GEO：范围检索（6.2+）
127.0.0.1:6379> GEOSEARCH shops FROMMEMBER leshan-station BYRADIUS 1 km ASC COUNT 5 WITHDIST
1) 1) "snack-street"
   2) "0.4291"                           # 距离，单位 km
127.0.0.1:6379> GEOSEARCH shops FROMLONLAT 104.0668 30.5728 BYBOX 2 1 km ASC

# 5. GEO 底层就是 ZSet：可以直接 ZRANGE
127.0.0.1:6379> ZRANGE shops 0 -1 WITHSCORES
1) "snack-street"
2) "3996xxxxxxxx"                        # 这个数字就是 52 位 geohash 的整数值
127.0.0.1:6379> TYPE shops
zset

# 6. Bitmap：签到
127.0.0.1:6379> SETBIT sign:u1:202301 0 1
(integer) 0
127.0.0.1:6379> SETBIT sign:u1:202301 5 1
(integer) 0
127.0.0.1:6379> BITCOUNT sign:u1:202301
(integer) 2
127.0.0.1:6379> BITPOS sign:u1:202301 1
(integer) 0                              # 第一个 1 在 offset 0
127.0.0.1:6379> MEMORY USAGE sign:u1:202301
(integer) 72                             # 一个月只写 2 位，但按最大 offset 分配

# 7. BITOP：多天按位与（「连续签到」判断）
127.0.0.1:6379> SETBIT sign:a 0 1
127.0.0.1:6379> SETBIT sign:b 0 1
127.0.0.1:6379> SETBIT sign:b 1 0
127.0.0.1:6379> BITOP AND dest sign:a sign:b
(integer) 1
127.0.0.1:6379> GETBIT dest 0
(integer) 1                              # 两天都在 offset 0 签到了

# 8. BITFIELD：把 value 当小整数数组
127.0.0.1:6379> BITFIELD bf SET u8 0 200 GET u8 0 INCRBY u8 0 55
1) (integer) 0                           # SET 返回旧值
2) (integer) 200
3) (integer) 255                         # 无符号 8 位上溢到 255

# 9. 超出 offset 上限会报错
127.0.0.1:6379> SETBIT big 4294967296 1
(error) ERR bit offset is not an integer or out of range

七、常见坑（官方明确说明的限制）

  1. HLL 只有 0.81% 的误差是「标准误差」，不是「保证误差」。做报表展示要标注「估算值」，别拿它跟精确账目对账。
  2. HLL 不能判断成员存在、不能列举成员。想「查某人是否来过」请用 Set 或 Bitmap。
  3. HLL 内存恒定约 12 KB，所以「只存一个元素」也占这么多——高频创建小 HLL（比如每个商品一个）会浪费大量内存。
  4. Bitmap 的空间由最大 offset 决定。offset 一跳大，内存立刻按字节补齐；SETBIT key 4000000000 1 会瞬间分配约 500 MB。
  5. offset 上限是 2^32-1（对应 512 MB），超过直接报错。
  6. BITCOUNT 的区间参数在老版本里只能按字节，7.0 起才有 BYBIT；按 bit 计数时务必显式写 BYBIT，否则区间含义完全不同。
  7. GEO 的坐标有精度损失：底层 52 位 geohash 编码，GEOPOS 返回的坐标和写入值不会完全一致；距离计算也有微小误差。需要厘米级精度的场景不要用 GEO。
  8. GEORADIUS 系列 6.2 起废弃，新代码用 GEOSEARCH；且 GEO 只能做「点与点的距离/范围」，做不了「沿路径距离」。

版本差异（8.x 标注）

这三种结构的命令在 7.4 与 8.x 之间没有语义变更；变化点分别是 6.2 的 GEOSEARCH（替代 GEORADIUS）与 7.0 的 BITCOUNT ... BYBIT。若环境是 5.x/6.0，GEOSEARCH 与 BYBIT 都不可用。

依据：https://redis.io/docs/latest/develop/data-types/geospatial/

八、课后小结

  • HLL：基数估算，标准误差 0.81%，内存恒定约 12 KB，不能取明细；
  • GEO：底层是 ZSet（score 为 52 位 geohash），支持半径/矩形范围与距离排序，有精度损失；
  • Bitmap：String 上的位操作，精确且极省，但空间由最大 offset 决定，offset 上限 2^32-1；
  • 三者都属于「明确知道自己要算什么」才用的结构，不能当通用存储；
  • 选型口径：要精确 → Bitmap / Set；要估算 → HLL；要按距离找 → GEO。

九、思考题

  1. 一个电商要统计每个商品的「浏览用户数」，10 万个商品。用 HLL 一个商品一个 key，内存会发生什么？换成什么方案更合适？
  2. GEOSEARCH ... BYRADIUS 1 km ASC 为什么能排序？排序用的是 ZSet 的什么能力？
  3. 用 Bitmap 存「用户 ID → 是否在线」，如果 ID 是雪花算法生成的 64 位整数，会发生什么？怎么改？
  4. BITCOUNT key 0 0 与 BITCOUNT key 0 0 BYTE 与 BITCOUNT key 0 0 BYBIT 三者结果为什么可能完全不同？
  5. HLL 的「合并」为什么是安全的？PFMERGE 之后误差会变大吗？为什么？
