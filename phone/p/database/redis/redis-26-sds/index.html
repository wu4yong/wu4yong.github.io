SDS 与 redisObject：字符串到底怎么存

C 字符串的三个硬伤、SDS 的头部字段与 redisObject 的五字段｜依据 Redis 7.4 官方文档与源码注释自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 Redis 为什么不用 C 字符串，SDS 用哪三个设计换来 O(1) 长度与二进制安全；
  2. 讲清 int / embstr / raw 三种字符串编码的判定条件，以及 44 字节这条线从哪来；
  3. 用 OBJECT ENCODING 判断任意 key 的真实底层表示，而不是靠猜。

二、前置知识

RD05（String 类型命令）。本讲是把「你用过的命令」拆到内存层面：同一句 SET，可能产生三种完全不同的内存结构。

三、理论讲解（官方定义）

官方对字符串编码的说明（原文）：

Redis can represent strings in three different ways: int … embstr … raw … The embstr encoding … is used for strings that are 44 bytes or less.

—— https://redis.io/docs/latest/develop/data-types/strings/

SDS 的定位（源码 sds.h 注释，原文要点）：

SDS is a binary safe string library … it stores the length of the string in a header before the actual string … so getting the length is O(1).

—— https://github.com/redis/redis/blob/7.4/src/sds.h

两条必须记死：

  • 编码是自动选择的，你无法指定。它由值的形态与长度决定；
  • 44 字节不是拍脑袋：embstr 要求「redisObject 头 + SDS 头 + 数据 + \0」一次分配、总长不超过 64 字节的 jemalloc size class。

四、原理拆解

1. C 字符串的三个硬伤与 SDS 的对策

预分配的具体规则（源码注释）：len < 1MB 时按 2 倍扩容；len ≥ 1MB 时每次多留 1MB。缩短字符串时不立即释放，把空间留给后续追加——这就是「惰性释放」。代价是内存可能短暂高于实际数据量。

2. SDS 的四种头部

sdshdr5（已弃用）/ sdshdr8 / sdshdr16 / sdshdr32 / sdshdr64，按字符串长度选择最小够用的头部：长度 < 256 用 8 位，< 65536 用 16 位，依此类推。flags 的低 3 位记录头部类型，所以同一份数据在内存里的「头部厚度」不同——这也是小字符串省内存的原因之一。

3. redisObject 的五个字段

type      → 数据类型（string / list / hash / set / zset / stream）
encoding  → 底层编码（int / embstr / raw / listpack / intset / skiplist …）
lru       → 最近访问时间或访问频率（淘汰策略用）
refcount  → 引用计数（共享对象、释放时机）
ptr       → 指向真实数据结构

encoding 是你排查内存问题的入口：同样是 hash，listpack 与 hashtable 的内存差可以到 3–10 倍（RD28 详述）。

embstr 是只读的：任何修改（APPEND、SETRANGE）都会先转成 raw 再改。原因很简单——一次分配意味着 robj 与 SDS 内存连续，扩容时无法原地完成。

5. 共享整数

Redis 启动时预建 0–9999 的整数对象并复用（shared.integers，默认 10000 个）。所以大量 SET k 1 这类小整数不额外占内存——但也带来一个副作用：OBJECT REFCOUNT 会显示一个很大的共享计数，别误以为泄漏。

五、场景说明

  1. 计数器：INCR 后仍是 int 编码，内存最省，是「省内存」的首选形态；
  2. 短 ID / 状态值：≤ 44 字节走 embstr，够用就别拼接成长串；
  3. JSON 大对象：raw，每次读都要整段传输与解析，应拆 Hash 字段；
  4. 排查内存异常：OBJECT ENCODING + MEMORY USAGE 两条命令就能判断「是不是编码选错了」。

六、示例代码/实操步骤

# 1. 三种编码的实际观察
127.0.0.1:6379> SET n 12345
OK
127.0.0.1:6379> OBJECT ENCODING n
"int"

127.0.0.1:6379> SET s "hello"
OK
127.0.0.1:6379> OBJECT ENCODING s
"embstr"

127.0.0.1:6379> SET big "0123456789012345678901234567890123456789012345"
OK
127.0.0.1:6379> OBJECT ENCODING big
"raw"                       # 46 字节，超过 44 → raw

# 2. embstr 被修改后转 raw
127.0.0.1:6379> APPEND s " world"
(integer) 11
127.0.0.1:6379> OBJECT ENCODING s
"raw"                       # 修改动作让 embstr 退化为 raw

# 3. 长度与内存
127.0.0.1:6379> STRLEN big
(integer) 46                # O(1)，读的是 SDS 头的 len
127.0.0.1:6379> MEMORY USAGE n
(integer) 48                # int 编码 + robj 的开销
127.0.0.1:6379> MEMORY USAGE big
(integer) 80                # raw：robj + SDS 头 + 数据 + 对齐

# 4. 共享整数
127.0.0.1:6379> SET shared:1 100
OK
127.0.0.1:6379> OBJECT REFCOUNT shared:1
(integer) 2147483647        # 共享对象，计数是上限值，不是泄漏

# 5. 追加的性能对比（大量 APPEND 会触发扩容）
127.0.0.1:6379> SET log ""
OK
127.0.0.1:6379> EVAL "for i=1,10000 do redis.call('APPEND', KEYS[1], 'abcdefghij') end return redis.call('STRLEN', KEYS[1])" 1 log
(integer) 100000            # 预分配让扩容次数远小于 10000 次

Java 侧怎么落地：序列化器决定编码

SDS 那 44 字节的红线，在 Java 侧几乎全由「序列化器」决定——选错了，一个小对象也会被顶成 raw。

  1. pom 只引 starter，序列化器自己配，不要用默认的 JDK 序列化。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. 短值、计数类一律用 StringRedisTemplate，value 是纯字节，长度可控；用 RedisTemplate<String,Object> + Jackson 会给每个值加类型信息，44 字节的小对象立刻越过阈值变 raw。
// 计数器保持 int 编码：值本身是纯数字，才能走 int
stringRedisTemplate.opsForValue().increment("pv:2023-01-16");
  1. 真需要存对象时，先序列化再压一遍，并把类型信息挪到 key 上（key 里带 v1:user: 之类），避免每个 value 都带一段 @class。
String json = objectMapper.writeValueAsString(dto);
stringRedisTemplate.opsForValue().set("v1:user:1001", gzip(json));  // >44B 必然 raw，压小才是省内存

  1. 不要指望「改小就回 embstr」：编码只升不降。要回收只能重建 key（RENAME 到临时 key，按新格式重写，再改回原名）。

  2. 上线前用一条断言兜住：对最热的 key 打 OBJECT ENCODING，一旦出现预期外的 raw 就报警。

String enc = stringRedisTemplate.execute((RedisCallback<String>) c ->
        new String(c.execute("OBJECT", "ENCODING".getBytes(), "v1:user:1001".getBytes())));
// 期望 embstr / int；出现 raw 说明 value 被序列化器撑大了

七、常见坑（官方明确说明的限制）

  1. 以为「字符串就是字符串」。int / embstr / raw 三者的内存与可变性都不同，MEMORY USAGE 差异明显。
  2. 拿 embstr 当可变缓冲区。频繁 APPEND 会立刻转 raw，并且每次都走扩容逻辑；要拼长串请用客户端拼好再 SET。
  3. 44 字节这条线记成 64。判定的是「robj + SDS 头 + 数据 + \0」整体，落在 jemalloc 的 64 字节 class，不是数据本身 64 字节。
  4. OBJECT REFCOUNT 显示大数字就以为内存泄漏。共享整数对象的 refcount 恒为上限值，这是正常现象。
  5. SDS 惰性释放被当成内存泄漏。缩短字符串后空间不还给分配器，used_memory 不会立刻下降，属预期行为。
  6. 用 int 编码存超大整数。超过 long 表示范围就退回 embstr，INCR 也会变慢。
  7. 在 embstr 上做 SETRANGE 想「原地改」。官方明确 embstr 只读，任何写都会转 raw。

版本差异（8.x 标注）

SDS 与 redisObject 的实现在 7.x 到 8.x 之间未发生结构性变化，int/embstr/raw 三种编码与 44 字节阈值保持一致。8.x 的差异集中在数据类型扩展与许可条款。

依据：https://redis.io/docs/latest/develop/data-types/strings/

八、课后小结

  • SDS 用 len / alloc / flags / buf 四个部分换来了 O(1) 长度、二进制安全、预分配；
  • 预分配规则：< 1MB 翻倍，≥ 1MB 每次多留 1MB；缩短不立即释放（惰性释放）；
  • redisObject 五字段：type / encoding / lru / refcount / ptr，encoding 是内存排查入口；
  • 字符串三编码：int（数值）、embstr（≤ 44 字节、只读）、raw（> 44 或已修改）；
  • 共享整数 0–9999 默认开启，refcount 大是正常现象；
  • OBJECT ENCODING + MEMORY USAGE 是最快的两个诊断命令。

九、思考题

  1. 一个 44 字节的字符串和一个 45 字节的字符串，内存能差多少？为什么？

    参考回答：44 字节走 embstr——robj 与 SDS 一次分配，塞进 64B 的 size class；45 字节必须 raw，robj 与 SDS 各自 malloc，还要加上分配器头与对齐。单个 key 大约多十几到几十字节，真正的问题是海量 key：多一次分配就是多一份碎片。

  2. SET k hello 之后连续 APPEND 三次，编码会怎么变？中间发生了什么分配？

    参考回答：第一次 APPEND 就从 embstr 转成 raw——embstr 是只读的，任何修改都要重建。之后每次追加走 SDS 的预分配：长度小于 1MB 时按「翻倍」扩（alloc = len*2），所以不会每次都 realloc。

  3. 为什么 embstr 被设计成只读？如果允许原地修改会有什么问题？

    参考回答：embstr 的 robj 与 SDS 在同一块内存里，SDS 指针指在块内偏移处；一旦原地 realloc 改变长度，整个块可能被移动，robj 与 SDS 的指针关系就断了。所以设计成只读，第一次修改直接转 raw，结构简单也不易出 bug。

  4. 业务把 200 KB 的 JSON 整个塞进一个 String，MEMORY USAGE 会显示什么？怎么优化？

    参考回答：显示约 200 KB 加对象头，且因为是大块分配，MEMORY USAGE 往往还高于 200 KB。优化：压缩后存二进制、只存热字段、改 Hash 按字段分存、或把大对象放对象存储、Redis 只留引用与索引。

  5. OBJECT REFCOUNT 返回 2147483647，你会怎么判断「是不是真泄漏」？

    参考回答：2147483647 是 INT_MAX 哨兵，表示共享对象（典型是 0–9999 的共享整数），不是泄漏。判断依据：编码为 int、值落在共享区间、且这个数不随访问增长；真泄漏要看 used_memory 持续上涨、MEMORY STATS 各类型条目数增长，以及 key 数量。
