redis-备份与恢复

分类：database · redis ｜ 标签：Redis · 系统课 · 运维

备份、迁移与恢复演练

BGSAVE → 拷贝 → 校验，恢复顺序与四种迁移手段｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 独立写出一个「能恢复」的 Redis 备份方案，知道 RDB 与 AOF 各自该拷什么、怎么校验；
  2. 掌握恢复的正确顺序（停服务 → 放文件 → 改配置 → 启动），以及最常见的三个恢复失败原因；
  3. 面对「不停机迁移 / 跨版本升级 / 单机 ↔ Cluster」三种需求，能选出对应手段并说清风险。

二、前置知识

RD14（RDB）、RD15（AOF）、RD16（重写与混合持久化）。备份的本质就是把前面三讲产出的文件搬走并保证可用。

三、理论讲解（官方定义）

官方的备份口径（原文要点）：

… you can copy the RDB file … Redis is able to reload it at startup … it is recommended to perform backups from a replica.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/

以及官方给出的在线拉取方式（原文）：

redis-cli --rdb /path/to/dump.rdb … transfer a RDB file from a remote Redis instance.

—— https://redis.io/docs/latest/develop/tools/cli/

两条要点：

  • 备份应从副本做，避免在主节点上额外触发一次 fork 与 CoW；
  • redis-cli --rdb 是官方支持的远程快照拉取，不需要登录机器就能拿到一致快照。

校验工具（官方明确列出）：redis-check-rdb 与 redis-check-aof，后者支持 --fix 修复被截断的尾部。

四、原理拆解

1. 备份：先有一致的快照，再谈拷贝

RDB 备份的标准流程：

  1. 在副本上（或低峰的主节点）执行 BGSAVE；
  2. 等 rdb_bgsave_in_progress 归零、rdb_last_bgsave_status: ok；
  3. 拷贝 dir/dbfilename 到备份介质；
  4. 立刻用 redis-check-rdb 校验一次；
  5. 记录版本号、时间、数据量（DBSIZE），写进备份清单。

为什么不能直接 cp 正在写的文件？因为 rename 之前是临时文件、rename 之后才是完整文件；直接拷 dump.rdb 大多没问题（它本身就是原子的），但在 BGSAVE 进行中拷可能拿到旧文件而误以为「已是最新」——所以要等状态归零再拷。

AOF 备份（7.x）：

ls appendonlydir/            # base.rdb + incr.aof + manifest

必须整个目录一起拷，manifest 是加载顺序的唯一依据。只拷 incr.aof 等于丢掉全量基线。

2. 恢复：顺序错了就是白忙

RDB 恢复：

  1. 停掉目标实例（不能让它在运行时替换文件）；
  2. 把备份文件放进 dir 目录，改名成 dbfilename 的值；
  3. 启动，日志里应有 DB loaded from disk: ...;
  4. DBSIZE 抽样校验，与备份清单比对。

AOF 恢复：

  1. 停实例；
  2. 整个 appendonlydir 目录替换（不是只覆盖某个文件）；
  3. 确认 appendonly yes；
  4. 启动，日志里应出现 DB loaded from append only file;
  5. 若日志报截断，用 redis-check-aof --fix 修复后再启。

三个最常见的失败原因：

  • dir 配错：文件放对位置了，但配置里 dir 指向别处，加载的是空数据；
  • 同时存在 AOF 与 RDB 且加载了错的那个：appendonly yes 时优先加载 AOF，你以为加载的是 RDB；
  • 权限/属主错：文件属主不是 redis 用户，启动报 Permission denied。

3. 迁移：四种手段的适用边界

场景
手段
风险与前提
同版本、可停机
拷 RDB / AOF 文件
最简单，停机时间 = 数据量/磁盘速度
不停机、同版本
REPLICAOF host port 建从库 → 提升为主
需要目标空库；切换要改客户端地址
跨版本升级
先建从库并升级从库，验证后切换
版本兼容要以官方兼容说明为准，禁止跳跃式升级后直接切
单机 ↔ Cluster
MIGRATE / DUMP + RESTORE，或重放业务数据
Cluster 只支持 0 号库；MIGRATE 按 key 搬，大 key 会卡住

REPLICAOF 是最常用的「不停机搬家」：新实例先当从库同步全量（这一步走的就是 RDB），再 REPLICAOF NO ONE 提升为主。整个过程几乎不影响线上读，代价是同步期间的网络与磁盘带宽。

备份（副本 + 校验 + 清单）、恢复（停服 → 放文件 → 启动 → 比对）、迁移四法的适用边界，以及三种失败检查点｜依据 Redis 7.4 Persistence / REPLICAOF / MIGRATE 文档自绘

五、场景说明

  1. 每日冷备：副本上 BGSAVE → 拷 RDB 到对象存储，保留 7–30 天；
  2. AOF 增量更可靠时的备份：每天拷一次 appendonlydir，频率可以低但必须整目录；
  3. 上线前的恢复演练：在隔离环境用生产备份恢复一次，跑通业务读写；
  4. 机房搬迁/扩容：REPLICAOF 同步，切主后改客户端连接串；
  5. Cluster 扩缩容：官方工具做 reshard，本质上也是按 slot 搬 key，大 key 会拖慢。

六、示例代码/实操步骤

# ===== 备份（在副本上执行）=====
127.0.0.1:6379> BGSAVE
Background saving started
127.0.0.1:6379> INFO persistence
# rdb_bgsave_in_progress:0
# rdb_last_bgsave_status:ok

$ cp /var/lib/redis/dump.rdb /backup/redis-$(date +%F).rdb
$ redis-check-rdb /backup/redis-2023-01-07.rdb
[offset 0] Checking RDB file ...
[offset 987654] Checksum OK

# 备份清单里记下这几项
127.0.0.1:6379> INFO server | grep redis_version
127.0.0.1:6379> DBSIZE

# ===== 远程拉快照（无需登录源机）=====
$ redis-cli -h 10.0.0.5 -p 6379 --rdb /backup/remote.rdb
Transfer started. Monitor progress with INFO persistence.
...
Transfer finished with success.

# ===== 恢复 RDB =====
$ systemctl stop redis
$ cp /backup/redis-2023-01-07.rdb /var/lib/redis/dump.rdb
$ chown redis:redis /var/lib/redis/dump.rdb
$ systemctl start redis
$ redis-cli DBSIZE
(integer) 1234567
# 日志核对：DB loaded from disk: 0.123 seconds

# ===== 恢复 AOF（7.x 目录）=====
$ systemctl stop redis
$ rm -rf /var/lib/redis/appendonlydir
$ cp -r /backup/appendonlydir /var/lib/redis/
$ redis-check-aof /var/lib/redis/appendonlydir/appendonly.aof.1.incr.aof
# 若提示文件被截断：
$ redis-check-aof --fix /var/lib/redis/appendonlydir/appendonly.aof.1.incr.aof
$ systemctl start redis

# ===== 不停机迁移：新实例当从库 =====
# 在目标实例（空数据）上执行
127.0.0.1:6380> REPLICAOF 10.0.0.5 6379
OK
127.0.0.1:6380> INFO replication
# role:slave
# master_host:10.0.0.5
# master_link_status:up          —— 同步完成后才是 up

# 验证数据量与抽样 key 后，提升为主
127.0.0.1:6380> REPLICAOF NO ONE
OK

# ===== 单 key 迁移（Cluster / 定向搬）=====
127.0.0.1:6379> MIGRATE 10.0.0.6 6379 user:1001 0 5000
OK
# 或先序列化再恢复
127.0.0.1:6379> DUMP user:1001
"..."                            # 二进制序列化内容
127.0.0.1:6380> RESTORE user:1001 0 "..." REPLACE
OK

master_link_status: up 是切换前的硬性检查点：down 表示全量同步还没完成，此时切主会丢掉同步期间的写入。

Java 侧怎么落地：把「换库」做成配置项，而不是改代码

备份恢复、迁移切主都意味着连接地址会变。应用侧要做好三件事：地址可配、重连可恢复、恢复后能自检。

  1. 依赖不变，spring-boot-starter-data-redis 一个就够；关键是别把 host 写死在代码或镜像里。
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. 地址走环境变量/配置中心，切换时只改变量、不重新构建。
spring:
  data:
    redis:
      host: ${REDIS_HOST:10.0.0.5}
      port: ${REDIS_PORT:6379}
      password: ${REDIS_PASS}
      timeout: 3s
      lettuce:
        pool:
          max-active: 32
          max-wait: 2s
        shutdown-timeout: 200ms
  1. 切换窗口要能扛住短暂不可用：恢复期间连接必然断，Lettuce 会重连，但业务线程拿到的是异常。对读路径可降级到本地缓存/回源，对写路径不要盲目重试（恢复后的实例可能是旧快照，重试写会把旧数据再覆盖一遍）。
try {
    redis.opsForValue().set(key, value);
} catch (RedisConnectionFailureException e) {
    metrics.counter("redis.switch.window.write_failed").increment();
    throw new SwitchWindowException("redis unavailable during restore", e);  // 交给上层排队，不自动重试
}
  1. 恢复后自检再放量：用一个启动钩子核对数据量，避免「服务起来了但库是空的」。
@Bean
ApplicationRunner redisRecoverCheck(StringRedisTemplate redis,
                                     @Value("${redis.expected-dbsize:0}") long expected) {
    return args -> {
        long actual = redis.execute((RedisCallback<Long>) c -> c.dbSize());
        if (expected > 0 && actual < expected * 0.99) {
            log.error("redis recover check failed: actual={}, expected={}", actual, expected);
            metrics.counter("redis.recover.check.failed").increment();
        }
    };
}

演练才是这套东西的验收：把生产备份恢复到隔离环境，改一个 REDIS_HOST 指向它，跑通读写再确认——没有实测 RTO 的备份方案不算方案。

七、常见坑（官方明确说明的限制）

  1. 不要在主节点上拷「正在跑 bgsave 时」的文件。要等 rdb_bgsave_in_progress: 0；否则可能拿到旧快照而以为是最新。
  2. AOF 备份必须整目录。appendonlydir 里的 manifest 决定加载顺序，缺任何文件都可能加载失败或数据残缺。
  3. 恢复前必须停服务。运行中替换文件，Redis 不会重新加载，你的操作等于无效；下次重启才生效，这时问题会突然爆发。
  4. appendonly yes 时优先加载 AOF。恢复 RDB 却忘了关 AOF，等于什么都没做。
  5. redis-check-aof --fix 会截断尾部。它保证「能启动」，但尾部那段命令会被丢弃——这是修复的代价，要记录丢了什么时间窗的数据。
  6. REPLICAOF 会让目标库先清空。目标实例上已有数据会被全量同步覆盖，别把「从库」建在有数据的实例上。
  7. 跨版本恢复要验证。RDB/AOF 是私有格式，版本兼容有边界；官方建议同版本验证后再迁移，禁止「大版本跳跃直接切」。
  8. MIGRATE 是同步阻塞的。搬大 key 时源实例和目标实例都会卡住，DUMP+RESTORE 同样要评估 key 体积。
  9. 备份不带校验等于没备份。redis-check-rdb / redis-check-aof 是官方工具，跑一次只要几秒，能挡掉大部分「文件损坏」事故。

版本差异（8.x 标注）

7.x 的 AOF 目录结构与 8.x 一致；REPLICAOF 自 5.0 起取代 SLAVEOF（后者仍可用但官方推荐前者）。8.x 迁移时需注意许可变更带来的镜像/发行版差异，但备份文件格式与命令语义不变。

依据：https://redis.io/docs/latest/commands/replicaof/

八、课后小结

  • 备份 = 一致快照 + 拷贝 + 校验 + 清单记录；官方建议在副本上做；
  • redis-cli --rdb 可远程拉快照，无需登录源机；
  • 恢复顺序：停服务 → 放文件（AOF 整目录）→ 改配置 → 启动 → 抽样校验；
  • appendonly yes 时优先加载 AOF，恢复 RDB 前必须先确认；
  • 迁移四法：拷文件（可停机）、REPLICAOF（不停机）、升从库（跨版本）、MIGRATE/DUMP+RESTORE（单 key / Cluster）；
  • 演练是备份的一部分：没有 RTO/RPO 实测的备份，不可信。

九、思考题

  1. 为什么官方建议在副本上做备份？在主节点上多做一次 BGSAVE 的真实代价是什么？

    参考回答：BGSAVE 要 fork，写量大时 CoW 额外内存可能接近数据量的一半以上，同时占磁盘 IO 与 CPU；这会直接抬高主节点的写延迟。放到副本上做，主节点只承担复制，代价转移到了不接写请求的机器上。

  2. 恢复后 DBSIZE 比备份清单少了 3 万条，最可能的原因是哪三种？各自的检查点在哪？

    参考回答：① 加载的是更旧的文件——查 dir/dbfilename 与备份清单的时间戳；② 实际加载了 AOF 而不是你以为的 RDB——查 appendonly；③ 从节点过期未同步/淘汰策略不同——比对 INFO keyspace 与 maxmemory-policy。先看启动日志那行 DB loaded from ... 就能砍掉一半可能。

  3. REPLICAOF 建从库时，目标实例上原有的数据会怎样？如果你不想丢，该换什么做法？

    参考回答：会被清空并全量覆盖（先 flush 再加载主库 RDB）。不想丢就把旧数据先 BGSAVE 备份，或改用 MIGRATE/DUMP+RESTORE 按 key 定向搬迁，而不是把有数据的实例挂成从库。

  4. redis-check-aof --fix 修复后能启动，但业务发现少了 20 分钟数据。这 20 分钟去哪了？

    参考回答：被 --fix 截掉了。它从尾部往前找到最后一个完整命令，之后的所有命令直接丢弃——那 20 分钟就是「文件末尾不完整的那一段」，属于磁盘写满/掉电时没落盘的部分。

  5. 一次「磁盘满了导致 AOF 写失败」的事故后，你要改哪三处配置或流程，避免下次重演？

    参考回答：① 磁盘水位告警（如 80% 预警、90% 阻断写入），并按「AOF × 2」预留重写空间；② maxmemory 之外单独监控数据盘，别只看内存；③ 把 no-appendfsync-on-rewrite、stop-writes-on-bgsave-error 的取舍写成明确策略，并加到演练用例里。
