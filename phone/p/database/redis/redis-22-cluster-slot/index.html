Cluster 的 hash slot 与请求路由

16384 个槽的分配、key→slot 定位公式与 MOVED/ASK 两种重定向｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 讲清 Cluster 用 16384 个槽做分片的原理，以及 slot = CRC16(key) mod 16384 的定位过程；
  2. 分清 MOVED 与 ASK：一个是「永久搬家」，一个是「临时借道」；
  3. 用 CLUSTER KEYSLOT / CLUSTER SLOTS / CLUSTER NODES 把「我这个 key 该去哪台」自己算出来。

二、前置知识

RD04（RESP，重定向就是错误回复变体）、RD18（复制，Cluster 的每个主节点也带从库）。以及 RD13（大 key），Cluster 里大 key 的危害被放大。

三、理论讲解（官方定义）

官方定义的槽位数量与定位方式（原文）：

Every Redis Cluster has 16384 hash slots … The hash slot for a given key is computed as CRC16(key) mod 16384.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/

以及重定向语义（原文要点）：

MOVED … means that the slot is permanently served by another node … ASK … means that the client should send the query to the specified node, but the next query for the same slot should be sent to the original node.

—— 同上

两条必须记死的定性：

  • 槽是第一等公民：路由、扩缩容、故障转移，操作对象都是「槽」，不是 key；
  • MOVED 是永久的，ASK 是临时的：客户端缓存规则完全不同。

四、原理拆解

1. 为什么是 16384

槽数是编译期常量 CLUSTER_SLOTS。选 16384（2^14）而不是更大，官方在 Cluster 规范里有说明，核心是两点权衡：心跳包要携带槽位位图（16384 bit = 2 KB，节点间心跳不至于太大），以及均摊到每个节点的槽数足够多，便于细粒度迁移。这是设计取舍，不是可配置项——你不能改槽数量。

2. 一次请求的完整路由

  1. 客户端算出 slot = CRC16(key) mod 16384；
  2. 查本地槽表，找到负责该槽的主节点；
  3. 直连该节点执行；
  4. 如果节点发现这个槽不归自己，返回重定向错误：
    • -MOVED 3999 127.0.0.1:6381 → 槽已永久迁走，更新本地槽表再重试；
    • -ASK 3999 127.0.0.1:6381 → 槽正在迁移中，本次去目标节点执行，不更新槽表。

第 4 步是 Cluster 客户端最核心的逻辑。写错的后果很典型：把 ASK 当成 MOVED 处理，客户端会把槽表永久改错，之后所有该槽的请求都发错节点，形成「重定向风暴」。

3. hash tag：把多个 key 绑到同一个槽

{user:1000}:name 与 {user:1000}:age 这两个 key，CRC16 只对 {} 内的内容（即 user:1000）计算，所以落在同一个槽。这是「多 key 操作」在 Cluster 中唯一合法的做法。

注意限制：同一个 {} 内不能嵌套，且 tag 必须非空（{} 空的等于没有 tag）。另外 tag 会让「分布均匀性」退化——如果大量 key 共享同一个 tag，它们会挤在一台节点上，形成热点与倾斜。

五、场景说明

  1. 数据量超过单机内存：多主分片，把数据摊到多台；
  2. 写入压力超过单主：多主同时承接写，这是 Cluster 相对 Sentinel 的核心价值；
  3. 按业务线分槽：用 hash tag 保证同业务的 key 同槽，便于多 key 命令；
  4. slot 倾斜排查：CLUSTER SLOTS 看槽区间长度，CLUSTER COUNTKEYSINSLOT 看实际 key 数。

不适合：强依赖多 key 事务/跨 key 操作的业务（同槽约束很硬）、需要 SELECT 多库的场景（Cluster 只有 0 号库）。

六、示例代码/实操步骤

# 1. 起一个 3 主 3 从的最小集群（详见下一讲，这里只看路由）
$ redis-cli --cluster create \
  127.0.0.1:7000 127.0.0.1:7001 127.0.0.1:7002 \
  127.0.0.1:7003 127.0.0.1:7004 127.0.0.1:7005 \
  --cluster-replicas 1

# 2. 查看集群拓扑
127.0.0.1:7000> CLUSTER NODES
# 07c37df... 127.0.0.1:7000@17000 myself,master - 0 0 1 connected 0-5460
# 45a1b1c... 127.0.0.1:7001@17001 master - 0 0 2 connected 5461-10922
# b6b7e4f... 127.0.0.1:7002@17002 master - 0 0 3 connected 10923-16383

# 3. 查看槽归属区间
127.0.0.1:7000> CLUSTER SLOTS
1) 1) (integer) 0
   2) (integer) 5460
   3) 1) "127.0.0.1"
      2) (integer) 7000

# 4. 算某个 key 的槽
127.0.0.1:7000> CLUSTER KEYSLOT user:1000
(integer) 15495                    # 落在 node 7002 上

# 5. hash tag 验证：两个 key 同槽
127.0.0.1:7000> CLUSTER KEYSLOT "{user:1000}:name"
(integer) 15495
127.0.0.1:7000> CLUSTER KEYSLOT "{user:1000}:age"
(integer) 15495                    # 相同 → 可以做多 key 操作

# 6. 触发一次 MOVED（连错节点）
127.0.0.1:7000> SET user:1000 v1
(error) MOVED 15495 127.0.0.1:7002
# 客户端应更新槽表后重试到 7002

# 7. 移动中的 ASK（reshard 过程中可能出现）
# (error) ASK 3999 127.0.0.1:7002
# 只本次转发，不更新槽表

# 8. 统计某槽的 key 数与抽样 key
127.0.0.1:7002> CLUSTER COUNTKEYSINSLOT 15495
(integer) 1234
127.0.0.1:7002> CLUSTER GETKEYSINSLOT 15495 10

Java 侧怎么落地：客户端必须换 Cluster 模式

代码层面最容易翻车的不是命令，而是连接方式：单机客户端连 Cluster，只能看到「碰巧在自己节点上的那部分 key」。

  1. 依赖：同样一个 starter，Lettuce 内置 Cluster 支持。
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. yml 用 cluster.nodes 而不是 host/port（至少写 2～3 个种子节点，节点全挂时才有退路）。
spring:
  data:
    redis:
      password: ${REDIS_PASS}
      timeout: 3s
      cluster:
        nodes:
          - 10.0.0.11:7000
          - 10.0.0.12:7001
          - 10.0.0.13:7002
        max-redirects: 3
  1. 打开槽表自动刷新：默认只在遇到 MOVED 时被动刷新；扩容/切换后主动刷新能少一轮重定向。
@Bean
LettuceClientConfigurationBuilderCustomizer clusterTopology() {
    return builder -> builder.clientOptions(ClientOptions.builder()
            .topologyRefreshOptions(ClusterTopologyRefreshOptions.builder()
                    .enableAllAdaptiveRefreshTriggers()
                    .adaptiveRefreshTriggersTimeout(Duration.ofSeconds(30))
                    .build())
            .build());
}
  1. key 设计先算槽再定 tag：需要一起读写的 key 用同一个 {}，且 tag 粒度要等于业务实体。
String tag = "{" + orderId + "}";
String k1 = tag + ":items";     // {1001}:items
String k2 = tag + ":total";     // {1001}:total → 与 k1 同槽
redisTemplate.opsForValue().multiGet(Arrays.asList(k1, k2));   // 同槽才不报 CROSSSLOT
  1. 删掉所有 SELECT n：Cluster 只有 0 号库，原本用库号做隔离的代码要改成 key 前缀（order: / user:），否则上线即报 ERR SELECT is not allowed in cluster mode。

七、常见坑（官方明确说明的限制）

  1. 多 key 命令必须同槽。MGET k1 k2、SUNION、MSET 等，跨槽直接报 CROSSSLOT Keys in request don't hash to the same slot。这不是客户端 bug，是分片模型的硬约束。
  2. ASK 与 MOVED 处理错。把 ASK 当 MOVED 缓存，会把槽表写坏；把 MOVED 当 ASK 不缓存，会一直重定向、性能崩塌。
  3. hash tag 用得过宽。所有 key 共用一个 tag = 全部落一台节点，等于没分片。
  4. {} 为空或嵌套无效。{} 空 tag 等价于无 tag；嵌套 {a{b}} 的实际 tag 是第一个 } 之前的内容，容易算错。
  5. 槽数不可配置。16384 是硬编码，不要试图「调大」。
  6. 客户端必须支持 Cluster 协议。单机客户端直连一个节点、不做重定向处理，只能读到「自己碰巧负责的那部分 key」，其余全报 MOVED——这是「上 Cluster 后数据好像少了一半」的典型原因。
  7. 只有 0 号库。SELECT 1 报错。想按库隔离就必须用 key 前缀。
  8. 主节点故障后槽不会自动消失，但集群在「槽覆盖不完整」时会拒绝服务（下一讲与 RD24 细说）。

版本差异（8.x 标注）

槽数、定位公式、MOVED/ASK 语义在 7.4 与 8.x 之间完全一致。8.x 的差异在运维与扩容细节（如更完善的 reshard 流程与集群管理命令），分片模型本身没有变化。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/

八、课后小结

  • Cluster 用 16384 个槽分片，槽是第一等公民；
  • 定位公式 slot = CRC16(key) mod 16384，{} 内的 hash tag 决定实际参与哈希的内容；
  • MOVED 永久、要更新槽表；ASK 临时、只本次转发；
  • 三张表：CLUSTER SLOTS / CLUSTER NODES / CLUSTER KEYSLOT；
  • 多 key 操作必须同槽，这是分片的硬约束；
  • 槽数不可改，客户端必须支持重定向。

九、思考题

  1. 两个 key 分别算出槽 15495 与 3999，怎么用 hash tag 让它们同槽？改完之后有什么副作用？

    参考回答：给两个 key 加同一个 tag，如 {user:1000}:name 与 {user:1000}:count，CRC16 只算 user:1000，两者必同槽。副作用：所有共享该 tag 的 key 都挤在同一节点，tag 越粗倾斜越严重；另外改 key 名意味着旧数据要迁移或双写过渡。

  2. 客户端把 ASK 和 MOVED 处理反了，会出现什么现象？怎么从日志上识别？

    参考回答：把 ASK 当 MOVED → 槽表被永久改错，之后所有该槽请求都发错节点，日志里出现大量指向同一节点的 MOVED；把 MOVED 当 ASK → 槽表永不更新，每次请求都多一次重定向，日志里同一槽的 MOVED 反复出现且延迟升高。

  3. 为什么 Cluster 选 16384 而不是 65536？提示：想想节点心跳要携带什么。

    参考回答：心跳（PING/PONG）里要带槽位位图，16384 bit 正好 2 KB，65536 就是 8 KB，60 个节点每秒多次心跳会白白吃掉带宽。同时 16384 分给上千节点也够细，是「带宽」与「迁移粒度」的折中。

  4. 一个业务所有 key 都用 {app} 作 tag，集群看起来「配好了但一台机器内存爆了」，原因是什么？

    参考回答：所有 key 的 CRC16 都只算 app，于是全部落进同一个槽、同一台节点——集群退化成单机，其余节点空转。修法是把 tag 细化到业务实体（{order:1001}），并用 CLUSTER COUNTKEYSINSLOT 抽查各槽 key 数确认倾斜已消除。

  5. 已知某 key 一直报 MOVED，你如何用三条命令确认「它到底该在哪台节点」？

    参考回答：① CLUSTER KEYSLOT <key> 拿到槽号；② CLUSTER SLOTS 查这个槽区间归哪个节点；③ 连到那台节点 CLUSTER COUNTKEYSINSLOT <slot> 或直接 GET 验证。三步就能判断是「槽表过期」还是「key 真的不在那」。
