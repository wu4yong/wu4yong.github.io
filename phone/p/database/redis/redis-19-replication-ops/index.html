复制配置与四类典型故障

7.x 的复制配置项、INFO replication 观测点与四类典型故障｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 把复制的必备配置项配全（replicaof / masterauth / replica-read-only / backlog / 优先级 / 可用性保护）；
  2. 用 INFO replication 的五个观测点，快速判断「延迟、全量风暴、写失败、数据漂移」是哪一类；
  3. 知道每个故障的根因与处置动作，而不是只会重启。

二、前置知识

RD18（PSYNC 与三要素）。本讲是它的运维面：同样的机制，换到「出问题时怎么定位」。

三、理论讲解（官方定义）

官方对从库可写性的规定（原文）：

Since Redis 2.6, replicas also support read-only mode, which is enabled by default and controlled by the replica-read-only configuration directive.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/replication/

以及可用性保护配置（原文要点）：

min-replicas-to-write … min-replicas-max-lag … if the number of connected replicas with a lag less than the specified value drops below the configured value, the master stops accepting writes.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/replication/

这两条是「从库只读」与「少从库就不让写」的官方依据，很多团队只知道前者。

四、原理拆解

1. 必备配置清单

其中 replica-priority 0 的用法值得单独记：它让某个从库永远不参与选主（比如只用于备份的延迟从库），避免切换后主库落在弱机器上。

2. 五个观测点

排查顺序建议固定成：role → link_status → offset 差 → sync_full 增速 → 日志。这个顺序能把「配置错、网络断、积压滚出、数据漂移」快速区分开。

3. 四类典型故障

① 全量风暴：多个从库同时重连，主库反复 fork + 传输。特征是 sync_full 短时间暴涨、主库内存与 IO 冲高、客户端延迟抖动。处置：错峰重启、加大 repl-backlog-size、开启无盘复制、必要时逐个恢复从库。

② 反复全量：sync_full 持续增长但每次都能连上。根因通常是 backlog 太小（断线一次就滚出）或网络抖动频繁。处置：重算 backlog = 写入速率 × 容忍断线秒数；检查网络丢包与超时。

③ 从库写失败：报 READONLY You can't write against a read only replica。要么代码把写请求路由到了从库，要么有人 replica-read-only no 后误写导致主从不一致。处置：修正路由；保持只读。

④ 主从数据漂移：从库 key 数少于主库、值更旧。常见根因是主从 maxmemory 与淘汰策略不一致（主库淘汰了某些 key，从库因为内存更大没淘汰，或反之），也可能是从库被写过。处置：两台机器配置对齐、定期用 DBSIZE 与抽样 key 比对。

五、场景说明

  1. 一主两从的缓存集群：replica-read-only yes + backlog 调到 32 MB + min-replicas-to-write 1；
  2. 备份专用从库：replica-priority 0，只承担 BGSAVE 与备份拷贝；
  3. 跨机房从库：延迟较大，min-replicas-max-lag 要按真实网络 RTT 调，不能照抄 10；
  4. 切换演练：故意 kill 一个从库，观察 sync_partial_ok 是否增长（说明走增量）而不是 sync_full。

六、示例代码/实操步骤

# 1. 从库配置（配置文件写法）
# replicaof 10.0.0.5 6379
# masterauth "YourPass"
# replica-read-only yes
# repl-backlog-size 64mb
# replica-priority 100

# 2. 运行时挂主并校验
127.0.0.1:6380> REPLICAOF 10.0.0.5 6379
OK
127.0.0.1:6380> INFO replication
# master_link_status:up
# slave_repl_offset:998877

# 3. 主库侧确认从库在线
127.0.0.1:6379> INFO replication
# connected_slaves:1
# slave0:ip=10.0.0.6,port=6380,state=online,offset=998877,lag=0

# 4. 测延迟：写入后立刻读从库
127.0.0.1:6379> SET latency:probe 1
OK
127.0.0.1:6380> GET latency:probe
(nil)                            # 还没同步过来，说明存在复制延迟窗口
127.0.0.1:6380> GET latency:probe
"1"                              # 稍后就有了

# 5. 打开可用性保护
127.0.0.1:6379> CONFIG SET min-replicas-to-write 1 min-replicas-max-lag 10
OK
# 现在若唯一的从库掉线超过 10 秒，主库会拒绝写：
# (error) NOREPLICAS Not enough good replicas to write.

# 6. 检查是否在反复全量
127.0.0.1:6379> INFO stats
# sync_full:37                  ← 37 次全量，明显异常
# sync_partial_ok:2
# sync_partial_err:35

# 7. 处置：加大 backlog 后复测
127.0.0.1:6379> CONFIG SET repl-backlog-size 64mb
OK
# 断开再从库重连，观察 sync_full 是否不再增长

# 8. 数据漂移核对
127.0.0.1:6379> DBSIZE
(integer) 1234567
127.0.0.1:6380> DBSIZE
(integer) 1234000                # 少了 567 个，需要查淘汰策略与写入

Java 侧怎么落地：把「复制健康」做进应用的告警面

复制配置是服务端的，Java 侧的价值在于「写失败会不会被正确处理」和「延迟能不能被看见」。

  1. 依赖照旧：spring-boot-starter-data-redis，不需要额外组件。
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. yml 里显式设置超时与重试语义：min-replicas-to-write 生效后，主库会返回 NOREPLICAS，默认重试只会把线程池耗光。
spring:
  data:
    redis:
      host: 10.0.0.5
      timeout: 3s
      lettuce:
        pool:
          max-active: 16
          max-wait: 1s
  1. 单独识别 NOREPLICAS / READONLY，不要当成普通异常吞掉：前者是「保护生效」，后者是「写到了从库」，处置完全不同。
try {
    redis.opsForValue().set(key, value);
} catch (RedisSystemException e) {
    String msg = String.valueOf(e.getMessage());
    if (msg.contains("NOREPLICAS")) {
        metrics.counter("redis.write.no_replicas").increment();   // 保护生效：走降级队列
        throw new DegradeException("replicas lost");
    }
    if (msg.contains("READONLY")) {
        metrics.counter("redis.write.readonly").increment();      // 路由错了：修正数据源
        throw new RoutingException("write hit a replica");
    }
    throw e;
}
  1. 延迟用 offset 差做指标，不要用 lag：lag 基于心跳、秒级且会被抖动放大；offset 差是字节级，更能反映真实落后。
long masterOffset = parseLong(infoMaster, "master_repl_offset");
long slaveOffset  = parseLong(infoSlave,  "slave_repl_offset");
Metrics.gauge("redis.repl.lag_bytes", masterOffset - slaveOffset);

配套一条硬规则：sync_full 建议按「每小时增量」打点，绝对值没有意义（重启会清零）；这个指标持续上涨就是全量风暴的前兆。

七、常见坑（官方明确说明的限制）

  1. masterauth 漏配是最常见的「复制起不来」原因：日志会反复出现 NOAUTH，master_link_status 一直是 down。
  2. replica-read-only 只是「默认只读」，把它设成 no 并不会让从库「更好用」，只会让主从数据漂移。
  3. min-replicas-to-write 默认 0，等于没保护；但它一旦生效，从库全掉时主库会拒绝写，业务要有降级预案，否则「保护」会变成「全站不可写」。
  4. lag 字段的单位是秒且基于心跳，网络抖动会把它放大，不能用它做精确的延迟数值，精确看 offset 差。
  5. sync_full 是累计计数，重启会清零，所以要看「单位时间增量」而不是绝对值。
  6. 跨机房从库的复制是全量数据过网，带宽成本很高；预算不足时优先同机房多从 + 异地备份文件，而不是异地实时从库。
  7. 从库不会主动过期（RD12 已讲），内存占用可能高于主库；maxmemory 要给从库留出这部分余量。

版本差异（8.x 标注）

配置项名称在 5.0 后统一为 replicaof / replica-read-only（旧的 slaveof / slave-read-only 仍兼容）。8.x 的复制配置语义不变，差异集中在许可与集群运维细节。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/replication/

八、课后小结

  • 复制配置六件套：replicaof、masterauth、replica-read-only、backlog、replica-priority、min-replicas-*；
  • 观测五字段：role、master_link_status、offset 差、master_last_io_seconds_ago、sync_full 增速；
  • 四类故障：全量风暴、反复全量、从库写失败、主从数据漂移；
  • backlog 要按「写入速率 × 容忍断线秒数」重算，默认 1 MB 太小；
  • min-replicas-to-write 是「少从库就不让写」的保护，用之前必须有降级预案。

九、思考题

  1. 一个从库连不上主库，master_link_status 一直是 down，日志只有 NOAUTH。最可能漏了哪个配置？

    参考回答：漏了 masterauth。主库设了 requirepass 而从库没配主库密码，握手阶段直接 NOAUTH，连接反复重试、状态永远 down。

  2. sync_full 一小时内涨了 50 次，你会先查哪三个东西？

    参考回答：① repl-backlog-size 是否太小（按写入速率 × 容忍断线秒数重算）；② 网络是否频繁抖动/超时（看丢包与 master_last_io_seconds_ago）；③ 是否有多个从库同时重连或主库刚重启（replid 变了）。这三项能覆盖绝大多数反复全量。

  3. min-replicas-to-write 1 生效后，唯一从库宕机 → 主库拒绝写 → 业务怎么办？给出两条降级路径。

    参考回答：一是降级为本地队列：写请求进内存队列/MQ，等从库恢复再补写（要求业务能容忍延迟）；二是临时关闭保护：运维确认可以接受 RPO 退化后 CONFIG SET min-replicas-to-write 0，恢复读写并同时告警。第二条是止血手段，必须留审计记录。

  4. 主库 maxmemory-policy allkeys-lru、从库 noeviction，会发生什么？为什么？

    参考回答：会数据漂移。淘汰只在主库发生并同步为 DEL，从库收到 DEL 才删；但从库自己是 noeviction，内存不足时不是淘汰而是拒绝写/报错，导致从库 key 集合与主库逐渐不一致，且从库内存可能更高。

  5. 为什么备份专用从库要设 replica-priority 0？

    参考回答：replica-priority 是故障转移的选主权重，0 表示永不参与选主。备份从库通常磁盘大、配置低、还跑着 BGSAVE，让它当了主会把弱机器变成写入口，所以显式排除。
