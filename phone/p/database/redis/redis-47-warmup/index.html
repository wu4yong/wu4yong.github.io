预热、降级与演练

上线前的预热、故障时的降级、上线后的演练｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 用「访问日志取 TopN」做预热，并用命中率而不是 key 数量判断预热是否完成；
  2. 给缓存层设计三道降级闸：限流、熔断、开关；
  3. 设计一次「真删缓存 + 真压库」的演练，并写出可执行的复盘结论。

二、前置知识

RD12（淘汰策略）、RD36（Pipeline 批量写入）、RD39–RD46（本模块前八讲）。这一讲是 M7 的收口：把前面所有设计放进一次「真的会坏」的场景里验证。

三、理论讲解（官方定义）

这里能用得上的官方表述有两类。

其一，内存与淘汰的真实行为（原文要点）：

When Redis reaches the max memory limit … it will apply the eviction policy … If no keys can be evicted, write commands return an error.

—— https://redis.io/docs/latest/develop/reference/eviction/

这句话的含义：缓存不是「无限可用」的。预热前必须算清「峰值数据量是否装得下」，否则没等业务被打挂，Redis 先开始拒绝写入。

其二，maxmemory-policy 的取值（原文列表摘要）：

noeviction / allkeys-lru / allkeys-lfu / allkeys-random / volatile-lru / volatile-lfu / volatile-random / volatile-ttl

缓存场景通常用 allkeys-lru 或 allkeys-lfu；用 volatile-* 系列时，没有设置过期的 key 永远不会被淘汰，这是一个非常常见的配置事故。

至于预热、降级、演练的具体做法，Redis 官方不提供规范，属于工程实践。

四、原理拆解

1. 预热：只有「热 key」值得预热

步骤：
① 从访问日志/监控里取 TopN key（按 QPS × 命中价值排序）
② 用 Pipeline 分批写入（RD36），每批 500–1000 条，避免单次阻塞
③ 观察命中率曲线：达到预期（如 95%+）才算完成

三个判断标准：

  • 不是全量预热：全量预热会把库的压力搬到发布窗口，还可能把冷数据塞满内存触发淘汰；
  • 判据是命中率：写进去 100 万个 key，命中率只涨了 2%，说明预热选错了 key；
  • 容量要先算：峰值 key 数 × 平均 value 大小 + 开销 是否小于 maxmemory，这个乘法必须先做。

2. 降级：三道闸的顺序

请求进入
 ① 限流（入口按 IP/接口 QPS 丢弃）→ 保护整个系统
 ② 熔断（缓存错误率超阈值，直接走兜底值/默认值）→ 保护单次调用
 ③ 开关（关掉非核心功能）→ 保护主链路

顺序不能颠倒：先限流（成本最低、影响面可控），再熔断（局部放弃），最后动开关（大范围关停）。颠倒会在小故障时触发大面积关停。

缓存的降级有一个额外要求：缓存层故障时应「变慢」而不是「不可用」。这意味着业务代码必须写 try { cache } catch { db }，且 db 侧的连接池要能承受这个放大。

3. 演练：验证的是「最坏情况」

演练不是「压测接口 QPS」，而是制造故障：

演练动作
验证目标
观察指标
停掉 Redis
业务是否只变慢
错误率、P99、库 QPS
删掉全部缓存
库能否撑住冷启动
库连接数、慢查询
网络延迟注入 200ms
超时配置是否合理
熔断触发点、重试次数
主从切换
客户端是否自动恢复
切换耗时、失败请求数

每一步都要有明确的通过判据（如「错误率 < 1%、P99 < 500ms」），否则演练只是「看了一眼」。

4. 复盘要落到「配置与代码」

演练结论如果只写成「Redis 挂了会很慢」，等于没做。有效的复盘产出是：

  • 具体的参数改动（如「库连接池 20 → 60」「熔断阈值 50% → 30%」）；
  • 具体的功能开关清单（哪些接口可以在故障时关掉）；
  • 具体的值班动作（谁在什么时候看什么指标、按什么顺序处理）。

TopN 预热与命中率判据、限流→熔断→开关的先后顺序、四类演练动作的观察指标与复盘产出｜依据 Eviction 与 INFO 文档自绘

五、场景说明

  1. 大促前一周：按历史峰值预热 TopN，压测「冷缓存」场景；
  2. 发布前：确认缓存层降级开关已配置并可一键触发；
  3. 季度演练：至少做一次「停 Redis」与「删缓存」，把结论写回配置；
  4. 不适合：无监控、无告警的系统先做演练——你无法判断是否通过。

六、示例代码/实操步骤

# 1. 先算容量：当前内存与上限
127.0.0.1:6379> INFO memory
# used_memory_human:3.21G
# maxmemory_human:4.00G
# maxmemory_policy:allkeys-lru

# 2. 预热：用 Pipeline 批量写（每批 500 条，示意）
#    redis-cli --pipe 读取准备好的命令文件
$ redis-cli --pipe < warmup.txt
# All data transferred. Waiting for the last reply...

# 3. 观察预热效果（命中率是否上来）
127.0.0.1:6379> INFO stats
# keyspace_hits:8_120_334
# keyspace_misses:201_776

# 4. 检查是否触发淘汰（说明容量不足）
127.0.0.1:6379> INFO stats
# evicted_keys:12044          ← 持续增长 = 预热过量或容量不足

# 5. 演练：删掉一批缓存，观察库的压力
#    （生产用具体 key 前缀，禁用 KEYS）
127.0.0.1:6379> SCAN 0 MATCH user:* COUNT 1000
# 拿到一批 key 后逐个 DEL，观察库的 QPS 与连接数

# 6. 演练：停掉 Redis（容器/服务方式），确认业务降级生效
#    观察应用日志：是否切到「查库 + 兜底值」，错误率是否可控

# 7. 确认降级开关可用（示例：运维侧配置读取）
127.0.0.1:6379> GET feature:cache:bypass
"0"                            # 1=跳过缓存直连库

Java 侧怎么落地：预热用管道，降级用熔断 + 开关

  1. pom：Redis（Pipeline 预热）、Caffeine（本地兜底缓存）、Resilience4j（熔断）。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<dependency>
  <groupId>io.github.resilience4j</groupId>
  <artifactId>resilience4j-spring-boot3</artifactId>
  <version>2.2.0</version>
</dependency>
  1. application.yml：熔断阈值与降级开关都外置，别写死在代码里：
resilience4j:
  circuitbreaker:
    instances:
      redisCache:
        failure-rate-threshold: 50
        slow-call-duration-threshold: 200ms
        wait-duration-in-open-state: 10s
feature:
  cache-bypass: false        # 1=跳过缓存直连库，故障时一键打开
spring:
  data:
    redis:
      timeout: 200ms
      lettuce:
        pool: { max-active: 64, max-wait: 100ms }
  1. 预热用 executePipelined 分批写，一批 500 条，别用 for 循环单条 SET：
for (List<Map.Entry<String, String>> batch : partition(topN, 500)) {
    redis.executePipelined((RedisCallback<Object>) c -> {
        batch.forEach(e -> c.set(e.getKey().getBytes(), e.getValue().getBytes()));
        return null;
    });
}
  1. 缓存调用包一层熔断，打开状态直接走兜底（查库或返回默认值），不要让异常冒到接口：
@CircuitBreaker(name = "redisCache", fallbackMethod = "fromDb")
public Item get(long id) { return cache.get(id); }
public Item fromDb(long id, Throwable t) { return repo.findById(id).orElse(null); }

  1. 降级开关做成运行时读取（配置中心 / @RefreshScope），打开后所有读走库并压掉缓存写入；同时准备「可关功能清单」，按接口粒度关非核心。

  2. 演练看指标而不是看感觉：actuator/prometheus 暴露 hikaricp_connections_pending、http_server_requests 的 P99 与错误率，演练前后对比；不达标就调连接池与超时，把新数值写回配置。

七、常见坑（官方明确说明的限制）

  1. 全量预热。把库压力搬到发布窗口，还可能撑爆 maxmemory 触发淘汰。
  2. 用「写入了多少 key」判断预热成功。应看命中率与回源 QPS。
  3. 不先算容量。used_memory 接近 maxmemory 时写入会开始失败（noeviction 下直接报错）。
  4. 用 volatile-* 策略但 key 没设 TTL。这类 key 永远不会被淘汰，内存只涨不降（官方淘汰规则如此）。
  5. 降级顺序颠倒。小故障直接触发大范围关停，损失比故障本身大。
  6. 缓存异常直接抛出。缓存是旁路，异常必须被吞掉并回源，否则一个小故障变成全站不可用。
  7. 演练没有判据。只「看了一眼」没有通过/不通过，等于没演练。
  8. 演练后不改配置。发现的连接池不足、超时过长不落到配置里，下次还会发生。
  9. 生产用 KEYS。官方明确警告 KEYS 是 O(N) 且阻塞，必须用 SCAN。

版本差异（8.x 标注）

maxmemory-policy 的八个取值与淘汰语义在 7.4 与 8.x 一致；8.x 在运维工具与集群管理上有增强，可作为演练自动化的载体。许可方面 8.0 起为 AGPLv3/SSPL 双许可，商用需评估。

依据：https://redis.io/docs/latest/develop/reference/eviction/

八、课后小结

  • 预热只做 TopN，判据是命中率，前提是先算容量；
  • 降级三道闸：限流 → 熔断 → 开关，顺序不能反；
  • 缓存是旁路，异常必须吞掉并回源，保证「变慢不变挂」；
  • 演练要制造故障、要有通过判据、要有复盘产出；
  • 复盘必须落到具体参数与开关清单，否则下次照旧。

九、思考题

  1. 你的业务峰值 key 数 × value 大小是多少？能装进当前 maxmemory 吗？

    参考回答：算法是「峰值 key 数 × (平均 value + key 与对象开销) × 1.2～1.5 余量」再和 maxmemory 比。举例：800 万个 key、平均 1.2 KB → 约 9.6 GB，若 maxmemory 只有 4 GB 就装不下，只能预热 TopN 并给冷数据更短 TTL。

  2. 预热 100 万个 key 后命中率只涨 2%，可能的原因有哪三个？

    参考回答：① key 选错——预热的是冷 key，真实请求集中在另外的 key；② 请求没走到缓存——入口绕过、key 拼装规则不一致（多前缀/多编码）；③ 预热后被淘汰——容量不足，evicted_keys 持续增长，写进去又被踢掉。

  3. 为什么降级顺序不能「先关开关再限流」？

    参考回答：开关影响面最大，先关会在一个小抖动里造成大面积功能不可用，损失大于故障本身。正确顺序是先限流（成本最低、影响面可控）、再熔断（局部放弃单次调用）、最后才动开关关掉非核心。

  4. 「停掉 Redis」演练的通过判据你会怎么写？给出具体数字。

    参考回答：例：停 Redis 30 分钟内，接口错误率 < 1%、P99 < 500 ms（正常 200 ms）、库 QPS 不超过容量 70%、hikaricp_connections_pending 不持续大于 0、无雪崩式超时。任一条不满足即判不通过，必须改配置后重跑。

  5. 演练发现库连接池不够，你会改哪一个参数？改完怎么验证有效？

    参考回答：改 HikariCP 的 maximumPoolSize（配套 connectionTimeout 与队列上限），例如 20 → 60，同时确认数据库侧 max_connections 够用。验证方式：用同样场景重跑演练，看 hikaricp_connections_pending 归零、获取连接超时告警消失、P99 回到判据内。
