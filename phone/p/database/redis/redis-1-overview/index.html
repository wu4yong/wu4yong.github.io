redis-1-能力边界

分类：database · redis ｜ 标签：系统课 · Redis · 缓存

能力边界与最小概念闭环

客户端 → RESP → 单线程执行 → keyspace 的最小闭环｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用一句话说清 Redis 是什么、官方把它定位在哪三种角色上；
  2. 讲明白「key → value + TTL」这个最小闭环，以及「逻辑库」是怎么回事；
  3. 遇到业务需求时，能判断这事该不该用 Redis，而不是默认「有缓存就上 Redis」。

二、前置知识

无。这一讲是整门课的地基，只需要你会用命令行、写过一个后端接口。

三、理论讲解（官方定义）

官方文档开篇给出的定义是这样的（原文）：

Redis is an open source (BSD licensed), in-memory data structure store, used as a database, cache, and message broker.

—— https://redis.io/docs/latest/get-started/

拆开这句话，有四个词是硬信息，一个都不能含糊：

  • in-memory（内存型）：数据主要在内存里操作，磁盘是持久化副本。所以容量上限由 RAM 决定，这决定了它天然不是「什么都能存」的仓库。
  • data structure store（数据结构存储）：它不是「一个 key 对应一段 JSON 字符串」这么简单，value 有 String、Hash、List、Set、Sorted Set、Stream、Bitmap、HyperLogLog、GEO 等多种类型，每种类型自带一套操作语义。
  • database / cache / message broker（三种角色）：官方把它同时定位成数据库、缓存和消息中间件。注意「数据库」这个角色是官方认可的，但后面我们会看到它的持久化和事务能力与关系型数据库不是一个量级——能当数据库用，不等于该当强一致主库用。
  • BSD licensed：7.4 及以前是 BSD 三条款许可。这条在 8.0 变了，见本节末尾的版本差异。

再看官方对「key」和「value」的定义（原文）：

Redis keys are binary safe, meaning you can use any binary sequence as a key, from a string like “foo” to the content of a JPEG file. The empty string is also a valid key. The maximum allowed key size is 512 MB.

—— https://redis.io/docs/latest/develop/data-types/

这句话有三个可以直接落地的结论：key 是二进制安全的；空字符串也是合法 key（但别这么干）；单个 key 上限 512 MB。

四、原理拆解

1. 最小闭环：客户端 → 协议 → 执行 → 键空间

一条命令的完整旅程只有四站（对应上面那张图）：

  1. 客户端把命令编码成 RESP 协议（文本协议，下一讲 RD04 细讲），通过 TCP 发到 6379 端口；
  2. 服务端解析成命令 + 参数；
  3. 主线程串行执行这条命令，命令执行期间不会同时执行别的命令；
  4. 结果写进 keyspace：一个 key 对应一个 value，value 上可以挂一个过期时间（TTL）。

所以「单线程」不是设计缺陷，而是官方刻意选择的一致性保证手段：命令级原子性天然成立，因为你不可能同时执行两条命令。这也是后面 INCR 能当计数器、SETNX 能当锁的前提。

官方在 FAQ 里明确写过：Redis 的命令执行是单线程的，而 6.0 起引入了可选的 I/O 多线程（io-threads）用于读写 socket，命令执行依旧是单线程。

—— https://redis.io/docs/latest/develop/get-started/faq/

这两件事经常被混为一谈，必须分清：IO 多线程 ≠ 命令并发执行。

命令从客户端到 keyspace 的四站，以及 io-threads 究竟加速了哪一段｜依据 Redis 7.4 Get started / FAQ 自绘

2. 逻辑库：默认 16 个

databases 16 是默认配置，于是有了 0–15 号库，SELECT 1 切库。要注意三点官方约束：

  • 集群模式下只有 0 号库可用，SELECT 会报错；
  • 不同库之间的 key 完全隔离，不能跨库原子操作（MOVE 除外，它是移动不是关联）；
  • 生产环境不建议按业务切库来隔离，官方更推荐用不同实例或者用 key 前缀做命名空间。

3. 三种角色的能力错位

五、场景说明

下面四类需求，用 Redis 是官方文档明确支持的用法，可以直接上：

  1. 缓存与会话：热点数据、登录态，配合 TTL 自动过期；
  2. 排行榜与计数：Sorted Set 天然按分值排序，INCR/HINCRBY 是原子计数；
  3. 分布式锁与限流：SET key value NX PX 的原子性来自单线程执行；
  4. 轻量消息：Stream 有消费组和 ack，比 Pub/Sub 可靠。

下面四类需求，建议在方案评审时就否掉，别等上线后返工：

  1. 需要多表 JOIN 的复杂查询——Redis 没有表、没有 JOIN、没有二级索引（除非自己维护）；
  2. 作为唯一持久化的主数据库——持久化是「可配置的可靠性」，不是「不丢」的承诺；
  3. 事务型强一致业务（转账那种）——MULTI 不支持回滚、不支持跨 key 的隔离级别承诺；
  4. 海量冷数据长期归档——内存单价与 RAM 容量都不允许。

六、示例代码/实操步骤

先起一个最干净的实例来验证上面的闭环（安装细节在下一讲，这里假设已有 redis-server）：

# 1. 起服务（前台，方便看日志）
redis-server --port 6379

# 2. 连上并验证协议闭环
redis-cli -p 6379
127.0.0.1:6379> PING
PONG

# 3. 最小 key-value：value 是二进制安全的字符串
127.0.0.1:6379> SET user:1:name "阿勇"
OK
127.0.0.1:6379> GET user:1:name
"阿勇"

# 4. 挂 TTL：这是缓存语义的核心
127.0.0.1:6379> SET session:abc "uid=1" EX 60
OK
127.0.0.1:6379> TTL session:abc
(integer) 60
127.0.0.1:6379> TTL user:1:name
(integer) -1          # -1 表示 key 存在但没有过期时间

# 5. 看逻辑库与键数量
127.0.0.1:6379> DBSIZE
(integer) 3
127.0.0.1:6379> SELECT 1
OK
127.0.0.1:6379> DBSIZE
(integer) 0           # 换库了，键空间是独立的

TTL 的三种返回值是官方定义，必须记住：-2 表示 key 不存在，-1 表示存在但无过期时间，正整数是剩余秒数。

Java 侧怎么落地：Spring Boot 接入的四步

命令行验证完，把它接进一个 Java 工程，只需要四步，代码不用写全，关键是知道「改哪里」。

  1. 建工程，选 Boot 版本：Spring Boot 2.7.x 或 3.x 都能用，JDK 8 / 17 均可；Boot 3 要求 JDK 17。

  2. pom 里只加一个 starter（这一步决定了客户端是 Lettuce，Spring Boot 默认装配）：

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<!-- 需要连接池参数时再加 commons-pool2，否则 lettuce.pool 配置不生效 -->
  1. application.yml 配连接（这几个键是 Boot 3 的写法，Boot 2.7 是 spring.redis.*，改名是升级时最常见的坑）：
spring:
  data:
    redis:
      host: 127.0.0.1
      port: 6379
      password: S3cretForClass   # 服务端 requirepass 配了就必须写，否则 NOAUTH
      database: 0                # 对应 SELECT 0；集群模式只能是 0
      timeout: 2s                # 一次往返的上限，不是空闲断连时间
      lettuce:
        pool:
          max-active: 16
          max-idle: 8
          min-idle: 2
  1. 注入模板并验证闭环：StringRedisTemplate 的 key/value 都用 UTF-8 字符串，避免 JDK 序列化在 redis-cli 里看到乱码；用一个 ApplicationRunner 打印 PING 与一次带 TTL 的写入即可完成自检。
@Bean
ApplicationRunner selfCheck(StringRedisTemplate tpl) {
    return args -> {
        tpl.opsForValue().set("session:abc", "uid=1", Duration.ofSeconds(60)); // 等价 SET ... EX 60
        log.info("ping={}, ttl={}", tpl.getConnectionFactory().getConnection().ping(), tpl.getExpire("session:abc"));
        tpl.delete("session:abc");
    };
}

三个必须记住的对应关系：Duration.ofSeconds(60) ↔ EX 60；getExpire 返回 -2/-1 与命令行一致；不要用 keys("*")（RedisTemplate.keys 就是 KEYS），批量扫描用 scan。

七、常见坑（官方明确说明的限制）

  1. KEYS * 在生产上是事故级操作。官方对 KEYS 的说明是 O(N) 扫描全部键，会阻塞主线程；官方明确建议用 SCAN 做增量迭代。
  2. 一个慢命令会卡住所有客户端。因为是单线程执行，KEYS、大 key 的 HGETALL、SMEMBERS、DEL 大集合都会阻塞。官方在 DEL 文档里专门推荐用 UNLINK（异步释放）。
  3. 持久化不是「已落盘」的同义词。默认 appendfsync everysec 意味着一秒窗口，官方在 AOF 文档中写得很清楚；RDB 更是按快照点，两次快照之间的写入在崩溃时会丢。
  4. maxmemory 不配置就没有上限，一直涨到被 OOM Killer 干掉。默认淘汰策略是 noeviction，此时写命令会直接返回错误，而不是自动删数据。
  5. 集群模式只有 0 号库，依赖 SELECT 的旧代码迁到 Cluster 会直接报错。

版本差异（8.x 标注）

8.0 起 Redis 的许可证改为 AGPLv3（并提供 SSPL 选项），不再沿用 BSD。这意味着闭源商用前需要走法务评估；本课程主线仍是 7.4 的 BSD 语境，8.x 只在每个相关章节单独标注差异。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/

八、课后小结

  • Redis 是内存型数据结构存储，官方定位为数据库、缓存、消息中间件三种角色；
  • 最小闭环是「客户端 → RESP → 单线程执行 → keyspace（key + value + TTL）」；
  • 单线程保证的是命令级原子性，IO 多线程只加速网络收发，不改变命令串行执行；
  • 逻辑库默认 16 个，集群模式只有 0 号库；
  • 别把「能当数据库」读成「能当强一致主库」。

九、思考题

  1. 你的业务要存一个 300 MB 的商品快照做缓存，单 key 上限 512 MB 没超，为什么这仍然是个坏设计？

    参考回答：问题不在「超没超 512 MB」，而在单线程处理它的一次读写就够阻塞所有人——网络传输、序列化、过期删除都是整块操作；同时它让主从同步、迁移、扩容都被一个大对象拖住。正确做法是拆分粒度（如按字段存 Hash）或把快照放对象存储，Redis 只留索引。

  2. 如果一个 key 上挂了 TTL，但客户端始终在读它，这个 key 到了过期时间会不会立刻消失？为什么？

    参考回答：不会立刻消失。官方是惰性删除 + 定期抽样删除：到期后 key 仍可能短暂存在，直到被访问或被抽样命中才真正删除；所以「过期」不等于「准时消失」，业务不能依赖 TTL 做精确时点控制。

  3. 为什么说「单线程」既是 Redis 快的来源，也是它最容易被打挂的原因？这两面各举一个具体命令。

    参考回答：快的一面是数据在内存、命令串行无锁竞争、无上下文切换，GET/SET 就是一次哈希查表。挂的一面是任何 O(N) 命令都会独占主线程：KEYS * 全库扫描，DEL 一个百万元素的集合同步释放，都会让其他客户端排队。

  4. 8.0 的许可证变化，对「公司内部系统用 Redis 做缓存」和「把 Redis 打包进对外销售的软件」分别意味着什么？

    参考回答：内部当缓存用，AGPL 的义务主要落在「向第三方分发 / 提供网络服务」上，内部自用通常不触发，但仍建议法务确认；把 Redis 打包进对外销售的软件属于分发，必须遵守 AGPLv3（或购买商业许可），不能继续按 BSD 时代的方式闭源分发。
