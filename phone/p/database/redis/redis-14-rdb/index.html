RDB 快照：fork、CoW 与丢数据的边界

BGSAVE 的三步流程、四类触发方式与四条官方约束｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 讲清 RDB 的本质是「某一时刻的全量内存快照」，以及 fork + 写时复制（CoW）是怎么做到「不停服」的；
  2. 记住四类触发方式与关键配置（save、dbfilename、dir、stop-writes-on-bgsave-error），知道每一项在事故里的表现；
  3. 能明确说出 RDB 的丢数据边界：为什么它天然做不到 RPO=0，以及什么时候这个代价可以接受。

二、前置知识

RD12（过期与淘汰，理解「内存里到底有什么」）。持久化就是把内存里的东西落盘，先清楚内存结构再谈落盘。

三、理论讲解（官方定义）

官方对 RDB 的定位（原文）：

RDB persistence performs point-in-time snapshots of your dataset at specified intervals.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/

这句话有三个词必须咬住：

  • point-in-time：它记录的是某个瞬间的完整状态，不是「逐条变更」；
  • snapshot：快照是整体，不存在「只备份一部分」；
  • at specified intervals：由配置点或手动触发决定，不是每条写都落盘。

四、原理拆解

1. 一次 BGSAVE 的三步

BGSAVE 是「后台保存」，它靠 fork 实现，全流程只有三步：

  1. fork()：主进程复制一份自己（子进程），此时父子进程共享同一份物理内存页，不复制数据；
  2. 子进程遍历写临时文件：子进程把内存里的所有 key 按 RDB 格式写到 temp-<pid>.rdb。主进程同时继续处理客户端命令；
  3. rename 原子替换：写完后把临时文件改名为 dump.rdb。rename 是原子的，所以任何时刻磁盘上都是一个完整文件，不会出现「写了一半的 RDB」。

这就是「快照能不停服」的全部秘密。但代价藏在第 2 步里，下一节讲。

2. 写时复制（CoW）：为什么内存会涨

fork 之后父子共享内存页，但只要主进程改写了某一页，内核就会为这一页复制一份给主进程，原页留给子进程继续读。这叫写时复制（Copy-on-Write）。

于是有两条必须记住的结论：

  • 子进程看到的内存是 fork 那一刻的固定视图，所以快照是「时间点」的，不会被后续写入污染；
  • 主进程每秒写入越多，CoW 复制的页越多，额外内存越多。极端情况下（全库都在被改），这份额外内存接近数据总量——即「快照期间内存翻倍」。

官方在 INFO 里专门给了观测字段：

INFO persistence
# rdb_bgsave_in_progress:0        —— 是否正在 bgsave
# rdb_last_bgsave_status:ok       —— 上次结果
# rdb_last_bgsave_time_sec:-1     —— 耗时
# rdb_changes_since_last_save:0   —— 距上次快照的写次数
# rdb_last_cow_size:0             —— 上次 fork 期间的 CoW 内存
# latest_fork_usec:0              —— 上次 fork 阻塞主线程的微秒数

latest_fork_usec 与 rdb_last_cow_size 是排查「快照期间变慢 / 内存报警」的第一手数据。

3. 四类触发方式

  1. 手动 SAVE：在主线程完成整个快照，期间完全阻塞，生产环境禁止使用；
  2. 手动 BGSAVE：后台 fork 执行，可用于「打备份点」；
  3. save 配置点自动触发：7.x 默认是 save 3600 1 300 100 60 10000，含义是「3600 秒内有 1 次写 / 300 秒内有 100 次写 / 60 秒内有 10000 次写」就触发一次；
  4. 其他隐式触发：SHUTDOWN 关服务时（有 save 配置才会保存）、主从首次全量同步时主节点自动 BGSAVE。

save "" 可以彻底关闭自动快照，仅保留手动 BGSAVE——很多「只要 AOF」的部署会这么做。

4. 丢数据的边界：RPO 不是 0

RDB 只在快照点落盘，所以：

  • 两次快照之间的所有写入，如果进程崩溃 / 机器掉电，全部丢失；
  • 最坏情况下的丢失窗口 = 最大间隔（save 配置里最长的那条，或你手动 BGSAVE 的间隔）。

这就是「RDB 天然不保证 RPO=0」。它适合「能接受几分钟丢失」的场景（缓存重建、可重放的派生数据），不适合账务、订单这类「丢一条就是事故」的数据——那需要 AOF（下一讲）。

五、场景说明

  1. 缓存层的兜底：宕机后从 RDB 快速恢复大部分缓存，剩余靠回源，恢复速度最快；
  2. 定期冷备：每天低峰 BGSAVE，把 dump.rdb 传到对象存储；
  3. 主从全量同步的载体：从节点首次接入、或复制积压断开后重连，都靠 RDB 全量传输；
  4. 大数据量搬迁：同版本搬迁直接拷 RDB，比逐条命令重放快得多。

不适合：要求「最多丢 1 秒」的在线业务（该开 AOF）、需要「精确到某条命令」审计的场景（RDB 是二进制快照，没有命令记录）。

六、示例代码/实操步骤

# 1. 看当前快照配置
127.0.0.1:6379> CONFIG GET save
1) "save"
2) "3600 1 300 100 60 10000"
127.0.0.1:6379> CONFIG GET dir
1) "dir"
2) "/var/lib/redis"
127.0.0.1:6379> CONFIG GET dbfilename
1) "dbfilename"
2) "dump.rdb"

# 2. 手动触发后台快照（生产可用）
127.0.0.1:6379> BGSAVE
Background saving started

# 3. 观察进度与结果
127.0.0.1:6379> INFO persistence
# rdb_bgsave_in_progress:1
# rdb_last_bgsave_status:ok
# rdb_last_cow_size:1048576
# latest_fork_usec:2345

# 4. 关掉自动快照，只留手动
127.0.0.1:6379> CONFIG SET save ""
OK

# 5. 校验文件完整性（在 shell 里执行）
$ redis-check-rdb /var/lib/redis/dump.rdb
[offset 0] Checking RDB file dump.rdb
[offset 1234] AUX FIELD redis-ver = '7.4.0'
[offset 567890] Checksum OK

# 6. 快照失败时的保护行为
127.0.0.1:6379> CONFIG GET stop-writes-on-bgsave-error
1) "stop-writes-on-bgsave-error"
2) "yes"
# 若 dir 不可写导致 bgsave 失败，接下来的写命令会返回：
# (error) MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk.

最后那条 MISCONF 错误是可观测的保护机制：它逼你修磁盘问题，而不是让服务「看起来很健康但数据不落盘」。要么修好 dir 权限，要么确认「确实不需要 RDB」后把该配置设为 no。

Java 侧怎么落地：应用不参与，但四件事必须做到

RDB 是服务端行为，Java 侧没有 API 可调，但下面四件事决定「快照能不能安全跑」。

  1. 配置留在服务端模板里：save 策略、dir、dbfilename 写进 redis.conf 并纳入 git；不要用 CONFIG SET dir 在线改——集群/容器里容易出现「一半节点写新目录、一半还写旧目录」。

  2. 应用侧算清内存余量：maxmemory 要给 CoW 留空间。把「数据量 × 1.2～2 倍」写进容量评估，别按物理内存的 90% 设 maxmemory（RD51 详讲）。

  3. 监控 MISCONF 错误而不是等业务反馈：写命令报 MISCONF Redis is configured to save RDB snapshots... 时，客户端应该保留原始错误并单独打点，因为这时候业务侧通常只看到「写失败率升高」，很难联想到磁盘。

catch (RedisSystemException e) {
    if (e.getMessage() != null && e.getMessage().contains("MISCONF")) {
        metrics.counter("redis.persist.misconf").increment();   // 直接告警到运维
    }
}
  1. 停机/发布流程要「等人恢复」：SHUTDOWN 带 save 会先落盘；容器 docker stop 的 grace period 太短会直接 SIGKILL 杀掉主进程，最后一次快照不会完成。所以在 K8s 里给 Redis 留足 terminationGracePeriodSeconds。

七、常见坑（官方明确说明的限制）

  1. SAVE 会阻塞全部客户端。它在主线程完成整个写盘过程，数据量越大卡得越久。线上只用 BGSAVE。
  2. 快照期间内存可能接近翻倍。CoW 复制的页数与写入量相关，maxmemory 需要给这部分留余量，否则会被 OOM Killer 干掉。
  3. fork 本身也会阻塞。虽然不复制数据，但复制页表在百万级 key 上仍需毫秒到数十毫秒，latest_fork_usec 就是它。
  4. stop-writes-on-bgsave-error yes 会让写全部失败。这不是 bug，是保护；但它会把「磁盘满了」升级成「服务不可写」，运维要监控 rdb_last_bgsave_status。
  5. dir 与 dbfilename 配错会静默不落盘。尤其是容器里 dir 指向临时目录，重启即丢。
  6. RDB 是二进制私有格式。跨大版本恢复要先用同版本 redis-check-rdb 校验；rdbchecksum yes 时校验和不符会拒绝加载。
  7. rdbcompression 只压缩字符串，不减少结构开销，所以大 Hash 压缩率有限，别指望它解决内存问题。
  8. RDB 没有增量。每次都是全量，数据量大时单次快照的耗时与磁盘 IO 都很可观。

版本差异（8.x 标注）

7.0 起支持多部分 AOF 后，RDB 仍是「全量快照」的唯一格式；8.x 的 RDB 文件格式与 7.x 兼容性需要在目标版本验证。save 默认值在 7.x 已调整为 3600 1 300 100 60 10000，老文档里的 900 1 300 10 属于旧默认值。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/

八、课后小结

  • RDB 是某一时刻的全量内存快照，靠 fork + CoW 实现「不停服」；
  • 三步：fork → 子进程写临时文件 → rename 原子替换；
  • 四类触发：SAVE（阻塞，禁用）/ BGSAVE / save 配置点 / 关服务与主从全量同步；
  • CoW 让快照期间内存可能接近翻倍，fork 本身也会短暂阻塞；
  • RDB 只在快照点落盘，两次快照之间的写入会丢，天然做不到 RPO=0；
  • stop-writes-on-bgsave-error yes 会让写失败，这是保护不是缺陷。

九、思考题

  1. fork 之后父子进程「共享内存」，为什么子进程写文件时不会看到主进程后来的改动？靠的机制叫什么？

    参考回答：靠写时复制（Copy-on-Write）。fork 后父子共享物理页且页表标为只读，主进程一旦要改某页，内核先复制一份给它、原页留给子进程读。于是子进程看到的是 fork 那一刻的固定视图，快照因此是「时间点」快照。

  2. 一次 BGSAVE 期间主进程写了 10 GB 数据，CoW 内存大约会是多少？这对 maxmemory 设置意味着什么？

    参考回答：CoW 额外内存 ≈ 被改写的页数，最坏情况接近被写入的数据量，即约 10 GB（现实中通常少一些，因为一页里可能被多次改写只复制一次）。这意味着 maxmemory 必须留出与「快照期间写入量」相当的余量，否则会被 OOM Killer 杀掉。

  3. 一台机器 64 GB 内存、数据 40 GB、maxmemory 设了 45 GB，跑 BGSAVE 时会发生什么？

    参考回答：fork 后主进程继续写入触发 CoW，额外内存最坏接近 40 GB，45 + 40 远超 64 GB，很可能被系统 OOM Killer 杀掉，或者触发 swap 把实例拖到卡死。正确做法是 maxmemory 设在 35 GB 以下（留出 CoW 与碎片余量），或把快照放到从节点/独立机器上做。

  4. 为什么线上推荐在从节点上做备份，而不是主节点？

    参考回答：备份动作（BGSAVE/SCP/压缩上传）会消耗 CPU、磁盘 IO 与 CoW 内存，放在从节点上就不会影响主节点的读写延迟与内存水位；主节点只承担复制，从节点出问题也不影响写入入口。

  5. 「RDB 恢复比 AOF 快」这句话对不对？为什么？

    参考回答：基本对。RDB 是把内存镜像直接按格式读入，恢复速度取决于数据量与磁盘吞吐；AOF 需要逐条重放命令（还要解析协议），同样的数据量通常慢数倍。但要注意 7.0 的混合持久化（AOF 里嵌 RDB 前缀）会兼顾两者：启动先加载 RDB 部分，快得多。
