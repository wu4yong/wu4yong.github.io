主从复制：PSYNC、replid 与全量增量

PSYNC 握手四步、replid/offset/backlog 三要素与全量触发条件｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 讲清 PSYNC 握手的完整流程，以及 +FULLRESYNC 与 +CONTINUE 两种回复分别意味着什么；
  2. 用 replid、offset、backlog 三要素解释「断点续传」成立的条件；
  3. 判断一次重连会走全量还是增量，并知道全量同步对主库的真实代价。

二、前置知识

RD14（RDB 快照，全量同步用的就是它）与 RD16（重写，理解 fork 的代价）。复制是全量 + 增量的组合，两者都建立在前两批的知识上。

三、理论讲解（官方定义）

官方对复制的定位（原文）：

Redis uses by default asynchronous replication, which is fast and non-blocking … Redis replication is a very simple yet fast approach.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/replication/

关键限定是 asynchronous：主库把命令写给从库后就继续自己的事，不等从库确认。这一条决定了后面所有「主从延迟」「切换时可能丢数据」的结论。

增量复制的机制（原文要点）：从库重连时发送 PSYNC <replid> <offset>，主库若能在复制积压缓冲区（replication backlog）里找到该偏移，就回 +CONTINUE，只补这段；否则回 +FULLRESYNC，走全量。

四、原理拆解

1. 握手四步

  1. 从库连上主库，完成 PING / AUTH（主库设了密码就要 masterauth）；
  2. 从库发 PSYNC：首次是 PSYNC ? -1，表示「我不知道你是谁、也没有偏移」；
  3. 主库回复：
    • +FULLRESYNC <replid> <offset> → 我要给你全量；
    • +CONTINUE → 你之前连过我，只补增量；
  4. 全量流程：主库 BGSAVE 生成 RDB → 传输给从库 → 从库加载 → 主库把「快照期间新产生的写命令」从 backlog 里补发 → 之后进入实时命令流。

注意第 4 步里的关键点：全量传输期间主库仍在接收写入，这些写入先进 backlog，等从库加载完 RDB 再补发。所以 RDB 是「旧」的，但补发之后能追平。

2. 三要素：为什么能断点续传

要素
是什么
作用
replid
主库的身份标识（40 位十六进制）
让从库确认「你还是当初那个主库」
offset
主库每处理一条写命令就累加的字节偏移
标记「我处理到哪了」
backlog
主库维护的环形缓冲区（repl-backlog-size，默认 1mb）
存放最近一段命令，供从库补差

判定逻辑只有一句：从库的 offset 是否落在 backlog 的覆盖范围内。落在范围里 → 补增量；滚出去了 → 只能全量。

7.0 起还引入了 replid2：当发生主从切换（比如 Sentinel 把从库提为主库）时，新主库会保留旧主库的 replid 作为 replid2，让其他从库仍能做部分同步而不是被迫全量。这是 7.x 相对旧版本在「切换后的复制连续性」上的重要改进。

3. 全量的真实代价

全量同步 = fork + 写 RDB + 传输 + 从库加载。四项开销：

  • 主库 fork 与 CoW：写量大时额外内存可能接近数据总量（RD14 讲过）；
  • 磁盘 IO：生成 RDB 要写盘（除非开无盘复制）；
  • 网络带宽：整份数据过一次网；
  • 从库加载阻塞：加载期间从库不可用，且加载完还要补发 backlog 里的新命令。

所以「多个从库同时重连」是最危险的情形——主库被反复 fork，内存与 IO 一起顶到峰值。这就是「全量风暴」，工程上要靠错峰重启、加大 backlog、开启无盘复制来缓解。

4. 复制是异步的，一致性别指望配置

主库写完就返回，从库可能落后几十毫秒到几秒。这带来两个必然结论：

  • 读从库可能读到旧值（复制延迟），对「读己之写」有要求的业务必须读主库；
  • 切换时可能丢最后一段写入（主库崩在「已写内存、未传给从库」的窗口里）。

没有任何配置项能把异步复制变成同步复制。要「少丢」，只能靠 min-replicas-to-write 这类「至少 N 个从库确认才允许写」的保护。

连上 → PSYNC ? -1 → 判定（FULLRESYNC / CONTINUE）→ 传输 → 补发的五步，断点续传三要素，以及一次全量的四份开销｜依据 Redis 7.4 Replication / PSYNC 文档自绘

五、场景说明

  1. 读写分离：一主多从，读请求打从库，写打主库——前提是业务能接受延迟；
  2. 备份与灾备：从库上做 BGSAVE，不干扰主库（RD17 的推荐做法）；
  3. 故障转移的基础：Sentinel 与 Cluster 的切换都建立在复制之上；
  4. 在线迁移：新实例 REPLICAOF 当从库，同步完成再提升为主。

不适合：要求「主从强一致」的账务读写分离（异步复制给不了）、写多到单主扛不住的场景（该用 Cluster）。

六、示例代码/实操步骤

# 1. 在从库上挂主库（两种方式）
$ redis-server --port 6380 --replicaof 127.0.0.1 6379
# 或运行中：
127.0.0.1:6380> REPLICAOF 127.0.0.1 6379
OK

# 2. 观察同步状态
127.0.0.1:6380> INFO replication
# role:slave
# master_host:127.0.0.1
# master_port:6379
# master_link_status:up          ← 必须是 up
# master_last_io_seconds_ago:0
# slave_repl_offset:1234567
# slave_read_only:1

# 3. 主库侧看从库列表
127.0.0.1:6379> INFO replication
# role:master
# connected_slaves:1
# slave0:ip=127.0.0.1,port=6380,state=online,offset=1234567,lag=0

# 4. 关键计数器：全量 vs 增量
127.0.0.1:6379> INFO stats
# sync_full:1                    ← 全量次数
# sync_partial_ok:5              ← 增量成功次数
# sync_partial_err:0             ← 增量失败次数

# 5. 调大 backlog（评估公式：写入速率 × 期望容忍的断线秒数）
127.0.0.1:6379> CONFIG GET repl-backlog-size
1) "repl-backlog-size"
2) "1048576"
127.0.0.1:6379> CONFIG SET repl-backlog-size 64mb
OK

# 6. 验证增量：断开再连，看 sync_full 是否增加
# 从库执行 REPLICAOF NO ONE 断开，再 REPLICAOF 连回
127.0.0.1:6379> INFO stats | grep sync_
# 未增长 → 走的是 +CONTINUE（增量）

# 7. 断开从库提升为主
127.0.0.1:6380> REPLICAOF NO ONE
OK
127.0.0.1:6380> INFO replication | grep role
# role:master

Java 侧怎么落地：读写分离在客户端怎么开

复制本身是服务端的事，Java 侧能做的是「把读命令真正打到从库」，并管住读己之写。

  1. 依赖：Spring Boot 3 + Lettuce（默认），一个 starter，不需要主从两套依赖。
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. yml 里挂从库地址：一主一从最简单的写法是 spring.data.redis.sentinel 或集群；纯主从则用自定义 LettuceConnectionFactory 指向主库，再从库地址单独配一项。
spring:
  data:
    redis:
      host: 10.0.0.5          # 主库：写 + 强一致读
      port: 6379
      timeout: 3s
app:
  redis:
    replica-uri: redis://10.0.0.6:6379
  1. 让 Lettuce 自动把读命令发给副本：ReadFrom.REPLICA_PREFERRED 会在有副本时优先用副本连接，写命令仍走主库。
@Configuration
public class RedisReadFromReplicaConfig {
    @Bean
    LettuceClientConfigurationBuilderCustomizer replicaPreferred() {
        return builder -> builder.readFrom(ReadFrom.REPLICA_PREFERRED);
    }
}
  1. 读己之写要自己兜：REPLICA_PREFERRED 不知道你刚写过什么，写后立刻读可能拿到旧值。工程做法是写操作后给当前请求打一个「短窗口强制读主」标记。
public String getProfile(long uid) {
    String key = "user:profile:" + uid;
    if (ReadYourWrite.forceMaster()) {            // 写后 100ms 内为 true
        return masterTemplate.opsForValue().get(key);
    }
    return redisTemplate.opsForValue().get(key);  // 走副本
}

上线前先量 master_repl_offset - slave_repl_offset 的常态差值：差值稳定在几十 KB 才谈读写分离，差值抖到几 MB 说明网络或从库跟不上，读从只会放大「脏读」投诉。

七、常见坑（官方明确说明的限制）

  1. master_link_status: down 时从库数据是旧的。此时读从库会拿到过期数据，监控必须盯这个字段，不能只看进程存活。
  2. repl-backlog-size 默认只有 1 MB。写入快的实例（每秒几 MB）断线几十秒就会滚出 backlog，被迫全量。生产上按「写入速率 × 容忍断线时间」重算，常见调到几十 MB。
  3. 全量同步期间从库不可用。加载 RDB 是阻塞的，几 GB 数据可能加载几十秒，这期间客户端读从库会超时。
  4. 主库重启可能改变 replid，导致所有从库全量。7.0 的 replid2 缓解了「切换」场景，但主库重启用的是新 replid，该全量还得全量。
  5. 从库默认只读（replica-read-only yes），写命令报 READONLY You can't write against a read only replica。这不是权限问题，是保护。
  6. min-replicas-to-write 默认 0，即不保护。要「至少 1 个从库可用才允许写」，必须显式配置，并配合 min-replicas-max-lag。
  7. 异步复制不会自动重试丢掉的写入。切换后若发现从库落后，只能人工核对补齐，Redis 没有「自动对账」能力。
  8. 复制不复制过期动作本身：从库不主动过期，等主库的 DEL 同步（RD12 已讲），所以从库内存可能涨得更快。

版本差异（8.x 标注）

7.0 起支持 replid2（主从切换后的部分同步）与无盘复制相关增强；8.x 沿用 PSYNC 协议。若环境是 5.x/6.x，切换后从库大概率被迫全量，切换成本要按全量预估。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/replication/

八、课后小结

  • PSYNC 握手只有两种结果：+FULLRESYNC（全量）与 +CONTINUE（增量）；
  • 断点续传靠三要素：replid 认身份、offset 记位置、backlog 存差额；
  • 全量 = fork + RDB + 传输 + 加载，四份开销同时压在主库与网络上；
  • 复制是异步的，读从库可能旧、切换可能丢最后一段写入，配置改不了这个事实；
  • repl-backlog-size 默认 1 MB，写入快的实例必须调大；
  • replid2（7.0+）让「切换后的从库」还能做部分同步。

九、思考题

  1. 从库重连时，主库根据什么判断「能不能只补增量」？如果 backlog 只有 1 MB 而写入是 5 MB/s，断线 3 秒会发生什么？

    参考回答：看从库上报的 offset 是否还落在 backlog 的覆盖范围内（即这段命令是否还在环形缓冲里）。1 MB 缓冲在 5 MB/s 下只覆盖约 0.2 秒，断线 3 秒需要补 15 MB，早已滚出，主库只能回 +FULLRESYNC——走全量。

  2. 全量同步正在进行，主库又写了 1 万条命令，这 1 万条去哪了？从库加载完 RDB 后怎么追上？

    参考回答：进了复制积压缓冲区（backlog）和从库的输出缓冲。从库加载完 RDB 后，主库把这些命令按 offset 顺序补发过去，之后转入实时命令流——所以 RDB 是「旧」的，但补发后能追平。

  3. master_link_status: up 就代表数据一致吗？请给出一个反例。

    参考回答：不代表。up 只说明连接在、同步在跑；复制是异步的，主库刚写的 key 从库可能还没有——SET 后立刻 GET 从库返回 nil 就是最直接的反例。

  4. 为什么 7.0 要引入 replid2？它解决了主从切换后的什么问题？

    参考回答：解决「切换后从库被迫全量」。新主会保留旧主 replid 作为 replid2，其它从库带着旧 replid+offset 来连时能被识别为「同一个复制历史」，从而走 +CONTINUE 增量，而不是整库重传。

  5. 主库重启会导致所有从库全量，这个代价怎么在变更窗口里规避？

    参考回答：主库重启会生成新 replid、backlog 也清空，从库必然全量。规避办法：重启前把从库逐个断开（REPLICAOF NO ONE），重启完再逐个挂回、错峰；或先切主到从库、重启原主后作为从库追平，避免全量风暴叠加。
