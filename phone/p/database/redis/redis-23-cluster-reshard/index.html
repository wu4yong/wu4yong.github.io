Cluster 搭建、扩容与 reshard

节点数要求、扩容四步流程与 reshard 期间的观测点｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 Cluster 的前提条件（至少 3 主、集群模式端口、节点配置文件），并亲手搭一个 3 主 3 从；
  2. 按「加节点 → 迁槽 → 平衡 → 复检」四步完成一次扩容；
  3. 知道 reshard 期间 ASK 重定向的原因，以及为什么它不能「停服迁移」。

二、前置知识

RD22（槽与路由）。本讲是把「槽」真正搬来搬去的操作面，也是 Cluster 最容易出事故的地方。

三、理论讲解（官方定义）

官方对最小集群的要求（原文）：

The minimal cluster that works as expected requires to contain at least three master nodes.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/

以及节点配置文件的说明（原文要点）：

Every Redis Cluster node requires two TCP connections open … the normal Redis TCP port … and the second port is obtained by adding 10000 to the data port (e.g. 16379 for port 6379).

—— 同上

两个硬性前提：

  • 至少 3 个主节点（否则多数票无法达成，故障转移没有意义）；
  • 每个节点要开两个端口：数据端口 + 集群总线端口（数据端口 + 10000）。防火墙只放行了 6379 而漏了 16379，是最常见的「集群配好了但一直 fail」的原因。

四、原理拆解

1. 搭建的三个前置条件

条件
要求
漏了的症状
cluster-enabled yes
每节点开启集群模式
启动后是普通单机，CLUSTER INFO 报未启用
cluster-config-file nodes-<port>.conf
每节点唯一的集群状态文件
同机多实例会互相踩配置
端口放行
数据端口 + port + 10000
CLUSTER NODES 里节点互相 fail

另外：集群模式启动后，节点会强制只用 0 号库，且不允许 SELECT。

2. 扩容四步

① 加节点：用 redis-cli --cluster add-node <new> <existing> 把新节点拉进集群。此时它是空主节点，没有任何槽，所以不承载任何 key。

② 迁槽：redis-cli --cluster reshard 交互式输入「迁多少槽、迁到哪个节点、从哪些节点迁」。底层是：

  • CLUSTER SETSLOT <slot> MIGRATING <target-id>（源节点标「迁出中」）；
  • CLUSTER SETSLOT <slot> IMPORTING <source-id>（目标节点标「迁入中」）；
  • 对槽内每个 key 执行 MIGRATE（逐 key 搬数据）；
  • 搬完 CLUSTER SETSLOT <slot> NODE <target-id> 收尾。

③ 平衡：redis-cli --cluster rebalance 按 key 数/槽数自动均摊。也可以只做 --cluster check 看倾斜。

④ 复检：CLUSTER INFO 的 cluster_state:ok、cluster_slots_assigned:16384、cluster_known_nodes，再抽样读几个 key。

3. 为什么 reshard 期间会出现 ASK

迁移中的槽处于「源节点还有一部分 key、目标节点已接过一部分」的状态。此时：

  • 请求打到源节点，key 还在 → 正常执行；
  • 请求打到源节点，key 已搬走 → 回 ASK，让客户端去目标节点；
  • 请求打到目标节点，槽还没正式归属它 → 也回 ASK，指回源节点（ASK 是双向的）。

所以 reshard 不需要停服，客户端只要正确处理 ASK 就能平滑过渡。代价是迁移期间这些 key 的延迟会升高（多一次网络跳转）。

4. 迁移的成本与节奏

  • MIGRATE 是同步阻塞命令，单 key 大时（大 key）会卡住源节点；
  • 建议按「小批量 + 限速」迁：reshard 支持 --cluster-pipeline / --cluster-yes 等参数控制批量；
  • 大 key 要先治理（RD13），否则一次 MIGRATE 可能阻塞几百毫秒甚至更久。

五、场景说明

  1. 从 3 主扩到 6 主：数据量翻倍后的标准扩容路径；
  2. 热点节点缓解：rebalance 或手工针对性迁槽；
  3. 机器替换：先 add-node 新机，迁完槽再 del-node 旧机；
  4. 演练环境：本机 6 个端口起 3 主 3 从，是最省资源的验证方式。

不要在业务高峰期做大比例 reshard：迁移期间源节点 CPU 与网络都会升高，且大 key 会造成明显抖动。

六、示例代码/实操步骤

# 1. 准备 6 个节点配置（7000-7005），每个都要独立目录与配置文件
# redis-7000.conf
# port 7000
# cluster-enabled yes
# cluster-config-file nodes-7000.conf
# cluster-node-timeout 15000
# appendonly yes
# dir /data/7000
$ redis-server /etc/redis/redis-7000.conf
# 其余 7001-7005 同理，只改端口

# 2. 确认端口都在（数据端口 + 10000）
$ ss -lntp | grep -E '700[0-5]|1700[0-5]'

# 3. 建集群：3 主 3 从
$ redis-cli --cluster create \
  127.0.0.1:7000 127.0.0.1:7001 127.0.0.1:7002 \
  127.0.0.1:7003 127.0.0.1:7004 127.0.0.1:7005 \
  --cluster-replicas 1 --cluster-yes

# 4. 检查集群健康
$ redis-cli --cluster check 127.0.0.1:7000
# [OK] All 16384 slots covered.
# [OK] All nodes agree about slots configuration.

127.0.0.1:7000> CLUSTER INFO
# cluster_state:ok
# cluster_slots_assigned:16384
# cluster_slots_ok:16384
# cluster_known_nodes:6
# cluster_size:3

# 5. 扩容：加两个新节点（一主一从）
$ redis-cli --cluster add-node 127.0.0.1:7006 127.0.0.1:7000
$ redis-cli --cluster add-node 127.0.0.1:7007 127.0.0.1:7000 --cluster-slave \
  --cluster-master-id <7006 的 node-id>

# 6. 迁槽：从三个老主各迁 1000 个槽到 7006
$ redis-cli --cluster reshard 127.0.0.1:7000 \
  --cluster-from <src1>,<src2>,<src3> \
  --cluster-to <7006 的 node-id> \
  --cluster-slots 3000 \
  --cluster-yes

# 7. 观察迁移过程
127.0.0.1:7000> CLUSTER NODES
# 7006 的槽数逐渐增长；老节点的槽区间被切走
# 迁移中的槽在有 key 时会返回 ASK：

127.0.0.1:7000> GET migrate:probe
(error) ASK 3999 127.0.0.1:7006

# 8. 平衡与复检
$ redis-cli --cluster rebalance 127.0.0.1:7000 --cluster-use-empty-masters
$ redis-cli --cluster check 127.0.0.1:7000

# 9. 移除旧节点（前提：它已无槽、无 key）
$ redis-cli --cluster del-node 127.0.0.1:7000 <old-node-id>

七、常见坑（官方明确说明的限制）

  1. 只开数据端口。集群总线端口（+10000）不通，节点永远无法握手，CLUSTER NODES 全是 fail 或 handshake。
  2. 少于 3 个主节点。官方明说 3 主是最小可用规模；2 主的「集群」在故障转移时无法凑够多数票。
  3. nodes.conf 复用。多实例共用或拷贝该文件，会把旧拓扑带进新集群，出现莫名的槽冲突。
  4. reshard 不做限速。默认一次性迁完指定槽，大 key 会导致源节点阻塞、客户端超时。
  5. 迁槽期间客户端不支持 ASK。表现为间歇性的 MOVED/ASK 错误与超时，业务感觉是「扩容期间莫名抖动」。
  6. del-node 删还有槽的节点。集群会立刻变成 cluster_state:fail（槽覆盖不完整），必须先迁空。
  7. cluster-node-timeout 默认 15 秒，跨机房或高负载下容易误判节点失败，要按真实 RTT 调。
  8. 扩容后没有重设从库。新主节点如果没有从库，故障转移时它的槽无人接管——扩容要「加主 + 加从」成对做。
  9. 集群模式禁用多库。迁移旧应用时要先改 SELECT 相关代码。

版本差异（8.x 标注）

redis-cli --cluster 子命令在 7.4 已完备（create/check/reshard/rebalance/del-node/add-node）。8.x 沿用同一套流程；差异主要在集群管理工具链的完善度与许可条款，操作步骤不变。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/

八、课后小结

  • 最小集群 3 主；每节点要开数据端口与 +10000 总线端口；nodes.conf 每节点独立；
  • 扩容四步：add-node → reshard → rebalance → check；
  • reshard 底层是 SETSLOT MIGRATING/IMPORTING + 逐 key MIGRATE + SETSLOT NODE；
  • 迁移中的槽会回 ASK（双向），因此可以不停服扩容；
  • MIGRATE 是同步阻塞的，大 key 必须先治理；
  • del-node 前必须把槽迁空，否则集群直接 fail。
