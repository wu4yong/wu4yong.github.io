Sentinel 架构与选举

Sentinel 集群拓扑、四个故障阶段与关键参数｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 说清 Sentinel 是什么：独立进程组成的监控集群，不是代理、不转发请求；
  2. 讲清 sdown → odown → 选领导者 → 选新主四阶段的判定链条，以及 quorum 的真实含义；
  3. 配好 sentinel monitor / down-after-milliseconds / failover-timeout / parallel-syncs 四个参数，并知道配错的后果。

二、前置知识

RD18（复制机制）与 RD19（复制配置与故障）。Sentinel 的所有动作都建立在「主从已经配好、从库能同步」之上。

三、理论讲解（官方定义）

官方定位（原文）：

Redis Sentinel provides high availability for Redis when not using Redis Cluster. … Sentinel is a distributed system …

—— https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/

两个要点：

  • provides high availability：它解决的是「主库挂了怎么办」，不解决容量与写入扩展；
  • distributed system：它本身是多进程协作，靠互相投票达成一致，所以单点部署等于没有 Sentinel。

它明确不做的事（官方也写了）：不代理流量、不做分片、不保证数据零丢失。客户端依旧直连主库，Sentinel 只负责「告诉客户端主库是谁，并在故障时改写这个答案」。

四、原理拆解

1. 拓扑：三样东西各司其职

  • 客户端：启动时向 Sentinel 询问主库地址，订阅切换通知；
  • Sentinel 集群：通常 3 个（或 5 个）独立进程，互相 PING、交换状态，共同判定故障；
  • 数据节点：一个主库 + N 个从库，被监控、被投票、被切换。

注意 Sentinel 与数据节点是不同进程，可以同机部署（生产一般分开，避免同机故障一起死）。

2. 四个阶段

① sdown（主观下线）：某个 Sentinel 在 down-after-milliseconds 内没收到目标节点的有效响应，就会在自己的视角里把它标为「主观下线」。这只是单个 Sentinel 的判断。

② odown（客观下线）：当标记 sdown 的 Sentinel 数量达到 quorum，该节点升级为「客观下线」。这一步是「多个独立观察者达成一致」，避免单台 Sentinel 的网络问题误判。

③ 选领导者：由至少多数（majority）Sentinel 投票选出一个 Sentinel 来执行本次切换。这一点必须和 quorum 分清：

  • quorum 决定「能不能判定客观下线」；
  • 领导者选举要求「超过半数 Sentinel 同意」。

举例：5 个 Sentinel、quorum 2。2 个就能判 odown，但执行切换仍需 3 票（多数）。这就是为什么 Sentinel 数量要奇数、且不要只部署 2 个。

④ 选新主并通知：领导者按规则挑一个从库提升为主：

  1. 先看 replica-priority（越小越优先，0 表示永不参选）；
  2. 再看复制 offset（越新越优先，尽量少丢数据）；
  3. 最后看 runid 字典序（兜底保证确定性）。

选定后：把其余从库 REPLICAOF 到新主、通过 Pub/Sub 广播 +switch-master、旧主恢复后以从库身份归队。

3. 四个关键参数

参数 默认 含义与配错后果
sentinel monitor mymaster <ip> <port> <quorum> 无 监控目标与 odown 票数；quorum 太大 = 切换迟钝，太小 = 易误判
down-after-milliseconds 30000 多久无响应算 sdown；太短会因网络抖动频繁误判
failover-timeout 180000 切换与重试的总时限；太短会导致切换半途被放弃
parallel-syncs 1 切换后同时向新主同步的从库数量；调大加快恢复但会拉高新主负载

parallel-syncs 的取舍很典型：它越大，切换后集群整体恢复越快，但新主瞬间要扛多份全量同步（RD18 讲的 fork + 传输），可能把刚上任的主库打挂。

4. Sentinel 的配置是自动改写的

官方明确说明：Sentinel 会自动重写自己的配置文件（记录已知的 Sentinel、从库、当前主库）。所以：

  • 运行中手动编辑 sentinel.conf 会被覆盖，改动要重启或通过 SENTINEL 命令；
  • 每台 Sentinel 的配置天然会「逐渐趋同」，但不要在运行期手工对齐它们。

五、场景说明

  1. 中小规模单主写入：3 个 Sentinel + 1 主 2 从，是最常见的高可用形态；
  2. 多套主从共用一组 Sentinel：可以监控多个 master（每组一个 sentinel monitor 名字）；
  3. 延迟从库：replica-priority 0 让它永不参选，只做备份与只读查询；
  4. 异地容灾：跨机房 Sentinel 要谨慎（网络分区会导致误判与脑裂），一般同机房为主。

不适合：需要写入水平扩展、数据量超单机（该上 Cluster）；要求 RPO=0（Sentinel 基于异步复制，切换必然可能丢最后一段）。

六、示例代码/实操步骤

# 1. 三台机器各起一个 Sentinel（端口 26379）
$ redis-sentinel /etc/redis/sentinel.conf

# 2. 最小配置（sentinel.conf）
# sentinel monitor mymaster 10.0.0.5 6379 2
# sentinel auth-pass mymaster YourPass
# sentinel down-after-milliseconds mymaster 30000
# sentinel failover-timeout mymaster 180000
# sentinel parallel-syncs mymaster 1

# 3. 查看监控状态
127.0.0.1:26379> SENTINEL master mymaster
# name mymaster
# ip 10.0.0.5
# port 6379
# flags master
# num-slaves 2
# num-other-sentinels 2
# quorum 2
# failover-timeout 180000

# 4. 查看从库与其它 Sentinel
127.0.0.1:26379> SENTINEL replicas mymaster
127.0.0.1:26379> SENTINEL sentinels mymaster

# 5. 主动查主库地址（客户端启动时就这么干）
127.0.0.1:26379> SENTINEL get-master-addr-by-name mymaster
1) "10.0.0.5"
2) "6379"

# 6. 手动触发一次切换（演练用）
127.0.0.1:26379> SENTINEL FAILOVER mymaster
OK
# 随后可看到：
127.0.0.1:26379> SENTINEL get-master-addr-by-name mymaster
1) "10.0.0.6"                    # 主库已换

# 7. 模拟主库宕机（真实验证）
$ redis-cli -h 10.0.0.5 -p 6379 SHUTDOWN NOSAVE
# 等 down-after-milliseconds + 选举时间后，看日志：
# +sdown master mymaster 10.0.0.5 6379
# +odown master mymaster 10.0.0.5 6379 #quorum 2/2
# +try-failover master mymaster 10.0.0.5 6379
# +switch-master mymaster 10.0.0.5 6379 10.0.0.6 6379

日志里这四行对应四个阶段，是排障时最该认识的文本。

七、常见坑（官方明确说明的限制）

  1. 只部署 1 个或 2 个 Sentinel。1 个没有「多数」可言；2 个在一次网络分区时可能各自选主，导致脑裂。生产至少 3 个且奇数。
  2. quorum 与「多数票」混淆。quorum 只负责判 odown；执行切换仍要多数。5 个 Sentinel 配 quorum 5 会让切换几乎不可能发生。
  3. down-after-milliseconds 调得太短。业务有慢查询或网络抖动时，短超时会频繁误判下线并触发无谓切换。
  4. parallel-syncs 调太大。切换后多个从库同时全量同步新主，新主可能直接被压垮，切换变成二次故障。
  5. 手工改 sentinel.conf：会被自动重写覆盖。改配置要改完重启，或用 SENTINEL SET。
  6. Sentinel 不做数据转发。客户端仍直连数据节点，所以客户端必须支持 Sentinel 协议（发 SENTINEL get-master-addr-by-name 或订阅 +switch-master）。写死 IP 的客户端会在切换后全量报错。
  7. Sentinel 不保证零丢失。选新主优先看 offset，但仍可能丢掉旧主未同步的最后一段写入。
  8. Sentinel 不能替代监控。它只保证「能切」，不告诉你「为什么挂」；进程、内存、慢查询要另配监控。

版本差异（8.x 标注）

主线仍按 7.4 讲述 Sentinel。8.x 中 Sentinel 的协议与参数语义未变；官方同时提供 Redis Enterprise/Stack 的更高可用方案，但开源版 Sentinel 仍是独立进程模式。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/

八、课后小结

  • Sentinel 是独立进程组成的分布式监控集群，不代理、不分片、不保证零丢失；
  • 四阶段：sdown（单点判断）→ odown（quorum 达成）→ 选领导者（多数票）→ 选新主并广播；
  • quorum 只决定「能否判客观下线」，执行切换需要「过半多数」；
  • 选新主顺序：replica-priority → offset → runid；
  • 配置文件会被自动重写，运行中手改无效；
  • 3 个起、奇数部署是底线。

九、思考题

  1. 5 个 Sentinel、quorum 2。判 odown 需要几票？执行切换需要几票？为什么两者不同？
  2. 为什么 2 个 Sentinel 反而比 1 个更危险？请描述一次网络分区下的脑裂过程。
  3. parallel-syncs 10 在「1 主 10 从」的集群里切换，会发生什么？如何取舍？
  4. Sentinel 为什么不保证数据零丢失？它挑新主时已经尽量选 offset 最新的了，为什么还会丢？
  5. 客户端如果只支持「连接一个固定 IP」，能不能用 Sentinel？该怎么改造？
