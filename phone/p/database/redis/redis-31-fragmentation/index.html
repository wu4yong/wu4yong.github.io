内存碎片与 jemalloc

used_memory 与 rss 的口径差、jemalloc 分配粒度与 activedefrag 关键参数｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 分清 used_memory、used_memory_rss、mem_fragmentation_ratio 三个口径，不再把「rss 大」当成泄漏；
  2. 说清碎片产生的四个来源（size class、空洞、混布、惰性释放）；
  3. 判断什么时候开 activedefrag、什么时候该重启，以及 ratio 小于 1 为什么更危险。

二、前置知识

RD26（SDS 的预分配与惰性释放）、RD12（过期与淘汰）、RD14（fork 与 CoW）。碎片是这些机制叠加出来的结果。

三、理论讲解（官方定义）

官方对碎片率的说明（原文）：

mem_fragmentation_ratio … used_memory_rss / used_memory … A ratio slightly greater than one is normal … a ratio greater than 1.5 means the fragmentation is high.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/

以及主动性整理（原文要点）：

Active defragmentation … is able to defragment the memory while Redis is running, by moving allocations.

—— 同上

两条定性：

  • ratio 略大于 1 是正常的，不要一看到 1.2 就重启；
  • ratio 小于 1 说明发生了 swap，这是比碎片更严重的问题（内存已经不够用了）。

四、原理拆解

1. 三个口径的差别

指标
谁在统计
含义
used_memory
Redis 自己
逻辑上「我申请了多少」
used_memory_rss
操作系统
物理上「进程占了多少页」
mem_fragmentation_ratio
计算值
rss / used，大于 1 是碎片，小于 1 是 swap

还有两个容易一起看的：used_memory_peak（历史峰值，评估容量要按它算）与 used_memory_lua（Lua 引擎占用）。

2. 碎片的四个来源

① jemalloc 的 size class。jemalloc 不按字节分配，而是按 size class（8、16、32、48、64、80、96、112、128 …）分配。申请 100 字节可能拿到 112 字节的块，内部浪费 ~10%。

② 空洞散落。反复增删后，空闲块散落在不同 page 里，无法合并成连续大块还给操作系统。

③ 大小混布。同一进程里既有几百字节的小对象，又有几 MB 的大 value，page 被切得很碎。

④ 惰性释放与 CoW。SDS 缩短不立即释放（RD26）；BGSAVE 期间写时复制会产生额外页（RD14），这些页在 fork 结束后不一定归还。

3. activedefrag 的参数

activedefrag yes
active-defrag-ignore-bytes 100mb        # 碎片量小于此不整理
active-defrag-threshold-lower 10        # 碎片率低于 10% 不动
active-defrag-threshold-upper 100       # 碎片率高于 100% 全力整理
active-defrag-cycle-min 25              # 最少占 25% CPU
active-defrag-cycle-max 100             # 最多占 100% CPU
active-defrag-max-scan-fields 1000      # 单个大对象最多扫描多少字段

四组参数各管一件事：要不要做（ignore-bytes + threshold-lower）、做多狠（threshold-upper + cycle-max）、至少做多少（cycle-min）、单个大对象的扫描上限（max-scan-fields）。

默认是 activedefrag no——官方不默认开启，因为它要花 CPU，且会与 fork、AOF 重写抢资源。

4. 什么时候该重启而不是整理

activedefrag 只能搬动「小块」。以下情况它救不回来：

  • 碎片来自单个超大对象（一个 2 GB 的 Hash），搬不动；
  • 碎片率长期 > 2 且 activedefrag 开了也没降；
  • 内存已经贴近 maxmemory，整理期间的额外开销可能触发淘汰。

这些情况的标准处置是主从切换到新实例（RD19/RD21 的机制），而不是硬重启。

五、场景说明

  1. 长跑实例（几个月不重启）：碎片率缓慢爬升，适合开 activedefrag；
  2. 大量短生命周期 key（验证码、会话）：增删频繁，碎片最明显；
  3. 大 value 混布：activedefrag-max-scan-fields 会成为瓶颈，整理效果有限；
  4. 容器内存受限：rss 才是 cgroup 计费的口径，ratio 高会直接导致 OOM Kill。

六、示例代码/实操步骤

# 1. 读三个口径
127.0.0.1:6379> INFO memory
# used_memory:13421772800
# used_memory_human:12.50G
# used_memory_rss:18874368000
# used_memory_rss_human:17.58G
# used_memory_peak_human:15.20G
# mem_fragmentation_ratio:1.41
# mem_allocator:jemalloc-5.3.0

# 2. 算出「有多少是碎片」
# rss - used = 17.58G - 12.50G ≈ 5.08G 的碎片/开销
127.0.0.1:6379> MEMORY DOCTOR
# Hi Sam, this instance is empty or is using very little memory...

# 3. 开启主动整理
127.0.0.1:6379> CONFIG SET activedefrag yes
OK
127.0.0.1:6379> CONFIG SET active-defrag-ignore-bytes 100mb
OK
127.0.0.1:6379> CONFIG SET active-defrag-threshold-lower 10
OK
127.0.0.1:6379> CONFIG GET active-defrag-*
# 逐项确认已生效

# 4. 观察整理效果（持续采样 ratio）
127.0.0.1:6379> INFO memory | grep -E "used_memory:|mem_fragmentation_ratio"
# 整理是渐进的，ratio 会缓慢下降，不会一步到位

# 5. 判断是否有 swap（ratio < 1）
# used_memory_rss 小于 used_memory 时，说明部分内存被换出
$ free -m
# Swap:  2048   1024   1024       ← 有使用就危险

# 6. 看单个 key 的真实占用（评估大对象）
127.0.0.1:6379> MEMORY USAGE big:hash
(integer) 2147483648            # 2GB 的单个对象，activedefrag 搬不动

# 7. 关掉整理（如果 CPU 紧张）
127.0.0.1:6379> CONFIG SET activedefrag no
OK

Java 侧怎么落地：碎片是客户端写出来的

碎片几乎都来自「value 反复变大变小、大小混布」，所以 Java 侧最有效的动作是让 value 尺寸稳定，而不是等运维去整理。

  1. pom 只引 starter，关键在序列化器与 value 尺寸治理。

  2. 同一类 key 的 value 长度尽量固定。用 Jackson 全量序列化对象时，字段增删会让 value 忽大忽小，反复 realloc 直接制造空洞；对高频写的 key，宁可拆成几个定长字段存 Hash。

// 反例：整个对象一把梭，字段增删就让 value 从 80B 跳到 300B
// 正例：拆成小字段，单个 value 长度稳定
stringRedisTemplate.opsForHash().putAll("cfg:app", Map.of("v", "3", "ttl", "3600"));

  1. 避免「先写大再改小」：SDS 缩短不释放（RD26），大 value 缩水后内存仍占着。要么重建 key，要么一开始就别写大。

  2. 批量导入按批提交（见 RD27），避免一次性申请大量不同尺寸的块，让 jemalloc 的 size class 分布更整齐。

  3. 把内存指标接进监控：Spring Boot Actuator + Micrometer 定时抓 INFO memory，把 mem_fragmentation_ratio 打成指标，超过 1.5 告警——比事后 MEMORY DOCTOR 猜要早得多。

String info = stringRedisTemplate.execute((RedisCallback<String>) c -> new String(c.info("memory")));
// 解析 mem_fragmentation_ratio / used_memory_rss / used_memory_peak 上报
  1. 容器部署必须留余量：maxmemory 不要等于容器 limit（见本文常见坑第 5 条），Java 侧改不了这一点，但要在交付清单里写死。

七、常见坑（官方明确说明的限制）

  1. ratio 1.4 就重启。官方口径是「略大于 1 正常」，1.4 属于可接受，先看趋势与峰值。
  2. 把 rss 当泄漏。rss 包含碎片、分配器元数据、CoW 页；判断泄漏要看 used_memory 的长期趋势，而不是 rss。
  3. ratio < 1 却只关注碎片。这是 swap 信号，性能会断崖下跌，必须优先解决内存不足。
  4. activedefrag 默认开。它默认关闭，贸然开启会在高负载时抢 CPU，且与 fork 叠加会放大延迟。
  5. 指望整理搞定大对象碎片。active-defrag-max-scan-fields 限制了单对象扫描，超大 Hash/List 基本整理不动。
  6. 忽略 used_memory_peak。容量规划要按峰值（含 fork 时的 CoW）算，按当前值算必然 OOM。
  7. 容器里只看 INFO memory。cgroup 的 limit 按 rss 计费，maxmemory 只约束 used_memory，两者口径不同。
  8. MEMORY DOCTOR 当诊断结论。它给的是提示性建议，不是精确诊断，还要结合 INFO memory 与业务形态判断。

版本差异（8.x 标注）

碎片指标、activedefrag 参数在 7.x 与 8.x 一致；8.x 未改变 jemalloc 的默认分配器角色。差异主要在内存相关命令的扩展与许可条款。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/

八、课后小结

  • 三口径：used_memory（逻辑申请）、used_memory_rss（物理占用）、ratio（两者之比）；
  • ratio 略大于 1 正常；> 1.5 关注；< 1 意味着 swap，更紧急；
  • 碎片四来源：size class 浪费、空洞散落、大小混布、惰性释放与 CoW；
  • activedefrag 默认关闭，四组参数分别控制「要不要做、做多狠、至少做多少、单对象扫描上限」；
  • 大对象碎片整理不动，标准解法是主从切到新实例；
  • 容量规划按 used_memory_peak，容器按 rss 计费。

九、思考题

  1. used_memory 12.5G、rss 17.6G，这 5G 差额由哪几部分组成？

    参考回答：jemalloc 按 size class 分配的块内浪费、散落在各 page 的空洞（拼不回连续大块还给 OS）、大小对象混布造成的 page 切碎、SDS 惰性释放未归还的空间，以及 fork/CoW 遗留下来的页与分配器元数据。

  2. 为什么 ratio 小于 1 比大于 1.5 更危险？怎么确认是否发生了 swap？

    参考回答：ratio < 1 说明 used_memory 已大于 rss，即部分内存被换到磁盘：访问会触发缺页，延迟从微秒级跳到毫秒级，且会连锁放大。确认方式：/proc/<pid>/smaps 里看 Swap 字段、vmstat 的 si/so、MEMORY DOCTOR 的提示。

  3. activedefrag 开着，但 ratio 一直不降，可能是哪三种原因？

    参考回答：①碎片主要来自单个超大对象（如 2GB Hash），整理搬不动；②整理门槛没达到——碎片量不足 active-defrag-ignore-bytes 或碎片率低于 threshold-lower；③CPU 被业务吃满，cycle-max 给不出整理时间，或已贴近 maxmemory、整理腾挪又触发淘汰。

  4. 为什么「大 Hash 的碎片整理不动」？active-defrag-max-scan-fields 起了什么作用？

    参考回答：大 Hash 是 hashtable + 千万个 SDS，整理要逐字段搬迁，且受 active-defrag-max-scan-fields（默认 1000）限制——单轮只扫有限字段，几千万字段的 Hash 需要极多轮才能搬完，实际等同搬不动。

  5. 容器环境里 maxmemory 8gb、容器 limit 8GiB，会发生什么？该怎么配？

    参考回答：8gb 是十进制 8×10⁹≈7.45GiB，看起来留了余量；但 rss 通常大于 used（碎片）、fork 期间 CoW 翻倍、客户端输出缓冲也算进程内存，很容易触顶被 OOM killer 杀掉。配法：maxmemory 取 limit 的 60%～70%（如 5～6gb），设好淘汰策略，并留出 fork 与复制缓冲的空间。
