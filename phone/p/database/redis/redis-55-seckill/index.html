秒杀：原子扣减与异步下单

Redis 做漏斗、队列做缓冲、库做出库的四步链路｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你能做到：

  1. 用一段 Lua 脚本完成「查库存 → 判断 → 扣减 → 记录用户」一条原子操作；
  2. 说清为什么 Redis 只做漏斗、订单必须异步落库；
  3. 找出秒杀链路里必须存在的三道防线（限流、幂等、对账）。

二、前置知识

RD05（DECRBY）、RD34（Lua 原子性）、RD46（限流）、RD22/RD24（集群 hash tag）。秒杀是「原子性 + 分布式 + 高并发」三件事交叠的典型场景。

三、理论讲解（官方定义）

两条用得上的官方定义。

脚本原子性（原文要点）：

Scripts are executed atomically … no other script or command will run while a script is running.

—— https://redis.io/docs/latest/develop/interact/programmability/eval-intro/

这意味着「读库存 → 判断 → 扣减」可以在一段脚本里完成，中间不会有别的命令插入——这是不超卖的技术前提。

集群的多 key 限制（原文要点）：

Multi-key commands and scripts must operate on keys in the same hash slot … keys are mapped to slots via CRC16(key) mod 16384.

—— https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/

所以在集群里，脚本涉及的所有 key（库存 + 用户标记）必须落在同一个槽，否则报 CROSSSLOT。解法是用 hash tag：stock:{act1} 与 order:{act1} 都会带 {act1} 落到同一个槽。

四、原理拆解

1. 四步链路

① 预热：把活动库存写入 Redis（stock:act1 = 100）
② 扣减：Lua 脚本原子地「判断 + 扣减 + 记录用户」
③ 入队：扣减成功的请求写入队列（LIST / Stream）
④ 落库：worker 消费队列、创建订单、扣减数据库库存（幂等）

Redis 只承担「谁有资格下单」，订单的真实性由数据库与对账保证。把 Redis 当成「账簿」是秒杀最常见的设计错误。

2. 为什么必须用 Lua

错误写法：
  GET stock        → 100
  （1000 个请求都读到 100）
  DECRBY stock 1   → 变成负数，超卖

正确写法：
  local s = tonumber(redis.call('get', KEYS[1]))
  if s <= 0 then return 0 end
  if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then return 2 end
  redis.call('decrby', KEYS[1], 1)
  redis.call('sadd', KEYS[2], ARGV[1])
  return 1

脚本里的三步在一次执行内完成，返回值区分三种结果：1 成功、0 售罄、2 重复请求。

3. 三道防线

防线
作用
不做会怎样
入口限流
把 99% 请求拒在 Redis 之外
Redis 被打满，正常用户也抢不到
幂等
同一用户只成功一次
一个人抢到多件，或重复下单
对账
比对「Redis 卖出数」与「库中订单数」
故障时差额无人发现

对账是最容易被省掉的一环，但它恰恰是「Redis 不可靠」这一事实的兜底。

4. 失败要能「还库存」

扣减成功后如果异步落库失败（队列消费异常），库存必须能退回：

① worker 消费失败 → 记录失败订单
② 定时任务扫描失败单 → INCRBY 归还库存 + 清理用户标记
③ 或由 TTL 兜底：活动结束后统一校对

没有归还机制，一次消费失败就会永久吃掉一件库存。

预热→Lua 原子扣减→入队→异步落库的四步、脚本的 1/0/2 三个返回码、限流幂等对账三道防线，以及补偿还库存与 hash tag 同槽｜依据 EVAL 原子性与 Cluster spec 自绘

五、场景说明

  1. 限量抢购：库存有限、并发极高，典型秒杀；
  2. 优惠券发放：与秒杀同构，券码数量就是库存；
  3. 预约名额：量小但要求严格不超发；
  4. 不适合：普通下单（不需要抢）——直接走数据库事务即可，别引入复杂度。

六、示例代码/实操步骤

# 1. 预热库存（活动开始前）
127.0.0.1:6379> SET stock:act1 100
OK
127.0.0.1:6379> DEL order:act1
(integer) 0

# 2. 扣减脚本（库存 + 用户标记同槽，集群下用 hash tag）
127.0.0.1:6379> EVAL "local s=tonumber(redis.call('get',KEYS[1])) if s==nil or s<=0 then return 0 end if redis.call('sismember',KEYS[2],ARGV[1])==1 then return 2 end redis.call('decrby',KEYS[1],1) redis.call('sadd',KEYS[2],ARGV[1]) return 1" 2 stock:{act1} order:{act1} u1001
(integer) 1                     # 1=成功，0=售罄，2=重复

# 3. 同一个用户再抢（应返回 2）
127.0.0.1:6379> EVAL "..." 2 stock:{act1} order:{act1} u1001
(integer) 2

# 4. 扣减成功后入队（Stream 可回溯，比 LIST 更稳）
127.0.0.1:6379> XADD queue:act1 * uid u1001 act act1
"1700000000000-0"

# 5. worker 消费（示例：读一条并确认）
127.0.0.1:6379> XREADGROUP GROUP g1 worker1 COUNT 1 STREAMS queue:act1 >
127.0.0.1:6379> XACK queue:act1 g1 1700000000000-0

# 6. 查看剩余库存与已抢人数
127.0.0.1:6379> GET stock:{act1}
"98"
127.0.0.1:6379> SCARD order:{act1}
(integer) 2

# 7. 失败归还库存（补偿脚本）
127.0.0.1:6379> INCRBY stock:{act1} 1
(integer) 99
127.0.0.1:6379> SREM order:{act1} u1001
(integer) 1

Java 侧怎么落地：一段脚本 + 一个 Stream 消费组

  1. pom：Redis 客户端 + Stream 监听容器（Spring Data Redis 已内置容器，不需要额外依赖）。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
  1. application.yml：连接池要够、超时要短，秒杀期间最怕「拿不到连接还在排队」：
spring:
  data:
    redis:
      timeout: 100ms
      lettuce:
        pool: { max-active: 128, max-wait: 50ms }
seckill:
  stock-key: stock:{act1}      # 带 hash tag，集群下同槽
  users-key: order:{act1}
  queue-key: queue:{act1}
  1. 脚本放 resources 下，用 DefaultRedisScript 加载，不要每次请求拼字符串（KEYS 声明为 2 个，Spring 才知道去哪找槽）：
DefaultRedisScript<Long> script = new DefaultRedisScript<>();
script.setLocation(new ClassPathResource("lua/seckill.lua"));
script.setResultType(Long.class);
Long r = redis.execute(script, List.of(stockKey, usersKey), uid);

  1. 三个返回码的语义要落到业务分支：1 入队并返回「排队中」，0 直接提示售罄（不要打到库），2 幂等命中，返回上次结果而不是再建单。

  2. 入队用 Stream（可回溯）而不是 LIST：生产端 XADD，消费端用 StreamMessageListenerContainer + 消费组，消费成功后 XACK，失败留在 PEL 里由补偿任务重试。

container.receive(Consumer.from("g1", "worker1"),
    StreamOffset.create(queueKey, ReadOffset.lastConsumed()), listener);

  1. 落库幂等靠数据库唯一索引（act_id + uid），不只靠 Redis 的 SADD 标记——补偿重试时 Redis 标记可能已被清理。

  2. 补偿任务写死动作：扫失败单 → INCRBY 还库存 + SREM 清用户标记 → 落一条审计记录，避免「一件库存永久丢失」。

  3. 入口限流必须在网关/应用层（RD46），别让所有请求都到 Redis 再被拒：Redis 只该看到「有机会成功」的那部分流量。

七、常见坑（官方明确说明的限制）

  1. GET 再 DECR 两步扣减。并发下必然超卖，必须走 Lua。
  2. 把 Redis 当唯一账簿。实例故障、主从切换丢写都会让「卖出数」失真，必须有对账。
  3. 集群里 key 不带 hash tag。脚本涉及多 key 时报 CROSSSLOT，秒杀直接不可用。
  4. 没有幂等标记。同一用户重试或连点会成功多次。
  5. 不做入口限流。Redis 被无效请求打满，正常用户也抢不到，反而放大故障面。
  6. 扣减成功但入队失败。库存已减、订单没生成，且没有补偿路径。
  7. 活动结束不清理 key。stock:* 与 order:* 会长期占内存，靠 TTL 或定时任务清理。
  8. 用 KEYS 扫活动 key。O(N) 阻塞主线程（官方明确生产禁用），活动期间等于自杀。

版本差异（8.x 标注）

EVAL、DECRBY、XADD、SISMEMBER 语义在 7.4 与 8.x 一致；集群 hash tag 规则不变（CRC16(key) mod 16384，{...} 参与计算）。8.x 的差异在运维工具与许可，不影响链路设计。

依据：https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/

八、课后小结

  • Redis 只做漏斗：原子扣减 + 记录用户，出库交给队列与数据库；
  • 扣减必须 Lua：判断、扣减、标记一次完成；
  • 三道防线：限流、幂等、对账，缺一不可；
  • 集群多 key 必须同槽（hash tag）；
  • 失败要能归还库存，否则一件库存永久丢失。

九、思考题

  1. 为什么 GET + DECR 会超卖？画出并发交错的时间线。

    参考回答：两条命令之间可插入别的客户端的命令。时间线：A GET 得 100 → B GET 也得 100 → A DECR 得 99 → B DECR 得 99。两个请求都认为自己抢到了同一件库存，实际卖了两件，最终 stock 只减了 1。

  2. 脚本返回 2 表示什么？客户端应该怎么处理？

    参考回答：表示该用户已在 order:{act1} 里，是重复请求（连点或重试）。客户端应把它当成功处理并返回「已抢到，请勿重复提交」，不要再入队、也不要再建单，避免一人多单。

  3. 库存 100、入口 QPS 10 万，Redis 需要承担多少扣减操作？怎么算？

    参考回答：若只在入口限流后放 100～200 个请求进来，Redis 的脚本执行是 100 次量级；若完全不限流，就是 10 万次脚本调用（每次 O(1) 但占连接与 CPU），其中只有 100 次返回 1。瓶颈不在脚本复杂度，而在「无效请求占满连接池」，所以限流是第一道防线。

  4. 扣减成功、落库失败，你的补偿路径是什么？

    参考回答：三步：① 消费失败写失败单（含 actId、uid、时间）；② 定时任务重试建单，超过次数则 INCRBY stock:{act1} 1 并 SREM order:{act1} uid 归还资格；③ 活动结束后做对账（SCARD order:{act1} vs 库中订单数），差额人工核对。没有第②步就会永久少卖。

  5. 集群里库存与用户标记不在同一槽，会报什么错误？怎么改 key 命名？

    参考回答：报 CROSSSLOT Keys in request don't hash to the same slot，脚本直接执行失败，秒杀不可用。改法是用 hash tag 让两个 key 落到同一槽：stock:{act1} 与 order:{act1}，{...} 里的内容参与 CRC16 计算，槽号相同。
