MULTI/EXEC/WATCH：事务能给什么保证

MULTI→入队→EXEC 的四阶段、WATCH 的乐观锁流程与事务的三条硬边界｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 准确说出 Redis 事务保证的是「不被插入」，不是「全做或全不做」；
  2. 分清入队错误与运行时错误两种失败，知道各自的后果；
  3. 用 WATCH + 重试实现乐观锁，并知道它在什么场景下不适用。

二、前置知识

RD30（单线程事件循环）。事务的「原子性」直接来自单线程执行——理解这一点，后面所有边界都能自己推出来。

三、理论讲解（官方定义）

官方对事务原子性的定义（原文）：

All the commands in a transaction are serialized and executed sequentially. A request sent by another client will never be served in the middle of the execution of a Redis Transaction.

—— https://redis.io/docs/latest/develop/using-commands/transactions/

以及关于错误的处理（原文要点）：

Errors happening … before the command is queued … cause the transaction to be discarded … Errors happening after EXEC … do not stop the other commands from being executed … Redis does not support rollbacks.

—— 同上

两条定性：

  • 事务 = 一串命令连续执行、中间不被插入，仅此而已；
  • Redis 明确不支持回滚，这是设计选择，不是缺陷。

四、原理拆解

1. 四个阶段

MULTI          → 客户端进入事务状态，返回 OK
命令 1..N      → 每条都返回 QUEUED（只是排队，没有执行）
EXEC           → 一次性按顺序执行全部，返回结果数组
DISCARD        → 放弃事务，清空队列

关键在第二阶段：命令只是入队，此时还没有任何数据被修改。所以「入队阶段语法错误」能让整批作废，代价很小。

2. 两种失败的后果完全不同

失败类型
发生时机
后果
入队错误
命令语法错误、命令不存在
服务端标记事务为「脏」，EXEC 直接返回 EXECABORT，整批不执行
运行时错误
命令语义错误（对 String 做 LPUSH、INCR 非数字）
该条报错，其余命令照常执行，且不撤销已执行的部分

第二条是工程上最容易踩的：日志里只有一条 WRONGTYPE 错误，但事务里在它之前、之后的写操作都已经生效。Redis 不会帮你回滚。

3. WATCH 的乐观锁

WATCH key 记录 key 的「版本」，不阻塞、不加锁。EXEC 时如果发现被监视的 key 被其他客户端改过，就返回 nil（空回复），整批不执行。

WATCH balance
GET balance               → 100
（客户端计算 100 + 10）
MULTI
SET balance 110
EXEC                      → 若期间有人改过 balance，返回 nil，需重试

三个细节：

  • WATCH 可多次调用，监视多个 key；
  • EXEC / DISCARD 后监视自动清除；想提前取消用 UNWATCH；
  • WATCH 的失效是「key 被写过」，即使写成了同样的值也算（保护的是「没被人动过」）。

4. 为什么事务不保证隔离级别

Redis 单线程执行，事务执行期间不会有其他命令插入——这已经提供了「串行化」的执行效果。但它不是数据库意义上的隔离级别：

  • 没有「读已提交/可重复读」的概念，MULTI 里读到的就是当时的真实值；
  • 事务内读到的值不受保护，别的客户端随时可能在你 EXEC 之前改掉；
  • 要防止「读后写被覆盖」，只能靠 WATCH 或 Lua。

五、场景说明

  1. 批量写无依赖：一次写 10 个不相关的 key，事务能避免被别的命令插进来；
  2. 计数器批量更新：INCR a、INCR b 互不影响，适合事务；
  3. 有依赖的读改写：库存扣减、余额转账，用 WATCH + 重试，或直接用 Lua；
  4. Cluster 环境：事务中的所有 key 必须同槽，否则 EXEC 直接报 CROSSSLOT（RD24）。

六、示例代码/实操步骤

# 1. 正常事务
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> SET t1 a
QUEUED
127.0.0.1:6379> INCR t2
QUEUED
127.0.0.1:6379> EXEC
1) OK
2) (integer) 1

# 2. 入队错误：整批作废
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> SET t3 a
QUEUED
127.0.0.1:6379> NOTACOMMAND
(error) ERR unknown command 'NOTACOMMAND'
127.0.0.1:6379> EXEC
(error) EXECABORT Transaction discarded because of previous errors.
127.0.0.1:6379> GET t3
(nil)                       # 确认没有被写入

# 3. 运行时错误：其余命令照样生效
127.0.0.1:6379> SET str hello
OK
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> INCR counter
QUEUED
127.0.0.1:6379> LPUSH str x
QUEUED
127.0.0.1:6379> INCR counter
QUEUED
127.0.0.1:6379> EXEC
1) (integer) 1
2) (error) WRONGTYPE Operation against a key holding the wrong kind of value
3) (integer) 2              # 前后两条都生效了，中间那条报错
127.0.0.1:6379> GET counter
"2"                         # INCR 生效了两次，没有回滚

# 4. WATCH 乐观锁：两步终端演示
# 终端 A
127.0.0.1:6379> SET balance 100
OK
127.0.0.1:6379> WATCH balance
OK
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> SET balance 110
QUEUED
# 终端 B（在 A 执行 EXEC 之前）
127.0.0.1:6379> SET balance 200
OK
# 回到终端 A
127.0.0.1:6379> EXEC
(nil)                       # 被改过 → 整批不执行，客户端应重试

# 5. 放弃事务
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> SET t4 a
QUEUED
127.0.0.1:6379> DISCARD
OK
127.0.0.1:6379> GET t4
(nil)

七、常见坑（官方明确说明的限制）

  1. 以为事务能回滚。官方明确不支持回滚：运行时错误之后，前面的写照样生效。
  2. 把入队错误当运行时错误。语法错误的后果更严重——EXEC 返回 EXECABORT，整批不执行，但客户端如果不看返回值，会以为写成功了。
  3. WATCH 之后忘记重试。EXEC 返回 nil 就是「事务失败」，业务必须重新读、重新算、重新提交。
  4. 在事务里做大量读。MULTI 里的读命令结果要到 EXEC 才返回，中间无法基于结果做分支——需要条件判断的场景应改用 Lua。
  5. WATCH 的 key 被自己改。自己在 WATCH 之后 MULTI 之前写同一个 key，也会让 EXEC 返回 nil。
  6. 事务跨槽。Cluster 下 EXEC 会因 CROSSSLOT 失败，必须用 hash tag 收敛（RD22/RD24）。
  7. 事务里放慢命令。整个事务连续执行，中间不插入任何命令，一条 KEYS * 会让所有客户端等到它结束。
  8. 用事务做「分布式锁」。事务不阻塞、不排队，两个客户端都能通过 WATCH 检查，只是其中一个 EXEC 会失败——锁要用 SET NX（RD42）。

版本差异（8.x 标注）

事务语义在 7.x 与 8.x 一致：串行执行、不支持回滚、WATCH 乐观锁。8.x 未引入回滚机制，差异主要在许可与生态。

依据：https://redis.io/docs/latest/develop/using-commands/transactions/

八、课后小结

  • 事务 = 命令连续执行、中间不被插入；MULTI 入队、EXEC 执行、DISCARD 放弃；
  • 入队错误 → EXECABORT，整批不执行；运行时错误 → 该条报错、其余照常生效；
  • 官方明确不支持回滚；
  • WATCH 是乐观锁：不阻塞，EXEC 时发现被改就返回 nil，业务必须重试；
  • 有依赖的读改写用 Lua 更合适（下一讲）；
  • 事务里不要放慢命令，也不要用它做分布式锁。

九、思考题

  1. 事务里第 2 条命令 WRONGTYPE 报错，第 1、3 条会怎样？为什么 Redis 不撤销它们？
  2. 入队错误和运行时错误的区别在哪？客户端该怎么分别处理？
  3. WATCH 为什么不阻塞？它靠什么判断「有没有被改过」？
  4. EXEC 返回 nil 时，业务应该做什么？只重试一次够吗？
  5. 为什么「库存扣减」用事务不可靠，用 Lua 就可靠？两者的差别在哪一点？
