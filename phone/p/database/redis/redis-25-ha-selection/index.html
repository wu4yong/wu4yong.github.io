高可用选型：主从、Sentinel 与 Cluster

单机 / 主从 / Sentinel / Cluster 四种形态的容量、写入、故障与适用场景｜依据 Redis 7.4 官方文档自绘

一、学习目标

学完这一讲，你要能做到三件事：

  1. 用「容量、写入、故障、成本」四个维度把四种形态摆在一起对比，而不是凭印象选；
  2. 按固定的三个问题（装得下吗、写得动吗、能接受人工切换吗）做出可辩护的选型；
  3. 说清每种方案的「隐性成本」，在评审时把这些成本摆到桌面上。

二、前置知识

RD14–RD24 全部。本篇是 M4 的收口：把复制、Sentinel、Cluster 三套机制收敛成决策。

三、理论讲解（官方定义）

官方明确把两种方案分开定位（原文）：

Redis Sentinel provides high availability for Redis when not using Redis Cluster.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/

Redis Cluster … allows you to shard your data automatically across multiple Redis nodes, and to continue operations when a subset of the nodes are experiencing failures.

—— https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/

两句话划清了界线：

  • Sentinel 解决「可用性」，一个主库的数据模型不变；
  • Cluster 解决「容量 + 写入扩展 + 可用性」，但代价是数据模型变成分片。

关键结论：这不是「高级 vs 低级」，而是「要不要分片」。不需要分片的业务上 Cluster，只会白拿一堆限制和运维成本。

这张表的读法：从「单机」到「主从」买的是备份与读扩展，从「主从」到「Sentinel」买的是自动切换，从「Sentinel」到「Cluster」买的是写入与容量水平扩展。每一步都是「花钱买能力」，不是「升级」。

2. 决策顺序（按优先级问三个问题）

问题一：数据量能不能装进一台机器？

  • 能 → 不进 Cluster 的讨论范围；
  • 不能，或未来 12 个月会超 → 继续问第二、第三题，指向 Cluster。

注意「装得下」要按实际内存 + 副本 + 碎片 + fork 峰值算，不是「理论内存」。RD28 会讲碎片率，RD14 讲了 CoW，这两项都要留余量。

问题二：写入是否超过单节点能力？

  • 没有 → Sentinel 足够（读靠加从库，写靠单主）；
  • 超过（QPS 或带宽打满单主）→ Cluster 的唯一理由就是这个。

很多团队误以为「数据大就必须 Cluster」，其实只有写入才是 Cluster 的硬需求；纯读多、数据大的场景，Sentinel + 多从库往往更省事。

问题三：能不能接受分钟级人工切换？

  • 能接受（如内部工具、可停机窗口）→ 主从就够；
  • 不能 → 至少要 Sentinel；
  • 连「节点故障导致部分槽不可用」都不能接受 → Cluster 的多数票机制本身就是你要的。

3. 每种方案的隐性成本

  • Sentinel：多一套进程与配置要维护；客户端必须支持 Sentinel 协议；切换窗口仍有写失败；
  • Cluster：跨槽限制要改代码；迁移与扩容是人工活；客户端要处理 MOVED/ASK；监控要按节点聚合；
  • 任何异步复制方案：切换都可能丢最后一段写入，关键数据要靠业务补偿；
  • 单机：没有隐性成本，但也没有任何容错。

把这些成本写进技术方案，比「我们上了 Cluster 所以高可用」更可信。

四种形态在容量、写入、故障、成本四维上的对比，以及按优先级问的三问与隐性成本｜依据 Redis 7.4 Scaling / Sentinel 文档自绘

五、场景说明

  1. 缓存 + 中小数据量 + 读多写少：主从或 Sentinel，简单可靠；
  2. 单主写入顶到瓶颈（QPS 高、带宽满）：Cluster，且必须接受跨槽限制；
  3. 数据量 200 GB、写入不高：优先 Sentinel + 多从库（读扩展），再评估是否真要 Cluster；
  4. 强事务/多 key 原子操作密集：留在 Sentinel 形态，或把相关 key 用 hash tag 收敛后再上 Cluster；
  5. 灾备：无论哪种形态，异地备份文件都是最后一道防线（RD17）。

六、示例代码/实操步骤

# 判断「装不装得下」——看真实内存与碎片
127.0.0.1:6379> INFO memory
# used_memory_human:12.50G
# used_memory_peak_human:15.20G          ← 峰值才是参考
# mem_fragmentation_ratio:1.35           ← 碎片率偏高

# 判断「写得动吗」——看单主写入压力
127.0.0.1:6379> INFO stats
# instantaneous_ops_per_sec:45000        ← 单主当前 QPS
# total_net_input_bytes:...

# 判断「网络是否打满」——看复制流量
127.0.0.1:6379> INFO replication
# master_repl_offset:987654321
# slave0:...,lag=0

# 判断「切换要不要人」——看是否已有 Sentinel
127.0.0.1:26379> SENTINEL masters
# 有输出 → 已具备自动切换能力

# 判断「是否已在 Cluster」
127.0.0.1:6379> INFO cluster
# cluster_enabled:0                      ← 0 表示单机/主从/Sentinel 形态

# 典型结论写法（技术方案里的三句话）
# 1) 数据 12.5G，峰值 15.2G，单机 32G 可容纳 → 不需要分片
# 2) 单主 QPS 4.5 万，未打满 → 写入不需要水平扩展
# 3) 允许 30 秒内切换完成 → Sentinel 3 节点足够

Java 侧怎么落地：一套代码切三种形态

选型结论不该落成一堆 if 分支，而是落成「连接工厂 + 配置档」两件事。

  1. pom 只引一个 starter。Spring Data Redis 自带 Lettuce，Sentinel 与 Cluster 都由它驱动，不要再额外挂 Jedis 的 Cluster 客户端。
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
<dependency>
  <groupId>org.apache.commons</groupId>
  <artifactId>commons-pool2</artifactId>
</dependency>
  1. 形态相关的连接参数拆到 profile。公共项留在 application.yml，形态项各写一份：
# application-sentinel.yml
spring:
  data:
    redis:
      sentinel:
        master: mymaster        # 必须与 sentinel.conf 中监控的名字一致
        nodes: 10.0.0.11:26379,10.0.0.12:26379,10.0.0.13:26379
      lettuce:
        pool:
          max-active: 32
# application-cluster.yml
spring:
  data:
    redis:
      cluster:
        nodes: 10.0.0.21:6379,10.0.0.22:6379,10.0.0.23:6379
        max-redirects: 3        # 跟随 MOVED/ASK 的上限
  1. 切换形态只改启动参数：--spring.profiles.active=sentinel 或 cluster。业务代码只注入 StringRedisTemplate，不在代码里判断形态。
@Service
public class CacheService {
    private final StringRedisTemplate redis;   // 形态变了，这里一个字都不改
    public CacheService(StringRedisTemplate redis) { this.redis = redis; }
}

  1. 微服务里别各写一份。连接参数放配置中心/Nacos 统一下发，各服务只保留 profile 名，避免十个服务十份 Sentinel 地址，切一次主库要改十处。

  2. 把「形态自检」写成启动断言，防止灰度时还连着旧形态：

@Test
void shapeShouldMatchProfile() {
    String info = redis.execute((org.springframework.data.redis.core.RedisCallback<String>) c -> new String(c.info()));
    assertTrue(info.contains("cluster_enabled:1"));   // Sentinel/主从应为 0
}
  1. 验证：Sentinel 形态看 SENTINEL masters 的 flags；Cluster 形态看客户端日志是否出现 MOVED 重定向——出现即说明在正确跟随，出现重定向风暴则说明槽表缓存没刷新。

七、常见坑（官方明确说明的限制）

  1. 「数据大就上 Cluster」。容量不是 Cluster 的唯一理由，写入才是；数据大而写不多时，Sentinel + 多从库更省心。
  2. 「上了 Cluster 就高可用」。Cluster 只解决节点级可用性，业务层的多 key、事务、客户端改造都要自己做。
  3. Sentinel 与 Cluster 混用。Cluster 自带故障转移，不需要外面再套 Sentinel；两套机制一起上只会打架。
  4. 忽略「写单点」。Sentinel 形态下写始终是单点，主库打满时加从库没有帮助。
  5. 不评估客户端改造成本。Cluster 要求客户端支持重定向，这个改造成本常被漏算。
  6. 不给切换做演练。无论哪种形态，没演练过的切换等于不存在；用 SENTINEL FAILOVER 或手工 kill 主节点做真实演练。
  7. 忘记「数据可能丢」。三种形态都是异步复制，切换都可能丢最后一段写入；关键数据必须能补偿。
  8. 忽略监控聚合。Cluster 下要看「每个节点 + 每段槽」，只看一个节点的 INFO 会漏问题。

版本差异（8.x 标注）

选型逻辑不随版本变化；8.x 的差异在于许可（AGPLv3/SSPL，商业使用需合规评估）与部分集群运维改进。7.4 是可作为「长期稳定主线」的版本，8.x 的新特性按需引入。

依据：https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/、https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/

八、课后小结

  • Sentinel 解决可用性，Cluster 解决容量与写入水平扩展，两者不是升级关系；
  • 决策三问：装得下吗 → 写得动吗 → 能接受人工切换吗；
  • 只有「写入超过单节点」才是 Cluster 的硬需求；
  • 每种方案都有隐性成本，写进方案才可信；
  • Cluster 与 Sentinel 不要混用；
  • 切换必须演练，异步复制的丢数据窗口必须业务侧兜。

九、思考题

  1. 数据 300 GB、写入只有 8000 QPS，你会选 Sentinel 还是 Cluster？给出三条理由。

    参考回答：选 Sentinel（配大内存机 + 多从库）。三条理由：①装得下——300 GB 用 512 GB 机型加副本仍有余量；②写得动——8000 QPS 远低于单主能力，没有水平扩展的必要；③运维成本——Cluster 的跨槽改造、迁槽、客户端重定向全省掉了。

  2. 「数据大就必须 Cluster」错在哪？什么指标才是 Cluster 的判据？

    参考回答：错在把「容量」当成 Cluster 的唯一理由，容量可以靠更大机型、按业务拆实例解决。Cluster 的硬判据是单主写入顶不住：写入 QPS 打满、复制带宽打满，或单机内存已无法再扩。

  3. Sentinel 形态下主库 QPS 打满，加三个从库有用吗？为什么？

    参考回答：没用。从库只分担读，写仍然落在唯一主库；主库写打满要从写入侧解决——拆业务、异步化、批量合并，最终才是 Cluster 分片。

  4. 为什么 Cluster 里不需要再部署 Sentinel？如果强行一起上会发生什么？

    参考回答：Cluster 自带基于 gossip + 多数票的故障转移，Sentinel 是另一套独立的主从认知。两套同时跑会出现「Sentinel 认为的主」与「集群选出的主」不一致，触发双主或反复切换，写入错乱。

  5. 三种形态都会丢数据，那「高可用」这个词到底保证了什么？请用一句话精确表述。

    参考回答：高可用保证的是「服务在可接受的时间内重新可用」，不保证「不丢数据」；数据不丢要靠持久化（AOF everysec/always）+ 业务侧幂等补偿。
