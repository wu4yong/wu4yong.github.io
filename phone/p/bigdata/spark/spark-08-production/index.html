生产实践与 AQE

作业从跑通到稳定上线，中间隔着资源配比、倾斜治理、故障定位这几道关。Spark 3.0 起 AQE（Adaptive Query Execution，自适应查询执行）默认开启，能在运行时根据实际数据量合并分区、拆分倾斜分区、调整 join 策略，很多老一套”提前拍脑袋定分区数”的调优可以交给它。这一篇把 AQE 的具体开关、shuffle 分区调法、监控入口和三类高频报错的现象与处置讲清楚。

运行时统计信息回流到优化器，小分区被合并、倾斜分区被拆分，执行计划随实际数据量自适应调整

1.1 AQE 是怎么工作的

AQE 在 shuffle 完成后读取实际统计信息（各分区大小、行数、倾斜情况），在运行时改写后续执行计划，而不是提交前一次性定死。Spark 3.0 起 spark.sql.adaptive.enabled 默认 true，三项核心能力如下：

能力
解决什么
对应参数
合并 shuffle 分区
小分区过多导致 Task 数膨胀
spark.sql.adaptive.coalescePartitions.enabled（默认 true）
倾斜 join 拆分
个别分区过大拖慢 join
spark.sql.adaptive.skewJoin.enabled（默认 true）
动态 join 策略
运行时按大小切换广播/排序 merge join
由优化器依据统计信息决策

AQE 的统计来源是上一轮 shuffle 后的实际分区数据，所以它能修正静态估算的偏差：估小了广播大表、估多了起一堆空 Task，这类问题运行时会被纠正。

要注意 AQE 不是万能：它只能在已有 shuffle 边界上调整计划，单 Stage 内部的算子顺序仍由静态优化器决定；输入数据本身倾斜严重且没有 shuffle 暴露统计时，AQE 也感知不到。另外 AQE 合并分区改变了下游并发度，依赖固定分区数的写入逻辑（如按分区落文件）要单独验证结果文件数量。

1.2 AQE 常用参数与分区调优

参数
默认值
作用与调优方向
spark.sql.adaptive.enabled
true（3.0+）
AQE 总开关，生产保持开启

200

调优顺序建议：先保证 AQE 与合并分区开启，再按 shuffle 数据量估初始分区数——经验值是单分区 128MB–256MB，shuffle 总大小 / 单分区目标 得出初始分区数，而不是照搬默认 200。分区不是越多越好：分区过多调度开销和任务启动成本上升，分区过大则单 Task 内存压力高。

AQE 合并分区后，下游分区数不再等于 spark.sql.shuffle.partitions，看 UI 实际 Stage 分区数判断并发度，而不是拿配置值对照。如果作业写入结果文件且对文件数量有要求，需要在写出前 repartition 固定分区，避免 AQE 合并导致小文件过多。

线上常用的一段配置，作为提交模板里的固定项：

# spark-defaults.conf（或 spark-submit --conf 逐条传入）
spark.sql.adaptive.enabled=true
spark.sql.adaptive.coalescePartitions.enabled=true
spark.sql.adaptive.coalescePartitions.minPartitionSize=64MB
spark.sql.adaptive.skewJoin.enabled=true
spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes=256MB
spark.sql.shuffle.partitions=400          # 按估算值给，交给 AQE 往下合并
spark.eventLog.enabled=true               # 保留历史 UI，便于事后复盘
spark.eventLog.dir=hdfs:///spark/eventlog

1.3 资源估算的基本口径

上线前给资源留余量，口径可以按数据规模倒推：单分区目标 128MB–256MB，分区数 = shuffle/输入数据量 ÷ 单分区目标；单 Executor 4–8 核、堆内存每核 1–2GB；Executor 总数 = 总核数 ÷ 单 Executor 核数。Driver 内存按结果回传规模给，纯调度型 Driver 1–2GB 起步，有全局聚合或收集结果时再加。

资源给得过于保守会频繁溢写和重试，给得过宽则占用队列、影响其他作业。第一版作业先按估算值提交，跑一轮后用 UI 上的实际内存占用、溢写字节和 Task 方差回调，比一次性猜准更现实。

按这套口径写出来的提交命令，参数是能对应到上面每一项的：

spark-submit \
  --master yarn \
  --deploy-mode cluster \
  --queue etl \
  --executor-cores 4 \
  --executor-memory 8g \
  --num-executors 20 \
  --conf spark.executor.memoryOverhead=2g \
  --conf spark.sql.shuffle.partitions=400 \
  --conf spark.sql.adaptive.enabled=true \
  --conf spark.serializer=org.apache.spark.serializer.KryoSerializer \
  --class com.example.etl.OrderDailyJob \
  order-daily.jar --dt 2022-03-23

memoryOverhead 别漏：堆外内存（序列化缓冲、Netty 直接内存）超限时容器会被 YARN 杀掉，日志表现为 Container killed by YARN for exceeding memory limits ... beyond ... physical memory used。

排查顺序固定下来：先在 SQL 页找耗时最长的 Stage，对比同 Stage 内 Task 的输入量和耗时方差，再看 Executor 页内存与 GC，最后翻日志确认异常类型。跳过 UI 直接 grep 日志，容易在海量日志里绕圈子。

生产环境建议打开事件日志（spark.eventLog.enabled=true，目录指向可靠存储），作业结束后 UI 仍可回放历史阶段；日志级别保持 INFO，异常栈会带 Stage 与 Task 编号，配合 UI 定位到具体分区。集群统一收集 Executor 标准输出与错误输出，避免节点重建后日志丢失。

1.5 高频报错：现象与处置

堆内存溢出（OOM）

现象：Executor 日志出现 java.lang.OutOfMemoryError: Java heap space，YARN 上伴随 Container killed by YARN for exceeding memory limits，Task 反复重试后作业失败。

处置：先看是不是分区过大或倾斜——少数 Task 输入量远超其他；是倾斜就走拆分/加盐/广播；确属分片整体过大，再提高 spark.executor.memory 或增加分区数。注意堆外内存占用也会计入 Container 限额，纯加堆内内存可能仍然超限。

GC 频繁、停顿长

现象：Executor 页 Full GC 次数与耗时持续上涨，Task 执行时间被 GC 拉长，日志反复出现 GC overhead limit exceeded。

处置：检查缓存对象是否未序列化、大对象是否堆内堆积；换 Kryo 序列化压缩缓存体积，清理不再使用的缓存；单 Executor 核数过多会共享堆内存，核数偏多时拆成更多 Executor。

数据倾斜与 shuffle 拉取失败

现象：同一 Stage 个别 Task 耗时是其他任务的几倍到几十倍，UI 上输入量严重不均；日志出现 FetchFailedException: Missing output 或 shuffle 文件拉取超时。

处置：确认倾斜 key（空值、热点维度、脏数据），过滤或加盐；大小表关联走广播；配合 AQE 倾斜 join 拆分；外部 shuffle 服务确认正常，避免 Executor 被回收后 shuffle 输出丢失。

Driver 端拉取大结果

现象：作业大部分 Task 正常，但 Driver 日志堆内存溢出，UI 上 Driver 内存接近上限；代码里常见 collect()、toLocalIterator() 把全量结果拉回驱动进程。

处置：结果只取 Top N 用 limit() + take()；需要落盘的结果直接由 Executor 写出到 HDFS/对象存储，不要经过 Driver；必须汇总全量指标时，先在集群内聚合到小体量再回驱动端。

磁盘溢写过多

现象：UI 上 spill (disk) 字节数很大，作业时长主要消耗在磁盘读写，数据量并未超出集群规模。

处置：检查分区数是否过少导致单分片过大，调整 spark.sql.shuffle.partitions；缓存级别是否把本该内存保留的数据溢写；聚合是否可以在 map 端提前 combiner。

1.6 上线前检查清单

  • AQE 总开关、分区合并、倾斜 join 保持默认开启，未被配置文件显式关掉
  • shuffle 分区数按数据量估算，没有照搬默认 200 或拍脑袋填 1000
  • 广播阈值与小表体量核对过，大表不会被误广播撑爆 Executor 缓存
  • checkpoint、持久化表路径在可靠存储上，目录不与输出结果混用
  • 作业失败重试次数、队列资源、Driver 内存按数据规模预留
  • 关键指标（Task 成功率、GC、溢写、队列占用）接入监控告警
  • 事件日志开启并落可靠存储，作业结束后 UI 可回放历史阶段
  • 结果写入路径与 checkpoint 目录分离，重跑不会覆盖状态
  • 作业重试与失败策略配置过，单 Task 失败不会拖垮整个应用

1.8 清单

  1. AQE 自 Spark 3.0 默认开启，运行时按实际统计信息合并分区、拆分倾斜分区、调整 join 策略
  2. 分区调优先开 AQE 合并，再按单分区 128MB–256MB 估初始 spark.sql.shuffle.partitions，不照搬默认 200
  3. 排查顺序：SQL 页找慢 Stage → Task 方差找倾斜 → Executor 页看内存 GC → 日志确认异常
  4. OOM 先查分区与倾斜，再谈加内存；GC 长优先查序列化与缓存对象；shuffle 失败核对外部 shuffle 服务
  5. 溢写过多往往是分区过少或缓存策略问题，不全是内存不够
  6. 上线前核对 AQE 开关、分区数、广播体量、checkpoint 路径与监控告警
  7. 资源按数据规模估算，首版跑完用 UI 实际占用回调，不追求一次猜准
  8. 排查先慢 Stage 再倾斜，再内存 GC，最后翻日志确认异常类型
