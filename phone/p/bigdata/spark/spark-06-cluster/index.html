部署模式与提交

同一套 Spark 程序，在笔记本上跑、在自有集群跑、挂到 YARN 或 Kubernetes 上跑，代码基本不动，变的是资源从哪来、Driver 住在哪、Executor 怎么拉起。这一篇梳理 local、standalone、YARN、Kubernetes 四种模式的取舍，spark-submit 真正要关心的参数，以及动态资源分配怎么配。

提交入口向不同资源管理器申请容器，工作节点上的执行器按分配并行跑任务

选型先看现有基础设施：已经有 Hadoop 集群就走 YARN，作业已经跑在 K8s 平台上就用 K8s，standalone 更多出现在教材和小规模隔离环境。local 模式只存在于开发阶段，不应该出现在生产脚本里。

无论哪种模式，Driver 与 Executor 都需要能互相通信：YARN/K8s 由集群网络保证，standalone 要注意节点间端口互通，local 则回环即可。网络不通时表现为作业卡在申请资源阶段，日志里反复出现连接超时，不是代码问题。

1.3 client 与 cluster：Driver 住在哪

模式
Driver 位置
适用
注意
client
提交命令所在机器
本地调试、需要直看日志
提交机关了作业就挂，不适合长作业
cluster
集群内某个节点容器里
生产长作业、定时任务
Driver 日志要到集群 UI 或容器日志里查

YARN 上 --deploy-mode cluster 时，ApplicationMaster 容器里跑 Driver，客户端提交完可以退出；client 模式下 Driver 留在提交机，AM 只负责申请 Executor。生产调度平台跑的批处理任务基本都是 cluster 模式；交互式查询、临时排障才用 client。

1.4 动态资源分配

静态分配在作业启动时一次性领走固定数量的 Executor，任务忙闲不均时容易浪费。动态资源分配（dynamic allocation） 按负载伸缩：空闲 Executor 被回收，积压时再补领，配合 shuffle 服务延长 Executor 存活，避免 shuffle 输出丢失。

# spark-defaults.conf 或 --conf 传入
spark.dynamicAllocation.enabled true
spark.dynamicAllocation.minExecutors 2
spark.dynamicAllocation.maxExecutors 20
spark.dynamicAllocation.executorIdleTimeout 60s
spark.shuffle.service.enabled true     # 外部 shuffle 服务，Executor 被回收后 shuffle 文件仍可取

要点：动态分配依赖集群提供外部 shuffle 服务（YARN 上是 NodeManager 侧的 shuffle service），只开客户端开关不开服务，Executor 一被回收下游就拿不到 shuffle 数据。Executor 初始数量由 spark.dynamicAllocation.initialExecutors 控制。

动态分配最适合批次间忙闲差异大的调度作业：早高峰批次多领 Executor，闲时回收给队列里其他作业。如果整条流水线都是稳态高负载，静态固定数量反而更可控，避免伸缩抖动。

Executor 规格搭配有个常见平衡：单 Executor 核数过多会共享同一堆内存，线程争抢内存与 CPU；核数偏少、Executor 数量偏多则调度开销上升。一般单 Executor 4–8 核，堆内存按每核 1–2GB 估算，再按队列可分配总额反推 Executor 数量。

提交前还要确认作业包与依赖在集群可达位置：HDFS、对象存储或镜像内均可，避免依赖提交机本地磁盘。多模块项目把公共依赖打成单独 jar 通过 --jars 分发，主 jar 只放业务代码，便于排障和复用。

1.5 一个生产提交示例

下面是 YARN cluster 模式的典型提交命令，队列、内存、核数按集群规格替换：

spark-submit \
  --class com.starry.bigdata.OrderReportJob \
  --master yarn \
  --deploy-mode cluster \
  --queue bigdata \
  --executor-memory 4g \
  --executor-cores 4 \
  --num-executors 10 \
  --conf spark.sql.shuffle.partitions=200 \
  --conf spark.serializer=org.apache.spark.serializer.KryoSerializer \
  --jars hdfs:///libs/udf-functions.jar \
  hdfs:///apps/starry-bigdata-job.jar \
  --date 2022-02-24

作业参数（--date 之后的部分）传给主类 main 方法，不被 spark-submit 解析。--jars 里的包会随任务分发到 Executor 工作目录，避免各节点手工摆包。

跑 YARN 模式前要让提交机认得 Hadoop 集群：配置 HADOOP_CONF_DIR 指向 hadoop-conf 目录，spark-submit 才能读到 ResourceManager 地址和队列信息；缺这个环境变量时，作业报找不到 YARN 配置，而不是代码错误。K8s 模式则需要 KUBECONFIG 或 API 地址，镜像里带上 Spark 发行版与作业包。

1.6 容易踩的坑

  • client 模式把长作业挂在登录机上，登录机重启或会话断开，作业直接失败
  • 提交脚本里残留 --master local[*]，上集群后不申请 YARN 资源，只在提交机上跑
  • 动态分配开了但没配外部 shuffle 服务，Executor 回收后 shuffle 拉取失败
  • 把大量第三方依赖塞进 fat jar，包体积膨胀，分发耗时拉长
  • 资源参数和队列规格不匹配，申请的内存超过队列上限，作业在 AM 阶段就被拒绝
  • cluster 模式下 Driver 日志不在提交机本地，直接翻控制台看不到异常栈，需要到 YARN UI 或容器日志里取
  • 作业包只放在提交机本地路径，Executor 节点读不到，任务启动时报类找不到或 jar 缺失

1.8 清单

  1. 四种模式：local 开发、standalone 小集群、YARN 大数据生产、K8s 云原生，按基础设施选型
  2. 提交参数三组：作业信息（--class）、资源（内存/核数/Executor 数）、配置（--conf）
  3. client 的 Driver 在提交机，cluster 的 Driver 在集群容器内；生产长作业用 cluster
  4. 动态分配按负载伸缩，必须配合外部 shuffle 服务，否则回收 Executor 会丢 shuffle 输出
  5. 作业业务参数放在 jar 包之后，spark-submit 不解析这一段
  6. 常见事故：local 残留、client 挂长作业、队列超规格被拒、fat jar 过胖
  7. 集群模式排障先取 YARN/K8s 上的 Driver 日志，不要在提交机本地找异常栈
  8. 提交机配置 HADOOP_CONF_DIR，否则 YARN 模式读不到集群地址与队列
