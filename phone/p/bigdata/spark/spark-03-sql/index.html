Spark SQL 与 DataFrame

直接写 RDD 算子能干活，但业务里绝大多数需求是”读一份结构化数据、按 SQL 条件过滤聚合、出一张表”。Spark SQL 把这类需求提到结构化数据层：用 SQL 或 DataFrame API 表达业务，底层交给 Catalyst 优化器生成执行计划。这一篇讲清 DataFrame、DataSet、RDD 三者的区别，Catalyst 怎么优化，以及和 Hive 怎么打通。

多层优化器把结构化查询逐层编译成分布式执行计划，数据沿管线流向结果表

1.1 为什么在 RDD 之上再加一层

RDD 只知道”一堆记录”，不知道每条记录有哪些字段、类型是什么。Spark SQL 在 RDD 之上补了一张 Schema（结构表）：列名、类型、可空性都登记在册，引擎据此可以做列裁剪、类型校验和表达式优化。

抽象

一句话区分：DataFrame 是”带 Schema 的 RDD”，DataSet 是”强类型版的 DataFrame”。Python 与 R 端没有样例类概念，只有 DataFrame；Scala/Java 端可以在两者之间切换。

1.2 DataFrame 上的两类写法

同一份聚合需求，SQL 字符串和 DataFrame DSL 两条路都能走，底层计划一致：

val spark = SparkSession.builder().master("local[*]").appName("sql-demo").getOrCreate()

val df = spark.read.option("header", "true").csv("hdfs:///data/orders.csv")

// 写法一：DataFrame DSL，编译期可做部分类型检查
val top = df.groupBy("city")
  .sum("amount")
  .orderBy(org.apache.spark.sql.functions.desc("sum(amount)"))

top.show(10)
-- 写法二：先注册临时视图，再写标准 SQL
CREATE OR REPLACE TEMP VIEW orders AS
SELECT * FROM csv.`hdfs:///data/orders.csv`;

SELECT city, SUM(amount) AS total
FROM orders
GROUP BY city
ORDER BY total DESC
LIMIT 10;

两种写法混用很常见：复杂链路用 DSL 拼，固定报表直接落 SQL 字符串。注意 DSL 里的列引用要么传列名字符串，要么用 col("amount")，别把 DataFrame 当普通集合去 map。

1.3 Catalyst 优化器做了什么

Catalyst 是 Spark SQL 的核心，把一条查询从文本变成可执行的 RDD 算子链，分四个阶段：

优化器是基于规则（rule）在树上做变换的，新版本还会结合代价模型挑选物理计划。业务侧能直接感受到的收益：WHERE 条件尽量下推到数据源，读列只取查询用到的列，表达式在编译期合并——这些不需要手写，写 SQL 时把过滤条件尽早写出来即可。

1.4 和 Hive 集成

Spark SQL 可以直接读 Hive 里已有的表，复用 Hive 的元数据和分区布局。接入方式是把 hive-site.xml 放进 conf 目录，建 SparkSession 时打开 Hive 支持：

val spark = SparkSession.builder()
  .appName("hive-integration")
  .enableHiveSupport()   // 复用 Hive 元数据与 SerDe
  .getOrCreate()

spark.sql("SHOW TABLES").show()
spark.sql("SELECT dt, COUNT(*) FROM dwd_order_detail GROUP BY dt").show()

1.5 读取外部数据源

spark.read 按格式加载，常见数据源都有对应入口：

// Parquet：列式存储，自带 Schema，分析场景首选
val parquet = spark.read.parquet("hdfs:///data/events.parquet")

// JSON：每行一条记录，Schema 可由采样推断
val json = spark.read.json("hdfs:///data/events.json")

// JDBC：直连关系库，按谓词下推分片读取
val jdbc = spark.read.format("jdbc")
  .option("url", "jdbc:mysql://host:3306/db")
  .option("dbtable", "orders")
  .option("user", "reader")
  .option("password", "******")
  .load()

1.6 容易踩的坑

  • 把 DataFrame 转成 RDD 再 map 逐行处理，丢掉 Schema，列裁剪和类型检查全部失效
  • 读 CSV 不设 header 选项，列名变成 _c0、_c1，后续 SQL 全靠位置猜
  • 以为 DataFrame 操作立刻执行，和 RDD 一样要等 action（show、write、count）才提交 Job
  • 混用 Hive 表时不接 Metastore，SHOW TABLES 为空，误以为表丢了
  • 大宽表只查几列却 select *，列式存储的裁剪优势完全浪费

1.8 清单

  1. DataFrame 带 Schema，DataSet 是 Scala/Java 端的强类型版本；Python 端只有 DataFrame
  2. SQL 字符串与 DataFrame DSL 底层生成同一套执行计划，可混用
  3. Catalyst 四阶段：解析 → 逻辑优化 → 物理计划 → 代码生成
  4. 谓词下推、列裁剪、常量折叠由优化器完成，业务侧把过滤条件尽早写出来
  5. 接 Hive 靠 hive-site.xml 与 enableHiveSupport()，元数据复用 Metastore
  6. 常见坑：丢 Schema、CSV 表头没识别、误以为 DSL 立即执行
