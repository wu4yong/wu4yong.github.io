Spark（一）生态与运行原理

分类：bigdata · spark ｜ 标签：Spark

生态与运行原理

MapReduce 把每一步中间结果都写回磁盘，一批迭代型作业跑一整夜是常态。Spark 把中间结果尽量留在内存，把多个算子串成一个 DAG 在一次调度里跑完，在同样的集群上把机器学习、图计算这类反复迭代的任务提速一两个数量级。这一篇先讲清楚 Spark 由哪几块组成，以及一个作业从提交到跑完经历了哪几个阶段。

主控节点向多个工作节点下发计算任务，任务沿有向无环图逐层汇聚

1.1 生态由哪几块组成

很多人把 Spark 当成”一个计算引擎”，其实它是一组围绕核心 RDD 抽象长出来的子项目，各模块可单独使用：

模块
解决什么
类比
Spark Core
RDD 抽象、任务调度、内存与存储管理
发动机
Spark SQL
在结构化数据上跑 SQL，提供 DataFrame/DataSet
发动机上的变速箱
Structured Streaming
把流当成不断增长的表来计算
换挡成持续运转
MLlib
机器学习算法库
车上的辅助驾驶套件
GraphX
图计算模型与算子
专门跑网络图的套件

对外统一的入口是 SparkSession：2.0 之后它把旧版的 SparkContext、SQLContext、HiveContext 收编到一个对象里，建上下文只拿它就够。

1.2 运行时角色：Driver 与 Executor

一个 Spark 应用（Application）跑起来后，进程分两类角色：

角色
职责
生命周期
Driver
持有 SparkSession，解析代码、生成 DAG、向集群申请资源、调度任务
整个应用一个，应用结束即退出
Executor
被分配到工作节点上的进程，执行 Driver 派下来的 Task，缓存数据也存在这里
随应用启动，随应用释放

关键点：Driver 是”大脑”，Executor 是”双手”。业务代码里写的 transformation 不会立刻执行，Driver 只是把它们记进 DAG；真正算的时候，数据分片和任务被打包送到各个 Executor 上并发跑。Driver 挂了，整个应用就失败，所以生产上 Driver 内存和稳定性不能当成配角。

Executor 之间互不通信，每个 Executor 由若干线程槽位并行跑 Task；一个 Executor 进程内既算数据也存缓存块，任务调度器尽量把 Task 派到持有对应缓存的节点上，这就是所谓的数据局部性（data locality）。

1.3 作业层级：Application → Job → Stage → Task

从代码到集群上跑的线程，层级要背下来：

层级
由什么触发
粒度
Application
一个 SparkSession 起的整套程序
一次提交
Job
碰到一个 action 算子就生成一个 Job
一次动作
Stage
宽依赖（shuffle）边界把 Job 切成若干 Stage
一组可流水线执行的算子
Task
Stage 按数据分片切出的最小执行单元
一个分片上的一段计算

一个 action 对应一个 Job，一个 Job 按 shuffle 边界拆成多个 Stage，一个 Stage 内的算子可以流水线串起来跑，Stage 之间必须等上一阶段 shuffle 落盘、拉取完成。Task 的数量通常等于 RDD 分区数，是集群真正并发度的来源。

1.4 DAG 是怎么被切分的

Driver 拿到代码后做三件事：把算子链转成 RDD 依赖图（DAG），沿依赖关系找出宽依赖位置作为 Stage 边界，再把每个 Stage 编译成可以序列化分发的 Task 集合。

这里先给结论，细节留到下一篇：

  • 窄依赖：一个子分区只依赖父 RDD 的一个分区，可以在同一轮计算里流水线执行
  • 宽依赖：子分区依赖父 RDD 的多个分区，中间必须发生 shuffle，天然成为 Stage 边界
  • DAG 调度器（DAGScheduler）负责切 Stage，底层调度器（TaskScheduler）负责任务分发到 Executor

要注意一个常见误解：Spark 不是”全内存计算”。内存装不下时它照样溢写磁盘，只是把磁盘 IO 推迟到真正需要的时刻，并且把多步计算合并到一次调度里，减少反复读写的次数。

1.6 一个最小可跑的程序

下面这段 Scala 代码读完文件，按空白分词，统计单词出现次数，再打印前 10：

import org.apache.spark.sql.SparkSession

val spark = SparkSession.builder()
  .appName("word-count")
  .master("local[*]")      // 本地调试用，提交到集群时去掉，由集群决定核数
  .getOrCreate()

val lines = spark.read.textFile("hdfs:///data/words.txt")

val counts = lines.flatMap(_.split("\\s+"))
  .groupBy("value")
  .count()

counts.sort(counts("count").desc).limit(10).show()
spark.stop()

show() 是一个 action，碰到它 Driver 才会把前面的聚合计划提交成 Job；在这之前所有算子都只是 DAG 上的节点。

1.7 容易踩的坑

  • 把 master("local[*]") 留在提交脚本里上生产，会直接压死集群调度，参数必须由部署侧覆盖
  • 在 Driver 端 collect() 大结果集，数据全部拉回驱动进程，很容易把 Driver 内存撑爆
  • 以为 Spark 不会碰磁盘，堆内存给得太保守，结果频繁溢写，作业比 MapReduce 还慢
  • 混淆 Job 与 Stage：调一个 action 出一个 Job，shuffle 边界才切 Stage，UI 上数不对通常是这层概念没分清

1.9 清单

  1. Spark 生态 = Core + SQL + Structured Streaming + MLlib + GraphX，统一入口是 SparkSession
  2. Driver 持上下文、生成 DAG、调度任务；Executor 跑 Task、缓存数据
  3. 层级链路：Application → Job（action 触发）→ Stage（宽依赖切分）→ Task（分区数）
  4. Stage 边界由宽依赖划出，窄依赖内部可以流水线执行
  5. Spark 的快来自内存复用与 DAG 合并，不是”完全不落盘”
  6. 本地 master 配置和 Driver 端 collect 是新人最常带进生产的两个坑
