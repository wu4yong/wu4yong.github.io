RDD 与算子体系

RDD（Resilient Distributed Dataset，弹性分布式数据集）是 Spark 最底层的抽象：一批被分区、可并行计算、出故障可重算的数据集合。理解 RDD 的关键不是记住接口，而是分清两件事——哪些算子只是”登记计划”，哪些算子会真正触发计算；以及一次算子链里哪里会发生 shuffle。这一篇把依赖、算子、缓存三件事串起来讲。

分区数据沿算子链分组汇聚，宽依赖处数据经过重分区后流向新的分区

1.1 RDD 到底是什么

RDD 有四个特性，对应它名字里的四个词：

特性
含义
落地方式
分区（Distributed）
数据被切成多个分片，分布在不同节点
分区数决定 Task 并发度
弹性（Resilient）
丢了能靠血缘（lineage）重算
不依赖固定副本，沿依赖链重建
数据集
每个元素是一条记录
RDD 是记录的集合，不是单张表
不可变
生成新 RDD，不修改老 RDD
算子返回新 RDD，源 RDD 原样保留

血缘（lineage）是 RDD 容错的核心：某个分区挂了，Driver 沿依赖关系找到父分区重新算一遍即可，不需要像复制副本那样提前存多份。代价是长血缘链一旦末端丢数据，重算成本会逐层放大，所以关键节点会做缓存或 checkpoint。

1.2 窄依赖与宽依赖

依赖描述”子分区怎么对应父分区”，是划分 Stage 和判断能不能流水线执行的依据：

类型
分区对应
是否 shuffle
典型算子
窄依赖
子分区只依赖一个父分区
否
map、filter、union、mapPartitions
宽依赖
子分区依赖父 RDD 多个分区
是
groupByKey、reduceByKey、join、repartition

窄依赖下，同一父分区的数据可以在一个线程里把 filter、map 串着跑完，中间不落盘；宽依赖下，同 key 的数据要从上游各分区拉到一起，必须经过网络传输和分区重写，也就是 shuffle。判断算子是窄是宽，先问一句：子分区是否要跨多个父分区取数。

1.3 transformation 与 action

算子分两类，区别在于是否触发一个 Job：

类别
行为
是否触发计算
代表算子
transformation
返回新 RDD，只登记计划
否，惰性求值
map、filter、flatMap、reduceByKey、join
action
把结果算出来并返回驱动端或写出
是，生成 Job
count、collect、take、saveAsTextFile、foreach

惰性求值的好处是 Driver 可以看到完整算子链再做优化：合并相邻窄依赖、裁剪不必要的列、判断哪些分区可以跳过。坏处是调试时容易误判——加了一行 map 不代表真的跑了，日志里看不到任何动作是正常的，必须等 action 出现。

1.4 shuffle 发生在哪、代价是什么

宽依赖算子执行时，上游每个分区按 key 的哈希（或分区器规则）把数据写入本地磁盘文件，下游分区再把属于自己的文件拉过来聚合。代价集中在三处：

  • 网络：上游到下游按分区批量传输，shuffle 数据量直接决定作业时长
  • 磁盘：map 端先落盘，reduce 端再读回，多一轮磁盘读写
  • 排序与归并：分组聚合前需要按 key 排序或归并

同一个业务需求，算子选法不同 shuffle 量差别很大：reduceByKey 在 map 端先做本地聚合（combiner）再 shuffle，groupByKey 则把全量记录都拉到下游，热点场景下 groupByKey 容易把 reduce 端压垮。

shuffle 过程中上游分区的输出会按分区器规则写成数据文件，下游拉取时按分区编号对应；分区器（Partitioner）决定 key 落到哪个分区，默认哈希分区，按 key 哈希值对分区数取模。

1.5 缓存：cache 与 persist

反复使用的 RDD 不缓存，每次 action 都会从头重算血缘。Spark 提供两个方法控制存储级别：

否

cache() 等价于 persist(MEMORY_ONLY)。缓存是惰性的：调用 persist 本身不存数据，第一次 action 跑完后块才留在 Executor 内存里。缓存不主动释放，应用结束才回收，长期运行的作业要注意用 unpersist() 清掉不再需要的缓存。

还要区分缓存与 checkpoint：缓存靠血缘重建，适合反复读取的中间结果；checkpoint 把数据真正写到可靠存储（HDFS），切断血缘，适合链路太长、重算成本高的场景。两者解决的是不同问题，不能互相替代。

1.6 一段可对照阅读的示例

val spark = SparkSession.builder().master("local[*]").appName("rdd-demo").getOrCreate()
val sc = spark.sparkContext

val raw = sc.textFile("hdfs:///data/access.log")

// 窄依赖链：切分、过滤，同一分区内流水线执行
val parsed = raw.map(line => line.split("\\s+"))
  .filter(arr => arr.length >= 8)
  .map(arr => (arr(0), arr(7)))

// 宽依赖：按首列分组聚合，触发一次 shuffle
val summary = parsed.reduceByKey((a, b) => a + b)

summary.persist(org.apache.spark.storage.StorageLevel.MEMORY_AND_DISK_SER)
println(summary.count())   // action，触发 Job；缓存块在这一轮之后落位
summary.take(5).foreach(println)

sc.stop()

1.7 容易踩的坑

  • 把 count()、collect() 当成 transformation 反复调，一个算子链被触发成多个 Job，重算血缘
  • 用 groupByKey 做聚合，map 端没有 combiner，数据倾斜时 reduce 端内存爆掉
  • 缓存级别选 MEMORY_ONLY，内存不足后被驱逐，下次 action 又从头重算，作业表现为”忽快忽慢”
  • 以为 persist 调用当下就把数据存好，在第一次 action 之前就去估算缓存大小
  • 缓存大对象用未序列化方式，Java 对象头和引用占掉大半内存，实际能存的记录远少于预期

1.9 清单

  1. RDD = 分区、弹性（血缘重算）、记录集合、不可变，容错靠 lineage 不靠多副本
  2. 窄依赖不 shuffle，可流水线；宽依赖必 shuffle，天然是 Stage 边界
  3. transformation 只登记计划，action 才触发 Job；调试时先找 action 在哪
  4. shuffle 代价在网络、磁盘、排序三处，优先用带 combiner 的聚合算子
  5. cache() 即 persist(MEMORY_ONLY)，缓存惰性落位，用完记得 unpersist
  6. 序列化存储级别省空间但吃 CPU，纯内存级别放不下就会被驱逐重算
