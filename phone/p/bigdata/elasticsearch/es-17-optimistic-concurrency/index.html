乐观并发：_version、_seq_no、_primary_term 与 409

两个服务同时改同一条文档，谁赢？Elasticsearch 不给你加锁，它给你一对「票据」：_seq_no + _primary_term。

带对了才能改，带错了返回 409。理解这套机制，才能写出不会互相覆盖的更新逻辑。

if_seq_no + if_primary_term 冲突时 202 与 409 的分流｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说清 _seq_no 与 _primary_term 各自的含义与作用域；
  2. 会写带 if_seq_no + if_primary_term 的条件更新；
  3. 知道 409 出现后该重试还是该放弃；
  4. 分清 _version 与业务版本号的区别。

官方机制叫乐观并发控制：不锁文档，而是要求你在写入时带上「我看到的版本」。条件不满足就拒绝，由你自己决定重读还是放弃。

PUT /goods/_doc/1?if_seq_no=5&if_primary_term=1

语义：只有当前文档的 _seq_no 仍是 5、主分片还是第 1 任期时，这次写入才生效；否则返回 409 version_conflict_engine_exception。

为什么必须两个字段一起带？因为主分片一旦故障转移，新主分片上的 _seq_no 序列可能与旧主分片重合，单看序号会误判；加上任期才能唯一标识「我看到的那一版」。

四、原理拆解：409 是不是错误

409 在语义上不是「失败」，而是「你的假设过期了」。处理方式取决于业务：

业务模型
建议
计数/累加类
重读最新版本再重算，通常重试 3 次内收敛
状态机流转（下单→支付）
重读后校验状态是否仍允许该动作，不允许就放弃
覆盖写（全量同步）
直接重发不带条件的 index（后写者赢）

内置的 _update API 也提供 retry_on_conflict 参数（默认 0，即不重试）：它在服务端自动重读并重放脚本，适合「脚本幂等」的场景。

六、实操

# 1) 拿到当前票据
curl -s "http://localhost:9200/goods/_doc/1" | jq '{_seq_no, _primary_term}'

# 2) 带条件更新（把上一步的值填进来）
curl -X PUT "http://localhost:9200/goods/_doc/1?if_seq_no=0&if_primary_term=1" \
  -H 'Content-Type: application/json' -d '{ "title": "改了", "price": 12 }'

# 3) 用错票据：预期 409
curl -X PUT "http://localhost:9200/goods/_doc/1?if_seq_no=0&if_primary_term=1" \
  -H 'Content-Type: application/json' -d '{ "title": "又改一次", "price": 13 }'

# 4) 服务端自动重试的更新（脚本幂等时可用）
curl -X POST "http://localhost:9200/goods/_update/1?retry_on_conflict=3" \
  -H 'Content-Type: application/json' -d '{ "doc": { "price": 14 } }'

第 3 步会返回 409，这是预期行为，把它当异常日志刷屏会掩盖真正的问题。

七、常见坑

  1. 把 _version 当业务版本号：它是内部计数，业务回滚/重建索引后会变。
  2. 只带 if_seq_no 不带 if_primary_term：主分片切换后可能误判。
  3. 409 直接重试不重读：同一票据重发永远 409，必须先重新读取。
  4. retry_on_conflict 调很大：脚本非幂等时会造成重复累加，官方默认 0 是有原因的。
  5. 以为有分布式锁：ES 不提供跨文档锁，只有文档级的乐观并发。

八、课后小结

  1. _seq_no 是分片内序号，_primary_term 是主分片任期，两者一起才构成有效票据。
  2. 不满足条件返回 409，属正常并发结果。
  3. 409 的处理策略由业务决定：重读重算、状态校验或放弃。
  4. _version 是内部计数，不要当业务版本。
  5. _update 的 retry_on_conflict 默认 0，脚本幂等才可放开。

九、思考题

  1. 两个线程同时用同一票据更新，为什么一定有一个失败？这和「加锁」的本质区别是什么？
  2. 库存扣减为什么不能只靠 _update 脚本 + retry_on_conflict？给出一个会出错的时序。
  3. _seq_no 是按分片递增的，那「同一文档的两次修改」在某些情况下会不会序号不连续？为什么？
