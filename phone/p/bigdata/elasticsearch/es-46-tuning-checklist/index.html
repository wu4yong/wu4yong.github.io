分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

优化清单：索引侧与查询侧，按收益排序

优化不是「把参数都调一遍」，而是按收益/风险比排序做。

这一篇是 M7 的收口：把前面讲散的手段汇总成两张清单，每条都标「官方依据在哪一讲」。

配图 46-1｜提示词：两块并排清单板。左板「索引侧」：bulk 批量、refresh_interval 调大、副本先 0 后回、translog async、force merge 只读索引、mapping 精简（index:false、norms:false）；右板「查询侧」：filter 打底、_source 裁剪、size:0、search_after 替代深翻、避免前置通配、track_total_hits。每块板右侧一根排序条，标「收益高→低、风险低→高」。深色星空背景，青蓝与琥珀。

一、学习目标

  1. 能按「收益/风险」给优化手段排序；
  2. 说清每条的官方依据与适用范围；
  3. 知道哪些手段只在特定阶段可做（如 force merge 只对只读索引）；
  4. 形成一套可复用的排查与优化顺序。

四、原理拆解：为什么「收益排序」比「全都调」重要

写入侧的核心矛盾是段生成速度 vs 查询效率：refresh 越频繁，段越多，查询要扫的段越多；merge 越激进，写入越慢。查询侧的核心矛盾是取多少数据 vs 响应速度：_source 越大、桶越多，fetch 与内存压力越大。

所以优化顺序应当固定为：

顺序
动作
为什么先做它
1
量清楚瓶颈（慢日志/profile/hot_threads）
不定位就调参等于赌博
2
剪数据量（_source 裁剪、缩查询范围）
收益最直接、风险最低
3
改写法（filter 化、避免前置通配、换分页）
不改架构就能见效
4
调参数（refresh、副本、translog）
影响面大，需与业务确认
5
改结构（mapping、分片数、reindex）
代价最高，最后手段

六、实操

# 导入期临时设置
curl -s -X PUT "http://localhost:9200/goods/_settings" -H 'Content-Type: application/json' -d '
{ "index.refresh_interval": "-1", "index.number_of_replicas": 0,
  "index.translog.durability": "async" }'

# 导入完成后恢复（顺序很重要：先 refresh，再加副本）
curl -s -X PUT "http://localhost:9200/goods/_settings" -H 'Content-Type: application/json' -d '
{ "index.refresh_interval": "30s", "index.number_of_replicas": 1,
  "index.translog.durability": "request" }'

# 只读索引合并（不要对写入中的索引做）
curl -s -X POST "http://localhost:9200/logs-2023/_forcemerge?max_num_segments=1"

# 列表页查询：只取三字段 + filter 打底
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "_source": { "includes": ["title","price","cover"] },
  "query": { "bool": { "filter": [ { "term": { "on_sale": true } } ],
    "must": [ { "match": { "title": "跑鞋" } } ] } },
  "sort": [ "_score" ], "size": 20 }'

max_num_segments=1 会重写整个索引，IO 很重，只能在低峰期针对只读索引执行——官方明确警告不要在活跃索引上做。

七、常见坑

  1. 对写入中的索引 force merge：产生巨大 IO 与段反复重写。
  2. 忘了把 refresh_interval 改回来：数据「看不见」，被当成丢数据。
  3. 副本加了又忘改回：长期单副本，容灾能力下降。
  4. translog.durability: async 留在生产：掉电可能丢已确认写入。
  5. 只调参数不改查询：收益小、风险大，最典型的无效优化。
  6. 不看 profile 就下结论：把 fetch 慢当成 query 慢，越调越糟。

八、课后小结

  1. 优化五步：定位 → 剪数据 → 改写法 → 调参数 → 改结构。
  2. 导入期与稳定期要两套配置，切换顺序不能乱。
  3. force merge 只属于只读索引。
  4. _source 裁剪与 filter 打底是「低风险高收益」的代表。
  5. 每条手段都要能说出官方依据，否则就是猜。

九、思考题

  1. 「导入期 refresh -1 + 副本 0」结束后，为什么必须先 refresh 再加副本？
  2. 一个查询 profile 显示 collector 占比 80%，你的前三步优化是什么？
  3. 如果只能做一件优化，你会选「_source 裁剪」还是「调 refresh_interval」？为什么？
