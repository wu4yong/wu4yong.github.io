故障处置剧本：CPU 高、写入被拒、分片未分配、集群红

事故现场最缺的不是知识，是顺序。

这一篇给四个高频故障各一份剧本：先做什么、看什么、在什么条件下才允许做「危险动作」。

  3. 说清哪些动作是「危险动作」，需要什么前提；

四、原理拆解：为什么「先止血」比「找根因」优先

事故中集群的自我修复动作（再平衡、副本重建、merge）会跟你的排查动作抢资源。所以第一步永远是减少输入：停掉批量导入、限制客户端并发、临时冻结分配。止血后再定位，才有稳定的观测环境。

allocation/explain 之所以是分片类故障的必经步骤，是因为它把原因归到有限的枚举（NODE_LEFT、ALLOCATION_FAILED、CLUSTER_RECOVERED、水位、过滤），每个枚举对应完全不同的处置——不看它就直接 reroute，是把「可恢复」变成「不可恢复」的最快方式。

六、实操

# CPU 高：先看线程
curl -s "http://localhost:9200/_nodes/hot_threads?threads=5"

# 写入 429：看池
curl -s "http://localhost:9200/_cat/thread_pool?v&h=node_name,name,active,queue,rejected"

# 分片未分配：看原因
curl -s "http://localhost:9200/_cluster/allocation/explain?pretty" -H 'Content-Type: application/json' -d '{}'

# 临时止血：冻结分配（避免边查边搬）
curl -s -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d '
{ "persistent": { "cluster.routing.allocation.enable": "none" } }'

# 恢复：处理完记得改回
curl -s -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d '
{ "persistent": { "cluster.routing.allocation.enable": "all" } }'

allocation.enable: none 是标准的「暂停再平衡」手段，止血后务必改回，否则新索引的分片永远不分配。

七、常见坑

  1. red 第一反应删索引：先 explain，多数情况可救。
  2. accept_data_loss 随手加：这是显式承认丢数据。
  3. 止血后忘了恢复设置：enable: none 遗留成「新索引永远 red」。
  4. 429 去调大队列：只是延后崩溃，客户端退避才是正解。
  5. CPU 高先扩容：没定位到线程就加机器，问题会跟着数据一起搬过去。
  6. 事故中同时做多件事：观测被自己干扰，越救越乱。

八、课后小结

  1. 四类故障各有一条固定顺序，先拿第一手信息。
  2. 先止血（限流/冻结分配），再定位，后修复。
  3. allocation/explain 是分片故障的必经步骤。
  4. 危险动作都有明确前提，不能省。
  5. 止血设置必须记回滚。

九、思考题

  1. 一个节点 CPU 100%，hot_threads 显示 search 线程占满，你会先限流还是先扩容？为什么？
  2. unassigned_info.reason 为 CLUSTER_RECOVERED 意味着什么？该等还是该强制？
  3. 为什么「调大线程池队列」在 429 场景里是错误方向？
