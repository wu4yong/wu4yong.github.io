聚合三层结构：metric、bucket、pipeline

聚合（aggregation）和查询用的是同一套数据结构，所以官方敢说「聚合和搜索一样快」。

但要算对，先得认清三层：指标（metric）算数、桶（bucket）分组、管道（pipeline）在结果上再算。

配图 30-1｜提示词：三层漏斗式结构图。底层一排原始文档小方块；中间左侧是 bucket 分组框（按 brand 分成三个彩色桶），右侧是 metric 图标（avg、sum、cardinality）贴在桶上；顶层是 pipeline 图标（bucket_script 与 bucket_sort）作用在「桶的产出」上，箭头标注「不能直接吃文档，只能吃兄弟聚合的结果」。深色星空背景，青蓝与琥珀。

一、学习目标

  1. 说清 metric / bucket / pipeline 三层的父子关系；
  2. 会写 size: 0 + aggs 的标准结构；
  3. 知道 pipeline 聚合只能引用兄弟聚合的结果，不能访问文档；
  4. 会用 filter 子聚合做「分区间统计」。

三、理论讲解

层
作用
典型成员
输入
metric（指标）
对一组文档算一个数
avg、sum、min、max、stats、cardinality、percentiles

bucket（桶）
把文档分组，每组一个桶
terms、range、date_histogram、histogram、filter、filters

pipeline（管道）
对其他聚合的输出再计算
bucket_script、bucket_selector、bucket_sort、derivative、cumulative_sum

嵌套规则：bucket 可以套 bucket（如 terms 里再 date_histogram），metric 挂在任意层级下；pipeline 只能挂在同级聚合的父级，通过 buckets_path 引用兄弟名字。

四、原理拆解：为什么聚合「快」又「贵」

快，是因为 doc_values：按列读字段值，不用解析 JSON，也不走倒排。

贵，是因为桶的数量会爆炸：terms 分成 100 组，每组下再 date_histogram 分 30 天，就是 3000 个桶；每个桶还要维护自己的 metric 状态。所以官方设了 search.max_buckets（默认 65536）这道闸，超了就报 too_many_buckets_exception。

另一个关键点：terms 的计数是每个分片先各算 Top N，再汇总，所以 doc_count 可能是「近似值」。返回里的 doc_count_error_upper_bound 就是这个近似误差的上界，sum_other_doc_count 是被截掉的长尾文档数——看这两个数字，就知道结果能不能直接拿去对账。

六、实操

# 基础结构：不要文档，只要聚合
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "size": 0,
  "query": { "term": { "on_sale": true } },
  "aggs": {
    "by_brand": { "terms": { "field": "brand", "size": 10 },
      "aggs": { "avg_price": { "avg": { "field": "price" } } } },
    "price_bands": { "range": { "field": "price",
      "ranges": [ { "to": 50 }, { "from": 50, "to": 200 }, { "from": 200 } ] } } } }'

# pipeline：算每个品牌的均价占全站均价的比例
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "size": 0,
  "aggs": {
    "all_avg": { "avg": { "field": "price" } },
    "by_brand": { "terms": { "field": "brand" },
      "aggs": {
        "b_avg": { "avg": { "field": "price" } },
        "ratio": { "bucket_script": { "buckets_path": { "b": "b_avg", "all": "all_avg" },
                                     "script": "params.b / params.all" } } } } } }'

buckets_path 里的名字是聚合名，不是字段名——写错会直接报 No aggregation found。

七、常见坑

  1. 忘了 size: 0：白取一堆 _source，聚合结果还混着文档。
  2. pipeline 引用子级聚合：只能引兄弟，跨层引用必然失败。
  3. terms 的 doc_count 当精确值：它是分片 Top N 汇总的近似值。
  4. 桶数超 search.max_buckets：报 too_many_buckets_exception，官方默认 65536。
  5. 对 text 字段聚合：没有 doc_values，需开 fielddata——官方明确不建议。
  6. date_histogram 空桶期望消失：min_doc_count 默认 0，会补空桶。

八、课后小结

  1. 三层：metric 算数、bucket 分组、pipeline 在结果上再算。
  2. bucket 可嵌套，metric 可挂任意层，pipeline 只认兄弟。
  3. 聚合读 doc_values，所以快；桶数爆炸，所以要设上限。
  4. size: 0 是聚合请求的标配。
  5. 看 doc_count_error_upper_bound 判断 terms 结果可不可信。

九、思考题

  1. 一个 terms 下挂 date_histogram，10 个品牌 × 31 天，桶数是多少？会不会撞上限？
  2. 为什么 pipeline 聚合不能直接访问文档？它执行在什么阶段？
  3. 「先过滤再统计」用 query 过滤和用子聚合 filter，结果有区别吗？
