监控与巡检：八个必看指标与一份日巡检清单

监控的目标不是「画一堆曲线」，而是提前发现那四类事故：堆快满、写入被拒、分片未分配、查询延迟飙升。

这一篇给出最小指标集，并说清每个指标「涨了意味着什么」。

配图 48-1｜提示词：一块监控大屏，八个指标卡片排成两行：heap_used_percent、gc 时间、thread_pool rejected、indexing rate、search latency p99、disk used%、unassigned shards、nodes count；每张卡片右上角一个阈值灯（绿/黄/红），下方一条对应「建议动作」文案。深色星空背景，青蓝卡片，阈值灯三色。

一、学习目标

  1. 说出八个必看指标及其阈值逻辑；
  2. 会用 _nodes/stats、_cluster/health、_cat 三件套采集；
  3. 会写一份可执行的日巡检清单；
  4. 知道「指标涨了」与「该做什么」的对应关系。

四、原理拆解：为什么是这八个

ES 的事故路径高度收敛：写入侧先表现为 rejected 上升 → 429；查询侧先表现为延迟 p99 上升 → 超时；资源侧先表现为堆与磁盘逼近阈值；拓扑侧先表现为未分配分片与节点数波动。八个指标正好各覆盖一条路径的「早期信号」。

关键在「早期」：等到 _cluster/health 变 red，已经是事故了。堆到 95% 触发熔断，也是事故。所以阈值要设在能力上限之下——堆 75%、磁盘 85% 才是可操作区间。

六、实操

# 日巡检：一条命令拿到关键数字
curl -s "http://localhost:9200/_cluster/health?pretty" | Select-String -Pattern 'status|number_of_nodes|unassigned_shards|active_shards_percent'
curl -s "http://localhost:9200/_nodes/stats/jvm,thread_pool,indices?pretty" | Select-String -Pattern 'heap_used_percent|rejected|gc_time|indexing'
curl -s "http://localhost:9200/_cat/allocation?v&h=node,shards,disk.used_percent,disk.avail,heap.percent"
curl -s "http://localhost:9200/_cat/indices?v&h=index,health,pri,rep,pri.store.size,docs.count&s=pri.store.size:desc"

# 大索引与段数（段多意味着 merge 落后）
curl -s "http://localhost:9200/goods/_segments?pretty" | Select-String -Pattern 'num_committed_segments|size_in_bytes'

# 如果启用了 Stack Monitoring，可直接看 Kibana 的集群面板

建议把上述命令固化成脚本，每天落一份快照存盘，趋势比瞬时值更有价值。

七、常见坑

  1. 只监控 green/red：等到变红已经晚了。
  2. 堆阈值设 95%：熔断都触发了，监控才报警。
  3. 不看 rejected：把 429 当「偶发网络问题」查半天。
  4. 磁盘阈值与水位设成一样：没有预警窗口。
  5. 把 _cluster/stats 当实时指标：它是快照，趋势要定时采集。
  6. 巡检没有 owner：报表天天生成，没人看。

八、课后小结

  1. 八个指标覆盖写入、查询、资源、拓扑四条路径。
  2. 阈值要设在能力上限之下（堆 75%、磁盘 85%）。
  3. rejected 是背压的最早信号。
  4. 未分配分片是 yellow/red 的入口指标。
  5. 巡检要固化成脚本与趋势，不靠人眼。

九、思考题

  1. 堆 78%、GC 时间上升、查询延迟也涨，你会先动哪一项？
  2. 为什么「磁盘 85%」就报警比「95%」更合理？与水位三档对照说明。
  3. 如果只能监控三个指标，你选哪三个？理由？
