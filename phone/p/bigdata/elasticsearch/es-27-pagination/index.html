ES27-分页四件套

分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

分页四件套：from+size、search_after、scroll、PIT

from=50000 报错、翻到第 3 页就慢了、导出全量数据把集群打挂——这三个问题对应三种不同的分页机制。

它们的差别不在语法，而在「谁来保存位置」：协调节点、客户端、还是集群里的一个搜索上下文。

分页四件套的选择｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说清 from+size 的上限来自哪个设置、默认多少；
  2. 会用 search_after 做无上限的顺序翻页，并知道它需要唯一排序键；
  3. 知道 scroll 的适用场景与「快照语义」；
  4. 会用 PIT + search_after 做一致性深分页。

四、原理拆解：深分页为什么贵

一次 from=10000, size=10 的查询，协调节点要向每个分片索要前 10010 条，再在内存里归并取第 10001–10010 条。分片数 5 就是 5 万条候选文档的排序成本，其中 99.9% 会被丢弃。这就是「越翻越慢」的根因，也是官方设 10000 上限的原因。

search_after 换了个思路：不告诉集群「我要第几页」，而告诉它「从我上次看到的那个值之后继续」。每个分片只需返回排序值大于该游标的前 size 条，成本与页深无关。代价是不能跳页，且排序键必须能唯一定序——否则相同排序值的文档会被跳过或重复。官方推荐用 _shard_doc（配合 PIT 时可用），或自己再加一个唯一字段（如 _id、自增 id）。

scroll 是「快照 + 游标」：第一次请求就把结果集固化在集群里，后续按批取。它不吃内存排序，但会长期占用上下文，keep_alive 到点自动清理。官方文档已把 scroll 定位为「大量文档导出」用途，深分页请用 PIT + search_after。

六、实操

# 1) 打开 PIT（1 分钟有效）
curl -s -X POST "http://localhost:9200/goods/_pit?keep_alive=1m"

# 2) 用 PIT + search_after + _shard_doc 翻页
curl -s -X GET "http://localhost:9200/_search" -H 'Content-Type: application/json' -d '
{ "size": 10,
  "query": { "match": { "title": "跑鞋" } },
  "pit": { "id": "<上一步返回的 id>" },
  "sort": [ { "price": "asc" }, { "_shard_doc": "asc" } ],
  "search_after": [ 199, 0 ] }'

# 3) scroll 导出：首次拿 scroll_id，之后循环
curl -s -X GET "http://localhost:9200/goods/_search?scroll=5m" -H 'Content-Type: application/json' -d '
{ "size": 1000, "query": { "match_all": {} }, "sort": [ "_doc" ] }'

# 4) 只要总数
curl -s -X GET "http://localhost:9200/goods/_count" -H 'Content-Type: application/json' -d '
{ "query": { "term": { "on_sale": true } } }'

search_after 的数组顺序必须与 sort 完全对齐，_shard_doc 只有在使用 PIT 时才允许。

七、常见坑

  1. 以为上限可随意调大：index.max_result_window 可以改，但深分页的内存与延迟问题不会消失。
  2. search_after 排序键不唯一：翻页出现重复或漏文档。
  3. scroll 当实时分页用：它是快照，用户看到的不是最新数据，还占上下文。
  4. 忘了关 scroll 上下文：keep_alive 内不清理会持续占用资源，官方提供 _search/scroll 的 DELETE 清理。
  5. track_total_hits 默认 10000：前端显示「共 12000 条」时其实只知「≥10000」。
  6. search_after 想跳页：机制上不支持，别硬凑。

八、课后小结

  1. from+size 受 max_result_window（默认 10000）限制，深了会慢。
  2. search_after 成本与页深无关，但要求唯一排序键、不能跳页。
  3. scroll 是快照导出，不是实时分页。
  4. PIT 给深分页提供一致视图，_shard_doc 是推荐兜底排序键。
  5. track_total_hits 默认只保证「≥10000」。

九、思考题

  1. 5 分片、from=9990, size=10，协调节点实际要处理多少条候选？为什么？
