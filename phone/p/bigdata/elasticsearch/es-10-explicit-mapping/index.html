显式 mapping 写法：multi-fields、copy_to、doc_values 与那几个开关

上一讲定了「用什么类型」，这一讲定「这个类型开哪些开关」。

同一个 text 字段，加不加 fields、开不开 norms、留不留 positions，直接决定它能搜什么、能排什么、占多少磁盘。这些参数写错了，不报错，只是「能力悄悄没了」。

一个 text 字段的四个开关：fields / index_options / doc_values / norms，各自决定一种能力｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 会用 fields 给一个字段配「搜 + 排 + 聚合」三种能力；
  2. 说清 copy_to 能做什么、官方明确不能做什么；
  3. 知道 index_options 的四个取值各支持什么查询；
  4. 说出 doc_values、norms、index、null_value 四个开关的代价。

四、原理拆解：为什么 text 需要「一个字段三种能力」

搜索引擎对同一个字段有三种诉求，而它们依赖的结构不同：

  • 搜：倒排索引（词条 → 文档），需要分词；
  • 排/聚合：doc values（文档 → 值），要求值可比较、不重复；
  • 精确匹配：整串作为一个词条（keyword 语义）。

一份 text 只能满足第一种。官方给的解法是 multi-fields：主字段 text 管搜，子字段 keyword 管精确匹配与聚合。这也是 Elastic 映射里最常见的结构：

"title": {
  "type": "text",
  "analyzer": "standard",
  "fields": {
    "raw":     { "type": "keyword", "ignore_above": 256 },
    "prefix":  { "type": "text", "analyzer": "edge_ngram_analyzer" }
  }
}

一个字段能挂多个子字段，每个子字段有独立的类型与分析器——这就是「同名字段不同能力」的官方实现方式。

六、实操

curl -X PUT "http://localhost:9200/blog" -H 'Content-Type: application/json' -d '
{
  "settings": { "analysis": {
      "filter": { "edge_ngram_front_2_10": { "type": "edge_ngram", "min_gram": 2, "max_gram": 10 } },
      "analyzer": { "edge": { "type": "custom", "tokenizer": "standard",
                              "filter": ["lowercase", "edge_ngram_front_2_10"] } } } },
  "mappings": { "properties": {
    "title": { "type": "text", "analyzer": "edge", "search_analyzer": "standard",
               "fields": { "raw": { "type": "keyword", "ignore_above": 256 } },
               "copy_to": "all" },
    "body":  { "type": "text", "copy_to": "all" },
    "tags":  { "type": "keyword", "copy_to": "all" },
    "all":   { "type": "text" }
  } }
}'

# 跨字段查询：只对 all 做一次 match
curl -s -X GET "http://localhost:9200/blog/_search" -H 'Content-Type: application/json' -d '
{ "query": { "match": { "all": "Elasticsearch 分词" } },
  "highlight": { "fields": { "body": {} } } }'

注意 edge 分析器的经典搭配：写入用 edge_ngram（生成前缀词条），检索用 standard（把查询词只切一次，否则查询词也会被拆成前缀导致误命中）。这是官方推荐的前缀搜索写法。

七、常见坑

  1. copy_to 当聚合字段用：官方定位是「供查询」，聚合排序请回原字段。
  2. index: false 后还想搜：不建倒排就搜不到，只能 _source 取回。
  3. doc_values: false 后做聚合：直接报错，且重新打开要 reindex。
  4. norms: false 求省空间：打分失去长度归一化，长文与短句分数不可比。
  5. index_options 只留 docs 却要短语查询：没有 positions，match_phrase 失效。
  6. 以为 null_value 能处理「字段缺失」：官方只替换显式 null，缺失字段依然是缺失。
  7. ignore_malformed 到处开：脏数据静默丢失，排查时更难定位。

八、课后小结

  1. fields 是「一字段多能力」的标准解法：搜 text、排聚合 keyword。
  2. copy_to 服务跨字段查询，不服务聚合。
  3. index、doc_values、norms、index_options 四个开关决定能力与体积的取舍。
  4. 前缀搜索的标准搭配是「写入 edge_ngram + 检索 standard」。
  5. 任何开关关掉都要想清楚「以后要不要用」。

九、思考题

  1. 一个字段既要全文检索、又要按它做 terms 聚合、还要支持前缀联想，你会怎么配？说出三个子字段各自的分工。
  2. copy_to 会让索引变大，什么情况下值得用、什么情况下应该改用 multi_match？
  3. 为什么前缀搜索要「写入时 ngram、检索时不分 ngram」？如果两边都 ngram 会发生什么？
