集群健康与诊断：从颜色到 explain，一步一步定位

green / yellow / red 不是三种「心情」，而是三种分片状态。

会读颜色只是第一步，能顺着 _cat 与 explain 找到「为什么这个分片没分配」，才算会运维。

配图 39-1｜提示词：一张诊断流程图，起点 GET _cluster/health 分出三条颜色分支：green（全部主副就位）、yellow（主齐、副本缺失）、red（存在未分配主分片）。yellow/red 分支汇入 GET _cat/shards 与 GET _cluster/allocation/explain，再分叉出四种原因标签：磁盘水位、分配过滤、节点未加入、分片数超限。深色星空背景，青绿/琥珀/红三色状态。

一、学习目标

  1. 准确解释三种健康状态各自的含义；
  2. 会用 _cat/shards、_cat/allocation、_cluster/stats 做初步排查；
  3. 会用 allocation/explain 拿到「未分配的具体原因」；
  4. 记住 wait_for_status 的用法与限制。

四、原理拆解：yellow 不是故障

副本的作用是容灾与读扩展。副本没分配，集群仍能读写，只是「丢一台机器就可能丢数据」。所以官方把 yellow 定义为「健康但降级」，不需要紧急处理，但需要知道原因——常见三种：只有一个节点（副本不能与主分片同节点）、磁盘水位把分片挡住、分配过滤把节点排除了。

red 才是真问题：主分片没分配，说明数据不可用。此时 allocation/explain 会直接告诉你 unassigned_info.reason，比如 NODE_LEFT、ALLOCATION_FAILED、CLUSTER_RECOVERED——不同 reason 对应完全不同的处置（等节点回来 / 强制分配 / 恢复快照）。

wait_for_status=yellow 是部署脚本常用参数：等了指定超时才返回，用来「确保索引可读写后再启动应用」。但它只等到 yellow，不代表副本已就绪。

六、实操

# 1) 总览
curl -s "http://localhost:9200/_cluster/health?pretty"

# 2) 哪些分片没分配
curl -s "http://localhost:9200/_cat/shards?v&h=index,shard,prirep,state,node,unassigned.reason" | Select-String -Pattern 'UNASSIGNED'

# 3) 节点与磁盘
curl -s "http://localhost:9200/_cat/allocation?v"

# 4) 未分配原因（最关键）
curl -s -X GET "http://localhost:9200/_cluster/allocation/explain?pretty" -H 'Content-Type: application/json' -d '
{ "index": "goods", "shard": 0, "primary": true }'

# 5) 脚本里等就绪
curl -s "http://localhost:9200/_cluster/health?wait_for_status=yellow&timeout=30s"

七、常见坑

  1. yellow 就报警：单节点集群天生 yellow，副本无处放。
  2. red 直接删索引：先 explain 看 reason，很多情况能救回来。
  3. 只看 health 不看 _cat/shards：不知道具体哪个分片、哪个节点。
  4. wait_for_status=green 卡死：副本永远凑不齐时脚本会一直等。
  5. 忽略 unassigned.reason：这是官方给出的第一手线索。
  6. 把 _cluster/stats 当实时监控：它偏「当前快照」，趋势要看监控系统。

八、课后小结

  1. green 全就位；yellow 主齐副本缺（可读写）；red 主分片缺失（不可用）。
  2. _cat/shards 看单分片，_cat/allocation 看磁盘与分布。
  3. allocation/explain 是排查未分配的第一入口。
  4. wait_for_status 用于启动就绪检查，不保证副本齐。
  5. 不同 unassigned_info.reason 处置方式完全不同。

九、思考题

  1. 3 节点集群、副本数 1，出现 yellow 说明什么？副本数改成 2 会怎样？
  2. unassigned_info.reason 为 NODE_LEFT 与 ALLOCATION_FAILED，处置差别在哪？
  3. 为什么 wait_for_status=green 在自动化部署里容易变成「永久等待」？
