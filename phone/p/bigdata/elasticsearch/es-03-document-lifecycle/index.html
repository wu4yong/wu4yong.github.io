ES03-从 REST 请求到能被搜到

分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 全文检索 · 系统课

一条数据的完整旅程：从 REST 请求到能被搜到

这一讲把「写入」和「检索」两条路走一遍，走完你会得到一个可以解释 80% 线上疑问的模型：为什么写完要等 1 秒、为什么 GET 能立刻读到、为什么搜索要分两个阶段、为什么分片多会长尾。

深挖（translog 细节、段合并策略、bulk 背压）留给 M3，这一讲只建骨架。

写入与检索两条路径：写入只管「持久化」，能否被搜到取决于 refresh（默认 1s）；检索分 query、fetch 两阶段｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说出一条写入请求经过哪些组件、在哪个环节被复制、什么时候向客户端返回成功；
  2. 说清 refresh、flush、merge 各自动作的对象，以及「写完为什么搜不到」的确切环节；
  3. 解释「GET _doc 能立刻读到，但 _search 读不到」为什么不矛盾；
  4. 讲清两阶段检索（query phase / fetch phase）的含义，以及分片数为何影响长尾耗时；
  5. 会读 _search 返回里的 _shards 结构，判断是部分失败还是正常跳过。

三、理论讲解：官方对这两个动作的定义

3.1 写入：先落主分片，再同步到副本

写入的入口永远是「任意一个节点」，它在这一跳里充当协调节点（coordinating node）。协调节点先算路由：

shard = hash(routing) % number_of_primary_shards

_routing 默认取文档 _id。这条公式解释了一个经典限制：主分片数不能改——改了公式结果就变，老文档会「找不到自己的家」。

请求落到目标主分片后，主分片做两件事：写内存缓冲区（buffer）与事务日志（translog），然后把操作同步复制到该分片的副本。官方《Reading and writing documents》把这套机制称为同步复制：主分片要等到副本确认（在 wait_for_active_shards 要求的份数内）之后，才向客户端返回成功。所以「返回 201」意味着这份数据已经在至少一份（通常两份）分片拷贝上落地，但尚未可被搜索。

3.2 可搜索：一次 refresh 才生效

官方 Refresh API 的原话只有一句，但它定义了整条时序：

A refresh makes recent operations performed on one or more indices available for search.

——Elastic 官方文档《Refresh API》

机制上，refresh 做的是：把内存缓冲区里积累的文档写成一份新的 Lucene 段（segment），并让搜索引擎能看到它。默认 index.refresh_interval 是 1s，所以「写入 → 可见」的延迟是 0 到 1 秒之间的随机值，而不是固定 1 秒。

3.3 读回：GET _doc 为什么不用等

按 ID 取文档走的是 GET API，它默认按实时语义读：直接从 translog 与段里定位那条记录，不依赖 refresh 打开的新段。所以会出现这个看似矛盾的现象——

PUT  /books/_doc/2      → 201，立即
GET  /books/_doc/2      → 立刻能读到
GET  /books/_search     → 1 秒窗口内可能搜不到

「能按 ID 读到」和「能被检索到」是两条不同的通道，M1-1 说过的 NRT 只约束后者。

四、原理拆解：检索为什么分两个阶段

一次 _search 的执行顺序：

  1. query phase：协调节点把查询广播到索引涉及的每个分片（主或副本，任选其一）；每个分片在本分片内执行查询、打分，返回「候选文档的 docId + score」，不返回原文；
  2. 归并：协调节点把所有分片返回的候选全局排序，取出前 from + size 条；
  3. fetch phase：协调节点按 docId 回到对应分片取 _source 与高亮等字段；
  4. 组装返回：拼成最终 JSON。

两个由此推出的硬结论：

  • 打分是分片内局部完成的。各分片只知道自己分片内的词频统计，所以跨分片分数不能严格比较；要让全局 IDF 一致必须用 dfs_query_then_fetch（代价是多一轮请求）。
  • 耗时受最慢分片支配（长尾）。协调节点必须等所有目标分片回话才能归并，分片越多、单分片越慢，整体越容易被拖住。

_search 返回里的 _shards 就是这件事的现场记录：

"_shards": { "total": 5, "successful": 5, "skipped": 0, "failed": 0 }

skipped 是「因查询条件不可能命中而被跳过」的正常优化（例如按时间范围过滤掉了整个分片），不是失败；只有 failed > 0 才是部分分片出错（默认这类请求仍返回 200，容易漏看）。

六、实操：亲手观测这条链路

# 1) 写入，观察返回里的 _shards 与 result
curl -X PUT "http://localhost:9200/books/_doc/3" -H 'Content-Type: application/json' -d '
{ "title": "链路观测", "author": "wu4yong", "price": 59.0, "publish_date": "2023-10-02", "tags": ["observe"] }'

# 2) 立刻按 ID 读：应当成功（实时通道）
curl -s "http://localhost:9200/books/_doc/3"

# 3) 立刻搜索：可能搜不到（refresh 窗口）
curl -s -X GET "http://localhost:9200/books/_search?track_total_hits=true" \
  -H 'Content-Type: application/json' -d '{ "query": { "match": { "author": "wu4yong" } } }'

# 4) 强制刷新后必能搜到
curl -s -X POST "http://localhost:9200/books/_refresh"
curl -s -X GET "http://localhost:9200/books/_search" -H 'Content-Type: application/json' -d '
{ "query": { "match": { "author": "wu4yong" } }, "_source": ["title","price"] }'

# 5) 用 wait_for 让写入自己等刷新（批量校验场景更合适）
curl -X PUT "http://localhost:9200/books/_doc/4?refresh=wait_for" -H 'Content-Type: application/json' -d '
{ "title": "wait_for 观测", "author": "wu4yong", "price": 39.0 }'

第 4 步注意 _source 过滤：只取需要的字段能显著减少 fetch 阶段的传输量（M4-9 细讲）。

七、常见坑（每条都有官方依据）

  1. 把「写完立刻搜不到」当 bug：refresh 默认 1s，这是官方设计上的 near real time。
  2. 每条写入都带 refresh=true：每次强制刷新都生成新段，段越多检索越慢；官方明确只建议在测试/校验场景使用。
  3. 把 flush 当成「让文档可搜索」：flush 管的是持久化与 translog 清理，可搜索是 refresh 的事。
  4. 看 _shards.successful 就以为没失败：skipped 是正常优化，真正的失败要看 failed。
  5. 用协调节点当 master 用：任何节点都能协调，master 只管集群状态，两者职责不同（M6-1）。
  6. 以为副本能分担「写」：写入只落主分片，副本同步复制；副本增加的是读并发与容灾（M6-2）。
  7. from + size 翻深页：官方上限 index.max_result_window 默认 10000，超过直接报错。

八、课后小结

  1. 写入路径：协调节点 → 路由到主分片 → buffer + translog → 同步复制到副本 → 返回。
  2. 一条文档「能被搜到」需要经过 refresh，默认每 1s 一次。
  3. GET _doc 走实时通道，不受 refresh 约束，所以会和 _search 表现不一致。
  4. 检索是 query phase + fetch phase 两阶段，打分在分片内完成、再全局归并。
  5. 分片数量决定长尾风险，耗时由最慢分片决定。
  6. _shards.skipped 不是错误，failed 才是。

九、思考题

  1. 一条写入已经返回 201，但此时节点断电，数据还在吗？请把这个问题的答案和时间轴（buffer / translog / flush）对上。
  2. 为什么官方要把「写入」和「可搜索」拆成两步？如果强行做成「写即可搜」，代价是什么？
  3. 一个索引有 20 个分片，检索 P99 明显高于平均。你会从哪三个方向排查长尾？
  4. GET _doc 的实时语义与副本同步复制之间有没有冲突？举一个可能读到旧数据的场景并说明原因。
