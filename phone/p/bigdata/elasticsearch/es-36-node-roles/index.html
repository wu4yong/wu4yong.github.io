ES36-节点角色

分类：bigdata · elasticsearch ｜ 标签：系统课 · Elasticsearch

节点角色与集群形态：把一台机器拆成合适的角色

一个节点该干什么，由 node.roles 决定。

生产集群出问题，很多不是「资源不够」，而是「角色摆错了位置」——比如让同一个节点既当 master 又扛全部数据写入。

集群形态与角色划分，以及索引沿 ILM 向下的流动｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 记住常用节点角色及其职责边界；
  2. 知道 node.roles 未配置时的默认行为；
  3. 会为「开发单机 / 小型生产 / 分层集群」三种形态选角色；
  4. 说清 master 节点为什么要奇数、为什么要独立。

默认行为：不显式配置 node.roles 时，节点会承担它满足条件的所有角色（官方 Node roles 文档）。这意味着开发机上「什么都是」，而生产上你可能想要「什么都不是」的纯协调节点——必须显式写 node.roles: []。

四、原理拆解：为什么 master 要独立且奇数

master 只做元数据决策（集群状态、分片分配），负载极轻，但要求稳定：一旦 master 抖动，整个集群的分片分配就会暂停或反复重算。所以官方建议 master 节点不承担 data 角色——数据节点一次 GC 停顿就可能把 master 拖掉线。

奇数是因为选举要「多数票」：3 个 master-eligible 能容忍 1 个掉线，5 个能容忍 2 个，偶数（如 4）容忍度与 3 相同却多花一台机器，没有收益。

splitting the brain（脑裂）在 7.0 之后由「多数票选举 + 自动最小 master 数」机制消除，不再需要手工配置 minimum_master_nodes（这个参数已被移除）。

六、实操

# 查看每个节点的角色
curl -s "http://localhost:9200/_cat/nodeattrs?v"
curl -s "http://localhost:9200/_nodes?filter_path=nodes.*.roles"

# elasticsearch.yml：独立 master（不存数据、不做 ingest）
# node.name: master-1
# node.roles: [ master ]
#
# elasticsearch.yml：热数据节点
# node.name: data-hot-1
# node.roles: [ data_hot, data_content ]
#
# elasticsearch.yml：纯协调节点
# node.name: coord-1
# node.roles: []

node.roles 是静态设置，改完必须重启节点；它不是动态可调的集群设置。

七、常见坑

  1. 以为不配 node.roles 就「只做协调」：默认会承担所有满足条件的角色。
  2. master 与 data 混布在大集群：GC 抖动引发选举，集群反复 rebalance。
  3. master 节点数为偶数：容忍度没提升，浪费机器。
  4. voting_only 当 master 用：它只投票，不能被选为 master。
  5. 纯协调节点忘了 node.roles: []：结果它也在存数据。
  6. 改角色不重启：node.roles 静态生效，热改无效。

八、课后小结

  1. node.roles 决定职责，未配置时承担所有适合的角色。
  2. master 只做元数据决策，生产应独立、奇数、不混 data。
  3. data_* 分层配合 ILM，冷热分离才落地。
  4. voting_only 只投票不参选。
  5. 纯协调节点要显式 node.roles: []。

九、思考题

  1. 3 台机器的生产集群，你会选「3 master + 3 data 混布」还是「3 master + 2 data + 1 协调」？理由？
  2. master 节点为什么不怕「查询压力大」，只怕「GC 停顿」？
  3. voting_only 在什么场景下有用？举一个具体集群规模。
