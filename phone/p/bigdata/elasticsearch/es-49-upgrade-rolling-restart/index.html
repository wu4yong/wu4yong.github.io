ES49-升级与滚动重启

分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

升级与滚动重启：把「不能停」变成「几乎不停」

滚动重启的正确姿势是：先冻结分片分配、停写入、刷盘、再逐台重启、最后解冻。少了任何一步，你会看到「重启一台，全集群搬了 200GB 分片」。

升级还多两条硬约束：不能跨 major 直达，且必须先验 deprecations。

配图 49-1｜提示词：一条六步流程箭头链：1 关闭分片分配（primaries） → 2 停止写入 + flush → 3 停一台节点并升级 → 4 启动并等它加入 → 5 逐台重复 → 6 恢复分配（all）；链条上方标注「期间保持副本可用、集群为 yellow 不报警」，下方一条副流程标升级顺序：minor 滚动升级 与 major 必须逐级 + 快照。深色星空背景，青蓝箭头，琥珀步骤号。

一、学习目标

  1. 背出滚动重启的六步顺序；
  2. 说清「先关分配」为什么能省掉几百 GB 迁移；
  3. 知道跨 major 升级的限制与前置检查；
  4. 会用 _migration/deprecations 与迁移文档做升级预检。

四、原理拆解：为什么第 1 步能省掉大规模迁移

节点停机时，master 会认为它的分片「没主了」，于是把副本提升为主，并在其他节点上重建副本——一次重启搬走几十上百 GB。把 allocation.enable 设为 primaries 后，master 只关心主分片是否有着落，不会为新主分片创建副本，于是搬迁量骤减。等所有节点都回来了，再设回 all，集群自己补齐副本。

第 2 步 _flush 的意义在于：重启后节点要靠 translog 恢复未刷盘的数据，刷过盘就意味着恢复只需加载段文件，启动快、恢复期短。

六、实操

# 1) 冻结分配（只允许主分片）
curl -s -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d '
{ "persistent": { "cluster.routing.allocation.enable": "primaries" } }'

# 2) 停写入 + 刷盘
curl -s -X POST "http://localhost:9200/_flush"

# 3) 升级前置检查：弃用点
curl -s "http://localhost:9200/_migration/deprecations?pretty"

# 4) 重启并确认回归（节点数、健康、未分配）
curl -s "http://localhost:9200/_cat/nodes?v&h=name,node.role,master"
curl -s "http://localhost:9200/_cluster/health?pretty"

# 5) 全部节点回来后恢复分配
curl -s -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d '
{ "persistent": { "cluster.routing.allocation.enable": "all" } }'

注意 persistent 与 transient 的区别：transient 在集群重启后失效，做长期设置请用 persistent。

七、常见坑

  1. 不关分配就逐台重启：全集群反复搬分片，IO 打满。
  2. 忘记把 enable 设回 all：副本永远补齐不了，长期 yellow。
  3. 升级前不打快照：出问题时没有回退路径。
  4. 跨 major 直接升：官方不支持，索引可能无法打开。
  5. 先升 master 节点：选举真空期，集群状态反复。
  6. 升级后不看 deprecations 与日志：把新版本告警带进下一轮。

八、课后小结

  1. 六步：关分配 → 停写刷新 → 逐台停机 → 启动确认 → 重复 → 恢复分配。
  2. primaries 模式让重启期间几乎不搬分片。
  3. 跨 major 不支持直接滚动，先看官方 Upgrade 文档。
  4. 升级前必做：快照 + _migration/deprecations + 插件盘点。
  5. persistent 设置才是长期生效。
