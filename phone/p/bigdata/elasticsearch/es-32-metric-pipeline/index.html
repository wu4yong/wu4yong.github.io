metric 与 pipeline 聚合：近似指标、占比与排序截断

平均数、去重数、百分位——三个看起来最普通的统计

前两个在分布式下都是近似值，只有你知道它们近似到什么程度，报表才敢上线。

metric 的近似性与 pipeline 处理顺序｜依据 Elasticsearch 官方文档 8.17 自绘

pipeline 常用四种：bucket_script（按公式算）、bucket_selector（按条件删桶）、bucket_sort（排序并截断）、derivative / cumulative_sum（差分与累计）。gap_policy 默认 skip（遇到空桶跳过），另一值是 insert_zeros。

四、原理拆解：为什么去重计数必须近似

精确去重要把每个不同的值都记下来，基数上百万时内存直接崩。HyperLogLog 用固定大小的寄存器做概率估算：precision_threshold 越大，精度越高、内存越大；官方给的上限是 40000，超过部分精度不再提升。默认 3000 意味着「基数远大于 3000 时误差约在个位数百分比」。

percentiles 用 TDigest 草图，误差集中在尾部；P99 这种极端分位数在数据量小或不均衡时波动明显。要精确分位数，只能把全部值取回本地算——这是工程取舍。

顺带说一个实用技巧：bucket_sort 是「官方支持的 Top N 截断」，比先取回 100 个桶再自己排序省得多。

六、实操

# 精确 + 近似指标混合
curl -s -X GET "http://localhost:9200/orders/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": {
    "amount_stats": { "extended_stats": { "field": "amount" } },
    "amount_pct":  { "percentiles": { "field": "amount", "percents": [50, 90, 99] } },
    "uv":          { "cardinality": { "field": "user_id", "precision_threshold": 1000 } } } }'

# bucket_sort：按销售额取前 5
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": {
    "by_brand": { "terms": { "field": "brand", "size": 100 },
      "aggs": { "sales": { "sum": { "field": "amount" } },
                "top5": { "bucket_sort": { "sort": [ { "sales": { "order": "desc" } } ], "size": 5 } } } } } }'

# bucket_selector：过滤小桶
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": {
    "by_brand": { "terms": { "field": "brand", "size": 100 },
      "aggs": { "cnt": { "value_count": { "field": "sku" } },
                "keep": { "bucket_selector": { "buckets_path": { "c": "cnt" }, "script": "params.c >= 10" } } } } } }'

bucket_selector 的脚本必须返回布尔值，返回数字会被当成「真值」而悄悄放行——这是很难查的一类错。

七、常见坑

  1. cardinality 当精确 UV：默认 precision_threshold 3000，结果本身带误差。
  2. percentiles 在小样本上算 P99：尾部波动极大，业务会质疑数据。
  3. bucket_selector 脚本返回数字：语义上要求布尔，写 params.c >= 10 而不是 params.c。
  4. bucket_sort 与 terms.size 混淆：前者截断桶，后者限制候选，两者要配合。
  5. gap_policy 不设就做累计：空桶被 skip 掉，累计曲线会「跳档」。
  6. top_hits 取太多：每个桶都带原始文档，响应体会很大。

八、课后小结

  1. avg/sum/min/max/value_count/stats 精确；cardinality/percentiles 近似。
  2. precision_threshold 默认 3000、上限 40000。
  3. pipeline 四种：算、筛、排、差分/累计。
  4. buckets_path 写聚合名，不写字段名。
  5. bucket_sort 是官方推荐的 Top N 截断方式。

九、思考题

  1. 业务要「精确 UV」，你会用什么方案替代 cardinality？代价是什么？
  2. bucket_sort 截断到 5 个桶后，hits.total 会变吗？为什么？
  3. gap_policy: skip 在做「日环比」时会带来什么异常？怎么规避？
