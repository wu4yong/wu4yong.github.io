高亮、suggest 与 _msearch：搜索框的三件配套

用户看得见的「搜索体验」由三样东西撑着：结果里的红色高亮、输入时的自动补全与纠错、以及一次请求打完多个查询。

它们都比主查询轻，但各有各的开关和前置条件。

高亮、suggest 与 _msearch｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 会用 highlight 的三种 type 与常用参数；
  2. 知道高亮为什么需要 offsets / term_vector；
  3. 区分 term / phrase / completion 三种 suggester 的用途；
  4. 会用 _msearch 一次批量提交多组查询。

四、原理拆解：高亮是怎么知道该染哪几个字的

高亮不是重新分词一遍原文，而是靠索引里记录的偏移量：index_options: offsets（unified/plain 需要）或 term_vector: with_positions_offsets（fvh 需要）。有了字符起止位置，高亮器才能在原文上切一段包上 <em>。

所以「能搜到但不高亮」的典型原因是：字段没开 offsets、或 require_field_match 把非查询字段的染色禁掉了。fvh 在字段很长、只需要少量片段时性能更好，但要求更重的 term vector 存储。

completion suggester 不是查倒排，而是走一套专门为「前缀自动补全」优化的数据结构（FST），因此必须把字段显式设成 completion 类型，且它只做前缀/模糊补全，不做相关性排序。

六、实操

# 高亮
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "query": { "match": { "title": "跑鞋" } },
  "highlight": { "fields": { "title": {} }, "pre_tags": ["<em class=\"hl\">"], "post_tags": ["</em>"] } }'

# term suggest 纠错
curl -s -X POST "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "suggest": { "my": { "text": "runnign shoe", "term": { "field": "title" } } } }'

# completion 补全（字段需为 completion 类型）
curl -s -X POST "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "suggest": { "s": { "prefix": "跑", "completion": { "field": "suggest", "skip_duplicates": true } } } }'

# _msearch：header 行 + body 行，逐对排列
curl -s -X POST "http://localhost:9200/_msearch" -H 'Content-Type: application/x-ndjson' --data-binary $'
{"index":"goods"}
{"query":{"match":{"title":"跑鞋"},"size":3}
{"index":"shops"}
{"query":{"match":{"name":"跑鞋"},"size":3}
'

最后一条的末尾换行别省，_msearch 与 _bulk 一样按 NDJSON 解析。

七、常见坑

  1. 字段没开 offsets 还等高亮：unified 拿不到位置，染色失败或只染整段。
  2. require_field_match 默认 true：只想在 title 过滤却在 body 高亮，必须显式设 false。
  3. fvh 不配 term_vector：直接报错，这是官方硬约束。
  4. completion 字段用普通 keyword 建：类型不对，suggest 无法执行。
  5. _msearch 少写 header 行或末尾无换行：整包解析失败。
  6. _msearch 塞几百条：单请求负载过大，建议分包。

八、课后小结

  1. 高亮依赖 offsets（unified/plain）或 term vector（fvh）。
  2. require_field_match 决定「非查询字段能不能染色」。
  3. term/phrase suggester 做纠错，completion 做前缀补全，用途不同。
  4. _msearch 用 NDJSON 成对提交，一次拿回 responses 数组。
  5. 这三样都是「体验配套」，别让它们拖慢主查询。

九、思考题

  1. 同样的 match 查询，一个字段能高亮、另一个不能，可能的两条原因是什么？
  2. completion suggester 为什么不做相关性打分？它的数据结构决定了什么？
  3. 前端要「首页 6 个模块各一屏数据」，用 6 次请求还是 1 次 _msearch？权衡点在哪？
