中文分析：官方插件的边界与第三方分词的取舍

中文是 Elasticsearch 上最容易「看起来能用、实际不好用」的一块。

默认 standard 分析器会把中文切成单字，于是「系统课」变成「系」「统」「课」三个词条——查得到，但召回和精度都糟糕。这一讲把官方给出的中文方案说清，并把第三方插件的边界划出来。

同一句中文的三种切分：官方内置分析器不含中文分词器，中文业务需要 smartcn / ICU 或第三方方案｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说清为什么 standard 对中文是单字切分，以及它的后果；
  2. 列出官方提供中文能力的两个插件，并说清各自定位；
  3. 明确第三方分词（如 ik）在「官方依据」上的位置——它是社区插件，不在官方支持范围；
  4. 会装插件、验证切词效果、并给出选型结论。

关于 ik 要说清楚：它是社区插件，官方文档没有覆盖。这不代表不能用（很多生产系统在用），但它带来两个额外责任：版本兼容自行验证、词典与分词效果自行负责。写作规则里「官方唯一权威」，指的就是这类边界必须标注。

四、原理拆解：为什么单字切分会拖垮检索质量

倒排表里如果是单字，那么：

  1. 召回爆炸：搜「课程」会命中所有含「课」或「程」的文档；
  2. 打分失真：BM25 认为「课」这个单字很常见，于是相关性被稀释；
  3. 短语查询代价高：要表达「系统课」必须用 match_phrase 并依赖位置信息。

按词切分则相反：词条更具体，match 的精度自然上来，代价是词典覆盖不到的新词会「查不到」（比如产品型号、网络新词）。这就是中文分词的经典取舍：召回与精度不可兼得，只能调平衡。

六、实操：装插件、验切词、配字段

# 1) 安装官方插件（容器环境；版本必须与 ES 一致）
docker exec -it es01 bin/elasticsearch-plugin install analysis-smartcn
docker restart es01

# 2) 验证切分
curl -s -X POST "http://localhost:9200/_analyze" -H 'Content-Type: application/json' -d '
{ "analyzer": "smartcn", "text": "时空秘境系统课程" }'

# 3) 建索引并挂到字段（索引级定义，字段引用）
curl -X PUT "http://localhost:9200/zh_docs" -H 'Content-Type: application/json' -d '
{ "settings": { "analysis": {
    "analyzer": { "zh": { "type": "custom", "tokenizer": "smartcn_tokenizer",
                          "filter": ["lowercase"] } } } },
  "mappings": { "properties": {
    "title":   { "type": "text", "analyzer": "zh" },
    "content": { "type": "text", "analyzer": "zh" },
    "code":    { "type": "keyword" } } } }'

# 4) 对比：同一句在 standard 与 zh 下的切分差异
curl -s -X POST "http://localhost:9200/zh_docs/_analyze" -H 'Content-Type: application/json' -d '
{ "field": "title", "text": "时空秘境系统课程" }'

第 4 步做完你会直观看到词条数量从 8 个降到 4 个左右——这就是召回收窄、精度提升的来源。

七、常见坑

  1. 以为默认就支持中文分词：standard 是单字切，官方从不承诺中文词级切分。
  2. 插件版本与 ES 不一致：官方要求严格对齐，错位会启动失败。
  3. 给 keyword 字段配中文分析器：keyword 不分词，配了也不生效。
  4. 混用不同分析器写读：写入 smartcn、检索 standard，词条对不上，必然漏搜。
  5. 把第三方插件当官方能力引用：文档、培训材料里必须标注来源，否则出问题无人背书。
  6. 词典不更新：行业新词半年不补，搜索质量会明显下滑。

八、课后小结

  1. standard 对中文是单字切分，召回高、精度低。
  2. 官方中文能力来自 analysis-smartcn 与 analysis-icu 两个插件，需手动安装且版本严格对齐。
  3. 第三方分词（ik 等）可用，但不在官方支持范围，需自行验证兼容与效果。
  4. 写入与检索必须用同一分析器。
  5. 精确匹配字段一律 keyword。

九、思考题

  1. 用户反馈「搜『课程』出来一堆含『课』的文章」，你会先改分析器还是先改查询？为什么？
  2. 一个中英混排的技术文档库，你会选 smartcn 还是 icu？给出判断依据与验证方法。
  3. 引入第三方分词后，如何证明「效果确实更好」？设计一个可复现的评测办法。
