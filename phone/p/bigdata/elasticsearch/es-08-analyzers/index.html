ES08-分析器三段式

分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

分析器三段式：字符过滤、分词、词条过滤

「搜不到」里有一半根本不是查询写错，而是写入时切成了 A，检索时又切成了 B。

分析器就是干这件事的：把一段文本切成词条，再对词条做归一化。这一讲把官方三段结构拆开，并教你用 _analyze 把问题当场验证出来。

analyzer 的三段流水线：character filter → tokenizer → token filters；normalizer 是 keyword 字段的轻量替代｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 记住分析器的官方三段结构，并能说出每段能做什么、不能做什么；
  2. 会用 _analyze API 验证「写入链路」与「检索链路」是否一致；
  3. 分清 analyzer、search_analyzer、normalizer 三者的适用对象；
  4. 说出自定义分析器在索引建好后为何改不动。

三、理论讲解（官方定义）

An analyzer — whether built-in or custom — consists of a tokenizer, optionally preceded by zero or more character filters and optionally followed by zero or more token filters.

——Elastic 官方文档《Text analysis》

三段各管一件事：

段
数量
输入到输出
典型用途
char filter
0 个或多个
原始字符串 → 处理后的字符串（不分词）
去 HTML 标签、&→and、正则替换
tokenizer
恰好 1 个
字符串 → 词条流（分词 + 记录位置）
standard、whitespace、keyword、pattern、ICU
token filter
0 个或多个
词条流 → 词条流
小写、停用词、词干、同义词、ngram

内置分析器多数是这三段的预设组合。常用的几个：

分析器
行为
适用
standard（默认）
Unicode 文本分段 + 小写，去标点
通用；中文会按单字切
simple
只按字母切、转小写
纯英文、干净文本
whitespace
只按空格切，不做任何过滤
精确保留原词形
keyword
整段当一个词条
与 keyword 字段搭配（其实等于不分词）
stop
类似 simple + 去停用词
英文检索
pattern
用正则切分
日志、结构化文本

关键点：写入（index time）与检索（search time）各用一次分析器。官方默认让检索复用字段的 analyzer；一旦你只改了 analyzer 而给 search_analyzer 留了别的值，两边切法不同，就会「明明有这个词却搜不到」。

四、原理拆解：一次查询到底分析了几次

以 match 查询 "Running Dogs" 打 title（standard 分析器）：

  1. 检索侧：对 Running Dogs 分词 → [running, dogs]；
  2. 拿这两个词条去倒排表查；
  3. 写入侧当初也是同样切法，所以能对上。

若写入时用了 keyword（整串一个词条 Running Dogs），检索时用 standard（切成两个词条），永远搜不到——这就是「analyzer 与 search_analyzer 不一致」的后果，也是最常见的隐性 bug。

六、实操：先验证，再改配置

# 1) 直接看标准分析器怎么切
curl -s -X POST "http://localhost:9200/_analyze" -H 'Content-Type: application/json' -d '
{ "analyzer": "standard", "text": "Running Dogs, THE 2nd!" }'

# 2) 看某个字段实际用的分析器（以 mapping 为准）
curl -s -X POST "http://localhost:9200/goods/_analyze" -H 'Content-Type: application/json' -d '
{ "field": "title", "text": "Running Dogs 跑鞋" }'

# 3) 自定义分析器并挂到字段
curl -X PUT "http://localhost:9200/goods2" -H 'Content-Type: application/json' -d '
{ "settings": { "analysis": {
    "filter": { "my_stop": { "type": "stop", "stopwords": ["the","a","an"] } },
    "analyzer": { "my_en": { "type": "custom", "tokenizer": "standard",
                             "filter": ["lowercase","my_stop","porter_stem"] } } } },
  "mappings": { "properties": { "title": { "type": "text", "analyzer": "my_en" } } } }'

第 2 步是排障核心动作：永远先看字段真实生效的分析器，再讨论为什么搜不到。

七、常见坑

  1. 只配 analyzer 不管 search_analyzer：两边切法不一致，直接搜不到。
  2. 给 keyword 字段配 analyzer：无效，keyword 不分词；要归一化用 normalizer（支持 lowercase、asciifolding 等）。
  3. 自定义分析器建完索引再改：官方不允许在已有数据上随意改分析器，改了要 reindex 重灌。
  4. 停用词用错地方：对「精确匹配型号」的字段去停用词，会把有意义的字符删掉。
  5. 词条超长：官方 index.max_token_length 默认 255，超长词条被截断或丢弃，正文类字段要注意。
  6. 把 _analyze 当查询用：它只返回分词结果，不参与检索。

八、课后小结

  1. 分析器 = char filter（可选）+ tokenizer（恰好一个）+ token filter（可选）。
  2. 写入与检索各分析一次，两边必须一致，search_analyzer 是关键开关。
  3. _analyze 是排障第一步，先看真实切法再谈查询。
  4. keyword 不分词，归一化靠 normalizer。
  5. 分析器改动基本等于「重建索引」。
