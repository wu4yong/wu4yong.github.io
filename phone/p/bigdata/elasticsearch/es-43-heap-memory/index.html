堆、内存与 bootstrap checks：为什么节点起不来

一台机器内存 128GB，堆给 120GB？节点会起来，然后每隔几小时 GC 停一次。

堆的边界不是「机器有多大」，而是两件事：给文件系统缓存留一半、别越过 compressed oops 的门槛。

堆比例、32GB 线与三条 bootstrap checks｜依据 Elasticsearch 官方文档 8.17 自绘

四、原理拆解：bootstrap checks 为什么只在「生产模式」才拦你

官方把检查分两档：开发模式只 warn，生产模式直接 fail。生产模式的判定条件是「节点绑定了非回环地址」或「设了 discovery.seed_hosts 等集群发现配置」——也就是说，一旦你打算组集群，检查就变成硬门槛。

这解释了最常见的困惑：「本机跑得好好的，换到服务器就起不来」。不是配置错了，是触发了 bootstrap checks，其中高频三项：

# sysctl -w vm.max_map_count=262144
# echo "vm.max_map_count=262144" >> /etc/sysctl.conf

# 关闭 swap
# swapoff -a ; 并在 /etc/fstab 注释 swap 行

# jvm.options 里固定堆
# -Xms31g
# -Xmx31g

Windows 开发机上没有 vm.max_map_count 这套检查，这也是「本地能跑、服务器起不来」的另一个来源。

七、常见坑

  1. Xms 与 Xmx 不一致：运行中扩堆，引发长停顿。
  2. 堆超过 32GB：compressed oops 失效，实际可用内存下降。
  3. 堆占满内存：没有页缓存，查询延迟升高。
  4. swap 没关：GC 期间页面换出，停顿从毫秒级跳到秒级。
  5. 只改 jvm.options 不改 systemd：LimitMEMLOCK 没放开，锁定失败。
  6. 以为 bootstrap checks 是「建议」：生产模式直接 fail 启动。

八、课后小结

  1. 堆 ≤ 内存 50%，且 ≤ 32GB。
  2. Xms 与 Xmx 设为相同值。
  3. 生产模式触发 bootstrap checks，不是建议而是硬门槛。
  4. vm.max_map_count ≥ 262144、swap 关闭、内存锁定三项高频。
  5. 大内存机器宁可拆节点，也别把堆开大。
