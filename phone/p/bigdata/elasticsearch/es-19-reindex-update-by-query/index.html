在线迁移：reindex 与 _update_by_query 的正确姿势

M2-7 给了迁移流程

这一讲把执行细节补齐：_reindex 到底怎么搬数据、为什么它「搬不全」、slices 与 conflicts 该怎么用、以及怎么判断一次迁移真的成功。

slices 并行灌入 v2，之后的写入不会自动同步｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说清 _reindex 的三个关键参数：source.query、dest.op_type、slices；
  2. 解释「reindex 用快照语义」带来的增量缺口；
  3. 会用 _tasks 观察进度，用返回的 failures/version_conflicts 判定成败；
  4. 分清 _reindex 与 _update_by_query 该用哪个。

要点：_reindex 不复制 settings 与 mapping，只搬文档；且它对源索引取的是快照语义——迁移开始之后源索引的新写入，不会自动出现在目标里。

四、原理拆解：为什么迁移完还要补一次增量

时序是这样的：

  1. _reindex 开始，读取源索引在某一时刻的可见数据；
  2. 期间应用继续写 v1（此时写入的是旧结构）；
  3. reindex 结束，v2 里只有第 1 步那批数据；
  4. 切别名到 v2，第 2 步写入的数据就丢了。

解法只有两种：迁移窗口内停写，或迁移结束后按时间范围补一次增量（source.query 用 range 卡住上次的截止时间）。工程上后者更常见，但需要业务字段里有可靠的时间戳。

六、实操

# 1) 建目标（结构一次写对）
curl -X PUT "http://localhost:9200/goods_v2" -H 'Content-Type: application/json' -d '
{ "settings": { "number_of_shards": 3, "number_of_replicas": 1 },
  "mappings": { "properties": { "title": { "type": "text" },
                                "price": { "type": "scaled_float", "scaling_factor": 100 } } } }'

# 2) 异步迁移 + 冲突策略
curl -X POST "http://localhost:9200/_reindex?wait_for_completion=false&slices=4" \
  -H 'Content-Type: application/json' -d '
{ "source": { "index": "goods_v1", "size": 1000 },
  "dest":   { "index": "goods_v2", "op_type": "create" } }'

# 3) 观察进度
curl -s "http://localhost:9200/_tasks?actions=*reindex*&detailed=true" | jq '.nodes[].tasks[].status'

# 4) 补增量（按时间范围）
curl -X POST "http://localhost:9200/_reindex" -H 'Content-Type: application/json' -d '
{ "source": { "index": "goods_v1", "query": { "range": { "updated_at": { "gte": "2023-11-19T00:00:00Z" } } } },
  "dest": { "index": "goods_v2", "op_type": "index" } }'

判定成功要同时满足：failures 为空、version_conflicts 为 0（或已被业务确认可跳过）、目标 _count 与源一致。

七、常见坑

  1. 以为 reindex 会带 settings/mapping：不会，目标必须提前建好。
  2. 迁移后不补增量：切换后神秘丢数据。
  3. op_type 用 index：把目标上已有的新数据覆盖成旧数据。
  4. 不看 failures：字段类型不兼容的文档被跳过，数量对不上才发现。
  5. slices 开太大：并行切片会同时压满磁盘与 CPU，反而拖慢在线检索。
  6. 大任务同步等待：HTTP 超时后任务仍在跑，容易误判失败并重复提交。

八、课后小结

  1. _reindex 只搬文档，结构与 settings 手工建。
  2. 迁移用 create 防覆盖，conflicts=proceed 要统计。
  3. 快照语义决定了必须补增量或停写窗口。
  4. _tasks 是观察大任务的唯一可靠入口。
  5. 成败看 failures、version_conflicts 与最终 _count。

九、思考题

  1. 一个 500 GB 索引迁移，你会怎么切成多批？每批的边界字段用什么？
  2. slices=8 与「串行跑 8 次」相比，优劣势各是什么？
  3. 迁移中 failures 里出现 mapper_parsing_exception，你会修数据还是改目标 mapping？判断依据是什么？
