ES07-字段类型

分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

字段类型选型：八类常用类型与它们的硬限制

选类型的判断顺序只有三步：这段文字要不要分词搜索 → 这个字段要不要排序/聚合 → 这个数组要不要保持对象级独立。

三步走完，类型基本就定了。这一讲把常用八类过一遍，每类都带官方的限制条款。

八类常用字段的能力矩阵：能不能搜、能不能排、能不能聚合，由类型本身决定｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 用「三分法」给任意业务字段选类型；
  2. 说清 text 与 keyword 在索引结构上的差别；
  3. 知道 object / nested / flattened 三者的适用边界；
  4. 说出 join 与 date 各自的官方硬限制。

三、理论讲解

官方把字段类型分成若干族：文本（text、keyword、wildcard、search_as_you_type）、数值（long/integer/short/byte、double/float/half_float/scaled_float、unsigned_long）、日期（date、date_nanos）、布尔、对象与关系（object、nested、flattened、join）、地理（geo_point、geo_shape）、向量（dense_vector）等。

四、原理拆解：三个容易踩的机制

① text 为什么不能排序聚合：排序聚合要「按文档取该字段的值」，靠的是 doc values 列存；text 为了体积默认不建 doc values，官方还默认关闭了内存版 fielddata（它会把词条全塞进堆）。所以给 text 排序必然报 Fielddata is disabled on text fields by default。

② object 数组为什么会误命中：[{"color":"red","size":"M"},{"color":"blue","size":"L"}] 扁平化后变成 color=[red,blue]、size=[M,L]，于是「color=red AND size=L」也能命中——这是官方写明的扁平化行为，不是精度问题。

③ nested 为什么查询必须换语法：每个嵌套对象被单独索引成一个隐藏文档，普通查询看不到它们，必须用 nested 查询 + nested 聚合。

六、实操

curl -X PUT "http://localhost:9200/shop" -H 'Content-Type: application/json' -d '
{
  "mappings": { "properties": {
    "title":  { "type": "text", "fields": { "raw": { "type": "keyword", "ignore_above": 256 } } },
    "sku":    { "type": "keyword" },
    "price":  { "type": "scaled_float", "scaling_factor": 100 },
    "on_sale":{ "type": "boolean" },
    "created":{ "type": "date" },
    "location": { "type": "geo_point" },
    "attrs":  { "type": "flattened" },
    "variants": { "type": "nested", "properties": {
        "color": { "type": "keyword" }, "size": { "type": "keyword" }, "stock": { "type": "integer" } } }
  } }
}'

# nested 查询：variants 里同一对象 color=red 且 size=L
curl -s -X GET "http://localhost:9200/shop/_search" -H 'Content-Type: application/json' -d '
{ "query": { "nested": { "path": "variants", "query": { "bool": { "must": [
  { "term": { "variants.color": "red" } }, { "term": { "variants.size": "L" } } ] } } } } }'

把 nested 换成 object 再跑同一个查询，会出现「color=red 且 size=L」的假命中——这就是为什么选型要先问「数组里的对象是否需要成组匹配」。

七、常见坑

  1. 给 text 排序聚合：官方 fielddata 默认关闭，直接报错。
  2. nested 用普通 term 查：查不到，必须 nested 查询。
  3. join 当外键用：官方限制一个索引只能有一个 join 字段，且父子文档必须同分片（routing 一致），不是通用关联。
  4. date 写了不匹配格式的值：直接 mapper_parsing_exception，默认格式是 strict_date_optional_time 或 epoch_millis。
  5. keyword 不收 ignore_above：超长字符串（如整段正文）照样进索引，段体积暴涨。
  6. geo_point 写成 lon, lat：顺序反了坐标会落到南极附近，官方顺序是 lat, lon。

八、课后小结

  1. 三分法选型：要不要分词 → 要不要排序聚合 → 数组要不要对象级独立。
  2. text 管搜、keyword 管精确与聚合，一个字段两种用法靠 fields。
  3. object 数组会扁平化误命中，要独立就 nested；键值太多的扩展属性用 flattened。
  4. 金额用 scaled_float 或整数分，数值类型按够用最小选。
  5. join 限制多，别当关系库外键用。

九、思考题

  1. 「文章正文需要全文检索，同时要按正文字数做区间统计」——你会怎么建字段？为什么不能直接给 text 加 doc_values？
  2. 一个埋点表字段上千个且名字不固定，用 object 会撞什么上限？flattened 又牺牲了什么？
  3. nested 写入开销更大的原因是什么？给出一个「不值得用 nested」的场景。
