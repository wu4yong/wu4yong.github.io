_bulk 的正确用法：格式、批量大小与部分失败处理

_bulk 是吞吐的生命线，也是「数据悄悄少了一批」的高发地。

原因不复杂：请求整体返回 200，单条可能已经失败。这一讲把格式、大小、失败处理三件事钉死。

NDJSON 成对两行，items 里每条文档各自成败｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 写出格式完全正确的 NDJSON 请求体（含末行换行）；
  2. 说清四个动作（index / create / update / delete）的差别；
  3. 知道批量大小该怎么定，以及官方调优章节的经验区间；
  4. 会用 filter_path 只捞出失败条目。

四、原理拆解：为什么「整体 200」不等于「全都成功」

_bulk 的语义是逐条独立执行：每条自己解析、自己走路由、自己落分片。某条因类型冲突失败，不会中断整批，也不会让整体状态码变成 4xx。于是响应里出现这种结构：

{ "took": 42, "errors": true,
  "items": [ { "index": { "_id": "1", "status": 201 } },
             { "index": { "_id": "2", "status": 400,
                          "error": { "type": "mapper_parsing_exception" } } } ] }

生产里最危险的写法是「只看 HTTP 200 就认为成功」。正确动作是：解析 items，按 status >= 400 收集失败 ID，再决定重试或告警。

批量大小官方在调优章节给的思路是「控制在 5–15 MB 量级、几百到几千条」，不是越大越好：过大会撑爆请求缓冲、拉长单次失败的影响面，也会让背压（M3-7）更容易触发。

六、实操

# 正确格式：末行换行、NDJSON
curl -X POST "http://localhost:9200/goods/_bulk" -H 'Content-Type: application/x-ndjson' -d '
{"create":{"_id":"1"}}
{"title":"批量一","price":10}
{"create":{"_id":"1"}}
{"title":"重复 ID，应当失败","price":20}
{"index":{"_id":"2"}}
{"title":"批量二","price":30}
'

# 只捞失败条目：排障首选
curl -s -X POST "http://localhost:9200/goods/_bulk" -H 'Content-Type: application/x-ndjson' \
  --data-binary @batch.ndjson | jq '.items[] | select(.create.status >= 400)'

第二条命令演示了正确的排障姿势：filter_path（或 jq）只挑失败项，避免在上万条 items 里肉眼找。

七、常见坑

  1. 写成 JSON 数组：_bulk 只认 NDJSON。
  2. 末行没换行：最后一条静默丢失，这是最隐蔽的一条。
  3. 只看 errors 不看 items：errors: true 只是「有失败」，具体哪条要逐项看。
  4. 该用 create 却用 index：重复导入会覆盖原文档，看起来「成功」其实数据被替换。
  5. 不指定 _id 让 ES 自动生成：之后无法按 ID 更新，只能整批重灌。
  6. 单批几十 MB：请求缓冲压力大，失败重试代价高，还容易触发 429。

八、课后小结

  1. _bulk 是 NDJSON、成对行、末行换行、x-ndjson。
  2. 四个动作里只有 create 不覆盖；防重复导入必须用它。
  3. 整体 200 ≠ 全部成功，必须解析 items 的 status。
  4. 批量大小控制在 5–15 MB 量级是官方调优思路，不是硬指标。
  5. 失败处理要能只取失败项，重试只重试失败项。

九、思考题

  1. 一次 1 万条的 bulk 有 12 条 400（类型冲突），你会怎么设计重试？会不会把成功那 9988 条重发？
  2. 为什么官方要求末行换行？从解析器实现角度解释。
  3. 用 index 导入历史数据导致「新数据被旧数据覆盖」，你会怎么发现？给出两个监控点。
