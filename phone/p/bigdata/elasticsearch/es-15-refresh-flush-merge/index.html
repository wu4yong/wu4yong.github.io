ES15-refresh、flush、merge

分类：bigdata · elasticsearch ｜ 标签：系统课 · Elasticsearch

四个「刷」的区别：refresh、flush、forcemerge、translog flush

线上排障时被问最多的一句是「要不要 flush 一下」。flush 不解决「搜不到」，那是 refresh 的事。

四个名字里带「刷」的动作，目标完全不同，混用只会把问题越修越大。

四个刷各自的作用对象、触发方式与代价｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 用一句话说清四个动作各自解决什么问题；
  2. 知道 refresh 的三个调用方式（周期、_refresh、?refresh=）；
  3. 说清官方对 forcemerge 的明确警告；
  4. 遇到「搜不到」「磁盘不降」「段太多」三种症状，能对应到正确动作。

官方对 forcemerge 有一句必须记住的限制：它只应在「已经不再写入」的索引上执行。原因很直接——合并会重写所有段，边写边合等于反复做无用功，还会把 CPU/IO 打满，拖垮同期检索。

四、原理拆解：三件事各归谁管

  • 能不能搜 → refresh 决定（把 buffer 里的文档变成可搜索段）；
  • 断电会不会丢 → translog 与 flush 决定（commit 之后 translog 换代，重放起点前移）；
  • 查询快不快、磁盘降不降 → segment 数量与 merge 决定（删除标记只有合并后才真正回收）。

六、实操

# refresh：立刻可搜
curl -s -X POST "http://localhost:9200/ledger/_refresh"

# 写入时等刷新（批量校验比 refresh=true 温和）
curl -X PUT "http://localhost:9200/ledger/_doc/9?refresh=wait_for" -H 'Content-Type: application/json' -d '
{ "amount": 999, "ts": "2023-11-07T09:00:00Z" }'

# flush：归档点
curl -s -X POST "http://localhost:9200/ledger/_flush"

# forcemerge：只读索引上做，一次就够
curl -s -X POST "http://localhost:9200/ledger/_forcemerge?max_num_segments=1"

# 观察段数变化
curl -s "http://localhost:9200/_cat/segments/ledger?v&h=index,shard,segment,docs.count,size"

_forcemerge 之后段数应从多个降到每分片 1 个；若再执行一次没有变化，说明已经合并到位。

七、常见坑

  1. 拿 flush 解决搜不到：flush 会顺带 refresh，但 O(段) 的代价换一次可见性，得不偿失。
  2. 生产里对每条写入 refresh=true：段暴涨、merge 压力飙升。
  3. 在活跃索引上 forcemerge：官方明确只建议在写完的索引上做，否则会与写入互相踩踏。
  4. 反复 forcemerge：已经 1 段再合没有收益，只是浪费 IO。
  5. 把 refresh_interval: -1 忘了改回来：上线后「数据延迟一小时」多半是这个。
  6. 以为 flush 会回收磁盘：空间回收要靠 merge。

八、课后小结

  1. refresh 管可见性，flush 管持久化归档，forcemerge 管段合并与空间回收，translog flush 管日志落盘。
  2. 只有 refresh 能让文档「被搜到」。
  3. forcemerge 的前置条件是不再写入。
  4. ?refresh=wait_for 比 refresh=true 温和，适合批量校验。
  5. 症状→动作的映射要背下来，别用「刷一下」解决一切。

九、思考题

  1. 一个索引删了 40% 文档但磁盘没降，你会做什么？前置条件是什么？
  2. 为什么 refresh_interval: -1 时，_count 会一直返回 0，而 GET _doc 正常？
  3. 如果业务要求「写入后 200ms 可见」，你会怎么配？代价是什么？
