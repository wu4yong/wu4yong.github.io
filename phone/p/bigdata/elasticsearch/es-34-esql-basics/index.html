ES|QL 入门：用管道语法写检索与统计

ES|QL 是 Elasticsearch 自己的一套管道式查询语言：写在 FROM 后面接一串 | 开头的处理步骤，读起来像 Shell。

它解决的是「一句话既要过滤又要分组统计」的痛点——原来得写两层嵌套 JSON。

ES|QL 的管道语法｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说清 ES|QL 的管道结构与关键字顺序；
  2. 会写 FROM / WHERE / STATS … BY / SORT / LIMIT 五步基础查询；
  3. 知道 _query 端点与 format 参数；
  4. 明白 ES|QL 与 Query DSL 不是等价替代关系。

四、原理拆解：为什么 ES|QL 能做「一次算完」

Query DSL 的模型是「请求体里嵌套 query + aggs + sort」，各部分只能各管一段；ES|QL 的模型是一条数据流：上一步的输出列就是下一步的输入，STATS 产出的列可以直接被 SORT、WHERE 使用。所以「分组后过滤」在 ES|QL 里是自然写法（STATS … BY 后再 WHERE），而在 DSL 里得靠 bucket_selector 这种 pipeline 聚合绕过去（M5-3）。

代价是：ES|QL 不是 DSL 的超集。官方文档明确列出了它的能力边界——它面向「检索 + 分析」的常用路径，DSL 里那些细粒度特性（某些打分函数、部分聚合参数、复杂嵌套）在 ES|QL 里并不都有对应写法。不要以为学会 ES|QL 就可以不学 DSL。

六、实操

# 基础五步：过滤 + 分组 + 排序 + 截断
curl -s -X POST "http://localhost:9200/_query?format=txt" -H 'Content-Type: application/json' -d '
{ "query": "FROM logs-*
    | WHERE @timestamp >= NOW() - 1 hour
    | STATS c = COUNT(*) BY level
    | SORT c DESC
    | LIMIT 5" }'

# 计算新列 + 保留列
curl -s -X POST "http://localhost:9200/_query?format=json" -H 'Content-Type: application/json' -d '
{ "query": "FROM orders
    | WHERE status == \"paid\"
    | EVAL amount_yuan = amount / 100.0
    | KEEP order_id, amount_yuan, created
    | SORT created DESC
    | LIMIT 20" }'

# 分组后过滤（DSL 写起来很绕，这里很直接）
curl -s -X POST "http://localhost:9200/_query?format=txt" -H 'Content-Type: application/json' -d '
{ "query": "FROM goods | STATS cnt = COUNT(*) BY brand | WHERE cnt >= 100 | SORT cnt DESC" }'

字符串字面量用双引号并转义，== 是等值判断（不是 =），这两点最容易踩。

七、常见坑

  1. 把 ES|QL 当 SQL 用：= 用于赋值（STATS c = COUNT(*)），判断相等是 ==。
  2. 以为 DSL 全部能力都有：打分函数、部分聚合参数、高亮等在 ES|QL 中缺失。
  3. 版本假设：ES|QL 在 8.11 引入，早期为技术预览，能力逐版本扩张；用前先看该版本官方文档的支持列表。
  4. FROM 写具体索引名却想跨集群：跨集群要 cluster:index 形式，且需相应权限。
  5. format=txt 拿去做程序解析：文本格式给人看，程序用 json 或 csv。
  6. 不写 LIMIT：默认返回量受限制，但大结果集仍应显式截断。

八、课后小结

  1. ES|QL 是管道语言：FROM → WHERE → STATS … BY → SORT → LIMIT。
  2. 上一步的列就是下一步的输入，STATS 之后还能继续过滤排序。
  3. 入口是 POST /_query，format 决定返回格式。
  4. 它是 DSL 的补充而非替代，能力边界以官方支持列表为准。
  5. == 判等、= 赋值，别混。

九、思考题

  1. 「按品牌统计销量，只要销量 ≥ 100 的品牌」用 DSL 要怎么写？为什么比 ES|QL 绕？
  2. 为什么 ES|QL 无法完全覆盖 DSL 的打分能力？从「数据流模型 vs 查询树模型」角度想。
  3. 一个已有大量 DSL 模板的系统，引入 ES|QL 的合理切入点在哪？
