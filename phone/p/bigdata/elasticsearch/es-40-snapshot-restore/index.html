快照与恢复：仓库、增量、SLM 与恢复的三个前提

快照是集群级备份：不只是数据，还包括索引的 mapping 与 settings。

它天然增量——第一次全量，后续只传变化的段文件。但恢复有三个前提，缺一个就恢复不了，这三个前提是本篇的重点。

仓库、增量快照、恢复流程与 SLM 保留策略｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 会注册仓库并知道 path.repo 白名单的作用；
  2. 说清快照的增量机制与「快照里有什么」；
  3. 记住恢复的三个前提（同名校验、版本兼容、仓库可访问）；
  4. 会用 SLM 做定期快照与保留策略。

四、原理拆解：为什么快照又快又省

Lucene 的索引是不可变段：写入产生新段，旧段只在 merge 时被替换。快照记录的是「此刻有哪些段」，第一次把全部段上传到仓库，之后每次只上传新增的段。所以做 7 天保留，占用的空间远小于 7 份全量。

想恢复成新索引，用 rename_pattern / rename_replacement（正则捕获组），这比先删旧索引安全得多。

六、实操

# 1) 注册仓库（必须位于 path.repo 白名单目录内）
curl -s -X PUT "http://localhost:9200/_snapshot/backup" -H 'Content-Type: application/json' -d '
{ "type": "fs", "settings": { "location": "/data/es-backup", "compress": true } }'

# 2) 打快照（异步，可加 wait_for_completion=true）
curl -s -X PUT "http://localhost:9200/_snapshot/backup/snap-2024-01-21?wait_for_completion=true" -H 'Content-Type: application/json' -d '
{ "indices": "goods,orders", "ignore_unavailable": true, "include_global_state": false }'

# 3) 恢复到新索引名，不动原索引
curl -s -X POST "http://localhost:9200/_snapshot/backup/snap-2024-01-21/_restore?wait_for_completion=true" -H 'Content-Type: application/json' -d '
{ "indices": "goods",
  "rename_pattern": "goods",
  "rename_replacement": "goods-restored",
  "include_global_state": false }'

# 4) 看快照与仓库状态
curl -s "http://localhost:9200/_snapshot/backup/_all?pretty"
curl -s "http://localhost:9200/_snapshot/backup/_status?pretty"

include_global_state: false 常用于「只恢复数据，不覆盖集群级模板与设置」。

七、常见坑

  1. 仓库目录不在 path.repo 白名单：注册直接失败，这是官方硬约束。
  2. 恢复同名索引：先关索引或删索引，或用 rename。
  3. 以为快照能恢复到更低版本：官方不支持降级恢复。
  4. include_global_state: true 覆盖模板：恢复后集群级配置被旧快照带回。
  5. 只打快照不验证恢复：真出事时才发现仓库权限/路径不通。
  6. 多集群共用一个仓库却不同步：并发写同一仓库会冲突，官方要求仓库只被一个集群写。

八、课后小结

  1. 快照 = 段引用 + 元数据，天然增量。
  2. path.repo 是 fs 仓库的白名单，绕不过。
  3. 恢复三前提：不重名、版本兼容、仓库可达。
  4. rename_pattern 是「安全恢复」的标准手法。
  5. SLM 让定期备份与保留策略可运维，且必须定期做恢复演练。
