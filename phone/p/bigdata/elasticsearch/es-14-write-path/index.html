一次写入的五个步骤：buffer、translog、segment、fsync、merge

M1-3 给了骨架，这一讲把骨架上每根钉子拧紧：一条 PUT 到底在内存和磁盘上留下了什么、哪一步决定「会不会丢数据」、哪一步决定「能不能被搜到」。

搞清这五步，后面 _bulk 调优、背压、段合并全都有据可依。

写入 201 / refresh / flush 三个时刻分别落下什么｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 按顺序说出写入的五步，并指出哪一步之后「客户端拿到 201」；
  2. 分清 buffer、translog、segment 三者的职责与生命周期；
  3. 说清官方默认的 translog 持久化策略（request）与代价；
  4. 知道「写成功」与「已持久化」「可搜索」是三件不同的事。

之后的三个异步动作，才是磁盘与可搜索性的关键：

  • refresh：buffer → 新 segment，可被搜索（默认 1s）；
  • flush：Lucene commit + 清空/换代 translog（持久化归档点）；
  • merge：多个 segment 合并成更少更大段（回收删除标记）。

四、原理拆解：丢不丢数据看 translog 策略

官方给 translog 一个索引级设置，默认值决定了「返回 201 之后断电会不会丢」：

设置
默认
行为
代价
index.translog.durability
request
每次请求都 fsync translog
每次写一次磁盘同步，吞吐受限但最安全
index.translog.durability
async

512mb
translog 超过阈值触发 flush

所以「返回 201」= 主分片 buffer 有、translog 已 fsync、副本已确认；不等于新 segment 已生成，也不等于可被搜索。

六、实操

# 写入并观察返回里的 _seq_no / _primary_term / result
curl -X PUT "http://localhost:9200/ledger/_doc/1?refresh=false" -H 'Content-Type: application/json' -d '
{ "amount": 100, "ts": "2023-11-04T09:00:00Z" }'

# 看 translog 与段的数量
curl -s "http://localhost:9200/ledger/_stats/translog,segments?human"
curl -s "http://localhost:9200/_cat/segments/ledger?v"

# 触发一次 flush（注意：flush 会顺带 refresh）
curl -s -X POST "http://localhost:9200/ledger/_flush"

_stats 返回里 translog.operations 在增长、segments.count 在 refresh 后才增加——这就是五步与三个异步动作的现场证据。

七、常见坑

  1. 把 201 当「已可搜索」：可搜索要等 refresh，默认 1s。
  2. 把 201 当「已落 segment」：segment 是异步生成的，落盘靠 translog + flush。
  3. 为吞吐改 durability: async 却要求零丢失：两者互斥，官方设置层面就写明代价。
  4. wait_for_active_shards 设成 all：任一副本未就绪就写不进去，可用性会下降。
  5. 以为副本也承担写分摊：写只到主分片，副本是同步复制（M6-2）。

八、课后小结

  1. 五步：校验 → buffer → translog → 副本确认 → 返回。
  2. translog 决定持久性，segment 决定可搜索性，两者异步。
  3. 官方默认 translog.durability: request，最安全也最慢。
  4. flush 是持久化归档点，不是「让文档可搜」的动作。
  5. 201 只代表「主分片与副本都收下了」，不代表可搜、也不代表已合并。

九、思考题

  1. 一条写入返回 201 后立刻 kill -9 节点，数据还在吗？分 request 与 async 两种配置回答。
  2. 为什么官方要把 translog 与 segment 分成两套机制，而不是写完直接生成 segment？
  3. 批量导入时把 refresh_interval 设为 -1，同时保持 durability: request，这套组合的收益与风险各是什么？
