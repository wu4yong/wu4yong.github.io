ES47-上线检查

分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

上线前检查清单：把这 12 项过一遍再开流量

上线不是「能搜就行」。ES 的问题往往在流量上来后才暴露：副本不够、分片太碎、堆没留余量、安全裸奔。

这一篇是一张可以打印出来逐项打勾的清单，每一项都对应前面某一讲的官方依据。

每项对应的验证入口｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 能背出上线前的 12 项检查；
  2. 说清每一项「不做会怎样」；
  3. 会把检查结果落成可复现的脚本或工单；
  4. 建立「变更前必打快照、变更后必验证」的习惯。

四、原理拆解：为什么清单比经验可靠

ES 的默认值是为「通用场景」设计的，而生产场景各有约束。清单的价值是把「隐式前提」显式化：比如「副本 ≥1」这条，在开发单节点上永远做不到，但生产必须做——不写进清单，就会在扩容时被忘掉。

另一个原理层面的事实：ES 的很多问题不可逆——分片数建好就不能改（只能 reindex/shrink），mapping 类型冲突后只能重建索引。所以检查必须在上线前做，而不是上线后补救。

六、实操

# 一键体检脚本：健康、分片分布、堆、水位、未分配
curl -s "http://localhost:9200/_cluster/health?pretty"
curl -s "http://localhost:9200/_cat/indices?v&h=index,pri,rep,pri.store.size,health&s=pri.store.size:desc"
curl -s "http://localhost:9200/_cat/allocation?v&h=node,shards,disk.used_percent,heap.percent"
curl -s "http://localhost:9200/_cat/shards?v" | Select-String -Pattern 'UNASSIGNED'
curl -s "http://localhost:9200/_cat/thread_pool?v&h=node_name,name,rejected"

# 快照是否真的可用（必须做恢复演练）
curl -s "http://localhost:9200/_snapshot/backup/_all?pretty"

# 升级/大变更前的迁移检查
curl -s "http://localhost:9200/_migration/deprecations?pretty"

最后那条 _migration/deprecations 是升级前的官方入口：它会列出当前配置与查询里「下一版本将不兼容」的点。

七、常见坑

  1. 配置了快照但从没恢复过一遍：等于没有备份。
  2. 预发不做压测就看上线：副本与水位余量全是猜的。
  3. mapping 靠动态推断：字段类型漂移，后期只能重建索引。
  4. 安全「先关着，以后再说」：数据一旦泄露就没有「以后」。
  5. 清单只过一遍就归档：扩容、大促、升级都需要重新过。
  6. 没人负责看慢日志与监控：工具装了等于没装。

八、课后小结

  1. 12 项检查覆盖资源、拓扑、容量、mapping、可观测、安全、备份。
  2. 分片数与 mapping 不可逆，必须上线前定好。
  3. 快照的价值只在「验证过恢复」之后成立。
  4. 生产必须有副本、必须双向 TLS、必须用 API key。
  5. 每次重大变更前重新过一遍清单。

九、思考题

  1. 12 项里哪三项「不做」的风险最不可逆？为什么？
  2. 一个只有两台机器的生产集群，副本 ≥1 与 master 奇数这两条冲突时怎么折中？
  3. 如果把清单做成 CI 检查，你会挑哪几项自动化？
