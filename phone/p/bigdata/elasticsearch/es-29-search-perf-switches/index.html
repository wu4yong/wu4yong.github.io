检索侧性能开关：从 _source 裁剪到 profile

查询慢，八成不是「匹配慢」，而是「取数据慢」。

这一篇把检索侧能拧的开关列全：少取字段、少算总数、少排序、必要时开 profile 看时间花在哪。

配图 29-1｜提示词：一张「查询请求解剖图」：请求体被拆成四块发光组件 query、sort、_source、highlight，每块旁边标注耗时条；下方一排开关面板：_source: false、includes/excludes、fields、docvalue_fields、track_total_hits、request_cache、terminate_after、profile，每个开关旁有小字代价说明。深色星空背景，青蓝为主，耗时条用琥珀色。

一、学习目标

  1. 会用 _source 裁剪减少网络与解析开销；
  2. 分清 fields、docvalue_fields、stored_fields 各自取什么；
  3. 知道 track_total_hits、request_cache、terminate_after 的适用面；
  4. 会用 profile 定位耗时阶段。

四、原理拆解：一次 search 的时间去哪了

官方把 search 拆成两个阶段：query phase（各分片算匹配与排序，返回 doc id + 排序值）与 fetch phase（协调节点按 doc id 去各分片取 _source）。真实生产里，慢常常出在第二阶段：取回一个 200KB 的 _source 只为渲染列表页的三个字段。

所以优化顺序应当固定：

顺序
动作
收益
1
_source.includes 只取需要的字段
直接减少网络与反序列化
2
只排序必要字段，避免大字段 doc_values
减少内存排序量
3
只要总数就 size: 0
跳过 fetch phase
4
正常分页就别精确 track_total_hits
省掉全量计数
5
仍慢再 profile 看是哪一段
定位而非猜测

六、实操

# 只取两个字段
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "query": { "match": { "title": "跑鞋" } },
  "_source": { "includes": ["title", "price"] }, "size": 10 }'

# 完全不取原文，只看元数据
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "query": { "term": { "on_sale": true } }, "_source": false, "size": 10 }'

# 聚合 + 请求缓存
curl -s -X GET "http://localhost:9200/goods/_search?request_cache=true" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": { "by_tag": { "terms": { "field": "tags" } } } }'

# profile 定位耗时
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "profile": true, "query": { "match": { "title": "跑鞋" } } }'

_source: false 时 highlight 仍可工作（它靠 offsets），但 _source 相关的字段回显全没了，前端要自己判断。

七、常见坑

  1. 列表页直接返回完整 _source：大文档把 fetch 阶段拖成瓶颈。
  2. stored_fields 用在没 store: true 的字段：返回空，误以为数据丢了。
  3. docvalue_fields 用在 text：没有 doc_values，取不到。
  4. track_total_hits: true 到处开：每个请求都全量计数，集群压力翻倍。
  5. request_cache 用在普通分页查询：官方只对 size: 0 一类请求生效，开了也白开。
  6. profile: true 上生产：额外统计开销不小，只在排查时临时开。
  7. terminate_after 当分页用：它返回的是「不完整结果」，语义完全不同。

八、课后小结

  1. 检索优化先剪数据量，再谈参数。
  2. _source 裁剪是收益最高、风险最低的一步。
  3. fields / docvalue_fields / stored_fields 取的是三种不同来源的值。
  4. size: 0 跳过 fetch，聚合与计数必备。
  5. profile 用来看时间花在 query 还是 fetch，不靠猜。

九、思考题

  1. 一个请求 _source: false + highlight，高亮还能出吗？为什么？
  2. 为什么 request_cache 对普通 from/size 查询无效？从「结果可复用性」解释。
  3. 列表页 QPS 很高、每个文档 200KB，你会先做哪三件事？
