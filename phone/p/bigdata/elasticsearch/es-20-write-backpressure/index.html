写入背压：bulk 队列、内存限流与 429 的正确处理

M3 最后一讲。写入侧的所有问题最终都收敛成一个信号：429 Too Many Requests（es_rejected_execution_exception）。

它是保护机制，不是故障；正确处理是「降速 + 退避」，错误处理是「无脑重试」，后者会把集群拖死。

从批量到 429 的拒绝路径与指数退避｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说清 429 在什么条件下产生（两道闸门）；

  4. 列出三种降低写入压力的手段及其代价。

设计的意图很明确：宁可让客户端收到 429 稍后重试，也不能让节点因为堆积请求而 OOM 或雪崩。

四、原理拆解：为什么不能「立刻重试」

被拒绝说明「队列已满」，此刻集群正在处理更早的批次。立刻重试只会让队列更满，形成正反馈，最后所有请求都超时。正确策略是：

  1. 只重试失败的部分（items 里 status == 429）；
  2. 指数退避 + 抖动（如 100ms → 200ms → 400ms，带随机抖动）；
  3. 限制在途并发（客户端侧并发数固定，而非无限提交）；
  4. 连续多次 429 就降低批量大小，而不是继续加并发。

  write: .thread_pool.write, pressure: .indexing_pressure }'

# 单条写入被拒时，响应形如：
# {"error":{"type":"es_rejected_execution_exception", ...}, "status":429}

# 触发条件观察：批量导流时看队列与拒绝计数是否同步上涨

客户端侧的退避逻辑（伪代码，语言无关）：

for attempt in 0..maxRetry:
    resp = bulk(failedBatch)
    ok   = items with status < 400
    retryable = items with status == 429 or 5xx
    if retryable empty: break
    sleep(backoff(attempt) + jitter)
    failedBatch = retryable items

关键点：failedBatch 只保留可重试项，4xx（如 mapper_parsing_exception）不该重试，应进死信队列。

七、常见坑

  1. 无脑立即重试：把背压变成雪崩。
  2. 把 4xx 也重试：类型冲突重试一万次也不会成功。
  3. 只看整体状态码：批量里部分 429、部分成功，必须按 items 拆分。
  4. 客户端并发无限：写入吞吐由服务端决定，客户端加并发只会增加 429。
  5. 靠调大队列解决问题：队列更长只意味着更长的排队延迟与更大的内存风险。
  6. 忽视 indexing_pressure：堆紧张时先被限流的是写入，不是检索。

八、课后小结

  1. 429 = 两道闸门之一触发（线程池队列、内存限流），是保护不是故障。
  2. indexing_pressure 官方默认占堆 10%。
  3. 正确策略：只重试失败项 + 指数退避 + 限并发 + 必要时降批量。
  4. 4xx 不该重试，应进死信。
  5. 提高写入吞吐要靠调结构（refresh、副本、段合并），不是靠堆并发。

九、思考题

  1. 集群 CPU 只有 30%，但写入大量 429，最可能的原因是什么？给出排查顺序。
  2. 为什么官方选择「拒绝」而不是「无限排队」？从内存与延迟两个角度说明。
  3. 设计一个客户端限流器：给出并发数与批量大小的初始取值，以及根据 429 率自适应的规则。
