ES35-查询语言的选型对照

分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

五种查询语言怎么选：DSL、ES|QL、SQL、EQL、KQL

同一个集群上有五套「语言」能用：Query DSL、ES|QL、SQL、EQL、KQL。

它们不是替代关系，而是面向不同人群与不同数据形态。选错的代价不是写不出来，而是「写出来也不对」——比如拿 EQL 查没有时间字段的索引。

五种查询语言的选择路径｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 用一张表说清五种语言的分工与硬限制；
  2. 知道各自的入口（端点 / UI）；
  3. 会给一个具体场景选出合适语言并说出理由；
  4. 记住「EQL 必须有 @timestamp」这条硬约束。

四、原理拆解：为什么会有五套

底层只有一套 Lucene 查询 + 聚合能力，五套语言是不同的表达层：

  • DSL 最贴近底层，参数最全，是「应用系统集成」的标准选择；
  • ES|QL 是 Elastic 自己推的新一代管道语言，目标是把「过滤 + 统计」压到一条语句；
  • SQL 走翻译，把 SQL 语义映射到 DSL，能覆盖常见分析但边界处不一定与 SQL 直觉一致；
  • EQL 为「有序事件」而生，比如「登录失败后 5 分钟内出现提权」这类序列匹配，它必须先有时间轴，所以硬性要求 @timestamp；
  • KQL 是 Kibana 的输入框语法，给人在界面上快速筛数据，官方定位就是 UI 层，不对外提供 API。

一句话总结：DSL 是地基，其余都是在地基上盖的不同立面。

六、实操

# 同一需求的三种写法：近 1 小时各等级日志条数

# 1) DSL
curl -s -X GET "http://localhost:9200/logs/_search" -H 'Content-Type: application/json' -d '
{ "size": 0,
  "query": { "range": { "@timestamp": { "gte": "now-1h" } } },
  "aggs": { "by_level": { "terms": { "field": "level" } } } }'

# 2) ES|QL
curl -s -X POST "http://localhost:9200/_query?format=txt" -H 'Content-Type: application/json' -d '
{ "query": "FROM logs | WHERE @timestamp >= NOW() - 1 hour | STATS c = COUNT(*) BY level" }'

# 3) SQL（走翻译层）
curl -s -X POST "http://localhost:9200/_sql?format=json" -H 'Content-Type: application/json' -d '
{ "query": "SELECT level, COUNT(*) AS c FROM logs WHERE @timestamp >= NOW() - INTERVAL 1 HOUR GROUP BY level" }'

# 4) EQL：注意必须有 @timestamp
curl -s -X POST "http://localhost:9200/logs/_eql/search" -H 'Content-Type: application/json' -d '
{ "query": "process where process.name == \"cmd.exe\"", "size": 10 }'

四段返回结构各不相同：DSL 是 aggregations，ES|QL 是 columns + values，SQL 是 rows，EQL 是 events。写代码时要按各自契约解析。

七、常见坑

  1. 用 EQL 查业务索引：没有 @timestamp 直接失败。
  2. 以为 SQL 与 ES 语义完全一致：翻译层有边界，复杂 JOIN、窗口函数等能力受限，以官方 SQL 文档为准。
  3. KQL 写进代码：它只在 Kibana UI 生效，不是公开 API。
  4. ES|QL 当成 DSL 替代品：高亮、suggest、打分细节仍然只能走 DSL。
  5. 同一系统混用四五种语言：维护成本剧增，应约定主语言与例外场景。
  6. 版本差异：各语言的能力随版本变化，写之前对照该版本官方文档。

八、课后小结

  1. DSL 是地基，参数最全，应用集成首选。
  2. ES|QL 擅长「一条语句出统计」，8.11 起提供。
  3. SQL 走 _sql 翻译层，适合已有 SQL 生态。
  4. EQL 做事件序列，硬要求 @timestamp。
  5. KQL 只活在 Kibana UI 里。
  6. 选型原则：按调用方与数据形态选，不按「哪个新」选。

九、思考题

  1. 一个团队既要做应用搜索又要做报表，为什么「DSL 打底 + ES|QL 做报表」是合理组合？
  2. EQL 为什么必须依赖 @timestamp？去掉时间轴后「序列」还剩什么语义？
  3. 如果 SQL 查询结果与 DSL 不一致，你会以哪个为准？依据是什么？
