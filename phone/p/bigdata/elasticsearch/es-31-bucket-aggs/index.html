bucket 聚合的精度与时间轴：terms、date_histogram、composite

terms 的计数可能是近似的，date_histogram 的「月」有两种算法，桶多到一屏放不下时得换 composite。

这三个坑不在语法里，在分布式聚合的机制里。

terms、date_histogram 与 composite｜依据 Elasticsearch 官方文档 8.17 自绘

四、原理拆解：terms 为什么会「少算」

分布式下，每个分片只能看到自己的数据。为了让最终 Top 10 尽量准，协调节点让每个分片各返回 shard_size 个候选，再合并取前 size 个。如果某个品牌在 A 分片排第 15、在 B 分片排第 1，它在 A 分片的票数就没被带上来，最终总数偏小——这就是 doc_count_error_upper_bound 的来源。

调大 shard_size 能降低误差，代价是分片间传输与内存上升。判断标准很实际：报表要对账就必须精确——要么把字段做成单分片索引，要么改用 composite 一页页全量遍历后自己累加，要么用 cardinality 那种近似指标时心里有数。

时间轴这块，month 是日历月（1 月 31 天、2 月 28 天），30d 是固定 30 天窗口，两者在跨月报表里结果完全不同。而 time_zone 决定「一天从几点开始」，做国内日报必须给 +08:00，否则会出现「昨天 8 点的数据算到今天」。

六、实操

# terms：看误差字段，并手动加大 shard_size
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": { "b": { "terms": { "field": "brand", "size": 10, "shard_size": 50 } } } }'

# 自然月 + 东八区
curl -s -X GET "http://localhost:9200/orders/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": { "m": { "date_histogram": {
    "field": "created", "calendar_interval": "month", "time_zone": "+08:00", "min_doc_count": 0 } } } }'

# composite：先拿第一批，用 after 继续
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": { "c": { "composite": {
    "size": 100,
    "sources": [ { "brand": { "terms": { "field": "brand" } } },
                 { "day": { "date_histogram": { "field": "created", "calendar_interval": "day" } } } ] } } } }'

composite 返回的 after_key 就是下一页游标，按 after 循环直到为空，即可拿到全部组合桶。

七、常见坑

  1. 把 terms.doc_count 当绝对值：多分片下是近似，报表对不上很正常。
  2. 不设 time_zone 做日报：跨时区边界错位，数据对不上账。
  3. calendar_interval 与 fixed_interval 混用：同一字段两套口径，趋势图会互相打架。
  4. min_doc_count: 0 画折线：空桶补 0 是对的，但桶数会显著上升。
  5. composite 忘了 after 循环：只拿到第一批就以为拿全了。
  6. shard_size 拉得过大：精度上去了，内存与网络也上去了。

八、课后小结

  1. terms 是分片 Top N 汇总，天然近似，看两个误差字段。
  2. shard_size 是精度旋钮，size 是返回量旋钮，两者不同。
  3. 日历月用 calendar_interval，固定窗口用 fixed_interval。
  4. time_zone 决定桶边界，跨时区统计必须显式给。
  5. 海量桶用 composite + after 分批遍历。
