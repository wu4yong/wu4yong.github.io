分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

聚合的内存与性能：桶上限、执行顺序与采样

聚合打挂集群的方式很统一：桶太多。一个 terms 分 10 万组，每组再挂两个 metric，堆内存瞬间就被吃掉。

官方给了两道防线——桶数上限与执行策略——这一篇讲怎么用它们。

四、原理拆解：先分桶还是先算子聚合

depth_first 是「来一篇文档，就把它塞进父桶、同时更新子聚合」，适合父子强耦合（如 nested）。但父桶太多时，每个桶都要维护一堆子聚合状态，内存吃不消。

breadth_first 反过来：先用一遍数据把父桶 key 收集齐，再按桶逐个取文档算子聚合。内存占用只跟「桶数」有关，不跟「桶数 × 子聚合数」有关。所以官方把它设为多数场景的默认——桶多、子聚合多的时候，这个选择能救命。

execution_hint 是另一档手动挡：global_ordinals 适合高基数字段（利用序数映射，省内存但预热慢），map 适合低基数，bytes_hash 居中。选错不会错结果，只会慢。

random_sampler 适合「趋势看一眼」的场景：抽 10% 文档算聚合，误差可接受、速度提升明显，但结果不能用于对账。

六、实操

# 看桶上限
curl -s "http://localhost:9200/_cluster/settings?include_defaults=true&flat_settings=true" | grep -o '"search.max_buckets":"[^"]*"'

# 指定执行策略
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": { "b": { "terms": { "field": "brand", "execution_hint": "global_ordinals" } } } }'

# 抽样聚合：10% 文档
curl -s -X GET "http://localhost:9200/logs/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": {
    "sample": { "random_sampler": { "probability": 0.1 },
      "aggs": { "by_level": { "terms": { "field": "level" } } } } } }'

# 先缩范围再聚合（最有效的一招）
curl -s -X GET "http://localhost:9200/logs/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "query": { "range": { "@timestamp": { "gte": "now-1h" } } },
  "aggs": { "by_level": { "terms": { "field": "level" } } } }'

七、常见坑

  1. search.max_buckets 调大当解法：内存问题不会消失，只是延后爆。
  2. 对 text 字段聚合：需 fielddata，官方明确不建议，堆占用极高。
  3. terms.size 设 10000：桶数与子聚合状态同步膨胀。
  4. 多维嵌套不估桶数：10 × 31 × 24 就是 7440 个桶，再加子聚合就很危险。
  5. random_sampler 结果拿去对账：抽样结果是估算值。
  6. execution_hint 盲调：不同数据分布最优解不同，改前先测。

八、课后小结

  1. 桶数上限 search.max_buckets 默认 65536。
  2. breadth_first 是多数聚合的默认，桶多时更省内存。
  3. execution_hint 调执行策略，不改结果只改速度。
  4. random_sampler 用概率换性能，不适合精确统计。
  5. 缩小查询范围永远是第一优先的手段。

九、思考题

  1. 为什么 depth_first 在父桶很多时会吃内存？用状态数量解释。
  2. 一个 terms(size:1000) 下挂 date_histogram（31 天）与 percentiles，桶与状态规模大概多少？
  3. 抽样 10% 得到的占比，与全量差多少才算出格？业务上怎么约定？
