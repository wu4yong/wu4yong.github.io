发现与选举：seed_hosts、initial_master_nodes 与多播的退场

节点怎么找到彼此？靠 discovery.seed_hosts。

新集群怎么选出第一个 master？靠 cluster.initial_master_nodes。这两个参数配错，集群要么起不来，要么一重启就分裂。

发现与选举：名单、投票与 7.0 移除的旧参数｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 会用 discovery.seed_hosts 组网，说清它「只用于发现」；
  2. 理解 cluster.initial_master_nodes 只在全新集群引导时使用一次；
  3. 知道 discovery.type: single-node 的适用面；
  4. 记住 7.0 起被移除的旧参数（多播、minimum_master_nodes）。

四、原理拆解：发现和选举是两件事

发现解决「怎么知道集群里还有谁」：每个节点拿着 seed_hosts 主动去连，连上之后交换节点清单，形成一张全局成员表。所以 seed_hosts 不需要列全所有节点，列几个「活着的入口」就够——这也是它能容忍部分节点更换 IP 的原因。

选举解决「谁是 master」：所有 master-eligible 节点参与投票，拿到多数票者当选；票数门槛随成员数自动计算（3 个节点要 2 票，5 个要 3 票）。这正是 7.0 之后不再需要手工配 minimum_master_nodes 的原因。

cluster.initial_master_nodes 是「引导」而不是「选举」：全新集群没有任何已有状态，官方要求你用这个列表指定「一开始可能的 master 候选」，让它们先形成法定人数。危险点在于——集群已经成形后还留着这个配置，重启时它们会各自主张自己是初始集群，造成分裂。官方文档对此有明确警告：引导完成后应从配置中移除。

六、实操

# 看当前集群成员与 master
curl -s "http://localhost:9200/_cat/nodes?v&h=name,node.role,master,ip"

# 看集群状态与节点数
curl -s "http://localhost:9200/_cluster/health?pretty" | Select-String -Pattern 'number_of_nodes|status|master'

# elasticsearch.yml（3 节点首启）
# cluster.name: prod-es
# node.name: master-1
# node.roles: [ master, data ]
# discovery.seed_hosts: [ "10.0.0.11:9300", "10.0.0.12:9300", "10.0.0.13:9300" ]
# cluster.initial_master_nodes: [ "master-1", "master-2", "master-3" ]

注意 initial_master_nodes 里写的是 node.name，不是 IP；seed_hosts 里写的是地址。

七、常见坑

  1. 成形后不移除 initial_master_nodes：重启引发脑裂式引导冲突。
  2. 扩容时给新节点配 initial_master_nodes：新节点会尝试自建集群。
  3. seed_hosts 只写一台：那台挂了，新节点就发现不了集群。
  4. cluster.name 不一致：节点各自成团，_cat/nodes 里看不到彼此。
  5. 还在查 minimum_master_nodes：7.0 起已移除，配了也会被忽略。
  6. 滚动重启先停 master：频繁选举、分片反复迁移。

八、课后小结

  1. seed_hosts 管发现，initial_master_nodes 只管首启引导。
  2. 引导完成即删 initial_master_nodes，扩容时绝不配它。
  3. 多数票规则自动生效，无需手配最小 master 数。
  4. discovery.type: single-node 只给开发用。
  5. 滚动重启顺序：先 data，后 master。

九、思考题

  1. 为什么 seed_hosts 不必列全所有节点，而 initial_master_nodes 必须列全候选？
  2. 一个已运行两年的集群，配置文件里还留着 initial_master_nodes，你会怎么处理？风险是什么？
