容量估算：分片数、堆、磁盘怎么算出来

容量规划不是「拍个数」，而是从文档量倒推分片数、从分片数倒推堆、从副本数倒推磁盘。

算错的典型后果是分片过多：每个分片都是独立的 Lucene 实例，开销叠加起来比数据本身还贵。

分片数、堆与磁盘的推算顺序｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 会用「文档量 → 分片数 → 堆 → 磁盘」这条推算链；
  2. 记住两条官方经验线：单分片体积区间、每 GB 堆的分片数；
  3. 知道堆的两个天花板：物理内存 50%、compressed oops 上限；
  4. 会追问「业务预留多少余量」并给出可解释的数字。

四、原理拆解：分片为什么是「固定成本」

每个分片是一个独立 Lucene 索引，自带词典、段元数据、文件句柄、segment 内存结构。空分片也要占几十 KB 到几百 KB 的堆，加上海量文件的打开句柄。所以「分片数 × 每分片固定开销」才是容量里最容易被忽略的一块——一个 500 分片的索引，就算每个分片只有 1GB 数据，管理成本也很可观。

反方向的坑是「单分片过大」：分片恢复要把整个分片从副本/快照搬过来，50GB 以上的分片恢复时间会明显拉长，滚动重启的窗口也随之变长。

六、实操

# 现有索引的真实体积与文档数
curl -s "http://localhost:9200/_cat/indices?v&h=index,pri,rep,pri.store.size,store.size,docs.count&s=store.size:desc"

# 每节点分片数与堆使用
curl -s "http://localhost:9200/_cat/allocation?v&h=node,shards,disk.used_percent,heap.percent"

# 集群分片上限
curl -s "http://localhost:9200/_cluster/settings?include_defaults=true&flat_settings=true" | Select-String -Pattern 'max_shards_per_node'

# 单个分片的段数与体积
curl -s "http://localhost:9200/goods/_segments?pretty" | Select-String -Pattern 'size_in_bytes|num_committed_segments'

估算时务必以 pri.store.size（主分片体积）为基准，store.size 已含副本。

七、常见坑

  1. 按「文档条数/100 万」直接定分片数：文档大小差异极大，必须按体积算。
  2. 堆开到 64GB：越过 compressed oops 阈值，指针变大，实际可用堆反而变少。
  3. 堆开到物理内存 100%：没有余量给文件系统缓存，性能反而崩。
  4. 分片数按「未来三年」预留：分片只能增不能减（除 reindex/shrink），但预留在初期是纯开销。
  5. 磁盘只算数据不算副本与 merge 峰值：写到一半磁盘满。
  6. 忽略快照仓库空间：增量快照也占地方，保留策略要一起算。

八、课后小结

  1. 推算链：文档量 → 索引体积 → 分片数 → 堆 → 机器规格 → 磁盘。
  2. 单分片控制在几十 GB，别太碎也别太大。
  3. 每 GB 堆 ≤ 20 分片，cluster.max_shards_per_node 默认 1000。
  4. 堆 ≤ 内存 50%、≤ 32GB（compressed oops）。
  5. 磁盘 = 数据 ×（1+副本）× 余量，还要留 merge 与快照空间。

九、思考题

  1. 一个索引 400GB、目标单分片 25GB，主分片该多少？如果业务要求「分片数必须是质数」你会怎么处理？
  2. 为什么堆超过 32GB 反而「更少」？用 compressed oops 解释。
  3. 保留 30 天的日志，用 ILM 滚动索引时，分片数与总容量怎么估？
