慢日志、profile 与 hot_threads：慢在哪一步

「查询慢」有三种完全不同的慢：查询阶段慢（算匹配与排序）、取回阶段慢（拉 _source）、集群层面慢（CPU/IO 打满）。

对应的观测工具也是三套：慢日志、profile API、hot_threads。

慢在哪一步的三段定位法｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 会用 index.search.slowlog.threshold.* 开启慢查询日志；
  2. 会用 profile: true 区分 query/fetch 耗时构成；
  3. 会用 _nodes/hot_threads 看是哪个线程在吃 CPU；
  4. 建立「先定位层次，再谈优化」的排查顺序。

四、原理拆解：profile 的数字怎么读

profile 返回一棵树：query 节点下是各子查询的耗时，collector 节点下是聚合/排序的耗时，最后还有 rewrite_time、build_scorer 这类准备开销。读法固定：

  • query 子节点占比大 → 匹配本身贵（常见：wildcard 前置、regexp、超大 bool）；
  • collector 占比大 → 聚合或排序贵（桶太多、排序字段无 doc_values）；
  • build_scorer 大 → 查询被反复构造（常见于 script 查询、复杂 bool 嵌套）；
  • fetch 大但 query 小 → 取回阶段问题（_source 太大），对应 M4-9 的裁剪。

hot_threads 是另一维度：如果 query 阶段并不慢，但节点 CPU 长期 90%，就该看「是不是别的线程池在抢」——比如 merge 线程、写入线程，或者 search 池里卡着大聚合。

六、实操

# 1) 开慢日志（按索引设置）
curl -s -X PUT "http://localhost:9200/goods/_settings" -H 'Content-Type: application/json' -d '
{ "index.search.slowlog.threshold.query.warn": "5s",
  "index.search.slowlog.threshold.query.info": "2s",
  "index.search.slowlog.threshold.fetch.warn": "1s" }'

# 2) profile 单个查询
curl -s -X GET "http://localhost:9200/goods/_search" -H 'Content-Type: application/json' -d '
{ "profile": true, "query": { "bool": { "must": [ { "match": { "title": "跑鞋" } } ],
  "filter": [ { "term": { "on_sale": true } } ] } } }'

# 3) 热点线程
curl -s "http://localhost:9200/_nodes/hot_threads?threads=3"

# 4) 正在跑的长任务
curl -s "http://localhost:9200/_tasks?actions=*search*&detailed=true"

慢日志写在节点日志文件里（logs/<cluster>.log），不是通过 API 返回。

七、常见坑

  1. 慢日志阈值设 0ms：等于全量记录，日志爆炸、磁盘写满。
  2. profile: true 上生产高频开：本身有明显开销。
  3. 只看总耗时不分阶段：把 fetch 慢误判成 query 慢。
  4. hot_threads 当长期监控：它是瞬时快照，抓不到周期性尖峰。
  5. 慢日志开了不看：最常见的浪费——开了阈值却没人读日志。
  6. 忽略 rewrite_time：查询重写开销大时，profile 树里 query 子节点会「莫名很快」。

八、课后小结

  1. 三种慢：query 慢、fetch 慢、资源慢，对应三套工具。
  2. 慢日志按阶段设阈值，默认关闭。
  3. profile 读法：query 子节点、collector、build_scorer、fetch 四块分开看。
  4. hot_threads 抓瞬时热点，_tasks 抓长任务。
  5. 定位层次比调参数重要——先证明慢在哪。

九、思考题

  1. profile 显示 query 很快但总耗时很高，问题可能在哪？
  2. 慢日志显示大量 fetch 超阈值，你会先改什么？
  3. 为什么 rewrite_time 高会让 profile 看起来「query 很快」？
