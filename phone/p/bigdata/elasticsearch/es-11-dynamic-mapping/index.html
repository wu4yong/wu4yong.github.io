分类：bigdata · elasticsearch ｜ 标签：系统课 · Elasticsearch

dynamic mapping 与 strict 模式：让结构失控之前先关上闸门

动态映射让「先写数据、后想结构」成为可能，也是生产事故的高发区：字段无限增长、日期被乱识别、类型一旦定死只能重建。

官方对它的态度很明确——能快速起步，但可能给出次优结果，生产建议显式映射。这一讲讲怎么把它变成可控的自动化。

dynamic 的三种取值分别如何处理未声明字段｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说出 dynamic 三个取值各自的行为差异；
  2. 知道官方默认的动态推断规则（字符串、日期、数字）；
  3. 会用 dynamic_templates 把某类字段批量定型；
  4. 说清 strict 上线后会发生什么，以及字段上限在哪。

dynamic_templates 就是把这套规则改成你想要的：按「字段名匹配」或「匹配映射类型」批量指定结构，官方按声明顺序匹配，命中即停。

四、原理拆解：两条最贵的失控路径

① 字段爆炸：每个新字段名都会往 mapping 里加一条，官方有 index.mapping.total_fields.limit（默认 1000）兜底，撞上就是「写不进去」。埋点类数据里 attrs.xxx 这种开放键值对，几天就能撞穿。

② 类型锁死：第一条文档把 price 写成 89（long），第二条写成 89.9（double），官方直接拒绝——类型不会「自动放宽」。这就是为什么生产必须显式声明。

strict 是最后一道闸门：任何未声明字段的写入都会被拒绝。代价是「上游加字段 → 写入全挂」，所以它必须配「变更流程」一起用，不能裸上。

六、实操

curl -X PUT "http://localhost:9200/events" -H 'Content-Type: application/json' -d '
{
  "mappings": {
    "dynamic": "strict",
    "dynamic_templates": [
      { "strings_as_keyword": { "match_mapping_type": "string",
                                "mapping": { "type": "keyword", "ignore_above": 256 } } },
      { "attrs_as_flattened": { "path_match": "attrs.*",
                                "mapping": { "type": "flattened" } } }
    ],
    "properties": {
      "event":     { "type": "keyword" },
      "ts":        { "type": "date" },
      "message":   { "type": "text" },
      "attrs":     { "type": "flattened" }
    }
  }
}'

# 合法写入
curl -X PUT "http://localhost:9200/events/_doc/1" -H 'Content-Type: application/json' -d '
{ "event": "login", "ts": "2023-10-26T09:00:00Z", "message": "user logged in",
  "attrs": { "channel": "web", "region": "cn-south" } }'

# 非法写入：未声明字段，strict 会拒绝（预期 400）
curl -X PUT "http://localhost:9200/events/_doc/2" -H 'Content-Type: application/json' -d '
{ "event": "logout", "ts": "2023-10-26T09:05:00Z", "unknown_field": "x" }'

第 3 条预期返回 strict_dynamic_mapping_exception。这条报错在生产里出现，通常意味着「上游偷偷加字段」，是好事——它把问题暴露在写入侧，而不是三个月后的检索精度。

七、常见坑

  1. 生产用 dynamic: true 图省事：字段爆炸与类型锁死两个坑都开着。
  2. 以为 dynamic: false 的字段能搜：不加入 mapping 就不建倒排，搜不到（但 _source 里还在）。
  3. strict 裸上无变更流程：上游加一个字段，整条写入链路挂掉。
  4. 数字写成字符串被 keyword 处理：numeric_detection 默认关闭，"89" 会被当字符串。
  5. 日期自动识别误判：像 "2023/10/26" 这类值会被识别成 date，之后写 "v1.2" 就冲突。
  6. dynamic_templates 顺序写反：官方按顺序匹配、首个命中生效，宽泛规则放前面会吃掉后面的精细规则。

八、课后小结

  1. dynamic 四态：true 自动推断、false 忽略、strict 拒绝、runtime 查询期字段。
  2. 官方默认：字符串→text+.keyword，像日期的字符串→date，纯数字字符串不变数值。
  3. 生产首选显式 mapping，strict 必须配变更流程。
  4. dynamic_templates 按声明顺序匹配，命中即停。
  5. 字段上限 total_fields.limit 默认 1000，开放键值对要用 flattened 收纳。

九、思考题

  1. 上游业务方坚持「随时能加字段、不能改代码」，你会给 false 还是 strict？说明代价与保底方案。
  2. numeric_detection 官方默认关闭，如果打开会带来什么风险？
  3. 一个索引已有 800 个字段，还剩 200 个额度，你会怎么规划才能不撞上限？
