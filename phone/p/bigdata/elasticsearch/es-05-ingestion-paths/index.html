数据怎么进 ES：摄入路径全景与选型

M1 的最后一讲解决一个工程上天天被问到的问题：数据到底该用什么方式灌进 ES。

官方按「有没有时间戳」把数据分成两类，给出了两条完全不同的推荐链路——选错了不是慢一点，而是索引会无限膨胀、生命周期管不住。

官方按「数据是否有时间戳」区分两条摄入路径：有时间戳走 data stream，其余走普通索引｜依据 Elasticsearch 官方文档 8.17 自绘

三、理论讲解：官方按「有没有时间戳」分两条路

The option that you choose depends on whether you’re working with timestamped data or non-timestamped data, where the data is coming from, its complexity, and more.

——Elastic 官方文档《Elasticsearch basics → Add data to Elasticsearch》

第一类：通用内容（general content） —— 没有时间戳的数据，比如商品目录、站点内容、向量嵌入、知识库文档。官方给四条路：

两条路的分界，其实是索引形态的分界：通用内容进普通 index，时间序列数据进 data stream。官方对 data stream 的定义是「optimized for append-only timestamped data，由隐藏的、自动生成的后备索引组成」。这句话里每个词都有用：

  • append-only：只追加，不按主键更新历史；
  • timestamped：必须有时间字段（ECS 规范下是 @timestamp）；
  • 后备索引自动生成：写入时自动滚到新索引，不需要你手工建 logs-2023.10.08 这种名字。

四、原理拆解：为什么日志不能直接灌普通索引

假设你用普通索引 logs 收日志，跑三个月会撞上三件事：

  1. 分片只增不减：一个索引的主分片数固定，但数据量涨 10 倍后，单分片体积超出稳妥区间（M2-1 会讲分片体积经验值），检索长尾变严重；
  2. 删不动：日志按天淘汰，普通索引只能 _delete_by_query 逐条删（产生大量删除标记，段合并压力大）或整索引重建；
  3. 生命周期不可管：官方 ILM（索引生命周期管理）的整套机制（hot → warm → cold → delete）是围绕「多索引 + 别名/数据流」设计的，单索引上根本用不起来。

data stream 把这三件事一次性解决：写入时自动滚动到新后备索引，旧索引按 ILM 策略降冷、删除。代价是它要求追加写 + 时间字段，所以商品库这种要按 ID 更新的数据不适合放进去。

六、实操：一个正确的 _bulk

curl -X POST "http://localhost:9200/books/_bulk?refresh=false" \
  -H 'Content-Type: application/x-ndjson' -d '
{"index":{"_id":"5"}}
{"title":"批量写入示例","author":"wu4yong","price":45.0,"publish_date":"2023-10-08"}
{"index":{"_id":"6"}}
{"title":"第二条批量","author":"wu4yong","price":55.0,"publish_date":"2023-10-08"}
'

响应里必须逐条检查 items：

{ "took": 30, "errors": false,
  "items": [ { "index": { "_id": "5", "status": 201 } },
             { "index": { "_id": "6", "status": 201 } } ] }

errors: false 只代表「整体没抛异常」，单条可能是 status: 400（例如字段类型冲突）。生产环境里最常见的丢数据，就发生在「只看 errors 不看 items」。

顺带一句写入参数：refresh=false 是默认值，批量导入时不要改成 true，否则每批都强制刷新，段数暴涨（M1-3 已讲过代价）。

七、常见坑

  1. _bulk 写成 JSON 数组：官方要求 NDJSON，且末行要换行。
  2. 只看 errors 不看 items：部分失败是 bulk 的常态，必须逐条判断 status。
  3. 日志塞普通索引：分片膨胀、删不动、ILM 用不起来。
  4. 时间序列数据缺 @timestamp：data stream 与 EQL 都以它为前提。
  5. 应用里同步双写：一次请求同时写库和写 ES，任一失败就产生不一致（工程结论：用消息队列或 CDC 解耦，ES 侧保持可重建）。
  6. 批量导入时开 refresh=true：写入吞吐会明显下降，段合并压力上升。

八、课后小结

  1. 官方按「是否有时间戳」分两条摄入路径，这是选型的第一判断。
  2. 时间序列数据的官方首选是 Elastic Agent + Fleet，其次 Beats、Logstash。
  3. 时间序列进 data stream，通用内容进普通 index。
  4. _bulk 是 NDJSON、末行换行、逐条看 items。
  5. 生命周期管理与「多索引 + 别名/数据流」绑定，单索引上用不起来。

九、思考题

  1. 一个「订单表」既有 created_at 又要按订单号更新状态，它算通用内容还是时间序列数据？该进 index 还是 data stream？
  2. 官方为什么把 Agent + Fleet 设为时间序列数据的首选，而不是 Logstash？从运维与模板一致性两个角度说明。
  3. _bulk 一次 5000 条，其中 3 条 400，你会怎么设计重试？重试时如何避免把成功的那 4997 条再写一遍？
  4. data stream 的后备索引是自动生成的，那「按天滚动」这个策略由谁来保证？说出涉及的机制名称。
