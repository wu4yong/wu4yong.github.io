ES18-更新与删除

分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

更新与删除语义：局部更新、软删除与空间回收

ES 的「更新」不是原地改字段，而是读出整条文档、改完、重新索引一遍；「删除」也不是立刻释放空间，而是先打标记。

这两个语义决定了：为什么更新比写入贵、为什么删了数据磁盘不降。

update 的四步与 delete 延迟到 merge 才回收｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说清 _update 的内部实现（读—改—重索引）；
  2. 知道对象合并与数组合并的行为差异；
  3. 说出删除标记与 merge 的关系，解释「磁盘不降」；
  4. 会判断什么时候该用 _delete_by_query、什么时候该用索引级淘汰。

合并规则官方写明：对象字段递归合并，数组字段整体替换。所以 {"tags":["a"]} 上加 {"doc":{"tags":["b"]}} 得到 ["b"]，不是 ["a","b"]。

四、原理拆解：删除为什么不释放空间

Lucene 段是不可变的：文档「删除」只是在 .liv（live docs）里标记该文档无效，检索时会跳过。磁盘上的字节还在，只有 merge 把多个段重写成新段时，才真正丢弃被标记的文档。这就是「删了 40% 数据、磁盘只降了一点」的全部原因。

六、实操

# 局部更新
curl -X POST "http://localhost:9200/goods/_update/1" -H 'Content-Type: application/json' -d '
{ "doc": { "price": 15, "tags": ["new"] } }'

# 脚本更新（把 price 加 1）
curl -X POST "http://localhost:9200/goods/_update/1" -H 'Content-Type: application/json' -d '
{ "script": { "source": "ctx._source.price += params.inc", "params": { "inc": 1 } } }'

# 按条件批量更新
curl -X POST "http://localhost:9200/goods/_update_by_query?conflicts=proceed" -H 'Content-Type: application/json' -d '
{ "query": { "term": { "on_sale": true } },
  "script": { "source": "ctx._source.price *= 0.9" } }'

# 按条件删除
curl -X POST "http://localhost:9200/goods/_delete_by_query?conflicts=proceed" -H 'Content-Type: application/json' -d '
{ "query": { "range": { "created": { "lt": "2023-01-01" } } } }'

# 观察删除标记与段
curl -s "http://localhost:9200/_cat/segments/goods?v&h=shard,segment,docs.count,size"

执行完第四条命令后，docs.count 会小于原始总量，但 size 未必同步下降——要等 merge。

七、常见坑

  1. 关掉 _source 还想用 _update：局部更新依赖原文，官方明确受限。
  2. 以为数组合并：官方是整体替换，追加要写脚本。
  3. 删除后期待磁盘立刻下降：要 merge 才回收。
  4. _delete_by_query 当日常清理：对在线索引压力大，且反复产生删除标记；日志场景用 ILM。
  5. conflicts=proceed 无监控：并发写造成的版本冲突被静默跳过，数据可能没改到。
  6. _update_by_query 前后不做对比校验：改错条件会一次性污染大量文档。

八、课后小结

  1. 更新 = 读 + 改 + 重索引，比写入贵。
  2. 对象递归合并、数组整体替换。
  3. 删除是打标记，空间靠 merge 回收。
  4. 批量改/删要用 _update_by_query / _delete_by_query，并关注冲突与资源。
  5. 时间序列清理优先用 ILM 淘汰索引，而不是逐条删。
