五种查询语言怎么选：Query DSL、ES|QL、EQL、SQL、KQL

官方在基础篇里列了一张表，五种查询语言并排摆着。

很多人第一次看到会犯选择困难，其实只要记住一句话：端点不同、能力不同、适用场景不同，选错了不是「麻烦一点」，而是「能力根本给不了」。

同一个 Lucene 内核的五种入口：能力范围与适用人群各不相同，KQL 只在 Kibana UI 内部生效｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说清五种语言各自对应的 API 端点，以及「端点决定能力」的含义；
  2. 判断一个需求该用 Query DSL 还是 ES|QL，尤其知道 8.17 里 ES|QL 的边界；
  3. 写同一需求的三份等价实现（DSL / ES|QL / SQL），能互相对照；
  4. 知道 KQL 只是 Kibana 的 UI 层语法，不能当服务端 API 用；
  5. 说出 EQL 的硬前置条件与适用场景。

三、理论讲解：官方这张表怎么读

Elasticsearch provides a number of query languages for interacting with your data. Query DSL is the primary query language for Elasticsearch today. ES|QL is a new piped query language and compute engine which was first added in version 8.11. ES|QL does not yet support all the features of Query DSL.

——Elastic 官方文档《Elasticsearch basics → Search and analyze data》

读这张表要读出三层意思：

  1. 能力轴：Query DSL 是全集，其它都是子集。任何「官方只在 DSL 里有」的能力（全文检索、聚合细节、打分微调），其它语言拿不到。
  2. 端点轴：语言和端点是绑死的。把 DSL 语法发给 _query 不会「降级执行」，只会报错。
  3. 场景轴：ES|QL 与 EQL 都偏向时间序列（日志、指标、事件），SQL 偏向 BI 报表，KQL 偏向人在 Kibana 里手查。

3.1 为什么还要引入 ES|QL

官方给的理由是「管道式语言 + 新的计算引擎」，并且明确它「increasingly used across Kibana tools」。管道的直观好处是：FROM 数据源 | WHERE 过滤 | STATS 聚合 | SORT 排序 | LIMIT 取数，从左到右就是数据流，读起来比嵌套 JSON 顺。代价是能力尚未追平 DSL——所以本课程主线仍用 DSL，ES|QL 放在 M5-6 单独讲。

3.2 SQL 只读这件事要记牢

Elasticsearch SQL 的定位是「让熟悉 SQL 的人查 ES 数据」，面向 JDBC/ODBC 与 BI 工具。它不是 MySQL 的替代品：官方文档里的 SQL 能力集中在查询（SELECT 语义），不承担 DML 写入。想写数据还是走 _doc / _bulk。

四、原理拆解：同一个需求，三种写法

需求：查 books 里价格大于 50、标题含「系统课」的书，按 publish_date 倒序取 5 条。

Query DSL（走 _search，filter 上下文不打分）：

GET /books/_search
{
  "size": 5,
  "query": {
    "bool": {
      "must":   [ { "match": { "title": "系统课" } } ],
      "filter": [ { "range": { "price": { "gt": 50 } } } ]
    }
  },
  "sort": [ { "publish_date": "desc" } ],
  "_source": ["title", "price", "publish_date"]
}

ES|QL（走 _query，注意这里没有全文检索能力，只能做数值/精确条件）：

POST /_query
{
  "query": """
    FROM books
    | WHERE price > 50
    | SORT publish_date DESC
    | LIMIT 5
    | KEEP title, price, publish_date
  """
}

SQL（走 _sql，适合 BI 接入）：

POST /_sql?format=json
{
  "query": "SELECT title, price, publish_date FROM books WHERE price > 50 ORDER BY publish_date DESC LIMIT 5"
}

三份写法都能拿到「价格大于 50 的前 5 条」，但只有 DSL 那份做了标题全文检索。这就是官方表格里那句「ES|QL does not yet support full-text search」的实际后果。

KQL 则在 Kibana 的搜索框里写成：

price > 50 and title: "系统课"

它只影响 Kibana 的界面查询，不会变成可被应用调用的 API。

六、实操：三种语言都跑一遍

# DSL
curl -s -X GET "http://localhost:9200/books/_search" -H 'Content-Type: application/json' -d '
{ "size": 5, "query": { "bool": { "must": [ { "match": { "title": "系统课" } } ],
  "filter": [ { "range": { "price": { "gt": 50 } } } ] } },
  "sort": [ { "publish_date": "desc" } ] }'

# ES|QL（若版本低于 8.11 会直接报未知端点）
curl -s -X POST "http://localhost:9200/_query" -H 'Content-Type: application/json' -d '
{ "query": "FROM books | WHERE price > 50 | SORT publish_date DESC | LIMIT 5 | KEEP title, price" }'

# SQL
curl -s -X POST "http://localhost:9200/_sql?format=json" -H 'Content-Type: application/json' -d '
{ "query": "SELECT title, price FROM books WHERE price > 50 ORDER BY publish_date DESC LIMIT 5" }'

三条命令的输出格式各不相同：DSL 是 hits.hits，ES|QL 是 columns + values，SQL 是 columns + rows。写客户端封装时不要试图统一成一种结构，老老实实按端点解析。

七、常见坑

  1. 把 DSL 发给 _query：端点是能力的边界，语法不通用，只会报错。
  2. 以为 ES|QL 能全文检索：8.17 官方表格明确「Does not yet support full-text search」，标题类需求仍走 DSL。
  3. KQL 当 API 用：KQL 只在 Kibana 界面生效，服务端没有对应端点。
  4. EQL 数据缺 @timestamp：官方要求事件数据必须含该字段，否则查询无从排序。
  5. 拿 SQL 当写入口：SQL 能力集中在查询，写入要走 _doc / _bulk。
  6. 版本没对齐：ES|QL 是 8.11 才有的端点，7.x 集群上照抄会 404。

八、课后小结

  1. 五种语言对应五个端点，端点即能力边界。
  2. Query DSL 是全集，其余都是它的子集或面向特定场景的语法糖。
  3. ES|QL 的优势是管道式表达与 Kibana 集成，短板是 8.17 还不支持全文检索。
  4. EQL 面向事件序列，前置条件是 @timestamp；SQL 面向 BI，只读。
  5. KQL 是 UI 层语法，不要写进服务端调用。

九、思考题

  1. 产品经理要求「用 ES|QL 写全文检索，理由是新语法更好维护」，你怎么回？给出官方依据与替代方案。
  2. 一个 BI 团队要用 Power BI 直连 ES 做报表，你会给他们 SQL 还是 DSL？说清两条路的维护成本。
  3. 同一份需求在 DSL 与 ES|QL 下返回结构不同，客户端封装时你会在哪一层做适配？为什么？
  4. EQL 要求 @timestamp，如果历史数据里字段叫 event_time，你会怎么处理？代价是什么？
