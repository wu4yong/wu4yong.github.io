ES51-ES 不做主库

分类：bigdata · elasticsearch ｜ 标签：Elasticsearch · 系统课

与业务侧的边界：ES 不做主库

最后一讲回到最容易被忽视的问题：把 ES 当主库。它能搜、能聚合、能扛高并发查询，但它的写入语义、事务能力、更新机制，都不是为「唯一数据源」设计的。

官方自己的定位是「distributed search and analytics engine」，不是数据库。

三条同步通道与主库、检索引擎的分工｜依据 Elasticsearch 官方文档 8.17 自绘

一、学习目标

  1. 说清 ES 不适合做主库的四条硬理由；
  2. 分清双写、CDC、发件箱三种同步方式的取舍；
  3. 会用「幂等 id + 版本控制 + 对账」设计最终一致；
  4. 能对外解释「为什么不以 ES 为准」。

四、原理拆解：为什么「近实时」决定了它不能当真相源

写入 ES 后，文档先进入 buffer 与 translog，只有 refresh 之后才进入新的段并对搜索可见。这意味着「写成功」与「能查到」之间存在一个时间窗。任何「下单后立刻按下单号查详情」的场景，如果走 ES，就可能查不到——除非显式 refresh=wait_for，而那样会拖慢写入。

更新机制同理：ES 的「更新」是取回原文、修改、重新索引，旧文档只被标记删除。这意味着高频原地更新会持续产生垃圾段，merge 压力上升。关系型数据库的原地更新语义，在 ES 里没有对应物。

所以正确的关系是：主库是真相源，ES 是可重建的检索副本。判断标准很简单——「删掉整个 ES，能否从主库把索引全量重建回来」？能，才是健康架构。

六、实操

# 幂等写入：用业务主键做 _id，重复写不会产生重复文档
curl -s -X PUT "http://localhost:9200/goods/_doc/SKU-1001" -H 'Content-Type: application/json' -d '
{ "sku": "SKU-1001", "title": "轻量跑鞋", "price": 299, "updated_at": "2024-02-23T10:00:00+08:00" }'

# 带版本控制的条件更新（避免旧数据覆盖新数据）
curl -s -X POST "http://localhost:9200/goods/_update/SKU-1001?if_seq_no=12&if_primary_term=1" -H 'Content-Type: application/json' -d '
{ "doc": { "price": 279 } }'

# 对账：抽样比对主库与 ES 的条数与关键字段
curl -s -X GET "http://localhost:9200/goods/_count" -H 'Content-Type: application/json' -d '
{ "query": { "range": { "updated_at": { "gte": "now-1d" } } } }'

同步链路上，_id 用业务主键 + updated_at 字段是两条最基本的「可对账」设计：既能幂等重放，也能按时间窗做增量校验。

七、常见坑

  1. 把 ES 当唯一数据源：一次误删索引就是全量数据事故。
  2. 双写不做补偿：一处写失败就永久漂移。
  3. 依赖「写完即查」：近实时窗口导致偶发「查不到」。
  4. 高频原地更新：段垃圾暴涨，merge 追不上。
  5. 把副本当备份：副本与主分片在同一集群，误删一起没。
  6. 不做对账：漂移积累到用户可见才发现。

八、课后小结

  1. ES 的定位是检索引擎，不是主库。
  2. 四条硬理由：近实时、无跨文档事务、更新即重建、无 JOIN。
  3. 同步首选 CDC/发件箱，双写需补偿，最终一致要靠幂等与对账。
  4. 判据：删掉 ES 能否从主库全量重建。
  5. 副本不是备份，快照才是。
