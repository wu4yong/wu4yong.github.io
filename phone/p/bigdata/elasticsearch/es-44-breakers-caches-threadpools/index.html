熔断器、缓存与线程池：内存是怎么被守住的

ES 保护内存靠三层：熔断器在分配前拒绝、缓存决定什么值得留、线程池决定请求排队还是直接拒绝。

三者协同的结果就是：宁可返回 429 或 circuit_breaking_exception，也不让 JVM 先 OOM。

配图 44-1｜提示词：三层防护塔。最上层一排熔断器开关，标 total 70%、fielddata 40%、request 60%，旁边一个红灯 circuit_breaking_exception；中层两块缓存：node query cache 10% 与 shard request cache，标「只对 filter 结果 / size:0 请求」；最下层三个线程池方块 search、write、get，队列满时抛出 429。深色星空背景，青蓝为主，告警红。

一、学习目标

  1. 记住四个主要熔断器的默认上限，并能说清「它在拦什么」；
  2. 知道 query cache 与 request cache 各自缓存什么；
  3. 会用 _nodes/stats 看线程池与拒绝数；
  4. 明白 429 与熔断异常的区别。

四、原理拆解：熔断是「预判」，不是「事后」

熔断器在分配内存之前估算这次操作要多少，加上已用量超过阈值就直接抛 circuit_breaking_exception。所以它保护的是「不要让一次大聚合把堆吃光」，代价是误判——估算偏保守时会「明明还有内存却拒绝」。

fielddata 熔断占 40% 是有原因的：它是唯一会把正排数据搬进堆的结构（text 字段排序/聚合时触发），最容易被大字段打爆。真正的解法不是调大熔断，而是给字段加 keyword 子字段并避免对 text 聚合。

六、实操

# 熔断器与线程池现状
curl -s "http://localhost:9200/_nodes/stats/breaker,thread_pool,jvm?pretty" | Select-String -Pattern 'tripped|limit_size|queue|rejected|heap_used_percent'

# 只看拒绝数
curl -s "http://localhost:9200/_cat/thread_pool?v&h=node_name,name,active,queue,rejected,completed"

# 缓存命中
curl -s "http://localhost:9200/_nodes/stats/indices/query_cache,request_cache?pretty"

rejected 持续增长就说明「队列长期满」，这是扩容或优化查询的信号，不是调大队列能解决的。

七、常见坑

  1. 遇到熔断就调大 limit：只是把 OOM 推后，问题根因还在。
  2. 对 text 字段排序/聚合：fielddata 吃堆，官方不建议。
  3. 以为 request cache 对所有查询生效：只对 size: 0 一类。
  4. 每次请求体带随机参数：缓存永久失效，命中率接近 0。
  5. 把 rejected 当集群故障：它是背压机制在工作（M3-7）。
  6. 线程池队列调得很大：请求堆积、延迟飙升，不如早拒绝。

八、课后小结

  1. total 70%、fielddata 40%、request 60%，是三层熔断的主参数。
  2. fielddata 是唯一把正排搬进堆的结构，最该防。
  3. query cache 缓 filter 结果，request cache 缓 size: 0 请求结果。
  4. search 线程池队列默认 1000，满了返回 429。
  5. 遇熔断先找「谁在吃内存」，别先调阈值。

九、思考题

  1. 一个请求报 fielddata 熔断，你会先改熔断阈值还是改 mapping？为什么？
  2. 为什么 request cache 只对 size: 0 生效？从「结果可复用性」解释。
  3. rejected 与 circuit_breaking_exception 分别代表哪一层在拦？
