窗口与水位线

无限流没有”最后一条”，想算”每分钟成交额””每半小时在线人数”，必须把流切成一段一段的窗口。窗口怎么划、什么时候算结果、迟到数据怎么办，都靠窗口机制和水位线配合。这一篇把窗口类型、触发时机、水位线策略和迟到兜底讲清楚。

流动时间轴被切成相邻窗口玻璃格，一条波浪形水位线沿轴推进，散落的迟到圆点落在波线之后

1.1 无限流为什么需要窗口

逐条聚合只能得到全局累计值，业务要的通常是”一段时间内”的统计。窗口把无界流按时间或数量切成有界集合，在这个集合上做 sum、count、avg、分组 TopN。

窗口逻辑必须解决三件事：怎么分段（窗口分配器）、什么时候触发计算（触发器）、迟到数据怎么收（水位线与宽限）。Flink 的窗口 API 把这三件事拆成可组合的组件，默认实现覆盖了大多数统计场景。

三种时间窗口的写法：

// 滚动窗口：每 1 分钟一个段
orders.windowAll(TumblingEventTimeWindows.of(Time.minutes(1)));

// 滑动窗口：窗口 10 分钟，每 1 分钟滑一次
orders.windowAll(SlidingEventTimeWindows.of(Time.minutes(10), Time.minutes(1)));

// 会话窗口：两条记录间隔超过 30 秒即断开
orders.windowAll(EventTimeSessionWindows.withGap(Time.seconds(30)));

按 key 分组后用 keyBy(...).window(...)，每个 key 独立维护一套窗口；不分组的全局窗口用 windowAll，并行度会被压成 1，大数据量下要避免。

窗口类名带 EventTime 与 ProcessingTime 后缀，对应上一篇讲的两种时间口径。选事件时间窗口才能配合水位线做乱序与迟到处理；处理时间窗口没有水位线概念，结果随回放变化，不要混用。

1.3 窗口生命周期与触发

一个窗口从创建到销毁经历：元素落入 → 窗口状态累积 → 水位线越过窗口结束时间 → 触发计算并输出 → 状态清理。默认触发器在水位线超过窗口末端时触发一次；会话窗口在空闲间隔到期后关闭。

窗口里存的是聚合状态，不是原始明细。增量聚合（ReduceFunction / AggregateFunction）每条数据直接更新状态，内存占用小；全量聚合（ProcessWindowFunction）能拿到窗口内全部元素，适合需要遍历明细的 TopN 场景，两者可以嵌套使用。

聚合函数
特点
典型场景
ReduceFunction
逐条折叠，只保留结果值
求和、最值、去重计数
AggregateFunction
累加器与输出分离，输入输出可不同类型

嵌套写法是先做增量聚合压缩状态，再把聚合结果交给 ProcessWindowFunction 补充窗口元信息，兼顾内存占用与表达能力。

1.4 Watermark 生成策略

水位线用来回答”这个窗口该到齐了吗”。策略在数据流上指定，负责从记录时间戳生成水位线：

WatermarkStrategy<Order> strategy = WatermarkStrategy
        .<Order>forBoundedOutOfOrderness(Duration.ofSeconds(10)) // 容忍 10 秒乱序
        .withTimestampAssigner((order, recordTimestamp) -> order.getEventTime())
        .withIdleness(Duration.ofMinutes(1));                      // 空闲分区不拖住水位线

orders.assignTimestampsAndWatermarks(strategy);
策略
假设
适用
forMonotonousTimestamps
时间戳单调递增，不乱序
日志按时间写入、采集顺序可靠
forBoundedOutOfOrderness
乱序有上界，设最大延迟
大多数业务流，平衡结果完整性与延迟
自定义策略
按分区特征推算水位线
多源异构、延迟分布不均

两条口径必须记牢：水位线只推进事件时间，不推进处理时间；水位线按分区分别计算，下游取已收到的最小值。某分区长时间空闲会卡住整条链路水位线，withIdleness 就是把长时间无数据的分区从水位线计算里剔除。

1.5 迟到数据：宽限与侧输出

水位线越过窗口末端后，晚到的记录就是迟到数据。处理分两层：

  • allowedLateness：宽限期内迟到数据仍进入窗口，窗口重新计算并补发结果；窗口状态在宽限期内保留，不清理。
  • 宽限期之后还到的数据，不再进入主窗口，可通过侧输出流（Side Output）单独收集，用于补偿或审计。
OutputTag<Order> lateTag = new OutputTag<Order>("late-order") {};

WindowedStream<Order, String, TimeWindow> windowed = orders
        .keyBy(Order::getUserId)
        .window(TumblingEventTimeWindows.of(Time.minutes(1)))
        .allowedLateness(Time.seconds(30))
        .sideOutputLateData(lateTag);

DataStream<Order> late = windowed.getSideOutput(lateTag);

宽限期不是越长越好：窗口状态保留越久，内存和 RocksDB 压力越大。取值按上游乱序分布的分位数定，尾部极端迟到走侧输出补数，而不是靠无限拉长宽限。

1.6 常见易错点

  • 用处理时间划窗口，却按事件时间校验结果，积压后两边对不上。
  • 上游有分区长期断流，水位线被拖住，窗口迟迟不触发；没配 withIdleness 时尤其明显。
  • 把 allowedLateness 当”永久兜底”，状态长期不清理，大状态直接拖垮后端。
  • 全局窗口 windowAll 误用在高并发链路，并行度退化为 1。
  • 水位线设得太乐观（乱序容忍不足），窗口提前关闭，结果漏掉一批数据。

1.8 清单

  1. 窗口把无限流切成有界集合，解决分段、触发、迟到三件事
  2. 滚动不重叠、滑动按步长重叠、会话按空闲间隔动态切分，全局窗口需自研触发器
  3. 增量聚合省内存，全量聚合拿得到明细，二者可嵌套
  4. 水位线按乱序上界生成，只推进事件时间；空闲分区用 withIdleness 剔除，避免拖住链路
  5. 迟到数据先走 allowedLateness 宽限重算，超宽限进侧输出流做补偿
  6. 宽限期按乱序分位数取值，不能用拉长宽限替代补数链路
