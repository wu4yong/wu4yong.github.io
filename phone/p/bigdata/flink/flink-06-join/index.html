维表关联与异步 IO

主流订单流要补城市、类目、渠道这些维度信息，维表数据量大、更新频繁，不可能全量广播到每条记录上。怎么关联外部维表、怎么避免逐条同步查询把链路拖死，是实时数仓里最常见的工程问题。这一篇讲三种关联思路、Lookup Join、异步 IO 和缓存策略，顺带区分双流 join 的几种形态。

两路流入从左侧汇入中央维表立方体，扇出异步箭头分支到并行缓存块，结果在右侧合并回流

1.1 维表关联的三种思路

方式
做法
适合
广播维表
维表变更流广播到所有子任务，内存里直接匹配
维表小、更新不频繁
预加载关联
Source 或富函数启动时全量加载，本地查找
维度稳定、数据量可控
Lookup Join
每条记录按 key 实时查外部维表（JDBC/Redis/HBase）
维表大、不能全量放内存

判断标准就是维表规模与更新频率：小表广播省掉外部查询；大表走 Lookup，靠缓存扛命中率。三种方式可以混着用——热点维度本地缓存，长尾维度回源查询。

1.2 Lookup Join 原理与配置

Lookup Join 在记录流经时按主键去外部系统查维度，查不到走维表缺失兜底。SQL 侧通过带 lookup 参数的连接器声明：

CREATE TABLE dim_city (
  city_id   STRING,
  city_name STRING,
  region    STRING,
  PRIMARY KEY (city_id) NOT ENFORCED
) WITH (
  'connector' = 'jdbc',
  'url' = 'jdbc:mysql://mysql:3306/dim',
  'table-name' = 'dim_city',
  'lookup.cache' = 'PARTIAL',       -- 部分缓存：只缓存查到过的 key
  'lookup.ttl' = '10min',           -- 缓存存活时间，过期回源
  'lookup.max-retries' = '2'
);

-- 主流按城市 id 关联维表
SELECT o.order_id, c.city_name, c.region
FROM order_log o
LEFT JOIN dim_city FOR SYSTEM_TIME AS OF PROCTIME() AS c
ON o.city_id = c.city_id;

Lookup 查询是逐条发起的：同步阻塞时一条记录卡住整个算子线程，吞吐被外部系统 RT 锁死。维表查询量大时，优先用异步 IO 并发发起请求。

1.3 Async I/O：并发查外部系统

异步 IO 的思路是：算子线程不等待外部响应，把请求发出去后继续处理下一条，响应回来再补全结果。Flink 提供 AsyncDataStream 封装这套并发模型。

AsyncFunction<Order, EnrichedOrder> asyncFunc = new AsyncFunction<>() {
    @Override
    public void asyncInvoke(Order order, ResultFuture<EnrichedOrder> resultFuture) {
        // 异步发起维表查询，回调里收集结果
        dimClient.queryAsync(order.getCityId())
                 .whenComplete((dim, ex) -> {
                     if (ex == null) {
                         resultFuture.complete(Collections.singleton(EnrichedOrder.of(order, dim)));
                     } else {
                         resultFuture.completeExceptionally(ex);
                     }
                 });
    }
};

// 无序等待：响应先后即输出先后；有序等待：按输入顺序补全
DataStream<EnrichedOrder> enriched = AsyncDataStream.unorderedWait(
        orders, asyncFunc,
        30, TimeUnit.SECONDS,   // 单次查询超时
        100);                   // 并发请求上限
要点
说明
并发上限
同时在途请求数，超过会背压，防止打爆外部系统
超时与重试
超时触发异常，按连接器策略重试，避免无限挂起
有序 / 无序
unorderedWait 吞吐高；orderedWait 保输入顺序，代价是排队等待
结果收集
回调里必须 complete 或 completeExceptionally，否则记录悬挂

异步 IO 要求外部客户端本身支持异步调用；拿到的是同步 JDBC 连接时，先换成异步驱动或用线程池模拟，别在算子线程里阻塞等待。

1.4 缓存策略

外部维表查询的成本主要在网络往返，缓存是 Lookup 性能的关键：

策略
做法
权衡
全量缓存 ALL
启动加载全表，本地命中
维表小才用，内存占用固定
部分缓存 PARTIAL
缓存查过的 key，按 TTL 过期
长尾维表常用，命中率决定回源量
缓存刷新
监听维表变更流主动失效
维度要求实时性高时搭配使用
兜底
查不到给默认值并打标记
避免脏数据拖垮主链路

本地缓存常用 Caffeine 实现，设置最大条目、存活时间和刷新策略；缓存击穿（同一 key 并发回源）要加单飞（single-flight）控制。命中率低的维度说明 key 分布漂移，要么扩缓存容量，要么重新评估维表拆分。

1.5 双流 Join 的几种形态

除了关联外部维表，两条主流之间也需要 join，容易和维表关联混在一起：

形态
条件
状态与语义
Regular Join
无条件区间，两路变更互相影响
保存两路历史状态，更新撤回旧结果
Interval Join
两路事件时间落在指定区间内
按时间边界配对，窗口到期清理状态
Temporal Join
按事件时间回溯版本化维表
维表由 CDC 版本流维护，见上一篇

Interval Join 写法上限定了时间上下界，状态可以随窗口到期清理；Regular Join 要保留两路全部历史匹配记录，维表膨胀时状态会很大，能用区间或时态关联就别用 Regular Join。

1.6 常见易错点

  • 同步 JDBC 查询塞进算子线程，吞吐被外部 RT 锁死，反压一路传到 Source。
  • 异步回调忘记 complete，记录悬挂不输出，排查时表现为数据无故丢失。
  • 并发上限设得过高，把维表数据库打挂；过低又发挥不出异步收益。
  • 缓存不设 TTL，维表更新后作业一直用旧值。
  • 用 Regular Join 关联大宽表，两路状态长期不清理，后端很快撑爆。

1.8 清单

  1. 维表关联分广播、预加载、Lookup 三种，按维表规模和更新频率选
  2. Lookup Join 逐条查外部系统，同步阻塞会锁死算子线程，量大走异步 IO
  3. 异步 IO 用 AsyncDataStream 并发发起请求，回调必须收尾；并发上限、超时、重试都要显式配置
  4. 缓存分全量与部分，按 TTL 过期，热点可监听变更主动失效
  5. 双流 join 分 Regular、Interval、Temporal 三种；Regular 保存两路历史状态，大宽表慎用
  6. 异步客户端能力、缓存命中率和状态清理策略，是维表关联性能的三个主要抓手
