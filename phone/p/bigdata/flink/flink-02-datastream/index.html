DataStream API

跑通一个 Flink 作业，代码层面就是一条流水线：从 Source 读数据，经过一连串 Transform 变换，最后交给 Sink 写出去。DataStream API 是这条流水线的编程入口，这一篇把三段式结构、常用算子、算子链和富函数讲清楚，写业务逻辑时能直接对上号。

数据 ribbon 从左侧源头流出，中段串起紧密相连的算子块，右侧汇入存储立方体

1.1 三段式结构：Source、Transform、Sink

任何流作业都能拆成三段，职责边界很清晰：

阶段
职责
典型实现
Source
构造数据流，分配时间戳与水位线
KafkaSource、FileSource、自定义 Source
Transform
逐条或按 key 分组后变换、聚合、关联
map、flatMap、filter、keyBy、process
Sink
把结果写到外部系统
KafkaSink、JDBC、文件、自定义 Sink

一段完整骨架：

StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

DataStream<Order> orders = env
        .fromSource(orderSource, WatermarkStrategy.noWatermarks(), "order-source")
        .filter(o -> o.getAmount().compareTo(BigDecimal.ZERO) > 0)
        .keyBy(Order::getUserId)
        .process(new UserOrderProcessFunction());

orders.addSink(new OrderReportSink());
env.execute("order-pipeline");

注意 execute 才真正提交作业：前面的链式调用只是在构建执行图，不触发任何数据读写。这一点和 Spark 的 lazy 求值思路一致。

1.2 入口环境与新旧 API 区分

流作业入口是 StreamExecutionEnvironment；批处理在老版本里用的是 ExecutionEnvironment，属于历史 API。新项目按 1.13 主线统一走 StreamExecutionEnvironment，有界流直接复用它，不要在教程里把两个入口混着抄。

入口
用途
说明
StreamExecutionEnvironment
流处理与流批统一作业
新项目唯一需要写的入口
ExecutionEnvironment
早期批处理环境
旧教程残留，勿用于新代码
StreamTableEnvironment
Table API / SQL 入口
与 DataStream 可互相转换

环境上的常用全局配置包括并行度、检查点间隔、重启策略，这些在提交参数或配置文件里也能覆盖，代码里写的默认值只是兜底。

1.3 常用转换算子

Transform 算子按”是否需要分组”分两类。不分组的逐条算子处理每条记录：

DataStream<String> lines = env.fromSource(textSource, WatermarkStrategy.noWatermarks(), "text");

// map：一条进一条出，做类型或字段转换
DataStream<Order> parsed = lines.map(Order::fromJson);

// flatMap：一条进多条出，适合拆分、展开
DataStream<Item> items = parsed.flatMap((Order o, Collector<Item> out) -> {
    o.getItems().forEach(out::collect);
});

// filter：保留满足条件的记录
DataStream<Item> valid = items.filter(i -> i.getQty() > 0);

需要分组聚合时先 keyBy，把相同 key 的记录送到同一并行子任务，再做 reduce 或 process：

算子
输入输出
典型用途
map
一条 → 一条
字段映射、类型转换
flatMap
一条 → 多条
列表展开、拆分明细
filter
一条 → 一条（过滤）
清洗脏数据
keyBy
按 key 重新分区
分组聚合的前置步骤
reduce
同 key 逐条折叠
累计求和、最值
union / connect
多路合并
同类型流 union，异构流 connect

union 要求两路数据类型一致；connect 允许两路类型不同，在 CoProcessFunction 里分别处理，常用于双流关联。

1.4 keyBy 与数据分区

keyBy 不是排序，而是按 key 的哈希把记录分配到对应并行子任务。同一个 key 永远落在同一个 SubTask，这是 Keyed State 能成立的前提。

分区规则由 key 的 hashCode 决定，热点 key 会让某个 SubTask 长期处于高负载，其他 SubTask 空闲。发现倾斜时先看 key 分布，再考虑加随机前缀、拆分子任务，而不是盲目调大并行度。

1.5 算子链（Operator Chain）

Flink 默认把上下游算子串成一条链，在同一个线程里依次调用，省去线程切换和序列化开销。这条链就是算子链：

机制
行为
控制方式
默认链式
上下游一对一、数据分区不变时自动串链
无需配置
startNewChain()
从当前算子起另起一条链
单个算子隔离
disableChaining()
关闭当前算子的链式合并
排查线程模型时用
slotSharingGroup
划分槽位共享组
重资源算子单独成组
valid.keyBy(Item::getSku)
     .process(new SkuAggFunction())
     .disableChaining()              // 与上下游拆开，便于单独观察
     .slotSharingGroup("heavy")      // 状态大的算子独占槽位
     .addSink(new ItemSink());

什么时候需要拆链：某算子状态特别大，想和轻量算子在槽位上隔离；或者上下游吞吐差异悬殊，串在一条线程里会互相拖慢。默认链式是性能最优解，不要为了”看起来清晰”到处拆。

1.6 富函数（RichFunction）

普通函数只做数据变换，拿不到运行时上下文。需要访问状态、注册定时器、读广播状态时，要用对应的富函数版本，例如 RichMapFunction、RichKeyProcessFunction。

富函数的生命周期方法：

public class CountUserFunction extends KeyedProcessFunction<String, Order, Long> {

    private transient ValueState<Long> countState;

    @Override
    public void open(Configuration parameters) {
        // 每个并行子任务初始化一次：取状态句柄、加载缓存
        ValueStateDescriptor<Long> desc =
                new ValueStateDescriptor<>("count", Long.class);
        countState = getRuntimeContext().getState(desc);
    }

    @Override
    public void processElement(Order order, Context ctx, Collector<Long> out) throws Exception {
        long count = (countState.value() == null ? 0L : countState.value()) + 1;
        countState.update(count);
        out.collect(count);
    }

    @Override
    public void close() {
        // 子任务结束时释放外部资源，连接、缓存在这里关
    }
}

要点：open 每个 SubTask 调一次，不是每条数据一次；状态句柄通过 getRuntimeContext() 获取；close 里务必释放外部连接，否则重启后会泄漏。

1.7 常见易错点

  • 把链式调用当成已经在跑：不调 execute，作业不会提交。
  • 在 map / flatMap 里直接新建大对象或打开连接，富函数的 open 才是初始化位置。
  • keyBy 用对象整体做 key，而对象没重写 hashCode，导致分区不可控。
  • 以为 union 能合并异构流：类型不同要走 connect。
  • 照搬旧教程里的批处理入口，混入流作业代码，部署行为和预期不一致。

1.9 清单

  1. 流作业三段式：Source 读入、Transform 变换、Sink 写出，execute 才真正提交
  2. 新项目统一用 StreamExecutionEnvironment，旧的批处理入口不要抄进流作业
  3. 逐条算子 map / flatMap / filter 不分组；聚合先 keyBy 保证同 key 同子任务
  4. union 要求类型一致，异构流用 connect 加 CoProcessFunction
  5. 默认算子链在同线程内依次调用，重资源算子可用 disableChaining 与 slotSharingGroup 隔离
  6. 富函数在 open 初始化状态与资源、close 释放连接，生命周期按 SubTask 走，不按数据走
