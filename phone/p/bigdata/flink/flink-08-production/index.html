高可用与生产运维

测试集群里跑通作业只是第一步，生产环境要面对节点宕机、版本升级、流量波动和数据链路补数。Flink 的高可用靠 JobManager 主备与持久化快照，运维靠指标监控和 Savepoint 升级流程；实时数仓里最典型的落地形态，是 CDC 捕获库表变更、经 Kafka 流入 Flink 清洗后入湖仓。这一篇把这几块串起来。

双活备节点之间带故障切换箭头，外围是监控环与表盘，一条 CDC 管道把变更行送入分层存储立方体

生产配置的基本原则：状态与快照落远端持久存储，本地磁盘只做缓存；作业关键参数（并行度、检查点间隔、重启策略）纳入配置管理，不靠手工改命令行。

1.2 HA 架构：ZooKeeper 与 K8s

JobManager 是作业协调者，单点挂了整个作业无法调度。HA 部署保留一个 Active、若干 Standby JobManager，元数据写在一致存储里，Active 故障后 Standby 接管。

部署环境
协调机制
元数据位置
ZooKeeper 集群
选主、记录作业元数据与检查点指针
ZooKeeper 节点 + 远端文件系统
Kubernetes
Leader Election，用 ConfigMap 存领导信息
K8s API + 远端持久存储

ZooKeeper 方式的典型配置：

# flink-conf.yaml：HA 元数据挂到 ZooKeeper，快照落持久存储
high-availability: zookeeper
high-availability.zookeeper.quorum: zk1:2181,zk2:2181,zk3:2181
high-availability.storageDir: oss://bucket/flink/ha
# 检查点与 savepoint 必须在 JM 之外的持久存储上，主备都能读到
state.checkpoints.dir: oss://bucket/flink/checkpoints

K8s 上部署时，JobManager 以 Deployment 多副本运行，选主由 K8s 领导选举完成；配合 Flink Kubernetes Operator 可以声明式管理作业生命周期。无论哪种方式，检查点目录不能放本地盘，否则 JM 切换后新节点读不到旧快照。

YARN 上又分 Session（集群常驻，多作业共享）和 Per-Job（每个作业独占集群）两类提交模式。生产实时数仓常见组合：长周期流作业走 Per-Job 或 K8s 独占，避免互相影响；批量补数作业按需申请 YARN 资源跑完即释放。

1.4 升级与 Savepoint 恢复

生产升级的标准流程：

  1. 停止作业前主动触发 Savepoint，拿到快照路径
  2. 修改作业代码或配置，确认状态结构兼容
  3. 从 Savepoint 恢复启动，核对位点与输出结果
  4. 观察一个业务周期，确认无重复、无丢数后下线旧版本
# 触发 savepoint 并停作业
flink stop --savepointPath oss://bucket/flink/savepoints <jobId>

# 从快照恢复，可同时调整并行度
flink run -s oss://bucket/flink/savepoints/savepoint-xxxx -p 8 ./job.jar

变更不兼容的情况：删除状态字段、改变状态类型、交换 key 语义，都不能直接从老快照恢复；需要设计状态迁移步骤，或接受清空状态重建。回滚预案要提前准备好老版本包和对应快照路径。

1.5 监控指标与告警

Flink 内置 Metrics 体系，可通过 Reporter 推到 Prometheus 等监控系统。生产至少覆盖这几类：

指标类别
关键项
告警方向
消费积压
Kafka / Source 滞后位点、记录吞吐
滞后持续上涨说明链路反压或故障
检查点
检查点成功次数、耗时、大小、失败率
连续失败或快照暴涨要立即介入
作业运行
重启次数、异常栈、Backpressure / Busy

告警要区分”瞬时抖动”和”持续恶化”：积压几分钟内回落可不打扰，检查点连续失败、作业反复重启必须立即通知。指标保留周期按排障需要设置，过早清理会丢失事后定位依据。

1.6 CDC 入湖链路

实时数仓最典型的生产链路，是把业务库变更持续同步到湖仓：

-- 采集层：MySQL CDC 读 binlog，变更写入 Kafka
CREATE TABLE order_cdc (
  order_id STRING,
  user_id STRING,
  amount DECIMAL(10,2),
  op_time TIMESTAMP(3),
  PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
  'connector' = 'mysql-cdc',
  'hostname' = 'mysql',
  'database-name' = 'trade',
  'table-name' = 'order_t',
  'username' = 'flink',
  'password' = '******'
);

链路分层通常是：业务库 binlog → CDC 采集 → Kafka 缓冲解耦 → Flink 清洗关联（ODS → DWD → DWS）→ 湖仓表（Iceberg / Paimon / Hive）。Kafka 在这里承担削峰和重放缓冲，Flink 负责口径加工，湖仓负责长期存储与分析。

运维要点：CDC 账号要有复制权限、binlog 保留期覆盖采集中断窗口；入湖 Sink 要确认提交语义，避免重复写入；补数时按位点或时间范围重放，不要整表全量重跑覆盖已有分区。

1.7 常见易错点

  • 检查点目录配成本地路径，JM 主备切换后读不到快照，恢复失败。
  • 升级前不做 Savepoint，直接换包重启，已有状态全部丢失。
  • 只监控作业存活，不看积压与检查点，故障靠下游报表发现。
  • CDC 中断后 binlog 已清理，位点无法续上，只能全量重建。
  • 入湖链路没有幂等或去重，重放后分区出现重复数据。

1.9 清单

  1. 生产四件事：HA 防单点、Savepoint 保升级、Metrics 做观测、CDC 接入仓
  2. JM 主备协调走 ZooKeeper 或 K8s 选举；检查点与 HA 目录必须在远端持久存储
  3. 部署分 Standalone、YARN、Native K8s；长作业独占资源，补数作业按需申请
  4. 升级标准流程：停作业存 Savepoint → 改代码核对兼容 → 快照恢复 → 观察业务周期
  5. 监控覆盖积压、检查点、重启反压、状态存储四类，区分抖动与持续恶化
  6. CDC 入湖链路：binlog → Kafka 缓冲 → Flink 分层加工 → 湖仓落地；注意 binlog 保留期与写入幂等
