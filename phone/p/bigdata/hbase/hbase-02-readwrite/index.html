分类：bigdata · hbase ｜ 标签：HBase

读写链路与合并

上一篇把集群角色和数据模型摆清楚了，这一篇顺着一次写入和一次读出来走：数据先进哪里、什么时候落盘、多个磁盘文件怎么合并、读的时候怎么避免把文件全翻一遍。理解这条链路，后面看 RegionServer 堆内存配比、compaction 抖动这些运维问题才有抓手。

写入先入内存缓冲再落磁盘文件，多条文件流在后台汇聚合并为有序持久化结构

1.1 写入链路：先 WAL，再 MemStore

HBase 写一条数据的顺序是固定的，官方口径必须记住：先写 WAL（Write-Ahead Log），再写 MemStore，两者都完成才向客户端返回成功。

步骤
动作
为什么这个顺序
1
客户端把 Put 发给目标 RegionServer
定位来自上一篇的 hbase:meta 缓存
2

先记日志，宕机后才能从日志回放
3

顺序不能反：如果先写内存、内存还没刷盘机器就挂，这条数据就丢了；先写 WAL，即使 MemStore 全没了，重启后也能重放 WAL 把数据恢复出来。

1.2 WAL：宕机恢复的依据

WAL 是 RegionServer 上的预写日志，默认存在 HDFS 上，它解决的是”内存数据还没落盘就宕机”的问题：

  • RegionServer 挂掉后，HMaster 把它托管的 Region 重新分配给其他 RegionServer
  • 新节点打开 Region 前，先重放该 Region 对应的 WAL，把还停留在旧 MemStore 里的写入补回来
  • 对应数据已经 flush 成 HFile 的 WAL 可以安全归档删除

WAL 的存在也解释了一个常见现象：RegionServer 长时间 GC 或卡住时，WAL 会持续增长，因为内存里的数据迟迟刷不出去，旧日志就一直不能清。

1.3 MemStore 与 flush：内存变磁盘文件

MemStore 是内存中的排序写缓冲。它写满到阈值后会触发 flush，把当前缓冲里的有序数据写成一个磁盘上的 HFile，然后清空 MemStore：

触发条件
说明
影响

单个 MemStore 写满阈值

flush 出来的 HFile 内部按 RowKey 有序，并且自带时间戳与版本信息。flush 是不可再分的落盘动作，过程中 Region 仍然可以读写，但 flush 期间内存占用不会立刻下降，需要等文件写完。

1.4 HFile：磁盘上的持久化结构

HFile 是 HBase 在 HDFS 上的实际存储格式，一个 HFile 对应一次 flush 的产物。它内部大致分为数据块、元信息块和块索引，要点是：

  • 数据按 RowKey 分块（block）存放，默认块大小 64KB 左右，读取按块加载到缓存
  • 文件尾部保存索引和 Trailer，记录每个数据块的偏移范围
  • 同一 Region 的多个 HFile 各自有序，但文件之间整体无序，读的时候需要跨文件归并

HFile 之上还会做压缩（第六篇运维篇展开压缩算法选择），压缩在块级别进行，不影响按 RowKey 的查找能力。

围绕 HFile 还有几个和读取相关的事实：

  • 一个 Region 下的 HFile 各自有序，文件之间无序，读时必须跨文件归并版本
  • 数据块按块索引定位，默认块大小在 KB 级，读取以块为单位加载进 BlockCache
  • 文件数量直接影响读放大：compaction 的核心目的之一就是把文件数量压下来

1.5 Compaction：把多个 HFile 合并

随着 flush 不断产生新 HFile，一个 Region 下的文件会越堆越多，读取要跨文件归并，代价越来越高。后台的 compaction 就是定期把若干 HFile 合并成更少、更大的文件：

类型
合并范围
做了什么
代价
Minor Compaction
选取相邻的若干小 HFile

合并一个 Region 的全部 HFile

两个易错点：

  • Minor 不清理无效版本，被覆盖的旧值和删除标记（tombstone）仍然留在文件里，只有 Major 才真正物理清除
  • Major Compaction 是重写全量数据，大表上一次跑很久，期间磁盘 IO 和网络带宽都会被占满，通常配置成在业务低峰期周期性触发，而不是一直自动跑

1.6 BloomFilter：少做无效的磁盘查找

读一行时，HBase 先看 BlockCache 和 MemStore，未命中再翻 HFile。如果每个请求都把所有 HFile 的块索引扫一遍，文件一多就扛不住。BloomFilter 是一个概率性过滤器，用位集合快速判断”某个 RowKey（或 RowKey + 列）是否可能在这个文件里”，明确不存在的文件直接跳过：

配置项
判定粒度
适用场景
ROW
按 RowKey 判断
只按整行查询，不带列条件
ROWCOL
按 RowKey + 列族 + 列限定符判断
行内只访问少数几列，定位更精确，也是默认值

官方默认 BloomFilter 是 ROWCOL。它只能保证”判断不存在则一定不存在”，判断存在时仍可能有假阳性，需要再查文件确认。BloomFilter 占用堆外内存，列非常多的大表要留意这块开销。

1.7 读取链路：归并多版本与多文件

一次 Get 或 Scan 的读取路径大致如下：

  1. 查 BlockCache（磁盘块缓存）和 MemStore，命中直接返回
  2. 用 BloomFilter 排除不可能包含目标的 HFile
  3. 对可能包含的 HFile 按块索引定位，读取数据块
  4. 跨 MemStore、BlockCache、各 HFile 归并同一路径下的版本，按时间戳倒序取满足版本数与 TTL 的结果

Scan 范围扫描和单行 Get 的区别在于：Scan 顺着 RowKey 区间顺序翻文件，能利用 HFile 的有序性批量读取，而 Get 是定点查找。

读取侧还有两个容易忽略的点：

  • 同一路径下的多个版本按时间戳倒序排列，超过 MAX_VERSIONS 或早于 TTL 的版本不返回
  • 扫描可以设置缓存行数（caching），行数太小会增加 RPC 次数，太大会单次拉回过多数据，需要按行大小折中

1.8 容易踩的坑

  • 以为写入只进内存：必须 WAL 写完才算成功，WAL 在 HDFS 上的副本配置直接影响写入延迟
  • 把 Major Compaction 当普通后台任务：它是全量重写，大表上跑起来会明显拖慢在线读写
  • 关掉 BloomFilter 省内存：文件数量上来后，关闭带来的随机读放大远大于过滤器本身的内存开销
  • 用 BlockCache 大小代替 MemStore 规划：一个管读缓存，一个管写缓冲，配比要分开算（第六篇展开）

1.10 清单

  1. 写入顺序固定：先 WAL 后 MemStore，两者都完成才返回成功
  2. WAL 存在 HDFS 上，RegionServer 宕机后由新节点重放，避免内存数据丢失
  3. MemStore 写满触发 flush，产出内部按 RowKey 有序的 HFile
  4. Minor 合并小文件但不清无效版本，Major 合并全量并物理清除过期与删除标记，需错峰
  5. BloomFilter 按位集合快速排除不存在目标的文件，默认粒度 ROWCOL，只报假阳性不报假阴性
  6. 读取要跨 MemStore、BlockCache、多个 HFile 归并版本，取最新有效版本
  7. 读缓存（BlockCache）与写缓冲（MemStore）是两套配置，运维时分别评估
