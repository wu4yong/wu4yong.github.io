HBase（一）架构与数据模型

分类：bigdata · hbase ｜ 标签：HBase

架构与数据模型

HDFS 解决了”海量数据怎么存”，但它只擅长顺序读写，不支持按主键随机查一行。业务侧真正高频的需求是：给一个主键，毫秒级取出最新值，再顺手写回一条新记录。HBase 就是跑在 HDFS 之上、面向这种海量随机读写的列式分布式数据库，这一篇先把它的集群角色和数据模型讲清楚。

多台 RegionServer 围绕元数据中枢组成分布式存储集群，数据按 RowKey 有序切片

1.1 HBase 到底解决什么问题

先把 HBase 的定位和相邻组件划清边界，避免一上来就把它当成”大号 MySQL”或”带索引的 HDFS”：

一句话：HBase 用 HDFS 当底层文件系统，把”按主键随机读写”这件事在 PB 级数据上做出来。它牺牲了跨行事务、二级索引和灵活的 Join，换来的是水平扩容和写入吞吐。

理解定位时先记住三条边界：

  • 它不是 MySQL 的分布式替代品，复杂关联查询和跨行事务要另外找方案
  • 它也不是给全文检索用的，倒排索引和分词检索属于 Elasticsearch 这类系统
  • 它的数据默认落在 HDFS 上，副本、磁盘容错由底层文件系统承担，HBase 自身管 Region 调度

1.2 集群角色：HMaster、RegionServer、ZooKeeper

HBase 集群由三类进程组成，职责边界非常清楚，面试和排障时最容易混的就是 HMaster 到底碰不碰业务数据：

角色
职责
不做什么
HMaster
Region 的分配与迁移、表的 DDL（建表 / 删表 / 改列族）、负载均衡
不参与客户端的读写数据传输
RegionServer
管理本机若干 Region，处理 Put / Get / Scan，读写 MemStore 与 HFile
不决定 Region 该放在哪台机器
ZooKeeper
Master 选举、集群状态、定位 hbase:meta 表所在 RegionServer
不存业务数据，不转发读写请求

这里有一条必须背下来的官方口径：客户端的读写都直接连 RegionServer，HMaster 只负责 Region 分配与元数据管理。所以 HMaster 短暂挂掉时，正在跑的读写不会断，受影响的只是建表、Region 迁移这类管理动作。

1.3 Region：表在集群里的切片方式

一张表不会整体放在一台机器上。HBase 按 RowKey 的字典序把表切成一段一段的 Region，每个 Region 负责一段连续的 RowKey 区间，由一台 RegionServer 托管：

概念
含义
关键点
Region
一段连续 RowKey 区间的数据
是 HBase 水平拆分与迁移的最小单位
RegionServer
一台机器上托管多个 Region
单机读写压力集中在这里
StartKey / EndKey
Region 的区间边界
区间左闭右开，边界由分裂产生

Region 数量会随着写入增长而自动分裂（split），HMaster 再把分裂出来的新 Region 调度到负载较低的 RegionServer 上。扩容新机器时，也是靠这种 Region 迁移把数据摊开，而不是做全量数据搬迁。

几个常被问到的边界细节：

  • 一个 Region 在同一时刻只由一台 RegionServer 托管，避免同一区间出现双写冲突
  • Region 分裂时，旧区间被切成两段，新段独立成为一个 Region，再由 HMaster 调度
  • 每个 Region 的起止 RowKey 与所在服务器记录在 hbase:meta 元数据表中，这张表本身也存放在 HBase 里
  • RegionServer 启动时向 ZooKeeper 注册，HMaster 据此掌握集群整体布局与负载状况

1.4 数据模型：RowKey、ColumnFamily、Cell、时间戳

HBase 的逻辑模型是一张稀疏的、按 RowKey 排序的多维映射表，理解它要从最外层往里剥：

概念
是什么
设计要点
RowKey
每行的主键，字节数组
全表按 RowKey 字典序排列，决定数据落在哪个 Region
ColumnFamily（列族）
列的分组，建表时必须定义
列族是存储与权限的单位，列族数量要少
Column Qualifier（列限定符）
列族下的具体列名
可以事后动态增加，不需要预先声明
Cell
某个 RowKey + 列 + 时间戳对应的具体值
是最小存储单元，值是未解释的字节数组
Timestamp
Cell 的版本号，写入时默认取当前时间
同一条数据可保留多个版本，按时间倒序取最新

一条完整的定位路径是：Table → RowKey → ColumnFamily → Qualifier → Timestamp → Cell。和关系库最大的区别有两点：

  • 稀疏：某一行没有的列就不占空间，不需要为不存在的值留空位
  • 多版本：同一个单元格每次写入都会留下一个带时间戳的新版本，读取时默认返回最新版本，历史版本按 VERSIONS 配置保留
  • 按字节排序：RowKey 以字节数组比较，数字、字符串的排序结果和 Java 里字符串排序一致，设计主键时要考虑字节序而不是业务直觉
  • 时间戳由服务端补：写入不显式指定时间戳时，RegionServer 取写入时刻作为版本号；显式指定后，同键后写的值不一定排在前面

补充一句一致性口径：HBase 保证单行（同一 RowKey）读写的强一致，跨行事务不在它的设计范围内，跨 Region 的多个写入之间不提供原子性。

1.5 一次定位是怎么完成的

客户端要读一行，先要知道这行落在哪个 RegionServer，这条定位链依赖元数据表：

  1. 客户端先问 ZooKeeper，拿到 hbase:meta 表所在的 RegionServer
  2. 查 hbase:meta，根据 RowKey 找到目标 Region 对应的 RegionServer
  3. 客户端直接连这台 RegionServer 发起读写

定位结果会缓存在客户端，Region 发生迁移后缓存才需要刷新。整个过程中 HMaster 不出现，这也是 1.2 节那条口径在数据面上的具体落地。

关于这条定位链的补充：

  • 客户端缓存的是”RowKey 区间 → RegionServer”映射，Region 未迁移前不需要反复问 ZooKeeper
  • Region 迁移后旧缓存可能指向已失效的服务器，客户端重试时会重新查 hbase:meta 刷新
  • hbase:meta 表本身的位置由 ZooKeeper 记录，避免再引入一层元数据查表
  • 这条链路只解决”去哪台机器”，真正的数据读写仍然由目标 RegionServer 完成

1.6 容易踩的坑

  • 把 HMaster 当成”读写入口”：它不转发数据，高并发读写压力全在 RegionServer 上，扩容要加的是 RegionServer
  • 列族随便建十几个：列族是存储和压缩的单位，列族过多会让 flush、compaction 都变重，一张表通常控制在两三个列族以内
  • 以为 RowKey 只是普通主键：它同时决定排序、Region 分布和热点位置，设计 RowKey 是 HBase 建模的核心工作（第三篇专门展开）
  • 把 Cell 当成字符串：HBase 不解释字节内容，序列化和反序列化必须由客户端自己保证一致

1.8 清单

  1. HBase 是跑在 HDFS 之上、面向海量随机读写的分布式列式数据库，牺牲跨行事务换水平扩容
  2. 三类角色：HMaster 管 Region 分配与 DDL，RegionServer 管本机 Region 的读写，ZooKeeper 管选举与元数据定位
  3. 客户端读写直连 RegionServer，HMaster 不参与数据传输，这是必须守住的官方口径
  4. 表按 RowKey 字典序切成 Region，Region 是拆分、分裂和迁移的最小单位
  5. 数据模型路径：Table → RowKey → ColumnFamily → Qualifier → Timestamp → Cell
  6. Cell 是带时间戳的多版本值，表天然稀疏，不存在的列不占空间
  7. 定位链路：ZooKeeper → hbase:meta → 目标 RegionServer，结果客户端缓存
