集群运维与调优

最后一篇从开发视角切到运维视角：RegionServer 堆内存怎么分、MemStore 和 BlockCache 各占多少、压缩算法怎么选、TTL 和版本数怎么配，以及出了问题按什么路径排查。调优没有万能参数，这一篇给的是判断顺序和边界条件，具体数值要结合压测和业务读写比例定。

内存分区与存储压缩带协同工作，监控仪表板上各节点负载保持均衡

1.1 调优先看读写比例

HBase 的资源争用主要发生在内存：写要 MemStore，读要 BlockCache，两者都从 RegionServer 堆里切。调优的第一步不是改参数，而是判断集群是写多读少还是读多写少，再决定内存往哪边偏：

业务类型
内存倾向
主要风险
写多读少
提高 MemStore 占比，关注 flush 与 compaction
内存刷盘跟不上，WAL 积压
读多写少
提高 BlockCache 占比，关注缓存命中
缓存不足，请求反复打磁盘
均衡读写
MemStore 与 BlockCache 各取稳妥比例
两边都不突出，靠分区打散热点

脱离读写比例调参数，是运维最常见的起点错误。

1.2 堆内存与 MemStore / BlockCache 配比

RegionServer 堆内存由 JVM -Xmx 指定，堆内部分给写缓冲（MemStore）和读缓存（BlockCache）。两组核心配置控制全局上限：

配置项
作用
调整思路
hbase.regionserver.global.memstore.size
堆内 MemStore 总占比上限
写多上调，读多下调，避免堆被写缓冲占满
hbase.regionserver.blockcache.size
堆内 BlockCache 总占比上限
读多上调；大堆场景可配合堆外 BucketCache

一组常见的配置片段（值仅为示例基线，需按压测调整）：

# RegionServer 堆内存由 JVM 启动参数 -Xmx 控制，这里只列 HBase 侧配比
# 写缓冲占堆比例：写多可适当上调，注意给系统和其他开销留余量
hbase.regionserver.global.memstore.size=0.4
# 读缓存占堆比例：与 MemStore 之和不宜顶满堆，防止碎片与元数据挤占
hbase.regionserver.blockcache.size=0.4

几条边界经验：

  • MemStore 与 BlockCache 占比之和不要顶到 1，堆里还要留给元数据、RPC 缓冲和临时对象
  • 堆不是越大越好：过大的堆会让单次 GC 停顿变长，RegionServer 长时间 Full GC 会被 ZooKeeper 判死
  • 高读吞吐集群推荐把块缓存放到堆外 BucketCache，减少堆内压力，具体按版本文档配置

1.3 压缩算法选择

HFile 在块级别压缩，压缩比例换 CPU。常用算法各有取舍：

压缩比
解压速度

Snappy
中等
快
在线读写为主，吞吐优先
LZ4
中等
很快
读多写少，解压延迟敏感
GZIP
高
慢
冷数据、归档存储，磁盘空间优先

选型判断：热数据在线服务用 Snappy 或 LZ4，换解压速度；长期不访问的冷数据用 GZIP，换存储成本。压缩在建表时按列族配置，不同列族可以用不同算法。

1.4 TTL 与版本数

数据不清理会无限堆积，compaction 越来越重。两张表上的生命周期参数要在建表时想清楚：

参数
控制什么
不配的后果
TTL（Time To Live）
Cell 存活秒数，过期版本在 compaction 时清除
历史数据永久留存，磁盘持续增长
MAX_VERSIONS
每个单元格保留的最大版本数
旧版本全部保留，读放大与存储都上升
# 列族级别生命周期参数，建表时通过 schema 声明
# 示例：info 列族保留 30 天、最多 3 个版本
# TTL=2592000，VERSIONS=3

注意 TTL 过期数据不是立刻物理删除，要等 Major Compaction 重写文件时才清除；只靠 TTL 不做 compaction 规划，磁盘占用不会自己掉下来。

1.5 常见故障排查路径

出问题先定位是单 Region、单机还是全局问题，再顺着链路往下查：

现象
先看什么
常见原因
单 RegionServer 压力高
该节点 Region 分布、GC 日志
热点 Region 集中在本机，或堆配置过小
写入延迟抖动
WAL 增长、flush 队列、compaction 队列
内存刷盘跟不上，后台 compaction 占用 IO
查询变慢
BlockCache 命中率、BloomFilter 状态
缓存不足，大量请求回磁盘
Region 长时间不可用
HMaster 状态、RegionServer 日志
分裂卡住、WAL 重放失败或节点掉线

排查顺序建议：先看 HMaster Web UI 上的 Region 分布与请求量，再抓 RegionServer 的 GC 日志确认是否长停顿，最后核对 WAL、flush 和 compaction 队列。不要一上来就调参数，先把瓶颈定位到读写哪一段。

1.6 调优检查清单

上线或扩容前过一遍下面几项：

  • 读写比例明确，MemStore 与 BlockCache 配比与之匹配
  • 堆大小控制在 GC 可接受范围，没有靠堆扩容掩盖问题
  • 热冷数据分列族，压缩算法与数据温度对应
  • 每张表评估过 TTL 与版本数，compaction 周期避开业务高峰
  • 热点 Region 已通过 RowKey 设计或预分区打散，不靠自动分裂硬扛
  • 监控覆盖请求量、延迟、缓存命中率、WAL 长度、compaction 队列

1.7 容易踩的坑

  • 把堆内存无脑调大：大堆 GC 停顿更长，反而增加 RegionServer 被判死的概率
  • MemStore 和 BlockCache 占比之和顶满：元数据与临时对象没有空间，容易触发频繁 GC
  • 只配 TTL 不排 compaction：过期版本要等 Major 重写才清除，磁盘不会自动释放
  • 所有列族用同一种压缩：热数据和冷数据应分开选型
  • 看到慢查询就加缓存：先确认是不是 RowKey 设计导致的大范围扫描，缓存救不了扫描代价

1.9 清单

  1. 调优先判断读写比例，再决定内存向 MemStore 还是 BlockCache 倾斜
  2. 堆内 MemStore 与 BlockCache 占比之和不要顶满堆，大堆会拉长 GC 停顿
  3. 热数据用 Snappy / LZ4 换速度，冷数据用 GZIP 换压缩比，按列族配置
  4. TTL 控制存活时间，MAX_VERSIONS 控制保留版本数，过期数据要等 compaction 物理清除
  5. 排查按 UI 分布 → GC 日志 → WAL / flush / compaction 队列的顺序定位
  6. 上线前核对读写配比、堆大小、压缩分层、生命周期参数、热点打散与监控覆盖
  7. 缓存和参数救不了 RowKey 设计缺陷，扫描层面的问题先回到主键建模
