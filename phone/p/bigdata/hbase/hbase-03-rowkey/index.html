RowKey 设计与热点治理

前两篇讲清楚了架构和读写链路，这一篇集中解决 HBase 建模里最关键的一件事：RowKey 怎么设计。RowKey 同时决定数据排序、Region 分布和访问负载，设计不好会出现写入全部压到一台机器、范围扫描根本扫不动的局面。下面先讲热点是怎么产生的，再逐个看盐析、哈希、反转和预分区这几种治理手段。

连续有序的主键流被打散前缀后均匀铺到多个存储分区上，避免单一节点堆积

1.1 为什么 RowKey 是建模核心

在 HBase 里，RowKey 不是关系库那种”随便选个唯一键”的角色，它一身兼三职：

角色
具体表现
设计不当的后果
排序依据
全表按 RowKey 字典序排列
想做的范围扫描扫不出来
分区依据
数据按 RowKey 区间落到不同 Region
负载集中到个别 Region
访问路径
Get / Scan 都从 RowKey 定位
只能按设计好的前缀查，换条件就要全表扫

所以建模时先定查询模式（点查还是范围扫、按什么字段前缀查），再反推 RowKey 拼接顺序，而不是先把表建好再补主键。

1.2 热点是怎么产生的

热点（hotspot）指大量读写集中落在少数几个 Region 上，对应的 RegionServer 压力远超其他节点。HBase 按 RowKey 字典序分区，最常见的热点来源有三类：

  • 单调递增主键：时间戳、自增 ID 这类 RowKey 越写越大，新数据全堆在最后一个 Region 上，前面的 Region 空闲
  • 集中前缀：所有 RowKey 共用同一个业务前缀（如同一个用户群、同一个门店编号），前缀区间被压成一个 Region
  • 集中后缀却按前缀查询：前缀相同、后缀分散，但 Region 仍按前缀切分，热点照旧

热点的直接表现是写入吞吐上不去、单台 RegionServer CPU 或磁盘打满，而集群其他节点很闲。

1.3 方案一：盐析（Salting）

盐析是在 RowKey 前面加一个随机分配的前缀字符，把原本连续的 RowKey 打散到多个 Region。”盐”就是有限个桶编号（如 0 到 9、a 到 f）：

原始 RowKey
加盐后
落到的分区
user001
a-user001
前缀 a 对应的 Region
user002
3-user002
前缀 3 对应的 Region
user003
f-user003
前缀 f 对应的 Region

好处是写入负载立刻被摊开；代价也很直接：点查需要知道盐值，不知道前缀只能逐个桶去扫。所以盐析适合写多读少、以批量导入为主的场景，不适合频繁按原始主键精确点查。

1.4 方案二：哈希前缀

哈希前缀是对原始 RowKey 做一次哈希，取哈希结果的前几位拼到前面。和盐析的区别在于：盐析的前缀是随机分配的，哈希前缀由原始 RowKey 确定性算出，同一个 RowKey 永远落到同一个桶：

// 用哈希前缀打散原始 RowKey，相同 key 得到相同前缀
String raw = "order202111250001";
String prefix = Integer.toHexString(Math.abs(raw.hashCode()) % 16);
String rowKey = prefix + "-" + raw;

这样既摊开了写入，又保留了可复现性：按已知 RowKey 查询时，先算哈希前缀再定位，不需要扫所有桶。代价是哈希打散后，原始字段上的范围扫描基本失效——本来按订单号顺序能扫的区间，哈希后分散在各个前缀里。

1.5 方案三：反转 RowKey

反转把 RowKey 中变化最有规律、最容易导致前缀集中的部分倒过来放。典型场景是手机号、身份证号这类后缀差异大、前缀（号段）集中的键：

  • 原始：13800000001、13800000002 号段前缀相同，容易挤在一个区间
  • 反转：10000000831、20000000831，高位变成原来的低位，分散到不同前缀

反转适合”键本身有业务规律、后缀随机性更强”的标识类主键。注意反转只改变字节顺序，不改变内容，取回原始值时再反转一次即可。它不解决范围扫描问题，只解决前缀集中问题。

1.6 预分区：建表时就把 Region 切开

默认情况下，一张新建的表只有一个 Region，所有写入先往这一个 Region 灌，写满才分裂。对数据量一开始就很大的表，这种”从零分裂”的过程会把压力集中在建表初期。预分区（pre-splitting）在建表时就按 RowKey 边界切出多个 Region，让首批写入直接分散到各分区：

# hbase shell：按十六进制边界预切 8 个分区
create 'user_table', {NAME => 'info'}, SPLITS => ['1', '2', '3', '4', '5', '6', '7']

分区边界要和 RowKey 设计对齐：如果用了哈希前缀，边界就按哈希桶的区间切；如果 RowKey 是时间 + 业务标识，就按时间前缀切。边界切得太密会产生大量小 Region，切得太疏又回到单 Region 扛写入。

1.7 Region 分裂与预分区怎么配合

Region 分裂（split）是运行期的自动行为：一个 Region 写超过上限后一分为二。预分区是建表期的手动行为，目的是跳过初期那段单 Region 扛压的阶段。两者关系如下：

手段
时机
解决什么
局限
预分区
建表时
首批写入直接分散，避免开局热点
边界要提前规划，事后调整代价大
自动分裂
运行期
随数据增长把过大的 Region 拆开
分裂瞬间有短暂抖动，热点分区仍会反复分裂

如果 RowKey 本身设计成持续递增，即使预分区，新数据还是会不断把最后一个 Region 撑大、反复分裂。所以先治 RowKey，再用预分区落地，顺序不能反过来。

1.8 选型对照与容易踩的坑

查询模式
推荐 RowKey 思路
不建议
批量写入、点查为主
哈希前缀或盐析
单调递增主键
按时间范围扫描
时间戳放高位，再接业务标识
哈希打散放在最前面
按手机号等标识点查
反转前缀
直接用号段做前缀

几个高频坑：

  • 先建表后想 RowKey：表一旦有数据，改 RowKey 等于重导全量数据，建模阶段必须定死
  • 把哈希前缀和范围扫描同时要：哈希打散牺牲顺序，二者通常只能取其一
  • 预分区边界随手填几个字母：边界和实际 RowKey 分布对不上，分区会集中在少数区间
  • .RowKey 拼接顺序里把高频查询字段放后面：HBase 只能从前缀开始匹配，字段顺序就是查询优先级

1.10 清单

  1. RowKey 同时决定排序、分区和访问路径，建模先定查询模式再反推主键拼接
  2. 热点指读写集中到少数 Region，最常见来源是单调递增主键和集中前缀
  3. 盐析加随机前缀打散写入，但点查必须知道盐值，适合批量导入场景
  4. 哈希前缀由原始键确定性算出，同键同桶，可复现点查，但牺牲范围扫描
  5. 反转主键把分散的低位提到高位，解决号段类前缀集中，不改内容
  6. 预分区在建表时切开 Region，跳过初期单 Region 扛压，边界必须对齐 RowKey 分布
  7. 先治 RowKey 设计，再用预分区落地；自动分裂不能掩盖主键层面的热点
