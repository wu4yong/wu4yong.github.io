Kafka（二）生产者与可靠性

分类：bigdata · kafka ｜ 标签：Kafka

生产者与可靠性

生产者的核心问题只有一个：这条消息到底算不算写成功了。acks 决定等几个副本确认，retries 决定失败后重不重发，幂等与事务决定重发会不会写出重复——三者串起来才是完整的可靠性方案。

批次（batch）是发送的最小单位，也是吞吐的来源

2.1 三个必配参数

# 兼顾吞吐与可靠性的一组常见配置
acks=all                      # 0/1/all，all 表示 ISR 全部确认
retries=2147483647            # 配合 delivery.timeout.ms 控制总时长
enable.idempotence=true       # 幂等生产者，避免重试产生重复
max.in.flight.requests.per.connection=5
linger.ms=10                  # 攒批时间，10–50ms 是常见折中
batch.size=32768
compression.type=lz4

enable.idempotence=true 会强制 acks=all 且 max.in.flight<=5，这不是限制而是约束：幂等需要 broker 侧按 PID + 序列号去重，乱序重发会让去重失效。

2.2 acks 的真实含义

acks
等待谁确认
风险
0
不等确认，发出去就算成功
网络或 broker 故障时静默丢数据
1
只等 leader 落盘
leader 挂掉且未同步时丢最近数据
all
等 ISR 全部确认
最慢，最安全；ISR 只剩 leader 时等同 acks=1

最后一行是关键细节：acks=all 的安全性依赖 ISR 大小。如果 min.insync.replicas=1 且副本都掉线了，集群仍会接受写入——这是很多”配了 all 还丢数据”故事的根源。min.insync.replicas=2 + replication.factor=3 才是常见生产组合。

2.3 生产者的内部流水

  1. send() 把消息交给拦截器与序列化器
  2. 分区器选分区，消息进 RecordAccumulator 里对应分区的批次
  3. Sender 线程按 broker 维度取出批次，组成一次请求发出
  4. broker 返回响应，回调 Callback 或抛出异常触发重试

第 2 步的攒批是吞吐的直接来源：batch.size 是单批次字节上限，linger.ms 是”最多等多久再发”。两条一起决定实际批次大小，调参要看平均批次字节，而不是只看配置值。

2.4 事务：跨分区原子写

props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-tx-01");

producer.initTransactions();
try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("order-events", key, payload));
    producer.send(new ProducerRecord<>("order-audit", key, auditJson));
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();   // 未提交的写入对读隔离级别下不可见
    throw e;
}

事务的价值是”两个 Topic 要么都成功要么都不成功”，代价是吞吐下降与 transactional.id 的运维复杂度（同一 id 只能有一个活跃实例）。绝大多数业务用”幂等生产者 + 下游幂等消费”就够，不必上事务。

2.5 顺序怎么保

  • 同 key 同分区：靠默认分区器，天然有序
  • 需要全局有序：只能单分区，吞吐受限
  • 开启重试后仍要顺序：max.in.flight.requests.per.connection=1，或用幂等生产者（幂等模式下最多 5 个在途请求仍保序）
  • 事务内多条消息：按发送顺序提交

2.6 容易踩的坑

  • 只调 retries 不调超时：总重试时长受 delivery.timeout.ms 限制，默认 120s，超过就抛 TimeoutException，此时消息可能已经写成功——调用方按失败处理反而制造重复。
  • 压缩算法与消费端不匹配：broker 只透传压缩批次，消费端要支持对应算法；换算法前先确认客户端版本。
  • 大消息打爆批次：单条超过 max.request.size（默认 1MB）直接报错；Kafka 不适合传大文件，要另存对象存储只传引用。
  • acks=0 用在业务消息上：丢了你也不知道，只适合埋点这类可丢数据。

2.7 自定义分区器与拦截器

默认分区器按 key 哈希、无 key 轮询。业务上需要”按地域分片””把小客户合并到一个分区”时，就得自己实现 Partitioner：

public class RegionPartitioner implements Partitioner {
    private final Map<String, Integer> regionMap = new HashMap<>();

    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionsForTopic(topic).size();
        String region = regionOf(key.toString());      // 从 key 解析地域
        return Math.abs(region.hashCode()) % numPartitions;   // 同地域落同一分区
    }

    @Override
    public void close() { }

    @Override
    public void configure(Map<String, ?> configs) {
        // 可在此读取 regionMap 等外部配置
    }
}

configure 里不要做阻塞的远程调用，它在初始化阶段执行，卡住会拖慢所有发送线程。拦截器（ProducerInterceptor）适合做统一打标、埋点、脱敏，注意它在发送线程上串行执行，里面做重活等于给自己上锁。

分区器改了要慎用：已经发出去的历史消息还在旧分区，新分区器只影响后续消息，同 key 的消费者可能在新旧分区里各有一份。

2.9 清单

  1. acks、retries、幂等三件套要一起配，单配一项没有可靠性保证
  2. acks=all 的实际安全性取决于 min.insync.replicas，生产一般 2/3 组合
  3. 攒批靠 batch.size + linger.ms，看平均批次字节调，不是看默认值
  4. 幂等生产者会锁死 acks=all 与在途请求上限，这是必要约束
  5. 事务适合跨 Topic 原子写，常规业务用幂等 + 下游幂等更划算
  6. 顺序只在分区内成立，重试要保序就得限制在途请求
  7. 重试超时后抛异常不代表没写入，调用方务必按幂等处理
  8. 自定义分区器只影响新消息，切换后同 key 可能跨新旧分区
  9. 拦截器在发送线程串行执行，别在里面做远程调用或重计算
