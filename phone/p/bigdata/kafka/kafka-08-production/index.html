Kafka（八）监控调优与故障处理

分类：bigdata · kafka ｜ 标签：Kafka

监控调优与故障处理

最后一篇讲运维视角：哪些指标必须盯、JVM 与 OS 层怎么调、出故障时的排查顺序。Kafka 的故障大多有明确信号，问题在于信号出现时没人看。

监控不是看”挂了没”，是看”离挂还有多远”

8.1 四个必看指标

指标
阈值参考
含义
UnderReplicatedPartitions
长时间 > 0
有分区副本不足，数据不安全
ActiveControllerCount
全集群合计应为 1
不为 1 说明脑裂或 controller 异常
RequestHandlerAvgIdlePercent
持续 < 30%
请求线程忙不过来，需加线程或减负载
MessagesInPerSec 与日志写入延迟
突降或抖动
生产受阻，常伴磁盘问题

再加两个消费侧指标：组的 lag 总量与 lag 增长趋势。lag 值本身不重要，”持续增长”才是问题。

8.2 JVM 与 OS 调优

# broker 启动参数（生产常见起点）
KAFKA_HEAP_OPTS="-Xmx6g -Xms6g"
KAFKA_JVM_PERFORMANCE_OPTS="-XX:+UseG1GC -XX:MaxGCPauseMillis=20 \
  -XX:InitiatingHeapOccupancyPercent=35 \
  -XX:+ExplicitGCInvokesConcurrent"

# OS 侧
vm.swappiness=1
vm.dirty_background_ratio=5
vm.dirty_ratio=60
vm.max_map_count=262144        # RocksDB / mmap 需要

堆不用给太大：Kafka 的数据主要待在页缓存里，堆大了反而拖长 GC。G1 是常规选择，MaxGCPauseMillis=20 是经验值，别设太小否则 GC 频繁。vm.max_map_count 不够时，Streams 应用会报 RocksDB 打开文件失败。

8.3 磁盘与网络排查

症状 → 检查顺序：

  1. 写入延迟升高 → 先看磁盘 iostat 的 await 与 util，再看是否有大量 segment 滚动
  2. 副本同步落后 → 看跨机柜带宽是否打满，是否有人在跑 reassign 未限流
  3. 消费延迟突增但磁盘正常 → 看下游依赖（DB 连接池、HTTP 超时）
  4. broker 频繁 GC → 看堆内对象，常见是大量小请求 + 过量 fetch 缓存

磁盘是唯一不能用”加机器”绕过的瓶颈：单分区写入速率受单盘限制，扩容只能加分区并分散到不同盘。

8.4 故障处置清单

broker 挂了一台

  • 确认副本在其他节点上、UnderReplicatedPartitions 是否回落
  • 重启前检查 log.dirs 是否完整，别在磁盘故障时反复重启
  • 重启后观察 ISR 恢复速度，慢说明网络或磁盘有问题

全组 rebalance 循环

  • 看日志里 CommitFailedException 与 max.poll.interval.ms
  • 降 max.poll.records，确认处理逻辑里没有长阻塞
  • 检查 session.timeout.ms 与 heartbeat.interval.ms 是否被调得过激进

位移丢失导致全量重读

  • 查 __consumer_offsets 副本数与是否被误删
  • 确认没有用 auto.offset.reset=earliest 的新组名重启
  • 业务侧先开幂等兜底，再想位移恢复

8.5 容量规划的口径

按”每天写入字节 ÷ 保留期 × 副本数 × 1.3（余量）”估原始磁盘，再留 30% 给 segment 滚动与 compact。分区数按”峰值生产 TPS ÷ 单分区可持续写入速率”估，单分区 5–10MB/s 是常见经验区间。

坑在于只算数据量不算峰值：日均能过，大促那两小时过不去，扩容来不及。

8.6 容易踩的坑

  • 把 UnderReplicatedPartitions 当瞬时抖动忽略：持续几分钟就说明有节点在拖后腿。
  • 堆设到 30G 以上：GC 停顿变长，且页缓存被挤占，吞吐反而下降。
  • 只监控 broker，不监控消费者 lag：数据在 Kafka 里安全，但业务侧已经停止更新。
  • 故障时先重启再说：不确认副本状态就重启，可能把唯一完整副本也弄坏。

8.7 告警阈值与响应口径

阈值不是照搬别人的数字，而是”在这台机器上触发时还有多少余量”：

告警项
建议阈值
响应
磁盘剩余
< 25% 预警，< 10% 严重
预警先扩盘或调保留期，严重时准备扩容
URP 持续

5 分钟

查副本所在节点、网络、磁盘
消费 lag 增长
连续 10 分钟单调上升
查下游依赖与处理耗时
broker 请求延迟 P99

分级的价值在于减少噪音：磁盘 25% 是”可以排期处理”，10% 是”现在就要动手”。只设一个阈值时，往往在 5% 才被叫醒，已经来不及。

8.9 清单

  1. 必须盯：URP、ActiveControllerCount、请求线程空闲率、写入速率
  2. 消费侧盯 lag 总量与增长趋势，”增长”才是问题
  3. 堆不用大，6G 起步，G1 + 20ms 暂停是常规起点
  4. vm.max_map_count 不够会让 Streams 的 RocksDB 直接报错
  5. 磁盘是硬瓶颈，只能靠加分区与分盘扩展
  6. broker 重启前先确认副本状态，别在磁盘故障时硬起
  7. 容量按保留期 × 副本 × 1.3 估算，并单独验峰值时段
  8. 告警要分级，单一阈值往往在余量耗尽时才响，来不及处理
  9. lag 看趋势、磁盘看两级阈值、URP 看持续时长，三者组合才准
