消费者组与位移

消费端的两个核心对象：消费者组决定谁来读哪些分区，位移（offset）决定从哪接着读。理解了这两件事，rebalance、重复消费、积压排查才有落点。

一个分区在同一时刻只能被组内一个消费者读取，这是并发的硬边界

3.1 消费者组的分配规则

同一 group 内的消费者共同瓜分 Topic 的所有分区：分区数 6、消费者 3，则每人 2 个；消费者多于分区，多出来的实例空转等 rebalance。

3.2 位移存在哪

老版本把位移存 ZooKeeper，新版本存在 Kafka 内部的 __consumer_offsets 主题（默认 50 个分区）。三个配置决定行为：

enable.auto.commit=true          # 自动提交，简单但不可控
auto.commit.interval.ms=5000     # 自动提交间隔
auto.offset.reset=latest         # 无位移时 earliest / latest / none

auto.commit.interval.ms 的语义容易被误解：它提交的是”上次 poll 返回的最后位移”，不是”处理完成的位置”。所以自动提交 + 业务处理失败 = 消息丢失。需要精确控制时改成手动提交：

props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    process(records);                                    // 业务处理完成
    consumer.commitSync();                               // 再提交位移
}

commitSync 阻塞到成功，commitAsync 不阻塞但失败不重试——常见做法是循环里 async、退出时 sync 兜底。

3.3 rebalance 的代价

触发条件：消费者加入或离开、订阅的 Topic 分区数变化、心跳超时。过程中分区归属重新分配，期间消费整体暂停。

阶段
做什么
影响
Revoke
消费者放弃已分配分区并提交位移
处理中的批次要么写完要么回滚

协调者重新计算分配方案

降低影响的手段：session.timeout.ms 别设太小（默认 45s 左右，太敏感会误判断线）、max.poll.interval.ms 要大于单批处理最坏耗时（默认 5 分钟，处理慢就报 CommitFailedException）、用增量协作式再均衡（partition.assignment.strategy=CooperativeStickyAssignor）减少全量 revoke。

3.4 从指定位移消费

# 看组的积压
bin/kafka-consumer-groups.sh --describe --group order-consumer \
  --bootstrap-server localhost:9092

# 重置位移到最早（必须先停组内所有消费者）
bin/kafka-consumer-groups.sh --reset-offsets --to-earliest \
  --group order-consumer --topic order-events --execute \
  --bootstrap-server localhost:9092

重置位移是有副作用的动作：只能在与组断开时执行，--execute 前先用不带该参数的命令预览。这说明”重放”能力很强，但不是随时可用，业务层面最好自带幂等，而不是依赖回滚位移。

3.5 重复消费从哪来

  • 处理完成但位移未提交就崩溃 → 重启后重读那段
  • 位移已提交但下游写入失败 → 需要补偿，本质是跨系统事务问题
  • rebalance 时未及时提交 → 新持有者从头续读

结论：至少一次是默认语义，正好一次要靠”消费幂等 + 位移与业务同事务”自己凑。常见落地是把位移随业务结果一起写进数据库，下次启动时从数据库读位移，而不是依赖 Kafka 内部存储。

3.6 容易踩的坑

  • max.poll.records 太大：单次拉太多，处理时间超过 max.poll.interval.ms 被判失联，反复 rebalance。
  • 多线程处理同一分区：分区内顺序会被打乱，需要顺序时按 key 分派到固定线程。
  • auto.offset.reset=earliest 用在已有组上：该配置只在无位移时生效，改它不能回溯历史，回溯要重置位移。
  • 消费者组名带环境混用：测试环境与生产共用组名，会互相抢分区，位移错乱。

3.6 批量与异步提交的组合

生产上更常见的是”批量处理 + 异步提交 + 退出时同步”的组合：

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(300));
    if (records.isEmpty()) continue;

    for (ConsumerRecord<String, String> r : records) {
        handle(r);                       // 幂等处理，失败写死信
    }
    consumer.commitAsync((offsets, e) -> {
        if (e != null) log.warn("async commit failed, rely on next poll", e);
    });
}

try {
    consumer.commitSync();               // 退出前再同步一次，兜住最后一次
} finally {
    consumer.close();
}

commitAsync 回调里的异常不要重试——下一次 poll 或后续提交会覆盖它，强重试反而可能提交更旧的位移。

Runnable 里若用多线程处理，位移提交必须串行且按”最小的已完成位移”提交：并发处理时如果前面的批次没完成却提交了后面位移，崩溃就会丢数据。

3.9 清单

  1. 分区是并发上限，消费者数不宜超过分区数
  2. 位移存 __consumer_offsets，自动提交提交的是 poll 位点，不是处理位点
  3. 要”处理完再提交”就必须关自动提交、手动 commitSync
  4. rebalance 期间全组停摆，参数要给慢处理留足 max.poll.interval.ms
  5. 重置位移只能在组离线时做，且先预览再 --execute
  6. 默认语义是至少一次，重复消费要靠业务幂等消化
  7. 需要顺序时限制 max.poll.records 并按 key 固定线程
  8. 生产推荐”批处理 + async 提交 + 退出 sync”，异步失败不要重试
  9. 多线程处理时位移按最小已完成位移提交，否则崩溃会丢数据
