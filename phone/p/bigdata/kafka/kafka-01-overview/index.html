Kafka（一）架构与核心概念

分类：bigdata · kafka ｜ 标签：Kafka

架构与核心概念

Kafka 常被当成”消息队列”用，但它真正的定位是一条可重放的分布式提交日志：写进去的数据按分区顺序落盘、按偏移量随机读，消费者自己记住读到哪。这个定位决定了后面所有设计选择，也决定了它和 RabbitMQ 那类”消费即删除”的队列在语义上不是一回事。

分区是并行单位，副本是可靠性单位，两者不要混着理解

1.1 四个基本概念

概念
含义
常见误解
Broker
一个 Kafka 服务进程
不是”一台机必有一个”，同机可多实例
Topic
逻辑上的数据类别
不是物理目录，数据落在分区里
Partition
Topic 的并行分片，有序追加
全局有序不存在，只有分区内有序
Replica

生产者写、消费者读，全部围绕”分区”发生。一个 Topic 有几个分区，理论上的最大并行度就是几——这也是为什么分区数要在建 Topic 时想清楚。

1.2 分区与顺序

分区内部是只追加的日志，每条消息拿到一个递增的 offset。相同 key 的消息经分区器哈希后落到同一分区，因此同 key 有序；不指定 key 时按轮询或粘性批次分配，顺序不保证。

顺序的边界必须说清：跨分区的顺序不存在，任何”全表有序”的需求都要退回到单分区或下游重排。单分区能给的吞吐有上限，这是拿顺序换并行度的必然代价。

1.3 副本、ISR 与 HW

每个分区有 N 个副本，其中一个 leader 负责读写，其余 follower 拉取日志。ISR（In-Sync Replicas） 是”跟得上 leader”的副本集合，落后太多的会被踢出 ISR。

术语
含义
影响
LEO
Log End Offset，下一条要写的位点
各副本 LEO 不同步说明有延迟
HW
High Watermark，ISR 中最小的 LEO
消费者最多只能读到 HW
ISR
同步副本集合
集合大小决定可用性与一致性的权衡

消费者读不到 HW 之后的数据，这条规则保证了”读到的消息在足够多副本上都存在”。所以 producer 的 acks 与 ISR 大小是一组参数，单独调其中一个没有意义。

1.4 最小可跑的环境

本地验证用官方二进制包最快，单节点 KRaft 模式（2.8 起提供预览，3.3 之后成为推荐形态）不需要再起 ZooKeeper：

# 2.8+ 单节点 KRaft 启动（示意，目录按实际改）
bin/kafka-storage.sh random-uuid
bin/kafka-storage.sh format -t <uuid> -c config/kraft/server.properties
bin/kafka-server-start.sh config/kraft/server.properties

bin/kafka-topics.sh --create --topic order-events \
  --partitions 3 --replication-factor 1 --bootstrap-server localhost:9092

老版本则是先起 ZooKeeper 再起 broker，server.properties 里配 zookeeper.connect。两种形态的客户端 API 一致，差别在元数据由谁管。

1.5 一次写入的完整链路

  1. 生产者按 key 选分区，把消息攒进批次缓冲
  2. 批次发到该分区 leader 所在的 broker
  3. leader 追加到本地日志（页缓存），并按 acks 等待副本确认
  4. 达到确认条件后返回，同时推进 HW
  5. 消费者按 offset 拉取，读到 HW 为止

第 3 步的”追加到页缓存”是 Kafka 高吞吐的关键：它不主动刷盘，靠操作系统页缓存与顺序写。代价是机器掉电可能丢最近未刷盘的数据，这也是”至少一次”语义的物理来源。

1.6 容易踩的坑

  • 把分区数当性能旋钮随手改：增加分区会让同 key 的消息落到新分区，历史顺序被打乱；减少分区官方不支持。
  • replication-factor 用 1 上生产：任何一台 broker 挂掉就有分区不可用，至少 2，重要数据 3。
  • 消费端以为”读到了就是处理完了”：位移提交与业务处理不在同一事务里，重复消费是常态，幂等要自己做。
  • 用 Kafka 存”需要删除”的任务队列：它的模型是保留 + 重放，不是出队即删；任务型队列要考虑 compact 或独立存储。

真正的分水岭是”消费完要不要留”。Kafka 留，所以能重放、能多组独立消费、能做流计算输入；RabbitMQ 删，所以队列长度是瞬时状态，堆积就等于内存压力。需要延迟消息、严格优先级这类队列特性时，Kafka 反而不合适。

1.9 清单

  1. Kafka 是可重放的分布式日志，不是”读完即删”的队列
  2. Broker 存分区，Partition 是有序追加单位，Replica 是可靠性单位
  3. 顺序只在分区内成立，同 key 靠分区器保证落同一分区
  4. ISR 决定可用性，HW 决定消费者能读到哪，两者共同构成”已提交”的定义
  5. 写入走页缓存 + 顺序写，吞吐靠这个，掉电风险也来自这个
  6. 分区数建表时定，后续只增不减，且增分区会打乱同 key 顺序
  7. 生产至少 2 副本，重要数据 3 副本
  8. 与 RabbitMQ / RocketMQ 的分水岭是”消费完是否保留”，不是吞吐数字
  9. 延迟消息、优先级这类队列特性 Kafka 不提供，需要外部方案
