存储与日志清理

Kafka 把分区实现成一个目录，里面躺着若干个日志段（segment）文件。读写性能、磁盘占用、数据保留期，全都落在这套文件结构上。

段文件是顺序写的最小单元，也是清理的粒度

4.1 一个分区目录里有什么

order-events-0/
├── 00000000000000000000.log     # 消息数据
├── 00000000000000000000.index   # 位移 → 物理位置 稀疏索引
├── 00000000000000000000.timeindex
├── 00000000000000000368.log
└── leader-epoch-checkpoint

log 是数据本体，文件名里的数字是该段起始位移。index 是稀疏索引，默认每写入 log.index.interval.bytes（4KB）记一条，查找时先二分索引再顺序扫一小段。

参数
默认
作用
log.segment.bytes
1GB
单段上限，设小会频繁滚动，设大会拖慢清理
log.retention.hours
168（7 天）
按时间保留，可改 ms/minutes/hours
log.retention.bytes
-1（不限）
单分区磁盘上限，与时间条件同时生效取更严格者
log.index.interval.bytes
4KB
索引密度，越小查找越快、索引文件越大

4.2 读一条消息要几步

  1. 定位段文件：按位移文件名二分，找到不大于目标位移的最大段
  2. 查 index：找不大于目标位移的最近索引项，得到物理偏移
  3. 从该偏移顺序扫 log，直到命中目标位移
  4. 页缓存命中则纯内存返回，否则触发磁盘读

顺序写 + 页缓存 + 稀疏索引三者合起来，就是 Kafka 用普通磁盘还能跑出高吞吐的原因。前提是不要用随机读方式访问，也就是不要频繁 seek 到远距离位移。

4.3 两种清理策略

策略
行为
适用
delete
删除超过保留期的整段文件
事件流、日志、埋点
compact
按 key 保留最新值，删除旧版本
状态快照、配置、CDC 的当前值表
delete,compact
先 compact 再按保留期删
既要去重又要有时间上限

启用 compact 的 Topic 需要 cleanup.policy=compact，并注意它不保证 key 数量下降后立即回收——压缩是后台周期性动作，磁盘占用会滞后。另一个坑是 tombstone（value 为 null 的消息）只保留 delete.retention.ms（默认 24 小时），过期后 key 会真正消失。

4.4 磁盘规划

# broker 侧磁盘与刷盘相关
log.dirs=/data1/kafka-logs,/data2/kafka-logs
num.io.threads=8
num.network.threads=3
log.flush.interval.messages=10000
log.flush.interval.ms=1000

log.dirs 配多个目录时，Kafka 会把新分区分散到不同盘，但同一分区的副本不会落到同一块盘（否则失去意义）。刷盘参数默认很宽松，靠操作系统回写；若业务不能容忍掉电丢最近数据，才需要收紧，代价是吞吐。

节点级监控看三项就够：磁盘剩余、单分区目录体积、UnderReplicatedPartitions。前两项决定还能写多久，第三项决定数据是否真的安全。

4.5 清理不及时的典型信号

  • 磁盘写入速度跟不上生产速度 → 保留期被迫缩短，消费者追不上就丢数据
  • segment 滚动过密（大量几十 MB 的段文件）→ 清理与索引开销上升
  • compact Topic 的段文件长期不收敛 → 检查 key 基数是否过高，compact 不是去重万灵药

一个常见误判：看到目录里段文件总大小远超 log.retention.bytes，以为配置没生效。实际是当前活跃段不参与清理，且清理按整段进行，所以体积会超出一点。

4.6 容易踩的坑

  • log.retention.bytes 设得比单段还小：永远删不掉，因为活跃段不删。
  • 手工删目录里的文件：Kafka 依赖索引与 checkpoint 一致性，手工删会损坏分区，正确做法是调保留策略或用 kafka-delete-records.sh。
  • 把 compact 当”按 key 去重表”无限增长：key 基数大时压缩收益低，内存与 IO 都会吃紧。
  • log.dirs 里混入非 Kafka 数据：启动扫描时会当成损坏分区处理。

4.7 段文件相关的运维命令

排查存储问题时，这几条命令比翻日志快得多：

# 看分区磁盘占用与段数
bin/kafka-log-dirs.sh --bootstrap-server localhost:9092 \
  --describe --topic-list order-events

# 直接读段文件内容（确认某条消息是否真的落盘）
bin/kafka-dump-log.sh --files /data/kafka-logs/order-events-0/00000000000000000000.log \
  --print-data-log | tail -n 5

# 按位移删除（比调保留策略更精确，但不可回滚）
bin/kafka-delete-records.sh --bootstrap-server localhost:9092 \
  --offset-json-file delete.json

delete.json 里按分区写 {"topic":"order-events","partition":0,"offset":1000}，表示删除 1000 之前的消息。这个操作直接改索引，误删无法恢复，执行前务必核对分区号。

kafka-log-dirs.sh 的输出里还有 size 与 offsetLag：前者是该分区实际占用，后者是副本同步落后量。看到同一分区在不同 broker 上 size 差很多，通常是某副本同步落后，正常状态下差异应该很小。

4.9 清单

  1. 分区目录 = 多个段文件（log + index + timeindex），段是清理与顺序写的粒度
  2. 读路径：段二分 → 索引定位 → 顺序扫 log，页缓存决定实际延迟
  3. 保留策略 delete / compact / delete,compact 三选一，按数据语义选
  4. log.retention.bytes 小于单段大小时永远不生效，活跃段不参与清理
  5. compact 是周期性后台动作，磁盘回收滞后，且 tombstone 只保留 24 小时
  6. log.dirs 多盘用于分散分区，副本必须落在不同盘
  7. 手工删文件会损坏分区，删数据请用保留策略或 delete-records 工具
  8. kafka-log-dirs.sh 的 size 与 offsetLag 能快速定位副本同步问题
  9. kafka-delete-records.sh 直接改索引，执行前必须核对分区与位移
