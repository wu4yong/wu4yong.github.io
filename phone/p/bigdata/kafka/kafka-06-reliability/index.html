顺序、积压与限流

线上 Kafka 的绝大多数事故不是”写不进去”，而是”读不过来”：消费积压、顺序错乱、重启后重复狂刷。这一篇把这三类问题的判定与处置拆开讲。

积压是结果，根因常在处理耗时、分区数与批大小之间

要让”同 key 有序”生效，三个条件必须同时满足：生产者用 key 且分区器稳定、分区数不在中途变化、消费端每个分区单线程处理（多线程要按 key 分派固定线程）。

6.2 积压怎么量化

先算清楚，再决定动作：

# 每个分区的积压量（CURRENT-OFFSET 与 LOG-END-OFFSET 的差）
bin/kafka-consumer-groups.sh --describe --group order-consumer \
  --bootstrap-server localhost:9092

再看消费速率，用一段时间的 LOG-END-OFFSET 增量估算。消化时间 = 积压总量 ÷ 净消费速率。如果这个值超过业务能容忍的窗口，就必须扩容消费者或提升单实例处理能力，而不是等它自己追上。

热 key 是最难处理的一类：分区内有序的要求与”把热 key 拆开”天然冲突。折中方案是两层结构——用复合 key（业务 key + 随机后缀）分散写入，消费端再聚合；代价是顺序变弱，需要业务能接受。

6.4 限流的两个位置

生产端限流：控制发送速率，避免把下游压垮。可用 max.in.flight.requests.per.connection 降并发、linger.ms 调批次，或直接由业务侧用令牌桶控制 send 速率。

// 简单的令牌桶限流，按每秒允许条数放行
RateLimiter limiter = RateLimiter.create(2000);   // Guava
while (hasMore()) {
    limiter.acquire();
    producer.send(record);
}

消费端限流：max.poll.records 与 fetch.max.bytes 控制单次拉取量。注意拉得多不等于处理得快，处理慢时拉太多反而增加 rebalance 风险。

6.5 重启后的”重复狂刷”

消费者重启后，如果位移未提交，会从上次提交点重读，表现为短时间大量重复消息。三种缓解：

  • 业务侧幂等（最可靠）：以业务主键 + 版本号去重
  • 缩短提交间隔：auto.commit.interval.ms 调小，代价是提交次数多
  • commitSync 与业务事务合一：把位移写进业务库，重启时从库读

第三条是很多团队最终采用的方案，因为它把”读进度”与”业务结果”绑成了一个事实。

6.6 容易踩的坑

  • 消费失败就 throw 让整批重试：一条坏消息反复卡住整个分区，应转死信主题并跳过。
  • 死信主题没配保留策略：死信本身也会积压，要配短保留期 + 告警。
  • 降 max.poll.records 当作万能药：它只是让单批变小，处理总耗时不变时改善有限。
  • 扩容消费者超过分区数：多出的实例分不到分区，扩容无效，必须先加分区。

6.7 死信队列的落地结构

坏消息不能无限重试卡住分区，标准做法是”有限重试 + 死信”：

for (ConsumerRecord<String, String> r : records) {
    try {
        handle(r);
    } catch (RetryableException e) {
        if (++attemptsOf(r) <= 3) {
            producer.send(new ProducerRecord<>("order-events-retry", r.key(), r.value()));
        } else {
            producer.send(new ProducerRecord<>("order-events-dlq", r.key(), r.value()));
        }
    }
}

6.9 清单

  1. 顺序只在分区内成立，同 key 有序需要”稳定分区器 + 分区数不变 + 单线程按 key 处理”
  2. 积压要用 LOG-END-OFFSET - CURRENT-OFFSET 量化，再算消化时间
  3. 积压根因分四类：量涨、下游慢、rebalance、热 key，处置完全不同
  4. 热 key 与强顺序冲突，只能用复合 key 弱化顺序换分散
  5. 生产端与消费端都要能限流，别只控一端
  6. 重启重复消费靠业务幂等消化，或把位移与业务结果同库
  7. 扩容消费者前先看分区数，超过分区数的实例是白加
  8. 坏消息要”有限重试 + 死信”，不能让一条消息卡死整个分区
  9. 死信与重试主题的分区数要与主主题一致，保留期分别按需设短/设长
