Kafka Streams 与 Connect

Kafka 自己带了两套”上下游”能力：Streams 做流式计算（拓扑在应用内跑），Connect 做数据搬运（源与汇的标准化连接器）。它们都不需要独立集群，是库与进程，不是平台。

Streams 算、Connect 搬，两者常常串在同一条链路里

7.1 Streams 的三个核心抽象

抽象
含义
关键点
KStream
事件流，每条记录独立
追加语义，不保存历史
KTable
变更日志视图，按 key 保留最新
底层是 compacted topic
GlobalKTable
全量广播到每个实例
适合小维度表，占内存

KStream 与 KTable 的差别不是类型包装，而是同一份数据被如何解读：把 topic 当事件流读就是 KStream，当”当前值集合”读就是 KTable。

7.2 一个最小拓扑

StreamsBuilder builder = new StreamsBuilder();

KStream<String, String> orders = builder.stream("order-events");
KTable<String, Long> counts = orders
    .groupByKey()
    .count(Materialized.as("order-count-store"));

counts.toStream().to("order-counts", Produced.with(Serdes.String(), Serdes.Long()));

KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();

Materialized.as("order-count-store") 建立的是本地状态存储，默认由 RocksDB 承载，并通过 changelog topic 在实例间同步。这个 changelog 是状态恢复的唯一依据——它的副本数不能是 1。

7.3 时间语义与水位线

概念
含义
取舍
Event time
事件自身携带的时间戳
结果正确，需处理乱序
Processing time
处理机器的时间
简单，受延迟影响大
Ingestion time
进入 Kafka 的时间
折中，接近 event time

窗口计算必须选 event time 才靠谱，代价是要处理乱序：grace 配置允许迟到多久内仍算入窗口，suppress 用于等窗口关闭后再输出。默认的”窗口一结束就输出”会让结果分成多条，下游要能接受这种更新语义。

7.4 Connect 的定位

Connect 把”从 A 读到 B”标准化成配置，不用写代码：

{
  "name": "mysql-source-orders",
  "config": {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "tasks.max": "1",
    "database.hostname": "mysql.example.com",
    "database.server.id": "184054",
    "topic.prefix": "cdc",
    "table.include.list": "shop.orders",
    "key.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter"
  }
}

tasks.max 决定并行度，但真正的上限由源端的可分片性决定——MySQL binlog 单实例只能一个 task 读，加 task 无效。

7.5 两套工具的边界

  • Streams 适合：有状态聚合、窗口、join、实时指标；拓扑复杂度中等、希望随应用一起部署
  • Connect 适合：整表同步、CDC、写入数仓或 ES；配置化、可运维、少改动
  • 都不适合：复杂机器学习推理、跨系统强事务、需要外部编排的长流程

如果只是为了”把数据从一个库搬到另一个库”，优先 Connect；如果要做”实时聚合出报表指标”，优先 Streams；两者常常组合——Connect 抽数进 Kafka，Streams 算指标，再 Connect 写出去。

7.6 容易踩的坑

  • changelog topic 副本数为 1：实例重启后状态无法恢复，只能全量重算。
  • 本地状态目录没配持久盘：容器重启后 RocksDB 丢失，恢复全靠 changelog 回放，启动时间飙升。
  • Connect 的 offset topic 用了默认 1 副本：connect-offsets 是连接器的进度账本，单副本会丢进度导致重复同步。
  • 窗口无条件输出：下游把它当”最终结果”，实际同一窗口会多次更新。

7.7 并行度与容错

Streams 的并行度由”任务数（task）”决定：一个分区对应一个任务，一个任务对应一条处理线程。所以分区数就是 Streams 应用的并行上限，应用实例再多也只是分摊任务。

num.stream.threads=4
processing.guarantee=exactly_once_v2      # 2.5+ 支持，事务写 + 事务提交位移
state.dir=/data/kafka-streams-state       # 必须落在持久盘
standby.replicas=1                        # 热备副本，缩短故障恢复

processing.guarantee=at_least_once 是默认值，重启可能重复输出；exactly_once_v2 用事务把”输出 + 位移”一起提交，代价是延迟与事务开销。选择标准很简单：下游能不能吃重复，能吃就选轻的。

standby.replicas=1 在别的实例上维护热备状态，故障切换时不必从 changelog 全量回放——这是把”分钟级恢复”压到”秒级”的关键配置，代价是多一份状态存储的磁盘与同步流量。

7.9 清单

  1. Streams 是库，跑在应用进程里，不需要独立集群
  2. KStream 看事件、KTable 看当前值，同一 topic 两种读法
  3. 本地状态靠 RocksDB + changelog，changelog 副本数必须 ≥2
  4. 窗口用 event time，配 grace 处理乱序，输出可能是多次更新
  5. Connect 是配置化的搬运工，tasks.max 受源端可分片性限制
  6. connect-offsets 不能单副本，否则进度丢失重复同步
  7. 先看清是要”搬”还是”算”，再决定用 Connect 还是 Streams
  8. Streams 并行度上限是分区数，num.stream.threads 只是单机内的线程数
  9. exactly_once_v2 用事务换语义，standby.replicas=1 换恢复速度，两者都要算成本
