集群搭建与扩缩容

单机跑通和线上稳定是两件事。集群要考虑的是：元数据由谁管（ZooKeeper 还是 KRaft）、副本怎么摆、扩容时分区的迁移路径，以及缩容时不能一把停。

副本迁移是扩容的核心动作，带宽和限流参数决定它会不会拖垮线上

5.1 两种元数据架构

形态
元数据存放
现状
ZooKeeper 模式
外部 ZK 集群存 controller 选举与元数据
长期可用，运维多一套组件
KRaft 模式
集群内部 controller quorum（Raft）
2.8 预览，3.3 起推荐，无需 ZK

KRaft 的关键是 controller quorum 的奇数节点数（3 或 5），它承担原 ZK 的角色。迁移路径官方提供 kafka-storage.sh 与双写过渡方案，但生产迁移要按官方文档逐步走，不建议脚本一把梭。

5.2 一个可用的三节点配置

# server.properties 关键片段（broker.id 各节点不同）
broker.id=1
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
advertised.listeners=PLAINTEXT://kafka-1.example.com:9092
log.dirs=/data/kafka-logs
num.partitions=6
default.replication.factor=3
min.insync.replicas=2
offsets.topic.replication.factor=3
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2
auto.create.topics.enable=false

advertised.listeners 是最容易配错的一项：客户端拿到的是这个地址，配了内网 IP 而客户端在外网，就会连接超时。auto.create.topics.enable=false 建议关掉，避免拼错 Topic 名时悄悄建出默认 1 副本的主题。

5.3 副本分布与机架感知

Kafka 默认按 broker 轮转分配副本，不感知机架。跨机架部署时要给 broker 配 broker.rack=rack-a，分配器才会尽量把副本摊到不同机架。三副本的典型期望是”两个同机架 + 一个跨机架”，全靠这个参数。

同机架两副本能扛单机故障，跨机架那份抗机架级故障（交换机、供电）。如果所有副本都在同一机架，等于把风险叠在一处。

5.4 扩分区与扩 broker

两件事要分开做，顺序也有讲究：

  1. 先加 broker：新节点启动后只是空目录，不会自动接管分区。
  2. 再迁移分区：用 kafka-reassign-partitions.sh 生成迁移方案，先 --generate 再 --execute，最后 --verify。
# 1) 生成方案（topics-to-move.json 里写要迁移的 topic 列表）
bin/kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
  --topics-to-move-json-file topics-to-move.json \
  --broker-list "1,2,3,4" --generate

# 2) 执行（加限流，避免打满网络）
bin/kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
  --reassignment-json-file plan.json --execute \
  --throttle 10485760

# 3) 校验
bin/kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
  --reassignment-json-file plan.json --verify

--throttle 是字节/秒的迁移限流，不给限流就把跨机柜带宽吃满，线上消费延迟会立刻抬起来。

5.5 缩容的正确姿势

先迁移再停机，顺序不能反：

  1. 把待下线 broker 上的分区迁走（同上，--broker-list 只写保留节点）
  2. 确认 --verify 完成、该节点上无 leader
  3. 停 broker，观察 UnderReplicatedPartitions 回到 0
  4. 清理其 log.dirs 后再复用机器

直接停机会触发副本重建，而不是迁移；重建走的是全量拉取，比计划迁移更贵。

5.6 容易踩的坑

  • offsets.topic.replication.factor 用 1：集群扩容后 __consumer_offsets 仍是单副本，位移可能丢，导致重复消费。
  • 迁移时同时做滚动重启：迁移本身在复制数据，再叠加重启，ISR 频繁抖动，可用性下降。
  • min.insync.replicas 大于可用副本数：写入直接失败（NOT_ENOUGH_REPLICAS），这是保护机制，恢复副本后再调。
  • 跨机房部署不设 rack：副本集中在一个机房，机房级故障全丢。

5.7 上线前的集群巡检

按顺序过一遍，能挡掉大部分部署事故：

# 1) 副本是否全部同步
bin/kafka-topics.sh --describe --under-replicated-partitions \
  --bootstrap-server localhost:9092

# 2) 分区分布在哪些 broker 上
bin/kafka-topics.sh --describe --topic order-events --bootstrap-server localhost:9092

# 3) 集群总体状态
bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092 | head -20

巡检的判定标准：--describe 输出里每个分区的 Isr 长度应等于 Replicas 长度；Leader 与 Replicas 的首项应一致（Kafka 会把 leader 挪到副本列表第一位）。任何分区 Isr 短于副本数，都说明有节点在拖后腿，此时不该做扩容或迁移。

5.9 清单

  1. 元数据要么交给 ZK，要么走 KRaft controller quorum（奇数节点）
  2. advertised.listeners 必须是客户端可达地址，否则连接超时
  3. 关掉 auto.create.topics.enable，Topic 显式建，副本数显式给
  4. 跨机架必须配 broker.rack，否则副本全挤在一处
  5. 扩容顺序：加 broker → 迁分区 → verify，迁移一定加 --throttle
  6. 缩容顺序：迁走分区 → 验证 → 停机，直接停会触发全量副本重建
  7. min.insync.replicas 与副本数要匹配，否则写入直接被拒
  8. 扩容与迁移前先跑巡检，Isr 长度不等于副本数时不要动手
  9. --describe 里 Leader 应等于 Replicas 首项，不一致且长期存在要查 controller
