分类：bigdata · hadoop ｜ 标签：Hadoop

YARN 资源调度与队列

HDFS 解决了数据放哪，这一篇解决算力怎么分。YARN 的核心思路是把集群的 CPU、内存统一收上来做成资源池，再按作业申请逐个发放；调度器决定”先给谁、给多少、排队还是抢占”。这一篇把角色、提交流程和三种调度器讲清楚。

中央资源总账向各工作节点分发封装好的算力容器，队列沿层级树形排布

1.1 YARN 要解决的问题

在 YARN 出现之前，MapReduce 自己管集群资源：作业框架和资源管理绑死在一起，想换一个计算框架就得再配一套机器。Hadoop 2.x 把这两层拆开，YARN 专门做资源管理，计算框架只需要按规范申请资源、在容器里跑任务。

拆开之后得到两个直接好处：

  • 同一套集群可以混跑 MapReduce、Spark、Flink、Tez，彼此只争资源，不抢管理权
  • 资源统计、队列隔离、抢占、配额这些能力集中在调度层做一次，各框架复用

代价是每个作业要多起一个 ApplicationMaster 进程，小作业的启动开销被放大，这也是短作业在 YARN 上体感偏慢的主要原因。

RM 又可以拆成两个子模块：Scheduler 纯按策略分配资源，不管权限与提交；ApplicationsManager 负责接收作业提交、协商第一个 Container 来启动 AM。理解分工时记住：Scheduler 发资源，AM 管作业，NM 管单机。

1.3 作业提交流程

一个作业从提交到跑起来，链路固定为六步：

  1. 客户端向 RM 提交作业，上传作业 jar、配置与输入切片信息
  2. ApplicationsManager 协商出第一个 Container，在某台 NodeManager 上启动 ApplicationMaster
  3. AM 向 Scheduler 注册并按任务清单申请资源（指定节点偏好、内存、vCPU）
  4. Scheduler 在满足队列配额与资源余量的前提下分配 Container，通知对应 NM 拉起
  5. Container 内执行 map/reduce 或其他框架任务，AM 持续跟踪进度与失败重试
  6. 全部任务完成后 AM 向 RM 注销并释放资源，客户端拿到最终状态

资源申请是 AM 主动拉取的模式：RM 不会把任务推给节点，而是 AM 反复询问”现在有没有满足条件的 Container”。这个节奏决定了作业在资源紧张时会长时间停留在 ACCEPTED 状态。

1.4 Container 的资源模型

Container 不是一台机器，只是一份配额声明。调度时按节点可用余量匹配，资源口径以内存为主、vCPU 为辅：

# 单机可分配的最大内存与虚拟核数，NM 上报时以此为上限
yarn.nodemanager.resource.memory-mb=8192
yarn.nodemanager.resource.cpu-vcores=8
# 单个 Container 允许申请的资源上下限，超出会被 RM 拒绝
yarn.scheduler.minimum-allocation-mb=1024
yarn.scheduler.maximum-allocation-mb=8192

内存超配是最常见的 kill 原因：任务堆内内存加上堆外、栈、直接内存之和超过 Container 配额，NM 直接杀掉进程并报 Container killed by YARN for exceeding memory limits。调优时先看物理占用，再决定是加配额还是降框架内存参数。

1.5 三种调度器：FIFO、Capacity、Fair

调度器是 YARN 里策略差异最大的部分，官方内置三种：

调度器
策略
适用场景
短板
FIFO
所有作业进一个队列，先提交先跑，后面排队
单机测试、内部小集群
大作业堵住后面所有小作业
Capacity
队列分层，每个队列有保证容量，队列内作业共享弹性余量
多团队共享集群，按部门切队列
队列间默认不抢占，闲置容量可能被占用
Fair
队列间公平共享资源，运行作业动态平分，空闲队列资源可被借用再收回
多租户、作业长短混合
配置项多，抢占与最小份额需要调

Capacity Scheduler 的核心概念是保证容量（guaranteed capacity）与最大容量（maximum capacity）：队列至少能拿到保证份额，空闲时可以借其他队列的余量，但不能超过自己的上限。它适合”每个团队保底多少，忙时可以蹭空闲”的组织形态。

Fair Scheduler 的目标是让同一时刻运行的作业在资源上尽量均分：新作业进来会从大块头作业那里逐步收回一部分容器，短作业不用长期排队。它对交互式、adhoc 查询更友好，但抢占阈值配得太激进会让长任务反复抖动。

1.6 队列配置与常见坑

Capacity 调度器的队列定义写在 capacity-scheduler.xml 里，层级队列用点号分隔：

<!-- 部门队列保底容量占集群 40%，上限不超过 80%，避免独占集群 -->
<property>
  <name>yarn.scheduler.capacity.root.data.capacity</name>
  <value>40</value>
</property>
<property>
  <name>yarn.scheduler.capacity.root.data.maximum-capacity</name>
  <value>80</value>
</property>

几个容易踩的点：

  • 只配了队列保底容量，没配上限制，一个团队的大作业把集群借满，其他队列长期排队
  • Container 内存配额只算堆内，任务的堆外与直接内存被忽略，频繁超内存被 kill
  • 把 vCPU 配成与物理核 1:1，框架线程池稍大就申请不到核；vCPU 本来就是可超分的软口径
  • 作业卡在 ACCEPTED 状态先查队列余量与最大 Container 限制，别急着怀疑集群挂了
  • 同一集群混用两种调度器不成立：RM 启动时选定一种，换调度器需要重启 RM
  • 队列 ACL 只配了提交权限，没配管理员与查看权限，后续改配额找不到可操作的人
  • Fair 抢占阈值配得过松，长任务跑到一半被反复收回容器，作业整体时长反而变长

1.7 两种调度器怎么选

选调度器先看组织形态，而不是看功能列表：

判断条件
倾向选择
理由
团队边界清晰、各有保底资源
Capacity
队列配额直观，运营成本低
作业长短混合、adhoc 查询多
Fair
短作业不必在长任务后面排长队
只有自己用的测试集群
FIFO
配置最简单，没有额外策略开销

实际存量集群里 Capacity 占多数，它的模型和部门预算对应关系最直接；Fair 更多出现在交互式分析平台。切换调度器要连同队列定义、ACL、抢占参数一起迁移，不能只改一个开关。

1.9 清单

  1. YARN 把资源管理与计算框架解耦，RM 发资源、AM 管作业、NM 管单机
  2. 作业提交后先由 AM 申请第一个 Container，再由 AM 反复拉取后续资源
  3. Container 是内存加 vCPU 的配额声明，超内存会被 NM 直接杀掉
  4. FIFO 适合测试，Capacity 按团队保底加弹性借用，Fair 让运行作业动态均分
  5. 队列必须同时设保底与上限，防止单个团队借满集群
  6. 卡在 ACCEPTED 先查队列余量与配额，调度器类型在 RM 启动时固定
