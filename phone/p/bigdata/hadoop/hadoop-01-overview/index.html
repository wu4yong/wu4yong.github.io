HDFS 与 YARN 生态全景

一台机器存不下、算不动的时候，最直觉的做法是”多堆几台”。但堆起来之后立刻冒出三个问题：数据放在哪台机器、多台机器怎么协同算、算到一半机器挂掉怎么办。Hadoop 就是这三件事的第一代标准答案，也是后面 Hive、HBase、Spark、Flink 全部长在上面的地基。

机架上的磁盘阵列向上汇聚成统一命名空间，计算贴着数据跑

1.1 先说清 Hadoop 到底由什么组成

很多人把 Hadoop 当成”一个大软件”，其实它是一组互相独立、可单独替换的模块：

模块
干什么
类比

这三者关系可以用一句话概括：HDFS 管存，YARN 管算力的分配，MapReduce 是第一个跑在 YARN 上的计算框架。后面的 Spark、Flink 之所以能复用同一套集群，靠的就是 YARN 把”资源”和”计算框架”解耦了。

1.2 HDFS：把一堆磁盘变成一块硬盘

HDFS 的设计假设非常朴素，甚至有点粗暴：

  • 硬件一定会坏，且坏是常态，不是异常
  • 数据量大到单机磁盘装不下，移动数据比移动计算贵得多
  • 一次写入、多次读取的场景占绝大多数，随机改一行的需求很少

于是有了三层抽象：

概念
是什么
关键点
Block
文件被切成固定大小的块，默认 128MB
块大是为了降低寻址开销，不是为省空间
Replica
每个块默认存 3 份
副本因子决定可靠性与存储成本
NameNode
记录”文件 → 块 → 机器”的映射
只存元数据，元数据全在内存
DataNode
真正存块、定期上报块列表
数据面，负责读写与校验

一次写入的流程大致是：客户端向 NameNode 申请写，NameNode 返回一组 DataNode，客户端把数据切成块、按 pipeline 顺序推给第一个节点，第一个节点边收边转给第二个，第二个再转给第三个，三份副本同时成型。

读取时，客户端只问 NameNode 要块的位置列表，然后直接连 DataNode 拉数据，NameNode 不参与数据传输——这是 HDFS 能扛住高并发的关键设计，也是”元数据与数据分离”最典型的落地。

早期版本里 NameNode 是单点，挂了整个集群就废。Hadoop 2.x 之后引入 HA（High Availability）：Active/Standby 两个 NameNode 通过 JournalNode 共享 editlog，ZooKeeper 上的 ZKFC 负责故障切换，Standby 还能顺带提供只读服务。

1.3 YARN：让计算跑到数据旁边

HDFS 解决了”存”，但”算”需要 CPU 和内存。如果每个计算框架自己管机器，集群就会变成一堆互不相让的割据势力。YARN 的作用是把集群资源统一收上来，再按需发下去。

角色
职责
生命周期
ResourceManager
全局资源总账，接收作业申请、分配 Container
整个集群一个（可 HA）
NodeManager
单机代理，上报本机资源、拉起并监控 Container
每台机器一个
Container
资源的最小分配单位（内存 + vCPU）
随任务创建销毁
ApplicationMaster
每个作业一个，向 RM 要资源、自己管任务
每作业一个

提交流程值得背下来：客户端提交作业 → RM 选一个 NodeManager 起 ApplicationMaster → AM 向 RM 申请 Container → RM 让各 NM 拉起 Container → Container 里跑 map/reduce task → 完成后 AM 注销。

这套模型的好处是框架可插拔：MapReduce、Spark、Flink 都只是”自己实现一个 ApplicationMaster”，资源调度统一交给 YARN。坏处也很明显：AM 本身是个额外进程，小作业启动开销大，所以 Spark on YARN 才有 client 与 cluster 两种部署模式之争。

1.4 MapReduce：最老的那批批处理

MapReduce 的思想只有两步：分而治之（map）+ 汇总归并（reduce）。它把”一个大任务”拆成”很多互不依赖的小任务”，正好对上 HDFS 的块分布——每个块在本地算，省掉网络传输。

阶段
输入输出
关键动作
Input
HDFS 块 → 记录
InputFormat 切分，默认按块切
Map
记录 → 键值对
业务逻辑，一记录一次
Shuffle
map 输出 → 按 key 分区排序
最耗时，网络与磁盘都在这
Reduce
一组同 key 值 → 结果
聚合、连接、去重
Output
结果 → HDFS
每个 reduce 一个 part 文件

现在新项目基本不会直接写 MapReduce 了，但它的模型仍然是理解 Spark、Flink 的坐标系：宽依赖就是 shuffle，stage 划分就是 map/reduce 边界。

一句话：HDFS 提供数据局部性，YARN 提供资源弹性，MapReduce 提供计算语义。缺任何一个，另外两个的价值都发挥不出来。

1.6 生态圈里各自站哪

Hadoop 从来不是孤岛。围绕”存 + 算”这两个基本需求，长出了一整圈组件，新人最容易迷路的就是这里：

看清这张表的方法很简单：先把”数据从哪来、存到哪、怎么算、算完给谁看”四段画出来，再把组件往上贴。贴不上去的，通常就是不需要的。

1.7 版本与选型

版本线
特征
建议
1.x
只有 HDFS + MapReduce，无 YARN
别用了，教材里的老架构
2.x
引入 YARN 与 NameNode HA
很多存量集群还在这条线
3.x
引入 Erasure Coding、多 NameNode 联邦增强、默认端口调整
新集群首选 3.x

几个容易踩的点：

  • 2.x 与 3.x 的默认 Web UI 端口改了（50070 → 9870，50090 → 9864），照着老教程敲必然连不上
  • dfs.replication 默认 3，测试集群只有两台机器时会一直报”副本不足”，不是坏了
  • 3.x 的 Erasure Coding 适合冷数据，能把 1.5 倍冗余压到 1.5 倍以下，但会牺牲本地读性能，热数据别用
  • 单 NameNode 的内存上限决定了文件数量的上限，小文件是 HDFS 的天敌，几百万个小文件能把元数据撑爆

1.9 清单

  1. Hadoop = HDFS（存）+ YARN（资源）+ MapReduce（算）+ Common（底座），四者可分别替换
  2. HDFS 的核心是”元数据与数据分离”，NameNode 只记映射，数据直连 DataNode
  3. 块默认 128MB、副本默认 3 份，块大是为了降寻址开销
  4. YARN 的价值是把资源和框架解耦，Spark、Flink 都是”自带 AM 的租客”
  5. MapReduce 的 shuffle 是理解一切分布式计算的入口，宽依赖即 shuffle
  6. 生态选型先画数据流向四段，再往上贴组件
  7. 新集群用 3.x，注意端口变更与小文件治理
