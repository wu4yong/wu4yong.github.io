分类：bigdata · hadoop ｜ 标签：Hadoop

运维调优与常见故障

集群跑起来之后，问题大多集中在存储效率、磁盘分布、拓扑感知与安全接入这几块。这一篇按”先治数据形态，再治磁盘分布，再谈拓扑与安全”的顺序梳理高频调优点，并给一张常见故障的排查入口。

多块存储介质之间做负载平衡，拓扑按机架分层，安全门禁横贯整个集群

1.1 小文件治理：HDFS 的天敌

小文件指体积远小于块大小（默认 128MB）的大量文件。它对 HDFS 的伤害不在磁盘容量，而在 NameNode 元数据：每个文件、目录、块在内存里都占一份对象，百万级小文件可以直接把主节点内存撑爆。

常见治理手段按介入位置分：

手段
做法
适用场景

用 HAR 归档或序列文件把小文件打包

判断小文件压力看两个指标：NameNode 内存占用与文件对象数。治理顺序是先堵源头（作业输出合并），再归档存量（HAR / 序列文件），不要一上来就扩 NameNode 内存——内存扩上去，瓶颈会转移到 GC 与启动恢复时间。

HAR 归档的边界要清楚：归档包里仍是一个个原始文件，访问时先查 HAR 索引再取内容，适合不再追加写入的历史数据；经常改写的数据集不要打 HAR，否则每次修改都要重打包。序列文件（SequenceFile）把多条记录拼成一个二进制文件，按 key 读取，适合作为计算链路中间格式。

1.2 DataNode 磁盘均衡与存储水位

单机多块磁盘时，新增磁盘或长期写入会造成盘间用量不均：一块盘写满报心跳失败，其他盘还很空。HDFS 提供两类均衡工具：

  • 集群级均衡（hdfs balancer）：在节点之间迁移块，让各节点存储使用率趋同
  • 盘内均衡（hdfs diskbalancer）：同一台 DataNode 的多块磁盘之间重新分布块
# 集群级均衡，默认阈值 10%，只在后台迁移副本，不影响在线读写
hdfs balancer -threshold 10
# 盘内均衡，先规划再执行，按节点盘间用量差调整
hdfs diskbalancer -plan node1.example.com
hdfs diskbalancer -execute node1.example.com.plan.json

均衡任务会占用网络与磁盘 IO，业务高峰期错开跑。日常要盯的是单机磁盘水位与单盘剩余空间，而不是只看集群总容量；总容量充足但单盘写满，节点同样会掉线。

磁盘选择上，DataNode 本地目录可配多块独立磁盘，HDFS 按目录轮询写块。新增磁盘后老数据不会自动过去，必须跑一次盘内均衡；只加目录不跑均衡，新写入分到新盘，老盘依然紧张。

# DataNode 本地存储目录，多块磁盘用逗号分隔，目录需提前授权
dfs.datanode.data.dir=/data1/dn,/data2/dn,/data3/dn

1.3 机架感知：让副本贴着拓扑放

机架感知（Rack Awareness）把机器挂到”机架 → 节点”的拓扑树上，NameNode 按这个拓扑选副本位置。没有拓扑脚本时，所有节点默认属于同一机架，副本保护退化为只防单机故障。

接入方式是提供一个拓扑解析脚本或 Java 类，把主机名映射成 /rack/node 形式的路径，配置在 net.topology.script.file.name。验证方法是用 hdfs dfsadmin -report 查看每台节点所属机架，确认副本没有扎堆。

配置点
作用
不配的后果
net.topology.script.file.name
主机名 → 机架路径映射
全部节点归同一机架，副本抗风险能力下降
副本放置策略
按机架分布三份副本
同机架堆多份，机架断电丢副本

机架感知不仅服务于副本放置，YARN 的节点距离判断、读取就近选择也依赖这棵拓扑树。拓扑脚本要返回稳定结果，不能随机输出，否则副本位置会反复漂移。

实际接入时容易忽略两点：脚本对每台节点都要能解析，新增机器不进拓扑表会被归入默认机架；脚本执行权限与超时要配好，解析卡住会拖慢 NameNode 的副本选择。变更拓扑后建议重新查看副本分布，确认旧副本在后续写入与均衡中逐步调整到位。

1.4 Kerberos 安全概述

裸 Hadoop 集群默认不做强身份认证，网络内任何进程都可以提交作业、读写文件。生产集群通常接入 Kerberos 做身份认证，再叠加 Ranger / Sentry 做授权。

Kerberos 在 Hadoop 里的角色分工：

  • KDC：发放票据（Ticket），维护主体（principal）与密钥
  • principal：每个服务与用户一个身份，如 nn/host@REALM
  • keytab：保存服务主体密钥的文件，服务用它免交互登录
  • 票据续期：长时间运行的任务需要刷新票据，否则凭证过期后任务失败

接入步骤的主线是：部署 KDC、为各服务与用户建主体、分发 keytab、在 Hadoop 配置里开启 hadoop.security.authentication=kerberos，再逐进程核对票据。安全开启后最常见的问题是主机名与 principal 不匹配、keytab 权限过宽、票据过期未续。

要区分两个层次：Kerberos 只解决”你是谁”的身份认证，不解决”你能读哪张表”的授权。授权通常交给 Ranger 或 Sentry 这类组件，按用户、组、资源路径配策略。两者叠加之后，作业提交失败先要判断是认证没过（票据问题）还是授权被拒（策略问题），排查路径不同。

排查顺序建议固定：先看 Web UI 与守护进程日志定位阶段，再看资源水位，最后动配置参数。一次只改一类参数，改完观察指标，避免多个变量混在一起无法归因。

补充几个高频现象的判断点：

  • 读写突然变慢且集中在某几台节点，先看这些节点磁盘 IO 与网络连接，再查副本是否偏置
  • 作业频繁失败在同一阶段，对比成功与失败任务的输入大小，优先怀疑数据倾斜
  • 守护进程启动即退出，先读启动日志里的权限、端口占用与配置解析错误，再谈业务参数
  • 扩容后集群性能没涨，检查新节点是否注册成功、块是否逐步迁移过去，而不是直接调调度器
  • 磁盘报错先看 SMART 与坏块标记，硬件层面的故障不要靠多副本长期兜底，坏盘要及时更换
  • 长期运行的 Streaming 任务或常驻 AM，要确认票据自动续期已配置，否则凭证过期后任务静默失败

调优的优先级建议固定：先看数据形态（小文件、副本分布），再看资源水位（磁盘、内存、网络），最后才动框架参数。存储层的问题靠调计算参数通常治不好，反过来也一样。

1.7 清单

  1. 小文件伤的是 NameNode 元数据而不是磁盘容量，先堵源头再归档存量
  2. 集群用 balancer 调节点间分布，盘内用 diskbalancer 调磁盘间分布，避开业务高峰
  3. 机架感知把主机映射成拓扑路径，副本就近放置，脚本结果必须稳定
  4. Kerberos 解决身份认证，principal 加 keytab 加票据续期是主线，授权另由 Ranger 等承担
  5. 故障排查先定位阶段与日志，再看资源水位，最后改参数，一次只调一类
  6. 日常关注元数据规模、磁盘水位、队列余量、Container 内存与票据有效期这五类指标
