集群规划与 HA 部署

前面几篇讲的是组件怎么工作，这一篇落到装机：一个生产集群怎么规划角色，三份核心配置各写什么，双 NameNode 高可用靠 JournalNode 与 ZKFC 怎么搭，以及启动顺序为什么不能乱。

双主节点通过共享日志通道与协调服务互联，外围工作节点统一接入

1.1 集群规划：角色先分开再谈机器

规划集群第一步不是选配置，而是把角色列出来，再按冗余要求分配机器：

角色
数量建议
说明
NameNode（Active/Standby）
2
HA 双主，共享 editlog，ZKFC 随主节点部署
JournalNode
奇数个（3 起步）
保存共享 editlog，多数派写入成功才算提交
ZooKeeper
奇数个（3 起步）
保存 HA 状态，ZKFC 据此做自动切换
DataNode / NodeManager
按数据量与算力扩缩
存储与计算混部，也可分开成专用节点

小集群可以让 NameNode、JournalNode、ZK 挤在同一批主节点上，但生产环境建议 JournalNode 与 ZK 单独落位，避免主节点重启影响多数派。规划时先定机架分布：副本与 JournalNode 都要跨机架，否则机架断电直接击穿冗余。

1.2 三份核心配置各管什么

Hadoop 的配置集中在 core-site.xml、hdfs-site.xml、yarn-site.xml 三个文件，职责边界先记清：

配置文件
管什么
典型参数
core-site.xml
集群默认文件名、身份、临时目录
fs.defaultFS、hadoop.tmp.dir
hdfs-site.xml
副本、块大小、HA 命名服务、JournalNode 地址
dfs.replication、dfs.namenode.shared.edits.dir

调度器、NM 资源、AM 重启策略

core-site.xml 里最基础的一项是默认文件系统地址：

<!-- 集群对外的 HDFS 入口，HA 下指向 nameservice 而非单台 NN -->
<property>
  <name>fs.defaultFS</name>
  <value>hdfs://mycluster</value>
</property>
<!-- 各节点本地临时目录，需提前建好并授权 -->
<property>
  <name>hadoop.tmp.dir</name>
  <value>/data/hadoop/tmp</value>
</property>

hdfs-site.xml 里配置副本、块大小与 HA 通道：

<!-- 副本因子与块大小，3.x 默认即 3 与 128MB，显式写出便于审计 -->
<property>
  <name>dfs.replication</name>
  <value>3</value>
</property>
<property>
  <name>dfs.blocksize</name>
  <value>134217728</value>
</property>
<!-- 共享 editlog 的 JournalNode 集合，QJM 多数派写成功即生效 -->
<property>
  <name>dfs.namenode.shared.edits.dir</name>
  <value>qjournal://jn1:8485;jn2:8485;jn3:8485/mycluster</value>
</property>

yarn-site.xml 选定调度器并声明 RM 角色：

<!-- 调度器类型，Capacity 与 Fair 二选一，切换需重启 RM -->
<property>
  <name>yarn.resourcemanager.scheduler.class</name>
  <value>org.apache.hadoop.yarn.server.resourcemanager.scheduler.capacity.CapacityScheduler</value>
</property>

1.3 QJM 加 ZKFC：双主怎么保持一致

单 NameNode 时代最大的风险是主节点单点。HA 方案由两部分组成：

QJM（Quorum Journal Manager）：Active NameNode 把 editlog 写入一组 JournalNode，超过半数节点写成功就视为提交；Standby 从同一组 JournalNode 读流水回放，保持元数据追平。JournalNode 数量必须是奇数，3 个节点允许挂 1 个。

ZKFC（ZooKeeper Failover Controller）：每个 NameNode 旁边驻留一个 ZKFC 进程，负责健康检查与抢占锁：

  • ZKFC 监测本机 NameNode 是否健康，健康则在 ZooKeeper 上持有主锁
  • Active 节点失效时，对应 ZKFC 失去锁，Standby 的 ZKFC 抢到锁并触发切换
  • 切换后新 Active 从 JournalNode 回放最新流水再对外服务
组件
解决什么
挂掉的影响
JournalNode
共享 editlog，保证两主元数据一致
多数派丢失后 NameNode 无法对外写
ZKFC
健康检查与自动故障切换
不会自动切换，需人工介入
ZooKeeper
保存主锁与 HA 状态
ZK 不可用时无法完成选主

1.4 部署步骤与启动顺序

HA 集群的初始化与启动有严格顺序，跳步会导致元数据不一致：

  1. 准备 JDK、免密 SSH、目录权限，同步 core-site.xml、hdfs-site.xml、yarn-site.xml 到所有节点
  2. 启动 ZooKeeper 集群并确认多数节点在线
  3. 启动所有 JournalNode 进程
  4. 在一台 NameNode 上执行 hdfs namenode -format 初始化元数据，再用 hdfs namenode -bootstrapStandby 把元数据同步到 Standby
  5. 依次启动两台 NameNode 与各自的 ZKFC，由 ZK 选举出 Active
  6. 启动所有 DataNode 与 NodeManager
  7. 通过 Web UI 核对：3.x NameNode 页面端口 9870，DataNode 页面端口 9864

启动顺序反过来记一遍：先 ZK，再 JournalNode，格式化并同步 NN，起 NN 与 ZKFC，最后起 DN 与 NM。不能先起 DataNode 再格式化 NN，否则块汇报与元数据对不上。

1.5 几个容易踩的坑

  • 三台 JournalNode 部署在同一台物理机上，机架或机器故障时多数派直接丢失，HA 名存实亡
  • 只格式化了 Active，Standby 没做 bootstrapStandby，两主元数据起点不一致，切换后报流水缺口
  • 照着 1.x 教程用 50070 端口访问，3.x 默认已改为 9870；DataNode 对应端口为 9864
  • 主机名、/etc/hosts 或 DNS 解析不一致，JournalNode 与 ZKFC 互联超时，选主反复失败
  • 目录权限只给了当前用户，NM 起 Container 时写临时目录被拒，任务全部失败
  • 以为配了 HA 就能丢盘，NameNode 本地 fsimage 损坏时仍需从备份或 JournalNode 恢复，日常元数据备份不能省

1.7 清单

  1. 规划先列角色：双 NameNode、奇数 JournalNode、奇数 ZooKeeper、若干 DataNode/NM
  2. core-site.xml 定入口与临时目录，hdfs-site.xml 定副本块与 HA 通道，yarn-site.xml 定调度器
  3. QJM 靠多数派写共享 editlog，ZKFC 靠 ZK 锁做健康检查与自动切换
  4. 启动顺序：ZK → JournalNode → 格式化并同步 NN → NN 与 ZKFC → DN 与 NM
  5. 3.x Web UI 端口：NameNode 9870，DataNode 9864；块默认 128MB、副本 3
  6. HA 不等于免备份，元数据日常备份与恢复演练仍要纳入运维
