MapReduce 原理与 Shuffle

新项目直接写 MapReduce 的已经不多，但它的两阶段模型和 Shuffle 机制是理解 Spark、Flink 的坐标系：宽依赖就是 Shuffle，stage 边界就是 map/reduce 分界。这一篇把从切片到落盘的全链路拆开，重点讲 Shuffle 的磁盘与网络细节。

数据流沿多节点分叉成映射分支，再按键值归并汇聚到下游节点

1.1 全链路概览

整体节奏是”先并行铺开算，再按 key 收拢合并”。Map 任务之间互不通信，所有跨节点的数据交换都集中在 Shuffle 段，作业最慢的环节通常也在这里。

1.2 InputFormat 与 InputSplit

切片（InputSplit）不等于 HDFS 块，但默认对齐块大小。切片由 InputFormat 生成，决定一个 Map 任务处理哪一段记录：

  • TextInputFormat 按行读文本，默认一个块对应一个切片
  • 切片记录的是起始偏移与长度，不是把数据复制一份到内存
  • 若一条记录跨块，InputFormat 负责跨边界读完整条记录

切片数直接决定 Map 任务并行度。切片切得过粗，单任务重试代价大、节点空闲时无法补位；切得过细，任务启动与调度开销占比升高。小文件过多时每个文件一个切片，Map 任务数被文件数量撑爆，这是典型的小文件后遗症。

1.3 Map 阶段

Map 任务对切片里的每条记录调用一次 map()，输出若干键值对。框架在 Map 侧做两件透明的事：

  • 输出先写环形内存缓冲区，达到阈值后 spill 到本地磁盘
  • 落盘前按分区（partition）与 key 排序，为后续拉取做准备

Map 端的业务代码只关心”一条记录变成什么键值对”，缓冲区大小、spill 阈值、压缩策略都由配置控制。缓冲区默认容量不大，Map 输出量大时频繁 spill，磁盘 IO 直接体现在作业时长上。

1.4 Shuffle：分区、排序、spill 与 merge

Shuffle 是 MapReduce 最复杂的一段，分 Map 端与 Reduce 端两侧看：

Map 端：

  1. 输出写入环形缓冲区，达到 mapreduce.map.sort.spill.percent 阈值开始 spill
  2. spill 前按 Partitioner 确定分区，再在分区内按 key 排序
  3. 多次 spill 形成多个磁盘文件，最后 merge 成一个已排序的分区文件
  4. Reduce 端按分区拉取对应文件片段

Reduce 端：

  1. 复制线程从各 Map 节点拉取属于自己分区的数据
  2. 拉到的数据先放内存，超阈值落盘，多个片段再次 merge 排序
  3. 排序完成后按 key 分组，同一 key 的值交给 reduce() 迭代处理
# Map 侧环形缓冲区大小，输出量大时适当上调以减少 spill
mapreduce.task.io.sort.mb=100
# spill 触发阈值，占缓冲区比例
mapreduce.map.sort.spill.percent=0.80
# Reduce 端同时复制的线程数
mapreduce.reduce.shuffle.parallelcopies=5

Shuffle 之所以贵，是因为它同时打满磁盘（spill 与 merge）和网络（跨节点拉取）。排查作业慢时先看 Shuffle 字节数与磁盘等待时间，而不是先怀疑业务逻辑。

1.5 Combiner 与 Partitioner

Partitioner 决定一条 map 输出落到哪个 Reduce。默认 HashPartitioner 用 key.hashCode() % reduceTasks 取模，保证同 key 进同一分区。自定义 Partitioner 可以按业务字段分流，比如按地区把数据送到不同 Reduce。

Combiner 是 Map 端的本地预聚合，作用等同于在 Map 节点上先跑一遍 Reduce：

  • 它在 spill 前对同分区同 key 的值做一次合并，减少 Shuffle 传输量
  • 不是所有聚合都能加 Combiner：求和、计数可以；求平均、拼接集合这类依赖全量样本的不能随便加
  • Combiner 被调用次数不固定，业务逻辑必须对”本地先聚一次”保持幂等

1.6 Reduce 与输出

Reduce 拿到的是已按 key 分组的值迭代器。reduce() 对每个 key 调用一次，输出结果键值对，最终由 OutputFormat 写入 HDFS：

  • 每个 Reduce 任务生成一个 part-r-xxxxx 文件，文件数等于 Reduce 数
  • Reduce 数量影响并行度与输出文件大小，设为 1 等于全量串行聚合
  • 结果文件直接在 HDFS 上，后续 Hive、Spark 都可以直接读

Reduce 侧同样有内存到磁盘的 merge 过程。拉取的数据在内存放不下时落盘，多次落盘再合并；Reduce 输入倾斜时，个别任务处理的 key 量远超其他节点，整体进度卡在 99%。

1.7 几个容易踩的坑

  • 把 Combiner 当性能开关到处加，求平均类聚合先在本地合并，最终结果直接算错
  • Reduce 数固定写死为 1，大作业全部挤在一个节点聚合，倾斜严重
  • 小文件场景切片数等于文件数，Map 任务成百上千，调度开销压过计算本身
  • 以为 Shuffle 只走网络，实际 Map 端 spill、Reduce 端 merge 都要读写本地磁盘
  • key 类型没有实现 Writable 与正确的 hashCode、equals，分区与分组行为错乱
  • 只调大 Map 缓冲区，忽略 Reduce 复制线程数与拉取超时，Shuffle 卡在复制阶段

1.9 清单

  1. MapReduce 全链路为切片、Map、Shuffle、Reduce、Output 五段
  2. 切片默认对齐 HDFS 块，切片数决定 Map 并行度，小文件会把切片数撑爆
  3. Shuffle 横跨磁盘与网络：Map 端 spill 排序，Reduce 端复制合并分组
  4. Partitioner 定分区，Combiner 做本地预聚合，Combiner 要求聚合函数可结合
  5. Reduce 输出每个任务一个 part 文件，Reduce 数既是并行度也是文件数
  6. 数据倾斜表现为个别 Reduce 长跑、整体进度卡住，先查 key 分布再调参数
