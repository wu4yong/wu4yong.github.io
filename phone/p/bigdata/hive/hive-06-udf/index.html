自定义函数与权限治理

内置函数覆盖不了所有业务口径时，Hive 允许用 Java 写自定义函数挂到引擎上；而数仓里沉淀了全量业务数据，谁能查哪张表、哪一列，必须有统一的权限管控。这一篇讲清 UDF、UDAF、UDTF 三类函数的区别、开发与注册方式，以及 Ranger、Sentry 在权限治理里各自承担的角色。

插件式函数模块挂载到引擎主干，外部权限网关以策略与审计屏障守护库表访问通道

1.1 三类自定义函数的分工

Hive 扩展 SQL 的入口是用户自定义函数（User Defined Function），按输入输出行数分为三类：

类别
输入 → 输出
抽象类
典型用途
UDF
一行进，一行出
GenericUDF
字段格式化、加密、字符串加工
UDAF
多行进，一行出
AbstractGenericUDAFResolver / GenericUDAFEvaluator
业务口径聚合、去重计数
UDTF
一行进，多行出
GenericUDTF
拆分复杂字段，配合 LATERAL VIEW 使用

判断归属只看行数变化：结果仍是一列一行就是 UDF；收敛成一行聚合值就是 UDAF；炸开成多行就是 UDTF。日常取数需求里，UDF 占绝大多数，UDTF 多用于数组、JSON 字段拆解。

1.2 开发一个 UDF

以 GenericUDF 为例，核心是实现 initialize（定义输入输出类型）和 evaluate（写计算逻辑）：

package com.starry.hive.udf;

import org.apache.hadoop.hive.ql.exec.UDFArgumentException;
import org.apache.hadoop.hive.ql.metadata.HiveException;
import org.apache.hadoop.hive.ql.udf.generic.GenericUDF;
import org.apache.hadoop.hive.serde2.objectinspector.ObjectInspector;
import org.apache.hadoop.hive.serde2.objectinspector.primitive.PrimitiveObjectInspectorFactory;

/**
 * 手机号脱敏：保留前三位与后四位，中间用星号替换
 */
public class MaskPhoneUDF extends GenericUDF {

    @Override
    public ObjectInspector initialize(ObjectInspector[] arguments)
            throws UDFArgumentException {
        if (arguments.length != 1) {
            throw new UDFArgumentException("mask_phone 只接受一个字符串参数");
        }
        // 输出类型固定为字符串
        return PrimitiveObjectInspectorFactory.javaStringObjectInspector;
    }

    @Override
    public Object evaluate(DeferredObject[] arguments) throws HiveException {
        String phone = arguments[0].get() == null ? null : arguments[0].get().toString();
        if (phone == null || phone.length() < 7) {
            return phone;
        }
        return phone.substring(0, 3) + "****" + phone.substring(phone.length() - 4);
    }

    @Override
    public String getDisplayString(String[] children) {
        return "mask_phone()";
    }
}

打包时把 Hive 依赖标记为 provided，避免把引擎类一起打进 jar 造成冲突。产物是一个普通 jar，不需要部署到集群节点，通过会话注册即可使用。

1.3 临时函数与永久函数

函数注册分两种生命周期，对应不同使用场景：

-- 把 jar 加入当前会话类路径（HDFS 或本地路径均可）
ADD JAR hdfs:///udf/hive-udf-1.0.0.jar;

-- 临时函数：只在当前会话有效，会话结束自动失效
CREATE TEMPORARY FUNCTION mask_phone AS 'com.starry.hive.udf.MaskPhoneUDF';

-- 使用临时函数
SELECT mask_phone(login_ip) FROM dwd.user_login LIMIT 10;

永久函数把函数名与类、jar 位置登记到 Metastore，所有会话都能调用：

-- 永久函数：元数据写入 Metastore，跨会话持久存在
CREATE FUNCTION mask_phone
AS 'com.starry.hive.udf.MaskPhoneUDF'
USING JAR 'hdfs:///udf/hive-udf-1.0.0.jar';

-- 查看与删除
SHOW FUNCTIONS LIKE 'mask*';
DROP FUNCTION mask_phone;

1.4 UDAF 与 UDTF 的要点

UDAF 承担聚合逻辑，执行过程分阶段：部分聚合（partial）与最终聚合（final），评估器要处理迭代、合并与输出三个环节。开发时先想清楚中间结果存什么类型，再实现 iterate、merge、terminate 等方法。

UDTF 继承 GenericUDTF，在 process 里调用 forward 逐行输出，查询侧必须挂 LATERAL VIEW：

-- 假设 parse_tags 是拆分 JSON 数组的 UDTF
SELECT user_id, tag
FROM dwd.user_profile
LATERAL VIEW parse_tags(ext_info) t AS tag;

UDTF 不能直接出现在普通 SELECT 列列表里脱离 LATERAL VIEW 使用；一行炸裂多行后，原表字段与炸裂列按行对应展开。

1.5 权限治理：Hive 原生授权与 Ranger、Sentry

数据仓库集中了明细与汇总数据，权限不能只靠”不把密码给别人”。Hive 自身提供授权模型，生产环境通常外接统一策略中心。

方案
定位
角色
Hive 原生授权
库、表、列、分区级别的 GRANT/REVOKE
轻量场景或作为底层校验
Apache Ranger
集中式权限策略平台，库表列级授权 + 审计
主流方案，策略统一配置
Apache Sentry
基于角色的访问控制（RBAC）策略层
早期 Cloudera 体系使用，社区活跃度已下降

Ranger 的工作方式是：在策略中心配置”谁能访问哪张表、哪些列、能否读写”，HiveServer2 在查询入口对接 Ranger 插件做校验，并把访问记录落到审计日志。策略集中管理的好处是新增、回收权限不用改集群配置，审计也有统一出口。

Sentry 走角色与授权集（Privilege Set）模型，早期随 CDH 生态普及；新项目评估时优先看 Ranger，存量 Sentry 链路重点关注长期维护与迁移路径。

1.6 容易踩的坑

  • 函数 jar 打包带重依赖：把 Hive、Hadoop 类打进 jar 会与服务端类冲突，依赖一律标 provided。
  • 临时函数当公共函数用：会话断开后函数消失，下游调度任务报”函数不存在”；公共口径必须注册永久函数。
  • 类名写错或 jar 没加进类路径：CREATE FUNCTION 报类找不到，先确认 ADD JAR 与 USING JAR 路径可达。
  • UDAF 中间结果类型设计失误：partial 与 final 阶段类型不一致，聚合结果出错且不易定位。
  • UDTF 脱离 LATERAL VIEW：直接写在 SELECT 列里会解析失败，必须配合 LATERAL VIEW。
  • 权限只在入口挡一次：策略要覆盖库、表、列与分区层级，敏感列单独授权；审计日志要能回溯谁在什么时间查了哪张表。

1.8 清单

  1. 自定义函数分三类：UDF 一行进一行出，UDAF 多行聚合成一行，UDTF 一行炸成多行
  2. UDF 继承 GenericUDF，实现 initialize 与 evaluate；依赖标 provided，避免 jar 冲突
  3. 临时函数随会话失效用于调试，永久函数写入 Metastore 供团队复用；公共口径必须走永久函数
  4. UDAF 分部分聚合与最终聚合阶段，先定中间结果类型再实现评估器；UDTF 必须配合 LATERAL VIEW
  5. 权限治理上，Ranger 是主流集中策略平台，覆盖库表列级授权与审计；Sentry 为早期 RBAC 方案，新项目优先评估 Ranger
  6. 权限策略要分层覆盖并留审计出口，敏感列单独授权，避免只靠口头管控
