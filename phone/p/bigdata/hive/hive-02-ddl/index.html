库表与分区分桶 DDL

建表语句看着像标准 SQL，但 Hive 里的表直接映射成 HDFS 目录，分区和分桶也不是数据库里的索引概念，而是文件组织方式。这一篇把库表 DDL、分区表、分桶表、SerDe 与常见存储格式串起来，目标是建出来的表既好查又不浪费扫描量。

目录树按分区键分层展开，文件按哈希切成固定数量的分桶块，格式层在底部承载数据

1.1 库与表的基础 DDL

Hive 的库本质上是 Metastore 里的命名空间，对应 HDFS 上的一层目录。建库、建表的常用语句如下：

-- 建库，LOCATION 指定库目录，不写则用仓库默认路径
CREATE DATABASE IF NOT EXISTS dwd
  LOCATION '/warehouse/dwd';

USE dwd;

-- 基础表：列类型与关系库接近，字符串统一用 STRING，大数用 BIGINT
CREATE TABLE IF NOT EXISTS dwd.user_login (
  user_id   BIGINT,
  login_ip  STRING,
  device    STRING,
  login_ts  BIGINT
)
COMMENT '用户登录明细'
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
STORED AS TEXTFILE;

查看结构与元信息的常用命令：

DESCRIBE FORMATTED dwd.user_login;   -- 看表位置、SerDe、存储格式
SHOW PARTITIONS dwd.user_login;      -- 列出已有分区
SHOW CREATE TABLE dwd.user_login;    -- 打印建表语句

1.2 分区表：把扫描压到目录级别

分区（Partition）的本质是目录：建表时用 PARTITIONED BY 声明分区键，表目录下按分区值再建一层或多层子目录。查询带分区过滤时，引擎直接只扫对应目录，而不是全表扫描，这叫分区裁剪（Partition Pruning）。

-- 按日期、渠道两级分区：dt 是一级目录，channel 是二级目录
CREATE EXTERNAL TABLE ods.access_log (
  ip   STRING,
  url  STRING,
  uid  STRING
)
PARTITIONED BY (dt STRING, channel STRING)
STORED AS ORC;

对应的 HDFS 结构：

/warehouse/ods/access_log/
├── dt=2022-01-06/
│   ├── channel=app/
│   └── channel=web/
└── dt=2022-01-07/
    ├── channel=app/
    └── channel=web/

几条硬规则：

  • 分区键写在 PARTITIONED BY 里，不能再出现在前面的列定义中，否则建表就报重复列。
  • 分区值来自目录名（dt=2022-01-06），不是文件内容里解析出来的。
  • 外部系统直接往 HDFS 塞目录时，Metastore 并不知道，需要 MSCK REPAIR TABLE 或 ALTER TABLE ADD PARTITION 补登记。
-- 批量扫描 HDFS 目录，把缺失的分区补进元数据
MSCK REPAIR TABLE ods.access_log;

-- 或手动登记单个分区
ALTER TABLE ods.access_log
  ADD PARTITION (dt='2022-01-06', channel='app')
  LOCATION '/warehouse/ods/access_log/dt=2022-01-06/channel=app';

1.3 分桶表：按哈希切成固定数量文件

分桶（Bucketing）和分区容易被混为一谈，但两者粒度完全不同：分区是目录，分桶是文件。CLUSTERED BY 指定分桶列，按列值哈希取模，把数据分散到固定数量的桶文件里。

-- 按 user_id 哈希，切成 32 个桶文件
CREATE TABLE dwd.order_bucket (
  order_id  STRING,
  user_id   BIGINT,
  amount    DOUBLE
)
CLUSTERED BY (user_id) INTO 32 BUCKETS
STORED AS ORC;

分桶带来的两个实际用途：

  • 抽样查询：开发调试时不用全表跑，取部分桶即可验证逻辑：
-- 取第 3 个桶，共 16 桶，等价于抽样约 1/16 的数据
SELECT * FROM dwd.order_bucket
TABLESAMPLE (BUCKET 3 OUT OF 16 ON user_id);
  • Join 优化：两表按同一列、相同桶数分桶后，连接时可以按桶对齐，避免全量 shuffle。

1.4 SerDe 与存储格式

读文件时，引擎要先把字节解析成行和列，这一步由 SerDe（Serializer / Deserializer，序列化/反序列化器）完成；文件本身怎么组织，则由存储格式决定。

一个 ORC 外部表的完整定义：

CREATE EXTERNAL TABLE dwd.user_login_orc (
  user_id  BIGINT,
  login_ip STRING,
  device   STRING,
  login_ts BIGINT
)
PARTITIONED BY (dt STRING)
ROW FORMAT SERDE 'org.apache.hadoop.hive.ql.io.orc.OrcSerde'
STORED AS ORC
LOCATION '/warehouse/dwd/user_login_orc';

选型结论：离线数仓默认 ORC，跨引擎共享选 Parquet，原始文本先落 TEXTFILE 再转列存。行存格式在列裁剪和压缩上天生吃亏，不要在中间层沿用。

1.5 表属性与常见约束

TBLPROPERTIES 用来挂元信息，常见用途包括注释、数据源标记、压缩与事务属性：

ALTER TABLE dwd.order_bucket SET TBLPROPERTIES (
  'owner' = 'dwd-team',
  'etl'   = 'daily'
);

容易踩的点：

  • 分区键重复定义：把 dt 同时写进列列表和 PARTITIONED BY，建表直接失败。
  • 分桶数拍脑袋：桶数要和文件大小配合，单桶文件过小会退化成小文件问题；桶数不是越多越好。
  • 直接传文件不登记分区：外部表目录手动建好后忘了 MSCK REPAIR TABLE，查询结果为空但表看着正常。
  • 格式混用：同一表内混入不同 SerDe 的文件，解析会报序列化异常；转格式时整表重建。
  • 分区键高基数：用用户 ID 这种高基字段做分区，目录数量失控，元数据会被撑爆，这类字段应该走分桶。

1.7 清单

  1. 分区是目录，按分区键值建子目录，查询靠分区裁剪少扫数据；分桶是文件，按哈希取模切成固定数量桶
  2. 分区键、分桶键不能与普通列重复定义；外部表手动建目录后要 MSCK REPAIR TABLE 补登记
  3. 分桶支持 TABLESAMPLE 抽样，同列同桶数两表 Join 可按桶对齐
  4. 存储格式：TEXTFILE 行存适合原始日志，ORC 列存适合数仓内部，Parquet 适合跨引擎共享
  5. 分区键选低基业务维度，高基字段走分桶；桶数要结合文件大小评估，避免制造小文件
  6. 表属性用 TBLPROPERTIES 挂载，转存储格式需要整表重建，不能混写
