分类：bigdata · hive ｜ 标签：Hive

执行计划与调优

查询慢的时候，最忌讳一上来改参数碰运气。正确顺序是先看执行计划，确认扫描范围、Join 方式和聚合边界，再判断瓶颈在输入量、shuffle 还是倾斜。这一篇讲 EXPLAIN 怎么读、三种计算引擎怎么选，以及数据倾斜和小文件这两类最常见问题的定位与处理。

执行计划 DAG 节点沿引擎流水线展开，倾斜的高负载条带被打散，零散小文件在出口处合并成规整块

1.1 用 EXPLAIN 读懂执行计划

EXPLAIN 不真正跑作业，只打印编译器生成的计划，是调优的第一入口：

EXPLAIN
SELECT channel, COUNT(*) AS pv
FROM dwd.order_daily
WHERE dt = '2022-01-20'
GROUP BY channel;

计划输出按阶段（Stage）组织，重点看四段：

读计划的顺序建议是：先确认分区裁剪是否生效，再看 Join 类型，最后看聚合与排序。计划里已经全表扫描的 SQL，再调 reducer 数量也救不回来，先改过滤条件。

1.2 计算引擎：MapReduce、Tez、Spark

Hive 的物理计划可以交给不同引擎执行，引擎在 hive-site.xml 里切换：

<!-- 底层执行引擎：2.x 起生产推荐 Tez，老集群可能仍是 mr，也可换成 spark -->
<property>
  <name>hive.execution.engine</name>
  <value>tez</value>
</property>

选型上没有绝对答案：存量 Hive 链路优先跟官方方向走 Tez；团队已经重度使用 Spark、愿意维护两套执行层时再评估 Spark 引擎。换引擎前先跑同一批 SQL 对比耗时与资源占用，不要凭印象迁移。

1.3 数据倾斜：表现、定位与处理

数据倾斜（Skew）是分布式任务最典型的瓶颈：少数 reducer 扛了绝大多数数据，进度卡在 99% 不动，其余节点早已空闲。

定位方式

  • 看执行计划与任务计数：某几个 reducer 处理的行数、写入量远高于均值。
  • 看 Key 分布：空值、默认值、热点维度集中在少数键上。
  • 看 Join 两侧：一张大表关联一张小表时，热点键会把压力全压到 Join 一侧。

相关参数（hive-site.xml）：

# 开启倾斜 Join 优化，识别热点键后单独拆分
hive.optimize.skewjoin=true
# 倾斜键在任务中超过该行数即判定为倾斜
hive.skewjoin.key=100000
# Map 端聚合，减少 shuffle 数据量
hive.map.aggr=true

两阶段聚合的典型写法：先给热点键拼随机前缀做局部聚合，第二轮去掉前缀再全局汇总。核心思路是别让同一个键落到同一个 reducer 上排队。

1.4 小文件合并

HDFS 上文件过多会带来两个问题：NameNode 元数据压力大，每个计算任务启动时 splits 数量爆炸。Hive 在输入侧和输出侧都提供合并手段：

# 输入侧：合并小文件作为 InputFormat，减少 map 任务数
hive.input.format=org.apache.hadoop.hive.ql.io.CombineHiveInputFormat
# Map 任务输出合并（Map-only 作业）
hive.merge.mapfiles=true
# Reduce 任务输出合并
hive.merge.mapredfiles=true
# 合并后单文件目标大小，单位字节
hive.merge.size.per.task=256000000
# 平均文件小于该大小时触发合并
hive.merge.smallfiles.avgsize=16000000

CombineHiveInputFormat

小文件的根源往往在上游：动态分区刷目录、INSERT INTO 反复追加、 reducer 数过多。合并是出口补救，源头要控制分区粒度和写入批次，否则合并参数压不住持续堆积的文件。

1.5 其他常用调优方向

除了倾斜与小文件，这几类动作收益最稳定：

  • 列裁剪：只 SELECT 用到的列，不 SELECT *，减少 shuffle 与扫描量。
  • 谓词下推：分区过滤、行级条件尽量写在 WHERE，让过滤在扫描阶段生效。
  • 并行执行：无依赖的 Stage 并行跑，缩短整体作业时长：
# 允许无依赖的 Stage 并行执行
hive.exec.parallel=true
# 单作业最大并行 Stage 数
hive.exec.parallel.thread.number=8
  • 中间结果压缩：shuffle 与落地结果启用压缩，列存格式配合 Snappy / Zlib 降低磁盘与网络开销。
  • 分桶与排序：同列同桶数两表 Join 可按桶对齐，避免全量 shuffle。

1.6 容易踩的坑

  • 不看计划先调参数：计划里全表扫描、没走分区裁剪，调 reducer 数和内存都无效。
  • 把倾斜当资源不足：加内存、加队列解决不了 Key 集中，热点键该打散还得打散。
  • 盲目提高 reducer 数：reducer 过多本身制造小文件，数量要按数据量与目标文件大小反推。
  • 只靠出口合并小文件：上游动态分区与追加写入不停，合并速度赶不上堆积速度。
  • 引擎切换拍脑袋：换 Tez 或 Spark 前要跑基准 SQL 对比耗时、稳定性与兼容性。
  • 压缩格式与列存不匹配：行存文本再压也跑不赢列存，格式选型先于压缩参数。

1.8 清单

  1. 调优先看 EXPLAIN：确认分区裁剪、Join 方式、聚合边界，全表扫描的 SQL 调参数无效
  2. 引擎可选 MapReduce、Tez、Spark；2.x 起生产方向是 Tez，迁移前用基准 SQL 对比
  3. 数据倾斜表现为少数 reducer 卡死；处理手段是过滤空键、随机前缀两阶段聚合、Map Join 与 skew join
  4. 小文件在输入侧用 CombineHiveInputFormat 合并，输出侧按 merge.size.per.task 控制文件大小
  5. 稳定收益：列裁剪、谓词下推、Stage 并行、中间结果压缩、分桶对齐 Join
  6. 合并是补救不是根治，源头要控制分区粒度与写入批次；reducer 数量按目标文件大小反推
