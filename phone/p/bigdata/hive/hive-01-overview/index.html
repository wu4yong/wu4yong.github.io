Hive（一）架构与元数据

分类：bigdata · hive ｜ 标签：Hive

架构与元数据

数据已经躺在 HDFS 上，但分析人员只会写 SQL，直接读文件要写一堆 MapReduce 程序，成本高得离谱。Hive 做的事情就是在文件之上加一层”表”的语义：你写 HQL，它负责翻译成分布式作业去跑，结果再以表的形式返回。这一篇先把它由哪些角色组成、元数据放在哪、内部表和外部表的边界讲清楚。

查询引擎节点把 SQL 翻译为分布式作业，元数据独立存储，数据留在 HDFS 上

1.1 Hive 到底是什么

Hive 建立在 Hadoop 之上，最初由 Facebook 开源，定位是数据仓库（Data Warehouse）而不是数据库。两者的差别决定了它的使用边界：

维度
传统数据库
Hive
定位
在线事务处理，随机读写
离线分析，批量扫描历史数据
存储
本地磁盘 / 共享存储
HDFS、对象存储、HBase 等
执行
单节点或共享集群进程
翻译为 MR / Tez / Spark 作业跑在 YARN
延迟
毫秒到秒级
分钟级，大作业更久
更新
支持行级增删改
早期只支持追加，后续版本才有限支持 ACID

一句话判断：要给前台页面供数据走 OLTP 数据库，要对全量历史做汇总分析走 Hive 这类数仓引擎。拿 Hive 去扛点查、去做实时写入，属于选型错误。

1.2 核心角色：Driver、HiveServer2、Metastore

一套典型部署里，经常被混淆的是这三个进程，它们各自管一段：

组件
职责
关键点
Driver
编译 SQL：解析、语义分析、生成逻辑计划与物理计划，提交执行并回收结果
一次查询的调度中枢，内部分为 Compiler 与 Executor
HiveServer2（HS2）
对外提供 JDBC/ODBC 服务，支持多客户端并发与会话隔离
早期的 HiveServer1 已废弃，现在说的服务端基本都是 HS2
Metastore
存库、表、分区、列、SerDe、表属性等元数据
本身是个服务，底层一般挂 MySQL 或 PostgreSQL

一条语句进来的路径是：客户端通过 JDBC 连到 HS2 → Driver 接管语句，先去 Metastore 查表结构 → 编译器把 SQL 变成可执行计划 → 计划提交给底层计算引擎在 YARN 上跑 → 结果回传客户端。

需要注意，Metastore 不是存数据的地方，它只存”数据长什么样”：表名对应哪个目录、有哪些分区、每列是什么类型。真正的行和字节仍然在 HDFS 上。

1.3 与 HDFS、YARN 的关系

Hive 自己不存数据，也不直接抢机器资源，它把这两件事分别交给 Hadoop 的既有组件：

层
谁负责
Hive 这边的对应关系
存储层
HDFS（也可接 S3、HBase）
一张表对应一个目录，分区对应子目录
资源层
YARN
计算作业以 Container 形式申请 CPU 与内存
计算层
MapReduce / Tez / Spark
Hive 把物理计划交给其中一种引擎执行
元数据层
Metastore 数据库
与数据文件分离，可独立备份与迁移

这种分层带来两个直接后果：一是换引擎不动表，同一份数据文件，底层从 MapReduce 切到 Tez，表定义和数据都不用改；二是元数据可以单独治理，Metastore 挂了查不了表，但 HDFS 上的文件不会丢，这也是区分内部表、外部表的前提。

1.4 Metastore 的三种部署模式

Metastore 本身有三种运行方式，生产环境基本只用第三种：

模式
结构
适用场景
嵌入式
Metastore 与 Hive 进程同进程，元数据默认存 Derby
本地调试、单用户，Derby 不支持并发写
本地模式
Metastore 仍在 Hive 进程内，但元数据外置到 MySQL
小规模单机部署
远程模式
Metastore 独立成服务，HS2 通过 RPC 访问
生产标准部署，多实例共享一套元数据

生产配置里常见的外置 Metastore 片段（hive-site.xml）：

<!-- 元数据外置到 MySQL，避免默认 Derby 的单进程限制 -->
<property>
  <name>hive.metastore.uris</name>
  <value>thrift://metastore-host:9083</value>
</property>
<property>
  <name>javax.jdo.option.ConnectionURL</name>
  <value>jdbc:mysql://mysql-host:3306/hive_meta?useSSL=false</value>
</property>

1.5 内部表与外部表：drop 时谁删数据

这是 Hive 最容易在面试和生产事故里反复出现的概念，判断标准只有一条：drop 表的时候，Hive 删不删 HDFS 上的文件。

对比项
内部表（Managed Table）
外部表（External Table）
创建方式
CREATE TABLE
CREATE EXTERNAL TABLE
数据归属
Hive 管理生命周期
文件由外部系统管理，Hive 只登记元数据
drop 行为
元数据和 HDFS 目录一起删
只删元数据，文件原样保留
典型用途
数仓中间层、临时结果表
原始日志、共享数据、多引擎共用的表
-- 内部表：drop 后目录一并消失
CREATE TABLE dwd_order (
  order_id STRING,
  amount  DOUBLE
) STORED AS ORC;

-- 外部表：drop 只清元数据，日志文件仍在 HDFS 上
CREATE EXTERNAL TABLE ods_access_log (
  ip      STRING,
  url     STRING,
  ts      BIGINT
)
LOCATION '/warehouse/ods/access_log'
STORED AS TEXTFILE;

实操建议：原始数据层一律建外部表，防止误操作把上游还在用的文件删掉；清洗后的中间结果可以用内部表，让 Hive 跟着任务周期回收空间。

</property>

1.7 容易踩的坑

  • 把 Metastore 当成数据仓库：它只存 schema，文件在 HDFS；备份元数据不等于备份业务数据。
  • 外部表误建成内部表：上线前确认 EXTERNAL 关键字，否则一次 drop 就把原始日志目录清掉。
  • Derby 当生产库：Derby 是嵌入式单连接数据库，第二个会话启动就会报元数据锁冲突。
  • 跨引擎共用表时删表：如果一张表还被 Spark、HBase 等读取，优先用外部表，避免 Hive 单方面删文件。
  • 误以为 Hive 是数据库：行级随机写、事务并发、点查都不是它的强项，需求落到这些场景要换组件。

1.9 清单

  1. Hive 是建在 Hadoop 之上的离线数仓引擎，把 HQL 翻译成分布式作业，不承担在线事务
  2. 三个核心角色：Driver 编译调度、HiveServer2 对外提供 JDBC/ODBC、Metastore 存元数据
  3. 数据在 HDFS，资源由 YARN 分配，计算引擎可在 MapReduce、Tez、Spark 之间替换
  4. 生产用远程模式 Metastore，元数据外置到 MySQL，不要用默认 Derby
  5. 内部表 drop 删元数据和文件，外部表 drop 只删元数据；原始层一律用外部表
  6. 2.x 起推荐 Tez，3.x 支持物化视图；选型先确认业务是离线分析还是在线读写
