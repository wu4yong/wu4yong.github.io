    mysql-22-MVCC

    📅 2022-12-02

    MVCC：版本链、Read View 与可重复读怎么实现

    每行都挂着自己的历史版本，ReadView 决定「这一次查询能看到哪个版本」｜依据 MySQL 8.4 Consistent Nonlocking Reads 与 undo 章节自绘

    一、学习目标

    1. 说出 InnoDB 行里的三个隐藏列，以及版本链是怎么串起来的；
    2. 会用 ReadView 的四要素手工推演一行数据「可见 / 不可见」；
    3. 说清 RR 与 RC 在快照建立时机上的唯一差异，以及 MVCC 为什么救不了当前读。

    二、前置知识

    事务与隔离级别（MQ21）、undo log 概念。知道「二级索引叶子存主键」也会帮助理解本节末尾的细节。

    三、理论讲解（官方定义）

    MVCC（多版本并发控制）让读不加锁也能读到一致的数据：写操作更新行时，把旧值留在 undo log 里，读操作按自己的「可见性规则」沿版本链找到合适的版本。

    官方（Consistent Nonlocking Reads）表述：

    • 一致性读通过多版本给查询一个时间点快照，看到的是「该时间点之前已提交」的数据；
    • RR 下同一事务所有一致性读共用第一次读建立的快照；
    • RC 下每次一致性读都新建快照；
    • 一致性读不加任何锁，所以不阻塞写。

    四、原理拆解

    先比 trx_id 落在哪个区间，再决定沿链往回走还是直接返回｜依据 MySQL 8.4 事务与 undo 章节自绘

    1. 行里的三个隐藏列

    InnoDB 每行都有：

    隐藏列 作用
    DB_TRX_ID 最后修改该行的事务 ID（6 字节）
    DB_ROLL_PTR 指向 undo log 里上一个版本（7 字节）
    DB_ROW_ID 无显式主键时的隐藏行号（6 字节）

    DB_ROLL_PTR 就是版本链的「指针」，每次更新都把旧版本写进 undo，新行指回旧版本。

    2. 版本链长什么样

    当前行 (trx 100) → undo (trx 90) → undo (trx 80) → ...

    每个 undo 记录里也有自己的 DB_TRX_ID。一次快照读拿到行之后，若发现 DB_TRX_ID 对自己不可见，就顺着 DB_ROLL_PTR 往回找，直到找到一个可见版本。

    3. ReadView 的四个要素

    事务第一次快照读时生成 ReadView：

    字段 含义
    m_ids 生成时**活跃（未提交）**的事务 ID 列表
    min_trx_id m_ids 中的最小值
    max_trx_id 生成时下一个将要分配的事务 ID
    creator_trx_id 当前事务自己的 ID

    可见性判断（对行的 DB_TRX_ID）：

    1. 等于 creator_trx_id → 可见（自己改的）；
    2. 小于 min_trx_id → 可见（早于所有活跃事务，已提交）；
    3. 大于等于 max_trx_id → 不可见（快照之后才开的事务）；
    4. 落在 [min_trx_id, max_trx_id)：在 m_ids 里 → 不可见（当时还活跃）；不在 → 可见（已提交）。

    4. RR 与 RC 的唯一差别

    • RR：ReadView 在第一次快照读时创建，整个事务复用；
    • RC：每次快照读都新建 ReadView。

    所以 RC 能看到别人刚提交的修改，RR 看不到。除此之外版本链与判断规则完全一样。

    5. MVCC 的三条边界

    1. 只作用于快照读。SELECT ... FOR UPDATE、UPDATE、DELETE 都是当前读，读最新版本并加锁；
    2. 不解决写写冲突。两个事务同时改同一行，靠行锁排队，不是 MVCC；
    3. 依赖 undo 不被清理。长事务会让旧版本无法 purge，版本链变长、undo 膨胀。

    五、场景说明

    1. 电商详情页：RR 下多次查询拿到同一快照，避免价格、库存显示错位；
    2. 对账任务：一次事务里扫多张表，保证都在同一时间点；
    3. 高并发读：快照读不加锁，读写互不阻塞，这是 InnoDB 读性能的基础；
    4. 读己之写：同一事务里 UPDATE 后再 SELECT，能看到自己的修改（creator_trx_id 规则）；
    5. 历史回溯：需要「某时刻的旧值」时，MVCC 并不提供 API，只能靠版本链 + 事件溯源表。

    六、示例代码/实操步骤

    1. 观察版本链的存在

    -- 事务 A（RR）
START TRANSACTION;
SELECT balance FROM t_account WHERE id = 1;      -- 100

-- 事务 B
UPDATE t_account SET balance = 50 WHERE id = 1;
COMMIT;

-- 事务 A 再读：仍 100，说明读的是 undo 里的旧版本
SELECT balance FROM t_account WHERE id = 1;

-- 事务 A 当前读：读到 50
SELECT balance FROM t_account WHERE id = 1 FOR UPDATE;
COMMIT;

    2. 查看事务与 undo

    SELECT trx_id, trx_state, trx_started, trx_isolation_level, trx_rows_modified
FROM information_schema.INNODB_TRX;

-- undo 表空间与回收情况
SELECT NAME, STATE, SIZE FROM information_schema.INNODB_TABLESPACES WHERE NAME LIKE '%undo%';
SHOW ENGINE INNODB STATUS;   -- 关注 History list length

    3. 手工推演一次可见性

    假设事务 200 开启，ReadView 为 m_ids=[150, 180]、min=150、max=201、creator=200：

    • 行 DB_TRX_ID=120：< min → 可见；
    • 行 DB_TRX_ID=150：在 m_ids → 不可见，沿链回退；
    • 行 DB_TRX_ID=175：不在 m_ids 且 < max → 可见（已提交）；
    • 行 DB_TRX_ID=210：≥ max → 不可见。

    4. 让 RC 与 RR 行为对比

    SET SESSION transaction_isolation = 'READ-COMMITTED';
START TRANSACTION;
SELECT balance FROM t_account WHERE id = 1;   -- 100
-- 另一会话更新并提交
SELECT balance FROM t_account WHERE id = 1;   -- 50
COMMIT;

    Java 侧怎么落地：别把快照读用错

    1. 查询不要加锁：只有需要「读后立刻改」时才用 FOR UPDATE，普通查询用快照读；
    2. 事务里别混用两种读：先 SELECT 判断再 UPDATE 是典型竞态，直接写 UPDATE ... WHERE 条件 让数据库判断；
    3. 对账类任务显式开事务：保证多表读同一快照，别分散在多次自动提交里；
    4. 避免长事务：查询大结果集分批处理，别把一个事务开几分钟，否则 undo 无法回收；
    5. 缓存与快照要分清：MVCC 保证的是事务内一致，不保证跨请求一致，跨请求要靠缓存版本号或读库重试。

    七、常见坑

    1. 以为 RR 的 SELECT 能看到最新数据：普通 SELECT 读快照，看不到别人新提交的行；
    2. SELECT 判断再 UPDATE：两条语句之间数据可能已变，必须用条件更新或加锁读；
    3. 长事务撑爆 undo：History list length 持续增长，磁盘与读性能双降；
    4. 把 MVCC 当「无锁」：写写仍要行锁，MVCC 只优化读；
    5. RC 下依赖「同一事务读一致」：每次读新建快照，多次查询可能看到不同数据；
    6. INSERT ... SELECT 的读不是快照读：默认用更强锁，读部分按 RC 语义处理；
    7. DDL 期间的一致性读报错：ALTER TABLE 重建表后，旧快照读到 ER_TABLE_DEF_CHANGED。

    八、版本差异

    • 5.7：MVCC 机制与 8.0 基本一致；information_schema.INNODB_TRX 字段较少；
    • 8.0：performance_schema.data_locks 提供更细的锁信息；隐藏列与 undo 结构不变；
    • 8.4：机制一致；undo 表空间管理沿用 8.0 的自动截断（innodb_undo_log_truncate）。

    九、课后小结

    • 隐藏列 DB_TRX_ID / DB_ROLL_PTR 构成版本链，旧版本存在 undo；
    • ReadView 四要素：m_ids、min_trx_id、max_trx_id、creator_trx_id；
    • 可见性判断四步：自己改的可见、早于 min 可见、晚于 max 不可见、区间内看是否活跃；
    • RR 一次快照用到底，RC 每次读都新建；
    • MVCC 只管快照读，写写冲突仍靠行锁，长事务会拖垮 undo。

    十、思考题

    1. 为什么同一事务里先 UPDATE 再 SELECT 能看到自己的修改？

      参考回答：判断可见性时，行的 DB_TRX_ID 等于当前事务的 creator_trx_id，直接判为可见，不需要沿版本链回退。

    2. RC 下「同一事务两次读到不同值」是 bug 吗？

      参考回答：不是。RC 每次一致性读都新建 ReadView，能看到期间其他事务已提交的修改，这正是 RC 的语义。

    3. MVCC 能不能防止两个事务同时扣减库存？

      参考回答：不能。MVCC 只影响读，两个 UPDATE 仍要靠行锁排队；正确写法是用 UPDATE ... SET stock = stock - 1 WHERE stock >= 1 让数据库做原子判断。

    4. 长事务为什么会撑大 undo？

      参考回答：只要旧 ReadView 还在，它可能需要的旧版本就不能被 purge，undo 记录持续累积；事务结束后 purge 线程才能回收。

    5. 当前读为什么读不到旧版本？

      参考回答：当前读的定义就是读最新已提交版本并加锁，用于保证「读到的值接下来可以安全修改」，它不参与 ReadView 判断。
