    redis-9-ZSet

    📅 2022-12-30

    Sorted Set：分值排序与范围查询

    dict 定位成员、skiplist 维持有序，以及六条高频命令｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 讲清 Sorted Set 的「成员唯一 + 分值可排序」双重约束，以及 score 是 double 意味着什么；
    2. 掌握 ZADD 的选项、ZRANGE 的三种取数方式（按排名 / 按分数 / 按字典序），不再用已废弃的命令；
    3. 理解 dict + skiplist 双结构的代价，能判断排行榜、延时队列、范围检索各自的实现成本。

    二、前置知识

    RD08（Set）。Sorted Set 相当于「给 Set 的每个成员挂一个分值」，所以先理解 Set 的唯一性，再来理解排序。

    三、理论讲解（官方定义）

    官方定义（原文）：

    A Redis sorted set is a collection of unique strings (members) ordered by an associated score. … If multiple elements have the same score, they are ordered lexicographically by their member string.

    —— https://redis.io/docs/latest/develop/data-types/sorted-sets/

    三个硬信息：

    • members 唯一：和 Set 一样，成员不能重复；
    • 按 score 排序：排序依据是分值，不是插入顺序；
    • 同分按 member 字典序：这是一条容易忽略但影响结果稳定性的规则。

    score 的类型（原文要点）：score 是双精度浮点（double），可以是负数，也支持 +inf / -inf 表示无穷。所以它不是一个「整数排行榜」，而是一个浮点排序键——精度问题（后面讲坑）就出在这里。

    四、原理拆解

    1. 双结构：为什么要存两份

    Sorted Set 内部同时维护：

    • dict（哈希表）：member → score，让 ZSCORE 是 O(1)；
    • skiplist（跳跃表）：按 (score, member) 排序，让范围查询与排名是 O(log N)。

    这解释了为什么相同数据要存两遍：一份用于「按成员找分」，一份用于「按分找成员」。内存开销约为同等规模 Set 的 2 倍上下，这是 Sorted Set 贵的原因，也是「能用 Set 就别用 ZSet」的依据。

    2. 三种取数方式，别再用废弃命令

    ZRANGE（6.2 起统一）覆盖了老的三条命令：

    ZRANGE key start stop [BYSCORE | BYLEX] [REV] [LIMIT offset count] [WITHSCORES]

    三种模式：

    模式
    参数含义
    典型用途
    默认（按排名）
    start/stop 是下标，0 是最低分，-1 是最高分
    ZRANGE rank 0 9 取 TOP 10
    BYSCORE
    start/stop 是分数区间，(1.5 表示不含
    取 80–100 分段
    BYLEX
    start/stop 是成员字典序，[a、(b
    同分内的字典序检索

    关键约束：BYLEX 只在「所有成员同分」时结果才被官方定义为有意义。分数不同时，BYLEX 的结果是未指定的（unspecified）。这条不是可选的注意事项，而是使用前提。

    REV 反转方向；LIMIT offset count 只对 BYSCORE / BYLEX 生效（按排名时用下标就够了）。

    被替代的旧命令：ZRANGEBYSCORE、ZREVRANGEBYSCORE、ZRANGEBYLEX、ZREVRANGEBYLEX 在 6.2 起标记为废弃（deprecated），仍可用但官方建议换 ZRANGE ... BYSCORE/BYLEX。

    3. ZADD 的选项：每个都在解决一个真实问题

    ZADD key [NX | XX] [GT | LT] [CH] [INCR] score member [score member ...]
    • NX：成员不存在才加；XX：成员存在才更新。二者互斥。
    • GT：只有新分数更大时才更新；LT：更小才更新。
      • 注意：GT/LT 与 NX 不能同时使用（官方明确限制）。
      • 这一点让 GT 成为「排行榜只涨不跌」的正确实现：重复上报分数不会把名次打下来。
    • CH：返回值从「新增成员数」变为「新增 + 变化成员数」。默认返回值只统计新增，很多人因此误判「更新没成功」。
    • INCR：把 ZADD 变成 ZINCRBY 的语义，对单个成员做增量并返回新分数。

    ZINCRBY 本身就是原子的「加分」：ZINCRBY rank 1 alice。这就是直播间热度、文章点赞排行的标准写法——它比「ZSCORE 读 + ZADD 写」安全，因为后者在并发下会丢更新。

    4. 范围删除与弹出

    • ZREMRANGEBYRANK / ZREMRANGEBYSCORE / ZREMRANGEBYLEX：按三种维度批量删，O(log N + M)；
    • ZPOPMIN / ZPOPMAX（可带 count）：弹出最小/最大；
    • BZPOPMIN / BZPOPMAX：阻塞版，这才是「延时队列」的可用形态——空集合上阻塞等待，到点前一直等。

    延时队列的经典做法不是「轮询 ZRANGEBYSCORE」，而是用阻塞弹出配合「下一个到期时间」判断；但要注意 BZPOPMIN 只能阻塞到有数据，不能阻塞到「某个时间点」，所以工程上常用「短超时轮询 + 小批量弹出」。

    dict + skiplist 双结构、rank 与分数的区别、新命令与四条陷阱｜依据 Redis 7.4 Sorted sets / ZADD / ZRANGE 自绘

    五、场景说明

    1. 排行榜：ZINCRBY rank:hot 1 post1001，ZREVRANGE rank:hot 0 9 WITHSCORES 取 TOP 10；
    2. 延时任务：score 存「到期时间戳（毫秒）」，ZRANGEBYSCORE/ZRANGE ... BYSCORE 捞到期任务，ZREM 后执行；
    3. 滑动窗口限流：ZADD rate:uid now uid:reqId + ZREMRANGEBYSCORE rate:uid 0 now-window + ZCARD；
    4. 分数区间筛选（比如价格区间）：ZRANGE products BYSCORE 100 200；
    5. 同分内的字典序分页：所有成员同分时用 BYLEX，比如「按手机号前缀找用户」；
    6. 带权重的抽奖/加权队列：score 是权重，ZPOPMAX 取权重最高者。

    不适合：需要存重复成员（用 List/Stream）、需要集合运算但不需要排序（用 Set，内存省一半）、成员分值会频繁抖动且总量极大（跳跃表维护成本高，考虑换成「分段桶 + 局部排序」）。

    六、示例代码/实操步骤

    # 1. 基础写入与读取
127.0.0.1:6379> ZADD rank 98 alice 88 bob 76 carl
(integer) 3
127.0.0.1:6379> ZRANGE rank 0 -1 WITHSCORES
1) "carl"
2) "76"
3) "bob"
4) "88"
5) "alice"
6) "98"
127.0.0.1:6379> ZREVRANGE rank 0 1 WITHSCORES    # 取前两名
1) "alice"
2) "98"
3) "bob"
4) "88"

# 2. 单人分数与排名
127.0.0.1:6379> ZSCORE rank alice
"98"
127.0.0.1:6379> ZRANK rank alice
(integer) 2                     # 从 0 开始，升序排名
127.0.0.1:6379> ZREVRANK rank alice
(integer) 0                     # 从高到低是第 1 名

# 3. 原子加分（排行榜标准写法）
127.0.0.1:6379> ZINCRBY rank 5 bob
"93"
127.0.0.1:6379> ZREVRANGE rank 0 0 WITHSCORES
1) "alice"
2) "98"

# 4. 只涨不跌：GT
127.0.0.1:6379> ZADD rank GT 90 bob
(integer) 0                     # 90 < 93，不更新
127.0.0.1:6379> ZADD rank LT 90 bob
(integer) 0                     # 90 < 93，LT 命中，更新了，但默认返回 0
127.0.0.1:6379> ZADD rank CH LT 80 bob
(integer) 1                     # 加 CH 才把「变化」计入返回值
127.0.0.1:6379> ZSCORE rank bob
"80"

# 5. 按分数区间取
127.0.0.1:6379> ZRANGE rank 80 100 BYSCORE WITHSCORES
1) "bob"
2) "80"
3) "alice"
4) "98"
127.0.0.1:6379> ZRANGE rank (80 +inf BYSCORE LIMIT 0 1
1) "alice"                      # 左括号表示不包含 80

# 6. 同分时的字典序
127.0.0.1:6379> DEL lex
127.0.0.1:6379> ZADD lex 0 a 0 b 0 c 0 d
(integer) 4
127.0.0.1:6379> ZRANGE lex [b (d BYLEX
1) "b"
2) "c"                          # [d 不含，所以到 c 为止

# 7. 计数与区间删除
127.0.0.1:6379> ZCOUNT rank 80 100
(integer) 2
127.0.0.1:6379> ZCARD rank
(integer) 3
127.0.0.1:6379> ZREMRANGEBYSCORE rank -inf 79
(integer) 0

# 8. 弹出与阻塞弹出（延时队列片段）
127.0.0.1:6379> ZADD delay:queue 1700000000000 taskA
127.0.0.1:6379> ZPOPMIN delay:queue
1) "taskA"
2) "1700000000000"
# 终端 A（阻塞版）：
127.0.0.1:6379> BZPOPMIN delay:queue 3
# 3 秒内有数据则立即返回，否则 nil

    Java 侧怎么落地：排行榜与延时队列

    ZSet 在 Spring Boot 里用 opsForZSet()，两个场景最典型：热度榜和延时任务。

    1. 加分只能 incrementScore，它就是 ZINCRBY，原子；不要「先 score(key, member) 再 add」，那会丢更新：
    Double now = tpl.opsForZSet().incrementScore("rank:hot", "post1001", 1);   // ZINCRBY
Set<TypedTuple<String>> top10 = tpl.opsForZSet()
        .reverseRangeWithScores("rank:hot", 0, 9);                        // ZREVRANGE 0 9 WITHSCORES

    1. rangeByScore 对应 ZRANGE ... BYSCORE，Offset / Limit 用 RedisZSetCommands.Limit 传，别一次捞全量；score(key, member) 是 ZSCORE，rank(key, member) 是 ZRANK（从 0 开始）。

    2. 延时队列用 popMin(key, timeout)（ZPOPMIN / BZPOPMIN）：score 存到期毫秒时间戳，消费者短超时阻塞轮询，取出后判断 score <= now 才执行，否则再 add 回去——这样才不会被「还没到点」的任务提前消费。

    3. 内存与裁剪：千万级 ZSet 别整取，用 removeRangeByRank(key, 0, -(N+1)) 定期裁到 TOP N，对应 ZREMRANGEBYRANK。

    七、常见坑（官方明确说明的限制）

    1. score 是 double，不是整数。0.1 + 0.2 这类浮点累加会积累误差，导致「明明该并列第一却差了一位」。要精确计数，score 存整数（比如以「分为单位」的整数）。
    2. 同分时按 member 字典序排。所以「同分随机顺序」是不存在的；需要随机就自己加扰动（如 score*1000 + random）。
    3. BYLEX 要求所有成员同分，分数不同时官方明确说结果是未指定的。把 BYLEX 用在「分数各不相同的排行榜」上是误用。
    4. ZADD 默认返回值只统计新增，不含更新。以为「更新失败」其实是返回值语义没搞清，加 CH 即可。
    5. GT/LT 不能与 NX 同时用（官方限制）。想同时表达「不存在则加、存在则只涨」，需要两步或 Lua。
    6. ZRANGEBYSCORE 等旧命令 6.2 起废弃，新代码统一用 ZRANGE ... BYSCORE/BYLEX/REV。
    7. 内存成本约为 Set 的两倍。十万成员的排行榜没问题，千万成员要评估；分片或定期裁剪（ZREMRANGEBYRANK 只留 TOP N）是常规手段。
    8. ZRANGE 大区间是 O(log N + M)，一次取十万成员会阻塞主线程；分页请用小 LIMIT。

    版本差异（8.x 标注）

    7.4 与 8.x 在 Sorted Set 语义上一致。历史节点：6.2 统一 ZRANGE 系列并废弃 ZRANGEBY*，7.2 起 ZRANK / ZREVRANK 支持 WITHSCORE。旧项目升级时优先替换废弃命令，行为差异主要在返回值。

    依据：https://redis.io/docs/latest/develop/data-types/sorted-sets/

    八、课后小结

    • Sorted Set = 唯一成员 + double 分值，同分按 member 字典序排；
    • 内部是 dict（成员→分值，O(1)）与 skiplist（有序范围，O(log N)）双结构，内存约为 Set 的两倍；
    • ZRANGE 三模式：默认按排名、BYSCORE 按分数、BYLEX 按字典序（须同分）；
    • ZADD 的 GT/LT 是「只涨/只跌」的正解，CH 才把更新计入返回值；
    • ZINCRBY 是并发安全的加分方式，别用「读+写」；
    • 旧 ZRANGEBYSCORE 系列自 6.2 废弃。

    九、思考题

    1. 排行榜用「ZSCORE 读 + ZADD 写」实现加分，两个客户端同时加分会发生什么？ZINCRBY 为什么没这个问题？

      参考回答：两个客户端都读到 98，各自算成 99 再 ZADD，最后只加了 1 分，丢一次更新。ZINCRBY 是单条命令，读改写全在服务端一次执行（单线程串行），所以两次加分必然得到 +2。

    2. 一个「按手机号前缀查用户」的需求，成员分数各不相同，能不能用 BYLEX？官方对此怎么说？

      参考回答：不能。官方明确：BYLEX 只在所有成员分数相同时结果才有意义，分数不同时结果是未指定的。正确做法是先把同前缀用户放进一个同分的 ZSet（score 统一为 0），再 ZRANGE ... BYLEX；或干脆用 SCAN MATCH prefix*（注意性能）。

    3. 用 score 存毫秒时间戳做延时队列，2038 年之后会出问题吗？score 的 double 精度能精确表示到多少位？

      参考回答：不会因为 32 位溢出出问题，score 是 64 位 double；但 double 只能精确表示到 2^53（约 9.007×10^15），毫秒时间戳到 2038 年约 2.1×10^12，远小于上限，安全区间内。真正的风险是超过 2^53 后（约公元 28 万年）失去秒级精度，工程上不用考虑。

    4. 千万级成员的排行榜，内存怎么估？有哪两种「只留 TOP N」的裁剪策略，各自的代价是什么？

      参考回答：按经验每个成员约 100 字节量级（dict entry + skiplist 节点 + member 字符串），千万成员就是 GB 级，必须在设计期就分片或裁剪。两种裁剪：① 写入后 ZREMRANGEBYRANK key 0 -(N+1)，每次写多一次 O(log N+M) 操作；② 定时任务批量裁，代价是榜单短暂「超员」，且裁剪期间内存峰值更高。

    5. ZADD key GT score member 在成员不存在时会怎样？这与 NX 组合为什么被官方禁止？

      参考回答：成员不存在时 GT 会照常插入（GT 只约束「已存在成员是否更新」，不拦新增），所以它本身已经带了「不存在就加」的语义。与 NX（只加不更新）组合时语义自相矛盾——NX 说「已存在就不动」，GT 说「已存在且更大就更新」，官方因此明确两者不能同时使用。
