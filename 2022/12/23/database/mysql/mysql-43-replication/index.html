    mysql-43-replication

    📅 2022-12-23

    主从复制：一条 binlog 怎么到从库

    主库写 binlog → 从库拉 relay log → 从库回放，三段各有自己的延迟｜依据 MySQL 8.4 Replication 说明自绘

    一、学习目标

    1. 说清复制链路的三个线程与两个日志，知道延迟可能卡在哪一段；
    2. 会用 File + Position 与 GTID 两种坐标搭建复制；
    3. 会用 SHOW REPLICA STATUS 的字段判断链路是否健康。

    二、前置知识

    binlog 三种格式与 sync_binlog（MQ32）、redo 与崩溃恢复（MQ30）。

    三、理论讲解（官方定义）

    MySQL 复制是基于 binlog 的异步复制，链路为：

    1. 主库把变更写入 binlog；
    2. 主库的 dump 线程（binlog dump thread）按位点或 GTID 把事件推给从库；
    3. 从库的 IO 线程 拉取事件并写入本地 relay log；
    4. 从库的 applier 线程（SQL 线程） 读 relay log 并在从库重放。

    8.0.22 起术语统一为 source / replica，SHOW SLAVE STATUS 改名为 SHOW REPLICA STATUS，CHANGE MASTER TO 改为 CHANGE REPLICATION SOURCE TO。

    四、原理拆解

    手写位点容易错，GTID 让「从哪继续」变成自动的｜依据 MySQL 8.4 GTID / SHOW REPLICA STATUS 说明自绘

    1. 两种复制坐标

    方式 记录什么 切换影响
    File + Position binlog 文件名 + 偏移量 主从切换必须重算，人肉易错
    GTID 每个事务的全局唯一编号集合 SOURCE_AUTO_POSITION=1 自动找位置

    GTID 是 5.6 引入、8.x 的推荐方式：从库知道自己执行过哪些事务，重搭或切换都不用手算位点。

    2. 三段延迟要分开看

    • 拉取段：主库 dump 推送慢 / 网络带宽不足 → Relay_Log_Space 持续增长；
    • 回放段：从库 applier 跟不上 → Seconds_Behind_Source 上升；
    • 结构变更段：从库执行 DDL 时后续事件全部排队，表现为「延迟突然拉高再回落」。

    Seconds_Behind_Source 只看回放线程，不能反映 IO 段与前段网络延迟，必须配合 Relay_Log_Space 与 GTID 差值一起看。

    3. 复制的三个前提

    1. server_id 全局唯一（主从都不能重复）；
    2. 主库 log_bin=ON、binlog_format=ROW（8.4 默认）；
    3. 从库 read_only=ON（super_read_only 更强），避免误写。

    4. 一致性从哪来

    异步复制不保证从库拿到最新数据；主库崩溃时，尚未推送的 binlog 就丢了。要「不丢已提交事务」，得叠加半同步复制（MQ44）或 MGR（MQ46）。

    五、场景说明

    1. 读写分离底座：一主两从，从库承接报表与列表查询；
    2. 备份窗口：在从库做逻辑/物理备份，避免影响主库；
    3. 机房容灾：跨机房从库，注意网络 RTT 对拉取段的影响；
    4. 灰度验证：把新版本应用连到从库做读写演练；
    5. 大表迁移：从库做 ALTER 验证，再上主库。

    六、示例代码/实操步骤

    1. 主库侧准备

    -- my.cnf
-- [mysqld]
-- server_id=1
-- log_bin=mysql-bin
-- binlog_format=ROW
-- gtid_mode=ON
-- enforce_gtid_consistency=ON
    CREATE USER 'repl'@'10.0.%' IDENTIFIED BY 'Repl_2022#';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'10.0.%';

    2. 从库侧建立复制（GTID 方式）

    -- my.cnf
-- [mysqld]
-- server_id=2
-- relay_log=relay-bin
-- read_only=ON
-- super_read_only=ON
-- gtid_mode=ON

CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='10.0.3.11',
  SOURCE_PORT=3306,
  SOURCE_USER='repl',
  SOURCE_PASSWORD='Repl_2022#',
  SOURCE_AUTO_POSITION=1;

START REPLICA;

    3. 看健康状况

    SHOW REPLICA STATUS\G
-- 关注：
-- Replica_IO_Running: Yes
-- Replica_SQL_Running: Yes
-- Seconds_Behind_Source
-- Relay_Log_Space
-- Retrieved_Gtid_Set / Executed_Gtid_Set

    4. 传统位点方式（老环境兼容）

    -- 主库
SHOW MASTER STATUS;   -- 记下 File 与 Position（8.4 用 SHOW BINARY LOG STATUS）
-- 从库
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='10.0.3.11', SOURCE_USER='repl', SOURCE_PASSWORD='...',
  SOURCE_LOG_FILE='mysql-bin.000023', SOURCE_LOG_POS=1048576;
START REPLICA;

    5. Java 侧怎么落地：主从在应用里的边界

    1. 数据源分组：HikariCP 配 master/replica 两个数据源，@Transactional 内强制走主库；
    2. 只读事务标记：@Transactional(readOnly = true) 交给路由层决定是否走从库；
    3. 健康检查：/actuator/health 里加复制延迟探针，延迟超阈值自动摘除该从库；
    4. 切换预案：切换后应用必须能重连新主，连接池 maxLifetime 要小于故障发现时间；
    5. 禁止直连从库写：从库开 super_read_only，应用侧不做任何绕过。

    七、常见坑

    1. server_id 冲突：复制直接起不来或循环复制；
    2. 从库被应用写入：主从数据分叉，后续只能重搭；
    3. 只看 Seconds_Behind_Source：忽略 IO 段，误判健康；
    4. binlog_format=STATEMENT：函数、时间戳类语句在从库重放出错；
    5. 大事务：单事务几百万行，从库回放长时间卡住；
    6. 改 gtid_mode 未按官方步骤：需 OFF → OFF_PERMISSIVE → ON_PERMISSIVE → ON 逐步切换；
    7. 网络抖动未监控：拉取段延迟全靠 Relay_Log_Space 才能看出来。

    八、版本差异

    • 5.6：GTID 引入，relay_log_info_repository=TABLE 可选；
    • 5.7：并行复制（LOGICAL_CLOCK）、gtid_mode 在线切换完善；
    • 8.0：CHANGE REPLICATION SOURCE TO（8.0.23 术语统一）、SHOW REPLICA STATUS（8.0.22）、崩溃安全复制（表存元数据）；
    • 8.4：沿用 8.0 复制体系，SHOW BINARY LOG STATUS 取代 SHOW MASTER STATUS，默认 binlog_format=ROW。

    九、课后小结

    • 复制三段：主库 dump → 从库 IO 拉 relay log → applier 回放；
    • 延迟要分段定位，Seconds_Behind_Source 只覆盖回放段；
    • GTID 是 8.x 推荐方式，切换与重搭不用手算位点；
    • 异步复制不保证不丢数据，要更强一致性得叠半同步或 MGR；
    • 从库必须 super_read_only，否则主从分叉不可逆。

    十、思考题

    1. Seconds_Behind_Source = 0 是否等于从库数据最新？

      参考回答：不等于。该值只反映 applier 线程的相对落后时间，IO 线程可能仍在拉取、网络可能积压，甚至主库刚提交的事务还没推送。要结合 Relay_Log_Space、GTID 差值与心跳表时间差综合判断。

    2. 为什么推荐 GTID 而不是 File + Position？

      参考回答：GTID 给每个事务全局唯一编号，从库通过 SOURCE_AUTO_POSITION=1 自动补齐缺失事务，主从切换、重建从库都不需要人工计算位点；位点方式一旦算错就会重复或漏掉事务，且难以校验。

    3. 从库 read_only=ON 足够吗，为什么还要 super_read_only？

      参考回答：read_only 对具有 SUPER 权限的账号无效，运维账号或应用误用高权限账号仍可写入，造成主从分叉。super_read_only 连 SUPER 也限制，只有复制线程能写，更安全。

    4. 主库执行一个大 DDL，从库延迟为什么会突然拉高？

      参考回答：relay log 中的事件严格串行回放，DDL 在从库执行期间会持有元数据锁，后续所有事件只能排队等待。窗口越长，堆积越多，延迟表现为陡升后缓慢回落。

    5. 复制断了，Replica_IO_Running=No 与 Replica_SQL_Running=No 有什么区别？

      参考回答：IO 为 No 表示从库连不上主库（网络、账号、权限、主库 dump 线程被占满）；SQL 为 No 表示回放出错（数据冲突、表不存在、GTID 冲突）。前者查连接与网络，后者看 Last_SQL_Error 与 performance_schema.replication_applier_status。
