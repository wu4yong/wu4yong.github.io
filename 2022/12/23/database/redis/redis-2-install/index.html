    redis-2-安装与连接

    📅 2022-12-23

    安装、启动与 redis-cli 上手

    取得 → 编译 → 启动 → 连接 → 验证的五步闭环｜依据 Redis 7.4 官方 Install / redis-cli 文档自绘

    一、学习目标

    1. 能在 Linux 上完整走完「源码编译安装 → 指定配置文件启动 → redis-cli 验证」这条路；
    2. 能在 macOS 与 Windows 上用官方 Docker 镜像跑起一个可连接、可持久化的实例；
    3. 知道官方支持的三种启动方式各自适用什么场景，生产为什么只选 systemd；
    4. 会用 INFO、DBSIZE、CONFIG GET 这些基础命令确认实例「活着且状态正常」。

    二、前置知识

    RD01：知道 Redis 是内存型数据结构存储，命令由单线程串行执行。

    三、理论讲解（官方定义）

    官方安装文档把安装方式分为三类：操作系统包管理器安装（apt install redis / yum install redis）、源码编译安装，以及官方 Docker 镜像。

    Redis can be installed from source code, compiled, and installed. The make command builds the Redis binaries (redis-server, redis-cli, redis-benchmark, redis-check-aof, redis-check-rdb, redis-sentinel) and make install copies them to /usr/local/bin.

    —— https://redis.io/docs/latest/operate/oss_and_stack/install/install-redis/install-redis-from-source/

    The official Docker image is published as redis on Docker Hub … you can run it with docker run --name some-redis -d redis … to run Redis with a configuration file, mount it and pass it as the container command.

    —— https://redis.io/docs/latest/operate/oss_and_stack/install/install-redis/install-redis-on-docker/

    关键点：编译产物是一组可执行文件，不是「一个服务」。redis-server、redis-cli、redis-sentinel、redis-benchmark 是同一个代码库编译出的不同入口，Sentinel 只是 redis-server 以 --sentinel 模式运行的别名（M4 会讲）。Docker 镜像只是把这组二进制打包进了容器，runs 的还是同一个 redis-server，所以配置项、目录语义、启动顺序完全一致。

    四、原理拆解

    1. 启动时到底发生了什么

    redis-server 启动时按固定顺序做这几件事，理解这个顺序能解释后面 90% 的「改了配置没生效」：

    1. 读取命令行参数与配置文件（默认读当前目录的 ./redis.conf，找不到就用内置默认值）；
    2. 加载配置、初始化事件循环、开始监听端口（默认 6379）；
    3. 如果开启了持久化，在 dir 目录下加载 RDB/AOF 恢复数据；
    4. 进入事件循环，开始接受客户端连接。

    这里有个高频误解：不带配置文件启动，不是「读不到配置所以报错」，而是「用内置默认配置静默运行」。default 里 daemonize no、bind 127.0.0.1、protected-mode yes、requirepass 为空、maxmemory 未设置——这就是为什么新手常常「连不上、也没设密码、内存还一直涨」。

    启动五步、命令行与配置文件的覆盖关系，以及两条启动期硬约束｜依据 Redis 7.4 配置与 redis-server 文档自绘

    2. 三种启动方式与官方推荐

    方式
    命令
    官方/实践口径
    前台
    redis-server / redis-server redis.conf
    只用于本地调试，日志直接打屏，退出即停
    后台
    配置 daemonize yes
    能做，但脱离终端后日志与重启全靠人工
    systemd
    systemctl start redis
    官方提供 unit 文件（Type=notify + supervised systemd），生产唯一推荐

    官方 redis.conf 里有一行专用参数配合 systemd：supervised systemd，它让 Redis 在就绪后通过 systemd 通知机制上报状态。手工改成 daemonize yes 又用 systemd 拉起，会导致 systemd 认为进程已退出而反复重启。

    3. redis-cli 是什么

    redis-cli 是官方自带的命令行客户端：一个 REPL，加一堆运维子命令。它不是「调试工具」那么简单——生产排障时最常用的 --scan、--bigkeys、--latency、--cluster 都在它里面。

    redis-cli --version              # 看客户端版本
redis-cli -h 127.0.0.1 -p 6379    # 指定主机端口
redis-cli -h 127.0.0.1 -p 6379 -a 'pass'   # 带密码（会进 history，生产用 --user/环境变量）
redis-cli --scan --pattern 'user:*'        # 官方推荐的替代 KEYS 的增量扫描

    五、场景说明

    • 开发机（Linux）：源码装 7.4.x，前台启动，随时看日志；
    • 开发机（macOS / Windows）：Docker Desktop + 官方 redis 镜像，一条 docker run 起停，不怕装坏本机；
    • 测试环境：systemd 托管 + 一份版本化的 redis.conf，方便压测与重启验证；
    • 生产：包管理器或官方源安装，配置全部走配置管理工具，禁止 CONFIG SET 后不落盘（RD03 讲边界）。生产不建议把 Redis 跑在 Docker 里做主库——内核参数、OOM killer、网络栈与持久化目录的控制权都不完整，这些在 M8 会展开。

    六、示例代码/实操步骤

    # ① 取得源码（官方源码地址）
wget https://download.redis.io/releases/redis-7.4.2.tar.gz
tar xzf redis-7.4.2.tar.gz && cd redis-7.4.2

# ② 编译与安装（PREFIX 建议显式给，避免污染 /usr/local/bin）
make -j$(nproc) && sudo make install PREFIX=/usr/local/redis

# ③ 准备一份最小配置（生产不要直接改仓库里的 redis.conf 示例）
sudo mkdir -p /etc/redis /var/lib/redis /var/log/redis
sudo cp redis.conf /etc/redis/redis.conf
sudo sed -i 's/^# requirepass .*/requirepass S3cretForClass/' /etc/redis/redis.conf

# ④ 前台启动并观察日志
/usr/local/redis/bin/redis-server /etc/redis/redis.conf

# ⑤ 另开一个终端验证
/usr/local/redis/bin/redis-cli -p 6379 -a 'S3cretForClass'
127.0.0.1:6379> PING
PONG
127.0.0.1:6379> INFO server
# Server
redis_version:7.4.2
redis_mode:standalone
os:Linux 5.15.0 x86_64
uptime_in_seconds:37
127.0.0.1:6379> DBSIZE
(integer) 0
127.0.0.1:6379> CONFIG GET maxmemory
1) "maxmemory"
2) "0"        # 0 = 不限制，这是默认值，也是生产事故的常见源头

    再补一个停止方式，避免 kill -9 之后怀疑人生：

    127.0.0.1:6379> SHUTDOWN          # 正常关闭：会尝试保存数据
127.0.0.1:6379> SHUTDOWN NOSAVE   # 不保存直接关，仅用于演练

    Docker 方式：macOS 与 Windows 走同一条路

    macOS 与 Windows 都没有「官方原生安装包」。官方文档写得很直接：Redis 不在 Windows 上官方支持，Windows 上要么用 WSL2，要么用 Docker；而 macOS 最省事的方式同样是 Docker。所以这两台机器上的路径其实是同一条：装 Docker Desktop → 跑官方 redis 镜像 → 用同一套 redis-cli 命令验证。

    ① 两台机器上唯一不同的前置

    平台
    前置
    说明
    macOS
    Docker Desktop for Mac
    Intel 与 Apple Silicon（arm64）都有对应安装包，镜像官方提供多架构
    Windows
    Docker Desktop + WSL2 后端
    官方推荐用 WSL2；不要用已停止维护的旧版 Hyper-V 方案
    通用
    docker version 能输出 Client 与 Server 两段
    只有 Client 说明 Docker 守护进程没起来

    ② 启动一个可连接、数据不丢的实例

    # 1. 拉取指定版本（不要用 latest，版本漂移会让实验结论不可复现）
docker pull redis:7.4

# 2. 准备宿主机上的数据目录与配置文件（macOS 与 Windows 路径见下方说明）
mkdir -p ~/redis-lab/conf ~/redis-lab/data
cp /path/to/redis.conf ~/redis-lab/conf/redis.conf

# 3. 启动：端口映射 + 配置挂载 + 数据挂载
docker run -d --name redis-lab \
  -p 6379:6379 \
  -v ~/redis-lab/conf/redis.conf:/usr/local/etc/redis/redis.conf \
  -v ~/redis-lab/data:/data \
  redis:7.4 redis-server /usr/local/etc/redis/redis.conf

# 4. 看日志确认真的起来了
docker logs -f redis-lab
# 预期能看到 "Ready to accept connections tcp"

    三个挂载点必须记住，它们对应镜像里的固定路径：

    • /usr/local/etc/redis/redis.conf：官方文档约定的配置文件位置，把宿主机文件挂进来后，启动命令再接上这个路径；
    • /data：镜像的工作目录，RDB 与 AOF 默认落在这里。不挂出来，docker rm 一次数据就没了；
    • -p 6379:6379：宿主机端口映射到容器端口，宿主机上的客户端才能用 127.0.0.1:6379 连。

    ③ 在 macOS 上验证

    # 方式一：容器内自带的 redis-cli
docker exec -it redis-lab redis-cli
127.0.0.1:6379> PING
PONG

# 方式二：宿主机装了 redis（brew install redis）后直连映射端口
redis-cli -h 127.0.0.1 -p 6379 PING

# 数据落盘位置确认（宿主机上能看到 dump.rdb）
ls -l ~/redis-lab/data

    ④ 在 Windows 上验证

    # PowerShell 里跑（Docker Desktop 已启动，WSL2 后端）
docker run -d --name redis-lab -p 6379:6379 redis:7.4
docker exec -it redis-lab redis-cli
127.0.0.1:6379> PING
PONG

# 带配置与数据卷的写法：Windows 上把路径换成盘符形式
docker run -d --name redis-lab `
  -p 6379:6379 `
  -v C:\redis-lab\data:/data `
  redis:7.4 redis-server --appendonly yes

    Windows 上两个容易踩的点：

    • 路径分隔符：Docker Desktop 接受 C:\redis-lab\data 这种写法，但写在脚本里时注意 PowerShell 的反引号续行与 \ 转义；
    • 性能：把数据卷放在 C:\ 之外的大盘上更稳；跨 WSL2 与宿主机的文件访问比容器内部慢，压测时别把 dir 指到挂载盘上做基准。

    ⑤ 连不上时按这个顺序查

    docker ps                      # 容器是否在跑（STATUS 不是 Exited）
docker logs --tail 50 redis-lab # 启动日志里有没有 config 报错
docker exec -it redis-lab redis-cli CONFIG GET bind
# 若配置里写了 bind 127.0.0.1，容器内只监听回环，宿主机映射端口也连不上
# 容器场景通常要 bind 0.0.0.0，安全性交给 -p 只映射到 127.0.0.1 与 ACL 负责

    最后一条是本讲最容易出错的地方：bind 127.0.0.1 在容器里等于「只有容器自己能连」。容器内的回环与宿主机的回环不是一个东西——这和第 124 行讲的「默认组合导致远程连不上」是同一个原因，只是容器把这个问题放大了。

    ⑥ 收尾

    docker stop redis-lab && docker rm redis-lab   # 停止并删除容器（数据卷仍在）
docker rmi redis:7.4                           # 需要时再删镜像

    数据还在不在，取决于你有没有把 /data 挂出来。没挂就是「删容器 = 删数据」，这也是本地实验环境最常见的一次性事故。

    Java 侧怎么落地：让 Spring Boot 连上刚起的实例

    起完服务，下一步是把 Java 工程连上去。顺序是先通网络、再通认证、最后才谈池参数。

    1. 确认服务可达：宿主机上 redis-cli -h 127.0.0.1 -p 6379 PING 先回 PONG，再动代码；容器场景先 docker ps 确认端口映射在。

    2. pom 加 starter：spring-boot-starter-data-redis 一个依赖即可，Boot 会自动装配 LettuceConnectionFactory；要用 Jedis 就排除 lettuce 再引 jedis。

    3. application.yml 按「地址 → 认证 → 超时 → 池」四段写：

    spring:
  data:
    redis:
      host: 127.0.0.1
      port: 6379
      password: S3cretForClass   # 对应 requirepass；不配就是 NOAUTH
      timeout: 2s                # 连不上会在这里暴露，别设成 0 无限等
      lettuce:
        pool: { max-active: 16, max-idle: 8, min-idle: 2, max-wait: 500ms }

    1. 启动自检放在 ApplicationRunner：ping() 成功即证明「网络 + 密码 + 协议」三件事同时通；失败时按异常类型分流：NOAUTH 是密码错，Connection refused 是端口/映射，RedisConnectionFailureException 多为 bind/protected-mode 挡住了。

    2. 写好优雅停机：spring.lifecycle.timeout-per-shutdown-phase 配合 lettuce.shutdown-timeout，避免发布时把进行中的命令掐断。

    3. 本地用 Docker 就固定标签：redis:7.4，别用 latest；Java 侧看到的版本可用 INFO server 或 RedisConnectionFactory 的 info() 打印出来核对。

    七、常见坑（官方明确说明的限制）

    1. protected-mode yes + bind 127.0.0.1 是默认组合，远程连不上是默认行为，不是 bug。要对外开放必须同时改 bind 与 protected-mode，并配 ACL/密码——官方文档在 protected-mode 说明里直接警告过裸奔实例被入侵的后果。
    2. daemonize yes 与 supervised systemd 不能同时用来托管，会打架。
    3. make install PREFIX= 不给的话默认装到 /usr/local/bin，多版本环境容易互相覆盖。
    4. 配置文件里的 dir 必须是存在的绝对路径，否则启动或持久化时报错；RDB/AOF 全部落在 dir 下。
    5. redis-server 前台启动时 Ctrl+C 会触发正常关闭流程，但如果 save 点配置了大快照，关闭会卡住等 fork 完成，看起来像「卡死」。
    6. 容器里沿用 bind 127.0.0.1。容器内的回环不是宿主机的回环，宿主机映射端口后依然连不上；容器场景要 bind 0.0.0.0，安全性交给端口只映射到本机 + ACL 负责。
    7. 不挂 /data 就 docker rm。RDB/AOF 全在容器可写层，删容器等于删数据；官方文档的持久化路径就是 /data。
    8. 用 latest 标签做实验。版本漂移会让「配置为什么不生效」「命令为什么不存在」变得无法复现，固定 redis:7.4 这类明确标签。

    八、课后小结

    • 安装 = 编译 + 落二进制；启动 = 读配置 + 监听 + 加载持久化数据；
    • 不带配置文件启动会用内置默认值静默运行，是「改了配置没生效」的头号原因；
    • 生产只用 systemd 托管，别用 daemonize yes；
    • macOS / Windows 上没有官方原生安装包，走 Docker Desktop + 官方 redis 镜像，配置与命令行完全一致；
    • 容器三件事：挂配置到 /usr/local/etc/redis/redis.conf、挂数据到 /data、-p 映射端口；容器里 bind 必须是 0.0.0.0；
    • PING → PONG 验证的是「服务 + 协议 + 网络」三件事同时通。

    九、思考题

    1. 一个实例 PING 回 PONG，但 INFO 里的 redis_version 是 7.0.11，你能推断出它的安装方式大概率是哪一种？为什么？

      参考回答：7.0.11 这种「次版本号停在很早」的版本，大概率是系统包管理器里的旧包（如 Ubuntu 的 redis-server 长期停在 7.0.x），或某个旧镜像标签；源码编译与官方源装的版本号会跟随上游，7.4.x 才是当前主线。

    2. 为什么官方要把 supervised systemd 单独做成一个配置项，而不是让 init 系统自己去猜？

      参考回答：「进程真的就绪」只有 Redis 自己最清楚（配置读完、持久化加载完、开始监听）。让 init 去猜只能轮询端口或日志，慢且不可靠；supervised systemd 让 Redis 主动 Type=notify 上报 READY，systemd 才能精确判定启动成功。

    3. 如果你在容器里跑 Redis，dir 应该指向哪里，为什么不能留在容器可写层？

      参考回答：指向挂载出来的卷，容器里就是 /data。留在可写层意味着 docker rm 或重建镜像时 RDB/AOF 一起消失；官方镜像的持久化路径就是 /data，挂出来才有「删容器不删数据」。

    4. 容器里为什么不能保留 bind 127.0.0.1？改了之后安全性靠什么补回来？

      参考回答：容器内的 127.0.0.1 是容器自己的回环，宿主机映射过去的端口进不来，要改 0.0.0.0。安全由三层补：-p 127.0.0.1:6379:6379 只映射到本机、requirepass / ACL 做认证、protected-mode 保持开启并配合防火墙。

    5. macOS 上用 Docker 起 Redis 比源码编译省了哪些事，又多了哪些检查点？

      参考回答：省掉编译、libc / 内核差异、版本不可复现和清理残留；多出的是 Docker 守护进程是否在跑、/data 有没有挂、bind 是否还是回环、端口映射是否只到本机、跨挂载盘的文件性能是否影响压测结论。
