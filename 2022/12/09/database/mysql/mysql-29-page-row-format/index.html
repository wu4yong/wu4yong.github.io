    mysql-29-页与行格式

    📅 2022-12-09

    页与行格式：16KB 页、DYNAMIC 与行溢出

    B+Tree 的节点是页，页内是链表，跨页靠指针｜依据 MySQL 8.4 InnoDB 物理结构与行格式说明自绘

    一、学习目标

    1. 记住一个 InnoDB 页的七段结构，理解「页内链表 + 页间 B+Tree」；
    2. 分清四种行格式，知道 DYNAMIC 怎么处理大字段；
    3. 会算一行大概占多少字节，能判断一页装多少行、索引前缀上限在哪。

    二、前置知识

    B+Tree 索引（MQ18）、索引设计（MQ19）。本篇是「为什么索引这么大、为什么大字段拖慢查询」的底层答案。

    三、理论讲解（官方定义）

    InnoDB 以页为磁盘与内存之间传输的最小单位，默认 innodb_page_size = 16KB。B+Tree 的每个节点就是一页（或若干页），一次 IO 至少读一页。

    页的七段结构：

    段 大小 作用
    File Header 38B 页号、前后页指针、校验和、页类型
    Page Header 56B 页内记录数、堆顶位置、目录槽数等
    Infimum + Supremum 26B 两条虚拟记录，页内链表的头与尾
    User Records 变长 实际数据行，按主键有序的单向链表
    Free Space 变长 尚未分配的空间
    Page Directory 变长 每 6 条记录一个槽位，支持页内二分
    File Trailer 8B 校验和 + LSN 低位，用于检测页损坏

    行格式（row format）决定行内字段如何排列、大字段放哪：REDUNDANT、COMPACT、DYNAMIC、COMPRESSED。8.x 新建表默认 DYNAMIC。

    四、原理拆解

    DYNAMIC 把超长字段整段挪到溢出页，行内只留 20 字节指针｜依据 MySQL 8.4 InnoDB Row Formats 说明自绘

    1. 一行里到底存了什么

    按顺序：

    1. 变长字段长度列表（逆序存放每个变长列的长度）；
    2. NULL 位图（可空列各占 1 bit）；
    3. 记录头 5 字节：删除标记、min_rec、n_owned、heap_no、记录类型、next_record 偏移；
    4. 列数据：DB_TRX_ID(6B)、DB_ROLL_PTR(7B)、主键列、其余列。

    next_record 是相对偏移，页内遍历就是沿着这条链走；页与页之间靠 B+Tree 的指针连接。

    2. 页内查找为什么快

    • 先按 Page Directory 槽位二分，定位到大致 6 条记录的范围；
    • 再沿 next_record 链表线性找 6 条；
    • 所以页内是「二分 + 短链表」，不是纯链表扫描。

    3. 四种行格式的差别

    格式 大字段溢出方式 索引前缀上限 备注
    REDUNDANT 768B 前缀 + 20B 指针 767B 最老，基本不用
    COMPACT 768B 前缀 + 20B 指针 767B 5.6 时代主流
    DYNAMIC 整段外移，仅留 20B 指针 3072B 8.x 默认
    COMPRESSED 同 DYNAMIC + 页压缩 3072B 以 CPU 换空间

    关键差别在「前缀」：COMPACT 会在行内保留 768 字节的大字段内容，行变长、页装得少；DYNAMIC 全部外移，行内只剩指针，页能装更多行，扫描更快。

    4. 什么时候会溢出

    行太长（超过页容量约一半）时，InnoDB 会把最长的变长列挪到溢出页，直到行能放进页。所以 TEXT、BLOB、长 VARCHAR 会触发溢出，而 INT、DATETIME 不会。

    5. 页大小的影响

    页大小 影响
    4KB / 8KB B+Tree 层数增加，IO 次数上升；适合小行宽
    16KB（默认） 通用最优，SSD 上顺序读划算
    32KB / 64KB 读放大明显，刷脏慢，一般只在特殊场景

    innodb_page_size 只能在初始化实例时指定，之后不可改。

    6. 估算一页能装多少行

    行大小 ≈ 变长长度列表 + NULL 位图 + 5B 头 + 6B trx_id + 7B roll_ptr + 各列字节
每页行数 ≈ (16384 - 页头/页尾开销约 200B) / 行大小

    一行 100B 时约 150 行/页；三层 B+Tree（根 + 分支 + 叶）在每页 150 行、每分支 200 指针的量级下可以撑到千万行。

    五、场景说明

    1. 宽表设计：列太多导致行超页，触发溢出，扫描成本上升；宽表应拆冷热列；
    2. 大字段存储：图片、长文本放对象存储，库里只存 URL，避免行溢出与备份膨胀；
    3. 索引前缀：VARCHAR(1000) 建索引会超 3072B 上限，需前缀索引或改设计；
    4. 压缩表：日志类历史表可用 COMPRESSED，在线业务慎用；
    5. 备份与恢复：页越大，单页损坏影响的行越多，但校验和能快速发现。

    六、示例代码/实操步骤

    1. 看表的行格式

    SELECT TABLE_NAME, ROW_FORMAT, AVG_ROW_LENGTH, DATA_LENGTH, INDEX_LENGTH
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'shop';

SHOW TABLE STATUS LIKE 't_order'\G

    2. 指定行格式建表

    CREATE TABLE t_doc (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(200) NOT NULL,
  content LONGTEXT,
  created_at DATETIME NOT NULL
) ENGINE = InnoDB ROW_FORMAT = DYNAMIC;

    3. 观察页与行大小

    -- 单页读取计数，验证「一次 IO 至少一页」
SHOW GLOBAL STATUS LIKE 'Innodb_pages_read';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_pages_data';

-- 行格式与压缩情况
SELECT NAME, ROW_FORMAT, SPACE, FILE_SIZE
FROM information_schema.INNODB_TABLESPACES
WHERE NAME LIKE 'shop/%';

    4. Java 侧怎么落地：让行别太长

    1. 实体拆分：Order 与 OrderDetail、OrderExt 分表，热字段与冷字段分离，单行控制在几百字节；
    2. 大字段外置：附件、富文本存 OSS，表里只留 url + hash；
    3. VARCHAR 长度按需：VARCHAR(64) 而不是 VARCHAR(1024)，长度不影响存储但影响校验与索引上限判断；
    4. 索引列避开大字段：需要检索长文本用全文索引或搜索引擎，不要给 TEXT 建普通索引；
    5. 批量读取按行宽调批大小：宽表一次取 500 行可能就超包大小，按 max_allowed_packet 调整；
    6. 监控 AVG_ROW_LENGTH：突增说明有大字段塞进来了，及时拆分。

    七、常见坑

    1. 以为 VARCHAR(n) 会预分配空间：实际按内容长度存，n 只做上限校验；
    2. 给 TEXT 建普通索引：超长键直接失败，或只能前缀索引；
    3. 宽表塞满 TEXT：行溢出后每次扫描多一次随机 IO；
    4. 以为页大小能改：innodb_page_size 初始化后不可变；
    5. COMPRESSED 当默认：写放大与 CPU 开销在 OLTP 上很明显；
    6. 忽略 NULL 位图：大量可空列也会让行头变长，能 NOT NULL 就 NOT NULL；
    7. ROW_FORMAT=COMPACT 迁移：老表迁移到 8.4 建议一并改 DYNAMIC，否则大字段仍占行内空间。

    八、版本差异

    • 5.6：默认行格式 COMPACT，大字段行内保留 768B 前缀；innodb_large_prefix 需手动开启才能到 3072B；
    • 5.7：innodb_large_prefix 默认开启，DYNAMIC 逐步成为推荐；
    • 8.0：innodb_large_prefix 移除，索引前缀上限由行格式与页大小决定；默认 innodb_default_row_format = dynamic；
    • 8.4：默认 DYNAMIC 不变，innodb_page_size 仍只能在初始化时设定；新建表统一用 DYNAMIC，除非确需页压缩。

    九、课后小结

    • 页是 IO 与内存的最小单位，16KB 默认，七段结构里 User Records 是链表、Page Directory 是槽位；
    • 行内顺序：变长长度列表 → NULL 位图 → 5 字节头 → 列数据（含 6B trx_id、7B roll_ptr）；
    • DYNAMIC 把大字段整段外移，行内只留 20B 指针，页能装更多行；
    • 索引前缀上限：COMPACT 767B，DYNAMIC/COMPRESSED 3072B（16KB 页）；
    • 宽表、大字段、超长索引都会在这里付代价，设计阶段就要避开。

    十、思考题

    1. 为什么说「B+Tree 的节点是页，不是行」？

      参考回答：InnoDB 以页为单位读写磁盘和缓存，B+Tree 的分支节点存的是一页页的索引记录，叶子节点是一页页的数据行；一次查找的 IO 次数等于树高，也就是经过的页数。

    2. DYNAMIC 相比 COMPACT 的优势在哪？

      参考回答：COMPACT 会在行内保留最多 768 字节的大字段前缀，行变长、每页装的行变少；DYNAMIC 把大字段整段放到溢出页，行内只留 20 字节指针，页内密度更高，扫描更快。

    3. 索引前缀 767B 与 3072B 的差别由什么决定？

      参考回答：由行格式与页大小共同决定。COMPACT/REDUNDANT 上限 767 字节；DYNAMIC/COMPRESSED 在 16KB 页下可到 3072 字节。8.0 起不再需要 innodb_large_prefix 开关。

    4. 一行 100B 的表，一页大约能放多少行，三层树能撑多少数据？

      参考回答：扣除页头页尾约 200B，一页约 160 行；按分支节点每页约 200 个指针估算，两层分支 + 一层叶子约 200×200×160 ≈ 640 万行，量级在千万。

    5. 大字段为什么建议外置到对象存储？

      参考回答：大字段触发行溢出，每次扫描多一次随机 IO；还会放大 binlog、备份与网络传输。库里只存 URL 与元信息，既保持行窄，也让大文件走更适合的存储。
