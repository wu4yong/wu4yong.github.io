    redis-5-String

    📅 2022-12-26

    String 类型：文本、整数与位操作

    String 的四种语义与 SET 选项、位图内存布局｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 说清 String 是「唯一的一种类型」，文本、整数、位图都是它的不同用法，而不是三种类型；
    2. 把 SET 的过期选项、NX/XX、KEEPTTL、GET 逐个用对，知道每个选项解决什么问题；
    3. 遇到计数器、分布式锁、签到打卡这类需求，能直接写出正确的命令组合，并且知道溢出与上限的边界在哪里。

    二、前置知识

    需要先读完 RD01（能力边界与最小概念闭环），理解「命令级原子性来自单线程执行」这一点——本讲所有「原子」二字都建立在它之上。

    三、理论讲解（官方定义）

    官方对 String 的定义（原文）：

    String is the most basic type of Redis value. … Strings are the only data type in Redis that can also be used as integers, which allows for atomic increments and decrements.

    —— https://redis.io/docs/latest/develop/data-types/strings/

    这句原文有两个要点必须咬住：

    • 它是最基础、也是唯一的「标量」类型：一个 key 对应一段二进制安全的字节序列；
    • 它同时能当整数用：这是 INCR 家族存在的前提，也是 Redis 能做计数器、能当锁的根基。

    官方对长度的约束（原文）：

    String values can be up to 512 MB.

    —— https://redis.io/docs/latest/develop/data-types/strings/

    512 MB 是单 value 的上限，不是单 key 的上限（key 上限同样是 512 MB，见 RD01）。

    四、原理拆解

    1. 一个类型，四种用法

    String 的「多副面孔」来自命令语义，而不是四种不同存储：

    用法
    典型命令
    语义要点
    文本
    SET / GET / APPEND / STRLEN
    二进制安全，可存 JSON、序列化对象、图片字节
    整数
    INCR / DECR / INCRBY / INCRBYFLOAT
    读改写一步完成，命令级原子
    位图
    SETBIT / GETBIT / BITCOUNT / BITOP / BITFIELD
    把一个 value 当 bit 数组，按 offset 寻址
    存在性/共享值
    SET ... NX / SET ... XX
    用「写不写得进去」表达互斥与覆盖

    关键认知：位图不是新类型。SETBIT 只是把 String 当成 bit 数组来改，所以它照样受 512 MB 上限约束——offset 最大 2^32 - 1，因为 2^32 个 bit 正好是 512 MB。

    2. SET 的选项组合：每个选项都在解决一个真实问题

    官方语法：

    SET key value [NX | XX] [GET] [EX seconds | PX milliseconds |
  EXAT unix-time-seconds | PXAT unix-time-milliseconds | KEEPTTL]

    逐个拆开：

    • EX / PX：相对过期，单位秒 / 毫秒。缓存过期最常用。
    • EXAT / PXAT：绝对时间点过期。适合「到今晚 24 点统一失效」这种业务口径，不用自己算剩余秒数。
    • NX：key 不存在才写。这是最朴素的分布式锁：谁写进去谁持有。
    • XX：key 存在才写。适合「只更新已有缓存，不新建」。
    • KEEPTTL：写入新值但保留原有 TTL。默认行为是「写新值会清掉 TTL」，这是新手最常踩的坑之一。
    • GET：写入的同时返回旧值，等价于原子的「先取旧值再覆盖」，替代已被标记为废弃的 GETSET。

    NX 与 XX 互斥，官方语法里用 | 隔开就是这个意思，同时传会报语法错误。

    3. INCR 的原子性从哪来

    INCR key 内部做三件事：读旧值 → 加一 → 写回。这三步之所以安全，是因为单线程执行时不会有第二条命令插进来。所以：

    • 两个客户端同时 INCR counter，结果一定是 +2，不会丢更新；
    • 但跨 key 的原子性不存在，INCR 只管自己这一个 key。

    溢出边界也是官方明确规定的（原文）：

    If the value … is not a valid integer, or if the operation would overflow, an error is returned.

    —— https://redis.io/docs/latest/commands/incr/

    64 位有符号整数上限是 9223372036854775807，再加就报错，不会回绕成负数。计数器设计时必须给这个错误留处理路径。

    4. 位图的空间账

    位图的空间 = 最大 offset / 8。所以：

    • 存「用户 1–1000 的每日签到」，最大 offset 1000，约 125 字节；
    • 但如果用户 ID 是 100 万起步的雪花 ID，直接用 ID 当 offset，一个 key 立刻膨胀到几百 KB——位图要求编号连续、从 0 开始，否则先用映射表转成连续序号。

    同一份存储的四种用法、SET 选项各管什么、位图的空间与四条硬边界｜依据 Redis 7.4 Data types / SET 自绘

    五、场景说明

    官方文档给出的典型用法，直接对应到业务：

    1. 缓存对象：SET user:1:profile "{...}" EX 3600，一次往返取整个对象；
    2. 计数器：文章阅读数、接口调用次数，INCR / INCRBY；
    3. 限流：INCR req:uid:minute + EXPIRE，或者用 SET 的 EX + NX 做固定窗口；
    4. 分布式锁：SET lock:order:1001 <token> NX PX 30000，释放时用 Lua 校验 token（RD42 详讲）；
    5. 签到/活跃标记：SETBIT sign:2022-12 3 1 + BITCOUNT，一个月一个人只占 4 字节；
    6. 布隆过滤器/去重位图：BITOP 做批量位运算。

    不适合的场景：需要按字段查询的对象（用 Hash）、需要排序的集合（用 ZSet）、超过 512 MB 的大对象（该拆或该放对象存储）。

    六、示例代码/实操步骤

    # 1. 基本读写与长度
127.0.0.1:6379> SET user:1:name "阿勇"
OK
127.0.0.1:6379> STRLEN user:1:name
(integer) 6
127.0.0.1:6379> APPEND user:1:name "-dev"
(integer) 10
127.0.0.1:6379> GET user:1:name
"阿勇-dev"

# 2. 四种过期写法
127.0.0.1:6379> SET cache:k1 v EX 60          # 60 秒后过期
127.0.0.1:6379> SET cache:k2 v PX 5000        # 5 秒后过期
127.0.0.1:6379> SET cache:k3 v EXAT 1700000000
127.0.0.1:6379> SET cache:k4 v PXAT 1700000000000
127.0.0.1:6379> TTL cache:k1
(integer) 60

# 3. 重写值会清 TTL，KEEPTTL 才是保留
127.0.0.1:6379> SET cache:k1 v2
OK
127.0.0.1:6379> TTL cache:k1
(integer) -1                                 # TTL 被清掉了
127.0.0.1:6379> SET cache:k1 v3 KEEPTTL EX 60
OK
127.0.0.1:6379> TTL cache:k1
(integer) 60

# 4. NX 当锁：第二次写不进去
127.0.0.1:6379> SET lock:job:1 token1 NX PX 30000
OK
127.0.0.1:6379> SET lock:job:1 token2 NX PX 30000
(nil)                                        # 已被占用

# 5. GET 选项：原子地取旧值并覆盖
127.0.0.1:6379> SET counter 10
OK
127.0.0.1:6379> SET counter 20 GET
"10"

# 6. 计数器与溢出边界
127.0.0.1:6379> SET visits 0
OK
127.0.0.1:6379> INCR visits
(integer) 1
127.0.0.1:6379> INCRBY visits 100
(integer) 101
127.0.0.1:6379> SET big 9223372036854775807
OK
127.0.0.1:6379> INCR big
(error) ERR increment or decrement would overflow

# 7. 位图：签到与统计
127.0.0.1:6379> SETBIT sign:2022-12 3 1
(integer) 0
127.0.0.1:6379> GETBIT sign:2022-12 3
(integer) 1
127.0.0.1:6379> BITCOUNT sign:2022-12
(integer) 1
127.0.0.1:6379> BITCOUNT sign:2022-12 0 0 BYBIT   # 7.0+ 按字节区间统计
(integer) 1

# 8. 批量写读：MSET / MGET 是单命令多 key
127.0.0.1:6379> MSET a 1 b 2 c 3
OK
127.0.0.1:6379> MGET a b c nope
1) "1"
2) "2"
3) "3"
4) (nil)

    注意 MSET 是一条命令，所以它天然原子；而循环 SET 三次不是。这类差别在写「要么全写要么全不写」的逻辑时非常关键——不过 MSET 没有 NX 选项，真正的「全有或全无」要靠 MSETNX 或 Lua。

    Java 侧怎么落地：缓存、计数、位图三段代码

    String 在 Spring Boot 里几乎全靠 StringRedisTemplate，因为它的 key/value 都是 UTF-8 字符串，和命令行看到的一致。

    1. pom 与配置：引 spring-boot-starter-data-redis，yml 里配 host/port/password/db/timeout；本地连 6379 默认库即可，生产把密码从环境变量注入。

    2. 写缓存要带过期，别用「先 set 再 expire」两条命令：

    @RequiredArgsConstructor @Service
class ProfileCache {
    private final StringRedisTemplate tpl;
    void put(String uid, String json, Duration ttl) {
        tpl.opsForValue().set("user:" + uid + ":profile", json, ttl);   // 等价 SET key val PX/PXAT
    }
    String get(String uid) { return tpl.opsForValue().get("user:" + uid + ":profile"); }
}
    1. 要「写不进去就表示已被占用」，用 setIfAbsent，它对应 SET key val NX；但 setIfAbsent 的过期时间版本在 Spring Data Redis 3.x 才有，2.x 要自己拼：
    Boolean ok = tpl.opsForValue().setIfAbsent("lock:job:1", token, Duration.ofSeconds(30));

    1. 计数器与位图：opsForValue().increment 对应 INCR，溢出会抛 RedisSystemException（底层 ERR increment or decrement would overflow），业务侧要兜住；签到用 setBit(key, offset, true) / bitCount(key)，offset 必须用「连续序号」而不是雪花 ID。

    2. 批量读：multiGet 对应 MGET，返回列表里可能有 null，业务代码必须判空——这一点和 Redis 里 $-1 是同一件事。

    七、常见坑（官方明确说明的限制）

    1. 重写值默认清 TTL。SET key newvalue 会把已有过期时间抹掉，这是官方定义的行为；要保留就得显式 KEEPTTL，否则缓存会变成永久 key。
    2. INCR 的 key 不存在时按 0 处理，但 key 里存的是非数字字符串会直接报错，不会「当成 0」。所以别用同一个 key 既存 JSON 又做计数。
    3. SETBIT 的 offset 有上限：最大 2^32 - 1（对应 512 MB）。offset 填得越大，Redis 会立刻分配（并按字节补 0）到那个位置，一次误传大 offset 就能打爆内存。
    4. GETDEL / GETEX 是 6.2 新增，SET ... GET 是 6.2 起可用；老版本要么升级，要么走 Lua。GETSET 在 6.2 起被标记为废弃（deprecated），文档仍保留但不再推荐。
    5. APPEND / SETRANGE 会让 value 变长，500 MB 级的拼接操作是同步阻塞的，等于给主线程上了一把锁。
    6. MGET 取回 N 个值，其中某个是几 MB 的大 String 时，带宽与阻塞一起放大——批量读的前提是每个 value 都足够小。

    版本差异（8.x 标注）

    主线按 7.4 讲述。8.x 在 String 层面没有破坏性变更，命令语法与 512 MB 上限一致；差异集中在许可（AGPLv3/SSPL）与集群/持久化细节，后续章节涉及处单独标注。

    依据：https://redis.io/docs/latest/develop/data-types/strings/

    八、课后小结

    • String 是唯一的基础标量类型，文本、整数、位图是同一份存储的三种用法；
    • SET 的选项各自解决一个具体问题：EX/PX 相对过期、EXAT/PXAT 绝对过期、NX/XX 互斥、KEEPTTL 保 TTL、GET 原子取旧值；
    • INCR 的原子性来自命令串行执行，溢出返回 error 不回绕；
    • 位图的空间取决于最大 offset，偏移必须连续，否则浪费惊人；
    • 单 value 上限 512 MB，位图 offset 上限 2^32-1。

    九、思考题

    1. 「更新缓存但保留原过期时间」这个需求，用 SET 和 GETSET 分别怎么写？为什么 SET ... KEEPTTL 更安全？

      参考回答：SET key v2 KEEPTTL 一条命令完成；GETSET 只能返回旧值并覆盖，做不到保留 TTL（覆盖后 TTL 就没了），要保留得再 TTL 读一次、SET 回去 EX，两次往返还可能被并发改。SET ... KEEPTTL 之所以更安全，是因为语义在服务端一次原子完成，不存在「读 TTL 与写值之间被别人改」的窗口。

    2. 用 SET NX PX 做锁，客户端拿到锁后进程被 kill，锁会怎样？这暴露了「锁」的什么隐含假设？

      参考回答：锁会在 PX 到期后自动释放，期间没有别人能拿到。它暴露的假设是「持有者活到释放那一刻」：进程被杀后没人执行删除，只能等超时。所以业务要么把锁时长设得比最长处理时间短、要么做续期（哨兵心跳），并让被保护的操作本身幂等。

    3. 一个 1000 万用户的签到系统，用用户 ID 直接当 SETBIT 的 offset 会发生什么？正确的做法是什么？

      参考回答：位图会按最大 offset 补齐，一个月的位图直接膨胀到 MB 级，且大部分空间是 0；更大问题是一人一个 key 时的 key 数量与内存碎片。正确做法：用「用户 ID → 连续自增序号」的映射（或分片位图），offset 从 0 连续排；也可以按天分 key，一天一个位图。

    4. MSET 原子而三次 SET 不原子，但 MSET 没有 NX。要「全有或全无地抢占多个锁」，你打算怎么实现？

      参考回答：用 MSETNX——多个 key 同时写，只要有一个已存在就整体失败；但它不返回是谁挡住了，需要 MGET 事后确认。要带过期时间或多 key 条件判断，就用 Lua 脚本一次执行 SET NX PX 循环，任一失败即回滚（脚本内 DEL 已写入的 key），保证整体原子。
