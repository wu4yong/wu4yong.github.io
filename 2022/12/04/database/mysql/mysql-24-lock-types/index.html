    mysql-24-锁的类型

    📅 2022-12-04

    锁的类型：表锁、行锁、意向锁、记录锁与临键锁

    表级锁管「意图」，行级锁管「具体记录」，两者靠意向锁衔接｜依据 MySQL 8.4 InnoDB Locking 与 Locks Set by SQL 章节自绘

    一、学习目标

    1. 把 InnoDB 的锁按「粒度 + 模式 + 用途」列清楚，不再混用名词；
    2. 说清意向锁存在的理由，以及它和表锁、行锁的兼容关系；
    3. 会用 SHOW ENGINE INNODB STATUS 与 performance_schema.data_locks 读出一段真实锁信息。

    二、前置知识

    MVCC（MQ22）、间隙锁（MQ23）。本节会把前面散落的锁名词收拢成一张表。

    三、理论讲解（官方定义）

    InnoDB 锁分两个层级：

    • 表级：共享 S / 排他 X 表锁（LOCK TABLES ... READ/WRITE），以及意向锁（IS / IX）；
    • 行级：记录锁（record lock）、间隙锁（gap lock）、next-key lock、插入意向锁（insert intention）、AUTO-INC 锁。

    两个模式：S（共享，读）与 X（排他，写）。多个粒度共存靠意向锁实现：事务在给某行加锁前，先在表上声明「我要加 S 还是 X」。

    官方强调：行锁实际加在索引记录上；表没有索引时，InnoDB 用隐藏聚簇索引来做记录锁定。

    四、原理拆解

    S 与 S 兼容、X 与谁都冲突；意向锁之间大多兼容，只与整表锁冲突｜依据 MySQL 8.4 锁兼容矩阵自绘

    1. 兼容矩阵

    当前锁 \ 请求锁 IS IX S X
    IS 兼容 兼容 兼容 冲突
    IX 兼容 兼容 冲突 冲突
    S 兼容 冲突 兼容 冲突
    X 冲突 冲突 冲突 冲突

    读一遍就够：意向锁之间基本兼容（IS 与 IX 兼容），它们只跟「整表 S/X」冲突。

    2. 各种行锁的语义

    锁 锁住什么 冲突对象
    记录锁 REC_NOT_GAP 某一条索引记录 其他记录锁
    间隙锁 GAP 记录之间的空隙 插入意向锁
    next-key lock 记录 + 前面的间隙 记录锁与插入
    插入意向锁 目标间隙（插入前） 已有间隙锁
    AUTO-INC 锁 自增分配 并发插入（模式 0/1 时）

    间隙锁「纯粹抑制插入」且彼此不冲突（MQ23 已展开），这是理解死锁的关键。

    3. 常见 SQL 加什么锁（RR）

    SQL 加锁结果
    SELECT ... （普通） 不加锁，快照读
    SELECT ... FOR SHARE 对匹配行加 S 记录锁（非唯一索引会加 next-key）
    SELECT ... FOR UPDATE 对匹配行加 X next-key；唯一索引等值只加记录锁
    UPDATE ... WHERE 唯一索引 = ? X 记录锁
    UPDATE ... WHERE 普通索引 = ? X next-key（记录 + 间隙）
    UPDATE ... WHERE 无索引列 = ? 锁住扫描到的所有记录（近似全表）
    INSERT 插入意向锁 + 新记录上的隐式锁

    4. 隐式锁与显式锁

    INSERT 时不显式加锁，靠「隐式锁」保护：其他事务要改这条新记录时，会检查其 DB_TRX_ID 是否活跃，若是则帮它升级为显式锁。这样绝大多数插入不需要真的维护锁结构。

    5. 表级锁与 MDL

    • LOCK TABLES ... READ/WRITE 是显式表锁，会与意向锁冲突，生产基本不用；
    • 元数据锁（MDL） 是另一套：ALTER TABLE、DROP 时自动加，长查询会阻塞 DDL，DDL 又会阻塞后续查询，形成「MDL 等待」雪崩——排查时看 performance_schema.metadata_locks。

    五、场景说明

    1. 秒杀扣库存：唯一索引等值 UPDATE，只锁一行，吞吐最高；
    2. 状态机流转：WHERE id = ? AND status = ? 条件更新，避免先查后改的竞态；
    3. 批量任务：按主键区间分批，减少 next-key 范围；
    4. DDL 窗口：先确认无长事务、无长查询，再执行 ALTER，否则卡在 MDL；
    5. 锁等待告警：监控 data_lock_waits 数量与 innodb_row_lock_time。

    六、示例代码/实操步骤

    1. 看一段真实的锁信息

    -- 会话 A
START TRANSACTION;
UPDATE t_order SET status = 1 WHERE user_id = 100;   -- user_id 有普通索引

-- 另一会话
SHOW ENGINE INNODB STATUS;   -- TRANSACTIONS 段里能看到 lock_mode X

    输出里 lock_mode X locks rec but not gap 是记录锁，lock_mode X 无 rec but not gap 通常是 next-key，locks gap before rec 是间隙锁。

    2. 用 performance_schema 精确查

    SELECT ENGINE_TRANSACTION_ID, OBJECT_NAME, INDEX_NAME,
       LOCK_TYPE, LOCK_MODE, LOCK_STATUS, LOCK_DATA
FROM performance_schema.data_locks
ORDER BY ENGINE_TRANSACTION_ID;

SELECT * FROM performance_schema.data_lock_waits;

    LOCK_MODE 速查：S、X（next-key）、S,REC_NOT_GAP、X,REC_NOT_GAP、X,GAP、X,INSERT_INTENTION。

    3. 验证「无索引 = 近似全表锁」

    -- status 无索引
START TRANSACTION;
UPDATE t_order SET status = 1 WHERE status = 0;
-- 另一会话改任意一行都会被阻塞，因为扫描到的记录都被加了锁

    4. 观察 MDL 阻塞

    -- 会话 A：长查询
SELECT SLEEP(30) FROM t_order LIMIT 1;

-- 会话 B：DDL 会被 MDL 阻塞
ALTER TABLE t_order ADD COLUMN remark VARCHAR(64);

    排查：SELECT * FROM performance_schema.metadata_locks; 找到持锁的会话再决定是否 kill。

    Java 侧怎么落地：锁的正确使用顺序

    1. 统一加锁顺序：多行更新按主键升序处理，避免交叉等待；
    2. 短事务 + 小批量：单事务行数控制在几百以内，减少 next-key 覆盖范围；
    3. 条件更新替代先查后改：UPDATE ... WHERE id=? AND version=? 用行锁 + 版本号做乐观并发；
    4. 捕获锁异常：1205（等待超时）与 1213（死锁）都应整事务重试，重试次数设上限；
    5. DDL 走窗口：发布前确认无长事务，必要时用 gh-ost / pt-osc 避免 MDL；
    6. 监控指标：innodb_row_lock_waits、innodb_row_lock_time_avg、data_lock_waits 数量。

    七、常见坑

    1. 把「行锁」当「锁一行数据」：实际锁的是索引记录，无索引时会锁住大量行；
    2. 在事务里 LOCK TABLES：表锁与行锁混用，容易自己把自己锁死；
    3. 以为意向锁会阻塞其他事务：IX 与 IX 兼容，它只是「声明意图」；
    4. SELECT FOR SHARE 当普通读：共享锁也会与写冲突，能快照读就别加锁；
    5. 长查询阻塞 DDL：MDL 等待会连带阻塞后续所有查询，比行锁更致命；
    6. INSERT ... ON DUPLICATE KEY UPDATE 以为无锁：冲突路径上仍会加锁，高并发下有死锁风险；
    7. 批量更新不带 LIMIT：一次锁住大量 next-key 区间，拖垮并发。

    八、版本差异

    • 5.7：锁视图为 information_schema.INNODB_LOCKS / INNODB_LOCK_WAITS；
    • 8.0：改为 performance_schema.data_locks / data_lock_waits，并新增 metadata_locks 视图；innodb_lock_wait_timeout 默认 50 秒；
    • 8.4：锁类型与语义一致；AUTO-INC 锁行为受 innodb_autoinc_lock_mode（默认 2）控制。

    九、课后小结

    • 表级有 S/X 表锁与 IS/IX 意向锁，行级有记录、间隙、next-key、插入意向、AUTO-INC；
    • 意向锁负责「多粒度衔接」，彼此兼容，只与整表锁冲突；
    • 行锁加在索引记录上，无索引就退化为近似全表锁；
    • INSERT 依赖隐式锁，冲突时才升级为显式锁；
    • MDL 是 DDL 与长查询的隐形杀手，排查看 metadata_locks。

    十、思考题

    1. 意向锁存在的意义是什么？

      参考回答：让表级锁不必逐行检查是否有行锁。事务加行锁前先在表上放 IS/IX，另一个想加整表 S/X 的事务只需看表上的意向锁就能判断冲突。

    2. 为什么 UPDATE ... WHERE 无索引列 会锁住几乎整张表？

      参考回答：InnoDB 只能全表扫描，扫到的每条记录都会被加锁；没有索引就无法把锁范围收敛到某几行，等价于全表写锁。

    3. X 与 IX 为什么冲突？

      参考回答：X 表锁要求整表独占，而 IX 表示某事务正在往表内某些行写，两者语义互斥，所以冲突；同理 S 与 IX 也冲突。

    4. INSERT 为什么不显式加锁？

      参考回答：新插入的记录对其他事务原本不可见，冲突概率低，InnoDB 用「隐式锁」标记（记录上的 DB_TRX_ID 是活跃事务），其他事务要动它时才帮忙升级为显式锁，节省锁结构开销。

    5. DDL 被卡住时先查什么？

      参考回答：先查 performance_schema.metadata_locks 找到持 MDL 的会话（通常是长查询或未提交事务），再决定 kill 查询还是等其结束；不要盲目重试 DDL。
