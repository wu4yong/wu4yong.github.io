    mysql-48-sharding-middleware

    📅 2022-12-28

    分片中间件：ShardingSphere 的路由与归并

    解析 → 路由 → 改写 → 归并，SQL 在中间件里被拆开又拼回｜依据 ShardingSphere 路由与归并机制 / MySQL 8.4 复制说明自绘

    一、学习目标

    1. 说清中间件把一条 SQL 变成「多片执行 + 结果合并」的完整链路；
    2. 分清 Proxy 与 JDBC 两种形态的适用边界，不在选型上拍脑袋；
    3. 知道哪些 SQL 会在归并阶段爆掉，提前在设计期规避。

    二、前置知识

    分库分表与分片键（MQ47）、索引与执行计划（M3/M6）、连接池与超时（M4）。

    三、理论讲解（官方定义）

    分片中间件是位于应用与数据库之间的 SQL 路由层：对上层暴露一个逻辑库/逻辑表，对下层把 SQL 拆到多个真实库表执行。ShardingSphere 官方把核心流程定义为四个阶段：

    阶段 做的事 失败后果
    SQL 解析 词法/语法分析，得到抽象语法树 不支持的语法直接抛错
    路由 按分片键与规则算出目标数据节点 路由错 → 查错片或全片扫描
    改写 逻辑表名换成真实表名，分页/聚合改写 改写漏 → 结果重复或缺失
    执行 + 归并 逐片执行，合并结果集 归并爆内存/爆耗时

    两种产品形态：ShardingSphere-JDBC（Jar 包，应用内路由，无额外网络跳数）与 ShardingSphere-Proxy（独立进程，对应用透明，支持任意语言客户端）。

    四、原理拆解

    选哪种算法取决于分片键形态与扩容方式｜依据 ShardingSphere 分片算法 / 归并说明自绘

    1. 路由：先算数据节点，再算表

    路由分两级：库路由（ds_0..3）与表路由（t_order_0..7）。常见算法四类：取模（均匀但扩容要重分布）、范围（范围查询友好但易热点）、一致性哈希（扩容只迁部分数据）、映射表（灵活可在线扩缩但多一次查询）。选型的实质是「扩容方式」的选择。

    2. 改写：三种最常见的改写

    • 表名改写：t_order → t_order_3；
    • 分页改写：LIMIT 100,10 变成各片 LIMIT 0,110 再归并取第 100–109 条；
    • 聚合改写：AVG 拆成 SUM + COUNT，ORDER BY 补到各片 SQL 里。

    改写是「正确性」的来源：写错一条，结果不会报错，只会悄悄不对。

    3. 归并：成本都堆在这里

    归并类型 做法 何时出现
    遍历归并 各片结果顺序拼接 无排序无聚合
    排序归并 各片先排序，再流式合并 ORDER BY / GROUP BY
    聚合归并 内存二次计算 SUM/AVG/COUNT/DISTINCT

    排序归并把 N 个有序流合并成 1 个有序流，内存只需每片一个游标 —— 这是它比「全拉回内存排序」优雅的地方。但跨片 GROUP BY 的聚合归并必须把各片的中间结果全部留在内存，分组基数一高就 OOM。

    4. 分片键缺失时会发生什么

    SQL 不带分片键 → 无法定位单片 → 退化为全路由（广播到所有分片）。读会被放大 N 倍，写则可能变成「所有分片都要执行」的广播写。这类 SQL 是中间件场景下最贵的操作，必须在 DAO 层拦截。

    5. 分布式主键

    多片各自自增必然冲突。中间件通常内置雪花算法（Snowflake）生成 BIGINT 主键，或号段模式从中心表取段。主键一旦由中间件生成，业务层就不能再依赖数据库自增。

    五、场景说明

    1. 订单按 user_id 分 8 表 4 库：用户维度查询单片命中，商家维度走异步宽表；
    2. Proxy 形态给多语言团队：Go/Python 服务不用各自实现路由；
    3. JDBC 形态给纯 Java 团队：少一跳网络，延迟更可控；
    4. 历史订单归档：冷数据分片下线，热分片只留近两年；
    5. 多租户 SaaS：按 tenant_id 分片，天然隔离与独立扩容。

    六、示例代码/实操步骤

    1. 依赖与版本对齐

    <dependency>
  <groupId>org.apache.shardingsphere</groupId>
  <artifactId>shardingsphere-jdbc</artifactId>
  <version>5.5.2</version>
</dependency>

    Spring Boot 3 场景用 shardingsphere-jdbc（5.5.x 起不再区分 spring-boot-starter 命名），版本必须与 JDK 对齐：JDK 17 + Spring Boot 3 用 5.5.x，JDK 8 用 5.3.x。

    2. 数据源与分片规则

    spring:
  datasource:
    driver-class-name: org.apache.shardingsphere.driver.ShardingDriver
    url: jdbc:shardingsphere:classpath:sharding.yaml

    sharding.yaml 里写逻辑库、真实数据源与分片规则：

    databaseName: shop
dataSources:
  ds_0: { jdbcUrl: jdbc:mysql://db0:3306/shop, username: app, password: *** }
  ds_1: { jdbcUrl: jdbc:mysql://db1:3306/shop, username: app, password: *** }
rules:
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_${0..1}.t_order_${0..7}
        databaseStrategy: { standard: { shardingColumn: user_id, shardingAlgorithmName: db_mod } }
        tableStrategy:    { standard: { shardingColumn: user_id, shardingAlgorithmName: tb_mod } }
    shardingAlgorithms:
      db_mod: { type: MOD, props: { sharding-count: 2 } }
      tb_mod: { type: MOD, props: { sharding-count: 8 } }

    3. 微服务里的落地位置

    中间件是数据访问层基础设施，不是业务代码的职责：

    1. 路由配置集中在 sharding.yaml，随环境（dev/staging/prod）拆分文件；
    2. 分片键由上下文透传：网关解析 user_id → 写入 ThreadLocal → DAO 层自动拼进 WHERE；
    3. 连接池按「真实数据源 × 分片数」评估：最大连接数 ≈ 分片数 × 单库池上限，避免把每个库打满；
    4. 事务边界收紧：跨片写不用本地事务，改用本地消息表或 TCC；
    5. 上线前跑影子流量，比对「中间件结果」与「单库结果」是否一致。

    4. 验证路由是否正确

    -- 打开逻辑 SQL 日志，确认实际下发的物理 SQL
SET LOG_LEVEL = 'INFO';
-- 观察日志中的 actual SQL：
-- Logic SQL: SELECT * FROM t_order WHERE user_id = 1001
-- Actual SQL: ds_1.t_order_1 : SELECT * FROM t_order_1 WHERE user_id = 1001

    只有一条 Actual SQL，说明单片路由成功；出现多条，就是广播路由，必须改 SQL。

    5. Java 侧怎么落地：把中间件当透明层

    1. DAO 层拦截：WHERE 不含分片键的查询直接抛异常，强制走宽表或 ES；
    2. 禁用跨片 JOIN：需要关联的数据在写入时冗余成宽表；
    3. 分页只做游标式：offset 上限写死（如 1000），避免深翻页归并；
    4. 主键交给中间件：实体主键用 Snowflake 生成，业务不再依赖自增；
    5. 监控归并耗时：在中间件埋点统计「单 SQL 路由片数、归并行数」，超阈值告警。

    七、常见坑

    1. SQL 不带分片键：全路由，读放大 N 倍；
    2. 跨片 JOIN：多数中间件不支持或性能极差；
    3. 深翻页：LIMIT 100000,10 要把 100010 行拉到内存归并；
    4. 跨片 GROUP BY 高基数：聚合归并直接 OOM；
    5. 分布式事务当本地事务：超时后无法回滚已提交的分片；
    6. 连接数按单库算：分片 × 池上限把数据库打满；
    7. ORDER BY 字段不在索引：各片排序后归并，CPU 翻倍；
    8. 中间件版本与 JDK 不匹配：启动即报 NoSuchMethodError。

    八、版本差异

    • 5.x 之前（Sharding-JDBC 1.x–4.x）：配置为 spring.shardingsphere 前缀，规则用 Yaml 老格式；
    • 5.0+：统一为 shardingsphere-jdbc 单一依赖，规则 API 重构，!SHARDING 标签化；
    • 5.3/5.4：支持 ShardingSphere-JDBC 与 Proxy 共享同一份规则配置；
    • 5.5：适配 Spring Boot 3 / JDK 17，废弃部分 spring.shardingsphere 老前缀；
    • MySQL 侧：8.4 的 INSTANT DDL 让分片表变更更快；caching_sha2_password 为默认认证插件，中间件数据源需确认驱动版本支持。

    九、课后小结

    • 中间件四步：解析 → 路由 → 改写 → 归并，改写决定正确性，归并决定性能；
    • Proxy 透明但多一跳，JDBC 少一跳但要自己管依赖；
    • 分片键缺失 = 全路由，是中间件场景最贵的 SQL；
    • 跨片 JOIN、深翻页、高基数聚合，是归并阶段的三颗雷；
    • 中间件是基础设施：路由集中配置、分片键上下文透传、DAO 层拦截兜底。

    十、思考题

    1. 为什么中间件的归并阶段最容易被拖垮？

      参考回答：路由与改写只做计算，成本是常数；归并要把 N 个分片的结果合并成一份，成本随分片数与结果集大小线性甚至超线性增长。排序归并要维持 N 个游标，聚合归并要把中间结果全部驻留内存，深翻页要把前 N 页数据全部拉回。所以「让 SQL 不跨片」比「让归并更快」更有效。

    2. LIMIT 0,10 在单片和跨片下的代价差异在哪？

      参考回答：单片只需读 10 行；跨片要每个分片都取前 10 条（实际还要取到 offset+size），再归并排序取全局前 10。分片数 × 每片读取量就是网络与内存开销。offset 越大，每片要多读的行数越多，代价近似 分片数 × (offset + size)。

    3. 什么情况下应该选 Proxy 而不是 JDBC？

      参考回答：技术栈不统一（有 Go/Python/Node 服务）、希望应用零改造、需要集中做权限与审计、运维希望统一升级规则时选 Proxy。纯 Java、对延迟敏感、希望少一跳网络与一个进程时选 JDBC。两者也可混用：核心 Java 服务走 JDBC，其他语言走 Proxy，共享同一套规则配置。

    4. 分片键没带上的查询，中间件会怎么处理？如何避免？

      参考回答：无法定位数据节点，退化为全路由，广播到所有分片执行后再归并，读放大 N 倍。避免办法：DAO 层校验 WHERE 必须含分片键；对确实按非分片键查询的场景，建异步宽表或 ES 二级索引；把这类查询收敛到少量接口并单独限流。

    5. 中间件生成的主键为什么不能再用数据库自增？

      参考回答：每个真实分片是独立表，自增序列各自独立，多个分片会生成相同值，导致全局唯一键冲突。中间件统一用雪花算法或号段模式在路由前生成主键，业务层把主键当作外部传入的值使用，不再依赖 AUTO_INCREMENT。
