    mysql-38-index-optimize

    📅 2022-12-18

    索引优化实战：回表、覆盖与索引合并

    二级索引只存索引列 + 主键，要其它列就得再回聚簇索引查一次｜依据 MySQL 8.4 Covering Index / ICP 说明自绘

    一、学习目标

    1. 算清一次查询的「回表次数」，并知道怎么把它降到零；
    2. 会用覆盖索引、ICP、MRR、Skip Scan 四件工具，知道各自的适用边界；
    3. 能识别 index_merge 是兜底而不是设计目标，学会用联合索引替换它。

    二、前置知识

    B+Tree 与回表（MQ18）、联合索引与 ICP（MQ19）、EXPLAIN（MQ35）、优化器与统计（MQ37）。

    三、理论讲解（官方定义）

    InnoDB 的索引分为两类：

    类型 叶子节点内容 一次查询的代价
    聚簇索引（主键） 完整行数据 一次 B+Tree 查找即可拿到整行
    二级索引 索引列 + 主键值 拿到主键后还要回聚簇索引查整行（回表）

    因此「走二级索引」不等于「更快」：如果命中的行很多、又要取索引外的列，回表次数会放大成本，优化器可能宁可全表扫。

    四、原理拆解

    index_merge 是优化器的兜底，不是设计目标｜依据 MySQL 8.4 Index Merge / ICP / Skip Scan 说明自绘

    1. 覆盖索引：把回表消掉

    查询需要的列全部在索引里，就不需要回表。EXPLAIN 的 Extra 出现 Using index 才是真覆盖；出现 Using index condition 只是 ICP，仍然回表。

    -- 需要 id, status, created_at
ALTER TABLE t_order ADD INDEX idx_user_status_time (user_id, status, created_at);
-- 只查这三列 → 覆盖
SELECT user_id, status, created_at FROM t_order WHERE user_id = 100 AND status = 1;

    代价是索引变宽、写入变慢、占用更多内存，只给高频查询做覆盖，别给每张表都堆宽索引。

    2. ICP：把过滤下推到索引层

    Using index condition 表示 WHERE 中有一部分条件能在二级索引上直接判断，先过滤再回表，减少回表次数。条件是「条件涉及的列都在索引里」且存储引擎支持。

    3. MRR：把随机回表变顺序

    Disk-Sweep MRR 把命中的主键排序后再批量回表，把随机 IO 变成近似顺序 IO。SSD 上收益明显变小，机械盘时代它是救命工具。

    4. Skip Scan：跳过前缀用后列

    8.0.13 起，若联合索引前缀列去重值很少（例如 status 只有 3 个值），优化器可以「跳过前缀」直接用后列。Extra 显示 Using index for skip scan。这是优化器的兜底能力，不能当作「不用管最左前缀」的理由。

    5. index_merge 的两种形态

    • intersection：a = 1 AND b = 2，两索引各扫一遍取交集；
    • union：a = 1 OR b = 2，两索引结果并集，常伴随去重与临时表。

    它出现说明「每个条件各有一个单列索引」，正确做法是建联合索引 (a, b)，让一次索引扫描完成。

    6. 优化顺序

    消 filesort → 消临时表 → 减少回表 → 收敛扫描行数。四步按收益从大到小排，别一上来就加索引。

    五、场景说明

    1. 列表页查询：WHERE user_id = ? ORDER BY created_at DESC LIMIT 20，索引 (user_id, created_at) 一次搞定排序与范围；
    2. 详情页：ORDER BY id LIMIT 1 走主键，天然覆盖；
    3. 统计报表：COUNT(*) / SUM(amount) 尽量走覆盖索引，避免回表；
    4. OR 查询：两侧字段各有索引 → 改 UNION ALL 两段；
    5. 大表范围扫描：BETWEEN 走 range，注意 filtered 与回表量。

    六、示例代码/实操步骤

    1. 量化回表：看 rows 与 filtered

    EXPLAIN SELECT id, amount, created_at
FROM t_order
WHERE user_id = 100 AND status = 1
ORDER BY created_at DESC
LIMIT 20;

    rows 是估算扫描行数，filtered 是过滤后剩余比例；两者相乘才是回表次数量级。

    2. 用覆盖索引消掉回表

    -- 原来要回表取 amount
SELECT id, amount FROM t_order WHERE user_id = 100;

-- 建覆盖索引（把 amount 放进索引）
ALTER TABLE t_order ADD INDEX idx_user_amount (user_id, amount);
EXPLAIN SELECT id, amount FROM t_order WHERE user_id = 100;  -- Extra: Using index

    注意：id 是主键，本来就在二级索引里，不用额外加列。

    3. 用 ICP 减少回表

    ALTER TABLE t_order ADD INDEX idx_status_time (status, created_at);
EXPLAIN SELECT * FROM t_order
WHERE status = 1 AND created_at > '2022-12-01';   -- Extra: Using index condition

    4. 用联合索引替掉 index_merge

    -- 前：两个单列索引，出现 index_merge
EXPLAIN SELECT * FROM t_order WHERE user_id = 100 AND status = 1;

-- 后：联合索引，一次 range/ref
ALTER TABLE t_order ADD INDEX idx_user_status (user_id, status);
ANALYZE TABLE t_order;

    5. Java 侧怎么落地：索引与代码一起改

    1. Mapper 只查必要列：把 SELECT * 改成显式列，覆盖索引才有机会生效；
    2. 分页参数校验：LIMIT offset 上限写死在 service 层，避免深翻页（MQ39）；
    3. 批量查询拆批：IN 列表按 100 一批，防止 index dive 失效；
    4. 索引变更走 Flyway/Liquibase：ALTER TABLE ... ADD INDEX, ALGORITHM=INPLACE, LOCK=NONE 写进迁移脚本，避免锁表；
    5. 回归用例：每个核心查询配一条 EXPLAIN 断言（Testcontainers），断言 key 命中预期索引。

    七、常见坑

    1. 以为走了索引就快：回表多时不如全表扫；
    2. SELECT * 破坏覆盖索引：哪怕只多取一列，也要回表；
    3. 把 Using index condition 当成覆盖：它仍然回表；
    4. 堆一排单列索引：index_merge 出现就是信号，应改联合索引；
    5. 盲目依赖 Skip Scan：条件苛刻（前缀列去重值少），写 SQL 仍要守最左前缀；
    6. 索引过宽：写入放大、buffer pool 命中率下降；
    7. ORDER BY 列不在索引尾部：排序借不到索引顺序，filesort 依旧。

    八、版本差异

    • 5.6：ICP 引入（5.6 起），MRR 可用；
    • 5.7：虚拟列索引、ALTER 在线 DDL 更完善；
    • 8.0：Skip Scan（8.0.13）、降序索引、函数索引（8.0.13）、hash join（8.0.18）、ALGORITHM=INSTANT 支持更多场景；
    • 8.4：ADD/DROP COLUMN 默认 INSTANT，索引相关能力与 8.0 一致；直方图与统计让优化器选索引更准。

    九、课后小结

    • 二级索引查一次 = 索引查找 + 可能的回表，回表是固定成本；
    • 覆盖索引（Using index）是消回表的唯一手段，代价是索引变宽；
    • ICP 减少回表次数但不消除回表，key_len 与 Extra 一起看；
    • index_merge 是兜底，出现就说明该建联合索引；
    • 优化顺序：filesort → 临时表 → 回表 → 扫描行数。

    十、思考题

    1. Extra 里 Using index 与 Using index condition 有什么本质差别？

      参考回答：Using index 是覆盖索引，查询所需列全在索引里，不需要回表；Using index condition 是 ICP，条件下推到索引层先过滤，减少了回表次数但仍要回表取剩余列。

    2. 已经走了二级索引，为什么还是慢？

      参考回答：命中的行太多，回表次数放大，随机 IO 成为瓶颈；或者排序、去重产生了临时表。看 rows × filtered 与 Extra 是否有 filesort/temporary，再考虑覆盖索引或改写。

    3. 什么时候该建覆盖索引，什么时候不该？

      参考回答：该建：某条查询频率高、列少、回表量大，且该表写入不重。不该建：查询列很多（索引会极宽）、写入频繁（放大写代价）、低频查询（维护成本大于收益）。

    4. index_merge 出现了，一定是坏事吗？

      参考回答：不一定坏，但通常不优。它意味着优化器用两个索引各扫一遍再合并，多了额外开销；如果这条 SQL 高频，应改写成联合索引让一次扫描完成。低频查询可以先不动。

    5. Skip Scan 能替代最左前缀原则吗？

      参考回答：不能。Skip Scan 只在「前缀列去重值很少」时才有效，且需要优化器判断划算；它的存在是为了兜底，不是让你不设计好联合索引。设计索引时仍按最左前缀与查询模式来。
