    mysql-27-分布式事务

    📅 2022-12-07

    分布式事务：XA 与本地消息表

    XA 用两阶段换强一致，消息表用补偿换可用性｜依据 MySQL 8.4 XA Transactions 与 Outbox 模式自绘

    一、学习目标

    1. 说清 XA 的两阶段流程，以及「悬挂事务」是怎么产生的；
    2. 掌握本地消息表（Outbox）的五步闭环，能自己建表并写出投递任务；
    3. 能按业务强度选型：哪些场景必须强一致，哪些用最终一致就够。

    二、前置知识

    事务与 ACID（MQ21）、锁与事务边界（MQ24、MQ26）。分布式事务不是数据库单点问题，是「跨服务写一致性」问题。

    三、理论讲解（官方定义）

    MySQL 的 XA 实现遵循 X/Open 分布式事务模型，用两阶段提交（2PC）保证多个资源管理器（这里指多个 MySQL 实例，或 MySQL 与其它支持 XA 的资源）要么都提交、要么都回滚。

    语法核心：

    XA START 'xid';
-- 业务 SQL
XA END 'xid';
XA PREPARE 'xid';    -- 第一阶段：所有参与者准备好但不提交
XA COMMIT 'xid';     -- 第二阶段：统一提交
XA ROLLBACK 'xid';   -- 第二阶段：统一回滚
XA RECOVER;          -- 查看处于 PREPARE 状态的事务

    关键语义：XA PREPARE 之后，行锁仍然被持有，直到 COMMIT 或 ROLLBACK。这也是 XA 吞吐上不去的根本原因。

    四、原理拆解

    同一本地事务写业务行与消息行，再靠投递 + 幂等把不一致收敛｜依据 MySQL 8.4 XA 与事务消息实践自绘

    1. XA 的两阶段与三个角色

    角色 职责
    协调者（应用或 TM） 发起 PREPARE，收集结果，决定 COMMIT/ROLLBACK
    参与者（各 MySQL 实例） 执行本地事务，进入 prepare 后等待裁决
    恢复日志 参与者把 prepare 状态持久化，崩溃后可 XA RECOVER

    2. 悬挂事务

    协调者在发完 PREPARE、还没发 COMMIT 时崩溃，参与者就停在 prepare 状态：锁不放、日志不落、业务无法推进。XA RECOVER 能看到它，但只能人工或由补偿任务裁决，这就是「悬挂」。

    3. XA 的性能代价

    • prepare 到 commit 之间持锁，等于把两段网络往返塞进临界区；
    • 每个参与者都要写 prepare 日志并刷盘，提交阶段再刷一次；
    • 协调者单点，挂了就悬挂；
    • 因此 XA 适合低频、强一致的场景（资金、账务），不适合高频交易主链路。

    4. 本地消息表（Outbox）

    思路：不发远程消息，先在本地库里写一行「待发送」记录。业务行与消息行在同一个本地事务里落库，天然原子；再由后台任务把消息投出去，下游幂等消费。

    表设计：

    CREATE TABLE msg_outbox (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  biz_id VARCHAR(64) NOT NULL,        -- 业务唯一键，用于幂等
  topic VARCHAR(64) NOT NULL,
  payload JSON NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,  -- 0 待发 1 已发 2 失败
  retry INT NOT NULL DEFAULT 0,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  KEY idx_status_id (status, id)
) ENGINE = InnoDB;

    投递任务用 FOR UPDATE SKIP LOCKED 抢占，多个 worker 互不阻塞：

    START TRANSACTION;
SELECT id, topic, payload FROM msg_outbox
WHERE status = 0 ORDER BY id LIMIT 100
FOR UPDATE SKIP LOCKED;
-- 逐条投递，成功后
UPDATE msg_outbox SET status = 1 WHERE id IN (...);
COMMIT;

    5. 三种方案的取舍

    维度 XA 本地消息表 TCC
    一致性 强一致 最终一致 最终一致
    锁范围 跨库行锁 无跨库锁 业务资源预留
    失败处理 XA RECOVER 人工裁决 重投 + 对账 cancel 补偿
    复杂度 中，运维重 低 高
    适用 资金、账务 通知、积分、日志 订单、库存

    五、场景说明

    1. 跨行转账：两个账户在不同实例，金额敏感，用 XA 或 TCC；
    2. 下单后发通知：订单库落库 + 消息表，异步通知，用 Outbox；
    3. 积分发放：支付成功后加积分，失败可补偿，Outbox + 对账；
    4. 跨服务库存扣减：TCC 的 Try/Confirm/Cancel 更合适，XA 会拖长锁；
    5. 遗留系统对接：对方不支持 XA，只能走消息表 + 对账兜底。

    六、示例代码/实操步骤

    1. XA 实操（两实例）

    -- 实例 A
XA START 'tx-1001';
UPDATE account SET bal = bal - 100 WHERE id = 1;
XA END 'tx-1001';
XA PREPARE 'tx-1001';

-- 实例 B
XA START 'tx-1001';
UPDATE account SET bal = bal + 100 WHERE id = 2;
XA END 'tx-1001';
XA PREPARE 'tx-1001';

-- 两边都 prepare 成功后
XA COMMIT 'tx-1001';   -- A、B 各执行一次

    任一 PREPARE 失败则两边都 XA ROLLBACK。中途崩溃用 XA RECOVER 查悬挂。

    2. Outbox 同事务写入

    START TRANSACTION;
INSERT INTO t_order (order_no, amount, status) VALUES ('NO20261207001', 99.00, 'PAID');
INSERT INTO msg_outbox (biz_id, topic, payload)
VALUES ('NO20261207001', 'order.paid', JSON_OBJECT('orderNo', 'NO20261207001'));
COMMIT;

    两行要么都成功、要么都失败，不存在「订单成功但消息丢」。

    3. Java 侧怎么落地：XA 与 Outbox 两条线

    XA 线（多数据源强一致）

    1. pom.xml 引入 spring-boot-starter-jdbc 与 mysql-connector-j，两个数据源分别配 DataSource；
    2. 使用 AtomikosDataSourceBean 或 Bitronix 包装两个 DataSource，交给 JtaTransactionManager；
    3. 事务管理器切换为 JTA：@Transactional 走 JtaTransactionManager，提交由协调者驱动两阶段；
    4. 连接串加 pinGlobalTxToPhysicalConnection=true（Atomikos）避免连接错乱；
    5. 一定要配 recovery 日志目录，否则协调者重启后无法恢复悬挂事务。

    Outbox 线（推荐主链路）

    1. pom.xml 引入 spring-boot-starter-jdbc、spring-boot-starter-quartz（或 XXL-Job），无需分布式事务组件；
    2. 业务方法内一个本地 @Transactional：写业务表 + 写 msg_outbox；
    3. 定时任务每 500ms 扫一批，FOR UPDATE SKIP LOCKED 抢占，投递 MQ（RocketMQ / Kafka）；
    4. 消费端以 biz_id 做幂等键，Redis SETNX 或唯一索引兜底；
    5. 失败重试指数退避，超过 N 次进「死信」表并告警，配日终对账补偿；
    6. 监控指标：outbox_lag（最老待发记录的时间差）、失败率、重试次数分布。

    微服务下的事务边界

    • 一个业务用例只允许一个服务写自己的库，其它服务通过消息驱动；
    • 跨服务查询用接口，跨服务写用消息，禁止「服务 A 直接连服务 B 的库」；
    • 若必须跨库强一致，优先缩小范围（同实例多库仍可用本地事务），再考虑 XA。

    七、常见坑

    1. XA PREPARE 后忘记裁决：悬挂事务长期持锁，拖死整张表；
    2. 把 XA 用在秒杀主链路：锁持有时间翻倍，吞吐直接塌；
    3. Outbox 投递不加锁：多 worker 重复投递，下游必须幂等才不出事；
    4. status 更新与投递不在同一事务：投递成功但状态没落，下一轮重复发；
    5. 消息体塞大 JSON：拖慢扫描与网络，只放关键字段 + 业务键；
    6. 没有对账：最终一致系统的最后一道防线是对账，不是重试；
    7. 幂等键用自增 id：重投时 id 会变，等于没有幂等。

    八、版本差异

    • 5.7：XA 支持但 innodb_support_xa 参数仍在，配置项较多；
    • 8.0：innodb_support_xa 已移除，XA 默认可用；新增 SKIP LOCKED，让消息表抢占成为标准做法；
    • 8.4：XA 语法与两阶段语义不变，仍是「prepare 后持锁」；binlog 默认 ROW，XA 事务的复制行为更可预期；社区更推荐 Outbox/TCC 替代高频 XA。

    九、课后小结

    • XA = 两阶段提交，强一致但持锁久、怕悬挂，适合低频资金场景；
    • 悬挂事务只能靠 XA RECOVER + 人工/补偿裁决；
    • Outbox = 本地事务写「业务行 + 消息行」，异步投递 + 幂等消费 + 对账兜底；
    • 高频主链路优先最终一致，别把强一致当默认；
    • 幂等键要业务唯一，不能用自增 id。

    十、思考题

    1. XA 的 PREPARE 阶段为什么要持锁？

      参考回答：参与者必须保证在最终裁决前数据不被别人改掉，否则提交时会与自己看到的状态不一致；持锁是隔离性的代价，也是 XA 吞吐低的根源。

    2. 什么是悬挂事务，怎么发现？

      参考回答：协调者在 PREPARE 后、COMMIT 前崩溃，参与者停在 prepare 状态，既未提交也未回滚。用 XA RECOVER 能列出这些 xid，再按业务日志决定提交或回滚。

    3. 本地消息表为什么能保证「订单成功消息不丢」？

      参考回答：业务行与消息行在同一个本地事务里写入，事务原子性保证两者同时可见；消息即使暂时没投出去也留在表里，投递任务会重试直到成功。

    4. Outbox 投递任务为什么用 SKIP LOCKED？

      参考回答：多个 worker 并发扫同一张表时，SKIP LOCKED 让它们跳过已被别人锁住的行，各取各的，不会互相等待，也不需要额外的分布式锁。

    5. 最终一致的系统里，对账为什么不可省？

      参考回答：重试只能处理「已知失败」，消息丢失、逻辑 bug、人工改库都可能造成静默不一致；对账是周期性全量比对，是最后一道兜底。
