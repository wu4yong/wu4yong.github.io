    mysql-51-monitor

    📅 2022-12-31

    监控指标与告警

    先看能不能连上，再看快不快，最后看数据对不对｜依据 MySQL 8.4 Performance Schema / 监控实践自绘

    一、学习目标

    1. 用四层（可用性、性能、资源、正确性）搭出覆盖到位的指标盘；
    2. 知道每个指标异常时该往哪里查，避免「有告警没结论」；
    3. 把告警分级定下来，让值班的人知道哪条要打电话。

    二、前置知识

    InnoDB 内存结构（MQ19）、慢日志与执行计划（MQ35/MQ36）、主从复制（MQ43）。

    三、理论讲解（官方定义）

    MySQL 的可观测数据来自四个入口：

    入口 提供什么 采集方式
    SHOW GLOBAL STATUS / performance_schema.global_status 计数器（连接、QPS、行操作、锁等待） 定期 SELECT，看增量而非绝对值
    performance_schema 语句、等待、锁、阶段、内存 表查询，开销可控
    慢查询日志 超阈值 SQL + 执行细节 long_query_time + log_slow_extra
    错误日志 / 复制状态 崩溃、复制错误、GTID 日志采集 + SHOW REPLICA STATUS

    官方建议监控以计数器增量 + 比率为主，绝对累计值只在重启后归零、不能直接当趋势。

    四、原理拆解

    指标不在多，在于「异常时能定位到层」｜依据 MySQL 8.4 Server Status Variables 说明自绘

    1. 可用性：先确认「活着」

    • Threads_connected 接近 max_connections（默认 151）→ 连接耗尽；
    • Aborted_connects 突增 → 认证失败、网络抖动或连接池配置错；
    • 复制状态：Replica_IO_Running / Replica_SQL_Running 任一为 No 即中断；
    • 探活用一个最小权限账号执行 SELECT 1，不要用 root。

    2. 性能：分清「慢在等」还是「慢在算」

    指标 异常含义 下一步
    Threads_running 远高于 CPU 核数 大量并发在跑或等锁 innodb_trx、metadata_locks
    Innodb_row_lock_waits / _time 增长 锁冲突 找出持锁事务与热点行
    Slow_queries 增速异常 新上线 SQL 或统计信息失真 按指纹聚合慢日志
    Questions 突增但 Com_select 比例下降 短连接/探活风暴 查连接池与探活

    Threads_running 是判断「是不是真堵」最快的指标：它统计正在执行（不含空闲）的线程数，持续高于核数说明要么 CPU 饱和、要么大量线程在等锁/等 IO。

    3. 资源：buffer pool、磁盘与临时表

    • 命中率 = 1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests，低于 95% 说明池小或有大范围扫描；
    • 临时表落盘 Created_tmp_disk_tables / Created_tmp_tables 高于 30% 通常意味着 GROUP BY/DISTINCT 缺索引或 tmp_table_size 偏小；
    • 磁盘：数据目录增长速率、binlog 目录增长速率、redo 目录（#innodb_redo）大小。

    4. 正确性：复制与备份

    • Seconds_Behind_Source（8.0.22+ 命名，旧名 Seconds_Behind_Master）只是粗指标，更准的是 SHOW REPLICA STATUS 里的 Relay_Log_File/Exec_Source_Log_Pos 与主库位点差；
    • Retrieved_Gtid_Set 与 Executed_Gtid_Set 的差值才是真实积压；
    • 备份任务的成功率与最近一次恢复演练结果，也要进监控盘。

    5. 告警分级

    级别 判据 通知方式
    P0 不可用（连不上、主库宕、复制全断） 电话 + 值班
    P1 性能劣化（P99 超阈值、慢 SQL 激增、延迟 > 60s） 群消息 @ 值班
    P2 容量趋势（磁盘 > 70%、连接数 > 60%） 日报

    分级不清的后果很直接：所有告警都发群消息，两周后没人看。

    五、场景说明

    1. 大促前：盯 Threads_running、连接数、从库延迟；
    2. 新上线：盯慢 SQL 指纹里是否出现新 SQL；
    3. 批处理时段：盯临时表落盘与磁盘 IO；
    4. 故障复盘：用 performance_schema 历史表还原当时的等待分布；
    5. 容量规划：按周采集数据/bilog 增长速率，提前扩盘。

    六、示例代码/实操步骤

    1. 采集核心计数器

    SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.global_status
WHERE VARIABLE_NAME IN (
  'Threads_connected','Threads_running','Max_used_connections',
  'Questions','Com_select','Com_insert','Com_update','Com_delete',
  'Innodb_row_lock_waits','Innodb_row_lock_time_avg',
  'Innodb_buffer_pool_reads','Innodb_buffer_pool_read_requests',
  'Created_tmp_tables','Created_tmp_disk_tables',
  'Slow_queries','Aborted_connects'
);

    采集间隔 10s，落时序库后算增量与比率，不要直接展示累计值。

    2. 计算 buffer pool 命中率

    SELECT
  1 - (SELECT VARIABLE_VALUE FROM performance_schema.global_status
       WHERE VARIABLE_NAME='Innodb_buffer_pool_reads') /
      (SELECT VARIABLE_VALUE FROM performance_schema.global_status
       WHERE VARIABLE_NAME='Innodb_buffer_pool_read_requests') AS hit_rate;

    低于 0.95 且伴随 Innodb_buffer_pool_reads 增量放大，优先查全表扫描。

    3. 慢 SQL 按指纹聚合

    SELECT DIGEST_TEXT, COUNT_STAR,
       ROUND(SUM_TIMER_WAIT/1000000000000, 3) AS total_sec,
       ROUND(AVG_TIMER_WAIT/1000000000, 2) AS avg_ms,
       SUM_ROWS_EXAMINED, SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 20;

    SUM_ROWS_EXAMINED / SUM_ROWS_SENT 比值过大，说明扫了很多行只返回很少 —— 索引或写法问题。

    4. 复制延迟的真实算法

    SHOW REPLICA STATUS\G
-- 关注：Replica_IO_Running / Replica_SQL_Running
--       Retrieved_Gtid_Set 与 Executed_Gtid_Set 的差
--       Seconds_Behind_Source（粗指标）

    精确积压用 GTID 集合差：SELECT GTID_SUBTRACT(retrieved, executed)，差集大小才是待重放事务量。

    5. Java 侧怎么落地：指标进统一监控平台

    1. 采集用只读账号：GRANT SELECT ON performance_schema.*，并限定来源网段；
    2. 不要在应用里高频查询：指标采集交给专用 exporter，应用侧只暴露业务指标；
    3. 告警带上下文：告警消息里附当时 QPS、连接数、Top3 慢 SQL、主从延迟；
    4. 阈值分环境：预发阈值放宽，生产按 SLA 定；
    5. 看板分角色：值班看四层总览，DBA 看实例细节，研发看自己服务的慢 SQL。

    七、常见坑

    1. 只看累计值不看增量：实例重启后计数器归零，曲线突变误判；
    2. 用 Seconds_Behind_Source 当唯一延迟指标：它在大事务/长 SQL 下不准；
    3. 探活用 root + SELECT *：既耗资源又放大权限；
    4. 告警阈值全局一套：小实例与大实例同样的绝对阈值，天天误报；
    5. 只监控主库：从库磁盘满、IO 打满无人知；
    6. 忽略 binlog 目录增长：磁盘被 binlog 写满导致主库宕；
    7. performance_schema 全开：开销上升，按需开 consumer；
    8. 没有历史基线：无法判断「现在的慢」是不是异常。

    八、版本差异

    • 5.6：performance_schema 覆盖有限，多数靠 SHOW STATUS 与 SHOW PROFILE；
    • 5.7：sys schema 提供开箱视图（sys.schema_table_statistics 等），SHOW PROFILE 仍可用；
    • 8.0：SHOW PROFILE 弃用，阶段耗时统一走 performance_schema；8.0.22 起复制相关变量改名（Seconds_Behind_Source）；
    • 8.4 LTS：SHOW REPLICA STATUS 为标准写法；log_slow_extra（8.0.14+）提供更多执行细节；mysql_native_password 默认关闭，监控账号统一 caching_sha2_password。

    九、课后小结

    • 四层指标：可用性 → 性能 → 资源 → 正确性，缺一层就有盲区；
    • 计数器看增量与比率，不看累计绝对值；
    • Threads_running 判断「是否真堵」，events_statements_summary_by_digest 定位「谁在堵」；
    • 复制延迟用 GTID 差集算，Seconds_Behind_Source 只作参考；
    • 告警必须分级，否则等于没有告警。

    十、思考题

    1. 为什么 Threads_running 比 Threads_connected 更能反映真实压力？

      参考回答：Threads_connected 包含空闲连接（连接池常驻但不干活的那些），数值高只说明连接多。Threads_running 只统计正在执行命令的线程，持续高于 CPU 核数说明要么计算饱和、要么大量线程在等锁/等 IO，是真正的压力信号。

    2. Seconds_Behind_Source 在什么情况下会「骗人」？

      参考回答：它计算的是从库 SQL 线程处理的事件时间戳与主库当前时间的差。当主库长时间没有写入时，从库即使位点落后也显示 0；当有一个超大事务在重放时，它可能长时间停在某个值不动；时钟不同步也会导致偏差。准确判断要用 Retrieved_Gtid_Set 与 Executed_Gtid_Set 的差集。

    3. buffer pool 命中率 90% 一定要扩池吗？

      参考回答：不一定。先看 Innodb_buffer_pool_reads 的增量是否集中在某几个 SQL（说明是全表扫描而非池小）；再看池是否已接近物理内存上限。如果是少数大范围扫描导致，优化 SQL 比扩池有效。命中率长期低于 95% 且扫描分散，才考虑扩池或拆分实例。

    4. 慢 SQL 为什么要按指纹（digest）聚合，而不是逐条看？

      参考回答：同一条 SQL 模板可能每秒执行上千次，逐条看会被淹没。events_statements_summary_by_digest 把参数不同的同类语句归一成一条指纹，给出总耗时、平均耗时、扫描行数，能直接排出「最贵的 20 条」。逐条看只适合定位单次异常。

    5. 告警分级做不好的典型后果是什么？

      参考回答：所有告警都走同一个通道，值班人员在噪声中逐渐忽略消息，真正 P0 时没人响应（告警疲劳）。分级之后 P0 才能触发电话与升级路径，P1/P2 走异步通道，同时要求每条告警附带足够上下文，减少「收到告警后还要自己查一圈」的时间。
