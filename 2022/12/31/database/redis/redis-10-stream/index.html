    redis-Stream

    📅 2022-12-31

    Stream 类型：追加日志与消费组入门

    单消费者游标读取、消费组投递与 PEL，以及四条官方约束｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 讲清 Stream 是「带自增 ID 的追加日志」，以及它与 List、Pub/Sub 的本质差别；
    2. 会写 XADD / XREAD / XGROUP CREATE / XREADGROUP / XACK 这条最小链路；
    3. 理解 PEL（pending entries list）的意义，知道「消息不会自动删除」与「消费者崩溃要 XAUTOCLAIM」这两条现实约束。

    二、前置知识

    RD06（List 的阻塞语义）与 RD09（ZSet）。本篇会频繁对比 List 队列与 Stream，先搞清 List 的「取走即消失」语义，才能理解 Stream 的差异。

    三、理论讲解（官方定义）

    官方定义（原文）：

    A Redis stream is a data structure that acts like an append-only log. … Streams are useful for recording events and for messaging.

    —— https://redis.io/docs/latest/develop/data-types/streams/

    两条硬信息：

    • append-only log：只能往后追加，历史条目不会被就地改写；
    • 每条条目有一个 ID，形如 毫秒时间戳-序号（例如 1600000000000-0），ID 单调递增。

    自动生成 ID 的规则（原文要点）：XADD key * 让服务端分配 ID；同一毫秒内连续写入时，序号递增（-0、-1…）。这也意味着 ID 里带了时间信息，可以直接当「事件发生时间」近似使用。

    四、原理拆解

    1. 三种「消息」结构的本质差别

    结构
    消费语义
    消息会丢吗
    能重放吗
    Pub/Sub
    广播，在线订阅者才收到
    掉线即丢
    不能
    List
    取走即从列表移除
    消费者崩溃就丢
    不能
    Stream
    条目留在日志里，用 ID 记录「读到哪」
    不删就不会丢
    能（按 ID 重读）

    这张表是选型的核心：要「消息可以重复读、可以补」，只有 Stream 能满足。这也是官方把 Stream 定位成「更可靠的消息方案」的原因。

    2. 单消费者：游标式读取

    XADD stream * field value          # 追加一条，ID 自动生成
XREAD COUNT 10 STREAMS stream 0    # 从头读
XREAD COUNT 10 STREAMS stream $    # 只读「从现在起」的新条目
XREAD BLOCK 0 STREAMS stream $     # 阻塞等待新条目

    要点：

    • 0 表示「从头读」，$ 表示「只要新消息」。两者是语义完全不同的特殊 ID。
    • BLOCK 的单位是毫秒，0 表示永久阻塞（注意：Stream 的阻塞单位是毫秒，与 BLPOP 的秒不同）。
    • 普通 XREAD 不记录任何消费进度，客户端要自己保存「上次读到的 ID」，下次用 XREAD STREAMS stream <上次ID> 续读。

    这就是「游标式」的含义：进度在客户端，不在服务端。单消费者够用，多消费者就会重复消费。

    3. 消费组：把进度交给服务端

    XGROUP CREATE stream g1 $ MKSTREAM     # 建组，$ 表示从新消息开始
XREADGROUP GROUP g1 c1 COUNT 10 STREAMS stream >   # c1 领新消息
XACK stream g1 <ID>                    # 确认处理完成
    • > 表示「组内还没投递过的消息」；
    • 同一组内，一条消息只会投给一个消费者（这就是「组」的价值）；
    • 不同组之间互不影响，各自独立消费全量——这是「广播 + 分组」的混合能力。

    4. PEL：为什么需要 ack

    消息投递给消费者后，会进入该组的 PEL（pending entries list，待处理条目列表），记录「谁领了、什么时候领的、投递过几次」。只有 XACK 之后才从 PEL 移除。

    这带来三个直接结论：

    1. 消费者崩溃，消息不会丢——它还在 PEL 里，可以由别的消费者接手；
    2. 接手要靠命令：XPENDING 查看积压，XCLAIM 手工认领，XAUTOCLAIM（6.2+）批量自动认领；
    3. XACK 只影响 PEL，不删除条目。所以「ack 完空间就释放」是错的——容量要靠 XTRIM / XDEL。

    五、场景说明

    1. 事件流/操作日志：XADD events * type order.created id 1001，下游多个服务各建一个组消费（订单服务、风控服务、数据服务互不干扰）；
    2. 可靠任务队列：XREADGROUP 领任务 + 处理完 XACK，崩溃后 XAUTOCLAIM 接手；
    3. IM 消息存储：一个会话一个 Stream，按 ID 范围拉历史（XRANGE）；
    4. 变更捕获（CDC）的轻量方案：业务写入时追加一条，下游按 ID 增量同步。

    不适合：需要「取走即消失」的简单队列（用 List 更省）、需要复杂路由与延迟/重试（该上专业 MQ）、需要精确「一次性投递且不重复」的强语义（Stream 是 at-least-once，重复消费要业务侧幂等）。

    六、示例代码/实操步骤

    # 1. 追加与范围读取
127.0.0.1:6379> XADD orders * type created id 1001
"1704083133000-0"
127.0.0.1:6379> XADD orders * type paid id 1001
"1704083133001-0"
127.0.0.1:6379> XLEN orders
(integer) 2
127.0.0.1:6379> XRANGE orders - + COUNT 2
1) 1) "1704083133000-0"
   2) 1) "type"
      2) "created"
      3) "id"
      4) "1001"
2) ...

# 2. 按 ID 范围取（含/不含）
127.0.0.1:6379> XRANGE orders 1704083133001-0 + 
127.0.0.1:6379> XRANGE orders (1704083133000-0 +   # 左括号表示不含

# 3. 单消费者：游标读
127.0.0.1:6379> XREAD COUNT 2 STREAMS orders 0
127.0.0.1:6379> XREAD BLOCK 0 STREAMS orders $
# 另开终端 XADD 一条，上面这条会立刻返回

# 4. 建消费组
127.0.0.1:6379> XGROUP CREATE orders g1 $
OK
127.0.0.1:6379> XINFO GROUPS orders
1) 1) "name" 2) "g1"
   3) "consumers" 4) (integer) 0
   5) "pending" 6) (integer) 0
   7) "last-delivered-id" 8) "1704083133001-0"

# 5. 组内消费：> 表示新消息
127.0.0.1:6379> XADD orders * type shipped id 1001
"1704083133002-0"
127.0.0.1:6379> XREADGROUP GROUP g1 c1 COUNT 1 STREAMS orders >
1) 1) "orders"
   2) 1) 1) "1704083133002-0"
         2) 1) "type" 2) "shipped" 3) "id" 4) "1001"

# 6. 未 ack 会进 PEL
127.0.0.1:6379> XPENDING orders g1
1) (integer) 1
2) "1704083133002-0"
3) "1704083133002-0"
4) 1) 1) "c1"
      2) "1"

# 7. ack 之后 PEL 清空，但条目还在
127.0.0.1:6379> XACK orders g1 1704083133002-0
(integer) 1
127.0.0.1:6379> XPENDING orders g1
1) (integer) 0
2) (nil)
3) (nil)
4) (nil)
127.0.0.1:6379> XLEN orders
(integer) 3                     # 条目没被删掉

# 8. 崩溃接手：批量认领
127.0.0.1:6379> XAUTOCLAIM orders g1 c2 0 0 COUNT 10
1) "0-0"
2) 1) 1) "1704083133002-0"
      2) 1) "type" 2) "shipped"
3) (empty array)

# 9. 控容量：截断
127.0.0.1:6379> XTRIM orders MAXLEN 100
(integer) 0
127.0.0.1:6379> XADD orders MAXLEN ~ 100 * type closed id 1002

    MAXLEN ~ 是近似截断（按节点整块裁剪，更省 CPU），官方允许这种「略微超一点」的取舍。精确上限用 MAXLEN =。

    七、常见坑（官方明确说明的限制）

    1. ack 不等于删除。消息留在 Stream 里直到 XTRIM / XDEL。不做截断的 Stream 会无限增长，这是线上最典型的事故——发布几个月后单个 key 涨到几 GB。
    2. BLOCK 的单位是毫秒。XREAD BLOCK 0 是永久阻塞，BLOCK 5 是 5 毫秒（不是 5 秒）。与 BLPOP 的秒级语义混用会得到完全错误的行为。
    3. XREADGROUP 的 > 与 0 语义相反：> 领新消息，0 读「自己的 PEL 历史」。想「读自己的积压」要用 0，用 > 永远读不到旧积压。
    4. 消费组的 $ 只对创建时刻生效。XGROUP CREATE key g $ 之后新入队的消息才算「新」，历史消息不会被投递；要从头补，用 0。
    5. XAUTOCLAIM 是 6.2 新增。更早版本只能 XPENDING + 逐个 XCLAIM。
    6. 投递语义是 at-least-once：处理成功但 XACK 前崩溃，消息会被重投。业务必须幂等——这不是 Redis 的缺陷，而是所有「至少一次」模型的共同前提。
    7. XDEL 不会重置 ID。删掉中间条目后新条目 ID 依旧递增，因此不能靠 ID 连续性判断「有没有丢」。
    8. 单 Stream 条目数没有官方硬上限，但内存是硬约束；容量规划按「每条目字节数 × 保留条数」算。

    版本差异（8.x 标注）

    6.2 引入 XAUTOCLAIM，7.0 起支持 XADD ... NOMKSTREAM 等细节选项。8.x 在 Stream 上无破坏性变更。若使用 6.0/6.2 之前版本，则自动认领能力不可用，需要自建巡检脚本。

    依据：https://redis.io/docs/latest/commands/xautoclaim/

    八、课后小结

    • Stream 是带自增 ID 的追加日志，ID 形如「毫秒-序号」且单调递增；
    • 单消费者用 XREAD 自管游标；多消费者用 XREADGROUP，进度由服务端 PEL 维护；
    • XACK 只清 PEL，不删条目；容量靠 XTRIM（MAXLEN/MINID）或 XDEL；
    • 崩溃接手用 XAUTOCLAIM（6.2+）或 XPENDING + XCLAIM；
    • 投递语义是 at-least-once，业务必须幂等；
    • BLOCK 单位是毫秒，$ 与 0 语义相反，这两处最易出错。

    九、思考题

    1. Pub/Sub、List、Stream 三者做「订单事件通知」，分别会丢消息吗？为什么？
    2. 一个消费组两个消费者，c1 领了消息后卡住 10 分钟没 ack。此时 XPENDING 会看到什么？c2 怎么接手？
    3. 为什么「ack 完就没空间问题」是错的？如果业务每天 100 万条、每条 200 字节，不做截断一个月会占多少内存？
    4. XREADGROUP GROUP g c 0 STREAMS s 与 ... > STREAMS s 分别在读什么？什么时候必须用 0？
    5. at-least-once 意味着可能重复消费。你的任务处理器需要哪一层幂等保护？举一个不加幂等会出事的例子。
