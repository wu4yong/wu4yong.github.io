    mysql-20-索引失效

    📅 2022-11-30

    索引失效的八种写法

    索引失效几乎都不是「优化器犯错」，而是 SQL 让 B+Tree 的有序性用不上｜依据 MySQL 8.4 Optimizer 与 Range Optimization 章节自绘

    一、学习目标

    1. 记住八种最常见的索引失效写法，看到 SQL 就能判断；
    2. 每种失效都能给出可落地的改写方案，而不是只说「别这么写」；
    3. 会用 EXPLAIN 的 key、type、rows、Extra 四列确认失效是否真的发生。

    二、前置知识

    联合索引的最左前缀、B+Tree 有序性（MQ18/MQ19）。知道「索引能用的前提是列的有序性被保留」这一句就够。

    三、理论讲解（官方定义）

    索引（B+Tree）能加速查询的唯一原因是有序：给定条件后能定位到一个连续区间。凡是让「列值 → 索引键」的映射被破坏的写法，都会让优化器退回全表扫描或索引全扫。

    官方在 Range Optimization 里明确：范围访问要求条件形如 col op const，且 op 是 =、<=>、>、<、>=、<=、IS NULL、BETWEEN、IN、LIKE 'prefix%' 等；列上套函数、类型不匹配、前缀通配都落在这张清单之外。

    四、原理拆解

    从「列值被改写」到「区间无法定位」，最后表现为 type=ALL 或 rows 暴涨｜依据 MySQL 8.4 优化器章节自绘

    1. 列上做函数或运算

    -- 失效：DATE(created_at) 不是索引列本身
SELECT * FROM t_order WHERE DATE(created_at) = '2022-11-01';

-- 改写：改成半开区间
SELECT * FROM t_order
WHERE created_at >= '2022-11-01 00:00:00'
  AND created_at <  '2022-11-02 00:00:00';

    同理 LOWER(name)、UPPER(code)、SUBSTR(phone,1,7)、amount + 0、id * 2 都会失效。8.0.13 起可以建函数索引兜住这类查询。

    2. 隐式类型转换

    -- phone 是 VARCHAR(20)，右侧给了数字 → 列被转成数字，索引失效
SELECT * FROM t_user WHERE phone = 13800000000;

-- 正确：给字符串
SELECT * FROM t_user WHERE phone = '13800000000';

    反过来「数字列 = 字符串常量」是安全的（常量被转成数字）。判断口诀：常量向列的类型靠，靠不过去就失效。

    3. 前导通配符

    -- 失效：LIKE '%abc'
SELECT * FROM t_product WHERE title LIKE '%手机%';

-- 可用：只有后缀通配能走范围
SELECT * FROM t_product WHERE title LIKE '手机%';

    真要支持全文模糊匹配，用 FULLTEXT 索引 + MATCH ... AGAINST，或外部搜索引擎。

    4. OR 连接了无索引列

    -- a 有索引，b 没有 → 整体退化为全表扫
SELECT * FROM t WHERE a = 1 OR b = 2;

-- 改写：UNION ALL 拆开，各自走索引
SELECT * FROM t WHERE a = 1
UNION ALL
SELECT * FROM t WHERE b = 2 AND a <> 1;

    如果 OR 两侧都有索引，优化器可能走 index_merge，但通常仍不如一个合适的联合索引。

    5. 联合索引跳过最左前缀

    -- idx (a, b, c)，只查 b → 用不了（除非 Skip Scan 条件满足）
SELECT * FROM t WHERE b = 2;

-- 可用：带上 a
SELECT * FROM t WHERE a = 1 AND b = 2;

    6. 字符集或排序规则不一致

    -- 两表连接，一个 utf8mb4_general_ci，一个 utf8mb4_0900_ai_ci
SELECT * FROM t1 JOIN t2 ON t2.code = t1.code;

    轻则 Illegal mix of collations，重则列被隐式转换导致索引失效。统一用 utf8mb4_0900_ai_ci（8.4 默认），迁移时把老表的 general_ci 一并改掉。

    7. NOT、!=、NOT IN 与 IS NOT NULL

    -- 否定条件要「排除」，无法定位区间，通常全表扫
SELECT * FROM t_order WHERE status <> 2;
SELECT * FROM t_user WHERE id NOT IN (1, 2, 3);

    != 在选择性极低时（如 99% 的行满足）必然全表扫；NOT IN 还有 NULL 陷阱（右侧含 NULL 时结果恒为空）。改写思路：把否定转成肯定枚举，或加一个能走索引的前置条件。

    8. 范围条件之后的列失效

    -- idx (a, b)：a 用了范围，b 只能靠 ICP 过滤，无法再缩小扫描
SELECT * FROM t WHERE a > 10 AND b = 2;

-- 更好：把等值列放前
-- idx (b, a) 或 idx (a) + (b) 视查询分布而定

    这类不算「完全失效」，但扫描量下不来，实际表现和失效类似。

    另外两种「看起来失效、其实是排序问题」：SELECT * 破坏覆盖索引；ORDER BY 方向与索引不一致触发 Using filesort（8.0 起降序索引可解）。

    五、场景说明

    1. 时间范围查询：改成半开区间，别用 DATE()；
    2. 手机号/订单号检索：入参统一转字符串，别让框架按数字绑定；
    3. 后台模糊搜索：LIKE 'xx%' 走索引，%xx% 交 ES；
    4. 多条件筛选：能拆 UNION ALL 的 OR 就拆，能建联合索引的就不拆；
    5. 老库迁移：字符集统一，避免连接时隐式转换。

    六、示例代码/实操步骤

    1. 逐条验证

    EXPLAIN SELECT * FROM t_order WHERE DATE(created_at) = '2022-11-01';   -- type=ALL
EXPLAIN SELECT * FROM t_order WHERE created_at >= '2022-11-01' AND created_at < '2022-11-02';  -- type=range
EXPLAIN SELECT * FROM t_user WHERE phone = 13800000000;   -- type=ALL
EXPLAIN SELECT * FROM t_user WHERE phone = '13800000000'; -- type=ref

    2. 用 EXPLAIN ANALYZE 看真实耗时

    EXPLAIN ANALYZE
SELECT * FROM t_order WHERE status = 2 AND created_at >= '2022-11-01';

    8.0.18 起可用，输出真实执行时间与行数，比传统 EXPLAIN 的估算更可靠。

    3. 函数索引兜住函数查询

    ALTER TABLE t_order ADD INDEX idx_created_day ((DATE(created_at)));
EXPLAIN SELECT * FROM t_order WHERE DATE(created_at) = '2022-11-01';  -- 走 idx_created_day

    注意函数索引的表达式必须与查询里的完全一致，否则仍然不匹配。

    4. 找出库里的可疑 SQL

    -- 慢查询日志里带函数的写法
SELECT * FROM mysql.slow_log
WHERE sql_text LIKE '%DATE(%' OR sql_text LIKE '%LOWER(%'
ORDER BY query_time DESC LIMIT 20;

    Java 侧怎么落地：从源头堵住失效

    1. 参数类型由实体决定：Mapper 方法签名用 String phone 而不是 Long，避免 MyBatis 按数字绑定；
    2. 禁止把函数写进 WHERE：需要按天统计就用半开区间，或在 DAO 层封装 betweenDay()；
    3. 动态 SQL 收口：<if test> 拼条件时只允许等值、范围、LIKE prefix，禁止拼 OR 与 !=；
    4. ORDER BY 白名单：字段名映射到固定 SQL 片段，杜绝 ${sortField}；
    5. 上线前跑 EXPLAIN 回归：把核心查询的 EXPLAIN 结果作为用例存进 CI，type 退化即失败。

    七、常见坑

    1. 只给列建索引，不给查询建索引：索引列对了，写法不对照样失效；
    2. 以为 != 一定失效：选择性高时（如排除极少数）仍可能走索引，看 rows 而不是看符号；
    3. LIKE 'x%' 用了 _ 通配：LIKE '_bc%' 仍能走范围，但 LIKE '%bc' 不行；
    4. 隐式转换方向搞反：INT 列 = 字符串常量没问题，VARCHAR 列 = 数字才失效；
    5. 函数索引与查询表达式不一致：DATE(created_at) 与 CAST(created_at AS DATE) 是两个不同的索引键；
    6. OR 拆 UNION ALL 忘了去重：UNION 会多一次排序去重，用 UNION ALL + 条件互斥；
    7. NOT IN 右侧有 NULL：结果恒为空，先 IS NOT NULL 过滤。

    八、版本差异

    • 5.7：无函数索引、无 EXPLAIN ANALYZE；隐式转换规则一致；
    • 8.0：8.0.13 起函数索引；8.0.18 起 EXPLAIN ANALYZE；8.0 起 index_merge 行为有调整；
    • 8.4：规则与 8.0 一致；utf8mb4_0900_ai_ci 为默认排序规则，跨库连接时更要注意老表字符集。

    九、课后小结

    • 失效的本质是「索引列的有序性用不上」；
    • 八种写法：列上函数、隐式转换、前导通配、无索引列的 OR、跳过最左前缀、字符集不一致、否定条件、范围后列；
    • 每种都有改写路径：半开区间、类型对齐、UNION ALL、联合索引重排、函数索引；
    • 判断失效看 type 与 rows，别靠记口诀；
    • 8.0 起 EXPLAIN ANALYZE 给真实耗时，比估算可靠。

    十、思考题

    1. WHERE phone = 13800000000（phone 为 VARCHAR）为什么失效？

      参考回答：比较时 MySQL 要把 phone 转成数字才能与数字常量比，等于在列上做了一次隐式函数运算，索引键的有序性被破坏，只能逐行转换后比较，退化为全表扫描。

    2. WHERE a > 10 AND b = 2 在 idx(a, b) 上能用几列？

      参考回答：只有 a 能定位范围；b 无法继续缩小扫描区间，只能靠 ICP 在引擎层过滤，减少回表次数但不减少索引扫描量。

    3. 为什么 LIKE 'abc%' 能用索引而 LIKE '%abc' 不能？

      参考回答：B+Tree 按前缀有序，已知前缀就能定位连续区间；前导通配符意味着「结尾未知」，任何位置都可能匹配，无法定位起点。

    4. OR 两侧都有索引时一定快吗？

      参考回答：不一定。优化器可能走 index_merge，需要分别扫描两个索引再合并，回表次数可能翻倍；多数情况一个设计良好的联合索引更快。

    5. 函数索引建了还是不生效，常见原因是什么？

      参考回答：查询里的表达式与索引定义不完全一致，例如索引是 DATE(created_at) 而查询写的是 CAST(created_at AS DATE)，或函数参数被隐式转换。
