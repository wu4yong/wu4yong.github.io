    mysql-19-索引设计

    📅 2022-11-29

    索引设计：联合索引、最左前缀、覆盖索引与索引下推

    联合索引只按「从左到右」的字典序生效，设计就是让最高频的查询恰好落在前缀上｜依据 MySQL 8.4 多列索引与优化器章节自绘

    一、学习目标

    1. 说清联合索引的排序规则，能用「字典序」判断一个查询能不能用上索引；
    2. 会安排联合索引的列顺序（等值优先、范围靠后、排序对齐）；
    3. 掌握覆盖索引、索引下推（ICP）、Skip Scan 三种「少回表」的手段。

    二、前置知识

    B+Tree 与聚簇索引（MQ18）、选择性概念。能读 EXPLAIN 的 key、type、Extra 三列。

    三、理论讲解（官方定义）

    多列索引（KEY idx (a, b, c)）在物理上按 (a, b, c) 的字典序排列：先比 a，a 相同再比 b，以此类推。

    官方给出的可用条件：

    • 索引可用于 WHERE 中「最左前缀」的等值与范围条件——(a)、(a,b)、(a,b,c) 都能用，跳过 a 直接用 b 则不能（8.0.13 起有 Skip Scan 例外）；
    • 一旦某一列使用了范围条件（>、<、BETWEEN、LIKE 'x%'），它右侧的列只能靠索引下推过滤，不能继续缩小扫描范围；
    • 若查询只需要索引里的列，可以只读索引不回表（覆盖索引），Extra 显示 Using index；
    • ICP 自 5.6 起默认开启，适用于 range、ref、eq_ref、ref_or_null 访问方式，且只对二级索引有效。

    四、原理拆解

    ICP 把过滤条件下推到引擎层，Skip Scan 让「跳过前缀」也能走索引｜依据 MySQL 8.4 ICP 与 Range Optimization 章节自绘

    1. 最左前缀：用字典序判断

    索引 (a, b, c) 的键序列形如：

    (1, 'x', 10)
(1, 'x', 20)
(1, 'y', 10)
(2, 'x', 10)
    • WHERE a=1：连续区间，能用；
    • WHERE a=1 AND b='x'：区间更窄，能用；
    • WHERE b='x'：b 的相同值散落在所有 a 上，不连续，用不了（除 Skip Scan）；
    • WHERE a=1 AND c=10：只能靠 a 定位，c 交给 ICP 过滤。

    2. 列顺序怎么排

    优先级从高到低：

    1. 等值条件列放前面，且把「最常用于过滤」的放最左；
    2. 范围条件列放最后，它右侧的列无法再缩小范围；
    3. 排序列与索引顺序对齐：ORDER BY b 想免排序，b 必须是索引里连续的一段且前面列都是等值；
    4. 选择性高的列靠前通常更好，但不如「查询形态」重要——列顺序首先服务于 SQL，其次才是选择性。

    3. 覆盖索引

    -- 需要回表：SELECT 里有 phone，索引里没有
SELECT id, name, phone FROM t_user WHERE name = '张三';

-- 覆盖：只读索引
ALTER TABLE t_user ADD INDEX idx_name_phone (name, phone);
SELECT id, name, phone FROM t_user WHERE name = '张三';   -- Extra: Using index

    注意：二级索引天然包含主键，所以 SELECT id 总是覆盖的。

    4. 索引下推（ICP）

    官方例子：索引 (zipcode, lastname, firstname)，查询

    SELECT * FROM people
WHERE zipcode='95054' AND lastname LIKE '%etrunia%' AND address LIKE '%Main Street%';

    lastname LIKE '%...%' 用不上索引范围，但可以在引擎层用索引里的 lastname 先过滤，只对通过的行回表读 address。Extra 显示 Using index condition。

    ICP 的边界（官方明确）：

    • 只对二级索引有效——聚簇索引本来就要读整行，没有收益；
    • 子查询、存储函数、触发器产生的条件下推不了；
    • 虚拟列上的二级索引不支持 ICP；
    • 依赖 optimizer_switch 的 index_condition_pushdown 开关，默认开。

    5. Skip Scan（8.0.13 起）

    索引 (f1, f2)，查询 WHERE f2 > 40 没有 f1 条件时，优化器可以对 f1 的每个去重值各做一次子范围扫描。官方条件很苛刻：

    • 单表查询，不带 GROUP BY / DISTINCT；
    • 只引用索引里的列；
    • 前缀列的条件必须是常量等值（含 IN）；
    • 后续列上必须有范围条件；
    • 前缀列的去重值数量要少，否则退化成全索引扫描。

    Extra 显示 Using index for skip scan。它救的是「前缀列基数很低」的场景，不能当成万能补丁。

    6. 索引合并（index merge）

    当两个单列索引各自能覆盖一部分条件时，优化器可能做 intersection / union / sort-union。实践里它经常不如一个合适的联合索引，遇到 type=index_merge 优先考虑合并索引。

    五、场景说明

    1. 订单列表：(user_id, created_at)，用户维度 + 时间倒序，一次扫描即出结果；
    2. 后台筛选：(status, created_at)，状态等值 + 时间范围；
    3. 商品搜索：(category_id, price)，分类等值 + 价格排序；
    4. 唯一业务号：uk_order_no，既是唯一约束又是查询索引；
    5. 日志表：(app_id, level, created_at)，前两列低基数等值、第三列范围。

    六、示例代码/实操步骤

    1. 从查询反推索引

    -- 高频查询
SELECT id, order_no, amount FROM t_order
WHERE user_id = 1001 AND status = 2
  AND created_at >= '2022-11-01'
ORDER BY created_at DESC
LIMIT 20;

    设计 (user_id, status, created_at)：

    • user_id、status 等值 → 放前；
    • created_at 既范围又排序 → 放最后，同时满足 ORDER BY；
    • SELECT 里的 order_no、amount 不在索引里 → 仍要回表，可考虑加进索引做覆盖（注意索引变宽）。
    ALTER TABLE t_order ADD INDEX idx_user_status_time (user_id, status, created_at);

    2. 验证是否免排序

    EXPLAIN FORMAT=TREE
SELECT id FROM t_order WHERE user_id=1001 AND status=2
ORDER BY created_at DESC LIMIT 20;

    没有 Sort 节点、只有 Index range scan 或 Index scan，说明排序被索引消化掉了。

    3. 覆盖索引 + 延迟关联解决深分页

    -- 坏：先扫 100 万行再丢弃
SELECT * FROM t_order WHERE status=2 ORDER BY created_at DESC LIMIT 900000, 20;

-- 好：先用覆盖索引取主键，再回表 20 行
SELECT o.* FROM t_order o
JOIN (
  SELECT id FROM t_order WHERE status=2 ORDER BY created_at DESC LIMIT 900000, 20
) t ON o.id = t.id;

    4. 前缀索引

    -- email 很长，只索引前 12 个字符
ALTER TABLE t_user ADD INDEX idx_email_prefix (email(12));

    代价：无法用于 ORDER BY email 与覆盖索引，只能加速 WHERE email LIKE 'xxx%' 这类查询。

    5. 找出冗余索引

    SELECT * FROM sys.schema_redundant_indexes;
SELECT * FROM sys.schema_unused_indexes;

    redundant_indexes 会指出「被更长索引前缀覆盖」的索引，unused_indexes 依赖 performance_schema 的统计，需运行足够长时间才有意义。

    Java 侧怎么落地：让 SQL 与索引对齐

    1. 先定查询再做索引：把 DAO 层的高频方法列出来，逐条比对索引前缀，别按实体字段批量建索引；
    2. 禁止动态拼 ORDER BY：ORDER BY ${sortField} 会让索引失效并带来注入风险，用白名单映射到固定 SQL；
    3. 分页统一走延迟关联：封装一个 PageQuery 模板，内部固定「取 ID → 回表」两步；
    4. 索引与 DDL 版本化：用 Flyway / Liquibase 管理 ADD INDEX，评审时标注对应查询；
    5. 上线后回归 EXPLAIN：把 TOP 查询的 EXPLAIN 结果存进监控，type 从 range 掉到 ALL 就报警。

    七、常见坑

    1. (a, b) 索引查 WHERE b=?：用不了，除非满足 Skip Scan 的苛刻条件；
    2. 范围列放中间：(a, range_col, c) 里 c 只能靠 ICP 过滤，扫描量下不来；
    3. ORDER BY 与索引方向不一致：ORDER BY a ASC, b DESC 需要 (a ASC, b DESC) 降序索引（8.0 起才真正生效）；
    4. 为覆盖索引把大字段塞进去：索引过宽，页数暴涨，反而更慢；
    5. LIKE '%x%' 指望索引：前置通配符无法走范围扫描；
    6. index_merge 当成优化：多数情况不如一个联合索引，且容易放大回表；
    7. 索引只加不删：写放大、优化器选择困难，定期用 sys 视图清理。

    八、版本差异

    • 5.7：支持 ICP、无 Skip Scan、降序索引只是语法；
    • 8.0：8.0.13 起 Skip Scan 与函数索引；降序索引物理生效；index_merge 行为有调整；
    • 8.4：ICP 与 Skip Scan 规则与 8.0 一致；ADD INDEX 仍为 INPLACE，大表建议外部工具在线建。

    九、课后小结

    • 联合索引按字典序生效，最左前缀决定可用范围；
    • 列顺序：等值在前、范围在后、排序列与索引方向对齐；
    • 覆盖索引免回表，Using index；ICP 减少回表，Using index condition；
    • Skip Scan 只救低基数前缀，条件苛刻；
    • 索引数量要控制，定期用 sys 视图清理冗余与未使用索引。

    十、思考题

    1. (a, b, c) 索引下，WHERE a=1 AND c=2 能用上几列？

      参考回答：只能用 a 定位区间，c 无法继续缩小扫描范围，但可以通过 ICP 在引擎层用索引里的 c 过滤，减少回表次数。

    2. 为什么 ORDER BY 想免排序，前面几列必须是等值条件？

      参考回答：索引按整体字典序排列，只有前缀列取值固定时，后续列的排列顺序才等价于全局有序；一旦前缀列是范围，后续列的全局顺序就被打乱，只能额外排序。

    3. ICP 为什么对聚簇索引没有收益？

      参考回答：聚簇索引的叶子就是整行，读索引时已经把行读进 Buffer Pool，没有「先过滤再回表」这一步可省，所以 ICP 只对二级索引有效。

    4. Using index 与 Using index condition 能同时出现吗？

      参考回答：不会。Using index 表示无需回表（覆盖），Using index condition 表示仍需回表但条件下推，二者语义互斥。

    5. 深分页为什么先取 ID 再回表会快很多？

      参考回答：第一次查询只走覆盖索引，扫描的是窄索引页，I/O 远小于读整行；丢弃前面的行时不必回表，最终只对需要的 20 行做一次回表。
