    Spark（四）内存模型与调优

    📅 2023-06-12

    内存模型与调优

    Spark 作业慢、OOM、GC 卡顿，九成问题出在内存分配和数据倾斜上。这一篇讲清 Executor 内存怎么分（UnifiedMemoryManager，1.6 起成为默认），序列化怎么选，广播变量在什么场景下省网络，以及数据倾斜的典型现象和处置思路。参数只给生产上真会动的几个，不堆砌配置表。

    执行内存与缓存内存共享一块堆内存，内存不足时向磁盘溢写，热点数据被广播到各节点

    1.1 Executor 内存怎么划分

    Spark 1.6 之前，执行内存（shuffle、聚合、排序用到的工作区）和存储内存（缓存 RDD/ DataFrame 块）是两块固定配额，互相抢占不到对方地盘，容易出现”一边闲着一边溢写”。UnifiedMemoryManager（统一内存管理） 把两块收进同一个池子里，按需借用，这也是 1.6 之后的默认实现。

    区域
    用途
    回收方式
    执行内存（Execution）
    shuffle 缓存、排序、聚合、join 工作区
    任务结束即可释放
    存储内存（Storage）
    缓存块、广播变量副本
    被内存压力驱逐时回源重算或溢写磁盘
    预留内存（Reserved）
    Spark 内部对象、用户数据结构
    不参与任务配额分配

    借用规则：存储内存可以借执行内存的空闲空间；反过来执行内存需要空间时，会把存储侧借走的部分驱逐回收。两块边界由 spark.memory.fraction（占堆内比例，默认 0.6）和 spark.memory.storageFraction（存储保底比例，默认 0.5）控制，日常调优先动 Executor 堆大小和分区数，再碰这两个比例。

    判断内存够不够，先看 Spark UI 的 Executor 页：已用执行内存、已用存储内存、溢写磁盘字节数都在上面。同一批数据反复缓存的作业，存储占用高是正常的；纯批处理作业存储几乎为零，溢写磁盘却很大，说明分片过大或分区数过少。

    1.2 序列化：省空间的第一手段

    未序列化的 JVM 对象有对象头、指针、哈希表引用等额外开销，一条记录实际占的内存常常是字段裸值的好几倍。序列化把对象压成字节数组存储，代价是读写时多一层编解码。

    序列化器
    特点
    适用
    Java 序列化
    默认，兼容所有可序列化类，体积大、慢
    兜底方案
    Kryo 序列化
    体积小、速度快，需注册类
    大数据量、迭代型作业首选

    启用 Kryo 并注册用到的类，避免运行时反射探测：

    # spark-defaults.conf 或提交参数
spark.serializer org.apache.spark.serializer.KryoSerializer
spark.kryo.registrationRequired true
    val conf = new org.apache.spark.SparkConf()
  .registerKryoClasses(Array(classOf[OrderRecord], classOf[UserProfile]))

    注册开关打开后，未注册的类直接报错而不是悄悄降级，这是有意为之：防止上线后才发现序列化体积失控。

    1.3 广播变量：小表 join 省网络

    大表关联小表时，如果小表在每个 Task 上都 shuffle 一份，网络和内存都浪费。广播变量把小数据集发到每个 Executor 本地一份，Task 直接查本地副本，省掉小表的 shuffle。

    val dim = spark.read.parquet("hdfs:///data/dim_city.parquet")
val dimBroadcast = org.apache.spark.sql.functions.broadcast(dim)

val fact = spark.read.parquet("hdfs:///data/fact_order.parquet")
val joined = fact.join(dimBroadcast, "city_id")

    判断能不能广播：小表体量要明显小于 Executor 可用存储内存，且 join 键上分布均匀。默认广播阈值由 spark.sql.autoBroadcastJoinThreshold（默认 10MB 左右）控制，超过这个大小引擎不会自动广播，手动 broadcast() 也要先算清内存账。

    广播变量在 Executor 端只存一份副本，多个 Task 共享；它不走 shuffle 链路，序列化一次后随任务分发。需要注意广播内容不能带 Driver 端的连接对象、不可序列化句柄，否则分发阶段就报错。

    1.4 数据倾斜：现象与处置

    数据倾斜指少数 key 分到的数据量远大于其他 key，对应到任务上就是个别 Task 跑很久、堆内存爆掉，其余 Task 早已结束。典型现象：

    • Spark UI 上同一个 Stage 的 Task 耗时和输入量方差极大
    • 日志反复出现 OutOfMemoryError: Java heap space 或 shuffle 溢写磁盘
    • join 之后结果行数异常膨胀，个别 key 占绝大多数
    思路
    做法
    适用
    增加拆分粒度
    提高 shuffle 分区数，让热点 key 分散到更多分区
    分区过少导致的倾斜
    加盐（salt）
    给热点 key 拼接随机前缀分两轮聚合
    聚合类倾斜，单 key 体量极大
    广播小表
    走广播 join，绕开大表 shuffle
    大小表关联
    过滤脏数据
    剔除空 key、异常 key
    倾斜来自缺失值或脏数据

    加盐的基本套路：第一轮给热点 key 加随机前缀分组聚合，第二轮去掉前缀再汇总；热点不提前识别，盲目加盐会把普通 key 的 shuffle 量也放大。

    定位热点 key 可以在聚合前对 join 键做一次计数排序，把出现次数 Top N 的 key 单独拎出来看；空字符串、null、默认占位值往往是倾斜主力，先在过滤段剔除再关联。

    1.5 生产上常动的几个参数

    参数
    作用
    调优方向
    spark.executor.memory
    单个 Executor 堆内存
    按数据分片大小给，不是越大越好
    spark.executor.cores
    单 Executor 并行线程数
    核数过多会争抢内存，一般 4–8
    spark.sql.shuffle.partitions
    shuffle 后分区数
    按 shuffle 数据量调，默认 200 常偏大或偏小
    spark.memory.fraction
    任务内存占堆内比例
    缓存很重时适当上调，纯计算保持默认
    spark.serializer
    序列化器
    大数据量换 Kryo

    1.6 容易踩的坑

    • 只加 Executor 内存不改分区数，大分片还是挤在少数 Task 上，OOM 照旧
    • 广播一张超过阈值的大表，Executor 缓存被撑满，反而拖垮整个作业
    • 序列化选 Kryo 却不注册类，反射探测消耗 CPU，体积优势打折
    • 在 Driver 端做全局聚合再分发，Driver 成为单点瓶颈
    • 把存储内存保底比例调得过高，执行内存被挤占，shuffle 频繁溢写
    • 序列化与缓存级别不匹配：未序列化对象堆内放得下，换成 MEMORY_ONLY_SER 后反序列化 CPU 开销被忽略，作业变慢却看不出原因

    • 内存管理说明：https://spark.apache.org/docs/latest/configuration.html#memory-management
    • 性能调优指南：https://spark.apache.org/docs/latest/tuning.html
    • 广播变量文档：https://spark.apache.org/docs/latest/rdd-programming-guide.html#broadcast-variables
    • 数据倾斜与 AQE：https://spark.apache.org/docs/latest/sql-performance-tuning.html

    1.8 清单

    1. UnifiedMemoryManager 自 1.6 起默认，执行与存储共享池、按需借用，告别两块固定配额
    2. Kryo 序列化体积小速度快，生产上配合注册类使用，注册严格模式避免静默降级
    3. 广播变量解决大小表 join 的小表 shuffle，前提是小表装得下 Executor 存储内存
    4. 倾斜先看 UI 上 Task 耗时与输入量方差，再选拆分、加盐、广播、过滤的路子
    5. 调优顺序：分区数 → Executor 内存与核数 → 序列化 → 内存比例，不要一上来改比例
    6. 常见误判：OOM 就加内存，往往分区或倾斜问题才是根因
    7. 内存调优先看 UI 上的溢写字节与分区方差，再决定动内存还是动分区数
