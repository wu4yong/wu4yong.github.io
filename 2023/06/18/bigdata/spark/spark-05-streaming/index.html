    Spark（五）Structured Streaming

    📅 2023-06-18

    Structured Streaming

    流计算最绕的地方是”数据没有边界”：查询跑着跑着新数据就来了，结果要持续更新，挂了还要能接着算。Structured Streaming 把流当成一张不断增长的无限表（unbounded table），用和批处理一样的 DataFrame/SQL 接口表达逻辑，引擎负责按微批不断增量计算。这一篇讲清它的模型、watermark、checkpoint，以及 exactly-once 语义靠什么保证。

    无限增长的数据表被切成一个个微批，状态随批次累积，水位线向前推进清理过期数据

    1.1 核心模型：流是一张不断长大的表

    概念
    类比
    说明
    无限表（unbounded table）
    一张只追加、不停止写入的表
    每行到达流的数据都是表的一行
    增量查询（incremental query）
    对这张表持续跑聚合
    新数据到达后只算新增部分
    结果表（result table）
    当前聚合结果的快照
    每个触发间隔更新一次，再按输出模式写出

    因为接口和批处理同源，同一段聚合代码改成流只需要把 read 换成 readStream、write 换成 writeStream。这也是 Structured Streaming 相对早期 DStream（离散流）的主要优势：不再把流切成 RDD 批次去手动管理。

    要注意：流查询启动后会持续占用资源，spark-submit 提交的长作业需要由调度平台或守护进程管理；开发调试时常用 AvailableNow 跑完存量数据自动停止，避免本地进程一直挂着。

    1.2 处理模型：微批为主，连续模式为辅

    模式
    行为
    适用
    微批（micro-batch）
    按触发间隔把到来的数据攒成小批次计算
    默认模式，吞吐高，延迟秒级
    连续处理（continuous）
    持续扫描数据、低延迟处理
    延迟要求到毫秒级，支持的算子有限

    生产上绝大多数作业走微批：Trigger.ProcessingTime 控制批次间隔，Trigger.AvailableNow 用于把存量数据追完后停止。连续模式只在明确需要更低延迟、且算子在支持名单内时才考虑。

    1.3 状态与 watermark

    做窗口聚合、会话分析这类需求，引擎要记住每组当前的聚合值，这部分内存就是状态（state）。数据迟到不可避免：上游抖动、网络重传都会让晚到的记录落在窗口之外。watermark（水位线） 按事件时间推进，划定”最晚还愿意等多久”，超过水位线的旧状态被清理。

    import org.apache.spark.sql.functions._

val events = spark.readStream
  .format("kafka")
  .option("kafka.bootstrap.servers", "host:9092")
  .option("subscribe", "order_topic")
  .load()
  .select(from_json(col("value").cast("string"), schema).as("evt"))
  .select("evt.*")

val windowed = events
  .withWatermark("event_time", "10 minutes")   // 容忍 10 分钟迟到，超期状态清理
  .groupBy(window(col("event_time"), "10 minutes"), "city")
  .count()

val query = windowed.writeStream
  .outputMode("append")
  .format("parquet")
  .option("checkpointLocation", "hdfs:///checkpoint/order-window")
  .start("hdfs:///data/order-window/")

    withWatermark 两个要点：时间列必须是事件时间，不能用处理时间；容忍时长按业务能接受的迟到上限给，给得过大状态积压，给得过小晚到数据被丢弃。

    1.4 checkpoint：进度与状态的持久化

    checkpoint 目录同时记两类东西：消费进度（从哪个偏移量开始读）和状态快照（各分组当前聚合值）。作业崩溃或重启后，引擎从 checkpoint 恢复，接着上次的位置继续算，不重复也不漏。

    配置项
    作用
    注意
    checkpointLocation
    状态与进度落盘目录
    输出到 Kafka/文件/表都应配置，目录不能与结果输出混用
    删除 checkpoint
    等于丢掉全部状态
    改逻辑、改 Schema 时常需要重建，重建前先备份
    多流复用
    每个独立查询一个目录
    两个查询共用同一 checkpoint 会损坏元数据

    1.5 exactly-once 怎么凑齐

    端到端恰好一次不是引擎单方面承诺的，需要三段都到位：

    环节
    要求
    落地方式
    数据源
    偏移量可重放、可回溯
    Kafka 按 offset 重读，进度记入 checkpoint
    计算
    状态可恢复、结果可重算
    状态快照落 checkpoint，重启后恢复聚合值
    结果写出
    重复写入不产生重复结果
    文件/表支持幂等或事务提交，Kafka 按 offset 幂等生产

    三段缺一段都会漏或重：数据源只能保留短期日志、写出端不支持幂等，单靠流引擎都做不到 exactly-once。理解这一点，比背”Structured Streaming 保证 exactly-once”这句话有用得多。

    1.6 输出模式

    模式
    写出内容
    适用
    Append
    只写本批次新增、且不会被更新的结果
    水位线保护下的窗口聚合
    Complete
    每次写出整张结果表
    全量聚合，状态量可控时用
    Update
    只写本批次发生变化的行
    流式维表、持续更新指标

    聚合查询能用哪种输出模式受语义约束：Complete 不能配合 watermark 清理无限增长的状态；选错模式引擎会直接报错，这是保护不是刁难。

    另外要区分事件时间与处理时间：事件时间是数据本身携带的业务发生时间，处理时间是引擎收到数据的时间。watermark 必须挂在事件时间列上，上游积压时处理时间会持续领先事件时间，用错列会导致状态该清不清。

    1.7 容易踩的坑

    • 用处理时间列做 watermark，上游一积压状态就持续膨胀
    • 不配 checkpoint 直接上生产，重启后从最早偏移量重读，结果重复
    • checkpoint 目录被手动清空后继续跑，状态丢失，聚合结果对不上
    • 把批处理 DataFrame 直接 start()，忘记流查询需要独立的停止与监控管理
    • 会话窗口给的迟到容忍过小，正常跨会话晚到的数据被直接丢弃

    1.8 官方资料

    • Structured Streaming 编程指南：https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html
    • 流式数据源与 Sink 参考：https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html#input-sources
    • 事件时间与 watermark：https://spark.apache.org/docs/latest/structured-streaming-programming-guide.html#event-time
    • Spark 配置（流式相关参数）：https://spark.apache.org/docs/latest/configuration.html

    1.9 清单

    1. Structured Streaming 把流建模成无限增长的表，查询接口与批处理同源
    2. 默认微批处理，吞吐高、延迟秒级；连续模式算子受限，只在低延迟刚需时用
    3. watermark 按事件时间推进，清理超期状态；容忍时长按业务迟到上限给
    4. checkpoint 同时存消费进度与状态快照，是故障恢复和 exactly-once 的前提
    5. 端到端恰好一次 = 数据源可重放 + 状态可恢复 + 写出幂等/事务，三段缺一不可
    6. 输出模式受聚合语义约束，Append/Complete/Update 不能随意互换
