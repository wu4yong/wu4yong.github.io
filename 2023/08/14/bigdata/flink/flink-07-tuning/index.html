    Flink（七）反压与性能调优

    📅 2023-08-14

    反压与性能调优

    实时作业跑着跑着延迟越来越大、Kafka 位点停滞，多半是链路出现了反压：下游算不动，缓冲区堆满，上游被卡住，压力一直传回到 Source。调优的第一步不是盲目加机器，而是先定位瓶颈算子，再按内存、序列化、并行度逐项排查。这一篇讲反压的传播规律、定位手段、TaskManager 内存模型和常见调优点。

    算子链路上某段压力堆积成增厚的青色流带，下方是分层内存板与一排横向扩容的并行槽位

    1.1 反压是怎么产生与传播的

    数据在算子之间通过缓冲区传递。下游处理速度低于上游生产速度时，下游缓冲区被填满，上游拿不到空缓冲区就被阻塞；上游被阻塞后又拖住更上游，压力逐级向上传播，最终 Source 消费停滞。这就是反压（Backpressure）。

    环节
    积压表现
    常见根因
    下游算子
    缓冲区满、busy 高
    计算重、外部查询慢、状态太大
    网络传输
    输出缓冲占满
    记录过大、序列化开销高、带宽不足
    上游算子
    被动等待空缓冲
    被下游反压，自身未必有问题
    Source
    位点停滞、消费滞后
    链路整体反压传导到入口

    反压是链路的自我保护机制，不是错误；要解决的是”哪个算子是瓶颈”。盲目调大上游并行度只会让更多数据堆到瓶颈后面。

    1.2 定位反压：看 Web UI 与指标

    Flink Web UI 的作业页面按算子展示背压状态、忙闲比例和缓冲占用：

    指标
    含义
    判读
    Backpressure
    算子线程被下游阻塞的比例
    HIGH 说明被反压严重，顺链路找瓶颈
    Busy
    算子线程在真正计算的比例
    高而无反压，说明计算本身是瓶颈
    Idle
    线程空闲等待比例
    持续高空闲，可能上游断流或分区倾斜
    Input / Output Buffer
    收发缓冲占用
    输出缓冲持续满，下游消费不动

    定位顺序：从 Source 往后看，第一个 busy 高、输出缓冲堆积的算子就是瓶颈；它上游的高反压是被连累的，不要在那里调优。除了 UI，还可以看消费延迟、记录吞吐量、GC 停顿和 RocksDB 读写指标，互相印证。

    1.3 TaskManager 内存模型

    调内存前先分清 TM 进程里几块内存各管什么，否则加了总量还是 OOM：

    内存区
    用途
    调优方向
    JVM Heap
    用户对象、状态堆存、批量处理
    状态对象大、批量大时上调
    Managed Memory
    RocksDB 本地存、排序批处理
    RocksDB 后端占大头，按状态规模配
    Network Memory
    算子间传输缓冲
    记录大、并发高时增加网络缓冲
    Off-Heap
    原生内存、堆外缓存
    外部客户端、异步框架占用
    # taskmanager 内存配置：先定进程总量，再按状态类型切分
taskmanager:
  memory:
    process:
      size: 4096mb              # 进程总内存上限
    network:
      min: 256mb                # 网络缓冲，大记录/高并发适当上调
    managed:
      min: 1024mb               # RocksDB 与批处理可用的托管内存

    常见错误是状态全放堆内存，快照和大对象直接撑爆 Heap；大状态走 RocksDB 后，堆压力下降，瓶颈转移到本地磁盘读写。

    稳定性配置和内存同样相关，重启策略决定作业失败后怎么拉起：

    策略
    行为
    适用
    固定延迟重启
    失败后间隔固定时间重试，限制总次数
    偶发外部抖动、测试作业
    失败率重启
    单位时间内失败超阈值才放弃
    生产长作业，避免反复重启
    不重启
    失败即停，交给外部调度拉起
    批量补数、一次性任务

    重启次数与间隔要和检查点间隔配合：重启后从最近检查点恢复，恢复时长取决于状态大小；状态越大，单次重启成本越高，不能只靠”失败自动拉起”兜底。

    1.4 序列化与数据倾斜

    吞吐问题里，序列化和倾斜占了很大比例：

    • 序列化：Flink 用类型信息生成高效序列化器；POJO 字段公开、有无参构造时走 POJO 序列化，开销低。混用泛型、闭包、不可识别类型会退到 Kryo，序列化体积和 CPU 都上涨。日志里出现 Kryo 序列化提示，要回头检查数据类型定义。
    • 记录体积：一条记录带大量未使用字段，网络与状态存储都跟着膨胀，先裁剪字段再谈扩容。
    • 数据倾斜：热点 key 集中到个别 SubTask，其他子任务空闲。表现为个别 Slot 负载极高、反压卡在同一算子。先按 key 统计分布，再用加随机前缀、拆分热点、局部扩并行度处理，不能简单全链路加并行度。

    1.5 并行度与槽位共享

    并行度调优要结合槽位共享一起看：

    手段
    效果
    注意
    提高并行度
    算子拆更多子任务，分摊负载
    只对瓶颈算子提，避免全链路盲目扩
    槽位共享
    轻量算子挤进同一 Slot，省资源
    重状态算子单独 slotSharingGroup
    禁用链式
    算子隔离线程与缓冲
    隔离有成本，默认链式最优
    资源均衡
    重算子分散到不同 Slot / 机器
    避免一个槽位堆多个大状态算子

    经验顺序：先定位瓶颈算子 → 判断是计算重、状态大还是外部查询慢 → 针对性提并行度或隔离资源 → 再核对内存与序列化。顺序反了，加机器和加内存都可能看不到收益。

    1.6 常见易错点

    • 看到反压就给 Source 加并行度，瓶颈在下游，上游扩了只会堆更多数据。
    • 状态全压堆内存，RocksDB 没用上，快照时 OOM。
    • 类型不可识别退到 Kryo，序列化开销翻倍却没被注意到。
    • 热点 key 不拆分，个别 Slot 跑满，集群整体利用率很低。
    • 网络缓冲给太小，大记录传输时缓冲反复申请释放，吞吐上不去。
    • 检查点间隔过短，快照抢占计算资源；过长则故障后重放与恢复成本升高。
    • 只看吞吐不看缓冲占用，反压初期被忙闲指标掩盖，等到积压明显才介入。

    1.8 清单

    1. 反压由下游慢引起，逐级向上传播到 Source；反压是保护机制，定位瓶颈算子才是关键
    2. UI 看 Backpressure、Busy、Idle 与缓冲占用；第一个 busy 高、输出堆积的算子才是瓶颈
    3. TM 内存分 Heap、Managed、Network、Off-Heap，各管一块，大状态用 RocksDB 吃托管内存
    4. 序列化优先 POJO，退到 Kryo 要回头查类型；记录裁剪后再谈扩容
    5. 倾斜先查 key 分布，热点拆分或局部扩并行度，不要全链路盲目提并行度
    6. 调优顺序：定位瓶颈 → 判断根因（计算/状态/外部查询）→ 调并行度与资源 → 核对内存序列化
