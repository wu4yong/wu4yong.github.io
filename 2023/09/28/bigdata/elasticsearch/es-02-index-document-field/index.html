    ES02-核心概念

    📅 2023-09-28

    索引、文档、字段、映射：数据模型三件套

    上一讲把「它是什么」钉住了，这一讲把「它怎么存」钉住。

    建模错了，后面调什么参数都白搭——Elasticsearch 里最常见的返工不是查得慢，而是字段类型当初选错，只能重建索引。

    图的读法：外层是 index（命名空间），中层是 document（可检索的最小单位），内层是 field（键值对）；右侧 mapping 决定每个字段的类型与索引方式｜依据 Elasticsearch 官方文档 8.17 自绘

    一、学习目标

    1. 说清 index、document、field、mapping 四者的层级关系，以及 _id 的唯一性范围；
    2. 记住官方给出的 mapping 定义，并解释「一个索引只有一份 mapping」意味着什么；
    3. 说清 text 与 keyword 在检索、排序、聚合三种能力上的差别，并能据此选型；
    4. 独立写出一个带显式 mapping 的建索引请求，并用 _mapping、_source 验证结果；
    5. 说出四条「mapping 一旦写错就很难救」的具体限制。

    三、理论讲解：官方怎么定义这四层

    The index is the fundamental unit of storage in Elasticsearch, a logical namespace for storing data that share similar characteristics. … An index is a collection of documents uniquely identified by a name or an alias.

    Elasticsearch serializes and stores data in the form of JSON documents. A document is a set of fields, which are key-value pairs that contain your data. Each document has a unique ID, which you can create or have Elasticsearch auto-generate.

    Each index has a mapping or schema for how the fields in your documents are indexed. A mapping defines the data type for each field, how the field should be indexed, and how it should be stored.

    ——Elastic 官方文档《Elasticsearch basics》

    三句话，三个硬信息：

    1. index 是逻辑命名空间，不是一个目录、也不是一张表；它靠名字或别名被定位，所以名字一旦定下，就是对外契约的一部分。
    2. document 是 JSON，field 是键值对；文档不必字段对齐——A 文档有 price、B 文档没有，这是允许的。
    3. 一个 index 只有一份 mapping，它规定每个字段类型、怎么索引、怎么存储三件事。

    第三句是整门课的分水岭。它意味着：

    推论
    直接后果
    什么时候会咬你
    索引级 schema
    同一索引里不能出现「同名字段、不同类型」
    两个系统往同一索引写数据，一边写字符串一边写数字，直接 mapper_parsing_exception
    类型不可改
    想从 text 改 keyword 只能新建索引 + reindex
    上线三个月后发现要按标题排序
    结构决定能力
    mapping 决定能不能搜、能不能排、能不能聚合
    选型阶段没想清楚，后面全是补丁

    3.1 文档长什么样：元数据字段

    一条索引后的文档，除了你自己写的业务字段，还有一组下划线开头的元数据字段（官方称 metadata fields）：

    元数据字段
    含义
    官方要点
    _index
    文档所在索引名
    检索结果里用于区分来源索引
    _id
    文档 ID
    官方明确「IDs must be unique per index」，索引内唯一
    _source
    写入时那份原始 JSON
    可关闭、可按 includes / excludes 裁剪
    _routing
    自定义路由值
    默认按 _id 计算，改了会影响分片落点
    _version
    版本号
    同 ID 覆盖时自增（并发控制见 M3-4）

    最容易误解的是 _source：它只是被存下来的那份原始 JSON，用于返回给调用方和 reindex。能不能被搜到，靠的是倒排索引；能不能排序聚合，靠的是 doc values。三者是三套东西，M1-1 第四章已经埋过这条线。

    3.2 字段类型：官方类型清单里常用的那几类

    官方把字段类型分成好几组（文本、数值、日期、布尔、对象与关系、地理、向量等）。这一讲只抓建模最常用的八类，其余在 M2-2 逐个展开：

    类型
    典型用途
    关键能力/限制
    text
    标题、正文、商品描述等需要分词的字段
    能全文检索，不能直接排序/聚合
    keyword
    标签、状态、邮箱、ID 等精确值
    能精确匹配、排序、聚合，不分词
    long / integer / double / float
    数值、价格、数量
    支持范围查询与数值聚合
    date
    时间戳
    支持范围查询与 date_histogram
    boolean
    真假值
    支持 term 过滤
    object
    嵌套对象（扁平化存储）
    子字段可用，但父子关系会丢
    nested
    数组里的对象要保持独立
    每个对象独立索引，查询要用 nested 查询
    geo_point
    经纬度
    支持距离、矩形、多边形查询

    object 与 nested 的差别常被忽略：对象数组扁平化后，[{"a":1,"b":2},{"a":3,"b":4}] 会被存成 a=[1,3]、b=[2,4]，于是 a=1 AND b=4 也能命中——这是官方在设计上就写明的行为，不是 bug，需要对象级独立性就用 nested。

    3.3 一个字段，两种用法：multi-fields

    官方给出的标准解法是给同一个字段挂子字段（fields），典型是「text 负责搜、keyword 子字段负责排和聚合」：

    "title": {
  "type": "text",
  "fields": {
    "keyword": { "type": "keyword", "ignore_above": 256 }
  }
}

    写入一份数据，两份索引结构，检索走 title，排序聚合走 title.keyword。ignore_above 是官方参数：超过长度的值不进 keyword 索引（避免超长字符串把索引撑爆）。

    四、原理拆解：mapping 是怎么决定「能不能搜 / 能不能排 / 能不能聚合」的

    一张官方能力矩阵（这一讲先建立直觉，M2-2 讲原理）：

    字段类型
    全文检索
    精确匹配
    排序
    聚合
    text
    能（分词后匹配）
    不能（除非配 keyword 子字段）
    不能
    不能
    keyword
    不能（整串当一个词条）
    能
    能
    能
    数值 / date
    不能（按值比较）
    能（term、range）
    能
    能
    boolean
    不能
    能
    能（少用）
    能（少用）

    底层原因只有一条：不同索引结构服务不同操作。

    • 全文检索要「词条 → 文档」，所以 text 必须建倒排索引，且必须分词；
    • 排序与聚合要「文档 → 该字段的值」按列读取，所以要有 doc values（列式存储）；
    • text 为了控制体积默认不建 doc values，于是它天然排不了、聚合不了。

    所以「为什么 text 排序报错」不是权限问题，是结构问题。这条因果链要背下来，选型时能省无数时间。

    五、场景说明：三种典型建模

    场景
    主键怎么写
    关键字段设计
    要避开的坑
    商品检索
    _id 用商品 ID
    title(text + keyword 子字段)、price(scaled_float 或 integer 分)、tags(keyword)、desc(text)
    价格用 float 做区间过滤会有精度漂移
    日志检索
    让 ES 自动生成 _id
    @timestamp(date)、message(text)、service.name(keyword)
    别把整条日志塞进一个 text 还指望聚合
    知识库/文档检索
    _id 用文档编号
    title(text)、content(text)、category(keyword)、updated_at(date)
    正文与标题共用一个字段，相关度会被长文稀释

    六、实操：从建索引到验证 mapping

    6.1 建一个带显式 mapping 的索引

    curl -X PUT "http://localhost:9200/books" \
  -H 'Content-Type: application/json' -d '
{
  "settings": { "number_of_shards": 1, "number_of_replicas": 0 },
  "mappings": {
    "properties": {
      "title":  { "type": "text", "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } } },
      "author": { "type": "keyword" },
      "price":  { "type": "scaled_float", "scaling_factor": 100 },
      "publish_date": { "type": "date" },
      "tags":   { "type": "keyword" }
    }
  }
}'

    scaled_float + scaling_factor: 100 是官方给金额的推荐写法：内部按整数存，避免浮点误差；number_of_replicas: 0 只用于单节点本地环境，生产至少 1（M6-2 讲副本语义）。

    6.2 写入并回看 mapping

    curl -X PUT "http://localhost:9200/books/_doc/1" -H 'Content-Type: application/json' -d '
{ "title": "Elasticsearch 系统课", "author": "wu4yong", "price": 89.0,
  "publish_date": "2023-09-25", "tags": ["search", "lucene"] }'

curl -s "http://localhost:9200/books/_mapping"

    _mapping 返回的就是当前真实结构——以它为准，不要以你脑中的设计为准。如果这里出现了你没写过的字段，说明动态映射悄悄加了字段（下一讲 M2-6 讲怎么禁）。

    6.3 验证「搜用 text、排和聚合用 keyword」

    # 全文检索：走 text
curl -s -X GET "http://localhost:9200/books/_search" -H 'Content-Type: application/json' -d '
{ "query": { "match": { "title": "系统课" } } }'

# 排序：必须走 keyword 子字段
curl -s -X GET "http://localhost:9200/books/_search" -H 'Content-Type: application/json' -d '
{ "query": { "match_all": {} }, "sort": [ { "title.keyword": "asc" } } ] }'

# 聚合：也必须走 keyword 子字段
curl -s -X GET "http://localhost:9200/books/_search" -H 'Content-Type: application/json' -d '
{ "size": 0, "aggs": { "by_author": { "terms": { "field": "author" } } } }'

    如果第二条把 title.keyword 换成 title，官方会直接报 Fielddata is disabled on text fields by default——这条报错原文值得记住，它出现的频率极高。

    6.4 看 _source 到底是什么

    curl -s "http://localhost:9200/books/_doc/1"

    返回的 _source 就是你写进去的那份 JSON，字段顺序、嵌套结构都在；但它不等于索引结构。想把 _source 关掉（只要检索不要原文档）在 mapping 里设 "_source": { "enabled": false }，代价是失去 reindex 与返回原文的能力。

    七、常见坑（每条都有官方依据）

    1. 同名字段两种类型：一个索引一份 mapping，第二条文档把 price 写成 "89" 字符串，直接 mapper_parsing_exception。
    2. text 直接排序或聚合：官方默认 fielddata 关闭，报 Fielddata is disabled on text fields by default；正确做法是喂 keyword 子字段。
    3. 字段类型改不了：官方没有「改 mapping 类型」的接口，只能新建索引 + _reindex（M3-6）。
    4. 动态映射悄悄加字段：字段数会持续增长，官方有 index.mapping.total_fields.limit（默认 1000）这类上限，撞上就是写不进去（M2-6 细讲）。
    5. 对象数组用 object 却按「对象级独立」写查询：扁平化后跨对象误命中，需要 nested。
    6. 金额用 float：二进制浮点误差会让 range 过滤出现「89.99 不匹配 89.99」的怪现象，用 scaled_float 或整数分。
    7. _source 当成权威数据源：它可以关闭、可以裁剪，不能当备份。

    八、课后小结

    1. index 是逻辑命名空间，document 是 JSON，field 是键值对，mapping 是索引级结构定义。
    2. _id 在索引内唯一，同 ID 重写是覆盖。
    3. mapping 决定三件事：类型、怎么索引、怎么存，一旦定型就极难改。
    4. text 管搜，keyword 管精确匹配/排序/聚合；一个字段两种用法用 fields 子字段。
    5. 排序聚合依赖 doc values，text 默认没有，所以报错不是配置问题而是结构问题。
    6. 元数据字段里 _source 是存储、不是索引，别把它当备份。

    九、思考题

    1. 一个索引里，A 系统写 "amount": 10（数字），B 系统写 "amount": "10.5"（字符串），会发生什么？给出两种解法各自的代价。
    2. 商品描述要做全文检索，还要按描述长度分桶统计。你会怎么设计字段？为什么不能只用一个 text？
    3. object 与 nested 在存储和查询上分别差在哪？给出一个必须用 nested 的例子。
    4. 如果业务方要求「索引建好后随时能加字段并立即生效」，你会答应吗？从官方限制角度说明风险。
