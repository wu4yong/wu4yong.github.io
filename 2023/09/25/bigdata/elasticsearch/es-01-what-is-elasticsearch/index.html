    ES01-能力边界

    📅 2023-09-25

    它是什么：官方定位、能力边界与最小概念闭环

    本节不写代码细节，先把三件事钉死：
    它是什么（官方定义）、它的概念模型长什么样（index / document / field / mapping）、以及一条数据从写进去到能被搜到发生了什么。
    这三件事理不清，后面所有「为什么搜不到」「为什么分片分配失败」「为什么聚合慢」都会变成玄学。

    本章要建立的三层认知：倒排索引（存什么）、集群分片（放在哪）、检索链路（怎么取）｜依据 Elasticsearch 官方文档 8.17 自绘

    一、学习目标

    学完这一讲，你应当能：

    1. 用官方原文说清 Elasticsearch 的定位，并说出「分布式检索引擎」「可扩展数据存储」「向量数据库」三个身份各自的含义；
    2. 讲清 index、document、field、mapping、_id 五个概念的关系，以及它们与关系型数据库的对应与不对应之处；
    3. 独立起一个本地单节点，完成「写入 → 取回 → 检索」的最小闭环；
    4. 解释「刚写进去为什么搜不到」，并把原因定位到 refresh 机制上，而不是猜分词；
    5. 说出至少四条官方明确写下的限制，避免在建模阶段就埋坑。

    二、前置知识

    需要掌握
    具体到什么程度
    为什么这一讲就要
    JSON
    会写嵌套对象与数组
    ES 的文档就是 JSON，字段类型由 JSON 值推断
    HTTP / REST
    知道 GET、PUT、POST、DELETE 与状态码含义
    所有操作都是 REST 请求，没有 SQL 客户端那一套
    「索引」一词的双重含义
    知道数据库里的索引是 B+ 树加速结构
    ES 的 index 是逻辑命名空间，不是加速结构，混淆会全程误解
    Lucene
    知道它是 Java 写的检索库即可
    ES 的倒排索引、段文件、BM25 全部来自 Lucene

    最后一条特别提醒：本课程里出现的「索引」有两种含义——Elasticsearch 的 index（一批同类文档的集合）和Lucene 的倒排索引（词条到文档的数据结构）。看到「建索引」指的是前者，看到「倒排索引」指的是后者。

    三、理论讲解：官方怎么定义它

    先看官方原文，这段是整门课的地基：

    Elasticsearch is a distributed search and analytics engine, scalable data store, and vector database built on Apache Lucene. It’s optimized for speed and relevance on production-scale workloads. Use Elasticsearch to search, index, store, and analyze data of all shapes and sizes in near real time.

    Elasticsearch is the heart of the Elastic Stack.

    ——Elastic 官方文档《Elasticsearch basics → What is Elasticsearch?》（8.17）

    逐句拆开，官方给的是四个身份，不是「一个搜索引擎」这么简单：

    身份
    官方原词
    落到实际的含义
    分布式检索引擎
    distributed search and analytics engine
    请求可以打到任意节点，检索与聚合在多个分片上并行完成再归并
    可扩展数据存储
    scalable data store
    它能存原始文档（_source），能扩容，但不是事务型主库
    向量数据库
    vector database
    支持 dense_vector / knn 检索，可做语义检索与 RAG
    Lucene 之上
    built on Apache Lucene
    倒排索引、段文件、BM25 打分都是 Lucene 的能力，ES 加的是分布式与 REST 层

    「optimized for speed and relevance」是它的设计目标：快和相关性。不是「一致性最强」，也不是「事务最全」。这四个字决定了后面所有取舍——为检索速度牺牲写后立即可见（NRT），为相关性引入打分与分词。

    3.1 数据模型三件套：官方定义

    The index is the fundamental unit of storage in Elasticsearch, a logical namespace for storing data that share similar characteristics. … An index is a collection of documents uniquely identified by a name or an alias.

    Elasticsearch serializes and stores data in the form of JSON documents. A document is a set of fields, which are key-value pairs that contain your data. Each document has a unique ID, which you can create or have Elasticsearch auto-generate.

    ——同上《Indices, documents, and fields》

    三层关系：index（命名空间）→ document（JSON 文档）→ field（键值对）。再加两个官方概念：

    • _index：文档所在的索引名，元数据字段；
    • _id：文档 ID，官方明确「IDs must be unique per index」，即在同一个索引内唯一。
    Elasticsearch
    关系型数据库
    关键差异
    index
    库 + 表（合体）
    一个 index 只有一种文档结构，没有「表」这一层（7.x 起 type 取消）
    document
    一行记录
    JSON，可嵌套、可数组，字段不必对齐
    field
    一列
    类型由 mapping 定义，不是由建表语句定义
    mapping
    表结构 + 索引策略
    决定「怎么分词、能不能聚合、能不能排序」
    _id
    主键
    同 ID 再写一次是覆盖，不是报主键冲突

    「没有表这一层」是 7.x 的重大变化：早期版本有 type 概念，7.x 废弃、8.x 彻底移除。所以看到老教程里 PUT /索引/类型/文档ID 的三段路径，要知道第二段现在的固定值就是 _doc。

    3.2 mapping 的两种建法，官方直接给了取舍

    Dynamic mapping: Let Elasticsearch automatically detect the data types and create the mappings for you. Dynamic mapping helps you get started quickly, but might yield suboptimal results for your specific use case due to automatic field type inference.

    Explicit mapping: Define the mappings up front by specifying data types for each field. Recommended for production use cases, because you have full control over how your data is indexed to suit your specific use case.

    ——同上《Mappings and data types》

    这段话是官方自己给的结论，不是我的经验：生产用显式 mapping。原因很硬——一个字符串字段一旦被推断成 text（分词），它就不能直接排序、不能精确匹配；反过来被推断成 keyword 后又要全文检索，只能重建索引。M2 会专门用一讲讲透映射设计。

    四、原理拆解：为什么它「搜得快、聚合也快」

    四个关键词，逐个拆：

    第一，倒排索引解决「搜得到」。
    正排是「文档 → 内容」，倒排是「词条 → 文档列表」。官方在全文检索的定义里写得很清楚：full-text search 依赖 inverted indexes, tokenization, and text analysis。写入时把字段切成词条，检索时直接拿词条查表，避免全表扫描。这也是为什么分词错了就搜不到——不是查询写错，是词条压根没进表。

    第二，同一份数据结构解决「聚合快」。
    官方原文：Because aggregations leverage the same data structures used for search, they are also very fast. 聚合不是「另起一套计算」，它复用检索用的列式结构（doc values），所以才能在同一个请求里既过滤又统计。这也解释了「为什么 text 字段聚合会报错」——text 没有 doc values，而 keyword 有。

    第三，near real time 是官方定位里的原词。
    不是 real time，是 near real time。写入先落内存缓冲与 translog，必须经过 refresh 才对搜索可见，index.refresh_interval 默认是 1s。所以「写完立刻查不到」是设计行为，不是 bug。这就是 1.5 秒现象的全部原因，M3-2 会讲透 refresh / flush 的区别。

    第四，分布式决定了「打分是局部的」。
    一个索引被切成若干主分片，每个主分片有副本；请求打到任意节点后，查询被广播到每个分片，各分片在本分片内打分并返回候选，协调节点再全局归并。这带来两个直接后果：分片数影响长尾耗时；跨分片分数不可直接比较。M4、M6 展开。

    五、场景说明：官方列的三条产品线

    官方把用途分成三大类，注意这些都是官方列出的场景，不是营销话术：

    产品线
    官方列举的典型场景
    关键能力依赖
    Observability
    日志、指标、链路追踪；APM；RUM；OpenTelemetry 接入
    data stream + 时间序列聚合
    Search
    全文检索；向量检索；语义检索；混合检索；地理检索；RAG 检索底座
    倒排索引 + 向量 + 打分
    Security
    SIEM；终端安全；威胁狩猎
    EQL（事件查询语言）+ 大规模写入

    那它不适合做什么？这里有两条必须分清性质：

    1. 官方层面：ES 的 API 里没有跨文档事务的概念，只有单条文档写入的原子性（M3-4 讲 _seq_no 与乐观并发时会带出这个边界）。要强一致、多行事务、复杂外键关联，那是关系库的活。
    2. 工程结论（非官方原文）：把 ES 当「唯一主库」用，是把检索副本当权威数据源，一旦重建索引（reindex / 改 mapping）就会暴露数据不可再生的问题。行业通行做法是「关系库或消息队列做权威源，ES 做可重建的检索副本」。

    两句话分开写，是因为第二条是我的工程判断，不能冒充官方规定。

    六、实操：十分钟跑通最小闭环

    6.1 起一个本地单节点

    docker run -d --name es01 \
  -p 9200:9200 \
  -e "discovery.type=single-node" \
  -e "xpack.security.enabled=false" \
  -e "ES_JAVA_OPTS=-Xms1g -Xmx1g" \
  docker.elastic.co/elasticsearch/elasticsearch:8.17.0

    三个参数都不是可选项：

    参数
    作用
    不设的后果
    discovery.type=single-node
    单节点模式，跳过选主组集群
    单机启动后会一直尝试发现其他节点，日志刷选举失败
    xpack.security.enabled=false
    关闭 8.x 默认开启的安全能力
    8.x 默认启用 TLS 与认证，curl http:// 直接连不上
    ES_JAVA_OPTS
    固定堆大小
    默认按宿主机内存推算，容易与 Docker 抢内存

    注意：xpack.security.enabled=false 只能用于本地学习。8.x 起官方默认开启安全，生产环境关掉它会触发启动阶段的 bootstrap checks 校验失败，M8-1 专门讲安全基线。

    6.2 探活

    curl -s http://localhost:9200

    返回里关键三行："name"（节点名）、"cluster_name"、"version.number"（确认是 8.17.x，版本对不上后面所有参数都可能不一样）。

    6.3 写入第一条文档

    curl -X PUT "http://localhost:9200/books/_doc/1" \
  -H 'Content-Type: application/json' -d '
{
  "title": "Elasticsearch 系统课",
  "author": "wu4yong",
  "publish_date": "2023-09-25",
  "price": 89.0,
  "tags": ["search", "lucene"]
}'

    返回里有三个字段值得看：result: created（新建；同 ID 再写会变成 updated）、_version: 1、_seq_no（后面讲并发控制就靠它）。

    6.4 取回与检索

    # 按 ID 取回整条文档
curl -s "http://localhost:9200/books/_doc/1"

# 全文检索 title
curl -s -X GET "http://localhost:9200/books/_search" \
  -H 'Content-Type: application/json' -d '
{ "query": { "match": { "title": "系统课" } } }'

    match 会先对查询词做同样的分析，再匹配倒排词条。中文没装分词插件时按单字切，所以「系统课」能命中——但这也意味着一堆不相干的单字也会命中，这是 M2-4 要处理的问题。

    6.5 观察 NRT：写完立刻查不到

    # 强制刷新，让刚写的文档立即可见（仅测试用）
curl -s -X POST "http://localhost:9200/books/_refresh"

# 再查一次，结果稳定包含新文档
curl -s "http://localhost:9200/books/_count"

    刷新周期是 1 秒，所以「刚写完立刻搜」在 1 秒窗口内确实搜不到。不要在生产里每条写入都带 refresh=true——每次强制刷新都生成新段，段越多检索越慢，这是官方文档反复强调的写入侧开销来源，M3-2 详述。

    「写成功」与「搜得到」是两件事：返回 201 只代表已进 translog，能否被搜到取决于 refresh｜依据 Elasticsearch 官方文档 8.17 自绘

    6.6 与 Kibana Dev Tools 的等价写法

    官方入门示例用的是 Kibana 的 Dev Tools Console，写法更省事：不用写 curl、不用带 Content-Type，直接

    PUT /books/_doc/2
{ "title": "Elasticsearch 系统课（二）", "price": 99.0 }

GET /books/_search
{ "query": { "match": { "title": "系统课" } } }

    两种写法打到的是同一批 REST 接口，本课程统一用 curl，方便直接搬进脚本。

    七、常见坑（每条都有官方依据）

    1. 写完立刻查不到：这是 NRT 的设计，不是分词问题。默认 refresh_interval 是 1s，需要即时可见才用 _refresh，且只在测试与数据校验时用。
    2. 生产用动态映射：官方原文明确 dynamic mapping「might yield suboptimal results」，并且推荐生产用 explicit mapping。第一条文档的字段类型会被固化，改类型只能重建索引。
    3. 以为同 _id 写入是「插入」：官方定义 _id 在索引内唯一，重复写入是同 ID 覆盖（result 从 created 变 updated），不是报错。想要冲突检测得用 op_type=create。
    4. 把 _source 当权威副本：_source 只是「存下来的那份 JSON」，官方允许关闭或裁剪（includes / excludes）。真正决定能否被检索的是倒排索引，不是 _source。
    5. 想给索引或字段改名：ES 没有「rename index」接口，改结构只能新建索引 + _reindex（M3-6 专讲）。
    6. 8.x 直接 curl http://localhost:9200：8.x 默认开启 TLS 与认证，正确姿势是 https:// + 账号密码或 API key；用 -k 跳过证书校验只适合自签名的本地环境。
    7. 把 ES 当唯一主库扛事务：官方 API 里没有跨文档事务（工程结论：需要事务的部分留给关系库，ES 只做可重建的检索副本）。
    8. from + size 翻深页：index.max_result_window 默认 10000，超过直接报错，且越翻越慢；正确做法是 search_after 或 scroll（M4-7）。

    八、课后小结

    1. 官方给的是四个身份：分布式检索引擎、可扩展数据存储、向量数据库、Lucene 之上——四个身份决定了它的强项与边界。
    2. 数据模型是 index → document → field，_id 在索引内唯一，重复写入是覆盖。
    3. mapping 是「表结构 + 索引策略」，官方明确生产用显式映射。
    4. 倒排索引管「搜得到」，doc values 管「聚合快、排得动」，两者不是一回事。
    5. near real time 是官方定位原词：写入后需 refresh 才可见，默认 1s。
    6. 打分在分片内完成、再全局归并，这是分布式检索的性能与正确性根源。
    7. 8.x 默认开启安全，本地关闭的配置不能照搬上生产。

    九、思考题

    1. 一条文档写入 books 索引后 3 秒才被搜到，另一条在 0.2 秒内就被搜到。在不改任何配置的前提下，解释这两者的差异可能来自哪些因素？（提示：refresh 是周期性的，不是每条都刷）
    2. 如果把一个「商品标题」字段用动态映射写成 text，之后要做「按标题精确排序 + 按标题前缀聚合」，你会怎么补救？给出两条路径并说明代价。
    3. 官方说聚合复用检索的数据结构所以快，那为什么对 text 字段做 terms 聚合会失败？这条限制属于「能力缺失」还是「设计取舍」？
    4. 你的业务要求「下单成功后 100ms 内必须能按订单号查到」。这个需求该落到 ES 还是关系库？如果一定要在 ES 里满足读侧，架构上你会怎么做？
