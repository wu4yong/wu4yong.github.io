    Flink（三）状态与容错

    📅 2023-07-22

    状态与容错

    流处理不能只看”这条数据怎么算”，还要记住”之前见过什么”：去重集合、累计计数、窗口里攒下的明细，都是状态。状态丢了，重算结果就对不上；状态太大，内存和恢复时间又扛不住。这一篇讲清楚状态的分类、存储后端、快照机制，以及端到端 Exactly-Once 在 Sink 侧是怎么落地的。

    分层透明快照板叠在状态存储立方体之上，每块快照由发光的两阶段锁封住

    1.1 为什么状态是运行时内建能力

    无状态作业挂了可以重放数据从头算；有状态作业不行——已经累加过的计数、已经判重过的记录，重放会重复计入。所以容错的核心问题是：在不停止处理的前提下，周期性地拿到一份一致的状态副本，故障时从副本恢复。

    Flink 把状态托管在运行时里，业务代码通过状态描述符（StateDescriptor）读写，不需要自己找 Redis 或数据库存中间结果。这样做的好处是快照、恢复、TTL 清理都由框架统一接管。

    1.2 Keyed State 与 Operator State

    状态按绑定范围分两类：

    类别
    绑定范围
    典型形态
    适用场景
    Keyed State
    绑定到 key，每个 key 一份
    ValueState、ListState、MapState
    按用户、按商品聚合去重
    Operator State
    绑定到算子并行子任务，与 key 无关
    ListState、BroadcastState
    Source 消费位点、路由表广播

    判断方法很简单：逻辑里先 keyBy 了，后面用的就是 Keyed State；没有分组、算子自己记一份全局信息，用的是 Operator State。Source 记 Kafka 消费位点、Broadcast State 下发配置规则，都是 Operator State 的典型用法。

    1.3 Keyed State 的几种类型

    类型
    存什么
    读写方式
    ValueState
    单个值
    value() / update()
    ListState
    一组元素
    add() / get() / update()
    MapState<K,V>
    键值集合
    put() / get() / entries()
    ReducingState
    折叠后的单值
    add() 时按 ReduceFunction 聚合
    AggregatingState<IN,OUT>
    输入进、聚合结果出
    与 ReducingState 类似，输入输出可不同类型

    一个 ValueState 的最小写法：

    ValueStateDescriptor<Long> desc =
        new ValueStateDescriptor<>("order-count", Long.class);
ValueState<Long> countState = getRuntimeContext().getState(desc);

Long current = countState.value();
countState.update(current == null ? 1L : current + 1);

    状态可以配 TTL（Time-To-Live），超过存活时间的条目自动清理，避免去重集合无限膨胀。TTL 基于事件时间或处理时间配置，清理策略分增量过期与全量过期，大状态要提前规划。

    1.4 StateBackend：状态存在哪

    StateBackend 决定状态的存储介质和快照落盘方式。1.13 主线的两类实现：

    后端
    介质
    适用场景
    HashMapStateBackend
    JVM 堆内存
    状态小、访问快，快照写远端文件系统
    EmbeddedRocksDBStateBackend
    本地 RocksDB，可溢出磁盘
    状态大、超过堆内存上限，支持增量快照
    # flink-conf.yaml：状态后端与检查点存储
state:
  backend: rocksdb                      # 大状态用 RocksDB，小状态可改 hashmap
  checkpoint:
    dir: oss://bucket/flink/checkpoints # 快照落远端存储，节点宕机不丢
    interval: 60000                     # 检查点间隔，按延迟与恢复成本权衡

    老教程里的 MemoryStateBackend、FsStateBackend、RocksDBStateBackend 是旧命名，新版本已合并成上面两类；线上大状态基本都选 RocksDB，代价是序列化访问比堆内存慢。

    1.5 Checkpoint：异步快照与屏障对齐

    Flink 的检查点基于 Chandy-Lamport 分布式快照算法。核心机制是在数据流里插入检查点屏障（Barrier），把流切成”快照前”和”快照后”两段：

    • JobManager 定时向 Source 注入屏障，屏障随记录向下游流动
    • 算子收到多个上游的屏障后先对齐：等所有上游屏障到齐，再对自己当前状态做快照
    • 快照默认异步进行：状态副本写到后端的同时，算子继续处理新数据，不阻塞流水线
    • 全部算子快照完成，这次检查点才算成功，JobManager 提交这次快照元数据

    对齐的作用是保证快照里不混入”部分上游已到、部分上游未到”的记录。 barrier 对齐期间算子会缓冲快分区的数据，反压严重时缓冲会涨。

    检查点是框架自动管理的内部恢复点，默认不对外保留；配置外部化检查点后，作业取消也能从最近检查点拉起。

    1.6 Savepoint 与作业升级

    Savepoint 是用户主动触发的、格式受版本兼容保证的快照，主要用于作业升级和迁移：

    用途
    说明
    修改作业逻辑
    从 savepoint 重启，延续已有状态
    调整并行度
    只要状态可重分区，可在 savepoint 基础上扩缩并行度
    迁移集群
    换 YARN / K8s / 换存储都可从 savepoint 恢复
    版本升级
    跨 Flink 小版本升级，优先走 savepoint 校验兼容性

    命令行触发与恢复的典型形式：

    # 主动做一次 savepoint
flink savepoint <jobId> oss://bucket/flink/savepoints

# 从 savepoint 恢复启动
flink run -s oss://bucket/flink/savepoints/savepoint-xxxx ./job.jar

    注意：状态结构改了（删了某个 state、改了 state 类型），直接从老 savepoint 恢复会报错；这类变更需要先做状态迁移或清空状态重启。

    1.7 Exactly-Once 与两阶段提交

    Checkpoint 只保证 Flink 内部状态一致，不等于端到端 Exactly-Once。结果已经写到外部系统后作业挂掉，重放会重复写。端到端一致性需要 Sink 配合实现两阶段提交（Two-Phase Commit, 2PC）：

    阶段
    动作
    失败影响
    预提交（Pre-commit）
    检查点快照时，Sink 把未提交数据暂存到外部事务
    预提交失败可丢弃，不影响外部可见数据
    提交（Commit）
    检查点对全部算子完成后，统一提交事务
    提交前故障，事务回滚，外部无重复写入

    这套机制的前提是 Sink 本身支持事务或两阶段提交协议，不是所有连接器都具备。以 Kafka 为例，2.0 之后的 KafkaSink 提供 DeliveryGuarantee.EXACTLY_ONCE，底层用事务生产者配合检查点提交；写文件、写 JDBC 的连接器若没有事务能力，只能做到 At-Least-Once，需要靠幂等写入或去重表兜底。

    1.8 常见易错点

    • 把 Checkpoint 当 Savepoint 用：检查点可能被框架清理，升级迁移必须用 savepoint。
    • 以为开了检查点就是端到端 Exactly-Once：Sink 不支持事务时，外部系统仍可能重复写。
    • 大状态选了堆内存后端，快照时直接 OOM；RocksDB 才是大状态的归宿。
    • 改了状态结构还从老快照恢复，启动阶段报状态不兼容。
    • 状态里存大对象、不设 TTL，去重集合随时间无限膨胀。

    • 状态架构文档：https://nightlies.apache.org/flink/flink-docs-release-1.13/docs/concepts/stateful-stream-processing/
    • State Backend 配置：https://nightlies.apache.org/flink/flink-docs-release-1.13/docs/ops/state/state_backends/
    • 检查点容错机制：https://nightlies.apache.org/flink/flink-docs-release-1.13/docs/concepts/checkpointing/
    • 两阶段提交 Sink：https://nightlies.apache.org/flink/flink-docs-release-1.13/docs/connectors/datastream/connectors/

    1.10 清单

    1. 状态分 Keyed State（绑 key）与 Operator State（绑算子子任务），通过 StateDescriptor 读写
    2. Keyed State 常用 Value / List / Map / Reducing / Aggregating 五种，大集合要配 TTL
    3. 后端分 HashMap（堆内存）与 EmbeddedRocksDB（磁盘溢出），大状态选 RocksDB
    4. Checkpoint 基于 Chandy-Lamport 快照，屏障对齐后默认异步快照，不阻塞持续处理
    5. Savepoint 用于升级、扩并行度、迁集群；状态结构变更需迁移或清空重启
    6. 端到端 Exactly-Once 依赖 Sink 的两阶段提交，Kafka 2.0+ 事务生产者支持；无事务能力的 Sink 只能幂等兜底
