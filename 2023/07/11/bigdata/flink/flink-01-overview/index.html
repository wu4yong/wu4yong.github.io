    Flink（一）架构与时间语义

    📅 2023-07-11

    架构与时间语义

    流计算和批计算最根本的差别，是数据”来不完”。一条订单流、一次点击流会一直滚动下去，作业必须边到边算，而不是等全部到齐。Flink 把这种”有状态的流式计算”做成了一套运行时框架，这一篇先把角色分工、资源单位和时间口径讲清楚，后面几篇再展开 API、状态与窗口。

    中央调度节点向后排工作节点分发数据流，每个工作节点内部是一格格并行槽位

    1.1 Flink 的定位：流批一体

    很多教程把 Flink 讲成”实时计算框架”，这个说法不算错，但漏掉了它现在的主线。从 1.12 起 Flink 把批处理当作流处理的一种特殊情况（有界流），DataStream API 与 Table API 逐步统一，一套作业可以同时跑无界流和有界批。理解 Flink 时建议按这个坐标系：

    概念
    含义
    落地形态
    流处理
    数据无界，逐条到达逐条计算
    实时指标、实时数仓、实时风控
    批处理
    数据有界，算完即结束
    离线补数、T+1 汇总，复用同一套 API
    有状态计算
    作业记住之前见过的数据
    计数、去重、窗口聚合、会话拆分
    事件时间
    以数据自带的时间戳为准
    乱流、延迟重放都能正确出结果

    和 Storm、Spark Streaming 这类早期框架相比，Flink 的两个硬特点值得记住：状态内建在运行时里，而不是靠外部存储拼出来；故障恢复基于快照，作业挂掉可以从最近一次一致状态续跑。这两点是后面容错一节的基础。

    1.2 运行时架构：JobManager 与 TaskManager

    一个 Flink 作业跑起来，集群里只有两类常驻进程，外加随作业生成的任务子任务。角色分工如下：

    角色
    职责
    数量
    JobManager
    作业调度、检查点协调、故障恢复、元数据管理
    每个作业一个（HA 下主备）
    TaskManager
    提供计算资源槽位，执行算子子任务，上报心跳与状态
    每个工作节点一个
    SubTask
    算子的并行实例，真正读写数据的执行单元
    由并行度决定
    Client
    解析作业图、提交到集群，本身不参与计算
    提交流程中短暂存在

    启动顺序是：Client 把用户代码翻译成执行图（ExecutionGraph）提交给 JobManager；JobManager 向 TaskManager 申请资源槽位，把 SubTask 部署进去；SubTask 之间通过网络交换数据，JobManager 定时触发检查点快照。

    JobManager 不碰业务数据，只做协调；真正的吞吐瓶颈几乎都在 TaskManager 这一侧。看集群问题时先分清”调度卡住”还是”计算积压”，方向就不会错。

    TaskManager 的资源在配置文件里按进程声明，槽位数直接决定单机能塞多少 SubTask：

    # taskmanager 配置：槽位与内存一起决定单机可承载的并行度
taskmanager:
  numberOfTaskSlots: 4          # 单机 4 个槽位，等于 4 份计算分片
  memory:
    process:
      size: 2048mb               # 进程总内存，按状态规模和批量大小调整

    一个集群能跑多大的并行度，是所有 TaskManager 槽位数之和；提交作业时申请的总槽位超过这个上限，SubTask 就会一直排队等待。

    1.3 并行度、子任务与 Slot

    Flink 里并行的最小单位是 SubTask，并行度（parallelism）就是某个算子起多少个 SubTask。资源的分配单位是 Slot（任务槽），一个 TaskManager 进程把自己的内存切成若干 Slot，每个 Slot 跑一个或多个 SubTask。

    概念
    是什么
    关键规则
    并行度
    算子并行子任务的数量
    可在代码、提交参数、配置文件三处覆盖
    Slot
    TaskManager 上的资源分片
    槽位之间内存隔离，CPU 不隔离
    Slot 共享
    同一链路不同算子的 SubTask 挤进同一个 Slot
    默认开启，避免算子之间空占资源
    资源槽位
    作业需要的总 Slot 数
    等于链路最大并行度，不是各算子并行度相加

    一段最小可跑的流作业骨架长这样：

    StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

env.setParallelism(4);                       // 全局默认并行度
env.enableCheckpointing(60_000);              // 每 60 秒做一次快照

env.addSource(new KafkaSource(...))
   .keyBy(Order::getUserId)
   .process(new OrderWindowProcessFunction())
   .addSink(new KafkaSink(...));

env.execute("order-realtime-job");

    这里要注意一个常见误区：Slot 共享不是”多任务争抢一份内存”。共享槽位内各 SubTask 各占自己的托管状态内存，只是把空闲 CPU 时间复用起来；真正需要独占资源的算子（比如状态很大的算子）可以单独禁用共享。

    1.4 三种时间语义

    窗口聚合、会话拆分这类逻辑必须回答一个问题：”按哪个时间算？”Flink 提供三种时间口径：

    时间类型
    取值依据
    适用场景
    主要风险
    事件时间（Event Time）
    数据自带的时间戳（如业务发生时间）
    乱序流、重放历史数据、结果可复现
    需要处理迟到与水位线
    摄入时间（Ingestion Time）
    数据进入 Flink 的机器时间
    简单场景，不要求结果可复现
    重放时结果会变
    处理时间（Processing Time）
    算子处理到这条数据时的本地时钟
    低延迟统计、对准确性要求不高
    受吞吐和排队影响，结果不稳定

    线上实时数仓、指标看板基本都用事件时间：同一份数据重放一遍，窗口边界和结果必须一致。处理时间只适合”看当下流量”这类容忍误差的场景。

    时间特征的设置在 1.13 主线已经简化：默认按事件时间处理，早期教程里的 setStreamTimeCharacteristic(...) 属于旧写法，新项目不要照搬；时间戳和水位线由 Source 或后续 assignTimestampsAndWatermarks 指定。

    1.5 Watermark 只推进事件时间

    水位线（Watermark）是事件时间体系里用来判断”数据该到齐了”的标记。它随数据流一起流动，水位线时间戳 W 表示：”事件时间不晚于 W 的数据，理论上已经到齐”。这里有一条容易被问住的口径：

    • Watermark 只推进事件时间，不推进处理时间。处理时间走的是算子本地时钟，和水位线没有关系。
    • 水位线是按算子链路上游各自计算的，下游取已收到水位线中的最小值，避免快分区提前关闭窗口。
    • 水位线可以停顿：上游某个分区长时间不来数据，整条链路的水位线就会卡住，窗口迟迟不触发。

    事件时间和处理时间混用是线上 bug 高发区：窗口按事件时间划，内部定时器却去读处理时间，一旦积压，两边口径对不上，结果就会飘。

    1.6 常见易错点

    • 把并行度当成”集群机器数”：并行度是 SubTask 数量，可以大于机器数，多个 SubTask 挤在同一台 TaskManager 的不同 Slot 里。
    • 以为 Slot 数等于算子并行度之和：开启槽位共享后，总 Slot 数取链路最大并行度。
    • 用处理时间做业务窗口，再拿历史数据回放校验，结果对不上是必然的。
    • 上游分区数据倾斜时，最慢的那个分区决定整条链路水位线，快分区会被拖住。

    • 并行执行文档：https://nightlies.apache.org/flink/flink-docs-release-1.13/docs/concepts/parallelization/

    1.8 清单

    1. Flink 现在的主线是流批一体，批是有界流，状态与快照内建在运行时里
    2. 运行时只有 JobManager（协调）和 TaskManager（干活）两类进程，SubTask 是真正执行单元
    3. 并行度决定 SubTask 数量，Slot 是资源分片，默认开启槽位共享，总 Slot 取链路最大并行度
    4. 时间口径分事件时间、摄入时间、处理时间；线上可复现的场景用事件时间
    5. Watermark 只推进事件时间，不推进处理时间；最慢分区决定链路水位线
    6. 混用两种时间口径是窗口结果漂移的常见原因，新项目按 1.13 主线写法，不照搬旧 API
