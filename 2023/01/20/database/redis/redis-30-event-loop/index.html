    redis-30-网络模型与事件循环

    📅 2023-01-20

    网络模型：从 epoll 到事件循环

    ae 事件循环的四步、io-threads 能并行什么、不能并行什么｜依据 Redis 7.4 官方文档与源码自绘

    一、学习目标

    学完这一讲，你能做到：

    1. 用「等待数据 / 拷贝数据」两个阶段，讲清 Linux 五种 IO 模型的区别；
    2. 讲清 select → poll → epoll 各自的结构与代价，以及 epoll 为什么不需要遍历；
    3. 画出 Redis 单线程网络模型的一次请求路径（ssfd → acceptTcpHandler → readQueryFromClient → pending_write）；
    4. 分清「IO 多线程」与「命令多线程」，判断自己的实例该不该开 io-threads。

    二、前置知识

    RD04（RESP 协议）、RD36（Pipeline 与 RTT）。本讲回答一个所有人都困惑过的问题：Redis 明明「单线程」，为什么还能扛十万 QPS？

    三、理论讲解（官方定义）

    官方对 6.0 引入 IO 多线程的说明（原文要点）：

    Redis 6.0 introduces threaded I/O … the main thread still executes commands … the threads are used to read from and write to sockets.

    —— https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/

    ae.c 对事件循环的定义（原文要点）：

    The ae event loop is a simple event-driven programming library … it can handle file events and time events.

    —— https://github.com/redis/redis/blob/7.4/src/ae.c

    Linux epoll 手册对「为什么快」的定义（原文要点）：

    The performance of epoll scales with the number of file descriptors that are ready, not with the total number that are being monitored.

    —— https://man7.org/linux/man-pages/man7/epoll.7.html

    三条定性：

    • 命令执行永远是主线程单线串行，这一点从 1.0 到 8.x 都没变；
    • 多线程只接管「socket 读写 + 协议解析 + 回复组装」，也就是 CPU 不重但量大的那部分；
    • 「快」来自多路复用，不来自线程数——一个线程能同时盯上万个 fd，才有后面的一切。

    四、原理拆解

    1. Linux 的五种 IO 模型

    任何一次网络读，都可以拆成两个阶段：

    1. 阶段一：等数据就绪——数据从网卡进到内核的 socket 接收缓冲；
    2. 阶段二：拷到用户空间——read 把内核缓冲里的字节复制到你的进程内存。

    五种 IO 模型的区别，全在这两个阶段上做文章：

    五种模型在「等待数据就绪」与「拷贝到用户空间」两个阶段的不同处理，以及 Redis 为什么停在「多路复用 + 阻塞拷贝」｜依据 epoll(7) 与 ae.c 自绘

    两句话概括这张图：

    • 同步/异步，看阶段二由谁做：自己调 read 就是同步，交给内核并等通知才是异步；
    • 阻塞/非阻塞，看阶段一进程在不在：睡着等是阻塞，转一圈回来问一次是非阻塞。

    Redis 没有走「异步 IO」那条路：它的阶段二仍然是阻塞拷贝，但因为「数据已在内存里、拷贝量小」，这个阻塞是纳秒到微秒级，换来的是实现极简——这是它敢用单线程的底气。

    2. 从 select 到 epoll：多路复用怎么演进

    select 的三个硬伤，正是 epoll 存在的理由：

    1. 监听上限 1024：fd_set 是定长位图，连接数一多就装不下；
    2. 每次调用都要全量拷贝：把整个 fd 集合从用户态拷进内核，再拷回来；
    3. 每次返回都要遍历：内核不知道「谁就绪」，只能挨个查，N 越大越慢。

    poll 只解决了第 1 点（改成数组/链表），第 2、3 点照旧——所以连接数上千后，poll 的耗时仍随 N 线性增长。

    epoll 换了个思路：把「查」变成「推」。

    • epoll_ctl 时给 fd 注册一个回调 ep_poll_callback；
    • 数据到达时内核主动调这个回调，把 fd 挂进就绪链表 rdllist；
    • epoll_wait 只把就绪链表里的 fd 拷回用户态，监听 1 万个 fd 和监听 10 个 fd，只要就绪数一样，耗时一样。

    3. epoll 的三段调用：fd、红黑树与 LT/ET

    aeApiPoll 只是一层包装，真正干活的是内核的 epoll。拆开看：

    • fd 是进程内的整数索引，指向内核的 struct file；一个客户端连接对应一个 socket，socket 在内核里有接收缓冲与发送缓冲两块内存；
    • 可读 = 接收缓冲里有数据（或对端发了 FIN），可写 = 发送缓冲还有空间。后者几乎永远成立，所以 Redis 只在「确实有回复要写」时才把 fd 注册进可写事件，否则 epoll_wait 会一直空转返回；
    • 三段调用各管一件事：epoll_create 建 eventpoll（红黑树 + 就绪链表）→ epoll_ctl 增删改监听（ADD/MOD/DEL）→ epoll_wait 取就绪链表，返回就绪个数。

    网卡→协议栈→rdllist→epoll_wait→ae 分发四段链路、eventpoll 的红黑树与就绪链表，以及 LT/ET 与三条内核参数｜依据 Linux epoll(7) 手册页与 ae.c、ae_epoll.c 自绘

    两个容易忽略的细节：

    1. 水平触发（LT）与边沿触发（ET）：LT 只要缓冲里还有数据就反复通知，允许「这次不读完」；ET 只在状态变化的那一刻通知一次，必须自己循环读到 EAGAIN。Redis 用 LT，并且在读事件里一次最多读固定配额的字节，读完配额就返回事件循环——用一点点效率换公平，避免一个超大请求把其他客户端饿死。
    2. 内核参数会直接变成线上故障：net.core.somaxconn 小于 Redis 的 tcp-backlog（默认 511）时，accept 队列溢出，现象是客户端连接超时而不是命令报错；ulimit -n 决定进程能开多少 fd，maxclients 配得再大也开不出来；epoll_wait 的超时由最近的时间事件决定（hz=10 即 100ms），所以 serverCron 的精度就是 100ms 级。

    4. 服务端流程：ssfd、accept 与客户端 fd

    任何一个 epoll 服务器都是同一套骨架，Redis 只是把它包进了 ae：

    ① epoll_create      →  建红黑树 + 就绪链表
② listen 端口        →  得到 ssfd（服务端监听 fd），注册 EPOLLIN
③ epoll_wait        →  等 ssfd 可读（= 有客户端连上来）
④ accept()          →  得到客户端 fd，epoll_ctl 注册它的读事件
⑤ 客户端 fd 可读     →  read/recv 读命令，处理后 write 回复
⑥ EPOLLERR / 关闭    →  close(fd)，并从红黑树里删掉

    关键认知：ssfd 和客户端 fd 挂在同一个 epoll 实例里，返回的事件里怎么区分？靠事件携带的 fd——是 ssfd 就走 accept，是客户端 fd 就走读命令。所以「一个线程同时接连接 + 处理命令」在结构上是成立的。

    5. Redis 单线程网络模型：从 main 到 aeMain

    把上面的骨架换成 Redis 的函数名，就是它的网络模型：

    main()                                  server.c
  └─ initServer()
       ├─ aeApiCreate()                 建 epoll 实例（≈ epoll_create）
       ├─ listen() 得到 ssfd，注册读事件 → acceptTcpHandler
       └─ 注册 beforeSleep 钩子
  └─ aeMain()                           死循环
       ├─ beforeSleep()                 处理 clients_pending_write、AOF 刷盘
       ├─ aeApiPoll()                   ≈ epoll_wait，超时由最近的时间事件决定
       ├─ 就绪 fd → 对应 handler
       │    ├─ ssfd 可读      → acceptTcpHandler  → accept 得客户端 fd，注册读事件
       │    └─ 客户端 fd 可读  → readQueryFromClient
       │           ├─ 读进 c->querybuf（字节）
       │           ├─ 解析成 c->argv（命令 + 参数）
       │           ├─ 查命令表 → 执行 setCommand 之类的函数
       │           ├─ 回复写进 c->buf（小）或 c->reply（链表，大）
       │           └─ 客户端进 clients_pending_write 队列
       └─ 处理时间事件 serverCron（过期清理、rehash、统计）

    一条命令的八步：注册 ssfd、accept 得客户端 fd、读进 querybuf、解析 argv、查表执行、写输出缓冲、入 pending_write，最后由 beforeSleep 的 sendReplyToClient 批量写回｜依据 server.c 与 networking.c 自绘

    三个必须记住的设计取舍：

    1. 回复不当场写回 socket。写 socket 可能因为对端接收窗口满而阻塞，会把整条单线程卡住；于是统一丢进 clients_pending_write，在下一圈的 beforeSleep 里由 sendReplyToClient 批量写——写失败只影响那一个客户端，不影响命令执行。
    2. 解析与执行分离在时间上，但不分离在线程上（默认配置下）。querybuf → argv → command 全在主线程，所以协议解析再快也救不了慢命令。
    3. 时间事件和文件事件在同一圈里。这就是「一条慢命令会让过期清理、rehash 一起延后」的根源。

    6. 事件循环的一圈与 io-threads 的边界

    beforeSleep          ← 处理待办：把 AOF 缓冲刷盘、把 pending_write 写回、处理阻塞客户端
    ↓
aeApiPoll (epoll_wait) ← 等待可读/可写的 fd，超时由最近的时间事件决定
    ↓
处理文件事件         ← 读请求、解析协议、执行命令、写回复
    ↓
处理时间事件         ← serverCron：过期清理、rehash 推进、统计更新

    6.0 的 IO 多线程只在这圈的「读写 + 解析」上加并行，边界非常清楚：

    能做
    不能做
    并行读 socket、解析 RESP
    并行执行命令
    并行组装并写回复
    让单条慢命令变快
    降低主线程的 CPU 占用
    突破单实例吞吐上限
    改善高带宽、小命令场景
    改变 Lua / MULTI 的原子性
    io-threads 4          # 默认 1 = 关闭；一般不超过 8

    官方建议：只有当实例确实被网络 IO 的 CPU 占用卡住时才开，且线程数不超过 CPU 核数。盲目开大反而因为线程切换与锁开销变慢。

    事件循环一圈的四个阶段、io-threads 能做与不能做的事情，以及单线程的三条底气｜依据 ae.c、server.c 与 redis.conf io-threads 注释自绘

    7. 为什么坚持单线程执行

    三个官方与工程上的理由：

    • 原子性天然成立：单线程执行意味着每条命令不会被其他命令插入，MULTI、Lua、INCR 都不需要额外加锁；
    • CPU 一般不是瓶颈：内存操作极快，瓶颈通常在网络带宽、内存容量、慢命令；
    • 加线程解决不了真问题：真问题是「单条命令太慢」（大 key、KEYS *、大范围 ZRANGE），多线程只会让多个慢命令一起慢。

    五、场景说明

    1. 高 QPS 小命令（GET/SET 为主）：开 io-threads 有收益，主线程不再被协议解析占满；
    2. 大 value 传输：网络写是瓶颈，多线程写回复能提升吞吐；
    3. 慢命令为主（大 key 操作）：开线程没用，必须治理命令；
    4. CPU 核数少的机器：io-threads 开到等于核数就够，别超过；
    5. 连接数暴涨、somaxconn 没调：先调内核参数（somaxconn ≥ tcp-backlog）与 ulimit -n，否则客户端连不上，跟 Redis 配置无关。

    六、示例代码/实操步骤

    # 1. 查看当前线程配置
127.0.0.1:6379> CONFIG GET io-threads
1) "io-threads"
2) "1"                      # 默认 1，即未开启 IO 多线程

# 2. 开启（建议不超过 CPU 核数）
127.0.0.1:6379> CONFIG SET io-threads 4
OK

# 3. 观察主线程 CPU 与吞吐
$ redis-cli --stat
# keys       mem      clients   blocked  requests  connections
# 1000000    1.2G     120       0        45000     120

# 4. 用 benchmark 对比开启前后的吞吐（注意：benchmark 会打满 CPU）
$ redis-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 1000000 -c 50 -q
# SET: 98000.00 requests per second
# GET: 101000.00 requests per second

# 5. 确认「慢命令仍是单线程」：跑一条大范围 ZRANGE，看其他请求是否被阻塞
127.0.0.1:6379> EVAL "for i=1,200000 do redis.call('ZADD', KEYS[1], i, 'm'..i) end return redis.call('ZCARD', KEYS[1])" 1 bigz
(integer) 200000
127.0.0.1:6379> ZRANGE bigz 0 -1 WITHSCORES
# 这一条执行期间，其他客户端全部等待——io-threads 帮不上忙

# 6. 从宿主机看「一个线程盯多少 fd」：确认 epoll 在干活
$ ls -l /proc/$(pgrep -f redis-server)/fd | wc -l     # 进程打开了多少 fd
$ cat /proc/sys/net/core/somaxconn                     # 必须 ≥ tcp-backlog(511)
$ ulimit -n                                            # 必须 ≥ maxclients + 预留

    第 5 步是这一讲最重要的实验：它证明「io-threads 提高的是 IO 吞吐，不是命令执行能力」。

    Java 侧怎么落地：别让客户端堵住那条单线程

    执行是单线程的，所以 Java 侧要做的是「少发慢命令、别排长队」，而不是「多开线程压上去」。

    1. pom 只引 starter，客户端用 Lettuce（Spring Boot 2.x 起默认），它是 Netty 驱动、连接可共享，适合并发。
    <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
    1. 连接池要配，命令超时必须设。池太小会让线程在客户端排队（慢日志里看不到），命令超时能防止一次慢命令拖死整个请求线程：
    spring:
  data:
    redis:
      timeout: 200ms                 # 命令级超时，别留 0（无限等）
      lettuce:
        pool:
          max-active: 32             # 按并发线程数配，不是越大越好
          max-wait: 100ms            # 拿不到连接立刻失败，别无限阻塞
          min-idle: 8
    1. 禁止在生产发「执行阶段很重」的命令：KEYS *、大 ZRANGE、HGETALL 十万字段、SMEMBERS 大集合——它们占的是单线程的执行时间，pool 开再大也没用。
    // 反例：KEYS 在生产禁用
// Set<String> keys = redis.keys("user:*");
// 正例：游标遍历，分批处理
ScanOptions opt = ScanOptions.scanOptions().count(500).match("user:*").build();
    1. 批量操作用 pipeline，把 N 次 RTT 压成 1 次：这也直接降低主线程的 epoll 唤醒次数。
    List<Object> res = stringRedisTemplate.executePipelined((RedisCallback<Object>) conn -> {
    for (String k : keys) conn.get(k.getBytes());
    return null;
});
    1. 微服务里统一连接参数：把 pool、timeout 放配置中心，避免某服务把 timeout 写成 0，一个慢命令把线程池占满后雪崩。

    七、常见坑（官方明确说明的限制）

    1. 以为开了 io-threads 就是「多线程 Redis」。命令执行仍是单线程，语义完全不变。
    2. 把 io-threads 开得很大。超过核数只增加切换与竞争开销，官方建议一般不超过 8。
    3. 把 Redis 说成「异步 IO」。它用的是多路复用 + 阻塞拷贝，阶段二由自己完成，属于同步 IO。
    4. 指望它解决慢查询。慢命令依旧阻塞所有人，这是单线程执行的必然结果。
    5. 以为单线程就不能扛高并发。多路复用 + 内存操作让单线程也能到十万级 QPS，瓶颈是网络与内存而不是「单线程」这个标签。
    6. serverCron 被慢命令拖住。时间事件在同一圈里执行，慢命令会让过期清理、rehash 推进都延后。
    7. beforeSleep 里的刷盘被忽略。AOF everysec 的刷盘发生在 beforeSleep，磁盘抖动会直接体现为命令延迟。
    8. 在容器里限制 CPU 却仍开多线程。CPU quota 小于 io-threads 数时，线程抢不到核，吞吐反而下降。
    9. 只调 Redis 不调内核。somaxconn < tcp-backlog 时连接被丢在 accept 队列里，表现为「客户端连不上、Redis 没报错」。
    10. 只看 QPS 不看 P99。开线程后平均 QPS 涨了，但 P99 可能因为线程同步而变差，必须两个指标一起看。

    版本差异（8.x 标注）

    6.0 引入 io-threads；7.x 中读写都可走 IO 线程（旧的 io-threads-do-reads 不再是必需项）。8.x 沿用该机制，未把命令执行改成多线程。

    依据：https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/

    八、课后小结

    • 网络读分两阶段：等数据就绪、拷到用户空间；五种 IO 模型的差别都在这两段上；
    • Redis 是「多路复用 + 阻塞拷贝」：同步 IO，不是异步 IO；
    • select 三硬伤（1024 上限、全量拷贝、全量遍历），poll 只解了第一条，epoll 用「回调 + 就绪链表」把开销变成 O(就绪数)；
    • epoll 三段：epoll_create（红黑树 + 就绪链表）、epoll_ctl（注册回调）、epoll_wait（取就绪链表）；
    • 服务端骨架：ssfd 与客户端 fd 同挂一个 epoll，靠返回的 fd 区分「接连接」还是「读命令」；
    • Redis 一次请求八步：acceptTcpHandler → readQueryFromClient → querybuf → argv → 命令表 → buf/reply → pending_write → beforeSleep 写回；
    • 事件循环一圈：beforeSleep → epoll_wait → 文件事件 → 时间事件（serverCron）；
    • io-threads 只并行 socket 读写、协议解析、回复组装，默认 1（关闭）；命令执行永远串行，慢命令只能靠治理。

    九、思考题

    1. 单线程为什么能扛十万 QPS？请从「多路复用 + 内存操作 + 无锁」三点各说一句。

      参考回答：多路复用——epoll 让一个线程同时盯上万个 fd，省掉「一连接一线程」的切换与内存；内存操作——命令在内存里执行，没有磁盘 IO 与解析开销，单条路径极短；无锁——串行执行天然原子，没有锁竞争与临界区。真实十万 QPS 通常是 pipeline 或多实例叠加的结果，单连接 RTT 仍是瓶颈。

    2. epoll_wait 为什么不随监听 fd 数变慢？select 慢在哪里？

      参考回答：epoll 在 epoll_ctl 时给 fd 注册回调，数据到达由内核把 fd 推进就绪链表，epoll_wait 只拷就绪链表，开销是 O(就绪数)。select 每次都要把整个 fd 集合拷进内核、内核线性扫描一遍、返回后用户态再遍历一遍，三个 O(N) 全压在同一调用里。

    3. Redis 用 LT 为什么还要「一次只读一部分」？改成 ET 会怎样？

      参考回答：LT 下只要还有数据就会反复通知，所以「这次读不完」是允许的；但若真把几 MB 一次读完，这一圈就全被一个客户端占住，其他人饿死。改 ET 则必须循环读到 EAGAIN，否则剩余数据不再通知、客户端超时——实现更复杂，收益也不大。

    4. ssfd 与客户端 fd 都在同一个 epoll 实例里，Redis 怎么区分两类事件？

      参考回答：靠事件里带的 fd 判断：等于 ssfd 就走 acceptTcpHandler 接新连接，其余是客户端 fd，走 readQueryFromClient 读命令；出现 EPOLLERR/EPOLLHUP 就 close 并从 epoll 里删掉。

    5. 为什么回复不直接 write 回 socket，而要先放进 clients_pending_write？

      参考回答：write 可能因为对端接收窗口满而阻塞，一阻塞就把整条单线程卡住，所有人都等这一个慢客户端。放进队列后由 beforeSleep 的 sendReplyToClient 统一写，写不完留到下次，个别客户端慢只影响它自己。

    6. io-threads 开了 8，一条 KEYS * 会变快吗？为什么？

      参考回答：不会。io-threads 只并行「读 socket、解析 RESP、组装写回复」，命令执行仍是单线程；KEYS * 的耗时全在遍历键空间这一步。

    7. 你的实例 CPU 使用率 60%、QPS 已打满、平均延迟 1ms、P99 30ms，该不该开 io-threads？怎么判断？

      参考回答：先别开。CPU 才 60%，说明瓶颈不在网络 IO 的 CPU 开销；P99 30ms 与均值 1ms 的差距更像慢命令/大 key/客户端排队。看 INFO cpu 是否主要耗在 IO、带宽是否打满、SLOWLOG/LATENCY 是否有周期事件；只有「带宽打满 + IO 吃满 CPU」才值得开。
