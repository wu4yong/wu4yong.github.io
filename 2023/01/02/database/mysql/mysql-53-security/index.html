    mysql-53-security

    📅 2023-01-02

    安全加固：TLS、注入与账号隔离

    链路加密、注入防护、账号隔离 —— 一条断了两条白搭｜依据 MySQL 8.4 Security / TLS 说明自绘

    一、学习目标

    1. 把服务端与客户端的 TLS 配置串起来，避免「配了但没校验」；
    2. 认清 SQL 注入的几种变形，用参数化 + 白名单把口子堵住；
    3. 按清单做实例加固，新实例上线即合规。

    二、前置知识

    账号与权限（MQ52）、认证插件（MQ16）、日志与审计（MQ36）。

    三、理论讲解（官方定义）

    MySQL 支持 TLS 加密的连接建立与数据传输，服务端通过 ssl_ca、ssl_cert、ssl_key 提供证书，客户端通过 --ssl-mode 选择校验强度：

    客户端模式 校验内容 风险
    DISABLED 不加密 明文抓包
    PREFERRED 尽量加密，不校验证书 中间人可伪装
    REQUIRED 加密，不校验 CA 中间人可伪装
    VERIFY_CA 加密 + 校验 CA 签发 推荐
    VERIFY_IDENTITY 再校验主机名 最严格

    服务端侧 require_secure_transport=ON 可强制所有连接必须加密。

    四、原理拆解

    加密是配置问题，注入是编码问题，两者都不靠自觉｜依据 MySQL 8.4 Encrypted Connections / 注入防护实践自绘

    1. TLS 只在「校验」时才是安全的

    REQUIRED 与 PREFERRED 只保证加密，不保证对端身份 —— 攻击者可以自签一张证书冒充数据库。只有 VERIFY_CA 以上才校验签发链，VERIFY_IDENTITY 还校验主机名。很多「已开启 TLS」的生产环境，客户端配的其实是 PREFERRED，等于没防。

    2. 注入的三种常见变形

    • 拼接："WHERE id=" + id，最典型；
    • 排序/列名：ORDER BY " + sort，列名无法参数化，必须白名单映射；
    • LIKE / IN：% 与 _ 是通配符，IN (" + ids + ") 会拼出超长语句或被注入。

    参数化（PreparedStatement）能解决值注入，解决不了标识符注入（表名、列名、排序方向），后者只能靠白名单。

    3. 账号隔离的三层

    • 权限隔离：读写/只读/DDL/备份分账号（MQ52）；
    • 网络隔离：bind-address + 安全组，只放应用网段；
    • 入口隔离：高危操作（DROP、大批量 DELETE）走审批流水线，不给人直连权限。

    4. 加固清单（摘）

    项 做法 验证 风险
    TLS 强制 require_secure_transport=ON SHOW VARIABLES 明文抓包
    账号口令 caching_sha2_password + 轮换 mysql.user 插件列 弱口令爆破
    网络边界 bind-address + 安全组 nmap 外网扫描 公网暴露
    审计日志 审计插件或代理审计 抽查高危语句 内鬼操作无痕
    本地文件 local_infile=OFF SHOW VARIABLES 读服务器文件
    版本 保持 LTS 小版本更新 SELECT VERSION() 已知漏洞

    5. 为什么 local_infile 要关

    LOAD DATA LOCAL INFILE 允许客户端让服务端读取客户端本地文件（历史上存在被恶意服务端反读文件的攻击面）。业务不用就关掉；要用则限定到特定账号与目录。

    五、场景说明

    1. 等保/合规要求：全链路 TLS + 审计日志 + 口令策略；
    2. 公网暴露的读库：至少 bind-address 收内网 + 安全组白名单；
    3. 多租户：账号按租户隔离，禁止跨租户授权；
    4. 数据导出：只允许只读账号 + 审批，导出文件加密；
    5. 第三方接入：单独账号、单独网段、单独限流。

    六、示例代码/实操步骤

    1. 服务端开启 TLS

    [mysqld]
ssl_ca   = /etc/mysql/certs/ca.pem
ssl_cert = /etc/mysql/certs/server-cert.pem
ssl_key  = /etc/mysql/certs/server-key.pem
require_secure_transport = ON
local_infile = OFF
    SHOW VARIABLES LIKE 'have_ssl';        -- YES 表示 TLS 可用
SHOW VARIABLES LIKE 'require_secure_transport';

    改 require_secure_transport 前先确认所有客户端都支持 TLS，否则会直接连不上。

    2. 客户端连接校验

    mysql --ssl-mode=VERIFY_CA --ssl-ca=/etc/mysql/certs/ca.pem -h db0 -u app -p

    VERIFY_IDENTITY 需要证书 SAN 与连接主机名一致，内网多用 IP 连接时反而会失败，按实际情况选。

    3. JDBC 侧配置

    jdbc:mysql://db0:3306/shop?sslMode=VERIFY_CA
  &trustCertificateKeyStoreUrl=file:/opt/app/certs/truststore.jks
  &trustCertificateKeyStorePassword=***

    禁止 sslMode=DISABLED 与 PREFERRED；VERIFY_CA 至少保证不会被中间人冒充。

    4. 防注入的写法对照

    // ❌ 拼接
String sql = "SELECT * FROM t_order WHERE id=" + id;

// ✅ 参数化
String sql = "SELECT * FROM t_order WHERE id=?";
jdbcTemplate.query(sql, new Object[]{id}, mapper);

// ✅ 排序字段白名单（列名不能参数化）
private static final Set<String> SORTABLE = Set.of("create_time","amount","id");
String col = SORTABLE.contains(sort) ? sort : "id";
String sql2 = "SELECT * FROM t_order ORDER BY " + col + " LIMIT 20";

    LIKE 查询要对 %/_ 转义：kw.replace("%","\\%").replace("_","\\_")，再拼进参数。

    5. Java 侧怎么落地：把安全做成默认值

    1. 数据源模板统一：连接串默认带 sslMode=VERIFY_CA，禁止业务自行改；
    2. 持久层强制参数化：MyBatis 用 #{} 而非 ${}，CI 里加静态检查规则拦截 ${}；
    3. SQL 审计：拦截器记录全表 DELETE、无 WHERE 的 UPDATE、超长 IN；
    4. 账号从配置中心取：口令轮换不改代码，重启即生效；
    5. 上线检查表：新实例必须过 TLS/账号/网络/审计四项检查，缺一项不放行。

    七、常见坑

    1. 客户端配 PREFERRED：看着加密了，其实不校验对端；
    2. 证书过期无监控：某天凌晨全站连不上库；
    3. ORDER BY 用 ${} 拼接：参数化管不到列名，仍是注入；
    4. LIKE 未转义通配符：用户输入 % 造成全表扫描甚至越权匹配；
    5. bind-address=0.0.0.0 + 安全组放通：等于公网裸奔；
    6. 开 local_infile 且用 root：可读服务器任意可读文件；
    7. 审计只看慢日志：注入语句往往很快，慢日志抓不到；
    8. 改 require_secure_transport 前未灰度：老客户端批量掉线。

    八、版本差异

    • 5.6：TLS 支持较弱，默认不强制；无 caching_sha2_password；
    • 5.7：--ssl-mode 体系成型，require_secure_transport 可用；
    • 8.0：TLS 1.2/1.3 支持完善；caching_sha2_password 成为默认插件；local_infile 默认关闭（8.0 起默认 OFF）；
    • 8.4 LTS：mysql_native_password 默认关闭，老客户端/libmysql 版本过低会直接认证失败；require_secure_transport 与 authentication_policy 共同构成默认安全基线；TLS 1.0/1.1 已不支持。

    九、课后小结

    • TLS 的安全来自「校验」，REQUIRED/PREFERRED 只加密不防冒充；
    • 注入要靠参数化 + 标识符白名单，${} 拼接是硬伤；
    • 账号隔离三层：权限、网络、入口；
    • 加固清单要变成上线检查项，而不是事故后的补丁；
    • 证书过期、插件默认关闭、版本漏洞，是最容易忽视的三类风险。

    十、思考题

    1. sslMode=REQUIRED 已经加密了，为什么还不够？

      参考回答：REQUIRED 只保证通道加密，不校验服务端证书的签发链。攻击者可以自签一张证书冒充数据库，客户端照样接受并加密通信，形成中间人。只有 VERIFY_CA（校验签发链）或 VERIFY_IDENTITY（再校验主机名）才能确认对端身份。

    2. 参数化为什么解决不了 ORDER BY 注入？

      参考回答：参数化是把「值」绑定到占位符，ORDER BY 后面跟的是标识符（列名/表达式），不是数据值，数据库不允许用占位符替代标识符。因此必须用白名单把前端传入的排序字段映射到固定的列名，未命中的一律回落到默认列。

    3. local_infile=ON 的风险具体是什么？

      参考回答：LOAD DATA LOCAL INFILE 由客户端发起、服务端请求客户端发送本地文件内容，历史上存在恶意服务端借此读取客户端机器文件的问题；同时若服务端允许，也可能被用来读取服务器侧可读文件。业务不需要就关闭，需要则限定账号与目录。

    4. 8.4 默认关闭 mysql_native_password 会带来什么上线风险？

      参考回答：老版本客户端驱动（如低版本 Connector/J、部分语言的旧驱动）只支持 mysql_native_password，升级到 8.4 后会直接认证失败。上线前要确认所有客户端驱动版本，必要时临时启用该插件过渡，同时把驱动升级排进计划。

    5. 怎样证明「加固真的生效」而不是「配置写了」？

      参考回答：用外部视角验证：从非授权网段 nmap/telnet 扫端口；用不带证书的客户端尝试连接看是否被拒；用只读账号尝试 INSERT 看是否报权限错；抽查审计日志是否记录高危语句；定期做恢复与权限巡检。配置项只是意图，验证才是证据。
