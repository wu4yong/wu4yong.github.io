    redis-28-listpack 与 intset

    📅 2023-01-18

    listpack 与 intset：小对象为什么省内存

    intset 的整数数组、listpack 的条目序列与四组编码转换阈值｜依据 Redis 7.4 redis.conf 与官方文档自绘

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 说清 intset 与 listpack 各自的适用场景，以及它们为什么比 hashtable / skiplist 省内存；
    2. 背下四组转换阈值（128 / 64 / 512 / 128），并知道「转换不可逆」的后果；
    3. 用 OBJECT ENCODING 与 MEMORY USAGE 判断一个集合的编码是否已经「越过了阈值」。

    二、前置知识

    RD07（Hash）、RD08（Set）、RD09（ZSet）、RD26（redisObject 与 encoding）。本讲是这四种类型的「底层画像」。

    三、理论讲解（官方定义）

    官方对紧凑编码的说明（原文要点）：

    Small hashes, lists, sets and sorted sets are stored in a compact encoding … listpack … These encodings are used to save memory.

    —— https://redis.io/docs/latest/develop/data-types/hashes/

    listpack 的设计目标（源码 listpack.h，原文要点）：

    A listpack is a compact flat representation of a list of elements … it has no pointers to other nodes, so it uses less memory.

    —— https://github.com/redis/redis/blob/7.4/src/listpack.h

    两条定性：

    • 紧凑编码用「连续内存 + 变长条目」换内存，代价是插入/删除要搬数据；
    • 转换是一次性的、不可逆的（intset 升级、listpack 转 hashtable/skiplist 都不会回退）。

    四、原理拆解

    1. intset：有序整数数组

    encoding（4 字节：int16 / int32 / int64）
length  （元素个数）
contents（有序存放的整数）

    三个要点：

    • 有序：插入要二分查找 + 搬移，所以是 O(N) 的最坏情况（N 是元素数，但 N 小）；
    • 只升不降：一旦因为插入大整数升级到 int32，即使删掉那个元素也不会退回 int16；
    • 只存整数：一旦插入非整数（如字符串），整个集合转 hashtable 表示。

    适用场景：SADD users 1001 1002 1003 这种「用户 ID 集合」，几百个元素时内存可以只有 hashtable 的几分之一。

    2. listpack：连续内存上的条目序列

    header（总字节数、元素个数）
entry × N（每项 = 编码 + 数据 + 回退长度）
0xFF（结束标记）

    entry 的回退长度是 listpack 的关键设计：从左往右遍历时不需要额外记录每项长度，从右往左时用回退长度也能走。这一点比老的 ziplist（用「前一项长度」双向维护、级联更新）更简洁。

    限制很明确：中间插入要整体搬移右侧数据。所以它只适合小集合（默认上限 128 项），超过就转成 hashtable（Hash/Set）或 skiplist（ZSet）。

    3. 7.2 起：ziplist 退役

    7.2 用 listpack 全面替换 ziplist。老配置项 hash-max-ziplist-entries 等仍然可用（向后兼容），但语义对应到 listpack。如果你的文档或监控脚本还在按 ziplist 判断编码，会读到 listpack 而误判。

    4. 四组阈值（redis.conf 官方默认）

    配置
    默认
    适用类型
    hash-max-listpack-entries
    128
    Hash：字段数上限
    hash-max-listpack-value
    64
    Hash：单字段/值字节上限
    zset-max-listpack-entries
    128
    ZSet：元素数上限
    zset-max-listpack-value
    64
    ZSet：单元素字节上限
    set-max-intset-entries
    512
    Set：整数集合元素数上限
    list-max-listpack-size
    128
    List：quicklist 单节点条目数

    判定规则是「任一条件超标就转换」：字段数超过 128，或任一字段/值超过 64 字节，都会转 hashtable。这条「任一」经常被忽略——业务里一个超长 value 就能把整张 Hash 打成 hashtable。

    intset 的有序数组结构、listpack 的 header/entry/0xFF 布局、四组阈值与三条不可逆结论｜依据 redis.conf 默认值与 listpack.h 自绘

    五、场景说明

    1. 配置类 Hash：几十个字段、值都是短字符串，listpack 编码，内存极省；
    2. 用户 ID 集合：整数且数量在几百内，intset；
    3. 排行榜：元素数超过 128 或 member 太长 → skiplist，此时每个元素都有指针开销；
    4. 订单快照 Hash：如果某个字段塞了整段 JSON（> 64 字节），整张 Hash 立刻转 hashtable，内存涨数倍。

    六、示例代码/实操步骤

    # 1. Hash 的编码与阈值验证
127.0.0.1:6379> HSET cfg name app
(integer) 1
127.0.0.1:6379> OBJECT ENCODING cfg
"listpack"

# 触发 value 超限（> 64 字节）
127.0.0.1:6379> HSET cfg blob "0123456789012345678901234567890123456789012345678901234567890123456789"
(integer) 1
127.0.0.1:6379> OBJECT ENCODING cfg
"hashtable"                  # 一个超长 value 就整表转换

# 2. intset 与升级
127.0.0.1:6379> SADD ids 1 2 3
(integer) 3
127.0.0.1:6379> OBJECT ENCODING ids
"intset"
127.0.0.1:6379> SADD ids hello
(integer) 1
127.0.0.1:6379> OBJECT ENCODING ids
"hashtable"                  # 非整数成员 → 转 hashtable

# 3. intset 的元素数上限（默认 512）
127.0.0.1:6379> EVAL "for i=1,520 do redis.call('SADD', KEYS[1], i) end return redis.call('SCARD', KEYS[1])" 1 big:ids
(integer) 520
127.0.0.1:6379> OBJECT ENCODING big:ids
"hashtable"                  # 超过 512 → 转 hashtable

# 4. ZSet 的编码
127.0.0.1:6379> ZADD board 1 a 2 b
(integer) 2
127.0.0.1:6379> OBJECT ENCODING board
"listpack"
127.0.0.1:6379> ZADD board 3 "this-member-name-is-way-too-long-for-listpack-value-limit"
(integer) 1
127.0.0.1:6379> OBJECT ENCODING board
"skiplist"                   # member 超过 64 字节

# 5. 内存对比
127.0.0.1:6379> MEMORY USAGE cfg
(integer) 160                # hashtable
127.0.0.1:6379> MEMORY USAGE ids
(integer) 200                # intset

# 6. 阈值调整（改完只影响后续转换，不会把已转换的改回来）
127.0.0.1:6379> CONFIG SET hash-max-listpack-entries 256
OK

    Java 侧怎么落地：别用序列化器踩阈值

    四组阈值在 Java 侧的敌人只有两个：序列化器把 value 撑大、业务把大对象塞进小容器。

    1. pom 只引 starter，序列化器必须显式指定，别用默认 JDK 序列化——它给每个值加一堆二进制头，10 字节的 age 会被写成几十字节，直接顶破 64 字节的 value 阈值。
    RedisTemplate<String, String> t = new RedisTemplate<>();
t.setConnectionFactory(factory);
t.setKeySerializer(new StringRedisSerializer());
t.setValueSerializer(new StringRedisSerializer());   // 或 GenericJackson2JsonRedisSerializer，但要算长度
t.setHashValueSerializer(new StringRedisSerializer());
t.afterPropertiesSet();
    1. 短字段用 Hash 存，别把整个对象序列化成一个 value：一个 200 字节的 JSON 进 Hash，hash-max-listpack-value 立刻被顶破，3 个字段也转 hashtable。
    // 反例：hSet("user:1001", "profile", 200字节JSON)
// 正例：拆字段，每个字段控制在 64 字节内
stringRedisTemplate.opsForHash().putAll("user:1001",
        Map.of("name", "alice", "age", "24", "city", "cd"));   // 保持 listpack

    1. 批量写入用 putAll/pipeline，逐条 hSet 在网络往返上就输了，也更容易在阈值边缘反复触发转换。

    2. 阈值改动只对新 key 生效：调大 hash-max-listpack-entries 后，存量 key 不会自动回去，必须重建（HGETALL → 删 → 重建）。

    3. 用断言把编码钉死，避免某次上线悄悄把热 key 全变成 hashtable：

    String enc = stringRedisTemplate.execute((RedisCallback<String>) c ->
        new String(c.execute("OBJECT", "ENCODING".getBytes(), "user:1001".getBytes())));
assertEquals("listpack", enc);   // 期望值随版本：7.2+ 是 listpack，不是 ziplist

    七、常见坑（官方明确说明的限制）

    1. 以为「小 Hash 一定省内存」。字段数少但 value 超 64 字节，同样是 hashtable。
    2. intset 只升不降。升级到 int32 后删元素不回头，内存会一直按大编码算。
    3. 编码转换不可逆。删到只剩 1 个元素，hashtable 也不会变回 listpack——只能重建 key。
    4. 把 ziplist 当现行编码。7.2 起是 listpack；按 ziplist 写监控会误判。
    5. list-max-listpack-size 语义混淆。正数表示「每节点条目数」，负数表示「每节点字节数上限」（-1 = 4KB，-2 = 8KB，依此类推）。
    6. listpack 中间插入。LSET / LINSERT 的元素多时是 O(N)，因为它要搬移后续数据。
    7. 改阈值不迁移存量。调大 hash-max-listpack-entries 只影响新建的 key，已有 hashtable 不会自动变回。
    8. MEMORY USAGE 的单 key视角。它不含 dict 的桶开销，评估总量时要以 INFO memory 为准。

    版本差异（8.x 标注）

    7.2 完成 ziplist → listpack 的替换，7.4 与 8.x 沿用；intset 结构未变。旧配置名（*-ziplist-*）仍被接受，但新代码与新文档统一用 listpack。

    依据：https://redis.io/docs/latest/develop/data-types/hashes/

    八、课后小结

    • intset：有序整数数组，编码 int16/32/64，只升不降，非整数成员即转 hashtable；
    • listpack：header + 变长 entry + 0xFF 结束标记，连续内存、无指针；
    • 四组阈值：hash 128/64、zset 128/64、set 512、list 128（任一超标即转换）；
    • 转换一次性、不可逆，想回去只能重建 key；
    • 7.2 起 ziplist 退役，编码名是 listpack；
    • OBJECT ENCODING 是唯一可靠的判定方式。

    九、思考题

    1. 一个 Hash 只有 3 个字段，但某个字段的 value 有 200 字节，它的编码是什么？为什么？

      参考回答：hashtable。阈值是「任一条件超标即转换」——字段数没超 128，但 200 字节超过了 hash-max-listpack-value 的 64，一个小 Hash 也会被转成大结构。

    2. intset 为什么「只升不降」？如果允许降级会带来什么代价？

      参考回答：升级要整块重分配并搬全部元素，降级同样要全量重排，还得判断所有元素是否都能塞进更小宽度；元素跨度大时（同时有 1 和 10⁹）降级会来回震荡。所以索性只升不降，回收内存只能重建 key。

    3. ZSet 从 listpack 转 skiplist 后，内存大概会涨多少？为什么？

      参考回答：通常涨 3～8 倍。listpack 是连续内存、无指针；skiplist 每个成员要一个 dictEntry、一个 zskiplistNode（含层数组）和独立 SDS，三份结构加指针开销。

    4. list-max-listpack-size 设成 -2 是什么意思？和设成 128 有什么区别？

      参考回答：负数表示按字节限制：-1 是 4KB、-2 是 8KB、-3 16KB、-4 32KB、-5 64KB；正数 128 表示按条目数限制。前者控制单节点体积（元素大时更安全），后者控制条目数（元素小时更省）。

    5. 一个 key 已经变成 hashtable，业务字段数降回 10 个，怎么让它变回 listpack？

      参考回答：编码只升不降，原地变不回去。做法是重建：RENAME 原 key 到临时名 → HGETALL 读出 → 确保字段 ≤128 且每个 value ≤64 字节 → 重新 HSET → 删掉临时 key，再改回原名。
