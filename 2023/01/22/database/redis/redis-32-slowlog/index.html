    redis-32-慢查询诊断

    📅 2023-01-22

    慢查询、LATENCY 与 MONITOR

    命令级、事件级、流量级三种视角的分工与三条官方警告｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 用 SLOWLOG 抓住「哪条命令慢」，并知道它测不到什么；
    2. 用 LATENCY 区分「命令慢」与「事件慢」（fork、AOF 刷盘、过期清理）；
    3. 用 MONITOR 做短时流量取证，并清楚它的性能代价。

    二、前置知识

    RD30（事件循环）、RD31（内存与 fork 代价）。三个工具对应三种「时间花在哪」的假设，组合使用才能定位。

    三、理论讲解（官方定义）

    官方对慢日志的定义（原文）：

    The Redis Slow Log is a system to log queries that exceeded a specified execution time … execution time does not include the I/O operations … nor the time spent in the network.

    —— https://redis.io/docs/latest/commands/slowlog-get/

    对 LATENCY 的定义（原文要点）：

    The LATENCY command … is able to record latency spikes for different events: command, fork, aof-write, expire-cycle …

    —— https://redis.io/docs/latest/commands/latency-latest/

    对 MONITOR 的警告（原文要点）：

    MONITOR … is a debugging command that streams back every command processed … it can reduce performance dramatically.

    —— https://redis.io/docs/latest/commands/monitor/

    三条定性：

    • SLOWLOG 只测服务端执行耗时，不含网络与排队；
    • LATENCY 测的是事件级尖峰，能抓到 fork、AOF 刷盘这类「不是命令但拖慢一切」的动作；
    • MONITOR 是重负载调试工具，官方明确说会显著降低性能。

    四、原理拆解

    1. SLOWLOG 的机制与边界

    slowlog-log-slower-than 10000    # 单位微秒，10000 = 10ms；-1 关闭；0 记录所有
slowlog-max-len 128              # 环形队列，最多保留 128 条

    记录的内容：自增 id、时间戳、执行耗时（微秒）、命令与参数、客户端地址与名称。不含网络往返与客户端侧排队，所以：

    • 客户端感觉慢、但 SLOWLOG 里没有 → 问题在网络、连接池或客户端排队；
    • SLOWLOG 里有、但客户端感觉还行 → 可能是单次偶发，看频率。

    注意 slowlog-max-len 是环形：写满后最老的被覆盖。要长期留存必须外部采集（如定时 SLOWLOG GET 落库）。

    2. LATENCY 的事件模型

    latency-monitor-threshold（默认 0 = 关闭）按毫秒设定阈值，超过阈值的事件被记录。常见事件：

    事件
    含义
    典型触发
    command
    单条命令执行超阈值
    大 key、大范围查询
    fork
    fork 子进程耗时
    BGSAVE / AOF 重写
    aof-write
    AOF 写盘耗时
    磁盘抖动、fsync 慢
    expire-cycle
    过期清理循环耗时
    大量 key 同时过期
    loading
    加载 RDB/AOF 耗时
    重启恢复

    LATENCY DOCTOR 会把这些事件翻译成人话建议，是排障时最省时间的一条命令。

    关键区别：SLOWLOG 看不见 fork 与 aof-write，因为它们不是命令。所以「客户端周期性卡顿、慢日志干净」的场景，答案通常在 LATENCY 里。

    3. MONITOR 的代价与正确用法

    MONITOR 会把每条被执行的命令实时推给客户端。代价是三重的：

    • 服务端要为每条命令做一次格式化与网络发送；
    • 客户端要能消费这个量级（十万 QPS 就是十万行/秒）；
    • 输出内容可能包含敏感数据（密码、手机号），要按合规要求处理。

    正确用法：只在已定位到时间窗口后，抓 10–30 秒，配合 CLIENT LIST 找到来源 IP/连接名。长时间开启等于给自己制造一次故障。

    SLOWLOG、LATENCY、MONITOR 各自记什么/盲区在哪/怎么配，以及三种症状该查哪一层｜依据 SLOWLOG、LATENCY、MONITOR 文档与 redis.conf 参数自绘

    五、场景说明

    1. 偶发 P99 毛刺：先看 LATENCY LATEST 有没有 fork/aof-write，再看 SLOWLOG；
    2. 某个接口固定慢：SLOWLOG GET 10 直接看命令与参数，通常能一眼看出大 key；
    3. 怀疑有人在扫库：MONITOR 短时抓，或用 CLIENT LIST 看 cmd 字段；
    4. 上线后延迟整体抬高：先排除 io-threads 配置、再排除持久化叠加。

    六、示例代码/实操步骤

    # 1. 配置慢日志（10ms 阈值，保留 128 条）
127.0.0.1:6379> CONFIG SET slowlog-log-slower-than 10000
OK
127.0.0.1:6379> CONFIG SET slowlog-max-len 128
OK

# 2. 读取慢日志
127.0.0.1:6379> SLOWLOG GET 5
1) 1) (integer) 14              # 日志 id
   2) (integer) 1720000000      # 发生时间戳
   3) (integer) 15234           # 执行耗时（微秒）= 15.2ms
   4) 1) "ZRANGE"
      2) "bigz"
      3) "0"
      4) "-1"
   5) "127.0.0.1:54321"
   6) ""

# 3. 统计条数与清空
127.0.0.1:6379> SLOWLOG LEN
(integer) 5
127.0.0.1:6379> SLOWLOG RESET
OK

# 4. 打开延迟监控（阈值 10 毫秒）
127.0.0.1:6379> CONFIG SET latency-monitor-threshold 10
OK

# 5. 看各类事件的最新尖峰
127.0.0.1:6379> LATENCY LATEST
1) 1) "fork"
   2) (integer) 1720000000
   3) (integer) 48
   4) (integer) 48
2) 1) "aof-write"
   2) (integer) 1720000000
   3) (integer) 12
   4) (integer) 12

# 6. 看某个事件的历史曲线
127.0.0.1:6379> LATENCY HISTORY fork
1) 1) (integer) 1719990000
   2) (integer) 45
2) 1) (integer) 1720000000
   2) (integer) 48

# 7. 让工具给结论
127.0.0.1:6379> LATENCY DOCTOR
# Dave, I have observed a fork taking 48 milliseconds ...

# 8. 短时抓流量（务必加超时）
$ timeout 15 redis-cli -h 127.0.0.1 MONITOR
# 1720000000.123 [0 127.0.0.1:54321] "GET" "user:1000"
# 1720000000.124 [0 127.0.0.1:54321] "HGETALL" "cart:1000"

# 9. 找来源连接
127.0.0.1:6379> CLIENT LIST
# id=12 addr=10.0.0.8:51234 name=order-svc cmd=hgetall

    第 8 步的 timeout 是必须的——这是防「忘记关 MONITOR 把自己拖死」的唯一保险。

    Java 侧怎么落地：把慢命令拦在应用层

    慢查询在 Java 侧有两种来源：发了重命令，或者根本没慢在 Redis（慢在网络与池）。落地要做的是可观测 + 不给慢命令机会。

    1. pom 引 starter + 监控，用 Micrometer 把 Redis 客户端指标接进 Prometheus：
    <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
    1. 命令超时与重试策略要分开：读操作可以短超时 + 有限重试，写操作短超时 + 不重试（避免重复写），别用一刀切的全局超时。
    spring:
  data:
    redis:
      timeout: 200ms
      lettuce:
        pool:
          max-active: 32
          max-wait: 100ms
    1. 在应用侧给命令计时并分桶：把「客户端耗时」和「Redis 报的耗时」分开记，两者差得大就是网络/池问题，而不是慢命令。
    long t0 = System.nanoTime();
try { return stringRedisTemplate.opsForValue().get(key); }
finally { timer.record(System.nanoTime() - t0, TimeUnit.NANOSECONDS); }   // 打 P50/P99

    1. 定时把 SLOWLOG GET 落库（环形 128 条会被覆盖），并在阈值上留余量：slowlog-log-slower-than 用 10000 微秒（10ms），不要写 10（那是 10 微秒，等于全量记录）。

    2. 重命令用替代写法：KEYS→SCAN，大集合遍历→分批，HGETALL 十万字段→HSCAN；Lua 脚本要限制执行时长，别在里面做范围遍历。

    七、常见坑（官方明确说明的限制）

    1. 以为 SLOWLOG 能抓所有慢。它不含网络与排队，客户端慢但服务端不慢时它一无所获。
    2. slowlog-log-slower-than 用毫秒。单位是微秒，写 10 实际是 10 微秒，会把所有命令都记下来并放大开销。
    3. 把 slowlog-max-len 当持久存储。它是环形队列，写满即覆盖，长期分析必须外部采集。
    4. 不看 LATENCY 就怪命令。周期性卡顿常来自 fork 与 aof-write，慢日志里干干净净。
    5. latency-monitor-threshold 0 以为在监控。0 表示关闭，必须显式设阈值。
    6. MONITOR 长期开启。官方明确会显著降低性能，还可能泄露敏感数据。
    7. MONITOR 输出当审计日志。它没有结构化字段，也不保证完整，合规审计要用 ACL 日志或代理层采样。
    8. 只看平均值。慢查询的价值在 P99 与「发生频率」，平均延迟 1ms 但每小时 10 次 30ms 毛刺，业务照样受影响。

    版本差异（8.x 标注）

    SLOWLOG、LATENCY、MONITOR 的语义与参数在 7.x 与 8.x 一致；8.x 未改变阈值单位与事件模型。差异主要在可观测性生态（外部采集工具）与许可条款。

    依据：https://redis.io/docs/latest/commands/slowlog-get/

    八、课后小结

    • SLOWLOG：命令级，单位微秒（默认 10000），环形 128 条，不含网络与排队；
    • LATENCY：事件级，阈值毫秒（默认 0 = 关闭），覆盖 command/fork/aof-write/expire-cycle/loading；
    • MONITOR：流量级，实时但重负载，只能短时用；
    • 排障顺序：LATENCY LATEST 看事件 → SLOWLOG GET 看命令 → MONITOR 短时取证 → CLIENT LIST 找来源；
    • 周期性毛刺优先怀疑 fork 与 aof-write，不是命令。

    九、思考题

    1. 客户端反馈「接口偶尔 200ms」，SLOWLOG 里只有 3ms 的记录，问题可能在哪？下一步查什么？

      参考回答：慢在命令之外——网络 RTT、连接池排队（池满 max-wait）、客户端 GC/线程调度、代理或 TLS。下一步：CLIENT LIST 看连接数与 qbuf、抓包看 RTT、看应用侧 GC 日志、用 LATENCY 看 fork/aof-write 是否周期性出现。

    2. slowlog-log-slower-than 10 与 10 毫秒的直觉差了多少倍？会造成什么后果？

      参考回答：单位是微秒，写 10 就是 10 微秒，比 10 毫秒严 1000 倍。后果：几乎每条命令都被记录，128 条的环形队列瞬间被填满、真正慢的命令被淹没，同时增加格式化与内存开销。

    3. 为什么 fork 和 aof-write 不会出现在慢日志里？它们属于哪一层的观测？

      参考回答：SLOWLOG 只统计「命令执行」耗时，fork 是进程操作、aof-write 是写盘动作，都不是命令。它们属于 LATENCY 的事件模型（fork、aof-write），阈值用 latency-monitor-threshold（毫秒）。

    4. LATENCY DOCTOR 提示 fork 耗时 48ms，你会怎么降低这个值？

      参考回答：三条：减小单实例内存（拆实例，fork 与页表大小成正比）、关闭透明大页 THP（避免逐页拆分）、把 BGSAVE/AOF 重写错峰到低峰并降低写入速率以减少 CoW。

    5. 用 MONITOR 抓流量时，为什么必须先限定时间窗口？除了性能还有什么风险？

      参考回答：性能上每条命令都要服务端格式化并推送，十万 QPS 就是十万行/秒，可能把实例与监控端一起拖垮。另一个风险是内容泄露：命令参数里常有密码、手机号、token，MONITOR 输出必须按合规要求脱敏与限期保存。

    十、官方资料

    • SLOWLOG GET（执行耗时定义与字段）：https://redis.io/docs/latest/commands/slowlog-get/
    • LATENCY LATEST / HISTORY / DOCTOR：https://redis.io/docs/latest/commands/latency-latest/
    • MONITOR（性能警告原文）：https://redis.io/docs/latest/commands/monitor/
