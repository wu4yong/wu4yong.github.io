    redis-37-Pub/Sub

    📅 2023-01-27

    Pub/Sub 的投递语义

    PUBLISH 到订阅者的分发路径、「至多一次」语义与常用观测命令｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 说清 Pub/Sub 是「实时广播」而非消息队列，并给出官方依据；
    2. 说清「至多一次」意味着什么，以及订阅关系为什么是内存态；
    3. 用 PUBSUB CHANNELS/NUMSUB/NUMPAT 观察线上的订阅状况。

    二、前置知识

    RD04（RESP，订阅是连接状态的一种切换）、RD38（Stream 消费组，下一讲做对照）。这一讲的重点不是命令，而是语义边界。

    三、理论讲解（官方定义）

    官方对 Pub/Sub 的定性（原文）：

    Pub/Sub is … a messaging paradigm where senders … send messages to a channel, and receivers … subscribe to channels … messages are not persisted.

    —— https://redis.io/docs/latest/develop/interact/pubsub/

    以及集群下的行为（原文要点）：

    In a Redis Cluster clients can publish to every node … the message is propagated to all nodes.

    —— https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/

    两条定性：

    • 不持久化：消息发出去就没了，没有队列、没有补发；
    • 集群下是全局广播：默认 PUBLISH 会传播到所有节点（7.0 起可用 SSUBSCRIBE 做分片订阅）。

    四、原理拆解

    1. 分发路径

    PUBLISH channel msg
  → 服务端查频道表，找出所有订阅了这个频道的连接
  → 逐个写入这些连接的输出缓冲区
  → 返回「收到消息的订阅者数量」

    注意最后一句：PUBLISH 的返回值是当时在线的订阅者数，不是「成功投递数」。没有订阅者时返回 0，消息直接被丢弃。

    2. 「至多一次」的真实含义

    场景
    结果
    订阅者不在线
    消息丢失，无补发
    订阅者在线但网络断开
    消息可能丢失，客户端重连后也不补
    订阅者的输出缓冲区满了
    连接可能被断开（client-output-buffer-limit pubsub）
    发布成功、业务处理失败
    没有重试机制，不会重投

    这就是「至多一次（at most once）」。要做「至少一次」，必须换 Stream 消费组（RD38）或引入外部 MQ。

    3. 订阅是连接状态，不是数据状态

    SUBSCRIBE 之后，这条连接进入「订阅模式」，此时只能执行少数命令（SUBSCRIBE/UNSUBSCRIBE/PSUBSCRIBE/PUNSUBSCRIBE/PING/QUIT/RESET）。所以：

    • 订阅关系只能挂在一条长连接上，不能用连接池的短连接；
    • 应用重启后要重新订阅，Redis 不会记住「上次订阅了什么」；
    • 每条订阅连接都要单独保活（半开连接检测），否则你会以为在收消息，实际已经掉线。

    4. 频道 vs 模式订阅

    方式
    命令
    匹配
    频道订阅
    SUBSCRIBE news.sports
    精确匹配
    模式订阅
    PSUBSCRIBE news.*
    glob 风格通配

    模式订阅会带来额外开销：每条消息都要与所有模式匹配一次。模式数量多时（比如每租户一个模式）会明显拖慢发布路径。

    5. 集群下的广播成本

    Cluster 中默认 PUBLISH 会把消息发给所有节点，因此：

    • 节点越多，消息复制的开销越大；
    • 每个节点都要处理一遍，即使上面没有订阅者；
    • 7.0 的 SSUBSCRIBE（分片订阅）把消息限定在某个槽所在的节点，大幅降低开销。

    PUBLISH 经频道表分发到各订阅连接、离线订阅者直接丢弃，以及至多一次的四种失败场景｜依据 Pub/Sub 文档与 client-output-buffer-limit pubsub 自绘

    五、场景说明

    1. 配置变更通知：一个实例改了配置，广播给所有服务节点刷新本地缓存；
    2. 在线状态广播：配合 Stream 做「尽力而为」的实时推送；
    3. 缓存失效通知：改库后广播「key 变了」，各节点清本地缓存（丢一两条可接受）；
    4. 不适合：订单、支付这类不允许丢的消息；需要重放与审计的场景。

    六、示例代码/实操步骤

    # 1. 终端 A：订阅
127.0.0.1:6379> SUBSCRIBE news
Reading messages... (press Ctrl-C to quit)
1) "subscribe"
2) "news"
3) (integer) 1

# 2. 终端 B：发布（注意返回值是订阅者数）
127.0.0.1:6379> PUBLISH news "hello"
(integer) 1

# 3. 终端 A 收到
1) "message"
2) "news"
3) "hello"

# 4. 没有订阅者时：消息直接丢弃
127.0.0.1:6379> PUBLISH nobody:listens "lost"
(integer) 0

# 5. 模式订阅
127.0.0.1:6379> PSUBSCRIBE news.*
Reading messages...
127.0.0.1:6379> PUBLISH news.sports "goal"
(integer) 1
# 订阅端收到的第三个元素是匹配到的频道名，不是模式名

# 6. 观察订阅状况
127.0.0.1:6379> PUBSUB CHANNELS
1) "news"
127.0.0.1:6379> PUBSUB NUMSUB news
1) "news"
2) (integer) 1
127.0.0.1:6379> PUBSUB NUMPAT
(integer) 1

# 7. 订阅模式下只能执行少数命令
127.0.0.1:6379> SUBSCRIBE news
127.0.0.1:6379> GET k
(error) ERR only (P|S)SUBSCRIBE / (P|S)UNSUBSCRIBE / PING / QUIT / RESET are allowed in this context

# 8. 7.0+ 分片订阅（Cluster 下降低广播开销）
127.0.0.1:6379> SSUBSCRIBE orders
127.0.0.1:6379> SPUBLISH orders "created"

    Java 侧怎么落地：订阅要用容器托住长连接

    订阅是连接状态，所以 Java 侧不能临时 subscribe 一下就返回——必须有一个容器持有连接、自动重连并重订阅。

    1. pom 只引 starter，Spring Data Redis 自带 RedisMessageListenerContainer。
    <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
    1. 容器 + 独立线程池：容器负责长连接与断线重连（重连后自动重新订阅），线程池不要和业务线程池共用，否则一条慢消息会拖垮全部订阅：
    @Bean
RedisMessageListenerContainer listenerContainer(RedisConnectionFactory f, MessageListener l) {
    RedisMessageListenerContainer c = new RedisMessageListenerContainer();
    c.setConnectionFactory(f);
    c.addMessageListener(l, new ChannelTopic("news.sports"));   // 尽量用精确频道
    c.setTaskExecutor(Executors.newFixedThreadPool(4));
    return c;
}

    1. 消费侧必须自己幂等：PUBLISH 是至多一次，反过来也可能重复（重连、订阅重叠），消息体带上业务 ID + 时间戳，消费侧按 ID 去重。

    2. 加「最后一条消息时间」监控：连上了但半开连接时，容器不会立刻发现；超过 N 分钟没收到任何消息就告警，必要时主动重连。

    3. 关键链路别用 Pub/Sub 承载：订单、扣款这类不能丢的，改走 Stream 消费组（RD38）或外部 MQ；Pub/Sub 只做「丢了也无所谓」的通知（配置变更、在线状态）。

    4. Cluster 下用 SSUBSCRIBE（7.0+）：普通 SUBSCRIBE 会把消息广播到所有节点，节点一多开销成倍；分片订阅只走槽归属节点。

    七、常见坑（官方明确说明的限制）

    1. 把 Pub/Sub 当消息队列。没有持久化、没有确认、没有重投，业务一抖动就丢消息。
    2. 以为 PUBLISH 返回 1 就是「送达了」。它只表示「当时有一个订阅者」，不代表对方业务处理成功。
    3. 用连接池做订阅。订阅是连接状态，短连接会立刻丢失订阅；必须用独立长连接。
    4. 应用重启忘记重新订阅。Redis 不保存订阅关系，重启后必须重新 SUBSCRIBE。
    5. 模式订阅开太多。每条消息都要与所有模式匹配，模式数量与发布延迟正相关。
    6. Cluster 下低估广播成本。默认全节点传播，节点越多开销越大，7.0+ 应用 SSUBSCRIBE。
    7. 不设输出缓冲上限。慢消费者会导致服务端缓冲区堆积，最终连接被断开；client-output-buffer-limit pubsub 要按业务量配置。
    8. 在订阅连接上执行普通命令。会报 ERR only (P|S)SUBSCRIBE ... allowed，客户端要单独维护订阅连接。

    版本差异（8.x 标注）

    6.2 起 PUBLISH 在集群中的传播机制有优化；7.0 引入分片订阅 SSUBSCRIBE/SPUBLISH。7.4 与 8.x 语义一致：仍是「至多一次、不持久化」。

    依据：https://redis.io/docs/latest/develop/interact/pubsub/

    八、课后小结

    • Pub/Sub 是实时广播：不持久化、不确认、不重投，至多一次；
    • PUBLISH 返回值是「当时在线订阅者数」，不是送达数；
    • 订阅是连接状态：必须长连接、必须重连后重新订阅；
    • 频道订阅精确匹配，模式订阅有逐条匹配开销；
    • Cluster 下默认全节点广播，7.0+ 用 SSUBSCRIBE 降低开销；
    • 不允许丢消息的场景必须换 Stream 消费组。

    九、思考题

    1. 为什么 PUBLISH 返回 0 时不报错？这个设计对业务有什么风险？

      参考回答：没有订阅者是正常状态而不是错误，所以返回 0。风险是业务把 PUBLISH 当可靠投递：没人订阅时消息静默丢弃，日志与监控都显示「发布成功」，数据丢了却没有告警。要么监控订阅者数，要么关键链路换 Stream。

    2. 「至多一次」与「至少一次」的差别在哪？各举一个适合的业务。

      参考回答：至多一次 = 可能丢、绝不重；至少一次 = 不丢、可能重（要靠幂等消化）。适合至多一次：配置变更通知、在线状态广播、埋点采样；适合至少一次：订单创建事件、扣款通知（用 Stream 消费组）。

    3. 为什么订阅必须用长连接？用连接池会发生什么？

      参考回答：SUBSCRIBE 是连接状态，订阅后该连接进入订阅模式、只能执行少数命令。连接池的短连接归还后订阅关系就失效，或被下一个使用者「串台」，结果是消息丢失或投给错误业务。

    4. 100 个模式订阅、每秒 1 万条消息，发布路径会发生什么？

      参考回答：每条消息都要与 100 个模式逐个 glob 匹配，1 万条/秒 = 100 万次匹配/秒，且全在主线程；发布延迟上升、CPU 飙高，严重时拖慢所有命令。应减少模式数量、改用精确频道，或迁到 SSUBSCRIBE。

    5. Cluster 有 20 个节点，一条 PUBLISH 会经过几次网络传输？SSUBSCRIBE 能省掉什么？

      参考回答：默认要广播到全部 20 个节点，即约 20 份节点间转发（每节点再投给本地订阅者）。SSUBSCRIBE 只把消息送到槽归属节点，省掉其余 19 份转发，开销与节点数解耦。
