    redis-27-dict 与 rehash

    📅 2023-01-17

    dict 与渐进式 rehash

    dict 的 ht[0]/ht[1] 双表、扩容与缩容触发条件、迁移期的四个行为变化｜依据 Redis 7.4 源码与官方文档自绘

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 讲清「一个 dict 两个哈希表」的结构，以及为什么扩容不能一次搬完；
    2. 说清 load factor 的两档触发条件（1 与 5），以及 BGSAVE 为什么会改变判定；
    3. 用 INTO 类观测与延迟现象判断实例是不是正处于 rehash 中。

    二、前置知识

    RD07（Hash 类型）、RD26（redisObject 与编码）。dict 不只是 Hash 的底层，也是整个 Redis 的「键空间字典」，每个 db 的 key 表就是 dict。

    三、理论讲解（官方定义）

    dict.c 的注释说明了设计动机（原文要点）：

    The rehashing is performed incrementally … because performing it in a blocking way would be too slow for large dictionaries.

    —— https://github.com/redis/redis/blob/7.4/src/dict.c

    以及扩容判定（dictExpandIfNeeded，原文要点）：

    if the hash table is empty, expand it to the initial size … if the load factor is greater than 1 and we are not doing a background save, expand … otherwise if the load factor is above 5, force the expansion.

    翻译成两句人话：

    • load factor > 1 且没有 BGSAVE → 扩容；
    • load factor > 5 → 不管有没有 BGSAVE 都强制扩容。

    四、原理拆解

    1. 两个哈希表的分工

    dict
├── ht[0]  ← 当前服务请求的表
└── ht[1]  ← rehash 期间才创建，作为迁移目标
    type / privdata / rehashidx

    rehashidx 是进度游标：-1 表示没在 rehash，≥ 0 表示「已迁移到这个桶」。整张 dict 有且只有一个 rehashidx，这决定了同一时刻只能有一次 rehash 在跑。

    2. 为什么要「渐进式」

    一次性 rehash 需要遍历所有桶并重新挂链，时间复杂度与元素数成正比。一个千万级 key 的实例，一次扩容可能阻塞几百毫秒到数秒——期间所有命令都排队。Redis 的选择是把这次搬迁摊到后续的每次读写操作里：每处理一次请求，顺手迁移一个桶（_dictRehashStep），另加 serverCron 里的定时任务每秒搬一部分（dictRehashMilliseconds）。

    3. 迁移期的四个行为变化

    操作
    行为
    原因
    查找
    先 ht[0]，再 ht[1]
    数据可能在旧表也可能在新表
    写入
    只写 ht[1]
    保证新数据不在旧表，避免迁移时重复搬
    删除 / 更新
    两张表都要尝试
    元素位置不确定
    遍历（SCAN）
    允许重复、保证不丢
    见下节

    「写入只写 ht[1]」这一条是关键：它保证 ht[0] 里的元素数量只减不增，rehash 一定能收敛。

    4. 扩容与缩容的尺寸

    • 扩容：ht[1] 的大小 = 第一个大于等于 used * 2 的 2 的幂；
    • 缩容：load factor < 0.1 时触发，ht[1] 大小 = 第一个大于等于 used 的 2 的幂。

    缩容阈值定得这么低（0.1）是有意的：避免「删一点就缩、再写又扩」的抖动。

    5. SCAN 与 rehash 的关系

    SCAN 的游标基于桶的倒序二进制遍历，官方承诺：

    A full iteration always retrieves all the elements that were present … from the start to the end of a full iteration … elements may be returned multiple times.

    —— https://redis.io/docs/latest/commands/scan/

    所以 rehash 期间 SCAN 可能重复返回某些 key，但不会漏。如果你的业务用 SCAN 做「一次性导出」，必须做去重。

    渐进式 rehash 的五步、扩容缩容两档阈值与迁移期的四个行为变化｜依据 dict.c 注释与 SCAN 文档自绘

    五、场景说明

    1. 大 Hash 的扩容抖动：一个 100 万字段的 Hash，从 listpack 转 hashtable 时会一次性重建（RD28 讲编码转换），之后才是渐进式扩容；
    2. key 空间爆炸：DBSIZE 从百万涨到千万，dict 会多次翻倍，每次翻倍都伴随一段 rehash；
    3. 延迟毛刺排查：rehash 与 fork、AOF 重写叠加时，P99 会明显抬高——这三个是同一类「异步大动作」；
    4. 缩容抖动：大批 key 过期后用 FLUSHDB 删空，dict 会缩容到最小。

    六、示例代码/实操步骤

    # 1. 看当前 dict 的状态（info 里的 overhead 与 rehash 迹象）
127.0.0.1:6379> INFO memory
# used_memory_human:...
# mem_overhead_ratio:...              # 结构开销占比

# 2. 观察扩容对延迟的影响：写入大量 key 后测 P99
127.0.0.1:6379> DEBUG POPULATE 1000000
OK
127.0.0.1:6379> INFO stats
# instantaneous_ops_per_sec:...

# 3. 用 LATENCY 观察命令级毛刺（rehash 会体现为 command 事件）
127.0.0.1:6379> CONFIG SET latency-monitor-threshold 10
OK
127.0.0.1:6379> LATENCY LATEST
1) 1) "command"
   2) (integer) 1720000000
   3) (integer) 15
   4) (integer) 15

# 4. SCAN 在 rehash 期间的行为：可能重复，但不漏
127.0.0.1:6379> SCAN 0 COUNT 100
# 游标随手记下结果，去重后与 DBSIZE 对比
127.0.0.1:6379> DBSIZE
(integer) 1000000

# 5. Hash 的字段数接近阈值时观察编码（编码转换是一次性的重建）
127.0.0.1:6379> HSET big f1 v1
127.0.0.1:6379> OBJECT ENCODING big
"listpack"
# 写入第 129 个字段后：
127.0.0.1:6379> OBJECT ENCODING big
"hashtable"                          # 一次性转换完成

# 6. 避免抖动：分批导入而不是一次性灌入
# 客户端侧每批 1 万条 + sleep，把扩容摊开到多个时间窗

    Java 侧怎么落地：别把 rehash 打成毛刺

    rehash 本身不阻塞，但「一次性灌入几十万 key」会让它连续触发扩容，叠加 fork 就是 P99 尖刺。Java 侧要做的是控节奏。

    1. pom 不变，仍然是 spring-boot-starter-data-redis；关键是写入方式。

    2. 批量灌数据要分批 + 限速，每批之间留一个空窗，让 cron 的 1ms 补搬跟上来：

    // 反例：pipeline 里塞 50 万个 HMSET，一次触发多次扩容
// 正例：按 2000 一批，批间 sleep，给渐进式 rehash 留时间
for (List<Map.Entry<String, String>> batch : partition(entries, 2000)) {
    stringRedisTemplate.executePipelined((RedisCallback<Object>) conn -> {
        batch.forEach(e -> conn.hSet(e.getKey().getBytes(), "f".getBytes(), e.getValue().getBytes()));
        return null;
    });
    Thread.sleep(20);
}

    1. 预热而不是冷启：灰度前先用脚本把热 key 铺进去，让扩容发生在低峰；生产启动瞬间涌入新 key 是最容易出毛刺的时刻。

    2. 遍历用 SCAN，不要 KEYS，并且必须允许重复——rehash 期间游标会重复返回，去重放在应用层：

    Set<String> seen = new HashSet<>();
ScanOptions opt = ScanOptions.scanOptions().count(1000).match("user:*").build();
try (Cursor<String> cur = stringRedisTemplate.scan(opt)) {
    cur.forEachRemaining(k -> { if (seen.add(k)) handle(k); });   // 重复不致命，漏才致命
}
    1. 观测：盯 used_memory 与 latency_percentiles_usec，rehash 与 fork、AOF 重写叠加时才最像故障。

    七、常见坑（官方明确说明的限制）

    1. 以为扩容是「瞬间完成」。渐进式 rehash 期间内存会同时保留两张表，used_memory 会比数据量高出 1.5–2 倍，这是正常的中间态。
    2. load factor ≥ 5 时才慌。1 与 5 的差别是：前者在持久化时被抑制（怕 CoW 放大内存），后者不再抑制。
    3. 把 BGSAVE 当成与 rehash 无关。BGSAVE 期间 CoW 会复制被写的页，此时扩容会显著增加内存占用，所以官方选择「有 BGSAVE 就暂缓」。
    4. SCAN 结果直接当唯一集合。官方明确可能重复返回，必须去重。
    5. 以为缩容很快。缩容同样是渐进式的，删完 key 后内存不会立刻归还。
    6. DEBUG POPULATE 用在生产。它会一次性灌入大量 key，触发大规模扩容与 rehash，只能在测试环境用。
    7. rehashidx 卡住不动。如果实例长期没有写入、serverCron 又被慢命令阻塞，rehash 会停在半途，表现为「内存一直是两倍」。
    8. Hash 字段数远超阈值。hashtable 编码的每个字段都有独立 entry 开销，比 listpack 贵得多，这是「大 Hash 吃内存」的原因。

    版本差异（8.x 标注）

    渐进式 rehash 机制在 7.x 与 8.x 之间一致；8.x 未改变 load factor 判定与 SCAN 保证。差异在于新数据类型与模块对 dict 的使用方式，核心结构不变。

    依据：https://github.com/redis/redis/blob/7.4/src/dict.c

    八、课后小结

    • dict = ht[0]（服务中）+ ht[1]（迁移目标）+ rehashidx（进度）；
    • 扩容：load factor ≥ 1 且无 BGSAVE，或 load factor ≥ 5 强制；缩容：< 0.1；
    • 渐进式 rehash 把搬迁摊到每次操作与每秒定时任务里，避免单次阻塞；
    • 迁移期：查两张表、只写新表、删改两张表、SCAN 可能重复但不会漏；
    • 扩容期内存会翻倍（两表并存），属预期；
    • rehash 与 fork、AOF 重写同属「异步大动作」，是延迟毛刺的常见来源。

    九、思考题

    1. 为什么「写入只写 ht[1]」能保证 rehash 一定收敛？如果写进 ht[0] 会怎样？

      参考回答：新键只进新表，旧表只减不增，ht[0].used 单调下降，rehashidx 必然推进到 -1。若允许写进 ht[0]，旧表边搬边增，迁移可能永远追不上，甚至触发二次扩容。

    2. load factor 1 与 5 两档条件，分别对应什么风险？

      参考回答：1 是常规扩容，兼顾冲突与内存；5 是强制扩容——BGSAVE 期间 fork 的 CoW 会让内存占用虚高，按 1 会误判成「该扩」，5 档避免频繁扩容。风险都指向同一件事：load factor 越高，桶内链越长约等于 O(N) 退化。

    3. rehash 期间 used_memory 涨到数据量的 2 倍，这是泄漏吗？怎么验证？

      参考回答：不是泄漏，是 ht[1] 已经分配、两张表并存的中间态，完成即回落。验证：看 INFO memory 的 used_memory 是否在持续写入后回落、MEMORY STATS 的 hashtable overhead；长期不回落说明实例没有写入且 cron 被慢命令堵住。

    4. SCAN 在 rehash 中为什么会重复返回 key 却不漏？这对「导出全量数据」有什么要求？

      参考回答：桶搬迁会让游标回头重扫刚搬走的那一段，于是同一个 key 可能被返回两次；但游标同时覆盖两张表，已搬的在新表、未搬的在旧表，所以不漏。导出要求：应用层按 key 去重、不依赖返回顺序、不在遍历中做破坏性修改。

    5. 一个实例长期只有读请求、没有写请求，rehash 会怎么进行？

      参考回答：读路径的查找同样会触发一步 rehash，所以会随读请求慢慢推进；如果连读都没有，只剩 cron 每秒 1ms 的补搬，极慢但最终会完成。
