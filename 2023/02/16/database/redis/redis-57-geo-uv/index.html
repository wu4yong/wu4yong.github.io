    redis-57-GEO 实战

    📅 2023-02-16

    附近商户、签到与 UV

    三个典型业务场景各自对应的数据结构与坑｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你能做到：

    1. 用 GEOADD + GEOSEARCH 做「附近的商户」，并说清坐标顺序；
    2. 用 SETBIT 做签到、BITCOUNT 统计当日人数，并估算位图内存；
    3. 用 PFADD / PFCOUNT 做 UV 统计，说清 0.81% 误差意味着什么。

    二、前置知识

    RD09（ZSet，GEO 的底层）、RD11（Bitmap 与 HLL 入门）、RD12（TTL 清理）。这一讲是系列最后一讲，把「结构选型」落到三个具体业务上。

    三、理论讲解（官方定义）

    GEO 的官方说明（原文要点）：

    Redis GEO commands … store longitude/latitude pairs in a sorted set … GEOADD adds members, GEOSEARCH queries within a radius or box … the underlying representation uses a 52-bit geohash integer score.

    —— https://redis.io/docs/latest/commands/geoadd/

    两点要注意：参数顺序是「经度、纬度、成员」（longitude first）；底层是 ZSet，所以 GEO key 也能用 ZSet 命令，但不要混用（会破坏 score 语义）。

    HyperLogLog 的官方说明（原文要点）：

    HyperLogLog is a probabilistic data structure used to estimate the cardinality of a set … standard error is 0.81% … the maximum memory used is about 12 KB per key.

    —— https://redis.io/docs/latest/commands/pfadd/

    「0.81% 误差」意味着：真实 UV 100 万时，估计值可能差 ±8 千。用于「看趋势、算大盘」完全够，用于「精确对账、算钱」不行。

    Bitmap 的官方说明（原文要点）：

    SETBIT key offset value … bit operations on strings … offsets are counted from 0.

    —— https://redis.io/docs/latest/commands/setbit/

    位图的内存 = 最大 offset / 8 字节。用用户 ID 做 offset，如果 ID 是 10 亿级，位图会非常稀疏且非常大。

    四、原理拆解

    1. GEO：底层就是 ZSet

    GEOADD shop:city 104.06 30.67 shop_1     # 经度 104.06，纬度 30.67
GEOSEARCH shop:city FROMMEMBER shop_1 BYRADIUS 1 km ASC COUNT 20
    • FROMMEMBER 以某个已存在成员为圆心，FROMLONLAT 用坐标；
    • BYRADIUS 半径 / BYBOX 矩形；
    • 返回的是「按距离排序的成员列表」，距离要用 GEODIST 单独取。

    坑的根源：把经纬度写反。写反不会报错（只要数值在合法范围内），但结果会跑到地球另一端。

    2. 签到：Bitmap 的本质是「按天分 key」

    SETBIT sign:20230216 1001 1      # 用户 1001 今天签到
GETBIT sign:20230216 1001        # 是否已签到
BITCOUNT sign:20230216           # 今天签到人数
    • 一天一个 key，EXPIRE 让它自动过期；
    • BITCOUNT 是 O(N) 但 N 是位图字节数，百万级用户也就百来 KB，很快；
    • offset 用用户 ID 的前提是 ID 连续且量级可控；ID 稀疏时改用「分配序号」或改用 SET。

    3. UV：HyperLogLog 只给「数量」，不给「是谁」

    PFADD uv:20230216 u1001 u1002 u1003
PFCOUNT uv:20230216              # 近似基数
    • 内存固定约 12KB，跟用户规模无关——这是它最大的价值；
    • 不能删元素、不能列出成员；
    • PFMERGE 可以合并多个 HLL（比如合并一周的 UV），但合并也是近似。

    4. 三个结构的选择逻辑

    需求
    结构
    为什么
    按距离排序找商户
    GEO（ZSet）
    天然有序 + 半径查询
    今天谁签到了（要精确名单）
    Bitmap / Set
    需要精确到人
    今天来了多少人（只要数量）
    HyperLogLog
    内存固定、误差可接受

    GEO（ZSet + 52 位 geohash，经度在前）、Bitmap 按天分 key 的 offset 成本、HLL 的 12KB 与 0.81% 误差，以及三个结构对应的三个需求与各自的坑｜依据 GEOADD、SETBIT、PFADD 官方文档自绘

    五、场景说明

    1. 本地生活：GEO 找附近商户，配合分页与业务过滤；
    2. 签到打卡：Bitmap 按天分 key，连续签到天数另用 HASH 或计数器维护；
    3. 内容 UV / 大盘统计：HLL 按天分 key，PFMERGE 汇总周/月；
    4. 不适合：要求「精确去重名单」的抽奖——必须用 Set/Bitmap，HLL 给不出名单。

    六、示例代码/实操步骤

    # 1. GEO：添加三家商户（经度在前，纬度在后）
127.0.0.1:6379> GEOADD shop:leshan 103.76 29.55 shop_1
(integer) 1
127.0.0.1:6379> GEOADD shop:leshan 103.77 29.56 shop_2 103.75 29.54 shop_3
(integer) 2

# 2. 查附近 2 公里内的商户，按距离升序
127.0.0.1:6379> GEOSEARCH shop:leshan FROMMEMBER shop_1 BYRADIUS 2 km ASC COUNT 10
1) "shop_1"
2) "shop_2"

# 3. 用坐标查（不依赖已有成员）
127.0.0.1:6379> GEOSEARCH shop:leshan FROMLONLAT 103.76 29.55 BYBOX 4 4 km ASC

# 4. 两地距离（单位可选 m/km/mi/ft）
127.0.0.1:6379> GEODIST shop:leshan shop_1 shop_2 km
"1.4142"

# 5. 签到：位图按天分 key
127.0.0.1:6379> SETBIT sign:20230216 1001 1
(integer) 0                    # 返回该位原来的值
127.0.0.1:6379> SETBIT sign:20230216 1002 1
(integer) 0
127.0.0.1:6379> GETBIT sign:20230216 1001
(integer) 1
127.0.0.1:6379> BITCOUNT sign:20230216
(integer) 2
127.0.0.1:6379> EXPIRE sign:20230216 2592000
(integer) 1                    # 保留 30 天后自动清理

# 6. UV：HyperLogLog
127.0.0.1:6379> PFADD uv:20230216 u1001 u1002 u1003
(integer) 1                    # 1 表示基数发生变化
127.0.0.1:6379> PFCOUNT uv:20230216
(integer) 3
127.0.0.1:6379> PFADD uv:20230216 u1001
(integer) 0                    # 已存在，基数不变

# 7. 合并一周 UV（近似，不精确）
127.0.0.1:6379> PFMERGE uv:week uv:20230213 uv:20230214 uv:20230215 uv:20230216
127.0.0.1:6379> PFCOUNT uv:week

# 8. 观察内存（HLL 应稳定在 12KB 左右）
127.0.0.1:6379> MEMORY USAGE uv:20230216
(integer) 12336

    Java 侧怎么落地：三个结构对应三个 API

    1. pom 只引 starter，GEO / Bitmap / HLL 都在 RedisTemplate 的现成操作类里。
    <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
    1. application.yml：key 前缀与保留天数外置，三个场景都按日期分 key：
    geo:
  key: shop:city
sign:
  prefix: sign:
  keep-days: 30
uv:
  prefix: uv:
spring:
  data:
    redis:
      timeout: 300ms
    1. GEO：Point(x=经度, y=纬度)，顺序写反不会报错但结果会跑到地球另一端：
    redis.opsForGeo().add("shop:city", new Point(103.76, 29.55), "shop_1");
GeoResults<RedisGeoCommands.GeoLocation<String>> r = redis.opsForGeo()
    .search("shop:city", GeoReference.fromMember("shop_1"),
            new RedisGeoCommands.GeoSearchCommandArgs().limit(10));
    1. Bitmap：一天一个 key，offset 是用户序号（不是原始大 ID），签到后统一设 TTL：
    String k = "sign:" + date;
redis.opsForValue().setBit(k, seq, true);          // seq 为连续序号
redis.expire(k, Duration.ofDays(30));
Long today = (Long) redis.execute((RedisCallback<Object>) c -> c.bitCount(k.getBytes()));
    1. HLL：只加不改，size() 即近似基数；周/月用 union() 汇总后单独存一个 key，别直接读明细日 key：
    redis.opsForHyperLogLog().add("uv:" + date, uid);
long uv = redis.opsForHyperLogLog().size("uv:" + date);
redis.opsForHyperLogLog().union("uv:week", "uv:20230213", "uv:20230214", "uv:20230215", "uv:20230216");

    1. 清理用一个定时任务：SCAN 匹配前缀（禁用 KEYS），对没有 TTL 的日 key 补 EXPIRE；跨月汇总完就把明细删掉。

    2. 精度分级使用：大盘 UV、转化漏斗用 HLL；涉及钱与名单（中奖、返现、风控名单）用 Set/Bitmap 精确统计。

    七、常见坑（官方明确说明的限制）

    1. GEOADD 经纬度写反。不报错，但结果在地球另一端；记住「经度在前」。
    2. 对 GEO key 用普通 ZSet 命令。会破坏 score 语义，导致距离查询失效。
    3. Bitmap 用超大用户 ID 做 offset。位图稀疏且巨大，内存按「最大 offset / 8」算。
    4. 签到 key 不设 TTL。一年后你会有一堆没人管的日 key。
    5. 以为 HLL 能列出成员。它只给基数，不给名单（官方明确是概率型结构）。
    6. 用 HLL 做需要精确的业务。0.81% 误差在百万级就是几千人的偏差，算钱不能用。
    7. PFADD 返回值误解。返回 1 只表示「基数可能变化」，不是「新增了一个用户」。
    8. KEYS sign:* 做清理。O(N) 阻塞主线程，必须用 SCAN 或依赖 TTL。

    版本差异（8.x 标注）

    GEO 命令（GEOSEARCH 自 6.2 取代 GEORADIUS）在 7.4 与 8.x 语义一致；Bitmap 与 HLL 的命令与误差说明未变。做「附近」功能优先用 GEOSEARCH，GEORADIUS 已被标记为弃用方向。

    依据：https://redis.io/docs/latest/commands/geosearch/

    八、课后小结

    • GEO 底层是 ZSet + 52 位 geohash，参数顺序「经度、纬度、成员」；
    • 签到用 Bitmap 按天分 key，精确到人，注意 offset 量级；
    • UV 用 HyperLogLog，12KB 固定内存、0.81% 误差，只给数量；
    • 三个结构都按日期分 key + TTL，避免历史 key 堆积；
    • 要精确名单就别用 HLL。

    九、思考题

    1. 用户 ID 最大 10 亿，用 Bitmap 做签到，位图多大？你会怎么优化？

      参考回答：内存 = 最大 offset / 8 = 10 亿 / 8 ≈ 125 MB，而且是按最大 ID 撑开的稀疏位图，实际签到用户可能只有几千。优化：把 uid 映射成连续序号（注册时分配 1..N）再当 offset；或按用户分桶拆成多个 key（sign:date:{0..99}）；或直接改用 Set（人数少时更省）。

    2. GEOSEARCH 返回的顺序由什么决定？要按距离排序需要加什么参数？

      参考回答：默认按底层 ZSet 的 score（52 位 geohash）排序，与距离无关。要按距离升序必须加 ASC（降序用 DESC），并可配 COUNT n 限量；距离数值本身还要用 GEODIST 或 WITHDIST 取。

    3. HLL 估计 100 万 UV，误差范围是多少？什么业务不能接受？

      参考回答：标准误差 0.81%，100 万时约 ±8 千。不能接受的业务是「按人数算钱或定名单」的：抽奖中奖、返现分摊、风控名单、需要精确去重的报表核对——这些必须用 Set/Bitmap。

    4. 一周 UV 用 PFMERGE 合并，与「把一周数据都 PFADD 进一个 key」等价吗？

      参考回答：在估计值上近似等价——PFMERGE 本质是对各 HLL 的寄存器取最大值，与把所有元素直接 PFADD 进同一个 HLL 得到的结果一致（误差仍 0.81%）。真正的差别在运维：合并后无法还原明细、日 key 过期后不能再合并，且不能给出成员名单。

    5. 三个场景的 key 都会按日期分，你打算怎么设计清理策略？

      参考回答：① 写入时就设 TTL（签到 30 天、UV 明细 7～35 天），靠惰性删除兜底；② 周/月先用 PFMERGE 汇总成新 key 再删明细；③ 活动/门店类 key 在活动结束后由定时任务清理；④ 巡检用 SCAN 找无 TTL 的 key，绝不用 KEYS。

    十、官方资料

    • GEOADD / GEOSEARCH / GEODIST：https://redis.io/docs/latest/commands/geosearch/
    • SETBIT / GETBIT / BITCOUNT：https://redis.io/docs/latest/commands/setbit/
    • PFADD / PFCOUNT / PFMERGE：https://redis.io/docs/latest/commands/pfadd/
    • Bitmaps 数据类型说明：https://redis.io/docs/latest/develop/data-types/bitmaps/
    • HyperLogLog 误差与内存说明：https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/
