    redis-48-ACL

    📅 2023-02-07

    ACL 权限模型

    用户身份、命令权限、key 模式、频道模式四段结构｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你能做到：

    1. 用 ACL SETUSER 写出一条完整规则，并说清 +@read、~app:*、&pub:* 各管什么；
    2. 用 ACL GETUSER / ACL LOG 验证规则是否真的生效；
    3. 说清为什么官方推荐用 ACL 取代 rename-command。

    二、前置知识

    RD03（配置文件与 CONFIG）、RD04（命令与协议）。M8 从这一讲开始：先把「谁能连、能干什么」管住，再谈加密与运维。

    三、理论讲解（官方定义）

    ACL 的官方定义（原文要点）：

    Redis ACLs … allow you to define users, and for each user define the commands and keys that the user can access.

    Rules are expressed as a list of tokens … you can specify commands (+set, -@all), key patterns (~prefix:*), channel patterns (&channel), and passwords (>password).

    —— https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/

    关键结论三条：

    1. 没有 ACL 之前的 requirepass 只是「一道门」，进门之后所有命令都能跑；
    2. ACL 把权限拆成命令类别、单条命令、key 模式、频道模式、密码几段；
    3. default 用户是内置的，未做任何配置时它拥有一切权限。

    关于「用 ACL 取代 rename-command」，官方文档在安全章节里明确建议：优先用 ACL 限制危险命令，只有在无法使用 ACL 的旧版本才考虑改名，并且改名会让客户端与工具链失效（如 CONFIG、DEBUG 改名后集群工具与监控脚本无法工作）。

    四、原理拆解

    1. 一条规则的四段

    ACL SETUSER app_ro on >pwd123 ~app:* ~cache:* +@read -@write -@dangerous
              └┬┘ └┬┘ └───┬───┘ └──┬──┘  └──┬───┘ └────┬─────┘
             用户  启用  密码     key 模式   命令权限    命令权限
    • 用户总线：user <name> 创建/编辑用户（在 ACL SETUSER 里 name 直接作为第一个参数）；
    • 启用位：on / off，nopass 表示免密（等于没有密码，慎用）；
    • key 段：~pattern 允许访问的 key 前缀，%R~ / %W~ 可分别限定读/写（7.0 引入）；
    • 命令段：+@all 全开、-@all 全关、+get 单命令、-@dangerous 排除危险类别。

    没有 ~ 的用户一条 key 都访问不了；没有 +/+@all 的用户一条命令都执行不了——这是新手最容易踩的空规则问题。

    2. 权限是「叠加 + 覆盖」，不是「取交集」

    规则按顺序生效：后写的覆盖先写的。所以常见写法是「先全开再收紧」：

    ACL SETUSER app on >pwd +@all -@dangerous ~app:*

    这与「先全关再逐条加」是两条不同的思路：前者漏项风险高，后者维护成本高。生产上更推荐后者（最小权限），并配合 ACL LOG 找出被拒的常用命令再逐条放开。

    3. key 模式的含义是「可见性」

    ~app:* 不只是「允许读写 app: 开头的 key」，它还影响 KEYS、SCAN、MGET、DEL 等命令能看到哪些 key。这意味着：

    • 限制 key 模式后，KEYS * 只能看到被允许的 key；
    • MGET a b c 若其中有不被允许的 key，会返回错误（不是部分成功）。

    4. 分布式场景的两个细节

    • 集群与哨兵也需要 ACL：masterauth / requirepass 之外，还要给复制连接配置带 +psync 等权限的用户，否则主从握手失败；
    • ACL 文件持久化：aclfile 指定的文件会持久化 ACL SETUSER 的结果，但通过 ACL SETUSER 改动的规则若不写 ACL SAVE，重启会丢失（配置文件中直接写 user ... 的才不会）。

    一条规则的「用户 / 密码与启停 / key 模式 / 命令权限」四段拆解、后写覆盖先写的叠加语义，以及复制与哨兵连接的授权缺口｜依据 ACL 文档自绘

    五、场景说明

    1. 读写分权：app_ro 只有 +@read，app_rw 加 +set +del +expire；
    2. 按业务前缀隔离：~order:* / ~user:* 分给不同服务，避免互相覆盖；
    3. 禁用管理命令：-@admin -config -flushall -keys；
    4. 监控与审计：只读账号 + +info +slowlog，供巡检脚本使用。

    六、示例代码/实操步骤

    # 1. 看当前有哪些用户与规则
127.0.0.1:6379> ACL LIST
1) "user default on nopass ~* &* +@all"

# 2. 建一个只读用户
127.0.0.1:6379> ACL SETUSER app_ro on >pwd123 ~app:* ~cache:* +@read -@write
OK

# 3. 建一个读写用户（先全开再禁危险命令）
127.0.0.1:6379> ACL SETUSER app_rw on >pwd456 ~app:* +@all -@dangerous
OK

# 4. 验证：查看某个用户的完整规则
127.0.0.1:6379> ACL GETUSER app_ro
1) "flags"
2) 1) "on"
3) "passwords"
4) 1) "5f9c...(sha256)"
5) "commands"
6) "-@all +@read -@write"
7) "keys"
8) "~app:* ~cache:*"
9) "channels"
10) ""

# 5. 登录后确认身份
$ redis-cli --user app_ro --pass pwd123
127.0.0.1:6379> ACL WHOAMI
"app_ro"

# 6. 被拒请求会记录在 ACL LOG 里（定位「到底缺哪条权限」）
127.0.0.1:6379> ACL LOG
1) 1) "count"
   2) (integer) 3
   3) "reason"
   4) "command"
   5) "context"
   6) "toplevel"
   7) "object"
   8) "set"

# 7. 持久化规则（用 aclfile 时）
127.0.0.1:6379> ACL SAVE
OK

# 8. 禁用默认用户（务必先把管理员账号配好）
127.0.0.1:6379> ACL SETUSER default off
OK

    Java 侧怎么落地：每个微服务一个 ACL 用户

    1. pom 只引 starter，ACL 是服务端能力，客户端只要能把用户名密码带上。
    <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
    1. application.yml 用 username（不是只有 password）：Spring Boot 2.4+ 会据此发 AUTH user pass：
    spring:
  data:
    redis:
      host: 10.0.0.11
      port: 6379
      username: order_svc
      password: ${REDIS_ORDER_PWD}
      timeout: 500ms
    1. 按服务划 key 前缀，一服务一账号：订单服务只用 ~order:*，用户服务只用 ~user:*，互相看不见对方的 key（KEYS/SCAN 也受限）。
    ACL SETUSER order_svc on >pwd -@all +@read +@write +@keyspace ~order:* &order:*
    1. 启动时自检身份，防止配错用户名静默连上 default（那等于全权限）：
    String who = redis.execute((RedisCallback<String>) c ->
        new String((byte[]) c.execute("ACL".getBytes(), "WHOAMI".getBytes())));
if (!"order_svc".equals(who)) throw new IllegalStateException("redis acl mismatch: " + who);

    1. 规则进配置管理，并写 aclfile：users.acl 纳入版本库，改完 ACL SAVE；否则 ACL SETUSER 只改内存，重启回滚。

    2. 排查被拒用 ACL LOG（会给出 reason=command/key 与具体对象），比猜「是不是权限不够」快得多；复制与哨兵要单独授权 +psync +replconf +ping +info（哨兵另加 +sentinel +publish +subscribe）。

    七、常见坑（官方明确说明的限制）

    1. 只设密码不设 ACL。requirepass 是全权限通行证，泄露即全丢。
    2. 规则里漏了 ~ 或 +。用户连不上任何 key / 执行不了任何命令，报错信息还很含糊。
    3. 用 rename-command 禁命令。官方建议改用 ACL；改名会破坏客户端、集群工具与监控脚本。
    4. nopass 当成「无需密码」的便利。它等于「谁都能以这个用户身份操作」。
    5. 改完不 ACL SAVE。用 aclfile 时，ACL SETUSER 的结果不落盘，重启即恢复旧规则。
    6. 忘了给复制/哨兵连接授权。主从握手、Sentinel 探测用独立连接，缺少 +psync 等权限会持续失败。
    7. key 模式写得太宽（~*）。等于没做隔离，FLUSHALL 一条就能清掉全部数据。
    8. 不查 ACL LOG。被拒命令只在日志里，不看就永远不知道线上缺哪条权限。

    版本差异（8.x 标注）

    ACL 自 6.0 引入；7.0 增加 key 级读写分离（%R~ / %W~）与 ACL GETUSER 的更多字段；8.x 沿用同一套语义。若从 6.x 升级，注意旧客户端的 AUTH 单参数写法仍可用但不再推荐。

    依据：https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/

    八、课后小结

    • ACL = 用户 + 命令权限 + key 模式 + 频道模式 + 密码；
    • 新用户默认零权限，必须显式给 + 与 ~；
    • 规则后者覆盖前者，最小权限从 -@all 起更安全；
    • 用 ACL GETUSER 验证、ACL LOG 定位被拒原因；
    • 官方推荐用 ACL 而非 rename-command 来收缩危险命令。

    九、思考题

    1. 一个用户只有 ~app:* 没有 +@read，他能做什么？

      参考回答：什么也做不了。他能通过认证连上，但任何命令都会返回 NOPERM——ACL 里「key 可见」和「命令可用」是两套独立开关，缺一个就等于零权限。

    2. 为什么 MGET 里只要有一个 key 不被允许就会整体失败？

      参考回答：MGET 是单条命令，ACL 在命令入口一次性校验所有 key；只要有一个越权就整条拒绝，避免「部分成功」把不存在/无权访问的 key 信息泄露出去。所以按前缀分权时，批量读的 key 必须同属一个前缀。

    3. ACL SETUSER 改动为什么可能重启后失效？怎么避免？

      参考回答：ACL SETUSER 只写内存，配置了 aclfile 时必须执行 ACL SAVE 才会落盘；直接写在 redis.conf 里的 user ... 才会随配置加载。避免方法：规则进 users.acl 纳入版本管理，变更后 ACL SAVE，并把这一步做进发布流程。

    4. 主从复制连接需要哪些权限？漏配会看到什么现象？

      参考回答：至少 +psync +replconf +ping +info，哨兵另需 +sentinel +publish +subscribe。漏配时从库日志反复出现 MASTER <-> REPLICA sync started 后失败，INFO replication 里 master_link_status:down，哨兵则探测超时、报不出状态。

    5. 你会怎么设计「只读巡检账号」的完整规则？

      参考回答：ACL SETUSER ops_ro on >pwd -@all +@read +info +slowlog +memory +client|list ~* &*：先全关再逐条放，只给读类与观测命令，key 放开但明确禁写、禁管理命令（-config -flushall -keys），并单独保管密码、定期轮换。
