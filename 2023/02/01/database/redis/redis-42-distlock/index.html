    redis-42-分布式锁

    📅 2023-02-01

    分布式锁：SET NX 与 Lua 释放

    加锁四步、为什么必须一条命令、解锁的三个坑｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你能做到：

    1. 用一条 SET key val NX PX ms 完成加锁，而不是 SETNX + EXPIRE 两步；
    2. 写出「比对 val 相同才删除」的 Lua 解锁脚本，并说明为什么必须放在一个脚本里；
    3. 说清这把锁到底保证什么、不保证什么，不把它当成万能的事务替代品。

    二、前置知识

    RD04（RESP 与命令原子性）、RD34（Lua 脚本）、RD41（一致性的窗口）。这一讲是把「单节点上的原子命令」升级成「跨进程的互斥」。

    三、理论讲解（官方定义）

    SET 的官方选项定义（原文）：

    SET key value [NX | XX] [GET] [EX seconds | PX milliseconds | EXAT unix-time-seconds | PXAT unix-time-milliseconds | KEEPTTL]

    • NX – Only set the key if it does not already exist.
    • PX milliseconds – Set the specified expire time, in milliseconds.

    —— https://redis.io/docs/latest/commands/set/

    两条关键结论，官方原文已经给出：

    1. SET 是单条命令，执行是原子的（同一份文档的 Atomicity 段落：SET 的选项组合在一次执行中完成）；
    2. NX 与 PX 可以写在同一条 SET 里，因此「不存在则写入 + 设置过期」是原子完成的。

    这两点合起来就是分布式锁的基础：加锁必须是「判断 + 写入 + 设过期」三件事的一次原子动作。

    关于 Lua 的原子性（原文）：

    Scripts are executed atomically … no other script or command will run while a script is running.

    —— https://redis.io/docs/latest/develop/interact/programmability/eval-intro/

    所以「比对值 + 删除」也必须在一次脚本里完成。

    四、原理拆解

    1. 为什么要 SET NX PX，而不是 SETNX + EXPIRE

    错误写法：
  SETNX lock 1        ← 成功
  （进程在这里崩溃）
  EXPIRE lock 30      ← 永远执行不到
→ 这把锁永久存在，所有人都拿不到 → 死锁
    正确写法：
  SET lock <token> NX PX 30000
  → 要么「写入成功且带 30 秒过期」，要么「什么都不做」

    一条命令的原子性，消灭了「中间态崩溃」这一类故障。这是本讲最重要的一条，其他都是它的推论。

    2. token 的作用：只能删自己的锁

    A 加锁（token=A1，PX 30s）→ 执行业务超过 30s
  → 锁过期
B 加锁（token=B1）← 成功
A 业务结束 → DEL lock
  → 删掉了 B 的锁！现在 C 也能拿到锁 → 两个写者

    所以值必须是唯一标识（UUID + 请求 ID + 线程 ID），解锁时先比对：

    if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end

    3. 为什么校验和删除必须在同一段脚本里

    如果你在客户端做「GET 然后判断然后 DEL」，这中间有一个往返窗口：

    客户端 GET → 值是我的 → （此时锁过期、别人拿到锁）
客户端 DEL → 删掉的是别人的锁

    Lua 脚本在服务端一次执行完毕，中间不会插入其他命令，这个窗口就消失了。

    4. 锁保证什么、不保证什么

    • 保证：同一时刻最多一个持有者（在锁未过期、Redis 可用、无主从切换丢锁的前提下）；
    • 不保证：业务正确性。业务超时后锁已过期，你仍在写数据，此时「两个写者」事实上已经发生；
    • 不保证：Redis 主从异步复制下的强一致。主库写完锁、未同步就宕机，从库升主后这把锁不存在（RD43 讲 Redlock 也是在这个问题上做文章）。

    5. 工程上的三条配套

    • 过期时间 = 业务最长耗时 + 余量，并在业务结束时主动释放（不要等它自然过期）；
    • 获取失败要退避重试（几十毫秒随机），否则大量线程同时抢锁会产生惊群；
    • 业务里加版本号或幂等键，因为锁失效后仍可能并发写，最后一道防线是业务自己。

    SETNX + EXPIRE 的死锁路径、一条 SET NX PX 消除中间态、A 超时后误删 B 的锁的时间线，以及 Lua 比对解锁｜依据 Redis 7.4 · SET 与 EVAL 文档自绘

    五、场景说明

    1. 定时任务防重：同一任务只允许一个实例执行（效率锁）；
    2. 缓存重建互斥：RD40 的击穿解法；
    3. 库存扣减（需谨慎）：锁只是减少冲突，扣减本身仍需数据库条件更新；
    4. 不适合：需要「绝对正确」的资金操作——应该用数据库行锁/事务，锁服务只能减少冲突。

    六、示例代码/实操步骤

    # 1. 加锁：一条命令，带唯一 token 与 30 秒过期
127.0.0.1:6379> SET lock:order:1001 "u-9f3a-4721" NX PX 30000
OK                             # 成功
# 若已被占用，返回 (nil)

# 2. 查看锁的持有人与剩余时间（排查用）
127.0.0.1:6379> GET lock:order:1001
"u-9f3a-4721"
127.0.0.1:6379> PTTL lock:order:1001
(integer) 29876

# 3. 解锁：Lua 脚本，比对后删除（原子）
127.0.0.1:6379> EVAL "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end" 1 lock:order:1001 "u-9f3a-4721"
(integer) 1                    # 1=删掉了自己的锁；0=已被别人持有

# 4. 反例：这一步不是原子的，不要这么写
127.0.0.1:6379> GET lock:order:1001
"u-9f3a-4721"
127.0.0.1:6379> DEL lock:order:1001     # 中间可能已经易主

# 5. 观察锁竞争（多实例并发抢同一把锁）
127.0.0.1:6379> INFO commandstats
# cmdstat_set:calls=...,usec=...

    业务侧的骨架（任意语言）：

    for (retry in 1..3):
    ok = SET key token NX PX 30000
    if ok: try { doWork() } finally { unlockScript(key, token) }
    sleep(rand(20,80)ms)
throw TimeoutException

    Java 侧怎么落地：Redisson 只是把三条规矩封装了

    1. pom 换成 Redisson starter：它自带 Spring Boot 自动配置，锁的看门狗、Lua 解锁、可重入都由它实现，比手写 SET NX PX + EVAL 省事且不易写错。
    <dependency>
  <groupId>org.redisson</groupId>
  <artifactId>redisson-spring-boot-starter</artifactId>
  <version>3.27.2</version>
</dependency>
    1. application.yml 指向同一套 Redis（微服务多实例必须连同一个集群，否则锁根本不在一个命名空间）：
    spring:
  data:
    redis:
      host: 10.0.0.11
      port: 6379
      timeout: 1s
      lettuce:
        pool:
          max-active: 64
          max-wait: 500ms
    1. 加锁用 tryLock，不要 lock()：lock() 会无限等待，一次锁泄漏就能把线程池拖死。leaseTime 传 -1 才启用看门狗自动续期：
    RLock lock = redisson.getLock("lock:order:" + orderId);
boolean ok = lock.tryLock(3, -1, TimeUnit.SECONDS);   // 最多等 3s，看门狗续期
if (!ok) throw new BizBusyException(orderId);
try { doWork(); } finally { if (lock.isHeldByCurrentThread()) lock.unlock(); }

    1. 显式 leaseTime 就别指望看门狗：tryLock(3, 30, SECONDS) 表示 30 秒后必定释放，无论业务是否做完——这正是「GC 停顿超过 PX 就双写」的来源。要么给足余量，要么用默认看门狗并保证 unlock 一定执行。

    2. 锁内禁止长耗时 IO 与大批量 GC：一次 Full GC 就可能超过 PX。长任务拆成小段，或在处理前 lock.isHeldByCurrentThread() 之外再加业务版本号校验。

    3. 微服务侧三件配套：锁 key 带业务前缀避免跨服务撞名；获取失败走 20～80 ms 随机退避重试而不是自旋；写库必须有幂等键或 WHERE version = ? 条件更新——锁失效后仍可能并发写，最后一道防线在数据库。

    七、常见坑（官方明确说明的限制）

    1. SETNX + EXPIRE 两步。中间崩溃就是永久死锁，这是最经典的一类线上事故。
    2. 不加过期时间。持锁进程被 kill 后，锁永不释放；SET 不带 EX/PX 时官方不会自动过期。
    3. 直接 DEL 解锁。会删掉别人的锁，产生「两个写者」。
    4. GET 后 DEL 两步解锁。中间有窗口，仍会误删；必须用 Lua。
    5. token 用固定值（如 1）。无法区分持有人，比对失去意义。
    6. 过期时间拍脑袋。太短 → 业务没做完锁就没了；太长 → 持锁进程崩溃后要等很久才恢复。
    7. 锁内做长耗时 IO 或 GC 停顿。JVM 一次 Full GC 就可能超过锁的 PX，锁已易主而你还在写。
    8. 把锁当成「分布式事务」。跨多个资源（库存 + 余额 + 订单）时，锁只能串行化，不能保证「都成功或都回滚」。

    版本差异（8.x 标注）

    SET 的 NX/PX 语义在 2.6.12 起就稳定，7.4 与 8.x 完全一致。8.x 的差异在许可条款与集群工具链，不影响本节写法。

    依据：https://redis.io/docs/latest/commands/set/

    八、课后小结

    • 加锁一条命令：SET key token NX PX ms；
    • 解锁一段脚本：比对 token 相等才 DEL；
    • 锁只保证「同一时刻一个持有者」，不保证业务正确；
    • 主从异步复制下会丢锁，强一致场景需要额外机制（下一讲）；
    • 业务侧还要幂等与版本号，锁不是最后一道防线。

    九、思考题

    1. 为什么 SETNX + EXPIRE 会死锁？画出崩溃发生在哪一行。

      参考回答：崩溃点在 SETNX 成功之后、EXPIRE 执行之前这两行之间：锁已经存在但没有过期时间，进程一死就永远没人删。后续请求全部 SETNX 失败，业务整体卡死，只能人工 DEL。

    2. 锁的 PX 应该怎么定？给出你项目的公式与一个具体数值。

      参考回答：公式 = 业务最长耗时 P99 × 2 ～ 3 + 网络余量。例：扣减业务 P99 = 200 ms → PX = 600～1000 ms；用看门狗续期时可先给 30 s 基准值，由续期维持。定太短业务没做完锁就没了，定太长进程崩溃后要等很久才恢复。

    3. GET + DEL 两步解锁，误删别人锁的窗口有多大？由什么决定？

      参考回答：窗口 = GET 返回到 DEL 到达服务端之间的时间，即一次 RTT 加客户端处理（正常零点几毫秒，遇到 GC/网络抖动可到几十毫秒）。能否误删取决于「这段时间里锁是否过期且被别人抢到」，所以由锁的剩余有效期、RTT 与客户端停顿共同决定。

    4. 业务超时后锁已过期，你还在写库，这时最坏的结果是什么？怎么防？

      参考回答：最坏是两个写者同时写同一行，产生覆盖写、超卖或状态回退，而你以为自己独占。防法：写库带条件（版本号/WHERE stock >= n）、业务幂等键、把长任务拆小并用看门狗续期、关键路径不要只依赖锁。

    5. 主库写完锁后立刻宕机，从库升主，锁还在吗？这会导致什么？

      参考回答：不在。锁的写入还没异步复制过去，从库升主后这把锁不存在，另一个客户端可以立刻抢到，形成「两个持有者」并发写。这就是 Redis 锁在主从异步复制下不保证强一致的根源，正确性场景要靠存储侧条件更新或 fencing token（下一讲）。
