    redis-53-故障剧本

    📅 2023-02-12

    生产故障剧本

    内存满、主从断、槽异常、延迟突增、连接耗尽的处置顺序｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你能做到：

    1. 对五类高频故障，按「先止血、再定位、后复盘」给出处置顺序；
    2. 用 INFO / CLUSTER / SLOWLOG 把现象定位到具体子系统；
    3. 说清哪些操作在故障中不能做（比如急着重启、手工改槽）。

    二、前置知识

    RD19（复制）、RD21（哨兵切换）、RD24（集群限制）、RD31（碎片）、RD32（慢日志）、RD50（监控）。这一讲是 M8 的收口：把指标与配置变成动作。

    三、理论讲解（官方定义）

    故障处置里最该引用的两条官方事实。

    其一，内存打满后的行为（原文要点）：

    When the max memory limit is reached … if the eviction policy is noeviction, commands that could result in more memory being used will return an error.

    —— https://redis.io/docs/latest/develop/reference/eviction/

    错误信息是 OOM command not allowed when used memory > 'maxmemory'。这条信息的含义很明确：不是「Redis 挂了」，而是「拒绝写入」，读通常仍可用。

    其二，集群的失联判定（原文要点）：

    If a node does not respond within cluster-node-timeout, it is considered failing … if a majority of masters consider a node unreachable, the cluster may enter a fail state and return CLUSTERDOWN.

    —— https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/

    也就是说：CLUSTERDOWN 往往是「多数主节点认为某些节点失联」的结果，急着重启单个节点通常无效，反而会扩大失联范围。

    四、原理拆解

    1. 通用三步（顺序不能反）

    ① 止血：限流 / 降级 / 切流量（先把损失控制住）
② 定位：看 INFO 分组 / SLOWLOG / LATENCY / 日志
③ 复盘：改配置 + 补监控 + 写进值班手册

    为什么先止血：故障中每多一分钟，就多一批失败请求；定位需要时间，止血不需要。反过来（先花 20 分钟定位再止血）是线上事故扩大的常见原因。

    2. 五类故障的处置要点

    故障
    现象
    先做什么
    不要做什么
    内存满
    OOM command not allowed、evicted_keys 暴涨
    扩内存或调淘汰策略；查大 key
    直接 FLUSHALL
    主从断
    master_link_status:down
    查网络与主库负载
    急着重启从库（会触发全量同步）
    槽异常
    CLUSTERDOWN、MOVED 风暴
    redis-cli --cluster check 定位
    手工改 slots 分配
    延迟突增
    P99 飙升、LATENCY 有记录
    看 SLOWLOG、AOF fsync、fork
    用 KEYS 排查（会让更慢）
    连接耗尽
    rejected_connections 增长
    先扩 maxclients 止血
    只扩上限不查泄漏

    3. 两个高频误操作的原理

    • 重启从库：从库重启后要重新与主库做同步，如果 repl-backlog 不够大，就是一次全量同步——它会打满带宽与磁盘 IO，把「小故障」变成「大故障」。
    • KEYS *：官方明确它是 O(N) 且阻塞主线程。故障中执行等于给已经过载的实例再补一刀；排查必须用 SCAN。

    4. 复盘要写成「动作」，不是「结论」

    无效复盘：「Redis 内存满了，需要扩容」。
    有效复盘：

    • 动作：maxmemory 由 4GB 调到 6GB，maxmemory-policy 由 noeviction 改为 allkeys-lru；
    • 监控：used_memory/maxmemory 在 80% 时告警，5 分钟内连续两次触发即电话通知；
    • 代码：给 20 个未设 TTL 的业务 key 补上过期时间。

    止血→定位→复盘不可颠倒的顺序、五类故障的「先做什么 / 忌什么」、两个高频误操作，以及复盘要落成参数与监控动作｜依据 Eviction、Replication 与 Cluster spec 自绘

    五、场景说明

    1. 大促前：把五类故障的止血动作提前配置成开关，故障时一键执行；
    2. 主从切换窗口：客户端要能识别新主库（哨兵/集群客户端自动发现）；
    3. 故障演练：按 RD47 的方法真删缓存、真停实例，验证剧本是否可执行；
    4. 不适合：没有监控与值班手册的团队直接套用——剧本需要「谁来执行」这一环。

    六、示例代码/实操步骤

    # 场景一：内存满（先确认是拒绝写还是整体不可用）
127.0.0.1:6379> INFO memory
# used_memory_human:3.98G
# maxmemory_human:4.00G
# maxmemory_policy:noeviction
127.0.0.1:6379> SET k v
(error) OOM command not allowed when used memory > 'maxmemory'
# 止血：扩容或改策略
127.0.0.1:6379> CONFIG SET maxmemory 6gb
127.0.0.1:6379> CONFIG SET maxmemory-policy allkeys-lru
# 定位大 key（用 SCAN + MEMORY USAGE，不要 KEYS）
127.0.0.1:6379> SCAN 0 COUNT 1000

# 场景二：主从断开
127.0.0.1:6379> INFO replication
# role:slave
# master_link_status:down
# master_last_io_seconds_ago:-1
# master_sync_in_progress:0
# 先看主库是否可连、复制偏移是否在追
127.0.0.1:6379> INFO replication      # 主库侧看 connected_slaves

# 场景三：集群失联
$ redis-cli --cluster check 10.0.1.10:6379
# 输出会指出哪个节点不可达、槽分布是否完整
127.0.0.1:6379> CLUSTER INFO
# cluster_state:fail
127.0.0.1:6379> CLUSTER NODES
# 每行末尾的 flags 会标出 fail? / handshake 等状态

# 场景四：延迟突增
127.0.0.1:6379> SLOWLOG GET 10
127.0.0.1:6379> LATENCY LATEST
# fork / aof-fsync-always / command 哪个事件在冒尖
127.0.0.1:6379> INFO persistence
# aof_rewrite_in_progress / rdb_bgsave_in_progress

# 场景五：连接耗尽
127.0.0.1:6379> INFO clients
# connected_clients:9980
# maxclients:10000
# rejected_connections:412
# 止血：临时扩上限；随后查客户端是否漏还连接
127.0.0.1:6379> CLIENT LIST

    Java 侧怎么落地：客户端的故障防护

    1. pom：熔断与限流用 Resilience4j，Actuator 用于探活与指标暴露。
    <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>io.github.resilience4j</groupId>
  <artifactId>resilience4j-spring-boot3</artifactId>
  <version>2.2.0</version>
</dependency>
    1. application.yml：超时必须短于接口 SLA，否则 Redis 卡顿会等比放大到业务线程：
    spring:
  data:
    redis:
      timeout: 300ms
      lettuce:
        pool:
          max-active: 64
          max-wait: 100ms        # 拿不到连接快速失败，别无限排队
          time-between-eviction-runs: 30s
resilience4j:
  circuitbreaker.instances.redis:
    failure-rate-threshold: 50
    slow-call-duration-threshold: 200ms
    wait-duration-in-open-state: 10s
  bulkhead.instances.redis:
    max-concurrent-calls: 80
    1. 缓存访问统一包一层熔断 + 舱壁，打开状态直接走库或返回默认值，不让 RedisConnectionFailureException 冒到接口：
    @CircuitBreaker(name = "redis", fallbackMethod = "fromDb")
@Bulkhead(name = "redis")
public Item get(long id) { return cache.get(id); }

    1. 降级开关做成运行时读（配置中心 / @RefreshScope）：cache.read-bypass、cache.write-bypass 两个开关分开，先关写（保护 Redis）再关读。

    2. 探活别用业务连接池：management.health.redis.enabled: true 的默认探针在 Redis 卡顿时会一起超时，导致实例被判不健康而摘流量；改独立连接 + 短超时，或干脆只看复制与关键命令的自检结果。

    3. 故障期的日志要能定位：把异常统一转成带 key 前缀、命令名、耗时 的告警指标（Micrometer Counter），别只在日志里刷 Timeout——事后复盘靠的是这组计数。

    七、常见坑（官方明确说明的限制）

    1. 先定位再止血。故障持续时间越长损失越大，止血动作应先于根因分析。
    2. 故障中执行 KEYS。O(N) 且阻塞，会让已经过载的实例更慢（官方明确生产禁用）。
    3. 急着重启从库。可能触发全量同步，打满带宽与磁盘，把小故障放大。
    4. 手工改集群槽。槽分配由集群自身维护，手工修改会导致状态不一致，正确做法是先 check 再按官方工具重分片。
    5. 把 OOM 当「彻底不可用」。多数情况下读仍可用，只是拒绝写入；盲目重启会丢掉诊断现场。
    6. 只扩 maxclients 不查泄漏。连接泄漏会把上限再吃满，几小时后同样故障重演。
    7. 复盘只写结论。没有具体参数、监控项、责任人，等于没复盘。
    8. 没有值班手册。故障时靠「临场发挥」，处置顺序每次都不一样。

    版本差异（8.x 标注）

    上述命令与状态字段在 7.4 与 8.x 基本一致。8.x 在集群与运维工具上有增强（如更完善的 cluster check 输出），可用作故障定位的辅助；许可变化与本节无关。

    依据：https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/

    八、课后小结

    • 三步顺序：止血 → 定位 → 复盘，不能颠倒；
    • 内存满先看「拒绝写还是不可用」，扩内存或调策略止血；
    • 主从断先查网络与负载，别急着重启（会触发全量同步）；
    • 槽异常先 cluster check，不要手工改槽；
    • 延迟突增看 SLOWLOG/LATENCY/fork，连接耗尽先扩上限再查泄漏。

    九、思考题

    1. 为什么止血必须先于定位？举一个「先定位」导致损失扩大的例子。

      参考回答：故障期间每分钟损失随流量累积，而定位需要时间和工具；先止血能把「正在扩大的部分」切断，让后面的诊断在可控状态下进行。反例：大促中 Redis 延迟飙升，值班同学花 20 分钟逐个节点抓 SLOWLOG 找根因，没有限流也没降级，请求积压到把数据库和线程池一起打满，小故障演变成全站不可用。

    2. 从库重启为什么可能触发全量同步？repl-backlog 在这里起什么作用？

      参考回答：从库重启会丢掉内存中的复制偏移量，重连时用 PSYNC 带上自己记得的 offset；主库只有在 repl-backlog 里还留有该 offset 之后的增量时才能回 +CONTINUE，否则只能全量。所以 backlog 太小或从库停机超过「backlog 覆盖的时长」，重启就等于触发一次全量同步。

    3. CLUSTERDOWN 与「所有节点都挂了」有什么区别？

      参考回答：CLUSTERDOWN 是「集群认为某些槽没有可用主节点」的自我保护状态，往往只是少数节点失联或被判定 fail，其余节点还活着但拒绝服务。它不等于所有节点宕机；急着重启单个节点可能扩大失联范围，正确做法是 redis-cli --cluster check 看槽与节点状态。

    4. 延迟突增时，你怎么区分是 AOF fsync、fork 还是慢命令？

      参考回答：看时间点与事件类型：LATENCY LATEST 里有 fork、aof-fsync-always、command 等事件及各自最大耗时；INFO persistence 看 rdb_last_bgsave_time 与 aof_rewrite 是否正在进行；SLOWLOG 里出现业务命令则指向慢命令或大 key。三者同时可交叉验证：fork 引起的尖刺是周期性的、fsync 与写入量相关、慢命令跟随具体 key。

    5. 给「内存满」写一份不超过五条动作的值班手册。

      参考回答：① 确认现象：INFO memory 的 used_memory/maxmemory、evicted_keys、是否出现 OOM command not allowed；② 立刻扩 maxmemory 或临时调 maxmemory-policy 止血（读通常仍可用，别当成实例已挂）；③ 禁 FLUSHALL/KEYS；④ 捞大 key 与无 TTL key（--bigkeys、SCAN + TTL）并限期补过期；⑤ 复盘落到参数、监控与代码三处动作。

    十、官方资料

    • Eviction（noeviction 与 OOM 错误行为）：https://redis.io/docs/latest/develop/reference/eviction/
