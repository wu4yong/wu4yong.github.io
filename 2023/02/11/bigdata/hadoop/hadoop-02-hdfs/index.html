    Hadoop（二）HDFS 架构与读写流程

    📅 2023-02-11

    HDFS 架构与读写流程

    上一篇把 Hadoop 的三大模块摆上了台面，这一篇先钻进存储这一层。理解 HDFS 的关键不是背组件名，而是看清两件事：元数据由谁管、数据由谁搬；文件写入和读取分别走哪条链路、在哪一步做副本容错。

    元数据集中在中央网关，数据流沿三节点管道并行落盘

    1.1 整体架构：两类节点各管一段

    HDFS 在部署形态上只有两类常驻进程，分工严格按”元数据”和”数据”切开：

    角色
    管什么
    部署位置
    挂掉的影响
    NameNode
    目录树、文件与块的映射、副本放置策略
    主节点（HA 下为 Active/Standby）
    元数据不可查，但已写入的数据不会丢
    DataNode
    实际存储块、校验和、心跳与块上报
    每台工作节点一个
    单节点故障由其他副本补齐
    Client
    切分文件、与两类节点通信、组装结果
    作业进程内的库
    不影响集群本身

    记住一条主线：NameNode 不碰实际数据。它只在内存里维护映射，所有块数据由客户端直接连 DataNode 读写。这样 NameNode 可以专心记账，不会被海量数据流拖垮，也是 HDFS 高并发读的根本原因。

    DataNode 每隔固定时间向 NameNode 发心跳，同时上报本机存了哪些块。心跳超时未收到，NameNode 就把该节点标记为失效，上面的块由其他副本重新补齐。这个周期性上报也决定了集群规模上限：节点越多、块越多，心跳与块汇报的开销越大。

    1.2 Block、副本与放置策略

    文件不会被原样存成一整个，而是切成固定大小的块（Block）：

    概念
    默认值
    说明
    Block Size
    128MB
    块大是为了降低寻址与心跳开销，不是为了压缩空间
    Replication Factor
    3
    副本数在 dfs.replication 配置，也可按目录单独设置
    Corruption Check
    校验和
    读时比对 checksum，损坏块自动从其他副本补

    三份副本不是随机撒在三台机器上。默认机架感知策略是：第一份在客户端同机架（写客户端所在节点优先），第二份放到另一机架，第三份与第二份同机架的不同节点。这样既挡住单机故障，又挡住整机架断电，跨机架网络流量只多一倍。

    副本放置可以用一句话验证：同一机架内不堆多份，跨机架至少留一份。如果集群 Web UI 里三块副本挤在同一台机器，通常是机架感知脚本没配好，退回了单机默认策略。

    1.3 写入流程：pipeline 逐层确认

    写文件是 HDFS 最容易被面试追问的链路，按顺序拆成五步：

    1. 客户端调用 create()，NameNode 校验目录与权限，在命名空间里新建文件记录
    2. 客户端把文件切成 packet，向 NameNode 申请第一批块对应的 DataNode 列表
    3. 列表按顺序组成 pipeline：DN1 ← DN2 ← DN3，客户端先把 packet 发给 DN1
    4. DN1 写本地后转发给 DN2，DN2 再转发给 DN3；每份都返回 ack，逐级回传到客户端
    5. 块写满且三份副本都 ack 成功，NameNode 才把该块标记为完整；继续写下一块

    pipeline 中途某台 DataNode 掉线的处理值得记：客户端把坏节点从管道剔除，剩余副本继续写，NameNode 随后按目标副本因子补齐缺失的那份。写入时不是三份同时写，而是串行流转、并行落盘，网络带宽只占一条上游链路。

    与写入相关的几个常见配置：

    # 单块大小，新文件默认继承该值，已写入文件不受影响
dfs.blocksize=134217728
# 副本因子，测试环境机器不足时可先降到 1
dfs.replication=3
# 写入 pipeline 上单个节点失败后允许的重试次数
dfs.client.block.write.retries=3

    1.4 读取流程与短路本地读

    读文件的链路比写简单，但有两个优化容易被忽略：

    1. 客户端向 NameNode 问每个块所在的 DataNode 列表，NameNode 按距离排序返回
    2. 客户端直接连最近的 DataNode 拉块，边拉边校验 checksum
    3. 读坏了就换下一个副本节点重试，对上层透明

    距离排序遵循”同节点 > 同机架 > 跨机架”的顺序，这就是数据局部性（data locality）：计算任务尽量调度到块所在的机器上。YARN 调度器在分配 Container 时会优先选块所在节点，其次同机架节点，最后才跨机架。

    Short-Circuit Local Read（短路本地读）是第二个优化：当读取进程与 DataNode 在同一台机器上时，绕过 DataNode 的 TCP 接口，直接打开本地磁盘上的块文件。配置上需要 dfs.client.read.shortcircuit=true，并通过本地 Unix domain socket 与 DataNode 交换文件描述符。它省掉了本机回环网络的拷贝，HBase、本地 MapReduce 这类同机读取场景收益明显。

    # 开启短路本地读，读取进程与 DataNode 同机时生效
dfs.client.read.shortcircuit=true
# 本地交换 socket 路径，目录权限需对读取用户开放
dfs.domain.socket.path=/var/run/hadoop-hdfs/dn_socket

    1.5 元数据怎么持久化：fsimage 与 editlog

    NameNode 的映射全在内存，但不能只靠内存重启。元数据由两份文件配合保存：

    文件
    记录什么
    更新方式
    fsimage
    某一时刻完整的命名空间快照
    定期合并，不是每次写都刷盘
    editlog
    快照之后的增删改操作流水
    每次写事务先写流水

    重启时 NameNode 先加载 fsimage，再回放 editlog，把元数据重建到内存。Secondary NameNode（或 HA 里的 Standby）周期性地把 fsimage 与 editlog 合并，避免流水无限膨胀。注意 Secondary NameNode 不是热备，它只做 checkpoint，HA 场景下不能拿它顶替 Active。

    checkpoint 触发有两个条件：流水写满到阈值，或距上次合并超过时间间隔。合并动作由辅助节点拉取快照与流水、生成新镜像再推回 NameNode，整个过程 NameNode 不停止服务，但合并窗口内事务仍然先记在流水里。

    1.6 几个容易踩的坑

    • 测试集群只有两台机器，副本因子仍设默认 3，块会长期处于”副本不足”状态，Web UI 里副本数达不到目标——不是故障，是机器不够
    • 块大小调得过大，小文件场景下寻址省了，但单块重试代价变高；调得过小，NameNode 元数据和网络握手都会暴涨
    • 以为 NameNode 存了文件内容，实际它只存映射；内存装不下的是文件与块的数量，不是文件体积
    • 跨机架带宽规划不足时，写三份副本会把机架间链路打满，业务高峰期读写都变慢
    • 短路本地读需要目录权限与 socket 路径配置正确，只开参数不装本地库会回退到普通读，且没有报错提示
    • 用 Secondary NameNode 当备份节点，机器一坏才发现它手里没有可切换的最新状态，HA 必须走 JournalNode 加 ZKFC 那套方案
    • 读文件时忽略距离排序，把计算任务固定调度到远端节点，网络传输吃掉本该用于聚合的时间

    1.8 清单

    1. HDFS 只有 NameNode 与 DataNode 两类节点，元数据与数据严格分离
    2. 块默认 128MB、副本默认 3 份，副本按机架感知策略放置
    3. 写入走 pipeline 串行转发、逐级 ack，节点掉线后由 NameNode 补副本
    4. 读取直连 DataNode 并按距离排序，同机场景可用短路本地读绕开网络层
    5. 元数据由 fsimage 快照加 editlog 流水构成，重启先加载快照再回放流水
    6. Secondary NameNode 只做 checkpoint，不是 HA 热备
    7. 副本不足、小文件撑爆元数据、跨机架带宽是三个最常见的运维痛点
