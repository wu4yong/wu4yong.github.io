    redis-43-Redlock

    📅 2023-02-02

    Redlock 与官方立场

    Redlock 算法五步、它想解决的故障与时钟/停顿争议｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你能做到：

    1. 按官方文档复述 Redlock 的五个步骤，包括「多数节点」与「耗时扣除」；
    2. 说清它解决的问题（单点故障导致丢锁）与它解决不了的问题（时钟漂移、GC 停顿）；
    3. 判断你的业务到底需要「效率锁」还是「正确性锁」，并给出对应选型。

    二、前置知识

    RD42（单节点 SET NX PX 锁）、RD18（PSYNC 与主从异步复制）、RD19（复制运维）。Redlock 的出现正是因为「主从切换会丢锁」这个具体缺陷。

    三、理论讲解（官方定义）

    官方 Distributed Locks 文档对 Redlock 的描述（原文要点）：

    The Redlock algorithm … assumes we have N independent Redis masters (usually 5). To acquire the lock, the client:

    1. gets the current time in milliseconds;
    2. tries to acquire the lock in all N instances sequentially, using the same key name and random value, with a timeout;
    3. the lock is considered acquired only if it was acquired in the majority of instances (N/2+1) and the total time elapsed is less than the validity time;
    4. if failed, it tries to unlock all the instances;
    5. the effective validity time is the initial validity minus the time elapsed to acquire.

    —— https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/

    同一份文档也明确写出了局限（原文要点）：

    The algorithm does not assume a synchronized clock … but it relies on bounded clock drift … a client that pauses for longer than the validity time (e.g. a GC pause) may hold the lock while another client already acquired it.

    —— 同上

    所以「官方立场」可以概括为：Redis 官方文档把 Redlock 列为一种基于 Redis 的分布式锁实现，同时在文档里如实写明了它的失效前提。它不是「官方保证的强一致锁」。

    四、原理拆解

    1. 五个步骤的工程含义

    N=5，有效期 validity=10s
① T1 = now()
② 依次向 5 个节点 SET key val NX PX 10s（每个都有短超时，如 50ms）
③ 成功数 ≥ 3，且 now() - T1 < 10s → 认为加锁成功
④ 失败 → 向 5 个节点都发删除（哪怕有的没成功）
⑤ 实际有效期 = 10s - (now() - T1)

    三个细节必须记：

    • 顺序加锁，不是并发。并发加锁会让「总耗时」无法判断；
    • 要扣掉加锁耗时。如果加锁花了 3 秒，你只剩 7 秒有效期，而不是 10 秒；
    • 失败也要向所有节点发删除。否则残留的锁会让下一次加锁更困难。

    2. 它想解决什么

    单节点 Redis 的根本问题：主从是异步复制。主库加了锁、还没同步到从库就宕机，从库升主后这把锁不存在 → 两个客户端同时持锁。

    Redlock 的思路是「不依赖单点」：5 个独立主节点，任意 1–2 个挂掉仍能达成多数。它的目标是降低「丢锁」概率，而不是消除它。

    3. 争议点在哪

    Antirez 与 Martin Kleppmann 的那场著名争论，核心是三个物理事实：

    • 时钟漂移：节点系统时间被 NTP 或人工改动，PX 的过期判断基于服务端时间，多节点时间不一致时「多数成功」的语义就松动；
    • 网络延迟：客户端与节点之间的延迟不确定，加锁/解锁的到达时间可能远超预期；
    • 进程停顿：客户端 GC、虚拟机暂停、CPU 抢占，可能停顿超过有效期。醒来时锁已被别人持有，而你并不知道。

    结论：Redlock 不提供「绝对安全」，它降低概率但不消除。任何声称「加了 Redlock 就绝对不会有并发写」的说法都是错的。

    4. 正确的用法：按锁的用途选

    锁的用途
    后果如果失效
    建议方案
    效率锁（防重复劳动）
    多做一次工作，无数据损坏
    单节点 SET NX PX + 幂等
    正确性锁（资金、库存）
    数据错乱、资损
    数据库行锁/事务、或带 fencing token 的方案

    fencing token（防伪令牌）的思路：锁服务每次授予锁时返回一个单调递增的编号，写入存储时带上编号，存储侧只接受「编号比上次大」的写。这样即使锁失效、两个客户端同时持有，后到的旧编号写会被存储拒绝。

    取时→顺序加锁→多数判定→失败全删→扣除耗时的五步顺序、时钟漂移/网络延迟/进程停顿三条物理事实，以及 fencing token 的写入校验｜依据 Distributed Locks 文档与 Kleppmann 争论要点自绘

    五、场景说明

    1. 定时任务防重：效率锁，单节点足够，不需要 Redlock；
    2. 多机房同一任务互斥：可用 Redlock 降低单机房故障导致的重复执行；
    3. 库存扣减：正确性锁，用数据库 UPDATE ... WHERE stock > 0 的条件更新，锁只做流量削峰；
    4. 不适合：任何「错一次就资损」的场景把 Redlock 当唯一防线。

    六、示例代码/实操步骤

    # Redlock 的原子单元，就是每个节点上一次 SET NX PX（这里用单机演示）
127.0.0.1:6379> SET lock:job:daily "node-A-uuid" NX PX 10000
OK                             # 节点 1 成功
# 依次对节点 2、3、4、5 执行同样的命令，统计成功数

# 失败回滚：向所有节点发删除（幂等，删不到也无所谓）
127.0.0.1:6379> EVAL "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end" 1 lock:job:daily "node-A-uuid"
(integer) 1

# 观察节点健康状况（Redlock 要求各节点独立，不能互为从属）
127.0.0.1:6379> INFO replication
# role:master
# connected_slaves:0            ← 必须是独立 master

    客户端侧的伪代码（强调「顺序 + 计时」）：

    t1 = now_ms()
ok = 0
for node in nodes:
    if node.SET(key, token, NX, PX=validity, timeout=50ms) == OK: ok++
if ok >= N/2+1 and now_ms() - t1 < validity:
    effective = validity - (now_ms() - t1)
    doWork(effective, fencingToken = token)
else:
    for node in nodes: unlockScript(node, key, token)

    Java 侧怎么落地：先判断你到底需不需要 Redlock

    官方文档本身写着「不保证正确性」，所以落地顺序应该是「先确认场景，再选实现」。

    1. 判断场景：定时任务防重、缓存重建这类效率锁，单节点 RLock 足够，不要上 Redlock；库存、余额、券核销这类正确性锁，锁只做削峰，真正防线是存储侧条件更新。

    2. 确需多节点容错时，pom 仍用 Redisson starter，但要给每个节点各建一个客户端（节点之间必须是独立 master，不能互为主从）：

    <dependency>
  <groupId>org.redisson</groupId>
  <artifactId>redisson-spring-boot-starter</artifactId>
  <version>3.27.2</version>
</dependency>
    1. 配置文件里三个独立节点（redisson-a.yml / b / c，各自 singleServerConfig，timeout 设 50～100 ms，与算法里的单节点超时一致）：
    singleServerConfig:
  address: "redis://10.0.0.11:6379"
  timeout: 50
  connectionMinimumIdleSize: 4
    1. 按顺序、按节点组合加锁，Redisson 3.x 的 RedissonRedLock 就是「顺序 + 多数 + 失败全删 + 扣耗时」的实现（4.x 已标注 deprecated，官方文档也不推荐它做主防线）：
    RLock l1 = clientA.getLock("lock:job:daily");
RLock l2 = clientB.getLock("lock:job:daily");
RLock l3 = clientC.getLock("lock:job:daily");
RedissonRedLock red = new RedissonRedLock(l1, l2, l3);
boolean ok = red.tryLock(3, 10, TimeUnit.SECONDS);   // 显式 leaseTime，自己扣加锁耗时

    1. 有效窗口自己扣：拿到的 leaseTime 不是「可安全工作时长」，要减去加锁耗时并留余量（工程上再留 20%），业务按扣完的值规划，而不是按配置值。

    2. 正确性场景补 fencing token：锁服务侧 INCR fence:order:1001 拿单调编号，带入写库条件，让存储只接受更大的编号：

    UPDATE stock SET qty = qty - 1, fence = ?
 WHERE id = ? AND fence < ?      -- 旧编号的迟到写直接被拒绝

    七、常见坑（官方明确说明的限制）

    1. 把 N 个节点做成主从关系。Redlock 要求节点相互独立，否则「多数」失去意义。
    2. 并发向 N 个节点加锁。总耗时无法判断，validity 扣除失效。
    3. 不扣加锁耗时。业务实际可用的有效期比你以为的短。
    4. 失败后不清理。残留锁会让下一次加锁的多节点判断漂移。
    5. 用 Redlock 保护资金类写。文档已明示停顿超过有效期会导致「两个持有者」，这类场景必须靠存储侧条件更新或 fencing token。
    6. 忽略时钟同步。虽然算法不要求严格同步时钟，但要求「有界的时钟漂移」；容器/NTP 抖动大时要评估。
    7. 以为「多数成功 = 强一致」。多数只代表「此刻多数节点有这条锁」，不代表「未来一段时间内不会丢」。

    版本差异（8.x 标注）

    Redlock 是客户端算法，官方文档在 7.x 与 8.x 中表述一致；8.x 的变化在许可条款（AGPLv3/SSPL）与集群工具链，不影响算法本身。若采用第三方客户端库，注意库是否已按文档实现「扣除耗时」与「失败全量解锁」。

    依据：https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/

    八、课后小结

    • Redlock 五步：取时间 → 顺序加锁 N 个独立节点 → 多数成功且耗时未超 → 失败全删 → 有效期扣耗时；
    • 它降低「单点故障丢锁」的概率，不消除「时钟/停顿」导致的双持有；
    • 效率锁用单节点足够，正确性锁要靠存储侧条件更新或 fencing token；
    • 官方文档已如实写明前提与局限，选型要以这些前提为准。

    九、思考题

    1. 为什么 Redlock 必须「顺序」而不是「并发」向 N 个节点加锁？

      参考回答：并发加锁的总耗时不可知，你就无法判断「是不是在 validity 内拿到了多数」，扣耗时这一步失去意义；顺序加锁每步有 50 ms 超时，最坏总耗时可控，失败清理也有确定的顺序。并发还会让失败回滚互相干扰。

    2. 加锁花了 3 秒、validity 是 10 秒，实际可用多久？为什么要扣？

      参考回答：约 7 秒（10 − 3），工程上再留 20% 余量则约 5～6 秒。因为加锁本身已经消耗了有效期，业务若按 10 秒规划，做完之前锁就可能已过期并易主。

    3. GC 停顿 12 秒后醒来，你手里的锁还有效吗？会发生什么？

      参考回答：无效，锁早已过期并被别人持有，你手里的只是本地变量引用。继续写就是「两个持有者」并发写，可能出现旧值覆盖新值；只有存储侧有条件更新或 fencing token 才能挡住这次迟到写。

    4. fencing token 是怎么防住「两个持有者」的？存储侧要做什么判断？

      参考回答：锁服务每次授予锁返回一个单调递增编号，客户端写时带上；存储侧记录已接受的最大编号，只接受「更大编号」的写，于是后到的旧编号写直接被拒绝。判断是原子的比较更新，如 UPDATE ... WHERE fence < ?。

    5. 你的项目里哪些锁是效率锁、哪些是正确性锁？列出来对照选型表。

      参考回答：效率锁——定时任务防重、缓存重建互斥、报表生成、消息去重（多跑一次只是浪费）。正确性锁——库存扣减、余额变动、订单状态流转、券核销、名额抢占（错一次就资损）。前者单节点 RLock 足够；后者必须靠数据库条件更新/fencing，锁只做流量削峰。
