    redis-50-监控与告警

    📅 2023-02-09

    监控指标与告警

    INFO 各分组里最该盯的字段与告警优先级｜依据 Redis 7.4 官方文档自绘

    一、学习目标

    学完这一讲，你能做到：

    1. 从 INFO 的十个分组里挑出真正需要告警的字段，而不是「全部采集」；
    2. 用四个判断顺序（会不会挂 → 是不是慢 → 有没有丢 → 有没有积压）看指标；
    3. 给每一组指标定出可执行的阈值与告警级别。

    二、前置知识

    RD12（淘汰）、RD31（碎片）、RD32（慢日志与延迟）、RD19（复制状态）。这一讲把前面散落的现象汇总成一张「看什么、看多少」的表。

    三、理论讲解（官方定义）

    INFO 的官方说明（原文）：

    The INFO command returns information and statistics about the server in a format that is simple to parse … you can optionally specify a section: server, clients, memory, persistence, stats, replication, cpu, commandstats, latencystats, cluster, keyspace, errorstats.

    —— https://redis.io/docs/latest/commands/info/

    「可选 section」这一点很重要：生产采集应当按段取（INFO memory、INFO stats），而不是每次拉全量 INFO——后者在大实例上本身就有成本。

    关于延迟观测，官方提供了独立机制（原文要点）：

    Redis has a latency monitoring feature … LATENCY HISTORY / LATENCY LATEST record events that exceed latency-monitor-threshold.

    —— https://redis.io/docs/latest/commands/latency-latest/

    默认 latency-monitor-threshold 为 0，表示关闭。这是最常见的「监控盲区」：不开启就永远不知道有慢事件。

    四、原理拆解

    1. 四组指标的分工

    ① 内存：会不会写不进去（used_memory / maxmemory / evicted_keys）
② 连接：会不会连不上（connected_clients / rejected_connections）
③ 性能：是不是变慢（instantaneous_ops / slowlog / latency）
④ 复制与持久化：会不会丢（master_link_status / rdb_last_bgsave_status）

    顺序不能乱：先保「可用」，再谈「快」。一个实例内存打满开始拒绝写，此时看 P99 意义不大。

    2. 每个字段的「阈值」怎么定

    字段
    建议阈值
    含义
    used_memory / maxmemory
    ≥ 80% 告警
    接近淘汰或写失败
    mem_fragmentation_ratio

    1.5 观察，> 2 处理

    碎片偏高（RD31）
    evicted_keys 增速
    持续 > 0
    容量不足，命中率会掉
    connected_clients / maxclients
    ≥ 80% 告警
    新连接会被拒
    rejected_connections

    0

    连接被拒，客户端会报错
    master_link_status
    down 立即告警
    复制断了
    rdb_last_bgsave_status
    err 立即告警
    快照失败
    aof_last_write_status
    err 立即告警
    AOF 写失败
    latency-monitor-threshold
    设为 50–100ms
    否则事件不记录

    「err / down / 拒绝」这三类是「会不会丢数据」级别的，必须最高优先级。

    3. 三个必须自己算的衍生指标

    原始字段不够用，要自己算：

    • 命中率 = keyspace_hits / (keyspace_hits + keyspace_misses)，低于 90% 要查为什么；
    • 回源 QPS = 未命中数 × （1/缓存比例），这个数直接对应数据库压力；
    • 命令延迟均值 = commandstats 的 usec_per_call，单命令变慢往往先于整体 P99 恶化。

    4. 延迟监控的三件套

    latency-monitor-threshold 100     # 记录超过 100ms 的事件
LATENCY LATEST                    # 最近一次各事件的最大延迟
LATENCY HISTORY <event>           # 某事件的时间序列
LATENCY RESET                     # 清空，用于重置基准

    常见事件：fork（RDB/AOF 重写）、aof-fsync-always、command、expire-cycle。看到 fork 事件频繁且延迟高，就该考虑内存规模（RD51）。

    内存/连接/性能/复制四组字段与判读阈值、命中率等三个必须自己算的衍生指标，以及延迟监控默认关闭这件事｜依据 INFO、LATENCY 与延迟排查文档自绘

    五、场景说明

    1. 新上线实例：先开 latency-monitor-threshold 与慢日志，再谈业务指标；
    2. 主从架构：master_link_status 与 master_last_io_seconds_ago 必须进告警；
    3. 缓存集群：evicted_keys 与命中率变化趋势比绝对 QPS 更有价值；
    4. 大内存实例：重点盯 fork 延迟与碎片率，避免 BGSAVE 期间抖动。

    六、示例代码/实操步骤

    # 1. 按段采集，别拉全量
127.0.0.1:6379> INFO memory
# used_memory_human:3.21G
# maxmemory_human:4.00G
# mem_fragmentation_ratio:1.42

127.0.0.1:6379> INFO clients
# connected_clients:842
# blocked_clients:0
# rejected_connections:0

127.0.0.1:6379> INFO stats
# total_connections_received:...
# instantaneous_ops_per_sec:15230
# keyspace_hits:8120334
# keyspace_misses:201776
# evicted_keys:0

127.0.0.1:6379> INFO replication
# role:master
# connected_slaves:2
# master_link_status:up
# master_last_io_seconds_ago:1

127.0.0.1:6379> INFO persistence
# rdb_last_bgsave_status:ok
# aof_last_write_status:ok
# rdb_last_bgsave_time_sec:1

# 2. 打开延迟监控（默认关闭）
127.0.0.1:6379> CONFIG SET latency-monitor-threshold 100
OK
127.0.0.1:6379> LATENCY LATEST
1) 1) "fork"
   2) (integer) 1700000000
   3) (integer) 230
   4) (integer) 460

# 3. 看单命令耗时
127.0.0.1:6379> INFO commandstats
# cmdstat_get:calls=8120334,usec=...,usec_per_call=12.40

# 4. 慢查询与阻塞
127.0.0.1:6379> SLOWLOG GET 10
127.0.0.1:6379> CONFIG GET slowlog-log-slower-than
# 10000（微秒，即 10ms）

# 5. 内存告警的判据（脚本里算比例）
# 若 used_memory/maxmemory >= 0.8 → 告警；>= 0.95 → 严重

    Java 侧怎么落地：Actuator + 定时采集 INFO

    1. pom：Actuator 出指标，Prometheus 做存储与告警源。
    <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
    1. application.yml：只暴露需要的端点，采集间隔别太密（INFO 本身有成本）：
    management:
  endpoints.web.exposure.include: health,info,prometheus
  endpoint.health.show-details: never
redis-monitor:
  interval: 30s          # 采集间隔
  memory-threshold: 0.8  # 与告警规则对齐，放配置不写死
spring:
  data:
    redis:
      timeout: 300ms
    1. 定时任务里取 INFO，不要再拼字符串：RedisConnection.info() 直接返回带结构的 Properties，按段取值：
    Properties p = connection.info("memory");
long used = Long.parseLong(p.getProperty("used_memory"));
long max  = Long.parseLong(p.getProperty("maxmemory"));
double ratio = max > 0 ? (double) used / max : 0;
    1. 注册成 Gauge，让告警规则在监控侧统一配（不要在每个服务里写 if 判断）：
    Gauge.builder("redis_memory_used_ratio", () -> ratio)
     .tag("instance", host).register(meterRegistry);

    1. 派生指标自己在应用里算：keyspace_hits / keyspace_misses 增量相除得命中率；commandstats 里取 usec_per_call；复制看 master_link_status，只要不是 up 就按异常上报。

    2. 延迟监控要显式打开：启动时 CONFIG SET latency-monitor-threshold 100（或写进 redis.conf），再用 LATENCY LATEST 取事件与最大耗时——它默认关闭，不开就永远查不到 fork 与 fsync 的尖刺。

    3. 采集本身要隔离：独立线程 + 独立连接 + 短超时，采集失败只记日志不抛给业务；用业务连接池跑 INFO，Redis 卡顿时会把业务一起拖住。

    七、常见坑（官方明确说明的限制）

    1. latency-monitor-threshold 保持 0。默认关闭，不设置就永远不会记录慢事件。
    2. 采集全量 INFO。大实例上 INFO 有成本；应按段采集并降低频率。
    3. 只看命中率不看回源 QPS。命中率 99% + 巨大总量，回源依然能打挂库。
    4. 把 evicted_keys 当正常现象。它意味着「有数据正在被丢」，命中率会随之下降。
    5. 忽略 blocked_clients。阻塞命令（BLPOP 等）堆积会占用连接，最终表现为「客户端超时但 Redis 很闲」。
    6. 不监控 fork 延迟。BGSAVE 与 AOF 重写时的 fork 停顿是延迟尖刺的常见来源。
    7. 告警阈值照抄别人的。80% 内存对 4GB 实例和 64GB 实例的处理方式完全不同（RD51）。
    8. 没有基线。不知道「正常是什么样」，告警只能靠猜；先记录一周再定阈值。

    版本差异（8.x 标注）

    INFO 的分组与字段在 7.4 与 8.x 基本一致；8.x 增加了若干新字段与指标（如更细的延迟统计），采集脚本应对「未知字段」做容错，不要把字段清单写死。

    依据：https://redis.io/docs/latest/commands/info/

    八、课后小结

    • 四组指标：内存、连接、性能、复制与持久化，顺序是「先可用再好用」；
    • err / down / rejected 是最高优先级；
    • 衍生指标：命中率、回源 QPS、单命令耗时；
    • 延迟监控默认关闭，必须显式设置阈值；
    • 阈值要有基线，别照抄。

    九、思考题

    1. used_memory 到 80% 时你会先做什么，为什么不是先扩容？

      参考回答：先看结构，不动容量：evicted_keys 是否增长、maxmemory-policy 是否合理、有没有无 TTL 的大 key、过期是否集中在同一时段。80% 常常是「该淘汰的没淘汰」而不是「真的不够」，先扩容会把内存问题变成成本问题，并掩盖 TTL 设计缺陷。

    2. keyspace_misses 增长但命中率没掉，说明什么？

      参考回答：说明读总量一起涨了。命中率是比值，hits 与 misses 同比例增长时比值不变，但回源 QPS 已经同比上升——要盯的是「回源压力」绝对值，而不是命中率这个比率。

    3. master_last_io_seconds_ago 持续增大，故障链条是怎样的？

      参考回答：主库长时间没有向从库发送数据 → 网络抖动或主库阻塞 → 从库判定超时 → master_link_status:down → 主库积压写入超出 repl-backlog 或被踢出 backlog → 从库重连只能 PSYNC 全量 → 带宽与磁盘被打满，延迟进一步恶化。所以这个字段是「即将全量同步」的早期信号。

    4. fork 延迟 400ms，对线上 P99 有什么影响？

      参考回答：fork 期间主线程被阻塞，这 400ms 内所有命令排队，P99 会出现一个明显尖刺（400ms 量级），若此时正好有超时设置较短的客户端，还会连带出现超时重试与连接重建。评估要看「尖刺频率 × 单次时长」是否已经把 P99 顶到 SLA 之外。

    5. 如果只能上三条告警，你选哪三条？给出理由。

      参考回答：① used_memory/maxmemory 持续 ≥ 80%（决定是否会写失败或开始淘汰）；② master_link_status 非 up 或 master_last_io 持续增大（决定数据是否还同步、是否会全量）；③ rejected_connections 增长或出现 OOM 错误（决定请求是否已经开始被拒）。三条分别对应「容量、数据、可用」三个不可回退的边界。
