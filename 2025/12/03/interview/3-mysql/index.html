3. MySQL（索引、事务、锁、主从、死锁、SQL优化）

第 1 题　为什么 InnoDB 索引选用 B+树，不用二叉树、AVL、红黑树

举例说明：一张 2000 万行的订单表，主键 bigint 占 8 字节，一个 16KB 的页大约能放上千个键值对，三层 B+树就能覆盖十亿级记录；同样数据量换成二叉树，树高接近 25 层，一次查询最多要做 25 次磁盘 IO。

问题 1：InnoDB 索引使用 B + 树，为什么不用逻辑更简单的二叉树？

候选人浅层回答： 二叉树树高度太高，查询慢；B + 树高度低，磁盘 IO 次数更少。

连环追问

  1. AVL 树、红黑树也是平衡树，也可以控制树的高度，为什么不用它们做数据库索引？
  2. 数据库数据存储在磁盘上，请讲清楚 B + 树适配磁盘存储的核心逻辑，磁盘页、页分裂、页合并关键点。

参考答案：

数据库索引的核心矛盾：磁盘 IO 很慢，内存很快，要尽可能减少磁盘读取次数。每访问树的一个节点，大概率发生一次磁盘 IO。

1、为什么不用普通二叉树普通二叉树在极端情况下会退化成链表，树高等于数据行数；千万级数据树高千万级别，千万次磁盘 IO，性能完全不可用。

2、为什么不用 AVL 平衡树、红黑树AVL、红黑树是二叉平衡树，每个节点最多两个子节点。 千万级数据，二叉平₂衡树树高大约 log (1000w) ≈ 24，一次查询最坏需要 24 次磁盘 IO。 而磁盘一次 IO 会读取一整页（InnoDB 页默认 16KB），只存两个子节点，页内大量空间浪费，没有充分利用磁盘页的读写特性，IO 次数还是太高，不适合磁盘存储场景。

3、B + 树（多路平衡查找树）适配磁盘的核心优势

  1. 多路多叉，压低树高度，减少磁盘 IO B + 树一个节点可以存放大量索引键与子节点指针。InnoDB 一页 16KB，可以存放成百上千个索引项。千万级数据，B + 树树高通常只有3‑4 层。根节点常驻内存，查找只需要 2~3 次磁盘 IO，IO 次数被压到很低。

  2. 非叶子节点只存索引键，不存完整行数据 非叶子节点只做路由，不保存真实数据，一页可以存放更多索引，进一步降低树高度；全部真实行数据都存放在叶子节点。

  3. 叶子节点双向链表串联 所有叶子节点通过双向有序链表连接。范围查询、order by 排序、limit 分页，不需要再回到上层树做遍历，直接顺着链表扫描叶子节点，范围查询性能极强。红黑树、AVL 做范围查询需要递归遍历，效率很低。

  4. 页分裂、页合并机制，适配磁盘页存储 B + 树按页管理数据，新增数据页满就触发页分裂；删除数据页利用率过低触发页合并，保证每一页尽量填满，减少空间浪费，维持树的多路平衡。

对比：红黑树 / AVL 主要适合内存场景，例如 Java TreeMap；不适合磁盘 IO 频繁的数据库索引场景。

  1. 补充：B 树和 B + 树简单区分B 树每个节点既存索引 key，又存数据；B + 树数据只存在叶子。B + 树非叶子节点可以存更多索引，树更矮；叶子链表对范围查询友好，所以 InnoDB 选择 B + 树。

追问：本题考察核心是什么？

参考答案： 不只是记住 “B + 树高度低” 这个结论。面试官想看理解磁盘IO 是主要矛盾。 很多开发只停留在会建索引，不理解数据结构和硬件特性之间的取舍：二叉平衡树适合内存，B + 树是专门针对磁盘设备设计的多路平衡树。理解页、页分裂、双向链表这些关键点，才真正懂索引底层。

核心设计思想：利用磁盘页批量读取的特性，用多叉降低树高，减少 IO；叶子链表优化范围查询

第 2 题　MySQL 主键就一定是聚集索引吗？

问题 1：数据库主键就一定是聚集索引吗？

候选人浅层回答： 是的，InnoDB 里面主键就是聚集索引。

连环追问

那为什么会有 “主键和聚集索引不是同一个” 的说法？能不能手动指定非主键字段作为聚集索引？这么做有什么适用场景、风险是什么？

参考答案

一、核心规则（InnoDB）

  1. InnoDB 一张表有且仅有一个聚集索引，聚集索引决定行数据在磁盘上的物理排序。

  2. 优先选择逻辑：

  3. 如果表定义了主键：主键作为聚集索引；

  4. 如果没有主键，会选第一个非空唯一索引作为聚集索引；

  5. 如果连非空唯一索引都没有，InnoDB 自动生成一个隐藏的 6 字节 row_id 作为聚集索引。

重点：InnoDB 不支持人为随意指定某个普通索引为聚集索引，聚集索引是按上面这套规则自动选定，不能在建表时单独指定。 而 MyISAM 引擎本身没有聚集索引，所有索引都是二级索引，数据文件和索引文件完全分离，这也是很多人混淆的源头。

所以一句话总结： 默认场景下，InnoDB 主键就是聚集索引；但聚集索引不一定是主键（无主键时，唯一索引 / 隐藏 row_id 充当聚集索引）。 并不是 “主键天然等于聚集索引”，二者概念完全不同：

  • 主键：约束，唯一、非空，业务层面用来唯一标识一行记录；
  • 聚集索引：索引存储组织形式，控制数据物理存放顺序，是存储引擎层面的结构。

二、误区拆解

很多人背 “主键就是聚集索引”，只是 InnoDB 有主键时的默认表现，不是铁律： 场景 1：有主键 → 主键 = 聚集索引（最常见） 场景 2：无主键，但有唯一非空索引 → 该唯一索引 = 聚集索引，此时主键不存在 场景 3：无主键、无唯一非空索引 → row_id 隐藏聚集索引，没有任何业务字段做聚集索引

三、能不能刻意不用主键当聚集索引？

InnoDB 语法层面不支持主动切换聚集索引。 如果业务不想用自增主键做聚集索引，常见两种方案：

  1. 把目标字段设置成唯一非空索引，并且不设置主键，引擎就会拿它当聚集索引； 风险：业务字段经常更新、非单调递增，会造成页分裂、大量磁盘碎片，写入性能暴跌。
  2. 保留自增主键，业务查询走二级联合索引，不修改聚集索引。（工业界主流稳妥方案）

四、聚集索引选择带来的业务影响

  1. 自增主键做聚集索引：有序写入，极少页分裂，插入性能好；范围查询按主键高效；
  2. 无序字段作为聚集索引（比如订单号、手机号、随机字符串）：随机 IO，频繁页分裂，高并发写入性能很差；
  3. 二级索引叶子节点存的是聚集索引键，聚集索引越大，二级索引体积膨胀，占用更多磁盘，查询、内存加载开销上升。

五、MyISAM 补充对比（面试加分）

MyISAM 不存在聚集索引，它的数据和索引分开存储，所有索引都是普通 B +树索引，叶子节点存的是数据行的物理偏移地址，所以主键也不是聚集索引。

这也是题目里 “主键和聚集索引不是一回事” 的来源。

追问：本题考察核心是什么？

参考答案：初级开发只会死记 “InnoDB 主键就是聚集索引”，分不清主键是约束、聚集索引是存储结构。高级工程师要理解：

  1. 区分两个完全不同维度的概念：主键（约束）、聚集索引（存储结构）；
  2. 掌握 InnoDB 聚集索引的自动选择优先级，理解隐藏 row_id；
  3. 明白聚集索引对写入、页分裂、索引体积的影响，知道为什么生产绝大多数场景都用自增主键做聚集索引；
  4. 能够区分 InnoDB 和 MyISAM 引擎底层索引模型差异，不会一概而论。

核心思想：“主键是聚集索引” 只是 InnoDB 有主键时的默认结果，不是定义；概念先行，再看引擎规则，不能当成普适真理。

举例说明：建了索引 idx(age, name)。where age=20 and name=’张三’ 可完整使用索引；where age>18 and name=’张三’ 只有 age 列生效、name 列失效；而 where name=’张三’ 完全用不上这个索引，只能全表扫描或走别的索引。

前置约定

假设联合索引：idx_age_name(age, name)（索引顺序：age 在前，name 在后） 三条 SQL：

  1. select * from user where name=’张三’ and age=20;

三层拆解回答第一层：SQL1：where name=’张三’ and age=20条件都是等值查询。 虽然 SQL 里先写 name、后写 age，但是优化器会自动调

  • 换等值条件顺序，匹配索引 (age,name)。

  • 都走索引，能定位行； 但 select *，不是覆盖索引，查到主键后会回表拿其他字段。

第二层：SQL2：where age>18 and name=’张三’索引顺序 age,name，age 是范围>。 规则：联合索引中，一旦遇到范围查询（> < between like 前缀模糊），范围之后的索引列无法使用索引过滤。

  • age 可以走索引，快速筛出 age>18 的数据；
  • name 在 age 后面，无法利用索引做过滤；name=’ 张三 ‘ 只能在 age 筛选出来的结果集里做内存过滤。

第三层：SQL3：where name=’张三’ and age>18这是本题最大陷阱！ 索引定义：(age, name)，索引最左第一列是 age。 没有

  • ❌age 等值前缀，直接用 name 查询，无法触发最左前缀。

这条SQL 不能走 idx_age_name 这个联合索引，几乎是全表扫描； 哪怕 where 里 name 写在最前面，也没用！索引的顺序是建表时定义的，和 SQL 条件顺序无关。

总结区分

  • 等值条件：优化器自动重排，书写顺序无关；
  • 范围条件：范围后面的索引列失效；
  • 最左前缀：以索引定义顺序为准，不是 SQL where 书写顺序。

第 4 题　MySQL 加了索引，查询就一定更快吗？

问题 1：索引是什么？加了索引查询就一定更快吗？

候选人浅层回答： 索引是用来加速查询的 B + 树结构，给查询字段建立索引，SQL 就能跑得更快。

连环追问

  1. 既然索引是提升检索效率的，那为什么有时候加了索引之后，SQL 反而跑得更慢？
  2. 那我建区分度很高的索引，执行计划也明确命中索引，是不是就一定没问题？

参考答案

一、索引本质

索引是数据库空间换时间的数据结构，核心目的是减少扫描行数。 InnoDB 使用 B + 树组织索引；创建索引，数据库就要额外维护一棵有序 B + 树。查询时可以沿着树快速定位，避免全表逐行扫描。 代价：占用磁盘空间；新增、修改、删除数据时，需要同步更新索引树，增加写操作开销。 重点：索引只是给优化器多了一个可选的执行路径，不等于一定会提升性能。

二、加索引反而变慢的典型场景

  1. 表数据量很小 几百行以内的小表，顺序全表扫描本身极快。走二级索引还要先扫描索引树，再回表读取行数据，两次 IO，开销反而高于顺序扫描。优化器甚至可能主动放弃索引。
  2. 索引字段区分度很低（选择性差） 例如状态、性别这类枚举字段，大量行的值相同。如果查询条件过滤后返回大量数据，走索引依然要读取大量索引页，并且大量回表；随机 IO 远大于全表扫描的顺序 IO，性能更差。
  3. 回表成本过高 二级索引叶子节点只存聚集索引主键 id，查到 id 后还要回主键索引拿全部字段。当查询返回结果集很大，大量回表，随机 IO 暴涨，速度不如直接全表扫描。覆盖索引可以解决这个问题，避免回表。
  4. 优化器统计信息不准，选错执行计划 统计信息没有及时更新，优化器误判行数，错误选择索引；测试环境正常，线上数据分布倾斜后，执行计划漂移，索引带来负收益。
  5. 索引本身维护开销拖累写入 大量冗余索引，读可能微涨，但插入、更新、删除变慢；高写入业务，盲目加索引会拖垮整体吞吐。

三、就算命中索引，依然可能慢的原因

  1. 没有做成覆盖索引，大量回表；
  2. 范围查询过大，索引过滤后结果集占比很高；
  3. 索引字段上做函数运算、隐式类型转换，索引失效；
  4. 联合索引不满足最左前缀，索引利用率低；
  5. 索引页不在缓冲池，大量磁盘冷 IO。

四、索引设计正确思路

  1. 优先评估索引收益：过滤后返回行数占比很低，索引才有价值；

  2. 优先使用覆盖索引，消除回表；

  3. 优先给高区分度、高频过滤字段建索引；低区分度字段不要单独建索引；

  4. 定期检查索引利用率，清理低频、无效冗余索引；

  5. 不能只看 explain 有没有走索引，还要评估回表开销、IO 类型（顺序 IO / 随

  6. 机 IO）；

  7. 读写权衡：写入压力大的表，索引数量要收敛。

追问：本题考察核心是什么？

参考答案：初级开发固化思维，认为索引 = 提速，只会背 B + 树、最左前缀。

高级工程师要理解：

  1. 索引是有成本的，收益是有前提条件的，不是万能优化手段；
  2. 明白 InnoDB 二级索引的回表机制，区分顺序 IO 和随机 IO 的性能差异；
  3. 理解优化器的选择逻辑：走不走索引，是优化器基于代价估算做出的选择；
  4. 会判断索引什么时候正收益、什么时候负收益，不是慢 SQL 就无脑加索引；
  5. 建立代价思维：查询收益、磁盘空间、写入开销、回表成本综合评估。

核心思想：索引只是一种查询备选路径，能不能变快，取决于过滤比例、区分度、是否回表、数据量、IO 模型，而不是只要建了索引就一定更快。

第 5 题　MySQL 灵魂三连问

问题 1：MySQL 索引失效有哪些常见情况？如何做优化？

候选人浅层回答： 查询没有命中索引，给慢查询加上索引就可以。

连环追问

  1. 联合索引失效有哪些规则？
  2. 什么是隐式类型转换，为什么会造成索引失效？
  3. 慢查询除了新增索引，还需要从哪些维度优化？
  4. explain 执行计划关键字段怎么解读？

参考答案：

索引失效常见场景

  1. 联合索引违反最左前缀原则 联合索引 (a,b,c)，查询条件缺少最左边 a 字段，索引失效；范围查询（>、<、between）之后的列会失效。

例：where a>10 and b=20，b 字段无法使用索引。

  1. 隐式类型转换 索引字段和传入参数数据类型不一致。例如 varchar 字符串索引，传入数字；数据库做函数转换，索引列发生运算，索引失效。

  2. 索引列上使用函数、运算、逻辑运算 wheredate(create_time)=’2026‑10‑23’，索引列包裹函数，索引失效；要改成表达式把计算放到参数一侧。

  3. like 通配符以 % 开头 like ‘%关键词’，前缀模糊查询无法使用 B + 树索引；后缀like ‘key%’可以走索引。

  4. or 条件一侧字段无索引 or 连接的字段，只要其中一个字段没有索引，整条SQL 不走索引。

  5. MySQL 优化器判断全表扫描更快，主动放弃索引 比如数据量占表很大比例、统计信息不准，优化器认为全表扫描成本更低，即使存在索引也不会使用。

  6. 优化手段

  7. 设计联合索引遵循最左前缀，把等值条件放前面，范围条件放最后；

  8. 避免索引字段做函数、算术运算，杜绝隐式类型转换；

  9. 前缀模糊匹配走索引，避免前缀百分号；需要全文检索考虑 ES；

  10. or 两边字段都建立索引；

  11. 定期更新表统计信息，保证优化器判断准确；

  12. 慢查询不只加索引，还要优化业务 SQL 逻辑、分页、join 关联、避免大事务；

  13. 使用explain 执行计划分析，重点看type、key、rows、Extra，判断是否命中索引、是否回表。

问题 2：MySQL 死锁是怎么产生的？死锁四个必要条件是什么？除了重试，还有哪些根治方案？

候选人浅层回答： 调整事务隔离级别，出现死锁就重试。

参考答案：

死锁产生原因InnoDB 行锁，两个或多个事务，互相持有对方需要的行锁，又互相等待对方释放锁，循环等待，形成死锁。MySQL 会检测死锁，主动回滚代价更小的一个事务。

死锁四个必要条件

  1. 互斥条件：资源是排他锁，一个事务占有，其他事务不能占用；
  2. 持有并等待：事务已经持有部分锁，同时等待获取其他锁；
  3. 不可剥夺：已经拿到的锁不能被其他事务强行抢占，只能自己释放；
  4. 循环等待：事务之间形成锁的环形等待链路。

四个条件同时满足，才会发生死锁。

解决方案

  1. 打破循环等待（根治核心）：统一资源加锁顺序 所有业务更新数据，固定按照主键 ID 升序 / 降序顺序更新，避免交叉加锁，从根源破坏循环等待。
  2. 缩小事务粒度 事务尽量小，减少锁持有时间；不要在事务中做外部 IO、RPC调用，尽快提交事务释放锁。
  3. 避免 select … for update 大范围加锁 查询条件务必命中索引；若未命中索引，InnoDB 需要扫描聚簇索引做过滤，RR 级别下会对扫描到的所有记录及间隙加锁（效果接近锁全表，本质是行锁+间隙锁的范围叠加，不是真正意义上的表锁），锁范围急剧放大，大幅提升死锁和锁等待概率。
  4. 控制锁粒度，尽量避免并发更新多条不同记录产生交叉锁等待。
  5. 兜底策略：业务捕获死锁异常做有限次重试，重试只是补救手段，不能当做根治方案。

注意：调整隔离级别不能解决死锁，RC、RR 都可能出现死锁。

第 6 题　MySQL 索引：执行计划显示走索引，但 SQL 依然很慢

场景回顾

候选人只会背索引失效：左 like、函数、隐式转换。 面试官连环灵魂拷问：

  1. explain 明明走二级索引，为什么还是很慢？
  2. 大范围二级索引查询，为什么优化器觉得不如全表扫描？
  3. 走主键索引，表从百万涨到千万，性能明显变差，主键索引也失效了？
  4. MySQL 优化器什么时候主动放弃索引、选全表扫描，判断逻辑是什么？

核心本质：索引不是免费加速工具，索引本身有 IO 代价；优化器是基于代价模型选择执行方案，不是有索引就一定优先走索引。

三层高分逻辑

第一层：二级索引 —— 回表成本（最常见）InnoDB 二级索引叶子节点存主键值，查到后需要回表，去聚簇索引读取完整行数据。 如果命中行数占整张表比例很高（一般超过 20% 左右，经验阈值）：

  • 二级索引 → 大量回表，随机 IO 非常多；
  • 全表扫描是顺序 IO，顺序 IO 远快于大量随机 IO； 所以优化器评估后，认为走索引的总代价更高，主动放弃二级索引，走全表扫描。 覆盖索引可以解决：把查询需要的字段全部放进联合索引，避免回表。

第二层：主键（聚簇）索引也会变慢，和 B + 树、页、IO 有关主键索引就是聚簇索引，本身不会失效，但数据量上涨后性能下滑原因：

  1. B + 树层数变高：百万数据一般 3 层，千万级数据 B + 树深度增加，多一次磁盘页读取；
  2. 数据页不能全部放进 Buffer Pool：热点页缓存命中率下降，大量访问落到磁盘IO；
  3. 范围查询：主键范围扫描，如果扫描区间很大，依然要遍历大量数据页；主键索引永远有效，只是扫描的数据量、磁盘 IO 变多，延迟上涨，不是失效。

第三层：优化器代价模型（优化器怎么选）MySQL 优化器统计信息（cardinality 基数、行数、过滤比例）估算代价： 代价 ≈ IO 代价（主要） + CPU 代价

  • 估算返回行数很少：索引代价低，选择索引；
  • 估算返回行数占比高：大量回表随机 IO，代价高，放弃索引，走全表扫描；坑点：统计信息不准（采样估算、数据倾斜、很久没 analyze），会导致优化器判断出错，选错执行计划。

就算执行计划显示走索引，查询慢主要有三层原因：第一是二级索引查询返回数据量大，大量回表带来随机 IO 开销，性能甚至不如顺序扫描的全表；第二是主键聚簇索引虽然不会失效，但千万级数据下 B + 树深度增加、Buffer Pool 缓存命中率下降，磁盘 IO 变多，范围查询延迟上涨；第三是 MySQL 优化器依靠统计信息做代价估算，当预估扫描行数占比高时，会主动放弃索引走全表扫描，如果统计信息不准，还会出现选错计划的情况。优先用覆盖索引消除回表，同时维护统计信息、控制扫描行数。

第 8 题　线上慢 SQL 引发数据库 CPU 99% 故障

场景复盘

线上核心接口超时，数据库 CPU 飙到 99%，定位到一条单次十几秒的慢 SQL，阻塞正常业务请求。

面试官连环追问：

  1. 加索引是不是万能？函数、隐式转换造成索引失效怎么定位？
  2. 索引加上依然慢，如何区分是回表、多表关联还是数据体量问题？
  3. SQL 之前正常，高峰突然执行计划漂移不走索引怎么快速恢复？
  4. 慢 SQL 持有行锁，堵塞其他写请求、连接打满，如何快速止血？
  5. 大量历史散落在代码里的 SQL，怎么提前预警，而不是事后救火？
  6. 是否存在不改 SQL、不加索引的临时防护手段？

核心认知：慢 SQL 治理分应急止血 → 根因定位修复 → 长效防控三层；很多故障不是缺索引，而是计划漂移、锁阻塞、统计信息不准、没有流量熔断防护。只懂 explain、只会加索引是远远不够的。

三层高分体系

第一层：应急止损层（优先，故障爆发第一时间操作，目标 1 分钟止血）核心目标：快速降低数据库压力，解除锁阻塞，恢复业务可用，不一定根治

  1. 杀掉故障会话：show processlist 找到慢 SQL 会话 ID，killsession_id，立刻释放锁、CPU、连接资源；这是锁阻塞场景最直接手段。
  2. 临时限流 / 熔断：网关或者应用层对这个接口降流量、降级、切缓存，阻断流量继续打入数据库；不需要改 SQL 和索引。
  3. SQL hint 临时绑定执行计划：如果是执行计划漂移（之前走索引、突然全表扫描），紧急加FORCE INDEX hint，临时强制走正确索引，快速恢复，适合线上紧急止血。
  4. 读写分离兜底：查询类慢 SQL 临时切到从库，保护主库写入。

重点：这一层就是面试官问的「不改 SQL、不加索引也能护住库」的方案：kill 会话、接口熔断限流、hint 强制索引、切从库。

第二层：根因定位与修复层（故障稳住之后，定位并根治这条 SQL）先用explain analyze 拿到真实执行计划，区分几类常见根因：

  1. 索引失效类：where 条件上用函数、隐式类型转换、模糊前缀%xx、or 跨字段；修复：去掉字段函数、统一字段类型、调整索引结构。
  2. 索引存在但效果差：回表过多（覆盖索引缺失）、联合索引顺序不对、基数低（区分度差）；修复：建立覆盖索引、调整索引顺序。
  3. 多表 join / 子查询：关联顺序错误、驱动表选错、笛卡尔积；优化：小表驱动大表，简化 join，拆成分段查询。
  4. 执行计划漂移：统计信息不准、数据分布突变，优化器误判选择全扫描；修复：analyze table 更新统计信息；长期方案：sql baseline 绑定稳定执行计划。
  5. 数据膨胀：索引已经最优，但数据量太大；方案：冷热分离、分库分表、归档历史数据。
  6. 长事务锁问题：慢查询是读，但长时间快照 / 事务持有，阻塞写入；缩短事务边界，查询尽量独立短事务。

第三层：长效防控体系（避免反复踩坑，事前发现隐患）

  1. 上线卡点：SQL 审核平台，变更自动 explain 校验，禁止高危 SQL 上线；拦截无索引、大 limit、不带条件全扫 SQL。
  2. 慢查询持续采集：慢日志、数据库审计，持续采集慢 SQL，告警入库；不是等CPU 炸了才发现。
  3. 执行计划基线（SQL Baseline）：对核心 SQL 固化稳定执行计划，防止统计信息变化导致计划漂移。
  4. 资源保护：数据库侧设置 SQL 最大执行时长（max_execution_time），超时自动终止；连接池、读写分离、热点缓存兜底，限制单 SQL 对库的破坏力。
  5. 巡检复盘：定期分析 TOP 慢 SQL，表数据增长监控，提前归档；接口增加缓存，把高频查询挡在 DB 之外。

高频追问

Q：kill 慢 SQL 会不会丢数据？ A：只读查询 kill 没有影响；如果是 DML语句，kill 后事务回滚，不会产生脏数据，代价是回滚消耗一点资源，紧急场景收益远大于代价。 Q：什么时候不能直接加 FORCE INDEX？ A：数据分布持续变化的场景，hint 是临时急救手段，长期要用 baseline，避免索引随数据变化反而变差。 Q：max_execution_time 作用？ A：给 select 设置超时，防止单条失控 SQL 长时间霸占 CPU，属于数据库自我保护。

第 9 题　MySQL 索引高并发踩坑，CPU 飙升线上故障复盘

问题 1：索引建好了，SQL 也没写错，为什么高并发下数据库 CPU 直接拉满、接口超时？

候选人浅层回答： 建合适的联合索引、避免索引失效语法，就能提升查询性能。

连环追问

测试环境 SQL explain 走索引，看起来一切正常，也避开了隐式转换、函数操作这些常见索引失效写法。一旦线上流量上来，登录、信息查询接口频繁超时，数据库 CPU 持续 99%，大量慢查询拖垮整个服务。

  1. 根源在哪？索引优化不能只看单条 SQL，系统性优化思路有哪些？
  2. 索引是不是建得越多越好？

参考答案

一、索引带来的隐性风险

很多人以为索引就是用来加速查询，只关注会不会走索引，忽略索引本身的代价和优化器行为： 1）索引过多 单表索引太多，磁盘占用上涨，写入、更新、删除时需要同步维护所有索引，写性能大幅下降。高并发写入场景下，IO 和 CPU 开销会持续走高。

2）索引区分度不足 索引字段基数低、区分度很差，比如性别、状态这类字段。

优化器评估后，认为走索引不如全表扫描，主动放弃索引，触发全表扫描，查询性能断崖下跌。

3）索引失效隐性场景 隐式类型转换、反向范围查询、or 连接条件不当等，都会导致索引失效。哪怕开发自认为规避了常规写法，复杂组合条件下依然踩坑。

4）优化器选择偏差 统计信息不准、数据分布倾斜，explain 在测试环境走索引，线上数据量变了，执行计划突变，大量请求变成慢查询，瞬间打满 CPU。

二、索引与 SQL 系统性优化方案

1）控制索引数量 单张表索引建议不超过 5 个，按需新建，无用索引及时清理，降低索引维护成本。

2）控制索引粒度，合理设计联合索引 遵循最左前缀原则，优先把区分度高的字段放前面；不要盲目把所有查询字段塞进联合索引。定期通过慢查询日志、performance_schema 分析索引利用率，下线低频无用索引。

3）SQL 改写优化 避免一次性查询大批量数据；分页限制单页条数，大数据量场景分批查询；避免 select *，只查询需要字段；优化范围查询、or 条件，减少索引失效概率。

4）高频查询增加缓存兜底 热点高频查询增加 SQL 缓存，减少重复请求打到数据库，降低数据库查询压力。

5）慢查询全链路监控 开启慢查询日志，接入监控平台，抓取执行计划变化；关注执行计划突变，而不是只看 SQL 语法。

三、数据库架构兜底方案

核心业务数据库采用主从架构，读请求分发到从库，分担主库查询压力； 增加查询限流，防止突发流量、异常查询 SQL 打垮数据库； 做好读写分离，区分实时强一致查询和可延迟查询。

四、完整排查闭环流程

  1. 告警触发：数据库 CPU 持续高、接口超时；
  2. 抓取慢 SQL，查看执行计划，核对是否预期走索引；
  3. 排查：索引数量、索引区分度、数据分布、统计信息是否准确；
  4. 验证：是否存在隐式转换、范围查询不当等隐性索引失效；
  5. 优化：清理冗余索引、改写 SQL、调整联合索引；
  6. 架构兜底：缓存、读写分离、查询限流；
  7. 回归压测验证，持续监控执行计划与慢查询。

追问：本题考察核心是什么？

参考答案：初级开发只会背索引最左前缀、索引失效几种语法。高级工程师要建立系统性思维：

  1. 索引是有成本的，不是越多越好，索引同时影响读和写；
  2. explain 只是参考，执行计划会随数据分布、数据量变化，测试环境正常不代表线上稳定；
  3. 数据库优化不是只靠建索引，需要 SQL 优化、缓存、读写分离、限流组合兜底；
  4. 具备线上故障复盘能力：看懂慢查询、定位执行计划漂移，建立全链路监控意识。

核心思想：索引优化不是单纯调 SQL 语法，是查询收益、写入成本、数据分布、架构方案之间的综合权衡。

第 10 题　MySQL 慢查询优化，百万订单分页筛选索引失效故障复盘

问题 1：MySQL 慢查询该怎么优化？

候选人浅层回答： 给查询字段加索引、避免全表扫描，规范 SQL 写法就够用了。

连环追问

电商后台订单表百万数据，管理员筛选历史订单分页查询，接口频繁超时、页面加载缓慢；查询字段已经建好普通索引，但慢查询持续告警，数据库 CPU 居高不下，拖累其他业务。

  1. 索引明明建好了却没有生效，一般有哪些原因？怎么一步步定位？
  2. 能不能只靠加索引解决慢查询？如何从 SQL、索引、架构全链路根治慢查询？

参考答案

一、索引建了但查询依然很慢 / 不走索引的常见原因

  1. 索引失效语法问题 隐式类型转换、where 条件对索引字段使用函数、运算、like 以 % 开头、or 两边字段一个有索引一个无索引，都会直接让索引失效。
  2. 联合索引不满足最左前缀原则 联合索引顺序设计不合理，查询没有命中最左字段，无法使用该联合索引。
  3. 优化器代价评估后主动放弃索引 过滤后返回结果集占比太高、索引区分度差、小表全表扫描更快、统计信息不准，优化器判定走索引代价更高，主动选择全表扫描。
  4. 回表开销巨大 普通二级索引只存主键，查询大量列、大量行时频繁回表，随机IO 过高，即使走索引，性能依旧很差。
  5. 分页深度问题（本案例高频坑） limit 100000,10 这种深分页，数据库要扫描前面十万行数据再丢弃，索引也救不了深分页。

二、慢查询排查闭环流程

  1. 抓告警与日志：开启慢查询日志，抓取慢 SQL，拿到 SQL 文本、执行耗时、扫描行数；
  2. explain 查看执行计划：看 type、key、rows、Extra，确认有没有走预期索引、有没有 Using filesort、Using temporary；
  3. 定位根因：区分是索引失效、回表、排序分组、深分页，还是锁等待、资源瓶颈；
  4. 针对性优化 SQL 和索引；
  5. 压测验证，持续监控慢查询。

三、三层优化体系（SQL 层 → 索引层 → 架构层）

第一层：SQL 语句优化（优先做，成本最低）

  1. 杜绝 select *，只查询业务需要的字段；

  2. 改写 like、函数、条件，避免索引字段做计算；

  3. 优化分页：禁止大 offset 深分页，改用主键书签分页（id > 上一页最大 id limit

10）；

  1. 减少不必要的 order by、group by，尽量利用索引有序性避免文件排序；

  2. 拆分复杂大 SQL，避免单条 SQL 扫描海量数据。

第二层：索引精细化设计

  1. 根据查询条件、排序字段设计联合索引，遵守最左前缀；
  2. 优先建立覆盖索引，把 where、order by、select 字段都放进索引，消除回表；
  3. 低区分度字段不单独建索引；定期清理无用、低频冗余索引；
  4. 索引不是越多越好，索引会增加写入开销。

第三层：架构兜底优化（后台报表、海量历史查询场景）

  1. 读写分离：后台报表、历史统计查询走从库，不和线上主业务争抢资源；
  2. 数据冷热分离：历史订单归档到归档库 / 分表，活跃订单和几年前历史数据分开；
  3. 引入缓存：高频后台查询结果缓存，减少重复查询；
  4. 大数据量报表：同步到 Elasticsearch、数仓，检索、统计不在 MySQL 里面做；
  5. 限流：后台管理员查询增加查询限流，防止恶意 / 异常查询打爆数据库。

四、本案例（订单后台分页筛选）推荐落地方案

  • 筛选条件 + 排序字段构建联合覆盖索引，消除回表和 filesort；
  • 把 offset 分页改成书签分页；
  • 后台查询路由到从库；
  • 超久历史订单归档，减小主表数据体积；
  • 复杂多条件导出、统计查询放到 ES 或者数据仓库。

追问：本题考察核心是什么？

参考答案：初级开发的思维局限在 “慢了就加索引”，只会简单规避索引失效语法。高级工程师要有完整调优体系思维：

  1. 明白索引只是优化手段之一，不是万能解药；索引存在 ≠ 一定会被使用、一定会变快；
  2. 看得懂 explain 执行计划，能够区分索引失效、回表、文件排序、深分页等不同瓶颈；
  3. 能区分在线业务查询和后台报表查询，使用冷热分离、读写分离、搜索引擎等架构方案；
  4. 具备风险意识：后台管理系统的报表、分页查询，很容易成为数据库的隐形杀手，要做资源隔离和限流。

核心思想：MySQL 慢查询优化，是 SQL 写法、索引结构、数据生命周期、架构资源隔离一起配合的系统工程，而不是单一靠建索引

第 11 题　MySQL 千万级单表加完索引、硬件高配，查询依旧很慢

问题 1：MySQL 单表数据量达到千万级别，简单 select 查询要好几秒。你觉得是什么原因？

候选人浅层回答： 数据量太大，加上索引就可以解决。

追问 1：主键索引、普通索引都已经建好，查询还是很慢，怎么解释？

候选人浅层回答： 服务器硬件配置差，升级 CPU、内存就能解决。

追问 2：硬件已经是高配，SSD 磁盘、大内存、多核 CPU 全部拉满，查询依旧卡顿。如果仅仅只是数据量大的问题，那分库分表的意义是什么？

参考答案： 千万级表慢，不全是单纯数据量、硬件问题，就算索引齐全、硬件高配，依然会慢，常见根因分为几大类：

1、索引层面问题（索引存在，但没有高效使用）

  1. 索引失效：隐式转换、索引列运算、like 左模糊、违反联合索引最左前缀，SQL虽然有索引，实际走全表扫描。

  2. 回表代价过高：二级索引查到大量数据，需要大量回表访问主键聚簇索引。比如查询返回大量行，回表 IO 次数巨大，即使命中索引，耗时依旧很高。

  3. 索引选择性差：字段区分度很低（例如 status 状态只有 0/1），哪怕建了索引，优化器判定索引收益低，主动放弃索引走全表扫描。

  4. 统计信息不准：MySQL 统计信息失真，优化器选错执行计划，没有选择最优索引。

2、SQL 执行层面

  1. limit 大分页：limit 1000000,10，需要扫描并丢弃前面 100 万行，开销巨大。

  2. join 关联、子查询：千万表做 join，笛卡尔积膨胀，产生大量临时表、文件排序Using filesort。

  3. 查询返回大量数据：业务写select *一次性查出几十万行，网络传输、内存处理开销大。

3、存储与表本身问题

  1. 碎片问题：大量 delete/update 产生页碎片，页填充率低，同样数据占用更多磁盘页，IO 变高。

  2. 大字段：表包含 text、blob 大字段，行数据很大，单页存放行数变少，读取需要加载更多数据页。

  3. 事务与锁冲突：有长事务，undo、MVCC 版本链很长，查询需要扫描大量历史版本，快照读变慢。

4、为什么硬件拉满还慢？

硬件再好，软件逻辑缺陷不会被硬件完全掩盖。 比如回表百万次、扫描大量页面、MVCC 版本链过长，瓶颈变成逻辑 IO、锁、执行计划，不是磁盘物理 IO，升级硬件收益有限。

5、分库分表的意义千万表不是上来就必须分库分表。

  • 分表：把一张大表拆成多张小表，降低单表数据量，减少 B + 树索引高度，减少单次扫描的数据页；同时分散读写压力。
  • 分库：分散数据库实例 CPU、IO、连接数资源。

注意：分库分表是最后手段，优先优化 SQL、索引、表结构；很多千万表，做好索引优化不分表也能跑得很快。

整套可落地的排查 & 优化方案

  1. 使用explain 看执行计划，确认是否真正命中索引，关注 type、rows、Extra，排查回表、filesort、临时表；
  2. 改写 SQL：避免大 offset 分页，用主键游标分页；杜绝 select *；减少 join；
  3. 索引优化：保证索引高选择性，避免回表，可以使用覆盖索引；定期 analyze更新统计信息；
  4. 表结构优化：拆分大字段，碎片严重可以 optimize；杜绝长事务，减少 MVCC版本链膨胀；
  5. 架构手段：分区表、分表、分库，热点查询增加缓存；
  6. 分库分表属于终局方案，优先做前面优化，不要一上来就分库分表。

追问：这道题考察点是什么？

参考答案： 区分只会背 “加索引、升级机器” 的普通开发。面试官希望看到不把慢查询简单归罪于数据量大，能够从执行计划、索引使用代价、回表、MVCC、表碎片、SQL 写法多维度分析；同时理解分库分表的适用场景，知道分库分表是最后手段，而不是万能解药。很多人只停留在表面，遇到千万表直接说分库分表，分不清优先优化顺序。

第 12 题　慢 SQL、索引治理，不能无脑建索引

问题 1：线上数据库 CPU 飙高遇到慢 SQL，你怎么处理？

候选人浅层回答： 给查询字段加上索引，避免全表扫描，提升 SQL 执行效率。

场景案例追问电商订单库，平时访问平稳。大促高峰期，多条件筛选订单接口大量触发，部分字段缺少索引触发全表扫描，数据库 CPU 直接 100%，新增订单、支付入库接口全部阻塞超时。 事后给查询字段新增索引，简单查询恢复正常；但是多字段联合查询依旧很慢，索引失效反复出现，频繁引发数据库雪崩。问题出在哪？

连环追问

  1. 如何从 SQL 编写、索引设计、架构层面完整治理慢查询？
  2. 能不能遇到查询慢，就无脑给所有查询字段建立索引？

参考答案：

一、事故根因

只给单独字段建立普通单列索引，而业务是多字段联合查询。

  1. 单列索引各自独立，MySQL 一次 SQL 一般只能选用其中一个单列索引，剩下条件只能过滤回表；回表量大，SQL 依旧慢。

  2. 多条件查询，优化器会评估各个单列索引成本，统计信息波动，会出现索引选择摇摆，时而走索引、时而全表扫描，造成索引失效反复复现。

  3. 不能无脑给全部字段建索引：索引不是越多越好。

  4. 索引占用磁盘存储空间；

  5. DML（insert/update/delete）需要维护全部索引，索引越多，写入性能越差，订单大促写入压力大，过多索引会拖垮订单入库、支付更新；

  6. 大量索引会增加优化器选择执行计划的开销。

幽灵陷阱：很多人遇到慢查询，直接给 where 条件每一个字段单独建索引，以为问题解决，实际联合查询场景依旧性能很差，故障反复发生。

二、完整治理方案：SQL 编写、索引设计、架构三层防御

1、SQL 编码层面

  1. 杜绝select *，只查询业务需要字段，尽量使用覆盖索引减少回表；

  2. 联合查询遵循最左前缀原则，等值条件放前面，范围条件放后面；

  3. 避免索引列做函数运算、隐式类型转换、like 前缀 % 等索引失效写法；

  4. 控制分页，避免大 offset 分页；大结果集不要一次性查询全部，分批处理；

  5. 业务层面限制查询条件，禁止无边界的全量筛选，例如时间范围强制限制最大查询区间。

2、索引设计层面

  1. 多条件联合查询优先创建联合索引，而不是一堆单列索引；根据业务查询频率设计联合索引顺序；

  2. 评估索引收益：查询收益 vs 写入损耗。大促订单这类写入压力很高的表，严格控制索引数量；

  3. 索引字段要具备高区分度，低区分度字段（status 状态）不适合单独建索引；

  4. 定期analyze table 更新表统计信息，防止 MySQL 优化器选错索引；

  5. 上线前使用生产量级仿真数据做 explain 执行计划校验，小测试环境执行计划不能代表线上。

3、架构层面（兜底，防止慢 SQL 拖垮核心业务）

  1. 读写分离：订单筛选这类查询压力，全部丢到从库执行，主库只承担订单写入、支付更新核心链路；

  2. 热点查询增加缓存，避免频繁查询数据库；

  3. 复杂多条件订单筛选，不要强压 MySQL；统计、筛选类业务迁移到 ES 搜索引擎；

  4. 业务增加防护：SQL 执行超时时间，接口增加限流，防止大量慢 SQL 打满数据库；

  5. 监控告警：慢查询日志、CPU、连接数监控，慢 SQL 及时发现。

三、线上故障应急处理

  1. 故障爆发 CPU 打满：优先限流、降级筛选接口，把流量压下去，保护订单支付写入核心链路；
  2. 不要在高峰期随意新增索引，大表 DDL 会锁表，加剧故障；索引优化选业务低峰变更；
  3. 排查 explain 确认执行计划，判断是索引设计不合理还是 SQL 写法问题。

追问：本题考察核心是什么？

参考答案： 考察能不能跳出 “慢查询就加索引” 的固化思维。 很多开发只知道索引可以加速查询，忽略索引对写入的代价；分不清单列索引和联合索引适用场景。 高级后端要权衡查询收益与写入损耗，不能无脑堆索引；需要从 SQL 编码、索引设计、存储架构整套体系解决慢查询，而不是只靠新增索引这一招。同时区分核心写入链路和查询链路，通过读写分离、搜索引擎做架构隔离，避免分析类查询拖垮核心交易

第 13 题　MySQL 线上雪崩应急止损、索引失效排查治理

问题 1：线上业务高峰期，MySQL CPU 瞬间打满，数据库连接池被占满，核心接口大面积超时报错，监控看到慢查询数量一分钟暴涨百倍。你如何第一时间止损，并且精准定位根因？

候选人浅层回答： 直接 kill 掉所有慢查询，重启 MySQL 服务恢复。

连环追问

  1. 批量 kill 慢查询会不会触发大事务回滚风暴？流量没有下降故障再次复现，如何快速降级？
  2. 如何区分故障根因：新上线 SQL 索引失效、数据量暴涨导致索引退化、行锁冲突堆积连锁反应？
  3. 如果同时存在主从延迟叠加慢查询，读写分离架构如何做切流兜底？
  4. 请描述慢 SQL 引发 MySQL 全链路雪崩完整故障时间线。

参考答案：

一、慢 SQL 引发 MySQL 雪崩完整故障时间线

  1. 触发点：一条 / 多条 SQL 发生索引失效，由索引扫描变成全表扫描；
  2. SQL 执行消耗大量 CPU，执行耗时变长，数据库连接被长时间占用不释放；
  3. 业务请求不断过来，新连接持续创建，数据库连接池被快速打满；
  4. 新业务请求拿不到 DB 连接，接口大量超时；大量超时请求堆积在应用服务线程池；
  5. 上游继续发起流量，形成恶性循环；数据库 CPU 持续 100%，正常业务 SQL也被拖慢；
  6. 如果开启读写分离，主库压力暴涨，产生大量 binlog，从库同步跟不上，主从延迟飙升；从库查询也会受影响，整个读写分离链路全部异常；
  7. 严重时锁等待堆积，锁超时，进一步放大故障，引发全链路雪崩。

风险点：直接批量 kill 正在执行的大事务慢 SQL，MySQL 需要执行回滚，回滚会消耗大量 CPU、IO，产生回滚风暴，数据库压力会进一步飙升，故障反而恶化，不能无脑全部 kill。

二、故障现场：优先应急止损（先保业务，再定位根因）

  1. 流量层面优先降级限流，而不是上来 kill、重启数据库

  2. 非核心业务直接开关降级关闭；核心接口限流，削减打到 DB 的 QPS；

  3. 热点查询尽可能切缓存，减少数据库访问；

  4. 读写分离场景：如果是从库慢查询导致故障，把读流量切回主库或者切换到其

  5. 他健康从节点；主库故障，优先切读流量，写流量做好降级保护。

  6. 谨慎处理慢 SQL

  7. 通过show processlist/performance_schema 找出慢 SQL；

  8. 优先 kill 小事务慢查询；谨慎 kill 大事务 SQL，避免回滚风暴；大事务尽量等

  9. 待执行完毕，配合流量压制。

  10. 重启 MySQL 是最后兜底手段，重启会断开全部连接，未提交事务全部回滚，业务中断时间长，尽量不优先使用。

  11. 临时业务止损手段

  12. 如果是新上线版本引入的 SQL 问题，立刻回滚发布版本；

  13. 通过临时开关屏蔽问题接口，阻断异常 SQL 持续涌入数据库。

三、根因区分定位

  1. 新上线 SQL 索引失效：故障时间点刚好对应版本发布；抓执行计划 explain，

  2. 确认 SQL 走全表扫描；属于上线引入问题。

  3. 数据量暴涨导致索引退化：SQL 本身有索引，随着表数据增长，索引选择性下降；MySQL 优化器判定全表扫描代价更低，主动放弃索引；表统计信息失真。

  4. 行锁冲突堆积连锁反应：慢查询本身性能不差，但是长事务持有行锁，大量业务 SQL 锁等待；连接堆积，CPU 升高；查看show engine innodb status 看锁等待信息。

排查工具：慢查询日志、performance_schema、explain、innodb状态、binlog，结合发布记录、监控指标（CPU、连接数、主从延迟、锁等待）综合判断。

四、索引失效长效治理完整方案

  1. 上线前阶段
  • 评审 SQL，使用 explain 校验执行计划；重点校验联合索引最左前缀、隐式转换、范围条件；
  • 大表变更禁止业务高峰期 DDL；
  • 压测使用生产量级仿真数据，不要只拿少量测试数据验证（小数据量执行计划和生产海量数据会不一样）。
  1. 线上监控告警
  • 开启慢查询日志，监控慢查询数量、执行时间；
  • 监控数据库 CPU、连接数、主从延迟、锁等待，设置告警；
  • 监控表统计信息，大表定期analyze table 更新统计信息，防止优化器选错索引。
  1. 故障事后治理
  • 修复失效索引，改写问题 SQL；
  • 区分故障等级：
  • 低风险：报表类非核心查询慢，优化索引即可；
  • 中风险：核心业务接口 SQL 性能随数据量下降，改写 SQL、优化索引、必要时分表；
  • 高风险：引发雪崩的 SQL，增加限流、缓存、熔断，增加防护。
  1. 架构兜底 读写分离、热点数据缓存；数据库连接池做好最大连接限制，防止DB 连接被耗尽；业务设置 SQL 执行超时时间，避免单 SQL 长时间占用连接。

追问：本题考察核心是什么？

参考答案： 区分测试环境和生产环境。很多开发以为建索引、上线看一眼explain 就万事大吉。 但测试环境数据量小，和线上海量高并发场景完全不一样。 考察点：

  1. 故障发生懂得先止损，而不是上来 kill、重启数据库，理解 kill 大事务带来回滚风暴的副作用；
  2. 能够区分索引失效、数据量退化、锁等待堆积这几类雪崩诱因；
  3. 读写分离架构下懂得切流兜底；
  4. 不止会应急，还要有完整长效治理手段，建立上线‑监控‑故障复盘闭环。 高级后端工程师需要懂得数据库故障连锁反应，不能只靠数据库本身扛住一切，业务层、架构层也要做防护。

第 14 题　MySQL InnoDB RR 可重复读与幻读

问题 1：InnoDB 默认的可重复读 (RR) 隔离级别，能不能彻底解决幻读？线上同一个事务内两次范围查询结果不一致，出现幻读引发业务数据异常，如何分析根因，如何选型隔离级别规避问题？

候选人浅层回答： RR 级别依靠 MVCC 就可以解决幻读，串行化完全没有幻读，普通项目直接用默认 RR 就够用；遇到幻读直接改成串行化。

连环追问

  1. SQL 标准中 RR 是无法解决幻读的，为什么 InnoDB 的 RR 可以？依靠什么机制？
  2. 事务先执行普通 select（快照读），紧接着 update 做范围更新，会不会更新到别的事务刚刚插入的新行？算不算幻读？
  3. select … for update 当前读，锁定的是单行还是整个范围区间？间隙锁、临键锁区别？间隙锁为什么容易产生死锁？
  4. 如果业务要求绝对杜绝幻读，直接改成串行化行不行？有什么性能代价？生产什么场景才使用串行化？
  5. 不依赖数据库锁，业务层面如何规避幻读？线上幻读导致数据异常，如何定位复现？

参考答案：

1、RR 可重复读到底能不能解决幻读SQL 标准定义的 RR 隔离级别不能解决幻读。 InnoDB 的 RR 做了增强，依靠两套机制配合：

  1. MVCC 快照读（普通 select）：事务内快照建立之后，看不到其他事务新插入的数据，快照读层面看不到幻读。

  2. 临键锁 (Next‑Key Lock，间隙锁 + 行锁)：针对当前读（update、delete、selectfor update），锁住范围间隙，阻止其他事务在这个区间插入新数据，解决当前读的幻读。

  • 重要坑点：同一个事务混合快照读 + 当前读，会出现幻读现象。 示例：事务先普通 select（快照读，看不到别人新插入记录）；接着执行 update 范围更新（当前读），会读到并且更新其他事务刚刚插入的新行。同事务前后结果不一致，业务上表现出幻读。MVCC 快照无法阻挡 update 当前读写入新数据。

3、间隙锁、临键锁概念

  • 行锁：锁住索引上已经存在的记录。
  • 间隙锁 (Gap Lock)：锁住索引记录之间的空隙，禁止其他事务往间隙插入新数据，专门用来防止幻读；间隙锁不锁定记录本身，只锁空隙。
  • 临键锁 Next‑Key Lock = 行锁 + 间隙锁，InnoDB RR 级别下范围当前读默认使用临键锁。

注意：如果查询条件命中唯一索引，能够精确匹配到一条记录，临键锁会退化为单纯行锁，不再加间隙锁。

间隙锁带来副作用： 间隙锁锁定的是索引空隙，不是真实数据，多个事务可以互不冲突持有不同间隙锁，互相等待对方释放间隙，极易产生死锁。这也是 RR 级别死锁概率高于 RC 的原因。

4、业务要求绝对不能幻读，直接改成串行化可行吗？

串行化（SERIALIZABLE）隔离级别下，InnoDB 会对所有读操作加锁（自动提交关闭、显式事务内的普通 SELECT 会隐式转为锁定读），完全杜绝幻读。 代价巨大： 并发能力急剧下降，大量锁等待，性能很差。 生产极少使用串行化，仅用于数据一致性要求极高、并发很低的小众场景，绝大多数业务不推荐。

5、线上幻读异常根因分析 & 复现定位常见根因：

  1. 事务内部混合快照读与当前读，快照看不到新插入行，但 update/delete 当前读可以操作新插入行，业务逻辑错乱；

  2. 加锁 SQL 没有命中索引，临键锁失效，没有锁住间隙，其他事务成功插入数据产生幻读；

  3. 业务逻辑错误，误认为 MVCC 可以阻止 update 操作看到新数据。

定位排查手段：

  1. 开启 binlog、观察锁等待日志，复现业务事务执行完整顺序；

  2. 区分 SQL 是快照读还是当前读；

  3. 确认加锁 SQL 是否命中索引，判断间隙锁是否生效。

5、规避幻读的方案，分为数据库层 + 业务层数据库层面

  1. RR 级别下，如果业务需要防止范围插入，做范围操作必须使用select …for update 当前读，并且一定要命中索引，让临键锁生效；

  2. RC 隔离级别：没有间隙锁，并发高、死锁少，但是 RC 本身无法解决幻读；适合业务可以容忍幻读的场景；

  3. 串行化：一致性最强，放弃并发，极少使用。

业务层面（不依赖数据库锁）

  1. 使用唯一业务约束：业务唯一键，从数据库层面禁止重复插入；
  2. 悲观逻辑改为乐观锁：版本号 version 机制；
  3. 尽量缩小事务范围，避免长事务中做多次范围查询；
  4. 避免同一个事务混合普通快照 select 和范围 update/delete；
  5. 业务增加幂等校验，即使出现幻读新增数据，业务可以自动修正。

追问：这道题考察核心是什么？

参考答案： 不考察死记隔离级别名词。很多人误以为 RR 的 MVCC 就彻底解决全部幻读。面试官想看你理解：MVCC 只作用快照读；当前读靠临键锁；混合快照读与当前读依然会出现业务幻读；清楚间隙锁带来死锁副作用；懂得权衡隔离级别一致性与性能；不止会调数据库参数，还能给出业务层兜底方案。

高级工程师认知：没有万能隔离级别，根据业务并发、一致性要求做取舍，优先业务层规避，而不是一味靠数据库锁硬扛。

第 15 题　RR 隔离级别下秒杀库存超卖问题

问题场景

商品库存服务使用 MySQL 默认 RR（可重复读）隔离级别。扣库存逻辑封装在事务内：先普通 select 快照读查询库存，判断库存充足之后，执行 update 扣减库存。 自测、压测没问题，线上秒杀并发场景出现库存扣成负数，发生超卖。每个事务单独执行读到的都是正数库存，都执行更新成功，无锁报错、无脏读、无不可重复读，多个事务同时扣减成功。请问问题出在哪里？

候选人浅层回答： RR 级别依靠 MVCC + 间隙锁已经彻底解决幻读，不会出现这种现象，应该是事务配置写错。

连环追问

  1. 事务开启正常，隔离级别配置无误，为什么并发下多个事务都读到同一份库存快照，并且先后完成扣减？
  2. 线上遇到该问题如何定位根因？是不是所有写业务都要加排他锁串行执行？

参考答案：

根因剖析

  1. 业务代码使用普通 select 快照读查询库存，MVCC 快照读不会加任何行锁。

多个并发事务，同一时刻读取到同一个快照版本，都看到库存 > 0，全部通过库存充足的校验。 快照读只解决当前事务内的视图一致性，不会阻止其他事务同时修改这行数据。

  1. 随后执行 update 属于当前读，会加行排他锁。事务排队依次执行扣减。 第一个事务扣完库存，但是其他事务已经基于旧快照做过 “库存充足” 的业务判断，后续排队执行 update 依旧会继续扣减，最终库存扣成负数，出现超卖。

关键点：这不是传统意义的幻读（插入新数据），属于快照读做业务判断带来的并发写冲突。RR 的 MVCC 只能保证本事务查询视图不变，不能用来做并发下的业务条件校验。间隙锁 / 临键锁在这里不会生效，因为 select 是快照读，没有加锁。

  1. 几种解决方案方案 1：悲观锁，查询阶段使用当前读把普通 select 改为select … for update，查询时加排他行锁。

注意：这是当前读，会加行锁。并发请求排队拿到锁，拿到锁之后读取的是最新已提交库存，再做库存充足判断，再扣减。 缺点：高并发秒杀场景大量锁等待，数据库压力大，性能差。

方案 2：update 原子条件更新（推荐，无锁，数据库层面原子操作）放弃先查询再判断再更新的逻辑，直接一条 update 语句完成条件判断 + 扣减。

数据库单条 SQL 是原子执行。返回受影响行数，如果等于 0，代表库存不足，业务返回秒杀失败。 优势：不需要手动加锁，利用 SQL 原子性，避免快照读带来的判断失效，并发性能好。

方案 3：乐观锁版本号机制增加 version 版本字段。

更新行数为 0 代表更新失败，业务捕获重试或返回失败。 适合并发没那么极端的场景；秒杀极高并发会出现大量更新失败，需要业务处理重试。

方案 4：前置限流 + Redis 预扣库存高并发秒杀，流量挡在 MySQL 之外。Redis 先预扣库存，库存耗尽直接返回失败；数据库做最终扣减，降低 DB 并发压力。

线上定位排查思路

  1. 区分 SQL 是快照读还是当前读，看业务是否拿普通 select 返回结果做业务条件判断；
  2. 观察 binlog，看多条事务 update 的执行顺序，确认多个事务读取的是旧快照；
  3. 复现：开启多个会话，模拟并发，复现 “快照读判断，update 扣减” 的现象。

不建议全部业务无脑加排他锁串行执行，会严重降低吞吐量，优先使用原子 update。

追问：这道题考察点是什么？

参考答案： 考察是否真正理解 MVCC 快照读的边界。很多人死记硬背 RR 解决幻读，误以为 RR 隔离级别就可以搞定并发业务校验。 MVCC 快照读只能保证查询视图一致性，快照读到的数据不能直接拿来做并发业务条件判断。 高级后端需要具备并发数据一致性工程思维：隔离级别只是基础，不能完全依赖数据库隔离级别解决业务并发问题，要结合原子 SQL、乐观锁、悲观锁、缓存限流做整套防护，避免资损事故。

三层防御总结

  1. 数据库层：优先使用原子条件 update，避免快照读做业务判断；必要时使用悲观锁 / 乐观锁；
  2. 业务层：扣减之后校验库存结果，失败直接返回；
  3. 架构层：高并发场景上层限流、Redis 预扣，削减打到 DB 的并发压力。

第 16 题　线上长事务引发连接打满、死锁、CPU 高、主从延迟，完整应急、排查、根治方案

考察重点：不是简单 “删代码缩短事务”，而是应急止损 → 定位根因 → 针对性治理 → 长效防控整套闭环，同时处理衍生问题：行锁排队雪崩、主从延迟、undo 膨胀、跨服务事务困境。

先明确长事务带来的连锁危害（InnoDB）长事务会持续持有行锁、MVCC 快照：

  1. 行锁长期不释放，并发更新排队，锁等待堆积、死锁暴涨，数据库连接池被吃光；
  2. undo 日志无法回收，undo 持续膨胀，磁盘占用上涨、回滚变慢；
  3. binlog 提交间隔拉长，主从同步延迟飙升；
  4. 大事务回滚代价极高，回滚期间进一步锁阻塞、CPU 冲高；
  5. 快照版本长期保留，查询扫描旧版本，查询性能衰减。

一、第一步：故障应急止损（优先保障核心业务，几分钟内操作）

目标：先阻断雪崩，恢复核心接口，再慢慢定位，不能直接重启库。

  1. 限流熔断：对触发长事务的接口 / 定时任务降级、限流，隔离故障流量，防止继续抢占连接和锁；非核心统计、导出、后台任务直接暂停。
  2. kill 掉正在执行的长事务会话 通过 information_schema.innodb_trx找到长时间运行的事务 trx_id、trx_mysql_thread_id，执行 kill thread_id；

注意：kill 后事务会回滚，大事务回滚本身也很重，不要一次性批量 kill，分批操作。

  1. 临时扩容数据库连接（如果还有余量），给核心业务预留连接；

  2. 读写分离场景：临时把强一致查询切回主库，避免从库延迟导致业务读到旧数

  3. 据引发逻辑错误。

二、第二步：根因排查（定位是哪类长事务）

核心查询：innodb_trx + show engine innodb status（锁等待、死锁日志）、慢日志、业务埋点。 常见几类根因：

  1. 事务内混入远程 RPC/HTTP 调用（最高频坑）：数据库 SQL 写完，事务不提交，等待外部接口返回；网络抖动就变成超长事务；
  2. 事务内大批量循环 DML，一次性更新上万行，单事务处理量太大；
  3. 事务内包含大查询，大表无索引扫描，SQL 执行耗时久，事务一直挂着；
  4. 代码 bug：异常分支没有提交 / 回滚，事务一直不关闭；
  5. 分布式事务场景：TCC/SAGA 协调器阻塞，分支事务不提交。

关键指标：事务持续时长、持有锁的行范围、undo 增长速率、binlog 提交间隔。

三、第三步：分场景根治方案（面试官追问重点）

场景 1：事务里面有远程调用 RPC / 第三方接口

  • 原则：事务里面绝对不要放远程调用 改造思路：
  1. 先提交本地 DB 事务，把「待调用外部服务」记录到本地任务表（任务状态：待执行）；
  2. 事务提交释放锁；
  3. 独立异步线程 / MQ 消费这条任务记录，发起远程调用；
  4. 调用成功更新任务状态；调用失败重试、死信告警；
  5. 配套幂等，防止重试重复调用第三方。

本质：把外部调用移出锁区间，数据库事务只做本地状态落盘。

场景 2：大批量数据更新，单事务处理太多行（批量 DML）不能一次性拆成无事务循环（容易中间宕机，数据半更新）。 方案：分批小事务

  • 分页分批，每一批只处理几百～几千条；每一批单独开启事务、提交、释放锁；
  • 业务允许的前提下，放到凌晨低峰执行；
  • 加合理分页条件（主键 id 分批，避免偏移量分页）；
  • 禁止一次性 update 全表、大范围无索引更新。

场景 3：事务内存在慢查询、大表扫描

  1. 优先加索引，优化 SQL；

  2. 如果是统计类只读查询，直接移出事务，丢到从库执行；

  3. 报表统计不要和业务写逻辑放在同一个事务里；报表走离线数仓。

场景 4：主从延迟暴涨的配套处理

根源：大事务一次性生成大量 binlog，从库回放跟不上。 治理：

  1. 上面的分批小事务，打散 binlog；
  2. 业务侧做延迟感知：读取前判断从库延迟，延迟超过阈值，自动路由到主库；
  3. 核心强一致查询走主库，非实时展示类放从库；
  4. 避免大批量 DDL，DDL 本身也是重事务。

场景 5：undo 日志膨胀问题undo 不能手动清理，undo 只有当没有活跃事务需要这个快照时才回收。 根治手段就是消灭长事务；应急只能杀掉长事务等待 undo 回收； 长期：控制事务时长，不要长时间打开只读事务（很多框架自动开启只读事务，非常隐蔽）。

场景 6：跨服务分布式事务场景（不能拆本地事务）不能用数据库长事务跨节点锁等待。根据一致性容忍度选型：

  1. 强一致：TCC，把资源锁定放在 try 阶段，缩短锁定时间，不要长时间占用资源；
  2. 最终一致：SAGA，本地小事务 + 补偿逻辑，避免全局锁等待；
  3. 尽可能降低分布式事务范围，把非强一致逻辑剥离出去，走 MQ 异步。

场景 7：业务链路特殊，业务上暂时无法拆分事务兜底方案（不推荐长期使用，只是临时手段）：

  1. 缩小锁范围：精确更新，避免范围锁、间隙锁；索引必须到位，减少锁覆盖行数；
  2. 隔离流量：把这个链路单独压控，低峰期执行；
  3. 锁超时设置合理，避免无限等待；
  4. 业务层面做补偿对账，兜底异常。

死锁配套优化统一所有 SQL 加锁顺序，避免循环等待； 尽量按主键顺序更新；减少同一个事务内多表交叉更新。

四、三层核心逻辑（面试官想要的三层框架）

第一层：编码与规范层（事前预防）

  1. 规约：事务内部禁止 RPC、HTTP、大查询、耗时逻辑；事务尽量短小，“快开快关”；
  2. 框架层面禁止隐式长只读事务（很多 ORM 自动开启事务）；
  3. 代码评审、SQL 审核环节拦截超大事务、事务内远程调用。

第二层：监控告警与熔断层（事中感知止损）监控指标：

  • 活跃事务时长 TOP、锁等待时间、死锁次数、undo 占用、主从延迟、binlog提交间隔；
  • 设置告警：事务超过阈值（比如 3s/5s）告警；
  • 限流熔断：识别长事务流量，自动降级。

第三层：对账补偿兜底层（事后兜底）即使做了拆分、异步化，依然存在极端故障。 定时对账任务，校验跨服务、跨表数据一致性，发现不一致自动告警、触发补偿逻辑。

五、初级 vs 高级工程师区别

初级：只想到精简代码、拆分事务，回答很笼统，回答不了衍生问题：undo 膨胀、主从延迟、RPC 在事务里怎么办、不能拆分的时候怎么办。 高级：

  1. 先应急止损，知道 kill 会话的风险（回滚开销），不是上来改代码；
  2. 区分不同类型长事务的改造方案，清楚 RPC 在事务内是头号杀手；
  3. 理解 MVCC、undo、binlog、主从延迟之间的联动关系；
  4. 有完整工程化体系：规范、SQL 审核、监控、限流、灰度改造，而不是单次修复。

第 17 题　MySQL 线上死锁故障排查与根治治理

问题 1：线上日志抛出死锁异常，事务被自动回滚，业务执行失败。你如何快速定位死锁根因？如何从根源避免死锁反复发生？

候选人浅层回答： 给查询加索引缩小锁范围；不行就上分布式锁让事务串行执行。

连环追问

  1. 线上突发死锁，执行什么命令拿到完整死锁现场？只看业务日志能不能分清两个事务各自持有锁、等待锁的情况？
  2. 两个事务更新同一张表两行，操作顺序相反触发循环等待死锁，不靠开发人工自觉，代码层面如何统一规避？
  3. 间隙锁导致死锁：两个事务做范围加锁查询，并发插入，互相等待间隙锁。如何识别、如何解决？
  4. 高并发场景，不能完全串行（性能暴跌），不能上分布式锁，不能改业务操作顺序，还有什么手段降低死锁概率？有没有不用改代码的临时方案？调低隔离级别能不能解决间隙锁死锁？副作用是什么？
  5. 多表事务，跨表锁交叉等待，如何系统性治理，而不是出现一例改一例？

参考答案：

一、线上死锁现场定位

  1. 核心命令：show engine innodb status;，输出结果中LATESTDETECTED DEADLOCK 模块，保存最近一次死锁完整现场。
  • 重点：业务应用日志只会报死锁异常，看不到锁信息、SQL、事务持有 / 等待关系，不能用来分析锁冲突；必须依赖 InnoDB 死锁日志。 死锁日志可以看到：两个事务分别执行什么 SQL、已经拿到什么锁、正在等待什么锁、锁类型（行锁 / 间隙锁）。
  1. 配套辅助信息：binlog、慢查询日志、业务代码事务逻辑；监控死锁次数、事务回滚率，死锁指标飙升及时告警。

注意：MySQL 只会保存最近一次死锁，如果死锁频繁发生，要定时采集 innodb 状态，防止现场被覆盖丢失。

二、两类典型死锁场景识别

场景 1：行锁循环等待（不同更新顺序）事务 A：更新 id=1，再更新 id=2 事务 B：更新 id=2，再更新 id=1 互相持有对方需要的行锁，循环等待触发死锁。 根治手段：统一资源加锁顺序，所有业务更新记录，按照主键 ID 升序（或降序）固定顺序操作，从根源破坏死锁「循环等待」必要条件。

不能依靠开发自觉：封装公共更新工具、代码 CR 阶段检查多记录更新顺序，强制排序。

场景 2：间隙锁 / 临键锁带来的死锁（RR 隔离级别特有）RR 级别范围select … for update 会加临键锁（行锁 + 间隙锁）；间隙锁锁住索引空隙，多个事务可以同时持有互不冲突的间隙锁，后续插入时互相等待，形成死锁。 识别特征：死锁日志中出现gap lock 关键字，SQL 是范围加锁查询。 解决方案：

  1. 能命中唯一索引，就用等值查询，临键锁退化为普通行锁，消除间隙锁；
  2. 临时方案：隔离级别从 RR 调整为 RC，RC 没有间隙锁，可以彻底消除间隙锁类死锁；RC 副作用：会出现幻读；业务要接受 RC 带来的隔离级别变化，业务层做好幂等、唯一约束兜底。

三、通用降死锁手段（不能改顺序、不能加分布式锁、高并发场景）

  1. 缩小事务粒度（最重要） 事务尽量短小，不要在事务内部做 RPC、大查询；尽快 commit，缩短锁持有时间，降低锁冲突概率。长事务会放大死锁发生概率。
  2. 索引一定要命中 加锁 SQL 必须命中索引；没命中索引会升级为表级意向锁，锁范围急剧放大，死锁概率暴涨。
  3. 业务捕获死锁异常，有限次数重试 重试只是补救，不能根治死锁；只适合少量偶发死锁场景。
  4. 不推荐直接上分布式锁处理数据库行锁死锁：会引入新组件，复杂度上升，性能损耗，属于重方案，优先数据库层优化。

四、多表跨表事务死锁系统性治理

  1. 梳理所有跨多张表的事务，统一表的访问顺序，例如固定先操作 A 表，再 B

  2. 表，再 C 表；禁止不同业务颠倒表操作顺序。

  3. 尽量拆分大事务，把跨表大事务拆成多个小事务；

  4. 代码评审卡点：对于多表更新、批量更新逻辑，重点评审锁顺序、事务大小，防止新增逻辑引入交叉锁；

  5. 线上监控死锁指标，定期复盘死锁日志，提前发现隐患，不要等故障爆发再修复。

追问：本题考察核心是什么？

参考答案： 不是考察背诵死锁四个必要条件。

  1. 知道怎么抓取真实死锁现场，明白业务日志不足以分析锁冲突；
  2. 区分普通行锁死锁和间隙锁死锁，理解 RR/RC 隔离级别对间隙锁的影响以及取舍；
  3. 区分补救手段（重试）和根治手段（锁顺序、缩小事务、优化索引）；
  4. 具备系统性治理思维，遇到跨表死锁，不是修单个 case，而是从编码规范、CR评审、监控告警整套体系规避。

高级工程师认知：分布式锁不是万能解药，优先在数据库、业务代码层面解决；隔离级别调整是临时手段，要清楚带来的业务风险。

第 18 题　MySQL 数据库死锁，电商大促死锁线上故障复盘

问题 1：数据库死锁怎么解决？

候选人浅层回答： 统一加锁顺序；设置锁超时，配合死锁检测自动回滚，基本就能避开死锁问题。

连环追问

电商有两条核心链路： 下单链路：先扣库存，再更新订单状态； 退款链路：先回滚订单状态，再返还库存。 两套逻辑都会对订单表、库存表加行锁。 大促高峰期突然大面积报错，大量下单、退款请求失败；用户付款后订单状态不更新，退款长时间处理卡住。查看数据库日志，频繁出现死锁。 两条链路加锁顺序相反，高并发下形成循环等待；但单独看每一条链路，执行顺序都符合业务逻辑。

  1. 问题根源是什么？
  2. 业务场景复杂，不同链路天然有不一样的操作流程，难道要强行把所有业务改成同一个加锁顺序，才能杜绝死锁吗？

参考答案

一、死锁形成四大必要条件

死锁必须同时满足四个条件：互斥、持有并等待、不可剥夺、循环等待。 统一加锁顺序，本质就是破坏循环等待，也是大家最常用的方案。 但这个方案有局限性：业务复杂时，不同业务链路业务流程本身就不一样，强行统一顺序会非常别扭，甚至改不动业务流程，只靠统一顺序无法覆盖全部场景。

本次事故根源： 下单：锁库存 → 锁订单 退款：锁订单 → 锁库存 高并发交错执行，事务 A 拿到库存锁等待订单锁，事务 B 拿到订单锁等待库存锁，形成循环等待，触发死锁。

二、三层防御体系（根源治理方案）

第一层：事前预防（优先做，成本最低）

  1. 梳理全链路锁资源清单，对公共资源约定全局加锁优先级，优先锁优先级编号小的资源。如果业务允许，尽量对齐加锁顺序，破坏循环等待条件。
  2. 缩小事务粒度，事务尽量短小，不要在事务内部做 RPC、等待外部接口、长时间业务计算；事务持有锁的时间越短，死锁概率指数下降。
  3. 避免在同一个事务里，交叉更新多张无关的热点表；热点资源尽量收敛。
  4. 能不加行锁就不加行锁：优先使用乐观锁（版本号 / 时间戳），version 版本控制，不加排他锁，从源头规避行锁竞争。适合库存扣减这类场景。

第二层：事中控制（并发冲突发生时兜底）

  1. 锁超时：innodb_lock_wait_timeout，等待超时主动回滚，避免事务无限阻塞。
  2. 死锁检测：InnoDB 默认开启死锁检测，检测到死锁自动选择代价更小的事务回滚，释放锁资源。

注意：高并发热点场景，死锁检测本身有性能开销；超高吞吐场景可以关闭死锁检测，依靠锁超时兜底，需要权衡。

  1. 排队串行化：热点资源引入分布式锁，把对同一个资源的并发更新串行化，避免数据库层面行锁交叉竞争。比如同一个商品库存的扣减排队。

第三层：事后兜底（死锁依然发生时）

  1. 捕获死锁异常（Deadlock found when trying to get lock），做有限次数重试，重试失败进入异常流程；禁止无限重试，防止风暴。
  2. 死锁日志常态化采集、监控告警，定时分析死锁栈，定位新增冲突链路，持续优化锁逻辑。
  3. 异常消息走死信队列，人工核对订单、库存数据，防止数据不一致。

三、方案选型对比

  1. 统一加锁顺序：简单可靠，适合新业务、链路少的场景；老业务多链路耦合时改造难度大。
  2. 乐观锁：无锁竞争，性能好；适合允许版本冲突重试的场景，不适合强阻塞、高冲突场景。
  3. 缩小短事务：普适最优实践，任何锁场景都应该遵守。
  4. 分布式锁串行热点：适合秒杀、库存这类超高竞争热点资源。

四、电商案例优化落地

原逻辑： 下单：begin；扣库存；更新订单；commit 退款：begin；更新订单；返还库存；commit优化方案可选其一： 方案 A（统一顺序）：两条链路都改成【先锁库存、再锁订单】，退款逻辑调整，优先操作库存回补，再更新订单。 方案 B（乐观锁改造）：库存表增加 version 版本号，扣减、回补库存使用乐观锁，不再加排他行锁，消除锁竞争。 方案 C（拆分事务）：把跨表更新拆成短事务，或者引入分布式锁对同一个商品 ID 串行处理。

追问：本题考察核心是什么？

参考答案：初级开发只会背统一加锁顺序、死锁检测、锁超时。高级工程师要有前置治理思维：

  1. 明白统一加锁顺序只是手段，不是万能银弹，有业务落地局限性；
  2. 理解死锁四大条件，所有解决方案本质都是破坏其中任意一个条件；
  3. 不是死锁出现了才去查日志，而是提前梳理全链路锁资源、评估锁竞争；
  4. 懂得分层设计：事前预防 > 事中控制 > 事后重试兜底，优先用乐观锁、短事务降低锁冲突；
  5. 能结合电商下单退款真实业务，权衡改造成本，给出可落地的多种方案，而不是只有一套标准答案。

核心思想：死锁治理不是只靠事后回滚，锁的风险要在业务设计阶段就纳入考量，短事务、少加锁，优先规避而不是事后补救。

第 19 题　明明统一了表更新顺序，依然发生 InnoDB 死锁

场景复盘

电商支付事务，同时操作三张表：订单表、支付流水表、用户余额表。 开发已经统一规定表更新顺序，但是高并发下仍然出现死锁，接口阻塞、支付失败，只能重启数据库恢复。

核心考点：死锁不只是跨表顺序问题，还有行锁、间隙锁、索引、加锁范围、隔离级别带来的隐性死锁；固定表顺序只是基础手段，不是万能解药。

先回答核心问题：为什么表顺序统一了，还会死锁？

InnoDB 是行级锁，锁的是索引记录，不是整张表。 常见几个高频原因：

  1. 同一张表内多行更新，行的访问顺序不一致 只控制 “表的先后”，但是事务A 更新行 1、行 2；事务 B 更新行 2、行 1。单表内部行顺序交叉，依然循环等待。
  2. 索引缺失，触发范围锁 / 间隙锁（最常见幽灵陷阱） 更新条件没命中唯一索引，InnoDB 退化成扫描，锁住一大片间隙（gap lock）。间隙锁互相抢占，很容易形成死锁；RR 隔离级别下这个问题尤为突出。
  3. 主键 / 唯一键不同，加锁顺序错乱 不同事务操作不同行，虽然表顺序一样，但命中的索引记录锁交叉等待。
  4. 事务内多段 SQL、分支逻辑导致动态加锁顺序 if/else 分支，不同支付场景走不同更新逻辑，部分分支偷偷改变行加锁顺序，代码评审很难一眼看出来。
  5. 悲观锁 select … for update 的坑 查询没命中索引，锁范围放大；或者两条select for update 锁定行互相交叉。

一句话总结：锁是锁索引行，不是锁表；统一表顺序 ≠ 统一行锁顺序。

一、死锁精准排查方法

开启 InnoDB 死锁日志，核心命令：

找到 LATEST DETECTED DEADLOCK 区块，里面会写明：

  • 两个事务分别持有什么锁、等待什么锁
  • SQL 语句、等待的索引记录
  • 锁类型：record lock /gap lock /next-key lock排查步骤：
  1. 拿到死锁日志，定位两条冲突 SQL；
  2. 检查 where 条件有没有命中唯一索引；
  3. 打印两条事务分别锁住的行主键；
  4. 核对代码分支，确认是否存在分支导致行顺序颠倒；
  5. 核对隔离级别：RR（默认）存在间隙锁，RC 无间隙锁。

配套监控： 采集 information_schema.innodb_locks、innodb_lock_waits，对接告警；死锁发生立刻推送日志。

二、三层防御体系（面试官想要的标准答案）

第一层：编码与 SQL 层（事前，从源头减少锁交叉）

  1. 优先固定【行主键顺序】，而不只是表顺序 更新多行时，统一按主键 id 升序排序之后再执行更新，避免行逆序抢占锁。
  2. 杜绝无索引更新、范围更新 update 条件必须命中主键 / 唯一索引，把锁精准限制在单行记录，消除间隙锁风险。
  3. 精简事务，缩小锁持有时间 事务短小，快开快提交；不要在事务里面放 RPC、sleep、复杂计算，减少锁持有窗口。
  4. 谨慎使用 select … for update 能后置更新就不用悲观锁；如果一定要用，同样保证索引命中、行顺序统一。
  5. 隔离级别取舍：
  • 业务可以接受幻读：改成 RC，消除间隙锁，死锁概率大幅下降；
  • 需要防幻读：保留 RR，严格控制索引，避免大范围扫描。

第二层：限流、重试、超时兜底（事中，死锁发生时避免雪崩）即使规范做好，极端并发下死锁依然小概率出现，不能让请求卡死排队：

  1. 设置合理 innodb_lock_wait_timeout，不要无限等待；锁等待超时自动回滚事务，释放锁；

  2. 业务侧捕获死锁异常（Deadlock found when trying to get lock），做短延迟重试（有限次数，比如最多 2 次），重试时依然保证行顺序；

  3. 高并发支付链路做流量削峰限流，避免瞬时流量打爆数据库锁竞争；

  4. 死锁不要频繁重试，防止越重试越锁。

重点：数据库重启是最后的急救手段，绝对不能当成常规方案；重启会强制回滚所有活跃事务，极易造成订单、余额状态错乱。

第三层：监控、审计、对账兜底（事后）

  1. 监控指标：死锁次数、锁等待时长、锁等待会话数；死锁突增立刻告警；
  2. SQL 审核平台拦截无索引 update、大范围 DML；上线前校验事务内多条更新的加锁顺序；
  3. 定时对账：订单、余额、流水三方核对，捕获死锁回滚带来的数据不一致，自动告警补偿。

三、补充优化方案（进阶）

  1. 业务拆分：把余额扣减、订单状态变更拆成串行异步，通过 MQ 串行化，同一用户的支付操作排队执行，从根源消除并发争抢；
  2. 状态机设计：依靠状态流转，减少多表同时更新；先落流水，再异步更新余额；
  3. 乐观锁替代悲观锁：版本号 version，update … where version = ?，避免行锁争抢，适合冲突不密集场景。

初级 vs 高级工程师差异初级工程师：只记住 “统一表顺序 + 超时”，以为万事大吉，无法解释顺序统一后仍然死锁，遇到间隙锁、行锁交叉场景就卡壳。 高级工程师：

  1. 理解 InnoDB 锁锁索引行，不是锁表，区分表顺序、行顺序两个概念；
  2. 看得懂 innodb 死锁日志，能定位间隙锁、索引缺失这类隐性诱因；
  3. 方案是组合体系：索引优化、行顺序控制、隔离级别选型、异常重试、限流、对账补偿；
  4. 明白死锁只能降低概率，无法 100% 消灭，必须配套容错机制，而不是单纯依赖编码规范。

第 20 题　MySQL 读写分离，主从延迟线上故障复盘

问题 1：数据库怎么扛高并发查询？

候选人浅层回答： 做主从复制、读写分离；主库负责写，从库负责读，分摊查询压力，性能直接翻倍。

连环追问

电商业务做了主从读写分离，订单查询全部走从库。 大促当天大量用户付款之后，进入订单详情页提示订单不存在，多次刷新才能刷出来，客诉暴涨； 还有用户下单后查看库存页面，库存没有变少，误以为下单失败，反复提交订单造成重复下单。 排查发现：主库订单、库存写入已经成功，但是从库数据延迟数秒才同步完成，用户查询刚好落在这个延迟窗口里面。

  1. 故障根本原因是什么？
  2. 如果业务要求写入之后马上能查到最新数据，难道所有查询全部强制走主库吗？

参考答案

一、故障根源：主从同步延迟带来的一致性问题

MySQL 默认异步复制，主库写完事务直接返回成功，Binlog 异步推送给从库回放。 大促流量大、事务多、SQL 执行慢、从库硬件资源不足、大事务，都会放大主从延迟。 读写分离天然牺牲强一致性，换取读能力水平扩展；它适合可以容忍短暂旧数据的查询场景，不适合写后立刻读自己刚提交数据的场景。 很多同学只知道读写分离能分担压力，忽略一致性代价，这就是读写分离最经典的隐形陷阱。

二、三层防御体系，兼顾并发性能与一致性

第一层：业务路由层（优先方案，落地成本最低）做请求路由区分，不是一刀切所有读请求都丢到从库：

  1. 强一致性查询（写后立刻读）走主库：用户刚下单查自己订单、扣减库存后查库存、支付状态校验，这类请求路由到主库查询；
  2. 最终一致性查询走从库：商品列表、历史订单、榜单、统计报表，允许短暂延迟，继续利用从库分摊压力；实现方式：ThreadLocal 标记、注解 AOP、中间件（Sharding-JDBC、MyCat）读写路由。

第二层：缓存兜底方案（最常用，减轻主库压力）热点数据增加 Redis 缓存，写数据库同时更新缓存：

  1. 下单成功，订单数据写入主库后，同步写入 Redis；用户查询优先读 Redis，绕开主从延迟；
  2. 缓存设置合理过期时间，缓存失效再去查询数据库；
  3. 注意缓存更新策略（更新数据库 + 更新缓存 / 更新数据库 + 删除缓存），保证缓存和数据库最终一致。

第三层：复制模式与架构优化（底层缩短延迟）

  1. 半同步复制（rpl_semi_sync）：主库至少等待一个从库收到 Binlog 应答之后，再返回客户端成功，降低延迟概率，但依然不是实时，会损失部分写入吞吐；
  2. 并行复制、优化从库回放线程，拆分大事务，避免单条超大事务阻塞从库回放；
  3. 资源隔离：从库单独高配，报表、统计类慢查询单独隔离到专用从库，防止慢SQL 拖垮所有从库同步；
  4. 监控主从延迟：监控 Seconds_Behind_Master，延迟超过阈值，自动把读流量切回主库，做动态路由降级。

三、方案取舍说明

  1. 全部查询强制走主库：简单粗暴，解决一致性，但是读写分离失去意义，主库压力很容易被打满，高并发场景不可取；
  2. 半同步复制：只能降低延迟发生概率，无法彻底消除延迟，不能当成强一致性方案；
  3. 缓存 + 读写路由组合：互联网电商主流方案，性能、一致性、成本平衡最好；
  4. 如果业务要求严格强一致、极高并发：可以考虑分布式数据库（TiDB 等），天然分布式强一致。

四、电商场景优化落地流程

  1. 下单事务在主库提交成功；
  2. 订单、库存数据同步写入 Redis；
  3. 用户立刻查询订单、库存，优先读取 Redis；
  4. 普通历史订单、商品列表走从库；
  5. 持续监控主从延迟，延迟过高自动切流保护；
  6. 缓存异步失效，保证最终数据一致。

追问：本题考察核心是什么？

参考答案：初级开发只会知道读写分离可以分担查询压力，把它当成提升性能的万能方案。高级工程师要理解取舍：

  1. 读写分离是牺牲强一致性换读扩展能力，异步复制天然存在延迟，这是架构特性，不是 bug；
  2. 数据库架构没有万能方案，核心是识别业务查询的一致性诉求，区分强一致 /最终一致性流量，做差异化路由；
  3. 懂分层组合：路由策略、缓存、复制模式、监控降级搭配使用，而不是单一靠主从；
  4. 能预判架构陷阱：上线前就要识别 “写后马上读” 这类场景，提前规避线上客诉故障。

核心思想：读写分离不是简单配置主从，性能和一致性永远需要权衡，根据业务诉求做流量隔离才是架构关键。

第 21 题　MySQL 主从读写分离，主从延迟业务治理

问题 1：系统使用 MySQL 主从读写分离，用户刚提交完订单，立刻查询订单详情，查不到刚刚生成的订单，这就是主从延迟。后端如何规避该问题？极端延迟场景下如何保证业务不出错？

候选人浅层回答： 一致性要求高的场景直接读主库，普通查询走从库，监控主从延迟时间。

连环追问

  1. 如果所有强一致业务全部强制读主，主库读压力持续上涨，主库成为性能瓶颈怎么办？
  2. 主库执行几十秒大事务，提交之后从库延迟数分钟，大量业务读到旧数据，库存、金额类业务逻辑出错，如何处理？
  3. 大表 DDL 引发主从延迟，业务高峰期如何避免？
  4. 用户付款成功立刻跳转订单详情，必须读到最新数据，不想全部读主消耗主库性能，有没有精细化方案，不做一刀切强制读主？
  5. 半同步复制、并行复制，能不能彻底根除主从延迟？
  6. 某一台从库延迟超过阈值，读写分离组件如何自动切换流量，避免用户持续读取旧数据？

参考答案：

一、主从延迟产生根源

binlog 同步是异步行为。主库执行完写操作立刻返回，binlog 传递到从库、从库重放 SQL 需要时间。

  • 大事务：主库大事务提交，大量 binlog 瞬间推送从库，从库重放跟不上，产生巨大延迟；
  • 从库硬件性能弱、单线程重放 binlog（老版本）；
  • 大表 DDL，DDL 语句同步到从库阻塞执行；半同步、并行复制只能降低延迟概率，不能彻底消除主从延迟，极端场景依然会出现延迟，不能当作银弹。

二、多种业务解决方案（区分一刀切读主 和精细化策略）

方案 1：简单粗暴：强一致场景强制读主优点简单直接；缺点：大量场景读主，主库读压力上升，容易把主库打满，不能大规模滥用。

方案 2：精细化读主策略，避免一刀切（付款后立刻查订单场景）

  1. 写后短时读主：用户本次会话，刚刚完成写操作，短时间窗口内（比如 1‑2s）该业务请求强制读主；超过时间之后切回从库。

例如：创建订单、支付成功之后，跳转详情页这一次请求走主库；后续用户再刷新页面，走从库。既保证刚写完能读到最新数据，又不会永久占用主库读流量。

  1. 按业务维度路由：订单、资金这类强一致性业务走主；统计、报表、历史查询走从库。

方案 3：缓存兜底写主库成功之后，同步写入 Redis 缓存；查询优先读缓存；缓存命中拿到最新数据，减少对主库的读取压力。注意缓存和数据库的一致性问题。

方案 4：复制层优化，减少延迟发生概率

  1. 开启半同步复制：主库等待至少一个从库收到 binlog 再返回；

注意：只是收到binlog，不等从库执行完成，依然会延迟；网络抖动会降级退化为异步复制。

  1. 开启并行复制，从库多线程重放 binlog，提升从库回放速度。

重点：二者只能缓解，不能彻底消灭主从延迟。

三、监控 + 读写分离自动降级机制

  1. 持续监控每个从库Seconds_Behind_Master 延迟指标；
  2. 当单个从库延迟超过预设阈值，读写分离中间件（Sharding‑Jdbc、MyCat）自动把该从库摘除，不再分配读流量；流量转发给其他健康从库；全部从库都延迟超标，全部读请求自动切到主库；
  3. 配置告警，延迟超标触发告警通知运维。

四、长效治理，从源头避免大延迟

  1. 严禁大事务：业务禁止超大事务，拆分长事务，避免提交瞬间大量 binlog 压垮从库；
  2. DDL 避开业务高峰期：大表 DDL 使用 pt‑online‑schema‑change /gh‑ost，不要高峰期直接执行 alter，防止 DDL 同步造成从库长时间阻塞；
  3. 保证从库硬件配置不能弱于主库，避免从库本身性能瓶颈拖慢回放；

五、极端大延迟故障应急

发生分钟级主从延迟，库存、金额等业务读到旧数据会产生资损：

  1. 读写分离组件自动摘除延迟从库，所有流量切健康节点，极端情况全部读主；
  2. 排查根源：是大事务、DDL 还是从库资源瓶颈；
  3. 业务层面增加兜底校验，涉及资金、库存关键逻辑，关键判断逻辑强制读取主库最新数据，不能依赖从库数据做业务判断。

追问：本题考察核心是什么？

参考答案： 普通后端只会简单一刀切 “强一致就全部读主”，会带来主库压力瓶颈。 高级工程师需要具备整套工程思维：

  1. 清楚半同步、并行复制只能缓解，不能彻底消除主从延迟；
  2. 掌握精细化策略，写后短时窗口读主，而不是永久读主，平衡一致性和主库性能；
  3. 要有降级能力：从库延迟超标自动摘除、流量切换；
  4. 不止故障补救，更要源头治理：禁止大事务、DDL 规范，避免大延迟事件发生；
  5. 区分普通查询和资金库存等高危业务，极端故障下保障核心业务不资损。

核心思想：读写分离不是简单读写分开，要把主从延迟这个风险点纳入整套架构设计。

第 22 题　读写分离架构，主库写入后从库查不到数据，全链路分级治理方案

问题 1：做了读写分离，主库写完立刻查从库，查不到刚写入的数据，用户直接报错，怎么从根上解决？

候选人浅层回答： 写完 sleep 一段时间再查；关键数据强制走主库；再加一个主从延迟监控。

连环追问

  1. sleep 多久合适？延迟波动大，设短了依然查不到，设长了接口超时，这个时间标准怎么定？
  2. 如果所有核心请求全部强制走主库，读写分离就失去意义，主库连接池被打满，矛盾怎么权衡？
  3. 主从切换场景：旧主降为从，新主的数据还没同步完成，流量切过去大量读请求查不到数据，切换窗口如何兜底？
  4. 一条下单长链路，主库写入后，后续多个步骤都要读数据，哪些走主、哪些走从？不能整条链路都走主库。
  5. 从库延迟突然飙升几秒，读到旧数据引发超卖、订单状态错乱，如何自动降级，而不是人工切流量？
  6. 分库分表 + 读写分离，多个从库延迟参差不齐，怎么路由？如何保证能读到本次事务自己刚写入的数据？

参考答案

一、核心根源

异步复制模式下，主库事务提交返回成功时，Binlog 是异步投递到从库回放，天然存在时间窗口的不一致。 sleep 是伪方案：延迟不是固定值，受大事务、流量、从库负载影响，无法设置一个稳定可靠的等待时长，生产禁止使用。 一刀切全部强行走主库，会耗尽主库资源，读写分离的水平扩展收益直接归零。

核心思路：不区分主库 / 从库，而是对读请求做一致性分级，配套路由标记、会话跟踪、延迟感知、自动降级一整套体系。

二、三层核心治理体系

第一层：会话级一致性标记（最核心，解决 “读自己写的数据”）同一个请求 / 同一个会话内，写入主库之后，本次链路后续的读请求，带上路由标记，优先路由到主库；跨会话、非强一致查询，正常走从库。 实现方案：

  • ThreadLocal / 请求上下文埋标记：当前链路有写操作，标记为【本次需要强一致读】；
  • 只在本次调用链内生效，不会全局放大主库流量；
  • 适合下单、支付、退款这类长事务链路，只让这条链路的后续读走主，历史查询、列表查询继续走从库。

特点：精准收敛强一致流量，而不是整个业务一刀切走主库。

第二层：按业务语义分级，定义三类读流量

  1. 强一致读（Read Your Writes，读己之写）：用户刚提交订单、支付校验、库存扣减校验、退款状态校验，必须看到本次写入结果 → 路由主库。
  2. 单调读：用户已经看到版本 A，不能再读到更早的旧版本，比如用户刷新订单页，不能一会新一会旧；可以结合 GTID 位点做位点路由：写入后记录 GTID，从库必须回放位点≥该 GTID 才允许读。
  3. 最终一致读：商品列表、历史订单、统计报表、榜单，允许短暂延迟 → 正常路由从库，享受读写分离扩容红利。

GTID 位点路由进阶：写入主库拿到本次事务 GTID，读从库前，筛选已经追上该 GTID 的从库，只向追上位点的从库分发请求。完美适配多从库延迟参差不齐、分库分表场景。

第三层：延迟感知 + 自动降级兜底（故障和切换场景）

  1. 持续采集每个从库的延迟指标（Seconds_Behind_Master、GTID 回放位点），维护每个从库健康状态；
  2. 阈值策略：单个从库延迟超过阈值，自动摘除路由池，不再分配读流量；
  3. 全局降级：当大部分从库延迟持续飙升，自动把最终一致性流量，按比例灰度切回主库，熔断异常从库；
  4. 主从切换窗口期兜底：切换完成后，等待从库追上切换时刻位点，再放量读流量，或者切换后短时间窗口内所有流量临时走新主，等同步追上再切回从库；
  5. 半同步复制：至少一个从库收到 Binlog 才返回写入成功，降低延迟概率；

注意：半同步只是降低概率，依然不能保证强一致，不能替代分级路由。

三、缓存配套补充方案（降低强一致主库压力）

热点写后强读场景，写入主库成功后同步更新 Redis 缓存；查询优先读取缓存，绕开数据库主从延迟问题。 适用：订单详情、库存余额这类高频写后立刻查的场景，大幅减少打到主库的强一致读请求。

四、方案对比，避坑总结

  • ❌
  1. sleep 等待： 不推荐，不稳定，极易引发故障；
  • ❌

  1. 全部强行走主库： 极端兜底手段，不能常态化；

  2. 会话标记 + 业务分级路由： 主流首选，精准控制主库流量；

  3. GTID 位点路由： 多从、分库分表复杂架构首选；

  4. 半同步复制： 辅助降低延迟发生概率，不是一致性方案；

  5. 缓存： 高频热点场景减负神器。

追问：本题考察核心是什么？

参考答案：初级开发只会想到强制走主库、sleep 等待，只知道现象，没有体系化思路。高级工程师要具备架构权衡能力：

  1. 明白主从异步复制的本质就是最终一致性，不存在免费的强一致；
  2. 一致性不是非黑即白，学会对读请求分级：读己之写、单调读、最终读；
  3. 流量精细化治理：只把必须强一致的少量请求打到主库，保护读写分离扩容收益；
  4. 覆盖全场景：普通流量、长业务链路、多从库延迟不均、主从切换、故障自动降级；
  5. 拒绝简单粗暴的应急手段，设计可自动化、可灰度、可监控的闭环方案。

核心思想：读写分离的一致性治理，不是 “要不要走主库”，而是谁、什么时候、在什么条件下可以走从库，用分级策略把强一致流量控制在最小范围。

第 23 题　MySQL limit 大偏移深分页优化

举例说明：limit 1000000,10 要先扫描并丢弃前 100 万行，再取 10 行；改写成 where id > 1000000 order by id limit 10 后，优化器通过索引直接定位到起点，扫描量从百万行降到 10 行。

问题 1：limit 100000,10 越翻越慢是什么原因？怎么优化？

候选人浅层回答： offset 越大，MySQL 需要扫描并丢弃前面十万条无效行，所以性能差；用主键游标方案，改写为 where id > 100000 limit 10，利用主键索引直接定位，性能大幅提升。

  2. 使用 ES 可以解决分页，但要考虑运维成本、数据同步延迟；如果只允许使用MySQL，不能引入外部中间件，还有哪些通用优化手段？

参考答案：

1、基础游标（keyset‑pagination，键集分页）优缺点原理：记录上一页最后一条的排序字段值，用where 排序字段 > last_val

  • limit pageSize，避免大 offset 扫描丢弃大量数据。

优点：性能极高，利用索引快速定位，适合 APP、前端只允许上一页、下一页，不支持跳页的场景。

  • ❌局限：

  1. 不支持任意跳页，无法直接跳到第几百页；必须拿到上一页末尾的排序值；

  2. 如果有多组筛选、多种排序，每种组合都要对应一套索引；筛选维度太多，索引爆炸，成本不可接受；

  3. 如果排序字段非唯一，要带上唯一主键做二级排序，避免重复、漏行。

示例：按创建时间倒序，where create_time < #{last_time}and id < #{last_id} limit 10，id 用来解决时间重复的场景。

2、只使用 MySQL，不引入 ES 的几种方案方案 A：覆盖索引子查询优化（适合允许跳页，单表场景）利用覆盖索引，先在索引层完成 offset 偏移定位主键，再回表拿完整行数据，减少回表次数。

注意：子查询只扫描索引（覆盖索引），不需要回表，快速拿到10 条主键，外层再回表读取完整行；比直接limit 100000,10 性能好很多。 局限：offset 特别巨大时依然会扫描很多索引行，只是比全表回表快。

方案 B：业务层面限制，产品规避深分页（成本最低，优先推荐）

  1. 产品禁止直接跳转到很高页码，只提供上一页、下一页；
  2. 限制最大查询页码，例如最多允许查询前 1000 页，超过提示用户缩小筛选条件；真实业务中，运营、用户几乎不会真的浏览几万页数据；大量深分页请求本身属于不合理业务访问。

方案 C：分区表按时间范围做分区，筛选条件带上时间，缩小扫描的数据范围，降低 offset 需要扫描的数据总量。

方案 D：预计算（适合后台统计类固定查询）定时任务把高频复杂分页结果预计算落地到一张中间结果表，业务直接查询中间表；适合查询条件固定、允许短暂数据延迟，不适合动态任意筛选。

3、ES 方案权衡（允许引入中间件场景）ES 的from/size 同样有深分页问题，也不能无限跳页；ES 推荐用search_after 对应 MySQL 游标；

  • 优势：支持多维度任意筛选、多字段排序；
  • 代价：要维护双写、处理数据同步延迟、运维 ES 集群；并不是上了 ES 就万事大吉，ES 也有深分页限制。

4、不同场景选型总结

  1. 移动端 APP，只上一页下一页，无跳页 → 优先使用键集游标（keyset）分页，排序字段 + 唯一主键，建立联合索引；

  2. 后台管理系统，需要跳页，但页码不会特别大 → 覆盖索引子查询优化，同时业务限制最大页码；

  3. 后台需要任意条件、任意页码、海量数据 → MySQL 很难完美支撑，考虑ES；同时接受同步延迟；

  4. 筛选维度爆炸，组合极多：不要试图建立所有组合联合索引；产品上做约束，强制用户必须传入时间、状态等过滤条件，缩小扫描数据集。

追问：本题考察核心是什么？

参考答案： 不能只背id>xxx limit 这个标准答案。很多人只记住游标法，忽略它的业务约束。面试官想看：

  1. 清楚游标分页的适用边界和短板（不能跳页、多筛选维度索引成本）；
  2. 不只一个解法，区分：产品约束、MySQL 索引层面、预计算、引入中间件多种方案；
  3. 具备业务思维：很多分页性能问题，最优解是产品层面做限制，而不是一味靠SQL 硬扛；
  4. 知道 ES 也不是银弹，要权衡运维成本与数据一致性。

第 24 题　千万级订单大表，加联合索引、修改字段长度，如何做到不停业务、全程尽量不锁表，数据不出错

问题背景

千万级订单大表，执行 DDL：新增联合索引 / 修改字段长度。要求业务不中断、数据不出错。

候选人回答：用 MySQL Online DDL 或者 pt-online-schema-change，影子表同步，不停服。

连环追问

  1. Online DDL 申请 MDL 元数据锁那一刻，如果存在长事务持有 MDL，后续所有读写全部阻塞，连接数打满、库雪崩，如何提前规避？
  2. 全量拷贝历史数据的同时，业务持续写入，增量同步丢数据、重复执行，怎么做一致性校验？
  3. 如果变更涉及主键 / 唯一键、外键，pt-osc 这类第三方工具不能直接使用，有什么不停机替代方案？
  4. 新增索引后，统计信息没有及时更新，优化器选错执行计划，查询性能恶化，如何兜底？
  5. 禁止使用任何第三方 DDL 工具，只靠业务代码层面，怎么做字段扩展，完全不影响线上？

参考答案

一、基础概念

MySQL InnoDB Online DDL：大部分操作允许 DDL 执行期间正常读写，但 DDL开始的瞬间，需要短暂申请排他 MDL 锁。 MDL（元数据锁）：只要事务未提交，就持有 MDL 读锁；DDL 需要 MDL 写锁。长事务是 Online DDL 最大杀手。

pt-online-schema-change（pt-osc）原理：建影子新表，拷贝原表全量数据，通过触发器捕获原表的增删改增量，同步到影子表；同步完成后原子 rename 交换新旧表。

注意：pt-osc 依赖触发器，遇到主键修改、外键、部分唯一键场景会受限，无法直接使用。

  1. MDL 锁、长事务导致库雪崩的规避方案风险根源：DDL 发起后，等待 MDL 排他锁；只要有一个长事务不提交，DDL 持续阻塞，后续所有新的查询请求都需要 MDL 读锁，全部排队阻塞，连接堆积打满，数据库雪崩。

前置防护手段：

  1. 变更前巡检：查询information_schema.innodb_trx，抓长时间运行事务，提前告警、kill 长事务；监控慢事务、事务执行时长。
  2. 设置 DDL 等待超时参数 lock_wait_timeout，不要无限等待 MDL 锁。等待超时直接放弃本次 DDL，不持续阻塞后续 SQL。
  3. 限流熔断：数据库侧监控连接数、等待队列。一旦出现大量 MDL 等待的会话，自动告警，必要时阻断 DDL。
  4. 选择低峰窗口，同时低峰窗口也不能忽略长事务；低峰只是降低概率，不是解决 MDL 阻塞。
  5. 读写分离：DDL 操作在从库先执行验证，主库执行时如果阻塞，可快速切换读流量到从库。

核心：Online DDL 不是完全无锁，只是拷贝数据阶段不锁表；获取 MDL 写锁的瞬间，会被长事务卡住。

  1. 全量拷贝 + 增量同步，数据一致性校验（pt-osc /gh-ost）pt-osc 靠触发器捕获 DML，gh-ost 是解析 binlog 做增量，两者都有一致性校验机制：

  2. 全量阶段分批分片拷贝，避免一次性大事务；

  3. 增量阶段持续同步 binlog / 触发器捕获的新增、更新、删除；

  5. 行数校验：新旧表总行数对比；

风险点：触发器方案（pt-osc）在高写入场景有额外性能开销；gh-ost 无触发器，对业务影响更小。

可选方案：

  1. gh-ost：binlog 解析方式，对外键支持相对更好，但依然要评估约束；

  2. 业务双写方案（自研影子表）：业务代码同时写原表 + 新影子表，双写。双写一段时间，数据对齐后，灰度切读流量到新表；验证无误后，再切写流量；旧表保留一段时间作为回滚基线；

  3. 分阶段改造：先删除外键（业务层做约束校验，数据库去掉外键），再执行DDL；生产环境一般不推荐数据库外键，本身就容易锁表。

  5. 变更前，在预发环境压测，验证 SQL 执行计划（explain）；

  6. 新增索引后，手动执行ANALYZE TABLE，主动更新统计信息；

  7. 监控慢查询、QPS、RT，监控索引使用情况sys.schema_unused_indexes；

  8. 业务层 SQL 可以加FORCE_INDEX 做临时强制索引兜底（慎用，作为应急手段）；

  9. 准备回滚脚本：索引性能恶化，立刻DROP INDEX 删除索引回滚。

  10. 禁止第三方 DDL 工具，业务层面实现字段扩展，零锁表业务双写 + 影子表方案，纯业务代码实现，完全绕开大表 DDL 适合场景：新增字段、扩展字段长度。

  11. 阶段 1：业务代码兼容：代码同时兼容新旧字段逻辑，新字段允许为 null；

  12. 阶段 2：创建影子新表（带新字段）；

  13. 阶段 3：业务开启双写：写入订单时，同时写入旧表和新影子表；读请求依然读旧表；后台异步任务，全量迁移历史数据到新表，持续增量对齐；

  14. 阶段 4：灰度切读：逐步切一部分流量读新表，做数据校验、监控；

  15. 阶段 5：全量切写读，全部流量切换到新表；旧表保留一段时间用于回滚；

  16. 下线旧表（等待一段时间确认无问题）。

优点：全程不执行任何大表 DDL，完全不会触发 MDL 锁阻塞，风险可控，可灰度，可随时回滚。缺点：业务代码改动量大，要维护双写逻辑、数据对账任务。

面试完整高分话术千万级订单大表 DDL，核心难点不是能不能执行 Online DDL，核心风险是MDL 元数据锁被长事务阻塞，引发全局阻塞雪崩，以及全量 + 增量同步的数据一致性、变更后执行计划退化问题。

第一，Online DDL 只是拷贝数据阶段不锁表，申请 MDL 排他锁那一瞬间，如果存在未提交长事务，DDL 会卡住，所有后续读写排队，数据库雪崩。规避手段：变更前巡检并 kill 长事务、设置 DDL 锁等待超时，增加监控告警，优先在业务低峰窗口执行。

第二，pt-osc/gh-ost 做影子表迁移，全量分批拷贝，增量通过触发器或者 binlog 捕获 DML。切换前做行数 + CRC 分片校验，保证新旧表一致；同时业务侧增加定时对账，作为兜底。pt-osc 依赖触发器，遇到主键、外键场景受限，这时可以改用 gh-ost 或者自研业务双写影子表方案。

第三，新增索引后统计信息不及时更新，优化器选错索引，我们可以预发压测验证执行计划，DDL 完成后手动 ANALYZE 更新统计信息，监控慢查询，准备 drop 索引回滚脚本。

如果不能使用任何第三方 DDL 工具，就采用业务双写影子表方案：业务同时写入新旧两张表，后台异步迁移存量，灰度切换读流量，验证无误后全量切流。全程不执行大表 DDL，无 MDL 锁风险，随时可以回滚。

整体流程遵循：前置巡检 -> 预发验证 -> 低峰执行 -> 过程监控 + 数据校验 -> 灰度切换 -> 回滚预案。

考察核心

初级工程师只知道 Online DDL、pt-osc 可以不停机，忽略 MDL 锁的致命风险，不懂长事务雪崩风险，不了解一致性校验，也没有业务层双写的备选方案，缺少变更全链路预案。 高级工程师要掌握：

  1. 区分 Online DDL「短暂 MDL 锁」和全程无锁的误区；
  2. 识别长事务是 DDL 线上事故头号元凶，知道如何提前检测；
  3. 理解 pt-osc/gh-ost 原理与各自局限性（外键、主键）；
  4. 掌握数据一致性校验手段；
  5. 考虑索引变更后优化器统计信息带来的性能风险；
  6. 掌握兜底方案：业务双写影子表，纯业务层完成表结构扩展。

核心思想：大表 DDL 的本质不是找一个工具免锁，而是全链路风险控制、灰度、校验与回滚能力。

第 25 题　大表查询优化，分表、索引、分页都做了，带用户昵称模糊+时间范围查询依然 CPU 飙升超时

问题

电商历史订单表 500 万，已经按创建时间水平分表，订单号、用户 ID 建索引，也做了 limit 分页。管理员查询近 3 年历史订单，时间范围 + 用户昵称模糊查询，接口超时，数据库 CPU 打到 90%+，影响其他业务，甚至触发熔断。问题根源在哪？如何从表结构、SQL、架构全方位优化？分库分表加索引是不是万能方案？

候选人回答：加索引、分库分表、分页就够了，模糊查询慢。

参考答案

事故根源

  1. like ‘%昵称%’ 前后通配模糊查询，无法命中 B + 树索引，即使用户 ID 有索引，昵称没有合适索引，只能全表扫描；
  2. 按创建时间分表，查询跨 3 年时间范围，需要扫描多个分表，多表聚合、合并结果集，开销放大；
  3. 管理员后台这类复杂检索，属于多条件、任意字段检索场景，MySQL B + 树索引天生不擅长全文检索；
  4. 分库分表、索引只能优化高并发、确定性等值 / 范围查询，不是万能方案；复杂模糊检索、多维度筛选，不能指望靠 MySQL 硬扛。

一句话：分表解决的是单表数据量过大问题，解决不了复杂检索、模糊全文检索的场景。

三层优化体系（SQL 与表结构优化 → 检索架构改造 → 数据库防护兜底）第一层：SQL 与表结构优化（MySQL 内部优化，治标手段）

  1. 避免前置通配%xxx%

  2. 尽量改成右模糊 like ‘xxx%’，才能使用前缀索引；

  3. 如果业务必须按昵称任意模糊检索，MySQL 索引解决不了，不能硬扛。

  4. 合理设计复合索引，遵循最左匹配。 当前场景：时间范围 + 用户昵称。索引的首列是时间，后面带上昵称，但前缀通配会终止索引使用。

  5. 分页优化： 禁止大偏移 limit offset,size。 优化方案：主键书签分页（seek 分页），where id>上一页最大id limit size，避免数据库扫描前面大量行。

  6. 分表策略优化： 时间分表，跨多年查询需要遍历全部匹配分表；可以限制管理员查询时间范围，禁止一次性查询 3 年超大跨度，拆成分片查询。

  7. 表结构瘦身： 大订单表只保留查询需要字段，大文本、长描述字段拆到扩展表，减少单行数据大小，减少 IO。

局限：只要业务要求任意昵称模糊检索，MySQL 再怎么调索引、分表，性能上限很低，依然容易 CPU 打满。

第二层：架构改造（治本，推荐方案）把复杂多条件检索从 MySQL 剥离，交给搜索引擎。

  1. 引入 Elasticsearch：订单数据同步到 ES，把订单号、用户 ID、用户昵称、创建时间等字段建立索引；

  2. 管理员后台的多条件筛选、昵称模糊检索，全部走 ES；

  3. ES 擅长全文检索、多维度组合筛选；MySQL 只做业务写入、明细查询（按订单号 / 用户 ID 等值查询）；

  4. 通过 binlog 同步 / 双写，保证 ES 与 MySQL 数据最终一致性。

  5. 冷热数据分离：历史订单归档。

  6. 近期热订单保留在在线分表；超过一定时间的冷订单归档到归档库 / 归档表，不参与日常后台检索。管理员查归档数据走单独归档实例，不占用主业务数据库资源。

  7. 读写分离：复杂后台检索走从库，绝对不要在主库执行后台报表、历史查询。

第三层：数据库防护兜底（防止一条慢 SQL 拖垮整个系统）

  1. SQL 限流、超时设置：数据库设置 SQL 最大执行时间，超过阈值直接终止；

  2. 资源隔离：后台查询使用独立从库，和交易主库物理隔离，后台慢查询不会影响线上交易接口；

  3. 网关 / 应用层防护：

  4. 限制查询时间跨度，禁止一次性查询 3 年范围；

  5. 限制返回最大条数；

  6. 慢 SQL 监控告警，捕获慢查询及时发现；

  7. 熔断降级：后台检索接口单独做熔断，慢查询异常时快速返回提示，避免连锁熔断影响核心订单交易。

面试高分话术

事故根源：虽然做了时间分表和普通索引，但是用户昵称 % 关键词 % 的前后模糊查询无法使用 B + 树索引，触发全表扫描；再加上查询跨度 3 年，需要扫描多张分表，多表合并计算，CPU 压力急剧升高。分库分表只能解决单表数据量过大，适合等值、范围类查询，不能解决多维度、全文模糊检索场景，不是万能方案。

整套优化分三层。第一层是 SQL 和表结构优化，尽量规避前置通配符，使用书签分页替代大 offset limit，精简表字段，限制查询的时间跨度。但这个只是 MySQL 层面的优化，有天花板，如果业务必须支持昵称任意模糊检索，这个方案无法根治。

第二层是架构层面根治方案。把复杂检索能力剥离到Elasticsearch，订单数据同步 ES，管理员后台的多条件筛选、昵称模糊查询全部走 ES；MySQL 只负责交易写入和订单号、用户 ID 这类确定性查询。同时做冷热数据分离，久远历史订单归档到独立归档库；后台查询走从库，不和交易主库抢资源。

第三层是数据库防护兜底，做 SQL 超时、资源隔离，应用层限制查询范围和结果条数，加上监控告警和接口熔断，防止后台分析类查询拖垮核心交易链路。

考察核心

初级开发只会背诵加索引、分表、分页，不理解 B + 树索引的限制，不知道模糊查询为什么不走索引，不清楚分表跨表查询的代价，想不到 ES 和冷热归档这类架构方案。 高级工程师重点体现：

  1. 理解分库分表适用边界：只解决单表容量，不能解决复杂检索；
  2. 掌握 B + 树索引限制，理解%xxx%无法走索引底层原因；
  3. 区分在线交易查询 vs 后台多维检索，两者适合不同存储；
  4. 具备数据库资源隔离的意识，后台查询不能污染主库；
  5. 分层思路：SQL 优化、存储架构改造、故障防护兜底。

核心思想：MySQL 适合确定性查询；任意多条件、模糊全文检索，应该交给搜索引擎，不要强行让 MySQL 扛。

首先，手机号是可变字段，不能直接作为分片和索引主 key，先通过手机号查用户拿到稳定的 uid，订单按 uid 哈希分库分表，分片内建立uid+create_time 覆盖索引，在线查询禁止多表 join，冗余字段做成宽表； 其次，哈希分片天生不适合跨分片统计、大范围时间查询、导出，用 binlog 同步订单数据到 ES 或者 ClickHouse，后台检索、跨多年查询、导出全部走异构引擎，不和在线 MySQL 争抢资源； 最后做冷热归档，热订单留在在线分片，历史订单归档；导出改成异步任务，限速调度；同时限制在线查询最大时间窗口，加超时和限流，保护主库不被慢查询打崩。

高频追问

Q：如果用户一定要用旧手机号查历史订单怎么办？ A：ES 里面同时保存历史手机号列表，用户换号时同步更新 ES 文档；MySQL 订单表不存历史手机号，保证分片稳定。 Q：ES 和 MySQL 数据不一致怎么处理？ A：Binlog 同步 + 定时校对任务，补偿不一致，后台检索场景允许短时间弱一致。 Q：为什么不直接按时间范围分表？ A：按时间分表，用户分散在各个时间片，一个用户查自己订单会扫大量分表，查询效率差；uid 哈希更适合 C 端 “查本人订单” 这个主流场景。
