4. Redis（原理、缓存三大问题、分布式锁、持久化）

第 1 题　Redis 是单线程，性能却很高，可达十万级 QPS，如何理解？

候选人浅层回答： Redis 是内存数据库，内存读写远快于磁盘；性能瓶颈不在CPU，而在内存和网络。

连环追问

  1. 既然内存读写很快，为什么不直接改成多线程，利用多核 CPU，4 核机器 QPS理论翻 4 倍？
  2. 上下文切换代价真的大到要放弃多核吗？如果单线程这么强，为什么所有高性能服务不全用单线程？
  3. Redis6.0 为什么又引入多线程？

参考答案：

一、Redis 单线程高性能的完整原因

  1. 全部数据放内存，内存访问速度远高于磁盘，不存在磁盘 IO 等待，这是基础。
  2. IO 多路复用（epoll）+ 非阻塞 IO。单线程可以监听数万 socket 连接，只在网络事件就绪的时候处理。大部分连接处于空闲等待网络包的状态，不是占用 CPU。
  3. 命令执行单线程串行：所有命令在主线程串行执行，内部复杂数据结构（dict、zset）不需要加锁，避免锁竞争、死锁的开发与运行开销。

重点澄清误区：这里的 “单线程”，指执行命令的主线程是单线程；Redis 内部还有独立子进程 / 线程做 RDB、AOF 刷盘等后台任务，并不是整个 Redis 只有一个线程。

  1. Redis 命令本身大多是简单 O (1)/O (logN) 操作，CPU 计算并不是瓶颈，瓶颈通常是网络 IO。 网络收包、解析协议、回包，才是大量耗时操作，而不是内存读写。

二、为什么早期 Redis 没有把命令执行改成多线程？

不是上下文切换开销大到不能用多核，而是收益很低，代价巨大：

  • 如果命令执行改成多线程，同一个 key 会被多个线程并发读写。Redis 大量复杂数据结构都需要加锁保护。锁竞争、死锁、调试难度上升，开发维护成本暴涨。
  • 本来瓶颈是网络 IO，不是 CPU；就算把命令执行并行，CPU 不是瓶颈，整体QPS 提升很小。
  • 不是所有系统都适合单线程：如果业务是 CPU 密集，或者大量阻塞 IO（数据库调用），单线程会直接卡住，所以不能全部服务都做成单线程。

一句话：早期 Redis 的瓶颈在网络，不在 CPU，为了多线程加锁带来的复杂度，得不偿失。

三、Redis6.0 引入多线程的真相

Redis6 多线程，只是多线程处理网络 IO；命令执行仍然是单线程串行执行！

  • 工作：主线程接收连接，把 socket 读、协议解析、写回响应包交给 IO 线程池并行处理；
  • 核心：解析完的命令，仍然交给主线程串行执行；读写 hash、zset 等数据结构依旧不用锁。
  • 目的：多核机器下，网络包的读取、协议解析、写回这些 IO 密集工作分到多个 CPU 核心，解决网络 IO 成为瓶颈的场景。
  • 限制：不会把命令执行并行，保留原来无锁、简单安全的模型。

所以：开 4 个 IO 线程不能让 QPS 直接翻 4 倍，只有网络 IO饱和场景才有明显提升；CPU 饱和场景提升很小。

追问：本题考察核心是什么？

参考答案： 初级开发只会记住 “内存快 + 避免上下文切换”。高级工程师要理解：

  1. 分清：命令执行单线程 ≠ Redis 整个进程只有一个线程；
  2. 性能瓶颈判断：早期瓶颈大多是网络 IO，不是 CPU，这是不做命令多线程的根本原因，而不是单纯怕上下文切换；
  3. Redis6 多线程只是IO 多线程，命令执行依旧串行，没有破坏原有无锁安全模型；
  4. 架构取舍思维：模型好坏看瓶颈，不是单线程一定强，多线程一定更快。

核心思想：单线程是为了简化并发控制，规避锁；Redis6 多线程只是把网络收发卸载到多核，核心数据操作依然串行。

第 2 题　Redis 过期的数据是立刻被删除的吗？

候选人浅层回答： 到了过期时间马上删掉。

连环追问

  1. 既然不会立刻删除，那为什么业务访问时，过期 key 就像失效了一样读不到？
  2. Redis 有哪三种过期删除策略，各自优缺点是什么？
  3. 过期删除和内存淘汰（maxmemory）有什么区别？

参考答案：

一、核心结论

过期的 key 不会到点就立刻从内存删除。Redis 不会单独开一个线程，轮询检查所有 key，时间一到就清理。

过期只是给 key 打上过期时间标记；过期之后，key 还留在内存占用空间，直到触发删除策略。业务读取时会校验过期时间，过期直接返回空，看起来像是删掉了。

二、三种过期删除策略（Redis 组合使用）

  1. 惰性删除（被动删除，主力） 只有当客户端访问这个 key 的时候，Redis 才检查它是否过期。如果已经过期，立刻删除，返回 nil。 优点：几乎不消耗 CPU； 缺点：如果 key 过期后再也没人访问，会一直占内存，形成内存泄漏。
  2. 定期删除（主动抽样清理，兜底） Redis 主线程每隔一段时间（默认100ms），随机抽样一批带过期的 key，检查并删除已经过期的 key。 不是遍历全库！只是抽样。
  • 如果抽样里面过期 key 多，就多删一会；过期少，快速结束，防止阻塞主线程。

缺点：抽样是随机的，有概率部分过期 key 一直没被抽到，继续留在内存。

Redis 实际是：惰性删除 + 定期抽样删除，两者配合。所以过期key 可能长时间残留在内存。

  1. 主动立即删除（Redis 并没有全局启用） 就是一到过期时间马上删，需要持续扫描所有 key。海量 key 场景下会严重阻塞 Redis 主线程，所以 Redis 不采用。

三、关键区分：过期删除 vs maxmemory 内存淘汰（非常容易混淆）

  • 过期删除：针对设置了 TTL 的 key；到时间后清理过期 key，属于 TTL 过期逻辑。就算内存空闲，到期 key 也会被慢慢清理。
  • 内存淘汰（maxmemory-policy）：Redis 内存达到 maxmemory 上限时，才触发。不管 key 有没有过期，按照配置策略（LRU/LFU 等）挑选 key 释放内存。

哪怕 key 还没过期，内存满了，也可能被内存淘汰删掉；反过来，key 过期了，但内存充足，也可以一直留在内存。

四、线上风险与运维注意点

  1. 大量冷数据带 TTL，过期后无人访问，内存不会自动释放，内存居高不下；
  2. 大 key 过期，刚好被访问触发惰性删除，瞬间释放大量内存，可能引发主从复制、碎片波动；
  3. 定期删除只是抽样，不能指望它把所有过期 key 一次性清干净。

追问：本题考察核心是什么？

参考答案： 初级开发以为过期时间一到就删除。高级工程师需要分清：

  1. Redis 不是定时全量扫描，是惰性删除为主，定期抽样为辅；
  2. 理解 “逻辑过期” 和 “物理删除” 不是同一时刻；业务读不到是读取时做过期校验，不代表内存已经释放；
  3. 区分两套独立机制：TTL 过期删除 和 maxmemory 内存淘汰，两个独立逻辑，很多人混淆；
  4. 能预判线上问题：大量过期冷 key 堆积，造成内存占用居高不下。

核心思想：过期时间只是逻辑失效标记；物理删除是延迟、按需进行的，有性能取舍，不能做到实时全部清理。

第 3 题　Redis 持久化怎么选才稳妥？

候选人浅层回答： 直接开启 RDB+AOF 混合持久化，定时快照 + 增量日志，兼顾数据安全和性能。

连环追问

电商商品库存缓存开启混合持久化。大促整点，QPS、CPU 均未到上限，但每隔一段时间出现数百毫秒全局阻塞，所有请求集体卡顿，定位为 RDB 快照触发时 fork 子进程阻塞主线程。

  1. 为什么 fork 会阻塞 Redis 主线程？
  2. 如何在保障数据可靠性的前提下，规避持久化带来的性能卡顿？
  3. 能不能直接关掉持久化，只依赖主从复制做备份？

参考答案：

一、根源：fork 阻塞原理

Redis 主线程调用fork()创建子进程用于 RDB 持久化。 fork 系统调用需要拷贝进程页表；Redis 内存越大，页表体量越大，fork 耗时越长。

Redis 是单线程模型，fork 操作是在主线程中执行，fork 期间主线程停止处理所有命令，产生全局停顿。子进程创建完成后，后续 RDB 文件写入使用写时复制 COW，不会阻塞主线程；阻塞点仅发生在 fork 瞬间。 大促流量高峰触发 RDB，业务请求大量堆积，就会出现周期性卡顿。 除了 RDB 的 fork，AOF 也有性能风险：

  1. AOF 刷盘策略：always 每次写都 fsync，性能极差；everysec 每秒刷盘，若磁盘 IO 打满，依然会阻塞主线程；
  2. AOF 重写 bgrewriteaof：同样会 fork 子进程，也存在 fork 阻塞风险；重写期间会产生大量磁盘 IO。 混合持久化（RDB+AOF）：加载时先加载 RDB 快照，再追加 AOF 增量日志，加速重启恢复；但并没有消除 fork 带来的停顿问题，这就是候选人认知的盲区。

二、优化方案：兼顾可靠性，规避卡顿

  1. 控制 Redis 单实例内存大小 单实例内存不要过大，建议控制在 10~20GB 以内。

内存越小，页表越小，fork 耗时越短，全局停顿越轻微。超大内存场景做分片，拆分多个 Redis 实例。

  1. 调整 RDB 触发时机，避开业务高峰
  • 不要依靠默认定时规则在流量峰值自动触发 RDB；
  • RDB 快照改在业务低峰期（凌晨）手动 / 定时脚本触发；大促期间临时关闭自动 RDB。

  1. AOF 刷盘策略选型 线上生产一般用appendfsync everysec。 同时配置no-appendfsync-on-rewrite yes：AOF 重写时，暂停 fsync，避免磁盘 IO 叠加阻塞主线程。

  2. 利用主从架构，把持久化压力下放给从节点 主节点关闭 RDB，只开 AOFeverysec；从节点开启 RDB 做快照备份。 主节点不再执行 fork，消除主库 fork 停顿；从库负责落地快照用于故障恢复。主从复制同步数据，主库只承担业务读写。

  3. 合理配置 AOF 重写触发阈值 控制auto-aof-rewrite-percentage，避免大促期间触发 AOF 重写，重写也会 fork。

三、第三个问题：能不能直接关闭持久化，只靠主从？

  1. 分业务场景，不能一刀切
  • 纯缓存场景（商品基础信息，允许宕机丢数据，可从
  • DB 回刷重建）：可以关闭 RDB、AOF，仅依靠主从集群高可用；宕机后缓存全丢，业务从数据库重新加载。
  • ❌
  • 有状态、计数、库存、限流计数这类业务：不能完全关闭持久化。主从复制是异步的，如果主库宕机，还没同步到从库的数据会丢失；只靠主从无法保证宕机数据不丢。

这种场景推荐：主库开启 AOF，RDB 放到从库执行。

追问：本题考察核心是什么？

参考答案： 初级开发只记住一句话：生产环境开 RDB+AOF 混合持久化。 高级工程师需要理解：

  1. 混合持久化只是加速重启加载，不能消除 fork 全局阻塞；阻塞根源是 fork 拷贝页表，不是 RDB 文件写入过程；
  2. 区分 RDB、AOF 各自的性能开销点：fork 停顿、磁盘 fsync、AOF 重写；
  3. 具备架构取舍：不是所有 Redis 都要全套持久化；缓存和有状态计数场景方案完全不同；
  4. 学会把持久化任务卸载到从节点，保护主库线上读写，这是线上高并发 Redis的经典实践。

核心思想：持久化操作是带代价的，不是开启配置就万事大吉；高并发系统要将备份任务和线上读写流量隔离。

第 4 题　Redis 缓存穿透

举例说明：攻击者用随机负数 ID 对商品详情接口发起每秒 5 万次请求，缓存和数据库都没有这些数据，请求全部落到 DB，两分钟就把数据库 CPU 打到 100%。接入布隆过滤器后，这类请求在缓存层就被拦下。

场景复盘

候选人回答：缓存空值 + 布隆过滤器。

面试官连环追问：

  1. 攻击者大量随机不存在 ID 刷接口，空 key 疯狂写入 Redis，会不会把 Redis内存打满？
  2. 布隆过滤器有误判、不能删除的短板，如果业务数据频繁增删，怎么处理？
  3. 怎么避免穿透引发 DB 雪崩？

核心认知：空缓存、布隆只是基础手段，单独用都有明显缺陷；需要分层防御，同时解决攻击防住、Redis 不爆、数据动态变更、兜底护 DB 四个问题。

三层防护体系第一层：前置流量层（挡恶意请求，从源头减少无效查询）

  1. 网关层限流、频率控制、验证码 / 风控 对接口做 IP / 用户维度的令牌桶限流；高频随机 ID 访问直接在网关拒绝，根本不进 Redis 和业务逻辑，这是对付恶意刷最划算的手段。
  2. 参数合法性校验 ID 格式、取值范围、长度校验，非法格式直接拦截，比如订单 ID 是固定长度数字，带特殊字符直接丢弃。

优点：不消耗 Redis、DB 资源；专门对付攻击者批量造随机ID。

第二层：缓存与存在性判断层（两种方案按需组合，解决空 key 膨胀、布隆不能删的痛点）方案 A：缓存空值（适合少量不存在 key、低攻击场景）

  • 空 key 必须设置很短的 TTL（几十秒），不能长期驻留；
  • 不允许无限写入空 key；配合 Redis 内存淘汰策略；
  • 缺点：遇到海量随机 ID 攻击，空 key 疯狂堆积，内存快速耗尽，不适合对抗恶意刷。

方案 B：布隆过滤器（适合海量主键集合），弥补它的短板

  • 布隆：只存业务合法主键集合；请求先过布隆，布隆说不存在直接返回；
  • 短板 1：不能删除 → 业务数据删除时，普通布隆没法清理；解决：改用计数布隆过滤器（Counting Bloom Filter），支持删除；或者定时全量重建布隆，Binlog 增量同步更新；
  • 短板 2：存在误判（说存在实际不存在）→ 误判的请求才会走到缓存、DB，这部分流量是少量可控的；
  • 注意：布隆只存有效 ID，攻击者随机 ID 绝大多数直接被拦下，不会产生大量空 key，解决空 key 膨胀问题。

选型区分： 正常业务少量 miss → 短 TTL 空缓存； 有被恶意刷风险、主键集合稳定 / 可同步 → 计数布隆优先。

第三层：数据库侧兜底防护（最后一道闸门，防止雪崩）哪怕前面两层失效，也要保护 DB：

  1. DB 查询加限流、熔断、超时；同一个接口打到 DB 的并发上限做控制；

  2. 禁止无限制穿透查询；数据库层面慢查询拦截；

  3. 监控告警：监控缓存 miss 率、DB 查询 QPS 突增，识别穿透攻击。

秒口述标准答案

单纯空缓存遇到海量随机攻击会堆积大量空 key 撑爆 Redis；普通布隆无法删除，数据频繁变更时容易失效。 完整方案分层：网关先做参数校验、IP 频率限流，拦截恶意流量；业务上优先用计数布隆过滤器存放合法主键，解决布隆删除问题，布隆判定不存在直接返回；少量误判的请求才走缓存，空缓存要设置极短 TTL 防止内存膨胀；最后数据库入口加限流熔断兜底，多层组合防护，避免穿透把数据库打崩。

高频追问

Q：计数布隆有什么代价？ A：每个位置多一个计数器，内存占用比普通布隆高几倍，适合主键总量可控的场景。 Q：为什么不直接全部用布隆，不用空缓存？

A：布隆有维护成本，数据频繁增删要同步；小流量、低攻击风险场景，短TTL 空缓存实现简单够用。 Q：布隆说不存在，就一定不存在吗？ A：是的；布隆的特性：说不存在，一定不存在；说存在，有可能误判。

第 5 题　布隆过滤器防缓存穿透，新品被误拦截、误判率持续上涨

场景复盘

商品详情页，使用布隆过滤器拦截不存在的商品 ID，防止穿透打库。 现象：新上架的商品数据库、Redis 缓存都存在，但是请求直接被布隆过滤器拦截，提示商品不存在；商品越多，误判率越来越高。

考点核心：布隆过滤器是概率型结构，只有误判（假阳性），没有漏判；不是配好就一劳永逸，考察取舍、同步策略、多层防护思维。

根源：为什么正常商品被拦住？

布隆过滤器特性：

  1. 不存在 → 一定返回不存在（无假阴性）

  2. 存在 → 有可能返回存在（假阳性，误判）事故的两个核心原因：

  3. 新增商品没有及时写入布隆过滤器 商品入库了，但布隆里没 add 这条商品id，查询时布隆判定不存在，直接拦截；这是最常见的上线事故。

  4. 预估容量不足，哈希函数配置不合理 初始化预估元素数量偏小，随着商品持续增加，填充率越来越高，哈希位大量重叠，假阳性概率持续上升。 不能无限放大容量：容量越大，内存占用越高；而且只是降低误判率，无法彻底消除误判。

面试官追问：难道把容量设无限大就可以？ 答案：不行。一是内存成本不可接受；二是布隆过滤器本身数学上就无法做到零误判。

三层防御体系（标准答案）第一层：同步管控层（事前，保证数据和布隆对齐）

  1. 商品写入和布隆写入保持原子配套 商品新增接口，入库成功之后，同步把商品ID 写入布隆过滤器； 更新、下架、删除要特殊处理：

  2. 普通布隆不支持删除！这是一大坑：如果商品下架删除，不能直接删元素，旧布隆不适合频繁删除场景。

  3. 方案：使用计数布隆过滤器（Counting Bloom Filter）支持删除；或者采用定时重建布隆的方案。

  4. 初始化时合理预估容量 + 预设可接受误判率 根据业务未来峰值商品量设置size，选择合适 hash 函数数量，控制填充率不要超过阈值（一般建议不超过 70%）。填充越满，误判爆炸。

  5. 预热机制：服务重启、过滤器重建时，先批量加载全量有效商品 ID，再对外提供流量，避免刚启动时大量正常 key 被拦截。

第二层：兜底容错层（事中，防止误杀正常流量）布隆只是前置防护，不能作为唯一拦截手段，不能直接返回不存在： 正确流程：

  1. 请求进来，先过布隆过滤器；
  2. 如果布隆判定不存在：不要直接拒绝，走降级兜底逻辑（短过期空值缓存方案）；
  3. 去查 Redis 缓存；缓存命中，直接返回商品；
  4. 缓存 miss 才查询数据库；数据库查到数据，回写 Redis，同时补写到布隆过滤器；
  5. 数据库确实不存在，写入短 TTL 空缓存，挡住后续穿透。

重点：布隆是第一道筛选，不是最终裁决。初级写法直接 return不存在，就会发生题目里的误杀事故。

两种方案对比：

  • 方案 A（错误）：布隆说不存在 → 直接返回无商品
  • 方案 B（正确）：布隆说不存在 → 进入兜底缓存流程第三层：监控、重建、兜底补偿层（事后）

  1. 监控指标：监控布隆假阳性命中率、被过滤器拦截的请求中，实际数据库存在的比例；这个指标突增就是误判变高的信号；

  2. 定时重建机制： 当填充率、误判率超过阈值，后台低峰期异步重建一份全新布隆过滤器，双过滤器灰度切换，再废弃旧过滤器；规避持续膨胀；

  3. 兜底补偿： 被拦截但数据库真实存在的 key，自动异步回刷布隆，做自修复；

  4. 限流防护叠加：针对高频不存在 ID 限流，降低穿透攻击流量。

两种方案选型对比

  1. 布隆过滤器方案：适合读远大于写、删除少的场景；优势：拦截效率极高；短板：不能删除、存在假阳性、需要同步。
  2. 空值缓存方案：实现简单，无误判；缺点：如果恶意攻击者随机海量 id，会撑满 Redis 内存。 工程上一般是布隆 + 短 TTL 空缓存组合。

初级 vs 高级工程师区别初级：只知道布隆可以防穿透，逻辑写成 “布隆判定不存在直接返回”，忽略假阳性、同步问题，把布隆当成绝对正确的判断器。 高级工程师：

  1. 吃透布隆概率特性：只有假阳性，没有假阴性，明白它只能做前置过滤，不能直接裁断；
  2. 关注数据同步、新增、删除场景下的坑，知道普通布隆不支持删除；
  3. 不会单一依赖布隆，组合空缓存形成多层防护；
  4. 懂得权衡：容量、内存、误判率之间取舍，知道靠重建、灰度切换来控制误判率，而不是幻想无限扩容。

第 6 题　缓存穿透专项（应急+定位+根治）

场景痛点

现象：Redis 命中率暴跌、大量请求直打 DB，数据库 CPU 飙升、接口超时。

候选人只说缓存空值，但是忽略两个致命问题：

  1. 海量恶意随机参数，每一个不存在的 key 都写入空缓存，大量空 key 撑爆Redis 内存；
  2. 布隆过滤器有固有缺陷：存在误判、新增 / 删除商品时同步麻烦。

核心：空缓存、布隆过滤器都只是手段，要分「应急止血 → 定位根因 → 架构长效防护」整套链路，并且理解两种方案的取舍、组合。

三层高分逻辑

第一层：线上应急止损（故障来了优先做，先降 DB 压力）

  1. 网关层紧急限流 + 拉黑恶意 IP，拦截批量随机非法参数；
  2. DB 侧开启熔断，Sentinel 拦截大量穿透过来的请求，快速返回兜底，保护数据库；
  3. 临时缩短空缓存 TTL，避免空 key 持续占内存；或者临时关闭空缓存，切换布隆过滤器优先拦截；
  4. 扩容 Redis，调高淘汰策略（volatile-lru），防止内存打满阻塞 Redis。

第二层：快速定位根因先区分穿透来源：

  • 恶意爬虫：大量随机 ID、随机参数；
  • 业务 bug：前端传错参数、分页越界、删除后没清理缓存；
  • 布隆过滤器不同步：新增商品还没刷进过滤器，导致误穿透；
  • 缓存和 DB 不一致：DB 有数据，但是缓存被误删，看起来像穿透。 看指标：缓存命中率、Redis key 数量增长曲线、访问日志的参数分布。

第三层：架构长效防护（组合方案，而不是单一方案）组合思路：网关限流 + 布隆过滤器为主 + 短 TTL 空缓存为辅，分层搭配

  1. 网关前置：参数合法性校验、黑名单、限流，第一道拦截恶意流量；

  2. 布隆过滤器：存放全部合法业务 ID（商品 ID 等）；请求先过过滤器，直接拦截不存在 ID；

  • 缺点：有极小误判率，不适合频繁删除数据场景；新增数据要异步同步到过滤器；
  1. 空缓存作为兜底补充：过滤器放行后，DB 查询为空，写入极短 TTL（几十秒）空标记；
  • 重点：TTL 一定要很短，防止海量空 key 堆积占用 Redis 内存；不能单独拿空缓存扛恶意刷量；
  1. 配套监控：监控缓存命中率、空 key 数量、布隆过滤器命中情况、DB 异常QPS，低于阈值告警。

取舍一句话：恶意随机海量请求优先布隆过滤器；少量零散不存在 key，用短 TTL 空缓存兜底，二者互补，不要单独依赖其中一种。

秒口述标准答案

遇到缓存穿透、命中率下跌、数据库 CPU 飙升，先做应急止血：网关拉黑恶意流量、开启服务熔断保护数据库，防止故障扩大；然后看访问日志区分是恶意刷量还是业务参数 bug。长效架构上分层防护：网关做参数校验和限流，主拦截方案用布隆过滤器过滤非法 ID，再搭配超短 TTL 的空缓存做兜底；空缓存 TTL 设置很小，避免恶意请求产生大量空 key 耗尽 Redis 内存；同时监控缓存命中率及时告警，还要处理布隆过滤器和数据源同步、误判的问题。

高频延伸追问

Q：布隆过滤器怎么解决数据新增、删除不同步？ A：新增商品异步同步到布隆；删除场景布隆不好处理，改用 Cuckoo 过滤器（支持删除），或者业务上做逻辑删除，不物理删 ID。

Q：空缓存设置多久合适？ A：尽量短，一般 30s~2min；目的只是挡住短时间内重复穿透同一个不存在 key，而不是长期占位。

Q：布隆过滤器误判怎么办？ A：误判就是不存在的数据被当成存在，请求放行到 DB；这时候靠空缓存兜底，查到为空写入短 TTL 标记，避免持续穿透。

第 7 题　项目加 Redis 缓存减轻 DB 压力，Redis 高可用正常、缓存命中率95% 以上、热点数据预热完成，为什么数据库还是被大量请求打垮？

举例说明：商品详情接口 QPS 20 万、命中率 95%，意味着仍有 1 万 QPS 会落到数据库。如果这一万请求刚好集中在热门 key 失效的瞬间，且没有排队与兜底，数据库照样被打穿。

候选人浅层回答：Redis 宕机，请求全部穿透到 DB；或者过期时间太短，频繁失效访问 DB。

连环追问

Redis 集群稳定、没宕机，过期时间设置很长，热点数据提前预热，命中率95%+，DB 还是被打垮。请分析原因并给出解决方案。

参考答案：

一、三个核心场景（缓存穿透、缓存击穿，还有容易忽略的业务流量结构问

题）

  1. 缓存穿透：查询不存在的数据大量请求查询数据库里根本不存在的 key（比如非法 ID、爬虫恶意参数）。

缓存查不到，直接穿透到数据库查询；数据库返回空，空结果没有写入缓存。

哪怕 95% 正常热点数据命中缓存，剩下 5% 全是这类不存在 key 的高并发请求，全部打到 DB，直接耗尽数据库连接。

典型场景：爬虫、恶意攻击传入随机不存在商品 ID。

解决方案

  • 空值缓存：DB 查询为空，在 Redis 缓存空值，设置较短过期时间；
  • 布隆过滤器：把所有有效业务主键提前放入布隆过滤器，请求先过布隆，不存在直接拦截，不去查 Redis 和 DB。
  1. 缓存击穿：热点 key 失效，瞬间大量并发打到 DB某个超级热点 key（爆款商品）过期一瞬间，海量并发请求同时缓存 miss，同时请求数据库。

虽然整体命中率 95%，但单点热点 key 过期瞬间，一瞬间并发全部击穿，短时间打爆 DB，和全局命中率不冲突。 即使调长过期时间，依然有风险：比如主动删除缓存、缓存被 LRU 淘汰。

解决方案

  • 热点 key 永不过期，后台异步主动更新缓存，不依赖 TTL 过期；
  • 互斥锁（Redisson 分布式锁）：缓存 miss 时，只放行一个线程去 DB 加载数据，其余线程等待重试；
  • 逻辑过期方案：缓存一直保留，后台线程异步刷新数据，不会出现缓存清空瞬间大量穿透。
  1. 容易漏掉的：流量结构问题，5% 的请求是超高并发全局命中率 95%，代表 100 次请求里 95 次命中。但如果请求分布极度不均匀： 95 次命中是低 QPS 的普通商品；剩下 5% 是爆款，这 5% 的请求占总 QPS 的 80%。 一旦这部分热点发生击穿 / 穿透，数据库瞬间压力拉满。

命中率是比例，不是流量权重，这是很多人理解的误区。

额外补充其他可能性：

  • 接口没有限流：大量请求同时进来，即使少量穿透请求，并发量巨大，耗尽数据库连接池；
  • 慢查询：打到 DB 的请求是慢 SQL，连接长时间不释放，连接池耗尽；
  • 批量查询场景：单次接口循环大量查 DB，缓存只缓存单条，批量场景没有做优化。

二、三者简单区分

  • 穿透：查不存在的数据，Redis、DB 都没有；
  • 击穿：热点 key 存在，但缓存失效，大量并发同时打到 DB；
  • 雪崩：大量 key 同时过期，大面积同时穿透（本题场景不是雪崩）。

追问：本题考察核心是什么？

参考答案： 初级开发只会想到 Redis 宕机、过期时间，只会看全局命中率这个表面指标。高级工程师要明白：

  1. 全局缓存命中率是一个加权指标，不能代表热点单点的情况，少量比例的请求，可能承载绝大多数流量；
  2. 分清穿透、击穿的底层差异，知道两种场景是独立风险，就算 Redis 正常、命中率很高依然会发生；
  3. 防御思路分层：前置拦截（布隆）、热点保护、空值缓存、接口限流、连接池保护，不是只靠调大过期时间；
  4. 不能只盯着缓存本身，数据库连接池、SQL 性能、流量限流同样是保护数据库的防线。

核心思想：缓存架构防护，不能只盯着正常命中场景，重点防御高并发下少数异常 miss 请求，这才是压垮数据库的元凶。

第 8 题　秒杀爆款商品，单 Key 每秒十几万请求集中打在同一个 Redis 分片，节点 CPU 打满，缓存超时，流量击穿数据库

候选人浅层回答：本地 Caffeine 缓存、分布式锁防击穿、扩容 Redis 节点；多复制几份相同 key 分散流量 + 限流。

连环追问

  1. 本地缓存和 Redis 存在数据不一致，更新时怎么处理？如何让所有应用实例本地缓存失效？
  2. 热搜突发热点，没有提前报备，如何实时自动发现热点 key？
  3. 即使加本地缓存，回源请求依然压垮单个 Redis 分片，怎么打散读流量？
  4. 写热点场景：库存扣减，大量请求抢同一个 key 的分布式锁，锁冲突严重、吞吐低，如何优化？
  5. value 过大，单次读取带宽与序列化开销高，不改动业务如何优化？
  6. 老项目无法大规模改造架构，突发热点来袭，应急止血手段？

参考答案：

一、先区分两类热点：读热点（商品详情查询）、写热点（库存扣减），方案

完全不一样

  1. 读热点治理（商品详情这类海量查询）方案① 本地 Caffeine 多级缓存（应用内存缓存）请求路径：本地缓存 → Redis → DB
  • 本地缓存 TTL 短（比如几十秒），接受短暂不一致；
  • 失效方案：发布更新时，广播失效消息（MQ/Redis PubSub），所有服务实例收到消息后，主动删除本地缓存，实现准实时失效；不需要等待本地 TTL 过期。

缺点：广播有延迟，适合允许短暂不一致场景；强敏感业务（价格）缩短 TTL，缩小不一致窗口。

方案② 热点 key 副本分片（key 复制打散流量）同一个商品，生成多个分片副本 key：goods:1001_0、goods:1001_1、goods:1001_2。客户端请求做随机路由，把流量分摊到多个 Redis 分片。

  • 读请求随机选副本；更新时批量更新全部副本 key；
  • 优点：天然把单分片压力拆分；适合大促提前预热的已知热点；
  • 局限：更新成本变高，副本越多维护成本越高，突发热点自动生成副本比较复杂。

方案③ 代理层热点自动发现与缓存（大厂常用，不用改业务代码）在 Redis 前置代理层（如 Redis Cluster Proxy、自定义中间件）做热点探测：

  • 实时统计 key 的 QPS，超过阈值自动判定为热点；
  • 代理内部做本地缓存，热点请求直接在代理层返回，不再转发到后端 Redis 分
  • 片； 优势：业务代码完全不用改动，自动识别突发、无报备的热搜热点，自动兜底，是老项目非常友好的方案。

大 Value 优化

  • 压缩 value：序列化使用 Protobuf/FlatBuffer 替代 JSON，减少序列化 CPU + 带宽；
  • 大对象拆字段：只返回前端需要字段，不返回完整大对象；
  • 分片存储：大对象拆成多个小 key。
  1. 写热点（库存扣减，大量请求抢同一个 key，锁竞争严重）核心思路：库存分片（库存分桶） 把一个商品总库存拆成 N 个独立库存桶，例如总库存 1000 拆成 10 个桶，每桶 100：stock:1001_0 ~ stock:1001_9。

下单时随机挑选一个库存桶，扣减对应桶的库存，分布式锁只锁单个桶 key。

效果：原本所有请求争抢 1 个 key，现在并发分摊到多个 Rediskey，锁冲突大幅下降，吞吐量显著提升。

业务逻辑：下单随机选桶；扣减失败（桶无库存），换其他桶重试；最后数据库保存总库存，数据库作为最终一致性兜底，防止超卖。

二、热点自动探测（突发热点，没有提前报备）

监控维度：Redis Proxy / 客户端埋点，统计每个 key 的 QPS、耗时、访问次数。 触发阈值：单 key 短时间 QPS 超过阈值，标记为热点； 动作：自动在代理层缓存、自动生成副本分流、触发告警通知运维。 指标告警：分片 CPU、命令耗时、单 key 访问量。

三、应急止血方案（老项目，来不及改架构，突发热点瞬间来袭）

  1. 接口限流：入口层对接口 QPS 做限流，削峰；
  2. 熔断保护：Redis 响应超时比例达到阈值，直接返回降级缓存旧值，禁止继续回源；
  3. 临时扩容 Redis 分片，手动复制热点 key 多副本；
  4. 临时缩短回源并发，用信号量控制同一分片并发请求数，防止打爆 CPU；
  5. 紧急关闭非核心接口，保护核心秒杀链路。

四、配套兜底

  1. 预热：大促已知热点提前预热到本地缓存 + Redis，避免活动开始瞬间大量miss；
  2. 监控大盘：热点 key 看板、分片 CPU、命中率、慢命令，提前预警；
  3. 降级预案 + 故障演练：模拟突发热点压测，验证降级逻辑。

追问：本题考察核心是什么？

参考答案： 初级开发只会简单本地缓存、加锁、扩容，只解决表面，分不清读热点、写热点差异，对突发热点没有自动识别方案，库存写热点没有分桶思路，忽略本地缓存一致性问题。 高级工程师要掌握：

  1. 读写热点分开治理：读热点核心是流量打散；写热点（库存）不能简单复制key，要用库存分桶降低锁竞争；
  2. 两种热点分流思路：业务层多副本，或者代理层无感自动热点缓存（老项目首选，不用改业务）；
  3. 多级缓存（应用本地缓存）要配套广播失效方案，解决多实例本地缓存一致性问题；
  4. 完整闭环：事前预热、实时探测突发热点、大 value 优化、限流熔断应急止血，数据库兜底；
  5. 选型权衡：已知热点用业务侧多副本；未知突发流量优先代理层无感热点缓存。

核心思想：热点 key 的本质是流量全部落在单一分片 / 单一锁资源上，治理的核心目标就是打散流量、拆分竞争资源；而不是单纯扩容 Redis 节点。

第 9 题　缓存雪崩，需要考虑三类场景：大量 key 同时过期、Redis 集群整体宕机、热点 key 集中失效。从长期预防到线上应急

候选人浅层回答：给 key 增加随机过期时间，搭建 Redis 集群保证高可用；集群挂了就把过期时间拉长，再加熔断。

连环追问

  1. 随机过期只能解决「批量 key 同一时刻过期」，如果 Redis 整个集群宕机，这套方案还能保护数据库吗？
  2. 热点 key 集中失效和普通缓存雪崩有什么区别，单独怎么防护？
  3. 雪崩发生时，应急止损和事后恢复怎么做？

参考答案：

一、先分清三类雪崩场景

  1. 场景 1：大量 key 同时 TTL 过期 大量缓存 key 在同一时间失效，大量请求穿透打到数据库，连接池瞬间耗尽。

普通预防：过期时间增加随机偏移量（± 几分钟），打散过期时间；核心业务热点 key 不依赖 TTL 过期，采用逻辑过期，后台异步刷新，永不过期。

  1. 场景 2：Redis 集群整体宕机（分片故障、主从切换失败、集群不可用）Redis 完全不可访问，所有请求全部穿透数据库，随机过期完全无效，这是更危险的雪崩。
  2. 场景 3：超级热点 key 集中失效 少数几个超高流量热点 key 失效，瞬间海量并发压到 DB。这个很多人会和普通雪崩混淆，本质属于缓存击穿，但大量热点同时失效会演变成雪崩。

二、长期预防体系（事前）

  1. 打散过期 + 热点 key 逻辑过期 普通 key：基础过期时间叠加随机偏移，避免同一时刻集体过期； 爆款热点 key：物理 key 永不过期，使用逻辑过期，后台单独线程异步更新缓存；业务读取不删除 key，不存在过期瞬间击穿。

  2. 多级缓存兜底（应对 Redis 集群宕机） 本地Caffeine 缓存(应用内存) →Redis 集群 → MySQL 数据库 请求优先读本地缓存；Redis 挂掉时，本地缓存继续承载流量，大幅减少直达数据库请求。本地缓存设置短 TTL，数据弱一致，做降级兜底，不做强业务。

  3. 流量保护：限流 + 熔断 + 信号量控制

  • 接口层限流：对核心接口做令牌桶限流，限制总 QPS；
  • 数据库保护：使用信号量控制同时访问数据库的并发请求数量，防止数据库连接池被打爆；
  • 熔断组件（Sentinel/Hystrix）：当 Redis 异常或者 DB 慢请求比例超过阈值，触发熔断，直接返回降级结果，拒绝继续访问 DB。
  1. Redis 高可用架构：主从 + 哨兵模式适合中小规模单分片场景；生产大规模一般直接使用 Redis Cluster（自带分片、主从复制、Gossip 故障转移，不需要再叠哨兵）。分片隔离，一个分片（主+从）故障不影响其他分片；避免大 key，防止主从同步阻塞、内存溢出导致节点宕机。
  2. 监控与预警 监控指标：Redis 内存、QPS、命中率、慢命令、集群节点状态、DB 连接数、慢查询； 热点 key 探测：实时识别超大流量 key，提前预警； 告警：命中异常、节点下线、命中率暴跌、数据库连接水位告警。 大促前做缓存预热，提前加载热点数据。

三、应急处置（雪崩发生时，核心是快速止损）

  1. 第一步快速降级：开启熔断，阻断大量请求继续访问数据库；优先返回降级数

  2. 据（缓存旧值 / 默认结果），保住数据库不宕机。

  3. 若只是批量过期：利用分布式锁，控制单条 key 只允许一个请求去数据库加载，其余请求等待，削峰。

  4. 若 Redis 集群宕机：依赖本地缓存承接流量；停止非核心业务，释放数据库连接，优先保障核心链路。

  5. 紧急限流：临时调低接口 QPS 上限，隔离非核心流量。

四、故障恢复（事后）

  1. 修复 Redis 集群，节点恢复后，逐步恢复缓存预热，不要一次性全量回写，避免瞬间压力。
  2. 逐步关闭熔断、恢复流量，灰度放量，观察数据库负载。
  3. 事后复盘：定位根因，补充故障演练，完善监控阈值。

五、热点 key 单独防护（容易漏掉）

热点 key 不能只靠随机过期：

  • 热点 key 单独拆分分片，避免大流量打在单个 Redis 实例；
  • 本地缓存兜底热点；
  • 后台异步更新，不依赖过期删除。

追问：本题考察核心是什么？

参考答案： 初级工程师只想到随机过期、集群高可用，只能解决批量 key 过期场景，无法应对 Redis 整体宕机，没有分层兜底思路。 高级工程师需要具备防御性架构思维：

  1. 区分三种雪崩，不同场景方案不一样；随机过期只是其中一个小手段，不是万能方案；
  2. 多层防护：多级缓存、限流、熔断、信号量，保护数据库是最终底线；
  3. 完整闭环：事前预防、实时监控预警、故障应急止损、事后恢复 + 故障演练；
  4. 明白缓存只是加速层，数据库是最后的保护对象，必须限制穿透流量上限。

核心思想：雪崩防护不能只在 Redis 层面做，要从流量入口、应用本地缓存、中间件、数据库多层建立防护；任何单一策略都无法覆盖全部故障场景。

第 10 题　缓存雪崩专项（应急+定位+根治）

场景回顾

现象：大批量缓存 key 同时失效 / Redis 集群宕机，大量请求绕过缓存打到数据库，DB 压力暴涨、接口大面积超时，整条微服务链路雪崩瘫痪。 很多候选人只会说：过期时间加随机偏移。但是忽略雪崩不止是过期集中这一种情况，还有Redis 集群故障、预热失误、主从切换、大 key 清理等都会引发雪崩，而且缺少故障发生后的应急止血流程。

三层高分逻辑

第一层：应急止损（故障爆发第一时间，优先保业务）

  1. 立刻触发熔断降级：Sentinel 对 DB 查询接口熔断，直接返回兜底静态数据，阻止流量持续灌入数据库，防止数据库被打挂；
  2. 快速恢复缓存：如果是 Redis 节点宕机，触发哨兵 / 集群自动切换；如果只是key 集中过期，紧急执行全量缓存预热脚本，把核心热点数据重新刷回 Redis；
  3. 流量削峰：网关层临时限流，降低进入服务的 QPS；非核心业务直接降级下线，优先保障核心链路；
  4. 临时读写隔离：DB 做只读保护，禁止非核心查询。

第二层：定位根因，区分雪崩类型

  1. 过期集中雪崩：批量 key 设置了相同 TTL，到期一起失效；
  2. Redis 故障雪崩：集群节点宕机、主从切换、内存满被驱逐、网络分区，整体缓存不可用；
  3. 人为操作：上线清理缓存、批量删除 key、预热脚本写坏，一次性清空大量缓存；
  4. 大 key 淘汰：Redis 内存淘汰策略一次性淘汰一大批 key，瞬间失效。 核对监控：Redis 节点状态、key 过期曲线、内存淘汰日志、变更记录、GC / 网络指标。

第三层：架构长效防护（多手段组合，不是单靠随机时间）

  1. 打散过期时间：给 TTL 增加随机偏移量，避免同一批次 key 同时过期；这是基础手段，但不足以应对 Redis 宕机类雪崩；
  2. 多级缓存架构：本地 Caffeine 缓存作为一级缓存，Redis 作为二级；Redis 挂了，本地缓存依然可以扛住读请求；本地缓存设置独立过期时间；
  3. Redis 高可用：小规模用主从 + 哨兵，大规模用 Redis Cluster（Cluster 自带主从副本与故障转移，不再额外部署哨兵），避免单点故障；做好扩容、内存水位监控，避免触发大量 key 淘汰；
  4. 差异化缓存策略：超热点 key 设置永不过期，后台异步主动刷新，不走自动过期；
  5. 灰度预热：预热分批次，不要一次性批量刷大量 key；缓存删除改成异步、分批删除；
  6. 监控告警：监控 Redis 存活、过期 key 数量、内存淘汰次数、缓存命中率、DB QPS，异常提前告警。

重点区分：TTL 加随机值，只能解决过期集中导致的雪崩；Redis集群宕机带来的雪崩，必须靠多级缓存 + 熔断降级来防护。

秒口述标准答案

缓存雪崩分两种，一种是 key 集中过期，另一种是 Redis 集群整体不可用。

故障发生先应急止血：开启熔断降级返回兜底数据，保护数据库，同时限流、紧急预热缓存；然后排查是过期集中、节点宕机还是人为清理 key。长效方案分层治理：基础上给过期时间加随机偏移打散；热点 key 永不过期、后台主动刷新；搭建本地 Caffeine+Redis 多级缓存；Redis 使用集群高可用架构；配合熔断降级作为最后的防线，同时监控内存淘汰、命中率等指标提前预警。

高频延伸追问

Q：多级缓存本地 Caffeine 有数据不一致问题怎么处理？ A：本地缓存允许短时间不一致；数据更新时发送消息，通知各个服务实例主动失效本地缓存，不需要强一致，适合商品详情这类读多写少场景。

Q：为什么不能只靠随机 TTL？ A：随机 TTL 只能解决过期雪崩，如果 Redis直接宕机，所有缓存全部失效，随机时间完全没用，必须熔断 + 多级缓存兜底。

Q：缓存批量删除怎么避免雪崩？ A：不要 del 批量删；用异步分批删除；或者标记失效，后台慢慢清理，不要一次性清空。

第 11 题　电商首页商品缓存，大批量 key 同时过期+Redis 宕机双重风险

场景复盘

首页上千商品缓存集中过期，大促流量涌入，大面积缓存击穿，流量直接打穿到 DB；同时还要兜底 Redis 宕机的情况。 简单方案的缺陷：单纯加过期时间会雪崩；互斥锁会阻塞、拖慢 RT；单纯拉长 TTL 会加剧数据不一致。

核心考点：缓存雪崩防护 + 缓存降级兜底 + 数据库限流保护整套体系，而不是只解决雪崩一个问题。

三层高分体系

第一层：根治集中过期（雪崩源头治理）

  1. 过期时间加随机偏移（基础手段） 统一基础 TTL + random 偏移，打散过期时间，避免大量 key 同一时刻失效。比如基础 30min，再加 0~5min 随机值。
  2. 主动更新 + 永不过期（热点商品推荐方案） 热点商品缓存 key 不设置 TTL；后台异步定时主动刷新缓存（后台线程 / 消息队列）。
  • 优点：从根源消除集中过期；
  • 代价：依赖主动刷新，刷新失败要保留旧缓存，不删 key；实现缓存续期，旧数据可以短暂容忍弱一致，符合首页商品场景。
  1. 逻辑过期（预热方案） 缓存里存expire_time 逻辑过期标记，Redis key 本身不删；请求读到逻辑过期后，单独起异步线程去更新缓存，当前请求直接返回旧值。

对比互斥锁：逻辑过期不会卡住用户请求，RT 稳定；缺点是会短暂返回旧数据，适合商品这种允许短时间不一致的业务。

第二层：击穿防护 + 限流隔离（就算缓存大面积失效，护住数据库）

  1. 接口层限流、熔断、单机令牌桶 给首页商品查询接口单独限流，控制放行到DB 的并发总量；和缓存解耦，是 DB 最后一道闸门。
  2. 分布式锁 / 轻量排队（兜底补缓存） 少量 miss 场景用互斥锁，只放行一个请求去回源写缓存，其余请求等待或短暂返回旧兜底；不适合上千 key 同时失效的场景，容易大面积阻塞，所以只能作为辅助，不能当主方案。
  3. 布隆过滤器拦截无效 ID 过滤不存在的商品 ID，杜绝无效 miss 穿透到 DB。

第三层：Redis 宕机兜底（题目重点追问的双重兜底）

  1. 本地 Caffeine 二级缓存 应用进程内本地缓存，作为 Redis 挂掉之后的降级层；优先读本地缓存，本地没有才尝试 Redis，Redis 异常直接走本地缓存兜底；本地缓存 TTL 设置更短。
  • 注意：多实例本地缓存会出现副本间数据不一致，首页场景可接受；

  1. 降级开关 + 静态兜底页 Redis 完全不可用时，关闭回源查询 DB 的逻辑，直接返回兜底缓存 / 静态预热首页；不允许流量继续穿透数据库；

  2. Redis 集群高可用：主从、哨兵 / 集群，降低 Redis 整体宕机概率，属于基础设施层面。

分层一句话：随机偏移打散过期是预防雪崩；逻辑过期 / 主动刷新保证热点 key 不集中失效；本地缓存 + 熔断限流是 Redis 故障时的兜底，防止 DB 被打崩。

秒口述标准答案

这个场景是典型缓存雪崩，还要兼顾 Redis 宕机兜底。第一层先打散过期，给TTL 增加随机偏移，首页热点商品优先采用逻辑过期或者后台主动异步刷新，避免集中失效；第二层加接口限流控制打到数据库的并发，配合布隆过滤器拦截无效请求，少量缓存 miss 才用分布式锁防击穿；第三层做二级兜底，在应用内增加 Caffeine 本地缓存，Redis 故障时直接降级返回本地缓存，并且熔断禁止继续访问数据库。首页商品允许短时间弱一致，优先保可用性，而不是强一致。

高频追问

Q：逻辑过期和互斥锁怎么选？ A：追求低延迟、允许短暂旧数据（首页商品）选逻辑过期；对一致性要求高、不能返回脏数据，才用互斥锁，代价是请求排队等待。 Q：本地 Caffeine 有什么缺点？ A：多节点之间数据不同步，更新商品后各个实例本地缓存失效时间不一致；适合非强一致场景；强一致场景不适合。 Q：如果商品修改了，怎么主动失效缓存？ A：商品更新后，删除 Redis 缓存；如果是逻辑过期方案，直接更新缓存里的数据和逻辑过期时间即可。

第 12 题　Redis 缓存穿透、击穿、雪崩

问题回顾

只设置过期时间、做预热远远不够。视频里同时出现三类问题：

  1. 缓存穿透：大量请求查询不存在的商品 ID，Redis 查不到，全部打到 DB，DBCPU 飙升；
  2. 缓存击穿：热点 key 到期，百万并发同时过来，一起访问 DB；
  3. 缓存雪崩：大量 key 集中同时过期，大面积缓存失效，DB 压力瞬间打爆。

误区：很多人以为预热 + 过期时间就能解决，预热挡不住不存在key 的穿透，也挡不住热点 key 同一时刻过期，更挡不住一批 key 同时失效雪崩。

三层防御体系

第一层：入口拦截层（挡无效请求，优先防穿透）

  1. 布隆过滤器：把所有合法商品 ID 预加载进布隆过滤器；请求进来先过过滤器，不存在的商品直接拦截，不进 Redis、不碰 DB；缺点是存在误判，不能删除元素。

举例说明：锁 TTL 设 30 秒，业务因为一次慢查询跑了 40 秒。第 30 秒锁自动释放，线程 B 拿到锁进入临界区；第 40 秒线程 A 执行完，执行 del 把线程 B 的锁删掉，线程 C 又能拿到锁——三个线程同时操作同一份库存。

连环追问

  1. 如果业务执行时间超过锁过期时长，锁被自动释放；后续线程拿到锁进入临界区；原线程恢复后，把别人的锁删掉，为什么会出现这个问题？
  2. 安全的分布式锁，要解决哪几个核心问题？只把过期时间调长能根治吗？

参考答案：

一、原生 setnx + expire 最致命的两个漏洞

注意：SETNX 和EXPIRE 是两条独立命令，非原子。如果 setnx 成功后，执行 expire 前进程宕机，key 永久不会过期，锁死，这是第一个大坑。 所以基础写法应该用单条原子命令：SET lock_key uuid NX EX 30，这一步解决原子加锁，但依然还有下面两大核心问题：

  1. 业务执行超时 > 锁过期，锁提前释放，锁失效，并发闯入 假设锁过期 30 秒，业务因为 GC 停顿、网络、数据库慢查询跑了 40 秒。30 秒时 Redis 自动删除 key，锁释放；第二个线程成功拿到锁，两个线程同时进入临界区，互斥失效，库存超卖、重复下单。

单纯调长过期时间不能根治：只是降低概率；极端 GC / 宕机场景依然会超时，同时锁卡死风险变大。

  1. 无锁持有者身份校验，导致误删除别人的锁 锁 key 的值如果只是固定字符串。

线程 A 拿到锁，业务超时锁过期；线程 B 拿到同一把锁；线程 A 业务终于跑完，执行 del 删除 key，直接删掉 B 正在持有的锁。 解决：锁的 value 必须是全局唯一标识（UUID / 随机串），删除锁的时候，先判断 value 等于自己持有的标识，再删除。 并且查询 + 删除也必须原子执行，要用 Lua 脚本，不能 get 然后判断再 del（两条命令存在竞态）。

二、安全分布式锁三大核心能力（Redisson 的实现思路）

  1. 锁持有者身份校验 加锁写入唯一随机 value；释放锁 Lua 脚本：ifredis.call(‘get’,KEYS[1]) == ARGV[1] then return redis.call(‘del’,KEYS[1]) else return 0 end。只有持有者能删自己的锁，杜绝误删。
  2. 看门狗自动续期（核心，解决业务超时锁过期） Redisson 的 WatchDog 看门狗后台线程，每 1/3 锁过期时间，自动延长锁有效期。业务只要还在运行，锁就不会过期；业务正常结束，看门狗停止，锁主动释放。

注意：看门狗只在业务线程存活时续期；如果进程宕机，不再续期，锁到期自动释放。

  1. 原子操作 加锁、释放锁都要保证原子性。加锁使用 SET NX EX；释放锁必须
  2. Lua 脚本，不能拆成多条命令。

三、额外风险：主从异步复制带来的锁丢失（Redis 单主 / 主从的短板）

主节点写入锁成功，但还没同步到从节点，主节点宕机，从节点晋升为主。新主没有锁记录，其他客户端可以再次拿到锁，锁失效。 高可靠场景解决方案：RedLock 红锁，同时向多个独立 Redis 实例申请锁，过半成功才算拿到锁；代价是复杂，性能差，一般业务很少使用。大部分业务接受主从异步的极小概率风险，使用单实例 + 看门狗方案。

四、选型总结

  • 简单 setnx + expire + del：不安全，不推荐生产直接手写；
  • 生产推荐直接使用 Redisson，自带看门狗、Lua 释放、身份校验；不要自己手写分布式锁。

一、核心结论

Redis 无法做到绝对可靠、100% 无缺陷的分布式锁，无法满足严格 CP 强一致场景。 单机 Redis 锁存在不少风险；Redlock 红锁也有争议，依然存在理论漏洞。 但绝大多数高并发业务，并不需要绝对的锁安全性，在业务增加兜底校验后，Redis 锁是性价比极高的选择，所以大厂大量使用。

二、单机 Redis 锁典型失效问题

  1. 锁过期，业务还没执行完 线程拿到锁，业务执行耗时超过锁 TTL，锁自动释放；其他线程抢占锁，出现两个线程同时执行业务，锁失效。

解决：看门狗自动续期（Redisson 自带），业务没执行完成，后台线程不断延长锁过期时间。

  1. 主从切换丢锁（最经典致命问题） Redis 主节点拿到锁，还没同步到从节点，主节点宕机；从节点晋升为主节点，锁丢失，别的客户端重新拿到同一把锁，并发冲突。

单机主从架构，这个问题看门狗解决不了。

  1. 错误释放别人的锁 简单 SETNX+expire，释放锁没有校验持有者标识，线程 A超时锁被释放，线程 B 拿到锁；A 执行完直接 del，把 B 的锁删掉。

解决：set key value NX EX，value 存唯一客户端标识；释放锁必须用 Lua 脚本，校验 value 匹配才允许删除，保证原子性。

三、Redlock 红锁方案

Redlock：向多个独立 Redis 主节点申请锁，超过半数节点获取成功才算拿到锁。

  • 优点：降低主从切换丢锁的概率；
  • 缺点：部署成本高、性能下降；分布式时钟漂移依然存在理论漏洞，业界（如Martin Kleppmann）对它安全性有争议；运维复杂。

大厂很少大规模落地红锁，太重，一般不作为首选。

  2. 大部分业务不需要绝对强一致锁：业务接受极低概率锁失效，只要业务层增加兜底校验，就算锁失效也不会出现严重事故。 举例：库存扣减，Redis 锁只是前置并发控制，最终扣减必须在数据库加事务 / 行锁校验，即使锁失效，数据库层拦截超卖。

参考答案

一、分布式锁五大核心原则（开篇必说）

  1. 互斥性：同一时刻只有一个客户端拿到锁；
  2. 防死锁：客户端拿到锁后宕机，锁最终一定能释放，不会永久卡死；
  3. 防误删：只能自己释放自己的锁，不能删掉别人持有的锁；
  4. 可重入：同一个线程，拿到锁之后可以再次加锁（避免自己把自己卡死）；
  5. 高可用：锁服务故障、网络抖动，锁机制不能大面积失效。

重要区分：分布式锁 ≠ 幂等

  • 分布式锁：控制并发串行执行，解决并发竞争（库存扣减、定时任务抢执行）；
  • 幂等：同一个请求重复提交，多次执行结果和一次一样；
  • 很多场景优先做幂等，不一定需要锁；超卖这类强竞争场景，锁+ 幂等 + 数据库兜底一起上。

二、主流三种实现方案：Redis 锁、Zookeeper 锁、数据库锁

方案 1：Redis 分布式锁（项目最常用，Redisson）基础正确写法（禁止 SETNX + EXPIRE 分开两行，非原子，宕机死锁）加锁原子命令：

  • NX：key 不存在才成功，保证互斥；
  • uuid：当前锁持有者唯一标识；
  • EX：过期时间，基础防死锁。

解决面试官几个问题

  1. 锁被误删：不能直接 DEL lockKey；使用 Lua 脚本，先判断 value 等于自己的uuid，才删除，原子执行。
  2. 业务执行超过 TTL，锁提前过期：Redisson 看门狗（自动续期）。拿到锁后后台线程定时刷新过期时间；业务执行完成，停止续期。

局限：看门狗解决不了Redis 主从异步复制丢锁（主节点加锁成功，未同步从，主宕机从晋升，锁消失）。

  1. 死锁：两层保障：①过期时间兜底；②正常流程业务完成主动释放锁。

  2. 可重入：Redis 原生不支持；Redisson 用 hash 结构：key = 锁名，field = 线程

  3. 标识，value = 重入次数，加锁次数 + 1，释放 - 1，次数为 0 才删除 key。

  4. 集群锁失效（主从丢锁）

  • 普通主从：异步复制，有丢锁风险，适合允许极小概率不一致场景（大部分业务、定时任务）；
  • Redlock：多独立节点过半加锁成功才算持有锁；缺点：依赖系统时钟、性能差、运维复杂，大厂很少上生产；
  • 强一致场景，不推荐用 Redis 锁做强互斥。

方案 2：Zookeeper 分布式锁原理：利用临时有序节点。抢锁时在指定目录创建临时节点；最小序号节点拿到锁；监听前一个节点，释放后触发下一个竞争者。 特点：

  1. 临时节点：客户端断开会话，节点自动删除，天然防死锁，不需要设置过期时间、不需要看门狗；
  2. ZK 是 CP，写过半成功，主节点宕机不会凭空丢锁，一致性比 Redis 好；

面试高分话术

分布式锁首先要满足五大特性：互斥、防死锁、防误删、可重入、高可用。同时要分清分布式锁和幂等不是同一个东西：锁控制并发串行，幂等保证重复请求结果不变，经常搭配使用。

主流三种实现：Redis 锁、ZK 锁、数据库锁。项目里最常用Redisson 实现 Redis 分布式锁。加锁必须原子 SET NX EX；释放锁用 Lua 脚本校验持有者标识，防止误删；长任务开启看门狗自动续期，避免业务没跑完锁过期；Redisson 用 hash 结构支持可重入。但普通 Redis 主从是异步复制，存在主从切换丢锁的风险，所以 Redis 锁适合大部分业务、定时任务，不能单独用来做强一致保障，底层一定要数据库兜底。Redlock 理论上解决单节点故障，但依赖系统时钟、性能差，生产很少使用。

Zookeeper 锁是 CP 模型，依靠临时有序节点，会话断开节点自动删除，天然防死锁，一致性更强，不会出现主从丢锁；缺点是吞吐量低、运维重，适合并发不高、一致性要求严格的场景。

数据库悲观锁性能差，乐观锁更多作为兜底方案。 我们项目日常优先 Redisson Redis 锁，兼顾开发成本和性能；库存扣减场景上层 Redis 锁削峰，底层数据库乐观锁防止超卖；只有少数强一致性、低并发流程，才考虑 ZK 锁。定时任务用分布式锁抢占执行权，同时任务本身做幂等，双重保障。

  1. 牢记五大特性，区分锁和幂等；
  2. 掌握 Redis 锁全套问题：原子加锁、Lua 释放、看门狗、可重入、主从缺陷；
  3. 清晰 Redis (AP) 和 ZK (CP) 取舍；
  4. 有分层思想：锁是上层互斥，数据库是兜底底线；
  5. 能结合业务场景给出真实项目选型，而不是一味说某一种最好。

核心思想：没有万能分布式锁，锁是取舍；AP 的 Redis 性能好但一致性弱；CP 的 ZK 一致性强但吞吐低；高并发防超卖永远需要数据库兜底。

四层可靠分布式锁 + 库存防超卖完整设计（面试标准答案四层）核心一句话：Redis 锁是【前置限流 / 互斥】，绝对不能单独作为防超卖的唯一屏障，数据库层必须兜底！

第一层：锁的基础语法规范（基础层）加锁：SET lock_key uuid NX EX ttl，必须原子； 释放锁：Lua 脚本，先判断 value 等于当前线程的唯一标识，再删除，防止误删别人的锁； 长任务开启看门狗自动续期（Redisson 自带）； 禁止单纯 SETNX 再 expire（非原子，宕机会死锁）。

第二层：锁的一致性加固（解决主从丢锁）两个路线二选一：

  1. 追求简单主流方案：放弃用 Redis 锁做强互斥，Redis 只做流量拦截、预扣，把强一致性交给数据库；
  2. 非要用 Redis 强锁：不依赖异步主从，要么用 Redis Cluster 强同步、或者改用Zookeeper 分布式锁（Zookeeper 是同步写过半，主节点挂了，锁不会凭空丢失）；重点：Redlock 谨慎上生产，一般不推荐。

第三层：业务层库存预扣、幂等控制

  • 下单携带全局唯一幂等号，防止同一个订单重复扣减；
  • 先在 Redis 预扣库存（预扣只是计数，用来挡高并发），预扣成功才往下走；预扣失败直接返回无货；
  • 预扣和 DB 真实扣减状态绑定，预扣超时自动回补 Redis 库存。

第四层：数据库最终兜底（最关键，Redis 锁再完美也要这一层）数据库扣库存，SQL 自带乐观锁：

依靠数据库行锁 + 条件判断，数据库层面保证不会扣成负数。 哪怕 Redis 锁失效、两个线程同时进来，这条 update 的 affected rows 只会有一个成功，另一个返回 0，判定库存不足，杜绝超卖。

四层总结：规范锁语法 → 选择合适的一致性组件（规避主从异步丢锁） → 业务幂等 + Redis 预扣限流 → DB 乐观锁兜底防超卖。

两个线程同时拿到锁，不只有锁超时这一种原因，还有一个更致命的：Redis 主从异步复制丢锁。 时序是：线程 A 在 master 加锁成功，锁还没同步到从节点，master 宕机，从晋升为主，新主没有锁记录，线程 B 就可以拿到同一把锁，造成并发进入。看门狗只能解决业务执行时间超过 TTL、锁提前过期的问题，它解决不了主从切换丢锁。Redlock 在多个独立 Redis 节点加锁，过半成功才算持有锁，但是强依赖系统时钟，部署复杂、性能差，生产很少落地。

可靠方案分为四层： 第一层，锁本身原子化，SET NX EX 加锁，Lua 脚本释放锁，带唯一 value 防误删；长任务用 Redisson 看门狗自动续期。 第二层，锁的一致性选型：如果业务库存绝对不能超卖，不要依赖异步主从的 Redis 锁做强互斥；要么 Redis 只做前置拦截，强互斥交给 Zookeeper，或者直接放弃 Redis 锁做强互斥。 第三层，业务层加全局幂等号，Redis 做库存预扣，拦截大部分无效流量，超时自动回补预扣库存。 第四层，数据库兜底，扣库存 SQL 带上num >=1 乐观锁条件。哪怕上层 Redis 锁全部失效，数据库这条更新语句也能保证库存不会被扣成负数，从根源杜绝超卖。 Redis 分布式锁更多是用来削峰、减少 DB 压力，不能单独作为防超卖的唯一保障。

（二）排查思路：高并发下偶发死锁

死锁：锁被永久持有，后续请求永远抢不到锁。常见原因：

  1. 加锁是非原子的：SETNX 成功，EXPIRE 之前宕机，key 永久存在，死锁；
  2. 业务抛出异常，没有走到释放锁代码（try-finally 没写好）；
  3. 可重入锁释放次数不对：Redisson hash 计数，加锁 2 次只释放 1 次，计数不为 0，key 不会删除；
  4. 跨资源循环等待：线程 1 拿 skuA 锁等 skuB 锁，线程 2 拿 skuB 锁等 skuA锁，经典循环死锁；
  5. 网络分区：客户端拿到锁之后，和 Redis 断开连接，客户端认为自己持有锁，Redis 端 TTL 到期释放；客户端继续执行业务，后续释放锁失败，逻辑错乱。
  • 死锁解决手段：

  1. 统一原子加锁命令，杜绝 SETNX+EXPIRE 分开写；

  2. 释放锁逻辑放在try-finally；

  3. 使用 Redisson 可重入锁，框架自动维护重入计数，避免手动释放次数错误；

  4. 禁止循环获取多把资源锁；如果必须多锁，固定加锁顺序（永远先小 id、后大id），破坏循环等待条件；

  5. TTL 兜底，哪怕业务异常、网络断连，锁到时间一定会释放，不会永久卡死。

第一层：锁层（Redisson）

  • 锁 key：lock:stock:{skuId}，按 sku 拆分粒度；
  • 原子加锁，Lua 脚本释放、持有者校验；
  • 持锁时间尽量短：拿到锁后快速扣库存，不要在锁内做复杂逻辑；
  • 看门狗续期应对链路抖动、慢 SQL；
  • 自旋加锁增加随机退避，减少 Redis QPS、减少 CPU 空转。

第三层：数据库乐观锁兜底（防超卖底线，必不可少）无论上层 Redis 锁、预扣怎么做，数据库条件更新count>0 兜底，这是杜绝超卖的最后防线。

三、面试高分话术

我会分开排查两个现象：偶发超卖、偶发死锁。 先说偶发超卖，优先排查顺序： 第一，检查加锁是否原子，有没有分开 SETNX 和 EXPIRE；释放锁有没有直接 DEL、缺少 Lua 持有者校验，防止误删锁。 第二，看持锁业务耗时，是否超过锁 TTL，锁提前释放，并发进入；长链路用 Redisson 看门狗续期，同时尽量缩短锁内业务逻辑。 第三，重点排查 Redis 主从异步复制丢锁，这是压测偶发超卖最典型的根因：master 加锁成功，还没同步到从就宕机，从晋升为主，锁丢失，新请求拿到锁，并发扣库存。

Redlock 可以缓解，但性能和运维成本高，一般不用；我们主流做法是 Redis 锁只用来削峰，数据库update … where count>0 乐观锁兜底，这是防超卖的底线。 第四，检查锁粒度，不能所有 sku 共用一把锁，按 skuId 隔离，降低竞争。

然后是偶发死锁： 死锁常见原因：非原子加锁宕机、异常分支没有释放锁、可重入锁释放次数不对、多资源锁循环等待。 解决：使用原子 SET 命令，释放锁放在 try-finally；使用 Redisson 自带可重入锁；多资源加锁强制固定顺序，破坏循环等待；TTL 兜底，保证锁最终一定释放，不会永久卡死。

整套秒杀方案分三层：第一层 Redisson 分布式锁，按 sku 粒度加锁，Lua 释放 + 看门狗；第二层 Redis 预扣库存，提前挡住大部分无效流量，减少锁竞争；第三层数据库乐观锁兜底。Redis 锁只是优化手段，不能单独保证不超卖。

考察核心

区分【概率性主从丢锁导致的偶发超卖】和普通锁超时；同时能识别分布式锁场景下的死锁成因（不只是单锁不释放，还有多锁循环等待）；最重要的认知：秒杀里 Redis 锁是流量闸门，数据库才是正确性闸门。

第 18 题　定时任务（订单对账）Redis 锁，配置了 setnx、过期时间、释放校验，负载高任务超时、锁过期，任务重复执行导致对账错乱

问题

定时对账任务，用 Redis 分布式锁防止多节点重复跑；设置 30s 过期，释放锁也做了 value 校验。集群负载高，任务执行超过 30s，锁自动过期，其他节点拿到锁再次执行对账，重复计算、金额错乱。 面试官：基础配置都没问题，为什么锁失效？怎么全方位规避，杜绝重复执行？只靠 setnx + 过期时间够吗？

参考答案

一、事故根因

根本不是锁写错、释放没校验，而是固定 TTL 的设计假设就错了：预设了任务一定在 30s 内跑完。 负载冲高、慢 SQL、下游抖动、GC 停顿，任务耗时不可控；锁先到期释放，但是第一个节点的对账逻辑还在继续跑。于是两个节点并行跑同一批对账，产生重复数据。

这里有一个关键误区：很多人以为加长过期时间就能解决。加长TTL 只是降低概率，如果任务卡住几分钟，依然会复现；而且锁长时间卡死，节点宕机后要等很久才释放锁，任务阻塞。

二、三层防御方案（定时任务场景专属）

第一层：锁层 → 动态续期（看门狗），替代静态固定过期时间使用 Redisson 的可重入锁 + 看门狗：

  • 拿到锁之后，后台线程每隔一段时间（默认 1/3 TTL）刷新锁过期时间；
  • 只要任务线程还活着、业务在正常执行，锁就持续续期，不会因为任务耗时变长提前释放；
  • 任务正常结束，主动释放锁，停止续期；
  • 如果节点直接宕机，看门狗线程一起死掉，锁等待 TTL 后自动释放，避免死锁。
  • 看门狗边界： 如果 JVM 长时间 STW、进程卡死、OOM，看门狗线程被冻结，续期失败，锁依旧会过期。看门狗是缓解，不是 100% 杜绝锁超时。

第二层：业务层 → 任务幂等 + 任务状态机（对账这类数据任务最重要）分布式锁只是 “抢执行权”，它有失效风险；对账、结算这类资金类任务，不能把正确性寄托在锁上面。

  1. 每一次定时任务，生成唯一批次号（batchNo，例如日期 + 小时）；
  2. 任务开始前先写任务执行表：batchNo, status(待执行/执行中/成功/失败), 节点ip, 开始时间；
  3. 加唯一索引：batchNo 唯一；
  4. 抢任务的逻辑：先尝试插入这条记录，插入成功才获得执行资格；插入失败代表已经有节点在跑 / 跑完了，直接放弃；
  5. 任务执行中持续更新心跳时间；定时清理程序扫描长时间心跳不更新、状态卡在执行中的脏批次，标记失败，允许重试。

这一层的价值：就算锁失效，第二个节点尝试插入同一个 batch也会被唯一索引拦住，对账不会重复跑。 对账计算逻辑本身也要幂等：同一 batch 重复跑，不会累加金额，结果不变（先清空该批次临时数据再计算，或者使用 insert ignore）。

第三层：兜底监控 + 异常自愈

  1. 锁监控：监控锁的持有时长、看门狗续期日志、同一任务锁被多次抢占告警；一旦发现同一个任务锁短时间多次被获取，立刻告警；
  2. 对账结果对账校验：对账完成后做金额勾稽校验，发现总分不平、重复流水标记异常工单；
  3. 重试策略：失败批次人工 / 半自动重试，重试依然基于 batchNo 幂等；
  4. 备选高可靠锁选型：资金对账这种低并发、强防重复场景，可以换成 ZK 锁。

ZK 临时会话节点，会话存活锁就存在，会话消失自动释放，不需要看门狗；缺点是吞吐低，适合对账、结算，不适合秒杀。

三、回答面试官追问：只靠 setnx + 过期时间行不行？

不行。 setnx + 固定 TTL 适合执行时长稳定、允许极小概率重复的场景；对账、结算、资金类任务，任务耗时受外部依赖影响波动大，固定 TTL 是巨大隐患。 加长 TTL 是治标不治本：任务卡住会锁很久，故障扩散；缩短 TTL 又容易超时重复。 看门狗解决 “动态适配任务时长”；幂等 + 任务表唯一索引，是防止重复执行的最后一道防线。

补充：网上说的 Redis+ZK 双重锁一般不推荐生产落地，复杂度太高，收益很低；优先：看门狗锁 + 任务批次幂等表，性价比最高。

面试高分话术

这个事故的根源不是锁命令写错、释放没校验，而是采用固定过期时间，强假设任务一定会在 30 秒内完成。负载升高、慢 SQL、GC 停顿都会拉长任务耗时，锁先过期释放，业务还在跑，多个节点并行对账造成重复计算。单纯把过期时间改大，只是降低概率，不能根治，还引入锁长时间卡死的风险。

完整的保障是三层防御： 第一层，锁层面改用 Redisson 看门狗续期，锁的过期时间动态刷新，只要任务正常运行就不会提前释放；同时认识到看门狗也会受 JVM 长时间 GC、进程卡死影响，存在失效可能。 第二层，业务层是核心，对账任务引入批次号 batchNo，建立任务执行表并对 batchNo 加唯一索引。抢任务的时候先插入这条记录，插入成功才执行；就算锁失效，其他节点插入同一个批次会被唯一索引拦截。对账逻辑本身实现幂等，同一个批次多次执行不会重复累加金额。 第三层，监控兜底，监控锁抢占、对账金额勾稽校验，异常及时告警，脏批次走人工修复流程。

所以只靠 setnx + 过期时间远远不够。锁只用来减少抢任务冲突，真正保证不会重复执行的是业务幂等和状态表唯一约束。资金对账这种强一致性、并发不高的场景，也可以直接选用 ZK 分布式锁，依托会话机制天然续期。

考察核心

区分【锁的互斥】和【业务正确性】。初级工程师以为锁负责保证不重复；高级工程师清楚：锁只是优化手段，锁永远有失效边界，资金类任务必须用数据库幂等约束兜底。定时任务和库存秒杀场景的侧重点不一样：秒杀重点防超卖，对账重点防重复计算。

第 19 题　库存扣减场景，Redis 分布式锁全链路风险点+生产级完整方案

问题

库存扣减，流程：加锁 → 执行业务扣库存 → 释放锁。 面试官连续抛出问题：

  1. 业务执行超过锁 TTL，锁提前释放，并发进入超卖怎么办？
  2. 锁超时后，线程执行完直接 del，误删别人的锁怎么防？
  3. Redis 主从切换 / 脑裂，主加锁成功未同步从，新主无锁记录，锁失效怎么处理？
  4. 同一线程嵌套加锁（可重入）如何实现？
  5. 大量线程抢一把锁自旋空转、锁饥饿怎么优化？
  6. 数据库悲观锁、ZK 锁方案对比、优缺点、适用场景？

参考答案

一、逐个拆解所有风险点 + 对应解法

风险 1：业务耗时 > 锁过期时间，锁提前释放，多线程同时进入原因：单纯设置固定 TTL，无法预判业务真实耗时；业务卡住、慢 SQL、下游

  • 超时，时间到 Redis 自动释放锁。

解法：看门狗（续期机制，Redisson 自带） 拿到锁后启动后台定时线程，在锁到期前不断刷新过期时间；业务正常执行完毕，关闭续期。

注意：看门狗不是万能的，如果进程 OOM、JVM 长时间 STW 停顿，看门狗线程也会卡住，续期失败，锁依然会过期。

风险 2：锁超时释放后，旧线程执行完成，直接 del 删掉新线程的锁（锁误删）原因：直接 del lock_key，不校验持有者。时序：A 锁超时释放 → B 拿到锁

  • → A 跑完业务执行 del，删掉 B 的锁。

解法：Lua 脚本原子释放锁 锁 value 存当前线程唯一标识（UUID + 线程 ID）；释放时 Lua 先判断 value 匹配，才删除，不匹配直接返回，禁止删别人的锁。

风险 3：主从异步复制、脑裂，锁丢失（高频难点）时序：A 在 master 加锁成功，锁还没异步同步到 slave；master 宕机，slave 被哨兵晋升为新 master；新 master 不存在这条锁；B 可以成功加锁。

  • 解法分层：
  1. 认知：普通 Redis 主从锁，本身不具备强一致性，只能做前置互斥，不能单独作为防超卖唯一保障；
  2. 方案 A（主流）：Redis 锁只用来削峰限流，数据库条件更新兜底（updatestock set num=num-1 where id=? and num>=1），就算锁失效，数据库拦住超卖；
  3. 方案 B（强一致低并发）：改用 ZK 分布式锁；
  4. 方案 C：Redlock，多独立节点过半加锁成功；缺点：依赖系统时钟、性能差、运维复杂，极少上生产；脑裂本质是 AP 集群的取舍，Redis 优先可用性，牺牲一致性。

风险 4：同一线程嵌套调用，重复加同一把锁（可重入问题）

  • 原生 SETNX 不支持可重入，同一线程第二次加锁直接失败，业务卡死。

解法：Redisson 用 Hash 结构实现可重入锁

  • key：锁名称
  • field：线程唯一标识
  • value：重入计数 加锁：计数 + 1；释放：计数 - 1；计数归零才删除 key。 不需要业务自己传递标记，框架内部封装。

风险 5：大量线程争抢同一把锁，自旋空转、CPU 飙升、锁饥饿自旋是不断循环尝试加锁，并发大的时候大量线程空跑；还有长时间拿不到锁

  • 的饥饿线程。

优化手段：

  1. 不要死循环自旋：退避策略，重试之间增加随机休眠（指数退避），减少Redis 压力和 CPU 消耗；

  2. 公平锁：Redisson 公平锁，按照请求排队顺序分配锁，避免饥饿；性能比非公平锁略低；

  3. 锁粒度拆分：不要所有商品共用一把大锁，按 skuId 做锁 key，打散竞争；

  4. 前置限流：令牌桶、Redis 预扣库存，拦截大部分无效请求，减少抢锁线程数量；

  5. 排队模型：MQ 异步化，秒杀流量削峰，避免大量线程同时抢锁。

风险 6：JVM STW、GC 长时间停顿导致看门狗续期失败GC 停顿几十～几百 ms，看门狗线程被挂起，来不及续期，锁超时释放，并发

  • 闯入。

解法：

  • JVM 调优，降低长 STW 概率；
  • 锁 TTL 预留足够缓冲；
  • 底层依然依赖数据库兜底。

二、其他备选锁方案对比（数据库悲观锁 / ZK 锁）

  1. Zookeeper 分布式锁（CP） 原理：临时有序节点，最小序号获得锁，监听前驱节点。 优点：
  • 临时节点，会话断开自动删除，天然防死锁，不需要看门狗；
  • ZK 过半写成功，主节点宕机不会丢锁，解决 Redis 脑裂丢锁痛点； 缺点：吞吐量低、重、运维复杂，网络抖动容易 session 失效释放锁； 适合：并发不高、一致性要求极高的流程（订单状态流转），不适合秒杀。

  1. 数据库悲观锁 select for update 优点：强一致，数据库原生； 缺点：行锁阻塞，并发能力差，容易长事务引发锁等待、死锁； 适合：低并发核心流程，不适合大促库存。

  2. 数据库乐观锁（version / 库存条件判断） 一般不作为分布式锁，是兜底防线，是库存防超卖的底线。

三、从基础 setnx → 生产级完整设计（三层核心）

  1. 基础层：锁语法规范 原子加锁：SET lockKey ownerId NX EX ttl，禁止setnx+expire 分两次； Lua 脚本释放锁，校验持有者； 需要长任务自动续期 → Redisson 可重入锁、看门狗； 锁 key 按资源维度（skuId），锁粒度尽量小，减少竞争。
  2. 并发优化层：控制争抢，避免自旋与饥饿 sku 维度分锁、限流、随机退避自旋、公平锁按需开启、大流量 MQ 异步。
  3. 一致性兜底层（最重要） 承认 Redis 锁有极小概率失效；数据库条件更新兜底，防止超卖。 Redis 锁的定位：减轻数据库压力，不是强一致保障。

四、面试高分回答话术

这套 Redis 分布式锁链路，一共有多个典型失效场景，我逐个梳理： 第一，业务执行超过锁过期时间，锁提前释放。基础方案是设置 TTL，生产上用 Redisson 看门狗，在锁到期前持续续期；但看门狗也会受 JVM GC 停顿影响，不能完全依赖。 第二，锁超时之后旧线程误删别人的锁，解决方式是锁 value 存线程唯一标识，用 Lua 脚本原子判断匹配再删除，禁止直接 del。 第三，Redis 主从异步复制、脑裂问题，主节点加锁成功还没同步从节点就宕机，新主丢失锁。这个是 Redis AP 模型天生的短板，没有低成本的完美解法；我们的策略是 Redis 锁只做前置削峰，库存扣减用数据库num>=1 条件更新兜底；强一致低并发场景换成 ZK 锁，Redlock 因为时钟依赖复杂，一般不上生产。 第四，可重入需求，原生 Redis 不支持，Redisson 用 hash 结构记录线程和重入次数，计数归零才释放锁，业务层不用自己传标记。 第五，大量线程抢同一锁，自旋空转、锁饥饿：拆分锁粒度，按 sku 隔离；自旋加随机退避；高并发用 MQ 异步削峰；需要顺序分配锁就开启公平锁。

备选方案：ZK 锁是 CP 模型，临时节点天然防死锁，不会脑裂丢锁，但是吞吐低、运维重；数据库悲观锁性能差，只适合低并发。

整体生产设计分为三层：第一层保证锁本身原子、可重入、自动续期、防误删；第二层做竞争优化，打散锁粒度、限流退避；第三层数据库兜底，接受 Redis 锁存在理论失效概率，用数据库拦住超卖。

考察核心

  1. 不再只是考命令，考察异常全链路风险识别：GC 停顿、脑裂、可重入、锁饥饿，同时要有取舍思维，明白 Redis 锁的定位是削峰，而不是强一致的终极方案，数据库兜底是底线。

核心思想：分布式锁没有绝对完美，所有锁都有失效场景；高级工程师不是写出一把不会坏的锁，而是识别所有失效路径，叠加兜底机制，控制故障影响。
