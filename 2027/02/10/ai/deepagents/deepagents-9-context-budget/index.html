    Deep Agents 09 · 上下文预算

    📅 2027-02-10

    09 上下文预算

    先卸载大结果，窗口到 85% 才摘要，原文另存文件｜依据官方 context engineering 页自绘

    版本不一致提示

    • 本篇基线是 deepagents 0.7.42 + langchain 1.5.2 + Python 3.13；
    • 上下文压缩是内置的：不用另加中间件，create_deep_agent 的 bare stack 里已有 FilesystemMiddleware 的卸载与 SummarizationMiddleware 的摘要；
    • 卸载阈值默认 20,000 token（tool_token_limit_before_evict=20000，实测签名默认值）；人类消息阈值默认 50,000；
    • 摘要触发点是模型 max_input_tokens 的 85%，保留最近 10% token；模型 profile 缺失时退回 170k 触发 / 保留 6 条消息；
    • 摘要以 HumanMessage 形式进上下文，metadata 的 lc_source 是 "summarization"——流式输出里要过滤掉它的 token；
    • 摘要不修改持久化的 state["messages"]，只改发给模型的请求。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 说清卸载（offloading）与摘要（summarization）各自的触发条件与产物；
    2. 用命令行工具量出一段内容大概多少 token，判断该落盘还是直接回；
    3. 会调阈值、会开按需压缩工具、会用 excluded_tools 缩工具面。

    二、前置知识

    • 读完 DA08 记忆；
    • 知道工具结果、文件工具与后端的关系（DA03 / DA04）；
    • 对 token 有直觉：1 个汉字约 1 token，1 个英文词约 1.3 token。

    三、理论讲解（官方定义）

    1. 两条压缩机制

    机制
    触发
    效果
    卸载 Offloading
    单个工具结果 > 20k token
    写后端，回「路径 + 前 10 行」
    摘要 Summarization
    上下文到窗口 85%
    旧消息换成结构化摘要

    卸载还有第二种形态：会话上下文过 85% 时，旧的 write_file / edit_file 调用（里面带着完整文件内容）会被截成指向磁盘的指针——因为这些内容本来就已经落盘，留在历史里是纯冗余。

    2. 摘要做什么

    1. 模型生成结构化摘要：会话意图、结论、产物、下一步；
    2. 摘要以 HumanMessage 进上下文（带 notification metadata，lc_source="summarization"）；
    3. 原文以文本形式写进文件系统，作为可检索的原始记录。

    3. 可调项

    • 阈值：FilesystemMiddleware(tool_token_limit_before_evict=…, human_message_token_limit_before_evict=…)；
    • 按需压缩：create_summarization_tool_middleware(...) 给 agent 一个 compact_conversation 工具；
    • 工具面：用 harness profile 的 excluded_tools 把用不到的内置工具从 schema 里去掉。

    四、原理拆解：为什么先卸载再摘要

    摘要是有损的：一旦摘要，细节只能靠文件找回。卸载是无损的：原文还在后端，只是上下文里换成了一个指针。

    所以顺序是「先无损、后有损」：

    1. 单条结果太大 → 先落盘（无损）；
    2. 历史里的写文件调用冗余 → 截成指针（无损）；
    3. 都做完了还是超窗口 → 才摘要（有损，但原文另存）。

    另一个关键点：摘要改的是请求，不是 state。持久化的消息历史不变，这保证了回放、评测、time travel 还能看到原始过程。

    五、场景说明

    • 长文档分析：先 read_file 分页读，分析结果落盘，主上下文只留结论；
    • 批量抓取：抓取结果直接写 /notes/，上下文只留路径与摘要；
    • 多轮长会话：靠自动摘要续命，但要在提示里要求「关键结论写到 /workspace/decisions.md」，防止摘要丢细节；
    • 工具很多：用 excluded_tools 去掉不用的文件工具，比调阈值更省；
    • 不该靠压缩解决的：任务本身需要全量数据同时在场（例如整表比对）——应该换成分块处理或子代理。

    六、示例代码

    步骤 1：环境准备

    uv init da09-budget
cd da09-budget
uv add deepagents

    步骤 2：凭证配置

    本讲干跑不需要 key；真跑时按 provider 配 key。

    步骤 3：导入

    from langchain_core.messages.utils import count_tokens_approximately
from deepagents.middleware import FilesystemMiddleware

    步骤 4：最小可运行代码（干跑，不需要 key）

    存成 budget.py，uv run budget.py。量一段材料占多少 token，并打印当前默认阈值。

    import inspect
from langchain_core.messages.utils import count_tokens_approximately
from deepagents.middleware import FilesystemMiddleware

sample = "长材料 " * 4000
tokens = count_tokens_approximately([("user", sample)])
print("样例 token 数:", tokens)

sig = inspect.signature(FilesystemMiddleware.__init__)
for name in ("tool_token_limit_before_evict", "human_message_token_limit_before_evict"):
    print(name, "=", sig.parameters[name].default)

    步骤 5：预期输出

    样例 token 数: 4004
tool_token_limit_before_evict = 20000
human_message_token_limit_before_evict = 50000

    步骤 6：验证是否成功

    • 4004 token 的样例没到 20k → 不会被卸载，会原样进上下文；
    • 同样的样例重复 5 次就超过 20k → 单条工具结果会被落盘成「路径 + 前 10 行」；
    • 两个默认值就是官方口径，改小便于本地观察，改大要小心窗口。

    写法 A · 调低阈值做本地观察

    from deepagents import create_deep_agent
from deepagents.middleware import FilesystemMiddleware

agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    middleware=[FilesystemMiddleware(tool_token_limit_before_evict=2000)],
)

    阈值调到 2000，一条千字搜索结果就会被落盘，方便肉眼确认「路径 + 预览」的形态。生产别调这么低——频繁落盘会让模型多跑几轮 read_file。

    写法 B · 给 agent 一个按需压缩工具

    from deepagents import create_deep_agent
from deepagents.backends import StateBackend
from deepagents.middleware import create_summarization_tool_middleware

backend = StateBackend()
agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    backend=backend,
    middleware=[create_summarization_tool_middleware("openai:gpt-6.1-sol", backend)],
    system_prompt="完成一个阶段、要开始下一个阶段前，先调用 compact_conversation。",
)

    工厂要求显式传 model 与 backend（摘要结果要写回后端）；它给 agent 加一个 compact_conversation 工具，同时 85% 的自动摘要照旧。

    写法 C · 换 provider 速查

    provider
    model 串
    窗口相关
    OpenAI
    openai:gpt-6.1-sol
    从 model profile 取 max_input_tokens
    Anthropic
    anthropic:claude-sonnet-5
    同上
    DeepSeek
    deepseek:deepseek-v4-pro
    无 profile 时按 170k 兜底
    智谱 / 通义
    ChatOpenAI(base_url=…, model="glm-5.2" / "qwen-plus")
    同上，建议显式给 profile

    摘要阈值依赖模型 profile；自建 provider 没有 profile 时，触发点会退到 170k，长上下文模型上等于「几乎不摘要」。

    七、常见坑（官方明确限制/版本差异）

    1. 以为要自己装压缩中间件。内置已有；重复加只会让栈变复杂。
    2. 把摘要当成删除。原文另存文件，grep 还能找回来；state 也没被改。
    3. 摘要后 status 报告混乱。摘要会丢中间态，关键状态要显式写进文件或 state 通道（异步子代理就是这么做的，DA12）。
    4. 流式输出里出现摘要 token。按 metadata["lc_source"] == "summarization" 过滤。
    5. 自建 provider 没 profile。触发点退到 170k，窗口小的话早就溢出了，要靠 ContextOverflowError 兜底。
    6. 只调阈值不缩工具面。工具 schema 每轮都发；用 excluded_tools 去掉不用的内置工具更划算。
    7. 大文件直接 read_file 全文。默认只读 100 行，用 offset / limit 分页，别一次拉全文。

    八、课后小结

    • 压缩内置：卸载（20k）+ 摘要（85%）；
    • 顺序是先无损后无损再有损；
    • read 分页、结果落盘、结论写文件，是最省上下文的三板斧；
    • 摘要改请求不改 state，原文可在文件系统找回；
    • 窗口大小来自模型 profile，自建 provider 要显式给。

    九、思考题

    1、为什么卸载阈值是「单个工具结果」而不是「整个上下文」？

    参考回答：单条超大结果是上下文膨胀的主要来源；按条处理粒度更细、也更容易在无损前提下腾出空间。

    2、摘要之后，模型怎么找回被压掉的细节？

    参考回答：原文已写成文件，模型可以 grep 关键词或 read_file 指定文件分页读。

    3、什么情况下压缩也救不了？

    参考回答：任务要求全量数据同时在场（整表比对、全量代码重构），这时要换分块或子代理隔离。

    4、compact_conversation 和自动摘要冲突吗？

    参考回答：不冲突，共用同一引擎与状态；手动只是把时机提前到阶段边界。
