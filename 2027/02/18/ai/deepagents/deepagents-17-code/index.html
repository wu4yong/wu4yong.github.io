    Deep Agents 17 · 终端里的 dcode

    📅 2027-02-18

    17 终端里的 dcode

    同一个 harness，换一层壳：终端交互、非交互、管道三种入口｜依据官方 Code 文档与本机 dcode doctor 自绘

    版本不一致提示

    • 本篇基线是 deepagents-code 0.1.88（内置 deepagents 0.7.30）+ Python 3.13；CLI 与 SDK 版本是两条线，别拿 SDK 的 0.7.42 去对 CLI，dcode doctor 会分两行打印；
    • 官方明确 Deep Agents Code 不在 Windows 原生支持，Windows 走 WSL；但 dcode --version / dcode doctor 这类诊断命令在 Windows 上能跑（本机实测 Platform: windows-amd64）；
    • 配置优先级是 DEEPAGENTS_CODE_* 前缀变量 > 同名变量 > ~/.deepagents/config.toml > 内置默认，dcode config show 会告诉你每个值来自哪一层；
    • 非交互模式默认关 shell：不加 -S 就只读不跑；-S all 等于放开任意命令；
    • --max-turns / --timeout 只在 -n 或管道输入时生效，超预算退出码 124；单独用会直接退 2；
    • 数据分两处：~/.deepagents/（Deep Agents 专属）与 ~/.agents/（跨 CLI 共享技能），别把两者混着放。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 说清 dcode 与 create_deep_agent 的关系：哪些能力是 CLI 自带、哪些要你在项目里配；
    2. 把一条任务从「手动在终端敲」搬到「CI 里无人值守跑」，并给它加上回合与时间两道闸；
    3. 会读 dcode doctor 与 dcode config show，出问题时先定位是哪一层没生效。

    二、前置知识

    • DA02 快速开始（create_deep_agent 的最小形态）；
    • DA03 工具、DA07 技能、DA10 规划、DA13 审批（CLI 里这些是默认打开或按开关打开的）；
    • 用过任意终端 TUI，知道 stdin / stdout 管道与退出码的含义。

    三、理论讲解（官方定义）

    1. 它是什么：一个装好的 harness 加一层终端壳

    官方定义很直接：Deep Agents Code（命令 dcode）是基于 Deep Agents SDK 的开源编码 agent，支持任意 tool-calling 模型、可换 provider、带跨会话记忆、可自定义技能、可对危险动作设审批。

    所以它不是新框架，而是把 DA01–DA16 那套能力打包成一个能直接用的产品：

    • 你写 create_deep_agent(...) 时，规划、文件工具、子代理要自己开；
    • dcode 里这些是默认就绪的，你要做的是「配置」而不是「编程」。

    官方能力面十条：远程沙箱、目标与评分标准（goals / rubrics）、子代理、记忆、上下文压缩、人工审批、技能、MCP 工具、追踪，以及任何模型都能接。

    2. 三种运行形态

    形态
    怎么进
    适合什么
    交互 TUI
    直接 dcode
    边看 diff 边改、需要人点头的任务
    非交互
    dcode -n "…"
    一条明确任务、跑完就退
    管道
    git diff | dcode -n "…"
    把上一条命令的输出当输入

    三种形态的差别不只是 UI：非交互默认关 shell（要用 -S 开白名单），每次非交互都是新线程（文件态的 memory / skills 仍在，对话历史不延续），管道输入上限 10 MiB。

    3. 配置的四个来源

    CLI 的配置不是「一个文件决定一切」，而是四层覆盖：

    1. DEEPAGENTS_CODE_ 前缀变量（最高，还能给第三方 key 单独取值，如 DEEPAGENTS_CODE_OPENAI_API_KEY）；
    2. 同名环境变量（shell export 永远压过 .env）；
    3. ~/.deepagents/config.toml（模型默认、主题、更新策略都在这里）；
    4. 内置默认。

    .env 的加载顺序也有讲究：先找启动目录向上最近的 .env，再落 ~/.deepagents/.env，项目级压全局级，但都压不过 shell。/reload 可以只重读配置与技能，不丢当前会话。

    4. 数据落在哪：两个目录、四层优先级

    目录
    放什么
    谁读
    ~/.deepagents/
    会话库、输入历史、用户技能、自定义子代理、config.toml
    本机 dcode
    ~/.agents/
    跨 CLI 共享的技能（skills/）
    任何兼容工具
    .deepagents/（项目内）
    项目指令、项目技能、项目子代理
    只在本仓库生效
    .agents/（项目内）
    项目级共享技能（优先级最高）
    跨工具

    指令是叠加的（包内置 prompt → 用户 AGENTS.md → 项目 .deepagents/AGENTS.md → 仓库根 AGENTS.md），而技能与子代理是同名覆盖：项目级压用户级，不做合并。这条差别是「为什么我的规则有时候不生效」的第一大原因。

    5. 审批与两个「别随便开」的开关

    CLI 的审批是三档：

    • 默认：文件改动给 diff，等你确认；
    • -y / --auto-approve：分类器判定的 Auto 模式（TUI 或 ACP 下有效，headless 只警告不生效）；
    • --yolo：确认后不再拦（同样只 TUI / ACP 有效）。

    headless 里真正管用的不是这三档，而是 -S 的 shell 白名单：不给就完全不执行命令，给 recommended 是官方策展的安全集，给 all 是「模型想跑什么就跑什么」。

    6. 追踪：两种 trace 要分开放

    dcode 自己的模型调用、工具调用、编排，与「它替你在 shell 里跑起来的程序」产生的 trace 是两回事。官方给了分开的开关：

    • DEEPAGENTS_CODE_LANGSMITH_PROJECT：dcode 自己的 agent trace 进哪个项目（默认 deepagents-code）；
    • LANGSMITH_PROJECT：shell 里跑的应用 trace 进哪个项目；
    • DEEPAGENTS_CODE_LANGSMITH_REPLICA_PROJECTS：同一份 agent trace 再镜像一份到团队项目。

    不分开的后果很具体：你让 dcode 去 debug 一个开了 tracing 的 LangGraph 应用，两种 trace 混在一个项目里，评测时根本数不清哪条是 agent 的思考。

    四、原理拆解：一条任务的路径

    把 TUI 剥掉，dcode 的路径只有五段：

    1. 入口层：TUI / -n / 管道，把用户输入、@file 引用、粘贴的图片整理成一条消息；
    2. agent server：CLI 内部起一个本地服务，持有会话、checkpointer、MCP 连接与技能缓存；/restart 重启的就是它；
    3. harness：DA01–DA16 的那套——规划、虚拟文件系统、子代理、审批；
    4. 执行层：文件工具落盘、shell 工具跑命令、沙箱后端把命令送远端；分类器与权限规则在这一层判「能不能做」；
    5. 回显层：diff、tool call 卡片、plan 面板、token 用量，全是 DA14 那套事件流的终端投影。

    这解释了三件常见困惑：

    • 为什么 /reload 不丢会话：它只重读配置与技能，agent server 没重启；
    • 为什么 -n 不延续对话：非交互每次新建 thread，落盘的只有文件态；
    • 为什么 --max-turns 必须配 -n：回合上限是给「无人看守」用的，交互模式里由人来停。

    五、场景说明

    • 适合：仓库内的改造类任务（改测试、补迁移、批量重构）、需要看 diff 再放行的场景、CI 里做「看一眼再报告」的检查；
    • 不适合：需要精确多步编排且不能有任何歧义的生产流水线（那该写成脚本，不是让模型自由发挥）；
    • 必须设闸：任何会 push、会改数据库、会发消息的任务，headless 里也要给 -S 白名单 + --max-turns；
    • Windows：官方口径是不支持，走 WSL；本机只建议用它跑 doctor 一类的诊断，别把长任务押在原生 Windows 上。

    六、示例代码

    步骤 1：安装

    # macOS / Linux（官方安装脚本）
curl -LsSf https://langch.in/dcode | bash

# 已经是 uv 环境，也可以直接装包
uv tool install deepagents-code

    管理大批机器时可以钉版本：curl -LsSf https://langch.in/dcode | DEEPAGENTS_CODE_VERSION="0.1.88" bash。

    步骤 2：凭证配置

    dcode
/auth            # 在 TUI 里连 provider，key 存进 ~/.deepagents/.state

    不想进 TUI 的话，直接把 key 写进 ~/.deepagents/.env：

    OPENAI_API_KEY=sk-...
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_...

    步骤 3：第一次交互任务

    > 给这个仓库加一个 pytest 的 smoke 测试，只测 CLI 入口能 --version

    模型会先给计划（write_todos），再逐个文件给 diff，你按 y / n 放行；Shift+Tab 是自动放行开关，! 进 shell 模式。

    步骤 4：非交互与管道

    # 一条任务，跑完就退
dcode -n "为 src/utils.py 补三个边界用例"

# 把上一条命令的输出当输入（自动进入非交互）
git diff | dcode -n "review 这些改动，只报风险，不改代码"

# 只读不跑：不给 -S，shell 全是关的
cat error.log | dcode -n "定位这段报错的原因"

    步骤 5：预期输出（本机诊断）

    $ dcode --version
deepagents-code 0.1.88
deepagents (SDK) 0.7.30

$ dcode doctor
Diagnostics ✓
├ deepagents-code: 0.1.88
├ deepagents (SDK): 0.7.30
├ Python: 3.13.18
├ Platform: windows-amd64
└ Install method: other
Configuration ✓
├ Data directory: C:\Users\...\.deepagents (not created)
└ Config file: ...\.deepagents\config.toml (not created)

    步骤 6：验证是否成功

    • dcode --version 与 doctor 里的 SDK 版本必须一致，对不上说明装了两份；
    • dcode config show 能指出每个值的来源（env / config.toml / default），排障先看它；
    • dcode config path 列出四处路径（managed config、config.toml、全局 .env、项目 hooks.json），确认你改的是被读的那一份。

    写法 A · 项目内落地：指令、技能、子代理各归其位

    repo/
├── AGENTS.md                      # 仓库总规则：技术栈、命令、禁区
├── .deepagents/
│   ├── AGENTS.md                  # 项目级补充规则（与根 AGENTS.md 叠加）
│   ├── skills/
│   │   └── release-check/
│   │       └── SKILL.md           # name 必须等于目录名
│   └── agents/
│       └── reviewer/
│           └── AGENTS.md          # 自定义子代理：frontmatter 写 name/description/model
└── src/

    SKILL.md 的最小骨架：

    ---
name: release-check
description: 发版前的检查清单，只在用户提到 release 时使用
---
1. 跑 `pytest -q`
2. 跑 `dcode -n "检查 CHANGELOG 是否覆盖本次改动" -q`
3. 任一失败就停下，把失败项贴给用户

    子代理的 AGENTS.md 只需要三行 frontmatter，正文就是它的系统提示：

    ---
name: reviewer
description: 只读评审员，不改代码
model: openai:gpt-6.1-sol
---
你只做评审：指出风险与测试盲区，不提交任何修改。

    写法 B · CI 里无人值守：两道闸一起上

    # .github/workflows/dcode-review.yml 里的核心一步
git diff origin/main...HEAD \
  | dcode -n "评审这次改动，输出 markdown 风险清单" \
      -S recommended \
      --max-turns 10 \
      --timeout 120 \
      -q --no-stream > review.md

echo "exit=$?"
    • -S recommended：只放开官方策展的命令集（pytest、git、make 一类）；
    • --max-turns 10：最多 10 轮，防止模型自己跟自己聊；
    • --timeout 120：两分钟墙钟上限，谁先到谁停；
    • 两者任一触发，退出码 124，CI 可以据此区分「预算用尽」与「真失败」；
    • -q --no-stream：干净输出，方便重定向成文件。

    写法 C · 追踪与排障：把 agent trace 与应用 trace 分开

    # ~/.deepagents/.env
DEEPAGENTS_CODE_LANGSMITH_PROJECT=deepagents-code
LANGSMITH_PROJECT=customer-support-agent
# 想镜像一份到团队项目
DEEPAGENTS_CODE_LANGSMITH_REPLICA_PROJECTS=team-shared

    出问题时的顺序：dcode doctor（环境与安装）→ dcode config show（配置来源）→ /trace（拿到 URL 看这次到底调了什么）→ DEEPAGENTS_CODE_DEBUG=1（保留 server 日志）。四步下来基本能定位到「是配置没生效、还是模型行为不对」。

    七、常见坑（官方明确限制/版本差异）

    1. 拿 SDK 版本对 CLI。dcode 内置自己的 SDK（0.1.88 对应 0.7.30），与你的项目 venv 无关；混着看会以为版本回退。
    2. Windows 上硬跑长任务。官方不支持，走 WSL；doctor 能跑不代表 TUI 与 shell 工具都正常。
    3. 以为 .env 压得过 shell。shell export 永远最高；/reload 也改不了这一点。
    4. 技能与子代理指望合并。它们同名是覆盖，不是叠加；项目级压用户级。
    5. headless 忘了 -S。默认关 shell，模型会「想跑但跑不了」，最后交一份没验证的结论。
    6. -S all 当默认。等于把审批这层拆了；CI 里只给 recommended 或明确命令列表。
    7. --max-turns 单独用。没 -n / 管道直接退 2，不是 124，脚本里判错会误判。
    8. trace 混项目。agent 与被它跑起来的应用写进同一个项目，评测时无法区分。

    八、课后小结

    • dcode 是「装好的 harness + 终端壳」，不是新框架；能力默认就绪，你要做的是配置；
    • 三种形态（TUI / -n / 管道）的差别在 shell 开关、线程延续与输入上限；
    • 配置四层覆盖、数据两个目录，config show 是唯一可靠的「现在到底用哪个值」；
    • headless 的两道闸是 -S 白名单与 --max-turns / --timeout，都用 124 报预算超限；
    • 追踪要把 agent trace 与应用 trace 分项目，否则评测数据会被污染。

    九、思考题

    1、为什么非交互模式默认关 shell，而不是默认开？

    参考回答：无人看守时没人能拦命令；默认关、要开显式给 -S，是把「风险默认最小」写进产品，而不是靠文档提醒。

    2、-y 与 --yolo 在 CI 里为什么没用？

    参考回答：两者都依赖 TUI / ACP 的交互确认流程；headless 只打警告，真正控风险的是 -S 白名单与回合上限。

    3、项目级技能同名覆盖用户级技能，这个设计合理吗？

    参考回答：合理。仓库的规则应该压过个人习惯，否则换台机器、换个人，行为就变；要让两份都生效就改名。

    4、如果 CI 里退出码是 124，你会怎么改？

    参考回答：先判断是回合还是时间先到——放宽对应一项，再看 trace 里是否在死循环调同一个工具；不要直接把预算翻倍。
