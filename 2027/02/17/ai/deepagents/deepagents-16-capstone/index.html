    Deep Agents 16 · 综合实战

    📅 2027-02-17

    16 综合实战

    业务规则与工具全部留用，只把「编排」交给 harness｜本篇自绘

    版本不一致提示

    • 本篇基线是 deepagents 0.7.42 + langchain 1.5.2 + langgraph 1.2.24 + Python 3.13；
    • 规划在 0.7 起是 opt-in：TodoListMiddleware 从 langchain.agents.middleware 导入，不是 deepagents；
    • files= 只在首次调用时喂给后端，值是 create_file_data("正文") 的返回值——它只收单个字符串，传 dict 直接报 AttributeError；
    • skills= 传的是源目录（如 /skills/），name 必须等于子目录名；memory= 传的是文件路径列表；
    • 项目里若把 interrupt_on 与 permissions(mode="interrupt") 同时用，两类审批会合并成一个批次；
    • 本篇干跑不需要模型 key；写法 A 的真跑才需要，评测回路见写法 C（LS06–LS08 口径）。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 把 LG16 的「分类 → 调查 → 审批 → 执行」手工图，改造成 harness 承载的同一个业务；
    2. 按风险顺序加装六层能力，并说清每加一层要重测什么；
    3. 给出可交付的三件套：agent 脚本、评测脚本、上线清单。

    二、前置知识

    • LG16 综合实战（工单审批 Agent 的原始图与业务规则）；
    • DA04 后端、DA05 权限、DA07 技能、DA08 记忆、DA10 规划、DA11 子代理、DA13 审批、DA14 事件流；
    • 知道 LangSmith 数据集与 evaluator 的用法（LS06–LS08）。

    三、理论讲解（官方定义）

    1. 这次改造的边界

    原图里不该动的：业务字段（ticket_id / risk / decision）、工具实现（查单、改单、通知）、审批的业务含义。

    该交给 harness 的：流程推进（write_todos）、上下文隔离（子代理）、口径知识（skill）、客户偏好（memory）、不可逆动作的门（interrupt_on）、对外可见性（事件流）。

    2. 六层能力各自解决什么

    层
    解决什么
    不加会怎样
    write_todos
    流程可见、漏步可查
    长任务跑着跑着忘了第几步
    子代理
    查单与写话术各用一套上下文
    主上下文被查询结果灌满
    skill
    回复口径按需加载
    口径写死在系统提示，改一次要重部署
    memory
    客户偏好跨会话保留
    每次都要用户重复一遍
    interrupt_on
    关单这种不可逆动作必须人点头
    模型手一抖就关单

    3. 加装顺序（按风险，不按方便）

    顺序
    加什么
    加完先测什么
    1
    TodoListMiddleware
    6 步任务不漏步、todo 状态能收敛
    2
    查单员子代理
    查单结果不回灌主上下文
    3
    回复员子代理
    话术符合口径、不越权改单
    4
    skill（回复口径）
    只在写回复时被读，闲聊不读
    5
    memory（客户偏好）
    换线程仍生效，且不变成隐藏指令
    6
    interrupt_on（关单）
    中断能拦住、拒绝后不重试

    每加一层，重测两件事：这一层自己，以及上一层没被破坏。加装不是「一起上，最后一起测」——出问题时你不知道是哪层坏的。

    四、原理拆解：为什么底座不用重画

    LG16 的图是「固定流程」：分类、调查、审批、执行，每步都写死。Deep Agents 的图是「模型驱动的循环 + 中间件」：模型决定下一步，中间件负责规划、文件、子代理、审批。

    所以改造不是把图拆掉，而是把编排权从边（edges）移到工具与中间件：

    • 原来的 classify 节点 → 系统提示里的路由规则 + 子代理 description；
    • 原来的 investigate 节点 → query_ticket 工具 + 查单员子代理；
    • 原来的 approve 节点 → interrupt_on={"update_ticket": ...}；
    • 原来的固定顺序 → write_todos 的任务表。

    代价是「流程不再由代码保证」：模型可能跳步、可能自己编结论。补偿手段正是后四层——规划、隔离、口径、审批。

    五、场景说明

    • 适合改造：步骤数不定、要查多个系统、要读写文件、要人审批的业务；
    • 不适合：步骤固定且只有两三步（如「查余额 → 回复」），手绘图更便宜；
    • 必须保留人工点：任何对外承诺（赔付金额、时效）与不可逆状态变更；
    • 评测口径：只看最终交付物（回复内容 / 工单状态）对不对，不看中间派了几次活。

    六、示例代码

    步骤 1：环境准备

    uv init da16-capstone
cd da16-capstone
uv add deepagents

    步骤 2：凭证配置

    干跑不需要 key；写法 A 需要 OPENAI_API_KEY（或换任意 provider）。

    步骤 3：导入

    from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage, HumanMessage
from langchain.agents.middleware import TodoListMiddleware
from langchain.tools import tool
from langgraph.checkpoint.memory import InMemorySaver
from deepagents import create_deep_agent
from deepagents.backends.utils import create_file_data

    步骤 4：最小可运行代码（干跑：验证六层都装上了）

    存成 ticket_agent.py，uv run ticket_agent.py。假模型只发一次 update_ticket 调用，脚本打印工具面与中断配置。

    from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage, HumanMessage
from langchain.agents.middleware import TodoListMiddleware
from langchain.tools import tool
from langgraph.checkpoint.memory import InMemorySaver
from deepagents import create_deep_agent
from deepagents.backends.utils import create_file_data

@tool
def query_ticket(ticket_id: str) -> str:
    """按工单号查询状态与历史。"""
    return f"{ticket_id}: 已发货，客户要求改地址"

@tool
def update_ticket(ticket_id: str, status: str) -> str:
    """修改工单状态（不可逆）。"""
    return f"{ticket_id} -> {status}"

captured = {}

class Cap(GenericFakeChatModel):
    def bind_tools(self, tools, **kw):
        captured["tools"] = [getattr(t, "name", "") for t in tools]
        return self

call = AIMessage(content="", tool_calls=[{
    "name": "update_ticket",
    "args": {"ticket_id": "1024", "status": "closed"},
    "id": "u1",
}])

agent = create_deep_agent(
    model=Cap(messages=iter([call, AIMessage(content="已处理")])),
    tools=[query_ticket, update_ticket],
    skills=["/skills/"],
    memory=["/memories/AGENTS.md"],
    middleware=[TodoListMiddleware()],
    subagents=[
        {"name": "investigator", "description": "查单员：只查不改",
         "system_prompt": "你只查工单", "tools": [query_ticket]},
        {"name": "writer", "description": "回复员：只写客户话术",
         "system_prompt": "你只写回复"},
    ],
    interrupt_on={"update_ticket": {"allowed_decisions": ["approve", "reject"]}},
    checkpointer=InMemorySaver(),
)

files = {
    "/skills/ticket-reply/SKILL.md": create_file_data(
        "---\nname: ticket-reply\ndescription: 工单回复口径\n---\n先道歉再给时限。"
    ),
    "/memories/AGENTS.md": create_file_data("# 客户偏好\n- 只用中文，不用敬语堆砌"),
}

cfg = {"configurable": {"thread_id": "cap-1"}}
out = agent.invoke(
    {"messages": [HumanMessage(content="把 1024 关掉")], "files": files},
    config=cfg,
)
print("tools:", captured["tools"][:8])
print("其余工具:", captured["tools"][8:])
print("interrupt:", out["__interrupt__"][0].value["review_configs"])

    步骤 5：预期输出

    tools: ['ls', 'read_file', 'write_file', 'edit_file', 'delete', 'glob', 'grep', 'task']
其余工具: ['write_todos', 'query_ticket', 'update_ticket']
interrupt: [{'action_name': 'update_ticket', 'allowed_decisions': ['approve', 'reject']}]

    步骤 6：验证是否成功

    • 工具面里同时有 task（子代理入口）、write_todos（规划）、两个业务工具；
    • interrupt 里只有 update_ticket，决策被裁成两项——说明审批是按工具粒度、不是整轮；
    • files 里有 skill 与 memory 路径，说明这两层已进后端（模型读不读是运行期的事）。

    写法 A · 真跑：把假模型换成真模型，走完审批

    investigator = {"name": "investigator", "description": "查单员：只查不改",
                "system_prompt": "你只查工单", "tools": [query_ticket]}
writer = {"name": "writer", "description": "回复员：只写客户话术",
          "system_prompt": "你只写回复"}

agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    tools=[query_ticket, update_ticket],
    system_prompt=(
        "你是工单助手。先查单，再决定是否需要改单；"
        "任何状态变更前先说明理由与影响。"
    ),
    skills=["/skills/"],
    memory=["/memories/AGENTS.md"],
    middleware=[TodoListMiddleware()],
    subagents=[investigator, writer],
    interrupt_on={"update_ticket": {"allowed_decisions": ["approve", "reject"]}},
    checkpointer=InMemorySaver(),
)

out = agent.invoke({"messages": [{"role": "user", "content": "客户要改地址，工单 1024"}]},
                   config={"configurable": {"thread_id": "cap-2"}})
# 命中审批后（记得 from langgraph.types import Command）：
out = agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}),
                   config={"configurable": {"thread_id": "cap-2"}})

    写法 B · 接前端：同一场运行的三条投影

    for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "客户要改地址，工单 1024"}]},
    stream_mode=["updates", "messages"],
    subgraphs=True,
    version="v2",
):
    mode, data = chunk["type"], chunk["data"]
    if mode == "updates" and "__interrupt__" in data:
        print("待审:", data["__interrupt__"][0].value["action_requests"])
    if mode == "messages":
        token, meta = data
        print("[主]" if not chunk["ns"] else "[子]", token.content, end="")

    审批弹窗读 updates，气泡读 messages，子代理卡片按 ns 分流——与 DA14 的口径一致。

    写法 C · 评测回路：同一数据集跑前后两版

    from langsmith import Client, evaluate

client = Client()
dataset = client.create_dataset("ticket-agent-capstone")

def target(inputs):
    out = agent.invoke({"messages": [{"role": "user", "content": inputs["question"]}]},
                       config={"configurable": {"thread_id": f"eval-{inputs['id']}"}})
    return {"answer": out["messages"][-1].content}

def exact_ticket(root_run, example):
    # 简化示例：只查最终回复里是否出现工单号与目标状态
    answer = root_run.outputs["answer"]
    return {"key": "ticket", "score": int(example.outputs["ticket_id"] in answer)}

evaluate(target, data=dataset.name, evaluators=[exact_ticket], experiment_prefix="deepagent-v1")

    真正的判据建议三条：工单状态正确、回复符合口径、该审批的确实审批了（第三项从 trace 里数 update_ticket 前的中断次数）。

    七、常见坑（官方明确限制/版本差异）

    1. create_file_data 传 dict。它只收单个字符串；要多个文件就一个路径调一次。
    2. skills= 传成技能目录。要传源目录（/skills/），name 必须等于子目录名，否则静默 0 个技能。
    3. 规划忘了开。0.7 起不传 TodoListMiddleware 就没有 write_todos，照着老文章会以为自带。
    4. 子代理 tools 以为会继承。指定即整体替换；不给就让子代理裸奔。
    5. 审批开在 query_ticket 上。查单被拦，人会被弹窗逼疯；只拦 update_ticket。
    6. memory 写成可变事实。今天日期、当前价格写进 AGENTS.md，第二天全是错的。
    7. 评测只看最终文本。工单状态错了但话说得漂亮，分数照样满分。
    8. 子代理报告当客户回复。子代理只说给主代理听，对外话术必须主代理重写。

    八、课后小结

    • 底座留用：业务字段、工具、审批的业务含义都不改；
    • 编排交给 harness：规划、隔离、口径、记忆、审批、事件流六层按风险顺序加；
    • 每加一层重测「自己 + 上一层」，别攒着一起测；
    • 评测看交付物（状态、口径、审批记录），不看中间派活次数；
    • 这套课到此闭环：LC 给 agent、LG 给运行时、LS 给评测，DA 把它们打包成能干长活的骨架。

    九、思考题

    1、为什么把 classify 节点换成「系统提示 + 子代理 description」？

    参考回答：harness 里没有固定边，模型靠工具描述与子代理描述做路由；写死节点反而会限制步数不定的任务。

    2、六层里哪一层最不该省？

    参考回答：interrupt_on。其他层是效率与质量，审批是不可逆动作的最后一道门。

    3、为什么评测要单独数「审批次数」？

    参考回答：最终回答正确不代表过程合规；没有审批记录就等于模型自己把单关了。

    4、如果只能加两层，你加哪两层？

    参考回答：查单员子代理（隔离上下文）+ 关单审批（控风险）；规划与记忆可以后补。
