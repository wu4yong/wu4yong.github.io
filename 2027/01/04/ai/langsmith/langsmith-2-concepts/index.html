    LangSmith 02 · 概念体系

    📅 2027-01-04

    02 概念体系

    调试看 trace，看多轮行为看 thread，看「说了什么」看 trajectory｜依据官方 Observability concepts 页自绘

    版本不一致提示

    • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + Python 3.13；
    • 单条 trace 上限 25,000 个 run，超过后该 trace 的新 run 会被直接拒绝；长跑任务要么拆 trace，要么降采样；
    • thread 的串联键是 metadata.thread_id，不是 run_id，也不是旧接口里的 session_id（后者指环境背后的存储）；
    • trace 按套餐保留期自动删除；dataset 里的 example 永久保留，要留证据就趁早落 dataset；
    • 本篇示例可在无 key 模式（LANGSMITH_TRACING=false）下跑通，只是不去 UI 看结果。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 说清 run / trace / thread / trajectory 四者的包含关系与各自用途；
    2. 用 metadata.thread_id 把多轮调用串成一条 thread，并在 UI 里切到 Trajectory 视图；
    3. 用 feedback、tags、metadata 三种富化手段给 run 打标，为后面的筛选与评测做准备。

    二、前置知识

    • 读完 01 账号与环境，能跑出第一条 trace；
    • 知道「一个函数 = 一个 run」的对应关系。

    三、理论讲解（官方定义）

    1. run：最小工作单元

    一个 run 是一次具体的工作，比如一次模型调用、一次工具执行、一次检索。官方给的类比是 OpenTelemetry 的 span。每个 run 都带：类型、名称、输入、输出、开始/结束时间、状态、错误栈、父子关系。

    2. trace：一次操作的 run 树

    一次用户请求触发的所有 run，用同一个 trace id 串成一棵树。上限 25,000 run，超了拒收。

    3. thread：一次多轮会话

    一轮交互（用户一句话 + Agent 的全部响应）记作一条 trace；把同一会话的多条 trace 串起来，就是 thread。串联方式是给每条 trace 的根 run 带上同一个 metadata.thread_id。

    4. trajectory：把 thread 拍平

    trajectory 是 thread 的一种投影：把嵌套的 run 去掉，只留 human / ai / tool 消息，按首次出现顺序排一遍。它不替代 trace，只是换个读法。

    对象
    形状
    含什么
    什么时候用
    trace
    run 树
    每个 run 的完整输入输出
    查「这一次为什么错/慢」
    thread
    trace 序列
    每条 trace 的全部 run
    查「跨轮发生了什么」
    trajectory
    扁平消息列表
    去重后的消息序列
    把会话当对话读

    5. 三种富化手段

    • feedback：给单个 run 打分，由 tag（名字）+ score（数值或分类）组成，可以人工写、也可以评测器自动写；
    • tags：字符串标签，用来分类与过滤（prod、canary、refund）；
    • metadata：键值对，用来带业务维度（tenant、agent_version、thread_id）。

    注意：feedback 分数 ≠ 评测器分数。前者是「挂在这个 run 上的一次打分」，后者是「实验里按评测器算出来的一列」。两者在 UI 里长得像，但来源与用途不同。

    四、原理拆解：四种视图是同一次写入的四种投影

    写入侧只有一份数据：run 记录（含 parent_run_id、trace_id、metadata、feedback）。

    读出侧有四种投影：

    1. Runs / Trace 视图：按 trace_id 聚成一棵树，回答「这一步的内部长什么样」；
    2. Thread 视图：按 metadata.thread_id 把多条 trace 排成时间序列，回答「跨轮怎么演变」；
    3. Trajectory 视图：把 thread 里的消息投影成扁平列表，回答「到底说了什么」；
    4. Dataset / Experiment 视图：把 run 当作样例或实验产物，回答「质量有没有变」。

    所以「看不到 thread」几乎总是写入侧的问题：thread_id 没传、传了不同值、或传成了随机 UUID。

    五、场景说明

    一个退款客服 Agent，用户前后说了三轮：「退款怎么走」→「那多久到账」→「帮我催一下」。

    • 只看单条 trace，你能看到第三轮为什么答错，但看不到前两轮已经承诺过「3 天到账」；
    • 切到 thread，才看得出第三轮的回答和前两轮的承诺冲突；
    • 切到 trajectory，能一眼读完这段对话，判断「是不是语气与承诺不一致」。

    六、示例代码

    步骤 1：环境准备

    uv init ls02-concepts
cd ls02-concepts
uv add langsmith python-dotenv

    步骤 2：凭证配置

    .env 同上一篇：LANGSMITH_TRACING=true、LANGSMITH_API_KEY=...、LANGSMITH_PROJECT=ticket-agent-dev。

    步骤 3：导入

    from langsmith import traceable, tracing_context

    步骤 4：最小可运行代码

    存成 concepts.py，uv run concepts.py。

    import os
from dotenv import load_dotenv
from langsmith import traceable, tracing_context

load_dotenv()

@traceable
def retrieve(q: str) -> str:
    return f"policy::{q}"

@traceable(run_type="llm")
def model(q: str, ctx: str) -> str:
    return f"回答：{q}（依据 {ctx}）"

@traceable
def turn(user_msg: str) -> str:
    ctx = retrieve(user_msg)
    return model(user_msg, ctx)

def chat(thread_id: str, msgs: list[str]):
    for m in msgs:
        # 关键：同一个 thread_id 写进 metadata
        out = turn(m, langsmith_extra={"metadata": {"thread_id": thread_id, "tenant": "A"}})
        print(out)

if __name__ == "__main__":
    chat("T-9d2", ["退款怎么走？", "那多久到账？", "帮我催一下"])

    # 富化：给整段上下文打 tag，省得逐条写
    with tracing_context(tags=["canary"], metadata={"agent_version": "v2"}):
        chat("T-9d3", ["换个问法：钱什么时候回来"])

    步骤 5：预期输出

    回答：退款怎么走？（依据 policy::退款怎么走？）
回答：那多久到账？（依据 policy::那多久到账？）
回答：帮我催一下？（依据 policy::帮我催一下？）
回答：换个问法：钱什么时候回来（依据 policy::换个问法：钱什么时候回来）

    步骤 6：验证是否成功

    • Runs 列表里两条 thread 各 3 条 trace，共 6 条；
    • 切到 Thread 视图，T-9d2 下三条 trace 按时间排好；
    • 切到 Trajectory 视图：能看到 3 组 human → ai 的消息，没有嵌套的 retrieve / model；
    • 把 langsmith_extra 那行去掉再跑一遍：三条 trace 各自独立，Thread 视图里没有新条目——这就是「忘传 thread_id」的典型症状。

    写法 A · 手动打 feedback

    from langsmith import Client
client = Client()

# run_id 从 UI 或 list_runs 里拿；key 是反馈名，score 可以是数值或分类
client.create_feedback(run_id="<run-id>", key="correctness", score=0)

    人工打分适合标注队列（LS09 展开），脚本里打 feedback 多用于「离线回放后写结论」。

    七、常见坑（官方明确限制/版本差异）

    1. thread_id 用请求 ID。一人多轮被拆成多条 thread，永远看不到上下文。
    2. trace 写成「一个 run 一条」。把循环里的每步都当成独立 trace，等于放弃了树形结构。
    3. 长跑任务不拆 trace。25,000 run 上限一到就被拒收，表现是「后半段没数据」。
    4. metadata 值类型不一致（"1" 与 1 混用）。后面按 metadata 过滤时一半查不到。
    5. 把 feedback 当评测结论。单条打分与实验里的评测器分数不是一回事，别混着汇报。
    6. 指望 trace 永久保存。保留期一到就删；要留证据，落 dataset。

    八、课后小结

    • 四个粒度是一份数据的四种投影：run → trace → thread → trajectory；
    • thread 只认 metadata.thread_id，且必须是业务会话 ID；
    • trace 有 25,000 run 上限，dataset 里的 example 才是永久证据；
    • feedback / tags / metadata 是筛选与评测的三种抓手；
    • 「看不到 thread」先查写入侧，不要先怀疑 UI。

    九、思考题

    1、为什么不直接用 thread_id 当 trace 的 id？

    参考回答：trace 是「一次操作」，thread 是「一次会话」，两者多对一；合并会让一条会话的所有 run 挤进同一棵树，25,000 上限与按轮排障都会失效。

    2、trajectory 里为什么会「去重」？

    参考回答：同一条消息可能在多轮里被反复传递（历史拼接），trajectory 只保留首次出现的顺序，避免读成一堆重复内容；代价是丢掉了执行细节。

    3、什么情况下应该主动拆 trace？

    参考回答：批量任务、长会话、定时巡检这类「一次运行里含多个独立请求」的场景，按请求拆 trace，再按批次打同一个 metadata（如 batch_id），比硬塞进一条树更可查。

    4、metadata 与 tags 该怎么分工？

    参考回答：需要取值的维度用 metadata（tenant、version、thread_id），需要枚举分类的用 tags（prod、canary）；两者都能过滤，但 metadata 更适合做精确匹配与分组统计。
