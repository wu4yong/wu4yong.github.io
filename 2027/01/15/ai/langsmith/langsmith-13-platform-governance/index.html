    LangSmith 13 · 平台形态与治理

    📅 2027-01-15

    13 平台形态与治理

    治理不是「加权限」，而是先把「谁能看、能看多久、谁来付」写成规则｜依据官方 Platform setup 页自绘

    版本不一致提示

    • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + Python 3.13；
    • 官方把托管形态分成 Cloud / BYOC（Bring Your Own Cloud）/ Self-hosted 三类，与 LS12 的部署拓扑是两张表：前者讲「平台本身放哪」，后者讲「agent 运行时放哪」；
    • trace 有保留期，dataset 里的 example 不受保留期影响；保留期按套餐分档，不是全局一个值；
    • 计费口径是 按席位 + 按 trace / 评测用量（部署另计算力与数据库），具体单价随套餐变动，本篇只讲口径不报价；
    • RBAC 的角色按 organization / workspace 两级划分，最小权限要先划 workspace 再谈角色；
    • 本篇示例需要 key。无 key 时脚本会 401。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 用「数据能不能出 VPC + 谁运维」两张问题，把三形态选成一个；
    2. 说清保留期、配额、席位三条成本线各在哪，并知道哪类数据不会过期；
    3. 按「谁能看什么」划出 RBAC 的最小权限，并用脚本自查题库与流量体量。

    二、前置知识

    • 读完 12 Agent Server，知道控制面/数据面；
    • 知道自己团队有几类角色（开发、评测、运营、外包）。

    三、理论讲解（官方定义）

    1. 三形态

    形态
    基础设施
    数据位置
    升级与扩容
    典型门槛
    Cloud
    平台方
    平台方
    平台方统一
    Plus 起可部署
    BYOC
    客户云账号
    客户云
    平台出镜像、客户执行
    Enterprise
    Self-hosted
    客户机房 / K8s
    客户
    客户自己
    Enterprise + license

    BYOC 与 Self-hosted 的差别常被搞混：BYOC 是「基础设施在你的云账号里，但编排与升级由平台方推动」；Self-hosted 是「镜像给你，从数据库到升级全是你自己的事」。

    2. 三条成本线

    • 席位：按人计，与用量无关；
    • trace 与评测用量：按 run 数 / 评测次数计，跑得多花得多；
    • 部署：按算力与数据库计（LS12 那些拓扑），与 trace 用量分开。

    所以「免费层够用」和「上线后账单暴涨」之间通常差的是第二条线：在线评测全量跑、judge 全量跑，都会体现在这里。

    3. 保留期与配额

    • trace 按套餐保留期到期删除；
    • dataset 的 example 永久保留；
    • 配额（如组织级 run 数上限）到顶后写入会被拒，表现为「后半段没数据」。

    这两条决定了数据治理的基本动作：要长期留的证据，尽早落 dataset 或导出。

    4. RBAC

    角色按 organization 与 workspace 两级：组织级管成员与账单，workspace 级管资源与可见性。最小权限的常见划法：

    • 开发：自己 workspace 的读写；
    • 评测 / 运营：只读 trace + 写 feedback / 标注队列；
    • 外包 / 外部：只给某个 workspace 的只读，不给组织级。

    四、原理拆解：为什么「先划 workspace 再谈角色」

    权限最终作用在资源上：trace、dataset、prompt、队列都属于某个 workspace。角色只是「能对资源做什么」。所以顺序是：

    1. 按团队 / 业务线划 workspace（谁的资源归谁）；
    2. 在每个 workspace 里定角色（谁能读、谁能写、谁能发布）；
    3. 组织级只留少数人（管成员、账单、审计）。

    反过来「先给人 admin 再说」的后果是：一次误删能跨 workspace 生效，且事后无法从审计日志里区分「谁在哪个 workspace 干的」。

    五、场景说明

    一家公司有 3 个业务线共用一套平台：客服 Agent（生产）、推荐 Agent（实验）、外包标注团队。

    • 划 3 个 workspace：support-prod、reco-lab、label-vendor；
    • 生产 workspace 只给研发 + 运营读写，外部标注只进队列页面；
    • 组织级 admin 只留 2 人；
    • 成本上：生产环境开在线评测按 10% 采样，实验环境不限但用 hard 子集控量。

    六、示例代码

    步骤 1：环境准备

    uv init ls13-governance
cd ls13-governance
uv add langsmith python-dotenv

    步骤 2：凭证配置

    .env：LANGSMITH_API_KEY、LANGSMITH_PROJECT=ticket-agent-prod。治理类操作要有对应角色权限，只读 key 也能跑下面的自查脚本。

    步骤 3：导入

    from langsmith import Client
from datetime import datetime, timedelta, timezone

    步骤 4：最小可运行代码

    存成 audit.py，uv run audit.py。这段脚本回答三个治理问题：题库多大、近七天进来多少 run、哪些 dataset 长期没动。

    import os
from datetime import datetime, timedelta, timezone
from dotenv import load_dotenv
from langsmith import Client

load_dotenv()
client = Client()
PROJ = os.getenv("LANGSMITH_PROJECT")

# 1) 题库体量：dataset 数与 example 数（example 永久保留，是长期成本）
total_ex = 0
for ds in client.list_datasets():
    n = len(list(client.list_examples(dataset_name=ds.name, limit=1000)))
    total_ex += n
    print(f"{ds.name:<24} examples={n}")
print("datasets examples total:", total_ex)

# 2) 近七天流量：trace 存储与保留期压力的输入
since = datetime.now(timezone.utc) - timedelta(days=7)
runs = list(client.list_runs(project_name=PROJ, start_time=since, is_root=True, limit=2000))
print("root runs last 7d:", len(runs), "(limit 2000, 超出说明量级需要采样)")

# 3) 长期没动的 dataset：可清理候选
print("stale candidates: 人工核对最后使用时间后再删，不要脚本直删")

    步骤 5：预期输出

    refund-faq               examples=4
refund-regression        examples=12
datasets examples total: 16
root runs last 7d: 1832 (limit 2000, 超出说明量级需要采样)
stale candidates: 人工核对最后使用时间后再删，不要脚本直删

    步骤 6：验证是否成功

    • 数字与 UI 的 Datasets / Runs 页一致（差一两条通常是分页边界）；
    • 把 start_time 改成 30 天前，run 数会明显变大——这就是保留期与成本的关系；
    • 在 UI 里切一个只有只读权限的 workspace 再跑：能读、不能建 dataset（写操作会 403）——验证 RBAC 生效。

    写法 A · 保留期到期的前兆

    写入被拒通常有两种：配额到顶、或该环境写入被停用。排查顺序是「先看配额、再看权限、最后看套餐」；脚本侧可以用 dry-run 写一条极小 run 验证（生产慎用）。

    写法 B · 按 workspace 划分权限的检查清单

    问题
    期望答案
    不满足的后果

    七、常见坑（官方明确限制/版本差异）

    1. 把 BYOC 当自建。以为「在我云上就是我运维」，其实升级节奏由平台方推动。
    2. 只算席位不算用量。在线评测全量跑，账单在第二条线上爆。
    3. 以为 dataset 也过期。example 永久保留——这既是资产也是长期成本。
    4. 给全员 admin。跨 workspace 误删，审计日志无法定位。
    5. 保留期到了才发现没导出。要留的证据，趁早 create_example_from_run 或导出。
    6. 配额到顶误判成 bug。表现是「trace 后半段没有」，先看配额。

    八、课后小结

    • 三形态的差别是「基础设施归谁、升级谁推动」；
    • 成本三条线：席位、用量、部署，分别管；
    • trace 会过期，example 不会；
    • RBAC 的顺序是「先 workspace、后角色、组织级留少数」；
    • 治理动作要写成规则，而不是靠「大家注意点」。

    九、思考题

    1、为什么治理要先划 workspace？

    参考回答：权限作用在资源上，资源归属决定权限边界；先划 workspace 才能把「谁看什么」落到具体对象上，角色才有意义。

    2、保留期与 dataset 的寿命差异，怎么影响你的日常操作？

    参考回答：任何「以后还要用」的证据必须转成 example 或导出；否则过期后只能靠记忆复现，评测基线也一起消失。

    3、BYOC 的隐藏成本在哪？

    参考回答：网络打通、镜像升级窗口、与平台方的联调；基础设施在你账号里，但变更节奏不完全由你定。

    4、给定一个 20 人的团队，你会怎么划 workspace？

    参考回答：按业务线划（生产 / 实验 / 外包），每线一个 owner；组织级 admin 不超过 2 人；外包只给队列与只读 trace。
