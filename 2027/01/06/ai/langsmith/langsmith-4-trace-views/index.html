    04 读一条 trace

    「慢」看 Turns，「错」看 Details，「答偏了」看 Messages｜依据官方 Manage traces 页自绘

    版本不一致提示

    • 本篇基线是 LangSmith 平台（2026-11 文档）+ langsmith 0.16.2 + Python 3.13；
    • 三个视图都在 Trace 详情页里切换，Turns 视图与甘特时间轴是 2026 年后的 UI 命名；
    • status 只有 ok / error / pending 三种，超时在 LangSmith 里通常表现为 error + 错误栈，不会自动变 timeout；
    • 错误栈只在 error 的 run 上可见；捕获异常但不 raise 会让 run 显示成功，排查时容易看错；
    • 本篇示例可在 LANGSMITH_TRACING=false 下跑通（终端输出可控，UI 部分需有 key）。

    一、学习目标

    学完这一讲，你要能做到三件事：

    1. 拿到一条报障 trace，按 Messages → Turns → Details 的顺序在三十秒内给出初步结论；
    2. 用代码造出「慢」和「错」两类坏样本，练习定位；
    3. 说清「状态成功但结果错」与「状态失败」的差别，以及为什么前者更难查。

    二、前置知识

    • 读完 03 三种埋点，能造出一棵多层 run 树；
    • 知道 run_type 会影响 UI 图标与统计。

    三、理论讲解（官方定义）

    1. Messages 视图：按消息读

    把 run 树里的输入输出投影成消息序列（human / ai / tool），适合回答「对话怎么被带偏的」。示例里那种「模型把 502 当成业务错误解释」的情况，只有在 Messages 里按顺序读才看得出来。

    2. Turns 视图：按时间读

    Turns 把一次交互切成「轮」，每轮给出起止时间与各 run 的耗时条，合计成总时长。它是定位慢的第一入口：先看哪一轮最长，再点进去看具体是 model 慢还是 tool 慢。

    3. Details 视图：按字段读

    Details 是单 run 的元数据面板：run_type、name、trace_id、latency、status、error、inputs / outputs。定位错就看这里：状态是否 error、错误栈第一行是什么、outputs 是不是空。

    4. 结论顺序

    官方文档没有规定顺序，但实操里最省时间的是：Messages 定性（答得对不对）→ Turns 定量（慢在哪一轮）→ Details 定点（是哪个 run、什么错）。

    四、原理拆解：三种视图各自读的是哪份数据

    • Messages：读 run 的 inputs / outputs 里的消息字段，按树序展开；
    • Turns：读每个 run 的 start_time 与 end_time，按「轮」聚合出区间；
    • Details：读 run 的元数据与 error 字段。

    三个视图共享同一份 run 记录，所以它们之间不会出现互相矛盾的数据；如果矛盾，多半是「你在看不同的 trace」。

    耗时统计的一个细节：并行分支（比如同时调两个工具）在 Turns 里是并列的两条条，总时长不是各条相加，而是区间并集。所以「三段加起来 2.30 s」这种算法只在串行时成立。

    五、场景说明

    报障原文：「用户问退款，Agent 说『系统 502，请稍后重试』，但用户看到的是『退款已提交』。」

    这是典型的状态成功、结果错：接口 502、代码捕获异常后返回了兜底文案，run 的 status 是 ok。只看 Details 永远查不出来，必须从 Messages 读。

    反过来，「慢」类报障，Messages 看不出问题，Turns 一眼就能看出是哪一轮拖长。

    六、示例代码

    步骤 1：环境准备

    uv init ls04-views
cd ls04-views
uv add langsmith python-dotenv

    步骤 2：凭证配置

    .env 同前：LANGSMITH_TRACING=true、LANGSMITH_API_KEY=...、LANGSMITH_PROJECT=ticket-agent-dev。

    步骤 3：导入

    import time
from langsmith import traceable

    步骤 4：最小可运行代码

    存成 views.py，uv run views.py。这段代码故意造三个样本：正常、慢、静默失败。

    import os, time
from dotenv import load_dotenv
from langsmith import traceable

load_dotenv()

@traceable(run_type="retriever")
def retrieve(q: str) -> str:
    time.sleep(0.05)
    return f"policy::{q}"

@traceable(run_type="llm")
def model(q: str, ctx: str) -> str:
    time.sleep(0.30)          # 慢样本：模型慢
    return f"回答：{q}（依据 {ctx}）"

@traceable(run_type="tool")
def submit_refund(order_id: str) -> dict:
    time.sleep(0.40)          # 慢样本：工具慢
    raise RuntimeError("HTTP 502 from refund-service")

@traceable
def turn(q: str, order_id: str) -> str:
    ctx = retrieve(q)
    try:
        submit_refund(order_id)
    except RuntimeError:
        # 静默失败：捕获后返回兜底文案，run 状态仍是 ok
        return "退款已提交，请稍后查看"
    return model(q, ctx)

@traceable
def turn_strict(q: str, order_id: str) -> str:
    ctx = retrieve(q)
    submit_refund(order_id)   # 不捕获：run 直接 error
    return model(q, ctx)

if __name__ == "__main__":
    print(turn("退款怎么走？", "SO-1001"))
    try:
        print(turn_strict("退款怎么走？", "SO-1002"))
    except RuntimeError as e:
        print("expected:", e)

    步骤 5：预期输出

    退款已提交，请稍后查看
expected: HTTP 502 from refund-service

    步骤 6：验证是否成功

    打开 ticket-agent-dev，对比两条 trace：

    • 第一条 turn：Messages 里没有「退款已提交」的来源解释，submit_refund 这个 run 的 status = error，但它的父 turn 是 ok；
    • 第二条 turn_strict：根 run 就是 status = error，Details 里 error 第一行是 HTTP 502 from refund-service；
    • Turns 视图里，第一条 submit_refund 的条是 0.40 s，model 是 0.30 s，总时长约 0.75 s（含 retrieve），串行相加成立；
    • 把 turn 里的 try/except 删掉，它就变成和第二条一样的红灯——这就是「捕获异常让状态失真」的直观演示。

    写法 A · 用 JSON 预览定位字段

    Details 的 inputs / outputs 默认折叠，官方支持切换成 JSON 视图。查「字段名写错」「值类型不对」这类问题，直接看 JSON 比看格式化面板快，因为空字符串、null、0 在那里面长得完全不一样。

    七、常见坑（官方明确限制/版本差异）

    1. 捕获异常却当作成功。run 状态 ok，错误只留在文本里；要么 raise，要么显式记 metadata。
    2. 以为 Turns 是「一条 run 一行」。它按轮聚合，并行分支是并列条。
    3. 拿单条 run 的 latency 相加当总时长。并行时高估。
    4. 只看 Details 不看 Messages。答偏、语气不一致、承诺冲突，这类问题只在 Messages 里显形。
    5. 错误栈被截断。Details 里错误栈是首段，深层原因可能在最后一个 Caused by；必要时看完整 outputs / 日志。

    八、课后小结

    • 三视图读同一份数据：Messages 定性、Turns 定量、Details 定点；
    • 静默失败（捕获异常）是最难查的一类，状态 ok 不代表结果对；
    • 并行分支的总时长是区间并集，不是相加；
    • 状态只有 ok / error / pending，超时也落成 error。

    九、思考题

    1、为什么「状态成功但结果错」比「状态失败」更难查？

    参考回答：失败有错误栈指向具体 run，成功没有任何信号；只能靠 Messages 比对「用户问的」与「模型答的」，或者靠评测器给出分数。

    2、Turns 里一轮很长，下一步该点哪里？

    参考回答：点这一轮展开子 run 的耗时条，先看是 llm 还是 tool；再看该 run 的 Details 里 latency 与实际请求参数，判断是模型慢还是外部服务慢。

    3、并行工具调用时，怎么估真实总耗时？

    参考回答：取最早开始与最晚结束的区间长度，而不是各 run 相加；如有串行段，再分段算。

    4、为什么错误栈要看最后一个 Caused by？

    参考回答：外层异常往往只是包装（如「提交失败」），真正的 502 / 权限 / 超时在深层；只看首行容易误判成业务逻辑问题。
